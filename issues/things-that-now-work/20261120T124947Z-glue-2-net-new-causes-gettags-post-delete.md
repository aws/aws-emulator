# glue: 2 net-new causes — GetTags' post-delete EntityNotFoundException is the generic 'Entity not found' instead of AWS's per-resource-type message, and StartColumnStatisticsTaskRunSchedule reports a missing settings entity as a missing table

> _Note: this issue was identified against the code base at commit `62927d8978ca4f69375a7d40d1cf62e1849504fb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTags

## Description
Two distinct net-new root causes in the Glue refusal-message surface of service-com-amazonaws-glue-awsglue. All three failing checks below are listed under service heading 'glue' with NO 'OWNED by' owner and NO 'ALREADY FILED' marker. TWO causes must be closed before this issue is submitted.

Cause 1 of 2: GetTags on the ARN of a resource that has been DELETED is refused with the correct code but a single generic message, 'Entity not found', instead of the resource-type-specific sentence real Glue returns. Failing checks: glue.get-tags-after-delete-database-and-registry-not-found, glue.crawler-tags-round-trip-then-not-found-after-delete.
AWS: Smithy: GetTags input {ResourceArn @required GlueResourceArn @length 1..10240, pattern ^arn:aws(-(cn|us-gov|iso(-[bef])?))?:glue:}; output {Tags: TagsMap @length 0..50}; errors EntityNotFoundException (client, HTTP 400), InvalidInputException, OperationTimeoutException, InternalServiceException. The message template is recorded behavior only (the model states the shape and status, not the text): the refusal names the resource the ARN addresses, and the wording is per resource TYPE — for a deleted database the fixed text is 'Database ' ... ' not found.' with the database name taken from the ARN in the request; for a deleted registry it is the fixed text 'Registry is not found. RegistryName: null, RegistryArn: ' followed by the registry ARN from the request (the literal 'null' is fixed text — the request carried an ARN, not a name); for a deleted crawler it is the fixed text 'Crawler entry with name ' ... ' does not exist' with the crawler name from the ARN. In every case the code is EntityNotFoundException at HTTP 400, and a SIBLING resource of the same kind that was not deleted still answers HTTP 200 with its exact tag map.
Emulator: all three answer 400 EntityNotFoundException with the message 'Entity not found' — one emulator-authored constant with no fixed/variable structure at all, naming neither the resource type nor the resource. Replay details: glue.get-tags-after-delete-database-and-registry-not-found asserts the database leg and fails with 'AssertionError: Entity not found' where 'Database <db> not found.' was required (the registry leg is reached only once the database leg passes); glue.crawler-tags-round-trip-then-not-found-after-delete fails with "expected ('EntityNotFoundException', 'Crawler entry with name <crawler> does not exist'), got ('EntityNotFoundException', 'Entity not found')". The names in those details are this run's generated resource names filling the template and are not part of the requirement.
Why: the message is the only part of this refusal that says WHICH resource is gone. A client reconciling tags across many ARNs (cost allocation, tag-driven inventory, a teardown that tolerates already-deleted resources) cannot attribute the failure to one ARN, and any handling or log-scraping keyed on Glue's sentence — in particular telling a deleted database apart from a deleted registry or crawler — never matches.
Fix: the not-found branch of the GetTags handler in the glue crate (and the shared resource-ARN resolution it calls): after parsing the ARN's resource type, raise EntityNotFoundException with that type's message template instead of a single shared constant. Note the OPEN issue 20261117T183344Z-glue-catalog-surface-7-net-new-causes-gettags.md: its Cause 1 covered GetTags refusing live database/registry ARNs with an empty-message InvalidInputException. That part no longer reproduces (the ARNs now resolve and the post-delete code is now EntityNotFoundException); what remains, and what this cause is, is the message text of the post-delete refusal, and it is not owned by that issue in this replay. 20261102T114851Z-glue-8-net-new-root-causes-refusal-messages.md also describes emulator-authored Glue refusal text but does not carry these checks or this branch.
Traces: glue.get-tags-after-delete-database-and-registry-not-found, glue.crawler-tags-round-trip-then-not-found-after-delete.

Cause 2 of 2: StartColumnStatisticsTaskRunSchedule on a (database, table) pair that has NO stored ColumnStatisticsTaskSettings reports the missing TABLE instead of the missing SETTINGS entity. Failing check: glue.column-statistics-task-settings-schedule-enable-disable.
AWS: Smithy: StartColumnStatisticsTaskRunSchedule input {DatabaseName @required NameString, TableName @required NameString, CatalogID CatalogIdString}; output {} (empty); errors AccessDeniedException, EntityNotFoundException (client, HTTP 400), InvalidInputException, OperationTimeoutException. StopColumnStatisticsTaskRunSchedule has the same input and models the same EntityNotFoundException. The message template is recorded behavior only: when no settings record exists for the (catalog, database, table) triple the refusal names the SETTINGS entity by its composite key — fixed text 'ColumnStatisticsTaskSettings ' and ' not found.', with the variable part '<catalogId>:<accountId>:<DatabaseName>-<TableName>' built from the request and the caller's account (for the default catalog both id components are the caller's account id). This is the message both for a table that was never created and for a settings record that was deleted after existing; the entity that is absent is the settings record, not the table. The companion read, GetColumnStatisticsTaskSettings on deleted settings, is refused with the fixed sentence 'ColumnStatisticsTaskSettings entry for input DatabaseName and TableName does not exist' (no variable part).
Emulator: the code is right (400 EntityNotFoundException) but the message is 'Table <TableName> not found.' — fixed text 'Table ' / ' not found.' with only the requested table name interpolated; the database name and the account-qualified settings key never appear. Replay detail: "AssertionError: unexpected message: 'Table sim2real_behav_cst2_other_<id> not found.'" (the table name there is this run's generated value filling the emulator's template). Because the check stops at this assertion, the two later assertions on the same wording — the post-delete GetColumnStatisticsTaskSettings sentence and the post-delete Start message — are not yet observed and must be made to hold too.
Why: a client reads this message to choose a recovery branch — 'this table has no column-statistics schedule yet, call CreateColumnStatisticsTaskSettings' versus 'this table is not in the catalog, a bootstrap/catalog error'. The emulator's wording sends it down the wrong branch, and tooling that parses the composite settings identifier out of AWS's message gets nothing.
Fix: the error-construction path of the StartColumnStatisticsTaskRunSchedule and StopColumnStatisticsTaskRunSchedule handlers and the shared column-statistics-settings lookup they use — look up and report the settings entity, not the table. The OPEN issue 20261120T030206Z-glue-iam-s3-glue-startcolumnstatisticstaskrunschedule-stopcolumnstatisticstaskrunschedule-report-a-missing-schedule-as.md describes this same wording defect but carries only the glue__iam__s3 check glue__iam__s3.column-statistics-task-run-schedule-unknown-table-rejected; the 'glue'-headed check named here is unowned in this replay, so it is filed with it named. The fixed issue 20261117T135333Z-glue-startcolumnstatisticstaskrunschedule-stub.md stood the operation up — the call is no longer a stub and the refusal AWS also makes is now produced, so this is a message divergence, not a re-refusal of a call AWS accepts.
Traces: glue.column-statistics-task-settings-schedule-enable-disable.
