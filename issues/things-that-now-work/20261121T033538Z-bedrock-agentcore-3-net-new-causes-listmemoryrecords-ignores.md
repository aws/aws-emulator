# bedrock-agentcore: 3 net-new causes — ListMemoryRecords ignores the bedrock-agentcore:namespace condition key, the CFN AWS::BedrockAgentCore::Runtime handler rejects a string ProtocolConfiguration, and CreateEvent long-term extraction never converges

> _Note: this issue was identified against the code base at commit `ddedefe2ba7626fc434a3b439556791987e3d078`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListMemoryRecords

## Description
Three independent root causes found in this sweep, all on the bedrock-agentcore surface. Each is numbered below with its own failing check ids; all three must be closed before this work item is submitted.

=== Cause 1 of 3: ListMemoryRecords authorizes on action+resource only and ignores the bedrock-agentcore:namespace condition key ===
AWS: Smithy models ListMemoryRecords as POST /memories/{memoryId}/memoryRecords with an optional `namespace` member (Namespace, @length 1..1024) and models AccessDeniedException (httpError 403) among its errors (source: smithy_query query="operation" operation="ListMemoryRecords" on com-amazonaws-bedrockagentcore-amazonbedrockagentcore.json). Recorded behavior: a principal whose only Allow for bedrock-agentcore:ListMemoryRecords on the memory's ARN is conditioned on StringEquals of the service condition key `bedrock-agentcore:namespace` to one namespace may list THAT namespace, and the same call naming a sibling namespace of the same memory is refused 403 AccessDeniedException. The refusal message's fixed text is `User: <caller principal ARN> is not authorized to perform this operation` — the principal ARN is the value taken from the request's signing identity (for an assumed role, arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>); nothing else in the sentence varies. Broadening the same condition to StringLike on the parent prefix makes the identical call succeed, and narrowing it again re-denies, so the authorization decision is a function of the request's `namespace` argument, not only of action and resource.
Emulator: the sibling-namespace call returns HTTP 200 with the sibling's records (memoryRecordSummaries carrying the other namespace's record, e.g. a record whose `namespaces` is exactly the namespace the policy does NOT allow). No condition-key evaluation happens: the authorizer grants on action+resource alone, so the scoped grant is a blanket grant over every namespace of the memory.
Why: namespace scoping is how AgentCore memories are multi-tenanted. A client that relies on a StringEquals/StringLike condition on bedrock-agentcore:namespace to keep one actor/session's derived facts away from another gets cross-tenant reads that succeed, and tests that prove isolation pass against the emulator and fail in production — the most dangerous direction for an authorization divergence.
Fix: the data-plane authorization path for the memory-record read operations (ListMemoryRecords, and the same condition key on RetrieveMemoryRecords/GetMemoryRecord) must extract the request's namespace argument into the request context the IAM policy evaluator sees as `bedrock-agentcore:namespace`, and the policy evaluator must apply StringEquals/StringLike conditions on it, refusing with 403 AccessDeniedException and the message above when no Allow matches.
Traces: bedrock-agentcore.namespace-condition-key-blocks-cross-namespace-memory-read (the check's positive control — the allowed namespace — passes, and an unrestricted principal sees the sibling record, so the sibling read really is data that must have been hidden).

=== Cause 2 of 3: the CloudFormation AWS::BedrockAgentCore::Runtime handler rejects a string ProtocolConfiguration ("expected object start, got string"), rolling the stack back ===
AWS: Recorded behavior only for the CloudFormation resource schema: a template whose AWS::BedrockAgentCore::Runtime Properties carry `ProtocolConfiguration: "HTTP"` (a plain string) alongside AgentRuntimeName, RoleArn, AgentRuntimeArtifact.CodeConfiguration (Code.S3 {Bucket, Prefix}, EntryPoint ["main.py"], Runtime "PYTHON_3_13") and NetworkConfiguration {NetworkMode: "PUBLIC"} is ACCEPTED and the stack reaches CREATE_COMPLETE, exporting Fn::GetAtt Runtime.AgentRuntimeArn. The underlying API shape is a STRUCTURE, not a string: CreateAgentRuntime.protocolConfiguration targets ProtocolConfiguration { serverProtocol: ServerProtocol (required, enum MCP|HTTP|A2A|AGUI) } (source: smithy_query query="shape" shape="ProtocolConfiguration,ServerProtocol" on com-amazonaws-bedrockagentcorecontrol-amazonbedrockagentcorecontrol.json). So the CFN property value is the enum string and the resource handler is what must lift it into {"serverProtocol": <value>} before calling the control plane; a template-level failure here is not a modeled AWS outcome at all.
Emulator: the create fails and the stack ends in ROLLBACK_COMPLETE with the resource-status reason `Runtime (AWS::BedrockAgentCore::Runtime): Resource handler returned message: "expected object start, got string" (HandlerErrorCode: InvalidRequest)`. The quoted text is a JSON-deserializer error: the handler feeds the template property value straight into the structure deserializer for ProtocolConfiguration. (The request token and the physical/stack names in the reason are per-run values, not part of the requirement.) Because the stack rolls back, nothing downstream of the deploy is reachable.
Why: infrastructure-as-code is the normal way an AgentCore runtime is created. A client whose template is accepted by AWS gets a failed stack and a rollback from the emulator, and CFN-based deployment of AgentCore runtimes is unusable.
Fix: the CloudFormation resource handler / property mapping for AWS::BedrockAgentCore::Runtime — translate the scalar CFN properties into the control-plane request shapes (ProtocolConfiguration string -> {serverProtocol: <enum>}; likewise check NetworkConfiguration/AgentRuntimeArtifact nesting) instead of deserializing the template value directly as the API structure.
Related but NOT covering this: open issue 20261029T221713Z-bedrock-agentcore-cloudformation-deployed-runtime-is-never-invokable-end-to-end.md carries the same check id but a different failure mode (it was grounded in the 501 NotImplemented InvokeAgentRuntime timeout, with the stack reaching CREATE_COMPLETE); open issue 20261109T123922Z-bedrock-agentcore-control-cloudformation-no-aws-bedrockagentcore-resource.md is about the resource type not being registered at all. The type is now registered and the stack now rolls back at create time on this deserialization error, which is a new, earlier defect.
Traces: bedrock-agentcore.deploy-agent-runtime-invokable-via-cfn.

=== Cause 3 of 3: long-term memory extraction from CreateEvent never converges, so extractionMode=SKIP cannot be distinguished and the check is killed on the clock ===
AWS: Smithy models CreateEvent as POST /memories/{memoryId}/events (201) with an optional `extractionMode` member whose enum has exactly one value, SKIP (source: smithy_query query="shape" shape="ExtractionMode"). Recorded behavior: a conversational event written to a memory that has a semanticMemoryStrategy whose namespace template resolves to /…/{actorId}/{sessionId}/ and NO extractionMode converges, asynchronously, into a derived memory record listable by ListMemoryRecords under that resolved namespace; each derived MemoryRecordSummary carries a non-empty required memoryStrategyId and content that reflects the ingested text, and the record is readable by GetMemoryRecord with the resolved namespace in its `namespaces`. An event written with extractionMode=SKIP stays readable short-term through ListEvents(includePayloads=True) but never produces a derived record in that namespace.
Emulator: no derived record ever appears. The check's first observable — a bounded poll of ListMemoryRecords for the namespace of the event written WITHOUT extractionMode — never satisfies, and the check is killed at the harness wall clock (`Error: Check timed out after 60.0s`) with no refusal text, so every later beat (the SKIP namespace staying empty, RetrieveMemoryRecords, the repair event, the terminal GetMemoryRecord) is unreachable. Hypothesis: the automatic extraction pipeline behind CreateEvent is not implemented at all — consistent with StartMemoryExtractionJob still being an unimplemented scaffold stub (open issue 20261112T062114Z-bedrock-agentcore-startmemoryextractionjob-stub.md, which covers only that operation's stub and asserts nothing about CreateEvent-driven extraction).
Why: derived long-term memory is the whole point of an AgentCore memory with a strategy. A client that writes events and then reads its strategy namespace gets an permanently empty namespace, and the one knob AWS exposes over that pipeline (extractionMode=SKIP) is unobservable: the emulator looks identical whether the flag is set or not, so code that depends on SKIP withholding a record is never exercised.
Fix: the memory data-plane state/extraction path behind CreateEvent — events ingested into a memory whose strategy namespaces resolve for the event's actorId/sessionId must produce derived memory records in that resolved namespace (with memoryStrategyId populated and content derived from the event payload) and must skip exactly the events carrying extractionMode=SKIP, while keeping those events readable through ListEvents.
Traces: bedrock-agentcore.create-event-extraction-mode-skip-withholds-the-long-term-record. Note for the fixer: this check's own hold window and convergence polls need more wall clock than the 60s replay budget, so confirm the fix by driving the same sequence directly (CreateEvent without extractionMode -> ListMemoryRecords on the resolved namespace) as well as by re-replaying the check.
