## Description

That issue's Cause 2 (DeleteDomain on a never-allocated domainId) and Cause 5 (the three patient-insights checks blocked in their FHIR seeding chain) were closed, but DeleteDomain is still refused with an error body that diverges from AWS, and the patient-insights checks now reach — or hang just short of — the operation under test and still diverge. === Cause 1 of 4: StartPatientInsightsJob refuses a well-formed but nonexistent domainId with the wrong error class, status and message ===
AWS: Smithy (com-amazonaws-connecthealth-connecthealth) StartPatientInsightsJob POST /domain/{domainId}/patient-insights-job (hostPrefix runtime.) models both AccessDeniedException (httpError 401) and ResourceNotFoundException (httpError 404); domainId is an httpLabel of DomainId, length 20-25, pattern ^(hai-|dom-)[a-z0-9]+$. Recorded behavior (confirmed twice independently against real AWS, per the check's own note): a domainId that satisfies that pattern but names no existing Domain is refused with HTTP 401, error code AccessDeniedException and message "Domain is not valid." — the whole message is FIXED text with NO variable part; in particular it deliberately does NOT echo the requested domainId, because the front door authorizes the resource ARN before confirming or denying the resource's existence (the same anti-enumeration pattern IAM resource-ARN authorization uses). ResourceNotFoundException remains the right refusal for sub-resources inside a domain the caller does own (see Cause 4's GetPatientInsightsJob contract).
Emulator: answers error code ResourceNotFoundException (httpError 404 per the model) with message "Domain not found: <domainId>" — fixed text "Domain not found: " plus the domainId taken verbatim from the request (observed: 'Domain not found: dom-33333333333333333333').
Why: a client cannot distinguish "not authorized / not a valid domain for you" from "this job or resource is gone". Callers that treat 404 as a benign, retry-after-create condition will loop creating state, and callers that must escalate a 401 authorization fault to an operator never see it. The emulator also leaks existence information AWS withholds: against the emulator, probing domainIds tells an unauthorized caller which ids exist, so tenancy/enumeration tests written against the emulator pass and fail on real AWS.
Fix: StartPatientInsightsJob's handler, in its domainId resolution/authorization step (before job validation): when the domainId resolves to no Domain owned by the caller, refuse with HTTP 401, code AccessDeniedException and the fixed message "Domain is not valid.", instead of routing it into the shared Domain-not-found constructor.

=== Cause 2 of 4: the AuthorizerConfigurationException DeleteDomain returns for a never-allocated domainId carries an empty-string message where AWS carries an explicit null ===
AWS: recorded behavior only (AuthorizerConfigurationException is not in DeleteDomain's modeled error set — Smithy declares only ResourceNotFoundException, httpError 404, for DELETE /domain/{domainId}). A well-formed domainId (pattern ^(hai-|dom-)[a-z0-9]+$, length 20-25) that was never allocated to any account is refused with error code AuthorizerConfigurationException and NO message content at all: the error body's message member is an explicit JSON null, which botocore surfaces as Error.Message is None. There is no fixed text and no variable part — the requirement is the absence of a message value, not a particular string.
Emulator: the error code is now right, but the message is surfaced as the empty string '' (either the member is omitted from the body, or it is serialized as ""), so botocore reports Error.Message == '' instead of None. AssertionError: expected AuthorizerConfigurationException with a null message, got ''.
Why: a client branching on the presence of a message (log/alert enrichment, support tooling, or any `if msg is None:` path that distinguishes an authorizer/config fault with no diagnosis from a service error that carries one) takes the wrong branch, and the previous fix for this operation reads as complete while the body still differs from AWS on the wire.
Fix: the connecthealth error serializer for this refusal (the shared error-body builder used by DeleteDomain's id-resolution path), so this error class emits message: null rather than an omitted member or "".
Traces: connecthealth.delete-domain-not-found

=== Cause 3 of 4: a Domain tagged through connecthealth TagResource is never discoverable through ResourceGroupsTaggingAPI GetResources ===
AWS: recorded behavior only. Smithy: connecthealth TagResource POST /tags/{resourceArn} (code 204, @idempotent, tags required) tags a Domain whose ARN matches ^arn:aws:health-agent:[a-z0-9-]+:[0-9]{12}:domain/(hai-|dom-)[a-z0-9]+$. A tag written that way is indexed account-wide and the Domain is returned by the Resource Groups Tagging API's GetResources when filtered by TagFilters=[{Key, Values:[...]}] and ResourceTypeFilters=["health-agent"], as a ResourceTagMappingList entry whose ResourceARN is that Domain ARN and whose Tags carry the key/value just written. Removing the tag with connecthealth UntagResource removes the Domain from that index again.
Emulator: connecthealth's own view is correct (ListTagsForResource returns exactly the just-written tag — that assertion passed), but the Domain never appears in GetResources: the check polled GetResources every 3s and was still polling when the harness cut it off at 60s, so the cross-service index never produced the ARN. The tag is visible only through the owning service.
Why: tag-driven discovery and governance is cross-service by design — inventory, cost allocation, backup selection and policy sweeps all read tags through ResourceGroupsTaggingAPI, not through each service's own ListTagsForResource. Against the emulator every such sweep returns nothing for health-agent Domains, so a client that builds its resource set from GetResources silently operates on an empty set and its tests pass. The removal half of the contract (the Domain must disappear from the index after UntagResource) is also unverifiable while the appearance half never happens.
Fix: whichever component owns cross-service tag indexing — connecthealth's tag store must register the Domain and its tags with the shared tag index that resourcegroupstaggingapi's GetResources reads, with resource type "health-agent", on CreateDomain/TagResource, and deregister the key on UntagResource. Both connecthealth and resourcegroupstaggingapi are bootstrapped, so this is a wiring gap between them, not a missing service.
Traces: connecthealth.domain-tags-visible-via-resourcegroupstaggingapi

=== Cause 4 of 4: the HealthLake FHIR search interaction never returns a Patient that was just written and is readable by id, so two patient-insights contracts can never be reached ===
AWS: recorded behavior only (FHIR REST data plane of the HealthLake datastore a connecthealth Domain is wired to). After PUT [base]/Patient/{id} succeeds (200/201) and GET [base]/Patient/{id} returns 200, a search GET [base]/Patient?identifier={value} returns HTTP 200 with a searchset Bundle containing at least one entry for that resource (indexing may lag briefly, but it converges). StartPatientInsightsJob resolves patientContext.patientId against that datastore, which is why the checks seed and then confirm searchability before calling it.
Emulator: the by-id PUT and GET now work (the Cause 1 check got past them and started a real job), but the two checks that additionally poll the search interaction never finish: both were cut off by the harness at 60.0s. The search poll (10s interval, breaking only on HTTP 200 with entry count >= 1) is the only unbounded wait those two checks contain and the third, now-progressing check does not. Hypothesis: GET [base]/{type}?<params> is still unrouted or answers a non-200 / an empty Bundle — the endpoint's own diagnostics quoted in the reopened issue said it implements only create (POST [base]/{type}) and read (GET [base]/{type}/{id}).
Why: no caller can confirm a seeded resource is indexed, which is the normal readiness gate before any workload that resolves patients by identifier; the hang also keeps two connecthealth contracts permanently unverified: (a) GetPatientInsightsJob on a never-created jobId must answer code ResourceNotFoundException with message "Job <jobArn> does not exist." — fixed text "Job " ... " does not exist." around the job ARN built from region, account, the requested domainId and jobId — while the real job in the same domain stays readable; and (b) StartPatientInsightsJob with outputDataConfig.s3OutputPath that is not an s3:// URI must answer ValidationException (httpError 400) with the fixed message "Request validation failed" and must persist NO job under that clientToken, so an identical retry re-fails validation instead of idempotently returning a job.
Fix: the HealthLake FHIR data-plane router/handler that serves the datastore endpoint (services/service-com-amazonaws-healthlake-healthlake/src, the same FHIR REST surface whose PUT route was added for the reopened issue): implement the type-level search interaction GET [base]/{type}?<param>=<value> (at minimum identifier) returning 200 and a searchset Bundle whose entries include resources written by id. NOTE: these failures are reported under connecthealth check ids because that is the suite's service attribution; the defective component is the HealthLake FHIR endpoint, which is itself bootstrapped.
Traces: connecthealth.get-patient-insights-job-not-found, connecthealth.start-patient-insights-job-malformed-s3-uri-rejected
