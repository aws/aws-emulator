# GetCSVHeader returns the pool's columns in the emulator's own schema order instead of the CSV column order AWS serves

> _Note: this issue was identified against the code base at commit `4a8024be86a6dad049d0fd9bbb9addeb9359d2ed`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCSVHeader

## Description
Two net-new wire divergence clusters in the cognito-idp surface from the simparity-wire-aws-v1 replay, both on GetCSVHeader and both expressing ONE root cause: the emulator derives the CSVHeader column order from its own stored schema order instead of emitting the column order Amazon Cognito serves. Neither cluster carries a stub_path and both have an empty owned_by in the replay report. These are the ONLY two unowned clusters in the whole run (the other 90 are owned by open issues).

Related issues named so a fixer does not conflate them: 20261030T200458Z-cognito-idp-createuserpool-refuses-a-valid-pool-configuration.md is RESOLVED and therefore covers nothing here — its Cause 2 (the missing trailing password_hash column) has landed, which is exactly why the trailing columns cognito:mfa_enabled / cognito:username / password_hash (indices 20, 21, 22) now MATCH in both recordings, while its Cause 3 hypothesis about ordering did NOT fix the order and is refuted by the evidence below. 20261024T114943Z-cognito-idp-getcsvheader-stub.md (open) is the scaffold-stub issue for the operation existing at all, not for the order of the list it returns. 20261030T174613Z-cognito-idp-the-user-import-plane-diverges-a.md (open) is a behavioral-corpus issue about the import plane and carries no wire replay key for column order.

=== Cause 1 of 2: for a pool created with an explicit Schema, every standard column is in the wrong position (fixture cognito-idp-csv-header-schema-matches-pool-custom-attributes, step task#3) ===
AWS: Smithy models GetCSVHeader's output as UserPoolId plus CSVHeader (target ListOfStringTypes, a plain list of strings) and documents it only as "A comma-separated list of attributes from your user pool. Save this output to a .csv file and populate it with the attributes of the users that you want to import" (Smithy: GetCSVHeader, member GetCSVHeaderResponse.CSVHeader; modeled errors InvalidParameterException/OperationNotEnabledException 400, NotAuthorizedException 403, ResourceNotFoundException 404, TooManyRequestsException 429, InternalErrorException 500). The model states no ordering, so: recorded behavior only. The recording answers HTTP 200 and the column order it carries is: profile, address, birthdate, gender, preferred_username, updated_at, website, picture, email_verified, phone_number_verified, phone_number, zoneinfo, custom:<the pool's custom attribute>, locale, email, given_name, family_name, middle_name, name, nickname, then cognito:mfa_enabled, cognito:username, password_hash. The pool's single custom attribute sits in the MIDDLE of the standard columns (index 12 of 23), not appended after them.
Emulator: status is 200 and the column SET is correct, but 19 of the 20 attribute positions are wrong. It serves name, given_name, family_name, middle_name, nickname, preferred_username, profile, picture, website, email, email_verified, gender, birthdate, zoneinfo, locale, phone_number, phone_number_verified, address, updated_at, custom:<name> — i.e. its own fixed standard-attribute table with the custom attribute appended last. Only index 7 ('picture') and the three trailing import columns land where AWS put them (replay detail, verbatim: "$.CSVHeader[0]: value_mismatch (expected 'profile', got 'name')" ... "$.CSVHeader[12]: value_mismatch (expected 'custom:MyOddlyCasedFieldXyz', got 'birthdate')" ... "$.CSVHeader[19]: value_mismatch (expected 'nickname', got 'custom:MyOddlyCasedFieldXyz')"). The custom attribute NAME in that detail ('MyOddlyCasedFieldXyz') is a value from the request and is not part of the requirement; the requirement is that the custom column occupy the position AWS gives it and that each standard column occupy its recorded position.
Why: the header row is the contract between the service and the CSV a client uploads to a user-import job. A client that calls GetCSVHeader, writes its rows in the order the service just handed it, and then uploads that file to CreateUserImportJob/StartUserImportJob writes every value into a different column against AWS than against the emulator — emails land in the gender column, the custom attribute's value lands in nickname, and the import silently populates the wrong attributes. Any code that maps column index to attribute name is likewise wrong, and tests that pin the header row pass against the emulator and fail against AWS.
Fix: the CSV-header rendering, i.e. UserPool::csv_header() and the stored-schema ordering it reads (crate::state::effective_schema, which CreateUserPool assigns to pool.schema). csv_header() currently projects pool.schema in its stored order and the stored order is the emulator's fixed STANDARD_SCHEMA table with requested/custom attributes merged around it, so the fix belongs either in a dedicated header-order table used by GetCSVHeader or in the schema-storage order itself — and whichever is chosen must keep DescribeUserPool's SchemaAttributes and this header mutually consistent.

Code sites consulted: services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/ops/get_csv_header.rs lines 175-181 (handle() returns pool.csv_header() unchanged); src/state.rs lines 3109-3120 (UserPool::csv_header projects self.schema in stored order and chains CSV_HEADER_TRAILING_COLUMNS); src/state.rs lines 6290-6311 (const STANDARD_SCHEMA, the fixed 20-entry table whose order the served header follows); src/state.rs lines 6327-6331 (CSV_HEADER_TRAILING_COLUMNS = cognito:mfa_enabled, cognito:username, password_hash — these three are correct and must stay last); src/ops/create_user_pool.rs line 328 (pool.schema = crate::state::effective_schema(input.schema)).

=== Cause 2 of 2: the same wrong order is served for a pool whose custom attribute is added on its own, proving the order is not derived from the request's Schema order (fixture cognito-idp-get-csv-header-matches-user-pool-schema, step task#2) ===
AWS: same modeled surface as Cause 1 (Smithy: GetCSVHeader -> CSVHeader: ListOfStringTypes, no ordering trait or documentation), so recorded behavior only. This second recording — a DIFFERENT pool, with a differently named custom attribute — answers HTTP 200 with the IDENTICAL column order as Cause 1, custom attribute again at index 12: profile, address, birthdate, gender, preferred_username, updated_at, website, picture, email_verified, phone_number_verified, phone_number, zoneinfo, custom:<name>, locale, email, given_name, family_name, middle_name, name, nickname, cognito:mfa_enabled, cognito:username, password_hash.
Emulator: status 200 and, for this pool, it serves custom:<name> FIRST and then its fixed standard table — custom:<the pool's custom attribute>, name, given_name, family_name, middle_name, nickname, preferred_username, profile, picture, website, email, email_verified, gender, birthdate, zoneinfo, locale, phone_number, phone_number_verified, address, updated_at — so ALL 20 attribute positions mismatch here, including index 7 (replay detail, verbatim: "$.CSVHeader[0]: value_mismatch (expected 'profile', got 'custom:favoritecolor')" ... "$.CSVHeader[12]: value_mismatch (expected 'custom:favoritecolor', got 'gender')" ... "$.CSVHeader[19]: value_mismatch (expected 'nickname', got 'updated_at')"). The custom attribute name ('favoritecolor') is again a request value, not part of the requirement.
Why: beyond the same wrong-column import breakage as Cause 1, this cluster is the diagnostic that must be honoured by the fix. Because the emulator puts the custom column in a DIFFERENT place for these two pools (last for Cause 1, first for Cause 2) while AWS puts it at the SAME index 12 for both, AWS's order is demonstrably NOT the order the CreateUserPool request listed its Schema in and NOT a function of the custom attribute's name. The previously resolved issue's hypothesis ("derive the header from the pool's stored schema order") is therefore wrong: implementing that is what produces the two different emulator orders seen here. A fixer that re-applies it will close this issue without the replay passing.
Fix: same component as Cause 1 — GetCSVHeader's header derivation must emit Amazon Cognito's own import-template column order (the recorded order above: a fixed standard-attribute sequence with the pool's custom attributes at the position AWS places them, then cognito:mfa_enabled, cognito:username, password_hash) rather than any projection of the stored schema order, for every pool regardless of how its Schema was submitted.
Traces: cognito-idp-get-csv-header-matches-user-pool-schema#task#2 (GetCSVHeader, 200 -> 200, affected_count 1, divergence_key service=cognito-idp|GetCSVHeader|status=200->200|keys=$.CSVHeader[0..19]). Same code sites as Cause 1.
