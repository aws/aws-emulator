# ecr__eks__logs: 3 net-new root causes — asynchronous EKS effects never settle: no /aws/eks/<cluster>/cluster log group after enabling 'api' logging, no Container Insights performance delivery, and a pod's private-ECR image pull never reports an outcome

> _Note: this issue was identified against the code base at commit `4589a545c981676c72550ecd598553d4d546f08e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateClusterConfig

## Description
Three distinct asynchronous EKS effects the emulator is responsible for producing are never produced. Each of the five failing checks below polls for one of them with a multi-minute budget and is cut off by the suite's per-check budget with 'Error: Check timed out after 60.0s' — the awaited effect had not appeared at any point the check observed it. Three net-new causes, numbered; each carries its own failing check ids.

SCOPE NOTE: these surface as timeouts, so the graded window is bounded by the suite budget rather than by an emulator error response. They are filed because the emulator serves the asynchronous state machine these checks poll and nothing it served ever advanced. A fixer should re-replay exactly the check ids in trace_ids.

Cause 1 of 3: a cluster created with no Logging block correctly has no control-plane log group, but enabling log type 'api' with UpdateClusterConfig on that same CloudFormation-provisioned cluster never creates /aws/eks/<cluster>/cluster and never produces a kube-apiserver-* log stream.
AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend): UpdateClusterConfig POST /clusters/{name}/update-config -> {update: Update}; input member logging targets Logging{clusterLogging: list<LogSetup>}; LogSetup{types: list<LogType>, enabled: boolean} with LogType enum values api, audit, authenticator, controllerManager, scheduler; LogSetup.enabled is documented 'If a log type is enabled, that log type exports its control plane logs to CloudWatch Logs. If a log type isn't enabled, that log type doesn't export its control plane logs.' AWS therefore (a) creates no control-plane log group while every log type is disabled — which is the case when the template declares no Logging property at all — and (b) once the update reaches DescribeUpdate status Successful, creates the CloudWatch Logs group named /aws/eks/<clusterName>/cluster and begins writing streams whose names start with 'kube-apiserver-'. The group name is a template: '/aws/eks/' and '/cluster' are its fixed text, the cluster name is the value taken from the request; 'kube-apiserver-' is the fixed stream-name prefix.
Emulator: the check deploys the cluster via CloudFormation (AWS::EKS::Cluster with no Logging), confirms absence of the group, calls UpdateClusterConfig with clusterLogging [{types:['api'], enabled:true}], then polls logs DescribeLogGroups for /aws/eks/<cluster>/cluster and DescribeLogStreams with logStreamNamePrefix='kube-apiserver-'. Neither the group nor any stream was ever observed; the check was cut off while still polling.
Why: a client that enables control-plane logging to drive audit or observability tooling sees DescribeLogGroups return no group and DescribeLogStreams return an empty logStreams list forever, so any consumer tailing control-plane logs — or any assertion that logging is now on — can never make progress against the emulator while the same code works on AWS.
Fix: the eks UpdateClusterConfig handler's logging side-effect and the state it shares with cloudwatchlogs — on reaching Successful the update must materialise the /aws/eks/<cluster>/cluster group in logs state and emit at least one kube-apiserver-<id> stream; the CloudFormation AWS::EKS::Cluster path must route to the same side-effect so a CFN-created cluster behaves like a CreateCluster one.
Traces: ecr__eks__logs.deploy-eks-cluster-without-logging-config-no-log-groups.

Cause 2 of 3: no Container Insights performance data is ever delivered — /aws/containerinsights/<cluster>/performance stays empty after the amazon-cloudwatch-observability add-on is ACTIVE with a pod-identity role carrying CloudWatchAgentServerPolicy, and it also stays empty in the negative control after the missing permission is attached to the same role.
AWS: recorded behavior only (the EKS Smithy model describes CreateAddon / CreatePodIdentityAssociation but not the add-on's data-plane emissions). The recording shows that once the cluster, the managed nodegroup, the eks-pod-identity-agent add-on and the amazon-cloudwatch-observability add-on are all ACTIVE and a pod identity association maps namespace amazon-cloudwatch / serviceAccount cloudwatch-agent to a role holding arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy, the CloudWatch Logs group /aws/containerinsights/<clusterName>/performance receives events whose message bodies parse as Embedded Metric Format records containing a CloudWatchMetrics key and ClusterName equal to the cluster's name. The group name is a template: '/aws/containerinsights/' and '/performance' are fixed text, the cluster name comes from the request. The negative control records the mirror image: with an agent role lacking CloudWatch write permission the group receives nothing, and after that policy is attached delivery starts without recreating anything.
Emulator: both checks poll FilterLogEvents on that group (900 s delivery window; 360 s deny window in the negative control). No performance event was ever observed in either check, so the positive assertion ('performance log events parse as EMF records tagged with ClusterName=<cluster>') can never be satisfied and the negative control can never reach its post-attachment delivery half. Both checks were cut off while polling.
Why: a client validating Container Insights — a dashboard, an alarm on an EMF-derived metric, or a test that the agent's permissions are correct — observes an empty log group and cannot distinguish 'permission denied' from 'the observability add-on produces nothing', which is exactly the distinction the negative control exists to make.
Fix: the eks add-on state machine's data-plane emission for amazon-cloudwatch-observability and the pod-identity authorization it consults — write EMF records into cloudwatchlogs state under /aws/containerinsights/<cluster>/performance, gated on the associated role's CloudWatch write permission.
Traces: ecr__eks__logs.eks-container-insights-metrics-logs-delivery, ecr__eks__logs.eks-container-insights-without-agent-permission-no-delivery.

Cause 3 of 3: a pod never reports any image-pull outcome for a private ECR image — no 'Pulled' event on a Fargate-profile pod whose pod execution role is authorized, and no pull-failure outcome on a pod whose role lacks ECR permission.
AWS: Smithy: CreateFargateProfile POST /clusters/{clusterName}/fargate-profiles requires fargateProfileName, clusterName and podExecutionRoleArn and returns FargateProfile{podExecutionRoleArn, selectors, status}; podExecutionRoleArn is documented as the Pod execution role to use for any Pod matching the profile's selectors. Recorded behavior: with the profile ACTIVE, no nodegroup and no imagePullSecrets, a pod scheduled onto it pulls its private ECR image through that role (AmazonEKSFargatePodExecutionRolePolicy) and the cluster Kubernetes API reports a core/v1 Event with reason 'Pulled' naming the image; when the role carries no ECR permission the pull is refused and the pod reports a pull failure instead (reason 'Failed' with an ECR authorization message) rather than silently never progressing. 'Pulled' and 'Failed' are the fixed reason strings; the image reference and pod name are values from the request.
Emulator: both checks stand the cluster up (and, for the Fargate case, the private subnets and Fargate profile), create the pod, then poll the served cluster Kubernetes API for the pod's events for up to 900 s. No pull outcome — neither success nor refusal — was ever observed; both checks were cut off while polling.
Why: a client cannot tell an authorized pull from an unauthorized one: both look like a pod stuck with no events. Any workflow that gates on the pull result (waiting for a pod to run, or asserting that a missing ECR permission is what broke it) hangs instead of resolving, and the negative control that proves ECR authorization is enforced cannot be expressed at all.
Fix: the served cluster Kubernetes API's pod admission/runtime path and the ECR authorization it consults — a pod must progress to an image-pull attempt and record the resulting core/v1 Event (reason 'Pulled' on success, a pull-failure Event when the pod execution or node role is not authorized for the repository).
Traces: ecr__eks__logs.eks-fargate-execution-role-pulls-ecr-image, ecr__eks__logs.eks-pod-image-pull-fails-without-ecr-permission-rejected.

## Resolution
Cause 2 is implemented: a cluster whose `amazon-cloudwatch-observability` add-on is ACTIVE now runs the CloudWatch agent on its nodes and delivers Container Insights performance records — Embedded Metric Format documents carrying a `CloudWatchMetrics` declaration, the cluster's name and the counts read off the cluster's own records — into `/aws/containerinsights/<cluster name>/performance`, one stream per node, gated on the IAM role the account put in force on the agent's service account (its EKS Pod Identity association, the add-on's `serviceAccountRoleArn`, else the node's own role): an agent whose role is not permitted `logs:CreateLogGroup`/`CreateLogStream`/`PutLogEvents` delivers nothing and starts delivering as soon as that grant is attached to the same role. The collection runs on its own interval, carried by a task of this service and materialised by the reads that materialise the add-on's status. Pinned by `core/router/tests/all/eks_container_insights_performance_delivery.rs`; the recorded check `eks-container-insights-metrics-logs-delivery` passes.

Causes 1 and 3 were already correct in the code base this issue was traced to, and the replay reached neither claim: cause 1's check spends its whole budget in its pre-update absence window, and cause 3's positive unit (`eks-fargate-execution-role-pulls-ecr-image`) passes. Enabling a log type with `UpdateClusterConfig` on a CloudFormation-provisioned cluster does create `/aws/eks/<cluster>/cluster` and its `kube-apiserver-*` stream, now pinned end to end by `core/router/tests/all/eks_stack_deployed_cluster_logging_enabled_afterwards.rs`; a pod's image pull is recorded as `Pulling`/`Pulled` or `Failed`/`BackOff` events for both capacity kinds and both authorization outcomes, pinned by `core/router/tests/all/eks_pod_image_pull_events.rs` and `core/router/tests/all/eks_fargate_pod_execution_role_pulls.rs`.

The three checks still ending on the suite's 60 s budget are the three whose expectation is an ABSENCE (no log group before any type is enabled, no delivery while the agent's role lacks the grant, no successful pull without the ECR grant): each spends its own multi-minute window asserting that nothing appears, which no emulator behaviour can shorten. Both checks whose expectation is a PRESENCE now pass.

2. 4. Pod image pull: push an image to a private ECR repository, create a cluster with private subnets and a Fargate profile whose podExecutionRoleArn carries AmazonEKSFargatePodExecutionRolePolicy, create a pod matching the profile's selectors with no imagePullSecrets, and poll the served cluster Kubernetes API for the pod's core/v1 events — no 'Pulled' event ever appears.
