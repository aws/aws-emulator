# CreateSecurityRequirementPack and CreateTargetDomain mint opaque hex identifiers instead of the service's prefixed forms

> _Note: this issue was identified against the code base at commit `3c42ba1b0bd2ccb43c9358bd117a182df6732fd7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSecurityRequirementPack

## Description
Two creating operations of securityagent hand back resource identifiers drawn from the service crate's ONE generic sequential mint (32 lowercase hex characters = a 16-hex namespace followed by a 16-hex per-account counter) rather than from the identifier form the recorded service uses for that resource class. Both causes are the same minting defect seen on two resource classes, so they are bundled; the already-open issue 20261111T054132Z-securityagent-createagentspace-mints-opaque-hex-agent-space-ids-instead.md covers the SAME generic mint on CreateAgentSpace's agentSpaceId only and does not own either of the two causes below.

Cause 1 of 2: CreateSecurityRequirementPack returns a packId that carries no resource-class prefix.
AWS: recorded behavior only - Smithy com.amazonaws.securityagent#SecurityRequirementPackId is an unconstrained string (no @pattern, no @length) and CreateSecurityRequirementPack (POST /CreateSecurityRequirementPack, HTTP 201) models packId as a required output member, so the model does not pin the form. The recording does: every pack id that appears literally in the corpus carries the 'srp-' prefix - the AWS-managed catalog packs come back as 'srp-am-base', 'srp-am-nist-csf', 'srp-am-pci-dss' and 'srp-am-well-architected' in securityagent-catalog-list-security-requirements, and the emulator's own seed table reproduces exactly those four literals. The fixture's expectation for a freshly created pack is a captured-variable reference ('{{pack_id}}') that the replay could not satisfy from the emulator's response. Hypothesis: a customer-managed pack id is therefore 'srp-' plus a per-pack unique body (the 'srp-' text being fixed and the body a freshly generated per-pack value), which is the same prefix-plus-unique-body template the service uses for its agent space ids ('as-' plus a UUID).
Emulator: the 201 response carries packId as a bare 32-character lowercase hex string with no prefix and no separator - '8b0bb7d540ae34880000000000000001' in securityagent-security-requirement-pack-lifecycle#task#1, whose trailing counter shows it came from the shared generic minter rather than from a pack-specific one. Status matches (201 vs 201); only the identifier's form diverges. The concrete hex value is a per-run value and is not itself the requirement - the requirement is the prefixed template.
Why: a client that validates, routes on or parses a pack id - for example telling a pack id apart from an agent space id or a target domain id by its prefix, or asserting that a created pack id looks like the AWS-managed ones it already handles - rejects or mis-classifies every id the emulator mints, and an id captured from the emulator is not accepted by code written against real pack ids. Because the emulator's created-pack ids and its seeded 'srp-am-*' ids are in two different namespaces, code that treats all pack ids uniformly behaves differently against the emulator than against AWS.
Fix: the pack-id minting step of CreateSecurityRequirementPack in the securityagent service crate's state (the helper that the handler calls to populate the new pack record's identifier), which must emit the service's prefixed pack-id form instead of borrowing the generic hex/counter identifier generator. The response serializer needs no change: it faithfully echoes whatever the state minted.
Traces: securityagent-security-requirement-pack-lifecycle#task#1.

Cause 2 of 2: CreateTargetDomain returns a targetDomainId and an HTTP-route verification token that likewise come straight from the generic mint.
AWS: recorded behavior only - Smithy TargetDomainId is an unconstrained string ('Unique identifier of the target domain.'), CreateTargetDomain (POST /CreateTargetDomain, HTTP 200, no modeled errors) models targetDomainId as required and verificationDetails as the optional structure whose httpRoute member carries the token plus the route path, and the model pins neither the id form nor the token form. The recording expects, for the created domain, the fixture's captured-variable references '{{target_domain_id}}' for $.targetDomainId and '{{http_route_token_2}}' for $.verificationDetails.httpRoute.token, neither of which the emulator's response satisfied. The recorded HTTP_ROUTE challenge document itself is the fixed path '.well-known/aws/securityagent-domain-verification.json' under the domain (as the recorded VerifyTargetDomain failure reason quotes it), so the token is the only per-domain part of that challenge. Hypothesis: as with the pack ids above and the recorded 'as-'-prefixed agent space ids, the target domain id is a prefixed, resource-class-specific form rather than a bare member of one account-wide hex counter space.
Emulator: the 200 response carries targetDomainId as the same bare 32-character hex counter value ('d427d0765bbe3fb10000000000000001' in securityagent-target-domain-tagging-and-errors#setup#1) and verificationDetails.httpRoute.token as a 64-character lowercase hex SHA-256 digest ('7bab8626d38f9995c8cf606b6b65c5afb0541c7b08cf48a7cb64023a3cf28460'); both are fresh draws of the one account-wide mint, so a target domain id is indistinguishable in form from a pack id or an agent space id. Status matches (200 vs 200). The concrete id and digest are per-run values and are not the requirement; the requirement is that each carries the form the service hands out for its own resource class and challenge.
Why: a client that stores, validates or prefix-matches a target domain id - or that wires a web server to serve the verification token and checks the token looks like the one AWS issues - cannot tell an emulator target domain id from any other resource's id, and ids it captures from the emulator fail validation written against real ones. Anything that round-trips the id into the target-domain ARN inherits the wrong resource segment.
Fix: the target-domain identity minting step of CreateTargetDomain in the securityagent service crate's state (the helper that mints the record's id and its ownership-verification token together), which must emit the service's target-domain identifier form and its challenge-token form rather than two fresh draws of the generic identifier/secret mint. The handler's verification-details projection needs no change: it echoes the stored token.
Traces: securityagent-target-domain-tagging-and-errors#setup#1.

The same helper backs mint_agent_space_id (line ~1635), which is the already-filed CreateAgentSpace id-format issue, confirming one minter is responsible for all of them. The emulator's own AWS_MANAGED_PACKS table (lines ~371-392) hard-codes the prefixed ids 'srp-am-base', 'srp-am-nist-csf', 'srp-am-pci-dss', 'srp-am-well-architected', so the prefixed pack-id form is already evidenced inside the crate.
