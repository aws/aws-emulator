# ListSigningPlatforms publishes the two AmazonFreeRTOS catalog entries with the wrong order and wrong field values

> _Note: this issue was identified against the code base at commit `3bd56f3581a93dde5b982de16e37f58616506edc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSigningPlatforms

## Description
One net-new wire divergence in the signer crate's published signing-platform catalog. ListSigningPlatforms answers 200 with the right number of platforms, but the two AmazonFreeRTOS entries are published in the wrong catalog position and with the wrong values for five of their members each, so the page body diverges at $.platforms[3] and $.platforms[4]. Not covered by any open issue: the only neighbouring open wire issue, 20261031T194210Z-signer-response-envelopes-diverge-empty-204-replies-omit.md, is about empty-204 Content-Length framing and ListProfilePermissions.policySizeBytes and says nothing about the platform catalog.

Cause 1 of 1: the AmazonFreeRTOS platform entries diverge in catalog order and in their published members.
AWS: Smithy signer#ListSigningPlatforms is GET /signing-platforms, 200, output ListSigningPlatformsResponse.platforms -> SigningPlatforms, a list of SigningPlatform {platformId, displayName, partner, target, category -> Category, signingConfiguration -> SigningConfiguration {encryptionAlgorithmOptions.allowedValues/defaultValue, hashAlgorithmOptions.allowedValues/defaultValue}, signingImageFormat -> SigningImageFormat {supportedFormats -> ImageFormats, defaultFormat -> ImageFormat (JSON|JSONEmbedded|JSONDetached)}, maxSizeInMB, revocationSupported}. The model constrains the member names and the ImageFormat value set but does NOT state the catalog's contents or its order, so the catalog itself is recorded behavior only. The recording shows AWS publishing, at positions 4 and 5 of the page: first platformId AmazonFreeRTOS-TI-CC3220SF with displayName 'Amazon FreeRTOS SHA1-RSA CC3220SF-Format', partner AmazonFreeRTOS, target 'SHA1-RSA-TISHA1', category 'AWS', encryptionAlgorithmOptions {allowedValues ['RSA'], defaultValue 'RSA'}, hashAlgorithmOptions {allowedValues ['SHA1'], defaultValue 'SHA1'}, signingImageFormat {supportedFormats ['JSONEmbedded'], defaultFormat 'JSONEmbedded'}, maxSizeInMB 16, revocationSupported false; then platformId AmazonFreeRTOS-Default with displayName 'Amazon FreeRTOS SHA256-ECDSA', partner AmazonFreeRTOS, target 'SHA256-ECDSA', category 'AWS', encryptionAlgorithmOptions {allowedValues ['ECDSA','RSA'], defaultValue 'ECDSA'}, hashAlgorithmOptions {allowedValues ['SHA256'], defaultValue 'SHA256'}, signingImageFormat {supportedFormats ['JSONEmbedded'], defaultFormat 'JSONEmbedded'}, maxSizeInMB 16, revocationSupported false. (Note the model's Category enum in this revision lists only AWSIoT, yet the recorded catalog reports 'AWS' for these entries — the recording governs the wire, and the emulator's other catalog entries already publish 'AWS' and replay clean.)
Emulator: publishes the two entries in the opposite order (AmazonFreeRTOS-Default at $.platforms[3], AmazonFreeRTOS-TI-CC3220SF at $.platforms[4]) and, for each of them, diverges on five members: displayName is spelled with no space after 'Amazon' ('AmazonFreeRTOS SHA1-RSA CC3220SF-Format' / 'AmazonFreeRTOS SHA256-ECDSA') instead of 'Amazon FreeRTOS ...'; target reports the id suffix ('TI-CC3220SF' / 'Default') instead of the signing-template name AWS publishes ('SHA1-RSA-TISHA1' / 'SHA256-ECDSA'); category reports 'AWSIoT' instead of 'AWS'; signingImageFormat reports supportedFormats ['JSON'] / defaultFormat 'JSON' instead of ['JSONEmbedded'] / 'JSONEmbedded'; and for AmazonFreeRTOS-Default encryptionAlgorithmOptions.allowedValues reports ['ECDSA'] instead of ['ECDSA','RSA']. platformId, partner, maxSizeInMB, revocationSupported and the hash algorithm options match.
Why: the platform catalog is the only published description of what Signer can sign, and clients read it to drive their own behavior. A client that lists with ?category=AWS (or filters the page by category) loses both FreeRTOS platforms entirely, and one that lists with ?target=SHA256-ECDSA or ?target=SHA1-RSA-TISHA1 gets an empty page, because the emulator's filter compares against the wrong published target. A client that selects a platform by the display name AWS documents never matches it. A client that picks a signing image format from supportedFormats chooses JSON where AWS only offers JSONEmbedded, and one that offers RSA for AmazonFreeRTOS-Default is told RSA is not allowed when AWS allows it — so a profile/signing configuration validated against the emulator's catalog is rejected on real Signer, and vice versa. The swapped order also means any client that indexes into the page, or that pages with maxResults=4 and then follows nextToken, sees a different platform than AWS returns at that position.
Fix: the published catalog table in the signer crate's state — the two AmazonFreeRTOS entries' field values and their position in SIGNING_PLATFORM_CATALOG — not the ListSigningPlatforms handler, whose paging and filtering logic reads the table in order and is otherwise correct. Entry order must also be corrected because the listing (and its page tokens) enumerate the catalog in declaration order.
