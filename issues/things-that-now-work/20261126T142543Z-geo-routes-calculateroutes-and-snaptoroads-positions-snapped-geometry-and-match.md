# CalculateRoutes and SnapToRoads positions, snapped geometry and match confidence are synthesized from the request coordinates

> _Note: this issue was identified against the code base at commit `a650362e0e15805c1963e4149e23a73be0a73a90`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CalculateRoutes

## Description
geo-routes answers CalculateRoutes (POST /v2/routes) and SnapToRoads (POST /v2/snap-to-roads) with HTTP 200 and a structurally valid, modelled body - the statuses, the required members, the enums and the x-amz-geo-pricing-bucket header all replay clean - but every value that AWS derives from the road network (the snapped Position, the echoed OriginalPosition, the snapped geometry Polyline and the per-point match Confidence) is instead computed arithmetically from the request coordinates. This bundle carries THREE causes, each its own replay cluster; all three must be closed.

=== Cause 1 of 3: CalculateRoutes leg Place.OriginalPosition is the request coordinate quantized, and Place.Position is an offset of that quantized value rather than a road-graph snap ===
AWS: Smithy com.amazonaws.georoutes#CalculateRoutes (POST /v2/routes, success code 200 defaulted; modelled errors ValidationException 400, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500 - none in play, both sides answer 200, so no status, error code or error message diverges). The leg's Arrival/Departure carry RouteVehicleArrival/RouteVehicleDeparture.Place of shape RouteVehiclePlace. Its member OriginalPosition targets Position23 (list of Double, @length min 2 max 3, @sensitive) and is documented "Position provided in the request" - it is a verbatim echo of the submitted coordinate, carried at the precision the caller sent (the recording shows 7 decimal places, e.g. longitude -122.3088001, latitude 47.4501999). Its member Position is @required, targets Position23 and is documented "Position in World Geodetic System (WGS 84) format: [longitude, latitude]" - the point on the road network that the leg actually arrives at / departs from, so it legitimately DIFFERS from OriginalPosition by the snap (the recording's arrival Position -122.3029601 / 47.45124 is displaced from its OriginalPosition -122.3088001 / 47.4501999 by roughly 440 m, the distance to the carriageway).
Emulator: OriginalPosition is not an echo - it is the request coordinate quantized to 4 decimal places, so the submitted digits are lost (arrival longitude -122.3088 for a submitted/recorded -122.3088001; arrival latitude 47.4502 for 47.4501999; departure longitude -122.341 for -122.3410001). Position is then produced from that quantized coordinate by a small fixed arithmetic offset rather than by resolving the road graph: the arrival Position comes back as -122.308836 / 47.4502 (longitude = the quantized value minus a constant, latitude unchanged) where the recording's road-snapped arrival is -122.3029601 / 47.45124, and the departure Position comes back as -122.340836 / 47.6089 against the recorded -122.3409556 / 47.6089359. The emitted Position is therefore within a few metres of the requested point and on no road, i.e. no snap occurred at all. The model states the members' semantics and the recording shows the resulting values; the exact emulator formula is recorded behavior only.
Why: a client that compares OriginalPosition with Position to answer "how far is my address from the road, and which side of the street is it on" gets ~0 m and a meaningless SideOfStreet; a client that re-feeds Position into a follow-up CalculateRoutes/OptimizeWaypoints call as a road-anchored waypoint submits an off-road point; and because OriginalPosition no longer round-trips the submitted coordinate, a client cannot correlate the returned legs with the waypoints it sent by matching positions. All of this is silent - the response is a 200 with correctly shaped 2-element Position lists.
Fix: the CalculateRoutes handler's leg/place response synthesis in the geo-routes service crate (services/service-com-amazonaws-georoutes-routesservice) - echo OriginalPosition verbatim from the request at the submitted precision, and resolve Position against the road graph instead of applying a constant offset to a quantized coordinate.
Traces: geo-routes-calculate-routes-truck-travel-mode-options-wiring-success#task#1 (cluster representative) and geo-routes-calculate-routes-zero-max-alternatives-returns-single-route#task#1 (affected_count 2).

=== Cause 2 of 3: SnapToRoads SnappedPosition, SnappedGeometry.Polyline and SnappedTracePoints[].Confidence are invented rather than derived from the road match ===
AWS: Smithy com.amazonaws.georoutes#SnapToRoads (POST /v2/snap-to-roads, success code 200 defaulted; modelled errors ValidationException 400, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500 - none in play, both sides answer 200). RoadSnapSnappedTracePoint.Confidence is @required, targets SensitiveDouble with @range min 0 max 1, and is documented "Confidence value for the correctness of this point match" - it is a per-point QUALITY measure of the match, so it varies with how well the trace point fits the road network (the recording carries 1, 0.05, 0.04 and 0.12 across four points of one trace: one certain match and three poor ones). SnappedPosition is @required and documented "Snapped position of the TracePoint provided within the request, at the same index", i.e. the point on the road network, carried at the precision of that computed position (the recording shows 5 decimals, e.g. -122.33662 / 47.61009). RoadSnapSnappedGeometry.Polyline is documented as "an ordered list of positions used to plot a route on a map in a lossy compression format" and is the interpolated geometry of the snapped route, so its decoded vertices must be the road-following path through the snapped points.
Emulator: Confidence is a locally generated pseudo-value in [0,1] that has no relation to match quality - the four points come back 0.5624402370375639, 0.9205739449522025, 0.5624154808054271 and 0.562403101865775, i.e. three nearly identical ~0.5624 values plus one ~0.92, where the recording's confidences for the same points differ by a factor of 25 (1 vs 0.04). The point the recording marks as a certain match (1) is reported ~0.56 and a point the recording marks as poor (0.05) is reported ~0.92, so the ordering is wrong as well as the magnitude, and the long mantissa shows it is computed, not measured. SnappedPosition is again the request coordinate quantized to 4 decimals with a small constant offset on one axis (-122.3366 / 47.610164 against the recorded snap -122.33662 / 47.61009; -122.336336 / 47.6111 against -122.33718 / 47.61071), so the "snapped" points sit on the trace, not on a road. SnappedGeometry.Polyline is correspondingly wrong and much shorter: the emulator emits 'BGoz856Cv16qpHAwQofAobAgEAofAofAAgVAoKofAofAAwI' where the recording carries 'BG0u856C326qpHwHnGgP3NgP3Nof_dkNvM8GnGoL_JkN7L8QvR8Lkc4IoVgKkX8B4D0UkwB8GoQ8G8Q' - the emulator interpolates straight between its own synthesized points instead of encoding the road segments traversed, so it carries far fewer vertices and a different starting vertex.
Why: filtering by confidence is the documented way to use this API - a client drops trace points below a threshold (e.g. 0.5) before map-matching a GPS trail. With a synthesized confidence it retains the bad matches and discards the good ones, and a fleet/telematics consumer cannot distinguish a tunnel dropout from a clean fix. The polyline drawn on a map cuts across blocks instead of following the streets, and SnappedPosition fed into distance or geofence maths yields the raw GPS error back rather than a road-anchored point.
Fix: the SnapToRoads handler in the geo-routes service crate - compute SnappedPosition by resolving each TracePoint against the road graph within SnapRadius, derive Confidence from that match (residual distance / candidate ambiguity) instead of generating a number, and build SnappedGeometry.Polyline by encoding the traversed road geometry rather than the synthesized points.
Traces: geo-routes-snap-to-roads-basic-success#task#1 (cluster representative; affected_count 1).
