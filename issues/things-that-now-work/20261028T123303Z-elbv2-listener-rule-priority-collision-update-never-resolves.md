# ELBv2 listener-rule priority-collision UPDATE never resolves: the CloudFormation-driven move of a rule onto a taken priority neither refuses with PriorityInUse nor reaches a terminal stack/data-plane state (check hangs)

> _Note: this issue was identified against the code base at commit `84725303c518fb402f10cf931cddd35e44c00d9a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetRulePriorities

## Description
One root cause, grounded in 1 failing behavioral check whose id's leading token is 'elbv2'.

Related but non-covering open issues: 20261023T025808Z-cloudformation-elbv2-a-cloudformation-stack-whose-elbv2-listener-rules-collide.md covers the CREATE path (two rules declared at the same priority in one template reach CREATE_COMPLETE) and does not carry this replay key; 20261023T205437Z-elbv2-ten-control-plane-operation-families-answer-501.md covers CreateRule/tagging/trust-store families answering 501; the scaffold issue filed for UNIMPLEMENTED ModifyRule (services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/ops/modify_rule.rs) covers that single operation being a stub. None of them covers the UPDATE-time priority-collision path exercised here, which is a rule being MOVED onto a priority another rule already holds.

Cause 1 of 1: moving an existing listener rule onto an already-used priority is never refused, and the update flow never reaches any terminal outcome the client can observe.
AWS: a rule's priority is changed with SetRulePriorities, not ModifyRule — Smithy com.amazonaws.elasticloadbalancingv2#ModifyRule has no Priority member (input: RuleArn required, Conditions, Actions, Transforms, ResetTransforms), while SetRulePriorities (input: RulePriorities required, list of RulePriorityPair) models PriorityInUseException with awsQueryError {code: 'PriorityInUse', httpResponseCode: 400}. So re-pointing rule A at the priority rule B already holds on the same listener is refused HTTP 400 with error code 'PriorityInUse'; the message's fixed text is the PriorityInUse wording "Priority '<priority>' is in use", whose only variable part is the requested priority value taken from the request (here the priority the template moved rule A to) — never a literal from one run. CloudFormation propagates that resource refusal: the AWS::ElasticLoadBalancingV2::ListenerRule resource emits an UPDATE_FAILED event for that logical id whose ResourceStatusReason carries CloudFormation's closed handler vocabulary 'HandlerErrorCode: AlreadyExists' (the elbv2 prose embedded in the reason is not asserted), the stack goes UPDATE_ROLLBACK_IN_PROGRESS -> UPDATE_ROLLBACK_COMPLETE, and the rollback leaves the rule's ARN, its original priority and its original action body unchanged; the ALB data plane keeps serving the pre-update fixed-response body at the rule's path. Recorded behavior only for the terminal stack status strings and for the data-plane body, which the check asserts.
Emulator: the check produces no terminal answer at all — it fails with 'Check timed out after 60.0s'. The check's only unbounded waits after create_stack are (a) the describe_stacks poll for a non-*_IN_PROGRESS stack status and (b) the data-plane poll for five consecutive GETs of http://<AlbDns>/a answering 200 with the rule's fixed-response body. Neither the PriorityInUse refusal nor the UPDATE_ROLLBACK_COMPLETE outcome nor the served body is ever observed. Hypothesis: the colliding-priority update is accepted (consistent with the CREATE-path issue above, where a duplicate priority is also accepted), so no resource failure is raised and either the stack update is left parked in an *_IN_PROGRESS status or the ALB fixed-response data plane never answers on the load balancer's DNS name — only one of (a) or (b) can be the blocking loop, and the replay output does not say which.
Why: a client that gates deployments on CloudFormation reaching a terminal status gets neither success nor failure — update_stack hangs forever instead of rolling back, so a template with a genuine routing conflict never surfaces one, and nothing ever returns the modeled PriorityInUse (HTTP 400) a client's error handling is written against. A rule move that AWS rejects atomically can also leak a partial change (new action body at the old priority) with no rollback to undo it.
Fix: the ELBv2 SetRulePriorities handler's priority-uniqueness validation (it must refuse with PriorityInUse / HTTP 400 when the requested priority is held by another rule on the same listener), the ELBv2 rule state that must treat (listener, priority) as unique on update as well as on create, the CloudFormation AWS::ElasticLoadBalancingV2::ListenerRule update handler that must map that refusal to an UPDATE_FAILED event with HandlerErrorCode: AlreadyExists and drive the stack to UPDATE_ROLLBACK_COMPLETE (never leaving it *_IN_PROGRESS), and the ALB listener-rule fixed-response data plane that must serve the rolled-back rule.

## Evidence
elbv2.deploy-elbv2-2-rule-priority-collision-update-rejected — [mismatch] 'Check timed out after 60.0s'. The check creates a stack (VPC/IGW/subnets/SG/ALB/HTTP listener with a 404 fixed-response default, RuleA at priority 10 serving body 'a1' on path /a, RuleB at priority 20 on the same path), then issues an update_stack moving RuleA to priority 20 and its body to 'a2'. Expected by AWS: _wait_stack returns 'UPDATE_ROLLBACK_COMPLETE'; the RuleA UPDATE_FAILED event's ResourceStatusReason matches r'HandlerErrorCode: ([A-Za-z]+)' with the single code 'AlreadyExists'; DescribeRules still shows RuleA at Priority '10' with FixedResponseConfig.MessageBody 'a1' and RuleB at Priority '20' with the same RuleArns as before; GET /a still serves 200 'a1'. Actual: none of these assertions is ever reached — the check never leaves a polling loop inside the 60s harness budget, so the emulator produced neither the PriorityInUse refusal nor any terminal stack status. Smithy citations: ModifyRule input has no Priority member; SetRulePriorities errors include PriorityInUseException, awsQueryError {code: 'PriorityInUse', httpResponseCode: 400}; CreateRule models the same PriorityInUseException for the create path.

1. Boot the emulator.
2. create_stack a template owning its own VPC, IGW + attachment, default route, two subnets in two AZs, a security group allowing TCP/80, an internet-facing application load balancer on those subnets, an HTTP:80 listener with a fixed-response 404 default action, RuleA (Priority 10, path-pattern /a, fixed-response 200 body 'a1') and RuleB (Priority 20, path-pattern /a, fixed-response 200 body 'b1').
