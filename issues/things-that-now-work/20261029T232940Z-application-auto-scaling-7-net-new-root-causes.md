# Application Auto Scaling: 7 net-new root causes — Lambda/custom-resource target validation missing or misworded, refusal messages diverge, and a registration floor never drives a scaling activity

> _Note: this issue was identified against the code base at commit `54073c01592ce4e56a3cca58cb5387afed010108`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterScalableTarget

## Description
This issue bundles SEVEN distinct net-new root causes in the Application Auto Scaling emulator (service token `application-auto-scaling`). All seven must be closed before submitting. None of them is covered by the three open Application Auto Scaling issues: 20261022T182203Z-application-auto-scaling-accepts-requests-real-aws-refuses.md (authorization / region / role / CloudFormation semantics), 20261024T115439Z-application-autoscaling-application-auto-scaling-scheduled-actions-never-fire-target.md (scheduled actions never fire, target tracking never scales, tag calls on stale ARNs), and 20261029T004004Z-application-autoscaling-ecs-application-auto-scaling-scaling-activities-carry-no-statusmessage.md (ECS step-scaling activities carry no StatusMessage at all). Causes 5 and 7 below are adjacent to those last two but are different defects: here the activity IS present and DOES carry a StatusMessage, it is simply the wrong one (cause 5), and here the scaling effect is a registration floor, not a policy firing (cause 7).

=== Cause 1 of 7: RegisterScalableTarget refuses the $LATEST Lambda qualifier with the wrong message ===
AWS: Smithy — RegisterScalableTarget.ResourceId (ResourceIdMaxLen1600, required), ScalableDimension (enum, required); modeled error ValidationException (errorKind client, httpError 400). The model does not state the per-namespace resource-id grammar, so the message is recorded behavior only. For the `lambda` namespace and dimension `lambda:function:ProvisionedConcurrency`, provisioned concurrency can only be scaled on a published version or an alias, so a resource id ending in the `$LATEST` qualifier is refused HTTP 400 ValidationException with the message whose text is entirely fixed: `$LATEST is not a supported qualifier for Auto Scaling`. There is no variable part in this message — it names neither the function nor the dimension.
Emulator: returns ValidationException (correct code) but with a different, self-invented message: `ResourceId not valid for ScalableDimension lambda:function:ProvisionedConcurrency: function:<function-name>:$LATEST must name an alias or a published version of the function, and $LATEST is neither`. Here `lambda:function:ProvisionedConcurrency` is the request's ScalableDimension and `function:<function-name>:$LATEST` is the request's ResourceId — i.e. the emulator built a generic templated message instead of AWS's fixed one.
Why: a client that branches on, logs, or asserts the refusal text for an unsupported qualifier sees text AWS never emits; the fixed-vs-variable split is inverted (AWS's text is constant, the emulator's interpolates the request), so any regex or equality match on the documented string fails.
Fix: the `lambda`-namespace resource-id validation inside the RegisterScalableTarget handler's validation step — emit the fixed `$LATEST` message for that one case rather than falling through to the generic resource-id/dimension mismatch message.
Traces: application-auto-scaling.lambda-latest-and-unqualified-targets-rejected. Note this check also asserts, after the $LATEST leg, that an UNQUALIFIED function id (`function:<name>`, no version/alias) is refused with ValidationException `Unsupported service namespace, resource type or scalable dimension` (also entirely fixed text) and that neither refused id is registered; the check aborted at the $LATEST assertion, so the unqualified leg was never reached and must be fixed and re-replayed together with it.

=== Cause 2 of 7: RegisterScalableTarget accepts a Lambda alias that does not exist ===
AWS: Smithy — RegisterScalableTarget errors include ValidationException (client, 400); the existence of the referenced downstream resource is not expressible in the model, so this is recorded behavior only. Registering `lambda:function:ProvisionedConcurrency` against `function:<function>:<alias>` where that alias does not exist on an existing function is refused HTTP 400 ValidationException and NOTHING is registered. The message's fixed text is `Validation failed for resource: `, `, scalable dimension: `, `. Reason: Cannot find alias arn: `; its variable parts come from the request and from the resolved partition/region/account — the resource id, the scalable dimension, and the alias ARN `arn:<partition>:lambda:<region>:<account>:function:<function>:<alias>`.
Emulator: returns HTTP 200 with a ScalableTargetARN, registering a scalable target that points at a nonexistent Lambda alias. No existence check against the Lambda namespace is performed at all.
Why: a client gets a silent success for a target that can never scale; the error path that surfaces a typo'd or not-yet-created alias is gone, and DescribeScalableTargets then reports a phantom target. Any test or deploy pipeline that relies on registration failing fast for a missing alias proceeds as if provisioned-concurrency scaling were configured.
Fix: RegisterScalableTarget handler validation for the `lambda` namespace — resolve the qualifier against Lambda state (published version or alias) before persisting, and refuse with the ValidationException above instead of writing the target.
Traces: application-auto-scaling.lambda-target-on-a-missing-alias-rejected (the same check's positive control registers the alias that DOES exist with bounds (0, 2)).

=== Cause 3 of 7: PutScalingPolicy's predefined-metric target-value range refusal is misworded ===
AWS: Smithy — PutScalingPolicy.TargetTrackingScalingPolicyConfiguration, modeled error ValidationException (client, 400); the per-predefined-metric valid range is not in the model, so the message is recorded behavior only. For PredefinedMetricType `LambdaProvisionedConcurrencyUtilization` the TargetValue is a FRACTION, valid in [0.1, 0.9]; a value outside it is refused HTTP 400 ValidationException with message fixed text `For predefined metric type `, `, target value must be between '`, `' and '`, `', but was '`, `'.` and variable parts taken from the request and from the metric's own range: the predefined metric type, the range endpoints for that metric, and the rejected TargetValue as submitted.
Emulator: refuses with the right code but the wrong message — `Target value must be between 0.1 and 0.9 for predefined metric type LambdaProvisionedConcurrencyUtilization`. The clauses are reordered, the endpoints are unquoted, and the offending submitted value is omitted entirely.
Why: the single most useful variable in the message — the value the caller actually sent — is dropped, so a client cannot tell from the error which of several policy puts was wrong; and any equality/regex match on AWS's documented wording fails.
Fix: the target-tracking validation in the PutScalingPolicy handler — emit AWS's clause order and include the submitted TargetValue and quoted range endpoints.
Traces: application-auto-scaling.lambda-utilization-target-given-as-a-percentage-rejected. The check continues, after the message assertion, to require that the refused policy is NOT stored and minted NO CloudWatch alarms, and that the same policy expressed as the fraction 0.7 is accepted and returns exactly 2 Alarms; those legs were never reached and must be re-replayed with the fix.

=== Cause 4 of 7: DeleteScheduledAction's ObjectNotFoundException identifies the target by resource id instead of by scalable target ID ===
AWS: Smithy — DeleteScheduledAction errors include ObjectNotFoundException (errorKind client, httpError 400), documented as thrown when the object depended on does not exist. The message wording is recorded behavior only. Deleting an already-deleted scheduled action is refused HTTP 400 ObjectNotFoundException with fixed text `No scheduled action found for service namespace: `, `, scalable target ID: `, `, scheduled action name: ` and variable parts from the request and from emulator state: the service namespace, the scalable target's ID — the UUID formed from the 32 hex digits that end the ScalableTargetARN returned by RegisterScalableTarget, hyphenated 8-4-4-4-12 — and the scheduled action name.
Emulator: refuses with the right code but names the target the wrong way: `No scheduled action found for service namespace: dynamodb, resource ID: table/<table>, scalable dimension: dynamodb:table:WriteCapacityUnits, scheduled action name: <action>`. It substitutes a `resource ID:` + `scalable dimension:` pair for AWS's single `scalable target ID:` UUID clause.
Why: the message no longer carries the scalable target's identity, which is how AWS correlates a scheduled action to the target it hangs off; a client that parses the target ID out of the refusal (or asserts the documented wording) cannot.
Fix: the ObjectNotFoundException construction in the DeleteScheduledAction handler — look up the scalable target's ID and render that single clause.
Traces: application-auto-scaling.scheduled-action-lifecycle. The earlier legs of this check passed: PutScheduledAction, DescribeScheduledActions round-trip of Schedule and ScalableTargetAction, the first delete, and the ObjectNotFoundException CODE on the second delete are all correct — only the message diverges.

=== Cause 5 of 7: an Overridden scaling activity's StatusMessage does not report the capacity it set or the value that displaced it ===
AWS: Smithy — ScalingActivity.StatusCode targets ScalingActivityStatusCode whose values are Pending, InProgress, Successful, Overridden, Unfulfilled, Failed; StatusMessage is `a simple message about the current status of the scaling activity`. The exact wording is recorded behavior only. When one activity's capacity change is displaced by a later activity before fulfilment is confirmed, the superseded activity settles StatusCode `Overridden` with a StatusMessage whose fixed text is `Successfully set read capacity units to `, `. Found it was later changed to `, `.` — its variable parts are the capacity the superseded activity itself set and the capacity that displaced it, both from emulator state. (The surviving activity settles `Successful` with `Successfully set read capacity units to <value>. Change successfully fulfilled by <namespace>.`)
Emulator: the superseded activity reaches StatusCode `Overridden` correctly, but its StatusMessage is `Setting read capacity units to 4.` — that is a Description-style present-tense sentence carrying the DISPLACING value only. It reports neither the capacity this activity set nor the fact that it was later changed, so the two-part override narrative is lost and the message does not even describe this activity's own action.
Why: a client reading activity history cannot tell what the overridden activity had actually applied before it was displaced; the status text contradicts the status code, and the Description/StatusMessage distinction collapses.
Fix: the scaling-activity state machine that resolves an activity to Overridden — render the two-clause override StatusMessage from the activity's own set value and the displacing value, rather than reusing the Description template.
Traces: application-auto-scaling.superseded-scaling-activity-resolves-to-overridden. (Distinct from open issue 20261029T004004Z, where ECS step-scaling activities carry NO StatusMessage at all; here the field is populated with the wrong text.)

=== Cause 6 of 7: custom-resource RegisterScalableTarget never probes the endpoint, so an undeployed stage is accepted ===
AWS: Smithy — RegisterScalableTarget errors include ValidationException (client, 400); the custom-resource reachability contract is not in the model, so this is recorded behavior only. In the `custom-resource` namespace the service CALLS the caller's endpoint (GET and PATCH on `/scalableTargetDimensions/{id}`) as part of registration. When the endpoint cannot be invoked — here because the API Gateway stage in the resource id was never deployed — registration is refused HTTP 400 ValidationException, NOTHING is registered, and the endpoint's capacity is left untouched. The message's fixed text is `User is missing the following permissions: ` followed by the required actions it could not exercise, `execute-api:Invoke:PATCH, execute-api:Invoke:GET`.
Emulator: returns HTTP 200 with a ScalableTargetARN. It registers the target against an endpoint it never contacted, so an unreachable custom resource is indistinguishable from a working one.
Why: the entire reachability/permission precondition of the custom-resource contract is unenforced. A client that depends on registration failing when its endpoint is not yet deployed or not yet authorized gets a success, then silently never scales; the documented permission-diagnostic message is never produced.
Fix: the `custom-resource` namespace branch of the RegisterScalableTarget handler — invoke the endpoint's GET/PATCH as a precondition and refuse with the ValidationException above (registering nothing) when either call cannot be made.
Traces: application-auto-scaling.custom-resource-stage-the-api-never-deployed-rejected (the same check's positive control, a DEPLOYED stage, registers with bounds (1, 4) and passes).

=== Cause 7 of 7: a registration MinCapacity floor above current capacity never drives a scaling activity or moves the downstream resource ===
AWS: Smithy — RegisterScalableTarget.MinCapacity/MaxCapacity (ResourceCapacity); DescribeScalingActivities returns ScalingActivities whose StatusCode settles `Successful`. The per-namespace fulfilment wording is recorded behavior only. Registering a target whose MinCapacity is ABOVE the downstream resource's current capacity makes Application Auto Scaling raise that resource to the floor and record ONE activity that settles `Successful`, with Cause fixed text `minimum capacity was set to ` + the registered MinCapacity, a Description naming the property being set (`Setting desired capacity to <min>.` for custom-resource; `Setting table write capacity units to <min>.` for cassandra), and a StatusMessage of fixed text `Successfully set <property> to `, `. Change successfully fulfilled by `, `.` with the floor value and the fulfilling namespace as variables. The downstream write is namespace-specific: for custom-resource a PATCH carrying exactly `{"desiredCapacity": <min>}` to the endpoint; for cassandra a Keyspaces table raised to `PROVISIONED` write capacity `<min>` with the READ capacity left untouched.
Emulator: neither happens. Both checks poll DescribeScalingActivities for an activity that settles `Successful` and both never observe one; the checks are killed at the harness budget while still polling, so registration produced no scaling activity and the downstream resource was never moved. Evidence here is a non-terminating poll rather than a wrong value — the emulator accepts the registration (HTTP 200) and then performs no scaling work for the floor, across two independent namespaces (`custom-resource` and `cassandra`), which is why they cluster as one cause.
Why: the floor side of a scalable target's bounds is inert. A client registers MinCapacity expecting the resource to be pulled up to it and expecting an auditable Successful activity; it gets neither, so capacity silently stays below the configured minimum and activity history is empty.
Fix: the scaling-activity engine invoked from the RegisterScalableTarget handler — on registration, compare the floor to the downstream resource's current capacity and, when the floor is higher, emit the activity and perform the namespace-specific downstream write (custom-resource endpoint PATCH; Keyspaces write-capacity update that leaves read capacity alone).
Traces: application-auto-scaling.custom-resource-registration-floor-patches-the-endpoint, application-auto-scaling.keyspaces-registration-floor-raises-the-table-write-capacity.
