# ecr__eks__logs: a pod on an EC2 managed nodegroup whose node role carries AmazonEC2ContainerRegistryReadOnly ends in phase 'Failed' instead of 'Succeeded' — the ECR pull-through-cache image pull never runs the container (1 cause)

> _Note: this issue was identified against the code base at commit `9034a7f4323bec4093511276a5153556005621ed`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
One net-new root cause in the ecr/eks/logs surface, found by behavioral replay of the single ecr__eks__logs check that no open issue owns. Everything up to the workload answers correctly: the CloudFormation stack (IAM cluster role + node role with AmazonEKSWorkerNodePolicy, AmazonEKS_CNI_Policy, AmazonEC2ContainerRegistryReadOnly and an inline ecr:BatchImportUpstreamImage/ecr:CreateRepository policy, AWS::EKS::Cluster, AWS::EKS::Nodegroup and AWS::ECR::PullThroughCacheRule) reaches CREATE_COMPLETE, ECR GetAuthorizationToken returns a proxyEndpoint, `aws eks update-kubeconfig` succeeds, a node reports Ready and `kubectl apply` of the test pod is accepted. Only the pod's own outcome diverges.

Cause 1 of 1: a pod admitted to the served cluster Kubernetes API, scheduled onto a Ready managed-nodegroup node, and whose image is an ECR pull-through-cache URI (<registry>/<cachePrefix>/amazonlinux/amazonlinux:latest) reaches the terminal phase 'Failed' instead of running its container to completion.
AWS: recorded behavior only for the cluster's Kubernetes API (the apiserver is not part of the EKS Smithy model — the model only publishes Cluster.endpoint and Cluster.certificateAuthority on DescribeCluster). Smithy (ECR): CreatePullThroughCacheRule — "Creates a pull through cache rule. A pull through cache rule provides a way to cache images from an upstream registry source in your Amazon ECR private registry"; the first pull of <cachePrefix>/<upstream repo> by a principal holding ecr:BatchImportUpstreamImage and ecr:CreateRepository materialises the mirrored private repository and imports the upstream image, after which DescribeRepositories lists <cachePrefix>/amazonlinux/amazonlinux. On real EKS, a one-shot pod with restartPolicy Never whose node role carries AmazonEC2ContainerRegistryReadOnly therefore moves status.phase Pending -> Running -> Succeeded, and its containerStatuses[0].state.terminated reports reason "Completed" with exitCode 0 for a command that exits 0. The fixed parts of that observation are the phase tokens and the terminated reason token; the pod name, container name, image URI, registry host and cache prefix are values taken from the request and from the account's registry. A genuine pull failure on AWS is never a terminal 'Failed': it is surfaced as a Pending pod with waiting reason ErrImagePull/ImagePullBackOff and a message naming the repository and the denied action.
Emulator: the pod reaches the terminal phase 'Failed'. The replayed assertion reads `pod <name> ended in phase 'Failed' instead of Succeeded -- the node role's AmazonEC2ContainerRegistryReadOnly permissions did not enable a real ECR image pull`, i.e. the emulator's cluster data plane terminates the admitted pod rather than pulling the pull-through-cache image and running the container to exit 0. No ErrImagePull/ImagePullBackOff waiting state is observed either, so the outcome is not even a faithful pull refusal.
Why: a client cannot verify that a node role's ECR permissions actually permit an image pull, and cannot use an ECR pull-through cache as a workload image source at all. Any Job, one-shot pod, init container, readiness gate or smoke test that waits for Running/Succeeded gets a hard terminal Failed, and a correctly-permissioned deployment is indistinguishable from a misconfigured one — the usual diagnosis path (a Pending pod with ImagePullBackOff naming the repository) is absent, so the failure is undiagnosable.
Fix: the pod runtime/state behind the served cluster Kubernetes API (the EKS cluster data-plane handler that admits a pod, resolves its image and computes status), together with the ECR pull-through-cache import seam it must consult: an image whose repository matches a stored pull-through cache rule prefix must be materialised into the private registry on first pull when the pulling principal is permitted, and the pod must then converge to Running and, for a terminating command, Succeeded with terminated reason Completed and exitCode 0; a pull that is genuinely not permitted must be reported as a Pending pod with waiting reason ImagePullBackOff, not as a terminal Failed.
