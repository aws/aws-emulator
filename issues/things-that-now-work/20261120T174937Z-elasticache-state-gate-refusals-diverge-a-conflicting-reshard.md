# ElastiCache state-gate refusals diverge: a conflicting reshard answers the emulator's own retry prose, and a second TestFailover answers InvalidReplicationGroupState instead of TestFailoverNotAvailableFault (2 causes)

> _Note: this issue was identified against the code base at commit `bdca4f331e3f84a5ee858acb1e0644b3d6ffabda`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyReplicationGroupShardConfiguration

## Description
Two net-new root causes in the elasticache emulator, grounded in the only two failing behavioral checks of this replay that the suite marked neither ALREADY FILED nor OWNED. Both are refusals of a state gate on a replication group that is mid-change, but each belongs to a different operation, produces a different wrong value (one a wrong MESSAGE, the other a wrong ERROR CODE as well), and lives in a different handler, so each must be closed and re-replayed on its own.

Cause 1 of 2: a second, conflicting ModifyReplicationGroupShardConfiguration on a group that is already resharding is refused with the right code but the emulator's own sentence instead of AWS's InvalidReplicationGroupState text.
  AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json) models ModifyReplicationGroupShardConfiguration with InvalidReplicationGroupStateFault (awsQueryError code InvalidReplicationGroupState, httpResponseCode 400), documented as "The requested replication group is not in the available state." Recorded behavior: with a cluster-mode-enabled group available, a first ModifyReplicationGroupShardConfiguration(NodeGroupCount=<fewer>, ApplyImmediately=true, NodeGroupsToRemove=[<shard>]) is accepted and moves the group to Status 'modifying'; a second, independently well-formed request (NodeGroupCount=<more>, ApplyImmediately=true — an increase needs no NodeGroupsToRemove/Retain) issued while the first is applying is refused HTTP 400, Error.Code 'InvalidReplicationGroupState', Error.Message 'Replication group must be in available state to modify.' That message is wholly FIXED text — it carries no request or state values at all — and it is the same sentence AWS uses for the general not-available modification gate on a replication group.
  Emulator: the refusal carries the right code but a different sentence: Error.Code 'InvalidReplicationGroupState' with Error.Message 'Could not reshard replication group. Please try again later.' That string is the emulator's own `crate::state::RESHARD_STATE_MESSAGE`, chosen deliberately (the handler comment says "The sentence is THIS operation's … rather than the general modification refusal, so the loser of a race between two reshards is told which work it lost"), so it is not a formatting slip but an authored divergence.
  Why: the message is part of the refusal's contract. A client that matches on the InvalidReplicationGroupState text to tell "the group is busy, wait for available and retry the same reshard" apart from other InvalidReplicationGroupState refusals of the same operation sees a sentence AWS never sends; worse, the emulator's wording ('Please try again later.') invites an immediate blind retry where AWS's wording states the precondition the client must wait for. Operator tooling, log scrapers and test assertions pinned to AWS's sentence all break, and a client written against the emulator's sentence breaks against AWS.
  Fix: the ModifyReplicationGroupShardConfiguration handler's state gate and the message constant it reads — the gate must answer AWS's fixed InvalidReplicationGroupState sentence for a group that is not available, not an operation-specific retry sentence.
  Traces: elasticache.shard-reconfiguration-state-machine.

Cause 2 of 2: a second TestFailover on the same node group right after an accepted one is refused with the WRONG modeled error — InvalidReplicationGroupState instead of the operation's dedicated TestFailoverNotAvailableFault — and with the wrong message.
  AWS: Smithy models TestFailover with BOTH InvalidReplicationGroupStateFault (InvalidReplicationGroupState, 400) and its own dedicated TestFailoverNotAvailableFault (awsQueryError code TestFailoverNotAvailableFault, httpResponseCode 400), documented as "The TestFailover action is not available." Recorded behavior: on an available replication group with two members and AutomaticFailoverEnabled, TestFailover(ReplicationGroupId, NodeGroupId=<existing shard>) is accepted; a second TestFailover on that same node group immediately after is refused HTTP 400, Error.Code 'TestFailoverNotAvailableFault', Error.Message 'Test failover already in progress' — wholly FIXED text, with no request or state values interpolated and no trailing period. The conflict is an internal per-node-group cooldown that is NOT visible as a Status transition: both the replication group and the node group keep reading 'available' across the refusal, and the refused call changes no member's CurrentRole. The cooldown is waited out by retrying the call itself until it stops being refused.
  Emulator: the second call is refused with a different modeled fault and a different sentence: Error.Code 'InvalidReplicationGroupState' with Error.Message 'Replication group <ReplicationGroupId> is in modifying state, not available.' (fixed parts 'Replication group ' + ' is in ' + ' state, not available.', the variable parts being the lowercased ReplicationGroupId from the request and the group's stored status — the recorded run's id value is a per-run name and is not part of the template). The handler reaches that gate at services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/test_failover.rs:260-270 because the accepted first failover put the group into 'modifying' (test_failover.rs:343, begin_transition(STATUS_MODIFYING)); the group's status gate is therefore consulted where AWS consults the per-node-group failover cooldown, and TestFailoverNotAvailableFault is only ever produced for two other conditions (automatic failover disabled, shard has no replica — test_failover.rs:279-300).
  Why: the error CODE is what a client branches on. A client that retries only TestFailoverNotAvailableFault to wait out the cooldown (the documented restore path, and the only way to proceed since no Status change marks it) gets InvalidReplicationGroupState instead, which its code treats as a different, non-retryable condition — so the retry loop never runs and the client gives up or fails hard. Conversely a client that treats InvalidReplicationGroupState as "the whole group is unusable" will abandon unrelated work. The emulator also asserts a group-wide 'modifying' state AWS does not report here, so a client polling for 'available' between failovers is given a transition AWS never shows.
  Fix: the TestFailover handler — give the operation a per-node-group failover-in-progress/cooldown gate that refuses with TestFailoverNotAvailableFault and AWS's fixed message, rather than letting the group-level status gate answer, and stop asserting a group-wide 'modifying' transition for the test failover itself.
  Traces: elasticache.test-failover-state-gating.

Neither cause is carried by an open issue. 20261114T131431Z-elasticache-transient-lifecycle-windows-are-not-observable-creating.md argues the opposite direction (transient statuses not observable at all) for other operations and carries neither check id; 20261102T083323Z-elasticache-refusals-carry-the-wrong-error-code-and.md and 20261118T043247Z-elasticache-validation-refusals-answer-the-emulator-s-own.md cover input-VALIDATION refusal wording, not these two state gates, and carry neither check id.
