# cloudtrail__cognito-identity__s3: a DENIED call made with Cognito-vended credentials is audited with no userIdentity.sessionContext.webIdFederationData, so the federation behind an AccessDenied is unauditable

> _Note: this issue was identified against the code base at commit `a5a3c6bd63789eb42e1283a455a4e127273ca01a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
Cause 1 of 1: the CloudTrail event-history record of a call signed with credentials vended by cognito-identity GetCredentialsForIdentity omits the userIdentity.sessionContext.webIdFederationData block entirely. This check exercises the REFUSAL path: a vended session whose mapped role grants nothing is correctly denied s3:ListBuckets (403/AccessDenied with the right message) and the denied record is correctly audited with errorCode AccessDenied, eventSource s3.amazonaws.com, type AssumedRole, the CognitoIdentityCredentials session ARN and the vended accessKeyId — every one of those assertions passed — but sessionContext carries no webIdFederationData, so the record says nothing about the web identity the denied session was federated from.

AWS: CloudTrail's record-contents reference documents, for a session obtained through sts:AssumeRoleWithWebIdentity (which is how Amazon Cognito vends identity-pool credentials), a userIdentity.sessionContext.webIdFederationData object beside sessionIssuer and attributes, with two members: federatedProvider — the issuer of the web identity token, the fixed string 'cognito-identity.amazonaws.com' for a Cognito-vended session — and attributes, the map of federation claims keyed by that provider name: '<provider>:aud' = the identity pool id the credentials were vended for, '<provider>:sub' = the IdentityId, '<provider>:amr' = the authentication-method reference. The member is present whether the audited call SUCCEEDED or was REFUSED: an errorCode record carries the same userIdentity as a successful one, since userIdentity describes the caller, not the outcome. A session minted by plain sts:AssumeRole carries NO webIdFederationData at all, so presence of the member is exactly what separates the two in event history. The fixed text is the member names, the literal provider 'cognito-identity.amazonaws.com' and the ':aud'/':sub'/':amr' key suffixes; the variable parts (pool id, IdentityId, amr value, developer provider name) come from the request and the emulator's identity-pool state. The Smithy model carries the record only as an opaque string, so this is a documented-behavior requirement rather than a model constraint (Smithy: com.amazonaws.cloudtrail#Event member CloudTrailEvent — "A JSON string that contains a representation of the event returned"; member AccessKeyId — the access key id of the temporary credentials the request was signed with).

Emulator: for the denied ListBuckets record looked up by the vended AccessKeyId, userIdentity.sessionContext has no webIdFederationData key whatsoever, so the check reads webIdFederationData=None where federatedProvider == 'cognito-identity.amazonaws.com' was required (AssertionError: "denied: webIdFederationData.federatedProvider must be 'cognito-identity.amazonaws.com', got None"). The shared session recorder has nowhere to hold the facts and the serializer never emits the member: services/common/src/management_events.rs RecordedSession declares no web-identity federation member, and ManagementEvent::to_cloudtrail_event_json() builds sessionContext from sessionIssuer + attributes.creationDate + sourceIdentity only. cognito-identity's GetCredentialsForIdentity — the only component that knows the pool id, the IdentityId and the AMR — records none of them in the session audit directory, so neither the allowed nor the denied record can carry them.

Why: a client auditing an identity pool cannot answer, for a REFUSED call, which end user (sub) under which pool (aud) was denied, nor whether the denied session was a guest or an authenticated one (amr). Because the member is absent rather than empty, a Cognito-federated denial is indistinguishable from a plain AssumeRole denial of the same role, so incident response on a burst of AccessDenied events cannot attribute them to end users or to a pool at all, and guest-vs-authenticated denial reporting is unexercisable.

Fix: the shared session audit state and serializer in services/common/src/management_events.rs (RecordedSession / SessionAuditDirectory and ManagementEvent::to_cloudtrail_event_json's sessionContext assembly) must carry and emit webIdFederationData{federatedProvider, attributes} for sessions that have them — on refused records as well as successful ones, since the block lives in userIdentity and is independent of errorCode — and the cognito-identity GetCredentialsForIdentity handler must populate them with provider 'cognito-identity.amazonaws.com' and the aud/sub/amr of the identity it vended for.

## Steps to Reproduce
1. Create a cognito-identity identity pool with AllowUnauthenticatedIdentities=false and a DeveloperProviderName.
2. Create an IAM role trusting cognito-identity.amazonaws.com via sts:AssumeRoleWithWebIdentity (conditions on '<provider>:aud' = the pool id and amr 'authenticated') with NO permission policy, and attach it with SetIdentityPoolRoles as 'authenticated'.
3. Mint an identity with GetOpenIdTokenForDeveloperIdentity, then call GetCredentialsForIdentity to vend temporary credentials for it.
4. Call s3:ListBuckets with those credentials and observe the expected 403 AccessDenied.
5. Grant s3:ListAllMyBuckets on the role with PutRolePolicy, vend a FRESH session for the same identity, and call s3:ListBuckets again (succeeds).
6. Call cloudtrail:LookupEvents with LookupAttributes=[{AttributeKey: 'AccessKeyId', AttributeValue: <each session's AccessKeyId>}] and json.loads the matching ListBuckets record's CloudTrailEvent.
7. Read userIdentity.sessionContext of the DENIED record: sessionIssuer and attributes.creationDate are present but webIdFederationData is absent entirely. AWS returns webIdFederationData with federatedProvider 'cognito-identity.amazonaws.com' and attributes '<provider>:aud' = the pool id and '<provider>:sub' = the IdentityId, on the refused record as well as the allowed one.
