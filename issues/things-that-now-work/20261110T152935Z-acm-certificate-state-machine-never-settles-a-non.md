# ACM certificate state machine never settles: a non-validatable requested certificate never reaches FAILED/ADDITIONAL_VERIFICATION_REQUIRED, and a DNS-validated one never reaches ISSUED (2 causes)

> _Note: this issue was identified against the code base at commit `8b7ff9be7fbfdfa6a874338015bc2fd39ac1e37f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RequestCertificate

## Description
Two net-new root causes on ACM's AMAZON_ISSUED certificate state machine, both observed as a check that exhausts its whole wall-clock budget ("Check timed out after 60.0s") because the state transition the check polls for never happens. Both must be closed before this issue is submitted.

=== Cause 1 of 2: a requested DNS-validated certificate for a name ACM cannot validate never settles into terminal Status FAILED with FailureReason ADDITIONAL_VERIFICATION_REQUIRED (failing check: acm.acm-reimport-into-an-amazon-issued-certificate-arn-rejected) ===

AWS: Smithy (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json) RequestCertificate{DomainName required -> DomainNameString @length 1..253 pattern ^(\*\.)?(((?!-)[A-Za-z0-9-]{0,62}[A-Za-z0-9])\.)+((?!-)[A-Za-z0-9-]{1,62}[A-Za-z0-9])$, ValidationMethod} -> CertificateArn; DescribeCertificate -> CertificateDetail with Status -> CertificateStatus [PENDING_VALIDATION, ISSUED, INACTIVE, EXPIRED, VALIDATION_TIMED_OUT, REVOKED, FAILED] and FailureReason -> FailureReason [NO_AVAILABLE_CONTACTS, ADDITIONAL_VERIFICATION_REQUIRED, DOMAIN_NOT_ALLOWED, INVALID_PUBLIC_DOMAIN, DOMAIN_VALIDATION_DENIED, CAA_ERROR, PCA_*, SLR_NOT_FOUND, OTHER], the latter documented as existing "only when the certificate status is FAILED". Recorded behavior for the general case the check exercises: a public certificate requested for a name ACM will not issue for (a reserved/non-validatable public name such as any *.example.com label) does NOT sit in PENDING_VALIDATION — it settles, within seconds, into the terminal Status 'FAILED' with FailureReason 'ADDITIONAL_VERIFICATION_REQUIRED', Type 'AMAZON_ISSUED', the requested DomainName echoed verbatim, no Serial (no material was ever issued) and InUseBy []. Those are modeled enum tokens and an echo of the request's own DomainName; the ARN, account id and timestamps of any one run fill the template and are not part of it.

Emulator: the certificate never becomes terminal. The check polls DescribeCertificate for (Status == 'FAILED' and DomainName present) with its own 180s budget and never satisfies it, so the check burns its entire wall clock and the suite reports "Error: Check timed out after 60.0s". Nothing downstream of that poll is reached. Hypothesis (consistent with the replay but not stated by the model): the ACM state machine has no request-failure path at all — every requested AMAZON_ISSUED certificate is parked non-terminal regardless of whether the requested names are validatable for the account, so no modeled FailureReason is ever produced.

Why: a client relying on AWS's behavior hangs instead of failing. The standard pattern — and the certificate-issued waiter — polls DescribeCertificate until the status is terminal; on AWS this request reaches FAILED with ADDITIONAL_VERIFICATION_REQUIRED, which tells the caller the names need manual verification and that it must stop. Against the emulator the caller cannot distinguish "still validating" from "will never issue", and code that branches on FailureReason reads None for a field AWS guarantees once Status is FAILED. It also makes a whole class of negative scenarios unreachable: this check's real subject is that ImportCertificate(CertificateArn=<an AMAZON_ISSUED ARN>) must be refused with ResourceNotFoundException and the message "The certificate ARN <CertificateArn> is not an imported certificate ARN." (fixed text; the only variable part is the ARN taken from the request), while the byte-identical payload re-imports successfully into an IMPORTED ARN and leaves the managed certificate's Type/Status/FailureReason/Serial/InUseBy untouched. None of that is ever exercised because the setup never produces a terminal managed certificate.

Fix: the ACM certificate state machine in the acm service crate — the RequestCertificate handler's validation/issuance driver and the stored certificate state that DescribeCertificate projects. A requested certificate whose names ACM cannot validate for the account must settle into Status 'FAILED' with a populated FailureReason ('ADDITIONAL_VERIFICATION_REQUIRED' for a name requiring manual verification), keep Type 'AMAZON_ISSUED', hold no Serial, and stay there (a refused ImportCertificate must not restart it).

=== Cause 2 of 2: a DNS-validated certificate for a name in the account's own public hosted zone never reaches ISSUED after its validation CNAME is published (failing check: acm.dns-validated-certificate-issues-under-a-delegated-zone) ===

AWS: Smithy (acm) RequestCertificate(DomainName, ValidationMethod='DNS') -> CertificateArn; DescribeCertificate -> CertificateDetail.Status of CertificateStatus, with per-domain DomainValidation.ValidationStatus (PENDING_VALIDATION | SUCCESS | FAILED) and DomainValidation.ResourceRecord, documented as the CNAME record the requester adds to its DNS database for domain validation. AWS behavior: the certificate starts PENDING_VALIDATION and publishes a CNAME challenge in DomainValidationOptions[0].ResourceRecord (Type 'CNAME'); once that exact record resolves in a public zone the account owns, ValidationStatus becomes 'SUCCESS' and Status becomes 'ISSUED', with Type 'AMAZON_ISSUED', InUseBy [], NotBefore < NotAfter, and the ARN indexed under ListCertificates(CertificateStatuses=['ISSUED']). FAILED is reserved for a definite refusal and must then be explained by a modeled FailureReason; a correctly published CNAME for a name under the account's own delegated zone is not one of those cases (and an unpublished challenge stays PENDING_VALIDATION, only becoming VALIDATION_TIMED_OUT after 72h).

Emulator: the certificate never reaches ISSUED. The check requests the certificate, polls for the ResourceRecord, UPSERTs exactly that Name/Type/Value in the baseline zone, waits for the Route 53 change to reach INSYNC, then polls DescribeCertificate until Status leaves PENDING_VALIDATION — and the check exhausts its whole wall clock instead ("Error: Check timed out after 60.0s"), so none of the post-issuance assertions (ValidationStatus 'SUCCESS', Type 'AMAZON_ISSUED', InUseBy [], NotBefore < NotAfter, ListCertificates(ISSUED) indexing) is reached. Hypothesis: the DNS-validation resolver that should compare the published CNAME against the hosted zone and drive PENDING_VALIDATION -> ISSUED either does not run or never matches, so the transition is never taken. A previous replay of the sibling check that drives the identical helper observed the certificate settle on Status 'FAILED' and stay there with no modeled FailureReason, so the same stage can also terminate wrongly rather than stall.

Why: every scenario that needs an AWS-issued, DNS-validated certificate is unreachable. A client (or IaC tooling) that correctly waits on Status either spins to its own timeout or, in the FAILED variant, sees a definite non-retryable failure for a certificate AWS would have issued, with nothing in FailureReason to explain it, so it tears down instead of proceeding.

Fix: the ACM DNS-validation state machine in the acm service crate — the RequestCertificate handler's validation driver (the resolver that checks the published challenge CNAME against Route 53 and the transition it drives) and the CertificateDetail projection DescribeCertificate reads. A matching published record must take the per-domain ValidationStatus to 'SUCCESS' and Status to 'ISSUED', and the state machine must never settle on 'FAILED' without a modeled FailureReason.

Traces: acm.dns-validated-certificate-issues-under-a-delegated-zone.
