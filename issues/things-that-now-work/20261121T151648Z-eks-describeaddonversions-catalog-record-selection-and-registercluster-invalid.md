Cause 1 of 2: a filtered DescribeAddonVersions query returns a different add-on record at addons[0] than the catalog's, and the Marketplace productUrl for that record is in the wrong form.
  AWS: DescribeAddonVersions is GET /addons/supported-versions (Smithy: services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json; input members kubernetesVersion, addonName, types, publishers, owners, maxResults, nextToken all @httpQuery; output addons : Addons, nextToken; @paginated items=addons; errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500). Each element is an AddonInfo (members addonName, type, addonVersions, publisher, owner, marketplaceInformation, defaultNamespace), and addonVersions is the add-on's full published release history selected by the request's filters, each AddonVersionInfo carrying its own addonVersion, architecture, computeTypes, compatibilities (clusterVersion / platformVersions / defaultVersion) and the requiresConfiguration / requiresIamPermissions flags (both @default false). For a Marketplace-owned add-on, MarketplaceInformation.productUrl is documented as "The product URL from the Amazon Web Services Marketplace" — the catalog's published URL for that productId. The response status is 200; no error class is at stake.
  Emulator: answers 200, but the add-on record the catalog publishes at addons[0] for the requested filter set is simply not present — a different, synthesised record is served in its place, and where a Marketplace record is served its marketplaceInformation.productUrl is a different URL form than the catalog publishes for the same product. The served record also collapses the multi-release version history (consecutive published releases, newest flagged defaultVersion true and the older ones false, each with its own compatibilities and computeTypes) into synthesised rows.
  Why: this listing is how a client discovers which add-ons exist and which versions of each may be installed on a given cluster version. With a different record served for the requested filter, a client that pins, upgrades or rolls back an add-on to a named version is told that version does not exist, and an installer that enumerates available add-ons for a cluster never sees the ones the catalog actually publishes. A client that follows marketplaceInformation.productUrl for a subscription or legal check lands on a URL that does not identify the product.
  Fix: the add-on catalog data behind DescribeAddonVersions' handler, and that handler's filter selection (kubernetesVersion / addonName / types / publishers / owners must select rows from the catalog rather than be dropped), plus the Marketplace productUrl the catalog record carries.
  Traces: eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni#task#20 (representative; 1 affected step).

Cause 2 of 2: RegisterCluster's invalid-provider refusal message omits the member path AWS names, reporting the bare member name instead.
  AWS: RegisterCluster is POST /cluster-registrations with required input members name and connectorConfig : ConnectorConfigRequest, whose own members roleArn and provider are both @required; provider targets the enum ConnectorConfigProvider with values EKS_ANYWHERE, ANTHOS, GKE, AKS, OPENSHIFT, TANZU, RANCHER, EC2, OTHER (Smithy, same model file). A value outside that enum is refused with HTTP 400 InvalidParameterException (modeled on RegisterCluster, httpError 400, member message). The recorded refusal's message names the offending member by its full request path: the fixed text is "The value of connectorConfig.provider must be one of [" + the enum's values, comma-separated in model order + "]" — i.e. the variable part is the member PATH within the request (connectorConfig.provider) and the enum value list from the model; no value from the request or from emulator state appears in it.
  Emulator: answers the correct 400 and the correct InvalidParameterException class, but words the message "provider must be one of [EKS_ANYWHERE, ANTHOS, GKE, AKS, OPENSHIFT, TANZU, RANCHER, EC2, OTHER]" — it drops the leading "The value of " and qualifies the member by its bare name "provider" rather than its path "connectorConfig.provider".
  Why: the message is the only thing that tells a caller WHICH member of a nested request structure was rejected. A bare "provider" is ambiguous in a request that nests it inside connectorConfig, so an operator or a client that parses or asserts on the refusal text cannot attribute the fault to the right field, and tooling that matches AWS's wording treats the refusal as an unrecognised error.
  Fix: the RegisterCluster input validation that builds the InvalidParameterException message (it must qualify the member by its full request path and use AWS's "The value of <path> must be one of [...]" wording).
  Traces: eks-register-cluster-request-shape-validation#task#2.

## Resolution
Cause 2 is fixed and replays clean: `provider_must_be_one_of_message` words the refusal "The value of connectorConfig.provider must be one of [...]" with the enum's values in model order, pinned by `tests/all/value_set_sentence.rs`, and the replay key `eks|RegisterCluster|4xx->4xx|$.message` reports fixed.

Cause 1 is fixed where the emulator was answering with values of its own: a vendor's Marketplace rebuild no longer inherits the rebuilt add-on's first offered Kubernetes version (so a version-filtered listing names only add-ons whose own listing publishes a build for that version, which is what put the wrong record at `addons[0]`), and a listing whose published product page the catalog cannot cite now reports no `marketplaceInformation.productUrl` instead of an address built from an identifier this emulator had minted. Both are pinned by `tests/all/addon_catalog_record_selection.rs` and `tests/all/marketplace_listing_reference_data.rs`.
