# appsync: 3 net-new causes — CreateFunction picks the wrong BadRequestException message for runtime+VTL, an AssociateMergedGraphqlApi merge never leaves MERGE_SCHEDULED, and GetSchemaCreationStatus details undercounts the created types by one

> _Note: this issue was identified against the code base at commit `16df41068e9592847de76789eb93312b3e770273`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateFunction, AssociateMergedGraphqlApi, GetSchemaCreationStatus

## Description
Three independent net-new root causes in the appsync control plane, all surviving the suite's ALREADY-FILED/OWNED marks. All three are service=appsync; each must be closed before this issue is submitted.

Related open issues that do NOT cover these: 20261112T064707Z-appsync-appsync-js-code-diagnostics-and-cachingkeys-validation.md covers APPSYNC_JS code diagnostics (codeErrors text / lint rules) on CreateFunction, not which refusal message wins when a runtime is combined with VTL templates (cause 1). 20261029T200818Z-appsync-source-api-association-projection-and-merge-status.md covers the association PROJECTION and, in its causes 8-9, the UpdateSourceApiAssociation auto-merge-reconfigure path left at MERGE_SCHEDULED; cause 2 below is the plain AssociateMergedGraphqlApi path for a source API that DOES have a schema, polled through GetSourceApiAssociation, which never settles at all. 20261115T000000Z-appsync-getschemacreationstatus-omits-details-for-a-not-applicable-schema.md covers a MISSING details member on the NOT_APPLICABLE path; cause 3 is a present-but-wrong count on the SUCCESS path. 20261111T012528Z-appsync-2-net-new-causes-startschemacreation-refuses-an.md covers StartSchemaCreation's refusal code for an unresolvable apiId, a different leg.

Cause 1 of 3 — CreateFunction with runtime=APPSYNC_JS plus a VTL requestMappingTemplate is refused with the WRONG BadRequestException message (the code-required message instead of the templates-incompatible-with-runtime message).
AWS: Smithy: CreateFunction POST /v1/apis/{apiId}/functions, errors BadRequestException (httpError 400); input carries both runtime (AppSyncRuntime, whose doc states "if a runtime is specified, code must also be specified") and requestMappingTemplate/responseMappingTemplate (MappingTemplate). Recorded behavior: when a request supplies a runtime AND a VTL mapping template, AWS refuses on the incompatibility, not on the missing code: BadRequestException with message "Request and Response mapping templates can not be supplied with provided runtime." — entirely fixed text, no variable parts. The "Invalid code given. Code is required when a runtime is specified." message is AWS's refusal for the DIFFERENT input class of a runtime with neither code nor templates; AWS evaluates the template/runtime conflict first.
Emulator: answers BadRequestException with message 'Invalid code given. Code is required when a runtime is specified.' for the runtime+requestMappingTemplate request — right error code and status, wrong message, because its validation order checks code-presence before the runtime/VTL conflict.
Why: a client (or IaC/codegen tool) that branches on the refusal message is told to add `code` to a function that must instead drop its VTL templates, so the suggested remediation produces a second refusal; error-message assertions in deployment tooling break.
Fix: CreateFunction's input validation (shared with UpdateFunction and the resolver write path) — detect runtime-plus-mapping-template first and raise BadRequestException "Request and Response mapping templates can not be supplied with provided runtime.", keeping the code-required refusal for runtime-without-code-or-templates.
Traces: appsync.create-ops-invalid-input-bad-request.

Cause 2 of 3 — a source-API association created by AssociateMergedGraphqlApi never reaches a terminal merge status: it stays MERGE_SCHEDULED indefinitely.
AWS: Smithy: AssociateMergedGraphqlApi POST /v1/sourceApis/{sourceApiIdentifier}/mergedApiAssociations returns SourceApiAssociation; SourceApiAssociationStatus values are MERGE_SCHEDULED, MERGE_IN_PROGRESS, MERGE_SUCCESS, MERGE_FAILED, AUTO_MERGE_SCHEDULE_FAILED, DELETION_* . Recorded behavior: the association starts MERGE_SCHEDULED, advances through MERGE_IN_PROGRESS and settles to a TERMINAL status (MERGE_SUCCESS for a source API that defines types, MERGE_FAILED / AUTO_MERGE_SCHEDULE_FAILED otherwise) within seconds, which is what GetSourceApiAssociation reports; while the merge is in flight DisassociateMergedGraphqlApi is refused ConcurrentModificationException, and only after it settles is a disassociate accepted.
Emulator: GetSourceApiAssociation still reports sourceApiAssociationStatus 'MERGE_SCHEDULED' after 180 s of polling (checked every 5 s) for a merged API associated with a source API that has an active schema — the scheduled merge is never executed, so no terminal status is ever reached.
Why: every client that waits for a merge to settle before using the merged API (or before disassociating) hangs forever; the whole MERGE_IN_PROGRESS/MERGE_SUCCESS/MERGE_FAILED half of the association state machine is unreachable, and so is the dependent rejection contract — DisassociateMergedGraphqlApi called with an associationId that belongs to a different sourceApiIdentifier must answer NotFoundException with message "No source API association was found" (fixed text, no variable parts) and leave the real association intact, which this run never got to exercise.
Fix: the schema-merge worker behind AssociateMergedGraphqlApi / association state — a scheduled merge must actually run and drive the association to a terminal SourceApiAssociationStatus (setting lastSuccessfulMergeDate only on MERGE_SUCCESS).
Traces: appsync.merged-api-disassociate-wrong-source-rejected.

Cause 3 of 3 — GetSchemaCreationStatus details undercounts the created types by one on the SUCCESS path.
AWS: Smithy: GetSchemaCreationStatus GET /v1/apis/{apiId}/schemacreation returns status (SchemaStatus, here SUCCESS) and details (String). Recorded behavior: on success details is the template "Successfully created schema with <N> types." — fixed text "Successfully created schema with " and " types.", with N a value derived from the submitted SDL: the declared object types plus the Query root type plus one built-in type. For a definition declaring 300 object types and a Query type, N is 302.
Emulator: status SUCCESS is right, but details is 'Successfully created schema with 301 types.' for that same definition — the count is one short, i.e. the built-in type AWS includes is not counted. (301/302 are the values this request's SDL produces; the requirement is the counting rule, not the literal.)
Why: a client that parses the type count out of details to confirm the schema it uploaded was fully ingested concludes a type was dropped, and schema-drift/validation tooling built on that number reports a false mismatch on every single API.
Fix: the schema-creation job's details template in the GraphQL schema state — count the declared object types plus Query plus the built-in type AWS includes when formatting "Successfully created schema with <N> types.".
Traces: appsync.start-schema-creation-conflict-in-progress.
