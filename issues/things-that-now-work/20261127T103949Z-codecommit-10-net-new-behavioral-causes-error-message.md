# CodeCommit: 10 net-new behavioral causes — error-message templates for five refusal classes diverge, a partial comment Location is accepted, a BEFORE-side comment is refused with the wrong error class, and the git smart-HTTP transport omits HEAD / serves a non-XML 401 / never authenticates the credential-helper push

> _Note: this issue was identified against the code base at commit `ab3264a14a30dede061951437467343aaef14e5b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PostCommentForComparedCommit

## Description
Ten net-new root causes in the codecommit crate, every one grounded in a failing behavioral check the replay report left unmarked (not ALREADY FILED, not OWNED). Related-but-not-covering open issues are named per cause.

Cause 1 of 10: IdempotencyParameterMismatchException is serialized with an emulator-authored message where AWS sends none.
AWS: Smithy models IdempotencyParameterMismatchException (client, httpError 400) on PostCommentForComparedCommit, PostCommentForPullRequest and PostCommentReply, each of which takes clientRequestToken (@idempotencyToken). Recorded behavior: reusing a clientRequestToken with different parameters (changed or new content) is refused with HTTP 400, error code IdempotencyParameterMismatchException and NO Message member at all — the checks read err.get('Message', '') and require the empty string. The code and status are the requirement together with the ABSENCE of a message.
Emulator: the code and 400 status are right, but the body carries Message 'the client request token <clientRequestToken> was used in a previous request with different parameters'. The fixed text is the emulator's own prose and the token is echoed from the request; neither belongs in an AWS response for this error class.
Why: a client or differential test that compares the serialized error (code + message) against AWS sees every idempotency-mismatch path diverge, and tooling that treats a present Message as the authoritative human-readable reason surfaces text AWS never produces.
Fix: the error-serialization path that builds IdempotencyParameterMismatchException in the codecommit crate's comment handlers (src/ops/post_comment_for_compared_commit.rs, post_comment_for_pull_request.rs, post_comment_reply.rs) and the shared idempotency-token check they call — the error must be emitted with no Message member.
Traces: codecommit.comment-token-reused-with-changed-content-rejected, codecommit.comment-reply-token-reused-with-changed-content-rejected, codecommit.comment-reply-token-reused-with-new-content-rejected, codecommit.compared-commit-comment-token-reused-with-new-content-rejected, codecommit.pull-request-comment-token-reused-with-changed-content-rejected.

Cause 2 of 10: InvalidFilePositionException's message is not AWS's fixed line-number template.
AWS: Smithy models InvalidFilePositionException (client, httpError 400) on PostCommentForComparedCommit; Location.filePosition is 1-based (https://docs.aws.amazon.com/codecommit/latest/APIReference/API_Location.html). A filePosition of 0 or a negative value is refused with HTTP 400 InvalidFilePositionException and the entirely fixed message 'The line number is not valid. Either the line number was 0 or a negative number. Check to make sure you've included the positive value of the line number in the file for the comment, and try again.' — no part of it is request-derived.
Emulator: code and status are right; the message is 'the position is not valid: a line number starts at 1'.
Why: the message is a requirement of this error class and every 0/negative-line rejection diverges from AWS, so clients matching on it (and users reading it) get text AWS never emits.
Fix: the message construction for InvalidFilePositionException in the codecommit crate's Location validation used by src/ops/post_comment_for_compared_commit.rs (and the same validation shared with post_comment_for_pull_request.rs).
Traces: codecommit.compared-commit-comment-line-zero-rejected.

Cause 3 of 10: InvalidPathException's message does not name the specific path defect and omits AWS's limits sentence.
AWS: Smithy models InvalidPathException (client, httpError 400) on PostCommentForComparedCommit. Recorded behavior: the message has a fixed first sentence, a fixed second sentence naming the defect, and a fixed trailing pointer — for a path that climbs out of the tree: 'The path is not valid. The path is a relative path. For more information about limitations for file paths, see Limits in the AWS CodeCommit User Guide.'; for a path with an empty segment: 'The path is not valid. The path contains an empty directory name. For more information about limitations for file paths, see Limits in the AWS CodeCommit User Guide.' The whole message is fixed text; the offending path is NOT interpolated.
Emulator: code and status are right; the message is 'the path <filePath> is not valid' — one template for both defects, echoing the request's path and dropping the defect sentence and the limits pointer.
Why: a caller cannot tell which path rule it broke, and the two distinct AWS messages collapse into one.
Fix: the path-validation rejection in the codecommit crate's comment Location validation (src/ops/post_comment_for_compared_commit.rs and the shared path validator), emitting the per-defect sentence AWS uses.
Traces: codecommit.compared-commit-comment-path-with-parent-or-empty-segment-rejected.

Cause 4 of 10: a BEFORE-side comment on a file that exists only in the after commit is refused with the wrong error class.
AWS: Smithy models both InvalidRelativeFileVersionEnumException and PathDoesNotExistException (client, httpError 400) on PostCommentForComparedCommit. For a Location whose filePath is absent from the requested relativeFileVersion side of the comparison, AWS answers HTTP 400 InvalidRelativeFileVersionEnumException with the fixed message 'You can only comment on existing files. You attempted to comment on a file that does not exist in this portion of the comparison between commits: BEFORE. Either the file has been deleted, or has not been added to the repository at the time of this commit. Try commenting on the file in the other commit portion of the comparison.' — the only variable part is the side name (BEFORE/AFTER) from the request.
Emulator: answers HTTP 400 PathDoesNotExistException with 'the path <filePath> does not exist in the BEFORE version of the comparison'.
Why: the error code is the thing clients branch on; PathDoesNotExistException says the path is unknown to the comparison, while AWS says the path exists but not on the side the caller named — a retry on the other side is the documented remedy, and a client cannot derive it from the emulator's code.
Fix: the side-resolution branch of the comment Location validation in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/post_comment_for_compared_commit.rs — choose InvalidRelativeFileVersionEnumException (with AWS's message) when the path exists in the comparison but not on the requested side.
Traces: codecommit.compared-commit-before-side-comment-on-added-file-rejected.

Cause 5 of 10: a half-specified comment Location is ACCEPTED instead of refused with InvalidFileLocationException.
AWS: Smithy models InvalidFileLocationException (client, httpError 400) on PostCommentForComparedCommit and PostCommentForPullRequest; Location may anchor to a whole file (filePath only) or to a line, in which case BOTH filePosition and relativeFileVersion are required (https://docs.aws.amazon.com/codecommit/latest/userguide/how-to-commit-comment.html). A filePosition without relativeFileVersion is refused with HTTP 400 InvalidFileLocationException and the fixed message 'RelativeFileVersion is not provided'; a relativeFileVersion without filePosition with the fixed message 'FilePosition is not provided'. No comment is created in either case.
Emulator: both calls return HTTP 200 and create a comment whose location echoes the partial Location (e.g. {'filePath': 'src/main.go', 'filePosition': 3} with no relativeFileVersion), so the comment is then listed on the comparison/pull request.
Why: half-anchored comments are persisted and served back; a client that relies on the rejection to catch a malformed anchor silently stores comments that cannot be rendered on either side of the diff, and the two modeled refusals are unreachable.
Fix: the Location validation shared by services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/post_comment_for_compared_commit.rs and src/ops/post_comment_for_pull_request.rs — require the position/side pair before any comment state is written.
Traces: codecommit.compared-commit-line-comment-missing-half-of-location-rejected, codecommit.pull-request-line-comment-location-missing-version-or-position-rejected.

Cause 6 of 10: CommentContentSizeLimitExceededException's message is not AWS's limit template.
AWS: Smithy models CommentContentSizeLimitExceededException (client, httpError 400) on PostCommentForPullRequest (and the sibling comment operations). Recorded behavior for content one character over the 10240-character comment limit: HTTP 400 with the message 'The size limit for comments is 10240' — fixed text 'The size limit for comments is ' followed by the service's comment-size limit.
Emulator: code and status are right; the message is 'the comment is too large: comments are limited to 10240 characters'.
Why: the message is part of this refusal's contract; callers that parse the limit out of it, and differential comparisons, diverge on every oversized comment.
Fix: the comment-size rejection message in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/post_comment_for_pull_request.rs and the shared comment-content validation.
Traces: codecommit.pull-request-comment-over-10240-characters-rejected.

Cause 7 of 10: PutFile's FileContentSizeLimitExceededException message is a one-line stub instead of AWS's guidance template.
AWS: Smithy PutFile takes fileContent (@required, blob, @length max 6291456) and models FileContentSizeLimitExceededException (client, httpError 400). For fileContent one byte over 6 MiB the refusal message is the fixed text 'The maximum file size for adding a file from the AWS CodeCommit console or using the PutFile API is 6 MB. For files larger than 6 MB but smaller than 2 GB, use a Git client.'
Emulator: code and status are right; the message is 'The file cannot be added because it is too large.'
Why: the message is the only place AWS tells the caller the limit and the supported alternative (a git client); clients and users relying on it get neither.
Fix: the size-limit rejection message in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/put_file.rs.
Traces: codecommit.put-file-one-byte-over-six-mib-rejected.

Cause 8 of 10: the git smart-HTTP receive-pack advertisement omits HEAD once the repository has a default branch.
AWS: recorded behavior only (the Smithy model does not describe the git transport); references https://docs.aws.amazon.com/codecommit/latest/userguide/setting-up-gc.html and https://git-scm.com/docs/http-protocol. GET <cloneUrlHttp>/info/refs?service=git-receive-pack on a repository whose only branch was just created by a receive-pack advertises TWO refs at that commit: 'HEAD' and 'refs/heads/main' (HEAD resolves to the default branch), after the '# service=git-receive-pack' pkt-line and its flush.
Emulator: the advertisement lists only {'refs/heads/main': <commit>}; HEAD is absent.
Why: HEAD in the advertisement is how a git client learns the repository's default branch; without it a clone cannot pick a branch to check out and tooling that reads the advertised HEAD to resolve the default branch sees none, even though GetRepository reports one.
Fix: the ref-advertisement builder of the CodeCommit git smart-HTTP transport (the info/refs handler in the codecommit crate's git transport module) — emit the symbolic HEAD entry resolved to the default branch alongside the branch refs.
Traces: codecommit.smart-http-receive-pack-push-advances-branch-tip (the receive-pack that created the branch reported 'unpack ok'/'ok refs/heads/main', so only the advertisement diverges).

Cause 9 of 10: an unauthenticated git smart-HTTP request is refused with a text/plain body instead of AWS's XML error document.
AWS: recorded behavior only. GET <cloneUrlHttp>/info/refs?service=git-receive-pack and POST <cloneUrlHttp>/git-receive-pack with no credentials answer HTTP 401 with Content-Type 'text/xml', a body whose root element is the error code — <NotAuthorizedException><Message>SPNEGO token required</Message></NotAuthorizedException> (both the element name and the message are fixed text) — and the challenge header WWW-Authenticate: Basic realm="". With a wrong password the same two requests answer HTTP 403, Content-Type 'text/xml' and <UnrecognizedClientException><Message>The security token included in the request is invalid.</Message></UnrecognizedClientException>.
Emulator: the 401 status is right, but Content-Type is 'text/plain; charset=utf-8', so no XML error document is served and the check cannot parse a code or message out of it; the challenge header and the 403/wrong-password leg behind the assertion are consequently unverified.
Why: an unmodified git client needs the Basic challenge to know to supply HTTPS Git credentials, and every CodeCommit client that parses the XML error body of a git-transport refusal (to distinguish 'no credentials' from 'bad credentials') cannot classify the failure at all.
Fix: the refusal serializer of the CodeCommit git smart-HTTP transport (the auth guard in front of the info/refs and git-receive-pack handlers) — emit the text/xml error document with the modeled code and message plus the Basic challenge header.
Traces: codecommit.smart-http-receive-pack-without-valid-login-rejected.

Cause 10 of 10: a git push over the announced cloneUrlHttp using the AWS credential helper is never authenticated, so the 6 MiB blob/file retrieval boundary is unobservable.
AWS: recorded behavior only (https://docs.aws.amazon.com/codecommit/latest/userguide/temporary-access.html). 'git -c credential.helper="!aws codecommit credential-helper $@" -c credential.UseHttpPath=true push <cloneUrlHttp> main:main' exits 0; the pushed branch then reads back through GetBranch, and GetBlob/GetFile serve objects at or under 6 MiB while an object one byte over is refused with FileTooLargeException ('This object exceeds the max size for retrieval via the API. Use the git client to retrieve this file.').
Emulator: git exits 128 before any object is transferred with 'fatal: could not read Username for \'<cloneUrlHttp>\': terminal prompts disabled' (fixed git text; the URL is a per-run value) — the request was answered with a challenge the credential helper's credentials never satisfied, so the push never authenticates and neither check reaches a single GetBlob/GetFile assertion. Hypothesis: the same git-transport auth guard as Cause 9 — a 401 that does not carry the Basic challenge git needs to hand the helper's user/password back — is what git reports as a missing username.
Why: the documented credential-helper push path is unusable, and with it the whole large-object story (git pushes an object over 6 MiB, the API then refuses to serve it and the git client must be used) cannot be exercised by any client.
Fix: the auth guard and challenge of the CodeCommit git smart-HTTP transport (same seam as Cause 9), so a SigV4 credential-helper push is accepted, plus the FileTooLargeException path in src/ops/get_blob.rs / src/ops/get_file.rs that the push gates.
Related: open issues 20261124T051640Z-codecommit-credential-helper-git-transport-the-announced-cloneurlhttp.md, 20261122T211920Z-codecommit-git-transport-no-clone-fetch-or-push.md and 20261025T040000Z-codecommit-announced-clone-url-is-served-with-an-untrusted-certificate.md all record git-transport unreachability, but their replay keys carry other check ids and none lists codecommit.get-blob-over-six-mib-pushed-by-git-rejected or codecommit.get-file-on-git-pushed-file-over-six-mib-rejected; the failure recorded here is also a different symptom (an authentication challenge git cannot satisfy, not a TLS trust failure).
Traces: codecommit.get-blob-over-six-mib-pushed-by-git-rejected, codecommit.get-file-on-git-pushed-file-over-six-mib-rejected.
