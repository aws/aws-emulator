# lambda: 3 net-new causes — CloudFormation alias RoutingConfig is sent to Lambda in CFN list form (400 "expected object start, got array start"), a handler cannot start a thread, and a function URL event's domainPrefix/apiId do not match the host the URL is served on

> _Note: this issue was identified against the code base at commit `b19562f8ca9de9711e1cde2d426cb1fc8bc6040d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateAlias

## Description
Three distinct net-new root causes in the Lambda service. Numbered; each carries its own failing check ids.

Cause 1 of 3: a CloudFormation AWS::Lambda::Alias whose `RoutingConfig.AdditionalVersionWeights` is the CFN list form is forwarded to the Lambda API unconverted, so UpdateAlias refuses it with HTTP 400 and the stack rolls back — a valid alias traffic-shifting configuration can never be deployed.
AWS: CloudFormation's AWS::Lambda::Alias takes `RoutingConfig.AdditionalVersionWeights` as a LIST of `{FunctionVersion, FunctionWeight}` objects, while the Lambda API models it as a MAP of version -> weight (Smithy: lambda AliasRoutingConfiguration.AdditionalVersionWeights is a map; key AdditionalVersion pattern `^[0-9]+$` length 1-1024, value Weight double range 0.0-1.0). The resource handler converts the list into that map, so UpdateAlias succeeds and the stack reaches UPDATE_COMPLETE with GetAlias reporting `FunctionVersion` = the primary and `AdditionalVersionWeights` = {<other version>: 0.5}. A weight naming the alias's OWN primary version is the only rejected case, and Lambda refuses it with `InvalidParameterValueException` and the message `Invalid function version <version>. Function version <version> is already included in routing configuration.` (fixed text; `<version>` is the version number from the request) — which the emulator already produces correctly for a direct UpdateAlias call.
Emulator: every CFN alias update that carries a RoutingConfig fails the resource, including the valid one that weights a DISTINCT version. The stack reaches `UPDATE_ROLLBACK_COMPLETE` with `Alias UPDATE_FAILED: Resource handler returned message: "expected object start, got array start (Service: Lambda, Status Code: 400, ...)" ... HandlerErrorCode: InvalidRequest` — a JSON-deserialization refusal produced because the array was passed straight through to the map-typed member. The rejection of the weight-on-primary phase therefore happens for the wrong reason, and the positive control (weight on another version, which must reach UPDATE_COMPLETE) is refused too.
Why: alias traffic shifting — the mechanism behind every canary/linear Lambda deployment — is undeployable through CloudFormation. A template that is valid on AWS rolls back, and a client debugging it is handed a wire-level parse error that names no template property.
Fix: the CloudFormation AWS::Lambda::Alias resource handler's property mapping — convert each `AdditionalVersionWeights` list entry's `FunctionVersion`/`FunctionWeight` into the Lambda API's version->weight map before calling CreateAlias/UpdateAlias (and keep Lambda's own InvalidParameterValueException as the only refusal for a weight on the alias's primary version).
Traces: lambda.deploy-lambda-alias-weight-on-primary-version-rejected

Cause 2 of 3: a handler cannot start a thread, so Invoke answers FunctionError 'Unhandled' for any function whose module starts one — and with it the whole internal-extension/Telemetry API surface is unobservable.
AWS: a managed runtime's execution environment is an ordinary Linux sandbox; `threading.Thread(...).start()` at module scope works, which is how an internal extension registers at `/2020-01-01/extension/register` during Init and then drains `/2020-01-01/extension/event/next` on a background thread. A RequestResponse Invoke of such a function answers StatusCode 200 with no `FunctionError` header. (Recorded behavior only: threads are not an API surface.)
Emulator: Invoke answers with `FunctionError: 'Unhandled'` and the log carries `[ERROR] RuntimeError: a Lambda function in this emulator cannot start a thread` with the handler's own frame — so the probing invoke never runs, and the Telemetry API `PUT /2022-07-01/telemetry` Subscribe contract behind it (its four validation refusals and the `"OK"` body of a valid subscribe) can never be reached.
Why: any handler that uses a background thread — an internal extension, a telemetry drainer, a concurrent client, a watchdog — fails outright with an error AWS never produces. Related but distinct: open issue 20261108T000000Z-lambda-a-handler-cannot-start-a-child-process.md covers child processes (`subprocess`/`os.popen`) only; threads are refused by a separate guest-runtime guard and no open issue names them.
Fix: the lambda guest Python runtime's `threading` support in the execution environment (the same component family as the child-process refusal in services/service-com-amazonaws-lambda-awsgirapiservice/src/state/execution/), plus the extension/telemetry endpoints the thread drives.
Traces: lambda.telemetry-api-subscribe-validation-rejected-with-exact-error-bodies

Cause 3 of 3: a function URL's payload-2.0 event reports a `requestContext.domainPrefix`/`apiId` that is not the first DNS label of the host the URL is published and served on.
AWS: a function URL is served at `https://<url-id>.lambda-url.<region>.on.aws`, and the payload-2.0 event's `requestContext.domainName` is that host while `requestContext.domainPrefix` and `requestContext.apiId` are both the URL id — i.e. the first label of `domainName`. The three agree by construction. (Smithy: lambda FunctionUrlConfig.FunctionUrl, "The HTTP URL endpoint for your function", length 40-100; the event's requestContext fields are documented in the function-URL invocation reference, not modelled — recorded behavior only for the agreement rule.)
Emulator: `domainName` does equal the host the request was made to, but `domainPrefix` and `apiId` are the 32-hex URL id, which is not that host's first label, so the identity `domainPrefix == domainName.split('.')[0] == apiId` that holds on AWS is broken. Verbatim: "domainPrefix and apiId must be the URL id, got '8f389f64ce054c968458d6bcb95b943a'/'8f389f64ce054c968458d6bcb95b943a'" (the id is a per-run value; the requirement is the agreement, not the literal).
Why: a handler or framework that reconstructs its own public origin from the event (`https://{domainPrefix}.lambda-url.{region}.on.aws`, or `domainPrefix` as a tenant/stage key) builds an address that is not the one it is reached on, and any assertion tying the event's apiId to the URL it was invoked through fails.
Fix: the function-URL data plane's payload-2.0 event builder together with the host the URL listener is published on — the published FunctionUrl's authority must carry the URL id as its first label, and `requestContext.domainName`/`domainPrefix`/`apiId` must be derived from that same authority. Related open issue that does not own this check: 20261109T152222Z-apigateway-lambda-function-urls-are-published-on-lambda.md (Cause 1, the published function-URL host).

Then UpdateStack adding to the alias `RoutingConfig: {AdditionalVersionWeights: [{FunctionVersion: <v1>, FunctionWeight: 0.5}]}` (expect UPDATE_ROLLBACK_COMPLETE, caused by Lambda's InvalidParameterValueException naming the version already in the routing configuration), then UpdateStack publishing a second version and weighting THAT version 0.5 (expect UPDATE_COMPLETE and GetAlias reporting {<v2>: 0.5}). Observed: both updates fail the Alias resource with a 400 "expected object start, got array start".

Observed FunctionError 'Unhandled' with RuntimeError "a Lambda function in this emulator cannot start a thread".
Cause 3: CreateFunction + CreateFunctionUrlConfig (AuthType AWS_IAM) + AddPermission for the caller; GET the published FunctionUrl with a SigV4-signed request and have the handler echo its event. Compare requestContext.domainName/domainPrefix/apiId against the host of the URL that was invoked.
