# ds: 3 net-new causes — the password @pattern refusal is InvalidParameterException instead of ValidationException, EnableSso with credentials always answers AuthenticationFailedException, and ten control-plane flows never reach a verdict inside the check budget

> _Note: this issue was identified against the code base at commit `7eb0bd3bda5e5fd14f4b01ea8dd2daf93fb4b55d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDirectory

## Description
Three independent, net-new root causes in the Directory Service (ds) control plane, found by replaying the behavioral suite against the emulator built from this checkout. All three must be closed before submitting. None is a scaffold stub: the service answers in every case (the suite marks stub-blocked checks separately).

Cause 1 of 3: a Password that violates the modeled @pattern is refused as a modeled service error with no constraint message, instead of the framework-level ValidationException whose body names the member and the pattern. Reproduces on CreateDirectory, and the same check asserts the byte-identical body for CreateMicrosoftAD (the constraint travels with the Password shape, not the entry point).
AWS: Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416) — CreateDirectoryRequest$Password targets Password, is @required and @sensitive and carries @pattern "^(?=^.{8,64}$)((?=.*\\d)(?=.*[A-Z])(?=.*[a-z])|(?=.*\\d)(?=.*[^A-Za-z0-9\\s])(?=.*[a-z])|(?=.*[^A-Za-z0-9\\s])(?=.*[A-Z])(?=.*[a-z])|(?=.*\\d)(?=.*[A-Z])(?=.*[^A-Za-z0-9\\s]))^" — read as a rule: length 8-64 and at least three of the four classes digit/upper/lower/symbol. CreateDirectory's modeled errors are ClientException, DirectoryLimitExceededException, InvalidParameterException, ServiceException; ValidationException is NOT among them, so the constraint refusal is the protocol-level one the front door raises before the handler runs. Recorded response: HTTP 400, error code ValidationException, message "1 validation error detected: Value at 'password' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>". Message anatomy — fixed text "1 validation error detected: Value at '" ... "' failed to satisfy constraint: Member must satisfy regular expression pattern: "; variable parts are the member path taken from the request ('password') and the regex taken from the model's @pattern for that member. Password is @sensitive, so the offending value is elided: "Value at 'password'", never "Value '<secret>' at 'password'". Conversely a password that SATISFIES the pattern (three classes, e.g. upper+lower+digit, no symbol) must clear validation and die later at resource resolution — ClientException "Invalid VPC ID. : RequestId: <RequestId>" for an absent VPC — so demanding a symbol is over-strict.
Emulator: the refusal is raised by the handler as the modeled InvalidParameterException.
Why: a client branches on the error class and on the diagnostic. ValidationException is the SDK's protocol/constraint error handled by generic input-validation code, while InvalidParameterException is a modeled Directory Service fault surfaced as a service error, so typed catch blocks and retry classification take the wrong path; and without the "N validation error(s) detected" message naming 'password' and the pattern, a caller cannot tell the user the admin password is too weak or distinguish it from any other invalid parameter.
Fix: CreateDirectory's (and CreateMicrosoftAD's) request validation — the @pattern check on Password belongs to the shared request-constraint validator that runs before the handler and emits the ValidationException body, not to a handler-level InvalidParameterException; the @sensitive elision belongs in that same shared constraint serializer.
Traces: ds.create-directory-rejects-noncompliant-password. Related open issues that do NOT cover this check: 20261110T140406Z-ds-createmicrosoftad-password-pattern-refusal-is-raised-as.md carries the same root cause but is keyed on the WIRE corpus and on CreateMicrosoftAD only — no replay key for this behavioral check and no mention of CreateDirectory; 20261109T135909Z-ds-3-net-new-causes-every-pattern-validationexception.md covers the missing ^/$ anchors INSIDE an otherwise correct ValidationException body, not the error class or the absent message. A fixer should land them together.

Cause 2 of 3: EnableSso refuses EVERY request carrying UserName/Password with AuthenticationFailedException, so single sign-on can never be turned on through the documented path.
AWS: Smithy — EnableSso input is DirectoryId (@required, pattern ^d-[0-9a-f]{10}$), UserName (pattern ^[a-zA-Z0-9._-]+$), Password (ConnectPassword, @sensitive, length 1-128); output empty; modeled errors AuthenticationFailedException, ClientException, EntityDoesNotExistException, InsufficientPermissionsException, ServiceException. Recorded behavior: on an Active directory that has an alias, EnableSso with the directory's own administrator account (UserName "Admin" and the Password the create set) answers HTTP 200, DescribeDirectories then reports SsoEnabled true, and DisableSso with the same credentials flips it back to false. AuthenticationFailedException ("An authentication error occurred.") is for credentials the directory does NOT accept — not for every credentialed call.
Emulator: the handler refuses as soon as either member is present — src/ops/enable_sso.rs:211-218 returns AuthenticationFailedException whenever `input.user_name.is_some() || input.password.is_some()`, with message "An authentication error occurred. : RequestId: <RequestId>" (fixed text plus the call's own request id) — before the alias precondition is even evaluated.
Why: the documented enable path (assign an alias, then EnableSso with a privileged directory account) is unreachable, SsoEnabled can never become true, and DisableSso's credentialed half is unexercisable. The caller is handed an authentication fault for correct credentials and has nothing to correct.
Fix: the EnableSso handler and the directory record it authenticates against — a request naming the directory's own administrator account must be accepted and must set the directory's sso_enabled, with AuthenticationFailedException reserved for an account or password the directory does not hold; DisableSso's credentialed form must mirror it.
Traces: ds.disable-sso-without-enable-is-an-idempotent-no-op.

Cause 3 of 3: ten control-plane flows reach NO verdict — each is killed at the suite's 60 s per-check budget while polling a clock-owed transition, so none of their assertions (refusal texts, status round trips, effect-absence checks) is ever graded.
AWS: recorded behavior only. Each of these checks is a poll-and-wait flow: on AWS a Managed Microsoft AD stays Requested/Creating for 20-45 minutes and the later transitions (IP route Adding→Added, certificate Registering→Registered, LDAPS Enabling→Enabled, data access Enabling/Disabling, trust Creating→Created/Failed, Deleting→Deleted) take minutes, so clients poll at human intervals — 10 s, 15 s, 20 s or 30 s in these checks — and eventually read the settled value.
Emulator: every transition is held for a span and the settled value is materialised only by a later call — TRANSITION_SPAN = 500 ms (src/state.rs:119) and a create's stage CHAIN is Requested → Creating for DIRECTORY_BUILD_SPAN = 3 s (src/state.rs:146) → Active (directory_active_at, src/state.rs:156). A client that probes immediately after the call that starts a transition therefore ALWAYS observes the transient value and learns the settled one a full poll interval later, so each check pays one interval per transition. With two to five transitions per flow the fixed sleeps alone exceed 60 s and the harness reports "Check timed out after 60.0s" with no exception frame and no response divergence: remove-primary-region-denied spends ~30 s waiting for Stage Active and another ~30 s on the post-delete stage; ldaps-enable-disable-server-enforced pays 30 s (Active) + 10 s (certificate) + 20 s (LDAPS enable) + 15 s (disable); directory-data-access-server-enforced-toggle pays 30 s (Active) plus four data-access transitions; the three trust flows pay one or two directory creates plus the trust transitions.
Why: ten ds control-plane behaviours are completely ungraded — the duplicate-IP-route ClientException text, the certificate CommonName round trip and its post-deregister refusal, the DescribeDirectories inventory/delete contract, the data-access toggle and its DirectoryInDesiredStateException, the LDAPS enable/disable statuses, the primary-Region UnsupportedOperationException, and the trust create/verify/delete state machine. A regression in any of them is invisible to this suite, and a real client polling at these intervals reads a transient value where AWS would have settled.
Fix: the ds service's clock-owed transition spans and the chain built on them (src/state.rs:119 TRANSITION_SPAN, :146 DIRECTORY_BUILD_SPAN, :156 directory_active_at, plus the per-feature spans advance_clock materialises) — a settled value must be reachable by a client polling at the intervals these flows use, within the suite's per-check budget; alternatively this is the transition-span-contract decision the related open issue already escalated and it has to be settled rather than left failing. Per that issue, with the spans set to zero the same checks replay green, which both localises the cause and shows its cost (the modeled transient values Requested/Creating/Enabling/Disabling stop being observable).
Traces: ds.add-ip-routes-duplicate-cidr-rejected, ds.certificate-registration-commonname-round-trip, ds.describe-directories-returns-inventory, ds.directory-data-access-server-enforced-toggle, ds.e2e-trust-schema-extension-flow, ds.ldaps-enable-disable-server-enforced, ds.remove-primary-region-denied, ds.state-machine-trust-create-verify-delete-404, ds.state-machine-trust-lifecycle, ds.trust-lifecycle-create-verify-delete.
