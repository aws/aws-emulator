# eks-auth: cluster.endpoint is published as a real <id>.<region>.eks.amazonaws.com host the emulator does not serve, so the four remaining pod-identity checks are refused on the announced address before any Kubernetes/eks-auth call (1 cause)

> _Note: this issue was identified against the code base at commit `d523205a25e89799b79f6d7553b80badf0bb176e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRoleForPodIdentity

## Description
Replaying simparity-behavioral-aws-v1 against this checkout, eks-auth scores 9/21 (12 failed). Eight of the 12 failures are marked OWNED by open issues and are excluded. The four that remain all die in the same place and for the same reason, and none of them is carried by an existing issue's replay key: the host the emulator itself published in cluster.endpoint is not an address the emulator answers on, so the harness refuses to route to it and no request is ever sent.

ONE root cause; it must be closed before this issue is complete.

Cause 1 of 1 - CreateCluster/DescribeCluster announce the Kubernetes API server at a production-AWS DNS name instead of at an authority on the emulator's own listener.
AWS: Smithy (com.amazonaws.eks#Cluster$endpoint): "The endpoint for your Kubernetes API server." Smithy (com.amazonaws.eks#Certificate$data): "The Base64-encoded certificate data required to communicate with your cluster. Add this to the certificate-authority-data section of the kubeconfig file for your cluster." The contract of the pair is that a client builds a kubeconfig from DescribeCluster and reaches a live Kubernetes API server at that endpoint over TLS validated by that CA; the Kubernetes API surface itself is recorded behavior only (it is not in the AWS Smithy surface) and serves POST /api/v1/namespaces/{ns}/pods and POST /api/v1/namespaces/{ns}/serviceaccounts/{sa}/token. For an emulator the requirement is that the announced authority is one the emulator actually serves, with the path layout preserved; the concrete host, port and cluster id are per-environment values and are themselves no part of the requirement.
Emulator: the endpoint member is a synthesized production-AWS DNS name of the shape https://<32-hex-uppercase>.<3-hex>.<region>.eks.amazonaws.com, naming no host or port the emulator listens on. Every one of the four checks is refused the moment it asks the harness to address that URL: `simparity.published.PublishedUrlRejected: endpoint_url was given https://<32-hex>.<3hex>.<region>.eks.amazonaws.com (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener`. In that message the only variable part is the announced URL - it is verbatim what the emulator returned in cluster.endpoint; the loopback host and port are the harness's own per-run values and are not a requirement. This is the emulator announcing an address other than the one it is reached on, not an outbound-egress failure of the runner.
Why: a client that does the documented thing - build a kubeconfig from DescribeCluster and talk to the cluster - is sent off-emulator to a name that does not resolve to it, while the control plane cheerfully reports the cluster ACTIVE with pod-identity associations attached. Because AssumeRoleForPodIdentity only accepts a token carrying the kubernetes.io/pod claim, and that claim can only come from a ServiceAccount TokenRequest bound to a Pod object created through the cluster's Kubernetes API, the published endpoint is the single gate in front of the entire positive side of eks-auth. The four behaviors these checks exist to pin are therefore never exercised at all: (a) after eks:DeletePodIdentityAssociation, AssumeRoleForPodIdentity must answer HTTP 404 ResourceNotFoundException with the message "The token included in the request has no service account role association for it." (fixed text, no variable part), and eks:DescribePodIdentityAssociation / eks:UpdatePodIdentityAssociation on the dead id must answer 404 ResourceNotFoundException with "No service account role association found for ID: <associationId>" (fixed text plus the associationId from the request); (b) the credentials returned must be scoped to the intersection of the association's role policy and the pod identity's permissions; (c) the issued session must carry the pod-identity session tags that an ABAC-scoped S3 read is gated on; (d) a target-role chain must bind to the generated externalId.
Fix: the eks crate's Cluster projection/serializer - the code that fills Cluster.endpoint for CreateCluster, DescribeCluster and the persisted cluster state - must publish an authority the emulator serves, and the eks cluster data plane must answer the Kubernetes API behind that authority (Pod create returning metadata.uid, and the ServiceAccount TokenRequest subresource minting a token whose claims include kubernetes.io/pod name+uid, kubernetes.io/serviceaccount, kubernetes.io/namespace and the requested audience, signed by a key the eks-auth AssumeRoleForPodIdentity handler validates against) under a TLS certificate issued by the CA whose PEM is published in certificateAuthority.data.
Related open issues, neither of which covers these four checks: 20261109T131727Z-eks-auth-the-pod-identity-data-plane-is.md describes this same published-endpoint defect but carries the replay keys of a different set of seven checks (frame _create_eks_cluster#1), and 20261104T053901Z-eks-auth-the-whole-pod-identity-data-plane.md lists these four check ids but carries them on SSLError/DATAPLANE_UNIMPLEMENTED keys reached further along, on the explicit premise that "the harness routes that advertised URL back to the emulator" - a premise that no longer holds, since these four are now refused on the announced host before any socket is opened.
Traces: eks-auth.pod-identity-association-deleted-rejected, eks-auth.pod-identity-association-policy-intersects-the-role-permissions, eks-auth.pod-identity-session-tags-gate-an-abac-scoped-s3-read, eks-auth.pod-identity-target-role-chain-binds-to-the-generated-external-id.

## Steps to Reproduce
1. Clone the repo, build the emulator from this checkout and boot it.
2. Point a boto3 `eks` client at the emulator, create a cluster in a VPC with two subnets in distinct AZs, and wait until describe_cluster(name=...)['cluster']['status'] == 'ACTIVE'.
3. Read cluster['endpoint']. Expected: a URL whose host:port is an authority the emulator listens on (its own host/port, or a per-resource listener). Observed: https://<32-hex-uppercase>.<3-hex>.<region>.eks.amazonaws.com - a real AWS production DNS name the emulator does not serve.
4. Use it as the documented contract requires: POST <cluster['endpoint']>/api/v1/namespaces/default/pods with a minimal Pod manifest, trusting base64-decoded cluster['certificateAuthority']['data']. Observed: the request is not addressed to the emulator at all; the harness refuses to route the published URL with simparity.published.PublishedUrlRejected ("its host is not one of the emulator's own hosts").
5. Consequence: no ServiceAccount TokenRequest bound to a Pod can be minted, so eks_auth.assume_role_for_pod_identity(clusterName=<cluster>, token=<pod-bound token>) can never be called with the only token class it accepts - and the delete/404, policy-intersection, session-tag and target-role-chain behaviors behind it are never exercised.
6. Or just replay simparity-behavioral-aws-v1 and observe the four eks-auth checks in trace_ids all failing in context.py endpoint_route with PublishedUrlRejected.
