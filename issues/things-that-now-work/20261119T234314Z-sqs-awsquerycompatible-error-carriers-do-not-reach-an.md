# SQS awsQueryCompatible error carriers do not reach an in-Lambda JS v3 client: an unmodeled refusal (DelaySeconds=901) is reported as 'InvalidParameterValueException' instead of the legacy 'InvalidParameterValue'

> _Note: this issue was identified against the code base at commit `360dea7200cfaf15b2eb2bc3d0288559a6d49d3a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause. Related open issue that does NOT carry this replay key and does NOT cover it: 20261109T185037Z-sqs-5-net-new-causes-the-query-protocol-does.md (that one is about the form-encoded AWS Query protocol serving non-XML, the raw-JSON missing-target refusal, anonymous routing, CreateQueue idempotence and AWSTraceHeader — none of them is the awsQueryCompatible error-carrier split graded here).

Cause 1 of 1: an AWS SDK for JavaScript v3 client running on the emulator's nodejs22.x Lambda runtime does not resolve an SQS refusal through the x-amzn-query-error carrier, so an UNMODELED refusal is reported under the modern code instead of the legacy one.
Failing check: sqs.query-compatible-error-carriers-differ-by-consumer-rejected

AWS: Smithy — the AmazonSQS service (version 2012-11-05) is awsJson1_0 with the awsQueryCompatible protocol modifier, and SendMessage's modeled errors are InvalidAddress, InvalidMessageContents, InvalidSecurity, the KMS* family, QueueDoesNotExist (awsQueryError 'AWS.SimpleQueueService.NonExistentQueue'), RequestThrottled and UnsupportedOperation. InvalidParameterValueException is NOT a modeled SQS shape. Because of awsQueryCompatible, one refusal response carries TWO error vocabularies: the legacy Query code in the x-amzn-query-error header as '<code>;<fault>' and the Smithy code in the body's __type. For DelaySeconds=901 the response is HTTP 400 with header 'x-amzn-query-error: InvalidParameterValue;Sender' and body __type 'com.amazon.coral.service#InvalidParameterValueException'. botocore reports Error.Code 'InvalidParameterValue' and QueryErrorCode 'InvalidParameterValueException'; JS v3, having no modeled class for 'InvalidParameterValueException', FALLS BACK to the header and reports name 'InvalidParameterValue' on a generic 'SQSServiceException'. For a MODELED error the same wire makes the two SDKs differ on purpose: on an absent queue botocore reports 'AWS.SimpleQueueService.NonExistentQueue' while JS v3 constructs the modeled QueueDoesNotExist — message 'The specified queue does not exist.' (fixed text, no variable part) for both.

Emulator: the raw wire is right on this run — the raw probes assert and PASS that an absent-queue GetQueueUrl answers 400 with 'x-amzn-query-error: AWS.SimpleQueueService.NonExistentQueue;Sender', body __type 'com.amazonaws.sqs#QueueDoesNotExist', no x-amzn-errortype header, the header present even when the request does not send x-amzn-query-mode, and that SendMessage with DelaySeconds=901 answers 400 with 'x-amzn-query-error: InvalidParameterValue;Sender' and body __type 'com.amazon.coral.service#InvalidParameterValueException'. botocore's two codes are also correct. What diverges is the JS v3 consumer invoked inside the emulator's Lambda: for DelaySeconds=901 it reports name 'InvalidParameterValueException' (the body's modern code) where AWS makes it report the legacy 'InvalidParameterValue' from the header, so the two SDKs no longer CONVERGE on the unmodeled refusal. The same client handles the modeled error correctly (it constructs QueueDoesNotExist, e instanceof QueueDoesNotExist is true, status 400, request id present, message 'The specified queue does not exist.'), i.e. the body/__type path works and only the header-fallback path does not. The function reports its bundled client version as '3.0.0'. Hypothesis (the model states neither, and the recording cannot separate them): either (a) the emulator's nodejs22.x managed runtime bundles an @aws-sdk/client-sqs that predates the awsQueryCompatible x-amzn-query-error fallback — the reported '3.0.0' is not a version AWS's nodejs22.x runtime ships — or (b) the x-amzn-query-error response header is dropped on the path that serves clients running inside the Lambda sandbox, even though it is present on the path the raw/botocore probes use. A fixer should check which of the two holds before patching.

Why: a JS v3 client's error handling for SQS silently changes vocabulary. Code that classifies refusals by e.name against the legacy code ('InvalidParameterValue', the code botocore and the CLI also report) never matches, so a validation refusal falls through to a generic retry-or-crash branch; and because a MODELED error is still reported under the modern code, the two SDKs now report different codes for a refusal where AWS makes them agree — the exact inversion of the awsQueryCompatible contract.

Fix: the SQS awsQueryCompatible error-serialization path as observed by in-sandbox clients, plus the contents of the nodejs22.x managed runtime's bundled AWS SDK — the x-amzn-query-error header must reach a Lambda-hosted JS v3 client on the same responses it reaches botocore on, and that runtime's bundled @aws-sdk/client-sqs must be a build that implements the awsQueryCompatible header fallback.

## Evidence
Expected: for SendMessage(QueueUrl=<existing queue>, MessageBody='x', DelaySeconds=901) — HTTP 400, header 'x-amzn-query-error: InvalidParameterValue;Sender', body __type 'com.amazon.coral.service#InvalidParameterValueException' — an AWS SDK for JavaScript v3 client reports e.name 'InvalidParameterValue' and e.constructor.name 'SQSServiceException' (the modern code is unmodeled, so the header fallback fires), agreeing with botocore's Error.Code 'InvalidParameterValue' / QueryErrorCode 'InvalidParameterValueException'.

Actual: AssertionError: JS v3 3.0.0 reported name 'InvalidParameterValueException' for DelaySeconds=901, expected the LEGACY 'InvalidParameterValue' -- with no modeled class for 'InvalidParameterValueException' it falls back to x-amzn-query-error, so an emulator that omits that header hands JS the modern code here and diverges from botocore.

All earlier assertions in the same check passed, which bounds the defect: the raw 400 + 'x-amzn-query-error: InvalidParameterValue;Sender' + coral-namespaced __type for DelaySeconds=901, the raw absent-queue carriers (header 'AWS.SimpleQueueService.NonExistentQueue;Sender', __type 'com.amazonaws.sqs#QueueDoesNotExist', no x-amzn-errortype, header also sent without the x-amzn-query-mode opt-in), botocore's Error.Code/QueryErrorCode on both refusals, and the same JS client's modeled QueueDoesNotExist with message 'The specified queue does not exist.'
