# sagemaker training-job and endpoint read-backs lose algorithm metric and resolved-image detail

> _Note: this issue was identified against the code base at commit `2352e453041dca9d0b463884f1fb4473cbd545be`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTrainingJob

## Description
2 causes, one shared fault: the read-back projections for a training job and for the endpoint that hosts its model do not report the container/algorithm detail the resource was created with. Where AWS resolves and reports that detail (the built-in algorithm's metric set; the digest the specified image resolved to), the emulator either omits the member entirely or emits a locally synthesized value. Both causes are read paths on resources created earlier in the SAME fixture (sagemaker-train-host-and-invoke-xgboost-model), and both answer 200, so nothing signals the loss. A fixer must close BOTH clusters.

Cause 1 of 2: DescribeTrainingJob omits AlgorithmSpecification.MetricDefinitions and ImageMetadata for a job launched from a built-in algorithm image (fixture sagemaker-train-host-and-invoke-xgboost-model, step task#6).
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json): DescribeTrainingJob output member AlgorithmSpecification -> AlgorithmSpecification; AlgorithmSpecification.MetricDefinitions -> MetricDefinitionList, @length 0..40, documented as "A list of metric definition objects. Each object specifies the metric name and regular expressions used to parse algorithm logs. SageMaker publishes each metric to Amazon CloudWatch." MetricDefinition is a structure with required Name (MetricName, @length 1..255, @pattern ^.+$) and required Regex (MetricRegex, @length 1..500, @pattern ^.+$). AlgorithmSpecification.EnableSageMakerMetricsTimeSeries documents that time-series metrics are generated when "You use one of the SageMaker built-in algorithms", i.e. a built-in algorithm image brings its OWN fixed metric set; AWS therefore resolves that set onto the described job even when CreateTrainingJob supplied no MetricDefinitions, and the describe returns one {Name, Regex} entry per metric the algorithm publishes (for the xgboost built-in: train:/validation: pairs such as train:mae, train:merror, train:mlogloss, train:error, train:auc, validation:logloss, validation:auc, validation:precision, validation:recall, validation:map, each with that algorithm's log-scraping regex template of the shape '.*\\[[0-9]+\\].*#011<metric-name>:([-+]?[0-9]*\\.?[0-9]+(?:[eE][-+]?[0-9]+)?).*'). The requirement is the metric NAMES and their regex templates, which follow from the algorithm image, not from this run. ImageMetadata is NOT declared in this checkout's DescribeTrainingJobResponse, so for that member it is recorded behavior only: the recorded 200 response carries it on a describe of a completed job.
Emulator: answers 200 with $.AlgorithmSpecification.MetricDefinitions absent (null) and $.ImageMetadata absent. Status is 200 and every other asserted scalar matches, so the omission is invisible to the client.
Why: a client that reads AlgorithmSpecification.MetricDefinitions to learn which metric names a job emits and which regexes parse them - the standard SageMaker analytics/tuning path, and the only place a built-in algorithm's metric set is exposed - gets nothing and concludes the job publishes no metrics, so metric collection does nothing and a tuning objective keyed on one of those names can never be satisfied.
Fix: the DescribeTrainingJob handler's output projection plus the training-job state it reads from: the algorithm image's metric set must be resolved onto the stored job at CreateTrainingJob time and echoed back, and the per-job image detail member must be stored and emitted.
Traces: sagemaker-train-host-and-invoke-xgboost-model#task#6.

Cause 2 of 2: DescribeEndpoint reports a ProductionVariants[].DeployedImages[].ResolvedImage whose digest is locally synthesized instead of the digest the specified image resolves to (fixture sagemaker-train-host-and-invoke-xgboost-model, step task#11).
AWS: Smithy: DescribeEndpoint output member ProductionVariants -> ProductionVariantSummaryList (@length min 1); ProductionVariantSummary.DeployedImages -> DeployedImages, a list of DeployedImage; DeployedImage.ResolvedImage -> ContainerImage (@length 0..255, @pattern ^[\\S]+$) documented as "The specific digest path of the image hosted in this ProductionVariant", and the shape doc states that when the model's container image was given in registry/repository[:tag] form "the path resolves to a path of the form registry/repository[@digest]. A digest is a hash value that identifies a specific version of an image." The digest is therefore a property of the image actually hosted - for an AWS-published built-in algorithm image it is the fixed digest of that published tag, the same value on every account and every run - not a value the service invents per endpoint. Status 200, no error.
Emulator: answers 200 with the registry/repository part correct but a DIFFERENT, locally derived sha256 digest appended, i.e. registry/repository@sha256:<64 hex> where the hex is not the hosted image's digest.
Why: ResolvedImage exists precisely so a client can pin or audit the exact image version serving an endpoint. A digest the emulator derived itself fails every comparison against the published image, and any pipeline that pulls the container by the reported digest resolves nothing, so provenance checks and image-drift alarms both misfire on a healthy endpoint.
Fix: the endpoint state built by CreateEndpoint/CreateModel (it must retain the model container's image reference and the digest it resolves to) and the DescribeEndpoint serializer that emits DeployedImages, which must emit the resolved digest rather than call a local digest helper. Hypothesis: the digest is being computed from the image URI at read time. Open issue 20261115T014541Z-sagemaker-container-imagedigest-fields-are-locally-synthesized-instead.md reports the same synthesized-digest fault on DescribeAlgorithm.TrainingSpecification.TrainingImageDigest and DescribeModelPackage.InferenceSpecification.Containers[].ImageDigest, but the replay reports this DescribeEndpoint cluster with NO owner (its key carries $.ProductionVariants[0].DeployedImages[0].ResolvedImage, which that issue does not), so it is filed here; a fixer closing both should expect one shared helper.
Traces: sagemaker-train-host-and-invoke-xgboost-model#task#11.

Not requirements, deliberately excluded from both causes: the same two clusters also list $.CreationTime, $.LastModifiedTime, $.TrainingStartTime, $.TrainingEndTime, $.FinalMetricDataList[0].Timestamp and $.ProductionVariants[0].DeployedImages[0].ResolutionTime against '<shaped-not-asserted>'. Those are per-run clock values and form no part of either cause. The literal digests and metric names quoted below are this corpus's values filling the template; the requirements are that the metric set follow from the algorithm image and that the reported digest be the hosted image's digest.
