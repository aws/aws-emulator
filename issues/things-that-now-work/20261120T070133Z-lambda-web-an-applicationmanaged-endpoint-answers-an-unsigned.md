# lambda-web: an ApplicationManaged endpoint answers an unsigned request 501 instead of the revision handler's response, so authType has no observable effect

> _Note: this issue was identified against the code base at commit `27aae757db5fa764a3702a0ead4409204ce3a274`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetWebFunctionEndpoint

## Description
Cause 1 of 1: a web function endpoint whose `authType` is `ApplicationManaged` does not serve the deployed revision's HTTP response to an UNSIGNED request. The emulator lets the unsigned request past the auth gate (correctly, for ApplicationManaged) and then answers every such request with a fixed HTTP 501 and a sentence saying no web function code ran, so the `ApplicationManaged` arm of `authType` is indistinguishable from the refused arm as far as a client can observe: nothing past the gate is ever the application's own answer. Failing check: lambda-web.endpoint-auth-type-enforces-sigv4-for-iamauth-and-allows-unsigned-for-applicationmanaged.

AWS: a web function endpoint IS an HTTP data plane, and `authType` decides who may reach it. Smithy (services/service-com-amazonaws-lambdaweb-lambdaweb/smithy-model/com-amazonaws-lambdaweb-lambdaweb.json): CreateWebFunctionEndpointRequest$authType is required, target enum AuthType (ApplicationManaged | IamAuth); CreateWebFunctionEndpointResponse/GetWebFunctionEndpointResponse$domainName is required, DomainName @length min 4 max 256, @pattern ^([a-z0-9-]+\.)+[a-z]+$ — the address that endpoint publishes; $state (enum EndpointState) and $revisionWeights (RevisionWeightList @length min 1 max 2, uniqueItems) say which revision(s) that address serves. The data-plane hop itself is NOT modelled — there is no operation shape, no restJson1 envelope and no modelled status on it — so for what comes back this is recorded behavior only: once an `ApplicationManaged` endpoint reports `state: Active`, a plain unsigned HTTPS GET to its `domainName` is forwarded to the application and answered with exactly what the deployed revision's handler returned (in the recording HTTP 200 with the handler's own body and its own content-type). The status, headers and body all belong to the handler; AWS serves no fixed document and no error code on this hop, so there is no AWS-worded message here at all — the recording's literal body string is that run's handler output, not part of the requirement.

Emulator: `serve_request` in services/service-com-amazonaws-lambdaweb-lambdaweb/src/state/endpoint_plane.rs resolves the Active endpoint, applies the `IamAuth`-and-no-credential refusal, and then falls through to the terminal arm `plain(head, 501, NO_WEB_FUNCTION_HANDLER)`: HTTP 501, content-type `text/plain; charset=utf-8`, body the module constant "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n". Because an unsigned request to an `ApplicationManaged` endpoint never takes the refusal arm, that 501 is the ONLY thing such a request can get — for every path, method and revision — since no execution engine is mounted in the crate (the deployment package is validated as an archive in src/state/code_package.rs but never run). The check polls the unsigned GET for a 200 and never observes one, so it is reported as an error whose message is the poll's own budget message ("an unsigned GET to the ApplicationManaged endpoint being served: the run budget ended first; not graded") rather than as a 501 assertion; the control plane meanwhile reports the endpoint `Active` with a `domainName` the emulator does answer on, so the divergence appears only at the last hop.

Why: a client that reads `domainName` off an `Active` ApplicationManaged endpoint and calls it the way AWS documents — unsigned, letting the application authorize — gets 501 for a function AWS reports healthy and serving. The whole point of `authType: ApplicationManaged` (the application handles authorization) is unobservable, the difference between the two AuthType values cannot be exercised, the handler's status/headers/body cannot be asserted, and `revisionWeights` routing is unobservable because every weight resolves to the same fixed 501. A client treating 501 as a transient server fault retries forever, which is what this check's poll does until the run budget ends.

Fix: the authorized/forwarded arm of the endpoint data plane — the terminal arm of `serve_request` in the lambda-web crate's endpoint-plane state module — must bridge the buffered request to the revision the endpoint's `revisionWeights` select and return that handler's own response, for the unsigned ApplicationManaged path as well as the signed IamAuth path, instead of a fixed 501 constant. That needs an execution layer for the revision's deployment package in this crate (containment and bounds first, then the request/response bridge); the emulated Lambda service's existing execution state is the closest reference and anything shared belongs in a shared crate rather than a second copy.

Related, already filed, named here rather than re-filed: issues/things-that-do-not-work/20261111T133800Z-lambda-web-a-signed-request-to-an-active.md and issues/things-that-do-not-work/20261110T090000Z-lambda-web-endpoint-serves-no-handler-response.md describe the same 501 on the SIGNED IamAuth path and do not carry this check's replay key (the suite did not report this check as OWNED); issues/things-that-do-not-work/20261111T072317Z-lambda-web-iamauth-endpoint-s-unsigned-request-refusal.md covers only the 403 refusal body/header on an IamAuth endpoint. Treat this with those as one data-plane work item, but this check's ApplicationManaged unsigned path must be replayed to close it.

## Evidence
Check lambda-web.endpoint-auth-type-enforces-sigv4-for-iamauth-and-allows-unsigned-for-applicationmanaged (GROUP endpoints) creates an execution role and a versioned S3 bucket holding a Node.js .zip deployment package whose handler answers every request with one fixed text/plain body; CreateWebFunction with revisionConfig.buildConfig.codeConfig.s3Object pointing at it, runtimeConfig.runtime "nodejs24.x", and endpointConfig {endpointName: "am", endpointType: "HomeRegion", authType: "ApplicationManaged"}; polls GetWebFunctionRevision to Active and GetWebFunctionEndpoint("am") to Active (both asserted Active, both reached); reads domainName; then polls an UNSIGNED HTTPS GET to that address for `status == 200` and asserts the body equals the handler's fixed output.

Reported verdict: [error] — TimeoutError: "an unsigned GET to the ApplicationManaged endpoint being served: the run budget ended first; not graded", raised from the check's `_poll_until` at line 142 (called at line 290/603 of the check source). The poll never observes a 200 because every unsigned request to the published address is answered HTTP 501, content-type `text/plain; charset=utf-8`, body "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n" — the `NO_WEB_FUNCTION_HANDLER` constant returned by the terminal `plain(head, 501, NO_WEB_FUNCTION_HANDLER)` arm of `serve_request` (services/service-com-amazonaws-lambdaweb-lambdaweb/src/state/endpoint_plane.rs line 434; the `IamAuth` refusal arm above it at lines 422-433 is not taken for `ApplicationManaged`). That status and that body are fixed for every request and carry nothing from the request or from the revision.

Expected per the recording: the handler's own response — HTTP 200 with the deployed handler's own body and content-type (the recording's literal body string is that run's handler output filling the template, not fixed text of a requirement). There is no AWS error code or AWS-worded message on this hop; the emulator's 501 and its sentence are not AWS behaviour on it at all.

## Steps to Reproduce
1. CreateRole with a lambda.amazonaws.com trust policy; CreateBucket with versioning enabled plus a bucket policy letting lambda.amazonaws.com GetObject/GetObjectVersion; PutObject a valid Node.js .zip deployment package whose handler returns a known literal body with a 200.
2. CreateWebFunction with revisionConfig.buildConfig.codeConfig.s3Object pointing at that object, runtimeConfig.runtime "nodejs24.x", serviceConfig.executionRoleArn the role, and endpointConfig {endpointName: "am", endpointType: "HomeRegion", authType: "ApplicationManaged"}.
3. Poll GetWebFunctionRevision until state == "Active", then GetWebFunctionEndpoint(functionName, endpointName="am") until state == "Active"; read domainName off the response.
4. Issue a plain UNSIGNED HTTPS GET to that address (no Authorization header, no X-Amz-Credential).
5. Observed: HTTP 501, content-type text/plain; charset=utf-8, body "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n", on every retry, so a client polling for 200 never terminates. Expected: the deployed revision's handler response — HTTP 200 with that handler's own body and content-type.
