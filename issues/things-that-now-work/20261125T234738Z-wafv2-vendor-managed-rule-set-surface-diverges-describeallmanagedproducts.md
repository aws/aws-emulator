# wafv2 vendor managed-rule-set surface diverges: DescribeAllManagedProducts publishes a catalogue short of AWS's Marketplace listings, and PutManagedRuleSetVersions misclassifies an unusable RESOURCE_ARN reference

> _Note: this issue was identified against the code base at commit `c11f37d9666aeec66c301c48be9695cec998b743`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAllManagedProducts

## Description
The vendor-facing managed-rule-set surface diverges in two independent places: what the service PUBLISHES about managed products, and how it REFUSES a put whose managed-rule-set reference is not usable. This is ONE issue with TWO causes; both must be closed before the fix is submitted.

Cause 1 of 2: DescribeAllManagedProducts reports a product catalogue that stops after the first two Amazon Web Services Marketplace listings, so every product after them is wrong or absent.
AWS: Smithy (com.amazonaws.wafv2#AWSWAF_20190729) DescribeAllManagedProducts takes required `Scope` (enum CLOUDFRONT|REGIONAL) and answers `ManagedProducts` (ManagedProductDescriptors), one ManagedProductDescriptor per product — `VendorName` (@length 1..128, @pattern \S), `ManagedRuleSetName` (EntityName @length 1..128 @pattern ^[\w\-]+$), `ProductId` (@length 1..128 @pattern \S), `ProductLink` ("for Amazon Web Services Marketplace managed rule groups only, the link to the rule group product page"), `ProductTitle`, `ProductDescription`, `SnsTopicArn` (ResourceArn @length 20..2048, the topic of the vendor that publishes the group), `IsVersioningSupported` and `IsAdvancedManagedRuleSet` (Boolean, default false); it models WAFInvalidParameterException and WAFInvalidOperationException (client, httpError 400) and WAFInternalErrorException (500). The operation's own doc: "Provides high-level information for the Amazon Web Services Managed Rules rule groups and Amazon Web Services Marketplace managed rule groups" — i.e. the report is the UNION of both vendor families. The model does not enumerate the catalogue itself, so for its CONTENT this is recorded behavior only: the recording answers HTTP 200 with a 46-entry ManagedProducts list (indices 0..45) whose Marketplace family continues past the two `CyberSecurityCloud-` listings — the next published entries are `CyberSecurityCloud-ProtocolEnforcement-` (VendorName "Cyber Security Cloud Inc.", a vendor-assigned ProductId, a ProductLink on the Marketplace product-page address, SnsTopicArn the VENDOR's own topic in the VENDOR's account, IsVersioningSupported true) and a Fortinet listing (`all_rules`, "OWASP Top 10 - The Complete Ruleset") — and only after the whole Marketplace family come the Amazon Web Services Managed Rules descriptors. The same list is published in BOTH scopes (a product is a vendor's publication, and Scope is only the namespace a request is made in): the REGIONAL and CLOUDFRONT recordings expect identical lists. The per-listing text, ids, links and topic ARNs are published reference data, not values from the request; the requirement is that every product AWS publishes is reported, in the published order, each as its own family publishes it.
Emulator: HTTP 200 with a SHORT list. Only two Marketplace listings are published, so from index 2 onward the response is off by the whole missing tail: where the recording has the third Marketplace listing, the emulator answers an Amazon Web Services Managed Rules descriptor instead (VendorName "AWS", ManagedRuleSetName "AWSManagedRulesCommonRuleSet", a ProductId derived from the vendor/name pair rather than a published identifier, SnsTopicArn minted in the emulator's own account, no ProductLink), and indices 2..45 all diverge. No Fortinet (or any other third-party seller's) product is reported at all.
Why: a client enumerates this catalogue to discover which managed rule groups exist and who sells them — to subscribe to a Marketplace group, to resolve a (VendorName, ManagedRuleSetName) pair a configuration names, or to find the SNS topic to watch for version changes. With most of the catalogue missing, that discovery silently returns "this vendor publishes nothing": DescribeManagedProductsByVendor for every absent seller answers an empty list, a configuration referencing an absent group cannot be validated against the catalogue, and the vendor notification topics and product pages the absent listings carry are unreachable. Because the omission also SHIFTS every later entry, a client that indexes positionally reads the wrong product.
Fix: the published catalogue reference data this operation reads, not the handler — `crate::state::managed_products` (the Marketplace listing table and the Amazon Web Services Managed Rules family it is chained with). Extend the Marketplace family with the remaining published listings, in published order, each with its vendor's own ProductId, ProductLink, ProductTitle/ProductDescription and SnsTopicArn (in the vendor's account), keeping the AWS Managed Rules family after it and keeping the list scope-independent.

Cause 2 of 2: PutManagedRuleSetVersions refuses a managed-rule-set reference it cannot use with WAFNonexistentItemException and drops every structured detail member of the refusal.
AWS: Smithy PutManagedRuleSetVersions takes required `Name` (EntityName @length 1..128 @pattern ^[\w\-]+$), `Scope`, `Id` (EntityId @length 1..36 @pattern ^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$) and `LockToken`, plus optional `RecommendedVersion` and `VersionsToPublish`, and models WAFInvalidParameterException, WAFNonexistentItemException, WAFInvalidOperationException, WAFOptimisticLockException (all client, httpError 400) and WAFInternalErrorException (500). WAFInvalidParameterException carries `message`, `Field` (ParameterExceptionField enum, "the settings where the invalid parameter was found"), `Parameter` ("the invalid parameter that resulted in the exception") and `Reason` ("additional information about the exception"), and is documented for the case "Your request references an ARN that is malformed, or corresponds to a resource with which a web ACL can't be associated" — i.e. a reference that is not a usable ARN is a PARAMETER failure, judged from the request before any store lookup. The recorded refusal is HTTP 400 with `__type` 'WAFInvalidParameterException' and all four members: `Field` = the fixed enum token 'RESOURCE_ARN'; `Parameter` = the managed-rule-set ARN resolved from the request's Scope, Name and Id and the caller's account and region (fully variable); `Reason` = the fixed sentence "The ARN isn't valid. A valid ARN begins with arn: and includes other information separated by colons or slashes."; `message` = the fixed framing "Error reason: " + that sentence + ", field: RESOURCE_ARN, parameter: " + that same ARN. Only the ARN is request/state-derived; the Field token, the Reason sentence and the "Error reason: ..., field: ..., parameter: ..." framing are fixed text for this error class.
Emulator: HTTP 400 (the status is right) but `__type` is 'WAFNonexistentItemException' and `Field`, `Parameter`, `Reason` and `message` are all absent — the handler goes straight to the managed-rule-set lookup, misses, and raises the not-found class carrying only its `Message`.
Why: a client tells "the request names something that cannot exist — fix the request" from "the item is not there yet — create it or retry" by the exception class alone. Vendor tooling that publishes managed rule set versions feeds WAFNonexistentItemException into a create-or-retry loop that can never converge, while the real fault (an unusable Name/Scope/Id reference) is never surfaced; the missing Field/Parameter/Reason members remove the only machine-readable statement of WHICH parameter was wrong, so the caller cannot distinguish this 400 from any other.
Fix: the validation ORDER in this operation's handler (services/service-com-amazonaws-wafv2-awswaf-20190729/src/ops/put_managed_rule_set_versions.rs): resolve the managed-rule-set ARN from Scope/Name/Id and classify a reference that is not a usable ARN as a RESOURCE_ARN WAFInvalidParameterException — with Field, Parameter, Reason and the composed message — before the state lookup that raises WAFNonexistentItemException. Note for the fixer: the RESOLVED issue 20261120T102658Z-wafv2-putmanagedrulesetversions-misclassifies-an-invalid-managed-rule-set.md carried this same fixture and step and is now in the resolved folder, so this is a REGRESSION of it and a resolved issue covers no live failure; and the OPEN behavioral issue 20261121T212310Z-wafv2-putmanagedrulesetversions-refuses-a-nonexistent-managed-rule-set.md asks for the opposite precedence on its own checks (target lookup first) — reconcile them the way that issue's own fixer note states, by splitting the judgement WAF splits: an unusable/malformed reference is decided from the request before any lookup (this cause), while a WELL-FORMED reference carried in the body that merely fails to RESOLVE is decided after the target lookup (that issue). Both recordings then hold.
