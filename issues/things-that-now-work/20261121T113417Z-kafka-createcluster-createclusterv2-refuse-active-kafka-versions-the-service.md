# CreateCluster/CreateClusterV2 refuse ACTIVE Kafka versions the service's own catalog publishes (3.6.0, 3.7.x, 3.7.x.kraft), so no provisioned cluster can be built on the oldest offered version

> _Note: this issue was identified against the code base at commit `3c6459ed73d0d3d48bff9506cc57e86075c7f1db`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateClusterV2

## Description
One root cause, grounded in the 11 failing behavioral checks listed in trace_ids. None of them is marked ALREADY FILED or OWNED by the suite, and no open kafka issue carries their replay keys.

Cause 1 of 1: the per-broker-category create gate admits a NARROWER version set than the catalog the same service publishes as ACTIVE, and the set it admits excludes every ACTIVE version below 3.8.x. A provisioned CreateCluster / CreateClusterV2 naming the OLDEST ACTIVE version that ListKafkaVersions publishes (3.6.0) with an ordinary standard broker instance type (kafka.t3.small, kafka.m5.large) is refused 400 BadRequestException. Failing checks: kafka.bootstrap-brokers-endpoint-formats-match-cluster-security, kafka.cluster-policy-large-document-round-trip, kafka.compatible-kafka-versions-matches-real-upgrade-path, kafka.describe-topic-partitions-invalid-topic-rejected, kafka.e2e-scram-secret-auth-grant-and-revoke, kafka.e2e-scram-secret-rotation-access-flow, kafka.e2e-topic-lifecycle-scale-and-teardown, kafka.scram-disassociate-nonexistent-secret-rejected, kafka.scram-secrets-list-reflects-association-order, kafka.deploy-msk-cluster-cfn-bootstrap-brokers-reachable, kafka.deploy-msk-cluster-cfn-active-and-bootstrap-brokers.

AWS: Smithy (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json): ListKafkaVersions GET /v1/kafka-versions -> KafkaVersions of KafkaVersion{Version, Status}, Status an enum KafkaVersionStatus = ACTIVE | DEPRECATED; CreateCluster POST /v1/clusters and CreateClusterV2 POST /api/v2/clusters, both with required KafkaVersion (__stringMin1Max128) and BrokerNodeGroupInfo.InstanceType, errors BadRequestException (400) / ConflictException (409) / ForbiddenException (403) / UnauthorizedException (401). The model enumerates no concrete versions, so WHICH version a create may name is recorded behavior only. The recorded behavior these checks encode is the contract between the two operations: a version the catalog publishes with Status=ACTIVE is a version MSK still offers for a NEW standard-broker cluster, so CreateCluster/CreateClusterV2 with that version and a standard instance type (kafka.t3.small / kafka.m5.large) is ACCEPTED and returns State=CREATING. Several of these checks deliberately pick the OLDEST ACTIVE row for exactly that reason: their own comments record that on real AWS the refusal "Standard instance types are not supported for Kafka version <v>. Valid values: [...]" is raised only for the newest Express/KRaft-only line (observed as "... not supported for Kafka version 4.2.x.kraft"), and that AWS's own valid-value list confirmed the oldest ACTIVE row IS standard-instance compatible. The requirement is that rule, not one run's version strings: the refusal's fixed text is "<category> instance types are not supported for Kafka version <version>. Valid values: [<versions>]" with category, version and the valid list taken from the request and the service's own offering, and it must be raised only for versions the service genuinely does not offer that broker category — never for a version it publishes as ACTIVE and offers to standard brokers.

Emulator: CreateCluster (POST /v1/clusters) and CreateClusterV2 (POST /api/v2/clusters, Provisioned body) answer 400 BadRequestException with message "Standard instance types are not supported for Kafka version 3.6.0. Valid values: [3.8.x, 3.8.x.kraft, 3.9.x, 3.9.x.kraft, 4.0.x.kraft, 4.1.x.kraft]" for a well-formed provisioned create whose InstanceType is kafka.t3.small or kafka.m5.large and whose KafkaVersion is 3.6.0 — the first/oldest ACTIVE row its own ListKafkaVersions page publishes. The emulator's create offering is a hard-coded six-entry list shared by both broker categories, so it also omits the ACTIVE rows 3.7.x, 3.7.x.kraft and 4.2.x.kraft, while handing the Express category exactly the same set as Standard. The catalog and the gate therefore contradict each other: the listing offers versions the create refuses, and the refusal's "Valid values" steers a client onto a different set than the one the catalog publishes.

Why: a client picks a version the documented way — enumerate ListKafkaVersions, keep the ACTIVE rows, create a cluster on one of them — and is refused outright with a 400 that names the version it was just told is offered. Every workflow that provisions an MSK cluster on anything but the four newest lines fails at setup: nine control-plane/e2e checks never create a cluster at all (so bootstrap-broker endpoint families, cluster policies, the upgrade-compatibility path, topic-partition refusals and the whole SCRAM secret surface are never exercised), and a CloudFormation stack carrying AWS::MSK::Cluster with such a version fails to create and rolls back to ROLLBACK_COMPLETE instead of reaching CREATE_COMPLETE.

Fix: the provisioned create's version admission gate and the per-category offering table it reads — the new-cluster offering must agree with the published catalog (every version the catalog publishes an ACTIVE row for is creatable for the standard broker category), and the Express category must carry its own set rather than sharing Standard's, so the refusal is raised only for a version that category truly does not offer. The CloudFormation AWS::MSK::Cluster provisioner needs no change of its own; it fails because the underlying create is refused.

Traces: the nine control-plane/e2e checks abort on the create itself (botocore BadRequestException from CreateCluster or CreateClusterV2, message above); kafka.deploy-msk-cluster-cfn-bootstrap-brokers-reachable fails one layer up, with the stack entering ROLLBACK_COMPLETE ("The following resource(s) failed to create: [MskCluster].") after taking its KafkaVersion from the first ACTIVE ListKafkaVersions row; kafka.deploy-msk-cluster-cfn-active-and-bootstrap-brokers is the same CFN deploy path, walking the ACTIVE versions newest-first and polling the stack, and its recorded symptom is only the harness cap ("Check timed out after 60.0s") because every candidate it tried rolled back. Code: services/service-com-amazonaws-kafka-kafka/src/state/kafka_versions.rs — KAFKA_VERSION_CATALOG row '3.6.0' ACTIVE (line 114), KAFKA_VERSIONS_EVERY_CATEGORY_IS_OFFERED (lines 530-537), KAFKA_VERSIONS_FOR_A_NEW_CLUSTER (lines 560-569), new_cluster_kafka_versions (lines 581-612) and create_kafka_version_violation (lines 633-641); the page is projected by src/ops/list_kafka_versions.rs (lines 202-214).

Related open issues that do NOT cover this cause: 20261111T115530Z-kafka-listkafkaversions-publishes-a-second-deprecated-3-9.md and 20261115T194344Z-kafka-msk-version-catalog-publishes-a-duplicate-deprecated-3.md report duplicate catalog ROWS (a version published under two statuses); this issue is about the create gate refusing versions the catalog publishes as ACTIVE, and neither of those issues carries any of the replay keys listed here.

Message anatomy: the fixed text is "<category> instance types are not supported for Kafka version <version>. Valid values: [<comma-separated versions>]". ## Steps to Reproduce
1. Boot the emulator from this checkout (the kafka service answers).
2. GET /v1/kafka-versions (`aws kafka list-kafka-versions`) and keep the rows with Status=ACTIVE. The oldest such row is 3.6.0.
3. Call CreateClusterV2 with Provisioned = {KafkaVersion: "3.6.0", BrokerNodeGroupInfo: {InstanceType: "kafka.t3.small", ClientSubnets: [two subnets in different AZs]}, NumberOfBrokerNodes: 2}, ClusterName: any 1-64 char name. Observe HTTP 400 BadRequestException "Standard instance types are not supported for Kafka version 3.6.0. Valid values: [3.8.x, 3.8.x.kraft, 3.9.x, 3.9.x.kraft, 4.0.x.kraft, 4.1.x.kraft]" instead of 200 with State=CREATING.
4. Repeat via CreateCluster (POST /v1/clusters) with KafkaVersion="3.6.0" and InstanceType="kafka.m5.large" — same refusal.
5. Repeat with KafkaVersion="3.7.x" and "3.7.x.kraft" (both published ACTIVE) — also refused, confirming the gate is narrower than the catalog rather than specific to 3.6.0.
6. Deploy a CloudFormation stack with one AWS::MSK::Cluster (InstanceType kafka.m5.large, NumberOfBrokerNodes 2, KafkaVersion taken from step 2) and observe the stack reach ROLLBACK_COMPLETE with "The following resource(s) failed to create: [MskCluster]." instead of CREATE_COMPLETE.
7. Re-replay the checks in trace_ids; each currently stops at cluster creation (or at the stack that wraps it).
