# cloudfront__events: an EventBridge rule whose Lambda target carries a DeadLetterConfig produces none of the three effects AWS guarantees — no delivery to a permitted target, no NO_PERMISSIONS dead-letter record, and no handler log output

> _Note: this issue was identified against the code base at commit `4ccad0ed25716432ca77154a59311743844eebd1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEvents

## Description
One net-new root cause, grounded in the only failing cloudfront__events check the replay report marks neither OWNED nor ALREADY FILED.

Related open issues — none of them carries this check's replay key, so this is filed separately and should be de-duplicated against them if one dispatch/dead-letter fix closes them all: 20261105T190602Z-cloudfront-events-2-net-new-causes-a-matched.md (its Cause 2 is the NO_PERMISSIONS DLQ record, but its only trace ids are eventbridge-rule-input-path-extracts-distribution-id, eventbridge-target-arn-resolves-to-specific-cloudfront-distribution and eventbridge-lambda-target-missing-permission-blocks-delivery), 20261102T091831Z-cloudfront-events-a-matched-rule-never-invokes-its.md (its dead-letter cause is FAILED_TO_ASSUME_ROLE on a target ROLE), 20261104T051153Z-cloudfront-events-a-matching-putevents-entry-never-invokes.md, 20261029T175823Z-cloudfront-events-13-more-cloudfront-eventbridge-checks-fail.md, 20261105T094343Z-cloudfront-events-the-lambda-python-runtime-provides-no.md (the python runtime ships no AWS SDK, which is the suspected blocker of this check's boto3-using relay function — see the Hypothesis below).

Cause 1 of 1: a rule whose Lambda target carries DeadLetterConfig + RetryPolicy neither delivers a matched event to a permitted target, nor dead-letters a delivery it is not permitted to make, nor runs the target handler at all — so the asynchronous-invocation contract this check exists to pin (a target's OWN raised exception is invisible to the rule's DLQ) can never be observed. Failing check: cloudfront__events.eventbridge-lambda-invalidation-failure-routes-to-dlq.

AWS: Smithy (services/service-com-amazonaws-eventbridge-awsevents/smithy-model/com-amazonaws-eventbridge-awsevents.json): PutTargets input Rule (@required) + Targets (@required); Target{Id @required @length 1..64 @pattern ^[\.\-_A-Za-z0-9]+$, Arn @required @length 1..1600} with DeadLetterConfig -> DeadLetterConfig{Arn -> ResourceArn @length 1..1600}, documented as "The DeadLetterConfig that defines the target queue to send dead-letter queue events to" and "The ARN of the SQS queue specified as the target for the dead-letter queue", and RetryPolicy -> RetryPolicy{MaximumRetryAttempts @range 0..185, MaximumEventAgeInSeconds @range 60..86400}, documented as bounding the attempts "until either the maximum number of attempts is made or until the duration of the MaximumEventAgeInSeconds is met". PutEvents models only InternalException, so an entry accepted with FailedEntryCount 0 is a promise of asynchronous delivery. AWS therefore guarantees three distinct effects for the wiring below: (1) an entry matching an ENABLED rule's EventPattern invokes a Lambda target whose resource policy admits events.amazonaws.com for that rule ARN (lambda:AddPermission Principal events.amazonaws.com, SourceArn arn:aws:events:<region>:<account>:rule/<ruleName>), and the handler's effects (here an sqs:SendMessage relay) and its stdout/stderr in /aws/lambda/<functionName> become visible; (2) a delivery EventBridge cannot make because no such grant exists is retried per RetryPolicy (MaximumRetryAttempts 0 = one attempt) and then written to Target.DeadLetterConfig.Arn, body = the original event envelope, with the delivery metadata as SQS message attributes — RULE_ARN = the rule ARN, TARGET_ARN = the target ARN, ERROR_CODE = NO_PERMISSIONS (fixed text; the two ARN values come from the request and from state); (3) because EventBridge invokes Lambda ASYNCHRONOUSLY, delivery completes before the handler runs, so a handler that raises is NOT a delivery failure and its event never reaches the rule's DLQ — the exception surfaces only in the function's logs (and in Lambda's own async failure handling), never as an EventBridge dead-letter record. Recorded behavior only for timing: the recording shows the relay, the log line and the NO_PERMISSIONS DLQ record all arriving well inside the check's windows (60 s relay poll, 60 s log poll, 30 s DLQ drain).

Emulator: every configuration call is accepted — sqs.CreateQueue + GetQueueAttributes(QueueArn) for the DLQ and the observation queue, sqs.SetQueueAttributes with a Policy granting events.amazonaws.com sqs:SendMessage on the DLQ under ArnEquals aws:SourceArn = the three rule ARNs, iam.CreateRole/AttachRolePolicy(AWSLambdaBasicExecutionRole)/PutRolePolicy(sqs:SendMessage), lambda.CreateFunction for both the raising handler and the boto3 relay handler, events.PutRule x3 (State=ENABLED), lambda.AddPermission for two of the three rule ARNs, events.PutTargets x3 each with DeadLetterConfig{Arn:<dlq arn>} + RetryPolicy{MaximumRetryAttempts:0, MaximumEventAgeInSeconds:60}, and events.PutEvents with three matching entries — and then NONE of the three guaranteed effects happens inside the harness budget. The check is killed at "Check timed out after 60.0s" with no status, no error code and no message to compare: the divergence is silent inaction. Nothing ever lands on the observation queue (so the positive control — the permitted target relaying detail.invalidationMarker — is never satisfied), the raising function's log group yields no record of its exception, and the DLQ receives no NO_PERMISSIONS record for the deliberately ungranted rule, so the main assertion (that the raising target's event is ABSENT from the DLQ) is never even reached and the async-vs-sync distinction is untestable. Hypothesis: the earliest blocking wait in the check is the direct RequestResponse warm-up Invoke of the relay function, which retries for up to 60 s while the invocation reports FunctionError; an open issue reports the emulator's python Lambda runtime ships no AWS SDK, which would fault that boto3 handler on import and consume the whole budget before any EventBridge assertion runs. Either way the effects above are the requirement, and the sibling cloudfront__events issues record the same rule-to-Lambda dispatch and DLQ paths as inert.

Why: a client wiring a CloudFront invalidation pipeline this way loses every event and every signal about the loss. PutEvents reports success, the invalidation Lambda is never invoked, no FailedInvocations/DLQ record distinguishes "pattern did not match" from "matched but undelivered", and the ERROR_CODE a remediation routine branches on (NO_PERMISSIONS -> add the resource policy) never exists. Conversely, code that treats a DLQ record as proof the target never ran would be wrong on real AWS, where a handler exception never dead-letters at the rule — an emulator that produces nothing at all lets both the correct and the incorrect assumption pass unchallenged, and DLQ-depth alarms stay flat while 100% of traffic is dropped.

Fix: the EventBridge target-dispatch component for rules on the default bus and its failure path — (a) match an accepted PutEvents entry against each ENABLED rule's EventPattern and invoke each matching Lambda target asynchronously under the target's permission check, completing delivery before the handler's outcome is known; (b) on a delivery refused because the target's resource policy does not admit events.amazonaws.com for the rule ARN, exhaust RetryPolicy and write the original envelope to Target.DeadLetterConfig.Arn with message attributes RULE_ARN, TARGET_ARN, ERROR_CODE=NO_PERMISSIONS (and ERROR_MESSAGE); (c) do NOT dead-letter at the rule when the invoked handler itself raises — that outcome belongs to the Lambda invocation, whose handler output must reach /aws/lambda/<functionName>. The Lambda python runtime's SDK availability is in scope only insofar as it blocks the relay handler used as the positive control.

Traces: cloudfront__events.eventbridge-lambda-invalidation-failure-routes-to-dlq (group error-propagation).

Replay of suite simparity-behavioral-aws-v1: 335/791 passed (42.4%), 404 mismatched + 52 errored. Service cloudfront__events: 11/55 (20%), 44 failed; 43 of those are marked OWNED by an open issue or ALREADY FILED (stub-blocked) and were skipped. The single remaining failure is the one below.

[mismatch] cloudfront__events.eventbridge-lambda-invalidation-failure-routes-to-dlq — "Error: Check timed out after 60.0s".

Setup, all accepted by the emulator: a DLQ and an observation ("ok") queue created, ARNs read; an SQS Policy set on the DLQ allowing Principal {Service: events.amazonaws.com} sqs:SendMessage on the DLQ ARN under Condition ArnEquals aws:SourceArn = [rule_fail_arn, rule_ok_arn, rule_permfail_arn]; two IAM roles trusting lambda.amazonaws.com with AWSLambdaBasicExecutionRole (the relay role additionally granted sqs:SendMessage on the observation queue); a python3.12 function whose handler raises Exception('simulated CreateInvalidation failure'); a python3.12 relay function whose handler does boto3 sqs.send_message(MessageBody=json.dumps(event)); three ENABLED rules on the default bus with patterns {"source":["sim2real.cloudfront"],"detail":{"invalidationMarker":[<marker>]}} for marker_ok / marker_fail / marker_permfail; lambda.AddPermission(Action lambda:InvokeFunction, Principal events.amazonaws.com, SourceArn <rule arn>) for the fail rule and the ok rule only — deliberately NOT for the permfail rule; three PutTargets calls, each one target {Id:"target-1", Arn:<fn arn>, DeadLetterConfig:{Arn:<dlq arn>}, RetryPolicy:{MaximumRetryAttempts:0, MaximumEventAgeInSeconds:60}}; one PutEvents with three entries (Source sim2real.cloudfront, DetailType "AWS API Call via CloudTrail", Detail {"eventName":"CreateInvalidation","invalidationMarker":<marker>}).

Expected (AWS):
1. positive control — ReceiveMessage on the observation queue returns a message whose body is the event envelope with detail.invalidationMarker == marker_ok (poll budget 60 s);
2. side channel — logs.FilterLogEvents on /aws/lambda/<raising function> matches the filter pattern "simulated CreateInvalidation failure" (poll budget 60 s), proving the raising handler really ran;
3. twin control — draining the DLQ for 30 s yields exactly the marker_permfail envelope, with MessageAttributes RULE_ARN == the permfail rule ARN, TARGET_ARN == the relay function ARN, ERROR_CODE == "NO_PERMISSIONS";
4. main assertion — across an absence window of max(3 x the measured dead-letter latency, 20 s) capped at 60 s, the marker_fail envelope NEVER appears in the DLQ, because EventBridge's invocation of Lambda is asynchronous and the handler's exception is not a delivery failure.

Actual (emulator): none of 1-4 is observable. No message ever reaches the observation queue, no log event ever matches in the raising function's log group, and the DLQ stays empty, so the harness kills the check at the 60 s cap before any assertion is evaluated. No refusal is produced anywhere: there is no HTTP status, error code or error message that diverges — every call returns 2xx and no effect follows.

Not environment-dependent: the generated queue, role, function and rule names, the account id, the per-run markers, the measured latency and the host/port differ on every run and are not part of the requirement. The requirements are the three effects named above: delivery to a permitted Lambda target (with its log output), a NO_PERMISSIONS dead-letter record carrying RULE_ARN and TARGET_ARN for an unpermitted one, and the ABSENCE of a dead-letter record when the invoked handler itself raises.

## Steps to Reproduce
1. git clone the repo and boot the emulator built from it.
2. Replay suite simparity-behavioral-aws-v1, service cloudfront__events, check eventbridge-lambda-invalidation-failure-routes-to-dlq.
3. Create two SQS queues (a DLQ and an observation queue) and read their ARNs. Set a Policy on the DLQ allowing Principal {Service: events.amazonaws.com} to sqs:SendMessage on it with Condition ArnEquals aws:SourceArn = the three rule ARNs created in step 5.
4. Create two IAM roles trusting lambda.amazonaws.com with AWSLambdaBasicExecutionRole attached; give the second an inline sqs:SendMessage grant on the observation queue. Create a python3.12 function A whose handler raises Exception('simulated CreateInvalidation failure'), and a python3.12 function B whose handler relays its event to the observation queue with boto3 sqs.send_message. Wait for both to reach State Active and confirm a direct RequestResponse Invoke of B succeeds (today this is where the check stalls).
5. events.PutRule three ENABLED rules on the default bus with EventPattern {"source":["sim2real.cloudfront"],"detail":{"invalidationMarker":[<markerOk|markerFail|markerPermfail>]}}.
6. lambda.AddPermission(Action lambda:InvokeFunction, Principal events.amazonaws.com, SourceArn <rule arn>) for the fail rule on A and the ok rule on B. Grant nothing for the permfail rule.
7. events.PutTargets for each rule with one target {Id:"target-1", Arn:<A or B>, DeadLetterConfig:{Arn:<dlq arn>}, RetryPolicy:{MaximumRetryAttempts:0, MaximumEventAgeInSeconds:60}} — the permfail rule targets B.
8. events.PutEvents with three entries, one per marker (Source sim2real.cloudfront, DetailType "AWS API Call via CloudTrail", Detail {"eventName":"CreateInvalidation","invalidationMarker":<marker>}); assert FailedEntryCount == 0.
9. Poll ReceiveMessage on the observation queue for up to 60 s.
   Expected: one message whose detail.invalidationMarker == markerOk. Actual: nothing arrives.
10. Poll logs.FilterLogEvents(logGroupName="/aws/lambda/<A>", filterPattern='"simulated CreateInvalidation failure"') for up to 60 s.
   Expected: at least one event. Actual: no event ever matches.
11. Drain the DLQ for 30 s with ReceiveMessage(MaxNumberOfMessages=10, WaitTimeSeconds=5, MessageAttributeNames=["All"]).
   Expected: exactly the markerPermfail envelope, with MessageAttributes RULE_ARN == the permfail rule ARN, TARGET_ARN == B's ARN and ERROR_CODE == "NO_PERMISSIONS", and NO markerFail message. Actual: the DLQ is empty, so neither the record nor its absence counterpart can be checked, and the check is killed at the harness's 60 s cap.
