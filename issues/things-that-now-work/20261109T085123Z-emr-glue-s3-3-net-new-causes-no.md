# emr__glue__s3: 3 net-new causes — no "Glue Job State Change" event is published, StartJobRun never validates script accessibility, and a role Glue cannot assume still runs to SUCCEEDED

> _Note: this issue was identified against the code base at commit `4ca728998286b7558a3f8204f86decdeb692036b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobRun

## Description
Three net-new root causes in the emr__glue__s3 group. All were reached after the control plane answered normally (CreateBucket/PutObject, IAM CreateRole/AttachRolePolicy, glue CreateJob, glue StartJobRun, events PutRule/PutTargets, sqs CreateQueue/SetQueueAttributes all succeeded) and after the positive-control job run settled, so none is a bootstrap gap or an unimplemented-stub failure.

Cause 1 of 3 — a terminal Glue job run publishes no "Glue Job State Change" EventBridge event, so no rule delivers to its target.
AWS: recorded behavior only for the emission (Glue's Smithy model gives the job-run surface — JobRun.JobRunState is a JobRunState enum, JobRun.JobName/Id are its identity — but not EventBridge publication). The recordings show that a run reaching SUCCEEDED produces an event with source "aws.glue", detail-type "Glue Job State Change" and a detail object carrying at least jobName and state, which EventBridge delivers to an SQS target whose queue policy grants events.amazonaws.com, and withholds from a sibling queue that has no such policy.
Emulator: nothing is ever published. In both checks the target queue (including the control queue that DOES carry the resource policy) stays empty and the poll fails with 'Last result: []' after 120s.
Why: every Glue-driven EventBridge pipeline is silently inert while the job run itself reports SUCCEEDED, so a client gets no signal that its post-job notification, chained job, or audit archive never happened; and the negative check cannot even be evaluated, because the missing-permission case is indistinguishable from the control that should have been delivered.
Fix: the Glue job-run state machine must publish a "Glue Job State Change" event on every terminal transition (services/service-com-amazonaws-glue-awsglue, the job-run executor behind StartJobRun/GetJobRun) and hand it to the EventBridge default bus for pattern matching and target delivery (services/service-com-amazonaws-eventbridge-awsevents). Open issues that do NOT cover this: 20261025T031335Z-glue-job-runs-never-execute-and-publish-no.md and 20261025T072821Z-glue-job-runs-are-terminated-failed-without-executing.md both premise the absent event on runs never executing, whereas here runs execute and succeed; 20261103T101621Z-athena-glue-s3-glue-publishes-no-glue-crawler-state-change-eventbridge.md covers the CRAWLER event.
Traces: emr__glue__s3.eventbridge-glue-job-state-change-triggers-rule-positive, emr__glue__s3.eventbridge-rule-missing-target-permission-negative.

Cause 2 of 3 — StartJobRun does not verify that the execution role can read the job's ScriptLocation, so a run whose role cannot fetch the script executes anyway.
AWS: recorded behavior only (Smithy models JobCommand.ScriptLocation as 'Specifies the Amazon Simple Storage Service (Amazon S3) path to a script that executes a job' and JobRun.ErrorMessage as ErrorString). The recording shows that when the role's permissions do not allow reading the script object, the run settles FAILED before any user code runs and ErrorMessage is Glue's script-access failure, whose fixed text is "Script file doesn't exist" and whose variable part is the script object the job's ScriptLocation names (here an `etl.py`). The role in this check carries only the AWSGlueServiceRole managed policy, which cannot read an arbitrary bucket's script.
Emulator: the script-accessibility precondition is never evaluated. The run proceeds, executes the script body under the role, and the failure that is reported is the DOWNSTREAM in-script S3 refusal instead: ErrorMessage was `AccessDenied: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account-id>:assumed-role/<role-name>/<job-name> is not authorized to perform: s3:PutObject on resource: "arn:aws:s3:::<bucket>/output/limited.txt" because no identity-based policy allows the s3:PutObject action`.
Why: the run's diagnostic attributes the failure to the wrong thing — an operator reading it adds an s3:PutObject grant to the output prefix and the job still cannot start in real AWS, because the actual blocker is that Glue cannot read the script. It also means a job whose script the role cannot fetch appears to have run user code, which real AWS never does.
Fix: StartJobRun's run admission must resolve JobCommand.ScriptLocation and authorize/fetch it under the execution role before dispatch, failing the run with Glue's "Script file doesn't exist" message naming that script object (services/service-com-amazonaws-glue-awsglue job-run executor, consulting the S3 crate services/service-com-amazonaws-s3-amazons3 and the IAM evaluator).
Traces: emr__glue__s3.cfn-deploy-glue-job-role-missing-s3-access-negative.

Cause 3 of 3 — StartJobRun never evaluates the execution role's trust policy, so a job whose role Glue cannot assume runs to SUCCEEDED.
AWS: Smithy models Job.Role as the role Glue assumes for the run; recorded behavior shows that a role whose AssumeRolePolicyDocument does not name the glue.amazonaws.com service principal (it trusts the account root, or ec2.amazonaws.com) cannot be assumed, the run settles FAILED, ErrorMessage names the assume-role failure (the real-AWS wording recorded in these checks matches /assume\s*role|not authorized|access.?denied/ — e.g. "…should be given assume role permissions for Glue Service."), and the job writes nothing to S3.
Emulator: both mistrusted runs settle 'SUCCEEDED' with no ErrorMessage at all, indistinguishable from the positive control whose role trusts glue.amazonaws.com. Replay: AssertionError: expected FAILED, got {... 'JobRunState': 'SUCCEEDED', 'ExecutionTime': 1, 'GlueVersion': '5.1'} — no ErrorMessage member present.
Why: a trust-policy misconfiguration — one of the most common Glue deployment faults, and the thing cross-account setups get wrong — produces a green run on the emulator and a failed run in AWS. Negative deployment tests pass against the emulator, and nothing tells a client its role is unassumable.
Fix: StartJobRun must resolve the job's Role and evaluate its AssumeRolePolicyDocument for glue.amazonaws.com (including the cross-account case, where trusting the account root is not sufficient) before dispatching the run (services/service-com-amazonaws-glue-awsglue job-run executor consulting services/service-com-amazonaws-iam-awsidentitymanagementv20100508). Open issue that does NOT cover this: 20261030T000623Z-glue-job-runs-never-execute-so-a-role.md describes the inverse state, where no run executed at all; here runs execute and succeed with the trust policy never consulted.
Traces: emr__glue__s3.glue-job-role-cross-account-trust-mismatch-rejected, emr__glue__s3.glue-job-start-with-role-missing-glue-trust-rejected.

## Evidence
Cause 1 — expected: after a pythonshell run settles SUCCEEDED, the SQS queue targeted by a rule matching {"source":["aws.glue"],"detail-type":["Glue Job State Change"]} and whose queue policy grants events.amazonaws.com receives one message whose detail names the job and state SUCCEEDED; the sibling queue without that policy receives none. Actual: nothing arrives on either queue. Replay: AssertionError 'eventbridge delivery of Glue Job State Change to SQS not met within 120s. Last result: []' (check line 134) and AssertionError 'control queue (with resource policy) receives the EventBridge delivery not met within 120s. Last result: []' (check line 157).

Cause 2 — expected: the limited-role job run's JobRun.ErrorMessage is Glue's script-access failure containing the fixed text "Script file doesn't exist" and naming the ScriptLocation object (etl.py). Actual: 'AccessDenied: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account-id>:assumed-role/<limited-role>/<limited-job> is not authorized to perform: s3:PutObject on resource: "arn:aws:s3:::<bucket>/output/limited.txt" because no identity-based policy allows the s3:PutObject action' — the script was fetched and executed. AssertionError at check line 164: 'limited-role job failed for the wrong reason … expected Glue's script-access error naming etl.py'.

Cause 3 — expected: GetJobRun reports JobRunState 'FAILED' with an assume-role ErrorMessage and no S3 object written, for (a) a role trusting the account root instead of glue.amazonaws.com and (b) a role trusting ec2.amazonaws.com. Actual in both: JobRunState 'SUCCEEDED', ExecutionTime 1, no ErrorMessage. AssertionError 'expected FAILED, got: {...JobRunState: SUCCEEDED...}' at check lines 66 and 53 respectively.
