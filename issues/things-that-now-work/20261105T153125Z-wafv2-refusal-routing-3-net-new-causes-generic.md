# wafv2 refusal routing: 3 net-new causes — generic constraint validation preempts the CLOUDFRONT-scope refusal on UpdateWebACL, GetTopPathStatisticsByTraffic reports SCOPE_VALUE instead of RESOURCE_ARN, and PutManagedRuleSetVersions misclassifies a nonexistent target

> _Note: this issue was identified against the code base at commit `b4c7b193ddb13157abcfba68f6253714324575f6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutManagedRuleSetVersions

## Description
Three net-new root causes in the wafv2 refusal-selection layer: for each, the emulator returns HTTP 400 as AWS does, but picks the wrong exception class or the wrong WAFInvalidParameterException detail/message, so a caller branching on the WAF error class is sent down the wrong path. These are distinct from the already-open wafv2 refusal issues: 20261102T094456Z-wafv2-scope-and-identifier-validation-refusals-carry-the.md covers UpdateWebACL/GetWebACL/ListWebACLs scope refusals answering WAFNonexistentItemException (a different wrong class than cause 1's ValidationException, and it says nothing about constraint-validation ordering); 20261026T120000Z-wafv2-two-refusals-carry-the-right-class-but-not-wafs-own-sentence.md covers PutManagedRuleSetVersions' invalid version-KEY message with the right class, whereas cause 3 is the wrong class entirely; 20261030T002309Z-wafv2-refusals-carry-the-wrong-class-or-not.md and 20261030T002309Z-wafv2-write-path-validation-is-over-permissive-seven.md carry none of the replay keys below. The replay report marked none of the four checks below as owned or stub-blocked. All three causes must be closed before submitting.

Cause 1 of 3: UpdateWebACL (and DeleteWebACL) with Scope=CLOUDFRONT outside us-east-1 — the generic member-constraint reporter fires before WAF's scope precondition.
AWS: Smithy: UpdateWebACL and DeleteWebACL both model WAFInvalidParameterException (client, httpError 400) with members message/Field/Parameter/Reason; ParameterExceptionField includes SCOPE_VALUE; Scope is @required enum [CLOUDFRONT, REGIONAL] and CLOUDFRONT is only usable in us-east-1. UpdateWebACL.LockToken and DeleteWebACL.LockToken target LockToken with @length 1..36 and @pattern ^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$. Recorded behavior: in a region that is not us-east-1, ListWebACLs, GetWebACL, UpdateWebACL and DeleteWebACL with Scope=CLOUDFRONT all answer the identical WAFInvalidParameterException whose message is "Error reason: The scope is not valid., field: SCOPE_VALUE, parameter: CLOUDFRONT" — and they answer it BEFORE any lock-token or existence check, i.e. even when LockToken is syntactically invalid. In that message the fixed text is "Error reason: ", ", field: " and ", parameter: "; the variable parts are the reason sentence, the field token (SCOPE_VALUE) and the offending scope value taken from the request.
Emulator: the same check's earlier ListWebACLs and GetWebACL assertions pass (the emulator does produce the scope refusal there), but UpdateWebACL with Scope=CLOUDFRONT and a non-UUID LockToken answers ('ValidationException', "1 validation error detected: Value 'not-a-real-lock-token' at 'lockToken' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$") — a class that is not in the wafv2 model at all, with no Field/Parameter/Reason. The check stops at that assertion, so the identical DeleteWebACL call (same scope precondition, same LockToken pattern) is not separately observed but goes through the same validator and must be fixed with it.
Why: a client that catches WAFInvalidParameterException to correct the scope (or reads Field/Parameter to point at the bad input) instead gets an unmodeled ValidationException about a lock token, so it re-fetches a fresh LockToken and retries forever against a region where CLOUDFRONT scope can never work. It also makes the refusal class depend on whether an unrelated member happened to be well-formed.
Fix: UpdateWebACL's and DeleteWebACL's input validation — the Scope precondition must be evaluated before the shared member-constraint reporter and before lock-token/existence checks, and the refusal must be built by the WAFInvalidParameterException serializer so Field/Parameter/Reason are emitted.
Traces: wafv2.dsw-cloudfront-scope-outside-us-east-1-rejected.

Cause 2 of 3: GetTopPathStatisticsByTraffic with Scope=CLOUDFRONT and a REGIONAL WebAcl ARN — the refusal names the wrong field and reason.
AWS: Smithy: GetTopPathStatisticsByTraffic models WAFInvalidParameterException (client, 400); WebAclArn is @required targeting ResourceArn (@length 20..2048, @pattern \\S); ParameterExceptionField includes RESOURCE_ARN. Recorded behavior: when the supplied WebAclArn does not belong to the requested Scope, WAF refuses on the ARN, not on the scope: WAFInvalidParameterException with message "Error reason: The ARN isn't valid. A valid ARN begins with arn: and includes other information separated by colons or slashes., field: RESOURCE_ARN, parameter: <the WebAclArn exactly as supplied>". Fixed text: "Error reason: The ARN isn't valid. A valid ARN begins with arn: and includes other information separated by colons or slashes., field: RESOURCE_ARN, parameter: "; the only variable part is the ARN from the request. The matching Scope=REGIONAL call on the same web ACL succeeds and reports TotalRequestCount 0 with an empty PathStatistics list.
Emulator: the class is right (WAFInvalidParameterException, so the code assertion passes) but the message is the scope refusal: "Error reason: The scope is not valid., field: SCOPE_VALUE, parameter: CLOUDFRONT" — wrong Reason, wrong Field, and Parameter echoes the scope rather than the ARN.
Why: the Field/Parameter members exist so a caller can report which input to fix. A client told SCOPE_VALUE/CLOUDFRONT retries with a different scope, when the request AWS rejects is the ARN/scope pairing and the fix is to pass the ARN of a web ACL in that scope. Automation that keys remediation off Field remediates the wrong parameter.
Fix: GetTopPathStatisticsByTraffic's handler validation — the WebAclArn-versus-Scope precondition must raise the RESOURCE_ARN invalid-ARN refusal (reason sentence, Field RESOURCE_ARN, Parameter = the supplied ARN) instead of falling through to the shared scope validator's refusal.
Traces: wafv2.get-top-path-statistics-pricing-plan-denied.

Cause 3 of 3: PutManagedRuleSetVersions against a ManagedRuleSet that does not exist answers WAFInvalidParameterException instead of WAFNonexistentItemException.
AWS: Smithy: PutManagedRuleSetVersions models both WAFInvalidParameterException and WAFNonexistentItemException (client, httpError 400); Name/Scope/Id/LockToken are all @required, with Id and LockToken constrained to the UUID pattern ^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$. Recorded behavior: with a well-formed but unknown Name/Id (and a well-formed LockToken), the call is refused WAFNonexistentItemException with the message "AWS WAF couldn\u2019t perform the operation because your resource doesn\u2019t exist." — that sentence is entirely fixed text, with a U+2019 right single quotation mark in "couldn\u2019t" and "doesn\u2019t", no variable parts. The target-existence check runs before the VersionsToPublish contents are examined, so a nonexistent AssociatedRuleGroupArn in the map does not change the class: the same WAFNonexistentItemException and message are returned. Nothing is published in either case (ListManagedRuleSets shows no entry for that Name or Id afterwards), and ListAvailableManagedRuleGroups continues to succeed with a non-empty catalog.
Emulator: both requests are refused WAFInvalidParameterException instead of WAFNonexistentItemException.
Why: WAFNonexistentItemException and WAFInvalidParameterException mean opposite things to a caller. A publisher that catches WAFNonexistentItemException to create the managed rule set and then retry never sees it; it reads WAFInvalidParameterException as "my request body is malformed" and fails the publish permanently instead of provisioning the missing rule set. The two classes are also retried differently by SDK/user error handling.
Fix: PutManagedRuleSetVersions' handler — look up the target ManagedRuleSet by Scope+Name+Id first and raise WAFNonexistentItemException with WAF's resource-doesn't-exist sentence when it is absent, ahead of any VersionsToPublish / AssociatedRuleGroupArn parameter validation; only a request whose target exists may be refused WAFInvalidParameterException.
Traces: wafv2.put-managed-rule-set-versions-invalid-version-format-rejected, wafv2.put-managed-rule-set-versions-nonexistent-rule-group-rejected.
