# athena: 2 net-new causes — an integer+varchar expression silently SUCCEEDS instead of failing the execution, and CTAS `CREATE TABLE ... WITH (...) AS SELECT` is refused as a SQLite syntax error

> _Note: this issue was identified against the code base at commit `a45eebcdd8d9a9d0a1f0906c2cbe25c9ebaa13ba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartQueryExecution

## Description
Two net-new root causes in the Athena data plane, both reached through StartQueryExecution/GetQueryExecution against an EXTERNAL TABLE over a CSV object in S3. Neither failing check was marked OWNED or ALREADY FILED by the suite. Related open issues that do NOT carry these checks' replay keys: 20261111T090701Z-athena-s-sql-engine-refuses-trino-hive-statements.md (its Cause 8 is CAST of non-numeric text, not arithmetic-operator type analysis; its Cause 1/6 describe the CTAS and qualified-name gaps but neither of the two checks below is listed in it), 20261111T040849Z-athena-s3-athena-s-sql-engine-parses-neither-ctas-with.md (filed under service athena__s3) and 20261104T163600Z-athena-statements-are-executed-by-a-sqlite-engine.md.

Cause 1 of 2: an expression that mixes incompatible types (integer + varchar) is silently evaluated instead of failing the query.
AWS: Athena's Trino engine rejects an arithmetic operator applied to operands with no such operator during query analysis, so the execution settles in the terminal state FAILED (Smithy: QueryExecutionStatus.State, enum QueryExecutionState QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED) and carries the failure envelope: Status.StateChangeReason explains the type error, and Status.AthenaError is present with ErrorCategory 2 (User — per the Smithy doc on AthenaError.ErrorCategory, 1=System, 2=User, 3=Other; @range 1-3), Retryable false (Smithy: AthenaError.Retryable, default false) and an integer ErrorType (Smithy: AthenaError.ErrorType, @range 0-9999). The message is Trino's type-mismatch form — fixed text `line <l>:<c>: '<operator>' cannot be applied to <left type>, <right type>`; the line/column, the operator and the two type names are variable parts taken from the submitted statement and the referenced columns' catalog types, never from one recorded run. Recorded behavior only for the exact ErrorType integer.
Emulator: the execution settles SUCCEEDED, with no StateChangeReason and no AthenaError at all — the underlying SQLite engine coerces the varchar operand to a number and returns a row. Observed for `SELECT id + name AS bad FROM "<db>"."<tbl>"` where `id` is int and `name` is string. The sibling legs of the same check (a missing table and a missing column) do reach FAILED, so only the type-mismatch class of SQL defect is undetected.
Why: a client that submits a statement AWS refuses receives a SUCCEEDED query and reads fabricated numeric values (the coerced 0) as if they were real results. The defect is silent: there is no state, no reason and no AthenaError to inspect, so neither an application nor a SQL tool can tell that its query was never valid, and bad input data is never surfaced. It also makes the three error classes AWS distinguishes (name error vs. type error) indistinguishable.
Fix: expression type analysis in the Athena query-execution engine's SQL front end (the component StartQueryExecution hands the statement to) — an operator applied to operands it has no signature for must abort the execution — together with the failure path that populates Status.State=FAILED, Status.StateChangeReason and the Status.AthenaError envelope.
Traces: athena.failed-query-error-classification-distinguishes-causes.

Cause 2 of 2: CTAS with table properties, `CREATE TABLE <name> WITH (...) AS SELECT ... GROUP BY ... HAVING ...`, is refused as a syntax error.
AWS: Athena accepts `CREATE TABLE "<db>"."<dest>" WITH (format = 'TEXTFILE', external_location = 's3://<bucket>/<prefix>/') AS SELECT <cols>, <agg> FROM "<db>"."<src>" GROUP BY <col> HAVING <agg predicate>` and settles it SUCCEEDED, materialising a queryable table whose rows are exactly the HAVING-filtered groups and whose data files land under `external_location`. Recorded behavior only for the exact table-property list; the statement form is Athena's documented CTAS syntax.
Emulator: the execution settles FAILED with Status.StateChangeReason of the form `near "WITH": syntax error in <the submitted statement> at offset <n>` — a SQLite parser diagnostic whose fixed text is `near "WITH": syntax error in ` plus the echoed statement plus ` at offset ` plus an offset, the statement and offset being the variable parts. No table is created, so the subsequent SELECT over the destination cannot run. The echoed statement additionally shows the submitted two-part quoted name `FROM "<db>"."<src>"` rewritten as a single quoted identifier `FROM "<db>.<src>"`, so the name would resolve against a table literally called `<db>.<src>` even once the parser accepted the statement.
Why: CTAS is the documented way to materialise a derived or reformatted dataset, and a client gets a FAILED query plus a parser error that names no fixable mistake in SQL that AWS accepts; every downstream read of the destination table then fails too. The same check's earlier legs pass (the GROUP BY aggregate equals the independently computed per-group count/sum/min/max, DataScannedInBytes matches the uploaded bytes, the aggregate ColumnInfo types are right, and HAVING filters groups server-side), so the CTAS is the sole divergence it reaches.
Fix: the SQL parser/translation layer of the Athena query-execution engine in services/service-com-amazonaws-athena-amazonathena — CTAS table properties must parse, qualified-name handling must preserve a two-part quoted identifier rather than collapsing it — plus the table-creation side effect that registers the new table in the catalog and writes its rows under `external_location`.
Traces: athena.group-by-aggregation-matches-independently-computed-values.

## Evidence
Cause 1 — check athena.failed-query-error-classification-distinguishes-causes.
Setup: a results bucket, a data bucket holding one CSV of `1,alpha,10.5,true` style rows, `CREATE DATABASE`, and `CREATE EXTERNAL TABLE `<db>`.`<tbl>` (`id` int, `name` string, `amount` double, `active` boolean) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE LOCATION 's3://<data-bucket>/data/'`.
Statement: `SELECT id + name AS bad FROM "<db>"."<tbl>"`.
Expected: GetQueryExecution Status.State == 'FAILED', Status.StateChangeReason a non-empty message naming the operator/type mismatch, Status.AthenaError present with ErrorCategory == 2, Retryable is False, ErrorType an int.
Actual: Status.State == 'SUCCEEDED'. Suite assertion: `AssertionError: type-error: expected the required terminal FAILED for 'SELECT id + name AS bad FROM "<db>"."<tbl>"', got SUCCEEDED`. The two sibling legs of the same check — `SELECT id FROM "<db>"."<no_such_table>"` and `SELECT <no_such_column> FROM "<db>"."<tbl>"` — both reached FAILED, so the envelope exists on other failure paths and is absent only because this query is not failed at all.

Cause 2 — check athena.group-by-aggregation-matches-independently-computed-values.
Statement: `CREATE TABLE "<db>"."<dest>" WITH (format = 'TEXTFILE', external_location = 's3://<data-bucket>/dest/') AS SELECT category, sum(amount) AS total FROM "<db>"."<src>" GROUP BY category HAVING sum(amount) > <threshold>`.
Expected: Status.State == 'SUCCEEDED' and `SELECT category, total FROM "<db>"."<dest>" ORDER BY category` then returning one row per HAVING-kept group with its computed sum.
Actual: Status.State == 'FAILED' with StateChangeReason `near "WITH": syntax error in CREATE TABLE "<db>"."<dest>" WITH (format = 'TEXTFILE', external_location = 's3://<data-bucket>/dest/') AS SELECT category, sum(amount) AS total FROM "<db>.<src>" GROUP BY category HAVING sum(amount) > 10 at offset 81`. Note the submitted `FROM "<db>"."<src>"` is echoed as `FROM "<db>.<src>"` — one collapsed identifier. The preceding legs of the check passed: the GROUP BY aggregate matched the per-group oracle, DataScannedInBytes equalled the uploaded byte count, ColumnInfo reported {category: varchar, n: bigint, total: bigint, lo: bigint, hi: bigint}, and HAVING kept exactly the expected groups.

## Steps to Reproduce
1. Build and boot the emulator and point a botocore `athena` client (and an `s3` client) at it.
2. Create a results bucket and a data bucket in the emulator's S3. Upload a small CSV to `s3://<data-bucket>/data/rows.csv` with rows of the form `<int>,<string>,<double>,<bool>`.
3. Via StartQueryExecution with ResultConfiguration.OutputLocation = `s3://<results-bucket>/results/`, run `CREATE DATABASE `<db>`` and then `CREATE EXTERNAL TABLE `<db>`.`<tbl>` (`id` int, `name` string, `amount` double, `active` boolean) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE LOCATION 's3://<data-bucket>/data/'`. Poll GetQueryExecution until each is SUCCEEDED.
4. Cause 1: submit `SELECT id + name AS bad FROM "<db>"."<tbl>"` with QueryExecutionContext.Database = `<db>` and poll GetQueryExecution to a terminal state. Observe Status.State == 'SUCCEEDED' with no StateChangeReason and no AthenaError, where AWS settles FAILED with a type-mismatch reason and an AthenaError of ErrorCategory 2 / Retryable false / an integer ErrorType. For contrast, submit `SELECT id FROM "<db>"."<no_such_table>"` and `SELECT <no_such_column> FROM "<db>"."<tbl>"`: both do reach FAILED.
5. Cause 2: upload a second CSV of `<int>,<category>,<bigint>` rows to `s3://<data-bucket>/src/rows.csv`, register it as `CREATE EXTERNAL TABLE `<db>`.`<src>` (`id` int, `category` string, `amount` bigint) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE LOCATION 's3://<data-bucket>/src/'`, then submit `CREATE TABLE "<db>"."<dest>" WITH (format = 'TEXTFILE', external_location = 's3://<data-bucket>/dest/') AS SELECT category, sum(amount) AS total FROM "<db>"."<src>" GROUP BY category HAVING sum(amount) > <threshold>` and poll GetQueryExecution. Observe State FAILED with the `near "WITH": syntax error in ... at offset <n>` reason, and that the echoed statement collapses `"<db>"."<src>"` into `"<db>.<src>"`. A following `SELECT category, total FROM "<db>"."<dest>"` then fails because no destination table was created.
