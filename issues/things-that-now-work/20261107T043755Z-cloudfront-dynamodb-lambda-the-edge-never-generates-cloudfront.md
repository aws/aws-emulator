# cloudfront__dynamodb__lambda: the edge never generates CloudFront-Viewer-Country / CloudFront-Forwarded-Proto for an origin request policy that whitelists them

> _Note: this issue was identified against the code base at commit `12bd58142e134c788a6e6e722018c3787d666c1f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateOriginRequestPolicy (edge-generated headers on the origin request)

## Description
This issue carries 1 net-new root cause.

Cause 1 of 1: a cache behaviour whose origin request policy whitelists the edge-generated headers CloudFront-Viewer-Country and CloudFront-Forwarded-Proto receives neither of them at the origin; the origin sees them absent even though the viewer request reached the edge over a known scheme.
Failing check ids for this cause: cloudfront__dynamodb__lambda.deep-cloudfront-3-cf-origin-edge-generates-viewer-country-and-forwarded-proto.

AWS: recorded behavior only — the CloudFront Smithy model describes OriginRequestPolicyConfig.HeadersConfig (HeaderBehavior=whitelist with the Headers list) but says nothing about header values. The recording shows that these two headers are generated by the edge, not forwarded from the client: for a viewer that never sent them, the origin receives CloudFront-Viewer-Country as an ISO 3166-1 alpha-2 code (two uppercase letters, resolved from the viewer, the same value for the same viewer on both schemes) and CloudFront-Forwarded-Proto as exactly the viewer's scheme — "https" for an https viewer request and "http" for a plain http one. A behaviour with no origin request policy receives neither header.
Emulator: the origin sees no cloudfront-viewer-country header at all (the echoed value is None, failing "the edge must generate CloudFront-Viewer-Country (an ISO 3166 alpha-2 code) for a client that never sent it; the origin saw None"), so the scheme-dependent CloudFront-Forwarded-Proto assertions behind it are never reached either.
Why: origins and Lambda backends that branch on viewer geography or on the original viewer scheme (geo routing, country-specific content, redirect-to-https logic, and cache keys built from these headers) see nothing and silently fall back to a default path; a whitelisted edge header that is documented to always be present becomes optional, so correct origin code breaks only behind CloudFront.
Fix: the CloudFront edge request path — the component that augments the origin request with edge-generated headers before applying the origin request policy's whitelist (viewer country resolution and the viewer-scheme-derived CloudFront-Forwarded-Proto), keeping them absent when the behaviour has no origin request policy naming them.
Traces: cloudfront__dynamodb__lambda.deep-cloudfront-3-cf-origin-edge-generates-viewer-country-and-forwarded-proto.

## Evidence
Expected (recorded AWS): GET https://<domain>/edge/secure -> the origin sees cloudfront-viewer-country matching ^[A-Z]{2}$ and cloudfront-forwarded-proto == 'https'; GET http://<domain>/edge/plain -> cloudfront-forwarded-proto == 'http' and the same country value; GET https://<domain>/bare (no origin request policy) -> neither header present.

Actual (emulator): AssertionError: the edge must generate CloudFront-Viewer-Country (an ISO 3166 alpha-2 code) for a client that never sent it; the origin saw None.

## Steps to Reproduce
1. Create a cache policy and an origin request policy with HeadersConfig {HeaderBehavior: whitelist, Headers: [CloudFront-Viewer-Country, CloudFront-Forwarded-Proto]}; create a distribution with an echo (Lambda) origin, a /edge/* behaviour using that origin request policy and a default behaviour without one.
2. GET https://<domain>/edge/secure and inspect the headers the origin echoed: cloudfront-viewer-country is absent (AWS sends a two-letter country code) and cloudfront-forwarded-proto is absent (AWS sends 'https'); repeat over http://<domain>/edge/plain (AWS sends 'http').
