# API Gateway REST list envelopes: empty collections, position tokens, echoed limit and the paged window (7 causes)

> _Note: this issue was identified against the code base at commit `2294bca91bc8bfde7308721c1d7853ded4942c2e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDocumentationParts

## Description
Seven net-new wire divergences on the API Gateway REST control plane (service token `apigateway`) share one area: the `position`/`limit` collection envelope every `Get*` listing of this service is served through, and the window that envelope is cut over. All seven answer the correct HTTP status; only the envelope and the page contents diverge.

Shared shape of the defect. Every paginated REST collection here is paged by one helper, `crate::state::Page` (`Page::cut`, `Page::echoed_limit`, services/service-com-amazonaws-apigateway-backplanecontrolservice/src/state.rs), and its contract differs from AWS's on three independent points: (a) an empty collection is serialized as an empty array for the `item` member instead of the member being omitted; (b) `position` is reported for the LAST page of a walk (the helper's own comment states it reports "the cursor of the LAST element on this page, whether or not the sequence holds more"), where AWS reports a `position` only when further elements follow; (c) the response carries a `limit` member that the operations' output shapes do not declare at all (Smithy: `ApiKeys` declares `warnings`, `items` (jsonName `item`) and `position`; `DocumentationParts` declares `items` (jsonName `item`) and `position` — neither declares `limit`), injected by the `Paged<...>` output wrapper via `Page::echoed_limit`. On top of that the documentation-parts collection is ordered and narrowed differently from AWS, so a limited page holds a different part than AWS's and one created part is not reported at all.

Cause 1 of 7 — GetBasePathMappings returns an empty `item` array instead of omitting the member. AWS: Smithy `GetBasePathMappings` GET /domainnames/{domainName}/basepathmappings, success 200, output `BasePathMappings{items -> ListOfBasePathMapping (jsonName "item"), position}`; restJson1 omits members that are not set, and the recording shows the body of a domain name that carries no base path mapping is exactly `{}`. Emulator: 200 with body `{"item": []}`. Why: a client that distinguishes an absent collection member from a present-but-empty one (any SDK that exposes `item` as nullable, or a consumer that branches on presence to decide whether the domain name has ever been mapped) reads a shape AWS never emits, and a strict body comparison against AWS fails. Fix: the GetBasePathMappings handler in src/ops/ — leave the `items` member unset when the page holds nothing, the same rule the `non_empty_*` helpers in state.rs already apply to maps. Trace: apigateway-create-base-path-mapping-nonexistent-restapi-fails#task#4.

Cause 2 of 7 — the GetApiKeys `position` cursor is not of the recorded token's shape. AWS: Smithy `GetApiKeys` is `@paginated(inputToken: position, outputToken: position, items: items, pageSize: limit)` and `position` is documented only as "The current pagination position in the paged result set" — the concrete token is recorded behavior only; in the recording the token's shape is asserted (the fixture carries it as a shaped, not literal, value) and the emulator's value fails that shape. Emulator: 200 with `$.position` = `8sh3tqaaaa`, i.e. the bare minted id of the last API key on the page (`Page::cut` sets `next_position = ids.last()`). Hypothesis: AWS's cursor for this collection is an opaque encoded token rather than the raw resource id of the page's last element, so handing back a raw id both fails the token shape and leaks the resource identity into the cursor. Why: a client that validates or stores the cursor, or that treats a cursor as opaque and compares it against AWS's family, gets a value AWS does not emit. Trace: apigw-envelope-api-keys-position-walk#task#3.

Cause 3 of 7 — GetApiKeys reports `position` on the final page of a walk and also reports an unmodeled `limit`. AWS: the recorded final page of the walk carries NEITHER member — `position` is absent once there is nothing after the page (that absence is how a `position` walk terminates), and `limit` is not an output member of `ApiKeys` at all, so AWS never returns it. Emulator: 200 with `$.position` = `7qygd7aaaa` (unexpected_present) and `$.limit` = `1` (unexpected_present) on the page that ends the walk. Why: a client that loops "while position is present, request the next page" never terminates against the emulator — it re-requests pages forever — and a strict deserializer rejects the undeclared `limit`. Fix: the shared `Page` helper in state.rs plus the `Paged` output wrapper used by the listing handlers in src/ops/ — set `position` only when elements remain after the page, and never serialize a `limit` member. Trace: apigw-envelope-api-keys-position-walk#task#4.

Cause 4 of 7 — the GetDocumentationParts `position` cursor names a different documentation part than AWS's, because the collection is ordered differently. AWS: recorded behavior only — the cursor has the form `<type>:<name>:<path>:<method>:<statusCode>`, and in the recording the first `limit=1` page of the API's parts ends at the MODEL part, so the token is `MODEL:<modelName>:::` (the model name is a value from the request/state; the fixed text is the five colon-separated location segments). Emulator: 200 with `$.position` = `API::::`, the cursor of the API-level part, because `DOCUMENTATION_PART_TYPE_ORDER` in src/ops/get_documentation_parts.rs sorts `API` first while AWS's collection begins elsewhere. Why: a client resuming at the emulator's cursor walks a different sequence than it would against AWS, so it skips or repeats parts. Fix: the collection order (`DOCUMENTATION_PART_TYPE_ORDER`/`LocationOrder`) and `location_cursor` in the GetDocumentationParts handler. The open issue `20261029T200808Z-apigateway-api-gateway-documentation-parts-ordering-properties-formatting-and.md` is adjacent in subject (documentation-part ordering) but owns none of these fixture steps. Trace: apigw-envelope-documentation-parts-position-walk#task#7 (also task#8).

Cause 5 of 7 — GetDocumentationParts reports `position` on the final page and the unmodeled `limit`, exactly as cause 3 does for API keys. AWS: the recorded final page carries neither member; `DocumentationParts` declares no `limit`. Emulator: 200 with `$.position` = `RESOURCE::/widgets::` (unexpected_present) and `$.limit` = `1` (unexpected_present). Why: the same non-terminating `position` walk, on a second collection, which shows the fault is in the shared envelope rather than in one handler. Trace: apigw-envelope-documentation-parts-position-walk#task#9 (also task#10).

Cause 6 of 7 — a created METHOD documentation part is absent from the listing. AWS: GetDocumentationParts reports every documentation part of the API that satisfies the request's `type`/`nameQuery`/`path`/`locationStatus` filters; the recorded listing at this step includes the part whose location is `{type: METHOD, path: /widgets, method: GET}` with properties `{"description": "List widgets"}`. Emulator: 200, and that part is missing from `item` entirely, with no other item present in its place. Why: a client cannot read back a documentation part it successfully created, so the documentation it attaches to a method is invisible to any later read, export or import. Fix: the GetDocumentationParts handler's narrowing and windowing (`matches_filters` requires exact equality of `location.name` and `location.path`, and the window is cut over the order of cause 4), or the key the CreateDocumentationPart handler stores the part under. Hypothesis: the part is either excluded by a filter comparison AWS does not require to match, or it falls outside the page window the emulator's ordering produces. Trace: apigateway-documentation-part-resource-and-method-locations#task#11.

Cause 7 of 7 — the filtered documentation-parts listing returns the wrong part. AWS: the recorded listing at this step reports the part whose location is `{type: METHOD, path: /pets, method: GET}` with properties `{"description": "list pets"}`. Emulator: 200, that METHOD part is missing and a MODEL part (location `{type: MODEL, name: <the pet model's name>}`, properties `{"description": "pet model"}`) is returned in its place. Why: a client listing or filtering documentation parts is handed a different entity's documentation than AWS would return, so a round trip of the API's documentation reproduces the wrong set. Fix: same component as cause 6 — the filter/order/window of GetDocumentationParts. Trace: apigateway-documentation-parts-multiple-locations-and-filtering#task#13.

No open issue carries the replay keys of these seven clusters, and no unimplemented stub blocks them.
