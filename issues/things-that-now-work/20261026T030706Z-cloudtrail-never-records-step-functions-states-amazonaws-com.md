# CloudTrail never records Step Functions (states.amazonaws.com) calls: LookupEvents has no StartExecution/DescribeStateMachine record and a StateMachine data selector delivers no StartSyncExecution log file

> _Note: this issue was identified against the code base at commit `ebfe4f059696b431f00c6abb397dd11b94b7073a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
TWO distinct causes in this issue; BOTH must be closed before submitting. They are the two CloudTrail delivery paths for a Step Functions API call, and neither carries anything today.

The already-open issue 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md describes the same shape of gap for dynamodb/s3/iam/lambda/elbv2/cloudformation/codepipeline/cognito-idp, but its Issue-Trace-Ids / replay set names NONE of the two cloudtrail__sfn checks below and its causes are scoped to the services it lists, so these two checks are not covered by it and are filed here. Closing that issue does not close these: the Step Functions leg additionally needs the resources.type/resources.ARN Data-selector path (Cause 2), which no other filed check exercises.

Cause 1 of 2 - LookupEvents returns no record for any Step Functions call, successful or rejected.
AWS: every management call of every service, including states.amazonaws.com, is recorded in the Region's event history and readable through LookupEvents (Smithy: LookupEvents, input LookupAttributes/StartTime/EndTime/EventCategory/MaxResults range 1-50, output Events carrying CloudTrailEvent; modelled errors InvalidLookupAttributesException/InvalidTimeRangeException/InvalidMaxResultsException - i.e. a lookup over a valid window is a 200 that returns the records). Read-only calls are recorded with readOnly true, write calls with readOnly false, and a REFUSED call is recorded with errorCode/errorMessage equal to what the caller received. For this check's rejection the recorded behavior (measured against real AWS by the check) is: DescribeStateMachine on a non-existent ARN returns error code StateMachineDoesNotExist with message "State Machine Does Not Exist: '<stateMachineArn>'" - the fixed text is "State Machine Does Not Exist: " and the quoted ARN is the stateMachineArn taken verbatim from the request - and the audit record carries that SAME code string in errorCode, that same message in errorMessage, responseElements null, readOnly true, eventSource states.amazonaws.com, requestParameters.stateMachineArn equal to the requested ARN, userIdentity.arn equal to the assumed-role session ARN that made the call, and requestID equal to the caller's own ResponseMetadata.RequestId. The successful StartExecution record carries NO errorCode, readOnly false, and responseElements containing the executionArn the SDK was returned.
Emulator: no record for StartExecution or for either DescribeStateMachine (the rejected one or the successful control) ever appears. The check makes its three calls through an assumed-role session and then polls LookupEvents(EventName=StartExecution) and LookupEvents(EventName=DescribeStateMachine) over a 3-minute-back window under a 900 s budget with a 15 s cadence, filtering on userIdentity.arn; it never collects any of the three and is still polling when the harness's 60 s cap kills it (verdict mismatch, detail 'Check timed out after 60.0s'). The check carries the suite's DATAPLANE_UNIMPLEMENTED marker for exactly this absence.
Why: a client cannot answer 'who started this execution' or 'which call was refused and why'. Every detective control built on event history over Step Functions - incident reconstruction, compliance evidence, reconciliation of failed calls, attribution to an assumed-role session rather than the base principal - reads an empty history and cannot distinguish 'nothing happened' from 'nothing is recorded'.
Fix: the shared management-event recording seam that CloudTrail's LookupEvents handler reads (the management-event log written today only by CloudTrail's own mutating handlers) must also be driven from the Step Functions service's served operations - for read-only calls and for REFUSED calls as well as successes - populating eventSource/eventName/readOnly/requestParameters/responseElements/errorCode/errorMessage/userIdentity/requestID.
Traces: cloudtrail__sfn.obs-sfn-2-lookup-events-audits-start-execution-and-a-rejected-describe-state-machine.

Cause 2 of 2 - an advanced Data event selector for AWS::StepFunctions::StateMachine stores fine but delivers no StartSyncExecution data event to the trail's S3 prefix.
AWS: PutEventSelectors accepts AdvancedEventSelectors whose FieldSelectors name eventCategory=Data, resources.type=AWS::StepFunctions::StateMachine and resources.ARN=<machine arn> (Smithy: PutEventSelectors input TrailName required + AdvancedEventSelectors, output echoing AdvancedEventSelectors; InvalidEventSelectorsException is the refusal for a selector AWS will not take, so an accepted selector must take effect). Recorded behavior only for the delivery semantics (measured by the check against real AWS): while the trail is logging, StartSyncExecution on the named machine is then written as a gzipped log file under <S3KeyPrefix>/AWSLogs/<account>/CloudTrail/<region>/YYYY/MM/DD/<account>_CloudTrail_<region>_<timestamp>_<suffix>.json.gz, and the record has eventCategory Data, managementEvent false, readOnly false, eventSource states.amazonaws.com, resources naming the machine ARN with type AWS::StepFunctions::StateMachine, responseElements null, requestID equal to the caller's own request id, and requestParameters.input replaced by the literal sentinel HIDDEN_DUE_TO_SECURITY_REASONS. A selector is NOT retroactive (a call made before it existed must never appear) and resources.ARN scopes it (a sibling machine's calls must never appear).
Emulator: nothing is delivered. The check creates the bucket with the CloudTrail policy, the trail with a management-only selector and a run-unique S3KeyPrefix, StartLogging (GetTrailStatus does report IsLogging true), then cannot even complete phase 0 - it issues DescribeStateMachine markers every 60 s and lists/downloads s3://<bucket>/<prefix>/AWSLogs/ every 15 s under a 1500 s budget waiting for any delivered record, and the prefix stays empty, so it is still polling when the harness's 60 s cap kills it (verdict mismatch, detail 'Check timed out after 60.0s'). It too carries the DATAPLANE_UNIMPLEMENTED marker.
Why: the S3 delivery path is what audit pipelines actually consume (Athena/Glue over the log prefix, SIEM ingestion, digest validation). A client reading logs from the bucket sees a permanently empty prefix, and the whole Data-event contract - selector scoping by resources.type/resources.ARN, non-retroactivity, input redaction, the Data vs Management classification of StartSyncExecution - is unobservable and silently 'passes'.
Fix: trail log-file delivery plus Data-event selector evaluation - the trail's logging state must write recorded events as gzipped objects into the configured S3 bucket under the documented key layout, and the recording seam from Cause 1 must emit StartSyncExecution as a Data event (managementEvent false, resources populated, input redacted to the sentinel) filtered by the trail's stored AdvancedEventSelectors, applied only from the time the selector was put.
Traces: cloudtrail__sfn.obs-sfn-2-data-selector-logs-start-sync-execution-to-the-trail-prefix-only-after-it-is-added.

## Evidence
Both checks are reported by the behavioral suite as verdict 'mismatch' with detail 'Check timed out after 60.0s' (service rows: cloudtrail__sfn 0/2, 2 failed). Neither is marked ALREADY FILED nor OWNED by any open issue.

Cause 1 (cloudtrail__sfn.obs-sfn-2-lookup-events-audits-start-execution-and-a-rejected-describe-state-machine): the check's own budget is _LOOKUP_BUDGET_S=900.0 with _POLL_INTERVAL_S=15.0 and a _STALL_WAIT_S=420.0 freeze detector, and the blocking loop is `for env in _lookup_all(ct, StartTime=window_start, EndTime=now+5min, LookupAttributes=[{AttributeKey: 'EventName', AttributeValue: event_name}])` for event_name in ('StartExecution','DescribeStateMachine'), collecting records whose userIdentity.arn equals the assumed-role session ARN. It needs three records ('start', 'missing', 'control') and breaks out only when len(found)==3; it never breaks. Expected on AWS: three records, the 'missing' one with errorCode 'StateMachineDoesNotExist', errorMessage "State Machine Does Not Exist: '<missing arn>'", responseElements null; actual: no record at all for states.amazonaws.com. The check's docstring states the measured AWS indexing latency for this rejection is ~120 s, far inside its own 900 s budget.

Cause 2 (cloudtrail__sfn.obs-sfn-2-data-selector-logs-start-sync-execution-to-the-trail-prefix-only-after-it-is-added): budgets _TOTAL_BUDGET_S=1500.0, _POLL_INTERVAL_S=15.0, _CALL_INTERVAL_S=60.0. After create_trail(S3KeyPrefix=prefix) + put_event_selectors(management-only) + start_logging, the check asserts GetTrailStatus IsLogging is True and then loops on `_collect(s3, bucket, prefix, files)` which pages list_objects_v2(Bucket=bucket, Prefix=f"{prefix}/AWSLogs/") and gzip-decompresses each *.json.gz; `files` stays empty so `_delivered_ids()` is empty and phase 0 never satisfies `set(live_markers) & _delivered_ids()`. Expected on AWS: gzipped objects matching ^<prefix>/AWSLogs/<account>/CloudTrail/<region>/\d{4}/\d{2}/\d{2}/<account>_CloudTrail_<region>_[0-9TZ]+_\w+\.json\.gz$; actual: the prefix is empty, so the later Data-event assertions (eventCategory 'Data', managementEvent False, requestParameters.input == 'HIDDEN_DUE_TO_SECURITY_REASONS', resources naming the subject as AWS::StepFunctions::StateMachine, bystander absence, BEFORE-call absence) are never reached.
