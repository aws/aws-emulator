# bedrock-agent-runtime: 2 net-new causes — GetDocumentContent refuses an inline-ingested document with an unmodeled ValidationException instead of 200 mimeType+presignedUrl, and InvokeFlow serves its stream without the x-amz-bedrock-flow-execution-id executionId header

## Operation

## Description
Two net-new root causes (2 causes) in the bedrock-agent-runtime emulator, both reached on operations that DO answer (so neither is a scaffold-stub symptom). Number of causes to close: 2.

=== Cause 1 of 2: GetDocumentContent refuses a document that was ingested IN_LINE with a 400 ValidationException instead of serving 200 {mimeType, presignedUrl} ===
Failing check ids: bedrock-agent-runtime.get-document-content-nonexistent-document-not-found
AWS: Smithy (services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/smithy-model): GetDocumentContent = POST /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents/{documentId}/content, @readonly, http code 200, output GetDocumentContentResponse { mimeType @required (String), presignedUrl @required @sensitive (PresignedUrl), documentContentLength (Long) }. Modeled errors are AccessDeniedException(403), InternalServerException(500), ResourceNotFoundException(404), ThrottlingException(429), ValidationException(400, "Input validation failed. Check your request parameters and retry the request."). The model draws NO distinction between a document whose bytes arrived via IngestKnowledgeBaseDocuments inline content (custom.inlineContent, sourceType IN_LINE) and one crawled from an object store: for any documentId the service holds in an INDEXED state the operation is a 200 carrying a non-empty mimeType and a presignedUrl the client can GET to read the document's exact ingested bytes. ValidationException is for input that violates the model's constraints; a well-formed, existing (knowledgeBaseId, dataSourceId, documentId) triple violates none, and the "storage shape" of the document is not an input property at all. A documentId that was never ingested under an existing knowledge base and data source draws ResourceNotFoundException (404), and a fabricated knowledgeBaseId draws ResourceNotFoundException with the message template "Knowledge Base with id <knowledgeBaseId> does not exist" — fixed text "Knowledge Base with id " / " does not exist", with the knowledgeBaseId taken verbatim from the request path.
Emulator: answers HTTP 400 ValidationException with the message "documentId: the content of <documentId> travelled in the ingestion that took it in rather than living in an object store, so this service holds no address a pre-signed URL could lead to". Everything but the leading member name "documentId:" and the interpolated documentId is fixed emulator prose; it corresponds to no AWS error class, status or wording. Because the refusal is unconditional for inline-ingested documents, the operation's 200 path is unreachable for a MANAGED knowledge base fed by direct document ingestion, and the two not-found branches the check then measures (never-ingested documentId in a real KB -> 404 ResourceNotFoundException; fully fabricated triple -> 404 with "Knowledge Base with id <id> does not exist") are never reached.
Why: a client that ingests a document with IngestKnowledgeBaseDocuments and then reads it back with GetDocumentContent — the documented round trip — gets its read rejected as an input-validation failure. There is no presignedUrl to fetch, so document-content retrieval cannot run against the emulator at all; and because an input-validation 400 is not a missing-resource 404, retry/fallback logic that distinguishes "bad request" from "not found" takes the wrong branch and surfaces a message AWS never emits.
Fix: the GetDocumentContent operation's handler and its input validation in the bedrock-agent-runtime crate (services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/src/ops/get_document_content.rs and the document-content state it reads) must serve an inline-ingested document: resolve knowledgeBaseId, then dataSourceId, then documentId, and on success return 200 with mimeType and a presignedUrl served by the emulator's own listener whose GET yields the ingested bytes byte-for-byte; reserve ValidationException for model-constraint violations, and emit ResourceNotFoundException(404) for an unknown documentId and for an unknown knowledge base with the "Knowledge Base with id <knowledgeBaseId> does not exist" template.
Related open issues that do NOT cover this: 20261103T030007Z-bedrock-agent-runtime-getdocumentcontent-stub.md describes the earlier unimplemented-scaffold symptom (the operation now answers); 20261111T002352Z-bedrock-agent-runtime-getdocumentcontent-rejects-the-modeled-usercontext.md covers a DIFFERENT unmodeled ValidationException, raised on the presence of the userContext member — this check sends no userContext and is refused on the document's storage shape instead; 20261106T140124Z-bedrock-agent-runtime-ingestknowledgebasedocuments-refuses-a-custom-document.md covers the ingestion call, not the content read.
Traces: bedrock-agent-runtime.get-document-content-nonexistent-document-not-found (the positive control on the real, INDEXED, inline-ingested document).

=== Cause 2 of 2: InvokeFlow's 200 response omits the modeled executionId header x-amz-bedrock-flow-execution-id ===
Failing check ids: bedrock-agent-runtime.invoke-flow-stream-ends-on-a-single-completion-event-and-gates-traces
AWS: Smithy: InvokeFlow = POST /flows/{flowIdentifier}/aliases/{flowAliasIdentifier}, http code 200, output InvokeFlowResponse { responseStream @required @httpPayload @streaming (FlowResponseStream), executionId -> FlowExecutionId @httpHeader("x-amz-bedrock-flow-execution-id"), length 2..100, pattern ^[0-9a-zA-Z._:-]+$ }. A served invocation therefore carries that header, and each invocation is a distinct execution, so two InvokeFlow calls on the same flow and alias carry two different executionId values (the value itself is per-run and not a requirement; its presence, its length/pattern conformance and its per-invocation distinctness are).
Emulator: serves the event stream but sets no x-amz-bedrock-flow-execution-id header, so the SDK-parsed response has executionId == None: "AssertionError: InvokeFlow response must carry a non-empty executionId (x-amz-bedrock-flow-execution-id); got None".
Why: a client cannot learn the id of the execution it just started, so it can neither correlate the stream it is reading with control-plane execution reads nor tell two invocations of the same alias apart; code that threads executionId into a follow-up call (or into logging/tracing keyed on it) gets a null and fails or mislabels every invocation as the same one.
Fix: the InvokeFlow operation's response serializer/handler in the bedrock-agent-runtime crate (services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/src/ops/invoke_flow.rs, which already documents the @httpHeader binding) must mint one FlowExecutionId per invocation — honouring the request's executionId when supplied, otherwise generating a fresh value matching the modeled length 2..100 and pattern ^[0-9a-zA-Z._:-]+$ — record it on the invocation state and emit it on the 200 response as x-amz-bedrock-flow-execution-id.
Related open issue that does NOT cover this: 20261108T071321Z-bedrock-agent-runtime-invokeflow-is-unrouted-the-front.md describes InvokeFlow being unrouted at the front door (UnknownService); InvokeFlow now routes and streams events, and the divergence here is the missing modeled response header.
Traces: bedrock-agent-runtime.invoke-flow-stream-ends-on-a-single-completion-event-and-gates-traces (arm A, enableTrace omitted; the check fails on the header before it can measure arm B's trace gating).
