## Description
One root cause of service `cloudformation__ec2`, grounded in the failing behavioral check in trace_ids. It was not marked ALREADY FILED or OWNED by the replay report. Two sibling checks in this same service group ARE already filed as blocked by unimplemented EC2 scaffolds — `DescribeInternetGateways` (services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_internet_gateways.rs) and `DescribeNatGateways` (.../describe_nat_gateways.rs), and `CreateInternetGateway` (.../create_internet_gateway.rs) is filed as blocking 35 checks — and those filed issues are named here because they are the most likely mechanism behind this hang; this check, however, never gets far enough to be refused by one, so it is a distinct observable failure and is filed on its own.

=== Cause 1 of 1: the VPC stack this check deploys never settles, so the check makes no observable progress ===
AWS: recorded behavior only — no part of this is in the CloudFormation or EC2 Smithy model. A `cdk deploy` of an app declaring a two-AZ VPC (AWS::EC2::VPC + two public AWS::EC2::Subnet with MapPublicIpOnLaunch true + AWS::EC2::InternetGateway + AWS::EC2::VPCGatewayAttachment + route table and routes) reaches CREATE_COMPLETE and writes the stack's Outputs (VpcId, PublicSubnetIds) to the outputs file. The contract the check then grades is the split between the two surfaces: `cdk diff --fail --no-change-set` compares the LOCAL synthesized template with the template CloudFormation holds, so it must exit 0 and report `Number of stacks with differences: 0` after an out-of-band `ModifySubnetAttribute(MapPublicIpOnLaunch=false)` — a real-resource mutation is invisible to it — while DetectStackDrift on the same stack must report `StackDriftStatus` `DRIFTED`, and DescribeStackResourceDrifts must report exactly one entry for that subnet with `StackResourceDriftStatus` `MODIFIED` and a single `PropertyDifferences` entry at PropertyPath `/MapPublicIpOnLaunch` with `ExpectedValue` true, `ActualValue` false and `DifferenceType` `NOT_EQUAL`; restoring the attribute must bring that entry back to `IN_SYNC`. A later LOCAL template change (a changed tag value) must make `cdk diff --fail` exit non-zero naming it, without mutating the deployed template.
Emulator: the check makes no observable progress past its setup and is killed at the harness ceiling: `Check timed out after 60.0s`. Its own budgets are much larger (bootstrap 300s, deploy 480s, diff 120s, drift 300s), and sibling CDK checks in this suite DO get through `cdk bootstrap` and a deploy inside the same 60s ceiling (they fail later, on a specific EC2 scaffold refusal), so the ceiling is reachable for a CDK check against this emulator and this one hanging is the emulator not settling. Hypothesis: the VPC app's stack never reaches a terminal status because the EC2 gateway resources it declares cannot be provisioned — `CreateInternetGateway` / `DescribeInternetGateways` / `DescribeNatGateways` are unimplemented scaffolds that answer HTTP 501 `operation <X> is scaffolded but not implemented in this emulator` — so the CDK CLI polls a stack that is neither complete nor failed. The replay output records only the timeout, so the exact stall point is not established by this run.
Why: a client cannot deploy the single most common CDK construct (a VPC) at all — `cdk deploy` hangs instead of returning, which blocks every downstream workload in the same app. And because the deploy never finishes, the diff-vs-drift distinction above is untested: a client that relies on `cdk diff` being blind to resource drift and on DetectStackDrift being the API that sees it (with the property path, expected and actual values an operator needs to act on) has no working path to either answer.
Fix: the stack-provisioning path for the EC2 network resource set (AWS::EC2::VPC, Subnet, InternetGateway, VPCGatewayAttachment, RouteTable, Route, SubnetRouteTableAssociation) must drive each resource to a terminal state and fail the stack when a resource cannot be provisioned rather than leaving it in progress, which requires the EC2 operations those resources call to exist (the three scaffolds named above carry their own filed issues). Once the deploy settles, the drift comparison for AWS::EC2::Subnet must report `/MapPublicIpOnLaunch` as a property difference with NOT_EQUAL and the template-vs-resource values, per `crate::state::drift`.
