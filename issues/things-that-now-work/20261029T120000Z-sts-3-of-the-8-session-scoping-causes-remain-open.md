# STS: 3 of the 8 causes of the session-scoping issue are still open — no session-scoped authorization is evaluated anywhere, the JWT-vending surface is unserved, and the fifteen refusal/expiry checks that depend on the first of those (3 causes)

> _Split out of `issues/things-that-now-work/20261024T065715Z-sts-sessions-carry-no-policy-scoping-packedpolicysize-oversized.md`, whose causes 2, 3 and 7 are fixed (PackedPolicySize is reported by every mint, an over-long inline session policy is a validation error answered before packing, and a constraint refusal quotes the value as submitted and the `@pattern` as modelled), and whose causes 4 and 6 were already correct in the tree by the time that fix landed. This report carries the replay keys that do NOT pass, re-filed here so they are not recorded as working. Everything below is what that fix established about them; a later fixer starts from here rather than from scratch._

## Operation
GetFederationToken

## Description
Three of the parent report's eight causes are untouched. They are numbered here as the parent numbered them, so the two reports can be read together.

Cause 1 of 8 (parent numbering): a temporary session's scoping is never evaluated — inline session policies, PolicyArns, permissions boundaries and principal tag/type conditions have no effect on any later call.
AWS: the effective permissions of a session are the intersection of the role's identity policy, the session policy (inline Policy and/or PolicyArns), the role's permissions boundary and any resource policy; an explicit Deny anywhere wins; a call outside that intersection is refused with AccessDenied/403 at the called service ("User: <session arn> is not authorized to perform: <action> on resource: <arn>"). A GetFederationToken session with NO policy has no permissions at all. aws:PrincipalTag/<key> and aws:PrincipalType conditions select on the session's own tags/class.
Emulator: every such call succeeds — s3:ListAllMyBuckets answers 200 under a federation token minted with no policy, secretsmanager:ListSecrets succeeds under a session policy granting only s3:ListAllMyBuckets, s3:GetObject succeeds where the session policy denies it, iam:ListUsers answers 200 to a federated session, and a blue-tagged session is granted what only the red tag allows.
Where the work is, as of the parent fix: the DECISION already exists once in the tree — `services/common/src/iam_authorization.rs` evaluates identity-based and resource-based documents against `(action, resource)` with conditions and set qualifiers, and `services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs` already gates IAM's own operations with it. What is missing is the SESSION half, in three pieces:
* nothing records a minted session's SCOPE. `src/state.rs`'s `Session` keeps the identity, the tags, the expiry and the packed size, and deliberately not the inline policy, the managed policy ARNs or the role it may not exceed; a data plane asked to decide a request signed with that credential has nothing to read. A shared directory (the shape `services/common/src/web_identity_tokens.rs` and `management_events.rs` take — one store in the one engine, written by the service that MINTS and read by the service that DECIDES) is what every enforcement site needs, written by `AssumeRole`, `AssumeRoleWithWebIdentity`, `GetFederationToken` and `GetSessionToken`.
* IAM's gate reads a session credential as a principal carrying NO documents at all and therefore ALLOWS it (the "callers that are not IAM users" note in that file). Once the directory exists this is the smallest site to close, because the role's own documents and its boundary are in IAM's own store: `sts.get-federation-token-cannot-call-iam-denied` is the check it closes.
* the other enforcement sites are other crates' data planes — S3 (`s3:ListAllMyBuckets`, `s3:GetObject`, `s3:PutObject`), Secrets Manager (`secretsmanager:ListSecrets`, `secretsmanager:GetSecretValue`) — each of which must derive the (action, resource) pair of ITS own request before asking the shared evaluation. A gate wired into one service and not the others refuses some calls and allows others, so this is one change per crate rather than one shared wrapper.

Cause 5 of 8 (parent numbering): the outbound web-identity federation surface is unserved — the two IAM account operations are not routed, and STS `GetWebIdentityToken` is a scaffold.
AWS: `EnableOutboundWebIdentityFederation` (output IssuerIdentifier; error FeatureEnabledException, awsQueryError code FeatureEnabled, HTTP 409) and `GetOutboundWebIdentityFederationInfo` (output IssuerIdentifier + JwtVendingEnabled; error FeatureDisabledException, awsQueryError code FeatureDisabled, HTTP 404) are bound on the IAM service; the issuer they report hosts the OIDC discovery endpoints at `/.well-known/openid-configuration` and `/.well-known/jwks.json`. STS `GetWebIdentityToken` then returns a JWT "signed by Amazon Web Services STS" and "publicly verified using the verification keys published at the issuer's JWKS endpoint", with errors JWTPayloadSizeExceededException (400), OutboundWebIdentityFederationDisabledException (403) and SessionDurationEscalationException (403).
Emulator: the two IAM actions answer `InvalidAction` / "unknown action: …", because the IAM crate has no `src/ops/<op>.rs` for either (the build discovers operations from that directory, so a model-bound operation with no file is absent from the routing table); `src/ops/get_web_identity_token.rs` in the STS crate still carries its `SCAFFOLDED, NOT IMPLEMENTED` header and answers 501.
Where the work is: the two IAM operations are small (an account-level flag plus a derived issuer URL in `services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state.rs`, two op files, and the `Unit`-input schema written out by hand the way `service-com-amazonaws-observabilityadmin-observabilityadmin/src/ops/stop_telemetry_evaluation.rs` writes one). `GetWebIdentityToken` is the larger half and must not be answered with a token nothing signed: the emulator has to MINT a signed JWT and PUBLISH the key set at the issuer it announced, which `service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice` already does per user pool (its `UserPool::jwks` and the `/<id>/.well-known/jwks.json` route in its `service.rs`), and `services/common/src/jwt.rs` already verifies a token against such a key set. Announcing an issuer whose key set nothing serves, or vending an unsigned token, would be an outcome no engine produced.

Cause 8 of 8 (parent numbering): fifteen checks never complete — each establishes a positive control, then polls for the AccessDenied / credential-expiry transition the emulator never produces, and exhausts the 60s harness cap.
AWS: every one of these transitions is observable: a session policy / trust-policy principal restriction / region condition / session tag condition / permissions boundary produces AccessDenied/403 on the next call; credentials stop being accepted once Expiration passes; deleting the role invalidates sessions already issued and re-creating it by name does not restore them; DecodeAuthorizationMessage round-trips an encoded authorization failure.
Emulator: no divergent RESPONSE is captured for these checks — the expected refusal never arrives, which is cause 1 above plus session-lifecycle enforcement at the services that ACCEPT the credential. STS itself already refuses a session credential past its own `Expiration` (`ExpiredSession` in `src/state.rs`) and already encodes and decodes an authorization message (`DecodeAuthorizationMessage` is implemented, with its own suite); what is missing is that any OTHER service accepting such a credential checks the same two facts — that the session has not expired, and that the role it was minted for still exists — which is the same shared directory cause 1 needs, plus a revocation hook on IAM's `DeleteRole`.
