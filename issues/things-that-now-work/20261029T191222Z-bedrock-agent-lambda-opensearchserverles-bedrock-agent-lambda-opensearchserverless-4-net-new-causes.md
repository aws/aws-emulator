# bedrock-agent__lambda__opensearchserverless: 4 net-new causes — collection endpoint serves the AWS-JSON front door, CreateCollection's missing-encryption message is reworded, CreateKnowledgeBase accepts a role that does not trust bedrock.amazonaws.com, and `aws lambda invoke` is refused NotImplemented

> _Note: this issue was identified against the code base at commit `92c3b140342b1bc1fab2a232b8cee3f25ea78ff5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateKnowledgeBase

## Description
FOUR net-new root causes reached through the cross-service bedrock-agent + lambda + opensearchserverless checks (service token taken from the leading segment of the check ids).

=== Cause 1 of 4: a VECTORSEARCH collection's published collectionEndpoint serves the AWS-JSON RPC dispatcher instead of the OpenSearch REST data plane ===
AWS: recorded behavior only (a collection's data plane is the OpenSearch REST API and is not described by the opensearchserverless Smithy model, which covers the control plane). Recorded behavior: with an ACTIVE collection, a SigV4-signed (service name `aoss`) `PUT https://<collectionEndpoint>/<indexName>` carrying a knn_vector mapping — no `x-amz-target` header, because REST has no RPC target — is accepted when the data-access policy names the calling principal, refused 403 when it does not, and refused 401 (opensearchpy AuthenticationException) when no network policy admits the caller.
Emulator: every such request is answered HTTP 400 `{"__type":"SerializationException","message":"missing required header `x-amz-target`"}` (fixed text, nothing derived from the request).
Why: no knowledge base can be provisioned through the documented path, and the policy boundaries these checks exist to prove are unobservable — a permitted principal, an unpermitted principal and a caller with no network policy all get the identical 400, so 'allowed', 'denied by data access policy' and 'denied by network policy' are indistinguishable.
Fix: the opensearchserverless collection data plane plus the emulator's host/endpoint routing table (services/service-com-amazonaws-opensearchserverless-opensearchserverless and the endpoint resolution that publishes collectionEndpoint) — serve OpenSearch REST on the published host and authorise SigV4 `aoss` requests against the collection's network and data-access policies. NOTE: open issue 20261029T171944Z-bedrock-agent-lambda-opensearchserverles-bedrock-agent-lambda-opensearchserverless-2-net-new-causes.md records this wall for OTHER checks of this same service token; the 7 checks below were not marked owned by it and must be re-replayed. If that fix lands first, this cause closes with it.
Traces: bedrock-agent__lambda__opensearchserverless.bedrock-kb-ingestion-job-writes-to-collection-positive and .deploy-bedrock-knowledge-base-vector-index-positive (400 surfaced directly from the index create); .bedrock-kb-opensearchserverless-network-policy-missing-negative (expected opensearchpy AuthenticationException(401), got RequestError(400, SerializationException)); .bedrock-kb-opensearchserverless-collection-arn-resolution-positive, .bedrock-kb-opensearchserverless-data-access-policy-missing-negative, .bedrock-kb-opensearchserverless-field-mapping-positive, .bedrock-kb-opensearchserverless-vector-index-creation-positive (all 'Check timed out after 60.0s' — the same 400 inside their index-create retry loop).

=== Cause 2 of 4: CreateCollection's refusal for a collection with neither encryptionConfig nor a matching encryption policy uses the emulator's own wording ===
AWS: Smithy: CreateCollection takes an optional encryptionConfig and models ValidationException (400). Recorded behavior: with no encryptionConfig and no encryption security policy covering the name, the call is refused ValidationException 400 with the message `No matching security policy of encryption type found for collection name: <name>. Please create security policy of encryption type for this collection.` — all of that is fixed text except `<name>`, the `name` from the request.
Emulator: ValidationException with `No encryption policy or encryption configuration exists for the collection <name>: specify encryptionConfig in the request, or create an encryption security policy whose rules cover collection/<name>`.
Why: a client (or a test) that matches on AWS's message — the only machine-usable discriminator, since the code is the generic ValidationException — does not recognise the refusal.
Fix: the CreateCollection handler's encryption validation message in the opensearchserverless crate.
Traces: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-encryption-policy-missing-negative. (The same cause is reported under the opensearchserverless token for its own two checks.)

=== Cause 3 of 4: CreateKnowledgeBase does not validate the service role's trust policy, so a role that never names bedrock.amazonaws.com is accepted ===
AWS: Smithy: CreateKnowledgeBase requires roleArn (pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$) and models ValidationException (400). Recorded behavior: when the role's trust policy trusts only lambda.amazonaws.com, the call is refused ValidationException with the message `Bedrock Knowledge Base was unable to assume the given role. Provide the proper permissions and retry the request.` (entirely fixed text), BEFORE the collection or index is validated, and no knowledge base appears in ListKnowledgeBases.
Emulator: the call SUCCEEDS — a knowledge base is created for a role whose trust policy never names bedrock.amazonaws.com, and with a collection ARN that does not exist either.
Why: the role-trust precondition is silently absent, so a misconfigured deployment that real AWS rejects immediately appears to work and fails later (or never), and the IAM boundary the check exists to prove is gone.
Fix: the CreateKnowledgeBase handler's validation in the bedrock-agent crate — read the roleArn's assume-role policy document and refuse with ValidationException and that message when no statement allows sts:AssumeRole for Service bedrock.amazonaws.com.
Traces: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-role-trust-missing-negative.

=== Cause 4 of 4: `aws lambda invoke` of a real deployment package is refused NotImplemented, so the aoss IAM permission boundary is never reached through the CLI path ===
AWS: recorded behavior only for the execution (Smithy models Invoke's success and error set, not the function body). Recorded behavior: `aws lambda invoke --function-name <fn> --payload <file> out.json` exits 0 and writes the handler's payload; the handler's own opensearchserverless call then reports a collection list when the execution role holds aoss:ListCollections and AccessDeniedException when it does not — that pair is what proves the boundary.
Emulator: the CLI exits rc=254 with `An error occurred (NotImplemented) when calling the Invoke operation: Invoke resolved arn:aws:lambda:<region>:<account>:function:<name> at version $LATEST, but running its python3.12 deployment package is not implemented in this emulator: there is no in-process runtime for it, and no response payload is returned that the function did not produce. InvocationType=DryRun validates an invocation without running the function.`
Why: the function body never runs, so no allow-vs-deny verdict is produced and nothing about the cross-service flow is observable.
Fix: the lambda Invoke handler's execution path (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs and the function-runtime component it would call). NOTE: open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md describes the same refusal and owns the SDK-path siblings; these two checks reach Invoke through the AWS CLI so their replay keys differ and were not marked owned — they are recorded here so they are re-replayed, and this cause should close with that issue if its fix lands first.
Traces: bedrock-agent__lambda__opensearchserverless.cli-create-opensearchserverless-collection-lambda-list-positive, .cli-opensearchserverless-collection-missing-permission-negative.
