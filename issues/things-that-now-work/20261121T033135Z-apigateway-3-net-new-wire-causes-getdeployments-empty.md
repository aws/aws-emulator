=== Cause 1 of 3: GetDeployments answers an empty deployment collection as the bare object {} instead of carrying item: [] ===
AWS: Smithy (services/service-com-amazonaws-apigateway-backplanecontrolservice/smithy-model/com-amazonaws-apigateway-backplanecontrolservice.json) models GetDeployments as GET /restapis/{restApiId}/deployments with http success code 200, output shape Deployments { items: ListOfDeployment with jsonName "item", position }, @paginated {inputToken: position, outputToken: position, items: items, pageSize: limit}; modeled errors BadRequestException(400), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401), ServiceUnavailableException(503). The model does not state member PRESENCE, so for the EMPTY case this is recorded behavior only: the recorded 200 for a REST API whose deployments have all been deleted carries the wire key `item` with an empty array, i.e. `{"item": []}`.
Emulator: the same GET is answered 200 with an empty JSON object — the `item` key is absent altogether (replay detail: `$: empty_body (expected {'item': []}, got {})`).
Why: the collection member is exactly what a client keys off to answer "is it deployed / is it gone?". The idiomatic botocore read `response["items"]` raises KeyError: 'items' and a paginator's `items` result key resolves to nothing — precisely on the fresh API that owns no deployment yet, which is the state every create-then-verify and delete-then-confirm sequence passes through. The two environments disagree on the wire bytes of the most common listing answer.
Fix: the GetDeployments response path (that operation's handler/serializer in the apigateway service crate) together with the shared paging/report helper that currently turns an empty sequence into an ABSENT optional member rather than a present empty list. Scope the change to GetDeployments: open issue 20261115T090346Z-apigateway-listing-envelope-diverges-from-the-recording-an.md records the OPPOSITE requirement for GetBasePathMappings (its recorded empty 200 body is `{}`), so do NOT flip the shared helper blanket-wise.
Not covered by an open issue: 20261117T145207Z-apigateway-empty-listing-200s-omit-the-item-member.md asserts this exact rule for six OTHER operations (GetApiKeys, GetAuthorizers, GetDocumentationVersions, GetUsagePlanKeys, GetVpcLinks, GetDocumentationParts) and explicitly does not name GetDeployments or this fixture step — the replay reports this cluster with owned_by=[]. 20261117T024849Z-apigateway-3-net-new-causes-stage-methodsettings-keyed.md and 20261117T024849Z-apigateway-cognito-idp-lambda-getdeployments-omits-the-items.md state the GetDeployments rule but are grounded in BEHAVIORAL checks only and carry no fixture/step for it, so a fix validated against them leaves this replay step unrun.

=== Cause 2 of 3: the TestInvokeMethod execution log is emulator-authored and does not have AWS's log shape ===
AWS: Smithy models TestInvokeMethod as POST /restapis/{restApiId}/resources/{resourceId}/methods/{httpMethod}, success 200, output TestInvokeMethodResponse { status: Integer, body: String, headers, multiValueHeaders, log: String, latency: Long }; the `log` member is documented only as "The API Gateway execution log for the test invoke request." The model therefore states no format, so the requirement is the recorded one: the harness asserts this member by SHAPE (the replay prints the expectation as '<shaped-not-asserted>'), and the emulator's string fails that shape check. AWS's execution log is a sequence of lines each PREFIXED with the invocation timestamp in the Java `EEE MMM dd HH:mm:ss z yyyy` form — e.g. `Fri Nov 21 03:25:41 UTC 2026 : Starting execution for request: <request-id>` — opening with `Execution log for request <request-id>` where the request id is a UUID minted per invocation. Hypothesis (neither the model nor the replay output reproduces the recorded text, only its shape verdict): the shape the recording pins is that per-line date prefix and the UUID request id, which is what the emulator's lines do not match.
Emulator: the log is emitted with ISO-8601 'Z' timestamps and a fixed literal request id — `Execution log for request test-invoke-request` followed by lines prefixed `2026-11-21T03:25:41Z : ` (`Starting execution for request: test-invoke-request`, `HTTP Method: GET, Resource Path: ...`, `Method request path: ...`, `Method request headers: []`, `Method request body before transformations: 0 byte(s)`, `Integration type: MOCK`, `Successfully completed execution`, `Method response headers: [...]`, `Method response body after transformations: 53 byte(s)`, `Method completed with status: 200`). The timestamps, trace id and byte counts of any ONE run are per-run values and are NOT the requirement; the per-line prefix FORM and the request-id form are.
Why: the execution log is the only diagnostic TestInvokeMethod returns, and tooling and CI assertions parse it — splitting each line on ` : ` after a date prefix, and correlating the request id in the log with the id reported elsewhere. Against the emulator every such parse mis-slices the timestamp (an ISO-8601 stamp contains no spaces where AWS's has four) and every correlation lands on the constant string `test-invoke-request` instead of a per-invocation id, so a client that debugs or gates on the test-invoke log behaves differently here than on AWS.
Fix: the TestInvokeMethod handler's execution-log builder (the component that formats the log lines and the request identifier it stamps into them), not the invoke path itself — status, body and headers of these steps all match.
Not covered by an open issue: the open TestInvokeMethod issues concern invocations that never return or AWS_PROXY/authorizer outcomes (e.g. 20261108T011128Z-apigateway-dynamodb-iam-lambda-3-net-new-causes.md, 20261104T143156Z-...-testinvokemethod-on-an-aws-proxy-method.md); none asserts the `log` member's shape, and the replay reports this cluster with owned_by=[].

=== Cause 3 of 3: ImportDocumentationParts in merge mode mints a new part id for a location the API already documents, instead of reporting the existing part's id ===
AWS: Smithy models ImportDocumentationParts as PUT /restapis/{restApiId}/documentation/parts with success 200, input { restApiId (httpLabel, required), mode: PutMode (httpQuery "mode"), failOnWarnings (httpQuery "failonwarnings", default false), body: Blob (httpPayload, required) }, output DocumentationPartIds { ids: ListOfString, warnings: ListOfString }; modeled errors BadRequestException(400), ConflictException(409), NotFoundException(404), LimitExceededException(429), TooManyRequestsException(429), UnauthorizedException(401). The `mode` member documents: "A query parameter to indicate whether to overwrite (overwrite) any existing DocumentationParts definition or to merge (merge) the new definition into the existing one. The default value is merge." The identity rule is recorded behavior only: the fixture asserts this response's `ids[0]` BY REFERENCE to the documentation-part id already bound earlier in the same fixture for the same location (the expectation is printed as the capture token `{{merged_id_0}}`, not as a literal id), and the recorded service answers 200 reporting THAT id — i.e. a documentation part is identified by its (restApiId, location) pair, so a merge import of a location that already has a part resolves to the part that is already there.
Emulator: the same import is answered 200 with a freshly generated 10-character part id in `ids[0]`, so the member diverges from the id of the part that already exists for that location. The generated id string observed in any run is a per-run value and is NOT the requirement; the requirement is the EQUALITY with the existing part's id.
Why: merge is the DEFAULT import mode and the normal pattern is to re-import documentation whenever it is regenerated from source. A client doing that silently accumulates one extra documentation part per location per import instead of landing on the one part for that location; it cannot correlate the returned ids with the parts it already tracks, GetDocumentationParts then enumerates duplicates for a single entity, and an OpenAPI export renders the location's documentation more than once. Nothing in the response signals the duplication.
Fix: the ImportDocumentationParts handler's merge path and the documentation-part state it writes — match each imported location against the restApi's existing parts and resolve to that part (reporting its id) instead of inserting a new entry with a new id.
Not covered by an open issue: 20261107T204751Z-apigateway-api-gateway-documentation-parts-method-location-parts-dropped.md asserted this exact rule (its cause 3, "merge import mints new ids") but is RESOLVED, so it covers nothing — this is the same behavior still diverging and needs a fresh fix. 20261116T063445Z-apigateway-duplicate-location-createdocumentationpart-mints-a-second-part.md covers the per-location identity rule on the CreateDocumentationPart path only (a different handler, and its own replay key), and 20261113T185449Z-apigateway-2-net-new-causes-importdocumentationparts-failonwarnings-rejection.md covers only the failOnWarnings refusal wording. The replay reports this cluster with owned_by=[].
