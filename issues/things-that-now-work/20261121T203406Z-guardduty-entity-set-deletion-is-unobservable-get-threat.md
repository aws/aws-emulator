# GuardDuty entity-set deletion is unobservable: Get{Threat,Trusted}EntitySet drops the deleted record and refuses its id with an unmodeled 404 ResourceNotFoundException instead of DELETE_PENDING/DELETED, then 400 BadRequestException

> _Note: this issue was identified against the code base at commit `6daf257af7fbb3a766577fc65424a8d09ee1c660`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetThreatEntitySet

## Description
This issue bundles 2 distinct root causes, both in the guardduty crate's threat/trusted entity-set family (ThreatEntitySet and TrustedEntitySet go through the same shared state helper and the same absence template, so both ops are affected by both causes). Fix BOTH before submitting.

Cause 1 of 2: after Delete{Threat,Trusted}EntitySet the record is DROPPED, so Get{Threat,Trusted}EntitySet can never report DELETE_PENDING or DELETED.
AWS: Smithy ThreatEntitySetStatus and TrustedEntitySetStatus are both enums with values [INACTIVE, ACTIVATING, ACTIVE, DEACTIVATING, ERROR, DELETE_PENDING, DELETED], and GetThreatEntitySet / GetTrustedEntitySet declare Status as a required output member — the two delete states exist precisely because a delete is asynchronous and observable through the read. Recorded behavior: after a successful Delete*, Get* on the SAME id keeps answering HTTP 200 and reports Status DELETE_PENDING while the removal is in flight and then DELETED when it finishes; a client polls that transition (the recorded check polls GetThreatEntitySet until Status == DELETED and treats any error as a failure, and its TrustedEntitySet sibling accepts DELETE_PENDING, DELETED or the family's 400 absence refusal).
Emulator: the delete removes the record outright, so the very next Get* answers HTTP 404 with code ResourceNotFoundException and message 'The specified entity set does not exist.' — DELETE_PENDING and DELETED are states no entity set on this emulator can ever be observed in. The handlers state this as intent: services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/get_threat_entity_set.rs lines 193-212 ('the deletion DROPS the record ... so its id resolves to nothing here from that instant on'), identical text in get_trusted_entity_set.rs lines 189-208, and the delete's own module doc, src/ops/delete_threat_entity_set.rs lines 4-9 ('GetThreatEntitySet refuses it exactly like an id no create ever minted').
Why: a client that deletes an entity set and then waits for the deletion to complete — the documented DELETE_PENDING -> DELETED progression — never sees either state and instead takes an exception out of its poll loop; teardown code and reconcilers that confirm removal by reading the terminal DELETED status cannot be written against this emulator, and no caller can distinguish 'delete accepted, still pending' from 'id never existed'.
Fix: the entity-set delete path in this crate's state (the shared delete_entity_set helper reached from DeleteThreatEntitySet/DeleteTrustedEntitySet) must RETAIN the record, stamp it DELETE_PENDING at acceptance and let the clock settle it to DELETED, and the absence branch of Get{Threat,Trusted}EntitySet must be reached only once that retained record is gone. Note: fixed issue 20261028T195001Z-guardduty-deletethreatentityset-wrong-behavior.md describes an earlier shape of this code that DID keep the deleted record 'so a read can still report DELETE_PENDING/DELETED'; the code now in the checkout no longer does, so that retention is what has to come back (bounded as it was).
Traces: guardduty.threatentityset-lifecycle, guardduty.trustedentityset-lifecycle-create-delete.

Cause 2 of 2: the entity-set absence refusal is an UNMODELED ResourceNotFoundException under HTTP 404 instead of BadRequestException under HTTP 400.
AWS: Smithy GetThreatEntitySet and GetTrustedEntitySet each declare exactly two errors — BadRequestException (errorKind client, httpError 400, members message/type) and InternalServerErrorException (errorKind server, httpError 500). ResourceNotFoundException appears nowhere in either operation's error list, so AWS cannot answer these reads with it. Recorded behavior: an entity-set id the detector holds no record for (never minted, minted elsewhere, or already fully removed) is refused with HTTP 400 and error code BadRequestException — the recorded checks encode that as the tolerated 'already gone' outcome ('GuardDuty reports a TrustedEntitySet that is already gone as BadRequestException', and the assertion accepts the code 'BadRequestException'). The message is GuardDuty's fixed absence sentence for this family; the requirement is the status/code pair plus one fixed sentence that interpolates nothing from the request (no member name, no id value), not any one run's id.
Emulator: HTTP 404 with code ResourceNotFoundException and message 'The specified entity set does not exist.', produced by crate::scaffolded::not_found with crate::scaffolded::ENTITY_SET_NOT_FOUND_MESSAGE at get_threat_entity_set.rs:209-211 and get_trusted_entity_set.rs:205-207; the handler comments call this the way 'BOTH entity-set families report it ... HTTP 404 under the ResourceNotFoundException class', which the model does not permit for these operations.
Why: an SDK builds its typed error classes from the model, so a caller that catches BadRequestException (the only client-error class these reads model) does not catch the emulator's ResourceNotFoundException; except/catch blocks written against AWS fall through and crash, retry classification is wrong, and the status code a client branches on is 404 where AWS gives 400.
Fix: the absence branch of the GetThreatEntitySet and GetTrustedEntitySet handlers (and the shared scaffolded absence helper they call) must construct the modeled BadRequestException at HTTP 400 carrying the family's fixed absence sentence, instead of the 404/ResourceNotFoundException channel.
Traces: guardduty.trustedentityset-lifecycle-create-delete, guardduty.threatentityset-lifecycle.

Context on an already-fixed issue that does NOT cover either cause: 20261029T183757Z-guardduty-lifecycle-state-is-wrong-missing-dry-run.md cause 5 made CreateThreatEntitySet accept an endpoint-relative S3 object URL as Location; that call now succeeds and returns a ThreatEntitySetId, and guardduty.threatentityset-lifecycle now fails further along, on the read side described above, which that issue never addressed.

## Evidence
- guardduty.threatentityset-lifecycle (verdict: error): CreateThreatEntitySet(DetectorId, Name, Format='TXT', Location=<s3 object URL>, Activate=True) returned a ThreatEntitySetId, and a later GetThreatEntitySet for that id raised 'botocore.errorfactory.ResourceNotFoundException: An error occurred (ResourceNotFoundException) when calling the GetThreatEntitySet operation: The specified entity set does not exist.' The check has no tolerance for an error from that read: it polls GetThreatEntitySet until Status is ACTIVE/ERROR, renames, deletes, then polls until Status == 'DELETED'. The emulator's only refusal path in that handler is the absent-record branch (get_threat_entity_set.rs:198-212), which the delete makes unconditional for the post-delete poll; whichever read reached it, the dropped record and the 404/ResourceNotFoundException class are the cause, and no run of this check can reach Status DELETED while the record is removed on delete.
- guardduty.trustedentityset-lifecycle-create-delete (verdict: mismatch): CreateTrustedEntitySet -> GetTrustedEntitySet succeeded (Name and an ACTIVATING/ACTIVE Status matched), DeleteTrustedEntitySet returned 200, and the post-delete read then produced 'AssertionError: expected DELETE_PENDING/DELETED status or BadRequestException after delete, got ResourceNotFoundException'. This pins the failure to the read AFTER the delete and shows both causes at once: no DELETE_PENDING/DELETED is ever observable (cause 1), and the refusal that replaces it carries an error code the operation does not model (cause 2).
- Smithy grounding (services/service-com-amazonaws-guardduty-guarddutyapiservice/smithy-model/com-amazonaws-guardduty-guarddutyapiservice.json): GetThreatEntitySet errors = [BadRequestException (400), InternalServerErrorException (500)]; GetTrustedEntitySet errors = the same two; ThreatEntitySetStatus = TrustedEntitySetStatus = [INACTIVE, ACTIVATING, ACTIVE, DEACTIVATING, ERROR, DELETE_PENDING, DELETED].
- Handler evidence: get_threat_entity_set.rs:193-212 and get_trusted_entity_set.rs:189-208 (record dropped on delete; absence reported as HTTP 404 ResourceNotFoundException via crate::scaffolded::not_found / ENTITY_SET_NOT_FOUND_MESSAGE); src/ops/delete_threat_entity_set.rs:4-9 (delete removes the set so the read 'refuses it exactly like an id no create ever minted').

## Steps to Reproduce
1. Replay guardduty.trustedentityset-lifecycle-create-delete: create/adopt a detector, put a TXT list object in an S3 bucket, call CreateTrustedEntitySet(Format='TXT', Location='s3://<bucket>/list.txt', Activate=True), confirm GetTrustedEntitySet reports the Name with Status ACTIVATING/ACTIVE, then call DeleteTrustedEntitySet and poll GetTrustedEntitySet. Expect HTTP 200 with Status DELETE_PENDING and then DELETED (or, once the record is finally gone, HTTP 400 BadRequestException); observe HTTP 404 with code ResourceNotFoundException and message 'The specified entity set does not exist.'
2. Replay guardduty.threatentityset-lifecycle: CreateThreatEntitySet with a TXT list Location and Activate=True, poll GetThreatEntitySet to ACTIVE, UpdateThreatEntitySet(Name=<new name>), then DeleteThreatEntitySet and poll GetThreatEntitySet until Status == 'DELETED'. Expect the DELETE_PENDING -> DELETED progression on 200 responses; observe the read raising ResourceNotFoundException so the terminal DELETED status is unreachable.
3. Cause 2 in isolation: call GetTrustedEntitySet (or GetThreatEntitySet) with a well-formed id that no create ever minted under the detector. Expect HTTP 400, error code BadRequestException, with GuardDuty's fixed absence sentence; observe HTTP 404 with code ResourceNotFoundException, a class neither operation models.
