# neptune: 2 net-new port causes — a DB instance's Endpoint.Port never inherits the cluster's Port, and ModifyDBCluster's out-of-range-Port refusal is emulator-authored

> _Note: this issue was identified against the code base at commit `561579de3e0b6bd91c56d47afed233bd7828579f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
Two net-new root causes in the Neptune DB cluster/instance control plane, both found by the behavioral suite. THIS ISSUE HAS 2 CAUSES — both must be closed before submitting.

Note on a related open issue: 20261117T150412Z-neptune-3-net-new-causes-createdbcluster-ignores-the.md covered (a) CreateDBCluster discarding the request's Port and (b) the out-of-range-port message on CreateDBCluster. The cluster-side half now behaves: in this replay CreateDBCluster/DescribeDBClusters report exactly the requested Port (8191, 8183, 8182 all asserted and passed), and the checks below are NOT marked OWNED by it — they fail on the next assertion down, which that issue does not carry. Cause 1 here is the INSTANCE-side inheritance of the cluster port, and cause 2 is the SAME message template on ModifyDBCluster, which is now reachable for the first time (it was previously blocked by the discarded-Port bug) and is still wrong. A similar open issue does not cover them.

Cause 1 of 2: a DB instance created in a cluster whose Port is not the engine default reports Endpoint.Port 8182 instead of inheriting the cluster's port.
AWS: Smithy (services/service-com-amazonaws-neptune-amazonrdsv19/smithy-model/com-amazonaws-neptune-amazonrdsv19.json) CreateDBInstanceMessage.Port (IntegerOptional) doc: "The port number on which the database accepts connections. Not applicable. The port is managed by the DB cluster. For more information, see CreateDBCluster. Default: 8182"; neptune#Endpoint.Port doc: "Specifies the port that the database engine is listening on"; CreateDBClusterMessage.Port doc: "The port number on which the instances in the DB cluster accept connections. Default: 8182". So the port is a CLUSTER-level property that its member instances take on: an instance created with no Port of its own in a cluster whose Port is 8191 (or 8183) reports Endpoint.Port == that cluster port from CreateDBInstance onward, and DescribeDBInstances reports the same value; 8182 appears only when the cluster itself is on the engine default. An unrelated ModifyDBInstance (e.g. PreferredMaintenanceWindow) must not change it.
Emulator: the cluster's Port is stored and reported correctly, but the member instance's Endpoint.Port is the engine default 8182 regardless — the instance's port is derived from a per-instance default rather than resolved from the cluster it belongs to. Observed: cluster Port 8191 -> instance Endpoint.Port 8182; cluster Port 8183 -> instance Endpoint.Port 8182 on both CreateDBInstance's projection path and DescribeDBInstances.
Why: a client that moves a Neptune graph endpoint off 8182 (the documented way to satisfy security-group, proxy or firewall rules) builds its connection string, SG rule or DNS record from DBInstance.Endpoint.Address/Port and is handed a port the cluster is not on, so every data-plane connection to the instance endpoint is aimed at the wrong port while the cluster record says otherwise — the two records contradict each other.
Fix: the CreateDBInstance handler's instance state and the shared DBInstance/Endpoint projection — Endpoint.Port must be resolved from the owning DB cluster's stored Port (falling back to 8182 only when the cluster itself has no port set), and must be preserved across unrelated ModifyDBInstance/ModifyDBCluster calls.
Traces: neptune.instance-endpoint-port-inherits-cluster-custom-port (cluster 8183, instance reported 8182); neptune.cluster-port-survives-modify-then-blocks-duplicate-and-busy-delete (cluster 8191, instance reported 8182).

Cause 2 of 2: ModifyDBCluster's refusal of a Port below the valid range carries the emulator's generic validation prose instead of AWS's endpoint-port message.
AWS: Smithy ModifyDBClusterMessage.Port (IntegerOptional) doc: "The port number on which the DB cluster accepts connections. Constraints: Value must be 1150-65535. Default: The same port as the original DB cluster." The message text is recorded behavior only (the member carries no range trait and InvalidParameterValue is a common query-protocol error): a ModifyDBCluster whose Port is below the floor is refused HTTP 400, Error.Code 'InvalidParameterValue', Error.Message 'Invalid endpoint port 1149. Valid range is: 1150-65535 '. Fixed text: 'Invalid endpoint port ', '. Valid range is: ', '-65535', and the TRAILING SPACE. Variable parts: the rejected port value taken from the request (1149 in this replay) and the floor 1150 (the engine minimum from the modelled constraint) — one run's value fills the template, it is not part of it. The refusal must also leave the cluster's stored Port unchanged, and the floor itself (Port=1150) must be accepted.
Emulator: the status and Error.Code are right, but the message is the generic member-validation template: 'invalid value 1149 for Port: must be a value from 1150 to 65535'.
Why: a client or operator that matches on, logs or surfaces the service wording sees text AWS never emits, and the refusal is indistinguishable from a generic parameter-shape complaint; CloudFormation and other wrappers that embed the service message verbatim propagate the wrong text to the user.
Fix: the port validation shared by the ModifyDBCluster (and CreateDBCluster) handler — it must raise the Neptune endpoint-port message rather than the crate's generic 'invalid value <v> for <member>' builder. Note the CreateDBCluster side of this same template is already described as cause 2 of 20261117T150412Z-neptune-3-net-new-causes-createdbcluster-ignores-the.md; the ModifyDBCluster path asserted here is not marked owned by it and is filed on its own evidence.
Traces: neptune.modify-cluster-port-outside-valid-range-rejected.
