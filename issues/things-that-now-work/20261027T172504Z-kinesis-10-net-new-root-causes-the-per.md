## Description

=== Cause 1 of 10: the per-shard WRITE quota is never enforced, so PutRecords is never partially failed ===
Failing checks: kinesis.conc-limits-and-fanout-shard-record-rate-quota-throttles-tiny-records-rejected, kinesis.put-records-partial-failure-reports-per-entry-error-codes, kinesis.kinpartial-resend-failed-subset-appears-exactly-once, kinesis.kinpartial-resend-preserves-per-partition-key-ack-order, kinesis.kinpartial-throttled-entries-rejected-and-absent-past-checkpoint, kinesis.kinpartial-whole-batch-resend-stores-acknowledged-records-twice.
AWS: a shard accepts at most 1,000 records/s and 1 MiB/s of writes. PutRecords reports an overshoot PER ENTRY inside a 200 response, never by refusing the call: Smithy models PutRecordsOutput$FailedRecordCount and PutRecordsResultEntry with ErrorCode/ErrorMessage, documented as "ErrorCodes can be either ProvisionedThroughputExceededException or InternalFailure" and "An ErrorCode value of ProvisionedThroughputExceededException has an error message that includes the account ID, stream name, and shard ID". The refused entries are NOT stored; the acknowledged ones are, exactly once. (ProvisionedThroughputExceededException is also modeled on PutRecords for the call-level case.)
Emulator: no write-rate or write-byte accounting exists on any shard. 16 producers issuing back-to-back 500-entry PutRecords calls for 45 s against ONE shard were all accepted ("never exceeded one shard's record-count write quota -- the limit is not enforced"); 1,800 records of 10,240 bytes (17.6 MiB) written to a ONE-shard stream in 4 calls were accepted entry-for-entry; and 60 back-to-back calls (30,000 entries) produced "0 rejected whole" and not one PARTIAL outcome — every call was wholly accepted. FailedRecordCount is therefore always 0 and no entry ever carries ErrorCode.
Why: the partial-failure contract is the whole reason the PutRecords idiom exists — producers (and the KPL) resend exactly the failed subset and rely on refused entries being absent. Against the emulator that branch is dead code, so a producer that duplicates on resend, or one that never backs off, looks correct in test and loses/duplicates records in production.
Fix: per-shard write-rate and write-byte accounting in the shard state, consulted by the PutRecord/PutRecords handlers; PutRecords must mark over-quota entries with ErrorCode `ProvisionedThroughputExceededException` and an ErrorMessage naming account, stream and shard, count them in FailedRecordCount, and store none of them while storing the accepted siblings.

=== Cause 2 of 10: PutRecords' per-entry size check charges PartitionKey against the 1 MiB budget and uses the wrong error class, code and member path ===
Failing check: kinesis.kinpartial-oversized-entry-rejects-whole-batch-and-stores-nothing.
AWS: PutRecordsRequestEntry$Data is a blob (@length max 10485760 in the model) and PartitionKey is a separate @length 1..256 member; the effective 1 MiB per-record ceiling is applied by the front-end validator to the DATA BLOB ALONE, so a 1048576-byte Data with any partition key is ACCEPTED, and one byte more is refused HTTP 400 `ValidationException` with `1 validation error detected: Value at 'records.<n>.member.data' failed to satisfy constraint: Member must have length less than or equal to 1048576` — fixed text apart from `<n>` (the offending entry's position in the submitted list) and the limit (the stream's MaxRecordSizeInKiB x 1024, default 1048576). The whole call is refused and no sibling entry is stored.
Emulator: it adds the partition key's bytes to the data length and refuses with HTTP 400 `InvalidArgumentException` and an invented message `record 3 of the batch: the record's data and partition key total 1048583 bytes, past the 1048576 bytes one record of this stream may carry` (1048583 = a 1048576-byte at-limit Data plus the 7-byte key `pk-over`; those numbers are this run's fill-ins, the defect is the addition). The consequence is visible on the HAPPY path: the check's at-limit control batch — the same five entries with the largest trimmed to exactly 1048576 bytes — is REFUSED outright, and the exception escapes the check.
Why: producers that fill records to the documented 1 MiB boundary are rejected by the emulator while working against AWS; and a client branching on ValidationException versus InvalidArgumentException takes the wrong path. This is the PutRecords sibling of Cause 2 of 20261027T011654Z-kinesis-9-net-new-root-causes-cloudformation-aws.md (PutRecord), which carries neither this check's replay key nor the entry-indexed `records.<n>.member.data` member path; both must be fixed at the same shared validation site.
Fix: the size validation shared by the PutRecord/PutRecords handlers must measure Data only, compare it against the stream's MaxRecordSizeInKiB-derived ceiling, and raise the front-end ValidationException with the entry-indexed member path in AWS's wording.

=== Cause 3 of 10: the 500-entry batch-length ValidationException does not echo the rejected value ===
Failing check: kinesis.put-records-exceeds-batch-limit-fails.
AWS: Smithy constrains PutRecordsInput$Records to @length 1..500. A 501-entry call is refused HTTP 400 `ValidationException` whose message echoes the submitted list as the validator rendered it: `1 validation error detected: Value '[PutRecordsRequestEntry(data=java.nio.HeapByteBuffer[pos=0 lim=1 cap=1], explicitHashKey=null, partitionKey=pk-0), …]' at 'records' failed to satisfy constraint: Member must have length less than or equal to 500` — fixed text is `1 validation error detected: Value '`, `' at 'records' failed to satisfy constraint: Member must have length less than or equal to 500`; the variable part is the rendered entry list taken from the request.
Emulator: same code and member path, but the value is replaced by a summary count: `1 validation error detected: Value '501 items' at 'records' failed to satisfy constraint: Member must have length less than or equal to 500`.
Why: these strings are compared character-for-character by SDK conformance tests and by operators diagnosing a rejected batch; `'501 items'` is emulator-specific text no AWS client can produce. It is the list-length branch of the same ValidationException renderer whose pattern/enum/length branches are Causes 6-8 of 20261027T011654Z-kinesis-9-net-new-root-causes-dryrun-not.md, which does not carry this check.
Fix: the list-length branch of the shared ValidationException renderer must echo the rendered value instead of an item count.

=== Cause 4 of 10: the stream-not-found message is invented on DescribeStreamSummary too ===
Failing check: kinesis.delete-stream-removes-it.
AWS: ResourceNotFoundException (client, HTTP 400) is modeled on DescribeStreamSummary, PutRecord and DeleteStream. After a completed DeleteStream, both an independent read and a write against the dead name are refused with `Stream <streamName> under account <accountId> not found.` — fixed text `Stream `, ` under account `, ` not found.`; variables = the requested stream name and the caller's account id.
Emulator: both answer the lower-case invented template `stream <streamName> not found under account <accountId>` — reversed word order, no trailing period. The delete itself, the disappearance from ListStreams and the 4xx status are all correct; only the message diverges.
Why: this text is how a client (and every message-matching test or runbook) distinguishes a deleted stream from the other 400s the same operations raise. Cause 2 of 20261027T011654Z-kinesis-9-net-new-root-causes-dryrun-not.md describes this same shared template for PutRecord/GetShardIterator/ListShards but carries neither this check's replay key nor the DescribeStreamSummary surface; one fix closes both, and whoever fixes either should close both.
Fix: the shared stream-lookup not-found construction used by DescribeStreamSummary and PutRecord must emit AWS's template filled from the request and the account in state.

=== Cause 5 of 10: SplitShard publishes the completed shard map while the stream still reports UPDATING, so DeleteStream is refused ===
Failing check: kinesis.split-shard-new-starting-hash-key-outside-parent-range-rejected.
AWS: a reshard is complete exactly when its result is visible: ListShards shows the two children with ParentShardId set and the parent carrying an EndingSequenceNumber, and at that point DescribeStreamSummary reports StreamStatus ACTIVE again. DeleteStream requires that state — Smithy: "If the stream is in the ACTIVE state, you can delete it", and ResourceInUseException is documented "The resource is not available for this operation. For successful operation, the resource must be in the ACTIVE state." A client that observes the settled shard map can therefore delete the stream.
Emulator: the three out-of-range SplitShard calls are correctly refused with InvalidArgumentException and the midpoint control split produces both children with the parent closed — but the stream still reads UPDATING afterwards, so the check's verified teardown is refused: HTTP 400 `ResourceInUseException`, `stream <streamName> is in state UPDATING, not ACTIVE; the stream must be ACTIVE for this operation` (that message's own wording is Cause 6 of 20261027T095220Z-kinesis-6-net-new-root-causes-startstreamencryption-accepts.md; the defect here is the STATE, not the text). Hypothesis: the shard map is mutated synchronously while StreamStatus is left on an independent (or never-completed) UPDATING transition.
Why: every reshard-then-act workflow breaks — the only completion signal AWS gives (the new shard map) no longer implies the stream is usable for control-plane calls, so teardown, tagging and further resharding fail with a retryable-looking error after the work is already done, and streams leak.
Fix: the SplitShard (and MergeShards/UpdateShardCount) handler must publish the new shard map and the return to StreamStatus=ACTIVE as one settled state, so no observable ordering exists in which children are listed and the parent is closed while the stream is still UPDATING.

=== Cause 6 of 10: the KMS-CMK data-plane contract is unreachable — the disabled-CMK check never observes either an encrypted read-back or a refusal ===
Failing check: kinesis.disabled-cmk-blocks-the-stream-data-plane-until-re-enabled.
AWS: on a stream with EncryptionType=KMS under a customer CMK, (a) a record read back through GetRecords reports EncryptionType `KMS`; (b) while that CMK is DISABLED, both PutRecord and GetRecords are refused HTTP 400 `KMSDisabledException` with message `<keyArn> is disabled.` — fixed text ` is disabled.`, variable = the key ARN from the stream's encryption state (Smithy models KMSDisabledException, KMSInvalidStateException, KMSNotFoundException, KMSAccessDeniedException on PutRecord/PutRecords/GetRecords); (c) StartStreamEncryption with that disabled key is refused HTTP 400 `InvalidArgumentException`, `Key is not enabled.` (fixed text, no variables); and (d) re-enabling the key makes the identical calls succeed again, with the shard holding exactly the accepted records.
Emulator: the check reached the harness's 60 s cap without ever getting past this contract — it either never read a record back tagged EncryptionType=KMS (its positive control, bounded at 60 s) or never saw PutRecord refused after the CMK was disabled (its next step, polled every 15 s). No step of the check waits on a long AWS-side window before those, so the stall is the emulator's. Hypothesis: the KMS key's state is never consulted on the data path and records are not tagged with the stream's encryption type — consistent with Cause 4 of 20261027T095220Z-kinesis-6-net-new-root-causes-startstreamencryption-accepts.md, where StartStreamEncryption accepts a key that does not resolve in KMS at all. That issue covers only the control-plane acceptance and carries neither this check nor the data-plane behavior.
Why: a disabled or revoked CMK is the standard break-glass control for a stream's data; against the emulator the whole KMS error family on the data plane is unreachable, so producer/consumer code that must handle KMSDisabledException is never exercised and an operator's key disable appears to have no effect at all.
Fix: the PutRecord/PutRecords/GetRecords handlers must resolve the stream's CMK against the KMS emulator's key state on every call and refuse with the modeled KMSDisabledException in AWS's wording while it is disabled, and the record read path must report EncryptionType from the stream's encryption state.

=== Cause 7 of 10: CreateChannel validates neither the KMS key's policy nor the service execution role's KMS permissions ===
Failing checks: kinesis.create-channel-invalid-kms-key-denied, kinesis.create-channel-kms-access-denied, kinesis.create-channel-without-kms-permission-must-be-denied.
AWS: CreateChannel models ValidationException, AccessDeniedException and the whole KMS error family (KMSAccessDeniedException, KMSDisabledException, KMSInvalidStateException, KMSNotFoundException, KMSOptInRequired, KMSThrottlingException), all client kind HTTP 400, because the service checks the EncryptionConfiguration.KeyId synchronously with the ServiceExecutionRoleARN before anything is created. Recorded behavior: when the key policy denies kms:GenerateDataKey*/kms:Decrypt to everyone, or when the role's IAM policy omits those actions, the call is refused HTTP 400 `ValidationException` with `The service execution role is not authorized to access the KMS key specified in EncryptionConfiguration.KeyId. Verify that the role's IAM policy and KMS key policy grants kms:Decrypt and kms:GenerateDataKey permissions.` (fixed text, no variable parts) and NO channel exists afterwards — ListChannels does not show the name.
Emulator: all three requests SUCCEED. CreateChannel answers HTTP 200 with a full ChannelDescription (ChannelStatus CREATING, a minted channel/<name> ARN) for a key whose policy denies every data-key action and for a role with no kms:* grant at all; the replay reports `channel with a denied KMS key should not have been created (got arn:aws:kinesis:<region>:<account>:channel/<name>)` and `create_channel unexpectedly succeeded while the role lacked KMS permission`.
Why: this is the over-permissive direction. A configuration that AWS refuses up front is accepted, so a channel is minted that can never deliver (its delivery role cannot use the key) and the client gets no failure signal at create time — exactly the misconfiguration the synchronous check exists to surface.
Fix: a KMS-authorization step in the CreateChannel handler, before any channel state is written: resolve EncryptionConfiguration.KeyId against the KMS emulator, evaluate the key policy and the ServiceExecutionRoleARN's IAM policy for kms:Decrypt/kms:GenerateDataKey, and refuse with the modeled ValidationException in AWS's wording, leaving no channel behind.

=== Cause 8 of 10: the channel duplicate-name and channel-not-found messages are invented ===
Failing checks: kinesis.create-channel-duplicate-name-rejected, kinesis.describe-channel-nonexistent-fails.
AWS: channel names are unique per account and region; a second CreateChannel with a live name is refused HTTP 400 (modeled ResourceInUseException) with `Channel <channelName> under account <accountId> already exists.` — fixed text `Channel `, ` under account `, ` already exists.`; variables = the requested channel name and the caller's account id. DescribeChannel for a channel that was never created is refused HTTP 400 `ResourceNotFoundException` with `Channel <channelId> under account <accountId> not found.` — same fixed spans, variable = the channel identifier taken from the supplied ChannelARN's `channel/<id>` segment (NOT the whole ARN) and the account id.
Emulator: the codes are right, the messages are invented lower-case sentences: `channel <channelName> already exists in this account and region; a channel name is unique within your account and region`, and `channel <full channel ARN> not found under account <accountId>` — reversed word order, no trailing period, and the not-found one echoes the entire ARN where AWS names only the channel identifier.
Why: both refusals share their code with other 400s on the same operations, so the message is the only discriminator a client or operator has; and the ARN-vs-name difference breaks anything parsing the identifier out of the sentence.
Fix: the duplicate-name guard in the CreateChannel handler and the not-found construction in the channel lookup shared by DescribeChannel/DeleteChannel must emit AWS's two templates, filled from the request and from state.

=== Cause 9 of 10: TagResource does not accept a channel ARN — it answers as if the channel were a missing stream ===
Failing check: kinesis.create-channel-lifecycle.
AWS: Smithy constrains TagResourceInput$ResourceARN with the pattern `^arn:aws.*:kinesis:.*:\d{12}:.*(stream|channel)/\S+$`, i.e. a channel ARN is a first-class tagging target, and TagResource on a channel that has left CREATING succeeds with an empty 200 body (ResourceInUseException is the modeled refusal while it is still CREATING; ResourceNotFoundException only when the channel really does not exist).
Emulator: TagResource with a well-formed channel ARN is refused HTTP 400 `ResourceNotFoundException` with `stream arn:aws:kinesis:<region>:<account>:channel/<name> not found under account <accountId>` — the handler resolves every ResourceARN as a STREAM and then reports the channel as a missing stream (note the message says "stream" for a `channel/` ARN). The channel exists and DescribeChannel can read it. Because this is the first call after the channel settles, the whole channel lifecycle contract behind it (ACTIVE status, ListChannels visibility, the dead-ARN refusal after DeleteChannel) is never graded.
Why: channels cannot be tagged at all, so tag-based discovery, cost allocation and the cleanup tooling that finds resources by tag silently miss every channel; and the error a client gets names the wrong resource type.
Fix: the TagResource (and UntagResource/ListTagsForResource) handler must dispatch on the ResourceARN's resource segment, resolving `channel/<name>` against channel state and tagging it, and reserve the stream not-found message for `stream/` ARNs.

=== Cause 10 of 10: DeleteStream ignores channels attached to the stream and deletes it ===
Failing check: kinesis.delete-channel-with-dependents-blocked.
AWS: a stream named in a channel's StreamConfigurationList is a dependency of that channel. DeleteStream on it is refused HTTP 400 `ResourceInUseException` (modeled on DeleteStream) with `Stream <streamName> under account <accountId> cannot be deleted because it is associated with one or more channels. Delete all associated channels before deleting the stream.` — fixed text apart from the stream name from the request and the caller's account id; the stream survives the refusal (DescribeStreamSummary still reports ACTIVE), and the identical call succeeds once the channel is deleted.
Emulator: the call SUCCEEDS — HTTP 200 with an empty body (`content-length: 2`) — and the stream is deleted out from under the live channel. The positive control (a stream with no channel) deletes correctly, so the dependency check is simply absent.
Why: this is the over-permissive direction and it corrupts state AWS cannot reach: a channel is left referencing a stream that no longer exists, so the delivery pipeline fails later with no signal at the moment of the destructive call, and the guard rail protecting a shared stream from a careless delete does not exist.
Fix: a dependency check in the DeleteStream handler (before any state mutation) that scans channel state for a StreamConfigurationList entry naming the stream and refuses with the modeled ResourceInUseException in AWS's wording.
