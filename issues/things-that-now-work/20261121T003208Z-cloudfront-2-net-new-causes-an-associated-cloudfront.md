# cloudfront: 2 net-new causes — an associated CLOUDFRONT web ACL is still not enforced on the e2e edge path, and GetOriginAccessControlConfig reports an absent OAC id as a malformed id

> _Note: this issue was identified against the code base at commit `4f8289a55da0569c35b4094a258c497c237277f1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateDistributionWebACL

## Description
TWO net-new root causes in the cloudfront service; a fixer must close BOTH before submitting. Numbered below with their own failing check ids.

Cause 1 of 2: a WAFv2 CLOUDFRONT-scope web ACL associated with a distribution has no effect on the served edge path, so the end-to-end block/restore workflow never completes.
AWS:      recorded behavior only for the edge path; the control-plane binding is modelled (Smithy, services/service-com-amazonaws-cloudfront-cloudfront2020-05-31: AssociateDistributionWebACL — PUT /2020-05-31/distribution/{Id}/associate-web-acl, input {Id @httpLabel required, WebACLArn required, IfMatch @httpHeader If-Match}, errors AccessDenied 403 / EntityLimitExceeded 400 / EntityNotFound 404 / InvalidArgument 400 / InvalidIfMatchVersion 400 / PreconditionFailed 412; DisassociateDistributionWebACL — PUT /2020-05-31/distribution/{Id}/disassociate-web-acl, same error set minus EntityLimitExceeded). Recorded behavior: once a CLOUDFRONT-scope web ACL with a Block rule (ByteMatchStatement CONTAINS on UriPath) is associated and the distribution is Deployed, (a) a viewer request on a path the rule does NOT match is answered 200 with the origin's bytes, (b) a viewer request on the MATCHING path is answered 403 by the edge and the origin is never reached, and (c) after DisassociateDistributionWebACL the same matching path is answered 200 with the real origin bytes again.
Emulator: the check never observes that sequence — it ends on 'Check timed out after 60.0s' while polling the distribution's DomainName, so the associated web ACL produces no observable change at the edge (no 403 for the blocked path) and the workflow stalls rather than answering either way. The association call itself is accepted (the check reached the data-plane polls), so the divergence is in the edge request pipeline, not in the control-plane binding.
Why:      WAF protection a client believes sits in front of its distribution is inert, and a request it expects to be blocked is instead carried to the origin (or left unanswered). A rule regression — one that blocks legitimate traffic or fails to block hostile traffic — cannot be detected before production, and because the edge answers nothing at all here, client code that depends on a definite 403/200 hangs instead of failing fast.
Fix:      the cloudfront edge request pipeline — evaluate the distribution's associated web ACL (DistributionConfig.WebACLId / the ARN bound by AssociateDistributionWebACL) against each viewer request BEFORE the origin fetch, answer 403 on a Block action, pass the request through on Allow, and drop the evaluation again on DisassociateDistributionWebACL; it must consult the wafv2 service's web-ACL rule evaluation. Related, NOT covering: open issue 20261110T105638Z-cloudfront-4-net-new-causes-origin-group-failover.md describes the same enforcement gap as its Cause 2, but it carries only the replay key cloudfront.web-acl-association-enforced-at-edge and not this e2e check's key, so closing it would leave this check failing. Also related and not covering: 20261117T151821Z-cloudfront-wafv2-2-net-new-causes-createdistribution-accepts.md (control-plane WebACLId admission only). Note on grading: the only diagnosis the replay emits for this check is the 60 s timeout, so the step it stalls on (the positive-control 200, the blocked 403, or the restored 200) must be confirmed on re-replay.
Traces:   cloudfront.e2e-distribution-webacl-association-blocks-request.

Cause 2 of 2: GetOriginAccessControlConfig refuses a well-formed but absent OAC id with a malformed-identifier message instead of AWS's not-found sentence.
AWS:      404 with error code NoSuchOriginAccessControl and Error.Message 'The specified origin access control does not exist.' Smithy: GetOriginAccessControlConfig input {Id: string, @httpLabel, required} with NO @pattern and NO @length constraint; http {method GET, uri /2020-05-31/origin-access-control/{Id}/config, code 200}; errors AccessDenied (httpError 403) and NoSuchOriginAccessControl (httpError 404, doc 'The origin access control does not exist.'). Because the model places no format constraint on Id, AWS carries any supplied id through to the state lookup and reports the resource ABSENT; no modelled basis exists for a malformed-identifier refusal on this route. The message for this class is wholly FIXED text — no id, name, limit or timestamp from the request or from state appears in it — so reproducing the sentence verbatim is the whole requirement (wording per recorded behavior; the model supplies the error shape, not the prose).
Emulator: answers the same 404 and the same code NoSuchOriginAccessControl, but with Error.Message 'Id format is invalid' — fixed text of a malformed-argument class AWS does not select here, emitted by a pre-lookup id-shape predicate on the /{Id}/config route. Only Error.Message diverges; the check's code assertion passed.
Why:      'Id format is invalid' tells a caller its own id handling is broken (a non-retryable programming error), while 'The specified origin access control does not exist.' tells it the OAC is gone and the correct response is to create or re-resolve it. Create-if-absent logic, cleanup paths that swallow not-found by message, and tests branching on the wording all take the wrong branch; and because the emulator's format predicate is narrower than AWS's (which has none per the model), ids AWS would resolve may never be looked up against state at all.
Fix:      GetOriginAccessControlConfig's request validation / handler for GET /2020-05-31/origin-access-control/{Id}/config — drop the pre-lookup malformed-id refusal for a form the model does not constrain and emit NoSuchOriginAccessControl 404 carrying its fixed not-found sentence whenever the id names no origin access control. Related, NOT covering: open issue 20261118T131652Z-cloudfront-getoriginaccesscontrolconfig-reports-a-well-formed-absent-id.md records this identical inversion but carries ONLY the replay key cloudfront.get-origin-access-control-config-nonexistent-rejected; this op-contract check's key is not on it, so it is filed here. Same family on sibling routes: 20261116T020304Z-cloudfront-2-net-new-causes-createinvalidation-and-getoriginaccesscontrol.md.
Traces:   cloudfront.op-contract-get-origin-access-control-config.
