# ELB Classic: 2 net-new causes — the published DNSName is an unserved *.elb.amazonaws.com host (cross-zone data plane unreachable), and the LB-cookie stickiness scenario never reaches a verdict because a registered instance never becomes InService

> _Note: this issue was identified against the code base at commit `c27f673b5184c286166c0255cbce219d9f1e7379`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateLoadBalancer

## Description
2 causes, both in the ELB Classic (elasticloadbalancing) emulator. Neither failing check below is marked ALREADY FILED or OWNED in the replay report, so neither is gated by an existing issue; the open issues that report the same faults from other recorded units are named per cause.

Cause 1 of 2 — CreateLoadBalancer publishes a real-AWS *.elb.amazonaws.com DNSName that the emulator does not serve, so the Classic load balancer has no reachable data plane and the cross-zone-load-balancing behaviour cannot be exercised at all. Failing check: elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.
AWS: Smithy: CreateLoadBalancer (input CreateAccessPointInput {LoadBalancerName required, Listeners required, AvailabilityZones/Subnets/SecurityGroups/Scheme/Tags}; output CreateAccessPointOutput {DNSName: DNSName}); DescribeLoadBalancers reports the same DNSName on LoadBalancerDescription. The contract of DNSName is that it is the host a client sends real HTTP to: resolving it and connecting to the listener port reaches the load balancer, which forwards to the registered, InService instances (with CrossZoneLoadBalancing enabled via ModifyLoadBalancerAttributes, a single node spreads requests to instances in every enabled zone). The host NAME is generated per load balancer and is not itself a requirement; what is required is that the name the emulator publishes is a host the emulator itself answers on, because an emulator run may reach only the emulator.
Emulator: CreateLoadBalancer returns a DNSName in real AWS's public namespace — of the form <lb-name>-<digits>.<region>.elb.amazonaws.com (the replay observed 'sim2real-behav-clb-718c26a928df-9879174754.us-west-2.elb.amazonaws.com'; the name and digits are per-run values, the elb.amazonaws.com suffix is the defect). The emulator is reached on the endpoint under test, so the first GET of http://<DNSName>/ is refused before it leaves the runner: simparity.egress.EgressRefused: egress refused: '<published DNSName>' is not the endpoint under test. No data-plane assertion in the check is ever evaluated.
Why: every client that uses the returned DNSName as AWS documents it — an HTTP client, a Route 53 alias, a health probe, an integration test — is pointed at a host outside the emulator. Against a real account that host is someone else's load balancer or does not resolve; inside a sandbox the request is refused. The whole Classic data plane (cross-zone spreading, listener forwarding, stickiness) is unreachable through the only address AWS gives a client.
Fix: the CreateLoadBalancer handler's DNSName construction and the same projection in DescribeLoadBalancers/state — the published host must be an address the emulator answers on (the endpoint it is reached on, with the load balancer's listener port), not a host in AWS's elb.amazonaws.com namespace, and the data-plane listener must accept HTTP there and forward to the registered instances honouring the CrossZoneLoadBalancing attribute.
Traces: check elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone. Code: services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/ops/create_load_balancer.rs, src/ops/describe_load_balancers.rs, src/state.rs. Related open issues that do NOT cover this check (they carry other checks'/fixtures' keys): 20261109T141728Z-elb-classic-the-published-dnsname-is-a-real.md (owns elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic, elb.registered-instance-serves-real-http-through-elb-dns-name) and 20261109T233833Z-elasticloadbalancing-elb-classic-publishes-an-unreachable-elb-amazonaws-com.md (wire corpus).

Cause 2 of 2 — the duration-based (LB-cookie) stickiness scenario never reaches any verdict: a backend registered with RegisterInstancesWithLoadBalancer and serving the configured HTTP health-check target never reports State=InService, so the checks spend their whole budget in the InService poll and are killed before the stickiness assertions run. Failing checks: elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance.
AWS: Smithy: DescribeInstanceHealth output InstanceStates/InstanceState {State 'Valid values: InService | OutOfService | Unknown', ReasonCode 'Valid values: ELB | Instance | N/A', Description}. State is the OUTCOME of the load balancer probing each registered instance on the health check configured by ConfigureHealthCheck: after HealthyThreshold consecutive successful probes the member is State='InService', ReasonCode='N/A', Description='N/A' (those strings are fixed AWS text; only InstanceId is request/state-derived). Only then does AWS route traffic, and only then can CreateLBCookieStickinessPolicy + SetLoadBalancerPoliciesOfListener be observed: AWS then mints a Set-Cookie: AWSELB=<opaque> on a cookie-less response and pins every subsequent request carrying that cookie to the same registered instance, while a cookie-less client is still spread across instances.
Emulator: both checks end 'Check timed out after 60.0s' having produced no assertion failure, although their own declared deadlines are _INSERVICE_DEADLINE_S=480 and _HTTP_DEADLINE_S=360 — i.e. they were still inside the bounded _wait_instance_health poll of DescribeInstanceHealth for State='InService' when the wrapper ended them. The handler (src/ops/describe_instance_health.rs calling state::settle_instance_health/instance_health) derives health from the registration instant rather than from a probe of the instance on the configured Target, so InService is unreachable by construction and the poll can never be satisfied. Hypothesis: with health stuck below InService the checks never advance to the AWSELB cookie legs, so whether stickiness itself is implemented is not yet observable.
Why: a client cannot distinguish a healthy backend from a failed one, every registration/deploy gate that waits for InService before sending traffic blocks until its own timeout, and the stickiness contract behind that gate (AWSELB cookie minting and pinning) can never be reached — a load balancer that never has an InService instance never serves traffic at all.
Fix: the per-load-balancer instance-health state and the health-check evaluation that feeds it in the ELB Classic crate's state, as read by the DescribeInstanceHealth handler — health must come from an actual probe of the registered instance against the load balancer's configured Target/Interval/Timeout/thresholds and emit the InService / 'N/A' / 'N/A' triple after HealthyThreshold consecutive successes; and the listener data plane must then mint and honour the AWSELB stickiness cookie once a duration-based policy created by CreateLBCookieStickinessPolicy is attached with SetLoadBalancerPoliciesOfListener.
Traces: checks elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance. ## Resolution

Both causes were implemented as the Fix sections above ask.

Cause 1: `CreateLoadBalancer` opens a core-owned loopback listener per load balancer and publishes its `host:port` as `DNSName` (`src/state/load_balancer_endpoint.rs`); `CanonicalHostedZoneName` keeps the Route 53 hosted-zone name; `DeleteLoadBalancer` closes the socket. A new data plane serves that address, and the reserved path `/_aws/elasticloadbalancing-classic/{region}/{name}/…` beside it (`src/service/data_plane.rs`, `src/service/listener_socket.rs`): it runs the health checks the clock owes, selects among the registered InService instances honouring `CrossZoneLoadBalancing`, and answers the statuses Classic documents for having no instance to send a request to (503) and for a registered instance it could not connect to (504).

Cause 2: `SetLoadBalancerPoliciesOfListener` is implemented (it answered 501), and a listener carrying a duration-based policy mints and honours the `AWSELB` cookie naming the instance it selected (`src/service/stickiness.rs`). The health half (probe-driven `InService` / `N/A` / `N/A`) was already in place from 20261107T072636Z and is now pinned from traffic as well.

Residual gap, recorded here rather than left implicit: the three recorded checks still do not pass, for two reasons OUTSIDE this crate.

* The cross-zone check resolves the published name with `socket.getaddrinfo(lb["dns"], 80)` and then connects to port 80, so it needs a BARE host that resolves plus a server on port 80. The core listener API vends a port of its own choosing and takes no requested port (`vendor/engine/src/lib.rs`, `emulator_server::Listeners::tcp_plaintext`), and publishing a bare host would announce an address nothing answers — so the `host:port` this fix publishes is the only reachable form available to the emulator (and the form the ELBv2 crate publishes).
* Every remaining leg of all three checks compares the BODY a backend served. No component of this emulator runs a server inside an EC2 instance: an instance's user data is interpreted as a shell session with no network (`services/service-com-amazonaws-ec2-amazonec2/src/state/guest_console.rs`), which is the same platform gap the open issues `20261108T200221Z-elbv2-an-alb-never-forwards-a-successful-http.md` and `20261110T143849Z-ec2-elbv2-ssm-the-guest-driven-alb-target.md` carry for ELBv2.
