# EBS direct-API snapshots are invisible to EC2 DescribeSnapshots, and PutSnapshotBlock ignores an explicit IAM Deny (2 causes)

> _Note: this issue was identified against the code base at commit `a12986f4241917f433abd9b7a93c682fd0b73a1b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Two net-new root causes found replaying the simparity-behavioral-aws-v1 EBS direct-API checks against this build (2/29 checks passed). === Cause 1 of 2: a snapshot created by EBS StartSnapshot never becomes visible to EC2 DescribeSnapshots, so no snapshot ever reaches `pending`/`completed` for a client ===
AWS: StartSnapshot creates a real EC2 snapshot in state `pending` and returns it (Smithy com.amazonaws.ebs#StartSnapshot: http POST /snapshots code 201, output SnapshotId/OwnerId/Status/VolumeSize/ParentSnapshotId); CompleteSnapshot (http POST /snapshots/completion/{SnapshotId} code 202, output Status) drives that same snapshot to `completed`. The EBS model exposes no read of snapshot state at all, so EC2 DescribeSnapshots is the only way a caller observes the lifecycle: immediately after StartSnapshot the id resolves with State `pending`, and after CompleteSnapshot it resolves with State `completed` and Progress `100%`; a filter on `description` matches the snapshot StartSnapshot was given. Recorded behavior only for the EC2 response shape. An id EC2 does not know is refused with error code `InvalidSnapshot.NotFound`.
Emulator: `ec2.describe_snapshots(SnapshotIds=[<id returned by StartSnapshot>])` is refused with code `InvalidSnapshot.NotFound` indefinitely — the id StartSnapshot just minted is in no EC2 snapshot state — and `ec2.describe_snapshots(Filters=[{Name: 'description', Values: [<the description passed to StartSnapshot>]}])` answers 200 with an EMPTY `Snapshots` list. So DescribeSnapshots is implemented now, but the EBS direct-API handlers write snapshot state the EC2 read path cannot see. 19 checks spin in their completion-poll loop until the 60 s check cap (`Check timed out after 60.0s`); two raise the poll's own TimeoutError (`...the 60.0s wait ended with snap-... not yet visible`); one fails the independent description-filter read with `expected exactly one snapshot 'snap-...' for description '...', found []`.
Why: the EBS direct-API contract is write-then-wait-then-read. A client that calls StartSnapshot / PutSnapshotBlock / CompleteSnapshot and then polls DescribeSnapshots (or the `snapshot_completed` waiter) is told the snapshot does not exist, so it never learns the snapshot is usable, cannot verify an idempotent StartSnapshot retry created exactly one snapshot, and cannot drive the delete path (every check's cleanup calls ec2:DeleteSnapshot on an id EC2 denies). The whole lifecycle is unusable end to end even though the individual EBS operations answer.
Fix: the snapshot state shared between the ebs and ec2 service crates — the EBS StartSnapshot/CompleteSnapshot handlers must register and update the snapshot in the same state the EC2 DescribeSnapshots/DeleteSnapshot handlers read, so StartSnapshot yields a pending snapshot visible by id and by `description`/`tag:` filter, CompleteSnapshot moves it to completed with Progress '100%', and DeleteSnapshot removes it. The previous fix implemented the EC2 handler against the EC2-only snapshot store; this is the missing registration on the EBS side.
Traces: ebs.start-snapshot-returns-pending-status and ebs.start-snapshot-client-token-conflict-rejected (shortest repros, both raise the 'not yet visible' TimeoutError), ebs.start-snapshot-client-token-idempotent-same-payload (description filter returns []), ebs.complete-snapshot-transitions-to-completed-state, ebs.complete-snapshot-twice-is-idempotent, ebs.concurrent-put-snapshot-block-distinct-indices, ebs.full-snapshot-round-trip-write-read-complete, ebs.get-snapshot-block-invalid-token-rejected, ebs.incremental-child-lists-and-serves-inherited-parent-blocks, ebs.incremental-snapshot-list-changed-blocks, ebs.list-changed-blocks-token-presence-distinguishes-new-from-rewritten-block, ebs.list-changed-blocks-unrelated-snapshots-rejected, ebs.list-snapshot-blocks-expiry-time-in-future, ebs.list-snapshot-blocks-maxresults-out-of-range-rejected, ebs.list-snapshot-blocks-reflects-written-blocks, ebs.list-snapshot-blocks-starting-block-index-windows-the-listing, ebs.put-snapshot-block-after-completion-rejected, ebs.put-snapshot-block-response-returns-checksum-and-algorithm, ebs.start-snapshot-description-and-tags-persist, ebs.start-snapshot-encrypted-with-parent-rejected, ebs.start-snapshot-nonexistent-parent-rejected.

=== Cause 2 of 2: PutSnapshotBlock performs no authorization — a caller whose identity policy explicitly Denies ebs:PutSnapshotBlock writes the block successfully ===
AWS: PutSnapshotBlock is an authorized data-plane write. Smithy com.amazonaws.ebs#PutSnapshotBlock declares `AccessDeniedException` (@httpError 403) among its errors and is bound to aws.auth#sigv4. An explicit Deny on `ebs:PutSnapshotBlock` in the caller's identity-based policy refuses the request with error code `AccessDeniedException` (HTTP 403) and the standard IAM denial message; the fixed text is 'User: <caller-arn> is not authorized to perform: ebs:PutSnapshotBlock on resource: <snapshot-arn> with an explicit deny in an identity-based policy', and its variable parts are the assumed-role caller arn built from the request's credentials (arn:aws:sts::<account-id>:assumed-role/<role-name>/<session-name>), the action name, and the target snapshot arn built from the request (arn:aws:ec2:<region>::snapshot/<snapshot-id>). The denied write leaves no block behind.
Emulator: the request SUCCEEDS — HTTP 201 with a normal PutSnapshotBlockResponse (`{'Checksum': '<b64 sha256>', 'ChecksumAlgorithm': 'SHA256'}`, headers x-amz-checksum / x-amz-checksum-algorithm) — so the block is written by a principal that is explicitly denied. No AccessDeniedException is produced at all. The same session's restricted ec2:DescribeSnapshots call (Allowed by the same policy) succeeds, so credentials and the assumed role are in effect; only the Deny evaluation is missing.
Why: authorization is silently absent on the EBS data plane. Any test or control that asserts a least-privilege boundary passes against the emulator while the write goes through, a denied principal corrupts snapshot content it must not be able to touch, and a client never sees the 403 class it would normally handle (re-assume/escalate) instead of treating the write as durable.
Fix: the PutSnapshotBlock handler's request authorization — evaluate the caller's identity policy for `ebs:PutSnapshotBlock` on the snapshot resource before touching block state, and refuse an explicit Deny with the modeled 403 AccessDeniedException rendered from the caller arn, the action and the snapshot arn; the write must not persist.
Traces: ebs.missing-permission-put-snapshot-block-rejected.
