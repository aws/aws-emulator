## Description
Two net-new root causes (Cause 1 of 2, Cause 2 of 2). Both must be closed before submitting.

Context on neighbouring open issues (neither covers these): 20261026T021948Z-firehose-s3-sesv2-both-sesv2-firehose-event-destination-e5ab30.md and 20261026T044445Z-sesv2-createconfigurationseteventdestination-stub.md report CreateConfigurationSetEventDestination answering 501 NotImplemented as a scaffold stub. The open Firehose-side issue 20261024T005347Z-firehose-never-delivers-buffered-records-to-the-s3.md covers Firehose's own S3 flush; Cause 2 below is upstream of it — SES never hands Firehose a record at all.

Cause 1 of 2: CreateConfigurationSetEventDestination does not validate the referenced IAM role's assumability, so a KinesisFirehoseDestination naming a role whose trust policy never allows ses.amazonaws.com is accepted and persisted.
Failing check ids for this cause: firehose__s3__sesv2.firehose-destination-rejects-a-role-the-stream-cannot-be-assumed-by.

AWS: SESv2 restJson1, POST /v2/email/configuration-sets/{ConfigurationSetName}/event-destinations, success HTTP 200 with an EMPTY body. Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json): CreateConfigurationSetEventDestination input {ConfigurationSetName @httpLabel required, EventDestinationName required, EventDestination (EventDestinationDefinition) required}; EventDestinationDefinition.KinesisFirehoseDestination requires IamRoleArn and DeliveryStreamArn (both AmazonResourceName, @length min 1); modeled errors are AlreadyExistsException 400, BadRequestException 400 ("The input you provided is invalid."), LimitExceededException 400, NotFoundException 404, TooManyRequestsException 429. SES validates the destination role SYNCHRONOUSLY at creation: a role the service cannot assume is refused with BadRequestException, HTTP 400, and the recorded refusal message is `Could not assume IAM role <ARN>.` — the fixed text is "Could not assume IAM role <" … ">." and the only variable part is the role ARN taken verbatim from the request's EventDestination.KinesisFirehoseDestination.IamRoleArn (no id, name or timestamp from any single run belongs in it). The refusal is permanent, not a propagation transient: it is returned on every repeated attempt, while the identical request against the same delivery stream naming a role trusted by ses.amazonaws.com returns 200, so this is a per-role trust decision and not a blanket refusal. A refused destination must also leave no trace: GetConfigurationSetEventDestinations must list only the accepted destination.

Emulator: the request is accepted — HTTP 200 with the empty body (`{'ResponseMetadata': {'HTTPStatusCode': 200, …, 'content-length': '2'}}`) — for a role whose trust policy allows only lambda.amazonaws.com. services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set_event_destination.rs validates only the configuration-set name, the enum-valued members (MatchingEventTypes, CloudWatch dimension value sources), set existence, duplicate destination name and the per-set destination count, then inserts the EventDestinationRecord. Nothing in the handler reads KinesisFirehoseDestination.IamRoleArn or DeliveryStreamArn, so neither the role's trust policy nor the stream's existence is ever checked, and no BadRequestException path for an unassumable role exists.

Why: a client relying on AWS's synchronous validation is told its wiring is good when it is not. The misconfigured event destination is stored and enabled, so the break surfaces (on AWS) only as silently undelivered events, and a client that uses the 400/200 split to distinguish "fix the trust policy" from "configuration accepted" takes the wrong branch. Negative-path tests that assert the refusal, and any code that treats acceptance as proof the role is assumable, pass against the emulator and fail against AWS.

Fix: the operation's validation inside its handler, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set_event_destination.rs — before inserting the record, resolve EventDestination.KinesisFirehoseDestination.IamRoleArn against the emulated IAM role state and refuse BadRequestException 400 with SES's could-not-assume-role wording (the ARN interpolated from the request) when its trust policy does not allow ses.amazonaws.com to assume it; the same check belongs on UpdateConfigurationSetEventDestination. A refused request must insert nothing into set.event_destinations.

Traces: firehose__s3__sesv2.firehose-destination-rejects-a-role-the-stream-cannot-be-assumed-by ([mismatch]) — its positive control (ses.amazonaws.com-trusted role, same stream and set) now succeeds, and it fails on the next assertion because the wrong-trust role is accepted too.

Cause 2 of 2: SendEmail against a configuration set that has an enabled KinesisFirehoseDestination for SEND publishes no event to the delivery stream, so nothing ever reaches the stream's S3 prefix.
Failing check ids for this cause: firehose__s3__sesv2.firehose-destination-delivers-two-send-events-within-the-buffering-interval.

AWS: SESv2 SendEmail (POST /v2/email/outbound-emails, 200 with MessageId). Smithy: SendEmail input carries ConfigurationSetName; EventDestinationDefinition declares Enabled and MatchingEventTypes (EventTypes) and a KinesisFirehoseDestination {IamRoleArn, DeliveryStreamArn} that, per the model's own documentation, is where "the Amazon SES API v2 sends email events". Recorded behavior: a message sent with that configuration set produces a Send event that SES puts into the named Firehose delivery stream using the destination's role; Firehose then buffers it and flushes newline-delimited JSON objects under the stream's configured S3 prefix within the stream's declared buffering interval. Each delivered line is a JSON event whose `eventType` is "Send" and whose `mail.source` is the sending address and `mail.commonHeaders.subject` the message's subject — the values are taken from the sent message, not fixed text.

Emulator: nothing is published. services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_email.rs validates content, sender verification and the 24-hour quota, appends a SentMessage to the in-process log (`store.record_sent(message)`, carrying only configuration_set_name as data) and returns MessageId. The configuration set's event_destinations are never read, no record is put to the destination's DeliveryStreamArn, and no event JSON is ever produced; consequently the check's poll of `ListObjectsV2(Bucket=…, Prefix='ses-events/')` never returns an object and the check is killed by the harness ("Check timed out after 60.0s"; the timeout carries no stack, so the absence is grounded in the handler above rather than in a stack frame). Note that even once SES publishes, Firehose's own S3 flush is separately broken — see 20261024T005347Z-firehose-never-delivers-buffered-records-to-the-s3.md — but that issue does not cover this one: it is a different service and a different fix site, and SES publishing nothing is observable on its own.

Why: a client using the standard SES event-publication path (configuration set → Firehose → S3/Redshift) gets a 200 from SendEmail and an accepted, enabled event destination, yet no event data ever appears. Any consumer that waits for, counts or parses Send/Delivery/Bounce event records sees an empty stream forever and cannot distinguish "no events yet" from "event publication does not exist", so analytics and audit pipelines built on it are silently empty.

Fix: the operation's handler/state, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_email.rs together with the configuration-set event-destination state in services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/state.rs — after recording the send, look up the named configuration set's enabled event destinations, and for each whose MatchingEventTypes include the event being emitted (SEND here) emit the SES event JSON (eventType, mail.source, mail.commonHeaders.subject, mail.messageId, …, built from the sent message) into the destination's KinesisFirehoseDestination.DeliveryStreamArn via the same path a Firehose PutRecordBatch takes.

Traces: firehose__s3__sesv2.firehose-destination-delivers-two-send-events-within-the-buffering-interval ([mismatch], timed out polling for the delivered Send events under the stream's S3 prefix).
