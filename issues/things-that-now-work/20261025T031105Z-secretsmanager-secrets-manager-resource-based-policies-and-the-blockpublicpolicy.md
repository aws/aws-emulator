# Secrets Manager: resource-based policies and the BlockPublicPolicy condition key are never evaluated, replica writes are accepted, CFN secrets are absent, rotation setup breaks on a bad Lambda ARN, and PutResourcePolicy refusal text diverges (6 causes)

> _Note: this issue was identified against the code base at commit `271fde8cc1a42675cd9f2105c7c7bd008dd933ab`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
Six distinct root causes in the Secrets Manager emulator, all grounded in failing behavioral checks. Cause count: 6. Each cause below must be closed before submitting.

Related open issues that do NOT carry these replay keys, named here so they are not re-discovered as the same work: 20261024T190718Z-secretsmanager-secrets-manager-enforces-no-authorization-and-never-consults.md (its Cause 2 covers IDENTITY-policy evaluation and the aws:RequestTag / aws:ResourceTag / secretsmanager:VersionStage condition keys only — not resource-BASED policy evaluation, and not secretsmanager:BlockPublicPolicy), 20261024T190718Z-secretsmanager-secrets-manager-replication-delete-lifecycle-access-metadata-and.md (replication metadata/lifecycle, not replica write-protection), and 20261024T190718Z-secretsmanager-cloudformation-managed-secrets-aws-secretsmanager-secret-deploys-but.md (CFN-managed secrets from the deploy side). The checks listed per cause below are not carried by any of them.

=== Cause 1 of 6: a secret's resource-based policy is stored but never evaluated, so an explicit Deny does not deny ===
AWS: Secrets Manager authorizes every secret-value call against the union of the caller's identity policy and the secret's resource-based policy, and an explicit Deny in either one wins. A resource policy that denies secretsmanager:GetSecretValue (to the account, or conditioned on aws:PrincipalArn not matching one role) makes that call fail while leaving DescribeSecret and other secrets unaffected, and removing the policy restores access; a principal with neither an identity grant nor a resource-policy grant is denied by default. Smithy: GetSecretValue models no authorization error of its own (errors are DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException), so the denial arrives as the service-common AccessDeniedException on HTTP 400 for awsJson1_1 — this is the status/code the checks record. The requirement is the DECISION and its code, not the message text.
Emulator: GetSecretValue returns HTTP 200 with the plaintext SecretString in every one of these shapes. The replay shows 'expected this call to be denied, but it SUCCEEDED and returned {... SecretString: \'server-side-secret\' ... HTTPStatusCode: 200}' and '... SecretString: \'denied-value\' ... HTTPStatusCode: 200}' with an explicit-Deny policy attached, and 'a role with no identity policy and no resource policy must be denied before any policy is attached; got (\'ok\', \'policy-test-value\')'. The four polling checks never converge and run to the suite's 60 s cap ('Check timed out after 60.0s') because they poll GetSecretValue until it is refused and it never is. PutResourcePolicy itself now works and stores the document (services/service-com-amazonaws-secretsmanager-secretsmanager/src/ops/put_resource_policy.rs attaches it verbatim), so the gap is purely on the read path: services/service-com-amazonaws-secretsmanager-secretsmanager/src/ops/get_secret_value.rs:192-229 goes straight from the state lock to the version lookup and never reads secret.resource_policy or the caller identity.
Why: a resource policy is how a team fences a production secret off from everything but one role. A client that attaches a Deny and then verifies the secret is unreadable gets a green result from an emulator that is still handing out the material, and an identity-Deny-beats-resource-Allow test proves nothing. Any least-privilege or blast-radius test written against this emulator is vacuous.
Fix: the service's request-authorization layer plus the GetSecretValue handler's pre-read check — evaluate the secret's stored resource policy together with the caller's identity policy (explicit Deny wins; absence of any Allow is a deny) and answer AccessDeniedException on HTTP 400 before the value is read. The same decision must be reachable from DescribeSecret/PutSecretValue so a per-action policy scopes only the action it names.
Traces: secretsmanager.server-side-resource-policy-blocks-get-secret-value, secretsmanager.server-side-resource-policy-enforced-on-access, secretsmanager.get-secret-value-access-denied-by-resource-policy, secretsmanager.resource-policy-deny-blocks-get-secret-value, secretsmanager.resource-policy-deny-unless-principal-arn-locks-reads-to-one-role, secretsmanager.identity-policy-deny-overrides-a-resource-policy-allow-for-the-same-role, secretsmanager.e2e-resource-policy-attach-detach-consequence.

=== Cause 2 of 6: the secretsmanager:BlockPublicPolicy condition key is not evaluated on PutResourcePolicy ===
AWS: secretsmanager:BlockPublicPolicy is a service condition key usable on secretsmanager:PutResourcePolicy, so an identity policy that allows PutResourcePolicy only when secretsmanager:BlockPublicPolicy is true refuses a call that passes BlockPublicPolicy=False. Smithy: PutResourcePolicy input carries BlockPublicPolicy (BooleanType, default false) and models InvalidParameterException / InvalidRequestException / MalformedPolicyDocumentException / PublicPolicyException / ResourceNotFoundException, all HTTP 400; the authorization refusal arrives as the service-common AccessDeniedException on HTTP 400. Requirement: the call is REFUSED, not accepted.
Emulator: the call succeeds. Replay: 'expected the call to be refused, but it succeeded: {\'ARN\': \'arn:aws:secretsmanager:...:secret:...\', \'Name\': ..., HTTPStatusCode: 200}' for a role whose grant is conditioned on the key, calling put_resource_policy(..., BlockPublicPolicy=False). put_resource_policy.rs:190 reads input.block_public_policy only to decide whether to run its own public-policy test; nothing consults the caller's policy or the condition key.
Why: this condition key is the account-level guardrail that stops a principal from opting out of public-policy blocking. An emulator that ignores it reports the guardrail as installed when it is inert, so a control that exists to prevent accidental public exposure of a secret is never actually tested.
Fix: the request-authorization layer's condition-key set — populate secretsmanager:BlockPublicPolicy from the request before authorizing PutResourcePolicy, and answer AccessDeniedException (400) when the caller's policy does not allow the action with the supplied value.
Traces: secretsmanager.block-public-policy-condition-key-refuses-a-put-resource-policy-that-disables-the-check.

=== Cause 3 of 6: a replica secret accepts mutations that must be refused in the replica region ===
AWS: a replica secret is read-only in its region; tag and policy mutations must be made in the primary's region. TagResource, UntagResource, PutResourcePolicy and DeleteResourcePolicy addressed to the replica are refused with InvalidParameterException (Smithy: TagResource errors are InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException — all HTTP 400; PutResourcePolicy models InvalidParameterException likewise), the replica's tags and policy stay exactly as they were, and the identical mutation against the primary succeeds and propagates to the replica. The recorded refusal message is 'Operation not permitted on a replica secret. Call must be made in primary secret\'s region.' (example text; the requirement is the 400 InvalidParameterException and the unchanged state).
Emulator: the mutation SUCCEEDS against the replica. Replay: 'the call was expected to fail but SUCCEEDED' raised from the check's mutation loop over TagResource/UntagResource/PutResourcePolicy/DeleteResourcePolicy against the replica-region client.
Why: a client that believes replicas are read-only will see divergent tag/policy state between regions in the emulator and none in AWS, and a test asserting 'you must mutate the primary' passes against an emulator where mutating either works.
Fix: the TagResource / UntagResource / PutResourcePolicy / DeleteResourcePolicy handlers plus the state's replica flag — when the addressed secret is a replica, refuse with InvalidParameterException (400) before any mutation is applied.
Traces: secretsmanager.replica-refuses-tag-and-resource-policy-mutations-while-reads-propagate.

=== Cause 4 of 6: a CloudFormation-provisioned AWS::SecretsManager::Secret with an inline ResourcePolicy leaves no secret behind ===
AWS: a stack containing AWS::SecretsManager::Secret (plus AWS::SecretsManager::ResourcePolicy) reaches CREATE_COMPLETE with the secret actually created, so GetResourcePolicy on the stack's secret returns the attached document and the policy denies access exactly as the same document set via PutResourcePolicy does.
Emulator: GetResourcePolicy on the secret the stack reports fails with HTTP 400 ResourceNotFoundException — 'An error occurred (ResourceNotFoundException) when calling the GetResourcePolicy operation: Secrets Manager can\'t find the specified secret.' The secret named by the completed stack does not exist in the Secrets Manager store.
Why: every deploy-shaped client (CFN, CDK, SAM) provisions secrets this way. The stack reports success and every subsequent call against the resource it claims to have created 404s, so an infrastructure test cannot distinguish 'deployed' from 'did nothing'.
Fix: the CloudFormation resource provider for AWS::SecretsManager::Secret / AWS::SecretsManager::ResourcePolicy — it must call through to the Secrets Manager state so the secret and its policy exist when the stack completes (and fail the resource, not silently succeed, when it cannot). Open issue 20261024T190718Z-secretsmanager-cloudformation-managed-secrets-aws-secretsmanager-secret-deploys-but.md records the same provider gap from the deploy side; it does not carry this check's replay key.
Traces: secretsmanager.deploy-cfn-resource-policy-attached-enforced.

=== Cause 5 of 6: the Lambda ARN handed back for a freshly created rotation function does not name that function, so rotation setup cannot proceed ===
AWS: CreateFunction returns a FunctionArn of the form arn:aws:lambda:<region>:<account>:function:<function-name>, and AddPermission addressed to that ARN (or to the function name) resolves to the just-created function and succeeds, which is how a caller grants secretsmanager.amazonaws.com permission to invoke a rotation function.
Emulator: AddPermission against the function the check just created fails with HTTP 400 ResourceNotFoundException — 'An error occurred (ResourceNotFoundException) when calling the AddPermission operation: Function not found: arn:aws:lambda:us-west-2:000000000000:function:1'. The ARN's function-name segment is the literal '1' rather than the created function's name, so the identifier the create path produced cannot be resolved by the lookup path. (Reported under the secretsmanager check that exercises it; the defective component is the Lambda function-identifier handling the rotation setup depends on.)
Why: no rotation can be wired up at all. Every client that creates a rotation function and then grants Secrets Manager invoke permission fails at the grant, before any rotation behavior is reachable, and the failure names a function the client never asked for.
Fix: the Lambda CreateFunction handler's ARN construction and the AddPermission handler's function resolver — build the ARN's function-name segment from the function's name and resolve a request by name, qualified name or full ARN consistently.
Traces: secretsmanager.e2e-rotation-produces-new-current-version.

=== Cause 6 of 6 (LOW): PutResourcePolicy refusal messages are the emulator's own prose, not the service's fixed text ===
AWS: PutResourcePolicy refuses a wildcard-principal policy under BlockPublicPolicy=True with PublicPolicyException (HTTP 400) carrying the service's fixed text 'You can not attach a resource policy that grants Public access to your secret.', and refuses a syntactically invalid document with MalformedPolicyDocumentException (HTTP 400) carrying 'This resource policy contains a syntax error.' These are constant service strings, not request-derived prose: three independent replayed checks assert the first byte-for-byte and one asserts the second. Smithy: PutResourcePolicy models PublicPolicyException ('The BlockPublicPolicy parameter is set to true, and the resource policy did not prevent broad access to the secret.') and MalformedPolicyDocumentException ('The resource policy has syntax errors.'), both HTTP 400.
Emulator: the status and the exception CODE are correct in both cases; only the text differs. PublicPolicyException carries 'Resource policy blocked by BlockPublicPolicy: the policy allows broad access to the secret.' (crate::state::PUBLIC_POLICY_MESSAGE, raised at put_resource_policy.rs:193-198) and MalformedPolicyDocumentException carries 'Syntax errors in policy. The resource policy must be a JSON object whose Statement is a statement, or a non-empty list of statements, each with an Effect of Allow or Deny.' (returned by crate::state::parse_resource_policy via put_resource_policy.rs:175-183).
Why: clients and regression suites that match on the service's constant refusal text (including the three blessed checks here) see a refusal they cannot identify. The refusal decision itself is already right, which is why this is LOW.
Fix: the PutResourcePolicy handler's message constants — emit the service's fixed strings for PublicPolicyException and MalformedPolicyDocumentException instead of locally authored prose.
Traces: secretsmanager.put-resource-policy-public-policy-rejected, secretsmanager.resource-policy-public-policy-blocked, secretsmanager.block-public-policy-false-attaches-the-policy-that-true-refuses, secretsmanager.put-resource-policy-malformed-json-rejected.
