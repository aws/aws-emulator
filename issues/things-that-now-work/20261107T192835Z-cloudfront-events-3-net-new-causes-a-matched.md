# cloudfront__events: 3 net-new causes — a matched rule's Lambda target produces no effect, a trust-condition-denied invocation never dead-letters, and read-only CloudFront management calls ARE delivered to an enabled rule

> _Note: this issue was identified against the code base at commit `8662809dae52673eae9c053e761f1b93b4d6fc67`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEvents / CreateInvalidation (EventBridge rule target delivery)

## Description
Three distinct net-new root causes. Several open issues describe the same area but carry none of the check ids below, so none of them covers these: 20261102T091831Z-cloudfront-events-a-matched-rule-never-invokes-its.md, 20261029T175823Z-cloudfront-events-13-more-cloudfront-eventbridge-checks-fail.md, 20261101T214154Z-cloudfront-events-two-more-root-causes-a-matched.md, 20261105T202027Z-cloudfront-events-an-eventbridge-rule-whose-lambda-target-3df0ce.md, 20261025T002357Z-cloudfront-events-cloudfront-read-only-calls-emit-no-events-and.md.

=== Cause 1 of 3: a matched EventBridge rule never produces its Lambda target's effect ===
AWS: a PutEvents entry (or an S3 "Object Created" event) that matches an ENABLED rule's EventPattern is delivered to the rule's Lambda target, which runs and performs its side effect — here CreateInvalidation (Smithy: CreateInvalidation POST /2020-05-31/distribution/{DistributionId}/invalidation, HTTP 201, InvalidationBatch required) and/or an SQS SendMessage carrying the call's result. ListInvalidations (Smithy: GET /2020-05-31/distribution/{DistributionId}/invalidation, items at InvalidationList.Items) then lists the new invalidation, and its InvalidationBatch.Paths.Items contain the path the event carried (the path value itself comes from the event, only the "/<key>" shape is required).
Emulator: no target effect ever appears — ListInvalidations stays empty ([]), the result/relay SQS queue stays empty, and the checks that need the effect before asserting run to the harness's 180 s cap. The negative variants (missing target permission, role scoped to the wrong distribution, pattern mismatch) therefore pass or hang vacuously against a pipeline that never ran.
Why: a client wiring the canonical "event → Lambda → CreateInvalidation" automation sees it silently do nothing, with no error anywhere to diagnose, and any authorization boundary around it is untestable because the authorized path never runs either.
Fix: the EventBridge rule-matching and target-invocation path for Lambda targets (and the Lambda invocation's own CloudFront/SQS client path), plus CloudFront's CreateInvalidation/ListInvalidations state.
Traces: cloudfront__events.cfn-deploy-eventbridge-rule-cloudfront-invalidation-lambda, cloudfront__events.cloudfront-invalidation-created-by-lambda-reflects-paths, cloudfront__events.eventbridge-cloudfront-putevents-custom-detail-invokes-lambda, cloudfront__events.eventbridge-invalidation-rule-pattern-mismatch-no-invalidation-created, cloudfront__events.eventbridge-put-events-custom-detail-triggers-cloudfront-cache-invalidation, cloudfront__events.eventbridge-role-without-events-trust-rejected, cloudfront__events.eventbridge-target-missing-cloudfront-invalidation-permission-not-invoked, cloudfront__events.eventbridge-target-role-scoped-to-wrong-distribution-denied, cloudfront__events.events-role-trust-policy-allows-assume-for-cloudfront-target, cloudfront__events.lambda-cloudfront-createinvalidation-response-propagated-to-sqs, cloudfront__events.lambda-role-missing-cloudfront-permission-denied-invalidation, cloudfront__events.xsvc-cloudfront-1-s3-object-created-lambda-invalidation-refreshes-edge.

=== Cause 2 of 3: an invocation denied by the target role's trust condition is neither performed nor dead-lettered ===
AWS: when a rule's target RoleArn trusts events.amazonaws.com only under a condition (aws:SourceArn / sts:ExternalId) and the invoking rule's ARN does not satisfy it, EventBridge cannot assume the role, the delivery fails, and because the target carries a DeadLetterConfig the failed event is written to that dead-letter SQS queue (with the delivery-failure metadata attributes EventBridge attaches). Recorded behavior only for the DLQ payload shape; the contract exercised is that the DLQ receives exactly that failed delivery while the correctly-scoped rule's delivery succeeds.
Emulator: nothing arrives on the dead-letter queue — the condition-scoped trust is not evaluated and no delivery-failure record is produced.
Why: a client relying on a DLQ to surface delivery failures gets silence, so a misconfigured target role (the single most common EventBridge failure mode) is invisible; and because the condition is not enforced, a role that AWS refuses to assume appears usable.
Fix: EventBridge's target role-assumption step (condition evaluation on the trust policy) and the target's DeadLetterConfig delivery-failure writer.
Traces: cloudfront__events.iam-role-trust-scoped-with-external-condition-enforced.

=== Cause 3 of 3: read-only CloudFront management API calls are delivered to a rule that must only receive write events ===
AWS: CloudFront read-only management calls (Get*/List*/Describe*, e.g. GetDistribution and ListDistributions) are not delivered as management events to an EventBridge rule that selects write management events; only the mutating calls are. The same reads do reach a rule that selects ALL management events, which is how the recording distinguishes "not emitted to this rule" from "not emitted at all". Recorded behavior only — event selection is not expressed in the Smithy model.
Emulator: the ENABLED write-event rule's sink receives GetDistribution and ListDistributions; the check's leak list is ['GetDistribution', 'ListDistributions'] where AWS yields []. The write event reached the same sink ~1 s after its call and the reads also reached the all-management-events rule, so delivery itself works here — the event selection is what diverges.
Why: a client that routes CloudFront write events to an automation (invalidation, audit, drift remediation) is flooded with read traffic: every console refresh or polling describe triggers the automation, which in AWS it never would.
Fix: the management-event emitter's read-only/write classification used when matching rules on CloudFront CloudTrail-derived events.
Traces: cloudfront__events.xsvc-cloudfront-1-read-only-calls-not-delivered-to-enabled-rule.

## Steps to Reproduce
Cause 1: create a Lambda that calls CreateInvalidation (and SendMessage with the result), grant events.amazonaws.com lambda:InvokeFunction on it, create an ENABLED rule with an EventPattern matching a custom detail-type, add the Lambda as a target, then PutEvents with a matching entry. Poll ListInvalidations on the distribution and ReceiveMessage on the result queue: both stay empty.
Cause 2: create two rules A and B with the same Lambda target and a target RoleArn whose trust policy allows sts:AssumeRole for events.amazonaws.com only under a condition on aws:SourceArn equal to rule A's ARN; give the target a DeadLetterConfig SQS queue; fire a matching event on both rules. A's delivery should succeed and B's should land on the DLQ — nothing arrives on the DLQ.
Cause 3: create an ENABLED rule selecting CloudFront WRITE management events with an SQS/Lambda sink, plus a control rule selecting all management events; call GetDistribution and ListDistributions, then a write call. The write-only sink receives GetDistribution and ListDistributions as well as the write.
