# ECR Public: GetAuthorizationToken is not authorization-gated, stored logo blobs are never served at the minted logoUrl, and six error/representation divergences (8 causes)

> _Note: this issue was identified against the code base at commit `1d15d4851343e3a31be69cd8cea36918aab666fe`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRepositoryCatalogData

## Description
Behavioral replay of the simparity-behavioral-aws-v1 ecr-public suite (33/92 passed; the emulator IS serving, implemented ops answer 200/400 and stubs answer 501, so none of this is a bootstrap gap) surfaced EIGHT independent root causes that no already-filed issue carries, beyond the auto-filed scaffold-stub issues (CompleteLayerUpload, TagResource) and the two open issues 20261022T154435Z-ecr-public-cfn-publicrepository-creates-nothing-putimage-accepts.md and 20261022T192707Z-ecr-public-putregistrycatalogdata-has-no-us-east-1.md. ALL EIGHT causes below must be closed before this issue is resolved.

=== Cause 1 of 8: GetAuthorizationToken answers 200 with a usable token to a principal that holds no ecr-public permission at all (no IAM authorization gate) ===
AWS: Smithy GetAuthorizationToken (empty input; output authorizationData -> AuthorizationData; modeled errors InvalidParameterException, UnsupportedCommandException both client/httpError 400, ServerException 500). Authorization is not a modeled operation error: it is the service-common IAM decision, which for a principal with no identity-based Allow for ecr-public:GetAuthorizationToken is a client failure with error code AccessDeniedException. Recorded behavior for the message, whose rule is IAM's standard implicit-deny template built from the request's signing identity and the action: an example is "User: arn:aws:iam::<account>:user/<user> is not authorized to perform: ecr-public:GetAuthorizationToken on resource: * because no identity-based policy allows the ecr-public:GetAuthorizationToken action".
Emulator: the request signed with a freshly created IAM user's access key (that user has NO inline or attached policy) returns HTTP 200 with a full authorizationData payload (base64 authorizationToken plus expiresAt). No AccessDeniedException is ever produced; the token handler answers any syntactically valid SigV4 request.
Why: this is an authorization bypass on the credential-minting operation of the registry. A caller testing least-privilege IAM against the emulator sees an unprivileged principal succeed, so IAM-denial handling (retry/escalate/abort) is never exercised and a policy that is in fact insufficient looks correct; against AWS the same code path fails 400 AccessDeniedException.
Fix: the GetAuthorizationToken handler, or the shared request-authorization step that runs before the ecr-public handlers, must resolve the signing principal's identity policy and return the AccessDeniedException client error when no Allow for ecr-public:GetAuthorizationToken exists, instead of unconditionally minting a token.
Traces: ecr-public.get-authorization-token-without-credentials-denied.

=== Cause 2 of 8: the logoImageBlob accepted by PutRepositoryCatalogData is never served at the logoUrl the service minted for it ===
AWS: Smithy RepositoryCatalogDataInput.logoImageBlob is a blob, @length 0..512000, INPUT-only ("The base64-encoded repository logo payload"); the output shape RepositoryCatalogData has no logoImageBlob and instead carries logoUrl -> ResourceUrl @length 0..2048. The service therefore transforms the uploaded bytes into a hosted asset: an anonymous HTTPS GET of the minted logoUrl answers 200 with the byte-identical payload that was uploaded (Content-Type image/png for a PNG), and an accepted replacement blob is published at a new URL. Recorded behavior only for the hosting leg (it is outside the modeled API surface).
Emulator: PutRepositoryCatalogData accepts the blob and both it and GetRepositoryCatalogData report a logoUrl on the target's own published host (the checks' published_url_mismatch assertion passes), but a GET of that URL never answers 200 within the budget: two independent checks exhaust their fetch polls and the suite kills them at the 60s check ceiling. The bytes are counted and discarded rather than stored, and nothing is routed for the URL that was minted.
Why: logoImageBlob is absent from every response, so the ONLY way a client can confirm the logo was stored is fetching the minted URL. Any tool that uploads a logo and then verifies or displays it (a publish pipeline, a gallery preview) gets a URL that 404s/hangs forever against the emulator while it serves the image against AWS; and because an emulator has no propagation delay, a poll that never converges means the condition is never true, not that it is slow.
Fix: the PutRepositoryCatalogData handler plus the repository catalog state must persist the logo bytes keyed by the minted URL, and the emulator's HTTP front door must serve that path with the stored bytes verbatim and the image content type; a replacement blob must mint a distinct URL that serves the new bytes.
Traces: ecr-public.catalog-logo-blob-is-stored-and-served-as-a-real-image, ecr-public.repository-catalog-data-base64-logo-round-trip.

=== Cause 3 of 8: InvalidParameterException for PutRepositoryCatalogData catalog members and SetRepositoryPolicy.policyText uses the generic framework validation template and echoes the rejected value ===
AWS: Smithy RepositoryCatalogDataInput.description -> RepositoryDescription @length 0..1024, logoImageBlob @length 0..512000, and SetRepositoryPolicy.policyText -> RepositoryPolicyText required @length 0..10240; both operations model InvalidParameterException (client, httpError 400). One unit past a member's maximum is refused 400 InvalidParameterException with a message ECR Public renders from the request as a fixed template naming only the member path and the violated rule, never the rejected value: e.g. "Invalid parameter at 'catalogData.description' failed to satisfy constraint: 'Member must have length less than or equal to 1024'", "Invalid parameter at 'catalogData.logoImageBlob' failed to satisfy constraint: 'Member must have length less than or equal to 512000'", "Invalid parameter at 'PolicyText' failed to satisfy constraint: 'Must have length less than or equal to 10240'". Since the message is a deterministic function of the request (member + rule), the template is the requirement and the quoted strings are examples.
Emulator: status 400 and code InvalidParameterException are correct on every leg, but the body carries the generic framework template "1 validation error detected: Value '<the entire rejected value, or '<N> bytes' for a blob>' at '<member>' failed to satisfy constraint: Member must have length less than or equal to <max>" — the "N validation error detected" preamble replaces the service wording and the caller's rejected value is copied back into the error body. NOTE: cause 5 of 20261022T154435Z-ecr-public-cfn-publicrepository-creates-nothing-putimage-accepts.md and cause 3 of 20261022T192707Z-ecr-public-putregistrycatalogdata-has-no-us-east-1.md describe this same template defect on CreateRepository.repositoryName / CreateRepository.catalogData.description / SetRepositoryPolicy.policyText (oversized leg) and PutRegistryCatalogData.displayName; neither carries the three legs recorded here, so if the shared validation layer is fixed these checks should be re-replayed to confirm this cause closes with it.
Why: this message is the only place the service states which member and which rule failed; SDK wrappers, CLIs and conformance suites match the AWS template to surface a field-level error and fail to match the framework preamble. Interpolating the rejected value also makes error bodies unbounded (here a 46KB policy document and a 512001-byte blob report) and reflects caller content back over the wire.
Fix: the shared modeled-constraint -> InvalidParameterException rendering for this service (the validation layer in front of the ecr-public handlers) must emit the ECR Public template over the member path and rule only, with no value interpolation.
Traces: ecr-public.catalog-logo-blob-is-input-only-and-size-capped, ecr-public.repository-catalog-text-limits-enforced, ecr-public.set-repository-policy-exceeds-size-limit-rejected.

=== Cause 4 of 8: SetRepositoryPolicy's unforced self-lockout refusal reports a synthetic 'force' constraint violation instead of the service's lockout refusal ===
AWS: Smithy SetRepositoryPolicy input carries force -> ForceFlag (boolean, default false) and models InvalidParameterException (client, httpError 400) as its only input-shaped error. A policyText that would Deny the caller ecr-public:SetRepositoryPolicy is refused 400 InvalidParameterException when force is absent/false, and the stored policy is left unchanged; the refusal is the service's documented fixed lockout sentence (AWS documents the force parameter in exactly these terms): "You are about to set a repository policy that will prevent you from setting another one in the future. Use the force parameter to override this exception."
Emulator: the status 400 and the code InvalidParameterException are correct, but the message is a fabricated member-constraint violation, "Invalid parameter at 'force' failed to satisfy constraint: 'Member must be true because the policy would prevent ecr-public:SetRepositoryPolicy from being called on this repository in the future'" — i.e. the lockout detection is reported as a constraint failure on the boolean input member rather than as the service's lockout refusal. The check stops here, so whether the forced lockout policy is subsequently ENFORCED is still unverified.
Why: force is a legal input value, not a constrained one, so a client that distinguishes "my policy document is malformed" from "this policy would lock me out, re-send with force" cannot recognize the condition from the emulator's body; the recommended remediation (set force=true) appears nowhere in it.
Fix: the SetRepositoryPolicy handler's lockout check must raise InvalidParameterException with the service's lockout message rather than routing the condition through the input-member constraint renderer.
Traces: ecr-public.repository-policy-self-lockout-with-force-actually-blocks-set-repository-policy.

=== Cause 5 of 8: a repository policy's Condition values are not canonicalized to strings on read-back ===
AWS: Smithy SetRepositoryPolicy.policyText / GetRepositoryPolicy.policyText -> RepositoryPolicyText @length 0..10240; the document is parsed by the IAM policy engine and re-serialized, which canonicalizes Condition operator values to strings. A Condition written as a JSON number ({"NumericLessThanEquals": {"aws:MultiFactorAuthAge": 300}}) comes back from GetRepositoryPolicy as the JSON string "300" while Version, statement count, Sid, Effect, Principal and Action order are preserved verbatim. Recorded behavior only for the coercion (the model constrains the document only by length).
Emulator: GetRepositoryPolicy returns the Condition value as the JSON number 300 (int) — the document is stored and returned as opaque bytes with no policy-engine round-trip, so no canonicalization occurs.
Why: a client that reads its policy back and compares it to, or type-checks it against, what AWS returns (policy diffing, drift detection, infrastructure-as-code reconciliation) sees a different JSON type for the same condition and reports spurious drift, or writes comparison code that breaks against AWS.
Fix: the SetRepositoryPolicy/GetRepositoryPolicy path (policy parsing and re-serialization in the repository-policy state, not a byte-preserving store) must canonicalize Condition operator values to strings while preserving statement structure, order and the other members.
Traces: ecr-public.repository-policy-document-byte-preserved.

=== Cause 6 of 8: UploadLayerPart's InvalidLayerPartException does not report the expected first byte in AWS's form ===
AWS: Smithy UploadLayerPart input partFirstByte/partLastByte -> PartSize (long, @range min 0), required; it models InvalidLayerPartException (client, httpError 400), documented "The layer part size isn't valid, or the first byte specified isn't consecutive to the last byte of a previous layer part upload", whose shape also carries registryId/repositoryName/uploadId/lastValidByteReceived. A part whose partFirstByte is not the next byte after the last byte received (a gap, or an out-of-order part) is refused 400 InvalidLayerPartException. Recorded behavior for the message, which is built from the request and the upload's state as a fixed template over the two byte offsets: examples are "First byte of the layer part is 1000 instead of 32" and "First byte of the layer part is 5242880 instead of 0".
Emulator: status 400 and code InvalidLayerPartException are correct, but the message is a different template, "The layer part beginning at byte '<first>' is not consecutive to the last byte received for the upload with ID '<uploadId>': the next layer part must begin at byte '<expected>'".
Why: the two offsets are what a resumable-push client needs to continue, and docker/SDK push logic that parses the AWS template to recover the expected offset extracts nothing from the emulator's wording; the divergence also hides whether lastValidByteReceived is being populated at all.
Fix: the UploadLayerPart handler's consecutiveness check (its error construction) must render the AWS template over the observed and expected first byte.
Traces: ecr-public.upload-layer-part-offset-gap-rejected, ecr-public.upload-layer-part-sequential-ordering-enforced.

=== Cause 7 of 8: UploadLayerPart's UploadNotFoundException message does not name the registry in AWS's form ===
AWS: Smithy UploadLayerPart.uploadId is required with pattern ^[0-9a-fA-F]{8}-...-[0-9a-fA-F]{12}$ and the operation models UploadNotFoundException (client, httpError 400), documented "The upload can't be found, or the specified upload ID isn't valid for this repository". A well-formed but never-issued uploadId is refused 400 UploadNotFoundException. Recorded behavior for the message, built from the request as a fixed template over the upload id, the repository name and the registry id: an example is "The upload with id '<uploadId>' in the repository with name '<repo>' in registry with id '<account>' does not exist".
Emulator: status 400 and code UploadNotFoundException are correct, but the message re-orders and re-words the template: "The upload with ID '<uploadId>' does not exist for the repository with name '<repo>' in the registry with id '<account>'".
Why: the three identifiers are present in both forms, so this is the narrowest of the divergences, but a conformance or log-matching consumer pinned to the AWS wording of the registry clause does not match.
Fix: the UploadLayerPart handler's not-found error construction must render the AWS template.
Traces: ecr-public.upload-layer-part-unknown-upload-id-rejected.

=== Cause 8 of 8: the digest-mismatch leg of CompleteLayerUpload answers NotImplemented instead of InvalidLayerException (same unimplemented scaffold already filed, additional leg) ===
AWS: Smithy CompleteLayerUpload (input repositoryName/uploadId/layerDigests @length 1..100, all required; output registryId/repositoryName/uploadId/layerDigest) models InvalidLayerException (client, httpError 400) alongside EmptyUploadException, UploadNotFoundException, LayerPartTooSmallException, LayerAlreadyExistsException, InvalidParameterException, RepositoryNotFoundException and RegistryNotFoundException. A layerDigests entry that does not match the sha256 of the bytes actually uploaded for that uploadId is refused 400 InvalidLayerException, and NEITHER the claimed digest nor the true digest becomes AVAILABLE at BatchCheckLayerAvailability afterwards; the same bytes with the honest digest on a fresh upload session complete 200 echoing layerDigest. Recorded behavior for the message, a fixed string: "None of the provided layer digests match the calculated layer digest".
Emulator: the call answers the scaffold's NotImplemented (services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/ops/complete_layer_upload.rs still returns the 501 not-implemented marker), so the check observes error code NotImplemented where InvalidLayerException is required. This is the SAME unimplemented operation already filed for this suite (the auto-filed CompleteLayerUpload stub issue, which the report says blocks 28 checks, and cause 2 of 20261022T192707Z-ecr-public-putregistrycatalogdata-has-no-us-east-1.md, which carries the EmptyUploadException leg); the replay report did not mark this check as covered, so it is recorded here to carry its replay key and the digest-mismatch requirement — closing the stub with digest verification closes this cause too.
Why: 501 is not a modeled response for CompleteLayerUpload, so no layer can be finalized and the integrity check at the commit point of the layer data plane (client-supplied digest vs computed digest) cannot be exercised at all; an implementation that trusts the client's digest would be an over-permissive accept of a layer whose content does not match its address.
Fix: implement complete_layer_upload.rs against the layer-upload/blob state so that it computes the sha256 of the uploaded parts and returns 400 InvalidLayerException when no supplied digest matches, committing nothing, and 200 echoing layerDigest when one does.
Traces: ecr-public.complete-layer-upload-digest-mismatch-rejected.
