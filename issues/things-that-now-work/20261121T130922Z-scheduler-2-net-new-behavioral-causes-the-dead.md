=== Cause 1 of 2: the dead-letter event's Body names the target queue by a hard-coded `https://sqs.<region>.amazonaws.com/<account>/<name>` URL instead of the QueueUrl this emulator's SQS actually publishes for that queue ===
Failing checks: scheduler.schedule-dead-letter-queue-receives-failed-invocation, scheduler.e2e-schedule-retry-then-dlq-delivery

AWS: Smithy (com.amazonaws.scheduler) — Target.DeadLetterConfig -> DeadLetterConfig.Arn, @pattern ^arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+$ @length 1..1600, documented "An object that contains information about an Amazon SQS queue that EventBridge Scheduler uses as a dead-letter queue for your schedule. If specified, EventBridge Scheduler delivers failed events that could not be successfully delivered to a target to the queue"; Target.Input @length min 1, "The text, or well-formed JSON, passed to the target"; Target.SqsParameters is documented as "The templated target type for the Amazon SQS SendMessage API operation". The model does not describe the dead-letter envelope, so for the envelope itself: recorded behavior only — for an SQS target the dead-letter message Body is a JSON object describing the SendMessage request Scheduler attempted, whose `MessageBody` member is the occurrence's Target.Input and whose `QueueUrl` member is THE QUEUE URL THAT SERVICE PUBLISHES FOR THE TARGET QUEUE — i.e. the identical string the same account's SQS returns from CreateQueue/GetQueueUrl for that queue ARN, against the endpoint the client is talking to. The member name `QueueUrl` is the fixed part; its value is taken from the target queue's own published URL, never from a literal host template. On real AWS those two coincide (`https://sqs.<region>.amazonaws.com/<account>/<name>`), which is why a hard-coded template passes there and is nevertheless not the rule.
Emulator: the dead-letter event arrives and its ERROR_CODE/SCHEDULE_ARN/TARGET_ARN/MessageBody assertions pass, but `json.loads(Body)["QueueUrl"]` is a synthesized public-AWS address that is NOT the URL this emulator's SQS hands out for the same queue. Replay: "AssertionError: dead-letter event QueueUrl='https://sqs.us-west-2.amazonaws.com/000000000000/sim2real-behav-sched-tgt-<id>' != target queue url 'https://<emulator-host>:<port>/000000000000/sim2real-behav-sched-tgt-<id>'", and in the e2e check the bare `assert payload["QueueUrl"] == main_url`. The two differ only in the scheme/host/port component: the account and queue-name path segments match, so the body is being built from a literal host template rather than from the queue's address.
Why: the dead-letter Body is the only record of WHERE the lost work was headed, and a DLQ consumer feeds `QueueUrl` straight back into sqs.send_message to redrive it. A client that does so against the emulator addresses a host it is not talking to — the redrive either leaves the emulator entirely or fails to resolve — so no redrive tooling written for AWS can be exercised end-to-end here, and the emulator announces an address other than the one it is reached on. It is also self-inconsistent: the same queue has two different URLs depending on whether the client asked SQS or read the DLQ event.
Fix: the dead-letter envelope's request snapshot in the scheduler crate's invocation/dead-letter component. The `QueueUrl` it writes into the event body (and the one it addresses the dead-letter queue itself by) must be resolved as the SQS service in use publishes it for that queue ARN — e.g. by asking SQS over the in-process callback (GetQueueUrl) and using the answer — instead of formatting a fixed `https://sqs.{region}.amazonaws.com/{account}/{name}` string. Same component, same helper, for both the target-request body and the dead-letter destination.

=== Cause 2 of 2: UpdateSchedule re-resolves Target.RoleArn and refuses a schedule whose execution role has been deleted; AWS accepts the update and only checks the role at invocation ===
Failing check: scheduler.update-schedule-target-role-deleted-succeeds

AWS: Smithy (com.amazonaws.scheduler) — UpdateSchedule (PUT /schedules/{Name}, 200) models ConflictException 409, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429, ValidationException 400; Target.RoleArn is required, @pattern ^arn:aws(-[a-z]+)?:iam::\d{12}:role\/[\w+=,.@\/-]+$, documented "The Amazon Resource Name (ARN) of the IAM role that EventBridge Scheduler will use for this target when the schedule is invoked" — i.e. the role is used AT INVOCATION. Recorded behavior: with the schedule's execution role deleted (independently confirmed: iam.get_role answers NoSuchEntity "The role with name <RoleName> cannot be found.", and CreateSchedule has already begun refusing that ARN, so the role is not merely still propagating), UpdateSchedule carrying that same dangling Target.RoleArn SUCCEEDS with HTTP 200 and APPLIES: GetSchedule afterwards reports the new Description, State=ENABLED and the unchanged dangling Target.RoleArn, and the schedule remains ordinarily updatable (a later update repointing it at a live role also succeeds). Role existence/assumability is enforced on the create path and at invocation time, not re-validated on update.
Emulator: UpdateSchedule refuses the call with HTTP 400 `ValidationException`. Replay: "AssertionError: expected UpdateSchedule to succeed despite a deleted target role, got 'ValidationException'". The update therefore does not apply at all — Description and State keep their pre-update values.
Why: a client cannot repair or re-point a schedule whose role was deleted, which is exactly the recovery path AWS leaves open (and the reason AWS does not re-validate: an update is how you move a schedule off a broken role). Against the emulator any schedule whose role is deleted becomes permanently frozen — every UpdateSchedule, including one that would replace the dangling RoleArn, is refused — and automation that reconciles schedules after a role rotation fails with a 400 that AWS never returns.
Fix: the UpdateSchedule handler's validation sequence — it must not run the execution-role existence/assumability resolution that the create path runs. Remove that gate from the update path (keeping the input-shape, expression, window, target-ARN, universal-target and payload-size validation, and keeping the role resolution on CreateSchedule and at invocation).

Code citations: services/service-com-amazonaws-scheduler-awschronosservice/src/state/invocation.rs lines 1651-1672 (`fn queue_url` returning the literal `https://sqs.{region}.amazonaws.com/{account}/{name}`), used at line 1303 to build the dead-letter body's QueueUrl member and at lines 1408-1409 to address the dead-letter queue (Cause 1); services/service-com-amazonaws-scheduler-awschronosservice/src/ops/update_schedule.rs lines 282-299 (`crate::state::execution_role_violation` -> ValidationException) (Cause 2).
