# CodePipeline execution plane: 5 net-new root causes (CMK artifact store unusable, approval decision not attributed, source failure misclassified with a leaked Rust SDK debug string, action variables unresolved, 6 checks still exhaust their budget)

## Description
FIVE net-new root causes in the CodePipeline execution plane. A fixer must close ALL FIVE before submitting; each cause names its own failing check ids below.

None of these checks is marked ALREADY FILED or OWNED in this replay. Related but NOT covering: the open issue 20261025T032228Z-codepipeline-execution-engine-still-stalls-an-action-never.md names several of these check ids, but it carries their old replay keys (a bare poll timeout). Causes 1-4 are now CONCRETE answers the engine produces after advancing past that stall, so they are new findings, not that stall.

=== Cause 1 of 5: a pipeline whose artifactStore declares a customer managed KMS key can never run ===
AWS: Smithy (com.amazonaws.codepipeline#CodePipeline_20150709) models ArtifactStore$encryptionKey -> EncryptionKey, documented as "The encryption key used to encrypt the data in the artifact store, such as an Amazon Web Services Key Management Service key. If this is undefined, the default key for Amazon S3 is used." An execution against such a store runs normally: each action's output artifact is written to the S3 artifact store encrypted with that CMK (SSE-KMS, the object reporting that key id), the execution reaches Succeeded, and JobData$encryptionKey carries the key to job workers. Only an actually unusable key (disabled/revoked) fails the execution.
Emulator: the execution fails immediately at the Source action. GetPipelineExecution reports status 'Failed' with statusSummary "action <actionName> in stage <stageName> failed: the pipeline's artifact store declares the customer managed key <keyArn>, and this emulator cannot encrypt an artifact object with KMS, so the artifact cannot be produced as declared" — an emulator-authored sentence that names the emulator itself, which no AWS response ever contains.
Why: every CMK-encrypted pipeline — the configuration AWS documents for cross-account and compliance-controlled artifact stores — is unusable, and the failure is reported as a pipeline/action failure, so a client sees "my pipeline is broken" rather than an unimplemented feature. It also makes the key-revocation behaviour untestable in both directions: an operator cannot distinguish "the disabled key blocked the execution" from "this pipeline never worked".
Fix: the artifact write/read path of the codepipeline crate's execution plane (the S3 PutObject/GetObject of artifacts must use SSE-KMS with the declared ArtifactStore$encryptionKey), plus propagating that key into JobData$encryptionKey; and the statusSummary text must never describe the emulator.
Traces: codepipeline.artifact-store-cmk-encrypts-the-delivered-artifact-object, codepipeline.disabling-the-artifact-store-cmk-fails-the-execution-and-reenabling-restores-it.

=== Cause 2 of 5: an approval decision is not attributed — ActionExecution$lastUpdatedBy is absent ===
AWS: Smithy models ActionExecution$lastUpdatedBy -> LastUpdatedBy, documented as "The ARN of the user who last changed the pipeline", and GetPipelineState/ListActionExecutions publish it on the manual-approval action once PutApprovalResult is accepted: it names the IAM principal that made the Approved/Rejected decision (the caller ARN of the PutApprovalResult request).
Emulator: after a successful PutApprovalResult(result={'status':'Rejected'}), the approval action's latestExecution has lastUpdatedBy absent (None). The decision is recorded but not attributed to anyone.
Why: manual approval exists to put a named human in the audit trail. With no lastUpdatedBy, a client cannot tell who approved or rejected a release — change-management and compliance reporting built on GetPipelineState/ListActionExecutions lose their only attribution field.
Fix: the PutApprovalResult handler in the codepipeline crate must record the request's caller identity on the approval action's execution record, and the GetPipelineState/ListActionExecutions serializers must emit it as lastUpdatedBy.
Traces: codepipeline.approval-rejection-records-the-reviewer-and-withholds-the-downstream-stage.

=== Cause 3 of 5: a missing source object is misclassified as JobFailed, and the message is a raw Rust SDK debug dump ===
AWS: Smithy models ActionExecution$errorDetails / ActionExecutionResult$errorDetails -> ErrorDetails{code, message}, where message is @length(min 1, max 5000). When an S3 Source action's configured object does not exist, the action fails with errorDetails.code 'RevisionUnavailable' and a short human-readable message naming the unavailable revision/object; 'JobFailed' is the code for a job worker reporting a failure through PutJobFailureResult(failureDetails.type=JobFailed), not for a source revision the service could not fetch.
Emulator: errorDetails.code is 'JobFailed', and both errorDetails.message and the action's summary carry the emulator's internal Rust SDK Debug formatting verbatim: "the source object s3://<bucket>/<key> could not be read: service error: NoSuchKey: ... (ServiceError(ServiceError { source: NoSuchKey(NoSuchKey { message: Some(\"The specified key does not exist.\"), meta: ErrorMetadata { code: Some(\"NoSuchKey\"), ... } }), raw: Response { status: StatusCode(404), headers: {}, body: SdkBody { inner: Once(Some(b\"<Error><Code>NoSuchKey</Code>...<RequestId>...</RequestId><HostId>...</HostId></Error>\")), retryable: true }, extensions: ... } }))" — including a nested XML body, a RequestId and a HostId.
Why: a client that branches on errorDetails.code takes the job-failure path (retry the worker) for what is really an unavailable source revision (fix the object), and operators are shown emulator internals — Rust type names, an embedded S3 error document and per-run request/host ids — instead of a message of the modelled, bounded form. Automation that parses or length-checks ErrorDetails$message breaks on the dump.
Fix: the source-action handler in the codepipeline crate's execution plane — it must map an unreadable source revision to ErrorDetails{code: 'RevisionUnavailable'} and build the message itself rather than formatting the inner SDK error with Debug; the same error-to-ErrorDetails mapping feeds GetPipelineState and ListActionExecutions.
Traces: codepipeline.missing-source-object-fails-the-execution-and-no-artifact-is-deployed.

=== Cause 4 of 5: pipeline variable references in an action configuration are passed through literally ===
AWS: an action configuration value may reference a variable produced upstream, in the form #{<namespace>.<key>} (e.g. #{SourceVariables.VersionId} for an S3 source action's consumed object version). Before the action runs, CodePipeline RESOLVES the reference against the producing action's output variables, and the action executes with the substituted value, so a deploy action writing to key "v/#{SourceVariables.VersionId}/out.zip" creates the object "v/<the consumed version id>/out.zip".
Emulator: the placeholder is shipped through verbatim — the object created under v/ is literally 'v/#{SourceVariables.VersionId}/out.zip'. No resolution is attempted (and the check equally rejects substituting a value of the emulator's own).
Why: every pipeline that threads a source revision, commit id or build tag into a downstream action's configuration writes to a path containing a raw template, so artifacts land at the wrong keys, deployments target the wrong resources, and nothing reports an error.
Fix: the variable-resolution step of the codepipeline crate's execution plane — the point where an action's configuration is materialised for the run must expand #{namespace.key} from the namespaces declared by upstream actions (source variables and PutJobSuccessResult outputVariables).
Traces: codepipeline.source-output-variable-resolves-into-the-downstream-object-key.

=== Cause 5 of 5: six further checks never observe the state they poll for and exhaust the suite's per-check budget ===
AWS: the service DRIVES an execution to a terminal PipelineExecutionStatus and publishes every intermediate state: a disabled stage transition holds entry to one stage while earlier stages still complete and EnableStageTransition releases it; stage CONDITIONS are evaluated and produce RuleExecutionDetails that ListRuleExecutions returns in evaluation order, with OverrideStageCondition refused when it conflicts; RetryStageExecution re-runs a failed stage to completion; RollbackStage starts a rollback execution that restores the previously successful stage revision; and a CloudFormation-declared pipeline behaves identically to a hand-created one.
Emulator: each of the six checks below stops at the suite's 60 s per-check ceiling ('Error: Check timed out after 60.0s') while polling for that next state, with no state observed to assert on. Against an emulator none of these waits should take seconds. Hypothesis (neither the model nor the recording states the mechanism): the driver does not advance these paths at all, so the dependent reporting (ListRuleExecutions, rollback and retry outcomes, transition release) is never produced.
Why: stage transitions, stage conditions/overrides, retry and rollback are the operational controls of CodePipeline. A client using any of them waits forever with no error and no state change, and because the state the negative classes act on is never reached, their refusals (condition-override conflicts, non-retryable stages) are unreachable too.
Fix: the codepipeline crate's execution driver and the state it publishes to GetPipelineState/GetPipelineExecution/ListActionExecutions/ListRuleExecutions, plus the stage-transition hold, condition evaluation, RetryStageExecution and RollbackStage paths.
Traces: codepipeline.deploy-codepipeline-pipeline-executes-via-cloudformation, codepipeline.disable-enable-stage-transition-controls-progression, codepipeline.list-rule-executions-matches-condition-evaluation-order, codepipeline.override-stage-condition-conflict-rejected, codepipeline.retry-stage-execution-resumes-failed-stage, codepipeline.rollback-stage-restores-previous-state.
