# Five MSK lifecycle families still reach no verdict: VPC-connection, replicator, channel, cluster-operation and SCRAM-revocation sequences all time out with nothing asserted (5 causes)

> _Note: this issue was identified against the code base at commit `99262483d434e1c358a4a36afbbe51aaea28d692`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateVpcConnection

## Description
Fifteen kafka behavioral checks produce NO verdict at all: each reports only 'Error: Check timed out after 60.0s' — no HTTP status, no error code, no traceback frame — so nothing was refused and no assertion was evaluated. They cluster into FIVE distinct root causes, one per asynchronous MSK resource family whose state never settles to its terminal value on the path these sequences walk. Each cause must be closed separately; all five must be closed before this issue is submitted.

Context a fixer needs first: 12 of these 15 check ids were listed in the RESOLVED issue 20261104T171616Z-kafka-msk-asynchronous-transitions-are-clock-owed-so-an.md (kafka.vpc-connection-create-available-lifecycle, kafka.vpc-connection-reject-transitions-state, kafka.vpc-connection-malformed-subnet-config-rejected, kafka.update-broker-count-operation-lifecycle, kafka.update-replication-info-concurrent-conflicting-updates, kafka.update-replication-info-invalid-target-topics-rejected, kafka.update-replication-info-server-enforced-propagation, kafka.update-channel-wrong-state-rejected, kafka.channel-list-pagination-and-filter-consistency, kafka.channel-update-unicode-fields-round-trip, kafka.configuration-delete-in-use-conflict, kafka.replicator-create-invalid-role-rejected). That fix did NOT make them reach a verdict: they still time out, and because the replay key frame moved, the suite now reports them unowned. Two of its 14 ids (kafka.describe-topic-partitions-invalid-topic-rejected, kafka.server-side-cluster-policy-cross-account-enforcement) no longer fail, so the generic clock-owed settling was partly addressed; what remains is per-resource-family and is described below. Three ids here are net-new to this symptom: kafka.channel-update-mutation-reflected-in-describe, kafka.e2e-replicator-cross-cluster-topic-sync-teardown, kafka.scram-secret-disassociation-immediate-auth-revocation. Open issues that describe neighbouring causes for OTHER ids and therefore do NOT cover any id here: 20261105T161551Z-kafka-two-more-msk-checks-never-reach-a-verdict.md, 20261104T171616Z-kafka-no-kafka-broker-answers-on-the-advertised-bootstrap.md, 20261109T211434Z-kafka-msk-bootstrap-endpoints-are-published-as-real-aws.md, 20261104T171616Z-kafka-updatemonitoring-updaterebalancing-and-updatetopic-still-answer-501-notimplemented.md, 20261104T171616Z-kafka-updatechannel-stub.md. The requirement in every cause below is only that the sequence reaches a pass/fail verdict at an AWS-appropriate poll cadence.

Cause 1 of 5: the multi-VPC private-connectivity sequence never completes, so no VPC-connection state transition is observable.
AWS: an ACTIVE cluster accepts UpdateConnectivity (multi-VPC, Sasl.Iam); the returned cluster operation progresses UPDATE_IN_PROGRESS -> UPDATE_COMPLETE and the cluster returns to ACTIVE. CreateVpcConnection then returns State 'CREATING' (Smithy: CreateVpcConnection -> VpcConnectionState enum CREATING|AVAILABLE|INACTIVE|DEACTIVATING|DELETING|FAILED|REJECTED|REJECTING) and DescribeVpcConnection reports AVAILABLE, echoing the submitted vpcId; RejectClientVpcConnection moves an AVAILABLE connection to REJECTED and it stops appearing as an active connection; after DeleteVpcConnection, DescribeVpcConnection and a second DeleteVpcConnection both answer 404 NotFoundException with the fixed message 'The requested resource doesn’t exist.' (fixed text in full; no request value is interpolated). CreateVpcConnection with client subnets that do not match the cluster's is refused 400 BadRequestException 'Specify the same number of client subnets as cluster subnets.' (fixed text in full).
Emulator: all three VPC-connection checks end with the bare 60 s timeout, having asserted nothing: the sequence create cluster -> wait ACTIVE -> UpdateConnectivity -> poll the cluster operation to UPDATE_COMPLETE -> CreateVpcConnection -> poll to AVAILABLE -> delete -> poll to not-found never finishes inside a bounded budget even though the checks poll at AWS-sized intervals (30 s for the cluster and the operation, 15 s for the connection). Hypothesis (not stated by the replay output): one of the UPDATE_CONNECTIVITY operation state, the cluster's return to ACTIVE, or the VPC connection's CREATING -> AVAILABLE/REJECTED/absent transition never reaches a terminal value, so the poll runs to its deadline rather than paying one interval.
Why: a client that enables multi-VPC connectivity and then waits for its connection hangs until its own timeout; the whole VPC-connection lifecycle, its reject transition, its delete idempotency and its subnet-mismatch refusal are unverifiable against the emulator.
Fix: the kafka service's state layer and the UpdateConnectivity / CreateVpcConnection / RejectClientVpcConnection / DeleteVpcConnection handlers must drive these states to terminal values that a first (or at most second) probe observes.
Traces: kafka.vpc-connection-create-available-lifecycle, kafka.vpc-connection-malformed-subnet-config-rejected, kafka.vpc-connection-reject-transitions-state.

Cause 2 of 5: a replicator never becomes observable as RUNNING, so the whole MSK Replicator surface reaches no verdict.
AWS: CreateReplicator returns replicatorState 'CREATING' (Smithy: ReplicatorState enum RUNNING|CREATING|UPDATING|DELETING|FAILED) and DescribeReplicator reports RUNNING once provisioning finishes; a source topic created after that appears in the target cluster's ListTopics; UpdateReplicationInfo on the RUNNING replicator takes currentVersion (Smithy: required member currentVersion) and is refused 400 BadRequestException on a stale version or an invalid target-topic/regex input, and its accepted form propagates to DescribeReplicator; CreateReplicator with a service-execution role MSK cannot assume is refused 400 BadRequestException; after DeleteReplicator, DescribeReplicator answers 404 NotFoundException 'The requested resource doesn’t exist.' (fixed text in full).
Emulator: every replicator check ends with the bare 60 s timeout. The sequences build two clusters, wait ACTIVE, create the replicator and poll DescribeReplicator at 15 s intervals for RUNNING (and, for the e2e check, poll the target cluster's ListTopics and the post-delete absence); none reaches an assertion. Hypothesis: the replicator stays CREATING indefinitely (and cross-cluster topic propagation is never performed), so neither the happy path nor the refusals behind it are ever evaluated.
Why: replication — the point of the Replicator API — cannot be exercised at all, and UpdateReplicationInfo's optimistic-lock, invalid-target-topics and invalid-pattern contracts are unverifiable.
Fix: the replicator state machine in the kafka service's state layer plus the CreateReplicator / DescribeReplicator / UpdateReplicationInfo / DeleteReplicator handlers must settle CREATING -> RUNNING and perform (or at least record) the configured topic replication.
Traces: kafka.replicator-create-invalid-role-rejected, kafka.update-replication-info-concurrent-conflicting-updates, kafka.update-replication-info-invalid-target-topics-rejected, kafka.update-replication-info-server-enforced-propagation, kafka.e2e-replicator-cross-cluster-topic-sync-teardown.

Cause 3 of 5: a data-delivery channel on an Express cluster never becomes ACTIVE, so the channel surface reaches no verdict.
AWS: CreateChannel returns a channelArn plus a clusterOperationArn and DescribeChannel reports Status 'CREATING' then 'ACTIVE' (Smithy: ChannelStatus enum CREATING|ACTIVE|UPDATING|DELETING|FAILED|SUSPENDING|SUSPENDED; DescribeChannel output requires status, destinationType, creationTime, topicConfigurationList). ListChannels then lists it and its filters/pagination are consistent with DescribeChannel; UpdateChannel on an ACTIVE channel applies the new S3DestinationConfiguration (e.g. DataFreshnessInSeconds) and the channel returns to ACTIVE, while UpdateChannel on a DELETING channel is refused 400 BadRequestException 'Channel cannot be updated in state DELETING. Channel must be in ACTIVE state to be updated.' — fixed text except for the state name, which is the channel's current state — and changes nothing.
Emulator: all four channel checks end with the bare 60 s timeout. They first wait for the Express cluster to be ACTIVE (20 s cadence) and for the source topic to be ACTIVE (5-15 s), then poll DescribeChannel/ListChannels at 10-15 s for ACTIVE; no assertion is reached. Hypothesis: the channel (and/or the CreateChannel cluster operation, and/or the topic the channel depends on) never leaves its non-terminal state. Note UpdateChannel and ListChannels also have unimplemented-stub issues on file (20261104T171616Z-kafka-updatechannel-stub.md, 20261029T175822Z-kafka-listchannels-stub.md); the requirement here is only that these sequences reach a verdict instead of a timeout.
Why: no client can observe a channel becoming usable, so channel listing/filtering, channel updates and the wrong-state refusal are all unverifiable.
Fix: the channel state machine in the kafka service's state layer plus the CreateChannel / DescribeChannel / ListChannels / UpdateChannel / DeleteChannel handlers must settle CREATING -> ACTIVE (and UPDATING -> ACTIVE) and settle the CreateChannel cluster operation.
Traces: kafka.channel-list-pagination-and-filter-consistency, kafka.channel-update-mutation-reflected-in-describe, kafka.channel-update-unicode-fields-round-trip, kafka.update-channel-wrong-state-rejected.

Cause 4 of 5: a cluster operation plus the re-read that must follow it never completes, so async cluster mutation and the in-use-configuration conflict reach no verdict.
AWS: UpdateBrokerCount returns clusterArn + clusterOperationArn (Smithy: targetNumberOfBrokerNodes @range 1..15, required currentVersion) and DescribeClusterOperation progresses UPDATE_IN_PROGRESS -> UPDATE_COMPLETE; only after that does DescribeClusterV2 report the new Provisioned.NumberOfBrokerNodes — scaling is asynchronous. Likewise, DeleteConfiguration on a configuration still attached to a cluster is refused 400 BadRequestException and the configuration stays ACTIVE (Smithy: ConfigurationState enum ACTIVE|DELETING|DELETE_FAILED), while once the cluster has been moved to another configuration (UpdateClusterConfiguration + its operation reaching UPDATE_COMPLETE) the delete succeeds and the configuration disappears.
Emulator: both checks end with the bare 60 s timeout while polling DescribeClusterOperation (15-20 s) and DescribeClusterV2 (30 s). Hypothesis: the UPDATE_BROKER_COUNT / UPDATE_CLUSTER_CONFIGURATION operations never reach a *_COMPLETE OperationState, or the cluster never returns to ACTIVE after them, so no re-read assertion is ever evaluated.
Why: a client that scales a cluster or re-points its configuration and waits for the operation never gets a terminal answer; the ordering guarantee (operation completes before the new value is visible) and the in-use-configuration conflict are unverifiable.
Fix: the cluster-operation state machine in the kafka service's state layer plus the UpdateBrokerCount / UpdateClusterConfiguration / DescribeClusterOperation(V2) / DeleteConfiguration handlers must settle operations to UPDATE_COMPLETE, return the cluster to ACTIVE, and apply the mutation on that boundary.
Traces: kafka.update-broker-count-operation-lifecycle, kafka.configuration-delete-in-use-conflict.

Cause 5 of 5: the SCRAM-revocation sequence reaches no verdict, so disassociation has no observable effect on authentication.
AWS: BatchDisassociateScramSecret on an associated secret returns an empty unprocessedScramSecrets, ListScramSecrets stops listing that secret immediately, and within the documented propagation window the brokers reject a SASL/SCRAM handshake using those credentials while a still-associated secret keeps authenticating (recorded behavior for the data-plane consequence; the model only states the control-plane shapes). The sequence in front of it is also AWS-defined: CreateClusterV2 -> ACTIVE, UpdateConnectivity to SERVICE_PROVIDED_EIPS with its operation reaching UPDATE_COMPLETE and the cluster ACTIVE again, then GetBootstrapBrokers' SASL/SCRAM endpoint accepting a TCP connection and completing the handshake on port 9196.
Emulator: the check ends with the bare 60 s timeout, having asserted nothing — neither the empty unprocessedScramSecrets, nor the ListScramSecrets effect, nor the authentication outcome. Hypothesis: it is blocked in the same unsettled cluster/operation polls as Cause 4 and, beyond them, on the absence of a broker that accepts a SASL/SCRAM connection on the advertised endpoint (the same family as the open issues named above, neither of which carries this check id). Because the emulator itself announces the bootstrap address, an unanswered connect there is the emulator's gap, not the runner's.
Why: credential revocation — the security-relevant consequence of BatchDisassociateScramSecret — cannot be observed at all.
Fix: settle the cluster and UpdateConnectivity transitions (as in Cause 4), and have the kafka service serve SASL/SCRAM on the endpoint it advertises so an authentication attempt yields an accept/reject outcome; the BatchDisassociateScramSecret handler and the cluster's SCRAM secret state must make the revocation effective there.
Traces: kafka.scram-secret-disassociation-immediate-auth-revocation.
