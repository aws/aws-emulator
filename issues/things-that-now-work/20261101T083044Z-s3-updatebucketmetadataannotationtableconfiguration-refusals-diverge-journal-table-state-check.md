# S3 UpdateBucketMetadataAnnotationTableConfiguration refusals diverge: journal-table-state check missing and BucketName dropped

> _Note: this issue was identified against the code base at commit `673cffa0a0a50f9e1f360478aae253685eee624e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateBucketMetadataAnnotationTableConfiguration

## Description
Two net-new root causes in the same handler: the annotation-table update path of the S3 metadata-configuration API does not produce the refusals AWS produces. One refusal is missing entirely (the request is accepted with a success status), and one is produced with the right status but an incomplete error envelope. A fixer must close both causes before submitting.

Cause 1 of 2: UpdateBucketMetadataAnnotationTableConfiguration is accepted while the bucket's journal table is still being created, instead of being refused.
AWS: recorded behavior only - Smithy (services/service-com-amazonaws-s3-amazons3) models UpdateBucketMetadataAnnotationTableConfiguration as PUT /{Bucket}?metadataAnnotationTable with success code 200, an empty output and an EMPTY modelled error list, so the refusal is not in the model and is taken from the recording. The recording shows that while the metadata configuration's journal table has not yet reached ACTIVE, the annotation-table update is refused with HTTP 400 and the REST-XML error document <Error><Code>InvalidRequest</Code><Message>You can't perform this operation while the journal table is being created. Wait for your journal table status to transition to ACTIVE, and then try again.</Message><RequestId/><HostId/></Error>. In that message every word is FIXED text of this error class - it interpolates nothing from the request or from state - so it must be reproduced verbatim; RequestId and HostId are per-request values generated by the responder and are not part of the requirement. The status (400) and the code (InvalidRequest) are requirements.
Emulator: returns HTTP 200 with an EMPTY body - the update is applied regardless of the journal table's state. Replay detail: "status: expected 400, got 200" and "$: empty_body (expected {'Error': {'Code': 'InvalidRequest', 'Message': \"You can't perform this operation while the journal table is being created...\"}}, got {})".
Why: a client that provisions a metadata configuration and then configures the annotation table relies on the 400/InvalidRequest to know it must wait and retry until the journal table is ACTIVE. Against the emulator the call reports success, so the client proceeds believing the annotation table is configured; the lifecycle ordering rule AWS enforces is invisible, and code that catches InvalidRequest to drive its retry loop never runs - a bug that only appears against real AWS.
Fix: the UpdateBucketMetadataAnnotationTableConfiguration handler's pre-condition validation - it must read the bucket's metadata-configuration journal-table status from state and refuse with the InvalidRequest error class (400) whenever that status is not ACTIVE, before applying the update.
Traces: s3-bucket-metadata-and-metadata-table-configuration-management#task#6.

Cause 2 of 2: UpdateBucketMetadataAnnotationTableConfiguration's not-found refusal omits the BucketName member from the error envelope.
AWS: recorded behavior only - the error is not modelled (the operation declares no errors), and the S3 error shapes carry no members. The recording shows the bucket/configuration-scoped refusal serialized as <Error><Code/><Message/><BucketName/><RequestId/><HostId/></Error>: Code and Message are the fixed text of the error class, and BucketName is a VARIABLE part copied straight from the request's {Bucket} path label. Status 400/404 and the code already match; only the envelope member diverges.
Emulator: the 404 body carries Code/Message/RequestId/HostId only. Replay detail: "$.Error.BucketName: missing (expected the requested bucket name, got None)".
Why: the envelope is the only place the refusal names the resource it is about. A client driving several buckets through one code path cannot attribute the failure, and the SDK error shape's BucketName accessor hands back None.
Fix: the UpdateBucketMetadataAnnotationTableConfiguration handler's not-found error construction / the REST-XML error serializer it calls, which must populate BucketName from the request's Bucket label.
Traces: s3-metadata-update-on-missing-config-errors#task#4.

Related open issues that do NOT cover these: "S3 metadata and tagging error envelopes drop BucketName and AnnotationName" (20261030T053639Z-s3-metadata-and-tagging-error-envelopes-drop-bucketname.md) lists UpdateBucketMetadataJournalTableConfiguration and UpdateBucketMetadataInventoryTableConfiguration but NOT the Annotation-table handler, and "S3 bucket error envelopes omit the BucketName member" (20261030T053639Z-s3-bucket-error-envelopes-omit-the-bucketname-member.md) covers bucket sub-resource reads; neither carries the replay key for either cause above, so both are filed here.
