# Step Functions alias operations: ResourceNotFound returned as HTTP 404 with emulator-local wording, UpdateStateMachineAlias mis-codes a foreign-version re-point as ValidationException, and a RedriveCount context-object run never progresses (3 causes)

> _Note: this issue was identified against the code base at commit `db7835caf474b2d4a8aed951b553bbb17b75b096`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStateMachineAlias

## Description
This issue bundles THREE distinct net-new root causes in the Step Functions emulator. All three must be closed before submitting; a fixer should re-replay every check id in trace_ids. All three checks were left UNMARKED by the replay report (no ALREADY-FILED and no OWNED marker), so no existing issue carries their replay keys.

=== Cause 1 of 3: ResourceNotFound on the alias read path is rendered with HTTP 404 and an emulator-local message instead of AWS's HTTP 400 / "Request references a resource that does not exist." ===
Failing check id: sfn.alias-create-describe-update-delete-lifecycle.
AWS: Smithy (services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json) models DescribeStateMachineAlias with input {stateMachineAliasArn (required, Arn, @length 1..256)} and errors InvalidArn (400), ResourceNotFound (@httpError 404, explicitly set in the model) and ValidationException (400). Recorded behavior contradicts that modeled status for this service: on real AWS, DescribeStateMachineAlias on an alias that has been deleted answers error code ResourceNotFound at HTTP **400**, not 404 — Step Functions is an awsJson1_0 service that returns 400 for this client error regardless of the model's @httpError. The message AWS returns for the ResourceNotFound class is the fixed text "Request references a resource that does not exist." with NO variable part (the same wording the sibling check sfn.alias-repoint-to-foreign-state-machine-version-rejected records for the same error shape on UpdateStateMachineAlias). So the requirement is: HTTP status 400, error code ResourceNotFound, message exactly "Request references a resource that does not exist."
Emulator: the refusal carries the right error code but the wrong status and a locally-invented message — observed {'Code': 'ResourceNotFound', 'Status': 404, 'Message': 'could not find the resource arn:aws:states:<region>:<account>:stateMachine:<state-machine-name>:<alias-name>'}. In that message, "could not find the resource " is emulator-authored fixed text and the trailing alias ARN is interpolated from the request; AWS emits neither part. The check fails with `AssertionError: DescribeStateMachineAlias on a deleted alias: expected ResourceNotFound/400, got {'Code': 'ResourceNotFound', 'Status': 404, ...}`.
Why: a client that branches on the HTTP status (SDK retry/throttle classification, API-gateway style proxies, and any code that treats 404 as "route/endpoint missing" versus 400 as "bad request about an existing API") takes the wrong branch, and a client or test that asserts on the error message — the documented, fixed AWS text — never matches. It also makes the emulator inconsistent with itself, because the same error shape is the one AWS uses across every alias/state-machine lookup.
Fix: the sfn error serializer / status mapping for the ResourceNotFound shape (it must emit 400 for this service rather than taking the modeled @httpError 404), plus the message construction wherever ResourceNotFound is raised in the alias handlers — the message must be AWS's fixed text and must not interpolate the requested ARN.
Traces: sfn.alias-create-describe-update-delete-lifecycle (assertion at check_sfn_alias_create_describe_update_delete_lifecycle.py line 211).

=== Cause 2 of 3: UpdateStateMachineAlias re-pointed at a version of a DIFFERENT state machine is refused with ValidationException instead of ResourceNotFound ===
Failing check id: sfn.alias-repoint-to-foreign-state-machine-version-rejected.
AWS: Smithy models UpdateStateMachineAlias input {stateMachineAliasArn (required), description, routingConfiguration (@length 1..2)} and declares BOTH ResourceNotFound (404 in the model, 400 on the wire for this service) and ValidationException (400) as errors, so the model alone cannot decide which applies. Recorded behavior: real AWS refuses the update with error code **ResourceNotFound** and the fixed message "Request references a resource that does not exist." — measured twice, 20 s apart, with the foreign version independently describable in between. Hypothesis for why: Update resolves the requested version ARN *under the alias's own state machine*, where it does not exist, so the lookup fails before any cross-machine validation runs. This is deliberately NOT the ValidationException that CreateStateMachineAlias returns for the same foreign version — the two operations diverge, and the refusal must leave the alias's routing exactly where it was (observable on the data plane by executing through the alias, not only by reading routingConfiguration back).
Emulator: the call is refused with {'Code': 'ValidationException', 'Message': 'the routing configuration names versions of state machine arn:aws:states:<region>:<account>:stateMachine:<other-state-machine>, and alias arn:aws:states:<region>:<account>:stateMachine:<own-state-machine>:<alias-name> points at versions of arn:aws:states:<region>:<account>:stateMachine:<own-state-machine>'}. Both the code and the entire message are emulator-authored: the fixed text ("the routing configuration names versions of state machine ", ", and alias ", " points at versions of ") appears nowhere in AWS, and the three ARNs are interpolated from the request and from the alias's stored routing. AWS's message for this refusal has no variable parts at all.
Why: a client that distinguishes "the version I named does not exist for this alias" (ResourceNotFound — a resource-resolution failure, typically retried after a PublishStateMachineVersion) from "my request shape is invalid" (ValidationException — never retryable) takes the wrong path. Concretely, `except sfn.exceptions.ResourceNotFound` handlers never fire, and Terraform's `aws_sfn_alias` re-point path, which depends on this exact code to decide whether to re-resolve the version, misbehaves.
Fix: UpdateStateMachineAlias's handler/validation — resolve each routingConfiguration stateMachineVersionArn *within the alias's own state machine* and raise ResourceNotFound (AWS's fixed message) when it does not resolve, instead of comparing the two ARNs and raising ValidationException; CreateStateMachineAlias's ValidationException for the same input must be left alone. Note: open issue 20261024T215142Z-sfn-updatestatemachinealias-stub.md reports UpdateStateMachineAlias as an unimplemented scaffold stub — it does NOT cover this, because the operation plainly answers here with a real, state-derived refusal; this is the error-classification defect on the implemented path.
Traces: sfn.alias-repoint-to-foreign-state-machine-version-rejected (assertion at check_sfn_alias_repoint_to_foreign_state_machine_version_rejected.py line 90).

=== Cause 3 of 3: an execution whose Task state names an activity ARN never delivers a task, so RedriveExecution's RedriveCount can never be observed through the context object, DescribeExecution or the history ===
Failing check id: sfn.deep-sfn-2-sfn-jsonata-context-redrive-count-joins-describe-execution.
AWS: Smithy models RedriveExecution with input {executionArn (required), clientToken (idempotency token)}, output {redriveDate (required)} and errors ExecutionDoesNotExist / ExecutionLimitExceeded / ExecutionNotRedrivable / InvalidArn / ValidationException. The behavior this check grades on top of that is recorded behavior (the ASL context object is not described by the model): entering a Task state whose Resource is an activity ARN enqueues a task that the next GetActivityTask long-poll returns with the state input; `$$.Execution.RedriveCount` (and, in a JSONata-overridden state, `$states.context.Execution.RedriveCount`) reads 0 on the original run and 1 in every state RE-ENTERED by a redrive; a state that already succeeded is NOT re-run, so its stamped value stays 0 in the final output; DescribeExecution reports redriveStatus REDRIVABLE with redriveCount 0 after the induced failure and redriveCount 1 after the redrive, agreeing with both context-object reads; and GetExecutionHistory contains exactly one ExecutionRedriven event whose executionRedrivenEventDetails.redriveCount is 1 and exactly one PassStateEntered event for the already-succeeded state.
Emulator: none of that is reachable. The check is killed with "Error: Check timed out after 60.0s" inside its _poll_activity_task helper (a GetActivityTask loop with a 90 s budget): GetActivityTask keeps answering with no taskToken, so the activity task is never enqueued when the Task state is entered, SendTaskFailure/RedriveExecution are never called, and no RedriveCount value, DescribeExecution redriveCount or ExecutionRedriven event is ever produced.
Why: redrive is the documented recovery path for a failed Standard execution. A client cannot tell an original run from a redriven one (the context object is how a workflow branches on that), cannot count redrives from DescribeExecution, and cannot audit the redrive from the history; worse, an activity worker driving the failure never receives work at all, so the execution never leaves RUNNING and no error explains why.
Fix: the activity task scheduling path shared by the interpreter's Task-state handler and GetActivityTask's handler/state (enqueue against the activity ARN, dequeue and mint a token), and then the redrive bookkeeping in the execution state and interpreter — the per-execution redriveCount surfaced in DescribeExecution, exposed to expression evaluation as Execution.RedriveCount for re-entered states only, and recorded on an ExecutionRedriven history event. Related but NOT covering this check: open issues 20261025T075213Z-sfn-step-functions-activity-tasks-are-never-delivered-to.md (GetActivityTask never hands out a token, grounded in other check ids), 20261024T190039Z-sfn-step-functions-activities-and-teststate-diverge-task-states.md and 20261024T043150Z-sfn-step-functions-interpreter-does-not-run-the-workflow.md (Task states and JSONata never execute) — the replay report marked this check as owned by none of them, and the RedriveCount/ExecutionRedriven requirements above are described in none of them.
Traces: sfn.deep-sfn-2-sfn-jsonata-context-redrive-count-joins-describe-execution (harness timeout inside _poll_activity_task).
