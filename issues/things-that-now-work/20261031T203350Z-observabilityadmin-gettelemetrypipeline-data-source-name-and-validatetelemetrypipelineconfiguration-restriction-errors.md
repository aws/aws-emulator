Cause 1 of 2 — ValidateTelemetryPipelineConfiguration reports only 2 of the 9 recorded defects of a multi-defect pipeline document: the five per-source-type/processor restriction defects and the two processor-position unknown-property defects are never produced, and the two defects it does produce are emitted first rather than last.
AWS: Smithy (services/service-com-amazonaws-observabilityadmin-observabilityadmin/smithy-model/com-amazonaws-observabilityadmin-observabilityadmin.json): ValidateTelemetryPipelineConfiguration input Configuration (required) -> TelemetryPipelineConfiguration; output Errors -> list<ValidationError{Message,Reason,FieldMap}>; http POST /ValidateTelemetryPipelineConfiguration, code 200 (defaulted); modeled errors AccessDeniedException(400), InternalServerException(500), TooManyRequestsException(429), ValidationException(400). The model documents Reason only as the reason code/category and FieldMap only as 'a mapping of field names to specific validation issues within the configuration', so the reason vocabulary, the FieldMap key names and the report ORDER are recorded behavior only. Recorded behavior: a content-level defect is always reported inside the 200 body's Errors list (never as a synchronous exception), and one defective document yields NINE entries in a stable order — five with Reason 'DATA_SOURCE_PROCESSOR_RESTRICTED', two with Reason 'UNKNOWN_PROPERTY' pinned to a processor POSITION (FieldMap {'path': 'processor[<i>]'}), and only then the two with Reason 'MISSING_FIELD' for the sections the document omits (FieldMap {'name': '<property>'}). A DATA_SOURCE_PROCESSOR_RESTRICTED entry's FieldMap is keyed by the RESTRICTION's own descriptors — 'source_type', 'data_source_name', and 'allowed_processor' (one) or 'allowed_processors' (a '/'-joined set) — and its Message is one of the schema templates 'must have at most <n> items but found <m>', "property '<name>' is not defined in the schema and the schema does not allow additional properties" and "required property '<name>' not found". Fixed text: the reason tokens, the FieldMap descriptor key names and those sentence templates. Variable parts, taken from the submitted document and the service's per-source-type restriction table: the source type, the data-source name, the allowed-processor list, the counts, the offending property name and the processor index.
Emulator: answers 200 with exactly TWO entries, both Reason 'MISSING_FIELD' — "required property 'source' not found" with FieldMap {'name': 'source'} and "required property 'sink' not found" with FieldMap {'name': 'sink'} (these two now match the recording's content) — and nothing else, so they occupy positions [0] and [1] where the recording has restriction defects. The validator's reason vocabulary has no DATA_SOURCE_PROCESSOR_RESTRICTED token at all (src/ops/validate_telemetry_pipeline_configuration.rs:273-297 declares only MISSING_FIELD, UNKNOWN_PROPERTY, PIPELINE_CONFIGURATION_PARSE_ERROR, PIPELINE_CONFIGURATION_VALIDATION_ERROR, INVALID_PATTERN and the emulator-private UNSUPPORTED_PROCESSOR), so per-source-type processor restrictions — how many processors a data source admits, which processors a source type allows, which processor names the schema defines at all — are not validated, and a processor name the emulator happens to run is silently accepted where the real schema does not define it.
Why: this operation exists so a caller can learn EVERY defect of a configuration in one round trip, before CreateTelemetryPipeline. A client is told two sections are missing and nothing about the restriction violations that will also stop the pipeline: it fixes the document, re-submits, and is refused again — or the emulator's CreateTelemetryPipeline accepts a configuration the real service rejects, so the validation step gives false confidence. A client that branches on Reason never sees DATA_SOURCE_PROCESSOR_RESTRICTED, and one that reads FieldMap's restriction descriptors to tell the user which processor is allowed for which source type finds no such entry.
Fix: the configuration validator behind the ValidateTelemetryPipelineConfiguration handler (services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/ops/validate_telemetry_pipeline_configuration.rs) — add the per-source-type data-source/processor restriction pass and the processor-position unknown-property pass to the schema walk, emit them under AWS's reason tokens with FieldMap keyed by the restriction descriptors ('source_type', 'data_source_name', 'allowed_processor'/'allowed_processors') or by 'path' for a processor position, and order them ahead of the missing-required-property defects. The restriction table (which processors each source type and vended data source admits, and how many) belongs beside the schema the same validator already walks, not in the handler.

Cause 2 of 2 — GetTelemetryPipeline's derived ConfigurationSummary names a source's undeclared data source with the pipeline name VERBATIM, where the recording names it with the pipeline name's underscore form.
AWS: Smithy: GetTelemetryPipeline input PipelineIdentifier (required, @length 1..512), output Pipeline -> TelemetryPipeline; http POST /GetTelemetryPipeline, 200 (defaulted); readonly. CreateTelemetryPipeline input Name is @length 3..28 with @pattern '[a-z][a-z0-9\-]+', so a pipeline NAME can never contain an underscore. The on-disk model declares no ConfigurationSummary member on the read's pipeline, so the summary and its derivation are recorded behavior only: a read of an ACTIVE pipeline carries Pipeline.ConfigurationSummary with Sources/DataSources/Processors/ProcessorCount/Sinks derived from the stored configuration document, and for a vended-log source that declares no data source the single DataSources entry is {Name: <the pipeline's name with every '-' replaced by '_'>, Type: 'default'}. The fixed part of the requirement is that normalization: the recorded name is the pipeline name in underscore form, a form the pipeline name itself cannot take, so it is produced by the service and not echoed from the request. Hypothesis: the name is the identifier of the log-event metadata the pipeline's vended events carry, which is why it is normalized to an identifier-safe form rather than reported as the hyphenated resource name.
Emulator: reports DataSources[0].Name as the pipeline's name exactly as created, hyphens included (e.g. 'sim2real-probe-pipe-<suffix>' against the recording's 'sim2real_probe_pipe_<suffix>'); Type 'default' and every other summary member match. src/state.rs:784-797 (data_source) falls back to `pipeline` unchanged for a vended source, and src/state.rs:664 passes `&record.name` into it.
Why: the data-source name is the key a caller correlates a pipeline's records by (it is what the restriction descriptors in Cause 1 call 'data_source_name', and what a console groups delivered records under). Reporting the hyphenated resource name instead of the normalized identifier gives a client a key that matches nothing the real service emits, and silently changes the shape of every pipeline whose name contains a hyphen — which the Name pattern makes the common case.
Fix: the summary derivation in services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/state.rs — normalize the pipeline name to its data-source identifier form ('-' -> '_') in the undeclared-data-source fallback, rather than cloning the resource name; a data-source name the document DOES declare must still be reported exactly as declared.

## Resolution

Both causes are FIXED.

* **Cause 1 — the vended-log restriction pass is WRITTEN.** The pipeline schema's
  branches for a source that reads AWS-vended log events now live beside the walk that
  reports a document's defects, in
  `src/ops/validate_telemetry_pipeline_configuration/vended_log_schema.rs`: one branch
  per vended source type, and per vended data source for a source type whose restriction
  is per data source, each carrying the processors it admits and the property its source
  requires. A section declaring a vended source type is measured against that type's
  branches, narrowed to the data sources it names; a section declaring NO source pins no
  branch, so every branch it violates is reported; a section reading from a third-party
  source carries none of these restrictions. Each violated branch answers one
  `DATA_SOURCE_PROCESSOR_RESTRICTED` entry whose `FieldMap` carries the restriction's own
  descriptors (`source_type`, `data_source_name`, and `allowed_processor` or the
  `/`-joined `allowed_processors`) and whose message is the schema's sentence for the
  keyword it violates, and a position of such a section's processor sequence naming a
  processor that branch does not define answers the plain `UNKNOWN_PROPERTY` entry at
  `processor[<i>]`. The restriction defects are reported ahead of the defects of the
  document's own properties. Fixture observabilityadmin-telemetry-pipeline-workflow step
  task#3 replays clean.
* **Cause 2 — the data-source identifier is NORMALIZED.** A vended source that declares
  no data source reads the events vended for the pipeline itself, and the
  `data_source_name` that metadata carries is an identifier, so `src/state.rs` reports the
  pipeline's name with `-` replaced by `_` rather than cloning the resource name; a data
  source the document declares is still reported exactly as declared, and a third-party
  source still defaults to its plugin name. The replay's residual difference at
  `$.Pipeline.ConfigurationSummary.DataSources[0]` is the fixture's per-run hex suffix in
  the pipeline name it generates, which this report already states is not a requirement.
