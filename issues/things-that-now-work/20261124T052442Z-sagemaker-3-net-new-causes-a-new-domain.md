# sagemaker: 3 net-new causes — a new Domain's Pending window is unobservable (the first request after CreateDomain already reports InService), the presigned domain URL never hands off to the domain's own Studio host, and CreateFeatureGroup accepts an offline store its RoleArn cannot write

> _Note: this issue was identified against the code base at commit `772b47d3bfe5aea8d8d555dc755349d8f3c1231b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomain, CreateUserProfile, CreateSpace, CreatePresignedDomainUrl, CreateFeatureGroup

## Description
THREE net-new root causes, all grounded in failing checks the suite report lists under `### sagemaker`, none of which the report marked ALREADY FILED or OWNED by an open issue. They are numbered and each carries its own failing check ids; ALL THREE must be closed before this issue is submitted.

=== Cause 1 of 3: a newly created Studio Domain's `Pending` window spans ZERO requests, so no caller ever observes it and the domain's not-InService refusals can never fire ===
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json) — CreateDomain models only ResourceInUse and ResourceLimitExceeded (both HTTP 400) and answers DomainArn/DomainId/Url; DescribeDomain reports `Status` -> `DomainStatus`, whose members include `Pending` and `InService`. Recorded behavior: CreateDomain is ASYNCHRONOUS — the domain is provisioned after the call answers, DescribeDomain reports `Status: Pending` for that whole window (minutes on AWS), and a call that hangs a member off the domain in that window is refused HTTP 400 `ValidationException`: `Unable to create UserProfile [<user-profile arn>] because Domain [<domain arn>] is not in InService.` for CreateUserProfile, `Unable to create Space [<space arn>] because Domain [<domain arn>] is not in InService.` for CreateSpace (fixed text `Unable to create <entity> [` / `] because Domain [` / `] is not in InService.`, with the would-be resource's ARN and the domain's ARN as the only variable parts), and `Domain must be in either InService or Update_Failed state and not in: <current status>` for CreatePresignedDomainUrl. Only once the domain reports InService are those same calls accepted. The window must therefore be observable: it is the state in which those refusals exist at all.
Emulator: the Pending->InService transition is owed from the instant CreateDomain ANSWERS — `in_service_due_at = transition_owed_at(now)`, materialised by `Domain::settle_status` on the first reporting read (services/service-com-amazonaws-sagemaker-sagemaker/src/state/domain.rs:48-55, 385-391, 455-472; the slice's own comment states the intent: "the first request after the create reports the settled domain"). The consequence measured by the replay: the three calls issued immediately after CreateDomain were all ACCEPTED (no refusal recorded for any of them) and the DescribeDomain that followed them read `InService` — for THREE consecutive freshly created domains, `['InService', 'InService', 'InService']`. There is no request at which a client can see `Pending`, so neither the Pending-state refusals (which the emulator does implement) nor the status itself is reachable.
Why: a client that does what AWS requires — CreateDomain, poll DescribeDomain until InService, then create user profiles/spaces or mint a presigned URL — sees a domain that is InService on its very first probe, so its waiter and its retry-on-not-InService paths are never exercised and a sequencing bug that breaks against AWS passes here; conversely an application that relies on the documented refusal to serialise its creates gets silent acceptance from the emulator for calls AWS refuses, and `DomainStatus: Pending`, which every describe/list reports, is a value no caller of this emulator can ever read.
Fix: the Studio domain slice's clock-owed span and the CreateDomain handler that sets it — the domain needs a non-zero provisioning span of its own (as `ENDPOINT_IN_SERVICE_AFTER` and `USER_PROFILE_IN_SERVICE_AFTER` give their resources) instead of `transition_owed_at(now)`, so the transient `Pending` status is still reported by the requests that immediately follow the create and the member-creates issued in that window are refused, while a waiter polling at a realistic interval still terminates. Open issue 20261123T054636Z-sagemaker-2-net-new-causes-createpresigneddomainurl-s-not.md is grounded in the SAME check for a different frame (Cause 1 there is the wording of the presigned refusal, reached only once a Pending domain is observable) and its Cause 2 asked that a settle not cost a polling client a whole interval — the fix here must satisfy both: Pending observable to the calls right after the create, without forcing a poller to sleep a full interval. The suite did not mark this failure as OWNED by that issue (its replay key names a different frame), and the refusal wording cannot be re-tested until this cause is fixed.

=== Cause 2 of 3: following a CreatePresignedDomainUrl AuthorizedUrl never reaches the domain's own Studio host — the /auth address answers 200 itself, with no hand-off ===
AWS: Smithy — CreatePresignedDomainUrl(DomainId, UserProfileName required) answers `AuthorizedUrl` (PresignedDomainUrl) and models only ResourceNotFound; its documentation states the purpose: "Creates a URL for a specified UserProfile in a Domain. When accessed in a web browser, the user will be automatically signed in to the domain, and granted access to all of the Apps and files associated with the Domain's Amazon Elastic File System volume", with a default 5-minute validity after which "you are directed to the Amazon Web Services console sign-in page". Recorded behavior for FOLLOWING a still-valid URL: the request at the presigned `/auth` address hands off (redirect chain) to THIS domain's own Studio host — a host whose first DNS label is `studio-<DomainId>` and whose remaining labels are exactly the presigned host's own zone — rather than to a sign-in challenge or any unrelated host. The final status is not part of the requirement (AWS answers 403 for a correctly authenticated hand-off into a domain with no provisioned Studio app); the per-domain host and the shared zone are.
Emulator: fetching the AuthorizedUrl returns HTTP 200 from the SAME single host the API was reached on, at `/_aws/sagemaker/user-profile/<DomainId>%2F<UserProfileName>/auth?authToken=...` — the auth address serves itself and redirects nowhere, so the final host's first label is not `studio-<DomainId>` and no per-domain Studio address exists. The URL is minted on the request's own endpoint at src/ops/create_presigned_domain_url.rs:317-329 (`crate::state::presigned_session_url`, served by `crate::service::presigned_session`), and the only per-domain Studio address this crate mints is a PATH on that same host (`crate::state::studio_domain_path` / `studio_domain_url`, src/state/domain.rs:97-126). Note also that the announced endpoint in this run was an IP literal, which cannot carry a per-domain label at all; the host and port in the quoted URLs are per-environment values and no part of the requirement — the requirement is the hand-off to a per-domain host inside the presigned host's own zone.
Why: a client that does what this operation exists for — open the AuthorizedUrl to be signed in to Studio — never lands on the domain's own Studio address, so everything keyed off that host (cookie scoping, per-domain allow-lists / VPC-endpoint restrictions, redirect-chain assertions, per-domain session isolation) cannot be exercised, and one shared host answers for every domain and every user profile of the account.
Fix: the presigned-session hand-off — the `/auth` route in `crate::service` (`presigned_session`) must answer a redirect to the domain's own Studio address rather than serving the session itself, and the Studio address this crate publishes must be a host of its own (`studio-<DomainId>` in the same zone as the presigned host) reachable from a client of the emulator, not a path on the shared endpoint.
Traces: sagemaker.deploy-domain-cfn-presigned-url-works.

=== Cause 3 of 3: CreateFeatureGroup accepts an OfflineStoreConfig whose RoleArn cannot access the S3 location, instead of refusing the call ===
AWS: Smithy — CreateFeatureGroup models only ResourceInUse and ResourceLimitExceeded (HTTP 400), so this refusal travels as the service-common `ValidationException` (HTTP 400); `RoleArn` is "the IAM execution role used to persist data into the OfflineStore". Recorded behavior: SageMaker probes the offline-store S3 location WITH that role up front, so the call is refused SYNCHRONOUSLY — HTTP 400, Error.Code `ValidationException`, and the message states the S3 access-denied cause (it contains `AccessDenied` / `not authorized`); the variable parts of that message are the per-call assumed-role session name and the S3 request ids, which is why only the access-denied cause is a requirement and no single recording's text is. Nothing is created: DescribeFeatureGroup for that name answers `ResourceNotFound` with `Resource Not Found: Amazon SageMaker can't find a FeatureGroup with name <FeatureGroupName>`, and after the same role is granted S3 access the IDENTICAL call is accepted and the group reaches `Created`.
Emulator: the call is ACCEPTED — the replay recorded no error at all (`expected ValidationException, got None ()`), i.e. HTTP 200 with a FeatureGroupArn, for a role created with a sagemaker.amazonaws.com trust policy and ZERO permissions against the freshly created bucket. By design the handler resolves `crate::state::offline_store_creation_failure_reason` and accepts the create either way, deferring any failure to the resource's own `FeatureGroupStatus: CreateFailed` (src/ops/create_feature_group.rs:244-261 and 343-348, 371-377) — and in this run it did not even resolve a failure reason for a role with no policies, so the group was admitted as healthy and claimed the name.
Why: this is the overly-permissive direction — a client whose offline store is mis-permissioned is told the feature group was created, the name is claimed, and the error AWS returns at the call site (which is where an application reports it and fails fast) never arrives; IAM/S3 permission boundaries around the FeatureStore offline store cannot be exercised at all.
Fix: CreateFeatureGroup's admission path — the offline-store probe (`crate::state::offline_store_creation_failure_reason`, called from src/ops/create_feature_group.rs:255-261) must refuse the request with HTTP 400 `ValidationException` naming the S3 access-denied cause BEFORE any record is stored or registered in the shared feature-group directory, instead of accepting the create and deferring the failure to `CreateFailed`.
Traces: sagemaker.feature-group-offline-store-permission-denied-create-failed-rejected.
