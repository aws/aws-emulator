# signer-data GetRevocationStatus mishandles the signatureTimestamp query value: well-formed values are refused and malformed ones are refused in the wrong envelope

> _Note: this issue was identified against the code base at commit `5b2a9eedb8fa287cac2318fd09ae07f52de03ab6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRevocationStatus

## Description
TWO net-new root causes on ONE operation of ONE service (signer-data / GetRevocationStatus, GET /revocations, served by services/service-com-amazonaws-signerdata-signerdataplane). Both sit on the same input member — the @httpQuery-bound signatureTimestamp — but they are independent defects in two different components (the request deserializer's accepted timestamp forms, and the envelope a deserialization failure is rendered in), and BOTH must be closed before this issue is submitted. Together they account for all three net-new wire divergence clusters this replay reported for signer-data (16 of the 20 mismatched steps in the corpus).

No open issue covers either cause. The only open issue on this operation, 20261029T230237Z-signer-data-getrevocationstatus-6-net-new-causes-certificatehashes.md, is a behavioral-suite issue about certificateHashes validation, future signatureTimestamp values, authorization and three refusal wordings; it never touches which timestamp FORMS the deserializer accepts, and it never touches the protocol-level envelope of a value that cannot be deserialized at all. 20261108T035301Z-signer-getrevocationstatus-is-never-authorized-...md is about authorization only.

Cause 1 of 2: a well-formed signatureTimestamp query value is refused as unparseable, so the whole request fails before any of the operation's own rules are applied.
AWS: signatureTimestamp is modelled only as `signatureTimestamp` -> Timestamp, @httpQuery "signatureTimestamp", @required (Smithy, com.amazonaws.signerdata#GetRevocationStatus; the member carries no @timestampFormat, and the model's prose says only "The timestamp when the artifact was signed, in ISO 8601 format"). The accepted set is therefore recorded behavior only, and the recording shows AWS DESERIALIZING the value and moving on: with signatureTimestamp supplied in epoch-seconds form, AWS answered the request's OTHER defect — 400 ValidationException with message "1 validation error detected: Value 'short' at 'jobArn' failed to satisfy constraint: Member must have length greater than or equal to 20" (fixed text "1 validation error detected: Value '" ... "' at 'jobArn' failed to satisfy constraint: Member must have length greater than or equal to 20"; the variable parts are the rejected value echoed whole, the wire member name, and the modelled minimum from Arn @length min 20) — and on requests whose every member is valid it answered HTTP 200 with the body {"revokedEntities": []} (GetRevocationStatusResponse.revokedEntities is documented "Empty if no revocations found", so the member is present and empty, never absent).
Emulator: refuses the same requests with HTTP 400 and the message "invalid timestamp `<the query value>`: invalid date-time: Smithy does not support timezone offsets in RFC-3339 date times" — a parser-internal sentence that names the Smithy toolchain, is not AWS wording for any error class, and is emitted for a value AWS accepts. Because the refusal is raised during deserialization, it preempts everything downstream: the modelled member constraints are never evaluated (so the jobArn minimum-length refusal above never surfaces), and valid requests never reach ops/get_revocation_status.rs::handle at all, which is why four otherwise-clean steps get a 400 and no revokedEntities list instead of a 200 and an empty one.
Why: signatureTimestamp is the parameter that decides this operation's answer (a profile revocation covers only signatures made at or after its effectiveTime), and the emulator refuses a serialization of it that AWS accepts. Every client that renders this query parameter that way — an epoch-seconds or offset-bearing RFC-3339 rendering — cannot call the operation AT ALL against the emulator: a revocation check that succeeds on AWS is a hard 400 here, so the emulator fails closed on correct traffic. The knock-on is just as bad for negative paths: a request with a genuinely bad jobArn is told its timestamp is broken, so the caller fixes the wrong parameter.
Fix: the request-deserialization layer for this operation's @httpQuery timestamp binding (the framework timestamp parser the generated GET_REVOCATION_STATUS_INPUT_SCHEMA binding drives for signatureTimestamp) must accept the timestamp forms AWS accepts for this member — epoch seconds and RFC-3339 including a zone offset — and reduce them to the same instant before the boundary validator runs, so that member-constraint refusals (jobArn/profileVersionArn @length, platformId @pattern) are what a request carrying both a valid timestamp and a bad ARN gets. The downstream refusal that must then surface is the "1 validation error detected: ..." sentence quoted above; src/service.rs:148-168 deliberately returns None for every non-list violation so that sentence comes from the shared framework rendering, which is where it has to be correct.
Traces: signer-data-arn-and-platformid-boundary-violations#task#1 (cluster of 12 steps, which also covers signer-data-required-field-validation#task#2..#5 and signerdata-missing-required-members-and-malformed-timestamp-rejected#task#2..#5); signer-data-required-field-validation#task#1 (cluster of 4 steps, which also covers signer-data-signature-timestamp-format-handling#task#1 and #task#2 and signerdata-missing-required-members-and-malformed-timestamp-rejected#task#1).

Cause 2 of 2: a signatureTimestamp that genuinely cannot be converted is refused in the MODELLED error envelope instead of the protocol-level one, with the message dropped entirely.
AWS: recorded behavior only — the model declares no error for an undeserializable value (its four modelled errors are AccessDeniedException 403, InternalServiceErrorException 500, TooManyRequestsException 429, ValidationException 400, each a structure of {message, code}), because the value never becomes a modelled input. The recording shows HTTP 400 whose body carries the text under the CAPITALIZED key "Message" with the value "'not-a-timestamp' can not be converted to Date" — fixed text "'" ... "' can not be converted to Date", the single variable part being the rejected query value echoed verbatim inside single quotes — and whose x-amzn-errortype header does NOT carry "ValidationException" (the recording asserts the header's shape, and "ValidationException" does not match it). A capital-M "Message" with no "code" member is the AWS protocol-level (framework) error envelope, not this service's modelled one, whose member is lowercase "message". Hypothesis: the errortype AWS names here is SerializationException, the standard protocol-level errortype for a query value that cannot be converted to its modelled type; the recording pins the shape and the body, not that literal token.
Emulator: HTTP 400 with x-amzn-errortype: ValidationException and a body carrying NO "Message" member at all — it renders the failure as this service's modelled ValidationException (lowercase message + code, per crate::service::VALIDATION_EXCEPTION_CODE and the ValidationException shape), so a client reading the documented "Message" field of a protocol error gets nothing, and a client switching on x-amzn-errortype is told the request violated a modelled constraint rather than that it was unparseable.
Why: the error code and the message are requirements, and both are wrong here. A malformed timestamp is the single most common way to get this parameter wrong, and the emulator gives the caller neither the error class AWS gives nor any message text: the body it returns has no field the client is looking for, so the caller sees an empty 400 and cannot tell which parameter it must fix. It also mislabels an unparseable request as a constraint violation, which routes it into modelled-error handling that AWS never reaches for this input.
Fix: the deserialization-failure path for this operation must be rendered through the protocol-level error renderer rather than the modelled ValidationException — in this crate that is the override_framework_error / ProtocolError seam in src/service.rs (currently returning None, line 211-223) together with the generated entry's default renderer: emit the protocol errortype in x-amzn-errortype and put the "'<value>' can not be converted to Date" sentence in the body's capital-M "Message" member, with the rejected query value taken from the request.
Traces: signer-data-signature-timestamp-format-handling#task#3 (cluster of 2 steps, which also covers signerdata-missing-required-members-and-malformed-timestamp-rejected#task#7).
