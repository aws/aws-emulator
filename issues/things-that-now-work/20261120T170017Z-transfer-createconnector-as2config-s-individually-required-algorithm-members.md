# Transfer CreateConnector: As2Config's individually-required algorithm members (Compression/EncryptionAlgorithm/SigningAlgorithm) are not validated, and a schemeless Url is refused with the wrong diagnostic

> _Note: this issue was identified against the code base at commit `8345989f6f1c1ad254046c37ef06556dbc8ed377`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConnector

## Description
Two distinct net-new root causes in the transfer emulator's CreateConnector request validation, both grounded in failing behavioral checks of this suite.

=== Cause 1 of 2: CreateConnector accepts an As2Config that is missing one of its individually-required algorithm members ===
AWS: Smithy CreateConnector input takes As2Config -> As2ConnectorConfig; none of that structure's members is marked @required in the model, so the requirement is service-side. Modeled error InvalidRequestException (errorKind client, httpError 400). Recorded behavior: for an AS2 connector, As2Config.Compression, As2Config.EncryptionAlgorithm and As2Config.SigningAlgorithm are each INDIVIDUALLY required — omitting any ONE of them (with every other AS2 member present and valid) is refused with HTTP 400 InvalidRequestException and a diagnostic that NAMES the missing member: the message template is `<MemberName> is required in As2Config`, whose fixed text is " is required in As2Config" and whose only variable part is the member name taken from the request (the member that is absent) — i.e. "Compression is required in As2Config", "EncryptionAlgorithm is required in As2Config", "SigningAlgorithm is required in As2Config". No connector is created by the refused call. Only MdnSigningAlgorithm (defaulted to DEFAULT) and PreserveContentType (defaulted to DISABLED) are service-filled; the three above are not.
Emulator: CreateConnector(Url=<valid https url>, AccessRole=<role arn>, As2Config={LocalProfileId, PartnerProfileId, MdnResponse, EncryptionAlgorithm, SigningAlgorithm}) — i.e. As2Config with Compression omitted — returns HTTP 200 with a ConnectorId (observed body `{"ConnectorId": "c-..."}`, content-type application/x-amz-json-1.1) and creates the connector. The check fails on the first iteration of its missing-member loop, so the generic requirement is absent; a single lumped "As2Config is invalid" message would also diverge, because the diagnostic must name the specific missing member.
Why: a client that relies on the service to validate its AS2 configuration persists a connector with no compression/encryption/signing algorithm settled. On AWS that request is a 400 at provisioning time with the exact member to fix; against the emulator the client gets a ConnectorId, and the AS2 transfer either fails much later or is attempted with algorithms the client never chose. Tests that assert the per-member diagnostic (to surface "you forgot Compression" to a user) get a success instead of an error.
Fix: As2Config cross-member validation in the CreateConnector handler of the transfer service crate (and the same rule on the UpdateConnector path), raising the modeled InvalidRequestException with the per-member message; the ordering must stay after the existing As2Config/SftpConfig exclusivity check and after the Url check, which both already behave correctly in this check's earlier legs.
Traces: transfer.connector-config-exclusivity-and-described-shape.

=== Cause 2 of 2: a Url with no scheme is refused with the generic "The specified Url is not valid" instead of AWS's path-information diagnostic ===
AWS: Smithy CreateConnector.Url -> Url (string, @length 0..255, free-form on the wire), so the scheme/path rule is service-side; modeled error InvalidRequestException (client, 400). Recorded behavior: Transfer distinguishes two Url rejection classes, and both are fixed text with no variable parts. (a) A Url whose host cannot be a real endpoint (e.g. the RFC 2606 `.invalid` TLD, `https://<host>.invalid/as2`) is refused with InvalidRequestException and the message "The specified Url is not valid". (b) A Url that omits the scheme (`ftp.example.com` instead of `sftp://ftp.example.com`) is parsed as pure path information for the configured protocol and is refused with InvalidRequestException and the message "Invalid URL; Configured protocol does not support path information in the url". In both cases no connector is created, and the identical request with `sftp://ftp.example.com` succeeds with DescribeConnector echoing the Url verbatim.
Emulator: CreateConnector(Url="ftp.example.com", AccessRole=<role arn>, SftpConfig={"UserSecretId": <secret arn>}) is refused with the correct code InvalidRequestException but the message "The specified Url is not valid" — class (a)'s text — instead of "Invalid URL; Configured protocol does not support path information in the url". So the emulator collapses both AWS Url rejection classes onto one message; the `.invalid`-host leg of the other check confirms it emits that same string there, where it IS correct.
Why: the error message is the only thing distinguishing "your URL has no scheme / carries path information the protocol cannot use" from "your URL's host is not usable". A client or operator log that branches on, or surfaces, the diagnostic is told the wrong thing to fix, and automated fixtures asserting AWS's wording fail. Note open issue 20261022T202037Z-transfer-input-validation-authorization-and-reference-data-diverge.md describes this operation accepting the schemeless Url outright (HTTP 200); the emulator now refuses it, so that description no longer matches — what remains is this message divergence, and it is not covered by that issue's replay key.
Fix: the Url validation in the CreateConnector handler (and the mirrored rule in UpdateConnector) of the transfer service crate must classify the failure and render the matching modeled InvalidRequestException message, rather than returning one generic string for every malformed Url.
Traces: transfer.create-connector-malformed-url-rejected.

## Evidence
Cause 1 — check transfer.connector-config-exclusivity-and-described-shape.
expected: CreateConnector(Url=<valid https url>, AccessRole=<role>, As2Config={LocalProfileId, PartnerProfileId, MdnResponse:'NONE', EncryptionAlgorithm:'NONE', SigningAlgorithm:'NONE'}) (Compression omitted) -> HTTP 400 ('InvalidRequestException', 'Compression is required in As2Config'); likewise 'EncryptionAlgorithm is required in As2Config' and 'SigningAlgorithm is required in As2Config' when those are the omitted member; no connector created.
actual: HTTP 200, body {'ConnectorId': 'c-00000000000000003'}, content-type application/x-amz-json-1.1 — harness raised AssertionError: "expected the call to be rejected, but it succeeded". (The earlier legs of the same check passed: BOTH configs -> 'Only one of As2Config or SftpConfig must be specified'; NEITHER -> 'One of As2Config or SftpConfig must be specified'; `.invalid` host Url -> 'The specified Url is not valid'.)

Cause 2 — check transfer.create-connector-malformed-url-rejected.
expected: CreateConnector(Url='ftp.example.com', AccessRole=<role arn>, SftpConfig={'UserSecretId': <secret arn>}) -> ('InvalidRequestException', 'Invalid URL; Configured protocol does not support path information in the url').
actual: ('InvalidRequestException', 'The specified Url is not valid') — AssertionError on the message; the error code and the 400 class are correct, only the message diverges. The positive control (Url='sftp://ftp.example.com') is expected to succeed and be echoed by DescribeConnector.

## Steps to Reproduce
1. Boot the emulator and point botocore at its transfer endpoint.
2. Cause 1: transfer.create_profile(As2Id=..., ProfileType='LOCAL') and transfer.create_profile(As2Id=..., ProfileType='PARTNER'); iam.create_role with a transfer.amazonaws.com trust policy. Then for each field in ('Compression','EncryptionAlgorithm','SigningAlgorithm') call transfer.create_connector(Url='https://<host>.example.com/as2', AccessRole=<role arn>, As2Config={'LocalProfileId':<local>,'PartnerProfileId':<partner>,'MdnResponse':'NONE','Compression':'DISABLED','EncryptionAlgorithm':'NONE','SigningAlgorithm':'NONE'} minus that one field). Observe HTTP 200 with a ConnectorId instead of 400 InvalidRequestException '<field> is required in As2Config'.
3. Cause 2: iam.create_role with the same trust policy and secretsmanager.create_secret, then transfer.create_connector(Url='ftp.example.com', AccessRole=<role arn>, SftpConfig={'UserSecretId': <secret arn>}). Observe the ClientError message 'The specified Url is not valid' instead of 'Invalid URL; Configured protocol does not support path information in the url'.
4. For contrast, call transfer.create_connector with Url='https://<host>.invalid/as2' and a complete As2Config: the emulator emits the same 'The specified Url is not valid' string there, which is the correct message for that class only.
