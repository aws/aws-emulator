# CodeDeploy deployments report success without executing: the Lambda alias never moves, traffic shifting and targets are absent, and the service role, S3 revision, agent and per-group exclusion are never enforced (8 causes)

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
A deployment in the emulator is a status field: CreateDeployment accepts the request, the record flips to the terminal status 'Succeeded', and none of the work the status asserts is performed — the Lambda alias is not re-pointed, no traffic-shift ladder exists, no deployment targets are created, the deployment group's service role is never assumed, the S3 revision is never fetched, and nothing fails. Eight independent causes below; each must be closed before submitting.

Cause 1 of 8: a Lambda-platform deployment terminates 'Succeeded' without moving the Lambda alias.
AWS: Smithy DeploymentInfo.status (enum DeploymentStatus: Created, Queued, InProgress, Baking, Succeeded, Failed, Stopped, Ready). Recorded behavior: a Lambda deployment whose AppSpec names a function, an alias, a CurrentVersion and a TargetVersion ends 'Succeeded' only after CodeDeploy has re-pointed that alias to TargetVersion; GetAlias then reports the new version. The reverse (rollback) deployment moves it back by re-pointing the SAME alias — it never publishes a new function version, and it leaves no residual routingConfig behind.
Emulator: GetDeployment reports status 'Succeeded', and GetAlias still reports the ORIGINAL version — the check reads the alias at '1' after a Succeeded deployment whose AppSpec targeted version '2'. The follow-on reverse-deployment check polls the alias and the two deployments' completeTime ordering and never completes.
Why: 'Succeeded' is the signal every CI/CD gate treats as 'the new code is live'. A client (or a human) reads success while production traffic is still served by the old version, and any emulator-backed test of a deploy-then-verify pipeline passes while the deploy did nothing.
Fix: the deployment execution path in the codedeploy service — CreateDeployment's progression must apply the AppSpec's Lambda alias shift against the lambda service state before reporting a terminal status (services/service-com-amazonaws-codedeploy-codedeploy-20141006/src/ops/create_deployment.rs and src/state.rs).
Traces: codedeploy.ignore-poll-alarm-failure-decides-whether-an-unpollable-alarm-stops-the-deployment (direct assertion), codedeploy.deployment-rollback-restores-alias-and-records-both-deployments (never completes while polling for the moved alias).

Cause 2 of 8: time-based traffic shifting is not modeled — a TimeBasedCanary / TimeBasedLinear deployment completes immediately as a single cutover.
AWS: Smithy CreateDeploymentConfig takes trafficRoutingConfig (TrafficRoutingConfig) with timeBasedCanary {canaryPercentage, canaryInterval} / timeBasedLinear {linearPercentage, linearInterval}. Recorded behavior: a deployment using such a config stays non-terminal for the configured interval(s) — status InProgress/Baking — while the alias exposes INTERMEDIATE weights (a 25%-every-1-minute linear shift walks the alias routingConfig through 0.25, 0.5, 0.75 before the full cutover), and only then reaches 'Succeeded'. Because it is non-terminal for that window, StopDeployment is accepted during it.
Emulator: the deployment reaches terminal 'Succeeded' at once. A TimeBasedCanary config with a 5-minute canaryInterval is terminal before the check can call StopDeployment, and the alias exposes no weighted routing at any sample ('the alias exposed [] across samples [("1", ())]').
Why: canary/linear deployments are the reason CodeDeploy exists for Lambda; a client cannot observe or abort a partial shift, StopDeployment/ContinueDeployment and bake-window behavior are unreachable, and the modeled Baking/Ready statuses are never produced.
Fix: the deployment progression/clock in the codedeploy state machine — honour the deployment config's trafficRoutingConfig by holding the deployment non-terminal and writing intermediate alias routingConfig weights.
Traces: codedeploy.lambda-deployment-stop-rolls-back-alias-and-refuses-restop, codedeploy.linear-traffic-shift-walks-the-weight-ladder-over-time.

Cause 3 of 8: a deployment exposes no deployment targets.
AWS: Smithy ListDeploymentTargets(deploymentId required) -> targetIds (TargetIdList) and BatchGetDeploymentTargets(deploymentId, targetIds required) -> deploymentTargets (DeploymentTargetList); both model DeploymentNotStartedException (HTTP 400) for a deployment that has not resolved its targets yet. Recorded behavior: once a Lambda deployment is under way it resolves EXACTLY ONE target (the function/alias), ListDeploymentTargets returns that one targetId, and BatchGetDeploymentTargets returns its lambdaTarget record with the lifecycle events.
Emulator: ListDeploymentTargets returns HTTP 200 with an empty targetIds list for a started (and already Succeeded) deployment — 'expected exactly one target id, got []' and 'deployment d-MW9R1HDCD exposed no deployment targets'.
Why: per-target inspection is the only way to read an individual target's lifecycle events and outcome; with no targets, every lifecycle-event and hook-status workflow is blind, and the empty 200 is indistinguishable from a deployment with nothing to do (AWS would instead answer DeploymentNotStartedException before targets exist).
Fix: target resolution in the deployment state machine, feeding ListDeploymentTargets / BatchGetDeploymentTargets / GetDeploymentTarget from it.
Traces: codedeploy.batch-get-deployment-targets-lambda-target-shape, codedeploy.lifecycle-hook-failed-status-denied-traffic-shift.

Cause 4 of 8: the deployment group's service role is never used, so a role granting no Lambda permissions still deploys.
AWS: recorded behavior (measured us-west-2). A service role CodeDeploy can assume but that grants no Lambda actions is accepted by CreateDeploymentGroup and by CreateDeployment (both HTTP 200); the denial surfaces as the deployment's own outcome — the deployment terminates with errorInformation.code IAM_ROLE_PERMISSIONS (Smithy ErrorCode enum includes IAM_ROLE_PERMISSIONS and IAM_ROLE_MISSING) naming the denied service, and the alias never moves. The identical deployment through a fully permissioned role in the same application shifts the alias.
Emulator: the check does not complete within the suite's 60s per-check cap while polling for that terminal denial; no deployment ever reports errorInformation.code IAM_ROLE_PERMISSIONS. Hypothesis: shares Causes 1/2 — the deployment is marked Succeeded without ever assuming the role or calling Lambda, so the state the check polls for cannot arrive. (On real AWS this check's three AllAtOnce deployments measured ~5s each, well inside the cap.)
Why: CodeDeploy acts on the customer's behalf, so this is the over-permissiveness boundary that matters most — an emulator that never assumes the service role shifts traffic with a role that grants nothing, exactly the misconfiguration a customer then meets for the first time in production.
Fix: the deployment execution path — resolve the deployment group's serviceRoleArn against the IAM service state and fail the deployment with errorInformation.code IAM_ROLE_PERMISSIONS when the required action is not granted.
Traces: codedeploy.deployment-service-role-without-lambda-permission-denied-and-alias-unmoved.

Cause 5 of 8: an S3 revision is never fetched, so neither its eTag nor its contents affect the deployment.
AWS: Smithy RevisionLocation / S3Location (bucket, key, bundleType, eTag, version). Recorded behavior: an eTag that does not match the stored object is NOT refused by CreateDeployment (HTTP 200 with a deploymentId) — the deployment is accepted and then terminates with errorInformation.code INVALID_REVISION (Smithy ErrorCode enum includes INVALID_REVISION), because the eTag is part of the object's identity and the AppSpec is therefore unlocatable, and the alias stays exactly where it was. With the real eTag the same object deploys, and the AppSpec bytes IN that object decide which alias version is targeted.
Emulator: neither check completes within the 60s cap while polling for those outcomes; no INVALID_REVISION terminal deployment is produced and the alias is not driven by the object's contents. Hypothesis: shares Causes 1/2 — the revision is stored as an opaque document and never resolved against the s3 service state. (On real AWS these checks' deployments measured ~5s each.)
Why: a client's only protection against deploying the wrong artifact is that CodeDeploy verifies the revision's identity; here any bucket/key/eTag triple 'succeeds', so a deployment of a bundle that does not exist is reported as a success.
Fix: revision resolution in the deployment execution path — fetch the S3 object (honouring eTag/version as part of its identity), parse the AppSpec from its bytes, and fail the deployment with INVALID_REVISION when it cannot be located.
Traces: codedeploy.s3-revision-etag-mismatch-rejected-and-alias-unmoved, codedeploy.s3-revision-object-contents-decide-alias-target.

Cause 6 of 8: a Server / on-premises deployment with no live CodeDeploy agent terminates 'Succeeded' instead of 'Failed'.
AWS: recorded behavior. An on-premises deployment whose registered hosts run no agent cannot complete its lifecycle events, so the deployment reaches the terminal status 'Failed' (or 'Stopped'); DeploymentInfo.errorInformation carries the reason.
Emulator: GetDeployment reports terminal status 'Succeeded' (assertion: `assert final["status"] in ("Failed", "Stopped")` -> 'Succeeded').
Why: the full on-premises flow — register host, tag it, deploy, observe the outcome — reports success for a deployment no host ever ran, so a client cannot distinguish a working fleet from an absent one. Note the fixed issue 20261022T171541Z-codedeploy-deployment-lifecycle-response-normalization-and-error-classification.md claimed the same class in its Cause 1 (zero-instance deployment must end Failed); that call is not refused, it simply still ends Succeeded for the on-premises path.
Fix: the deployment state machine's terminal-status decision for the Server/on-premises compute platform (no reachable agent / no instance ever reports a lifecycle event => Failed with errorInformation).
Traces: codedeploy.e2e-onprem-deployment-full-flow.

Cause 7 of 8: a deployment group admits any number of simultaneous non-terminal deployments.
AWS: Smithy CreateDeployment models DeploymentLimitExceededException (HTTP 400). Recorded behavior: a deployment group holds AT MOST ONE non-terminal deployment — of several CreateDeployment calls released simultaneously against one group exactly one is accepted and the rest are refused with DeploymentLimitExceededException (not queued, not run in parallel); once the winner is terminal the group accepts work again.
Emulator: all five concurrent CreateDeployment calls are accepted, returning five distinct deploymentIds against one deployment group.
Why: the mutual exclusion is the service's core concurrency contract; a client relying on it (or on the refusal to serialise its own pipeline) gets several deployments mutating the same alias at once, and the modeled refusal is unreachable.
Fix: CreateDeployment's precondition against the deployment group's current non-terminal deployment, enforced atomically in the codedeploy state.
Traces: codedeploy.concurrent-create-deployment-one-wins-rest-rejected.

Cause 8 of 8: ListOnPremisesInstances still lists an instance after DeregisterOnPremisesInstance.
AWS: Smithy ListOnPremisesInstances takes the optional registrationStatus (enum RegistrationStatus) and returns instanceNames; DeregisterOnPremisesInstance removes the host's registration. Recorded behavior: after a successful deregistration the host no longer appears in the default (unfiltered) ListOnPremisesInstances listing, while other registered hosts still do.
Emulator: the deregistered instance is still returned by ListOnPremisesInstances (observed listing contains both the deregistered host and the untouched control host).
Why: fleet inventory built on this listing counts hosts AWS no longer reports, so deregistration appears to have had no effect and clean-up/reconciliation loops never converge.
Fix: the on-premises instance store — have DeregisterOnPremisesInstance update the registration state that ListOnPremisesInstances' default listing and its registrationStatus filter read.
Traces: codedeploy.e2e-on-premises-instance-tag-and-deploy.
