# wafv2 logging surface: PutLoggingConfiguration accepts a destination whose log-group name lacks the aws-waf-logs- prefix, and an accepted destination never yields a sampled request or a delivered log record (2 causes)

> _Note: this issue was identified against the code base at commit `13cd51356c86db6d039912819137db7f55e61de7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutLoggingConfiguration

## Description
Two net-new root causes in the wafv2 logging surface, both grounded in wafv2-token behavioral checks that the suite marked neither ALREADY FILED nor OWNED.

Related open issues that do NOT cover these: 20261026T010229Z-apigateway-logs-wafv2-waf-logging-is-now-accepted.md describes the unprefixed-destination accept and the missing CloudWatch-Logs delivery under the apigateway__logs__wafv2 token only, and it explicitly states that the refusal MESSAGE for that path was not asserted there; Cause 1 below adds WAF's own sentence as the requirement and is reached through plain wafv2 calls with no API Gateway edge involved. 20261025T092822Z-apigateway-logs-wafv2-putloggingconfiguration-answers-notimplemented-so-waf.md and 20261024T065754Z-wafv2-putloggingconfiguration-stub.md describe the older 501/NotImplemented mode, which no longer reproduces (the operation now answers 200). Nothing filed describes an S3 destination or GetSampledRequests, which is Cause 2.

Cause 1 of 2: PutLoggingConfiguration accepts a LogDestinationConfigs entry whose CloudWatch Logs log-group name does not begin with 'aws-waf-logs-'.
Failing check: wafv2.logging-configuration-invalid-destination-name-rejected
AWS: WAF validates the destination NAME, not only ARN syntax — a logging destination must be named with the 'aws-waf-logs-' prefix, and a destination that is not is refused as a client error before anything is stored. Smithy (services/service-com-amazonaws-wafv2-awswaf-20190729/smithy-model/com-amazonaws-wafv2-awswaf-20190729.json): PutLoggingConfiguration input LoggingConfiguration (required), member LogDestinationConfigs ("The logging destination configuration that you want to associate with the web ACL... You can associate one logging destination to a web ACL"); modeled errors include WAFInvalidParameterException (errorKind client, httpError 400, with members Field/Parameter/Reason — doc: "Your request references an ARN that is malformed, or corresponds to a resource with which a web ACL can't be associated") and WAFNonexistentItemException (client, 400). The recorded refusal for this class is HTTP 400, Error.Code 'WAFInvalidParameterException', Error.Message "Error reason: The ARN isn't valid. A valid ARN begins with arn: and includes other information separated by colons or slashes., field: LOG_DESTINATION, parameter: <submitted destination ARN>". In that message everything up to and including 'parameter: ' is fixed text (note the Reason clause, the 'field: LOG_DESTINATION' naming of WAFInvalidParameterException.Field, and the comma-space separators); the only variable part is the destination ARN echoed verbatim from LoggingConfiguration.LogDestinationConfigs in the request. Nothing is persisted, so a subsequent GetLoggingConfiguration on the same web ACL must answer HTTP 400 WAFNonexistentItemException with WAF's not-found sentence ("AWS WAF couldn\u2019t perform the operation because your resource doesn\u2019t exist.", curly apostrophe).
Emulator: the call SUCCEEDS. The replay shows HTTPStatusCode 200 and a body echoing the rejected configuration — LogDestinationConfigs carrying the unprefixed log-group ARN, plus ManagedByFirewallManager=false, LogType=WAF_LOGS, LogScope=CUSTOMER — so the 400/WAFInvalidParameterException pair and its message are never produced, and the configuration AWS would have refused is stored (the later GetLoggingConfiguration leg can therefore no longer reach WAFNonexistentItemException). The check's positive control in the same run proves the only difference is the prefix: the identical call shape with an 'aws-waf-logs-' group is accepted and round-trips.
Why: the 'aws-waf-logs-' prefix is the contract that log-delivery permissions, subscription filters and metric filters are written against. A client that typos or omits it is told at configuration time by AWS; against the emulator it is told nothing, stores a configuration AWS would never have stored, and later sees no records — a silent logging outage instead of a 400. Negative tests asserting the refusal pass against a permissive target.
Fix: the validation stage of the wafv2 PutLoggingConfiguration handler — parse every LoggingConfiguration.LogDestinationConfigs ARN and, for a CloudWatch Logs log-group destination, require the group name to begin with 'aws-waf-logs-', refusing with HTTP 400 WAFInvalidParameterException (Field=LOG_DESTINATION, Parameter=<the submitted ARN>) and WAF's sentence above BEFORE any state is written, so GetLoggingConfiguration still answers WAFNonexistentItemException afterwards.
Traces: wafv2.logging-configuration-invalid-destination-name-rejected (mismatch).

Cause 2 of 2: with logging accepted against an S3 destination and a Count-rule web ACL associated with a deployed API Gateway stage, neither a sampled request nor a delivered log record is ever observable, so the check cannot complete and exhausts the 60 s cap.
Failing check: wafv2.e2e-logging-configuration-capture-flow
AWS: a REGIONAL web ACL associated with a REST stage inspects each request; a rule whose VisibilityConfig has SampledRequestsEnabled=true makes matching requests retrievable through GetSampledRequests for that rule's MetricName within the requested TimeWindow, and an enabled logging configuration delivers one JSON record per inspected request to the configured destination. Smithy: GetSampledRequests input WebAclArn/RuleMetricName/Scope/TimeWindow/MaxItems (all required) and output SampledRequests (list of SampledHTTPRequest, whose Action member is "The action that WAF applied to the request") plus PopulationSize; GetLoggingConfiguration/DeleteLoggingConfiguration are modelled with WAFNonexistentItemException (client, 400). For the asynchronous S3 delivery itself this is recorded behavior only: the check's measurement notes delivery takes well over a minute on real AWS and batches newline-delimited JSON records into gzip objects, each record carrying httpRequest.headers and, for a Count rule, the rule listed under nonTerminatingMatchingRules with action COUNT. After DeleteLoggingConfiguration, GetLoggingConfiguration must answer HTTP 400 WAFNonexistentItemException with the not-found sentence quoted in Cause 1.
Emulator: the check never completes — the replay reports 'Check timed out after 60.0s'. Its only unbounded work is the two bounded polls that keep driving fresh matching traffic through the associated stage: GetSampledRequests for the rule's metric, and a ListObjectsV2/GetObject poll of the configured S3 destination for a record naming the sampling marker header. Neither converges, so the emulator produced no sampled request for a matched rule and no delivered log record for an accepted destination; the post-delete 404 leg is never reached either. Hypothesis: the association is accepted but the data plane neither samples nor delivers, consistent with the already-filed edge-enforcement issues for the apigateway__wafv2 and cloudwatch__wafv2 tokens.
Why: GetSampledRequests and the delivered log records are the only evidence a client has of what a web ACL did. An emulator that accepts PutLoggingConfiguration with a 200 and then produces nothing tells a client logging is on while leaving it with no audit trail, no per-rule attribution and no way to distinguish 'no traffic matched' from 'nothing is wired up'; the same silence makes the stored LogDestinationConfigs unverifiable.
Fix: the wafv2 request-sampling store and log-delivery path, plus the web-ACL enforcement hook at the associated API Gateway stage — an inspected request matching a rule with SampledRequestsEnabled must become retrievable through GetSampledRequests keyed by that rule's MetricName and the requested TimeWindow with Action reflecting the rule action, and an enabled logging configuration must write a record per inspected request to the configured destination (for an S3 destination, gzip newline-delimited JSON whose httpRequest.headers reproduce the request headers and whose nonTerminatingMatchingRules names a Count rule with action COUNT). DeleteLoggingConfiguration must then make GetLoggingConfiguration answer WAFNonexistentItemException again.
Traces: wafv2.e2e-logging-configuration-capture-flow (mismatch, timed out at the 60 s cap).
