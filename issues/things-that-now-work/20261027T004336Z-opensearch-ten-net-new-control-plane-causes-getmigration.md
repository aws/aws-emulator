# opensearch: ten net-new control-plane causes — GetMigration/ListMigrations/DescribeDataSourceAttachment answer 501, GetPackageVersionHistory and AttachDataSource enforce no IAM, PutDefaultApplicationSetting/CreateDomain/UpdateVpcEndpoint accept input AWS refuses

> _Note: this issue was identified against the code base at commit `88eb145164ed6e7175261f755ebef46622c173d0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMigration

## Description
Ten net-new root causes in the OpenSearch Service control plane, all grounded in surviving behavioral checks of the `opensearch` service (every other opensearch failure in this run was marked ALREADY FILED or OWNED and was skipped). All ten share the service token `opensearch` and one gate verdict, so they are bundled here. A fixer must close ALL TEN before submitting.

=== Cause 1 of 10: GetMigration answers 501 NotImplemented, so its authorization refusal never happens ===
AWS: Smithy: `GetMigration` is `GET /2021-01-01/opensearch/app-migrations/{migrationId}` with required `migrationId` (httpLabel) and models AccessDeniedException (HTTP 403), ResourceNotFoundException (HTTP 409), ValidationException (HTTP 400), DisabledOperationException (HTTP 409), InternalException (HTTP 500). The ordering of the permission check relative to the existence check is recorded behavior only: the recording shows the permission check running FIRST — a principal with zero opensearch permissions naming a migrationId that does not exist is refused `AccessDeniedException`/403, while the SAME nonexistent migrationId under a fully authorized caller resolves to `ResourceNotFoundException`. The denial message's fixed text is `User: `, ` is not authorized to perform: es:GetMigration on resource: `, and either ` because no identity-based policy allows the es:GetMigration action` (no allow) or ` with an explicit deny in an identity-based policy` (explicit Deny); its variable parts are the caller's principal ARN (from the signing credentials) and the resource ARN `arn:aws:opensearch:<region>:<account-id>:application/*`, whose region and account come from the request context — never the literal ARN of one recorded run.
Emulator: answers `NotImplemented` (501) for GetMigration, so neither the denial nor the not-found refusal is ever produced. Both checks fail with `expected AccessDeniedException, got NotImplemented`.
Why: a client cannot distinguish "you may not read this migration" from "this migration does not exist" from "this API is unavailable"; IAM-scoped access to the migration read is entirely unenforced and unobservable, and a caller that retries on 501 retries forever.
Fix: implement the GetMigration handler and its authorization-before-lookup ordering (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/get_migration.rs), raising the modeled AccessDeniedException before the migrationId is resolved and ResourceNotFoundException afterwards. Note the open issue 20261025T020249Z-opensearch-control-plane-startdomainmaintenance-and-canceldomainconfigchange-answer-notimplemented.md covers other NotImplemented control-plane ops but carries neither of these replay keys nor this operation.
Traces: opensearch.access-denied-precedes-not-found, opensearch.get-migration-without-permission-denied.

=== Cause 2 of 10: ListMigrations answers 501 NotImplemented instead of a specific documented refusal ===
AWS: Smithy: `ListMigrations` is `GET /2021-01-01/opensearch/app-migrations` with required `applicationId` (httpQuery, pattern `^[a-z0-9]{3,30}$`) and models AccessDeniedException (403), DisabledOperationException (409), ValidationException (400), InternalException (500) — notably NOT ResourceNotFoundException. Recorded behavior: against a well-formed but nonexistent applicationId the service answers one of its own specific documented codes (DisabledOperationException when the feature is off for the account/region, otherwise a specific not-found/validation refusal) and never a generic envelope.
Emulator: answers `NotImplemented` (501). The check fails with `unexpected ListMigrations error when the feature is enabled: NotImplemented`.
Why: this operation is the documented canary for the account/region feature-entitlement state that AssociatePackages, DetachDataSource and UpdateVpcEndpoint share, so a client cannot discover whether the migration feature is enabled at all, and the uniformity requirement across those four operations cannot hold.
Fix: implement the ListMigrations handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/list_migrations.rs) so a nonexistent applicationId yields one of the operation's modeled client errors rather than 501.
Traces: opensearch.disabled-operation-feature-off-unreachable.

=== Cause 3 of 10: DescribeDataSourceAttachment answers 501 NotImplemented, collapsing three distinct refusal classes ===
AWS: Smithy: `DescribeDataSourceAttachment` is `POST /2021-01-01/opensearch/application/{id}/describeDataSourceAttachment` with required `id` (pattern `^[a-z0-9]{3,30}$`) and `dataSourceArn` (@length 20..2048), modeling AccessDeniedException (403), ResourceNotFoundException (409), ValidationException (400), DisabledOperationException (409). The model documents ResourceNotFoundException for "no attachment record exists for the specified application and data source combination"; the recording shows that refusal carrying the message whose fixed text is `Data source attachment not found for application ` and ` and data source `, with the application id and the data source ARN taken verbatim from the request. An `id` that violates the documented application-id shape is refused ValidationException at the input-validation layer before any lookup, and an unauthorized caller is refused AccessDeniedException with fixed text `User: `, ` is not authorized to perform: es:DescribeDataSourceAttachment on resource: `, ` because no identity-based policy allows the es:DescribeDataSourceAttachment action` and resource `arn:aws:es:<region>:<account-id>:domain/*`.
Emulator: answers `NotImplemented` (501) for every one of those three inputs. The checks fail with `expected ResourceNotFoundException for a well-formed but nonexistent attachment, got 'NotImplemented'` and `expected AccessDeniedException, got NotImplemented`.
Why: all three genuinely different failure classes (not found, malformed id, not permitted) read identically to a client, and no code or status it is documented to branch on is ever sent.
Fix: implement the DescribeDataSourceAttachment handler, its input validation and its lookup (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/describe_data_source_attachment.rs), keeping validation before lookup and authorization before both.
Traces: opensearch.describe-data-source-attachment-not-found-vs-malformed-id-distinct, opensearch.access-denied-precedes-not-found.

=== Cause 4 of 10: RegisterCapability never validates capabilityName against the one reserved identifier ===
AWS: Smithy: `RegisterCapability` requires `capabilityName` (@length 3..30, pattern `^[a-zA-Z0-9-]+$`) and `capabilityConfig`, and models ValidationException (400), ConflictException (409), ResourceNotFoundException (409), ServiceQuotaExceededException (402). The reserved-value rule is recorded behavior only: a capabilityName that satisfies the modeled length and pattern but is not the fixed identifier `ai-capability` is refused `ValidationException` with the message whose fixed text is `Invalid capability name for AI Capability: `, `. Only ai-capability is allowed` and whose variable part is the rejected name from the request; no capability record is created, so a following `GetCapability` for that name answers ResourceNotFoundException with fixed text `Capability `, ` not found for application ` and the rejected name plus the application id as values.
Emulator: answers `NotImplemented` (501) for RegisterCapability, so the reserved-name rule is unenforced. The check fails with `expected ValidationException for invalid capability name, got 'NotImplemented'`.
Why: a caller is told nothing about why the registration failed, and once the operation is stood up it will accept arbitrary names unless this specific value rule is implemented alongside it.
Fix: the RegisterCapability handler and its capabilityName validation (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/register_capability.rs). An ALREADY-FILED stub issue covers standing the operation up at all; this cause adds the net-new value rule and refusal message, plus the GetCapability not-found message, which that stub issue does not carry.
Traces: opensearch.capability-invalid-name-rejected.

=== Cause 5 of 10: PutDefaultApplicationSetting accepts a nonexistent applicationArn (200) instead of refusing it ===
AWS: Smithy: `PutDefaultApplicationSetting` is `PUT /2021-01-01/opensearch/defaultApplicationSetting` with required `applicationArn` (@length 20..2048) and `setAsDefault`, and models ResourceNotFoundException (HTTP 409), ValidationException (400), AccessDeniedException (403). Recorded behavior: a well-formed applicationArn for which no application exists is refused `ResourceNotFoundException` with the message whose fixed text is `Application not found for ARN: ` followed by the ARN taken verbatim from the request, and the account's live default is left untouched (an independent GetDefaultApplicationSetting still reports the previous value).
Emulator: answers HTTP 200 and echoes the bogus `applicationArn` back, designating a nonexistent application as the account default. The check fails with `real AWS rejects this call, but it SUCCEEDED and returned {... 'applicationArn': 'arn:aws:es:<region>:<account>:application/app-0000...'}`.
Why: an account-level singleton is silently pointed at a resource that does not exist; every later GetDefaultApplicationSetting reports a dangling ARN, and a client that relies on the refusal to validate its input never learns the ARN was wrong.
Fix: the existence check in the PutDefaultApplicationSetting handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/put_default_application_setting.rs), which must resolve the ARN against the application store and raise the modeled ResourceNotFoundException before writing the setting.
Traces: opensearch.default-application-setting-managed.

=== Cause 6 of 10: GetPackageVersionHistory performs no IAM authorization check — an unprivileged principal gets 200 and the full history ===
AWS: Smithy: `GetPackageVersionHistory` is `GET /2021-01-01/packages/{PackageID}/history` and models AccessDeniedException (HTTP 403) among its errors. Recorded behavior: a principal with no identity-based permission on the package is refused `AccessDeniedException` even though the package genuinely exists — "you may not see this" is a different refusal than "this does not exist" (a PackageID that does not exist is refused with a `Package not found.` message instead). The denial message's fixed text is `User: `, ` is not authorized to perform: es:GetPackageVersionHistory on resource: `, ` because no identity-based policy allows the es:GetPackageVersionHistory action`, with the caller's principal ARN and the resource ARN `arn:aws:es:<region>:<account-id>:domain/*` as values from the request context.
Emulator: answers HTTP 200 with the complete `PackageVersionHistoryList` to the zero-permission / explicitly-denied caller. Both checks fail with `expected a ClientError, but the call succeeded: {... 'PackageVersionHistoryList': [{'PackageVersion': '1', ...}]}`.
Why: package metadata is readable by any principal that can reach the endpoint, so the emulator is overly permissive on a real authorization boundary; a client (or a test of least-privilege policy) that depends on the 403 sees success and concludes an unprivileged role is authorized.
Fix: the authorization layer in front of the GetPackageVersionHistory handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/get_package_version_history.rs), evaluating the caller's identity-based policy for `es:GetPackageVersionHistory` before the package is read. Compare the sibling open issue 20261025T163435Z-opensearch-updateindex-performs-no-iam-authorization-check-a.md, which records the same missing-authorization class for UpdateIndex but carries neither of these replay keys nor this operation.
Traces: opensearch.get-package-version-history-access-denied-cross-account, opensearch.get-package-version-history-cross-account-denied.

=== Cause 7 of 10: AttachDataSource answers 501 NotImplemented, so its authorization refusal is unreachable ===
AWS: Smithy: `AttachDataSource` is `POST /2021-01-01/opensearch/application/{id}/attachDataSource` with required `id` and `dataSourceArn`, and models AccessDeniedException (403), ValidationException (400), ResourceNotFoundException (409), ConflictException (409). Recorded behavior: a caller with no opensearch permissions is refused `AccessDeniedException` with fixed text `User: `, ` is not authorized to perform: es:AttachDataSource on resource: `, ` because no identity-based policy allows the es:AttachDataSource action` and the assumed-role principal ARN plus `arn:aws:es:<region>:<account-id>:domain/*` as values, and the denied call creates no attachment record (ListDataSourceAttachments shows none). A fully permitted caller passes authorization and is accepted asynchronously — status `PENDING` — even when the named domain does not exist, and that attachment then settles non-ATTACHED rather than being refused synchronously.
Emulator: answers `NotImplemented` (501) for AttachDataSource, so both the denial and the asynchronous-accept control are unreachable. Both checks fail with `expected AccessDeniedException ..., got NotImplemented`.
Why: a client cannot tell an authorization failure from an unavailable API, and the authorization boundary on a mutating operation is entirely unenforced.
Fix: the authorization check in the AttachDataSource handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/attach_data_source.rs), which must deny before any state is touched and otherwise mint a PENDING attachment. An ALREADY-FILED stub issue covers standing the operation up; this cause adds the net-new IAM-denial requirement and its message rule, which that stub issue does not carry.
Traces: opensearch.overly-permissive-attach-data-source-missing-role-rejected, opensearch.overly-permissive-data-source-attach-unauthorized-role-rejected.

=== Cause 8 of 10: CreateDomain accepts UltraWarm on an instance family that does not offer it ===
AWS: Smithy: `CreateDomain` takes `ClusterConfig` with `WarmEnabled`/`WarmType`/`WarmCount`; which instance families offer warm storage is not stated by the model, so this is recorded behavior only. The recording shows AWS refusing a warm tier whose hot-tier instance type is a burstable family with `ValidationException` and the message whose fixed text is `Warm storage is not available for the ` and ` instance type. Select a different instance type.`, with the rejected instance type taken verbatim from the request's ClusterConfig; the refused create provisions no cluster. The emulator already answers the neighbouring rules in this same chain correctly (cold-storage-without-UltraWarm as `BaseException` / `To use cold storage, you must have UltraWarm enabled.`, and warm-without-dedicated-masters as ValidationException / `To use warm storage, your domain must have dedicated master nodes.`), which is why the check reaches this third rule before failing.
Emulator: accepts the request with HTTP 200 and creates the domain. The check fails with `UltraWarm on an unsupported instance family: CreateDomain should have been rejected but succeeded with DomainId=<account>/<domain-name>`.
Why: each broken link in the tier chain has its own diagnosis, and this one is a cost constraint: warm nodes are separately billed, so a topology real AWS refuses becomes a surprise bill or an un-deployable template the moment it is promoted out of the emulator.
Fix: the warm-tier validation in the CreateDomain handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/create_domain.rs and the instance-family capability table in src/state.rs), which must consult the same warm-storage capability data `DescribeInstanceTypeLimits` reports rather than one global instance-type list.
Traces: opensearch.overly-permissive-storage-tier-dependency-rules.

=== Cause 9 of 10: UpdateVpcEndpoint accepts more SecurityGroupIds than an ENI can carry ===
AWS: Smithy: `UpdateVpcEndpoint` requires `VpcEndpointId` (pattern `^aos-[a-zA-Z0-9]*$`) and `VpcOptions`, and models ValidationException (HTTP 400); `VPCOptions.SecurityGroupIds` carries no modeled cardinality bound, so the ceiling is the account's own adjustable security-groups-per-network-interface quota and the rule is recorded behavior only. The recording shows a VpcOptions one group past that quota refused with `ValidationException`, the endpoint keeping exactly its original `SecurityGroupIds` (read back through DescribeVpcEndpoints, not from the refused call), and a subsequent well-formed update on the same endpoint still succeeding.
Emulator: answers HTTP 200 with `Status: UPDATING` and persists the over-quota list. The check fails with `expected rejection, but the call succeeded and returned {... 'VpcOptions': {'SubnetIds': [...], 'SecurityGroupIds': [six groups]}, 'Status': 'UPDATING' ...}`.
Why: a configuration no ENI can carry is accepted and reported back as the endpoint's live state, so a client believes it attached security groups that could never exist in AWS.
Fix: the VpcOptions cardinality validation in the UpdateVpcEndpoint handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/update_vpc_endpoint.rs), checked against the account's security-groups-per-ENI quota rather than a hardcoded number, and leaving the stored endpoint untouched on refusal.
Traces: opensearch.update-vpc-endpoint-out-of-range-config-rejected.

=== Cause 10 of 10: UpdateVpcEndpoint accepts a subnet from a different VPC than the endpoint's ===
AWS: Smithy: `UpdateVpcEndpoint` models ValidationException (HTTP 400). An endpoint's `VpcOptions.VPCId` is fixed at creation, so recorded behavior is that a `VpcOptions` whose subnet belongs to a different VPC than the endpoint's security group / stored VPC is refused with `ValidationException`, the endpoint's `SubnetIds` are left unchanged, and the same update with a subnet from the SAME VPC is accepted.
Emulator: issues no error at all — the check's error-code probe returns `None`, i.e. the cross-VPC update was accepted. The check fails with `expected ValidationException, got None`.
Why: the invariant that an endpoint cannot move between VPCs is unenforced, and a client can believe it relocated an endpoint into a VPC where its ENI could not exist. This is the rule the open issue 20261025T124157Z-opensearch-six-net-new-control-plane-causes-describedomainhealth.md describes as its cause 6, but there it was never reached (that check timed out in setup and CreateVpcEndpoint was still a stub); the call is now served and is observably accepting the input, under a different check and replay key than that issue carries.
Fix: validate `VpcOptions.SubnetIds` against the endpoint's stored VPCId in the UpdateVpcEndpoint handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/update_vpc_endpoint.rs), resolving each subnet's VPC through the EC2 state rather than trusting the request.
Traces: opensearch.update-vpc-endpoint-invalid-subnet-rejected.
