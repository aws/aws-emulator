# network-security-manager policy validation and scope read path diverge: 3 causes — CreatePolicy accepts a WAF policy with no associations, its resourcesCleanUp field message drops AWS's sentence period, and GetScope's miss path answers 200

> _Note: this issue was identified against the code base at commit `10bb3ab49cc19973576b0028b7945e9506b7aea9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Three net-new divergence clusters in the Network Security Manager (com.amazonaws.networksecuritymanager#PiccoloCustomerAPIService, restJson1) POLICY-validation and SCOPE-read surfaces, observed replaying the simparity-wire-aws-v1 wire corpus against the emulator built from this checkout (emulator_up true, /__admin/health 200, 8 fixtures, 55 steps, 20 passed, score 36.4%). All three clusters report stub_path "" and owned_by [], i.e. no filed issue carries their replay key. They share one fault: the request the service must refuse is not refused in AWS's words or not refused at all, and a resource that must no longer resolve still resolves — the emulator's refusal/miss path does not state what AWS states.

Related open issues, none of which owns any cause here: '20261118T031240Z-network-security-manager-rule-read-path-and-response.md' owns the GetRule miss path and the non-ARN ruleIdentifier refusal (the replay names it as owner of those clusters, not of these); '20261118T134137Z-network-security-manager-template-read-path-and-response.md' owns the same miss-path clause on the TEMPLATE entity and carries only template replay keys, so the SCOPE step below is exercised by nothing it names. A fixed issue about CreatePolicy's WAF validation ('...create-entity-operations-diverge-3') does not cover Cause 1: the replay reports owned_by [] for it and the behavior is still divergent at this commit.

=== Cause 1 of 3: CreatePolicy accepts a WAF policy whose associatedTemplateAndRuleList carries no template or rule — HTTP 201 with a created policy instead of the modeled 400 ValidationException ===
AWS: Smithy model com.amazonaws.networksecuritymanager#CreatePolicy — POST /policies, success @http code 201. Input member associatedTemplateAndRuleList (TemplateAndRuleReferenceList, @length 0..100) is documented "The templates and rules to associate with the policy. For AWS WAF policies, specify 1 to 100 templates or rules, of which at most 2 can be templates. For AWS Shield Advanced policies, this list must be empty." firewallType is @required PolicyFirewallType (WAF | SHIELD_ADVANCED). The minimum of one association for a WAF policy is a prose rule no constraint trait expresses, so the SERVICE enforces it: modeled error ValidationException (@error client, @httpError 400, documented "The request failed validation. For details, see the reason and fieldList members of the response.") with @required message, reason (ValidationExceptionReason, one of ACCOUNT_NOT_ONBOARDED | FIELD_VALIDATION_FAILED | OTHER) and fieldList (ValidationExceptionField { name required, message required }). The recorded AWS response for a WAF CreatePolicy with an empty association list is HTTP 400 with an x-amzn-errortype header naming the error shape, reason "FIELD_VALIDATION_FAILED", message "associatedTemplateAndRuleList is required for WAF policies" and one fieldList entry { name: "associatedTemplateAndRuleList", message: "associatedTemplateAndRuleList must contain at least one template or rule when firewallType is WAF." }. All of that is fixed text for this error class except the firewall type, which is the firewallType the request sent, and the member name, which is the model's.
Emulator: answers HTTP 201 and mints the policy. The replay reports `status: expected 400, got 201`, `$.fieldList: missing`, `$.message: missing`, `$.reason: missing (expected 'FIELD_VALIDATION_FAILED')` and `$headers.x-amzn-errortype: missing`. The rule is deliberately skipped: crate::state::association_list_violation only refuses a non-empty list on SHIELD_ADVANCED, more than MAX_ASSOCIATED_TEMPLATES templates, and a non-ARN identifier, and its own doc comment states the WAF minimum "is deliberately not enforced".
Why: a client that relies on AWS refusing an incomplete WAF policy instead gets a 201 and a policy id for a policy AWS would never have created, so the emulator's state diverges permanently from what the same calls produce on AWS: later reads, ListPolicies pages and association updates all see a policy that cannot exist. Negative tests asserting ValidationException/FIELD_VALIDATION_FAILED pass on AWS and fail here, and a caller never sees the member name that tells it what to fix.
Fix: CreatePolicy's validation — the WAF-minimum clause missing from crate::state::association_list_violation (shared with UpdatePolicy), which must return the message, reason FIELD_VALIDATION_FAILED and the single associatedTemplateAndRuleList fieldList entry above; the handler already lifts that into the modeled ValidationException.
Traces: network-security-manager-policy-validation#task#3.

=== Cause 2 of 3: the resourcesCleanUp refusal's fieldList message omits the sentence-final period AWS sends ===
AWS: same operation and the same modeled ValidationException shape; ValidationExceptionField.message is documented "A message describing the validation error for the field." For a policyConfiguration whose resourcesCleanUp is false, the recorded AWS response is HTTP 400 with reason FIELD_VALIDATION_FAILED and one fieldList entry whose name is the member's dotted path and whose message is the complete sentence "resourcesCleanUp must be true." — a full sentence terminated by a period, the same wording style every other fieldList message in this service's recordings uses. The fixed text is the whole sentence; the only variable part is the member name, taken from the request's policyConfiguration.
Emulator: emits "resourcesCleanUp must be true" (no terminating period) for $.fieldList[0].message. The replay reports `$.fieldList[0].message: value_mismatch (expected 'resourcesCleanUp must be true.', got 'resourcesCleanUp must be true')`; the 400 status, the reason, the top-level message and the entry's name all match. The text comes from crate::state::resources_clean_up_violation, which formats one string without a period and reuses it for BOTH the top-level message and the fieldList entry, although the recording shows the two differ exactly by that period.
Why: the error message is part of the contract. A client that matches, logs or displays the per-field message sees a different sentence than AWS sends, and a test asserting AWS's exact field message fails against the emulator; the shared string also makes the per-field message unable to ever differ from the top-level one, which the recording shows it does.
Fix: CreatePolicy's validation path — crate::state::resources_clean_up_violation must state the fieldList entry's message as its own complete sentence ending in a period, separately from the top-level message.
Traces: network-security-manager-policy-validation#task#2.

=== Cause 3 of 3: GetScope still resolves a scope identifier that must no longer resolve — HTTP 200 with the scope body instead of the modeled 404 ResourceNotFoundException, and the miss message is the wrong text ===
AWS: Smithy model GetScope — GET /scopes/{scopeIdentifier}, success @http code 200; input scopeIdentifier is @httpLabel + @required (ScopeIdentifier, @length 1..1010). Modeled errors: AccessDeniedException 403, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429, ValidationException 400. ResourceNotFoundException (@error client, @httpError 404) is documented "The specified resource was not found. Verify that the resource identifier is correct and that the resource exists, then try your request again." and carries @required message plus optional resourceId/resourceType. When the identifier names a scope that no longer exists — in the recorded CRUD fixture, the scope the preceding removal step deleted — the recorded AWS response is HTTP 404 with an x-amzn-errortype response header naming the error shape and message "Scope not found: <scopeId>": the fixed text is "Scope not found: " and the one variable part is the scope id taken from the request's scopeIdentifier (the recording's own id value is one run's fill of that template, not part of it). A removed scope must never again be served by this read.
Emulator: answers HTTP 200 with the full GetScopeOutput. The replay reports `status: expected 404, got 200`, `$.message: missing (expected 'Scope not found: <scopeId>', got None)` and `$headers.x-amzn-errortype: missing`. Two defects compound: (a) the scope is still present in the scope store at that point in the lifecycle, so GetScope's miss branch never runs; (b) when that branch does run it states the shared constant "The requested resource was not found." instead of AWS's "Scope not found: <scopeId>" — the rule read already carries its own wording and the scope read needs its own too. Hypothesis for (a): the fixture's scope-removal step is the unimplemented DeleteScope scaffold (it answers 501 NotImplemented), so nothing ever drops the entity from state. The requirement filed here is GetScope's own contract: an unresolvable scope identifier must produce the modeled 404 with AWS's message wording and the x-amzn-errortype header, never a 200 body.
Why: a client cannot distinguish a live scope from a deleted one. Existence probes and idempotent teardown loops ("delete, then confirm GetScope raises ResourceNotFoundException") never terminate the way they do on AWS, `except nsm.exceptions.ResourceNotFoundException` is dead code, and a caller re-reads and re-references a scope AWS considers gone. A client matching or displaying the error text also sees a different sentence than AWS sends.
Fix: GetScope's handler and the scope entity state it reads — the lookup that resolves scopeIdentifier against the scope store must not return removed scopes — plus the ResourceNotFoundException message text its miss branch constructs.
Traces: network-security-manager-scope-and-template-crud#task#9.
