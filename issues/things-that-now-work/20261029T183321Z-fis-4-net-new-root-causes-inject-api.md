# FIS: 4 net-new root causes — inject-api privileges gate demands only ec2:InjectApiError, multi-account action permission read off the orchestrator role, alarm stop conditions never evaluated, injected API faults never reach the data path

> _Note: this issue was identified against the code base at commit `d4c3381173b09dc1be1da315e64a87a78d438272`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExperiment

## Description
This issue bundles FOUR distinct net-new root causes in the FIS experiment RUN path. All four must be closed before submitting; each names its own failing checks. The only open FIS issue near this area, 20261028T115314Z-fis-startexperiment-maintainability.md, is a maintainability finding about the duplicated role lookup inside StartExperiment's role gate and covers NONE of the behaviours below; the two issues the suite marked OWNED (TargetAccountConfiguration accountId validation, CloudFormation AWS::FIS::ExperimentTemplate) are skipped here.

Cause 1 of 4 — an experiment role holding the FIS-namespaced inject permission is judged under-privileged, so every aws:fis:inject-api-* experiment ends `failed`/insufficientPrivileges instead of running.
AWS: recorded behavior only (the Smithy model describes no authorization rule for the run; Experiment$state carries status + reason, ExperimentActionState the per-action status). In all four recordings the experiment role's inline policy grants the FIS-namespaced inject actions on Resource "*" — `fis:InjectApiInternalError` (plus cloudwatch:DescribeAlarms / iam:GetRole / iam:ListRoles / tag:GetResources where the action needs them), or the trio fis:InjectApiInternalError, fis:InjectApiThrottleError, fis:InjectApiUnavailableError — and real AWS started the experiment, reported state.status 'running' and then 'completed'. Real AWS therefore treats the FIS-namespaced grant as sufficient for the aws:fis:inject-api-* family; it is not the only documented spelling (the FIS actions reference also documents an ec2:InjectApiError grant scoped by ec2:FisActionId), so the requirement is "allowed by ANY of the documented grants", not "allowed by ec2:InjectApiError alone".
Emulator: the action catalog records `permissions: &[EC2_INJECT_API_ERROR]` for aws:fis:inject-api-internal-error / -throttle-error / -unavailable-error (and for the aws:ec2:api-* family), and the privileges gate refuses the run when the role's documents do not allow that one string. GetExperiment then reports, for the multi-account recording, state = {'status': 'failed', 'reason': 'Not enough privileges to run action ThrottleAPI (aws:fis:inject-api-throttle-error): the experiment role <roleArn> is not allowed to perform ec2:InjectApiError', 'error': {'accountId': '<accountId>', 'code': 'insufficientPrivileges', 'location': 'actions.<actionName>'}} — the fixed text is 'Not enough privileges to run action … is not allowed to perform …', the action name, action id, role ARN, accountId and location being values taken from the request/state. The single-account recordings reach 'failed' the same way (the assertion only printed status='failed').
Why: a client that wires an experiment exactly as AWS accepts it never observes a run at all: the happy path (initiating → running → completed), ListExperimentResolvedTargets while active, StopExperiment, and every downstream assertion are unreachable, and the client is told its IAM is wrong when it is not.
Fix: the action catalog's permission table for the inject-api/api-error families and the deciding walk that consumes it (services/service-com-amazonaws-fis-faultinjectionsimulator/src/state.rs, ACTION_CATALOG entries for the aws:fis:inject-api-* ids and the EC2_INJECT_API_ERROR constant; services/service-com-amazonaws-fis-faultinjectionsimulator/src/state/action_permissions.rs::permission_failure/role_may_perform) — an entry must be able to state alternative grants and be satisfied when any one of them is allowed.
Traces: fis.e2e-experiment-create-start-observe-stop-teardown, fis.fis-injected-api-internal-error-fails-a-role-scoped-ec2-call-and-spares-a-control-caller, fis.fis-stop-condition-breach-halts-a-live-api-fault-and-the-fault-actually-stops, fis.e2e-experiment-full-flow-with-target-accounts.

Cause 2 of 4 — for a multi-account experiment the action's permission is decided against the TEMPLATE's roleArn (the orchestrator) instead of the target account configuration role.
AWS: recorded behavior only. The recording creates a template with experimentOptions.accountTargeting = 'multi-account', an orchestrator roleArn whose only inline grant is sts:AssumeRole on the target-chain role, and a TargetAccountConfiguration for the account whose roleArn carries the inject permissions. Real AWS ran that experiment to state.status 'completed': in a multi-account experiment FIS performs the action in the target account under the role the TargetAccountConfiguration names, so that role — not the orchestrator — is the one that must be allowed to perform the action's API call.
Emulator: the gate reads the documents of template.roleArn only and attributes the failure to it ('the experiment role arn:aws:iam::<account>:role/<orchestrator> is not allowed to perform …', location actions.<actionName>). Even once Cause 1 is fixed this recording still fails, because the orchestrator role carries no inject grant under any spelling.
Why: the whole multi-account wiring (CreateTargetAccountConfiguration + accountTargeting) is unusable — a correctly split orchestrator/target-role setup is rejected, and the privileges verdict is attributed to the wrong role, so a client cannot tell which policy to change.
Fix: StartExperiment's role gate / the privileges gate must select the role whose documents decide an action by the experiment's accountTargeting — the frozen target account configuration role per targeted account for a multi-account run, the template role for a single-account run (services/service-com-amazonaws-fis-faultinjectionsimulator/src/ops/start_experiment.rs role-gate block; src/state/action_permissions.rs).
Traces: fis.e2e-experiment-full-flow-with-target-accounts.

Cause 3 of 4 — an aws:cloudwatch:alarm stop condition is never evaluated while the experiment runs, so an alarm breach does not stop the experiment.
AWS: recorded behavior only (the model carries ExperimentStopCondition {source, value} and the experiment statuses, but states no evaluation rule). The recording puts a metric alarm, forces it to OK (FIS's documented precondition at start), starts an experiment whose single action is aws:fis:wait for PT10M with stopConditions [{source: 'aws:cloudwatch:alarm', value: <alarmArn>}], waits for state.status 'running', then sets the alarm to ALARM with SetAlarmState — and the service itself transitions the experiment to 'stopped', with no StopExperiment call ever made, long before the PT10M wait could elapse.
Emulator: the experiment is stored with its stop conditions and then run purely on the compressed run clock: the breach is ignored and the run settles to status 'completed'. Observed final status 'completed' where 'stopped' is required.
Why: the stop condition is the blast-radius guardrail. A client that relies on FIS halting an experiment when its alarm fires sees the experiment run to completion instead, and cannot distinguish a halted run ('stopped') from a run that expired ('completed').
Fix: the experiment run/settle path must consult the CloudWatch alarms its stop conditions name when materialising a clock-owed transition, and end the run via stopping → 'stopped' (state.reason naming the stop condition) rather than 'completed' (services/service-com-amazonaws-fis-faultinjectionsimulator/src/state.rs — ExperimentRecord::settle / run_plan and the stop-condition records built by experiment_stop_condition).
Traces: fis.experiment-halts-on-stop-condition-breach, and fis.fis-stop-condition-breach-halts-a-live-api-fault-and-the-fault-actually-stops (which reaches the same rule after Causes 1–2).

Cause 4 of 4 — a live aws:fis:inject-api-* experiment produces no fault in the emulator's own EC2 request path, and nothing is withdrawn when the run ends.
AWS: recorded behavior only, measured in the recordings (real AWS us-west-2): while an experiment with parameters {service: 'ec2', operations: 'DescribeAvailabilityZones', percentage: '100', duration: 'PT2M'} is running, EC2 calls signed by the credentials of the role named in the action's aws:iam:role target fail with HTTP 500, Error.Code 'InternalError', Error.Message 'An internal error has occurred' — deterministically at percentage 100 — while a DIFFERENT operation on the same client and a different (control) principal are unaffected; the 500 disappears once the experiment leaves the running state (or is stopped by a stop condition).
Emulator: by its own design note, state.rs documents that "the effect of an action on another service (an aws:fis:inject-api-* fault making the targeted role's calls to another service fail …) happens in THAT service's responses, and this emulator does not produce it". So no injected fault is ever installed, scoped to the target role's identity, or withdrawn. Both fault-injection checks currently stop earlier (at Cause 1), so this cause will surface as the next failure once the gate is fixed: the targeted EC2 call keeps returning 200 for the whole poll budget.
Why: the only thing a chaos-engineering client uses FIS for is the fault. An emulator that moves status fields but never changes a targeted call's response lets a resilience test pass without ever exercising a failure, and (for Cause 3) lets a "halted" experiment leave a fault installed.
Fix: couple the FIS control plane to the request path per principal, per operation, for the action's duration — the FIS run state must publish the live faults (targeted role ARNs, service, operations, percentage, duration) and the EC2 dispatcher must honour them while the experiment is running and drop them when it reaches a terminal status (services/service-com-amazonaws-fis-faultinjectionsimulator/src/state.rs run plan/settle, plus the shared engine hook the EC2 crate's request dispatch reads).
Traces: fis.fis-injected-api-internal-error-fails-a-role-scoped-ec2-call-and-spares-a-control-caller, fis.fis-stop-condition-breach-halts-a-live-api-fault-and-the-fault-actually-stops.

## Steps to Reproduce

Cause 2 (multi-account):
1. CreateRole ORCH (trusting fis.amazonaws.com with the aws:SourceAccount/aws:SourceArn conditions) and CreateRole TGT whose inline policy allows fis:InjectApiInternalError/ThrottleError/UnavailableError; give ORCH only sts:AssumeRole on TGT.
2. Cause 3 (stop condition):

2. CreateExperimentTemplate with stopConditions [{source:'aws:cloudwatch:alarm', value:<A arn>}], actions {wait1:{actionId:'aws:fis:wait', parameters:{duration:'PT10M'}}}, targets {}, roleArn allowing cloudwatch:DescribeAlarms.

Cause 4 (fault in the data path):
1. Build the Cause-1 rig but make the target role assumable by the caller and grant it ec2:DescribeAvailabilityZones + ec2:DescribeRegions; action parameters {duration:'PT2M', service:'ec2', percentage:'100', operations:'DescribeAvailabilityZones'}.

Call DescribeAvailabilityZones with the assumed credentials: expected HTTP 500 InternalError 'An internal error has occurred', while DescribeRegions on the same client and any other principal stay 200; after the experiment leaves 'running' the call returns 200 again.
