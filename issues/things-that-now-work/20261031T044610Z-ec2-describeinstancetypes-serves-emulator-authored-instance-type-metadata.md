# EC2 DescribeInstanceTypes serves emulator-authored instance-type metadata that contradicts AWS

> _Note: this issue was identified against the code base at commit `cfccde4fe05803c815da2258c2579267e1874cb3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers 200 but the per-instance-type hardware facts it returns are emulator-authored: several modeled members are omitted entirely and many that are present carry values that are not the values AWS reports for that instance type. The instance-type catalog is static reference data (the facts are fixed properties of the instance type, not per-account or per-run values), so every wrong or missing entry is a permanent wire divergence for any client that reads it. Two causes are bundled here; both are DescribeInstanceTypes 200->200 clusters on the EC2 instance-type catalog, and BOTH must be closed before submitting.

Cause 1 of 2: c5ad.* instance-type family (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#7).
AWS: for an instance type in the c5ad family DescribeInstanceTypes returns, inside instanceTypeSet.item, the modeled members cpuBurstModel, dedicatedHostsSupported, hibernationSupported, phcSupport, rebootMigrationSupport, ebsInfo.maximumEbsAttachments, ebsInfo.ebsOptimizedInfo.{baselineBandwidthInMbps, baselineIops, baselineThroughputInMBps, maximumBandwidthInMbps, maximumIops, maximumThroughputInMBps}, instanceStorageInfo.disks.item.{count,sizeInGB}, instanceStorageInfo.totalSizeInGB, networkInfo.{defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, maximumNetworkCards, networkCards, networkPerformance, secondaryNetworkSupported, trafficMirroringSupport}, processorInfo.sustainedClockSpeedInGhz and vCpuInfo.validCores. Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json): EbsOptimizedInfo is a structure with BaselineBandwidthInMbps (integer, xmlName baselineBandwidthInMbps), BaselineIops (integer), BaselineThroughputInMBps (double), MaximumBandwidthInMbps (integer), MaximumIops (integer), MaximumThroughputInMBps (double); these are documented as 'The baseline/maximum bandwidth, throughput and IOPS performance for an EBS-optimized instance type'. The exact per-type figures are recorded behavior only (the model states the members, the recording states the values).
Emulator: answers 200 but, for c5ad.8xlarge, omits cpuBurstModel (AWS: 'none'), reports dedicatedHostsSupported 'true' (AWS: 'false'), hibernationSupported 'true' (AWS: 'false'), ebsOptimizedInfo.baselineBandwidthInMbps '6800' (AWS: '3170'), baselineIops '30000' (AWS: '13300'), baselineThroughputInMBps '850' (AWS: '396.25'), the same three wrong figures again for the maximum* members, ebsInfo.maximumEbsAttachments '28' (AWS: '25'), instanceStorageInfo.disks.item.count '1' (AWS: '2') and sizeInGB '800' (AWS: '600'); and it omits networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.maximumNetworkCards, networkInfo.networkCards, phcSupport and rebootMigrationSupport outright. The same wrong-and-missing pattern repeats for every member of the family (c5ad.large .. c5ad.24xlarge) in this one cluster.

Cause 2 of 2: c8gb.* instance-type family (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#25).
AWS: same members as above, plus ebsInfo.attachmentLimitType, ebsInfo.ebsCardSet, ebsInfo.maximumEbsCards, networkInfo.efaInfo, networkInfo.efaSupported, networkInfo.ipv4AddressesPerSecondaryInterface, networkInfo.maximumNetworkInterfaces and networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout for this generation. Recorded behavior only for the per-type figures.
Emulator: answers 200 but, for c8gb.16xlarge, omits cpuBurstModel (AWS: 'none'), reports ebsInfo.attachmentLimitType 'shared' (AWS: 'dedicated'), ebsOptimizedInfo.baselineBandwidthInMbps '13600' (AWS: '100000'), baselineIops '60000' (AWS: '480000'), baselineThroughputInMBps '1700' (AWS: '12500.0'), the same three wrong figures again for the maximum* members, ebsInfo.maximumEbsAttachments '28' (AWS: '48'), networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout '432000' (AWS: '350'), and omits networkInfo.defaultNetworkCardIndex, networkInfo.efaInfo, networkInfo.efaSupported, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.ipv4AddressesPerSecondaryInterface, networkInfo.maximumNetworkCards, networkInfo.maximumNetworkInterfaces, networkInfo.networkCards, phcSupport and rebootMigrationSupport. Again the pattern repeats across the whole family (c8gb.2xlarge .. c8gb.48xlarge, including the validCores list of c8gb.48xlarge) inside this one cluster.

Why: DescribeInstanceTypes is the authority clients use to pick an instance type and to size EBS and network capacity. A client that reads ebsOptimizedInfo to decide whether a type can sustain its IO budget is told a c8gb.16xlarge sustains 13600 Mbps / 60000 IOPS when AWS reports 100000 Mbps / 480000 IOPS, and is told a c5ad.8xlarge sustains more than it does; a client that counts instanceStorageInfo disks provisions the wrong number of ephemeral volumes; a client that reads attachmentLimitType/maximumEbsAttachments computes the wrong attachment budget; and a client that reads the omitted members (cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.networkCards, networkInfo.maximumNetworkCards, efaSupported, phcSupport, rebootMigrationSupport) gets null where AWS always returns a value, so capability probes silently read as 'unsupported'.

Fix: the static instance-type catalog behind the DescribeInstanceTypes handler in the ec2 service crate (services/service-com-amazonaws-ec2-amazonec2, the describe_instance_types op and the instance-type catalog table it serializes from) - the catalog rows must carry AWS's per-type figures and must populate every member the model defines for that type rather than leaving them unset. This is a data/serializer fix, not a protocol fix: status, envelope and element names already match.
