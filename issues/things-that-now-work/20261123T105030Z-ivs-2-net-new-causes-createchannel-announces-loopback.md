# IVS: 2 net-new causes — CreateChannel announces loopback host:port endpoints, and GetStreamSession answers 404 ResourceNotFoundException for an invalid streamId instead of 400 ValidationException

## Description
Replaying the wire corpus (simparity-wire-aws-v1) against the IVS emulator (service token `ivs`, crate services/service-com-amazonaws-ivs-amazoninteractivevideoservice) leaves TWO net-new divergence clusters that no open issue owns (the replay reports owned_by [] and stub_path "" for both). They are bundled here because they belong to one service; they are INDEPENDENT causes in different handlers and a fixer must close BOTH before submitting.

Cause 1 of 2 — CreateChannel announces its three channel endpoints (`$.channel.ingestEndpoint`, `$.channel.playbackUrl`, `$.channel.srt.endpoint`) as a bare loopback address with an explicit port instead of as a DNS hostname. Fixture ivs-channel-lifecycle, step task#1 (cluster also covers ivs-viewer-session-revocation#setup#1).
AWS: recorded behavior only. Smithy (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/smithy-model/com-amazonaws-ivs-amazoninteractivevideoservice.json, com.amazonaws.ivs, restJson1): `Channel.ingestEndpoint` -> `IngestEndpoint`, `Channel.playbackUrl` -> `PlaybackURL` and `Srt.endpoint` -> `SrtEndpoint` are plain strings with NO @length and NO @pattern, so the model states no form and the recording is the only authority. The corpus does not pin these values literally (it reports them `<shaped-not-asserted>`, because the minted label, region, account id and channel id are per-run); it pins their SHAPE CLASS, and the recording establishes that class as: the ingest endpoint is a DNS HOSTNAME — a minted label under a service-owned contribute domain — carrying NO scheme and NO port; `srt.endpoint` is that SAME host as `ingestEndpoint` (corroborated inside this corpus by ivs-batch-get-channel-and-stream-key#task#3, where `$.channels[0].ingestEndpoint` and `$.channels[0].srt.endpoint` are one identical host); and `playbackUrl` is an `https://` URL whose HOST is a hostname of that class and whose path is the recorded `/api/video/v1/<region>.<account>.channel.<channel-id>.m3u8` layout. Hostname form, absence of a port, scheme and path layout are the requirement; the particular host, port and ids in any one run are not.
Emulator: the replay reports all three members as shape mismatches on an otherwise correct 200 response (expected 200, got 200). `ingestEndpoint` and `srt.endpoint` come back as a bare loopback IP literal with a `:<port>` suffix and no domain label at all; `playbackUrl` comes back as `https://<loopback-host>:<port>/api/video/v1/<region>.<account>.channel.<id>.m3u8` — the recorded path layout is kept, the host is the emulator's own listener address. create_channel.rs is explicit that this is deliberate: it stores `ingest_endpoint: None`, `playback_url: None` and `Srt.endpoint: None` (lines 252-281) and defers all three to the shared projection `crate::state::announced_channel`, which composes the deployment's own socket for each request that reports a channel. The emulator's two announced addresses are not even the same socket in this run, so the recorded identity of `ingestEndpoint` and `srt.endpoint` versus the playback host is lost as well.
Why: a client does not treat the contribute address as an opaque string. It composes `rtmps://<ingestEndpoint>:443/app/<streamKey>` or `srt://<srt.endpoint>`, appending its own port, so an endpoint that already carries `:<port>` yields a doubly-ported, unusable URL; code that validates the value as a hostname, stores it in a hostname-typed field, or splits it on `.` to recover the channel label rejects a bare IP outright. For `playbackUrl` a player that parses the host to pick a CDN or to assert TLS-by-hostname mis-handles it. All of this works against AWS and breaks here.
Fix: the shared channel projection that composes these three members — `crate::state::announced_channel` in services/service-com-amazonaws-ivs-amazoninteractivevideoservice/src/state.rs, which create_channel.rs delegates to (see the comments at lines 240-274) — not the serializer and not the store, since the members are never persisted. It must announce an address of AWS's recorded shape class: one hostname (label plus domain, no port) shared by `ingestEndpoint` and `srt.endpoint`, and that same class of host inside the `https://.../api/video/v1/<region>.<account>.channel.<id>.m3u8` playback URL.
Traces: ivs-channel-lifecycle#task#1 (representative), ivs-viewer-session-revocation#setup#1 (same cluster); shape corroboration ivs-batch-get-channel-and-stream-key#task#3.

Cause 2 of 2 — GetStreamSession reports an invalid `streamId` as a missing resource: HTTP 404 `ResourceNotFoundException` instead of HTTP 400 `ValidationException`. Fixture ivs-stream-operations-not-broadcasting, step task#8.
AWS: Smithy GetStreamSession(channelArn: ChannelArn required @length 1..128 @pattern ^arn:aws:ivs:[a-z0-9-]+:[0-9]+:channel/[a-zA-Z0-9-]+$, streamId: StreamId @length 26..26 @pattern ^st-[a-zA-Z0-9]+$) -> streamSession; modelled errors AccessDeniedException (@httpError 403), ResourceNotFoundException (@httpError 404), ValidationException (@httpError 400, documented "The input fails to satisfy the constraints specified by an Amazon Web Services service"). Per the recording, a request whose `streamId` is not a well-formed IVS stream id is an INPUT-constraint failure, answered HTTP 400 with error code `ValidationException` in both the body's error-code member and the `x-amzn-errortype` header, and the member-named constraint message `Request member: streamId failed to satisfy the constraints: invalid stream id`. In that message the whole text is fixed except the member name (`streamId`) and the constraint reason (`invalid stream id`) — it is the same `Request member: <member> failed to satisfy the constraints: <reason>` template this service uses for its other recorded validation failures; no request value or generated id appears in it. The input constraint is evaluated BEFORE any channel or session lookup, so the 404 ResourceNotFoundException path ("Request references a resource which does not exist") is reached only for a well-formed streamId that names no session.
Emulator: answers HTTP 404 with `$.Code` / `x-amzn-errortype` = `ResourceNotFoundException` and message `Resource: <channelArn> not found` for the same request — i.e. it never evaluates the streamId's form and reports the CHANNEL's ARN as the missing resource even though the channel exists and only the streamId is bad. get_stream_session.rs asserts the opposite of what replay shows: its handler comment (lines 157-159) states "`streamId` [carries] the modelled `StreamId` ones, which the framework's constraint walk has already enforced, so reaching here means both are well formed", yet the handler is reached and falls through `channel_exists` / `crate::state::stream_session` to `crate::state::resource_not_found(..., &input.channel_arn)` (lines 167-181). So either the framework's constraint walk is not enforcing StreamId's @length 26..26 / @pattern ^st-[a-zA-Z0-9]+$, or the recorded id-form check it needs is not modelled and must be done explicitly.
Why: a client is told the wrong thing about its own request, with the wrong status class. Against AWS a bad stream id is a non-retryable 400 the caller fixes by correcting the id it passed; against the emulator it is a 404 on the CHANNEL, so a caller's "channel was deleted / not yet created" branch fires, it re-creates or re-polls the channel, and any ValidationException branch is dead. The status difference (404 vs 400) also changes SDK error classification and retry decisions.
Fix: GetStreamSession's input validation, ahead of its state lookup — reject a `streamId` that is not a well-formed stream id with ValidationException and the member-named message above BEFORE resolving the channel or the session in services/service-com-amazonaws-ivs-amazoninteractivevideoservice/src/ops/get_stream_session.rs (handler lines 152-186); if the framework's constraint walk is silently skipping StreamId's modelled @length/@pattern, that walk is the component to repair, since every other operation taking a constrained optional member inherits the same gap.
Traces: ivs-stream-operations-not-broadcasting#task#8.
