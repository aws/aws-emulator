# iot: the HTTP topic-rule-destination lifecycle (create → confirmation POST → confirm → DISABLED → ENABLED → deliver) never settles, so the unconfirmed-destination delivery gate reaches no verdict (1 cause)

> _Note: this issue was identified against the code base at commit `89dcb84bc001d630dd4b5e9068fc0fc72dd2f2e3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTopicRuleDestination

## Description
Cause 1 of 1: the IoT HTTP topic-rule-destination trajectory — CreateTopicRuleDestination, the outbound DestinationConfirmation POST to the confirmationUrl, ConfirmTopicRuleDestination, the IN_PROGRESS → DISABLED → ENABLED status transitions, and the topic-rule `http` action's status-gated delivery — produces nothing a client can act on. The check that asserts an enabled rule delivers NOTHING while its destination is unconfirmed and DOES deliver once the destination is confirmed and ENABLED therefore reaches no verdict at all. Failing check: iot.topic-rule-with-unconfirmed-destination-blocks-delivery.

AWS: Smithy (services/service-com-amazonaws-iot-awsiotservice) models CreateTopicRuleDestination POST /destinations, success 200, required input destinationConfiguration: TopicRuleDestinationConfiguration, output topicRuleDestination: TopicRuleDestination; errors InvalidRequestException 400, ConflictingResourceUpdateException 409, ResourceAlreadyExistsException 409, UnauthorizedException 401, InternalException 500, ServiceUnavailableException 503. TopicRuleDestination.status is enum TopicRuleDestinationStatus [ENABLED, IN_PROGRESS, DISABLED, ERROR, DELETING]; its modeled documentation states that a destination "was created but has not been confirmed" in IN_PROGRESS, that calling UpdateTopicRuleDestination "causes a new confirmation challenge to be sent to your confirmation endpoint", that in ENABLED "traffic to this destination is allowed" and in DISABLED "traffic to this destination is not allowed". HttpUrlDestinationProperties.confirmationUrl (@length 0..2000) is "the URL used to confirm the HTTP topic rule destination URL": AWS sends an HTTPS DestinationConfirmation POST to it carrying a confirmationToken. ConfirmTopicRuleDestination GET /confirmdestination/{confirmationToken+} (confirmationToken @length 1..2048, success 200, empty output) accepts that token; the destination leaves IN_PROGRESS asynchronously and rests at DISABLED, and only UpdateTopicRuleDestination PATCH /destinations (required arn: AwsArn, required status, success 200, empty output) with status=ENABLED makes it ENABLED. GetTopicRuleDestination GET /destinations/{arn+} (200) reports that status. Recorded behavior: while the destination is not ENABLED a published message is not POSTed to the URL; once ENABLED it is. Every one of these calls is bounded and answered promptly with a 200 or one of the modeled errors.

Emulator: the replay produces no response the check can act on — the only output the suite reports is `Error: Check timed out after 60.0s`. Every step of this trajectory is a bounded poll whose own budget exceeds the harness cap (endpoint self-test 60 s, confirmation-token poll 240 s including UpdateTopicRuleDestination status=IN_PROGRESS resends, two 60 s GetTopicRuleDestination status polls, 180 s post-enable delivery poll), so the cap fires because a step AWS answers never produces its value. No HTTP status, no error code, no error message, and no delivered or suppressed payload is served in its place: not even a prompt modeled refusal (400 InvalidRequestException, 409 ConflictingResourceUpdateException, 401 UnauthorizedException, 503 ServiceUnavailableException) that would at least give the caller a verdict. Consistent with this, no outbound DestinationConfirmation POST and no destination-status gate on the `http` rule action is observable anywhere in this suite, and CreateTopicRuleDestination is still an unimplemented scaffold stub in this checkout. Hypothesis: with no destination record there is no confirmation challenge to send and no status for the rule's http action to consult, so each poll spins until the cap.

Why: a client that follows AWS — create the destination, receive the confirmation POST, call ConfirmTopicRuleDestination with the token, set ENABLED, then publish — never progresses and never learns why; it blocks until its own timeout instead of failing fast on a modeled error. The security-relevant guarantee this check exists to assert, that an enabled rule delivers NOTHING to a destination that has not been confirmed and enabled, is unobservable, so neither the block nor the post-enable delivery can be relied on.

Fix: the iot topic-rule-destination component — the CreateTopicRuleDestination, ConfirmTopicRuleDestination, UpdateTopicRuleDestination and GetTopicRuleDestination handlers and the destination state machine they share (IN_PROGRESS on create, DISABLED after confirmation, ENABLED only on an explicit update, IN_PROGRESS again on an update that re-issues the challenge), the outbound HTTPS DestinationConfirmation POST that carries the confirmationToken to the configured confirmationUrl, and the topic-rule `http` action's delivery path, which must consult the destination's status and suppress delivery unless it is ENABLED. Each must either do the work or answer one of the modeled errors promptly rather than leaving the caller waiting.

Traces: iot.topic-rule-with-unconfirmed-destination-blocks-delivery.

## Evidence
Expected (AWS): CreateTopicRuleDestination returns 200 with topicRuleDestination.status=IN_PROGRESS, and a DestinationConfirmation POST carrying a confirmationToken query parameter arrives at the configured confirmationUrl. A message published to the rule's topic while the destination is unconfirmed is NOT delivered to that URL. ConfirmTopicRuleDestination(confirmationToken) returns 200, and GetTopicRuleDestination then reports status DISABLED. UpdateTopicRuleDestination(arn, status="ENABLED") returns 200 and GetTopicRuleDestination reports ENABLED. A message published after that IS POSTed to the URL. Every call is bounded and answered with 200 or a modeled error (InvalidRequestException 400, ConflictingResourceUpdateException 409, ResourceAlreadyExistsException 409, UnauthorizedException 401, InternalException 500, ServiceUnavailableException 503).

Actual (emulator): the suite reports exactly `Error: Check timed out after 60.0s` for iot.topic-rule-with-unconfirmed-destination-blocks-delivery — no HTTP status, no error code, no error message, no delivered or suppressed marker, and no destination status. The check's own waits (60 s endpoint self-test, 240 s confirmation-token poll with status=IN_PROGRESS resends, 2 x 60 s status polls, 180 s delivery poll) all exceed the 60 s harness cap, so the cap is reached because the trajectory never produces a value AWS would have produced. The run never reaches the confirm/enable or post-enable delivery assertions. CreateTopicRuleDestination is an unimplemented scaffold stub in this checkout, and no outbound confirmation POST or http-action status gate is observable anywhere in this suite.

## Steps to Reproduce
1. Stand up an HTTPS endpoint that logs what it receives (the check uses an API Gateway v2 HTTP API with a $default route fronting a python3.12 Lambda that prints the request's confirmationToken query parameter and the body's `marker`), and self-test it by POSTing a probe and finding the probe marker in the function's CloudWatch Logs.
2. iot.create_topic_rule_destination(destinationConfiguration={"httpUrlConfiguration": {"confirmationUrl": <endpoint url>}}) and keep topicRuleDestination.arn; expect status IN_PROGRESS.
3. Wait for the DestinationConfirmation POST at the endpoint and read its confirmationToken; if it does not arrive, call iot.update_topic_rule_destination(arn=<arn>, status="IN_PROGRESS") to request a resend. Observe that no confirmation request ever arrives.
4. iot.create_topic_rule(ruleName=<name>, topicRulePayload={"sql": "SELECT * FROM '<topic>'", "actions": [{"http": {"url": <endpoint url>}}], "ruleDisabled": False}).
5. Publish a unique marker to <topic> through the iot-data plane and assert it never reaches the endpoint (the unconfirmed-destination block).
6. iot.confirm_topic_rule_destination(confirmationToken=<token>), poll iot.get_topic_rule_destination(arn=<arn>) until DISABLED, then iot.update_topic_rule_destination(arn=<arn>, status="ENABLED") and poll until ENABLED.
7. Publish a second marker and assert it now reaches the endpoint. Against the emulator the run never gets past step 3 and is killed at the harness's 60 s cap with no verdict.
