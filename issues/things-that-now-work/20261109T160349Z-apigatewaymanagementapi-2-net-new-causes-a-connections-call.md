## Description
TWO net-new root causes on the apigatewaymanagementapi service token, taken from the five failures the replay marks neither ALREADY FILED nor OWNED. They are numbered below and each carries its own failing check ids; BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: a @connections request whose endpoint stage segment names a stage that is NOT deployed for that API is answered by aborting the TCP/TLS connection with no HTTP response at all, instead of HTTP 403 ForbiddenException with the message 'Forbidden' ===
AWS: the modelled surface is Smithy ApiGatewayManagementApi (sdk_id ApiGatewayManagementApi, protocols [restJson1], authSchemes [sigv4], 3 operations): GetConnection GET /@connections/{ConnectionId}; PostToConnection POST /@connections/{ConnectionId} with Data @httpPayload blob @length{min 0,max 131072}, error PayloadTooLargeException (413); DeleteConnection DELETE /@connections/{ConnectionId} code 204; service-common errors ForbiddenException (client, @httpError 403, NO members, doc 'The caller is not authorized to invoke this operation.'), GoneException (410, no members), LimitExceededException (429). Stage routing on the execute-api data plane is not a modelled operation, so the refusal itself is recorded behavior only: when the management endpoint's path segment names a stage that is not a deployed stage of that API, GetConnection, PostToConnection and DeleteConnection are each answered HTTP 403 with error code ForbiddenException and the message 'Forbidden' — entirely fixed text, no variable parts — and the connection store is never consulted. Whatever the verdict, AWS always ANSWERS the request with an HTTP response; it never drops the connection.
Emulator: the call produces no HTTP response whatsoever. botocore raises `ConnectionClosedError: Connection was closed before we received a valid response from endpoint URL: "https://<host>:<port>/<stage>/@connections/<connection-id>"` (the host, port and id are per-run values; the requirement is that a response arrives at all). This is a change of failure mode, not a repeat: the same check previously reached the assertion and compared error codes, so the emulator used to answer an (incorrect) 410 GoneException envelope here and now answers nothing.
Why: a client gets a transport-level reset in place of a modelled refusal, so every SDK surfaces it as a connection/retry error rather than as AccessDenied/Forbidden. The SDK will retry an aborted connection, so a simple stage typo or a stale/deleted stage name becomes a hang-and-retry loop instead of an immediate 403; nothing in the client can distinguish 'you may not invoke this endpoint' from 'the emulator crashed'. The per-stage authorization boundary AWS enforces on @connections therefore does not exist here, and error-handling code written against ForbiddenException is unreachable.
Fix: the @connections data-plane front door / endpoint resolution that sits in front of the three handlers — resolve {api-id, stage} from the request path against the API's deployed stages and return a complete HTTP response (status 403, error code ForbiddenException, message 'Forbidden') before dispatching to the connection store, and never terminate the connection without a response.

The replay reports no owner for this failure.

=== Cause 2 of 2: a deployed apigatewayv2 WEBSOCKET stage still never yields a usable WebSocket connection, so four live-connection @connections checks reach no verdict at all ===
AWS: the RFC 6455 opening handshake is the execute-api data plane and is not a modelled operation, so this is recorded behavior only. Recorded: a GET on the deployed stage path carrying `Connection: Upgrade`, `Upgrade: websocket`, `Sec-WebSocket-Key: <base64 of 16 bytes>` and `Sec-WebSocket-Version: 13` is answered `HTTP/1.1 101 Switching Protocols` with `Upgrade: websocket`, `Connection: Upgrade` and `Sec-WebSocket-Accept: base64(SHA1(Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`; $connect then runs, the service mints the connection id, and that id is what the modelled @connections surface addresses (GetConnection returning ConnectedAt/LastActiveAt as ISO8601 date-times plus Identity, PostToConnection delivering the payload as one frame on that socket, DeleteConnection closing it with 204).
Emulator: no connection is ever established. One check polls for a status line containing ' 101 ' for its whole budget and fails with `TimeoutError: a 101 WebSocket upgrade on the new stage: the run budget ended first; not graded`; the other three complete their control-plane setup (iam role, lambda, dynamodb table, create_api/create_integration/create_route/create_deployment/create_stage) and are then killed by the harness — `Check timed out after 60.0s` — inside the same step, which opens the socket to the stage's wss URL and waits for the $connect record/connection id. No 101, no Sec-WebSocket-Accept, no minted connection id.
Why: with no connection id minted, the entire server-push surface is unobservable and unusable: ordering of sequential PostToConnection deliveries on one socket, a reconnect producing a distinct ConnectionId with a strictly later ConnectedAt, the AccessDeniedException a principal without execute-api:ManageConnections must get from PostToConnection (with its positive control on a live connection), and a backend route that calls GetConnection/PostToConnection/DeleteConnection on live clients. A developer pointing a WebSocket client at the stage cannot tell a missing data plane from a misconfigured stage, and no server-push application code can be exercised at all.
Fix: the execute-api data-plane front door / request router plus the apigatewayv2 WebSocket session layer — claim an upgrade request addressed to a deployed WEBSOCKET-protocol API's stage path, complete the handshake (101 + correct Sec-WebSocket-Accept) instead of falling through, mint a connection id, dispatch $connect/$disconnect/route selection, and register the connection in the store the @connections handlers read. An upgrade that cannot be served must still be answered with a terminal HTTP status immediately rather than absorbed. This is a capability gap, not an error-shape bug.
