# bedrock-agent__lambda__opensearchserverless: the AOSS collection data plane ignores a data access policy's Principal list, so a Lambda role excluded from every data access policy writes documents successfully (201) instead of being refused 403

## Description
ONE net-new root cause, grounded in the single failing behavioral check of this service group that the suite did not mark OWNED or ALREADY FILED.

Overlap note (not a duplicate): open issue 20261108T223024Z-opensearchserverless-3-net-new-causes-on-the-collection.md, 'Cause 1 of 3', describes the data plane ignoring a data access policy's per-operation *Permission* list (withdrawing aoss:WriteDocument keeps accepting writes) under the `opensearchserverless` service token. The divergence filed here is the *Principal* dimension of the same authorization step: the caller is not in ANY data access policy's Principal list at all — nothing was withdrawn, nothing was ever granted — and it is reached through the Lambda→AOSS data-plane path of this service group, whose check the suite reported as unowned. If that issue is fixed by implementing full policy evaluation (principal selection AND permission mapping), this one closes with it; if only the Permission list is wired up, this one still reproduces.

Cause 1 of 1: a data access policy's Principal list is not evaluated on the collection data plane, so an unlisted principal is authorized.
Failing check: bedrock-agent__lambda__opensearchserverless.lambda-opensearchserverless-data-plane-access-denied-negative

AWS:      recorded behavior only — the AOSS collection data plane (the OpenSearch REST surface published as CollectionDetail.collectionEndpoint) is not Smithy-modeled. The control-plane writers that configure it ARE modeled: Smithy com.amazonaws.opensearchserverless#CreateAccessPolicy(type: AccessPolicyType (required), name: PolicyName (required, @length 3..32, pattern ^[a-z][a-z0-9-]+$), policy: PolicyDocument (required, @length 1..20480)) and #UpdateAccessPolicy(type, name, policyVersion (required), policy), both of which REPLACE the policy document; CollectionDetail.collectionEndpoint is documented as the 'Collection-specific endpoint used to submit index, search, and data upload requests to an OpenSearch Serverless collection'. AWS's rule (documented in 'Data access control for Amazon OpenSearch Serverless') is that data-plane access requires BOTH an IAM permission (aoss:APIAccessAll) AND a data access policy whose Principal list names the caller; an identity holding aoss:APIAccessAll but named in NO data access policy for the target collection/index is refused. Recorded: a role holding aoss:APIAccessAll and listed in the collection's data access policy Principal list has its aoss-signed `PUT /<index>/_doc/<id>` accepted (201, body `{"_index","_id","_version","result","_shards","_seq_no","_primary_term"}`) and the document becomes searchable; a second role identical in every way EXCEPT that it is absent from the policy's Principal list has the SAME request refused with HTTP 403 and an OpenSearch error document whose `error.type` is the fixed text `forbidden`, on EVERY attempt across the window (never intermittently), its write never lands (a subsequent authorized `GET /<index>/_doc/<id>` is 404), and adding that role to the Principal list via UpdateAccessPolicy then makes the identical call succeed. The requirement is the 403 status and the fixed `forbidden` error type; the collection name, index name, document id, role ARNs and `_version`/`_seq_no` numbers are request/state values that fill the template.
Emulator: the Principal list is not consulted. The excluded role's write is ACCEPTED on the first attempt of the denial window: `{'ok': True, 'status': 201, 'body': '{"_index":"items","_id":"bad-doc","_version":1,"result":"created","_shards":{"total":1,"successful":1,"failed":0},"_seq_no":1,"_primary_term":1}'}` — a real document created under a policy that names a different principal. No 403 is ever produced, so the check's later assertions (the EFFECT-ABSENT 404 GET of `bad-doc`, and the restore step proving the identical call succeeds once the role IS granted) are never reached. Allowed and excluded principals are indistinguishable at the endpoint: any aoss-signed request is served.
Why:      a client that treats the data access policy as its authorization boundary gets none on the data plane. Any identity that can reach the collection endpoint and sign for `aoss` can index, overwrite and read every document in every index of the collection, regardless of whether a data access policy names it — so a least-privilege design validated against the emulator (one Lambda role granted, a second deliberately excluded) appears to pass while the exclusion is a no-op, and a test asserting the excluded path is denied will pass in the emulator and fail against AWS (or, worse, ship a privilege escalation). Nothing in the API signals the difference: CreateAccessPolicy/UpdateAccessPolicy succeed and report the policy with the restricted Principal list.
Fix:      the collection data-plane request handler's authorization step in the opensearchserverless service crate (the host serving collectionEndpoint, not the AWS-JSON control-plane front door). It must resolve the signing principal from the SigV4 credential, select the `type=data` access policies whose Principal list matches that principal AND whose Rules' Resource matches the target `collection/<name>` / `index/<name>/<index>`, and when no such policy statement exists refuse the request with HTTP 403 and an OpenSearch error document (`{"status": 403, "error": {"type": "forbidden", ...}}`) — deterministically on every attempt, not as a propagation window — instead of serving every signed request unconditionally. The decision must be driven by the live control-plane policy state so that adding the principal via UpdateAccessPolicy makes the same call start succeeding.
Traces:   bedrock-agent__lambda__opensearchserverless.lambda-opensearchserverless-data-plane-access-denied-negative
