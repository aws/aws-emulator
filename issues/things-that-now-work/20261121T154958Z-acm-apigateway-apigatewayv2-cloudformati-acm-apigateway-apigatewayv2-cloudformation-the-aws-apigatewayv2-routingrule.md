# acm__apigateway__apigatewayv2__cloudformation: the AWS::ApiGatewayV2::RoutingRule deploy-and-serve scenario reaches no verdict — it hangs to the 60 s harness cap with no response and no refusal (1 cause)

## Operation
CreateRoutingRule

## Description
Cause 1 of 1: the cross-service CloudFormation routing-rule scenario never converges, so the whole RoutingRule lifecycle (create, in-place update, create-only replacement, delete) is unobservable. Failing check: acm__apigateway__apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-routingrule-matches-then-updates-and-replaces.

AWS: the scenario exercises a modeled, documented path end to end. ApiGatewayV2 CreateDomainName for a REGIONAL domain with RoutingMode=ROUTING_RULE_ONLY and one DomainNameConfigurations entry (CertificateArn of an ACM-imported, ISSUED leaf; EndpointType=REGIONAL; SecurityPolicy=TLS_1_2) settles at DomainNameConfigurations[0].DomainNameStatus=AVAILABLE and publishes an ApiGatewayDomainName that is a dialable DNS name presenting that certificate (Smithy: GetDomainName GET /v2/domainnames/{DomainName}, output members domainNameConfigurations, routingMode, domainNameArn). A CloudFormation stack declaring AWS::ApiGatewayV2::RoutingRule (DomainNameArn, Priority, Conditions=[{MatchBasePaths:{AnyOf:[<basePath>]}}], Actions=[{InvokeApi:{ApiId,Stage}}]) reaches CREATE_COMPLETE and resolves Fn::GetAtt RoutingRule.RoutingRuleId / RoutingRuleArn; GetRoutingRule then reports exactly the templated priority, conditions and action (Smithy: CreateRoutingRule POST /v2/domainnames/{DomainName}/routingrules -> 201 with routingRuleId/routingRuleArn/priority (@range 1..1000000)/conditions/actions; GetRoutingRule GET /v2/domainnames/{DomainName}/routingrules/{RoutingRuleId} -> 200 with the same members; ListRoutingRules GET .../routingrules -> routingRules). On the data plane the custom domain forwards a request whose base path matches a rule's MatchBasePaths to the named REST API stage (here a MOCK GET returning 200 and the body {"served": "<leaf>"}), and answers 403 for a path no rule's condition matches. Changing only Priority/Conditions updates the SAME physical resource (its PhysicalResourceId, the rule ARN, is unchanged); changing the create-only DomainNameArn replaces it, after which GetRoutingRule on the old domain for the superseded RoutingRuleId is refused 404 NotFoundException with message "Unable to find RoutingRule." — that text is fixed, it carries no request or state values — and the replacement rule is readable on the new domain with the same Priority/Conditions. Deleting the stack removes the rule: GetRoutingRule is again refused 404 NotFoundException "Unable to find RoutingRule." and ListRoutingRules on that domain returns an empty routingRules list.

Emulator: the check produces no verdict at all. The replay report records only "Check timed out after 60.0s" — every assertion in the scenario is still unreached when the harness budget expires, so the emulator returned neither a success nor a refusal for the blocking leg. The report does not say which call hangs; the scenario's own ordering means the blocking leg is inside the regional custom-domain / routing-rule deploy-and-serve path: GetDomainName polling for DomainNameStatus=AVAILABLE with a dialable ApiGatewayDomainName, the create_stack for AWS::ApiGatewayV2::RoutingRule reaching a terminal CREATE_COMPLETE with its two Fn::GetAtt outputs, or the TLS GET to the published gateway host returning 200/403. Nothing downstream of that — the in-place update keeping the physical id, the DomainNameArn replacement swapping it, the two NotFoundException refusals, the empty ListRoutingRules after the stack delete — is exercised at all.

Why: a client that deploys a routing rule by CloudFormation and then routes traffic through a REGIONAL custom domain gets a run that never finishes instead of a deployed, serving rule. CDK/CFN users see a stack that does not settle (or a domain that never becomes AVAILABLE), path-based multi-API fan-out on a custom domain never routes, and the refusal contract that tells a client a superseded or deleted rule is gone (404 NotFoundException "Unable to find RoutingRule.") can never be observed — so retry/cleanup logic keyed on it hangs or loops.

Fix: this spans the ApiGatewayV2 domain-name state machine (the handler that must drive DomainNameStatus to AVAILABLE and publish an ApiGatewayDomainName that the front door actually serves with the bound ACM certificate), the RoutingRule handlers and state (CreateRoutingRule/GetRoutingRule/ListRoutingRules/DeleteRoutingRule, including the NotFoundException refusal), the CloudFormation resource provider for AWS::ApiGatewayV2::RoutingRule (terminal stack status, Fn::GetAtt RoutingRuleId/RoutingRuleArn, in-place update vs create-only DomainNameArn replacement), and the custom-domain data-plane dispatcher that must match MatchBasePaths to InvokeApi and answer 403 on no match. Each leg must answer or refuse within the harness budget rather than hanging.

## Steps to Reproduce
1. Import an ACM certificate for a test domain A (root-signed leaf + chain) and poll DescribeCertificate until Status=ISSUED.
2. apigatewayv2 CreateDomainName(DomainName=A, RoutingMode="ROUTING_RULE_ONLY", DomainNameConfigurations=[{CertificateArn:<arn>, EndpointType:"REGIONAL", SecurityPolicy:"TLS_1_2"}]).
3. Poll GetDomainName(DomainName=A) until DomainNameConfigurations[0].DomainNameStatus == "AVAILABLE" and read ApiGatewayDomainName.
4. apigateway: create a REGIONAL REST API with MOCK GET /widgets and GET /gadgets, each integration response returning {"served": "<leaf>"}; create a deployment and a "prod" stage.
5. cloudformation CreateStack with a template whose single resource is AWS::ApiGatewayV2::RoutingRule{DomainNameArn: arn:aws:apigateway:<region>::/domainnames/A, Priority: 100, Conditions: [{MatchBasePaths:{AnyOf:["widgets"]}}], Actions: [{InvokeApi:{ApiId:<api-id>, Stage:"prod"}}]} and Outputs RoutingRuleId / RoutingRuleArn via Fn::GetAtt. Wait for a terminal StackStatus.
6. GetRoutingRule(DomainName=A, RoutingRuleId=<output>) and compare Priority/Conditions/Actions to the template.
7. TLS GET https://A/widgets through the published ApiGatewayDomainName (SNI and Host = A) expecting 200 {"served":"widgets"}, and /gadgets expecting 403.
8. UpdateStack with Priority 200 and MatchBasePaths ["gadgets"]; expect UPDATE_COMPLETE and an unchanged PhysicalResourceId; re-dial /gadgets (200) and /widgets (403).
9. Import a certificate for domain B, create domain B the same way, UpdateStack changing DomainNameArn to B; expect UPDATE_COMPLETE, a NEW PhysicalResourceId/RoutingRuleId, GetRoutingRule(A, old id) refused 404 NotFoundException "Unable to find RoutingRule.", and the rule readable on B.
10. DeleteStack; expect GetRoutingRule(B, new id) refused 404 NotFoundException "Unable to find RoutingRule." and ListRoutingRules(B).RoutingRules == [].
Observed: the run never reaches step 6's assertions — it hangs until the 60 s harness cap with no response and no refusal.
