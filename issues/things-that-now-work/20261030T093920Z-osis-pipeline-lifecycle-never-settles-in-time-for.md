# osis pipeline lifecycle never settles in time for a polling client: multi-leg CREATING/STOPPING/STARTING flows never complete

> _Note: this issue was identified against the code base at commit `e0e11b7672600d6645a012dfa38238750280479b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartPipeline

## Description
Cause 1 of 1: a pipeline's owed status transition is held for a wall-clock dwell, so the read that immediately follows a lifecycle call always still reports the transient status, and every lifecycle leg costs a polling client a whole poll interval. Any flow that chains more than two legs (CreatePipeline -> ACTIVE, StopPipeline -> STOPPED, StartPipeline -> ACTIVE) therefore never reaches its last leg inside the suite's per-check budget, and both checks that exercise the full start/stop lifecycle fail with 'Check timed out after 60.0s' without ever getting to their assertions.

AWS: Smithy GetPipeline (GET /2022-01-01/osis/getPipeline/{PipelineName}, 200) -> Pipeline.Status, of enum com.amazonaws.osis#PipelineStatus = CREATING, ACTIVE, UPDATING, DELETING, CREATE_FAILED, UPDATE_FAILED, STARTING, START_FAILED, STOPPING, STOPPED; StartPipeline and StopPipeline (PUT /2022-01-01/osis/startPipeline/{PipelineName} and .../stopPipeline/{PipelineName}, 200) each answer with the Pipeline in its transient status and model ConflictException (409) for an ineligible status. The model states no provisioning duration, so this is recorded behavior only: against real AWS both checks were recorded green (2/2 replays) and a client polling GetPipeline observes CREATING -> ACTIVE, ACTIVE -> STOPPING -> STOPPED and STOPPED -> STARTING -> ACTIVE, each leg settling on its own and all three legs completing within the check's budget. The requirement is that a pipeline the service reports in a transient status does actually settle into the terminal one, observably, for a client that keeps reading GetPipeline.

Emulator: the owed transition is materialised only after a fixed wall-clock dwell (services/.../src/state.rs: TRANSITION_SPAN = 500ms, applied by StoredPipeline::settle, which refuses to advance while now < pending.due_at). CreatePipeline, StopPipeline and StartPipeline each set pending.due_at = now + TRANSITION_SPAN. A client's follow-up GetPipeline arrives within a few milliseconds over the loopback endpoint, so it is served the transient status (CREATING / STOPPING / STARTING) every time, and the client then sleeps its whole poll interval (20s in these checks) before the next read. Three legs therefore cost >= 60s of pure polling and the check is killed at the 60.0s budget: osis.start-pipeline-when-already-active-rejected dies in the wait for ACTIVE after its restoring StartPipeline, osis.concurrent-start-pipeline-exactly-one-succeeds dies in the wait for ACTIVE after the two concurrent starts. Neither check reaches the behavior it is there to measure, so the StartPipeline ConflictException wording for an already-ACTIVE pipeline ('Only pipelines with one of the following statuses are eligible for starting: STOPPED, START_FAILED, CREATE_FAILED. The current status is ACTIVE.' - fixed text with the eligible-status list and the current status as its variable parts) and the concurrent-duplicate-start idempotency (both racers must see 200, never ConflictException, and the pipeline must make exactly one STOPPED -> STARTING -> ACTIVE transition) are both unverified.
Hypothesis: the dwell is the cause of the timeouts rather than a hang in any single call - the timing is grounded in the check code and the emulator source (3 transient legs x 20s poll interval >= the 60s budget), and matched by the fact that every other osis check in this suite that waits through only ONE transient leg got past its wait and failed later for an unrelated, already-filed reason. The replay gives no per-call latency to confirm it directly.

Why: a client that drives the pipeline lifecycle - wait for ACTIVE, stop, wait for STOPPED, start, wait for ACTIVE - cannot complete against this emulator in bounded time, so CI suites, IaC waiters and SDK waiters that are tuned to AWS's own settling behavior stall or time out on a pipeline the emulator reports as perpetually mid-flight on the read right after the call. Everything gated behind a settled status (StopPipeline's ACTIVE-only precondition, StartPipeline's eligible-status set, PutResourcePolicy's refusal of CREATING, DeletePipeline) becomes reachable only by a caller that happens to wait longer than the dwell, and the start/stop conflict and idempotency semantics above cannot be exercised at all.

Fix: the pipeline lifecycle state machine - crate::state::TRANSITION_SPAN and StoredPipeline::settle in state.rs, plus the three handlers that arm a PendingTransition (create_pipeline.rs, stop_pipeline.rs, start_pipeline.rs). The transition must become observable to the NEXT request that reads the record (owe it to the next observation, not to a wall clock a loopback client always beats), while the operation's own response keeps reporting the transient status it is modelled to report, so the checks that depend on seeing CREATING/STOPPING/STARTING in the lifecycle call's own response still see it.

## Steps to Reproduce
1. Boot the emulator from this checkout and point a botocore osis client at it.
2. CreatePipeline (PipelineName 3-28 chars matching ^[a-z][a-z0-9\-]+$, MinUnits 1, MaxUnits 1, a valid PipelineConfigurationBody).
3. Immediately GET /2022-01-01/osis/getPipeline/{PipelineName} -> observe Pipeline.Status == 'CREATING' (the emulator holds the owed ACTIVE for TRANSITION_SPAN, so any read inside the first 500ms is transient).
4. Poll GetPipeline on a 20-second interval until Status is ACTIVE (it takes one full interval, not the first read).
5. StopPipeline, then immediately GetPipeline -> 'STOPPING'; poll on the same 20s interval until 'STOPPED' (another full interval).
6. StartPipeline, then immediately GetPipeline -> 'STARTING'; poll until 'ACTIVE' (a third full interval). The three legs together exceed 60 seconds of polling.
7. Re-replay behavioral checks osis.start-pipeline-when-already-active-rejected and osis.concurrent-start-pipeline-exactly-one-succeeds to confirm the fix: both must complete inside the 60s budget, the first observing 409 ConflictException with the eligible-status message for an already-ACTIVE pipeline and an unchanged ACTIVE status, the second observing 200 on both concurrent StartPipeline racers and exactly one STOPPED -> STARTING -> ACTIVE transition.
