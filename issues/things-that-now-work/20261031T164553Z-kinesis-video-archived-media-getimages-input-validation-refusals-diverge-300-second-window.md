# GetImages input-validation refusals diverge: 300-second window message reworded and incomplete WidthPixels/HeightPixels pair not refused (2 causes)

## Description

Cause 1 of 2: the GetImages maximum-window refusal is emulator-authored rather than AWS's wording. AWS: Smithy GetImages (POST /getImages, success 200) requires StartTimestamp and EndTimestamp (both target Timestamp) and models InvalidArgumentException (errorKind client, httpError 400). The modeled documentation of GetImagesInput$EndTimestamp states the rule: "The end timestamp for the range of images to be generated. If the time range between StartTimestamp and EndTimestamp is more than 300 seconds above StartTimestamp, you will receive an IllegalArgumentException." The recorded response for a window wider than 300 seconds is HTTP 400 with message 'EndTimestamp must be within 300 seconds of StartTimestamp.' — entirely fixed text; the only value the rule is parameterised by is the 300-second limit the model states, and nothing from the request (no stream name, no timestamp, no computed width) is interpolated. Emulator: the status (400) and error class are right, but the message is 'The time range between StartTimestamp and EndTimestamp must not be more than 300 seconds.' — a differently worded sentence that happens to state the same limit. Why: the message is a requirement of the error class, so a client or operator that matches, logs or asserts on AWS's refusal sentence sees text no AWS region produces; suites pinned to AWS's wording fail against the emulator while suites written against the emulator pass against text AWS never emits. Fix: GetImages' input validation in the operation's handler — emit AWS's fixed sentence for the >300s window refusal instead of the locally composed one, keeping the 300-second limit as the only parameterised part. Traces: kinesisvideoarchivedmedia-get-images-validation-surface#task#6.

Cause 2 of 2: GetImages does not enforce the both-or-neither rule on the WidthPixels/HeightPixels resize pair, so a request naming exactly one side is accepted as well-formed and falls through to the archive lookup. AWS: Smithy GetImages models WidthPixels (@range min 1 max 3840) and HeightPixels (@range min 1 max 2160), both optional, and models InvalidArgumentException (errorKind client, httpError 400) and ResourceNotFoundException (errorKind client, httpError 404). The modeled documentation of GetImagesInput$WidthPixels states the rule: "When both WidthPixels and HeightPixels parameters are provided, the image will be stretched to fit the specified aspect ratio. If only the WidthPixels parameter is provided or if only the HeightPixels is provided, a ValidationException will be thrown. If neither parameter is provided, the original image size from the stream will be returned." The recorded refusal for an incomplete pair is HTTP 400 with message 'Height and width for the images need to be provided or none.' — entirely fixed text, with no part taken from the request or state (no side value, no member name, no stream name is interpolated). It is an input-validation refusal raised BEFORE the archive is consulted, which is what makes it distinguishable from the fragment-absence refusal: on the same stream the fixture's complete-pair step is refused 404 ResourceNotFoundException 'No fragments found in the stream for the GetImages request.', so the ordering of the two checks is part of the requirement. Emulator: the incomplete-pair request is accepted by validation and refused by the later fragment lookup instead — HTTP 404, x-amzn-errortype ResourceNotFoundException, message 'No fragments found in the stream for the GetImages request.' — i.e. a wrong status (404 for 400), a wrong error code and a wrong message, indistinguishable from the complete-pair case. Why: this is an overly-permissive validation gap. A client that sent a half-specified resize gets a 'resource missing' signal rather than a 'bad argument' signal, so it concludes the window holds no media and keeps polling or provisions media instead of correcting the request; and once the stream does hold fragments the emulator will serve images for a resize whose output size is undefined, while AWS refuses the request outright. Fix: GetImages' input validation in the operation's handler — add a cross-member presence check rejecting a request in which exactly one of WidthPixels / HeightPixels is present, raising InvalidArgumentException with AWS's fixed sentence, and order it with the existing per-side range checks so it is evaluated before the stream/fragment lookup, the same way the window checks are. Traces: kinesisvideoarchivedmedia-get-images-validation-surface#task#8.
