# Textract document analysis returns garbled OCR text and extracts no FORMS, TABLES, QUERIES or expense fields from rendered documents

> _Note: this issue was identified against the code base at commit `3b929b447a52a39dfc36e4a4cbd93099ed5ef8cf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AnalyzeDocument

## Description
Replaying the behavioral suite against the emulator booted from this checkout shows the textract data plane now answers HTTP 200 with well-formed Block/ExpenseDocument structures (the earlier placeholder-payload and rejection issues are in the resolved folder), but the CONTENT it reports does not describe the submitted document: the recognized text is garbage and every feature that is derived from that text (FORMS, TABLES, QUERIES answers, AnalyzeExpense summary fields) comes back empty. This issue bundles 5 distinct root causes, all in the textract crate; a fixer must close ALL FIVE before submitting.

Cause 1 of 5 — the OCR recognizer misreads rendered glyphs, so Block$Text is not the document's text.
AWS: Smithy (services/service-com-amazonaws-textract-textract/smithy-model/com-amazonaws-textract-textract.json): DetectDocumentText input {Document required}, output {DocumentMetadata, Blocks, DetectDocumentTextModelVersion}; BlockType enum includes PAGE/LINE/WORD and Block$Text is documented as "the word or line of text that's recognized by Amazon Textract". AWS returns, for a PNG that renders the ASCII line "SIM2REAL <token>", LINE and WORD blocks whose Text is that same text (case preserved), with Confidence in [0,100] and a BoundingBox inside [0,1]. The requirement is that the reported text equals the text drawn in the pixels, for any supplied string — not one recording's string.
Emulator: the block structure, Confidence, Geometry and DetectDocumentTextModelVersion are all present and in range, but the characters are wrong. For the rendered line "SIM2REAL 6XLHG9A2" / "TEXTRACT CHECK" it reported LINE texts ['5|W2HMU 0KUH09Q', 'ZT CH[['], for "S3 SOURCED DOCUMENT" it reported ['ZBU[[UEUW[NT'], and for the async job over "ASYNC TEXTRACT JOB LINE" it reported 'A5YN8TMTETJ0HU|N['. The same garbling appears on the inline-Bytes path, the Document.S3Object path and the asynchronous Get* path, i.e. it is in the single shared recognizer, not in any one handler.
Why: a client uses Textract to read a document. It receives a response that is structurally valid and therefore passes its own schema checks, yet every string in it is corrupt, so downstream matching, indexing and parsing silently operate on text that was never in the document. Because the error is in content rather than in status, nothing in the client signals a failure.
Fix: the glyph recognition in the service's OCR module (crate::state::ocr, reached from crate::state::read_submitted_document / read_content) — the per-glyph classification and word/line segmentation must resolve rendered ASCII glyphs to the characters actually drawn before any block text is emitted. Note this cause is upstream of Causes 2, 4 and 5: those features parse the recognized text, so they cannot be confirmed fixed until this one is.
Traces: textract.detect-document-text-reads-rendered-text, textract.detect-document-text-from-s3-object-source, textract.start-document-text-detection-job-lifecycle.

Cause 2 of 5 — AnalyzeDocument with FeatureTypes=[FORMS] returns no KEY_VALUE_SET blocks for a rendered form.
AWS: Smithy: AnalyzeDocument input {Document required, FeatureTypes required, HumanLoopConfig, QueriesConfig, AdaptersConfig}, output {DocumentMetadata, Blocks, HumanLoopActivationOutput, AnalyzeDocumentModelVersion}; BlockType includes KEY_VALUE_SET, EntityType includes KEY and VALUE, RelationshipType includes VALUE and CHILD. The operation's own documentation states form data is "returned in two Block objects, each of type KEY_VALUE_SET: a KEY Block object and a VALUE Block object", the KEY block carrying a VALUE relationship to its value block and CHILD relationships to the WORD blocks of its text. For a page rendering "Name: John Smith" AWS returns a KEY KEY_VALUE_SET whose CHILD words spell the label and whose VALUE relationship resolves to a block whose CHILD words spell the value.
Emulator: the Blocks list contains no KEY_VALUE_SET block at all — the check fails on `assert kv_blocks, "no KEY_VALUE_SET blocks returned for a form-like document"`. The form derivation (crate::state::form_blocks, via crate::state::blocks with FeatureSet.forms) recognizes a field only from a line that `labelled_split` accepts, i.e. a line of recognized text containing a colon; a raster page whose label text is not recognized correctly yields no such line and therefore no pair.
Why: a client that asks for FORMS gets a 200 whose block list is indistinguishable from a plain DetectDocumentText answer, so its key/value extraction loop finds nothing and it concludes the document contains no form fields rather than that the service failed.
Fix: AnalyzeDocument's FORMS derivation in crate::state (form_blocks / labelled_split, called from crate::state::blocks) — KEY/VALUE pairing must be derived from the page's recognized words and their layout, and must emit the KEY/VALUE EntityTypes with the VALUE and CHILD relationships for a label/value pair on a raster page.
Traces: textract.analyze-document-forms-extracts-key-value-pairs, textract.analyze-document-combined-features-tables-and-forms.

Cause 3 of 5 — AnalyzeDocument/StartDocumentAnalysis with FeatureTypes=[TABLES] detects a table only from tab characters, so a table drawn as ruling lines yields no TABLE or CELL blocks.
AWS: Smithy: BlockType includes TABLE, CELL and MERGED_CELL; Block carries RowIndex/ColumnIndex (1-based) and CHILD relationships. AnalyzeDocument's documentation states "A TABLE Block object contains information about a detected table. A CELL Block object is returned for each cell in a table." StartDocumentAnalysis + GetDocumentAnalysis return the same block set for the S3-hosted document plus AnalyzeDocumentModelVersion. For an image that renders a 2x2 grid of ruled cells containing Item/Price and Widget/10.00, AWS returns one TABLE block with at least four CELL children whose CHILD words carry those cell texts.
Emulator: no TABLE block is produced on either the synchronous or the asynchronous path — `assert table_blocks, "no TABLE block detected in the rendered grid"` and `assert table_blocks, "no TABLE block detected in the async job's rendered grid"`. crate::state::table_blocks/table_runs builds a table from "the page's tab-separated rows" (a contiguous run of lines containing U+0009) and cell_texts splits a line on '\t'. A page rasterized with drawn grid lines contains no tab characters, so the table run set is empty by construction; the async job still reaches SUCCEEDED and reports AnalyzeDocumentModelVersion, so the omission is silent.
Why: TABLES is the reason a client calls AnalyzeDocument instead of DetectDocumentText. It receives a successful response with no TABLE/CELL blocks and concludes the scanned document has no tables, which is wrong for exactly the class of document (a scanned/ruled grid) the feature exists for.
Fix: the TABLES derivation in crate::state (table_runs / table_blocks / cell_texts, reached from crate::state::blocks and shared by GetDocumentAnalysis) — table and cell segmentation must be derived from the recognized words' geometry (column/row bands, ruling lines) for raster pages, not only from tab-delimited character text, and must emit TABLE with CELL children carrying 1-based RowIndex/ColumnIndex and CHILD word relationships.
Traces: textract.analyze-document-combined-features-tables-and-forms, textract.start-document-analysis-async-tables-feature.

Cause 4 of 5 — a QUERY block is returned with no ANSWER relationship and no QUERY_RESULT block.
AWS: Smithy: QueriesConfig{Queries required, @length min 1}, Query{Text required @length 1..200, Alias, Pages}; BlockType includes QUERY and QUERY_RESULT; RelationshipType includes ANSWER. AnalyzeDocument's documentation: "A QUERY Block object contains the query text, alias and link to the associated Query results block object. Query Result. A QUERY_RESULT Block object contains the answer to the query and an ID that connects it to the query asked. This Block also contains a confidence score." So for a document whose pixels render "Invoice Number: INV-99887" and a query "What is the invoice number?", AWS returns the QUERY block linked by an ANSWER relationship to a QUERY_RESULT block whose Text is the answer read from the document.
Emulator: the QUERY block is present and correctly echoes Query.Text and Query.Alias, but it carries no ANSWER relationship, so there is no QUERY_RESULT — `assert answer_ids, "QUERY block has no ANSWER relationship to a QUERY_RESULT block"`. crate::state::query_blocks answers a query by matching the query's terms against crate::state::fields, which are only the colon-labelled lines of the recognized text, and documents "A query the document holds no answer to gets a QUERY block with no ANSWER" — so a document whose label line is not recovered can never produce an answer.
Why: a client using QUERIES reads the answer off the QUERY_RESULT block. It gets its question echoed back with no answer and no error, which it must interpret as "the document does not contain this" — a false negative for a document that plainly does.
Fix: the QUERIES answer derivation in crate::state::query_blocks and the field index it searches (crate::state::fields) — a matched query must emit a QUERY_RESULT block with the answer text and confidence and link it from the QUERY block with an ANSWER relationship; the searchable field set must be built from the page's recognized words rather than only colon-delimited character lines.
Traces: textract.analyze-document-queries-feature-returns-query-block.

Cause 5 of 5 — AnalyzeExpense returns an ExpenseDocument with empty SummaryFields for a receipt.
AWS: Smithy: AnalyzeExpense input {Document required}, output {DocumentMetadata, ExpenseDocuments}; ExpenseDocument{ExpenseIndex, SummaryFields ("Any information found outside of a table by Amazon Textract"), LineItemGroups, Blocks}. For a receipt rendering "RECEIPT", "TOTAL $12.34", "DATE 01/02/2023" AWS returns at least one SummaryField (TOTAL typed, with LabelDetection/ValueDetection) and Blocks whose text contains TOTAL and 12.34.
Emulator: ExpenseDocuments[0]["SummaryFields"] is empty — `assert expense_doc["SummaryFields"], "no SummaryFields extracted from the receipt"`. crate::state::summary_fields (called from crate::state::expense_documents) accepts a line only when `labelled_split` finds a colon on it, so receipt lines of the common "LABEL VALUE" form ("TOTAL $12.34") produce no field even when their text is read correctly; the colon requirement is in addition to the text being garbled by Cause 1.
Why: AnalyzeExpense exists to give a client typed summary fields (TOTAL, DATE, VENDOR) without parsing. It receives a successful response with an empty SummaryFields list, so its expense pipeline silently records a receipt with no total.
Fix: AnalyzeExpense's summary-field derivation in crate::state::summary_fields / labelled_split (shared with the FORMS path) — a label/value pair must be recognized from whitespace-separated and currency-amount receipt lines, not only from colon-delimited ones, and typed through summary_field_type.
Traces: textract.analyze-expense-extracts-summary-fields.
