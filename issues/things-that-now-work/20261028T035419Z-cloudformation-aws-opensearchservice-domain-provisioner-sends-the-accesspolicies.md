# CloudFormation AWS::OpenSearchService::Domain provisioner sends the AccessPolicies policy document as a JSON object, so CreateDomain refuses it with HTTP 400 "Invalid request provided: expected string, got object start" and the stack never creates

> _Note: this issue was identified against the code base at commit `b46de20c42d1d13a6a9554983f2e031495be43a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One root cause, grounded in 1 failing behavioral check whose check-id leading token is the composite 'cloudformation__iam__opensearch__sts'.

Related open issue that does NOT carry this replay key: 20261028T032345Z-ec2-elbv2-opensearch-cloudformation-provisioned-aws-opensearchservice-domain-is-refused-by.md. That issue describes the same deserializer refusal, but its Issue-Key/Issue-Trace-Ids name only ec2__elbv2__opensearch.e2e-opensearch-cognito-alb-timeout-diagnosis-lifecycle, and the replay report does NOT mark the check below as OWNED by it or as ALREADY FILED. Filing this so the cloudformation__iam__opensearch__sts check is also re-replayed when the provisioner mapping is fixed; a fixer closing only that issue would leave this check failing. The two should be verified together.

Cause 1 of 1: CloudFormation cannot provision an AWS::OpenSearchService::Domain whose AccessPolicies property is written in the normal CloudFormation form — a nested policy-document object with intrinsic functions inside it (here Principal.AWS: !GetAtt RoleA.Arn / !GetAtt RoleB.Arn and Resource: !Sub ...). The CreateDomain request the resource provisioner emits carries that member as a JSON object rather than as the JSON string the model requires, the OpenSearch input deserializer refuses the body with HTTP 400, the Domain resource fails with HandlerErrorCode InvalidRequest, and the stack never reaches CREATE_COMPLETE.

AWS: Smithy com.amazonaws.opensearch#CreateDomain (services/service-com-amazonaws-opensearch-amazonopensearchservice/smithy-model/com-amazonaws-opensearch-amazonopensearchservice.json) — POST /2021-01-01/opensearch/domain, success 200. Member AccessPolicies targets com.amazonaws.opensearch#PolicyDocument, which is a STRING with @length {min 0, max 102400} and @pattern '.*' ("Identity and Access Management (IAM) policy document specifying the access policies for the new domain"). Modeled client errors are ValidationException (400) and BaseException (400), plus InvalidTypeException/ResourceAlreadyExistsException/LimitExceededException/DisabledOperationException (409). On AWS, the AWS::OpenSearchService::Domain resource handler accepts AccessPolicies declared as a policy-document OBJECT in the template, resolves the intrinsics inside it, serializes it to a JSON string, and calls CreateDomain — so a template declaring ClusterConfig + EBSOptions + DomainEndpointOptions (EnforceHTTPS true, TLSSecurityPolicy Policy-Min-TLS-1-2-2019-07) + an object AccessPolicies reaches CREATE_COMPLETE, DescribeDomain returns AccessPolicies as a JSON string whose statements name the resolved role ARNs, and the stack publishes its Outputs. For a request that genuinely is ill-typed, AWS answers one of the modeled client errors with a message naming the offending member and the expected type; it never emits a deserializer's internal parser text as the service message. Recorded behavior only for CloudFormation's wrapper, which the recording shows in AWS's documented resource-failure shape: `Resource handler returned message: "<service message> (Service: OpenSearch, Status Code: <status>, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: <code>)` — that frame is the fixed text and <service message>/<status>/<id>/<token>/<code> are per-request values.

Emulator: the Domain resource fails at create time. The stack-level reason is `The following resource(s) failed to create: [Domain]. ` and the resource reason is `Resource handler returned message: "Invalid request provided: expected string, got object start (Service: OpenSearch, Status Code: 400, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)`. In that message the fixed text is `Invalid request provided: expected string, got object start` — it carries no value from the request and names no member; only the request id and request token vary per run, so this is a template-level divergence, not a per-run value difference. Two things diverge: (a) a CreateDomain request real AWS accepts is refused HTTP 400, and (b) the refusal's message is the request deserializer's internal text rather than an AWS message naming the member and the expected type under a modeled error class (ValidationException/BaseException, 400).

Why: a client relying on AWS's behavior cannot deploy an OpenSearch domain through CloudFormation whenever the domain carries a resource policy — the normal case, since AccessPolicies is how a domain is made reachable. The stack ends in rollback, so no Outputs (DomainArn, DomainEndpoint, RoleAArn, RoleBArn here) are ever published and nothing downstream is reachable: the whole change-set/in-place-update flow that swaps Allow/Deny between two !GetAtt-resolved role ARNs is never exercised, and the data-plane verdicts it validates are never reached. Because the failure surfaces as a resource-handler InvalidRequest with raw parser text, an IaC user reads it as a fault in their own template and has no way to tell which property is wrong.

Fix: the CloudFormation AWS::OpenSearchService::Domain resource provisioner's property-to-request mapping — after resolving intrinsics, a policy-document property must be serialized to a JSON string before it is placed in the CreateDomain body, so the forwarded members match the modeled member types. Secondarily, the OpenSearch CreateDomain input deserializer/handler must report a genuine type mismatch through a modeled client error whose message names the member and the expected type, instead of surfacing its internal parser text as the service message.

Traces: cloudformation__iam__opensearch__sts.deploy-opensearch-1-changeset-swaps-allowed-and-denied-roles-in-place (fails in _create_stack_tolerating_role_propagation, before any change set is created). This failure is NOT marked ALREADY FILED or OWNED in the replay report.
