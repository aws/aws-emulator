# eks: 4 net-new root causes — admitted pods never run their containers, CA rotation never settles, a nodegroup node never reports Ready, and the pod-identity webhook never injects the credential env

> _Note: this issue was identified against the code base at commit `8cbf0dcd0020846f13fa76c0319ab04fca2e29a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
Four independent defects in the eks emulator, found by behavioral replay of the five eks checks that are not already owned by an open issue. Each cause below is a SEPARATE defect and must be closed separately; its own failing check ids are listed with it.

Cause 1 of 4: a pod admitted by the served cluster Kubernetes API never runs its containers — it goes straight to phase Failed with an emulator-authored StartError.
AWS: recorded behavior only (the cluster's Kubernetes API server is not part of the EKS Smithy model; the model only publishes Cluster.endpoint and Cluster.certificateAuthority on DescribeCluster). On a real EKS cluster with a registered managed-nodegroup node, a pod scheduled onto that node runs its image: status.phase moves Pending -> Running and, for a one-shot command with restartPolicy Never, -> Succeeded, and each status.containerStatuses entry reports state.terminated.reason "Completed" with exitCode 0 for a command that exits 0. The fixed parts are the phase and reason tokens themselves; the container name and image come from the submitted PodSpec. A genuine start failure on AWS is reported as ImagePullBackOff / CrashLoopBackOff / RunContainerError, never as "StartError" with exit code 128.
Emulator: the pod is scheduled (PodScheduled=True, Initialized=True) and then ends phase "Failed" with reason "StartError" and message "This emulator does not run containers, so the pod's containers were never started"; containerStatuses[0].state.terminated = {reason: "StartError", exitCode: 128, message: the same sentence}, ready=false, started=false, and ContainersReady/Ready are False with reason "ContainersNotReady" and message "containers with unready status: [<container name>]".
Why: every client that verifies a workload actually ran — a Job or one-shot pod, an init container, a readiness gate, a smoke test that reads a pod's logs or exit code, or anything that waits for Running/Succeeded — sees a hard Failed carrying a reason no Kubernetes client knows, and the emulator's own sentence is surfaced to the caller as if it were a cluster condition.
Fix: the pod runtime/state of the served cluster Kubernetes API (the EKS cluster data-plane handler that admits pods and computes their status): an admitted pod must converge to Running and, for a terminating command, Succeeded with terminated reason Completed and exitCode 0, instead of being terminated with a not-implemented reason.
Traces: eks.eks-managed-nodegroup-node-joins-and-runs-a-targeted-pod.

Cause 2 of 4: the certificate-authority rotation lifecycle never reaches a verdict — both end-to-end CA checks exhaust their budget without reaching any assertion.
AWS: Smithy: CreateCertificateAuthority returns a CertificateAuthoritySummary (signingStatus NOT_USED, distributionStatus IN_PROGRESS) plus the Update that tracks trust distribution; CertificateAuthorityDistributionStatus = IN_PROGRESS | COMPLETE | FAILED | DELETING and the operation's own documentation states "The successor CA can't be activated until its distributionStatus is COMPLETE". ActivateCertificateAuthority (POST /clusters/{clusterName}/certificate-authorities/{certificateAuthorityId}/activate) then makes the successor IN_USE and the outgoing CA NOT_USED, and DeleteCertificateAuthority refuses the signing CA with 409 ResourceInUseException and the fixed sentence "Cannot delete the active certificate authority. Activate a different CA first." Each of those transitions is observable to a poller within one polling interval.
Emulator: neither rotation check reaches any of its assertions — both are cut off with "Check timed out after 60.0s" while polling the chain cluster CREATING -> ACTIVE, CA distributionStatus IN_PROGRESS -> COMPLETE, the activation update InProgress -> Successful, signingStatus NOT_USED -> IN_USE and finally the deleted CA leaving ListCertificateAuthorities. No status is ever observed to converge, so neither the activation path nor the protected-signer refusal is exercised.
Hypothesis: every one of those moves is owed only after a stored due instant and is materialised lazily by the next read (see CreateCertificateAuthority's handler doc, and the CLUSTER_ACTIVATION_DELAY / UPDATE_COMPLETION_DELAY constants the CA delay is modelled on), so a caller's first probe immediately after each call always observes the non-terminal status and pays a full polling interval per step; chained across cluster activation, distribution, the activation update, retirement and deletion, the sequence cannot settle inside a client's budget.
Why: a client that rotates a cluster CA cannot complete the documented workflow — it never sees distributionStatus COMPLETE, so it never gets to activate, and the whole rotation is unobservable; the wait hangs instead of failing with a diagnosable status.
Fix: the certificate-authority lifecycle clock in the EKS state slice (the due-instant/materialisation seam for CA distribution, the activation update, the retirement of the outgoing CA and the cluster's UPDATING -> ACTIVE return), so each transition is observable promptly rather than only after a chain of lazily-materialised delays.
Traces: eks.e2e-certificate-authority-activation-to-teardown, eks.e2e-certificate-authority-issue-activate-disable-delete.

Cause 3 of 4: a managed nodegroup's node never reports Ready to the served cluster Kubernetes API, so the DeleteCluster-with-a-dependent refusal is never reached.
AWS: recorded behavior only for the cluster API; Smithy models DeleteCluster's ResourceInUseException (HTTP 409). On a real cluster a managed nodegroup that reaches ACTIVE has its EC2 node registered with the cluster: GET /api/v1/nodes?labelSelector=eks.amazonaws.com/nodegroup=<nodegroup name> returns one Node whose status.conditions carries type "Ready" with status "True" (the label value is the nodegroup name from the request; the node name comes from the instance), and DeleteCluster on that cluster is then refused 409 ResourceInUseException with the message "Cluster has nodegroups attached" (fixed text in its entirety).
Emulator: the check is cut off with "Check timed out after 60.0s" while polling that labelled node collection for exactly one Ready node, after CreateCluster and CreateNodegroup both reported ACTIVE — the nodes collection answers (it is no longer a 404), but no node owned by the nodegroup ever reports Ready within the budget, so neither the refusal nor the post-refusal no-side-effect reads are exercised.
Why: a client cannot verify that a managed nodegroup actually carries compute, and the EKS API's ACTIVE nodegroup is contradicted by a cluster that has no Ready node — so dependency refusals, drains and capacity checks can never be driven.
Fix: the node-registration state behind the served cluster Kubernetes API (the EKS nodegroup data-plane seam that must materialise one Node per nodegroup instance, labelled eks.amazonaws.com/nodegroup=<nodegroup>, and report it Ready once the nodegroup is ACTIVE).
Traces: eks.eks-delete-cluster-with-a-live-node-is-rejected.

Cause 4 of 4: the EKS Pod Identity admission webhook never injects the credential environment into an admitted pod, so the admission retry never resolves.
AWS: recorded behavior only (the webhook is cluster-side, not modelled); EKS documents that with the eks-pod-identity-agent add-on installed and a pod-identity association for a namespace/serviceAccount, the mutating webhook injects AWS_CONTAINER_CREDENTIALS_FULL_URI = "http://169.254.170.23/v1/credentials" and AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE pointing into a projected volume named eks-pod-identity-token whose serviceAccountToken source has audience "pods.eks.amazonaws.com". Smithy: CreatePodIdentityAssociation/DescribePodIdentityAssociation record the clusterName/namespace/serviceAccount/roleArn the association is created with.
Emulator: the check is cut off with "Check timed out after 60.0s" inside the loop that creates the pod, inspects spec.containers[0].env for AWS_CONTAINER_CREDENTIALS_FULL_URI, deletes it and retries — the pod is admitted and echoes its containers, but the credential variables and the projected eks-pod-identity-token volume are never present, so the loop re-admits until the budget ends and the credential-scoping assertions are never reached.
Why: a client cannot obtain pod-identity credentials in a pod at all: without the injected endpoint and token file the AWS SDK inside the workload has no credential source, so neither the allowed-bucket read nor the AccessDenied on an uncovered bucket can be exercised, and a pod-identity misconfiguration is indistinguishable from a working one.
Fix: the admission/mutation path of the served cluster Kubernetes API (the pod-identity webhook seam): when a pod's serviceAccountName and namespace match a stored PodIdentityAssociation of the cluster and the eks-pod-identity-agent add-on is installed, the admitted PodSpec must carry the two credential env vars and the projected token volume with audience pods.eks.amazonaws.com.
Traces: eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied.

Cause 3: 'Check timed out after 60.0s' while polling GET /api/v1/nodes?labelSelector=eks.amazonaws.com%2Fnodegroup=<ng> for exactly one node with Ready=True (600 s budget, 15 s interval) after ListNodegroups showed the nodegroup and DescribeNodegroup reported ACTIVE; the expected follow-on, DeleteCluster -> 409 ResourceInUseException 'Cluster has nodegroups attached', was never reached. ## Steps to Reproduce
1. CreateCluster, wait ACTIVE; CreateNodegroup with a valid scalingConfig, wait ACTIVE. Through the cluster endpoint POST a pod pinned to that nodegroup's node with restartPolicy Never and a busybox command that exits 0, then poll the pod -> observe phase 'Failed', reason 'StartError' and the emulator sentence instead of 'Succeeded'/Completed/exitCode 0 (cause 1).
2. On an ACTIVE cluster: ListCertificateAuthorities (one CA, IN_USE), CreateCertificateAuthority, then poll DescribeCertificateAuthority for distributionStatus COMPLETE, ActivateCertificateAuthority and poll DescribeUpdate for Successful and signingStatus IN_USE, then DeleteCertificateAuthority on the retired CA and poll it out of the listing -> the chain does not converge inside a client budget; each probe pays a full polling interval (cause 2).
3. On a cluster whose nodegroup is ACTIVE: GET /api/v1/nodes?labelSelector=eks.amazonaws.com/nodegroup=<nodegroup> on the cluster endpoint -> no node ever reports Ready=True, so the following DeleteCluster (expected 409 ResourceInUseException 'Cluster has nodegroups attached') is never issued (cause 3).
4. Install the eks-pod-identity-agent add-on, CreatePodIdentityAssociation(clusterName, namespace, serviceAccount, roleArn), create that namespace and ServiceAccount through the cluster API, then POST a pod with that serviceAccountName and read back spec.containers[0].env -> AWS_CONTAINER_CREDENTIALS_FULL_URI / AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE and the projected eks-pod-identity-token volume are absent on every retry (cause 4).
