# iam: every AccessDenied refusal message stops at '...action' and omits AWS's authorization-details trailer (1 cause, 26 checks)

> _Note: this issue was identified against the code base at commit `e4a7a3b48c24597c7ccc34be8282569ef10bbe11`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAccessKeys

## Description
REOPENS 20261028T012639Z-iam-the-implicit-deny-accessdenied-message-no-longer.md: its fix left the call refused. That fixed issue carries the replay key iam.permissions-boundary-alone-never-grants-a-real-signed-call, and that check still fails here on the same refusal with the same truncated AccessDenied message. The fixed issues 20261029T114202Z-iam-the-implicit-deny-accessdenied-message-for-a.md (condition-denied implicit deny) and 20261107T153110Z-iam-the-session-policy-accessdenied-message-omits-aws.md (session-policy deny) asked for the same trailer on the other two refusal flavours and are reproduced too. This is not a new defect: it is the same shared denial-message builder, still truncating.

The open issues 20261117T135333Z-iam-6-net-new-causes-denials-omit-the.md, 20261109T163411Z-iam-3-net-new-causes-denials-omit-the.md and 20261118T021609Z-iam-4-net-new-causes-denials-append-an.md describe this same message family but carry none of the 26 replay keys listed under Traces, so they do not cover them.

=== Cause 1 of 1: the AccessDenied message IAM returns for an authorization refusal ends at '... action' / '... policy' and omits the whole second sentence that points at the request's authorization details ===

AWS: IAM speaks awsQuery (service com.amazonaws.iam#AWSIdentityManagementV20100508, version 2010-05-08). Smithy: the refused operations model no authorization error at all - ListAccessKeys models only NoSuchEntityException (awsQueryError NoSuchEntity, HTTP 404) and ServiceFailureException (ServiceFailure, 500); ListUsers, GenerateCredentialReport and SetSecurityTokenServicePreferences model only ServiceFailureException (plus LimitExceededException on GenerateCredentialReport). AccessDenied / HTTP 403 is a service-common error whose message text the model does not state, so the message requirement is recorded behavior only. The recorded refusal is TWO sentences: the documented deny-reason sentence, then a pointer sentence. Fixed text of the pointer sentence, byte for byte: `. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/` + `<authorization-id>` + ` for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: ` + `<authorization-id>`. The `us-east-1` host and the `region=us-east-1` query parameter are FIXED text (IAM is global and signed in us-east-1), not the caller's region. The only variable part is `<authorization-id>`, the per-request authorization id from the emulator's own authorization context - the checks read that token back out of the received message, so its concrete value is never asserted and is not part of the requirement. The first sentence, whose fixed text varies only by deny reason, is already emitted correctly in all four recorded flavours: `User: <caller-arn> is not authorized to perform: <service>:<Action> on resource: <resource-description> because no identity-based policy allows the <service>:<Action> action`; `... with an explicit deny in an identity-based policy`; `... because no permissions boundary allows the <service>:<Action> action`; `... because no session policy allows the <service>:<Action> action`. Its variable parts come from the signed request and emulator state: `<caller-arn>` (the IAM user or sts assumed-role ARN that signed the request), `<service>:<Action>` (the refused action), `<resource-description>` (how IAM names the evaluated resource for that action - e.g. `user <UserName>`, `role <RoleName>`, a bare `*`, or an ARN).

Emulator: the error code and HTTP status are right (403 / AccessDenied) and the first sentence is right, then the message ENDS. No pointer sentence, and therefore no authorization id, on any of the four flavours. The divergence is the whole missing second sentence, identical on every refusal, not a per-run id or timestamp. One instance, from iam.set-security-token-service-preferences: expected `User: arn:aws:iam::<account>:user/<user> is not authorized to perform: iam:SetSecurityTokenServicePreferences on resource: * because no identity-based policy allows the iam:SetSecurityTokenServicePreferences action. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/<authorization-id> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>`, got `User: arn:aws:iam::<account>:user/<user> is not authorized to perform: iam:SetSecurityTokenServicePreferences on resource: * because no identity-based policy allows the iam:SetSecurityTokenServicePreferences action`. The `<absent>` / `<no authorization id>` / `<authorization-details pointer>` placeholders visible in the replay output are the checks' own fallbacks for 'the marker was not in the message at all', so expected and received differ by exactly the whole sentence. The same single truncation is what fails all 26 checks, across the implicit-deny (e.g. iam.simulate-allow-agrees-with-a-real-signed-call), explicit-deny (iam.sep-policy-composition-securetransport-condition-denied-when-policy-requires-plaintext), permissions-boundary (iam.permissions-boundary-caps-a-real-signed-call, iam.sep-policy-composition-boundary-caps-identity-allow-denied-by-simulator-and-real-call) and session-policy (iam.sep-policy-composition-session-policy-narrows-never-widens-denied-by-simulator-and-real-call) flavours, and whether the resource is a user, a role, an ARN or `*`.

Why: a client that reads AWS's denial text to route an operator to the IAM authorization-details console page, or to extract the authorization id to pass to GetRequestAuthorizationDetails, gets a string with neither. Policy-troubleshooting tooling built on real AWS silently loses its only handle on why a request was denied, and any assertion on the documented full message fails even though the allow/deny decision itself was correct.

Fix: the shared authorization-refusal denial-message builder in the IAM crate - the component that renders the AccessDenied body for iam operations (the same one the fix for 20261028T012639Z touched). It must append the pointer sentence to the refusals AWS records with it, for all four deny reasons, with the console host and the region query parameter pinned to the literal us-east-1 and the authorization id taken from the request's authorization context and repeated in both positions. The deny-reason sentence itself needs no change.

Traces: the 26 check ids in trace_ids, all under the suite's `### iam` heading. Representative assertions: iam.set-security-token-service-preferences (`assert message == expected` on the exact AccessDenied message), iam.permissions-boundary-alone-never-grants-a-real-signed-call, iam.op-contract-list-open-id-connect-providers (expects the pointer with the console URL), iam.iam-eval-deep-iam-1-tag-keys-set-operator-swap-inverts-denied (expected built by its `_with_authorization_details()` helper).
