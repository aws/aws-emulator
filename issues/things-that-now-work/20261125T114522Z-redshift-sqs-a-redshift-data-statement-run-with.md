=== Cause 1 of 1: WithEvent=true publishes no EventBridge statement-status-change envelope, so an SQS target of a rule matching it is never written ===
Failing checks: redshift__sqs.cli-eventbridge-put-rule-wrong-target-arn-negative, redshift__sqs.cli-sqs-purge-queue-then-no-stale-redshift-event-negative

AWS: Smithy (redshift-data) ExecuteStatement, input member WithEvent -> Boolean, documented verbatim as 'A value that indicates whether to send an event to the Amazon EventBridge event bus after the SQL statement runs.' (ExecuteStatementInput$WithEvent). WithEvent is not required and has no modeled default; its absence means no event. When it is true and the statement reaches a terminal status, the Data API publishes exactly one envelope on the account's default EventBridge bus with source 'aws.redshift-data' and detail-type 'Redshift Data Statement Status Change'. In that envelope `account` is the calling account, `region` is the request region, `resources` names the target the statement ran on (for a provisioned cluster, arn:aws:redshift:<region>:<account>:cluster:<ClusterIdentifier>; for the serverless form, the workgroup ARN), and `detail` carries `statementId` equal to the ExecuteStatement response Id and `state` equal to the terminal status ('FINISHED' for these checks). Every one of those values is taken from the caller, the request and the statement record — none of them is fixed text. A rule whose EventPattern names only that source and detail-type therefore forwards the envelope to its SQS target, authorised by the queue's resource policy. (Recorded behavior only for the stall point itself: the replay output carries no frame.)

Emulator: no envelope is ever delivered. Both checks create the cluster subnet group and single-node cluster, wait for ClusterStatus='available', PutRule the source/detail-type pattern, create the queue(s), SetQueueAttributes with a Policy allowing events.amazonaws.com sqs:SendMessage conditioned on aws:SourceArn = the rule ARN, PutTargets, then run `aws redshift-data execute-statement ... --with-event` and poll DescribeStatement to a terminal status. Each then long-polls its correctly-wired SQS target for a body whose detail.statementId equals that statement Id (the checks' own _poll_for_statement_message, timeout_s=180.0, ReceiveMessage WaitTimeSeconds=10). Nothing arrives, so each check sits in that window and is killed by the harness: 'Error: Check timed out after 60.0s'. Hypothesis (neither the model nor the replay output states the stall point): the redshift-data statement state machine performs no EventBridge publication on terminal transition, so the rule has nothing to match. The EventBridge->SQS hop itself is exercised successfully elsewhere in this suite for redshift cluster-event envelopes, which points at the publication rather than the delivery.

Why: a client that uses WithEvent to drive asynchronous completion handling — an EventBridge rule fanning statement-status changes to a queue, a Lambda or a Step Functions execution — waits indefinitely with no error and no signal that distinguishes 'WithEvent was honoured' from 'WithEvent was silently ignored'. Both of these checks are additionally negative-delivery checks, so every graded assertion they exist to make is downstream of that one delivery and is never evaluated: the wrong-target-ARN check cannot show that PutTargets accepts a same-account ARN naming a nonexistent queue (FailedEntryCount=0) and that the event then lands only on the correctly wired target, and the purge check cannot show that a PurgeQueue-deleted message stays gone past its documented 60-second window while a fresh statement's event is still delivered with its own statementId. An emulator that delivers nothing at all satisfies both absence halves vacuously, so a real over-delivery regression on this wiring is undetectable.

Fix: the redshift-data ExecuteStatement handler and the statement state machine that moves a statement to a terminal status. On terminal transition, and only when the request set WithEvent=true, publish one envelope to the default EventBridge bus with source 'aws.redshift-data', detail-type 'Redshift Data Statement Status Change', account/region from the caller and request, resources naming the cluster (or workgroup) ARN resolved from the request, and detail.statementId / detail.state from the statement record, so the existing rule-to-SQS routing delivers it. A statement submitted without WithEvent must publish nothing.

## Evidence
Expected (both checks): after `aws redshift-data execute-statement --cluster-identifier <cluster> --database dev --db-user <user> --sql 'SELECT 1' --with-event` on an available single-node cluster reaches Status=FINISHED, ReceiveMessage on the SQS queue targeted by a rule whose EventPattern is {"source":["aws.redshift-data"],"detail-type":["Redshift Data Statement Status Change"]} returns a message whose JSON body has detail.statementId equal to the ExecuteStatement Id and detail.state='FINISHED', with account/region/resources taken from the caller, the request region and the cluster ARN.

Actual (both checks): 'Error: Check timed out after 60.0s', reported with no stack frame. ExecuteStatement is accepted and DescribeStatement reaches a terminal status, but no envelope ever reaches the correctly-wired queue, so each check never leaves its first delivery long-poll and is killed before any graded assertion runs. Verdicts recorded as mismatch for redshift__sqs.cli-eventbridge-put-rule-wrong-target-arn-negative and redshift__sqs.cli-sqs-purge-queue-then-no-stale-redshift-event-negative. No HTTP status or error code diverges here — the divergence is a missing asynchronous publication, not a refusal.
