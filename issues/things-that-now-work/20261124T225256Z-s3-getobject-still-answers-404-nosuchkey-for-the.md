Message anatomy: 'The specified key does not exist.' is NoSuchKey's fixed AWS text and 'Key' is the key copied verbatim from the request, so the refusal is correctly WORDED — the defect is that it is served at all for a key AWS has by this point in the flow; RequestId and HostId are per-run values and are not part of this finding. Hypothesis: there is no s3files-to-S3 write-through path, so nothing the file system receives is ever materialised as an object; in this fixture the in-guest write is additionally never performed, because the SSM Run Command invocation that mounts and writes ends Status 'Failed' with ResponseCode 1 (step task#29 of this same fixture, owned by the two ssm issues named above).

Why: the premise of s3files is that file-system writes ARE S3 objects. A client that writes through the mount and then reads the key with the S3 API — the canonical round trip, and how data-landing checks, ETL hand-offs and lifecycle rules observe the data — gets a hard 404 for the whole polling window and concludes the data was lost; SDK retries cannot help and any 'object exists' precondition fails. Because the body never arrives, every downstream assertion is unreachable too: byte equality, CRC64NVME/FULL_OBJECT checksum reporting, SSE state, the inferred content type, and the POSIX/provenance metadata a permission-preserving restore reads back from x-amz-meta-file-* / x-amz-meta-fs-id.

Fix: the s3files file-system write path and the S3 object state it must write into — the write-through that materialises the key with its bytes, size, etag, inferred content type, version id, SSE state and CRC64NVME/FULL_OBJECT checksum, plus the x-amz-meta-file-*/fs-id/user-agent user-metadata stamping. The GetObject handler's 404/NoSuchKey branch needs no change once the object exists; any residual gap in projecting those members then belongs in the GetObject response-header serializer. The ssm Run Command failure named above is a prerequisite for the in-guest write to run at all.
