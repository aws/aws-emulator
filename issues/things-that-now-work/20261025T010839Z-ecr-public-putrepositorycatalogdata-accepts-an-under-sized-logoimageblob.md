# ECR Public: PutRepositoryCatalogData accepts an under-sized logoImageBlob instead of refusing it with InvalidParameterException 'Invalid image dimensions.' (1 cause)

> _Note: this issue was identified against the code base at commit `a0c9c8ccc8bc5abababeef7ae6993b0ce3338eb3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Behavioral replay of the simparity-behavioral-ga-prod-v1 suite (61/75 passed; ecr-public 61/74, the emulator IS serving and implemented ops answer 200/400, so this is not a bootstrap gap) surfaced ONE net-new root cause on PutRepositoryCatalogData that no already-filed issue carries. This cause must be closed before this issue is resolved.

NOTE on overlap: the open issue 20261023T055032Z-ecr-public-getauthorizationtoken-is-not-authorization-gated-stored.md already carries this same check id, but for a DIFFERENT leg of it — its cause 3 (the generic '1 validation error detected' template on the OVER-LENGTH 512001-byte blob) and its cause 2 (the minted logoUrl is never served). The replay report did not mark this check OWNED, i.e. its replay key is new.

=== Cause 1 of 1: an image below the 60x60-pixel floor is accepted (HTTP 200, a logoUrl is minted) instead of being refused with InvalidParameterException ===
AWS: Smithy RepositoryCatalogDataInput.logoImageBlob is a blob with @length min 0 / max 512000 ("The base64-encoded repository logo payload"); PutRepositoryCatalogData models InvalidParameterException (errorKind client, httpError 400) — plus RepositoryNotFoundException, UnsupportedCommandException (400) and ServerException (500). The model carries NO dimension trait, so for the pixel floor this is recorded behavior only: measured against real ECR Public (us-east-1), on top of the modeled byte cap the service also validates that the logo decodes as an image and meets a minimum of 60 pixels in BOTH axes. The boundary is exact and per-axis — 59x59, 59x60 and 60x59 are each refused with HTTP 400, error code InvalidParameterException, while 60x60, 63x63, 64x128, 320x240 and 2048x2048 are accepted. The refusal message is a deterministic function of the request (the member path plus the rule that failed), so the template is the requirement; an example is "Invalid parameter at 'logoImageBlob' failed to satisfy constraint: 'Invalid image dimensions.'". It must NOT be the length refusal in disguise: the dimension refusal does not mention the 512000-byte maximum, and the two constraints share the code but differ in the rule they name.
Emulator: a structurally valid 59x60 greyscale PNG of 1024 bytes — well inside the byte cap, so its only defect is its pixel size — is ACCEPTED. The call answers HTTP 200 with {'catalogData': {'description': ..., 'logoUrl': 'https://public.ecr.aws/logos/<repo>/<sha256>'}}: the emulator validates only the modeled @length trait, mints a logoUrl for the under-sized image, and raises no error at all. The check's _err() helper reports "expected a ClientError, but the call succeeded and returned {... 'HTTPStatusCode': 200 ...}".
Why: this is an over-permissive accept on externally published data. A publishing client that uploads an under-sized logo gets a 200 and a URL from the emulator and believes a Gallery logo was published; the same code against AWS gets 400 InvalidParameterException and must resize or re-encode the asset, so the error-handling branch (and any pre-upload resize) is never exercised. Because the only signal that the blob was stored is the minted logoUrl, the emulator actively manufactures evidence of a success AWS refuses. It also makes the two distinct blob constraints indistinguishable: a client that tells "too big" apart from "wrong dimensions" cannot do so against the emulator, since one of the two conditions produces no error.
Fix: the PutRepositoryCatalogData handler's catalogData validation (the logoImageBlob leg, alongside the modeled length check, in services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/ops/put_repository_catalog_data.rs and the catalog-data validation it calls in src/state.rs) must decode the uploaded image, reject any image under 60 pixels in either axis with the modeled InvalidParameterException (400) naming 'logoImageBlob' and the invalid-dimensions rule, mint no logoUrl, and leave the stored catalog (description and previous logoUrl) untouched. It must stay distinct from the over-length refusal, which names the 512000-byte rule.
Traces: ecr-public.catalog-logo-blob-is-input-only-and-size-capped.
