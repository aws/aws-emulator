# eks: 3 net-new root causes in the served cluster Kubernetes API — no OpenAPI schema document is served, DELETE is answered 405 MethodNotAllowed, and admitted pods never run their containers

> _Note: this issue was identified against the code base at commit `ce4ee9e56b2f664f3ccf49966acace7716de13e8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
THREE separate net-new root causes in the Kubernetes API the EKS emulator serves at cluster.endpoint (DescribeCluster publishes it, Smithy models only Cluster.endpoint/Cluster.certificateAuthority — the API's own behavior is recorded behavior only). Each cause below is a SEPARATE defect and must be closed separately; its own failing check ids are listed with it.

Cause 1 of 3: the served cluster Kubernetes API serves no OpenAPI schema document that a kubectl client can consume, so EVERY `kubectl apply` fails client-side validation before any request is sent.
AWS:      recorded behavior only. A real EKS cluster's apiserver answers GET /openapi/v2 and GET /openapi/v3 (and the per-group /openapi/v3/apis/... documents) anonymously-authenticated for an authorized principal with HTTP 200 and a content type the client negotiated — for v2 `application/com.github.proto-openapi.spec.v2@v1.0+protobuf` (or `application/json` when that is what the Accept header offers), for v3 `application/json`. kubectl downloads that document to validate a manifest, so `kubectl apply -f -` of a well-formed Deployment/ConfigMap/Service/HorizontalPodAutoscaler/ResourceQuota/Role manifest succeeds. The fixed text of the client-side failure a missing document produces is kubectl's own, not AWS's; the requirement is that the document is served at all with a negotiated content type.
Emulator: kubectl aborts with rc=1 and `error: error validating "STDIN": error validating data: failed to download openapi: the server was unable to respond with a content type that the client supports; if you choose to ignore these errors, turn validation off with --validate=false` — i.e. the OpenAPI endpoints either do not exist or answer with a content type outside the client's Accept set. No apply ever reaches the apiserver, so the whole declarative data plane (deployments, scaling, rolling updates, services, configmaps, RBAC roles, resource quotas, HPAs) is unreachable through kubectl.
Why:      a client cannot use kubectl, Helm, kustomize or any controller that validates against the cluster's schema; every GitOps/deploy flow against an emulated EKS cluster dies before contacting the server, and the only workaround (--validate=false) is not what a real client does.
Fix:      the served cluster Kubernetes API's discovery/schema surface (the EKS cluster data-plane handler that must route /openapi/v2 and /openapi/v3[/apis/...] and content-negotiate them against the Accept header).
Note:     the open issue 20261115T110546Z-ecr-eks-logs-eks-the-served-cluster-kubernetes-api-exposes-no.md describes this same unserved-OpenAPI behavior, but it carries only the ecr__eks__logs replay key it was filed from; none of the eleven eks checks below is owned by it, and they reproduce at this commit.
Traces:   eks.hpa-min-replicas-above-max-replicas-rejected, eks.hpa-scales-out-under-cpu-load-and-back-in-when-it-stops, eks.hpa-target-without-a-cpu-request-is-blocked-from-scaling, eks.k8s-configmap-mounted-value-readable-inside-the-pod, eks.k8s-deployment-apply-runs-pods-on-real-nodes, eks.k8s-deployment-scale-converges-to-the-requested-replicas, eks.k8s-rbac-get-only-role-rejects-deleting-a-pod, eks.k8s-resourcequota-rejects-a-pod-over-the-namespace-limit, eks.k8s-rolling-update-replaces-pods-without-dropping-the-service, eks.k8s-service-clusterip-load-balances-across-pods, eks.kubectl-applied-deployment-pod-runs-and-serves-its-configmap-through-a-service.

Cause 2 of 3: the served cluster Kubernetes API accepts no DELETE at all — deleting a namespace or a namespaced object is answered 405 MethodNotAllowed, so objects cannot be removed and an RBAC-denied delete is never even authorized.
AWS:      recorded behavior only. A real apiserver answers DELETE /api/v1/namespaces/<ns> with 200 and the Namespace object in phase Terminating, and DELETE /api/v1/namespaces/<ns>/configmaps/<name> with 200 and a Status object (status "Success"). When the caller's RBAC does not permit the verb, the answer is 403 with reason Forbidden and the apiserver's forbidden sentence — fixed text `<subject> cannot delete resource "<resource>" in API group "" in the namespace "<namespace>"`, where the subject (e.g. `system:serviceaccount:<ns>:<sa>`), resource, API group and namespace are taken from the request and the bound Role/RoleBinding; kubectl renders it as `Error from server (Forbidden): ...`. Authorization is evaluated only for a verb the server routes, so 403 — never 405 — is the refusal a denied delete gets.
Emulator: `Error from server (MethodNotAllowed): the server does not allow DELETE on /api/v1/namespaces/<ns>` and `Error from server (MethodNotAllowed): the server does not allow DELETE on /api/v1/namespaces/<ns>/configmaps/<name>` (HTTP 405). In the RBAC check the reader ServiceAccount's forbidden delete is therefore reported as MethodNotAllowed with no `(Forbidden)` marker and none of AWS's sentence, so a permitted-vs-denied contrast is indistinguishable: both verbs fail the same way for the wrong reason. (Open issues 20261113T151622Z-ecr-eks-logs-2-net-new-root-causes.md and 20261114T130859Z-ecr-eks-logs-2-net-new-root-causes-b62cb4.md record 405 MethodNotAllowed for ConfigMap CREATE and the core/v1 events collection respectively; neither covers the DELETE verb or these checks.)
Why:      no client can tear down what it created (kubectl delete, Helm uninstall, a controller's garbage collection, a test's cleanup), and every authorization test reads a transport-level 405 where it must see a 403 Forbidden carrying the subject and resource — so RBAC appears neither enforced nor reportable.
Fix:      the request routing and authorization path of the served cluster Kubernetes API (the EKS cluster data-plane handler's verb table): route DELETE for namespaces and namespaced resources, evaluate the caller's RBAC for it, and answer 200 with the Status/object on success or 403 Forbidden with the apiserver's sentence when the bound role lacks the verb.
Traces:   eks.eks-kubectl-namespace, eks.kubectl-denied-verb-returns-the-exact-forbidden-message-while-a-permitted-verb-succeeds.

Cause 3 of 3: a pod admitted by the served cluster API is scheduled but never runs its containers — it ends phase Failed with an emulator-authored StartError, so a nodegroup taint/toleration contrast cannot be observed.
AWS:      recorded behavior only. On a real cluster a pod that tolerates a nodegroup's taint is scheduled onto that node and runs its image: status.phase goes Pending -> Running and, for a one-shot command with restartPolicy Never that exits 0, -> Succeeded, with containerStatuses[].state.terminated.reason "Completed" and exitCode 0. The phase and reason tokens are fixed text; the container name and image come from the submitted PodSpec. A genuine start failure on AWS is ImagePullBackOff / CrashLoopBackOff / RunContainerError — never "StartError" with exitCode 128.
Emulator: the pod is scheduled (PodScheduled=True, Initialized=True) and then ends phase "Failed", reason "StartError", message "This emulator does not run containers, so the pod's containers were never started"; containerStatuses[0].state.terminated = {reason: "StartError", exitCode: 128, message: the same sentence}, ready=false, started=false, with ContainersReady/Ready False (reason "ContainersNotReady", message "containers with unready status: [<container name>]"). The emulator's own limitation sentence is surfaced to the client as a pod condition.
Why:      a client cannot verify that a workload ran: a Job, init container, readiness gate or smoke test that waits for Running/Succeeded sees a hard Failed with a reason no Kubernetes client understands, and taint/toleration scheduling semantics cannot be distinguished from a broken image.
Fix:      the pod runtime/status computation of the served cluster Kubernetes API (the EKS cluster data-plane handler that admits pods and materialises their status) — an admitted pod must converge to Running and, for a terminating command, Succeeded with terminated reason Completed and exitCode 0.
Note:     the open issue 20261121T142446Z-eks-4-net-new-root-causes-admitted-pods.md states this same class as its Cause 1, but carries only the eks.eks-managed-nodegroup-node-joins-and-runs-a-targeted-pod replay key; it does not cover the check below, which reproduces the identical sentence at this commit.
Traces:   eks.nodegroup-taint-effect-is-translated-and-repels-an-untolerating-pod.
