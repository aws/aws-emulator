# iot: 7 net-new causes — the published iot:Data-ATS MQTT broker completes no session (11 checks), GetEffectivePolicies ignores its identity requirement and the thing-group walk, and three refusal messages are emulator-authored

> _Note: this issue was identified against the code base at commit `8470bd15600894c04d6297f04472e87ed5582e16`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetEffectivePolicies

## Description
Seven net-new root causes in the iot service, each failing behavioral check the replay report marks neither ALREADY FILED nor OWNED. SEVEN causes must be closed before submitting; each is numbered with its own failing check ids.

Cause 1 of 7: no MQTT session can be established at the published iot:Data-ATS endpoint, so every native-MQTT behavior check hangs to its budget.
AWS: recorded behavior only. DescribeEndpoint(endpointType="iot:Data-ATS") returns a host that serves MQTT over TLS on port 8883 with mutual TLS; a CONNECT presenting an ACTIVE certificate whose attached policy allows iot:Connect for the client ARN is answered CONNACK with return code 0 (and 5/connection-refused when the policy does not allow it), after which SUBSCRIBE/PUBLISH, QoS1 persistent-session queueing, last-will on an ungraceful close, retained-message replay and $aws/things/* job topics all work, and GetThingConnectivityData reports connected=true while the session is open.
Emulator: the TLS connection to the published address is accepted but no CONNACK ever arrives — paho's on_connect never fires (the connectivity checks poll the callback's return code for 20 s and it stays None: "condition not met within 20.0s; last value=None"), and the nine behavior checks that need a live session run to the harness's 60 s budget ("Check timed out after 60.0s"). No verdict is reached on any MQTT semantics: authorization at CONNECT, topic-scoped publish/subscribe confinement, QoS0-vs-QoS1 offline behavior, last will, rule republish to a native subscriber, job-document delivery and device-reported completion, and connectivity indexing.
Why: this is the whole device-facing data plane. A device SDK cannot connect at all, so nothing a real fleet does is possible against the emulator, and every policy decision the broker is supposed to enforce (allow/deny at CONNECT, per-topic publish and subscribe) is unobservable rather than merely wrong.
Fix: the native MQTT listener behind the address DescribeEndpoint publishes — it must complete the MQTT CONNECT handshake (CONNACK) on the mTLS connection it already accepts, then serve session state, subscriptions and QoS1 queueing; and the IoT policy evaluation that gates CONNECT/PUBLISH/SUBSCRIBE on that path.

Cause 2 of 7: GetEffectivePolicies with thingName and no identity member answers 200 instead of refusing the request.
AWS: Smithy — GetEffectivePolicies (POST /effective-policies) takes principal, cognitoIdentityPoolId and thingName (httpQuery, @length 1..128, pattern ^[a-zA-Z0-9:_-]+$) as three optional members and models InvalidRequestException @httpError 400. Recorded behavior: AWS requires an IDENTITY (principal or cognitoIdentityPoolId) before anything else and refuses a thingName-only request — and a no-arguments request identically — with HTTP 400, InvalidRequestException and the message "Both principal and CognitoIdentityPoolId can not be null." The message is entirely fixed text with no variable part. A Cognito identity pool that does not exist is instead HTTP 404 ResourceNotFoundException "IdentityPool '<region>:<pool-id>' not found." — fixed text "IdentityPool '" ... "' not found." with the pool id echoed from the request.
Emulator: get_effective_policies(thingName=<an existing thing attached to a certificate that holds a policy>) answers HTTP 200 with {"effectivePolicies": []} — no refusal at all.
Why: a caller that forgot the identity member is handed a plausible authorization answer AWS would never produce. An audit that asks "which policies govern this device?" concludes the device is ungoverned on the strength of a response the real API rejects, and nothing signals the request was malformed.
Fix: the GetEffectivePolicies handler's identity-member validation — refuse before resolving any scope, with that fixed text, and keep the Cognito-pool 404 wording above.
Traces: iot.get-effective-policies-reflects-principal-attachment. (The open WIRE issue 20261113T063920Z-iot-geteffectivepolicies-diverges-on-5-causes-identity-validation.md reports the same handler from wire fixtures and carries none of this check's key; it does not cover this check.)

Cause 3 of 7: GetEffectivePolicies(principal, thingName) does not resolve a policy attached to the thing's thing group.
AWS: Smithy — the operation's output is EffectivePolicies, each entry exactly policyName + policyArn + policyDocument. Recorded behavior: thingName is optional CONTEXT that extends the resolution to the policies attached to the thing groups the named thing belongs to. With a policy attached only to a thing group, GetEffectivePolicies(principal=<cert ARN of a certificate attached to the thing>) returns an empty list (the certificate alone cannot reach the group), while GetEffectivePolicies(principal=<same cert ARN>, thingName=<the thing>) returns exactly that one policy with its own ARN and its default version's document.
Emulator: the thingName-qualified call returns [] — the certificate -> thing -> thing-group walk is absent (the principal-only call's empty answer is correct, and ListAttachedPolicies on the group does report the attachment, so the attachment state is present and only this resolution is missing).
Why: thing-group attachment is how fleets grant permissions at scale. A client verifying a device's effective permissions sees none, concludes the device is unauthorized (or that its group attachment did not take), and re-attaches policies per-certificate — the opposite of the model AWS documents.
Fix: the GetEffectivePolicies handler's resolution, which must union the principal's own attached policies with those attached to the thing groups of the thingName given (including parent groups), reading the same attachment state ListAttachedPolicies serves.
Traces: iot.iot-thing-group-policy-resolves-only-with-thingname.

Cause 4 of 7: CreateFleetMetric's Percentiles-on-a-string-field refusal is worded by the emulator.
AWS: Smithy — CreateFleetMetric (PUT /fleet-metric/{metricName}) requires queryString, aggregationType, aggregationField and period, and models InvalidRequestException @httpError 400 (alongside InvalidAggregationException 400). Recorded behavior: Percentiles over a string-typed index field is refused HTTP 400 InvalidRequestException with the message "Invalid dataType String for field registry.thingTypeName. Only Number dataType is allowed for Percentiles aggregation" — fixed text "Invalid dataType ", " for field ", ". Only Number dataType is allowed for Percentiles aggregation", with the field's data type and the request's aggregationField as the variable parts; no metric is created, and Cardinality over the same field succeeds.
Emulator: right status and right error class, but the message is "Percentiles aggregation is not supported on String field" — different fixed text that names neither the offending field nor the allowed dataType.
Why: the message is the only part of the refusal that tells the caller which aggregationField to change; a client or test matching AWS's sentence (or parsing the field name out of it) never matches, and an operator is told nothing about which field failed.
Fix: the CreateFleetMetric handler's aggregation/field-type validation message.
Traces: iot.create-fleet-metric-invalid-aggregation-rejected. (Related open issue 20261114T082236Z-iot-refusal-message-fidelity-7-causes-addthingtothinggroup-createstream.md owns the differently-named fleet-metric checks and not this one.)

Cause 5 of 7: UpdateThingGroup's not-found refusal uses the shared account-qualified registry sentence.
AWS: Smithy — UpdateThingGroup (PATCH /thing-groups/{thingGroupName}) models ResourceNotFoundException @httpError 404. Recorded behavior: for a group that does not exist (here, one just deleted) the refusal is HTTP 404 ResourceNotFoundException with the message "Group <thingGroupName> does not exist" — fixed text "Group " and " does not exist", no trailing period, no account id, the group name taken from the {thingGroupName} URI label. DescribeThingGroup for the same deleted group is correctly answered "ThingGroup <account>:<name> not found." by this emulator, so only the update path's wording diverges.
Emulator: answers 404 with "ThingGroup <account>:<thingGroupName> not found." — the describe-path formatter, with a resource type spelled as one word, an account-qualified name AWS does not include, and a trailing period.
Why: a client that branches or logs on the service's refusal text gets a sentence AWS never sends for this operation, and the leaked "<account>:" prefix makes the response read as being about a differently named resource.
Fix: the UpdateThingGroup handler's not-found refusal path — it must emit this operation's own fixed text rather than the shared "<Type> <account>:<name> not found." formatter.
Traces: iot.deleted-thing-group-blocks-reads-writes-sibling-unaffected. (Same formatter family as open issue 20261115T093926Z-iot-updatething-s-resourcenotfoundexception-message-is-account-qualified.md, which is about UpdateThing and carries neither this operation nor this check.)

Cause 6 of 7: the tag plane's thing-ARN refusal names the ARN instead of the unsupported resource type.
AWS: Smithy — ListTagsForResource (GET /tags, resourceArn httpQuery, required) and TagResource (POST /tags) both model InvalidRequestException @httpError 400. Recorded behavior: an IoT thing ARN is not a taggable resource for these operations; both are refused HTTP 400 InvalidRequestException with the message "Invalid resource type in ARN: thing" — fixed text "Invalid resource type in ARN: " with the resource type parsed out of the request's resourceArn as the only variable part. The same two calls against a thing-group ARN succeed and read/modify that group's tags.
Emulator: answers 400 InvalidRequestException with "Invalid ResourceArn: <the whole ARN>" — different fixed text, and it echoes the full ARN where AWS reports only the offending resource type.
Why: the refusal is supposed to tell a caller that the resource TYPE is not taggable (so it stops retrying with that ARN shape); the emulator's text reads as a malformed-ARN complaint, so a client reformats a perfectly valid ARN instead, and assertions keyed to AWS's sentence never match.
Fix: the shared tag-plane resourceArn validation used by the ListTagsForResource and TagResource handlers — refuse with the resource type extracted from the ARN in AWS's fixed text.
Traces: iot.tag-resource-and-list-tags-reject-thing-arn-but-apply-to-thing-group.
