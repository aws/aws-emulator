# cloudwatch__sfn: an activity-backed Task state never enqueues a task, so GetActivityTask hands out no token and the late-answer TaskTimedOut refusal plus the AWS/States timed-out counters are unreachable (1 cause)

> _Note: this issue was identified against the code base at commit `e730bd97e23027ce38421dab7cedb53db537ccde`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetActivityTask

## Description
One net-new root cause, grounded in the single failing behavioral check the replay report left unmarked (no ALREADY-FILED marker and no OWNED marker on its line). Every other failure in this run was marked ALREADY FILED or OWNED and was skipped.

Cause 1 of 1 — a RUNNING execution whose Task state names an activity ARN never enqueues a task against that activity. GetActivityTask therefore long-polls forever without ever returning a taskToken, so the entire activity-worker scenario behind this check (claim -> let the Task state's TimeoutSeconds elapse -> late SendTaskSuccess refused with TaskTimedOut -> AWS/States counters) is unreachable.
Failing check id: cloudwatch__sfn.metrics-states-stream-late-activity-result-rejected-after-task-timeout-and-only-timed-out-moves.

AWS: Smithy (services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json) models GetActivityTask with input {activityArn (required, @length 1..256), workerName (@length 1..80)} and output {taskToken (@length 1..2048, @sensitive), input (@length 0..1048576, @sensitive)}; its modeled errors are ActivityDoesNotExist, ActivityWorkerLimitExceeded, InvalidArn, KmsAccessDeniedException, KmsInvalidStateException, KmsThrottlingException, all HTTP 400. In AWS, as soon as an execution enters a Task state whose Resource is an activity ARN the task is enqueued against that activity and the next long-poll returns a NON-EMPTY taskToken together with the state input. SendTaskSuccess is modeled with input {taskToken (required), output (required, @length 0..262144)} and among its modeled errors are TaskDoesNotExist, InvalidToken and TaskTimedOut (all HTTP 400). The behavior graded on top of delivery: when the worker answers AFTER the Task state's TimeoutSeconds has elapsed, the Task has already timed out, so (a) the execution is already terminal FAILED with error exactly "States.Timeout" and carries NO output member, and (b) SendTaskSuccess with that stale token is refused with HTTP 400 and error code exactly TaskTimedOut. The error-code string TaskTimedOut and the error-name string States.Timeout are the fixed requirement; the token, ARNs and the TimeoutSeconds value are request/state-supplied. The refused late answer must change nothing: a subsequent DescribeExecution still reports status FAILED and still has no output. The CloudWatch consequence is recorded behavior only (the Smithy model does not describe AWS/States publication): namespace AWS/States moves ActivitiesTimedOut under Dimensions exactly [ActivityArn=<subject activity>] and ExecutionsFailed under Dimensions exactly [StateMachineArn=<subject machine>], while ActivitiesSucceeded and ExecutionsSucceeded for the subject, and ExecutionsTimedOut for the subject machine, stay at zero; the in-time control machine on a second activity, driven by the same worker in the same window, moves exactly ActivitiesSucceeded and ExecutionsSucceeded and does NOT move ActivitiesTimedOut or ExecutionsFailed. AWS publishes the untouched counters as explicit zero-valued datapoints in the same batch as the moved ones.

Emulator: the check is killed by the harness with "Error: Check timed out after 60.0s" while still inside its _poll_task helper, which calls GetActivityTask in a loop with its own 120 s budget. No taskToken is ever handed out for either the subject activity or the control activity — GetActivityTask answers without the member rather than refusing — so SendTaskSuccess is never called, neither execution ever leaves RUNNING, the States.Timeout failure never happens, the TaskTimedOut refusal is never produced, and no AWS/States datapoint under either the ActivityArn or the StateMachineArn dimension is ever written or read.

Why: a client built on the first-class activity-worker pattern (CreateActivity -> Task whose Resource is the activity ARN -> long-poll GetActivityTask -> SendTaskSuccess/SendTaskFailure) never receives work and gets no error explaining why; its executions hang in RUNNING indefinitely and TimeoutSeconds is never enforced. Worse for correctness testing, the guard AWS uses to stop a slow worker from corrupting an already-failed execution — the TaskTimedOut refusal of a late SendTaskSuccess — is never exercised, so code that wrongly accepts a late result passes against the emulator and fails in production. Operational tooling that reads AWS/States counters sees an empty namespace, so dashboards and alarms built on activity-level and execution-level attribution silently read zero.

Fix: the activity task scheduling path shared by the interpreter's Task-state handler and the GetActivityTask handler/state — entering a Task state whose Resource is an activity ARN must enqueue a task against that activity, and GetActivityTask must dequeue it and mint a token carrying the state input. Then the Task-state timeout path (mark the outstanding token timed out, fail the execution with error States.Timeout and no output), the SendTaskSuccess validation that must answer a timed-out token with TaskTimedOut and leave the execution untouched, and the AWS/States metric emission for ActivitiesTimedOut / ActivitiesSucceeded under the ActivityArn dimension and ExecutionsFailed / ExecutionsSucceeded / ExecutionsTimedOut under the StateMachineArn dimension.

Variable parts taken from the request/state: the activity ARNs, the state-machine ARNs, the execution ARNs, the task tokens and the TimeoutSeconds value.
