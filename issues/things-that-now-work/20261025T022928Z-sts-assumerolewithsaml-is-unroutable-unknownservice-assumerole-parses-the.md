# STS: AssumeRoleWithSAML is unroutable (UnknownService), AssumeRole parses the session policy before authorizing, and GetFederationToken is served to session credentials (3 causes)

> _Note: this issue was identified against the code base at commit `41653b1a2410c65454bc5a3f409b81a56735e5e0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRoleWithSAML

## Description
This issue bundles THREE distinct net-new root causes in the STS service (service token `sts`). A fixer must close all three before submitting; each cause names its own failing check ids below.

None of these three is covered by the open issues 20261024T065715Z-sts-assumerole-getsessiontoken-admit-requests-aws-refuses-no.md, 20261024T065715Z-sts-sessions-carry-no-policy-scoping-packedpolicysize-oversized.md, 20261024T214811Z-sts-assumerole-never-converges-to-accessdenied-after-updateassumerolepolicy.md or 20261024T154246Z-sts-assumerolewithwebidentity-is-unroutable-unknownservice-trust-policy-conditions.md. The last of those is adjacent to cause 1 and is named there.

Cause 1 of 3: the anonymous (unsigned) STS federation operations cannot be dispatched at all — the request router resolves a target service only from a SigV4 credential scope, an X-Amz-Target header or the Host header, so every AssumeRoleWithSAML call is answered with a JSON UnknownService body instead of STS.
AWS: Smithy (com.amazonaws.sts#AWSSecurityTokenServiceV20110615): AssumeRoleWithSAML carries `auth: []` with `optionalAuth: true` — it is an ANONYMOUS operation, so a conforming client sends it with no Authorization header (hence no SigV4 credential scope), and the awsQuery protocol sends no X-Amz-Target. Its input is RoleArn (required, arnType, @length 20..2048), PrincipalArn (required, arnType, @length 20..2048) and SAMLAssertion (required, SAMLAssertionType, @length 4..100000, @sensitive). Its modeled errors, each serialized as an awsQuery XML ErrorResponse, are InvalidIdentityTokenException (awsQueryError code InvalidIdentityToken, HTTP 400), ExpiredTokenException (ExpiredTokenException, 400), IDPRejectedClaimException (IDPRejectedClaim, 403), MalformedPolicyDocumentException (MalformedPolicyDocument, 400), PackedPolicyTooLargeException (PackedPolicyTooLarge, 400) and RegionDisabledException (RegionDisabledException, 403). On success it returns Credentials, AssumedRoleUser, Subject, SubjectType, Issuer, Audience, NameQualifier. AssumeRoleWithWebIdentity is modeled the same way (`auth: []`, `optionalAuth: true`).
Emulator: the unsigned call is answered with a JSON body `{"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}`. That is not even the right protocol for STS, so botocore never reaches an error object and crashes in its XML parser: `botocore.parsers.ResponseParserError: Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received`. Every SAML check fails this way, including the one that only needs a SUCCESSFUL assume as its positive control (assume-role-with-saml-provider-deleted-blocked reports it could not obtain any successful AssumeRoleWithSAML, with the same UnknownService body as the last error). The same routing defect is reached on AssumeRoleWithWebIdentity by sts.assume-role-with-web-identity-invalid-token-format-rejected, which the suite did not mark as owned by 20261024T154246Z-sts-assumerolewithwebidentity-is-unroutable-unknownservice-trust-policy-conditions.md; it is recorded here so it is replayed, and a fixer should close it together with that issue's cause 1.
Why: the entire SAML federation surface is unreachable. A client gets a parser crash rather than a modeled error, so it cannot distinguish an expired assertion, a forged/unsigned assertion, a non-base64 assertion, an IdP-rejected claim or an XPath-transform attack, and no SAML 2.0 federation flow — the normal enterprise sign-in path — can be exercised against the emulator at all. Security negative tests written against the emulator cannot fail, because no response is ever classifiable.
Why it is the emulator's: the request reaches the emulator and the emulator answers; it simply refuses to attribute an unsigned request to STS.
Fix: the request-routing / service-resolution layer must resolve an anonymous awsQuery request to STS (e.g. from the Action parameter plus the endpoint it is reached on) before authentication; then the AssumeRoleWithSAML handler must validate and classify the assertion into the modeled errors above (InvalidIdentityToken 400 for a non-base64 / malformed / forged assertion and for an assertion whose signature or transforms are not acceptable, ExpiredTokenException 400 for an assertion whose Conditions/SubjectConfirmationData NotOnOrAfter has passed, IDPRejectedClaim 403 for a claim the provider rejects) and its awsQuery XML error serializer must render them.
Traces: sts.assume-role-with-saml-expired-assertion-rejected, sts.assume-role-with-saml-forged-assertion-rejected, sts.assume-role-with-saml-idp-rejected-claim-denied, sts.assume-role-with-saml-invalid-identity-token-rejected, sts.assume-role-with-saml-non-base64-assertion-rejected, sts.assume-role-with-saml-provider-deleted-blocked, sts.assume-role-with-saml-rejects-xpath-based-transforms, sts.assume-role-with-web-identity-invalid-token-format-rejected.

Cause 2 of 3: AssumeRole parses the inline session policy BEFORE it authorizes the assume, so an unauthorized role is reported as a policy-syntax problem.
AWS: the evaluation order is request-shape validation (ARN pattern, DurationSeconds range, RoleSessionName pattern), then authorization, and only then session-policy parsing (recorded behavior against real STS). With an unauthorized/nonexistent RoleArn AND a syntactically invalid `Policy`, real STS refuses with the service-common client error AccessDenied (HTTP 403) — not MalformedPolicyDocument. Smithy: AssumeRole models MalformedPolicyDocumentException (awsQueryError MalformedPolicyDocument, HTTP 400) for the parse failure, which is the correct outcome only on the positive-control path where the caller genuinely can assume the role.
Emulator: the same request is refused with error code MalformedPolicyDocument — `AssertionError: authorization must be evaluated before session-policy parsing: expected AccessDenied, got MalformedPolicyDocument`.
Why: the error code leaks information across an authorization boundary. A caller who cannot assume a role learns from the code whether the role exists and is assumable, simply by attaching a deliberately malformed session policy; and a client that branches on MalformedPolicyDocument to retry with a corrected policy will loop forever against a role it is not allowed to assume, instead of surfacing the access denial.
Fix: the AssumeRole handler's request pipeline — move the trust/authorization step ahead of session-policy parsing (shape validation first, then authorization emitting AccessDenied / HTTP 403, then policy parsing emitting MalformedPolicyDocument / HTTP 400).
Traces: sts.assume-role-authorization-precedes-policy-parsing.

Cause 3 of 3: GetFederationToken succeeds when it is called with temporary session credentials minted by GetSessionToken; AWS refuses it.
AWS: GetFederationToken must be called with an IAM user's long-term credentials. Called with temporary session credentials it is refused with AccessDenied (HTTP 403) regardless of the caller's identity policy — the check's user carries an explicit allow-all `sts:*` policy and AWS still refuses, so the refusal is a property of the credential type and not of IAM. The message is the constant STS produces for exactly this condition: "Cannot call GetFederationToken with session credentials" (recorded behavior; the rule that produces it — GetFederationToken invoked under a session credential — is known, so the text is the requirement for this refusal and not merely an example).
Emulator: the call returns HTTP 200 with a full GetFederationToken result under those session credentials (Credentials, FederatedUser with Arn `arn:aws:sts::<account>:federated-user/<name>`, SessionTokenUtilization, SessionTokenSize). The check establishes its positive control first — GetCallerIdentity under the same session credentials works — so this is an over-permissive grant, not broken credentials.
Why: this is an overly-permissive hole in credential-type restriction. A developer validating that a short-lived MFA/session credential cannot be re-federated into a further, independently scoped federated-user session is told it is blocked when, against AWS, it is; worse, the emulator lets a session credential mint a new principal (a federated user) with its own policy, which AWS deliberately forbids to stop privilege laundering through session chaining.
Fix: the GetFederationToken handler's caller-type check — reject any caller whose presented credential is a temporary session (STS-minted) rather than an IAM user's long-term access key, with AccessDenied / HTTP 403 and the message above, before any policy evaluation.
Traces: sts.get-session-token-cannot-call-other-sts-operations.
