Cause 1 of 1 — the Config recording pass writes no AWS::SQS::Queue configuration item while a customer-managed recorder with recordingGroup {allSupported: true, includeGlobalResourceTypes: false} is RECORDING with a delivery channel in place, and the recorder's status machine never advances lastStatus out of 'Pending'. Failing check: config__sqs.config-history-rejects-unrecorded-queue-while-batch-get-omits-it.

AWS: recorded behavior only for the recording side effect itself — the Smithy model (com.amazonaws.configservice#StarlingDoveService) models the read paths, not discovery. GetResourceConfigHistory takes required resourceType (enum ResourceType) and resourceId (@length 1..768) plus optional laterTime/earlierTime/chronologicalOrder/limit (@range 0..100)/nextToken, returns configurationItems (ConfigurationItemList) + nextToken, and declares InvalidLimitException / InvalidNextTokenException / InvalidTimeRangeException / NoAvailableConfigurationRecorderException / ResourceNotDiscoveredException / ValidationException (all client, HTTP 400). BatchGetResourceConfig takes resourceKeys (@length 1..100) and returns baseConfigurationItems + unprocessedResourceKeys (HTTP 200). SelectResourceConfig takes Expression (@length 1..4096) and returns Results (HTTP 200). DescribeConfigurationRecorderStatus returns ConfigurationRecordersStatus, whose lastStatus targets the RecorderStatus enum (Pending | Success | Failure | NotApplicable). On AWS, once such a recorder is recording, CreateQueue causes Config to discover the queue asynchronously and write a configuration item for resourceType AWS::SQS::Queue, so GetResourceConfigHistory for that queue URL answers HTTP 200 with a non-empty configurationItems list whose latest item's arn equals the queue's QueueArn, BatchGetResourceConfig returns exactly one baseConfigurationItem for that resourceKey (its configuration document carrying the queue's QueueArn), and DescribeConfigurationRecorderStatus leaves lastStatus 'Pending' for 'Success' once a recording event has been processed. Only against that recorded control is the refusal leg meaningful: GetResourceConfigHistory for a never-created queue URL of the same shape answers HTTP 400 ResourceNotDiscoveredException with message `Resource <resourceId> of resourceType:<resourceType> is unknown or has not been discovered` — fixed text `Resource `, ` of resourceType:` and ` is unknown or has not been discovered`, with resourceId and resourceType substituted verbatim from the request — while BatchGetResourceConfig and SelectResourceConfig answer the same absence by OMISSION and HTTP 200 (baseConfigurationItems=[], unprocessedResourceKeys=[], Results=[]), never by an error.

Emulator: after PutConfigurationRecorder + PutDeliveryChannel + StartConfigurationRecorder succeed and DescribeConfigurationRecorderStatus confirms recording=true, a CreateQueue (Attributes VisibilityTimeout) produces nothing in Config: no AWS::SQS::Queue configuration item ever exists for the queue, and the emulator's own DescribeConfigurationRecorderStatus response at the moment of failure is {'recording': True, 'lastStatus': 'Pending', 'lastErrorCode': None, 'lastErrorMessage': None} — a recorder that reports itself healthy and recording while having recorded nothing and never advancing out of 'Pending'. HONEST SCOPE OF THIS RUN: the check derives its control wait from ctx.time_left() minus a 180 s reserve, and under the suite's 60 s per-check budget that window collapsed to 0.0 s, so the harness reports "not met within 0.0s" with "Last result: None" and the history read was not actually polled in this replay. What is grounded is (a) the recorder state the emulator itself reported — recording=true, lastStatus pinned at 'Pending', no error code — and (b) that the whole per-check budget was consumed by the recorder/delivery-channel setup before any read, leaving the check structurally unable to reach a verdict. The queue URL, queue name, recorder name, account id and the 0.0 s/60 s budgets above are per-run values and are not part of any requirement.

Why: a client that uses Config as its inventory of SQS sees an account that contains no queues while Config insists it is recording. Because nothing is ever recorded, ResourceNotDiscoveredException becomes the answer to every GetResourceConfigHistory call, so the error loses its meaning — a caller cannot distinguish "this resource was never created" from "Config records nothing at all" — and the HTTP 200 omission answers of BatchGetResourceConfig and SelectResourceConfig are indistinguishable from an empty account. Drift, audit and compliance tooling that gates on a resource being discovered blocks on its first wait, and anything gating on lastStatus == 'Success' to confirm the recorder came up waits on 'Pending' forever.

Fix: the configuration-recorder recording pass in the configservice crate — while a customer-managed recorder is RECORDING and its recordingGroup covers the type, create/change/delete of resources in the other emulated services (here AWS::SQS::Queue from the SQS crate) must be captured into Config's configuration-item state, which today only grows from an explicit PutResourceConfig write; GetResourceConfigHistory's handler must then project those items and reserve ResourceNotDiscoveredException for ids genuinely absent from that state, with BatchGetResourceConfig's and SelectResourceConfig's handlers answering the same state by omission; and the recorder status machine behind DescribeConfigurationRecorderStatus must advance lastStatus/lastStatusChangeTime out of 'Pending' once a recording event is processed.
