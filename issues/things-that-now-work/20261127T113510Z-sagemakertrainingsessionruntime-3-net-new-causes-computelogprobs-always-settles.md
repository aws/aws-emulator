# sagemakertrainingsessionruntime: 3 net-new causes — computeLogprobs always settles Failed, a Stopped session still accepts ExecuteSamplingOperation, and an over-context-length prompt Completes instead of Failing

> _Note: this issue was identified against the code base at commit `f73c567c518c4ea32fbc68f3ca5cb3fd81df2cf2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteSamplingOperation

## Description
Three net-new behavioral root causes on the asynchronous sampling surface of this service (Cause 1 of 3 .. Cause 3 of 3). All three are in the same service (sagemakertrainingsessionruntime) and each has its own failing check ids below; a fixer must close all three before submitting.

Cause 1 of 3: a `computeLogprobs` sampling operation never completes — it always settles in the terminal status `Failed` with the emulator's own errorDetails, and `operationResult` is never populated.
Failing check: sagemakertrainingsessionruntime.compute-logprobs-scores-every-prompt-token.
AWS:      Smithy (com.amazonaws.sagemakertrainingsessionruntime#LegoRouterService, restJson1): ExecuteSamplingOperation POST /v1/training-sessions/{trainingSessionName}/sampling-operations is documented as "Submits an asynchronous sampling operation to generate text **or compute log-probabilities** from the model associated with the specified training session"; SampleOperationConfig$computeLogprobs -> ComputeLogprobsConfig{prompt (ModelInput, required)}; GetSamplingOperationResult output `status` (RequestStatus: Pending|InProgress|Completed|Failed|Skipped), `operationResult` (SampleOperationResult — "Exactly one member is populated, corresponding to the operation type that was submitted") with member computeLogprobs -> ComputeLogprobsResult{logprobs (DoubleList, @required) "The per-token log-probabilities for the input prompt"}, and `errorDetails` "The service populates this field only when the status is Failed". So for a computeLogprobs config submitted against a Running session AWS answers 200 with status="Completed" and operationResult.computeLogprobs.logprobs. Recorded behavior for the content of that list (the model states only that it is a list of Double, and it is not @sparse): exactly one entry per prompt token counted across all of the prompt's chunks, the FIRST entry null because that token has no context, every later entry a finite non-positive double with at least one strictly negative, and splitting the identical token sequence into two chunks leaves each later token's score unchanged (same values within tolerance).
Emulator: the submit is accepted and mints an operationId, but polling GetSamplingOperationResult terminates at status="Failed" with NO operationResult and errorDetails = "This SageMaker training-session runtime emulator runs no language model or training engine, so the computeLogprobs operation was not executed and produced no result." (fixed text; `computeLogprobs` is the submitted union member interpolated into it). Replay: "AssertionError: computeLogprobs ended 'Failed': 'This SageMaker training-session runtime emulator runs no language model or training engine, so the computeLogprobs operation was not executed and produced no result.'"
Why:      log-probability scoring is one of the two operation kinds this API exists for. A client that submits computeLogprobs and polls never takes the success branch; every consumer of operationResult.computeLogprobs.logprobs sees nothing, and because the emulator reports this through the service's own modelled FAILURE channel a client cannot tell a genuinely failed operation from one the emulator declined to execute — error-handling, retry and alarm paths fire on a healthy request.
Fix:      the sampling settle path in the service's state — the predicate that diverts a config into the no-model-runtime `Failed` status, and the settle step that populates SampleOperationResult — must settle a computeLogprobs operation into `Completed` and populate ComputeLogprobsResult.logprobs with one score per prompt token (null for the first, non-positive finite doubles afterwards, and independent of how the prompt was chunked). errorDetails must then be emitted only for operations that genuinely fail.
Note on an already-resolved issue: 20261118T040630Z-sagemakertrainingsessionruntime-a-sampling-operation-submitted-against-a-running.md (status fixed) covered the same gap for the `sample` config; that fix made `sample` complete but left the computeLogprobs config on the no-model-runtime path, which is what this cause is about. The open wire issue 20261117T022256Z-sagemakertrainingsessionruntime-sampling-operations-never-produce-a-result-getsamplingoperationresult.md carries only wire replay keys for the `sample` path and does not cover computeLogprobs or carry this check id.

Cause 2 of 3: the session's lifecycle state is never consulted on submit — a Stopped training session still accepts ExecuteSamplingOperation with 200.
Failing check: sagemakertrainingsessionruntime.execute-sampling-operation-stopped-session-rejected-with-conflict.
AWS:      Smithy: ExecuteSamplingOperation models ConflictException (HTTP 409), documented as "The training session is in a state that cannot accept new operations. The session must be in Running or Blocked state to accept requests", and the operation's own doc repeats "The session must be in Running or Blocked state". Recorded behavior for the wording: after sagemaker StopTrainingSession has left the session TrainingSessionStatus="Stopped", the submit is refused with HTTP 409, error code `ConflictException` and message "Session is in <State> state and cannot accept requests" — the fixed text is "Session is in " / " state and cannot accept requests" and the variable part is the session's current TrainingSessionStatus from the emulator's state (here `Stopped`). The refusal does not move the session out of Stopped, and a sampling operation that completed while the session was Running stays readable with its result unchanged.
Emulator: the submit returns HTTP 200 with an operationId (replay: "expected the stopped session to refuse the call, it returned {'ResponseMetadata': {'HTTPStatusCode': 200, ...}, 'operationId': 'sampling-...'}"), so a terminal session keeps accepting and executing work. ExecuteSamplingOperation's handler only asks whether the control plane HOLDS the name (services/.../src/ops/execute_sampling_operation.rs:169-182) and never reads the session's status; the directory the data plane shares with the control plane exposes only `holds(name)` (src/state.rs:842-850).
Why:      a client's stop is not a stop: work submitted after StopTrainingSession is accepted and billed/accounted, and the 409 branch every SDK caller writes against this operation (stop, then expect ConflictException) is unreachable, so tests and operational tooling that assert a stopped session is inert pass against AWS and silently diverge here.
Fix:      the shared session directory must expose the control plane's TrainingSessionStatus to this data plane, and the submit path (ExecuteSamplingOperation's handler, before it mints an operation id — and the same guard belongs on ExecuteTrainingOperation and on the two inference handlers, which resolve through crate::state::resolve_sample_checkpoint and today also ignore lifecycle state) must refuse any session not in Running or Blocked with the modelled ConflictException and the message above.

Cause 3 of 3: a prompt longer than the model's context length is executed and Completes instead of settling Failed with the documented context-length reason.
Failing check: sagemakertrainingsessionruntime.sampling-operation-over-context-length-rejected-as-failed.
AWS:      Smithy: SampleConfig{prompt (ModelInput, required), numSamples 1..1000, samplingParams (SamplingParams{maxTokens 512..131072})}; GetSamplingOperationResultOutput$errorDetails is "A message describing why the sample operation failed. The service populates this field only when the status is Failed". Recorded behavior for the rule and wording: a `sample` whose prompt plus requested maxTokens exceeds the base model's context window (gpt-oss-20b: 65,536 tokens) is ACCEPTED at submit (200 + operationId) and then settles status="Failed" with errorDetails exactly "The input exceeds the model's maximum context length. Please reduce the length of your prompt or the requested max tokens." — this message is entirely fixed text, with no request values interpolated — and carries NO operationResult; the same status/errorDetails is returned on every later read of that operation id, while a short prompt on the same session still Completes.
Emulator: the operation Completes with a sample result; there is no notion of the session's base model context length anywhere on the sampling path, so the over-long prompt is served like any other. Replay: "AssertionError: the over-long prompt's operation ended ('Completed', None), expected ('Failed', \"The input exceeds the model's maximum context length. Please reduce the length of your prompt or the requested max tokens.\")".
Why:      the one failure mode every real caller of this API has to handle — an over-long prompt — never occurs against the emulator, so client code that catches it (truncating the prompt, lowering maxTokens, surfacing the message to a user) is never exercised and a client instead receives a fabricated successful sample for input the service cannot process.
Fix:      the sampling validation/settle path in the service's state must compare the submitted prompt's total token count (summed over ModelInput.chunks) plus samplingParams.maxTokens against the context length of the session's base model and settle such an operation into `Failed` with the message above and no operationResult, leaving the status and errorDetails stable across re-reads.
