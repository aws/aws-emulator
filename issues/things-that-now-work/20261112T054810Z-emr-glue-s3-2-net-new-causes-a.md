# emr__glue__s3: 2 net-new causes — a transient EMR cluster never self-terminates and publishes no 'EMR Cluster State Change' event, and an S3 Batch Operations job never leaves a non-terminal status, so both scenarios are cut off at the harness budget

## Operation
DescribeCluster (cause 1); DescribeJob (cause 2)

## Description
Two independent defects reached by the emr__glue__s3 cross-service checks. Each has its own failing check and must be closed separately. THIS ISSUE BUNDLES 2 CAUSES. Both must be closed before submitting.

Cause 1 of 2: a transient EMR cluster (no steps, Instances.KeepJobFlowAliveWhenNoSteps=false) never self-terminates, and no 'EMR Cluster State Change' event is ever published, so an EventBridge rule targeting SQS receives nothing.
  AWS: Smithy: com.amazonaws.emr#JobFlowInstancesConfig$KeepJobFlowAliveWhenNoSteps — "Specifies whether the cluster should remain available after completing all steps. Defaults to false". A cluster run with that flag false and no steps therefore walks the modeled cluster-state machine (Smithy: com.amazonaws.emr#ClusterState = STARTING, BOOTSTRAPPING, RUNNING, WAITING, TERMINATING, TERMINATED, TERMINATED_WITH_ERRORS) from STARTING/BOOTSTRAPPING through RUNNING to TERMINATING and settles in the terminal TERMINATED, with DescribeCluster reporting Cluster.Status.State TERMINATED and a ClusterStatus.StateChangeReason/Timeline for that transition. Each state transition is announced on the default event bus as an event with source 'aws.emr' and detail-type 'EMR Cluster State Change' whose detail carries at least clusterId (the JobFlowId returned by RunJobFlow) and state (the ClusterState just entered, here TERMINATED); EventBridge then delivers that event, unchanged, to every ENABLED rule whose pattern matches, including an SQS queue target whose queue policy allows events.amazonaws.com to SendMessage. Recorded behavior: the check polls DescribeCluster until the state is TERMINATED or TERMINATED_WITH_ERRORS and then polls the SQS queue until at least one message arrives; the recording reaches both.
  Emulator: the check never reaches a verdict — the replay reports only 'Check timed out after 60.0s', so neither the DescribeCluster poll for a terminal state nor the subsequent ReceiveMessage poll for the delivered event is ever satisfied inside the harness budget. Nothing is malformed on the wire: RunJobFlow, PutRule, PutTargets, CreateQueue and the queue policy all succeed, and the cluster simply stays in a non-terminal state with no cluster state-change event emitted, so the scenario produces no observable outcome at all. Open issues 20261029T184212Z-emr-clusters-accept-steps-but-never-execute-them.md ("no cluster self-terminates") and 20261110T132412Z-emr-glue-s3-2-net-new-causes-emr.md ("EMR clusters never execute their steps, auto-terminate or upload logs") describe the same non-advancing cluster lifecycle, and 20261105T074141Z-emr-events-sqs-a-step-submitted-to-a.md describes the missing 'EMR Step Status Change' event; none of them carries this check's replay key and the replay report did not mark this failure as owned, so it is filed here with those issues named.
  Why: a client that launches a transient cluster and waits for it to finish hangs forever — the cluster never reports a terminal state, so cost/completion detection, 'wait cluster-terminated' style polling and any teardown keyed on TERMINATED never fire. Worse, because no 'EMR Cluster State Change' event is published, every event-driven architecture built on EMR cluster lifecycle (EventBridge rules fanning out to SQS, Lambda or Step Functions) is silently dead: the rule matches nothing, so the consumer cannot distinguish "cluster still running" from "notification lost".
  Fix: the EMR cluster lifecycle state machine behind RunJobFlow/DescribeCluster (the cluster state in the emr service state), which must advance a KeepJobFlowAliveWhenNoSteps=false cluster with an empty step list to TERMINATING and then terminal TERMINATED, plus the emr side of the event publisher that must emit a source='aws.emr', detail-type='EMR Cluster State Change' event carrying detail.clusterId and detail.state onto the default event bus for each transition so the existing EventBridge rule/target delivery path can match it.
  Traces: emr__glue__s3.eventbridge-emr-cluster-state-change-rule-positive.

Cause 2 of 2: an S3 Control Batch Operations job created with ConfirmationRequired=false never reaches a terminal status, so neither the healthy-role nor the mistrusted-role outcome is observable.
  AWS: s3control CreateJob returns a JobId and the job then advances through the modeled status machine (Smithy: com.amazonaws.s3control#JobStatus = Active, Cancelled, Cancelling, Complete, Completing, Failed, Failing, New, Paused, Pausing, Preparing, Ready, Suspended) out of New/Preparing/Ready into Active and on to the terminal Complete when the RoleArn's trust policy names batchoperations.s3.amazonaws.com and its permissions allow the operation — applying Operation.S3PutObjectTagging to every object the manifest lists and writing the completion report under Report.Prefix. A job whose role cannot be assumed by Batch Operations (for example a role whose trust policy names only ec2.amazonaws.com, the only difference from the healthy role in this scenario) instead settles in the terminal Failed with JobDescriptor.FailureReasons populated (Smithy: com.amazonaws.s3control#JobFailure{FailureCode, FailureReason}; DescribeJob's JobDescriptor.FailureReasons — "If the specified job failed, this field contains information describing the failure"), the FailureReason naming the role that could not be assumed, and it tags nothing. The fixed part of that message is the assume-role sentence AWS uses for this failure class (the check matches on 'Could not assume the IAM role'); its variable part is the role ARN taken from the request. The terminal job also carries TerminationDate.
  Emulator: the check never reaches a verdict — the replay reports only 'Check timed out after 60.0s', so the DescribeJob poll for a status in {Complete, Failed, Cancelled} is never satisfied for either job. The job is accepted and described with a legal but non-terminal JobStatus and with no FailureReasons and no ProgressSummary, the manifest's target object keeps an empty TagSet, and no report object appears under the report prefix. Because the healthy-trust job and the ec2.amazonaws.com-trust job are indistinguishable, the job role's trust contract is never enforced. Open issue 20261107T182201Z-emr-glue-s3-2-net-new-root-causes-f0288f.md already describes this same non-settling Batch Operations job and even lists this check id, but the replay report did not mark this failure as owned — its recorded replay key is the check's internal _poll_until AssertionError, whereas the check now exhausts the 60s harness budget before that assertion is reached, so the key no longer matches. Open issues 20261102T121736Z-s3control-s3-control-batch-job-s3putobjecttagging-never-reaches-a.md, 20261029T192817Z-s3control-batch-operations-jobs-never-settle-and-refuse.md, 20261029T195302Z-s3control-batch-operations-a-confirmationrequired-false-s3putobjecttagging-job.md and 20261029T184212Z-s3control-an-s3-batch-operations-job-created-with-an.md describe the same defect under the s3control service.
  Why: a client that submits a Batch Operations job and waits on DescribeJob hangs indefinitely; no bulk tagging/copy/restore side effect ever lands, no completion report is written, and a misconfigured job role looks exactly like a healthy one, so permission-boundary tests around Batch Operations always pass vacuously.
  Fix: the s3control Batch Operations job runner behind CreateJob/DescribeJob (the job state machine in the s3control service state), which must drive a ConfirmationRequired=false job out of Ready into Active and on to terminal Complete, apply Operation to each manifest entry, write the report, and settle terminal Failed with FailureReasons when the RoleArn cannot be assumed by batchoperations.s3.amazonaws.com.
  Traces: emr__glue__s3.s3-batch-operation-role-missing-s3-trust-rejected.
