# bedrock-agent: 2 net-new causes — IngestKnowledgeBaseDocuments caps a vector knowledge base's batch at 10 documents instead of 25, and an ingestion job counts a document with unparseable metadata as newly indexed instead of failed

> _Note: this issue was identified against the code base at commit `723e24d0ff9083736505f1fa49c337be40d1d9c1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
IngestKnowledgeBaseDocuments, StartIngestionJob

## Description
Two net-new root causes in the bedrock-agent knowledge-base document/ingestion data plane. Cause 1 refuses a request AWS accepts, so the multi-document ingest path is unreachable at all; cause 2 reports a successful job where AWS reports a partial failure. Each is a separate defect and each must be closed.

Cause 1 of 2: IngestKnowledgeBaseDocuments enforces a per-request bound of 10 documents on a VECTOR knowledge base, where AWS accepts 25, and its over-limit message omits the rendered value clause.
AWS: Smithy (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/smithy-model/com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda.json) models IngestKnowledgeBaseDocuments as PUT /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents, success 202, input member documents (target KnowledgeBaseDocuments, required, @length min 1 max 10), errors including ValidationException (errorKind client, httpError 400). The modeled max of 10 is NOT the bound AWS applies on this path — recorded behavior: against a VECTOR knowledge base on an S3_VECTORS index with a CUSTOM data source, a request carrying 25 documents is ACCEPTED (HTTP 202, documentDetails echoing all 25 custom identifiers, all of which settle INDEXED), and only a 26-document request is refused. The refusal is HTTP 400, error code ValidationException, with the generic constraint sentence whose FIXED text is "<n> validation error(s) detected: Value '[<rendered documents>]' at 'documents' failed to satisfy constraint: Member must have length less than or equal to <max>"; the VARIABLE parts are the error count, the rendered list of the request's own documents (each KnowledgeBaseDocument printed in full with the @sensitive inline text data replaced by *** REDACTED ***) and the bound, which on this path is 25. Note that the open issue '20261127T133852Z-bedrock-agent-refusal-messages-diverge-from-aws-text.md' (cause 5) records a DIFFERENT batch-limit refusal — a MANAGED knowledge base, bound 10, service-authored sentence "The number of documents (<n>) exceeds the maximum allowed (<max>) for <kbType> knowledge base type." — so the bound and the message form AWS emits depend on the addressed knowledge base's type; that issue carries no replay key for this check and does not cover it.
Emulator: refuses the 25-document request itself with HTTP 400 ValidationException "1 validation error detected: Value at 'documents' failed to satisfy constraint: Member must have length less than or equal to 10" — i.e. it applies the stale modeled @length max 10 in the shared request-validation layer before the handler runs, and it also drops the "Value '[...]' at" clause that quotes the submitted list.
Why: a client batching documents up to AWS's per-request limit for a vector knowledge base gets every such request refused, so bulk ingestion is impossible against the emulator and the client's success path is never exercised; the generic 10-document message also tells the client to shrink to a limit AWS does not impose. Because the valid request is refused, the whole downstream flow (documentDetails echo, settling to INDEXED, and the genuine over-limit refusal) is unreachable.
Fix: IngestKnowledgeBaseDocuments' validation — the documents list-length refusal must not be left to the stale modeled bound; enforce the per-knowledge-base-type per-request bound (25 for a VECTOR knowledge base) in the operation's handler/pre-validation, and render the over-limit ValidationException with the Value '[<rendered documents>]' clause, redacting the sensitive inline text.
Traces: check bedrock-agent.ingest-documents-request-over-twenty-five-documents-rejected.

Cause 2 of 2: an S3 ingestion job indexes a document whose sibling metadata object is not valid JSON, counting it as newly indexed instead of failed.
AWS: Smithy models StartIngestionJob (PUT /knowledgebases/{kb}/datasources/{ds}/ingestionjobs/, 202) and GetIngestionJob -> IngestionJob with status, failureReasons and statistics (IngestionJobStatistics: numberOfDocumentsScanned, numberOfMetadataDocumentsScanned, numberOfNewDocumentsIndexed, numberOfModifiedDocumentsIndexed, numberOfDocumentsDeleted, numberOfDocumentsFailed, numberOfDocumentsSkipped). The model does not state the per-document outcome, so this is recorded behavior only: for an S3 data source holding three text documents, exactly one of which has a sibling <key>.metadata.json object whose body is not parseable JSON, AWS finishes the job with status COMPLETE and counts the malformed-metadata document as FAILED, not indexed — scanned = the number of documents found, metadataDocumentsScanned = the number of metadata objects found, newDocumentsIndexed = the number of well-formed documents, documentsFailed = the number of documents whose metadata could not be parsed, with modifiedDocumentsIndexed / documentsDeleted / documentsSkipped at 0. failureReasons names the refused document's s3:// URI and names no indexed document, the refused document does not appear in ListKnowledgeBaseDocuments, and after the metadata object is replaced with valid JSON the next job indexes exactly that one document as new, fails none, and lists all three as INDEXED.
Emulator: finishes the job COMPLETE with every document indexed — it gets scanned and metadataDocumentsScanned right but reports newDocumentsIndexed equal to the full document count and documentsFailed 0, because the job simulation never reads or parses a document's <key>.metadata.json sibling and so has no notion of a document refused for malformed metadata. The check's assertion stops at the statistics, so the subsequent failureReasons and listing assertions were not reached; they follow from the same missing per-document metadata validation.
Why: partial failure is invisible. A client that polls an ingestion job and reads statistics/failureReasons to learn which source objects need fixing sees a completely successful job and never repairs the broken metadata; worse, the document AWS refused is reported as INDEXED by ListKnowledgeBaseDocuments and is queryable, so retrieval results against the emulator include content AWS would never have embedded.
Fix: the ingestion-job simulation that backs StartIngestionJob/GetIngestionJob for an S3 data source — for each scanned object, parse its <key>.metadata.json sibling when present; on a parse failure count that document under numberOfDocumentsFailed instead of numberOfNewDocumentsIndexed, do not write a document record for it (so it stays out of ListKnowledgeBaseDocuments), and append a failure reason naming its s3:// URI, leaving the job's terminal status COMPLETE.
Traces: check bedrock-agent.ingestion-job-reports-malformed-metadata-document-beside-indexed-ones.
