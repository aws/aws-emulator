# apigateway__cloudwatch__dynamodb__lambda__logs__sqs: the plain-CloudFormation order-service deployment hangs — no terminal StackStatus and no graded leg before the check cap (1 cause)

> _Note: this issue was identified against the code base at commit `992eebbb1a1c5db8bb6bfb43357b4e2de2d0ccf2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause in the order-intake ("order-service") cross-flavor scenario of this service group. The check is killed by the harness cap with its ONLY output being a timeout line, so not one of its nine legs (deploy, wiring, worker, logs, metrics, alarm, denial, drift, teardown) is ever graded: the emulator produced neither a usable deployment nor an error a caller could branch on.

NOTE on already-filed work: open issue 20261121T044528Z-apigateway-cloudwatch-dynamodb-lambda-lo-apigateway-cloudwatch-dynamodb-lambda-logs-sqs-both-order.md describes a hang of this same check, but the replay key it carries for it is '...xflavor-order-service-cfn-alarm-echoes-declared-period|<lambda>#12|Timeout|("table", lambda: ddb.describe_table(TableName=state["TableName"])),' — i.e. a run that got as far as the TEARDOWN leg's table probe. This replay does not die at that frame, so that key does not carry this failure and the suite did not mark the check as owned; it is filed here as net-new, and a fixer should treat the two as the same family of defect (the plain-CFN order-service deploy path) rather than as unrelated work.

Cause 1 of 1: a CreateStack/UpdateStack of the hand-written order-intake CloudFormation template (REST API POST /orders -> intake Lambda -> SQS queue -> event-source mapping -> worker Lambda -> DynamoDB table, plus two log groups and an AWS::CloudWatch::Alarm) never converges, so nothing downstream of the deploy leg is observable.
AWS: Smithy (cloudformation) DescribeStacks -> Stack.StackStatus targets com.amazonaws.cloudformation#StackStatus, whose members are CREATE_IN_PROGRESS, CREATE_FAILED, CREATE_COMPLETE, ROLLBACK_IN_PROGRESS, ROLLBACK_FAILED, ROLLBACK_COMPLETE, DELETE_IN_PROGRESS, DELETE_FAILED, DELETE_COMPLETE, UPDATE_IN_PROGRESS, UPDATE_COMPLETE_CLEANUP_IN_PROGRESS, UPDATE_COMPLETE, UPDATE_FAILED, UPDATE_ROLLBACK_IN_PROGRESS, UPDATE_ROLLBACK_FAILED, UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS, UPDATE_ROLLBACK_COMPLETE, REVIEW_IN_PROGRESS, IMPORT_* . A real stack ALWAYS leaves its *_IN_PROGRESS status for a terminal one (CREATE_COMPLETE, CREATE_FAILED, ROLLBACK_COMPLETE/ROLLBACK_FAILED, UPDATE_COMPLETE/UPDATE_FAILED, UPDATE_ROLLBACK_COMPLETE/UPDATE_ROLLBACK_FAILED, DELETE_COMPLETE/DELETE_FAILED) in bounded time, every DescribeStacks/DescribeStackEvents poll on that walk returns a response, a failure carries a resource-level ResourceStatusReason on DescribeStackEvents, and the deployed stage answers the POST with an HTTP status. Recorded behavior only for the individual leg assertions (the declared alarm echo: Statistic=Sum, Period=60, EvaluationPeriods=1, Threshold=1.0, ComparisonOperator=GreaterThanOrEqualToThreshold, TreatMissingData=missing, ActionsEnabled=false, echoed verbatim by DescribeAlarms).
Emulator: the check's entire replay output is 'Error: Check timed out after 60.0s'. No terminal StackStatus and no HTTP status line from the deployed stage was ever observed, so the stack stays in an *_IN_PROGRESS status (or one call on the deploy path never returns) for longer than the whole check budget. The check's own per-leg ceilings are all far larger than the cap that killed it (deploy 600 s, route 180 s, row 60 s, worker 180 s, queue 120 s, logs 240 s, metrics 300 s, denial 900 s), so this is the absence of any response rather than a leg assertion firing.
Why: a client deploying a plain CloudFormation application gets neither a converged stack nor a failure it can branch on — every waiter written against DescribeStacks blocks indefinitely, no ResourceStatusReason is ever available to diagnose a rollback, and every behavior behind the deploy (POST /orders persisting a row, the queue draining into the worker, the structured log lines, the custom OrdersFulfilled datapoint, the alarm's declared period echo, the AccessDeniedException on the denied UpdateItem, in-place update on the second apply, and the post-destroy refusal) is unreachable.
Fix: the CloudFormation CreateStack/UpdateStack progression in the cloudformation crate — a stack must always leave *_IN_PROGRESS for a modeled terminal StackStatus within bounded time, including when a nested resource handler (apigateway REST API/deployment/stage, lambda function + event-source mapping, dynamodb table, sqs queue, logs log group, cloudwatch alarm) errors, which must land as *_FAILED / ROLLBACK_COMPLETE with a resource-level failure reason on DescribeStackEvents; no call on that path may block.
