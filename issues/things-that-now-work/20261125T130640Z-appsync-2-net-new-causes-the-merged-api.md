# appsync: 2 net-new causes — the merged API's data plane shapes an introspection selection but resolves it to null, and removing a SourceApiAssociation never withdraws the source's fields from the MERGED endpoint

Cause 1 of 2 — on a MERGED API's GraphQL endpoint, an introspection document is answered HTTP 200 but every introspection field resolves to null, so the composed merged schema cannot be discovered.
AWS: introspection is part of the GraphQL contract and AppSync serves it on the data plane by default — Smithy GraphqlApi$introspectionConfig: "Sets the value of the GraphQL API to enable (ENABLED) or disable (DISABLED) introspection. If no value is provided, the introspection configuration will be set to ENABLED by default." (enum GraphQLApiIntrospectionConfig = ENABLED | DISABLED); the control-plane counterpart GetIntrospectionSchema (GET /v1/apis/{apiId}/schema) exposes the same compiled schema. A MERGED API whose source association reached MERGE_SUCCESS serves the COMPOSED schema, so POSTing `query { __schema { queryType { fields { name } } } }` to GraphqlApi$uris.GRAPHQL with a valid x-api-key returns HTTP 200, no `errors` key, and data.__schema.queryType.fields as a non-null list of field objects, each with a `name`, containing every field contributed by the associated source APIs (here the source-only field selected by the check's SDL). The rule, not one run's values: the list names exactly the merged query root's fields.
Emulator: the same POST returns HTTP 200 with a `data` object whose `__schema.queryType.fields` is null — the introspection selection set is shaped into the response document but never resolved — so the check's set comprehension over the field list raised `TypeError: 'NoneType' object is not iterable`. Note that the preceding legs of the same check PASSED: the merged API was created as MERGED, the association settled MERGE_SUCCESS, and `query { sourceOnly }` at the merged endpoint returned the source resolver's marker — so the merged routing works and only introspection is unresolved.
Why: introspection is how every GraphQL client, codegen tool and IDE (Amplify, Apollo, graphql-codegen, the AppSync console query editor) discovers a schema. A client cannot verify that a merge actually composed the source's types, and codegen against a merged API silently produces an empty schema instead of failing loudly; a null inside a 200 envelope is worse than an error because clients treat it as "the merged schema has no fields".
Fix: introspection support in the GraphQL data-plane executor — build the introspection meta-types (__Schema, __Type, __Field, __TypeKind with NON_NULL/LIST wrappers) from the API's compiled schema and resolve the __schema / __type root meta-fields without a resolver, and make that path read the COMPOSED schema for an apiType=MERGED API rather than an empty one.
Traces: appsync.appsync-merged-api-executes-source-api-resolver.

Cause 2 of 2 — after the SourceApiAssociation is removed, the merged API never withdraws the source's fields and the association's removal is never observable; the check never reaches a verdict and the suite kills it at the 60 s budget.
AWS: Smithy: DisassociateMergedGraphqlApi DELETE /v1/sourceApis/{sourceApiIdentifier}/mergedApiAssociations/{associationId} -> {sourceApiAssociationStatus}, errors NotFoundException (httpError 404) / ConcurrentModificationException (409); GetSourceApiAssociation GET /v1/mergedApis/{mergedApiIdentifier}/sourceApiAssociations/{associationId}, errors NotFoundException (404); ListSourceApiAssociations GET /v1/apis/{apiId}/sourceApiAssociations -> sourceApiAssociationSummaries. Recorded behavior: once the association is gone (here by a CloudFormation stack update that drops the AWS::AppSync::SourceApiAssociation resource), GetSourceApiAssociation for that associationId is refused 404 NotFoundException, ListSourceApiAssociations on the merged apiId returns an EMPTY sourceApiAssociationSummaries list, and the MERGED API — now with no source — has no schema to serve: the same keyed POST of `query { greeting }` to the merged endpoint returns HTTP 502 with NO `data` member and exactly one entry in `errors` whose errorType is "GraphQLSchemaException". The merged API itself still reports apiType MERGED, and the SOURCE API's own endpoint keeps answering the query with its resolver's value, which is what makes the withdrawal attributable to the disassociation. Status 502 and errorType GraphQLSchemaException are the requirement; the field name and literal are values from the request/state.
Emulator: the check never reaches any of those observations — the suite reports "Error: Check timed out after 60.0s" for a check whose own waits are bounded at 180-300 s, so the emulator never produced a condition the check was waiting on. Hypothesis (the recording states the end state, not which wait stalls): the awaited conditions are, in order, the create/update stack leaving *_IN_PROGRESS, the association settling MERGE_SUCCESS, the merged endpoint serving `greeting`, then — after the association is dropped — GetSourceApiAssociation turning into NotFoundException and the merged endpoint ceasing to answer 200. The post-removal legs are the novel ones: Cause 1's check shows create + merge + merged-endpoint serving all work, so the stall is most likely that the merged API keeps serving the withdrawn source's field (the composed schema is never recomputed when an association is removed) and/or that the removed association remains readable instead of 404.
Why: a client that unlinks a source API from a merged API is told nothing changed — the merged endpoint keeps answering with fields the account no longer associates, the deleted association still reads back, and tooling that waits for the withdrawal (IaC teardown, blue/green schema cutovers) hangs forever. Serving fields from a disassociated source is also a data-exposure divergence: access was revoked at the control plane but not at the data plane.
Fix: the source-API association state and the merged API's schema composition — removing an association (DisassociateMergedGraphqlApi, and the CloudFormation delete path for AWS::AppSync::SourceApiAssociation) must delete the association record so GetSourceApiAssociation answers 404 NotFoundException and ListSourceApiAssociations omits it, and must recompose the merged API's served schema, leaving a sourceless MERGED API with no schema so the data plane answers 502 with a single GraphQLSchemaException error and no data member.
Traces: appsync.deploy-appsync-3-cfn-merged-api-disassociation-withdraws-source-fields.
