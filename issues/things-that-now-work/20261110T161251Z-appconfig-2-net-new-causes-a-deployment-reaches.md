# appconfig: 2 net-new causes — a deployment reaches 100%/COMPLETE instantly so no rollout step is ever observable, and FinalBakeTimeInMinutes never holds it in BAKING (so a bake-window StopDeployment is refused)

> _Note: this issue was identified against the code base at commit `6cc05b66b5dc4f3acc804c4a889717eb31d245db`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartDeployment

## Description
Two net-new root causes in the AppConfig deployment lifecycle, both observed on freshly started deployments whose strategy declares a non-zero duration and/or bake time. Related open issues that do NOT carry these checks' replay keys: 20261103T021132Z-appconfig-deployment-lifecycle-advances-instantly-through-deploy-bake.md, 20261029T233120Z-appconfig-rollout-percentage-never-gates-what-the-data.md, 20261107T214633Z-appconfig-2-net-new-causes-an-exponential-rollout.md and 20261107T182959Z-appconfig-2-net-new-causes-startexperimentrun-accepts-an.md — none of them owns the checks below, so they are filed here.

Cause 1 of 2: a rollout never advances through percentage steps — it is at 100% / COMPLETE from the first read, so the configuration is served to the whole fleet at once instead of to a growing percentage of sessions.
AWS: Smithy (appconfig) CreateDeploymentStrategy requires DeploymentDurationInMinutes (MinutesBetween0And24Hours, range 0..1440) and GrowthFactor (range 1..100) and takes GrowthType (enum LINEAR | EXPONENTIAL). Deployment/GetDeployment project State (DeploymentState enum: BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED) and PercentageComplete (Percentage, 1..100). Over a deployment of D minutes AppConfig raises PercentageComplete from the first growth step to 100 — LINEAR adds GrowthFactor per step (GrowthFactor=25 → 25/50/75/100), EXPONENTIAL multiplies it by powers of two capped at 100 (GrowthFactor=10 → 10/20/40/80/100) — logging one PERCENTAGE_UPDATED DeploymentEvent per step, and the data plane (GetLatestConfiguration) serves the new version to only that percentage of sessions, bucketed per session, while the rest keep receiving the previous version. State is DEPLOYING for the whole window and only then COMPLETE.
Emulator: with a 4-minute EXPONENTIAL GrowthFactor=10 strategy and with a LINEAR GrowthFactor=25 strategy, every mid-rollout sample observed zero partial states: the suite reports 'the rollout was not partial — across 0 mid-rollout sessions only [] was ever served' and, for the mid-rollout stop, 'the rollout reached COMPLETE at 100.0% before both versions were ever observed in service; only [] was seen, so there was no partial state to stop'. The deployment is already terminal (COMPLETE, PercentageComplete 100.0) by the first poll, so neither GrowthType nor GrowthFactor nor DeploymentDurationInMinutes has any effect and no mixed-version window exists.
Why: a client that starts a deployment to ramp a change and watches PercentageComplete/State (or runs a canary against the mixed fleet, or stops a bad rollout mid-ramp) sees the change go to 100% of sessions immediately. There is no window in which the rollout can be observed, measured or aborted, so progressive-deployment logic and alarm-based guardrails are silently bypassed.
Fix: the deployment state machine behind StartDeployment/GetDeployment (its clock-paced advance of PercentageComplete and State, plus the per-session bucketing the data plane applies when choosing which configuration version to serve).
Traces: appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor, appconfig.linear-rollout-serves-both-versions-across-sessions, appconfig.stop-deployment-mid-rollout-reverts-every-session.

Cause 2 of 2: FinalBakeTimeInMinutes is ignored — the deployment never enters BAKING, so it cannot be stopped during the bake and StopDeployment is refused as already COMPLETE.
AWS: Smithy CreateDeploymentStrategy.FinalBakeTimeInMinutes (MinutesBetween0And24Hours, 0..1440, default 0) is the time AppConfig monitors the configuration AFTER it has reached 100% of targets, before the deployment completes. During that window GetDeployment reports State=BAKING (DeploymentState enum) and the EventLog carries a BAKE_TIME_STARTED DeploymentEvent; reads do not advance it, so consecutive GetDeployment calls inside the window all report BAKING. Only when the window elapses with no alarm does it become COMPLETE. A StopDeployment issued during BAKING is accepted and drives the deployment to ROLLED_BACK with TriggeredBy=USER, and the data plane serves the previous configuration again; a second stop on the terminal deployment is then refused with BadRequestException (400).
Emulator: with FinalBakeTimeInMinutes=1 three consecutive GetDeployment reads returned ['COMPLETE', 'COMPLETE', 'COMPLETE'] instead of ['BAKING', 'BAKING', 'BAKING'] — there is no bake window at all. With FinalBakeTimeInMinutes=2, StopDeployment issued as soon as the deployment was started is refused HTTP 400 BadRequestException with message 'Deployment <deploymentNumber> for App <applicationId> and Environment <environmentId> cannot be stopped, it has a status of COMPLETE.' (fixed text 'Deployment ', ' for App ', ' and Environment ', ' cannot be stopped, it has a status of ', '.'; the deployment number, application id, environment id and status are values from the request and the emulator's state) — i.e. the stoppable state was skipped entirely.
Why: a client that sets a bake time to get an abort window, or that waits for BAKING before running post-deploy verification, never sees it: the deployment is terminal before the first read, a stop that AWS accepts is refused 400, and no rollback-to-previous-version path can be exercised. CloudWatch-alarm rollback has no window to act in either.
Fix: the deployment state machine behind StartDeployment/GetDeployment (entering and timing the BAKING state from FinalBakeTimeInMinutes and emitting BAKE_TIME_STARTED) and StopDeployment's state precondition, which must accept a BAKING deployment and drive it to ROLLED_BACK.
Traces: appconfig.final-bake-time-window-holds-the-deployment-non-terminal, appconfig.stop-deployment-during-bake-reverts-to-the-previous-version.

## Evidence
Cause 1 — expected: during a 4-minute EXPONENTIAL GrowthFactor=10 deployment, GetDeployment reports State=DEPLOYING with PercentageComplete stepping 10 → 20 → 40 → 80 → 100 (one PERCENTAGE_UPDATED EventLog entry per step) and the data plane serves both the old and the new document across sessions; actual: 'AssertionError: the rollout was not partial — across 0 mid-rollout sessions only [] was ever served, so the new version reached either none or all of the fleet instead of a percentage of it'. Same for LINEAR GrowthFactor=25. For the mid-rollout stop: 'AssertionError: the rollout reached COMPLETE at 100.0% before both versions were ever observed in service; only [] was seen, so there was no partial state to stop'.

Cause 2 — expected: with FinalBakeTimeInMinutes=1, three consecutive GetDeployment reads all report State=BAKING; actual: ['COMPLETE', 'COMPLETE', 'COMPLETE'] ('AssertionError: three consecutive GetDeployment reads during the bake must all report BAKING — reading must not advance the deployment'). Expected: with FinalBakeTimeInMinutes=2, StopDeployment during the bake returns 200 and the deployment settles ROLLED_BACK (TriggeredBy USER, BAKE_TIME_STARTED retained in EventLog); actual: HTTP 400 botocore.errorfactory.BadRequestException 'Deployment 2 for App ho65pb1 and Environment algcbw8 cannot be stopped, it has a status of COMPLETE.' (ids/numbers in that line are one run's values; the requirement is the status/code/message template, not those values).

## Steps to Reproduce
1. CreateApplication, CreateEnvironment (no Monitors), CreateConfigurationProfile with two distinct hosted configuration versions.
2. Cause 1: CreateDeploymentStrategy with DeploymentDurationInMinutes=4, GrowthType=EXPONENTIAL, GrowthFactor=10 (and again with GrowthType=LINEAR, GrowthFactor=25, ReplicateTo=NONE). StartDeployment of version 2, then poll GetDeployment and, in parallel, open many AppConfigData sessions and read GetLatestConfiguration. Observe the deployment is COMPLETE at PercentageComplete=100 on the first poll and every session gets version 2 — no intermediate percentage step and no session ever receives version 1.
3. Cause 2: CreateDeploymentStrategy with DeploymentDurationInMinutes=0, GrowthFactor=100, FinalBakeTimeInMinutes=1. StartDeployment, then call GetDeployment three times in a row: all three report COMPLETE instead of BAKING, and the EventLog has no BAKE_TIME_STARTED entry.
4. Repeat step 3 with FinalBakeTimeInMinutes=2 and call StopDeployment immediately after StartDeployment: it is refused HTTP 400 BadRequestException '... cannot be stopped, it has a status of COMPLETE.' instead of being accepted and settling the deployment ROLLED_BACK with the previous configuration served again.
