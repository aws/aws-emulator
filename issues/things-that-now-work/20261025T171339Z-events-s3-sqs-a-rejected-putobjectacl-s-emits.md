# events__s3__sqs: a rejected PutObjectAcl's "emits no event" contract is ungradeable because S3 publishes nothing on either notification path (the previously recorded GetBucketOwnershipControls key no longer reproduces)

> _Note: this issue was identified against the code base at commit `b3c7a1d3b5e40780898598751dac20435d474802`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutBucketNotificationConfiguration

## Description
One root cause. Cause count: 1.

=== Cause 1 of 1: an S3 data-plane write emits nothing on either notification path, so the "a REJECTED PutObjectAcl emits no ACL event" contract cannot be graded ===

AWS: with PutBucketNotificationConfiguration carrying `EventBridgeConfiguration: {}`, S3 publishes envelopes with source `aws.s3` to the account's DEFAULT event bus, detail-type naming the change ("Object Created", "Object ACL Updated", "Object Tags Added", "Object Tags Deleted", "Object Restore Initiated") and `detail.request-id` equal to the x-amz-request-id of the request that caused it; with a `QueueConfigurations` entry on the same bucket, S3 additionally sends the classic records (`s3:ObjectAcl:Put`, `s3:ObjectTagging:Put`) straight to the named SQS queue with `responseElements."x-amz-request-id"` set to that same request id. Both paths fire for the same write, and GetBucketNotificationConfiguration reads both configurations back. Crucially, a REFUSED request emits nothing on either path: under the default `BucketOwnerEnforced` object ownership, PutObjectAcl is refused with HTTP 400 and error code `AccessControlListNotSupported`, message `The bucket does not allow ACLs` (that message is entirely fixed text — it has no request- or state-derived parts), the object's ACL is left unchanged, and no `s3:ObjectAcl:Put` record and no "Object ACL Updated" envelope is produced for it. After PutBucketOwnershipControls switches the bucket to `BucketOwnerPreferred`, the same PutObjectAcl succeeds and BOTH paths deliver an ACL event whose request id is the SUCCESSFUL request's id, never the rejected one.
Emulator: `Check timed out after 60.0s`. The check first wires the bucket (both EventBridgeConfiguration and a QueueConfigurations entry in one PutBucketNotificationConfiguration), a queue policy admitting s3.amazonaws.com for the bucket ARN, and a default-bus rule on {"source":["aws.s3"],"detail-type":["Object ACL Updated","Object Tags Added"]} targeting a second queue; it then requires TWO CONSECUTIVE warm-up rounds (a PutObject + PutObjectTagging pair) to reach BOTH inboxes before it will grade anything. Neither inbox ever receives a message, so the warm-up never completes and the check is cut off at the cap. Nothing downstream of the write is observable: not the classic path, not the EventBridge path, and therefore not the absence that the rejected ACL call is supposed to produce.
Why: a client wiring an ACL/tagging audit trail gets a bucket, a queue, a rule and a notification configuration that all report healthy, and a consumer that is never invoked — it cannot distinguish "no event yet" from "no event ever". Worse for this contract specifically: because nothing is ever delivered, an emulator that fires the notification BEFORE (or regardless of) the ownership check would be indistinguishable from one that correctly suppresses it, so a consumer cannot rely on "an event means the mutation happened". Any downstream that treats an ACL event as proof of an applied ACL change would act on a refused request.
Fix: the S3 notification publisher in the s3 service crate — the code that must emit to EventBridge (default bus, source `aws.s3`) and to the configured QueueConfigurations targets from the PutObject / PutObjectAcl / PutObjectTagging / DeleteObjectTagging handlers under services/service-com-amazonaws-s3-amazons3/src/ops/ — plus the EventBridge default-bus ingestion of `aws.s3` events. The emit must be placed AFTER the ownership-control admission check in put_object_acl so a refused call publishes nothing, and the published request id must be the id of the request that actually mutated the object.
Related issues, neither of which covers this check at its current signature: the open issue 20261025T002357Z-events-s3-sqs-s3-produces-no-aws-s3-events-on-either.md names this check id in its trace ids, but only under its Cause 2 (GetBucketOwnershipControls answering OwnershipControlsNotFoundError for a fresh bucket) and it carries the replay key `s3|GetBucketOwnershipControls|OwnershipControlsNotFoundError`. That key no longer reproduces: the check now gets past `get_bucket_ownership_controls` asserting the default [{'ObjectOwnership': 'BucketOwnerEnforced'}] and stalls later, in the notification warm-up, which is why the replay report did not mark it OWNED. A fixer replaying only that key would see the failure move rather than close, so this issue records the current signature. The open issue 20261024T190039Z-events-lambda-s3-sfn-s3-event-notifications-never-fire-a-putobject-publishes.md covers the PutObject/LambdaFunctionConfiguration pair under a different service group and neither names this check nor the ACL/tagging detail-types.
