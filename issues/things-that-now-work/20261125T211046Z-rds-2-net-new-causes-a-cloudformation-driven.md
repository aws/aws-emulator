# rds: 2 net-new causes — a CloudFormation-driven DBParameterGroupName switch never settles in-sync on the live instance, and the ApplyImmediately=false / maintenance-window pending-change contract is never observed to hold

> _Note: this issue was identified against the code base at commit `e0dd7a4e9d8aa683c383dd9c3df969fda9922d23`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyDBInstance

## Description
Two net-new root causes in the RDS DB-instance parameter-group / pending-modification surface, both grounded in failing behavioral checks of this replay that the suite marked neither ALREADY FILED nor OWNED. They are bundled because they belong to ONE service (rds); a fixer must close BOTH before submitting.

Cause 1 of 2: after a CloudFormation stack update that repoints AWS::RDS::DBInstance.DBParameterGroupName at a different parameter group, DescribeDBInstances never reports the live instance associated with the new group at ParameterApplyStatus "in-sync", so a client's convergence poll never settles.
AWS: Smithy (com-amazonaws-rds-amazonrdsv19) — DBInstance carries DBParameterGroups, a list of DBParameterGroupStatus{DBParameterGroupName, ParameterApplyStatus}. ParameterApplyStatus is documented with exactly these values: "applying" (the parameter group change is being applied to the database), "failed-to-apply", "in-sync" (the parameter group change is synchronized with the database), "pending-database-upgrade", "pending-reboot" (the change will be applied after the DB instance reboots). The group being switched to differs only by a parameter the engine-default catalog itself reports as ApplyType=dynamic and IsModifiable=true (the check selects it from DescribeEngineDefaultParameters), so AWS applies it WITHOUT a reboot: the instance's DBParameterGroups[0].DBParameterGroupName becomes the new group and its ParameterApplyStatus moves "applying" -> "in-sync" on its own, with no RebootDBInstance. Changing DBParameterGroupName on AWS::RDS::DBInstance is an in-place update, so DbiResourceId is unchanged, and DescribeDBParameters on the new group reports the explicitly set parameter with Source "user". The requirement is the settling to in-sync under its own power for a dynamic parameter, not any particular timing.
Emulator: the stack UPDATE itself reaches UPDATE_COMPLETE (the check gets past its UPDATE_COMPLETE wait), but the following poll of DescribeDBInstances for (DBParameterGroups[0].DBParameterGroupName == new group AND ParameterApplyStatus == "in-sync") never becomes true and the check is cut off: TimeoutError "instance <id> parameter group <group-b> in-sync: the run budget ended first; not graded". No refusal was recorded on any call. Hypothesis (neither the model nor the recording states it): the instance's association is either not rewritten by the CloudFormation update at all, or it is rewritten but parked permanently at "pending-reboot"/"applying" so a dynamic-only difference never reaches "in-sync". Note the harness itself labels this step "not graded" because the run budget, not the poll's own 300 s deadline, ended it — re-replay this check with budget to confirm. The resolved issue 20261123T230939Z-rds-describedbinstances-never-reports-a-switched-db-parameter.md covers the opposite direction (a switch that must report pending-reboot) and does NOT cover a dynamic-only switch that must settle to in-sync; it is named here only as context, not as coverage.
Why: a client that repoints a DB instance at a new parameter group — directly or through a CloudFormation stack update — waits forever for the documented terminal state. Every deployment pipeline that gates on DBParameterGroups[*].ParameterApplyStatus == "in-sync" before continuing (the standard way to know a parameter change has landed) hangs instead of converging, and a client cannot distinguish "still applying" from "will never apply".
Fix: the RDS DB-instance parameter-group association state and the status it projects — the ModifyDBInstance handler and the DescribeDBInstances projection of DBParameterGroups in services/service-com-amazonaws-rds-amazonrdsv19/src/ops/ and the instance record in src/state — plus the CloudFormation AWS::RDS::DBInstance update path that must drive that association when DBParameterGroupName changes: a group whose difference is a dynamic, modifiable parameter must settle to "in-sync" without a reboot and without replacing the instance.
Traces: rds.deploy-cfn-stack-update-modifies-live-parameter-group (verdict error).

Cause 2 of 2: the ApplyImmediately=false contract for ModifyDBInstance is never observed to hold — the check that asserts the requested AllocatedStorage stays pending (and does NOT self-apply outside the preferred maintenance window) produces no verdict at all inside a client's polling window.
AWS: Smithy (com-amazonaws-rds-amazonrdsv19) — ModifyDBInstance.ApplyImmediately: "Specifies whether the modifications in this request and any pending modifications are asynchronously applied as soon as possible, regardless of the PreferredMaintenanceWindow setting for the DB instance. By default, this parameter is disabled. If this parameter is disabled, changes to the DB instance are applied during the next maintenance window." DBInstance.PendingModifiedValues is "used as a response element in the ModifyDBInstance operation and contains changes that will be applied during the next maintenance window", and carries AllocatedStorage ("The allocated storage size for the DB instance specified in gibibytes (GiB)"). So with ApplyImmediately=false and a PreferredMaintenanceWindow several days out: DescribeDBInstances must keep reporting the LIVE AllocatedStorage (20) unchanged and must report PendingModifiedValues.AllocatedStorage == 30 continuously, for as long as the window stays shut; the pending entry must neither self-apply nor silently disappear. DescribeDBInstances must also echo PreferredMaintenanceWindow as the instance was created with it.
Emulator: the check produces no graded answer — "Error: Check timed out after 60.0s" — so the steady-state assertion (live 20 / pending 30 held open, neither applied nor dropped) was never satisfied within the window the suite gives a client. Its earlier single-shot assertions (AllocatedStorage==20, PendingModifiedValues.AllocatedStorage==30 immediately after the modify) raise AssertionError rather than time out, so the divergence is in the SETTLING of this sequence — CreateDBInstance to "available", then the deferred modification held stably pending — not in one malformed field. Hypothesis (neither the model nor the recording states it): either the instance does not reach "available" quickly enough for the deferred-modification phase to be reached at all, or the deferred record does not stay pending for the whole poll (it is applied early or withdrawn), so the asserted state is never published long enough to be read.
Why: a client that defers a storage change to the maintenance window cannot verify the deferral. If the change self-applies it causes an unscheduled storage operation AWS would not have performed outside the window; if the pending entry vanishes the change is lost silently — in either case PendingModifiedValues stops being a truthful statement of what is scheduled, which is the only thing a client has to reconcile desired against live configuration.
Fix: the ModifyDBInstance deferred-modification path and its projection — services/service-com-amazonaws-rds-amazonrdsv19/src/ops/modify_db_instance.rs (the apply_immediately / DeferredModification staging) together with the DescribeDBInstances projection of PendingModifiedValues and the instance's status convergence to "available" in src/state — must hold a non-immediate modification pending indefinitely while the PreferredMaintenanceWindow is shut, leaving the live value untouched.
Traces: rds.maintenance-window-controls-pending-change-application (verdict mismatch).
