# API Gateway: per-method usage-plan throttle overrides are silently dropped, a CFN-provisioned BasePathMapping is unresolvable, and the private VPC_LINK estate never converges (3 causes)

> _Note: this issue was identified against the code base at commit `df009dd79b3a670d3c0c53c12bb5e37a115b862c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateUsagePlan

## Description
Three net-new root causes on the API Gateway (REST, v1) surface, each grounded in a failing behavioral check that no open issue carries the replay key for. A fixer must close ALL THREE before submitting.

Cause 1 of 3: UpdateUsagePlan accepts a method-scoped throttle-override patch and then neither applies nor refuses it — GetUsagePlan reports apiStages[].throttle without the overridden method entry.
AWS: Smithy (com.amazonaws.apigateway#UpdateUsagePlan): PATCH /usageplans/{usagePlanId} with patchOperations, success 200 -> UsagePlan; modeled errors BadRequestException(400), ConflictException(409), NotFoundException(404), LimitExceededException(429), TooManyRequestsException(429), UnauthorizedException(401). GetUsagePlan: GET /usageplans/{usagePlanId}, 200 -> UsagePlan. UsagePlan.apiStages targets ListOfApiStage; ApiStage.throttle targets MapOfApiStageThrottleSettings (key String -> value ThrottleSettings{rateLimit:Double, burstLimit:Integer}), documented as "Map containing method level throttling information for API stage in a usage plan". Recorded behavior (the model does not spell the key format): the map is keyed by "{resourcePath}/{httpMethod}" — for a top-level resource created with pathPart P and method M the key is "/P/M" — and the patch path that addresses that entry is "/apiStages/{apiId}:{stage}/throttle/{resourcePath}/{httpMethod}/rateLimit" (and .../burstLimit), with the resourcePath segment given bare for a top-level resource. An `add` of those two paths makes GetUsagePlan report that key with the patched rateLimit/burstLimit while leaving the plan-level UsagePlan.throttle untouched; a `remove` of "/apiStages/{apiId}:{stage}/throttle/{resourcePath}/{httpMethod}" makes the key disappear again. A patch path the service cannot address is refused BadRequestException(400) — it is never accepted as a no-op.
Emulator: both `add` patch operations are accepted with a 200 UsagePlan response, but the following GetUsagePlan returns apiStages[0] whose throttle map does not contain the method key at all (the check's lookup of that key raises KeyError), so the override is neither stored under the AWS key nor refused. The plan-level throttle is the only throttling representation that survives a write.
Why: a client that provisions per-method throttles through a usage plan gets a 200 for a write that did nothing, so its read-back of apiStages[].throttle shows no override and its reconciliation loop either re-patches forever or concludes AWS lost the setting; because the bad path is not refused either, a genuinely malformed patch path is indistinguishable from a successful one. Any per-method rate limiting configured this way is silently absent.
Fix: the UpdateUsagePlan patch handler and the usage-plan state it writes (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/update_usage_plan.rs), plus the ApiStage.throttle serialization read back by get_usage_plan.rs — the "/apiStages/{apiId}:{stage}/throttle/{resourcePath}/{httpMethod}/{rateLimit|burstLimit}" path family must be addressable, must store under the "{resourcePath}/{httpMethod}" key, must support `remove`, and any path outside that family must be refused BadRequestException rather than accepted.
Traces: apigateway.usage-plan-key-throttle-override-window.

Cause 2 of 3: a CloudFormation stack whose AWS::ApiGateway::BasePathMapping reaches CREATE_COMPLETE leaves nothing resolvable — GetBasePathMapping answers 404 NotFoundException "Invalid domain name identifier specified".
AWS: Smithy (com.amazonaws.apigateway#GetBasePathMapping): GET /domainnames/{domainName}/basepathmappings/{basePath}, success 200 -> BasePathMapping{basePath, restApiId, stage}; modeled errors BadRequestException(400), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). NotFoundException at 404 is for a domain name or base path that does not exist. CloudFormation only reports CREATE_COMPLETE for a resource it actually created, so once the stack containing AWS::ApiGateway::DomainName (REGIONAL, RegionalCertificateArn from an imported ACM certificate) and AWS::ApiGateway::BasePathMapping{BasePath: <path>, RestApiId: Ref RestApi, Stage: Ref Stage} is complete, GetBasePathMapping for that (domainName, basePath) must answer 200 with restApiId/stage equal to the stack's own REST API and stage, and the domain must converge to domainNameStatus=AVAILABLE. Recorded behavior: "Invalid domain name identifier specified" is AWS's NotFoundException message for an unknown domain-name identifier — entirely fixed text, with no part taken from the request.
Emulator: cloudformation.CreateStack plus the stack_create_complete waiter succeed, and then apigateway.GetBasePathMapping(domainName=<the templated DomainName>, basePath=<the templated BasePath>) answers HTTP 404 Error.Code=NotFoundException, Error.Message="Invalid domain name identifier specified" — the domain, and therefore the mapping, was never materialised in the API Gateway control plane, so the stack's reported success is a lie.
Why: a client that provisions a custom domain and its base-path mapping by template is told the stack converged and then cannot resolve, poll or route that base path through the API Gateway API; it cannot tell "never created" from "correctly deleted", and infrastructure-as-code over API Gateway custom domains fails silently.
Fix: the CloudFormation resource providers for AWS::ApiGateway::DomainName and AWS::ApiGateway::BasePathMapping (services/service-com-amazonaws-cloudformation-cloudformation), which must drive the apigateway CreateDomainName / CreateBasePathMapping state rather than only recording the logical resource, so the apigateway read path can resolve them. Related open issue that does NOT carry this check id: 20261025T174338Z-apigateway-api-gateway-custom-domain-surface-cloudformation-provisioned-domainname.md (its Cause 1 is the same family, keyed on GetDomainName for two sibling checks); also 20261023T125454Z-apigateway-cloudformation-provisioned-api-gateway-resources-are-unaddressable-through.md for RestApi/Stage/Authorizer/UsagePlan.
Traces: apigateway.deploy-domain-name-cfn-behaves.

Cause 3 of 3: the private VPC_LINK integration estate never converges — the check builds an isolated VPC, two subnets, an internal ALB, an internal NLB and a VpcLink and never completes, hanging to the harness's 60 s cap.
AWS: Smithy (com.amazonaws.apigateway#GetVpcLink): GET /vpclinks/{vpcLinkId}, 200 -> VpcLink{id,name,targetArns,status,statusMessage,tags} where status targets enum VpcLinkStatus = [AVAILABLE, PENDING, DELETING, FAILED]; a created link is observed PENDING and then advances to AVAILABLE, i.e. the state machine terminates. Recorded behavior for the rest of the estate: each prerequisite resource reaches an available state in bounded time (ec2 CreateVpc/CreateSubnet report available to their waiters, elbv2 load balancers become active), and a {proxy+} HTTP_PROXY integration with connectionType=VPC_LINK then forwards the request to the private backend, returning the backend's own body and status (both the matched rule's body/status and the default action's differing body/404) at the public stage URL.
Emulator: no terminal answer at all — the check is killed by the runner at 60 s ("Check timed out after 60.0s") with no response recorded, so some step in that chain never returns a converged state. Hypothesis: one of the resource state machines in the chain never leaves its pending state (the same failure mode as the EC2 interface VPC endpoint in open issue 20261026T090242Z-apigateway-every-private-custom-domain-domain-name-access.md), so the waiter polls until the cap; the private-integration data-plane leg is never reached.
Why: every private-integration client blocks instead of failing — a caller gets neither a converged resource nor a modeled refusal, so waiters and readiness polls spin to their own timeouts, and no VPC_LINK-backed REST API can be stood up or exercised against the emulator.
Fix: the resource state machines backing this chain must converge in bounded time and be reported as such — apigateway CreateVpcLink/GetVpcLink must advance VpcLinkStatus PENDING -> AVAILABLE (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/create_vpc_link.rs, get_vpc_link.rs), and the ec2/elbv2 resources the link targets must report an available/active state rather than remaining pending. Related open issue (different replay key, EC2 VPC endpoint rather than VpcLink): 20261026T090242Z-apigateway-every-private-custom-domain-domain-name-access.md; the open scaffold-stub issue 20261023T125454Z-apigateway-createvpclink-stub.md names create_vpc_link.rs but does not carry this check id and does not describe the non-convergence.
Traces: apigateway.deep-apigateway-3-apigw-private-vpclink-positive.
