=== Cause 1 of 3: a deployed REST stage whose method uses a CUSTOM REQUEST Lambda authorizer answers HTTP 500 {"message":"Internal server error"} on every request, so no authorize decision is ever produced and the authorizer-result cache and its flush are unreachable ===
AWS: Smithy (com.amazonaws.apigateway#BackplaneControlService) CreateAuthorizer — POST /restapis/{restApiId}/authorizers, success 201, output shape Authorizer; required members restApiId, name, type (enum AuthorizerType), plus authorizerUri, identitySource and authorizerResultTtlInSeconds (NullableInteger); modeled errors BadRequestException(400), ConflictException(409), LimitExceededException(429), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). Smithy FlushStageAuthorizersCache — DELETE /restapis/{restApiId}/stages/{stageName}/cache/authorizers, success 202, output smithy.api#Unit, same modeled error set. The data plane itself is not spelled by the control-plane model, so for it: recorded behavior only — a request to the deployed stage carrying the configured identity source invokes the authorizer Lambda through its authorizerUri; an Allow policyDocument for the request's methodArn makes the gateway run the method's integration and return the INTEGRATION's own status and body (here HTTP 200 from a MOCK integration with requestTemplates {"application/json":'{"statusCode": 200}'}); within authorizerResultTtlInSeconds (300 s here) a repeat request whose identity-source VALUE is the same reuses the cached decision and does not re-invoke the Lambda; a different identity-source value invokes it exactly once; after FlushStageAuthorizersCache (202) the next request with the original identity re-invokes it exactly once. HTTP 500 with body {"message":"Internal server error"} is the envelope AWS reserves for an authorizer that errors, times out or returns a malformed policy — fixed text, no variable part.
Emulator: every GET on the deployed stage URL with the configured Authorization header answers HTTP 500 with body {"message":"Internal server error"}. The check polls for a 200 for 180 s and its last observed value is (500, b'{"message":"Internal server error"}'). The authorizer Lambda is never observed to run — the per-invocation record it posts to its SQS queue never arrives — so the Allow decision is never obtained, the TTL-reuse and per-identity keying behaviour is never reached, and FlushStageAuthorizersCache is never exercised at all.
Why: the whole CUSTOM-authorizer data plane is unusable for REQUEST authorizers. A client gets a 500 where AWS returns the integration's 200, and cannot distinguish "my authorizer code failed" (which is what that envelope means in AWS) from "the gateway cannot invoke authorizers at all". Every behaviour layered on an authorize decision — TTL reuse, per-identity cache keying, cache invalidation via flush — is silently unverifiable, and a protected API simply cannot be called.
Fix: the API Gateway execute-api data-plane invoke path's authorizer stage and its authorizer-result cache (the apigateway crate's data-plane invoke handling, not CreateAuthorizer's control-plane handler, which accepts the authorizer correctly): invoke the configured REQUEST authorizer's Lambda through its authorizerUri, interpret the returned IAM policy document, run the method integration on Allow and return the integration's own status and body, key the cached decision by the identitySource value for authorizerResultTtlInSeconds, and have FlushStageAuthorizersCache drop those entries for the named stage. The 500 envelope must be emitted only when the authorizer genuinely errors, times out or returns a malformed policy.
