# CodeCommit git transport: no clone, fetch or push over the announced cloneUrlHttp ever completes, so nine git data-plane checks exhaust their window

> _Note: this issue was identified against the code base at commit `9a6c9844b7b2b3cba2945c38dfe9b6ac305cdb4c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GitPull/GitPush (git smart-HTTP transport) and GetRepository (repositoryMetadata.cloneUrlHttp)

## Description
One root cause, in the codecommit service crate: the address announced as `repositoryMetadata.cloneUrlHttp` does not complete a git exchange for an unmodified git client, so every behavioral check that has to clone, fetch or push over it — including the POSITIVE CONTROL that four authentication checks run before their negative half — never gets a successful git invocation and the check exhausts its budget.

Related but NOT covering (both open, both carrying other check ids/replay keys): 20261025T040000Z-codecommit-announced-clone-url-is-served-with-an-untrusted-certificate.md (same family of symptom, carries codecommit.delete-file-on-tag-named-branch-blocked, codecommit.git-push-non-fast-forward-refused-by-the-server, codecommit.git-push-over-https-is-readable-through-the-api) and 20261120T182842Z-codecommit-git-transport-authenticates-nobody-any-password-and.md (password/revocation not verified, and the then-announced `http://` scheme; it carries codecommit.git-credential-helper-clone-push-roundtrip and codecommit.git-transport-with-forged-sigv4-refused). Neither carries the nine check ids below, and the two authentication checks it names (wrong password, deleted credential) no longer fail at their assertions at all — they now die earlier, in the positive control, which is the cause reported here.

Cause 1 of 1 — the announced cloneUrlHttp is not an origin a stock git client can complete a request against, so every git clone/fetch/push against it fails and is retried until the check's window closes.
AWS: Smithy: RepositoryMetadata.cloneUrlHttp — "The URL to use for cloning the repository over HTTPS". It is an address, not a label: a client is handed it and dials it with the configuration it already has (`https://git-codecommit.<region>.amazonaws.com/v1/repos/<name>`, served over TLS with a certificate the client's trust store accepts). With CodeCommit HTTPS git credentials minted by IAM CreateServiceSpecificCredential(ServiceName="codecommit.amazonaws.com"), `git clone <cloneUrlHttp>` completes and yields the content the API seeded at the commit GetBranch reports as the tip; `git fetch` advances to a commit a later PutFile created; `git push` of a branch, a deleted branch or an annotated tag is accepted and becomes visible through ListBranches/GetBranch/GetReference; an unauthenticated request is refused promptly with 401 + `WWW-Authenticate: Basic realm="CodeCommit"` so git exits non-zero immediately. Every one of those outcomes is reached in seconds, not after minutes of retrying.
Emulator: not one of the nine checks below records a completed git exchange. Each reports only `Check timed out after 60.0s`: the checks retry a failing git invocation (`_retry_git`/`_poll_git`, 5 s apart, 150 s window) and never see a zero exit, so the 60 s check budget expires with the transport having served nothing usable. Four of them (wrong password, deleted credential, no-credential clone/push, unauthenticated branch delete) reach this in their POSITIVE CONTROL, so their negative assertions are never evaluated — the two causes 20261120T182842Z filed on that negative half are now unobservable, and this cause masks them. Hypothesis for the mechanism, from the checkout rather than from the replay (the replay carries no git stderr, only the timeout): services/service-com-amazonaws-codecommit-codecommit-20150413/src/state/git_endpoint.rs:67 and :155-159 now announce the TLS half of the in-band address (`GIT_SCHEME_TLS = "https"`) whenever `listeners.tls_upgrader()` succeeds, and that upgrader's certificate is the core's own self-signed material (vendor/server/src/listeners.rs:192-196, `TlsCertificateAuthority::covering(None)`, lent at :244-246). A stock git client refuses that origin before any git protocol exchange, exiting 128 with the fixed text `fatal: unable to access '<clone url>/': server verification failed: certificate signer not trusted.` — the `<clone url>` is the announced cloneUrlHttp and the CAfile path is the client's, both per-run values, not requirements; that exact stderr is what the earlier recording in 20261025T040000Z captured on this same address. Whatever the mechanism, the requirement the replay establishes is the observable one: an authenticated git clone, fetch and push against the announced cloneUrlHttp must COMPLETE, and an unauthenticated one must be REFUSED promptly rather than retried to exhaustion.
Why: the whole CodeCommit git data plane is unreachable for any client that does what AWS documents — read `cloneUrlHttp` and hand it to git. No repository can be cloned, no commit fetched, no branch or tag pushed, and no push-time behavior (branch protection, non-fast-forward refusal, tag-vs-branch rules, which CodeCommit exposes ONLY over git) can be exercised. Worse, every negative authentication check becomes vacuous: it can no longer distinguish "refused correctly" from "the transport answered nothing at all", so a client cannot tell that the emulator in fact verifies no password and refuses no revoked credential.
Fix: the announced address in src/state/git_endpoint.rs (`GIT_SCHEME_TLS`/`GIT_SCHEME_CLEAR`, `ensure_git_endpoint`) must publish an origin an unmodified git client completes a request against — either a TLS origin whose certificate chain the client's trust store accepts, or the clear half of the in-band address when it cannot — and src/service/git_http.rs must answer upload-pack/receive-pack on exactly that announced address, with the 401 challenge for a request presenting no credential. File and line citations are given above under Traces/Emulator for orientation only.

## Evidence
All nine checks are [mismatch] with the identical detail `Check timed out after 60.0s`; none records a git exchange that completed.

Expected (AWS): with an IAM service-specific credential for codecommit.amazonaws.com in the URL, `git clone <cloneUrlHttp>` exits 0 and HEAD equals the commitId PutFile returned; `git fetch` brings the branch to the commit a later PutFile created; `git push` of a new branch / a deleted branch / an annotated tag exits 0 and the ref is then visible through GetBranch/ListBranches/GetReference; a request with no credential is refused at once (401 + `WWW-Authenticate: Basic realm="CodeCommit"`, git exits non-zero with its own `fatal: Authentication failed for '<url>'`).

Actual (emulator): every git invocation against the announced cloneUrlHttp returns non-zero, the checks' retry loops (5 s interval, 150 s window) keep retrying it, and the check is killed at 60 s with nothing served. Four checks hit this inside the positive control they run FIRST (codecommit.git-clone-push-without-git-credentials-refused line "POSITIVE CONTROL: the identical transport with real IAM git credentials succeeds"; codecommit.git-credentials-with-wrong-password-refused line "POSITIVE CONTROL FIRST: the correct password clones"), so their negative assertions were never reached.

From the checkout (hypothesis for the mechanism, not from the replay): src/state/git_endpoint.rs:67,155-159 announces `https` whenever `listeners.tls_upgrader()` is available, and that upgrader carries the core's self-signed certificate (vendor/server/src/listeners.rs:192-196,244-246). The earlier recording on this same address (issue 20261025T040000Z) captured git exiting 128 with `fatal: unable to access '<url>': server verification failed: certificate signer not trusted.` — fixed text, with the URL and the CAfile path per-run values. Host, port, repository name, commit ids and credential values in any of these runs are per-run and are not requirements.

## Steps to Reproduce
1. `meta = cc.create_repository(repositoryName=R)['repositoryMetadata']`; `cc.put_file(repositoryName=R, branchName='main', filePath='README.md', fileContent=b'seed\n', commitMessage='seed')` and keep the returned commitId.
2. Create an IAM user, attach a policy allowing `codecommit:GitPull` and `codecommit:GitPush` on `meta['Arn']`, then `iam.create_service_specific_credential(UserName=U, ServiceName='codecommit.amazonaws.com')`.
3. With a hermetic git (`GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`), run `git clone <scheme>://<ServiceUserName>:<ServicePassword>@<authority>/v1/repos/R` where the scheme/authority come from `meta['cloneUrlHttp']` -> expect exit 0 with HEAD equal to the commitId from step 1; observe a non-zero exit, repeated for the full retry window.
4. Same address: `git fetch` after a further PutFile, `git push` of a new branch, of an annotated tag, and of a branch deletion -> expect exit 0 and the ref visible through GetBranch/ListBranches/GetReference; observe none of them completing.
5. Same address with NO credential: `git clone <cloneUrlHttp>` and `git push` -> expect an immediate non-zero exit after a 401 challenge, with the API-seeded tip unmoved; observe the check never getting past its positive control.
6. Re-replay the nine check ids in trace_ids.
