# GetSprites sprites.json reports a uniform 20x20 icon box and shifted atlas offsets

> _Note: this issue was identified against the code base at commit `3fa8c42c1df735de25d8beda9af18b43438c14a4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSprites

## Description
The emulator answers GetSprites for the sprite index (FileName=sprites.json) with a synthesised atlas descriptor in which every icon is described as a fixed 20x20 box laid out on a regular grid. AWS publishes a real packed sprite atlas: each icon carries its own natural width/height and the x/y offset where it actually sits in the sheet. Two net-new divergence clusters share this one root cause; both are GetSprites on the sprites.json index, reached through two different fixtures and style/colour-scheme/variant combinations. This issue bundles 2 causes.

Cause 1 of 2 - sprites.json icon box sizes and x offsets for the colour-variant sprite index (fixture geo-maps-sprites-style-color-variants, step task#3).
AWS: recorded behavior only. Smithy: GetSprites input is FileName (@pattern ^sprites(@2x)?\.(png|json)$), Style, ColorScheme, Variant, all @httpLabel/@required; output is an opaque Blob bound with @httpPayload plus Content-Type/Cache-Control/ETag headers, and the operation models no errors (http GET /v2/styles/{Style}/{ColorScheme}/{Variant}/sprites/{FileName}, code 200). The model therefore says nothing about the body, so the requirement is what the recording shows: HTTP 200 whose body is the sprite-atlas index, an object keyed by icon name where each entry's width/height are that icon's own pixel dimensions and x/y are its position in the packed sheet. The recording shows icons of many different sizes - tall shields, wide shields and small square glyphs - and x offsets that advance by each preceding icon's real width rather than by a constant step.
Emulator: returns 200 with an index in which the icons are all the same size and are packed on a constant-pitch grid. Every differing entry collapses to width=20 and height=20, and the x offsets drift from the recorded ones as a consequence. Replayed examples: shield-AE width 21->20, height 30->20; shield-AE:E-route width 21->20, height 30->20, x 1407->1406; shield-AU:MR width 19->20, x 1428->1426; shield-AU:T width 21->20, height 22->20; shield-BAB width 36->20, x 1507->1506; shield-BR width 22->20, height 27->20, x 1543->1526; shield-CA:transcanada width 24->20, height 24->20, x 1565->1566; shield-CN:expressway-long width 43->27, height 28->20, x 1589->1606; shield-CN:expressway width 30->20, height 28->20, x 1632->1586; shield-CR:CR width 23->20, height 26->20, x 1662->1633. The cluster covers several hundred such width/height/x/y keys across the shield-*, hgv-*, rectangle-* and point-of-interest icon families.
Why: a MapLibre/Mapbox GL client loads sprites.json to slice icons out of sprites.png. Because every entry claims a 20x20 box at the wrong offset, the client crops the wrong rectangle of the sheet for every non-20x20 icon: route shields and restriction plates render clipped or show a slice of the neighbouring icon, and icon-image lookups in the style descriptor resolve to visually wrong art. A client that validates sprite dimensions against the style (icon-size, text-offset, shield padding) also computes wrong label placement. Nothing fails loudly - the response is 200 - so the defect surfaces only as a mis-rendered basemap.
Fix: the GetSprites handler's sprites.json body, i.e. the sprite-atlas index the maps.geo asset layer serves. It must emit the per-icon dimensions and packed offsets of the sprite sheet it actually serves instead of generating a uniform grid; the index's width/height/x/y must be derived from the real atlas packing, not from a fixed cell size.
Traces: geo-maps-sprites-style-color-variants#task#3 (GetSprites, expected 200, actual 200, body mismatch).

Cause 2 of 2 - the same uniform-grid sprite index served on the basemap style workflow's sprite fetch (fixture geo-maps-vector-basemap-style-workflow, step task#3).
AWS: recorded behavior only; same Smithy signature as above (GetSprites, opaque Blob @httpPayload, no modeled errors). This step reaches GetSprites after the style descriptor fetch, for a different Style/ColorScheme/Variant combination, and the recording again shows per-icon natural sizes and packed offsets - and a slightly different icon-name set for that variant (e.g. the atlas names the Trans-Canada shield shield-CA-TransCanada here, where the other fixture's variant names it shield-CA:transcanada). The requirement is that the index describes whichever atlas that style/variant actually serves.
Emulator: again 200 with every differing icon flattened to width=20 and height=20 on a constant-pitch grid, so the same class of keys diverges for this variant too. Replayed examples: shield-AE width 21->20, height 30->20; shield-BAB width 36->20, x 1507->1506; shield-BR width 22->20, height 27->20, x 1543->1526; shield-CA-TransCanada width 24->20, height 24->20, x 1565->1566; shield-CN:expressway-long width 43->27, height 28->20, x 1589->1606; shield-CR:CR width 23->20, height 26->20, x 1662->1633; plus truck-parking, stadium and the hgv-* restriction plates.
Why: this is the path a real map client takes - GetStyleDescriptor, then the sprite URL the descriptor advertises. A client walking that workflow gets a sprite index that does not describe the sheet, so every shield and restriction plate in the vector basemap is cropped wrongly, and the defect is variant-independent: switching style, colour scheme or variant does not get the client a correct atlas.
Fix: same component as Cause 1 - the GetSprites sprites.json index must be generated from the real per-variant atlas packing, so the fix has to hold for every Style/ColorScheme/Variant the service serves, not just the one in Cause 1.
Traces: geo-maps-vector-basemap-style-workflow#task#3 (GetSprites, expected 200, actual 200, body mismatch).

## Resolution, and what remains

Fixed: a route shield is no longer reported at one family box. The catalog now carries each
shield's own published plate where the published index reports one — the tall Emirati route
plate, the two Australian plates narrower than the base box, the Australian tourist plate, the
German Autobahn plate (under both of its published names), the Brazilian plate, the square
Trans-Canada plate (under whichever name the sheet publishes) and the Chinese expressway plates
and Costa Rican plates — and the digit-capacity rule answers only for a shield the index
reports at no plate of its own. The index's listing order was generalised from the city dots to
every family the sheet carries (every name one root name is a prefix of, widest plate first), so
a `-long` number plate is listed before the plate it widens, and the bare country code
`shield-CA`, which the published index does not carry, was dropped. The sheet's width moved with
those footprints so the published row break still falls where the index shows it: the first row
runs through the Korean expressway shields and the second opens with the Korean national shield.
Every offset this report quotes is reproduced (1386, 1407, 1428, 1447, 1466, 1486, 1507, 1543,
1565, 1589, 1632, 1662, 1685 and the 1708 that follows them).

Remaining, and declined: the `width`/`height` of the shields this report quotes no value for —
the Australian state plate's height, and the plates of `shield-HU:national`, `shield-JP:*`,
`shield-KR:*`, `shield-NL-ring`/`shield-NL:binnenstedelijke_ring`, `shield-PH:E`,
`shield-PK:*`, `shield-SA:national`, `shield-TR:*`, `shield-TW:*`, `shield-VE:T`,
`shield-ch:national`, `shield-cy:national` and `shield-md:national` — and the `x`/`y` that
follow from a width. Those are the pixel sizes of individual pieces of published artwork: the
model says nothing about the payload, no rule produces them, this report quotes no value for any
of them, and the replay withholds the recorded values, so they could only be matched by
transcribing one recording's bytes plate by plate. Everything the record does expose about them
— the names the sheet publishes, the order the index lists them in, that they share the sheet's
first row with the symbol iconography and where that row wraps — is implemented.
