# signin: CreateOAuth2TokenWithIAM refuses a grantType outside ^client_credentials$ with the RFC unsupported_grant_type sentence instead of the INVALID_REQUEST wording

> _Note: this issue was identified against the code base at commit `f32430db6efba8f0e69b19469a03fa7e522d5fbe`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateOAuth2TokenWithIAM

## Description
One net-new cause in AWS Sign-In's IAM-authenticated OAuth 2.0 token endpoint (POST /v1/token?x-amz-client-auth-method=iam). The emulator does refuse a grant type it does not implement, and it refuses it with the right shape and status, but it words the refusal with the wrong sentence for this error class: a grantType the request SUPPLIES whose value is outside the modelled pattern is an invalid parameter VALUE, and AWS states that class with the INVALID_REQUEST sentence, not with RFC 6749's unsupported_grant_type description.

=== Cause 1 of 1: a present-but-invalid grantType is refused with the unsupported_grant_type description instead of the INVALID_REQUEST sentence (check signin.create-oauth2-token-with-iam-wrong-grant-type-rejected) ===
AWS: Smithy (services/service-com-amazonaws-signin-signin/smithy-model/com-amazonaws-signin-signin.json): CreateOAuth2TokenWithIAM input grantType targets ClientCredentialsGrantType, jsonName 'grant_type', @required, @pattern ^client_credentials$; resource @required @length(1..2048); the operation models ValidationException with @httpError(400), whose members are error (OAuth2ErrorCode, @required — documented 'Will be INVALID_REQUEST for validation errors') and message (@required). OAuth2ErrorCode declares INVALID_REQUEST with the documentation 'The request is missing a required parameter, includes an invalid parameter value, or is otherwise malformed' — and declares NO 'unsupported_grant_type' member at all. Recorded behavior: a client-credentials token request that names grantType 'authorization_code' is refused HTTP 400 as ValidationException (x-amzn-errortype 'ValidationException', the code an SDK surfaces) with the message 'The request is missing a required parameter, includes an invalid parameter value, or is otherwise malformed.' — that sentence is entirely FIXED text for this error class: it interpolates nothing from the request (no member name, no offending value) and nothing from state. The variable part of this refusal is nothing; only the class is selected by the request.
Emulator: HTTP 400 ValidationException (status and code match) with message 'The authorization grant type is not supported by the authorization server.' — RFC 6749 §5.2's description of unsupported_grant_type, paired in the same body with error 'unsupported_grant_type', a value the model's OAuth2ErrorCode enum does not declare. services/service-com-amazonaws-signin-signin/src/service/oauth2_token_endpoint.rs answers EVERY grant type other than client_credentials on the IamSigned form with that one refusal, so a supplied-but-invalid value and an absent value are not distinguished.
Why: a client that reads the refusal message (the only human-readable discriminator an SDK surfaces, since both classes share the ValidationException code and the 400 status) is told the authorization server does not support the grant it asked for — i.e. 'this endpoint cannot serve this flow' — when AWS is telling it 'the parameter value you sent is not acceptable'. A client that branches on these two sentences, logs them, or asserts on them (as the behavioral check does) diverges; and the paired error code is outside the modelled enum, so a client deserializing ValidationException$error into the generated OAuth2ErrorCode enum gets an unknown variant where AWS sends INVALID_REQUEST.
Fix: the IamSigned branch of the token endpoint's refusal selection — the layer that judges a token request's parameters before the handler runs (crate::service::oauth2_token_endpoint, the Endpoint::IamSigned arm of refusal_for and the unsupported_grant_type()/malformed_request() constructors). A grantType the body SUPPLIES whose value is outside ^client_credentials$ must be refused with the INVALID_REQUEST error code and the INVALID_REQUEST sentence this service already holds for that class, leaving unsupported_grant_type for the classes the recorded wire actually gives it to. NOTE: cause 3 of the resolved issue 20261109T154022Z-signin-5-net-new-causes-in-the-oauth introduced the unsupported_grant_type wording for this operation from a wire fixture whose grant type the emulator read as null (absent); the behavioral recording here shows the sentence must not be reused for a grant type the request does supply, so the two classes have to be split rather than one wording replacing the other.
Traces: check signin.create-oauth2-token-with-iam-wrong-grant-type-rejected (assertion on the refusal message; the check's positive-control client_credentials call is never reached).
