# lambda__s3: the presigned S3 GET minted against the emulator carries the legacy query-credential form, so a nodejs22.x fetch never reaches S3's SignatureDoesNotMatch refusal

> _Note: this issue was identified against the code base at commit `2c0383d3f45d9a884fc7df5a8574c31cc457bda8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
One net-new failure mode, grounded in one failing behavioral check the replay report left unmarked (no ALREADY FILED marker and no OWNED-by marker). Open issue 20261121T130631Z-lambda-s3-a-nodejs22-x-handler-s-global.md names this check in its trace list, but it is scoped to a later failure point (the in-handler 'TypeError: fetch failed' at the invoke assertion) and does not carry the replay key this check now fails on, so it does not cover it; open issue 20261027T190000Z-s3-legacy-query-credential-presigned-get.md describes the legacy presigned credential form for s3.multipart-upload-and-presigned-get-round-trip only.

Cause 1 of 1: the presigned GetObject URL produced for an object in this emulator carries the LEGACY query-credential form - query keys AWSAccessKeyId, Signature, Expires - and no SigV4 credential (no X-Amz-Algorithm / X-Amz-Credential / X-Amz-Signature). The check that exercises S3's refusal of a tampered presigned signature can therefore not locate a signature to alter, and the whole presigned-refusal behavior (403 SignatureDoesNotMatch) is never reached.
Failing check ids: lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected

  AWS:      Smithy (com.amazonaws.s3#AmazonS3): GetObject is GET /{Key+} on the bucket endpoint; the model does not describe the presigned query form, so the credential form is recorded/documented behavior only. AWS accepts a presigned GET in either query-credential form - the SigV4 form (X-Amz-Algorithm, X-Amz-Credential, X-Amz-Date, X-Amz-Expires, X-Amz-SignedHeaders, X-Amz-Signature, the signature being lowercase hex) and the legacy form (AWSAccessKeyId, Signature, Expires) - and serves the object's bytes with HTTP 200. When one character of a valid presigned signature is altered, AWS refuses with HTTP 403 and an XML Error body whose Code is SignatureDoesNotMatch and whose Message is the fixed text 'The request signature we calculated does not match the signature you provided. Check your key and signing method.' (that message interpolates nothing from the request or from state). A 403 is an HTTP response, so a handler fetching it still returns normally - Invoke answers StatusCode 200 with no FunctionError.
  Emulator: the presigned URL minted for an object in this emulator carries only the legacy three query keys: the check aborts with 'AssertionError: the presigned URL carries no signature (query keys [\'AWSAccessKeyId\', \'Signature\', \'Expires\'])' when it looks for X-Amz-Signature (or a hex Signature) to tamper with, so no request is sent and the emulator serves no status, code or message for this check. The emulator's answer to such a legacy-form presigned GET, where one is replayed in this same suite, is HTTP 403 <Code>InvalidAccessKeyId</Code><Message>The AWS Access Key Id you provided does not exist in our records.</Message> rather than the object's bytes (see _smoke.sigv4-query-presigned-requests-identify-the-account, owned by 20261109T220008Z-smoke-query-string-presigned-sigv4-requests-are-refused.md). Hypothesis: the emulator's presigned handling recognises/validates only one credential form, so the signature-verification path that must answer SignatureDoesNotMatch is unreachable from a presigned URL issued against it.
  Why:      Fetching a presigned URL is the documented way to give in-function code object access without credentials, and client code distinguishes 'the signature was tampered with or expired' (403 SignatureDoesNotMatch) from 'the key is unknown' (403 InvalidAccessKeyId) and from 'the object is missing' (404 NoSuchKey). Against this emulator a presigned GET of an existing object is neither served nor refused with the signature error AWS gives, so error handling written against AWS's codes and messages is never exercised and breaks in production.
  Fix:      the S3 presigned-request authentication/verification path (the operation's request authentication, ahead of the GetObject handler) - a presigned GET must be served 200 with the object's bytes when its signature verifies, and refused 403 with Code SignatureDoesNotMatch and the fixed message above when the signature does not verify, for both the SigV4 and the legacy AWSAccessKeyId/Signature/Expires credential forms; InvalidAccessKeyId belongs only to a credential naming a key the emulator does not know. The in-function egress half of this check (node's global fetch reaching the emulator's own S3 address) is already filed as 20261121T130631Z-lambda-s3-a-nodejs22-x-handler-s-global.md and is not re-filed here.
  Traces:   lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected (_tamper, on the URL returned by generate_presigned_url).
