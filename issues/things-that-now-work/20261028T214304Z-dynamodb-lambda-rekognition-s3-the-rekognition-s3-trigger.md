# dynamodb__lambda__rekognition__s3: the Rekognition/S3-trigger stack now ends ROLLBACK_COMPLETE instead of CREATE_COMPLETE, so the whole deploy phase fails at phase 1 of 6

> _Note: this issue was identified against the code base at commit `f3979e0246435c1672d170ef00d4539e5318fdf8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One root cause.

Cause 1 of 1: a CreateStack of the reference `rekognition-s3-trigger` template (AWS::DynamoDB::Table + AWS::IAM::Role + AWS::Lambda::Function with inline `Code.ZipFile` + AWS::Lambda::Permission + AWS::S3::Bucket carrying three suffix-filtered LambdaConfigurations, all physical names supplied as Parameters) is accepted (CreateStack returns a StackId) but the stack's provisioning then fails and the stack settles in ROLLBACK_COMPLETE instead of CREATE_COMPLETE. Failing check: dynamodb__lambda__rekognition__s3.e2e-diagnose-rekognition-reupload-stale-lifecycle.

AWS: Smithy — CreateStack (input StackName/TemplateBody/Parameters/Capabilities/Tags; modelled errors only AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException, TokenAlreadyExistsException, all client/HTTP 400) returns a StackId and the stack is then provisioned asynchronously; the terminal status is drawn from the modelled StackStatus enum (com.amazonaws.cloudformation#StackStatus includes CREATE_COMPLETE, CREATE_FAILED, ROLLBACK_IN_PROGRESS, ROLLBACK_COMPLETE). On real AWS this template is a supported resource set: every declared resource type is a first-party provider, `Code.ZipFile` with runtime nodejs20.x is a valid inline-source Lambda, CAPABILITY_IAM is passed so the AWS::IAM::Role is permitted, and the bucket DependsOn the AWS::Lambda::Permission so S3's test-invoke of the destination succeeds before the NotificationConfiguration is stored. The stack therefore reaches CREATE_COMPLETE and DescribeStacks reports Outputs BucketName/TableName/FunctionName/BucketArn/FunctionArn. ROLLBACK_COMPLETE is only reached when a declared resource genuinely fails to create, and in that case DescribeStackEvents carries a per-resource event with ResourceStatus=CREATE_FAILED and a ResourceStatusReason naming the resource and the reason.

Emulator: the stack `sim2real-scn-rekstack-<suffix>` is polled to a terminal state and reports `ROLLBACK_COMPLETE`, never CREATE_COMPLETE, so the check aborts in its first phase: `[phase 1/6 deploy] stack sim2real-scn-rekstack-<id> reached 'ROLLBACK_COMPLETE', not CREATE_COMPLETE`. No modelled error was returned by CreateStack itself (the call is a 2xx) — the failure is in the resource provisioning that follows. This is a behavioural MOVE for this same check: open issue 20261026T070343Z-dynamodb-lambda-rekognition-s3-cloudformation-stack-reports-create-complete-and-exports-a.md records the previous state, where this very stack reached CREATE_COMPLETE with non-empty Outputs and the three S3 notification configurations installed, and the check instead failed one phase later on dynamodb:DeleteItem answering ResourceNotFoundException. That issue is about a CREATE_COMPLETE stack whose table does not exist; it does not cover a stack that no longer creates at all, so this is filed as its own cause rather than folded into it. Which declared resource fails cannot be read off the replay, and open issue 20261025T053459Z-cloudformation-emits-no-per-resource-stack-events-and.md records that the emulator emits no per-resource stack events — so the diagnostic AWS provides for exactly this situation (the CREATE_FAILED event plus its ResourceStatusReason) is also unavailable here. Hypothesis: the provider for one of AWS::DynamoDB::Table, AWS::Lambda::Function (inline Code.ZipFile), AWS::Lambda::Permission or AWS::S3::Bucket (NotificationConfiguration with three suffix filters, DependsOn the permission) now reports a create failure where it previously reported success.

Why: a client that deploys this ordinary serverless estate — a bucket whose ObjectCreated notifications invoke a Lambda that writes to a DynamoDB table — gets a rolled-back stack and no resources at all. Every downstream step is unreachable: there are no stack Outputs to read, no bucket to upload to, no function to invoke and nothing to clean up, and the deploy fails with no indication of which resource was at fault. This is strictly worse for the caller than the earlier partially-materialised stack, because the failure is total and undiagnosable.

Fix: the CloudFormation stack-provisioning path and the individual resource providers it dispatches to for this template's resource types (AWS::DynamoDB::Table, AWS::IAM::Role, AWS::Lambda::Function with inline ZipFile code, AWS::Lambda::Permission, AWS::S3::Bucket with a NotificationConfiguration), in the cloudformation service crate's stack-provisioning/state code — a template of only first-party, supported resource types with CAPABILITY_IAM granted must provision to CREATE_COMPLETE and publish its Outputs. Secondarily, the rollback path must record a per-resource CREATE_FAILED event with a ResourceStatusReason naming the failing logical resource, so a create failure is attributable at all.

Traces: dynamodb__lambda__rekognition__s3.e2e-diagnose-rekognition-reupload-stale-lifecycle (fails in phase 1/6 deploy).

## Evidence
Expected (real AWS): CreateStack(StackName=<stack>, TemplateBody=<rekognition-s3-trigger template>, Capabilities=[CAPABILITY_IAM], Parameters=[BucketName, TableName, FunctionName, HandlerSource]) returns a StackId; polling DescribeStacks yields StackStatus=CREATE_COMPLETE, and DescribeStacks(StackName=<stack>).Stacks[0].Outputs carries non-empty BucketName, TableName, FunctionName, BucketArn, FunctionArn and SupportedImageFormats.

Actual (emulator): polling DescribeStacks for any terminal state yields StackStatus='ROLLBACK_COMPLETE'. The check's assertion is surfaced verbatim as:
  AssertionError: [phase 1/6 deploy] stack sim2real-scn-rekstack-e8f18ce6dded reached 'ROLLBACK_COMPLETE', not CREATE_COMPLETE — read its stack events for the resource that failed
(The stack name `sim2real-scn-rekstack-e8f18ce6dded` is a per-run generated name, not part of the requirement; the requirement is the terminal status.) CreateStack itself returned 2xx with a StackId — no modelled CloudFormation error was raised — so the divergence is wholly in the asynchronous provisioning outcome.

Corroborating history for the same check id: issue 20261026T070343Z (open, Issue-Trace-Ids: dynamodb__lambda__rekognition__s3.e2e-diagnose-rekognition-reupload-stale-lifecycle) records that this stack previously reached CREATE_COMPLETE, exported non-empty Outputs, and had all three declared suffix-filtered LambdaFunctionConfigurations installed on the bucket, with the check failing only later at phase 2/6 on dynamodb:DeleteItem. The deploy phase that used to pass now does not.

Diagnostic gap: DescribeStackEvents is the documented way to identify which resource failed, and the emulator publishes no per-resource stack events (see open issue 20261025T053459Z), so the ResourceStatusReason AWS would supply for the CREATE_FAILED resource is absent.

## Steps to Reproduce
1. Call cloudformation:CreateStack with the `rekognition-s3-trigger` template — Parameters BucketName / TableName / FunctionName / HandlerSource (the Node.js index.js source), Capabilities=["CAPABILITY_IAM"], Tags=[{Key: sim2real}] — declaring: AWS::DynamoDB::Table (hash key `image_name`, type S, ProvisionedThroughput 5/5), AWS::IAM::Role (lambda.amazonaws.com trust + one inline policy), AWS::Lambda::Function (Runtime nodejs20.x, Handler index.handler, Code.ZipFile = {"Ref": "HandlerSource"}, Role = GetAtt HandlerRole.Arn, Environment BUCKET_NAME/TABLE_NAME), AWS::Lambda::Permission (Principal s3.amazonaws.com, SourceArn Fn::Sub on the bucket name) and AWS::S3::Bucket (DependsOn the permission, PublicAccessBlockConfiguration, NotificationConfiguration with three s3:ObjectCreated:* LambdaConfigurations filtered on suffixes .jpg / .jpeg / .png), with Outputs BucketName, BucketArn, TableName, FunctionName, FunctionArn.
2. Poll cloudformation:DescribeStacks(StackName=<stack>) every 5 s until StackStatus is one of CREATE_COMPLETE, CREATE_FAILED, ROLLBACK_COMPLETE, ROLLBACK_FAILED.
3. Observe StackStatus == 'ROLLBACK_COMPLETE' instead of 'CREATE_COMPLETE', and DescribeStacks returning no usable Outputs.
4. Call cloudformation:DescribeStackEvents(StackName=<stack>) to find the CREATE_FAILED resource event and its ResourceStatusReason — observe that no per-resource event identifies the failing resource.
5. Narrow the failing provider by creating the same stack with the resources split out one at a time (table only; role+function with inline ZipFile only; function+permission; then the bucket with its NotificationConfiguration).
