# PutEventSelectors advanced-event-selector validation: the missing-eventCategory refusal uses an emulator-authored sentence, and the field-name/category, empty-operator, eventCategory-cardinality and resources.type rules AWS enforces are not applied

> _Note: this issue was identified against the code base at commit `9cfb70c8dd865d3301250e334464bd408152814b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEventSelectors

## Description
ONE root cause: the advanced-event-selector validator in PutEventSelectors re-words the one refusal it does raise and does not implement the rest of AWS's advanced-selector rule set. Context, not coverage: the open issue 20261102T102343Z-cloudtrail-2-net-new-root-causes-puteventselectors-invalid.md covers the BASIC selector path's DataResources.Type message; this failing check is on the ADVANCED selector path and the replay report marked it neither owned nor already filed.

AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) binds InvalidEventSelectorsException to PutEventSelectors (errorKind client, httpError 400, awsQueryError code InvalidEventSelectors). The model constrains SelectorField only by length and the pattern ^[\w|\d|\.|_]+$, so the per-field rules are recorded behavior, each message a fixed text with at most one slot taken from the request:
  * an advanced selector with no eventCategory field selector -> `The following fields are required: [eventCategory].` (entirely fixed text; the bracketed member name is the missing member, not a request value);
  * a field name that does not exist, or a real field that is not allowed for the selector's category (e.g. eventName under eventCategory=Management) -> `The following field is not allowed when the eventCategory field value equals <category>: <field>.` — fixed text with two slots, the selector's eventCategory value and the offending Field, both copied from the request;
  * a field selector carrying no comparison operator at all -> `One or more of the selectors for the <field> field is empty.` — one slot, the Field name;
  * more than one value under eventCategory -> `There are too many values specified for eventCategory. The eventCategory field can have a maximum of 1 values.` (entirely fixed);
  * an unsupported resources.type value -> `The resources.type field value is not valid.` (entirely fixed).
In every case the refusal is HTTP 400 / InvalidEventSelectorsException and NOTHING is applied: GetEventSelectors still returns the selector set last successfully put, verbatim.

Emulator: for the missing-eventCategory case the code and 400 status are right, but the message is a self-authored remedy sentence: `Specify an eventCategory field selector in every advanced event selector` (src/ops/put_event_selectors.rs:598, raised at :576). The remaining rules are absent or differently worded in the same validator, validate_advanced_event_selectors (src/ops/put_event_selectors.rs:528-590): the empty-operator refusal is worded `The advanced field selector for "<field>" states no condition; each field selector needs one of Equals, StartsWith, EndsWith, NotEquals, NotStartsWith or NotEndsWith` (:547-552, with Rust Debug quoting around the field name AWS renders bare), and the function's own doc comment (:521-527) states that the field NAME is deliberately not checked against a catalog and that a well-formed field is stored as given — so an unknown field, a field illegal for the selector's eventCategory, a two-value eventCategory and an unsupported resources.type are all ACCEPTED and persisted.

Why: the message is part of the contract — clients, CDK/Terraform providers and operators match CloudTrail's fixed refusal text to tell one selector defect from another, and a re-worded sentence makes that classification fail. Worse, because the accepted-but-invalid cases are stored, a caller is told a selector set is live that AWS would never have installed: the trail then appears to be scoped (by a field that does not exist, or a resources.type AWS rejects) while nothing matching it can ever be selected, and the refusal branch is untestable.

Fix: the advanced-selector validation in the PutEventSelectors handler — validate_advanced_event_selectors and the refusal-text constants it returns (shared with CreateEventDataStore/UpdateEventDataStore, per its own doc) must emit AWS's fixed texts with the request's values in their slots, and must additionally enforce the eventCategory cardinality, the per-category field allowlist and the resources.type value set before anything is persisted, leaving the previously applied selector set untouched on refusal.

Traces: cloudtrail.advanced-event-selectors-operators-and-field-validation. The missing-eventCategory message divergence is the OBSERVED failure (the check asserts messages exactly and stops there); the other four rules are the same check's next assertions, which were never reached — expect them to surface in order once the first message is corrected.
