# pinpoint-sms-voice: the account's legacy V1 entitlement gate is not enforced — CreateConfigurationSet and SendVoiceMessage succeed, and Create/Delete/Get on event destinations and configuration sets answer 404 NotFoundException, where AWS answers 403 AccessDeniedException (5 causes)

> _Note: this issue was identified against the code base at commit `7c3ecfa1a25692ce41ad054c5d4a0fbbc15f7c4b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfigurationSet

## Description
The Pinpoint SMS/Voice V1 router collision previously filed as open issue 20261029T190906Z-pinpoint-sms-voice-v1-is-entirely-unreachable-the.md no longer masks the service: PinpointSMSVoice V1 is now dispatched and ListConfigurationSets answers 200 with a ConfigurationSets member (the positive control inside several of these checks now passes). That unmasks the actual fidelity gap underneath, which that issue could only predict and never exercise: the account-level entitlement gate that closes this legacy V1 surface is not implemented anywhere in the crate. Five distinct handler-level causes follow. They are NOT the router cause, and none of them carries that issue's replay keys (its keys are all of the form `pinpoint-sms-voice|<Op>|AmbiguousService`, which no longer reproduce).

Shared AWS fact used by every cause below (recorded behavior only — the Smithy model does not model it): the account these checks were recorded against has the legacy Pinpoint SMS/Voice V1 resource-scoped surface closed by an entitlement gate. Every resource-scoped operation — CreateConfigurationSet, CreateConfigurationSetEventDestination, UpdateConfigurationSetEventDestination, DeleteConfigurationSet, DeleteConfigurationSetEventDestination, GetConfigurationSetEventDestinations and SendVoiceMessage — is refused with HTTP 403, Error.Code `AccessDeniedException` and a non-empty Error.Message (recorded text `Access Denied`; that is the entire fixed text, there is no variable part). The refusal fires BEFORE any resource-existence lookup and before any semantic payload inspection, so it is input-independent and never depends on whether the named configuration set exists. ListConfigurationSets carries no resource-scoped ARN, stays open and answers 200. Request-shape validation on a malformed request still precedes the gate (see cause 4's second leg). `AccessDeniedException` is not in the V1 Smithy error vocabulary (Smithy: service PinpointSMSVoice, protocol restJson1; common_errors BadRequestException/InternalServiceErrorException/TooManyRequestsException plus per-operation AlreadyExistsException @httpError 409, LimitExceededException and NotFoundException @httpError 404), so the gate must be served as an untyped/synthetic 403 error envelope with Code `AccessDeniedException` and member Message, exactly as the recording shows.

Cause 1 of 5 — CreateConfigurationSet performs the create instead of refusing it.
AWS: recorded behavior only — POST /v1/sms-voice/configuration-sets with a syntactically valid ConfigurationSetName is refused HTTP 403 / Code `AccessDeniedException` / Message `Access Denied`, nothing is created, and the name never appears in a subsequent ListConfigurationSets. Under 8 concurrent racers at one identical name, every racer gets that same 403 denial: there is no winner, because no racer reaches the state layer at all.
Emulator: the call succeeds. `create-configuration-set-denied` fails at `assert not created, "CreateConfigurationSet unexpectedly succeeded"` — a 200 was returned and a configuration set was actually materialised. The race check confirms it reached state: of 8 racers 1 won with `{'ok': True}` and the other 7 were refused with Code `AlreadyExistsException`, Message `configuration set <ConfigurationSetName> already exists`, HTTP 409 — i.e. the handler ran its own create-or-conflict logic where AWS never lets any racer in. (Note the emulator's AlreadyExistsException message is itself emulator-authored lowercase prose; its fixed text is not AWS's — AWS's AlreadyExistsException doc wording is "The resource specified in your request already exists." — but that error class is unreachable on this account once the gate is in place, so fixing the gate removes it from this path.)
Why: a client is overly permitted. Code written against this account believes the legacy V1 control plane accepts new writes, so it creates configuration sets that will never exist on real AWS, and its `AccessDeniedException` handling (surface a permissions message, fall back to the V2 Pinpoint SMS Voice API) never fires. The concurrency contract inverts too: callers that rely on a deterministic uniform denial instead see a lucky winner and six 409 conflicts, so idempotency/leader-election logic built on "nobody can create this" silently elects a leader.
Fix: the CreateConfigurationSet handler — add the entitlement denial ahead of the state mutation, so no configuration set is ever inserted and no AlreadyExistsException path is reachable.
Checks: pinpoint-sms-voice.create-configuration-set-denied, pinpoint-sms-voice.concurrent-create-configuration-set-denied-consistently.

Cause 2 of 5 — CreateConfigurationSetEventDestination answers the existence check instead of the denial.
AWS: recorded behavior only — POST /v1/sms-voice/configuration-sets/{ConfigurationSetName}/event-destinations against a configuration set that was never created is refused HTTP 403 / `AccessDeniedException` / `Access Denied`, with a non-empty Message, and identically for every destination-target shape (SnsDestination, CloudWatchLogsDestination, KinesisFirehoseDestination): authorization is checked before any resource lookup and before the destination payload is examined. Nothing is created, so the configuration set still does not appear in ListConfigurationSets.
Emulator: the handler skips the gate and runs the parent-existence lookup first, answering the modelled `NotFoundException` (Smithy: NotFoundException @error client @httpError 404, member Message, doc "The resource you attempted to access doesn't exist."). `create-event-destination-on-nonexistent-configset-denied` fails with `expected AccessDeniedException, got 'NotFoundException'`; `create-event-destination-denied-across-destination-types` fails the same way on the very first (sns) destination shape, so the shape-independence of the denial is not observable at all.
Why: a client distinguishes "I may not do this" (403, stop and escalate permissions) from "the parent does not exist yet" (404, create the parent and retry). The emulator steers every caller onto the create-the-parent-and-retry branch, which on real AWS loops forever because the parent create is itself denied.
Fix: the CreateConfigurationSetEventDestination handler — the entitlement denial must precede the parent-existence lookup and the EventDestination payload inspection.
Checks: pinpoint-sms-voice.create-event-destination-on-nonexistent-configset-denied, pinpoint-sms-voice.create-event-destination-denied-across-destination-types.

Cause 3 of 5 — DeleteConfigurationSet answers the existence check instead of the denial.
AWS: recorded behavior only — DELETE /v1/sms-voice/configuration-sets/{ConfigurationSetName} on a name that was never created is refused HTTP 403 / `AccessDeniedException` / non-empty Message (`Access Denied`), NOT the 404 one would expect for an absent resource, because the write path is closed at the authorization layer before any existence check runs.
Emulator: answers the modelled `NotFoundException` (404). `delete-configuration-set-nonexistent-denied` fails with `expected AccessDeniedException, got 'NotFoundException'`.
Why: the same 403-vs-404 branch inversion as cause 2, on the teardown path: cleanup code treats the delete as a benign "already gone" instead of a permissions failure, so a caller believes it successfully tore down a resource it was never allowed to touch, and status==403 assertions/alerting never fire.
Fix: the DeleteConfigurationSet handler — the entitlement denial must precede the existence lookup.
Checks: pinpoint-sms-voice.delete-configuration-set-nonexistent-denied.

Cause 4 of 5 — GetConfigurationSetEventDestinations answers the existence check instead of the denial, and its empty-ConfigurationSetName validation is unverified behind that.
AWS: recorded behavior only — GET /v1/sms-voice/configuration-sets/{ConfigurationSetName}/event-destinations is resource-scoped, so this READ is gated too: a well-formed but never-created name is refused HTTP 403 / `AccessDeniedException` / non-empty Message, while ListConfigurationSets on the same credentials answers 200 (proving it is the resource-scoped action, not the account, that is closed). Second leg, where the request is malformed rather than merely unauthorized, validation still precedes the gate: ConfigurationSetName is @required and @httpLabel on __string with no length or pattern constraint (Smithy: GetConfigurationSetEventDestinationsRequest.ConfigurationSetName -> __string, httpLabel, required), so botocore serialises an empty value into the URI and the request reaches the service, which answers HTTP 400 / `BadRequestException` (Smithy: BadRequestException @error client @httpError 400, member Message, doc "The input you provided is invalid.") with a Message that NAMES the member — the fixed text is AWS's missing/invalid-parameter wording and the only variable part is the member name `ConfigurationSetName` taken from the request.
Emulator: answers `NotFoundException` (404) for the well-formed nonexistent name. Both checks fail at that first assertion — `get-configuration-set-event-destinations-nonexistent-configset-error`: `expected AccessDeniedException, got 'NotFoundException'`, and `get-configuration-set-event-destinations-empty-name-validation`: `expected AccessDeniedException for a well-formed nonexistent set, got 'NotFoundException'`. Because that assertion aborts the check, the empty-name leg was never reached and the emulator's answer to ConfigurationSetName='' is unverified; it must be a 400 BadRequestException whose Message names ConfigurationSetName, and it must be reached ahead of the entitlement denial.
Why: a reader cannot tell a permissions failure from an absent resource, so retry/bootstrap logic ("404 — create it") runs against a closed write path; and a caller cannot tell a malformed request (fix the input, 400) from an unauthorized one (escalate, 403).
Fix: the GetConfigurationSetEventDestinations handler and its input validation — validate the required path member first (400 BadRequestException naming the member), then apply the entitlement denial, and only then the existence lookup.
Checks: pinpoint-sms-voice.get-configuration-set-event-destinations-nonexistent-configset-error, pinpoint-sms-voice.get-configuration-set-event-destinations-empty-name-validation.

Cause 5 of 5 — SendVoiceMessage accepts the call instead of refusing it, and its Content one-of is not validated.
AWS: recorded behavior only — POST /v1/sms-voice/voice/message is refused HTTP 403 / `AccessDeniedException` / Message `Access Denied`, input-independently: a malformed non-E.164 DestinationPhoneNumber (`not-a-phone-number`) and a well-formed E.164 one get the IDENTICAL code and message, because the gate on placing a billable voice call fires before any input is inspected. Second leg: Content is a one-of (Smithy: VoiceMessageContent has members CallInstructionsMessage, PlainTextMessage, SSMLMessage, mutually exclusive), so a request setting PlainTextMessage and SSMLMessage at once must be refused for the content shape itself with HTTP 400 `BadRequestException` — a different, more specific code than the entitlement denial, never folded into it.
Emulator: the call SUCCEEDS. `send-voice-message-invalid-phone-number-format-rejected` fails at `SendVoiceMessage unexpectedly succeeded for destination='not-a-phone-number'`, and `send-voice-message-mutually-exclusive-content-rejected` fails at `the well-formed single-content-type control call unexpectedly succeeded`. Both checks abort on that success, so the emulator's handling of the two-content-type Content is unverified behind it; it must be 400 `BadRequestException`, distinct from the 403.
Why: this is the most permissive divergence in the service and it is on the data plane — a client believes it placed a voice call. Code validated against the emulator ships believing the send path works, then fails closed in production with a 403 it has no handler for; and an ambiguous two-content-type request is accepted rather than rejected, so a caller never learns its payload is invalid.
Fix: the SendVoiceMessage handler and its validation — validate the Content one-of (400 BadRequestException for more than one content member set), then apply the entitlement denial ahead of any send/state effect, independently of DestinationPhoneNumber/OriginationPhoneNumber content.
Checks: pinpoint-sms-voice.send-voice-message-invalid-phone-number-format-rejected, pinpoint-sms-voice.send-voice-message-mutually-exclusive-content-rejected.

Not included here (already filed, do not duplicate): DeleteConfigurationSetEventDestination and UpdateConfigurationSetEventDestination answer `NotImplemented` because they are unimplemented scaffold stubs — the suite marks those ALREADY FILED. pinpoint-sms-voice.create-configuration-set-invalid-name-validated-before-denied is marked OWNED by 20261029T190906Z-pinpoint-sms-voice-v1-is-entirely-unreachable-the.md and is skipped.
