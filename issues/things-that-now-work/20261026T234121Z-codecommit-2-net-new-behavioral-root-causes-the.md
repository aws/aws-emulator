# CodeCommit: 2 net-new behavioral root causes — the branch-merge ManualMergeRequiredException carries the pull-request wording, and no "CodeCommit Pull Request State Change" events ever reach the default EventBridge bus

> _Note: this issue was identified against the code base at commit `f2163892bf40cea6da7d1662f28c14ec75c797c6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
MergeBranchesByThreeWay

## Description
Two net-new root causes in the codecommit crate, each grounded in a failing behavioral check the replay report left UNMARKED (neither ALREADY FILED nor OWNED by an open issue). A fixer must close BOTH causes before submitting.

Cause 1 of 2: MergeBranchesByThreeWay's ManualMergeRequiredException message is the Smithy shape's documentation sentence (which describes the PULL-REQUEST merge APIs) instead of the message AWS actually returns on the BRANCH merge APIs.
AWS: Smithy models ManualMergeRequiredException on MergeBranchesByThreeWay (errorKind client, httpError 400 [defaulted]; members: message -> Message). The shape's own documentation reads 'The pull request cannot be merged automatically into the destination branch. You must manually merge the branches and resolve any conflicts.' — that is prose describing the error CLASS, shared by the pull-request merge operations and the branch merge operations alike, and it is not the wire message for the branch-merge path. Recorded behavior: when MergeBranchesByThreeWay is called on two tips with an unresolved content conflict and conflictResolutionStrategy left at its default NONE, AWS answers HTTP 400 with code ManualMergeRequiredException and message 'Current branches cannot be merged, please try to merge using a Git client locally.' That message is entirely FIXED text — it interpolates nothing from the request or from state (no repository name, no branch names, no commit ids, no conflicting path). The status and the code are already right; only the message diverges. Hypothesis: AWS keeps two messages behind one modelled shape — the branch-merge wording above, and the pull-request wording (the shape doc) for MergePullRequestByThreeWay/BySquash/ByFastForward — and the emulator single-homed the shape doc for every caller.
Emulator: HTTP 400 / ManualMergeRequiredException with message 'The pull request cannot be merged automatically into the destination branch. You must manually merge the branches and resolve any conflicts.' The literal is built in the handler: services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/merge_branches_by_three_way.rs lines 714-723, in the `if !merged.unresolved().is_empty()` arm, as `ManualMergeRequiredException { message: Some("The pull request cannot be merged automatically into the destination branch. You must manually merge the branches and resolve any conflicts.".to_string()), .. }`, copied from the model documentation reproduced in that file's own header at lines 163-165.
Why: the message is the only thing distinguishing the two refusal classes once the code is shared, and it is also the only user-facing text. A caller merging BRANCHES is told to go look at a pull request that does not exist, which is actively misleading; differential clients and log/alert matchers written against AWS's branch-merge sentence do not match, and any tool that surfaces the message to a developer sends them down the wrong remediation path (open/inspect a PR instead of merging locally with git).
Fix: the ManualMergeRequiredException construction in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/merge_branches_by_three_way.rs (the unresolved-conflict arm), and the equivalent arm in the crate's other BRANCH merge handlers (src/ops/merge_branches_by_squash.rs, src/ops/merge_branches_by_fast_forward.rs) — ideally via one shared refusal-message helper in src/state.rs alongside the crate's other error-message helpers, so the branch-merge wording and the pull-request wording are each stated once. Do NOT change the pull-request merge handlers' wording. Traces: codecommit.unreferenced-merge-commit-accept-source-tree (every other assertion in that check — GetMergeConflicts' mergeable=false with exact per-side fileSizes/fileModes/objectTypes/mergeOperations, the positive-control non-conflicting three-way merge, the refused merge leaving the destination branch and its content untouched, and the ACCEPT_SOURCE unreferenced merge commit's tree/parents — is reached only after this assertion, which is where it stops).

Cause 2 of 2: CodeCommit publishes no 'CodeCommit Pull Request State Change' events to the default EventBridge bus, so a pull request's create / source-branch-update / status-change lifecycle is unobservable to any consumer.
AWS: recorded behavior only — eventing is not in the Smithy model. CodeCommit emits events to the DEFAULT event bus with no opt-in and no trigger configuration. For pull requests the envelope carries source 'aws.codecommit', detail-type 'CodeCommit Pull Request State Change', account = the caller's account, region = the caller's region, and resources = exactly [the repository ARN]; detail carries event (one of 'pullRequestCreated', 'pullRequestSourceBranchUpdated', 'pullRequestStatusChanged'), pullRequestId, repositoryNames (a LIST containing the repository name), sourceCommit, destinationCommit and pullRequestStatus. The ids must be the ones the API itself reported: pullRequestCreated's destinationCommit is the destination tip CreatePullRequest resolved and its sourceCommit is the source tip at creation, and pullRequestSourceBranchUpdated's sourceCommit is the NEW tip, not the previous one. Because resources is the repository ARN, an EventBridge rule pattern pinning resources to one repository's ARN scopes delivery to that repository and a pull request in a different repository cannot match.
Emulator: nothing is delivered. With an SQS queue wired as the target of an ENABLED rule whose pattern is {"source":["aws.codecommit"],"detail-type":["CodeCommit Pull Request State Change"],"resources":[<watched repo ARN>]} and a queue policy allowing events.amazonaws.com for that rule's ARN (PutTargets reported FailedEntryCount 0, so the wiring itself is accepted), three real pull-request mutations in the watched repository produce zero matching messages: the consumer's long poll (ReceiveMessage MaxNumberOfMessages=10, WaitTimeSeconds=10, in a loop) never sees a single record and the check burns its whole budget, reported as 'Check timed out after 60.0s'. Had the events been emitted at all, the first long poll would have returned them within seconds; the deadline is consumed because no record ever arrives.
Why: EventBridge is the ONLY way to observe pull-request lifecycle in CodeCommit — repository triggers fire on refs, not on pull requests — so every review automation built on pullRequestCreated / pullRequestSourceBranchUpdated / pullRequestStatusChanged silently never runs against this emulator. Worse, a consumer cannot distinguish 'no event because the mutation was refused' (a property real test suites assert on) from 'this service never emits events at all', so absence-based assertions pass for entirely the wrong reason and a scoping rule that filters on resources is graded as working when nothing was ever filtered.
Fix: event publication in the codecommit crate's pull-request write path — services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/create_pull_request.rs (pullRequestCreated), the source-branch-advancing writes that update an open pull request's revision (src/ops/put_file.rs / delete_file.rs / create_commit.rs feeding the pull-request revision update) for pullRequestSourceBranchUpdated, and src/ops/update_pull_request_status.rs plus the merge handlers for pullRequestStatusChanged — each emitted onto the EventBridge default bus only AFTER the write is accepted, with resources set to the repository ARN. Related but NOT covering: open issue 20261022T171422Z-codecommit-events-sqs-codecommit-createbranch-is-a-501-stub-and-no.md lists this check id in its Issue-Trace-Ids, but its Cause 1 (CreateBranch answering 501) is already fixed and its Cause 2 is scoped to 'CodeCommit Repository State Change' events on reference-moving writes — a different detail-type, a different envelope and a different emission site from the pull-request lifecycle events this cause is about, and that issue's replay key is the sibling check codecommit__events__sqs.a-commit-refused-for-a-stale-parent-moves-no-reference-and-emits-no-state-change-event.
Traces: codecommit__events__sqs.pull-request-lifecycle-reaches-eventbridge-scoped-to-one-repository.
