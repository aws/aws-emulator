# ssm-quicksetup: 4 net-new root causes — anchored pattern in ValidationException text, invented empty-definitions message, unvalidated local-deployment roles, and identity-policy Deny not enforced

> _Note: this issue was identified against the code base at commit `5dbb2ab27a0402c002f5157a9a56e61b81adc0a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfigurationManager

## Description
Four independent root causes in the ssm-quicksetup control plane, all found by replaying the behavioral suite (simparity-behavioral-aws-v1) against this checkout. 4 causes; all must be closed before this issue is submitted.

Cause 1 of 4: the ValidationException constraint message renders the Smithy @pattern with its outer anchors, so every pattern-constraint refusal of this service reports a regex AWS never reports.
AWS: the sentence is built from the request and the modeled constraint — fixed text "1 validation error detected: Value '<rejected value>' at '<lowerCamel member path>' failed to satisfy constraint: Member must satisfy regular expression pattern: " followed by the pattern with the pattern's LEADING ^ and TRAILING $ stripped (interior anchors kept). The variable parts are the rejected value and the member path, both taken from the request; the pattern comes from the model. Smithy: CreateConfigurationManagerInput.Name @pattern ^[ A-Za-z0-9._-]{0,120}$ -> AWS renders "[ A-Za-z0-9._-]{0,120}"; UpdateConfigurationDefinitionInput.TypeVersion @pattern ^\d{1,3}(\.\d{1,3})?$|^LATEST$ -> AWS renders "\d{1,3}(\.\d{1,3})?$|^LATEST". Both operations bind ValidationException (httpError 400), which is the status and code the emulator already gets right.
Emulator: emits the anchored form verbatim from the model — "...pattern: ^[ A-Za-z0-9._-]{0,120}$" for Name and "...pattern: ^\d{1,3}(\.\d{1,3})?$|^LATEST$" for TypeVersion. Two different operations and two different members diverge identically, so it is the shared renderer, not one message.
Why: harnesses, SDK add-ons and operators that parse, log or compare AWS's validation text against the service model's own rendering see a constraint string AWS never emits; anything matching the reported pattern mismatches on every pattern refusal this service makes.
Fix: the shared ValidationException message renderer used by this crate's input validation (the pattern-constraint formatter) — strip the outer ^ and $ when formatting a pattern constraint.
Traces: ssm-quicksetup.create-configuration-manager-invalid-name-pattern-rejected, ssm-quicksetup.update-configuration-definition-invalid-type-version-rejected. NOTE: open wire issue 20261022T034519Z-ssm-quicksetup-error-paths-wrong-rejection-class-unvalidated.md describes the same renderer defect as its cause 6, grounded in wire fixtures (ConfigurationDefinitionInput.Type); it carries no behavioral replay key, so these two checks are recorded here. Fixing the renderer once closes both.

Cause 2 of 4: CreateConfigurationManager's empty-ConfigurationDefinitions refusal uses a locally invented sentence.
AWS: recorded behavior only — POST /configurationManager with ConfigurationDefinitions=[] is refused 400 ValidationException (Smithy: CreateConfigurationManagerInput.ConfigurationDefinitions is @required, target ConfigurationDefinitionsInputList carries no @length, so the non-empty rule is not modelled) with the FIXED, request-independent message "At least 1 configuration definition must be provided." Nothing in that sentence is interpolated from the request or the environment.
Emulator: status 400 and code ValidationException are right; the message is "ConfigurationDefinitions must carry at least one configuration definition".
Why: a client that surfaces or matches the service's own refusal sentence (negative tests, error-classification middleware, operator runbooks) sees wording AWS never emits for this error class.
Fix: the CreateConfigurationManager input validation in the ssm-quicksetup service crate — emit AWS's fixed sentence for an empty definitions list.
Traces: ssm-quicksetup.create-configuration-manager-requires-nonempty-definitions.

Cause 3 of 4: CreateConfigurationManager accepts a single-account (TargetAccounts) definition that names NO local deployment roles, returning 200 where AWS refuses.
AWS: a definition deployed into a named account has no other way for Quick Setup to obtain credentials than the local-deployment roles, so a ConfigurationDefinitions entry whose Parameters set TargetType/TargetTagKey/TargetTagValue/TargetAccounts/TargetRegions but which omits LocalDeploymentAdministrationRoleArn and LocalDeploymentExecutionRoleName is refused 400 ValidationException with the message "The required parameter LocalDeploymentAdministrationRoleArn is missing." — fixed text naming the missing member; the member name is the only variable part. Smithy states the basis but not the rule: ConfigurationDefinitionInput.LocalDeploymentAdministrationRoleArn (IAMRoleArn, "The ARN of the IAM role used to administrate local configuration deployments") and LocalDeploymentExecutionRoleName are both optional members, so this is a cross-member requirement conditional on the definition targeting accounts rather than organizational units; the status, code and sentence are recorded behavior.
Emulator: status 200 — it mints a manager and returns a ManagerArn (observed: ManagerArn arn:aws:ssm-quicksetup:<region>:<account>:configuration-manager/<uuid>), so a manager is stored that AWS would never have accepted and every later read reports a local deployment with no role to assume.
Why: a client's negative test passes, and worse, the emulator's state diverges for the rest of the scenario — a manager exists that cannot deploy, and because AWSQuickSetupType-SSMHostMgmt is an account singleton it also blocks the slot for later creates.
Fix: CreateConfigurationManager input validation in the ssm-quicksetup service crate (the same stage that runs crate::state::deployment_targets_rejection) — require the local-deployment role pair when a definition's Parameters name TargetAccounts, before anything is stored.
Traces: ssm-quicksetup.local-deployment-missing-role-rejected. Related but distinct: open issue 20261028T183419Z-ssm-quicksetup-createconfigurationmanager-validation--r4.md covers missing per-type keys INSIDE the Parameters map; this cause is about the definition's own role members, which that issue does not name.

Cause 4 of 4: an identity-based policy that explicitly denies ssm-quicksetup:GetConfigurationManager is not enforced — the denied principal's read succeeds.
AWS: a caller whose in-effect identity policy carries an explicit Deny for the action is refused with AccessDeniedException (Smithy: GetConfigurationManager binds AccessDeniedException, httpError 403) and the message follows AWS's explicit-deny template — fixed text "User: <caller principal ARN> is not authorized to perform: ssm-quicksetup:GetConfigurationManager on resource: <ManagerArn> with an explicit deny in an identity-based policy", whose variable parts are the assumed-role principal ARN of the caller (from the signing credentials) and the ManagerArn from the request path. Recorded behavior supplies the code and this template; the per-run role name, session name, account id and manager uuid are only fillers.
Emulator: the denied principal's GetConfigurationManager keeps answering 200, so no AccessDeniedException ever appears; the check polls for the refusal to its deadline and the whole check is killed at its 60s budget (verdict: "Check timed out after 60.0s"). Hypothesis: the exhausted poll is the deny-enforcement loop — it is the only poll in that check that waits on an ssm-quicksetup refusal the emulator never produces; the check's other bounded waits (CreateConfigurationManager, sts:AssumeRole) are served by the emulator immediately.
Why: every authorization-negative test against this service passes silently, and a client cannot distinguish "not permitted" from "permitted": a principal that AWS refuses reads and could mutate configuration managers it has been explicitly denied, so emulated security regressions are undetectable.
Fix: the request-authorization stage fronting the ssm-quicksetup routes — it must evaluate the caller's in-effect identity policy for the ssm-quicksetup action before the handler's resource lookup and refuse an explicit Deny with 403 AccessDeniedException carrying AWS's explicit-deny sentence.
Traces: ssm-quicksetup.access-denied-without-permission-rejected.
