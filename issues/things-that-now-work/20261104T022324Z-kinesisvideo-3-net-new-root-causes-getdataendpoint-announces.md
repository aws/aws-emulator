=== Cause 1 of 3: the DataEndpoint GetDataEndpoint announces is not an address the emulator serves, so every discovered-endpoint call (PutMedia ingest and all archived-media/media reads) is refused before it is made ===
AWS: Smithy com.amazonaws.kinesisvideo#GetDataEndpoint, POST /getDataEndpoint -> 200, input APIName (required enum GET_CLIP | GET_DASH_STREAMING_SESSION_URL | GET_HLS_STREAMING_SESSION_URL | GET_IMAGES | GET_MEDIA | GET_MEDIA_FOR_FRAGMENT_LIST | LIST_FRAGMENTS | PUT_MEDIA) + StreamName/StreamARN, output DataEndpoint documented as "The endpoint value. To read data from the stream or to write data to it, specify this endpoint in your application"; the operation doc is "Gets an endpoint for a specified stream for either reading or writing ... The returned endpoint does not have the API name appended." The contract a client depends on is OPERATIONAL, not cosmetic: the value is an endpoint the client then ADDRESSES — a bare http(s) origin, empty path, whose host differs per plane and differs from the control-plane host, AND which actually accepts that plane's calls for that stream (POST /putMedia -> 200 acknowledgement stream; /getMedia, /listFragments, /getMediaForFragmentList, /getClip on the read host). For an emulator, the only host that satisfies "a client can address it" is one that resolves to the endpoint under test; the per-plane distinction is expressible with a distinct label/port that still resolves there. Hostnames, ids and ports are per-environment and are not themselves requirements.
Emulator: GetDataEndpoint returns `https://s-<8 hex>.kinesisvideo.us-west-2.amazonaws.com` for PUT_MEDIA and `https://b-<8 hex>.kinesisvideo.us-west-2.amazonaws.com` for the read APIs — a name derived only from the plane marker, a SHA-256 of the stream ARN and `kinesisvideo.<region>.amazonaws.com` (state/data_endpoint.rs:112-143), with nothing tying it to the address the request arrived on. Every check that follows the documented discovery flow is then refused at the first byte: `simparity.egress.EgressRefused: egress refused: 's-<id>.kinesisvideo.us-west-2.amazonaws.com' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on` (21 checks; the `b-` host for the archive APIs is refused identically, see kinesisvideo.putmedia-on-the-archive-endpoint-rejected). The module header at state/data_endpoint.rs:27-39 asserts a client "reaches either by directing that name at the emulator" — that assumption is what is wrong: a client given a DataEndpoint dials exactly that host, so an announced address the emulator does not answer on makes the whole data plane unreachable and makes every producer/consumer contract unobservable.
Why: the entire documented producer and consumer path of Kinesis Video Streams is unusable through the only way to find it. A client (KVS C/Java producer, GStreamer kvssink, boto3 with endpoint_url=DataEndpoint) resolves the announced name, gets either a real-AWS address or NXDOMAIN, and never reaches the emulator — so PutMedia ingest, GetMedia, ListFragments, GetMediaForFragmentList and GetClip cannot be exercised at all, and none of the refusal contracts on those paths (absent stream, malformed container, undeclared track, regressed cluster timecode, missing x-amz-content-sha256, future producer timestamp, wrong plane) can ever be observed. This is strictly worse for a client than the previously filed echo-the-control-host defect, which at least pointed at a reachable socket.
Fix: GetDataEndpoint's endpoint projection — crate::state::data_endpoint / service_host in services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs, together with whatever endpoint mapping the engine exposes for the kinesisvideo family: the announced origin must be one the emulator answers on (the listener's own authority, per-plane distinct via label or port, resolvable from the request's address), and the media/archived-media routes must be bound on it.

=== Cause 2 of 3: GET_MEDIA is projected onto the archive/read host instead of sharing one host with PUT_MEDIA, so the ingest APIs do not resolve to a single host ===
AWS: recorded behavior only for the host grouping (the model says only that DataEndpoint is selected per APIName and carries no path). The recording shows THREE host groups, not two: PUT_MEDIA and GET_MEDIA resolve to ONE per-stream media/ingest host, while the archive APIs LIST_FRAGMENTS, GET_MEDIA_FOR_FRAGMENT_LIST and GET_CLIP resolve to a DIFFERENT per-stream archive host, and neither is the control-plane host. The requirement is the grouping and the distinctness — which APIs share a host — never the particular labels.
Emulator: state/data_endpoint.rs:83-98 keys the plane off a two-valued access mode, mapping PUT_MEDIA to Write and EVERY other APIName, GET_MEDIA included, to Read, so GetDataEndpoint(GET_MEDIA) returns the archive host. Replay: `AssertionError: the ingest APIs must share one host, got {'PUT_MEDIA': 's-<id>.kinesisvideo.us-west-2.amazonaws.com', 'GET_MEDIA': 'b-<id>.kinesisvideo.us-west-2.amazonaws.com', 'LIST_FRAGMENTS': 'b-<id>...', 'GET_MEDIA_FOR_FRAGMENT_LIST': 'b-<id>...', 'GET_CLIP': 'b-<id>...'}` (the labels and ids are per-run values; the divergence is that GET_MEDIA is grouped with the archive APIs).
Why: a consumer that discovers GET_MEDIA and caches it as the stream's media host, or that reuses one discovered media host for both the write and the read leg of a session the way the KVS SDKs do, is pointed at the archive plane; and because the emulator exposes only two groups, a client can never observe the real three-way plane split or the wrong-plane refusal that split exists to produce.
Fix: the APIName -> plane catalog in crate::state::data_endpoint::data_plane_of (services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs:83-98) — GET_MEDIA belongs with PUT_MEDIA on the media/ingest plane, with the archived-media APIs on their own plane.

=== Cause 3 of 3: a control-plane operation sent to a discovered data endpoint is answered 200 instead of being refused UnknownOperationException with no message ===
AWS: recorded behavior only (UnknownOperationException is not a modeled kinesisvideo error; the model binds only the control operations to the control endpoint). A data host serves that plane's media APIs ONLY, so a control-plane call addressed to it is refused with error code UnknownOperationException and, as recorded, NO message member at all — the error code is the fixed part, there is no variable part, and no stream name or ARN appears in it.
Emulator: DescribeStream sent to the DataEndpoint returned for APIName=PUT_MEDIA is served normally — HTTP 200 with a full StreamInfo body. Replay: `AssertionError: the call was expected to fail but succeeded, returning {'ResponseMetadata': {'HTTPStatusCode': 200, ...}, 'StreamInfo': {'StreamName': ..., 'StreamARN': ..., 'Status': 'ACTIVE', ...}}` (the names, ARNs, Version and timestamps in that body are per-run values; the divergence is the 200 itself). The cause is that the front door resolves the target service from the SigV4 signing name and the modelled path and ignores the host entirely (stated as intended at state/data_endpoint.rs:27-39), so every plane's routes are bound on every announced host.
Why: endpoint discovery is unverifiable and misrouting is silent. A client probing which host serves which plane — exactly what GetDataEndpoint makes it do — is told every host serves everything, so it never learns that a call went to the wrong plane, and the InvalidEndpointException/UnknownOperationException feedback loop that KVS producers rely on to re-discover an endpoint never fires. It also means a wrong-plane PutMedia or a control call on a media host cannot be refused, hiding the very misrouting contract the sibling checks assert.
Fix: route scoping in the kinesisvideo front door together with the endpoint projection from Cause 1 — once each plane has its own reachable authority, bind only that plane's operations on it and answer anything else with the UnknownOperationException refusal carrying no message, rather than dispatching every operation on every host.
