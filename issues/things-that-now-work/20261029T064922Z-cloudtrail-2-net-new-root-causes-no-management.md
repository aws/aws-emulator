# cloudtrail: 2 net-new root causes — no management event is recorded for a read-only or refused CloudTrail call, and ListTrails is never authorized (an unprivileged IAM user is served 200)

> _Note: this issue was identified against the code base at commit `004a13bc6b62a404600c0a09686b1d7dd87c7440`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents, ListTrails

## Description
Two independent net-new root causes in the cloudtrail service, both grounded in failing behavioral checks of this suite. Neither failing check is marked ALREADY FILED or OWNED in the replay report, so neither carries an existing issue's replay key. Related open issues are named per cause; none of them covers these keys.

Cause 1 of 2 — a CloudTrail call that is READ-ONLY, or that is REFUSED, is never recorded in the account's management-event log, so LookupEvents' ReadOnly partition can never be exercised.
AWS: LookupEvents "Looks up management events ... captured by CloudTrail" and supports the lookup attribute `ReadOnly` (Smithy: LookupAttributeKey enum values EventId, EventName, ReadOnly, Username, ResourceType, ResourceName, EventSource, AccessKeyId; Event$ReadOnly is a String member — "Information about whether the event is a write event or a read event"). AWS records EVERY API call of the account as a management event, classified by the OPERATION and not by its outcome: a successful read (cloudtrail:DescribeTrails) is recorded with readOnly=true, and a REFUSED write (cloudtrail:DeleteTrail answered TrailNotFoundException) is still recorded with readOnly=false plus its errorCode/errorMessage. Both become visible to LookupEvents within roughly 135 s, and a lookup with LookupAttributes ReadOnly=true/false must partition the same window disjointly and completely, with each returned envelope's Event$ReadOnly string agreeing with the JSON boolean `readOnly` inside its CloudTrailEvent payload.
Emulator: the check's two self-caused anchors never appear. The rejected DeleteTrail is refused correctly (TrailNotFoundException with the expected "Unknown trail: arn:aws:cloudtrail:<region>:<account-id>:trail/<name> for the user: <account-id>" message), and DescribeTrails succeeds, but LookupEvents filtered by EventName=DescribeTrails and by EventName=DeleteTrail returns neither record for the whole poll; the check polls until its budget is exhausted and ends with `TimeoutError: CloudTrail to index this check's own markers: the run budget ended first; not graded`. services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/lookup_events.rs reads `service_common::management_events` faithfully (it filters by Region, category, window and the single attribute, and projects readOnly as a string), so the divergence is upstream: nothing appends a record for a read-only CloudTrail call or for a refused one.
Why: a client that audits its own activity sees an empty history. Anything built on readOnly classification — a "who read my trails" report, an EventBridge/CloudTrail-driven rule on a refused write, a compliance query that partitions a window into reads and writes — silently returns nothing instead of the records AWS guarantees, and the absence is indistinguishable from "no such activity".
Fix: the management-event recording seam — the middleware/handler hook that appends a `ManagementEvent` to `service_common::management_events` must fire for EVERY dispatched CloudTrail operation, including read-only ones (DescribeTrails, GetTrailStatus, ListTrails, LookupEvents' subjects) and including calls that end in a modelled refusal, with read_only derived from the operation's classification rather than from whether state changed, and with errorCode/errorMessage set on the refusal path.

Cause 2 of 2 — ListTrails is served to an IAM identity with no policy that allows it, instead of being denied.
AWS: ListTrails models no authorization error of its own (Smithy: ListTrails errors are only OperationNotPermittedException and UnsupportedOperationException), so this is the service-common IAM authorization behavior: a request signed by an IAM user with NO identity-based policy is refused with the service's AccessDeniedException (Smithy: com.amazonaws.cloudtrail#AccessDeniedException, errorKind client, httpError 403) and the standard IAM message. Fixed text of that message: "User: " ... " is not authorized to perform: " ... " because no identity-based policy allows the " ... " action"; the variable parts are the signing principal's ARN (taken from the request's credentials — arn:aws:iam::<account-id>:user/<user-name>) and the action string "cloudtrail:ListTrails" derived from the operation being called, which appears twice. Granting that action to the same identity must then make the identical call succeed.
Emulator: the call by the freshly created, policy-less IAM user SUCCEEDS. Recorded response: HTTP 200 with `{'Trails': [{'TrailARN': 'arn:aws:cloudtrail:<region>:<account-id>:trail/<trail-name>', 'Name': '<trail-name>', 'HomeRegion': '<region>'}]}` (the suite's run shows us-west-2 / 000000000000 / sim2real-ct-trail-b6b48be19e18 — environment values, not part of the requirement). No AccessDeniedException is ever produced, so the check's denial poll never converges and it asserts "ListTrails by an identity with no attached policy succeeded". The same request is also answered the authorized caller's full trail list, so the unprivileged identity reads another principal's inventory.
Why: authorization is a security contract. A client testing least-privilege, a policy-simulation test, or any negative test that asserts a caller is denied passes vacuously here, and code that treats a 200 as proof of entitlement ships a privilege escalation that real AWS would have refused with 403 AccessDeniedException.
Fix: the service's request-authorization seam for cloudtrail operations (the sigv4 principal resolution plus IAM policy evaluation applied before dispatch), which must deny by default when no identity-based policy allows the operation's action and render the AccessDeniedException message above.
Traces: cloudtrail.op-contract-list-trails.
