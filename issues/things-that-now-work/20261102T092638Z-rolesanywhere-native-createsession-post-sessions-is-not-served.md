# rolesanywhere native CreateSession (POST /sessions) is not served, so no X.509 session is ever vended and a disabled profile is never refused

> _Note: this issue was identified against the code base at commit `9f5148798275000480c887daf4e17bbd7b05ffea`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSession

## Description
Two net-new root causes on the rolesanywhere native data plane, numbered below; a fixer must close BOTH before submitting.

NOTE ON OVERLAP: the open issue 20261029T195344Z-rolesanywhere-does-not-serve-the-native-createsession-data.md describes a related CreateSession gap, but the replay suite did NOT mark either of these two checks as OWNED by it or as ALREADY FILED in this run (its recorded replay keys point at `_poll_create_session#13|Timeout|time.sleep(3)`, which no longer matches the current check bodies — the round-trip check now routes its HTTPS call through a `_tls_context(ctx)` helper, shifting the key). Both checks therefore still fail unowned and are re-grounded here with their current ids so a fixer has a replay key that actually resolves. If that issue is closed by the same handler work, close this one with it; it does not cover these checks today.

Cause 1 of 2 — CreateSession / POST /sessions is never served, so no credentialSet is ever vended:
AWS: CreateSession is IAM Roles Anywhere's native data plane. It is NOT in this checkout's Smithy model — smithy_query query=operation operation=CreateSession on services/service-com-amazonaws-rolesanywhere-rolesanywhere/smithy-model/com-amazonaws-rolesanywhere-rolesanywhere.json answers "operation 'CreateSession' not found" (did_you_mean CreateProfile, CreateTrustAnchor) — so this is recorded behavior only. AWS serves it as POST /sessions on the rolesanywhere endpoint, hand-signed with the SigV4-derived algorithm AWS4-X509-RSA-SHA256: Authorization carries Credential=<signing certificate serial number>/<date-stamp>/<region>/rolesanywhere/aws4_request, the signature is RSA PKCS#1 v1.5 SHA-256 over the standard string-to-sign, and the DER client certificate is base64 in the X-Amz-X509 header. Given an enabled profile whose roleArns name a role trusting rolesanywhere.amazonaws.com, and an enabled trust anchor holding the signing certificate's CA, AWS answers HTTP 201 with a body holding exactly one credentialSet entry: roleArn echoing the requested role, assumedRoleUser.arn ending in '/<session name>' where the default session name is the signing certificate's serial number hex-encoded, and credentials {accessKeyId, secretAccessKey, sessionToken, expiration} that are usable against sts:GetCallerIdentity and resolve to an ':assumed-role/<role name>/<session name>' Arn.
Emulator: POST /sessions never answers 201. Both checks poll the signed request to exhaustion and report 'Check timed out after 60.0s'; no credential set is ever returned. The operation has no handler in the service crate (no src/ops/create_session.rs; src/ops/mod.rs only includes the build-generated handler set, and the operation is absent from the model those handlers are generated from), so there is no route for /sessions at all.
Why: exchanging an X.509 identity for temporary AWS credentials is the entire purpose of IAM Roles Anywhere. A client built against this emulator can create trust anchors and profiles but can never obtain credentials; the product's only data-plane path is untestable, and a workload wired to the emulator hangs and retries instead of receiving either credentials or a modelled refusal.
Fix: add a CreateSession handler for the service (POST /sessions) plus its route registration and state wiring — parse the X-Amz-X509 certificate, verify it chains to a registered and enabled trust anchor, resolve the profile and role, and vend one credentialSet whose default role session name is the certificate's hex-encoded serial. It does not exist yet, so it must be added alongside the generated ops rather than corrected in one.
Traces: rolesanywhere.create-session-native-x509-round-trip, rolesanywhere.create-session-disabled-profile-rejected.

Cause 2 of 2 — a DISABLED profile is not refused on the data plane:
AWS: when the profile named by profileArn has enabled=false, the identical signed CreateSession request is refused with HTTP 403 and error code AccessDeniedException — the response carries an x-amzn-ErrorType header whose part before the ':' is exactly 'AccessDeniedException' (the remainder after the colon is a URL, not part of the code) — and the body contains no 'credentialSet' key. Re-enabling the profile makes the identical signed request succeed again with 201 and one credentialSet. Recorded behavior only for the status/code pairing on /sessions, since CreateSession is not modelled; the control-plane operations do model AccessDeniedException with httpError 403 (Smithy: GetProfile/DisableProfile errors AccessDeniedException httpError 403, ResourceNotFoundException httpError 404), which is the same error shape AWS reuses here. The error code and the 403 are the requirement; no part of this refusal is a per-run value.
Emulator: unreachable, and therefore silently absent. The positive-control leg of rolesanywhere.create-session-disabled-profile-rejected never receives a 201 from /sessions (cause 1), so the check dies on its 60s budget before the disable leg runs; there is no enabled/disabled gate on a data plane that does not exist. Independently, DisableProfile is still an unimplemented scaffold stub (owned by its own auto-filed issue), so even once /sessions is served there would be no disabled profile for it to refuse.
Why: 'a disabled profile vends no credentials' is the kill switch operators rely on to revoke an X.509 fleet's access. An emulator that cannot express it lets a client conclude revocation took effect when nothing was ever checked, and a 403 the client is written to handle never arrives.
Fix: the CreateSession handler added in cause 1 must consult the resolved profile's `enabled` flag (and the trust anchor's) before vending anything, and refuse with HTTP 403, error code AccessDeniedException, and the matching x-amzn-ErrorType header, emitting a body with no credentialSet member.
Traces: rolesanywhere.create-session-disabled-profile-rejected.
