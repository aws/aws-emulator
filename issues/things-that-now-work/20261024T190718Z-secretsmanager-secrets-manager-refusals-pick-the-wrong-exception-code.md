# Secrets Manager refusals pick the wrong exception code, and validation messages echo secret material (3 causes)

> _Note: this issue was identified against the code base at commit `ee21bdc0559bb252101e2375a2c132d26bd8f920`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSecret

## Description
Three root causes. Cause count: 3.

=== Cause 1 of 3: the refusal is right but the exception code is not ===
AWS: Secrets Manager splits its 400s by meaning (Smithy CreateSecret/PutSecretValue/TagResource/RotateSecret all model InvalidParameterException and InvalidRequestException, plus the protocol-level ValidationException for constraint violations). The recorded behaviour of each path: a secret Name containing an illegal character -> ValidationException; PutSecretValue carrying neither SecretString nor SecretBinary -> InvalidRequestException; RotateSecret with a rotation Duration but no schedule expression and no AutomaticallyAfterDays -> InvalidParameterException; TagResource attaching a 51st tag -> InvalidRequestException; GetSecretValue naming a VersionId and a VersionStage that resolve to different versions -> InvalidRequestException.
Emulator: the same five calls are refused with 400 but under the wrong code - InvalidParameterException for the illegal name, InvalidParameterException for the valueless PutSecretValue, InvalidRequestException for the Duration-only RotateSecret, InvalidParameterException for the 51st tag, and ResourceNotFoundException for the disagreeing VersionId/VersionStage.
Why: clients branch on the code, not the prose. InvalidParameterException ('fix this field') and InvalidRequestException ('not valid for this resource state/combination') drive different retry paths, and answering ResourceNotFoundException for a contradictory request makes a caller conclude the secret or version is gone and recreate it.
Fix: the error selection in each handler's validation (CreateSecret name validation, PutSecretValue value-presence check, RotateSecret rules validation, TagResource tag-cap check, GetSecretValue version resolution).
Traces: secretsmanager.create-secret-invalid-name-rejected, secretsmanager.put-secret-value-missing-value-fails, secretsmanager.rotate-secret-duration-without-a-schedule-or-frequency-rejected, secretsmanager.tag-resource-fifty-tag-cap-and-duplicate-keys-rejected, secretsmanager.get-secret-value-rejects-a-version-id-and-version-stage-that-disagree.

=== Cause 2 of 3: constraint-violation messages reproduce the submitted member value, including secret material ===
AWS: the constraint message is built from the request to a fixed rule, and for a @sensitive member the VALUE is omitted: "1 validation error detected: Value at 'secretString' failed to satisfy constraint: Member must have length less than or equal to 65536" (and the same shape for the length>=1 case). Smithy marks SecretString and SecretBinary @sensitive with length 1..65536; long non-sensitive values are likewise not reproduced whole.
Emulator: it splices the value in - "Value 'xxxxx...' [70000 bytes] at 'secretString' failed to satisfy constraint...", "Value '' at 'secretString' ...", and the full 192-character tag key at 'tags.1.member.key' where AWS's message does not carry the whole value.
Why: this is a credential leak by error path. An over-long or empty PutSecretValue/CreateSecret is refused with the submitted secret bytes inside the error body, which clients log, trace and attach to tickets.
Fix: the constraint-violation message builder - omit the value for @sensitive members and do not reproduce oversized member values.
Traces: secretsmanager.put-secret-value-exceeds-size-limit-rejected, secretsmanager.secret-string-max-size-boundary-enforced, secretsmanager.secret-value-empty-string-preserved, secretsmanager.tag-resource-invalid-tag-key-format-rejected.

=== Cause 3 of 3: emulator-authored message text on refusal paths whose wording AWS fixes ===
AWS: these refusals carry a fixed sentence (constant, or constant plus the identifier AWS chooses to name), pinned by the recorded response for each path: 'You can\'t specify both a binary secret value and a string secret value in the same secret.' (CreateSecret/PutSecretValue with both values); "Secrets Manager can't find the specified secret value for VersionId: <id>" (GetSecretValue with an unknown VersionId); 'Invalid name. Must be a valid name containing alphanumeric characters, or any of the following: -/_+=.@!' (CreateSecret with an unusable Name); 'No Lambda rotation function ARN is associated with this secret.' (RotateSecret with no rotation function); "You can't modify system tags. Tag key: '<key>'." (TagResource with an aws: prefix); "You can't create this secret because a secret with this name is already scheduled for deletion." (CreateSecret while the name sits in a recovery window - constant, with no name spliced in); and the ListSecrets unknown-filter-key message.
Emulator: every one of these is its own sentence - "You can't specify both SecretString and SecretBinary in the same request.", "Secrets Manager can't find the specified secret version: <id>", a Smithy length-constraint message for the bad Name, 'You must specify RotationLambdaARN, or the secret must already have a Lambda rotation function configured, to enable rotation.', 'Invalid Tags. The prefix aws: is reserved for Amazon Web Services tags; got key "aws:reserved".', and the recovery-window sentence with the caller's name appended. Statuses and codes on these paths match; only the text diverges.
Why: lowest impact of the three - control flow is unaffected - but message-asserting clients, log pipelines and the operator reading the error diverge, and the recovery-window message additionally reflects a caller-supplied identifier back into the body, which AWS does not. Related: fixed issue 20261023T182429Z-secretsmanager-secrets-manager-error-responses-diverge-wrong-exception-type.md addressed the constant not-found/pagination sentences on other operations; these are different paths (the VersionId-scoped not-found, CreateSecret, RotateSecret, TagResource, ListSecrets filter validation) and were not covered by it.
Fix: the message construction in each of those refusal paths - one shared table of the service's fixed sentences rather than per-handler prose.
Traces: secretsmanager.create-secret-both-string-and-binary-rejected, secretsmanager.create-secret-conflicting-secret-value-params-rejected, secretsmanager.put-secret-value-conflicting-binary-and-string-rejected, secretsmanager.create-secret-name-exceeds-max-length-rejected, secretsmanager.get-secret-value-wrong-version-id-fails, secretsmanager.list-secrets-invalid-filter-key-value-and-page-size-rejected, secretsmanager.rotate-secret-without-lambda-arn-configured-rejected, secretsmanager.rotation-rules-validation-rejected, secretsmanager.tag-resource-reserved-prefix-fails, secretsmanager.deep-secrets-and-params-force-deleted-secret-old-arn-and-version-ids-rejected-after-name-reuse.
