# config__lambda__sqs: 2 net-new causes — a change-triggered CUSTOM_LAMBDA rule is never push-invoked (while DescribeConfigRuleEvaluationStatus reports invocation timestamps anyway), and the uninvokable-evaluator rejection leg reaches no verdict in budget

> _Note: this issue was identified against the code base at commit `f420f96d635d512f65dbfe0e5d9b800a5c85b936`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutConfigRule

## Description
TWO CAUSES must be closed.

Cause 1 of 2: AWS Config never push-invokes a change-triggered (ConfigurationItemChangeNotification) CUSTOM_LAMBDA rule, yet DescribeConfigRuleEvaluationStatus reports the rule as having been successfully invoked and evaluated.
AWS: a rule whose Source is {Owner: CUSTOM_LAMBDA, SourceIdentifier: <function ARN>, SourceDetails: [{EventSource: aws.config, MessageType: ConfigurationItemChangeNotification}]} is invoked by Config unprompted — no StartConfigRulesEvaluation — once for the recorded resource shortly after PutConfigRule (recorded latency ~20 s), and again whenever the recorded resource changes. Each invocation carries an invokingEvent whose messageType is "ConfigurationItemChangeNotification" and whose configurationItem is the item Config itself built: configurationItemStatus "ResourceDiscovered" on the first (discovery) push and "OK" on the change-driven push, resourceId equal to the SQS queue URL (Config keys AWS::SQS::Queue by URL, not by name), resourceType "AWS::SQS::Queue", and a configuration carrying the queue's live VisibilityTimeout as a string. The evaluation the function reports via PutEvaluations then appears under GetComplianceDetailsByConfigRule with EvaluationMode "DETECTIVE", and the by-resource index (GetComplianceDetailsByResource) must agree with the by-rule index. Smithy: PutConfigRule accepts Source.Owner CUSTOM_LAMBDA with SourceDetails; the push path itself is recorded behavior only (no model surface), and the recording shows the first pushed verdict arriving without any caller-initiated evaluation.
Emulator: no evaluation result ever appears for the recorded queue under the rule. GetComplianceDetailsByConfigRule stays empty for the resource for the whole budget, while DescribeConfigRuleEvaluationStatus answers with a fully populated record for the rule — LastSuccessfulInvocationTime, LastSuccessfulEvaluationTime, FirstActivatedTime and FirstEvaluationStarted true — so the status surface asserts invocations that never happened. The configured Lambda is never called, so the second leg (change VisibilityTimeout out of band, expect a new COMPLIANT verdict with a strictly later ResultRecordedTime and configurationItemStatus OK) is unreachable too. Hypothesis: only the PULL path (StartConfigRulesEvaluation) is wired, and the evaluation-status record is synthesised at PutConfigRule time rather than written by an actual invocation.
Why: near-real-time compliance is exactly what a change-triggered custom rule is for. A client gets a rule that reports healthy — successful invocation and evaluation timestamps, FirstEvaluationStarted true — while nothing is ever evaluated, so a non-compliant resource is never flagged and CI/CD gates and dashboards built on it read clean. The fabricated status is worse than an empty one: it defeats the diagnostic a client would use to notice the rule is inert.
Fix: Config's rule-evaluation engine — the change-detection/push path that, on each new configuration item for a recorded resource in a rule's Scope, invokes the rule's CUSTOM_LAMBDA target with invokingEvent.messageType ConfigurationItemChangeNotification and the item Config built, and records the PutEvaluations verdict into both compliance indexes; and DescribeConfigRuleEvaluationStatus must report only invocations/evaluations that actually occurred (configservice rule-evaluation state and DescribeConfigRuleEvaluationStatus handler).
Traces: config__lambda__sqs.change-triggered-custom-rule-is-push-invoked-with-a-real-configuration-item.

Cause 2 of 2: the uninvokable-evaluator rejection leg reaches no verdict inside the budget, so PutConfigRule's invokability pre-check (InsufficientPermissionsException) is never exercised and the scenario is ungraded.
AWS: PutConfigRule for a CUSTOM_LAMBDA change-triggered rule whose target function has no resource policy granting config.amazonaws.com lambda:InvokeFunction is refused with InsufficientPermissionsException — Smithy: PutConfigRule.errors includes InsufficientPermissionsException {errorKind client, httpError 400 defaulted}, whose documentation states "For PutConfigRule, the Lambda function cannot be invoked. Check the function ARN, and check the function's permissions." The message names the function ARN from the request's Source.SourceIdentifier and says the function cannot be invoked (fixed text to that effect plus the ARN as the variable part); no rule is created (DescribeConfigRules answers NoSuchConfigRuleException for it and no evaluation result exists for the resource), and after AddPermission(Principal=config.amazonaws.com, Action=lambda:InvokeFunction) the identical call is accepted.
Emulator: the check is killed by the harness's 60 s budget — "Error: Check timed out after 60.0s" — before it can assert anything, so the refusal, the no-effect assertions and the positive control are all ungraded. The check's blocking waits before that assertion are all data-plane waits with budgets far above the harness ceiling (configuration-item capture for the new queue, 300 s; function CreateFunction/Active settle, 180 s each), and its final leg is the same push-invocation path Cause 1 shows is not served.
Why: the whole class "Config refuses a rule it could not evaluate" is unverified against the emulator, and a client cannot distinguish "accepted" from "accepted and permanently inert". Combined with Cause 1, a rule pointing at a function Config has no grant on is admitted and then reported as successfully invoked.
Fix: the same rule-evaluation/recording path as Cause 1 so the scenario can settle inside a normal budget, plus PutConfigRule's handler validation — resolve the CUSTOM_LAMBDA Source.SourceIdentifier's resource policy and refuse with 400 InsufficientPermissionsException naming the function ARN when config.amazonaws.com has no lambda:InvokeFunction grant, persisting nothing (services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/put_config_rule.rs).
Traces: config__lambda__sqs.change-triggered-rule-creation-is-denied-when-config-cannot-invoke-the-evaluator.
