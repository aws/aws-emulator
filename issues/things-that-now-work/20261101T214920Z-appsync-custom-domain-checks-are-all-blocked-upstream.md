# AppSync custom-domain checks are all blocked upstream: an ACM DNS-validated certificate for a name in the account's own hosted zone ends FAILED instead of ISSUED (2 causes)

> _Note: this issue was identified against the code base at commit `78d451b133906486fa3b840444972b2844d34551`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RequestCertificate

## Description
Two root causes, both in the ACM certificate state machine, reached from six net-new failing AppSync behavioral checks. Every one of the six is tagged `requires:dns-baseline` and begins by minting a real, DNS-validated ACM certificate (helper `_dns_validated_cert`) because AppSync's CreateDomainName accepts only a certificate ACM itself issued; all six abort in that helper, before a single AppSync call is made, on `assert status == "ISSUED"` with the certificate reporting `FAILED`.

Service attribution: the failing check ids' leading token is `appsync` (their SERVICES list is ["appsync"]), so the issue is filed under `appsync`; the diverging operations and the component to fix are ACM's and are named below.

Cause 1 of 2: a public DNS-validated certificate request for a name under an RFC 2606 reserved second-level name is terminally FAILED up front, even when the account holds and is delegated the public hosted zone that name lives in. Failing checks: all six listed in Traces.
AWS: Smithy (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json) CertificateDetail$Status -> CertificateStatus [PENDING_VALIDATION, ISSUED, INACTIVE, EXPIRED, VALIDATION_TIMED_OUT, REVOKED, FAILED], documented: "A certificate enters status PENDING_VALIDATION upon being requested, unless it fails for any of the reasons given in the troubleshooting topic Certificate request fails. ACM makes repeated attempts to validate a certificate for 72 hours and then times out. ... If validation succeeds, the certificate enters status ISSUED." DomainValidation$ValidationStatus -> DomainStatus [PENDING_VALIDATION, SUCCESS, FAILED]; DomainValidation$ResourceRecord carries "the CNAME record that you add to your DNS database for domain validation". The rule the model states is therefore: a requested AMAZON_ISSUED certificate is PENDING_VALIDATION until the published evidence is observed (-> ISSUED), the 72-hour window elapses (-> VALIDATION_TIMED_OUT), or the request fails for one of the enumerated FailureReason causes (-> FAILED, and only then is FailureReason present). Beyond that it is recorded behavior only: in the recording, the checks' own domain — a label under the account's tagged public hosted zone, whose apex in this environment is `sim2real-baseline-<hex>.example.net` — is requested with ValidationMethod='DNS', the returned validation CNAME is UPSERTed into that zone, and the certificate reaches Status 'ISSUED' (per-domain ValidationStatus 'SUCCESS'), which is why the checks then proceed to CreateDomainName.
Emulator: `validation_outcome` in the RequestCertificate handler decides the owed outcome from the request alone, and `domain_control_is_unprovable` classifies any name under RESERVED_DOMAIN_NAMES ["example.com", "example.net", "example.org"] / RESERVED_DOMAIN_SUFFIXES as one whose control "can never be proven", yielding ValidationOutcome::Failed. Because the account's DNS baseline zone itself sits under `example.net`, every name the checks can validate in is pre-judged unprovable, so DescribeCertificate reports Status 'FAILED' (HTTP 200; no FailureReason, which AWS guarantees whenever Status is FAILED). The account IS delegated that zone in this emulator — route53 enumerates it and serves its records — so control of the name is provable, and the up-front refusal contradicts the emulator's own DNS state.
Why: a client that asks ACM for a certificate for a domain it genuinely controls is told, terminally, that the request failed. FAILED is documented as "delete the request, correct the issue ... and try again", so a client stops polling and reports a hard provisioning error instead of waiting for issuance. Every downstream feature that needs an ACM-issued certificate (AppSync custom domains, CloudFront-backed custom domains, API Gateway domain names) becomes unreachable, and here it masks the whole AppSync custom-domain surface: six checks never issue an AppSync request at all.
Fix: the ACM RequestCertificate handler's validation-outcome decision and the certificate state machine it feeds (services/service-com-amazonaws-acm-certificatemanager/src/ops/request_certificate.rs `validation_outcome`, and `domain_control_is_unprovable` / RESERVED_DOMAIN_NAMES in services/service-com-amazonaws-acm-certificatemanager/src/state.rs). A name under a public hosted zone this account holds must not be pre-judged unprovable; such a request must enter PENDING_VALIDATION with its validation CNAME live, and FAILED must be reserved for a modelled FailureReason (and then populate FailureReason).

Cause 2 of 2: the ACM emulator never observes published DNS validation evidence, so no DNS-validated request can ever reach ISSUED — once Cause 1 no longer fires, the same six checks stall in PENDING_VALIDATION and then VALIDATION_TIMED_OUT instead of being issued. Failing checks: all six listed in Traces (the same six: Cause 1 is what they hit first, Cause 2 is what they hit next).
AWS: Smithy as cited above — "If validation succeeds, the certificate enters status ISSUED", with DomainValidation$ResourceRecord being the CNAME the requester publishes and DomainStatus carrying SUCCESS per domain once it is seen. Recorded behavior: after the CNAME from DomainValidationOptions[0].ResourceRecord is UPSERTed into the delegated zone, DescribeCertificate transitions PENDING_VALIDATION -> ISSUED with ValidationStatus 'SUCCESS', Type 'AMAZON_ISSUED' and NotBefore < NotAfter, well inside the 72-hour window; the particular domain label, certificate ARN and timestamps are per-run values, the transition is the requirement.
Emulator: by its own documentation in request_certificate.rs, "This emulator observes no published evidence, so nothing shortens the wait": the only outcome owed to a public request is ValidationOutcome::TimedOut after the 72-hour VALIDATION_WINDOW (or ::Issued, but only when a private CertificateAuthorityArn is supplied). Publishing the challenge CNAME through route53 ChangeResourceRecordSets has no effect on the certificate's status, so the documented DNS issuance path (RequestCertificate -> PENDING_VALIDATION -> publish CNAME -> ISSUED) has no reachable success outcome at all.
Why: DNS validation is the recommended and default ACM issuance workflow. A client that publishes exactly the record ACM asked for and polls DescribeCertificate (the standard pattern, and what the certificate-validated waiter does) never sees ISSUED, so it either waits out the whole window or gives up; nothing that requires an ACM-issued certificate can be provisioned end to end.
Fix: the ACM certificate state machine's DNS-validation progression (services/service-com-amazonaws-acm-certificatemanager/src/ops/request_certificate.rs `validation_outcome` / `crate::state::PendingValidation`, and the pending-validation materialisation DescribeCertificate's CertificateDetail projection reads) must consult the route53 record set for the challenge name it minted, and move Status to ISSUED with every DomainValidationOptions[*].ValidationStatus 'SUCCESS' (plus Serial/NotBefore/NotAfter/IssuedAt) once that CNAME resolves to the published value.

## Steps to Reproduce
1. Clone the repo, build and boot the emulator, then run the behavioral suite; the six checks listed in Traces reproduce as [mismatch] with `AssertionError: DNS-validated certificate for <domain> ended 'FAILED'`.
2. Directly: route53.list_hosted_zones() and route53.list_tags_for_resource(ResourceType='hostedzone', ResourceId=<id>) to find the public zone tagged {'Key': 'sim2real-infra-dns-baseline', 'Value': 'true'}; note its apex (in this environment a name under example.net).
3. acm.request_certificate(DomainName='sim2real<hex>.<apex>', ValidationMethod='DNS', IdempotencyToken='<hex>') against acm in us-east-1 and keep the CertificateArn.
4. Poll acm.describe_certificate(CertificateArn=<arn>) for Certificate.DomainValidationOptions[0].ResourceRecord and UPSERT that {Name, Type: 'CNAME', Value} record into the hosted zone with route53.change_resource_record_sets.
5. Poll acm.describe_certificate until Certificate.Status leaves 'PENDING_VALIDATION'. Observed (Cause 1): Status == 'FAILED' — in fact already FAILED before the record is published — with Certificate.FailureReason absent. Expected (AWS): PENDING_VALIDATION, then 'ISSUED' with DomainValidationOptions[0].ValidationStatus == 'SUCCESS' once the CNAME resolves.
6. Cause 2: repeat steps 3-5 with a domain under a non-reserved apex, or after relaxing the reserved-name judgement, and observe that publishing the CNAME still never moves the certificate out of PENDING_VALIDATION (its only owed outcome is VALIDATION_TIMED_OUT after 72h), so no DNS-validated certificate is ever issued.
7. With an issued certificate, appsync.create_domain_name(domainName=<domain>, certificateArn=<arn>) is what the six checks go on to exercise; re-replay all six check ids in trace_ids and confirm they pass before closing.
