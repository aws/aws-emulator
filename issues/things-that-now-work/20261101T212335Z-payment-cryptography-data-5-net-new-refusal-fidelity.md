# payment-cryptography-data: 5 net-new refusal-fidelity root causes — VerificationFailedException message is the shape's doc string, block-length refusal reworded, constraint ValidationException echoes @sensitive PlainText with a lower-cased member path, GenerateMac checks modes-of-use before the key/MAC-algorithm match, and the data plane enforces no IAM authorization

> _Note: this issue was identified against the code base at commit `6df8ee8a64c175c1ec46c5456c673946e1d299f9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
VerifyMac, VerifyCardValidationData, DecryptData, EncryptData, GenerateMac, GenerateCardValidationData

## Description
Five independent root causes in the Payment Cryptography DATA plane, all reached over the wire by the behavioral suite. Each cause below must be closed before this issue is submitted.

=== Cause 1 of 5: every VerificationFailedException carries the EXCEPTION SHAPE'S DOC STRING as its message instead of the operation's own verification-failure sentence ===
AWS: Smithy (services/service-com-amazonaws-paymentcryptographydata-paymentcryptographydataplane/smithy-model/...json) models VerificationFailedException as a client error, HTTP 400, with required members Reason (VerificationFailedReason: INVALID_MAC | INVALID_PIN | INVALID_VALIDATION_DATA | INVALID_AUTH_REQUEST_CRYPTOGRAM) and Message. The model does not state the message text, so this is recorded behavior only: real AWS words the message PER OPERATION. For VerifyMac the recorded refusal is HTTP 400, Code VerificationFailedException, Reason INVALID_MAC, Message exactly 'Mac verification failed.'; for VerifyCardValidationData it is HTTP 400, Code VerificationFailedException, Reason INVALID_VALIDATION_DATA, Message exactly 'Card validation data verification failed.' Both sentences are entirely FIXED text — they interpolate nothing from the request or from state.
Emulator: both operations answer the single shared constant crate::state::VERIFICATION_FAILED_MESSAGE = 'This request failed verification.' (src/state.rs), which is verbatim the Smithy @documentation string of the VerificationFailedException shape, not a message AWS ever returns in the Message member. Status (400), Code (VerificationFailedException) and Reason are correct; only Message diverges. Replayed: VerifyMac against a tampered message and against another thread's message both answer Message 'This request failed verification.' where AWS answers 'Mac verification failed.'; VerifyCardValidationData against a one-digit-corrupted CVV answers 'This request failed verification.' where AWS answers 'Card validation data verification failed.'
Why: a client that distinguishes verification outcomes by the error message — log scrapers, PIN/MAC retry counters, operator runbooks and SDK-level string assertions — cannot tell a MAC failure from a card-validation failure from any other verification failure, because one sentence is emitted for all of them. The sentence it does emit is a documentation string, so it will never match anything written against AWS.
Fix: the per-operation message belongs in each verifying operation's handler (src/ops/verify_mac.rs builds VerificationFailedException at the MAC comparison; src/ops/verify_card_validation_data.rs likewise), replacing the one shared crate::state::VERIFICATION_FAILED_MESSAGE constant with one sentence per verification class (the Reason the operation already sets is the discriminator). The remaining Reason values (INVALID_PIN, INVALID_AUTH_REQUEST_CRYPTOGRAM) need their own sentences when those operations are implemented.
Traces: payment-cryptography-data.verify-mac-wrong-message-rejected, payment-cryptography-data.verify-card-validation-data-wrong-value-rejected, payment-cryptography-data.concurrent-generate-mac-same-key-no-cross-talk (the concurrency check's cross-talk assertions on code and distinctness pass; it fails only on this message).

=== Cause 2 of 5: the block-length refusal of EncryptData/DecryptData is emulator-authored and expressed in BYTES, not AWS's fixed sentence expressed in hex characters ===
AWS: Smithy models PlainTextType and CipherTextType as hex strings (@pattern ^(?:[0-9a-fA-F][0-9a-fA-F])+$) and EncryptData's own documentation states 'When you use TDES or TDES DUKPT, the plaintext data length must be a multiple of 8 bytes. For AES or AES DUKPT, the plaintext data length must be a multiple of 16 bytes.' The model does not word the refusal, so the message is recorded behavior only: a DecryptData whose CipherText is not a whole number of cipher blocks is refused HTTP 400, Code ValidationException, Message exactly 'Invalid data provided. Please provide data of length multiple of 16.' The fixed text is 'Invalid data provided. Please provide data of length multiple of ' + N + '.'; the only variable part is N, the required length counted in HEX CHARACTERS of the wire value — 16 for a Triple DES key (an 8-byte block). Hypothesis: for an AES key the same sentence carries N = 32, since the block is 16 bytes; this suite only recorded the TDES_2KEY case.
Emulator: src/state/crypto.rs (SymmetricRequest::resolve, the is_multiple_of(block_len) guard) authors its own sentence, 'The data length must be a multiple of {block_len} bytes for KeyAlgorithm {key_algorithm}.', which the operation lifts into ValidationException. Replayed: DecryptData with a ciphertext truncated to 8 hex characters under a TDES_2KEY key answers 400 ValidationException with Message 'The data length must be a multiple of 8 bytes for KeyAlgorithm TDES_2KEY.' — right status and code, wrong sentence, wrong unit (bytes instead of hex characters), and it adds a KeyAlgorithm clause AWS's sentence does not carry.
Why: the status and code match, so a client only sees the divergence in the message — exactly what a payment client surfaces to an operator or matches on when deciding whether to re-pad and retry versus escalate. The unit difference is worse than cosmetic: an operator reading 'multiple of 8 bytes' and a client reading AWS's 'multiple of 16' are told two different numbers for the same requirement.
Fix: the refusal wording belongs in the shared length guard in src/state/crypto.rs (SymmetricRequest::resolve) so both EncryptData and DecryptData answer the one AWS sentence, with N derived from the cipher's block length expressed in hex characters (block_len * 2).
Traces: payment-cryptography-data.decrypt-data-ciphertext-wrong-length-rejected.

=== Cause 3 of 5: the shared constraint-validation layer formats ValidationException with the wrong separator and a lower-cased bare member name, and ECHOES the value of a @sensitive member ===
AWS: Smithy marks PlainTextType @sensitive with @pattern ^(?:[0-9a-fA-F][0-9a-fA-F])+$ and @length 2..4096. A request violating that pattern is refused HTTP 400, Code ValidationException, Message exactly "1 validation error detected. Value at '/PlainText' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(?:[0-9a-fA-F][0-9a-fA-F])+$". Fixed text: '1 validation error detected. Value at ' + path + ' failed to satisfy constraint: Member must satisfy regular expression pattern: ' + pattern. The variable parts are the path — a JSON-pointer-style '/PlainText' using the MODELED member name, capitalisation included — and the @pattern as the model states it. The offending VALUE is NOT in the message, because the member is @sensitive.
Emulator: the centralized validate step of the request walk (deserialize -> validate -> handle, the shared smithy_server_runtime constraint layer this crate's operations are driven through) emits "1 validation error detected: Value '00112233ZZ556677' at 'plainText' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(?:[0-9a-fA-F][0-9a-fA-F])+$". Three divergences in one formatter: 'detected:' where AWS writes 'detected.'; the member rendered as the lower-camel wire name in bare quotes ('plainText') where AWS writes the JSON pointer of the modeled member ('/PlainText'); and the rejected value interpolated into the message, where AWS omits it. Status (400) and Code (ValidationException) are correct.
Why: every constraint refusal in this crate is worded by this one formatter, so no client assertion, log filter or operator runbook written against AWS's constraint message matches the emulator for ANY member of ANY operation here — the divergence is not specific to PlainText. The value echo is a disclosure defect in its own right: PlainTextType and CipherTextType are @sensitive precisely so cardholder plaintext and ciphertext never appear in an error body or a log line, and the emulator puts the caller's plaintext there.
Fix: the constraint-violation message formatter in the shared validation step of the request walk — the separator after 'detected', the member path rendering (modeled member name, '/'-prefixed), and suppression of the value for any member whose target shape carries @sensitive.
Traces: payment-cryptography-data.encrypt-data-invalid-hex-plaintext-rejected.

=== Cause 4 of 5: GenerateMac applies the KeyModesOfUse gate BEFORE checking the key's algorithm against the requested MAC algorithm, so a non-MAC key is refused with the wrong sentence ===
AWS: GenerateMac's own documentation requires a MAC key (KeyUsage TR31_M7_HMAC_KEY for HMAC) with KeyModesOfUse set to Generate; errors include ValidationException (HTTP 400). The model does not word the refusal, so the message is recorded behavior only: GenerateMac with GenerationAttributes {Algorithm: HMAC} against a TDES_2KEY / TR31_D0_SYMMETRIC_DATA_ENCRYPTION_KEY key is refused HTTP 400, Code ValidationException, Message exactly 'Invalid key with KeyAlgorithm HMAC used with MacAlgorithm TDES_2KEY. Please use valid HMAC Key.' Fixed text: 'Invalid key with KeyAlgorithm ' + A + ' used with MacAlgorithm ' + B + '. Please use valid ' + A + ' Key.'; the variable parts are the MAC algorithm the request named (A, from GenerationAttributes) and the key's own KeyAlgorithm (B, from state). AWS evaluates this algorithm-compatibility check FIRST — the key in the recording also lacks the Generate mode of use, and AWS still answers the algorithm sentence, never a modes-of-use sentence.
Emulator: src/ops/generate_mac.rs resolves the key and then immediately gates on `if !key.modes.generate()`, returning 'The KeyModesOfUse of key <keyArn> do not include Generate.' The key/MAC-algorithm compatibility check only happens later, inside crate::state::crypto::generate_mac (whose own refusal, 'KeyAlgorithm {key_algorithm} is not valid for the algorithm {algorithm}.', is itself not AWS's sentence). Replayed: the call answers 400 ValidationException with Message 'The KeyModesOfUse of key arn:aws:payment-cryptography:<region>:<account>:key/<keyId> do not include Generate.' — right status and code, wrong precedence and wrong sentence, and it interpolates a key ARN that AWS's sentence does not contain.
Why: a client is told the wrong thing is wrong. It is pointed at the key's modes of use (a control-plane attribute it might try to change) when the actual fault is that it handed a data-encryption key to a MAC operation; a caller that retries after widening KeyModesOfUse still fails. The same mis-ordering means the algorithm-compatibility sentence is unreachable for any key that also lacks the mode, i.e. for the normal case.
Fix: the validation order and wording in src/ops/generate_mac.rs — check the requested MAC algorithm against the resolved key's KeyAlgorithm/KeyUsage before the KeyModesOfUse gate, and word that refusal as AWS does (same ordering question applies to the sibling src/ops/verify_mac.rs, which gates on key.modes.verify() first for the same reason).
Traces: payment-cryptography-data.generate-mac-key-usage-mismatch-rejected.

=== Cause 5 of 5: the data plane performs NO IAM authorization — an assumed role with no attached policy is served instead of being refused AccessDeniedException ===
AWS: Smithy declares AccessDeniedException (HTTP 403) on every data-plane operation, including GenerateCardValidationData, documented 'You do not have sufficient access to perform this action.' Recorded behavior: a caller using credentials from sts:AssumeRole on a role with NO attached identity-based policy (implicit deny) is refused HTTP 403, Code AccessDeniedException, with the standard IAM denial sentence — fixed text 'User: ' + principalArn + ' is not authorized to perform: ' + action + ' on resource: ' + resourceArn + ' because no identity-based policy allows the ' + action + ' action'. The variable parts come from the request's signing principal (the assumed-role ARN arn:aws:sts::<account>:assumed-role/<roleName>/<sessionName>), the action (payment-cryptography:GenerateCardValidationData) and the key ARN the request named. Granting that one action to the SAME role restores the identical call to success, which is what isolates authorization as the only variable.
Emulator: the call SUCCEEDS. GenerateCardValidationData under the unprivileged session returned a 200 with ValidationData; no error was raised at all, so the check failed on 'an implicit-deny role must not be able to generate CVV data'. Nothing in the data-plane handlers or their request walk consults the caller's identity: src/ops/*.rs read only the engine state and the request body, and the resolve-key path (src/state.rs resolve_key) applies key state and KeyModesOfUse but never an authorization decision.
Why: this is an overly-permissive divergence on a payment-data API — the emulator cannot be used to test least-privilege policies, a negative authorization test passes vacuously, and any regression that drops a required IAM grant is invisible until it reaches real AWS. Cardholder-data operations are exactly where a wrongly-granted call matters most.
Fix: an authorization gate in the data plane's request walk (before each operation's handler runs), evaluating the signed principal against its identity-based policies for the payment-cryptography:<Operation> action on the target key ARN, and answering the modeled AccessDeniedException (HTTP 403) with the IAM denial sentence above when no statement allows it.
Traces: payment-cryptography-data.generate-card-validation-data-missing-permission-rejected (its positive control with the harness's own credentials succeeds, and its restore step re-grants the single action to the same role).
