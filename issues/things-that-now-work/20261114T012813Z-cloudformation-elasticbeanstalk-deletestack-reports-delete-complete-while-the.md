Adjacent open issues describe neighbouring ground but do NOT carry this failure. 20261111T111216Z-cloudformation-elasticbeanstalk-2-net-new-causes-elastic-beanstalk-in-place.md lists this check id, but its replay keys for it are the in-place-update UPDATE_FAILED and the `_assert_replaced_and_retained` replacement-event assertions; this replay gets past both of those and fails much later, in the post-DeleteStack step, with a different assertion, so this is a distinct cause and not a reopening. 20261109T144630Z-cloudformation-elasticbeanstalk-stack-outputs-omit-outputvalue-a-stack.md Cause 3 concerns a ROLLBACK leaving an application behind on a create that should have failed; this one is a successful, completed DELETE of a healthy stack.

Cause 1 of 1: a stack whose resources include an AWS::ElasticBeanstalk::Application reaches DELETE_COMPLETE, but the Elastic Beanstalk application the stack created is still present in the elasticbeanstalk service state afterwards.
AWS: recorded behavior only for the CloudFormation side — deleting a stack that owns an AWS::ElasticBeanstalk::Application deletes that application (the handler performs Elastic Beanstalk's DeleteApplication and waits for it), and CloudFormation only reports DELETE_COMPLETE once every resource it owns is gone; any subsequent read or write under that application name therefore finds nothing. Smithy (elasticbeanstalk): CreateConfigurationTemplate takes ApplicationName (required) — "The name of the Elastic Beanstalk application to associate with this configuration template" — and a request naming an application that does not exist is refused HTTP 400 with the service-common error code `InvalidParameterValue` and the message `No Application named '<ApplicationName>' found.` (fixed text `No Application named '` … `' found.`; the only variable part is the ApplicationName taken from the request). DescribeApplications(ApplicationNames=[<that name>]) answers 200 with an empty Applications list.
Emulator: after the stack has been deleted (CloudFormation settles at DELETE_COMPLETE) and both environments read Terminated, elasticbeanstalk CreateConfigurationTemplate under the stack's application name is served HTTP 200 and mints a template: the response carries SolutionStackName, PlatformArn, ApplicationName (the deleted application), TemplateName, DeploymentStatus 'deployed', DateCreated/DateUpdated and a full resolved OptionSettings list, instead of the 400 `InvalidParameterValue` / `No Application named '<app>' found.` refusal. The elasticbeanstalk handler itself does contain that guard (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/create_configuration_template.rs, the `store.applications.contains_key` check that formats exactly this message), so the guard passing proves the application record is still in the Elastic Beanstalk store — the stack's delete never removed it (or removed it only on a deferred transition that DELETE_COMPLETE does not wait for).
Why: a client that tears a Beanstalk deployment down through CloudFormation is told the deletion finished while the application — and everything that hangs off it (configuration templates, application versions, the per-application name space) — is still live. Re-creating the same stack then hits "already exists" refusals, the application name is never freed, CloudFormation and Elastic Beanstalk disagree about what exists, and negative-path assertions built on "after the stack is gone, the application is gone" silently pass against stale state.
Fix: the AWS::ElasticBeanstalk::Application resource handler's DELETE path in CloudFormation's resource-provisioning engine — stack deletion must perform Elastic Beanstalk's DeleteApplication against the same elasticbeanstalk store the service's own operations read (removing the application, its configuration templates and its application versions) and must not report the resource DELETE_COMPLETE (hence the stack DELETE_COMPLETE) until that removal is visible to elasticbeanstalk reads.
Traces: cloudformation__elasticbeanstalk.cfn-elasticbeanstalk-environment-retained-replacement-keeps-old-running-then-terminated (step 3 of the check, after `_delete_stack` asserted DELETE_COMPLETE).
