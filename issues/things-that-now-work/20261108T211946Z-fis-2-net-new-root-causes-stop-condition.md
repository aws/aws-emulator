# FIS: 2 net-new root causes — stop-condition halt reason is the emulator's own wording instead of AWS's fixed text, and a rebooted guest's console never carries what the instance actually booted (no user-data/kernel log), so the reboot check cannot complete

> _Note: this issue was identified against the code base at commit `ae54f48f2b6fca43108843f25838024299d6c3fb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetExperiment

## Description
This issue bundles TWO distinct net-new root causes reached by the FIS fault-injection checks. Both must be closed before submitting; each names its own failing checks. Neither was marked ALREADY FILED or OWNED by the suite. The nearest open issue, 20261029T183321Z-fis-4-net-new-root-causes-inject-api.md, covered the run path up to and including 'an alarm stop condition is never evaluated' (its Cause 3) — the experiment now DOES halt as 'stopped' on the breach, so the check progressed past that assertion; what fails now is the reason text, which that issue's Cause 3 actually prescribed wrongly (it asked for a reason 'naming the stop condition'). Cause 1 below supersedes that prescription with what the recording shows. 20261024T000450Z / 20261104T032609Z / 20261107T200341Z (resourceTags resolution) and 20261106T163756Z (catalog data) cover none of the behaviour below.

Cause 1 of 2 — the state.reason of an experiment halted by a stop condition is the emulator's own sentence with the alarm ARN interpolated, instead of AWS's fixed sentence.
AWS: recorded behavior only. Smithy says nothing about the wording: ExperimentState$reason is just 'The reason for the state.' (com.amazonaws.fis#ExperimentStatusReason, @length 0..512, pattern ^[\s\S]+$), and ExperimentActionState$reason likewise. The recording of this check breaches an aws:cloudwatch:alarm stop condition of a running experiment with no StopExperiment call, and real AWS reports state = {status: 'stopped', reason: 'Experiment halted by stop condition.'}. That whole sentence is FIXED text — it has no variable part at all: no alarm name, no ARN, no account, no region is substituted into it. The HTTP status is 200 on GetExperiment; this is a response-field divergence, not an error.
Emulator: GetExperiment reports status 'stopped' (correct) with reason 'Stopped by the stop condition monitoring <alarmArn>' — the fixed half is 'Stopped by the stop condition monitoring' and the alarm ARN is a value taken from the experiment's own stopConditions. The text is declared as the emulator's own invention in services/service-com-amazonaws-fis-faultinjectionsimulator/src/state.rs:634-646 (STOPPED_BY_STOP_CONDITION, stop_condition_reason), whose doc comment states 'FIS documents no wording for ExperimentState$reason, so … the text is this emulator's own'.
Why: state.reason is how a client distinguishes WHY a run ended — an operator dashboard, a CI gate or a chaos-engineering harness matches on the sentence AWS emits. A client that asserts (or logs, or alerts on) AWS's 'Experiment halted by stop condition.' sees an unrecognised string and reports an unknown halt cause, even though the status is right. It is also not merely cosmetic: the emulator's variant embeds a per-run ARN, so no exact-match comparison can ever succeed.
Fix: the stop-condition halt path's reason text — the constant and its formatter in services/service-com-amazonaws-fis-faultinjectionsimulator/src/state.rs (STOPPED_BY_STOP_CONDITION / stop_condition_reason) and the settle path that stores it on the experiment record — must emit AWS's fixed sentence with no interpolation. The sibling 'safety lever'/StopExperiment reasons and the halted action's own reason ('Action was stopped.' is what this check asserts next, at check line 620) belong to the same wording table and should be taken from the recordings rather than invented.
Traces: fis.fis-stop-condition-breach-halts-a-live-api-fault-and-the-fault-actually-stops.

Cause 2 of 2 — an instance's console carries only a synthesized label/value dump of the instance record, never what the guest actually booted, so a FIS aws:ec2:reboot-instances experiment produces no guest-side evidence of the reboot and the check can never finish.
AWS: recorded behavior only (GetConsoleOutput documents 'the instance console output displays the exact console output that would normally be displayed on a physical monitor attached to a computer', $Output base64-encoded, $Timestamp the last update). The recording launches a t3.micro from the AL2023 AMI with cloud-init user-data whose bootcmd writes a marker line to /dev/console on EVERY boot, and real AWS's console then carries: that marker line (nonce, /proc/sys/kernel/random/boot_id, a counter kept on the root volume), many kernel printk-prefixed lines of the form '[    6.096338] ', and 'cloud-init[' lines — appended per boot, measured at ~10,002 NEW bytes between the first and the second boot's markers. Across the FIS reboot the instance keeps its InstanceId and LaunchTime and returns to State 'running' with status checks ('ok','ok').
Emulator: no guest runs, so none of that text exists. services/service-com-amazonaws-ec2-amazonec2/src/ops/get_console_output.rs serves crate::state::instance_console_text, which is services/service-com-amazonaws-ec2-amazonec2/src/state/instance_console.rs:72-109: a fixed label column of record facts (instance-id, instance-state, instance-type, image-id, availability-zone, private-ip-address, private-dns-name, public-ip-address, launch-time) followed by one three-line block per boot ('boot', 'boot-id', 'boot-time' — services/service-com-amazonaws-ec2-amazonec2/src/state/instance_boots.rs:169-178). UserData is never executed or echoed anywhere in that text, and there is no kernel log and no cloud-init output. Hypothesis for the observed verdict: because the console can never match the marker regex, the check's first marker poll (budget 600s) spins until the harness kills the check — the reported failure is 'Check timed out after 180.0s' rather than an assertion, so the stall point is inferred from the source above, not from an assertion message.
Why: a client cannot obtain any guest-side evidence from the emulator. Every use of GetConsoleOutput — reading cloud-init/user-data output to confirm bootstrap, grepping a boot log for a failure, or proving a reboot actually restarted the kernel rather than relaunching the instance — gets a synthetic inventory of API fields instead. A resilience test that verifies a FIS aws:ec2:reboot-instances action really restarted the guest passes vacuously or, as here, hangs; and the emulator's 'boot-id' label is not where any AWS client looks for a boot identity.
Fix: EC2's console derivation and the instance record behind it (services/service-com-amazonaws-ec2-amazonec2/src/state/instance_console.rs::instance_console_lines/instance_console_text, services/service-com-amazonaws-ec2-amazonec2/src/state/instance_boots.rs boot records, and the RunInstances path that stores UserData) must render a per-boot console block in the shape a Linux guest writes — printk-timestamped kernel lines, init-system ('cloud-init[') lines, and the output of the instance's own UserData (cloud-init bootcmd on every boot, runcmd on the first only, with the marker text written to /dev/console appearing verbatim) — appended across boots, with each boot's identity distinct and the instance's id and LaunchTime unchanged by a reboot.
Traces: fis.fis-reboot-instances-restarts-the-guest-kernel-and-the-boot-id-changes.

## Steps to Reproduce
Cause 1 (stop-condition halt reason):
1. cloudwatch:PutMetricAlarm A; SetAlarmState(A, 'OK').
2. iam:CreateRole R trusting fis.amazonaws.com with an inline policy allowing the inject action plus cloudwatch:DescribeAlarms; iam:CreateRole T as the aws:iam:role target.
3. fis:CreateExperimentTemplate roleArn=R, one aws:fis:inject-api-internal-error action with parameters {duration: 'PT10M', service: 'ec2', operations: 'DescribeAvailabilityZones', percentage: '100'} targeting T, stopConditions [{source: 'aws:cloudwatch:alarm', value: <A arn>}].
4. fis:StartExperiment; poll fis:GetExperiment until state.status == 'running'.
5. cloudwatch:SetAlarmState(A, 'ALARM'). Do NOT call StopExperiment. Poll GetExperiment until state.status == 'stopped'.
6. Read experiment.state.reason. Emulator: 'Stopped by the stop condition monitoring <alarmArn>'. Expected: exactly 'Experiment halted by stop condition.'

Cause 2 (guest console across a FIS reboot):
1. ssm:GetParameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 for the AMI; pick an AZ that offers t3.micro and a subnet in it.
2. ec2:RunInstances (t3.micro, that AMI, that subnet) with UserData = a #cloud-config whose bootcmd writes 'SIM2REAL_BOOT <nonce> $(cat /proc/sys/kernel/random/boot_id) <counter>' to /dev/console on every boot; wait for instance_running.
3. ec2:GetConsoleOutput(InstanceId, Latest=True) and base64-decode. Expected: the marker line with counter '1', kernel printk-prefixed lines and 'cloud-init[' lines. Emulator: only the labelled record dump ('instance-id …', 'launch-time …', 'boot 1', 'boot-id …', 'boot-time …') — no marker, no printk prefixes, no cloud-init lines, so a client polling for the marker never sees it.
4. Create a FIS role with AWSFaultInjectionSimulatorEC2Access, a template whose single action is aws:ec2:reboot-instances targeting that instance by explicit resourceArns, and StartExperiment; wait for state.status 'completed'.
5. GetConsoleOutput again. Expected: the FIRST boot's marker unchanged plus a SECOND marker with a different boot_id and counter '2', with >=500 new bytes, >=20 printk prefixes and a 'cloud-init[' line between them; DescribeInstances still reports the same InstanceId and LaunchTime, State 'running'. Emulator: the console gains only a second 'boot/boot-id/boot-time' triple, so the check's marker poll never satisfies and the run is killed at the harness's 180s cap.
