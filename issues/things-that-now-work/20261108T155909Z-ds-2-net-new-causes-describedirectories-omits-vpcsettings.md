# ds: 2 net-new causes — DescribeDirectories omits VpcSettings.SecurityGroupId, and a trust to a .test remote domain always settles on Failed, so the trust lifecycle is unreachable

> _Note: this issue was identified against the code base at commit `32a26f18a0fb4dc356c9d3ce1ecec069a0aff304`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTrust

## Description
Two independent, net-new fidelity defects in the Directory Service emulator's Managed Microsoft AD trust surface. Both causes must be closed before submitting. Neither failure is a scaffold stub: the service answers in both cases.

Cause 1 of 2: DescribeDirectories does not report the domain controller security group of a VPC-placed directory, so VpcSettings.SecurityGroupId is absent.
AWS: Smithy — DirectoryVpcSettingsDescription$SecurityGroupId, target SecurityGroupId with @pattern ^(sg-[0-9a-f]{8}|sg-[0-9a-f]{17})$, documented "The domain controller security group identifier for the directory." Recorded behavior: once a Managed Microsoft AD directory created with VpcSettings has left Requested, DescribeDirectories reports DirectoryDescriptions[0].VpcSettings with VpcId, SubnetIds, AvailabilityZones AND SecurityGroupId naming the AWS-managed controllers security group the service minted in the subnets' VPC. The id value differs per run and is not a requirement; its PRESENCE and sg- shape are.
Emulator: the member is simply missing from the serialized VpcSettings — a client reading desc["VpcSettings"]["SecurityGroupId"] gets KeyError: 'SecurityGroupId'. The stored placement is echoed back unchanged (crate state builds DirectoryVpcSettingsDescription from the create's settings with `..settings.clone()` and only fills AvailabilityZones), and nothing ever assigns a security group id.
Why: a client cannot reach the directory's network at all. Any workflow that authorizes the directory's AD ports — a same-VPC trust between two directories, which must add an ingress rule naming the peer directory's controllers group, or any reconciliation of the directory against EC2 — has no group id to work with and fails on a missing field rather than on a modelled refusal.
Fix: the directory's network provisioning in the CreateMicrosoftAD/CreateDirectory handler (it must mint a controllers security group id and persist it on the directory) and the single rendering point that builds DirectoryVpcSettingsDescription for every reporting operation, in the ds service state.
Traces: ds.e2e-trust-create-verify-delete-flow (KeyError at desc_a["VpcSettings"]["SecurityGroupId"]). Citations: services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state.rs:2707-2713 (described_vpc_settings). An open issue, 20261024T081028Z-ds-directory-service-a-microsoft-ad-never-provisions-its.md, covers the security group / ENIs not EXISTING in EC2 for two ds__ec2 checks; it does not carry this check's replay key and does not cover the ds-side member being absent from the DescribeDirectories response, which is this cause. A fixer should land them together.

Cause 2 of 2: a trust whose remote domain's top-level label is one of invalid/test/localhost/example is always settled on Failed, even when the emulator's own store holds the directory that serves that domain and a conditional forwarder for it exists.
AWS: Smithy — CreateTrust returns a TrustId; Trust$TrustState is the TrustState enum (Creating, Created, Verifying, VerifyFailed, Verified, Updating, UpdateFailed, Updated, Deleting, Deleted, Failed) and Trust$TrustStateReason is "The reason for the TrustState". Recorded behavior: CreateTrust between two Managed Microsoft AD directories that each hold a conditional forwarder for the other's domain leaves Creating for Created, VerifyTrust then takes it to Verified, and DeleteTrust takes it to Deleting/Deleted so DescribeTrusts stops reporting it and a repeat DeleteTrust is refused EntityDoesNotExistException with message "Trust: <TrustId> does not exist : RequestId: <RequestId>" (fixed text "Trust: ", " does not exist : RequestId: "; the trust id and request id are values from the request and the call). Whether a remote domain is reachable is a property of the DNS the directory is configured with, not of the domain's top-level label.
Emulator: the clock's trust transition classifies the remote domain purely by its last label — any domain under invalid, test, localhost or example settles on TrustState Failed with TrustStateReason "An internal service error has been encountered while creating the trust. Please retry the operation." — so a trust between two directories the emulator itself created with .test names, with CreateConditionalForwarder already called on both sides pointing at the other's DnsIpAddrs, never reaches Created. The check observes "trust entered failure state Failed".
Why: the whole trust state machine past Creating is unreachable in the emulator: Created, VerifyTrust→Verifying→Verified, DeleteTrust→Deleting→Deleted, the post-delete DescribeTrusts emptiness and the double-delete EntityDoesNotExistException can never be exercised, and a client that waits for Created (the documented pattern, since CreateTrust only "initiates the creation") is handed a terminal Failed with an internal-error reason it cannot act on. It also makes the emulator's own two-directory trust topology — the one AWS supports in a single VPC — impossible to model.
Fix: the trust state transition in the ds service state's advance_clock, and the reachability predicate it consults: a remote domain the store itself serves (a stored directory whose Name matches, or a conditional forwarder on the local directory for that domain) must settle on Created, with the reserved-top-level-domain shortcut applying only to domains nothing in the store can resolve.
Traces: ds.state-machine-trust-create-verify-delete-404 (AssertionError: trust entered failure state Failed). ds.e2e-trust-create-verify-delete-flow exercises the same lifecycle and will reach this cause once cause 1 is fixed. Citations: services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state.rs:3587-3597 (CREATING branch), :744-765 (TRUST_STATE_FAILED, TRUST_CREATE_FAILURE_REASON, NON_RESOLVABLE_TOP_LEVEL_DOMAINS), src/ops/create_trust.rs:304-308.
