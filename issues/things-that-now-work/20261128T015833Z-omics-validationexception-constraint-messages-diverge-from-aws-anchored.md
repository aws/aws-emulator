# omics ValidationException constraint messages diverge from AWS: anchored @pattern echoed, @range value echoed, enum set mis-ordered

> _Note: this issue was identified against the code base at commit `429bdfecbf56545571d755c8b6ad852b4e3ed1bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelRun

## Description
Three net-new root causes in the way the omics emulator RENDERS the message of a modelled constraint violation. In every case the HTTP status (400) and the error code (ValidationException) are already correct and only the message text diverges, but the message text is part of the requirement. All three live in the centralized deserialize/validate walk that refuses a request before any handler runs, not in the individual operation handlers — which is why one cause shows up across several operations at once. Each cause below must be closed on its own before submitting. The open issues 20261127T141502Z-omics-7-net-new-root-causes-read-set.md (handler-authored upload refusal prose), 20261029T184954Z-omics-4-net-new-root-causes-startrun-refuses.md, 20261124T224008Z-omics-tagresource-on-a-deleted-resource-s-arn.md, 20261124T171120Z-omics-getreadsetmetadata-returns-a-malformed-sequence-store-s3.md and 20261126T233811Z-omics-getreadset-serves-the-read-set-part-with.md are NOT these causes and do not cover them; neither do the open scaffold-stub issues (CancelRun, StartRunBatch, GetReadSet, AbortMultipartReadSetUpload, CreateReferenceStore, ListRunCaches), because these operations do answer and answer with the wrong text.

=== Cause 1 of 3: a @pattern violation echoes the regex WITH the model's ^...$ anchors, where AWS echoes it without them ===
AWS: the numeric-id members of this API are modelled with an anchored pattern -- Smithy: CancelRun.id -> RunId @required @httpLabel @length(1..18) @pattern "^[0-9]+$"; GetRun.id -> RunId, same constraints; CancelRunBatch.batchId -> BatchId @required @length(1..18) @pattern "^[0-9]+$"; GetBatch.batchId -> BatchId @required @httpLabel, same; every one of these operations declares ValidationException with httpError 400. Recorded behavior: the refusal is 400 ValidationException whose message is the template "1 validation error detected: Value '<value>' at '<member path>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>". The FIXED text is "1 validation error detected: Value '", "' at '", "' failed to satisfy constraint: Member must satisfy regular expression pattern: ". The VARIABLE parts are (a) the rejected value exactly as the request carried it, (b) the member path of the offending member, and (c) the pattern -- and the recording shows the pattern rendered WITHOUT the leading ^ and trailing $, i.e. "[0-9]+" for a member whose model pattern is "^[0-9]+$". AWS strips the anchors when it renders the constraint into the message.
Emulator: the pattern is copied verbatim out of the Smithy model, anchors included, so the message ends "... Member must satisfy regular expression pattern: ^[0-9]+$". Observed across four operations, all 400 -> 400 with only $.message differing: CancelRun and GetRun on id='abc123', CancelRunBatch and GetBatch on batchId='batch-abc' / 'not-a-number'.
Why: a client, SDK error handler, test fixture or runbook that matches, logs or displays this refusal's message sees a regex AWS never puts on the wire, and anything that re-uses the echoed pattern to build its own client-side check now carries anchors AWS did not advertise. The anchors also leak the emulator's model representation rather than the service's rendering.
Fix: the @pattern branch of the shared constraint-validation message formatter used by the centralized request walk (the component that composes "1 validation error detected: ..." before any operation's handle runs) -- it must render the constraint with the ^ / $ anchors stripped. Not a per-operation fix: the same formatter serves every pattern-constrained member of this service.
Traces: cancel-run-malformed-id-validation-rejected#task#1 (CancelRun), cancel-run-malformed-id-validation-rejected#task#4 (GetRun), omics-run-cancel-get-delete-refusals#task#4 (CancelRun, same cluster), omics-cancel-run-batch-malformed-and-unknown-batch-id#task#1 (CancelRunBatch), run-batch-and-configuration-unknown-id-not-found#task#2 (GetBatch).

=== Cause 2 of 3: a @range violation on an integer member echoes the rejected value, where AWS omits it ===
AWS: Smithy: GetReadSet.partNumber -> Integer @required @httpQuery("partNumber") @range(min 1, max 10000); UploadReadSetPart.partNumber -> Integer @required @httpQuery("partNumber") @range(min 1, max 10000); both operations declare ValidationException httpError 400. Recorded behavior: the refusal is 400 ValidationException whose message is the template "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must have value greater than or equal to <min>" (and the symmetric "... Member must have value less than or equal to <max>" for the upper bound). The FIXED text is "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must have value greater than or equal to " / "' failed to satisfy constraint: Member must have value less than or equal to "; the VARIABLE parts are the member path and the bound taken from the model's @range. Note what is NOT there: unlike the string-pattern form in Cause 1, this form carries NO rejected value -- it reads "Value at 'partNumber'", not "Value '0' at 'partNumber'".
Emulator: it uses the string form for integers too and interpolates the rejected number, producing "1 validation error detected: Value '0' at 'partNumber' failed to satisfy constraint: Member must have value greater than or equal to 1" and "1 validation error detected: Value '10001' at 'partNumber' failed to satisfy constraint: Member must have value less than or equal to 10000". Status 400 and code ValidationException are correct; only the inserted "'<n>' " diverges. The '0' and '10001' in those strings are values from the request filling the emulator's own template -- the defect is that the template has a value slot at all for a range violation.
Why: a caller matching the refusal text of an out-of-range part number never matches, and a caller that parses the message to recover which member failed now has to cope with a shape AWS does not emit. It also makes the two constraint classes indistinguishable, where AWS deliberately renders a numeric range violation without quoting the value.
Fix: the @range branch of the same shared constraint-validation message formatter -- a range violation must render the "Value at '<member>'" form with no value interpolated, while the @pattern/enum forms keep quoting the value.
Traces: omics-get-read-set-rejects-out-of-range-part-and-unknown-file#task#7 (GetReadSet partNumber below min; cluster also covers #task#8, #task#9, #task#10), omics-read-set-part-upload-refusals#task#5 (UploadReadSetPart partNumber above max; cluster also covers #task#6).

=== Cause 3 of 3: an enum violation lists the enum value set in the model's declaration order instead of the order AWS renders ===
AWS: Smithy: StartRunBatch.defaultRunSetting -> DefaultRunSetting @required, whose member logLevel targets RunLogLevel (a string enum, @length 1..64); StartRunBatch declares ValidationException httpError 400. Recorded behavior only for the ORDER: the refusal is 400 ValidationException with the template "1 validation error detected: Value '<value>' at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [<the enum's values, comma-space separated>]", and the recorded set for RunLogLevel is exactly "[ALL, FATAL, ERROR, OFF]". The fixed text is the sentence frame and the bracketed set; the variable parts are the rejected value and the dotted member path ("defaultRunSetting.logLevel" for a violation inside the nested structure, which the emulator already gets right).
Emulator: it renders the set in the order the Smithy model declares the enum, which for RunLogLevel is ["OFF", "FATAL", "ERROR", "ALL"], so the message ends "... enum value set: [OFF, FATAL, ERROR, ALL]" -- the right four values in the wrong order. Observed: expected "... Value 'VERBOSE' at 'defaultRunSetting.logLevel' failed to satisfy constraint: Member must satisfy enum value set: [ALL, FATAL, ERROR, OFF]", got the same sentence with "[OFF, FATAL, ERROR, ALL]".
Hypothesis: AWS renders the set from its internal enum constant order, which for this enum is not the order the published Smithy model lists, so the renderer cannot derive the sequence from the model's member order alone; the recorded order is the requirement.
Why: the message is a requirement, and any client, test or support tooling that asserts on or diffs the advertised value set sees a list AWS never emits; a caller that reads the bracketed set as the authoritative allowed-values list gets it in an order that will not match the service's.
Fix: the enum branch of the shared constraint-validation message formatter, plus the per-enum value ordering it reads for RunLogLevel -- the bracketed set must be emitted in the order AWS renders rather than in model declaration order.
Traces: omics-start-run-batch-member-constraint-validation-errors#task#2 (cluster also covers #task#4).
