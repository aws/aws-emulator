# cloudwatch: 3 net-new causes — the metric-math undefined-id ValidationError trailer carries an empty Request ID, a live band alarm never re-creates its deleted anomaly detector, and GetMetricData admits more than one Metrics Insights SELECT

> _Note: this issue was identified against the code base at commit `f2df981fb0c1f12eddc631127604ad1ca2a057a3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricAlarm

## Description
This issue bundles 3 net-new root causes, all in the cloudwatch (monitoring, 2010-08-01) emulator. Each is numbered below with its own failing check ids. All three must be closed before submitting.

Cause 1 of 3: the metric-math "ID not found" ValidationError message's backend trailer leaves its Request ID slot empty, although the very same response carries a request id.
AWS: Smithy (com.amazonaws.cloudwatch#GraniteServiceVersion20100801) declares only LimitExceededFault for PutMetricAlarm, so this refusal is recorded behavior only. When a PutMetricAlarm Metrics array contains an Expression referring to a query Id that is not defined in that same array, AWS refuses with HTTP 400 and Error.Code ValidationError, creates/changes no alarm, and the Error.Message is the template "Error in expression '<expression id>': ID '<undefined id>' not found (Service: AmazonCloudWatch; Status Code: 400; Error Code: ValidationException; Request ID: <this request's own id>; Proxy: null)". Fixed text: "Error in expression '", "': ID '", "' not found (Service: AmazonCloudWatch; Status Code: 400; Error Code: ValidationException; Request ID: ", "; Proxy: null)". Variable parts taken from the request and the response: the offending expression's Id, the undefined id named inside the expression, and the request id AWS also returns in ResponseMetadata.RequestId / x-amzn-requestid. Both failing checks derive the expected trailer from the request id the emulator itself returned, so no literal recorded id is required here.
Emulator: status 400, Error.Code ValidationError and every other part of the sentence are correct, but the trailer's request-id slot is empty — "... Error Code: ValidationException; Request ID: ; Proxy: null)" — while ResponseMetadata.RequestId on the same response is populated (a fresh uuid). The divergence is structural, not a per-run value difference: the field is blank for every such refusal.
Why: the message is a requirement of the error class, and this trailer is what AWS gives a caller to correlate a refusal with a support case or a log line. A client that parses the trailer reads an empty id, and a client comparing the trailer against the response's own request id (as both checks do) sees two different values from one response. Any code asserting on CloudWatch's wording for this error breaks.
Fix: the metric-math expression validation of PutMetricAlarm (the construction of the ValidationError message's backend trailer) — interpolate the request context's id, the same value the serializer puts in ResponseMetadata.RequestId. The trailer is shared by the whole metric-math refusal family, so fix it where the trailer is built rather than at one call site.
Traces: cloudwatch.alarm-math-and-anomaly-search-and-undefined-id-rejected (undefined-id case; its SEARCH refusals passed), cloudwatch.put-metric-alarm-update-rejected-leaves-prior-config-untouched (the same empty trailer on an update; the check's prior-config-untouched assertions were never reached).

Cause 2 of 3: a live ANOMALY_DETECTION_BAND alarm does not re-create the anomaly detector it references after DeleteAnomalyDetector, so the model stays gone.
AWS: Smithy models DeleteAnomalyDetector (errors InvalidParameterCombination, InvalidParameterValue, MissingRequiredParameter, ResourceNotFound 404) and DescribeAnomalyDetectors, but says nothing about re-creation, so this is recorded behavior only, matching the anomaly-detection documentation (https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Create_Anomaly_Detection_Alarm.html): deleting an anomaly detection model that an alarm still references is not durable — within roughly a minute the alarm's evaluator re-creates a detector for its own metric/stat, and DescribeAnomalyDetectors lists it again; a detector referenced by no alarm, deleted in the same breath, stays deleted. The alarm itself stays OK across the delete/re-create.
Emulator: DeleteAnomalyDetector succeeds for both the alarm-referenced detector (metric X) and the unreferenced control (metric Y), and DescribeAnomalyDetectors then serves an empty AnomalyDetectors list for the namespace and keeps serving it for the whole 240 s window while metric data continues to be published — the check's last observation is {}. The referenced detector never comes back, so the out-of-band ALARM phase that depends on the re-created model is never reached.
Why: a client relying on AWS's behavior believes an alarm's model is self-healing: deleting a detector by mistake, or deleting detectors as a cleanup step while alarms live on, leaves the alarm working on AWS. Against the emulator the alarm is permanently de-modelled, so band thresholds and any ALARM/OK verdicts derived from them silently stop tracking the series, and tooling that reconciles DescribeAnomalyDetectors against alarm definitions reports a detector that AWS would have restored as missing forever.
Fix: the alarm evaluator's anomaly-detector state — when evaluating an alarm whose ThresholdMetricId resolves to an ANOMALY_DETECTION_BAND expression, ensure the detector for that metric/stat exists (re-create it if absent) and keep its presence visible to DescribeAnomalyDetectors; detectors no alarm references must not be re-created.
Traces: cloudwatch.anomaly-band-alarm-cites-band-high-recreates-its-deleted-detector-and-fires-out-of-band (its in-band phase — OK state, band served by GetMetricData, cited upper threshold equal to the band High — passed).

Cause 3 of 3: GetMetricData accepts two Metrics Insights SELECT queries in one request instead of refusing the request.
AWS: Smithy models GetMetricData with MetricDataQueries required and declares only InvalidNextToken, so this refusal is recorded behavior only. A GetMetricData request may contain at most ONE Metrics Insights query (a MetricDataQuery whose Expression is a SELECT statement), beside any number of MetricStat and metric-math entries. A request carrying two SELECT expressions is refused with HTTP 400, Error.Code ValidationError and the message "Maximum number of queries (1) exceeded" — fixed text whose only variable part is the per-request SELECT quota (1) — and no MetricDataResults are returned.
Emulator: the request SUCCEEDS with HTTP 200 and both SELECTs are evaluated, returning MetricDataResults for q1 and q2 (StatusCode Complete for each) and an empty top-level Messages list. The limit is not enforced anywhere in GetMetricData's input validation.
Why: a client that batches Insights queries is told by AWS to split them into separate requests; against the emulator it gets answers for all of them, so code written and tested against the emulator fails the moment it runs on AWS — exactly the direction of divergence an emulator must not have. There is also no error to drive a client's split-and-retry path. Because the check stops at this unraised refusal, two further behaviors in the same operation were never exercised and may be broken the same way: one SELECT beside a MetricStat and a math expression must return all three rows (q=36, m=6, e=12), and a 20-day SELECT window must come back with exactly one top-level message {Code: MaxQueryTimeRangeExceeded, Value: "Max time window exceeded for query"} while a 1-day SELECT and a 20-day MetricStat-only request carry none.
Fix: GetMetricData's input validation (count the MetricDataQueries entries whose Expression is a Metrics Insights SELECT and refuse before any query is executed), not its evaluator or serializer.
Traces: cloudwatch.get-metric-data-insights-select-aggregates-per-group-and-admits-one-query (its per-group SUM/AVG/COUNT aggregation, SCHEMA dimension scoping and ORDER BY ... LIMIT assertions all passed before this point).
