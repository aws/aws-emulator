# EKS add-on, cluster-version and configuration-schema catalogs diverge from AWS reference data (6 causes)

> _Note: this issue was identified against the code base at commit `0e97705e9904239bd55bed92c4be71546a783c93`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAddonVersions

## Description
SIX net-new root causes share one fault: the read-only EKS catalogs (DescribeAddonVersions, DescribeClusterVersions, DescribeAddonConfiguration) are backed by emulator-authored reference data rather than the catalog AWS publishes. Every one of the six answers HTTP 200 with a well-formed envelope, so no status or error code is at issue — the payload content is. All six must be closed before this issue is resubmitted.

Related OPEN issues that do NOT cover these clusters (the replay reports every cluster below as owned by none of them; each is named here only so a fixer can see the family): '20261102T083656Z-eks-add-on-and-cluster-version-catalogs-serve.md' (wrong version records for add-ons already in the catalog, plus DescribeAddonConfiguration mis-routing), '20261109T131212Z-eks-describeaddonversions-catalog-omits-further-marketplace-add-ons.md' (the task#35/#37 Marketplace cluster of the same fixture), '20261029T185333Z-eks-read-only-catalogs-serve-incomplete-static-data.md', '20261104T053622Z-eks-responses-omit-fields-aws-returns-cluster-vendedlogs.md' and '20261104T105252Z-eks-2-net-new-root-causes-the-metrics.md' (the metrics-server schema). A resolved or similar-looking issue does not cover these replay units.

Cause 1 of 6: a DescribeAddonVersions read whose filter selects an add-on AWS publishes answers 200 with NO entry at that position at all — the add-on is simply absent from the emulator's catalog.
  AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json) DescribeAddonVersions GET /addons/supported-versions, success 200, output DescribeAddonVersionsResponse.addons -> Addons (list of AddonInfo) + nextToken; paginated (inputToken nextToken / outputToken nextToken / items addons / pageSize maxResults); httpQuery filters addonName, types, publishers, owners, kubernetesVersion, maxResults, nextToken; errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500. AddonInfo = addonName, type, addonVersions (AddonVersionInfoList), publisher, owner, marketplaceInformation, defaultNamespace. AddonVersionInfo = addonVersion, architecture, computeTypes ("Indicates the compute type of the add-on version"), compatibilities (one Compatibility per supported Kubernetes minor: clusterVersion, platformVersions, defaultVersion), requiresConfiguration (@default false), requiresIamPermissions (@default false). The rule: a read that matches an add-on in AWS's catalog returns that add-on's AddonInfo, fully populated. Recorded behavior for the specific entry: the catalog contains the observability add-on 'adot', whose newest version carries architecture ['amd64','arm64'], computeTypes ['ec2','hybrid','fargate','auto'], one compatibilities entry per currently-supported minor with defaultVersion true on the newest and false on the superseded ones, and requiresIamPermissions true.
  Emulator: 200 with the addons list empty for that read — $.addons[0] is absent (got None).
  Why: a client that discovers add-ons, or version-pins one before CreateAddon/UpdateAddon, sees an add-on AWS offers as nonexistent. Every downstream choice keyed to the catalog (addonVersion, computeTypes, compatibilities, requiresConfiguration, requiresIamPermissions) cannot be made at all, and a conditional install keyed on "is this add-on available" takes the wrong branch forever.
  Fix: the static add-on catalog seed behind DescribeAddonVersions in the eks service crate, and the addonName/types/publishers/owners filter paths that project it. Not the serializer — the envelope and status are already correct.
  Traces: eks-catalog-describe-addon-versions-accuknox-kubearmor-eg-innovations-eg-universal-agent-operator#task#2 (representative; the cluster covers 72 steps across that fixture and eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni).

Cause 2 of 6: where a Marketplace/partner add-on IS in the catalog, the AddonInfo served for it is invented — its version list, per-version computeTypes, per-minor compatibilities and defaultVersion flags do not match AWS's, and marketplaceInformation.productUrl is wrong.
  AWS: as cited in cause 1; MarketplaceInformation carries productId and the product URL from the AWS Marketplace listing. The rule: for a Marketplace-owned add-on, owner/publisher plus marketplaceInformation.productId and productUrl identify the real listing, and each AddonVersionInfo enumerates the versions AWS actually offers with the architectures, computeTypes and per-minor compatibilities of that version. Recorded behavior for the specific entry: the security add-on 'accuknox_kubearmor' (publisher AccuKnox, owner aws-marketplace, defaultNamespace kubearmor) is served with a version whose computeTypes is ['ec2'] and whose compatibilities span the minors that version supports, each flagged defaultVersion true, and with the productUrl of that Marketplace listing.
  Emulator: 200 with an AddonInfo for the same addonName whose addonVersions are a generated ladder (versions AWS does not publish for it, each carrying only architecture and two synthetic compatibilities entries pinned to the two newest minors, with defaultVersion true on exactly one), with computeTypes omitted from every version, and with a marketplaceInformation.productUrl that is not that listing's URL.
  Why: a caller that picks a version from the catalog then calls CreateAddon with a version AWS does not offer, or filters by compute type and discards every version because computeTypes is absent; a subscriber that follows productUrl to accept the seller EULA — the step that gates a Marketplace install — is sent to the wrong product page.
  Fix: the same static add-on catalog seed and its marketplaceInformation records; the per-version fields (computeTypes, compatibilities, defaultVersion) must come from the catalog data, not be synthesized from the cluster-version ladder.
  Traces: eks-catalog-describe-addon-versions-accuknox-kubearmor-eg-innovations-eg-universal-agent-operator#task#1 (cluster covers 15 steps across that fixture and eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni).

Cause 3 of 6: DescribeClusterVersions returns a cluster-version catalog that matches AWS at no index — every entry of the list diverges.
  AWS: Smithy DescribeClusterVersions GET /cluster-versions, success 200, output clusterVersions -> ClusterVersionList + nextToken, paginated; httpQuery filters clusterType, clusterVersions, defaultOnly, includeAll, status (deprecated, replaced by versionStatus), versionStatus, maxResults @range 1..100; errors InvalidParameterException 400, InvalidRequestException 400, ServerException 500. ClusterVersionInformation = clusterVersion, clusterType, defaultPlatformVersion, defaultVersion (@default false), releaseDate, endOfStandardSupportDate, endOfExtendedSupportDate, status (deprecated enum), versionStatus, kubernetesPatchVersion, controlPlaneScalingTiers (@length 0..10) and controlPlaneComponentConfig ("the default control plane component configuration and constraints for this Kubernetes version"). The rule: an unfiltered read enumerates the Kubernetes versions EKS supports, each with its clusterType, default platform version, support-lifecycle dates, versionStatus, patch version, and the scaling tiers and component-config constraints published for that version.
  Emulator: 200 with a clusterVersions list in which no element matches the catalog — the representative step reports $.clusterVersions[0] through $.clusterVersions[14] all diverging, including the entries' controlPlaneScalingTiers (tier names with apiRequestConcurrency, podSchedulingRatePerSecond, clusterDatabaseSizeGb and controlPlaneComponentConfigOverrides) and the support-lifecycle timestamps.
  Why: anything that reads this catalog to choose a cluster version, to plan an upgrade against end-of-standard/extended-support dates, or to size a provisioned control plane from the scaling tiers acts on fabricated data: an upgrade planner computes wrong deadlines and a sizing step picks a tier with wrong concurrency and scheduling-rate capabilities.
  Fix: the static cluster-version catalog seed behind DescribeClusterVersions in the eks service crate, including the per-version controlPlaneScalingTiers and controlPlaneComponentConfig records. The dates and tier numbers are reference data, not per-run values.
  Traces: eks-catalog-describe-cluster-versions#task#1.

Cause 4 of 6: for an EKS-owned add-on the catalog does serve, the version records themselves are wrong (and a Marketplace sibling's productUrl with them).
  AWS: as cited in cause 1. The rule: each AddonVersionInfo for an add-on lists an actually-offered addonVersion with its architecture, computeTypes and one compatibilities entry per supported minor, with defaultVersion marking the version AWS defaults to for that minor. Recorded behavior for the specific entry: the storage add-on 'aws-efs-csi-driver' is served with its real version ladder, each version carrying computeTypes ['ec2','auto'] and compatibilities across the supported minors, the newest marked defaultVersion true per minor and the superseded ones false.
  Emulator: 200 with an entry for the same addonName whose addonVersions are generated (version strings and per-minor compatibilities AWS does not publish, computeTypes missing, defaultVersion flags set from the synthetic ladder), and with $.addons[3].marketplaceInformation.productUrl diverging from the recorded listing URL.
  Why: a client that reads the catalog to find the default version for its cluster's minor installs a version that does not exist, and CreateAddon/UpdateAddon version negotiation built on this catalog can never agree with AWS.
  Fix: same static add-on catalog seed; the add-on's version records and the Marketplace entries' productUrl.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#8.

Cause 5 of 6: DescribeAddonConfiguration serves a configurationSchema that is not the schema document AWS publishes for that add-on version, and omits a podIdentityConfiguration entry.
  AWS: Smithy DescribeAddonConfiguration GET /addons/configuration-schemas, success 200, required httpQuery members addonName and addonVersion; output addonName, addonVersion, configurationSchema (string) and podIdentityConfiguration -> AddonPodIdentityConfigurationList, whose AddonPodIdentityConfiguration carries serviceAccount ("the Kubernetes Service Account name used by the add-on") and recommendedManagedPolicies ("a suggested IAM Policy for the add-on"); errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500. The rule: the response returns the JSON-Schema document that governs that add-on version's configurationValues, and one podIdentityConfiguration element per service account the add-on uses. Recorded behavior for the specific entry: for the EFS CSI driver the schema is a draft/2019-09 document ("$schema":"https://json-schema.org/draft/2019-09/schema", additionalProperties false) describing the controller and node property objects (logLevel with maximum 6/minimum 0, nodeSelector, podAnnotations, tolerations), replicaCount, deleteAccessPointRootDir and useFIPS; and the add-on reports more than one podIdentityConfiguration element.
  Emulator: 200 with a configurationSchema that is a different document entirely (it begins "$schema":"http://json-schema.org/draft-06/schema#" with a $ref-based definition tree), and with $.podIdentityConfiguration[1] absent.
  Why: a caller that validates its configurationValues against the returned schema accepts configuration AWS rejects and rejects configuration AWS accepts — in particular the add-on's real knobs (here the FIPS and access-point switches) are not describable at all; and a caller that provisions pod-identity associations from podIdentityConfiguration creates fewer service-account/role pairs than the add-on needs, so the add-on comes up without the permissions it requires.
  Fix: the per-add-on-version configuration-schema and pod-identity reference data behind DescribeAddonConfiguration in the eks service crate — the schema documents must be the published ones, not a generic generated schema, and the podIdentityConfiguration list must be complete.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#1.

Cause 6 of 6: the same configurationSchema substitution on a core EKS add-on.
  AWS: as cited in cause 5. Recorded behavior for the specific entry: the VPC CNI add-on's configurationSchema is the published VpcCni document ({"$ref":"#/definitions/VpcCni","$schema":"http://json-schema.org/draft-06/schema#", definitions Affinity / EniConfig / Env ...), whose Env definition enumerates the driver's supported environment variables with their formats and whose EniConfig definition declares create/region/subnets with subnets required.
  Emulator: 200 with a configurationSchema whose content differs from that document, so the typed properties a client configures the add-on through are not the ones AWS declares.
  Why: identical to cause 5 — client-side validation of configurationValues is performed against a schema AWS does not serve, so a configuration the emulator blesses is refused by AWS and vice versa.
  Fix: the same per-add-on-version configuration-schema reference data; this add-on's published schema document must be stored and returned verbatim.
  Traces: eks-eks-catalog-read-only-discovery#task#3.

Note on values: the concrete add-on names, version strings, Kubernetes minors, product URLs, timestamps and tier numbers quoted above are the recording's EXAMPLES of the requirement (the catalogs must serve the add-ons, versions, support dates, scaling tiers and schema documents AWS publishes). They are reference data to seed, not literals to hard-code per run.
