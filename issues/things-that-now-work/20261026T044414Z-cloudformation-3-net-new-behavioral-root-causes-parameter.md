# cloudformation: 3 net-new behavioral root causes — Parameter constraints (AllowedPattern/MinLength/MaxLength/Number range), missing-required and undeclared ParameterKey are never enforced at CreateStack, and GetTemplateSummary omits ResourceIdentifierSummaries and de-duplicates ResourceTypes

> _Note: this issue was identified against the code base at commit `d20f3863f60340619cdbd48f5982ebeef462a933`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Three distinct net-new root causes in the bootstrapped `cloudformation` service, all grounded in failing behavioral checks of this suite. None of the three is marked ALREADY FILED or OWNED in the replay report. A fixer must close ALL THREE before submitting.

Cause 1 of 3: the declared `Parameters` constraints are not enforced at CreateStack — every violating value is accepted with HTTP 200 and a StackId.
AWS: Smithy (com.amazonaws.cloudformation#CreateStack) takes `Parameters` (list of Parameter) and models AlreadyExistsException / InsufficientCapabilitiesException / LimitExceededException / TokenAlreadyExistsException; the parameter-constraint refusal is CloudFormation's common `ValidationError` (HTTP 400, awsQuery error code `ValidationError`), and the call leaves NO stack behind. Every constraint a parameter declaration states is a gate: `AllowedPattern`, `MinLength`, `MaxLength`, `Type: Number` with `MinValue`/`MaxValue`, plus a parameter with no `Default` that the request omits, and a `ParameterKey` the template does not declare. The refusal messages are templates whose fixed text is AWS's and whose variable parts come from the request and the template:
  * pattern/length violation — fixed text `Parameter <ParameterKey> failed to satisfy constraint: ` followed by the template's own `ConstraintDescription` (here `lowercase, digits and dashes, 3-20 chars`). `<ParameterKey>` is the declared key from the template; the trailing clause is the template's `ConstraintDescription` verbatim. The same single message covers AllowedPattern, MinLength and MaxLength when a `ConstraintDescription` is declared.
  * below `MinValue` — fixed text `Parameter '<ParameterKey>' must be a number not less than <MinValue>`; `<ParameterKey>` and `<MinValue>` are taken from the declaration.
  * above `MaxValue` — fixed text `Parameter '<ParameterKey>' must be a number not greater than <MaxValue>`.
  * non-numeric value for `Type: Number` — fixed text `Parameter '<ParameterKey>' must be a number.` (trailing period is part of the fixed text).
  * required parameter not supplied — fixed text `Parameters: [` + the comma-separated missing keys + `] must have values`.
  * undeclared `ParameterKey` supplied — fixed text `Parameters: [` + the comma-separated undeclared keys + `] do not exist in the template`.
Emulator: the FIRST violating leg already succeeds. `CreateStack` with `Slug="Invalid-Slug"` against a declaration of `AllowedPattern: ^[a-z0-9-]+$` / `MinLength: 3` / `MaxLength: 20` returned HTTP 200 with a `StackId` and an `OperationId` instead of raising ValidationError, so the remaining legs (MinLength, MaxLength, Number range, Number typing, missing required, undeclared key) were never reached. The positive-control legs of the same check pass: `GetTemplateSummary` already reports the declarations correctly (`ParameterType: Number`, `NoEcho: true`), a conforming create deploys to CREATE_COMPLETE, `Fn::Sub` renders `valid-slug/7` into the SSM parameter, and the NoEcho value does not leak into the event stream — so the gap is specifically the ENFORCEMENT of the declared constraints against the supplied values, not the reading of the declarations.
Why: parameter validation is the first gate every deployment passes through. A client that treats a 200 + StackId as "this template and these values are valid" deploys a stack real CloudFormation would have refused outright, and the bad value is then substituted into resource properties (here it renders straight into an SSM parameter's Value), so the only symptom is a wrong resource rather than a refusal. CI gates that assert "this invalid value is rejected" pass vacuously, and a stack is left behind for every call that was supposed to create nothing.
Fix: a parameter-resolution/validation stage in the CreateStack handler (and the matching UpdateStack / CreateChangeSet paths), run against the declarations the template reader already produces, raising `ValidationError` 400 with the message templates above and creating no stack. The declarations it must check against are already parsed — `crate::state::template::DeclaredParameter` carries `declared_type`, `default` and `allowed_values` but no pattern/length/range fields, so the reader needs those members too. The open issue 20261025T015306Z-cloudformation-accepts-templates-and-requests-that-real-aws.md covers a DIFFERENT set of template-validation gaps (dependency cycles, the 200-parameter count limit, CAPABILITY_AUTO_EXPAND, malformed JSON, Fn::FindInMap, Fn::ForEach, LanguageExtensions, Rules, Conditions, unresolvable Outputs); it does NOT cover per-parameter constraint enforcement and does not carry this check's replay key.
Traces: cloudformation.parameter-constraint-violations-rejected.

Cause 2 of 3: GetTemplateSummary de-duplicates `ResourceTypes`, so it reports fewer entries than the template declares resources.
AWS: Smithy GetTemplateSummary output member `ResourceTypes` targets the list `ResourceTypes`, documented as "A list of all the template resource types that are defined in the template". Recorded behavior (measured on real AWS): the list is ONE ENTRY PER RESOURCE and is NOT deduplicated — a template declaring two `AWS::SSM::Parameter` resources reports `AWS::SSM::Parameter` twice — so it is a multiset of the template's resource types whose length equals the number of declared resources. Its order is not a documented guarantee.
Emulator: for a template declaring four resources of three distinct types (`Param`/`Second`: AWS::SSM::Parameter, `Queue`: AWS::SQS::Queue, `Topic`: AWS::SNS::Topic) the response carried three entries, `['AWS::SNS::Topic', 'AWS::SQS::Queue', 'AWS::SSM::Parameter']`, where AWS carries four, `['AWS::SNS::Topic', 'AWS::SQS::Queue', 'AWS::SSM::Parameter', 'AWS::SSM::Parameter']`.
Why: a client that counts `len(ResourceTypes)` to answer "how many resources does this template create" under-reports whenever any type repeats, which is the common case; the number then disagrees with `ListStackResources` and with the stored template for the same stack, so the three views of "which resources" no longer reconcile and the count read off one response is not the count read off another.
Fix: the resource-type projection behind GetTemplateSummary's `resource_types` — it must emit one entry per declared `Resources` entry rather than a set of distinct types.
Traces: cloudformation.ec2mr-cfnres-template-summary-matches-resource-set.

Cause 3 of 3: GetTemplateSummary never reports `ResourceIdentifierSummaries` — the member is always absent.
AWS: Smithy GetTemplateSummary output member `ResourceIdentifierSummaries` targets the list `ResourceIdentifierSummaries`, documented as "A list of resource identifier summaries that describe the target resources of an import operation and the properties you can provide during the import to identify the target resources. For example, BucketName is a possible identifier property for an AWS::S3::Bucket resource." Each entry carries `ResourceType` and `LogicalResourceIds`, and the entries GROUP logical ids BY TYPE: a template with two `AWS::SSM::Parameter` resources yields ONE entry for that type whose `LogicalResourceIds` holds both ids, so the total number of indexed logical ids equals the number of declared resources. The member is reported for a stack whose create is still in flight too: the TEMPLATE view holds every DECLARED resource even while the live resource view does not yet list a resource CloudFormation has not started.
Emulator: the member is unconditionally absent from every GetTemplateSummary response, so a client reading it raises `KeyError: 'ResourceIdentifierSummaries'`. The handler sets it to `None` by design, on the stated ground that the emulator's resource-type catalogue carries no published primary identifiers — but AWS populates `ResourceType` + `LogicalResourceIds` from the TEMPLATE alone, which this service already parses; only the optional per-type identifier-property detail needs a catalogue, and omitting the whole member is not the same as omitting that detail.
Why: any client that reads the type-to-logical-id index — resource-import tooling, which the member exists for, and anything reconciling "which resources does this template declare" against the live stack — gets a hard key error rather than a list, and the mid-create disagreement between the template view and the resource view (the template still declares a resource the stack has not started) becomes unobservable. Note the same check's mid-create assertions all PASS: the stack correctly OMITS the unstarted `Blocked` resource from ListStackResources, reports the in-flight WaitCondition as CREATE_IN_PROGRESS with `ResourceStatusReason: "Resource creation Initiated"`, carries no reason on the settled resource, and refuses `DescribeStackResource` for the unstarted logical id with `ValidationError` / `Resource <LogicalResourceId> does not exist for stack <StackName>`. The only divergence is the absent member.
Fix: populate `ResourceIdentifierSummaries` in the GetTemplateSummary handler from the parsed template's `Resources` section, one entry per distinct resource type with that type's logical ids collected into `LogicalResourceIds`.
Traces: cloudformation.ec2mr-cfnres-in-progress-stack-omits-unstarted-resource.
