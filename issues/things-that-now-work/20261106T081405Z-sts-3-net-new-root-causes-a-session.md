# sts: 3 net-new root causes — a session from a DELETED role is refused AccessDenied instead of InvalidAccessKeyId, matched explicit Denies are reported with the implicit-deny message, and a source-identity trust refusal names sts:AssumeRole instead of sts:SetSourceIdentity

## Operation
AssumeRole

## Description
THREE net-new root causes in the STS service (service token `sts`), grounded in 4 failing behavioral checks under the suite heading `sts`. None of the 4 is marked ALREADY FILED or OWNED in the replay report. All three causes must be closed before submitting.

=== Cause 1 of 3: credentials minted from a role that has since been deleted still resolve, and are refused at the AUTHORIZATION stage instead of at credential resolution ===
AWS: a temporary session's identity is the role's RoleId, not its name (Smithy: com.amazonaws.sts#AssumeRole -> AssumeRoleResponse.Credentials + AssumedRoleUser; the condition/credential-resolution behaviour itself is recorded behavior only, no modeled member carries it). Once the role is deleted, the access key id in that session no longer resolves to any principal, so the called service refuses BEFORE any policy is consulted: S3 answers HTTP 403 with error code `InvalidAccessKeyId` and the message `The AWS Access Key Id you provided does not exist in our records.` — that sentence is entirely FIXED text, it carries no request or state values. Recreating the role under the same name with byte-identical policies does NOT revive the old session (new RoleId, same ARN), while a session assumed from the recreated role reads normally.
Emulator: the call is refused, but with error code `AccessDenied` — the authorization-stage verdict — so the key is still being resolved to a live principal and only the grant is missing. The check's own words: "a session issued from a role that has since been deleted must be rejected with InvalidAccessKeyId -- at credential resolution, before any policy is consulted; got 'AccessDenied'".
Why: the two codes mean opposite things to a client. `InvalidAccessKeyId` is terminal and tells an SDK/credential provider to stop using and refresh the credential; `AccessDenied` reads as a policy problem on a credential that is still believed valid, so retry/refresh logic keeps the dead session in rotation and an operator hunting a permissions bug never learns the role is gone. It also hides the role-identity-is-the-RoleId guarantee: a by-name recreation would appear to restore access.
Fix: the credential-resolution step shared by the data-plane handlers (resolve-the-signing-key path for session credentials) — a session whose role no longer exists (or whose recorded RoleId no longer matches the role at that ARN) must fail resolution and the called service must serialize HTTP 403 / `InvalidAccessKeyId` / the fixed sentence above, ahead of any policy evaluation.
Traces: sts.deleting-the-role-invalidates-credentials-already-issued-and-recreating-it-by-name-does-not-restore-them.

=== Cause 2 of 3: a refusal decided by a MATCHED explicit Deny is worded with the implicit-deny (no-grant) clause, and the policy SOURCE is never named ===
AWS: recorded behavior only for the message framing (no modeled error member carries it; S3 serializes the code in its REST-XML body with HTTP 403). AWS words an authorization refusal with one of three mutually exclusive diagnoses, and the trailing clause IS the diagnosis: ` with an explicit deny in an identity-based policy` when a Deny statement in an identity-based document (inline/attached role or user policy) decided it; ` with an explicit deny in a session policy` when the deciding Deny came from the session policy passed in `Policy=` (Smithy: AssumeRole.Policy / GetFederationToken.Policy, sessionPolicyDocumentType); and ` because no identity-based policy allows the <action> action` ONLY when nothing granted the action. The fixed text is `User: `, ` is not authorized to perform: `, ` on resource: `, the double quotes around the resource, and the chosen trailing clause; the variable parts are the caller ARN (an assumed-role session ARN `arn:aws:sts::<account>:assumed-role/<role>/<session>` or a federated-user ARN `arn:aws:sts::<account>:federated-user/<name>`), the action (`s3:GetObject`), and the object ARN built from the request. Unicode in the resource is immaterial: a Deny whose Resource ARN carries accented-Latin/CJK object-key bytes must match that exact key and leave a sibling ASCII key readable.
Emulator: the status (403) and code (`AccessDenied`) are right and the refusal does now arrive, but the message always ends `because no identity-based policy allows the s3:GetObject action`, for both deciding sources. Observed on (a) a GetFederationToken session policy of [Allow s3:GetObject on `arn:aws:s3:::<bucket>/*`, Deny s3:GetObject on `arn:aws:s3:::<bucket>/café/日本語/Zürich-résumé.txt`] — expected tail ` with an explicit deny in a session policy`; and (b) an inline ROLE policy Deny `*`/`*` under `DateLessThan {aws:TokenIssueTime: <cut-off>}` (the AWSRevokeOlderSessions shape) refusing an already-issued session — expected tail ` with an explicit deny in an identity-based policy`. Caller ARN, action and quoted resource ARN all match in both; only the diagnosis clause (and with it the policy source) diverges.
Why: that clause is the entire remediation signal. Told "no identity-based policy allows" the action, a caller or its tooling hunts a missing Allow that is already present and never finds the Deny it must satisfy; policy-troubleshooting flows, runbooks and log alerts keyed on AWS's three forms draw the opposite conclusion, and a client can no longer tell an explicit deny from an un-granted action, nor a session-policy deny from an identity-policy one. Adjacent OPEN issues, neither of which covers these two check ids: 20261106T072814Z-iam-s3-sts-2-root-causes-an-aws.md (same classification defect reported for the identity-policy form under the `iam__s3__sts` heading — if it is fixed in the shared evaluator, re-replay these ids too, but the session-policy variant here is additional), and 20261025T131636Z-sts-session-revocation-is-a-no-op-an.md (a different corpus; it describes check (b) FAILING OPEN, the revoked session still being SERVED — that is no longer true in this run: the session is now refused AccessDenied and only the deny classification is wrong, so the divergence filed here is the current, narrower one).
Fix: the refusal-message construction in the request-authorization gate shared by the data-plane handlers — the evaluation already knows which statement decided the request and which document it came from, and the message must carry that: emit ` with an explicit deny in an identity-based policy` / ` with an explicit deny in a session policy` when a Deny decided it, reserving the `because no identity-based policy allows the <action> action` form for the no-grant case.
Traces: sts.get-federation-token-policy-document-unicode-round-trip (session-policy form), sts.in-flight-session-denied-after-a-revoke-older-sessions-policy-is-attached-to-the-role (identity-policy form).

=== Cause 3 of 3: a chained AssumeRole refused by an unsatisfied sts:SourceIdentity trust condition names sts:AssumeRole as the action instead of sts:SetSourceIdentity ===
AWS: SourceIdentity carries over a role chain (Smithy: AssumeRoleRequest.SourceIdentity, sourceIdentityType @length 2..64 @pattern `^[\w+=,.@-]*$`, echoed as AssumeRoleResponse.SourceIdentity). When the next role's trust policy conditions on `sts:SourceIdentity` and the calling session's carried value does not satisfy it, the refusal is `AccessDenied` naming the SetSourceIdentity action, not AssumeRole: `User: <calling session ARN> is not authorized to perform: sts:SetSourceIdentity on resource: <target role ARN>` (ref: https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html). Fixed text: `User: `, ` is not authorized to perform: sts:SetSourceIdentity on resource: `; variable parts: the calling assumed-role session ARN and the target role ARN, both from the request/state. Recorded behavior for the exact sentence; the action name is what AWS uses because the condition gates the source-identity SET, not the assume itself.
Emulator: same status and code, but the message names the wrong action — `User: arn:aws:sts::<account>:assumed-role/<roleA>/<session> is not authorized to perform: sts:AssumeRole on resource: arn:aws:iam::<account>:role/<roleB>`. The neighbouring legs pass (a conflicting SourceIdentity mid-chain is ValidationError with `The source identity is already set for this assume role session`, and the code here is AccessDenied), so only the action token in the message diverges.
Why: a caller debugging a source-identity guardrail is told the principal cannot assume the role at all and goes looking at the AssumeRole statement in the trust policy, when the blocked permission is the sts:SetSourceIdentity grant/condition; CloudTrail-style and log-scraping flows that key on the action in the refusal attribute the denial to the wrong permission entirely.
Fix: the AssumeRole handler's trust-policy evaluation and its refusal-message construction — when the deciding statement is the one gating `sts:SetSourceIdentity` (a trust-policy condition on `sts:SourceIdentity` that the carried value fails), the message's action must be `sts:SetSourceIdentity`.
Traces: sts.role-chain-with-a-conflicting-source-identity-denied-and-the-matching-one-permitted.
