# CloudWatch Enable/DisableInsightRules refuse the whole batch instead of reporting per-item Failures: a pattern-violating RuleNames member answers 400 ValidationError and an empty-string member answers 400 MissingParameter (2 causes)

> _Note: this issue was identified against the code base at commit `c9b3683fb3b4c78663b901b146c2331c62479a92`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
EnableInsightRules

## Description
REOPENS 20261027T074335Z-cloudwatch-contributor-insights-batch-failures-are-misclassified-disable.md: its fix left the call refused. That issue's cause 1 claimed to fix the per-item (PartialFailure) loop of DisableInsightRules and EnableInsightRules so that an unknown-but-well-formed rule name is reported as ExceptionType 'ResourceNotFoundException' / FailureCode 'RULE_NAME' on an HTTP 200. For the three checks below that per-item loop is never reached at all: as soon as the batch also contains a member that violates InsightRuleName's pattern, or a member that is the empty string, the emulator refuses the ENTIRE request with a 400 before any rule is looked up, so neither the promised ResourceNotFoundException entry nor the enable/disable of the valid rules in the same batch is observable. Two distinct refusal paths do this and both must be closed before this issue is submitted; each cause names its own failing check ids.

Also related, and NOT a substitute for this issue: open issue 20261027T005601Z-cloudwatch-6-net-new-root-causes-putmetricdata-s.md records the pattern-refusal as its cause 2, but its registered replay key is 'cloudwatch|EnableInsightRules|ValidationException' and the emulator now answers error code 'ValidationError' (and renders the pattern unanchored), so that key no longer joins and the replay report marks none of these three checks OWNED. Open issue 20261029T182452Z-cloudwatch-request-validation-and-error-envelope-divergences-10.md covers the generic ValidationError envelope for other cloudwatch operations; it does not carry these check ids and does not say that these two operations must not run model-constraint validation on RuleNames at all.

==================================================================
Cause 1 of 2: a RuleNames member that violates InsightRuleName's @pattern makes Enable/DisableInsightRules refuse the whole batch with an unmodeled 400 ValidationError, instead of answering 200 and reporting that member as a per-item PartialFailure.
Failing check ids: cloudwatch.disable-insight-rules-and-malformed-name-reported-as-failure-entry, cloudwatch.enable-insight-rules-and-malformed-name-reported-as-failure-entry

AWS: Smithy (com.amazonaws.cloudwatch#GraniteServiceVersion20100801) models DisableInsightRules and EnableInsightRules with input RuleNames (@required, target InsightRuleNames, a list whose member targets InsightRuleName with @length min 1 max 128 and @pattern ^[\x20-\x7E]+$) and output Failures -> BatchFailures, a list of PartialFailure{FailureResource, ExceptionType, FailureCode, FailureDescription}. The PartialFailure shape documentation is the contract: 'This array is empty if the API operation was successful for all the rules specified in the request. If the operation could not process one of the rules, the following data is returned for each of those rules.' Modeled errors are InvalidParameterValueException (client, httpError 400, awsQueryError InvalidParameterValue) and MissingRequiredParameterException (400, awsQueryError MissingParameter), plus LimitExceededException (400) on EnableInsightRules — 'ValidationError'/'ValidationException' is NOT a modeled error of either operation. Recorded behavior (both checks' real-AWS replays): a batch of [<an existing rule>, <a well-formed name that names no rule>, <a name containing the ASCII control character \x01>] answers HTTP 200; the existing rule's State flips (DISABLED for Disable, ENABLED for Enable, readable via DescribeInsightRules); and Failures[] carries exactly two entries, independently classified — the well-formed-but-unknown name with ExceptionType 'ResourceNotFoundException' and FailureCode 'RULE_NAME', and the pattern-violating name with ExceptionType 'InvalidParameterException' and FailureCode 'INVALID_RULE_NAME'. The ExceptionType/FailureCode strings are the fixed vocabulary; FailureResource is the member taken verbatim from the request, including its control byte.

Emulator: the request is refused whole. DisableInsightRules and EnableInsightRules each answer HTTP 400 with Error.Code 'ValidationError' and Error.Message '1 validation error detected: Value <value> at \'ruleNames.<i>.member\' failed to satisfy constraint: Member must satisfy regular expression pattern: [\x20-\x7E]+'. Three things diverge in that one response beyond the status: (a) the code is not a modeled error of the operation and AWS does not refuse this request at all; (b) no Failures[] is produced, so the two different per-item reasons collapse and the ResourceNotFoundException/RULE_NAME entry that fixed issue 20261027T074335Z delivers is unreachable; (c) the valid rule in the same batch is never flipped, so the check's subsequent DescribeInsightRules state assertion can never hold. The echoed diagnostics are themselves wrong: the emulator strips the control character out of the value it quotes (it reports Value 'bad-rule' for a member sent as '\x01bad-rule'), it renders the member path with a 1-based index of 3 for a three-element list whose offending member is at index 2, and it prints the pattern unanchored ([\x20-\x7E]+) where the model's pattern is ^[\x20-\x7E]+$.

Why: a batch caller loses the valid work in the batch because one name was bad, and loses the per-item classification it is supposed to branch on. 'This rule does not exist, create it' (ResourceNotFoundException/RULE_NAME) and 'this string is not a legal rule name, the request is a client bug' (InvalidParameterException/INVALID_RULE_NAME) collapse into one generic 400 ValidationError, so a console or IaC reconciler enabling/disabling a set of Contributor Insights rules either retries the whole batch forever or abandons rules AWS would have flipped.

Fix: the EnableInsightRules and DisableInsightRules handlers in the cloudwatch crate and the shared model-constraint validator they are wired through — RuleNames members must be exempt from the request-level @length/@pattern validator that emits ValidationError; the length/pattern check belongs inside the handlers' per-item loop, which emits PartialFailure{ExceptionType 'InvalidParameterException', FailureCode 'INVALID_RULE_NAME'} for the offending member and continues, so every well-formed name in the batch is still resolved (unknown -> ExceptionType 'ResourceNotFoundException', FailureCode 'RULE_NAME') and every existing rule is still flipped, with the whole call answering 200.

Traces: cloudwatch.disable-insight-rules-and-malformed-name-reported-as-failure-entry, cloudwatch.enable-insight-rules-and-malformed-name-reported-as-failure-entry. Handler files named by the earlier fixed issue: services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/ops/enable_insight_rules.rs and .../src/ops/disable_insight_rules.rs.

Cause 2 of 2: an empty-string RuleNames member is treated as an ABSENT required parameter, so EnableInsightRules answers 400 MissingParameter instead of 200 with an InvalidParameterException PartialFailure for that member.
Failing check id: cloudwatch.op-contract-enableInsightRules

AWS: Smithy models EnableInsightRules input RuleNames as @required (clientOptional) targeting InsightRuleNames; the required-ness is on the LIST, and a present list holding one empty-string member satisfies it. The member constraint (@length min 1) is a member constraint, not a presence rule. MissingRequiredParameterException (400, awsQueryError code 'MissingParameter') is modeled for the case where RuleNames itself is absent. Recorded behavior (the check's real-AWS replay, taken with botocore parameter_validation disabled so the empty member actually reaches the service): EnableInsightRules(RuleNames=['']) answers HTTP 200 — not a raised exception — with a Failures[] entry whose FailureResource is '' (the member echoed verbatim), ExceptionType 'InvalidParameterException' and FailureDescription exactly 'RuleName cannot be an empty string.' That sentence is wholly fixed text with nothing interpolated. This is the same non-raising shape as the unknown-name case in the same check, which AWS answers with ExceptionType 'ResourceNotFoundException' and FailureDescription 'Rule <ruleName> does not exist.' (fixed text 'Rule ' + ' does not exist.' around the request's own name) — the two are distinguished only by ExceptionType and the description.

Emulator: EnableInsightRules(RuleNames=['']) answers HTTP 400 with Error.Code 'MissingParameter' and Error.Message 'The parameter RuleNames.member.1 is required.' — i.e. the empty member is read as a missing one. AWS reserves MissingParameter for an absent RuleNames, and never refuses this request at all; no Failures[] is produced and the InvalidParameterException classification is unreachable. The legs of the same check before this point pass, which localises the defect: the rule is created DISABLED, the batch [<existing rule>, <well-formed unknown name>] answers 200 with exactly one ResourceNotFoundException entry carrying FailureDescription 'Rule <name> does not exist.', and the existing rule transitions to ENABLED.

Why: the caller cannot tell 'you sent no rule names' from 'one of the rule names you sent is empty'. The first is a wholly malformed request to abort on; the second is a per-item data problem AWS reports while still processing the rest of the batch. A client that normalises user input into a batch (an empty cell in a spreadsheet, an unset template variable) sees its entire enable call rejected as structurally invalid and never learns which member was at fault.

Fix: EnableInsightRules' (and, for symmetry, DisableInsightRules') input handling in the cloudwatch crate — required-ness must be evaluated on the RuleNames list itself, so MissingParameter 'The parameter RuleNames.member.1 is required.' is emitted only when RuleNames is absent or empty; an empty-string MEMBER must flow into the per-item loop and produce PartialFailure{FailureResource: '', ExceptionType: 'InvalidParameterException', FailureDescription: 'RuleName cannot be an empty string.'} on an HTTP 200 response.

Traces: cloudwatch.op-contract-enableInsightRules (the empty-RuleNames leg, after the ResourceNotFoundException leg has already passed). Handler file: services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/ops/enable_insight_rules.rs.
