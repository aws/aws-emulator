# cloudwatch__cognito-idp: Cognito publishes no AWS/Cognito CloudWatch metrics — authentication counters and threat-protection NoRisk never appear, so both metric-emission checks hang to the 60 s cap (2 causes)

> _Note: this issue was identified against the code base at commit `4e0be56b24c0fc13c424c1a1b18bb5f0120957ed`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMetricStatistics

## Description
Cognito user-pool traffic produces no CloudWatch metric data at all. Both of this service pair's metric-emission checks drive real end-user traffic against a user pool and then poll CloudWatch for the AWS/Cognito series that traffic must create; the series never becomes non-empty, so each check's settle loop (per-series budget 900 s, 15 s poll, 90 s stability window) never terminates and the check is killed at the harness's 60 s cap. The two causes below are distinct publishing paths, with distinct namespaces/dimension keys, and each must be closed before these checks pass.

Cause 1 of 2: the AWS/Cognito authentication counters are never published under the (UserPool, UserPoolClient) dimension set.
  AWS: recorded behavior only — the CloudWatch metric catalogue is not part of the cognito-idp Smithy model, and the model's GetMetricStatistics/ListMetrics shapes say nothing about which series a user pool creates. The recordings measured against real AWS (us-west-2) show that a user pool publishes, per app client, the namespace AWS/Cognito series SignInSuccesses, TokenRefreshSuccesses and SignUpSuccesses keyed on the two dimensions UserPool (the pool id) and UserPoolClient (the app-client id). Each series counts outcomes, not just successes: a refused sign-in — whether refused on the credential (NotAuthorizedException) or refused at validation because the app client does not allow the requested flow (InvalidParameterException, message "USER_PASSWORD_AUTH flow not enabled for this client") — is published into SignInSuccesses as a ZERO-VALUED sample, so Sum counts only successes while SampleCount counts every attempt. The recordings settle at Sum 2 / SampleCount 5 / Average 0.4 for a client taking 2 good and 3 refused sign-ins, and at Sum 1 / SampleCount 4 for a client taking 3 flow-refused attempts and 1 repaired sign-in. REFRESH_TOKEN_AUTH calls do not touch SignInSuccesses and land in TokenRefreshSuccesses instead (Sum 2 for 2 refreshes); SignUp contributes Sum 1 to SignUpSuccesses and AdminConfirmSignUp adds nothing. An app client on the same pool that is never used has NO datapoints in any of the three series.
  Emulator: GetMetricStatistics for Namespace=AWS/Cognito, MetricName=SignInSuccesses with Dimensions [UserPool, UserPoolClient] returns an empty Datapoints list forever, both before and after the sign-in/refresh/sign-up traffic. The individual cognito-idp calls themselves answer normally (the refusals carry the right code), so nothing fails until the CloudWatch read: the settle loop sees None on every probe and the check is killed at 60 s. The emulator therefore has no Cognito-to-CloudWatch metric emission path at all, not merely wrong values.
  Why: a client that uses these counters to observe authentication health — dashboards, alarms on a drop in SignInSuccesses Sum, or a failure-rate computed as 1 - Sum/SampleCount — sees a permanently empty series and cannot distinguish "no traffic" from "all traffic failing". Any alarm built on them stays in INSUFFICIENT_DATA, and the zero-sample convention (which is what makes the failure rate computable at all) cannot be relied on.
  Fix: the metric-emission side effect belongs in the cognito-idp operation handlers that terminate an authentication/registration attempt (InitiateAuth / AdminInitiateAuth for SignInSuccesses and TokenRefreshSuccesses, SignUp for SignUpSuccesses), which must publish one datapoint per attempt — value 1 on success and 0 on a refusal, including a refusal raised by request validation before any credential is checked — into the emulator's CloudWatch metric state under namespace AWS/Cognito with dimensions UserPool and UserPoolClient.
  Traces: cloudwatch__cognito-idp.obs-cognito-idp-2-auth-counters-per-client-and-plus-tier-no-risk, cloudwatch__cognito-idp.obs-cognito-idp-2-sign-in-rejected-for-disabled-flow-is-a-zero-sample.

Cause 2 of 2: the Plus-tier threat-protection NoRisk series is never published, and ListMetrics catalogues no AWS/Cognito dimension set.
  AWS: recorded behavior only (not modeled). On a PLUS-tier pool with threat protection in AUDIT mode, one successful sign-in publishes the AWS/Cognito metric NoRisk keyed on the dimensions Operation (value SignIn) and UserPoolId — note UserPoolId, a DIFFERENT dimension key from the UserPool key the authentication counters in Cause 1 use. The recording reads both halves: the (Operation, UserPoolId) query carries Sum 1, and the same query keyed UserPool returns nothing, because CloudWatch dimension matching is exact. ListMetrics for namespace AWS/Cognito names both dimension sets.
  Emulator: no NoRisk datapoint is published under either dimension key after the sign-in, and ListMetrics returns no AWS/Cognito entry, so the dimension-key half of the claim cannot even be read. The check hangs on the same empty-series poll as Cause 1 and is killed at 60 s.
  Why: a client reading threat-protection telemetry gets an empty namespace and cannot tell AUDIT mode from threat protection being off; a client that writes the dimension key by hand has no way to discover from ListMetrics that the threat-protection series is keyed UserPoolId while the authentication series is keyed UserPool, so it silently queries a series that will never have data.
  Fix: the threat-protection evaluation path of the sign-in handlers (the component that records the per-request risk decision on a PLUS-tier pool) must publish the risk-outcome datapoint into the emulator's CloudWatch metric state under namespace AWS/Cognito with dimensions Operation and UserPoolId, and that series must be registered so ListMetrics catalogues it alongside the (UserPool, UserPoolClient) sets from Cause 1.
  Traces: cloudwatch__cognito-idp.obs-cognito-idp-2-auth-counters-per-client-and-plus-tier-no-risk.

No open issue covers this pair: the existing cognito-idp issues concern control-plane and Lambda-trigger fidelity, and the existing cloudwatch metric-emission issues name other producer services (e.g. 20261025T020208Z-cloudwatch-dynamodb-dynamodb-transactwriteitems-consumedcapacity-omits-writecapacityunits-and-no-aws.md for AWS/DynamoDB). Cognito is not among them.

## Evidence
Both checks are reported as [mismatch] with "Error: Check timed out after 60.0s".

obs-cognito-idp-2-auth-counters-per-client-and-plus-tier-no-risk (report lines 7921-8253): creates an ESSENTIALS pool with app clients A and B and a PLUS/AUDIT pool, drives 2 good + 3 wrong-password USER_PASSWORD_AUTH sign-ins, 2 REFRESH_TOKEN_AUTH calls and 1 SignUp+AdminConfirmSignUp on A, then polls GetMetricStatistics(Namespace="AWS/Cognito", MetricName="SignInSuccesses", Dimensions=[{UserPool: pool},{UserPoolClient: clientA}]) until the series holds one value for 90 s within a 900 s budget. Expected settled readings: SignInSuccesses Sum 2 / SampleCount 5 / Average 0.4; TokenRefreshSuccesses Sum 2; SignUpSuccesses Sum 1; client B empty in all three; and NoRisk Sum 1 under [{Operation: SignIn},{UserPoolId: plusPool}] with the same query keyed UserPool empty, with ListMetrics naming both dimension sets. Actual: the probe returns None (no Datapoints) on every poll, so the loop never settles and the harness kills the check at 60 s.

obs-cognito-idp-2-sign-in-rejected-for-disabled-flow-is-a-zero-sample (report lines 8254-8439): a client with only ALLOW_REFRESH_TOKEN_AUTH + ALLOW_USER_SRP_AUTH takes 3 USER_PASSWORD_AUTH attempts with the CORRECT password, each correctly refused (the check's own assertion on the refusal passes: ("InvalidParameterException", "USER_PASSWORD_AUTH flow not enabled for this client")); the client is then updated to allow the flow and one sign-in succeeds and returns an AccessToken. The series read is GetMetricStatistics(Namespace="AWS/Cognito", MetricName="SignInSuccesses", Dimensions=[{UserPool: pool},{UserPoolClient: client}], Period=3600, Statistics=["Sum","SampleCount"]). Expected settled (Sum, SampleCount) == (1.0, 4.0) — the 3 flow-refused attempts are zero-valued samples and the repaired sign-in is the only success. Actual: Datapoints is empty on every poll; the check's own diagnostic for this state is "series never held one non-empty value for 90.0s within 900.0s; last reading None", and the harness cap fires first at 60 s.

That the cognito-idp refusal assertions pass while only the CloudWatch read fails isolates the divergence to metric emission rather than to the authentication operations themselves.

## Steps to Reproduce
1. Boot the emulator (cognito-idp and cloudwatch both answer).
2. CreateUserPool, then CreateUserPoolClient with GenerateSecret=false and ExplicitAuthFlows=[ALLOW_REFRESH_TOKEN_AUTH, ALLOW_USER_SRP_AUTH, ALLOW_USER_PASSWORD_AUTH]. AdminCreateUser + AdminSetUserPassword(Permanent=true) to get a CONFIRMED user.
3. Call InitiateAuth with AuthFlow=USER_PASSWORD_AUTH twice with the correct password (success) and three times with a wrong password (NotAuthorizedException).
4. Call GetMetricStatistics with Namespace="AWS/Cognito", MetricName="SignInSuccesses", Dimensions=[{Name: "UserPool", Value: <poolId>}, {Name: "UserPoolClient", Value: <clientId>}], a StartTime 20 minutes back, Period=3600, Statistics=["Sum","SampleCount"]. Observe Datapoints == [] instead of a settled Sum 2 / SampleCount 5. Repeat for TokenRefreshSuccesses after a REFRESH_TOKEN_AUTH call and SignUpSuccesses after SignUp — all empty (Cause 1).
5. Repeat step 3 with an app client whose ExplicitAuthFlows omit ALLOW_USER_PASSWORD_AUTH: the call is refused with InvalidParameterException "USER_PASSWORD_AUTH flow not enabled for this client", and SignInSuccesses still has no zero-valued sample (Cause 1).
6. CreateUserPool with UserPoolTier=PLUS and threat protection in AUDIT mode, take one successful sign-in, then call GetMetricStatistics for MetricName="NoRisk" with Dimensions=[{Name: "Operation", Value: "SignIn"}, {Name: "UserPoolId", Value: <poolId>}] and ListMetrics for Namespace="AWS/Cognito". Observe no datapoint under either dimension key and no catalogued AWS/Cognito metric (Cause 2).
