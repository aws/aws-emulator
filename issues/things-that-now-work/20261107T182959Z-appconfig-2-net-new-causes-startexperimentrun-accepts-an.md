=== Cause 1 of 2: StartExperimentRun never validates an inline treatment override against the experiment definition's own treatments, so an allocation AWS refuses starts a RUNNING run ===
Failing check id: appconfig.start-experiment-run-invalid-treatment-allocation-rejected.

AWS: Smithy StartExperimentRun — POST /applications/{ApplicationIdentifier}/experimentdefinitions/{ExperimentDefinitionIdentifier}/experimentruns, success code 201, output ExperimentRun, modelled errors BadRequestException (400), ConflictException (409), ResourceNotFoundException (404), InternalServerException (500). StartExperimentRun.TreatmentOverrides targets the union TreatmentOverrides whose single member Inline targets TreatmentOverrideMap (@length 0-32, value TreatmentKey @pattern ^[a-zA-Z0-9]{1,8}$), documented "A map of entity IDs to treatment keys. Each entry assigns the specified entity to the specified treatment, bypassing random assignment." The model states the key's SHAPE only; that the assigned key must be one the addressed definition actually defines is recorded behavior only. The recording shows AWS refusing such a start with BadRequestException / HTTP 400 and the message template "Invalid treatment name: <key>. Valid treatment names are: [<control key>, <treatment keys in declaration order>]" — the fixed text is "Invalid treatment name: ", ". Valid treatment names are: [", "]"; the variable parts are the rejected key taken from the request's Inline map and the list of the addressed definition's own generated keys read from state (control key first, then each treatment key in declaration order). The refusal has no side effect: ListExperimentRuns stays empty and GetExperimentDefinition stays Status IDLE; the same call with a key the definition defines then starts a run with Status RUNNING.

Emulator: the key-existence rule is absent and the call SUCCEEDS. The replay shows HTTP 201 with Status 'RUNNING', the bogus assignment echoed back in TreatmentOverrides.Inline, a Run number consumed and an ExperimentDefinitionSnapshot whose Treatments/Control do not contain the assigned key at all — i.e. the over-permissive direction, where AWS answers 400 and writes nothing. Only the override map's shape (map length, entity-id length, the 1-8 alphanumeric TreatmentKey pattern) is enforced, so any 1-8 alphanumeric string naming no treatment passes.

Why: TreatmentOverrides is the one place an experiment assignment can be pinned deterministically (QA entities, allow-listed accounts). AWS reports a typo or a stale treatment key at the start call, before any audience is exposed. Against this emulator the typo is accepted, a run goes RUNNING with an assignment that can never resolve to a treatment, the pinned entity is silently served something other than what the caller asked for, and the caller's negative test for BadRequestException passes on AWS and fails only here.

Fix: the StartExperimentRun handler's pre-write validation in the appconfig service — after the application and definition are resolved and before any state is written, every value of TreatmentOverrides.Inline must be compared against that definition's control key and treatment keys and refused with BadRequestException/400 carrying the message above; the same rule belongs on the sibling write (UpdateExperimentRun) so the start and update paths cannot drift, which means the shared override-validation helper needs the definition's keys passed in rather than the overrides alone.

Prior work that does NOT carry this check's replay key: open issue 20261030T064749Z-appconfig-startexperimentrun-accepts-an-inline-treatment-override-naming.md names the same check id, but it was filed from a replay in which the check was killed in its SETUP (its Issue-Key is a _poll_until timeout) and its analysis was source-derived. In THIS replay the setup completes and the graded call is actually issued and actually answered 201, so the cause is now confirmed from the wire rather than hypothesised; grade it on that 201.

=== Cause 2 of 2: a LINEAR rollout is never observably partial at the data plane, so a mid-rollout StopDeployment withdrawal can never be reached ===
Failing check id: appconfig.stop-deployment-mid-rollout-reverts-every-session.

AWS: Smithy GrowthType LINEAR with DeploymentDurationInMinutes>0 and GrowthFactor<100 ramps a deployment over wall-clock time, and Deployment$PercentageComplete is documented as "The percentage of targets for which the deployment is available" — so while 0 < PercentageComplete < 100 the SAME environment serves the previous version to some fresh configuration sessions and the deploying version to others. StopDeployment — DELETE /applications/{ApplicationId}/environments/{EnvironmentId}/deployments/{DeploymentNumber}, success code 202, output Deployment, errors BadRequestException (400) / ResourceNotFoundException (404) / InternalServerException (500) — is a withdrawal, not a freeze: it answers synchronously with State 'ROLLED_BACK' (DeploymentState has values BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED — there is no 'STOPPED'; 'REVERTED' is the AllowRevert path on a COMPLETE deployment) and PercentageComplete 0.0, the deployment settles ROLLED_BACK with a ROLLBACK_COMPLETED EventLog entry, GetEnvironment reports the CamelCase State 'RolledBack', every fresh session is served the previous version's exact bytes again, and a second StopDeployment on the terminal deployment is refused BadRequestException/400 with the message template "Deployment <n> for App <app-id> and Environment <env-id> cannot be stopped, it has a status of <State>." (fixed text "Deployment ", " for App ", " and Environment ", " cannot be stopped, it has a status of ", "."; variable parts: the deployment number and the application/environment ids from the request and the deployment's State from state).

Emulator: the check is killed — "Error: Check timed out after 180.0s" — inside the barrier that establishes the precondition, so none of the StopDeployment behavior above is ever exercised. The barrier polls GetDeployment and, whenever 0 < PercentageComplete < 100, samples 20 independent StartConfigurationSession+GetLatestConfiguration sessions, breaking only once BOTH the previous and the deploying payload have been served. That never happens: the deployment correctly stays non-terminal for its 5-minute duration (the guard that fires when a rollout reaches a terminal state before both versions were seen does not fire), but a full width of fresh sessions is never split across the two versions. Hypothesis: PercentageComplete is tracked on the deployment record but does not gate what a configuration session is served, so every session gets the in-flight version from StartDeployment onward and no partial state exists to stop.

Why: a caller cannot verify, or even observe, AppConfig's central safety property — that a release is withdrawn from EVERY client when it is stopped part way through. With no partial state the gradual-rollout contract is absent, and the whole stop path (202 + synchronous ROLLED_BACK, PercentageComplete 0.0, the ROLLBACK_COMPLETED event, Environment State 'RolledBack', the previous bytes back in service, and the BadRequestException on a second stop) is unverifiable against this emulator.

Fix: the rollout-percentage seam between the deployment state machine and the appconfigdata data plane — a session must be bucketed against the in-flight deployment's PercentageComplete so that a mid-rollout environment serves the previous version to the complementary fraction of sessions — together with the StopDeployment handler and the same state machine, which must withdraw rather than freeze (synchronous State ROLLED_BACK and PercentageComplete 0.0, ROLLBACK_COMPLETED logged, environment State 'RolledBack', previous bytes served to all fresh sessions, and BadRequestException with the message above on a stop of a terminal deployment).

Prior work that does NOT carry this check's replay key: open issues 20261029T233120Z-appconfig-rollout-percentage-never-gates-what-the-data.md (same seam, grounded in appconfig.linear-rollout-serves-both-versions-across-sessions, which IS owned by it in this replay) and 20261101T232607Z-appconfig-exponential-rollout-is-never-partial-at-the.md (the EXPONENTIAL growth type). This check adds the stop-mid-rollout consequence and the StopDeployment requirements above, which neither of those issues grades.

Note on budget for the fixer: this check paces a 5-minute LINEAR strategy in real time, so confirming it needs a wall-clock budget larger than the 180 s per-check cap it was killed at (the check itself declares _PARTIAL_ROLLOUT_TIMEOUT_S=600 and _CONVERGE_TIMEOUT_S=300). A partial rollout can also be observed directly with the steps below.
