# cloudwatch__ecr__ecs: 2 net-new causes — an ECR repository policy's explicit Deny is never enforced (TagResource succeeds), and RunTask never validates that the task definition's execution role trusts ecs-tasks.amazonaws.com

> _Note: this issue was identified against the code base at commit `6ec43c73f71e6013077e783d53ce3ba5d179d34d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource, RunTask

## Description
Two independent net-new root causes, both grounded in failing behavioral checks under the suite's `cloudwatch__ecr__ecs` heading. Both are authorization/trust decisions the emulator never makes: it answers 2xx where AWS refuses, so every negative ("rejected") path built on a resource-based Deny or on a role ECS cannot assume is unreachable. Neither is covered by an open issue: 20261110T181833Z-kms-lambda-a-kms-key-policy-explicit-deny.md reports the same class of gap for a KMS key policy and Lambda, and 20261111T131404Z-cloudwatch-ecr-ecs-a-fargate-container-s-image.md covers container execution, but neither names ECR repository-policy evaluation or RunTask execution-role trust validation.

=== Cause 1 of 2: an ECR repository policy with an explicit Deny for the calling principal is not evaluated, so ECR control-plane calls on that repository are allowed ===
AWS: a repository policy set by SetRepositoryPolicy (Smithy: ecr#SetRepositoryPolicy, policyText required, RepositoryPolicyText @length 0..10240) is a resource-based policy that ECR evaluates on every request against that repository. An explicit Deny statement naming the caller's principal (Principal {"AWS": "arn:aws:iam::<account>:role/<role>"}, Effect Deny, Action ["ecr:TagResource"]) makes ECR refuse the call with the service-common authorization error AccessDeniedException. Smithy models no AccessDeniedException on ecr#TagResource (its modeled errors are InvalidParameterException, InvalidTagParameterException, RepositoryNotFoundException, TooManyTagsException, ServerException), so this is the service-common IAM/resource-policy refusal, not an operation-specific one; the recorded behavior the check asserts is error code `AccessDeniedException` with message `User: <caller ARN> is not authorized to perform: ecr:TagResource on resource: <repository ARN> with an explicit deny in a resource-based policy`. In that message the FIXED text is `User: `, ` is not authorized to perform: `, ` on resource: ` and ` with an explicit deny in a resource-based policy`; the VARIABLE parts are the caller's ARN (from the signing identity, i.e. what GetCallerIdentity returns), the action id (`ecr:TagResource` — the service prefix plus the operation being refused) and the full repository ARN from the request (`arn:aws:ecr:<region>:<account>:repository/<repositoryName>`). The call must also have no effect: ListTagsForResource must not show the tag afterwards. Removing only the caller-scoped Deny (leaving the PrincipalAccount-conditioned pull Deny in place) must make the identical TagResource succeed.
Emulator: TagResource on a repository whose stored policy explicitly Denies `ecr:TagResource` for the caller's own role returns HTTP 200 with an empty JSON body (`{'ResponseMetadata': {'HTTPStatusCode': 200, ... 'content-length': '2'}}`) and the tag lands. The replay reports `AssertionError: expected AccessDeniedException, but the call SUCCEEDED and returned {...'HTTPStatusCode': 200...}`. The policy document itself round-trips correctly through GetRepositoryPolicy — it is stored but never consulted as an authorization input.
Why: a client cannot test, or rely on, any ECR repository-policy restriction. Deny statements that in AWS block tagging, pulling (ecr:BatchGetImage / GetDownloadUrlForLayer / BatchCheckLayerAvailability) or cross-account access are inert, so least-privilege and cross-account-isolation configurations appear to work while every call is in fact permitted, and the differential a test uses to prove enforcement (denied -> AccessDeniedException, policy narrowed -> success) collapses into "always succeeds".
Fix: the ECR request-authorization path — the repository-policy evaluation step that must run before the ECR operation handlers (TagResource and the other repository-scoped operations) execute, plus the serializer path that emits the service-common AccessDeniedException with the message template above. Repository-policy state itself is already correct; what is missing is the evaluation of it (including Principal matching that resolves an assumed-role session ARN to its underlying role ARN, and Condition keys such as aws:PrincipalAccount).
Traces: cloudwatch__ecr__ecs.deploy-cfn-ecr-repository-policy-restricts-cross-account-pull-rejected.

=== Cause 2 of 2: RunTask does not validate that the task definition's execution role can be assumed by ECS, so a role with the wrong trust principal launches a task ===
AWS: before placing a task, ECS attempts to assume the task definition's ExecutionRoleArn. A role whose trust policy allows only `ec2.amazonaws.com` (instead of `ecs-tasks.amazonaws.com`) for sts:AssumeRole cannot be assumed, and ecs#RunTask is refused synchronously with the modeled error ClientException (Smithy: ecs#RunTask errors include ClientException, httpError 400) rather than returning tasks. The recorded message is `ECS was unable to assume the role '<roleArn>' that was provided for this task. Please verify that the role being passed has the proper trust relationship and permissions and that your IAM user has permissions to pass this role.` — all of that is FIXED text except `<roleArn>`, which is the ExecutionRoleArn from the named task definition (quoted in single quotes). Because the task never starts, no log stream for it is created and its container's stdout never reaches the awslogs log group. A sibling task definition in the same stack whose role trusts ecs-tasks.amazonaws.com must still run.
Emulator: RunTask with that task definition returns 200 with a task in `tasks` and no `failures`; no ClientException is raised at all. The replay reports `AssertionError: RunTask succeeded with a role trusting ec2.amazonaws.com (not ecs-tasks.amazonaws.com) -- ECS should never have been able to assume it`. The emulator therefore treats ExecutionRoleArn as an opaque string and never performs (or simulates) the sts:AssumeRole against the role's trust policy.
Why: a client gets no signal that an execution role is mis-trusted — the single most common ECS misconfiguration. Code and IaC that AWS rejects at RunTask (and that makes a service never stabilize) appears to deploy and run, so trust-policy regressions are invisible and the negative control "wrong trust principal => ClientException" cannot be exercised; downstream assertions about absent log delivery also become meaningless because the task runs.
Fix: the ECS RunTask handler's pre-placement validation (and the same check on CreateService/UpdateService task placement), which must resolve the task definition's ExecutionRoleArn (and TaskRoleArn) against IAM's stored trust policy for that role and refuse with ClientException and the message template above when `ecs-tasks.amazonaws.com` is not an allowed sts:AssumeRole principal.
Traces: cloudwatch__ecr__ecs.deploy-cfn-ecs-service-fails-without-iam-trust-policy-rejected.

GetRepositoryPolicy round-trips both statements correctly.
  Call: ecr.tag_resource(resourceArn="arn:aws:ecr:<region>:<account>:repository/<repo>", tags=[{Key: probe, Value: denied}])
  Expected: error code AccessDeniedException, message "User: <caller ARN> is not authorized to perform: ecr:TagResource on resource: arn:aws:ecr:<region>:<account>:repository/<repo> with an explicit deny in a resource-based policy", and ListTagsForResource shows no `probe` tag.
  Actual: HTTP 200, empty JSON body (content-length 2), tag applied. Replay detail: `AssertionError: expected AccessDeniedException, but the call SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'application/x-amz-json-1.1', 'content-length': '2', ...}, 'RetryAttempts': 0}}` (check file line 115 -> _error at line 323).

Cause 2 — cloudwatch__ecr__ecs.deploy-cfn-ecs-service-fails-without-iam-trust-policy-rejected [mismatch]
  Setup: one CFN stack creates a log group, an ECS cluster, and two IAM roles that differ ONLY in their trust principal — GoodRole trusts ecs-tasks.amazonaws.com, BadRole trusts ec2.amazonaws.com (both carry AmazonECSTaskExecutionRolePolicy) — plus two FARGATE/awsvpc task definitions (Cpu 256, Memory 512) using those roles as ExecutionRoleArn.
  Call: ecs.run_task(cluster=<cluster>, taskDefinition=<bad family>, launchType="FARGATE", networkConfiguration={awsvpcConfiguration:{subnets, securityGroups, assignPublicIp ENABLED}}, count=1)

## Steps to Reproduce
Cause 1 (ECR repository-policy Deny not enforced):
1. Create an ECR repository (directly or via a CFN AWS::ECR::Repository with RepositoryPolicyText).
2. SetRepositoryPolicy with a statement {"Sid":"DenyCallerTag","Effect":"Deny","Principal":{"AWS":"<the calling identity's role ARN>"},"Action":["ecr:TagResource"]} (resolve an assumed-role session ARN to its role ARN).
3. GetRepositoryPolicy — the document is stored verbatim.
4. Call TagResource on arn:aws:ecr:<region>:<account>:repository/<repo> with any tag.
   Observed: HTTP 200, empty body, and ListTagsForResource shows the tag.
   Expected: AccessDeniedException with the "...with an explicit deny in a resource-based policy" message and no tag applied.
5. Remove only that statement with SetRepositoryPolicy and repeat step 4 — in AWS this is the positive control that now succeeds; in the emulator both calls behave identically, so there is no differential.

Cause 2 (RunTask ignores execution-role trust):
1. Create an IAM role whose AssumeRolePolicyDocument allows sts:AssumeRole only for Principal {"Service": "ec2.amazonaws.com"}.
2. RegisterTaskDefinition (requiresCompatibilities FARGATE, networkMode awsvpc, cpu 256, memory 512) with executionRoleArn set to that role's ARN.
3. Create an ECS cluster and call RunTask with launchType FARGATE and an awsvpcConfiguration.
   Observed: 200 with one task in `tasks` and an empty `failures` list; the task proceeds and its container output is delivered.
   Expected: ClientException with the message "ECS was unable to assume the role '<role ARN>' that was provided for this task. Please verify that the role being passed has the proper trust relationship and permissions and that your IAM user has permissions to pass this role.", no task created, and no log stream/events for it.
4. Repeat with an otherwise identical role trusting ecs-tasks.amazonaws.com — that one must run (positive control).
