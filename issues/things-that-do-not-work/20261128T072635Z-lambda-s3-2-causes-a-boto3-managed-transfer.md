# lambda__s3: 2 causes — a boto3 managed transfer of a 9 MiB object is OOM-killed at MemorySize=256, and (REOPENED) the presigned S3 GET is still minted in the legacy query-credential form

> _Note: this issue was identified against the code base at commit `ac13a1e3dcf5c46abb305d32ec965601a01eddff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Two root causes, both grounded in failing behavioral checks the replay report left unmarked (no ALREADY FILED marker, no OWNED-by marker). Both are listed under the report heading '### lambda__s3'.

Cause 1 of 2: an in-function boto3 managed transfer (upload_fileobj / download_fileobj) of a 9 MiB object is killed out-of-memory in a function whose MemorySize is 256 MB.
Failing check ids: lambda__s3.function-sdk-upload-fileobj-and-download-fileobj-round-trip
  AWS:      Smithy (com.amazonaws.lambda#AWSGirApiService): CreateFunction.MemorySize is @range min 128 max 32768 and is the sandbox's memory ceiling; Invoke is POST /2015-03-31/functions/{FunctionName}/invocations with http code 200, and on success the response carries NO X-Amz-Function-Error header (output member FunctionError absent) and the handler's own JSON as the payload. The model says nothing about transfer buffering, so that part is documented/recorded behavior only: boto3's managed transfer methods stream through an 8 MiB chunk buffer and switch to a multipart upload above the 8 MiB threshold, so a 9 MiB object moves as two parts with a few tens of MB of resident memory — far inside a 256 MB function. On AWS the invoke answers StatusCode 200 with no FunctionError and a body reporting sent/received sha256 equal and size 9437184, and the stored object's ETag ends in '-2'.
  Emulator: the invoke is answered with FunctionError='Unhandled' and the payload {"errorType": "Runtime.OutOfMemory", "errorMessage": "RequestId: <request id> Error: Runtime exited with error: signal: killed"} — the sandbox is killed before the handler returns. (Only the fixed text of that message is a requirement; the request id is a per-run value.) The handler never gets to issue its S3 calls, so the two-part multipart upload and the ranged download are never exercised.
  Why:      a client that sizes a function the way AWS documents (256 MB is ample for s3transfer's 8 MiB chunking) sees its function crash with an out-of-memory kill instead of completing. Any handler that moves a file of a few MiB through the AWS SDK — the single most common Lambda+S3 pattern — is unusable against the emulator, and retry/error handling written for AWS (where no FunctionError is returned at all) is never exercised.
  Fix:      the memory accounting and run ceiling of the Lambda Python execution environment (the engine's measurement of what the guest actually holds, rather than the pages the invoking thread faulted) — a guest holding well under its configured MemorySize must not be retired or killed, and only an allocation past MemorySize may produce Runtime.OutOfMemory. Note the converse defect is already open as 20261119T000000Z-lambda-7-of-the-parent-reports-10-causes-remain-....md cause 4 (MemorySize not enforced at all, a 400 MB allocation at 128 MB is NOT killed); that issue does not carry this check's replay key and describes under-enforcement, while this cause is over-enforcement on the same accounting seam, so a fixer must make the accounting correct in both directions.
  Traces:   lambda__s3.function-sdk-upload-fileobj-and-download-fileobj-round-trip (assertion '_invoke_granted: the function failed').

Cause 2 of 2: REOPENS issues/things-that-now-work/20261124T120026Z-lambda-s3-the-presigned-s3-get-minted-against.md: its fix left the presigned S3 GET minted against this emulator in the LEGACY query-credential form, so S3's tampered-signature refusal is still unreachable. That resolved issue carries exactly this check's replay key (lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected | _tamper | 'the presigned URL carries no signature'), and the check fails at the same point, so this is not a new defect — it is that one, still present.
Failing check ids: lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected
  AWS:      Smithy (com.amazonaws.s3#AmazonS3): GetObject is GET /{Key+} on the bucket endpoint; the model does not describe the presigned query form, so this is documented/recorded behavior only. A presigned GetObject URL minted for an S3 endpoint carries the SigV4 query credential — X-Amz-Algorithm, X-Amz-Credential, X-Amz-Date, X-Amz-Expires, X-Amz-SignedHeaders and a lowercase-hex X-Amz-Signature — and serves the object's bytes with HTTP 200. When one character of that signature is altered, AWS answers HTTP 403 with an XML Error body whose Code is 'SignatureDoesNotMatch' and whose Message is the fixed text 'The request signature we calculated does not match the signature you provided. Check your key and signing method.' (that message interpolates nothing from the request or from state). A 403 is still an HTTP response, so a nodejs22.x handler fetching it returns normally and Invoke answers StatusCode 200 with no FunctionError.
  Emulator: the presigned GetObject URL produced against this emulator still carries only the legacy trio of query keys — AWSAccessKeyId, Signature, Expires — and no SigV4 credential, so the check aborts with "AssertionError: the presigned URL carries no signature (query keys ['AWSAccessKeyId', 'Signature', 'Expires'])" and no request is ever sent: the emulator serves no status, code or message for the tampered-signature path at all. The suite's own replays of the legacy form against this emulator are answered HTTP 403 <Code>InvalidAccessKeyId</Code> instead of the object's bytes (see the open issues 20261124T183921Z-lambda-s3-a-presigned-s3-get-the-emulator.md and 20261109T220008Z-smoke-query-string-presigned-sigv4-requests-are-refused.md), so the signature-verification path that must answer SignatureDoesNotMatch remains unreachable from any presigned URL issued against the emulator.
  Why:      presigned URLs are the documented way to hand in-function or browser code object access without credentials, and client code distinguishes 'the signature was tampered with or expired' (403 SignatureDoesNotMatch) from 'the key is unknown' (403 InvalidAccessKeyId) and from 'the object is missing' (404 NoSuchKey). Against this emulator neither the SigV4 presigned form nor its refusal exists, so error handling written against AWS's codes and messages is never exercised and breaks in production.
  Fix:      the S3 presigned/query-credential authentication path (request authentication ahead of the GetObject handler) together with whatever the emulator announces about its S3 endpoint that makes a client resolve the legacy signer: a presigned GET must be minted and accepted in the SigV4 query form, served 200 with the object's bytes when its signature verifies, and refused 403 Code 'SignatureDoesNotMatch' with the fixed message above when it does not; InvalidAccessKeyId belongs only to a credential naming a key the emulator does not know. The in-sandbox egress half of this check (node's global fetch reaching the emulator's own S3 address) is already open as 20261121T130631Z-lambda-s3-a-nodejs22-x-handler-s-global.md and is not re-filed here.
  Traces:   lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected (_tamper, on the URL returned by generate_presigned_url).
