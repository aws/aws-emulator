# ElastiCache: 2 net-new causes — replication-group node ReadEndpoints are published as the bare loopback literal 127.0.0.1 and do not resolve inside the VPC, and a revoked security-group ingress rule is enforced by resetting an established connection instead of dropping the connect

> _Note: this issue was identified against the code base at commit `50a80390bb1e2ddab0fc937c65e59ad0dcd543f4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeReplicationGroups

## Description
Two net-new root causes grounded in the four failing `elasticache` behavioral checks that the replay report binds to no open issue and does not mark ALREADY FILED. THIS BUNDLE CARRIES 2 CAUSES (Cause 1 of 2 .. Cause 2 of 2); both must be closed before submitting.

Cause 1 of 2 — every NodeGroupMembers[].ReadEndpoint.Address of a cluster-mode-disabled replication group is published as the bare loopback IP literal `127.0.0.1`, and that published address does not resolve from inside the group's own VPC: the VPC resolver answers rcode 2 (SERVFAIL). Failing checks: elasticache.replication-group-node-and-reader-endpoints-resolve-to-node-addresses, elasticache.replication-group-primary-endpoint-follows-the-promoted-replica, elasticache.deleted-replication-group-endpoints-stop-resolving-rejected.
AWS: Smithy com.amazonaws.elasticache#NodeGroupMember$ReadEndpoint -> Endpoint, documented 'The information required for client programs to connect to a node for read operations. The read endpoint is only applicable on Valkey or Redis OSS (cluster mode disabled) clusters.'; com.amazonaws.elasticache#Endpoint$Address is documented 'The DNS hostname of the cache node.' and the Endpoint structure 'Represents the information required for client programs to connect to a cache node.' Recorded behavior: once DescribeReplicationGroups reports Status 'available' with one NodeGroup whose NodeGroupMembers each carry CurrentRole, PreferredAvailabilityZone and a ReadEndpoint, an A query for each member's ReadEndpoint.Address sent to the VPC resolver (the VPC CIDR base + 2) from inside that VPC is answered rcode 0 with exactly ONE A record; that address lies inside the CIDR of the subnet of the member's PreferredAvailabilityZone, and the members' addresses are distinct from one another. The requirement is the shape of the answer (a DNS hostname that the serving environment's own resolver answers, one A record per node, in that node's subnet, distinct per node) — not any particular hostname or address, which is per-environment.
Emulator: the member host read straight out of the response is the string '127.0.0.1' for the node, i.e. an IP literal rather than a DNS hostname, and the query for it is answered rcode 2: 'AssertionError: node endpoint 127.0.0.1 answered rcode 2, expected 0'. Because it is loopback it is also outside every subnet CIDR of the group's VPC and identical for every member, so the follow-on requirements (one address per node, inside the node's zone subnet, distinct per node) cannot hold either.
Why: a client that provisions a replication group and reads NodeGroupMembers[].ReadEndpoint.Address to open a read connection to a specific node — the only documented way to address one replica — gets a name its resolver will not answer, and if it uses the literal it is pointed at its own loopback instead of the cache node. Reader-endpoint load spreading, per-node read routing and 'the promoted node keeps its own node address across a failover' are all unobservable, and the deleted-group check can never reach its real assertion (that the endpoints STOP resolving after DeleteReplicationGroup) because they never resolved.
Fix: the elasticache replication-group endpoint synthesis (the NodeGroup/NodeGroupMember projection in the service's state plus whatever registers cache names with the emulator's VPC resolver) must publish a per-node DNS hostname the emulator's own resolver answers with a single A record for that node's in-subnet address, instead of embedding a raw loopback literal in ReadEndpoint.Address. Related open issues that do NOT cover these check ids: 20261125T064538Z-elasticache-3-net-new-causes-a-3-shard.md (a 3-shard cluster-mode group's node endpoints all resolve to ONE address — there the names DO resolve) and 20261126T022331Z-elasticache-cluster-and-replication-group-reads-omit-deleteprotection.md Cause 3 (a memcached ConfigurationEndpoint.Address that is an amazonaws.com name the emulator does not own).
Traces: elasticache.replication-group-node-and-reader-endpoints-resolve-to-node-addresses, elasticache.replication-group-primary-endpoint-follows-the-promoted-replica, elasticache.deleted-replication-group-endpoints-stop-resolving-rejected.

Cause 2 of 2 — after the only security-group rule admitting tcp/6379 to a cache cluster is revoked, the cache endpoint still ACCEPTS the TCP connection and then resets it mid-session, instead of the connection attempt failing. Failing check: elasticache.elasticache-revoked-security-group-ingress-blocked-from-cache-data-plane.
AWS: recorded behavior only (no Smithy shape governs packet filtering). RevokeSecurityGroupIngress returns Return=true, DescribeSecurityGroups no longer reports the permission, and from then on a TCP connection attempt from a source the withdrawn rule used to admit never completes: the SYN is dropped at the network layer, so the client fails in connect() (timeout / unreachable) and no RESP byte is ever exchanged. The subsequent legs of the recorded behavior are that nothing the blocked attempt wrote exists (GET returns the null bulk $-1, EXISTS returns 0) and that restoring the rule restores both connectivity and the pre-revoke keyspace.
Emulator: the attempt does fail (ok=false), but at the wrong layer — 'AssertionError: [runner-outside-vpc] the blocked attempt failed at stage \'io\', expected \'connect\'. ... Full probe result: {'ok': False, 'stage': 'io', 'errno': 104, 'error': 'ConnectionResetError: [Errno 104] Connection reset by peer', ... 'replies': [], 'stopped_at': 0}'. So the emulator completes the TCP handshake on the cache endpoint and then resets the established connection rather than dropping the packet, which is the signature of an application-level kill, not of a withdrawn ingress rule.
Why: a client cannot distinguish a security-group misconfiguration from an engine crash or a mid-flight failover. Code and runbooks keyed on the AWS signal (connect timeouts ⇒ check the security group; resets ⇒ check the node/engine) diagnose the wrong fault, retry logic that treats ECONNRESET as a transient server-side blip retries forever against a network that will never admit it, and any test that asserts a revoked rule prevents the connection from being established fails.
Fix: the elasticache data-plane listener / the emulator's security-group enforcement path must refuse the connection before it is established for a source no ingress rule admits (drop or refuse the connect), instead of accepting and then resetting. Related open issue that does NOT cover this id: 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md lists this check under its Cause 1, but its replay key is pinned to the `_bring_up_executor#3` frame, which no longer matches — the in-VPC executor now stands up and the probe reaches the endpoint, so what this check now measures is the enforcement layer, not the absent executor.
Traces: elasticache.elasticache-revoked-security-group-ingress-blocked-from-cache-data-plane.
