# eventbridgev2: 4 net-new behavioral causes — CreateSubscriber's idempotency-mismatch and name-collision messages are emulator-authored, DeleteEventBus is not gated on existing subscribers, and a plain SQS-target subscriber never delivers

> _Note: this issue was identified against the code base at commit `fdfcfa2cda546449d36bf7f86b864972a870ca03`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSubscriber

## Description
Four distinct, net-new root causes on the bootstrapped eventbridgev2 service (sdkId EventBridgeV2, AWSEventsV2 v2025-05-15, protocol rpcv2Cbor, endpointPrefix eventsv2). They are independent and ALL FOUR must be fixed and re-replayed before this issue is closed. CreateSubscriber is now implemented (it answers 200 and refuses correctly classified errors), so these are the next layer of divergences on that operation, not the already-filed CreateSubscriber stub issue (20261104T183027Z-eventbridgev2-createsubscriber-stub.md / 20261109T163411Z-...-createsubscriber-answers-notimplemented-so-no-subscriber.md). Related open issues that do NOT cover these checks and do NOT carry their replay keys: 20261104T183027Z-eventbridgev2-2-net-new-behavioral-root-causes-the.md (same wording-defect family, but its Cause 1 is CreateEventBus's name-collision path, a different handler and a different code path), 20261110T210822Z-eventbridgev2-3-net-new-behavioral-causes-deleteeventbus-is.md (its Cause 1 is the DeleteEventBus gate on un-revoked EVENT SOURCES; Cause 3 below is the gate on SUBSCRIBERS, a different relation with a different AWS message), and 20261113T094431Z-eventbridgev2-iam-sqs-9-net-new-causes-putevents.md (its Cause 3 covers only filtered / transformer / message-attribute / FIFO subscribers and explicitly states that PLAIN SQS-target delivery works; Cause 4 below shows the plain path does not deliver either, and is reported under the eventbridgev2 service heading).

=== Cause 1 of 4: CreateSubscriber's IdempotentParameterMismatchException message is emulator-authored and interpolates the token and the subscriber ARN ===
AWS: Smithy: CreateSubscriber declares IdempotentParameterMismatchException (@error client, @httpError 409, single member Message), documented "The request reuses the client token of an earlier request with different parameters. Use a new client token, or resend the earlier request unchanged."; ClientToken is @idempotencyToken (@length 1-64, @pattern ^[\u0021-\u007E]+$), so a replay with the SAME token and the SAME parameters must return the first subscriber's ARN, and the same token with ANY other parameter (a Description that was not sent before, a different Name) is this mismatch. Recorded behavior: AWS refuses with error code IdempotentParameterMismatchException and Message exactly "ClientToken was used by a previous request with different parameters". That message is entirely FIXED text — AWS interpolates nothing from the request or from state: no token, no name, no ARN. The refused replay must also leave the first subscriber untouched (ListSubscribers still shows exactly one, and its Description is still absent).
Emulator: the status and the error code are right, but the message is a sentence the handler composes from the request and from its own state, of the form "ClientToken <token> was already used to create subscriber <existing subscriber ARN> with different parameters". The replay shows ('IdempotentParameterMismatchException', 'ClientToken sim2real-behav-stok-8cfa99862255 was already used to create subscriber arn:aws:events:us-west-2:000000000000:subscriber/sim2real-behav-ebv2-sub-0ab2de89c091a/a6y1i0nxgj5r0gn9kuhztbefi with different parameters'). In that value the token, the account, the region, the subscriber name and the 25-char id are this run's request and state filling the emulator's own template; the defect is the wording and the interpolation, not those particular values.
Why: the error message is part of the contract. A client or test that asserts on, logs or parses AWS's constant sentence sees different text from the emulator, and the emulator additionally leaks the colliding subscriber's ARN into a message AWS deliberately keeps constant — so code that learns to read an ARN out of this message against the emulator has nothing to read against AWS.
Fix: the CreateSubscriber handler's client-token replay path and the shared IdempotentParameterMismatchException construction it uses must emit the constant message AWS words for this error class instead of formatting the token and the existing ARN into it. Code: services/service-com-amazonaws-eventbridgev2-awseventsv2/src/ops/create_subscriber.rs:325-341.
Traces: eventbridgev2.create-subscriber-client-token-replay-idempotent-and-mismatch-rejected.

=== Cause 2 of 4: CreateSubscriber's ResourceAlreadyExistsException message is emulator-authored and interpolates the name and the existing ARN ===
AWS: Smithy: CreateSubscriber declares ResourceAlreadyExistsException (@error client, @httpError 409, single member Message), documented "A resource with the same name already exists."; Name is @required (@length 1-256, @pattern ^[A-Za-z0-9][\.\-_A-Za-z0-9]*$). Recorded behavior: a second CreateSubscriber using a name already held on the SAME bus (with a fresh ClientToken, so it is a collision and not a replay) is refused with error code ResourceAlreadyExistsException and Message exactly "Resource already exists" — entirely FIXED text, with no variable part; the same name on ANOTHER bus is accepted.
Emulator: the status and the error code are right; the message is the handler's own sentence of the form "subscriber <Name> already exists as <existing subscriber ARN>". The replay shows ('ResourceAlreadyExistsException', 'subscriber sim2real-behav-ebv2-sub-a3fa0af14f8b already exists as arn:aws:events:us-west-2:000000000000:subscriber/sim2real-behav-ebv2-sub-a3fa0af14f8b/112c83dgia6nskdcry8smgk4t') — the name, account, region and 25-char id there are this run's values, not the requirement.
Why: same contract break as Cause 1 — an assertion or log matcher on AWS's constant "Resource already exists" fails, and the emulator leaks a generated resource id AWS never puts in this message. (Note for the fixer: the emulator also scopes the collision per REGION rather than per bus, at create_subscriber.rs:359 `subscriber_by_name(&region, &input.name)`. The check only proves the same-bus refusal and the other-bus acceptance, so the per-bus scoping must be preserved when the wording is fixed.)
Fix: the CreateSubscriber handler's name-collision path and the shared ResourceAlreadyExistsException construction it uses. Code: services/service-com-amazonaws-eventbridgev2-awseventsv2/src/ops/create_subscriber.rs:359-369. Same wording-defect family as 20261104T183027Z-eventbridgev2-2-net-new-behavioral-root-causes-the.md Cause 1 (CreateEventBus), but a different handler and code path, so it is not closed by that fix.
Traces: eventbridgev2.subscriber-name-collision-on-same-bus-rejected-but-allowed-on-another.

=== Cause 3 of 4: DeleteEventBus succeeds on a bus that still has a subscriber, instead of refusing with ResourceInUseException ===
AWS: Smithy: DeleteEventBus declares ResourceInUseException (@error client, @httpError 409), documented "The resource is in use and cannot be deleted. For example, an event bus with subscribers or event sources cannot be deleted until they are deleted." Recorded behavior: while a subscriber exists on the bus and has not been revoked, DeleteEventBus is refused with code ResourceInUseException and Message "The event bus cannot be deleted because it has one or more subscribers that are not revoked. Delete or revoke them and retry." — entirely FIXED text, interpolating nothing from the request or state. The refused delete must leave the bus State == ACTIVE; after DeleteSubscriber the very same DeleteEventBus call succeeds, which is what proves the block is scoped to the subscriber and not to the bus.
Emulator: DeleteEventBus answers HTTP 200 with an empty rpc-v2-cbor body (content-length 2) and moves the bus to DELETING even though a subscriber exists; no error is raised. The handler goes straight from the bus lookup to the DELETING transition with no in-use gate on the bus's children at all.
Why: a client relying on AWS's ordering constraint ("delete the subscribers, then the bus") can never observe the guard against the emulator, and the emulator destroys a bus AWS would have kept — the subscriber's parent bus disappears underneath it (settle_lifecycles then forgets the subscribers of the deleted bus), so account state diverges from that point on and every error branch keyed on ResourceInUseException/409 is dead code.
Fix: the DeleteEventBus handler's pre-delete validation and the bus/subscriber relation in service state — refuse with the modeled ResourceInUseException while any non-revoked subscriber is attached to the bus, leaving the bus untouched. Code: services/service-com-amazonaws-eventbridgev2-awseventsv2/src/ops/delete_event_bus.rs:160-182 (lookup straight to the DELETING transition) and src/state.rs:296 (`subscribers`) / state.rs:351 (`forget_subscribers_of_bus`). The event-source half of this gate is a different cause filed as 20261110T210822Z-eventbridgev2-3-net-new-behavioral-causes-deleteeventbus-is.md Cause 1, with a different message ("...one or more event sources that are not revoked..."); both gates must exist, each with its own wording.
Traces: eventbridgev2.delete-event-bus-with-subscriber-rejected-until-removed.

=== Cause 4 of 4: a subscriber with a plain SQS target never delivers a published event to its queue ===
AWS: Smithy/recorded behavior: CreateSubscriber "Creates a subscriber on an event bus, which delivers matching events to the configured target", and a fresh subscriber is returned State RUNNING. Recorded behavior: with InvokeConfiguration {RoleArn, TargetArn: <sqs queue arn>, SqsParameters: {}}, a PutEvents entry accepted on the ACTIVE bus (FailedEntryCount 0) becomes one SQS message within seconds, whose Body is the classic EventBridge envelope — source = the entry's Source, detail-type = the entry's DetailType, detail = the entry's Detail parsed as JSON, account = the bus's account, plus version/id/time/region. The delivered envelope's own id is a bus-minted delivery id, not the PutEvents EventId.
Emulator: nothing ever arrives on the target queue. The check creates the bus (ACTIVE), the queue (with a policy allowing events.amazonaws.com sqs:SendMessage), the delivery role (allowing sqs:SendMessage on that queue) and the subscriber, then republishes a marked entry every 10 s while long-polling the queue (ReceiveMessage WaitTimeSeconds=5) — and exhausts its whole 60 s budget without ever seeing the marker, i.e. roughly six accepted publishes produced zero messages. The bus lifecycle span is only 500 ms (state.rs:57 LIFECYCLE_SPAN), so the budget was spent waiting for a delivery, not for provisioning. Note that the delivery path swallows its own failures: every failure mode in services/service-com-amazonaws-eventbridgev2-awseventsv2/src/state/subscriber_delivery.rs (unparseable TargetArn at 92-100, unrecognised vendor at 118-123, unbuildable entry at 193-200, failed SendMessageBatch entries at 202-210) only emits a tracing::warn!, so a dropped delivery is silent to the client.
Why: the whole EventBridge v2 -> SQS fan-out is unobservable for the simplest possible subscriber shape: a client publishes successfully, gets EventIds and SuccessCode PUBLISHED, and its consumer waits forever on an empty queue with no error anywhere to explain it. Every downstream assertion on the delivered envelope (source, detail-type, detail, account) is unreachable.
Fix: the eventbridgev2 subscriber delivery path — the deliveries PutEvents/CreateSubscriber make due (ops/put_events.rs:357 take_due_deliveries, ops/create_subscriber.rs:234 deliver_due) and the SQS leg that performs them (src/state/subscriber_delivery.rs:52-230 deliver_due / deliver_to_target / send_to_queue, including the queue-URL derivation and the in-process SendMessageBatch call); a send that fails must not be discarded silently. Note the FIXED issue 20261109T155235Z-sqs-events-published-to-an-eventbridgev2-bus-are.md claimed this delivery leg: its fix added the delivery code but a published event still does not land on a plain SQS target in this build.
Traces: eventbridgev2.subscriber-put-events-delivers-to-sqs.
