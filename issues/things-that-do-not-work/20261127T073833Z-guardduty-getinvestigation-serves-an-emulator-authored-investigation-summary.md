# GuardDuty GetInvestigation serves an emulator-authored Investigation.Summary that does not match the shape of GuardDuty's investigation summary

> _Note: this issue was identified against the code base at commit `929983b8776c4202c2a162ee50b02314bb9b729f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetInvestigation

## Description
One cause (1 of 1), in the GuardDuty investigation-analysis state: the text this emulator puts in `Investigation$Summary` is its own composed Markdown report, and it does not match the shape the recorded GuardDuty response for the same read carries. The whole rest of the response agrees — HTTP 200 on both sides and `$.investigation.summary` is the ONLY diverging key in the cluster, so `investigationId`, `status`, `triggerPrompt`, `triggeredBy`, `metadata`, `cloud`, `riskLevel`, `risk`, `confidence`, `startTime` and `endTime` all replay clean.

AWS: Smithy `com.amazonaws.guardduty#Investigation$Summary` (jsonName `summary`, target `com.amazonaws.guardduty#String`, optional, no length/pattern constraint) is documented as "A structured summary of the investigation findings, including affected resources, threat assessment, and recommended remediation steps"; it is served inside `GetInvestigation`'s required `investigation` member (GET /detector/{DetectorId}/investigation/{InvestigationId}, success 200, errors AccessDeniedException 400/403, BadRequestException 400, InternalServerErrorException 500, ResourceNotFoundException 404). Beyond that one sentence the model states nothing about the member's content, so for the text itself this is RECORDED BEHAVIOR ONLY: the fixture carries the recorded GuardDuty summary as a SHAPED, non-asserted expectation (the replay reports expected `<shaped-not-asserted>`), i.e. the prose is produced per investigation and only its shape is a requirement, not any one run's words. The requirement is therefore: the `summary` member of a COMPLETED investigation is GuardDuty's structured investigation summary — covering the documented parts (the findings analysed, the affected resources, the threat assessment, the recommended remediation) — in GuardDuty's own form, with the variable parts (the trigger prompt, the finding counts, the account, the Region, the severities and the finding types) taken from the request and from the detector's state. The values in the recording and in the replayed response (the prompt text, account `000000000000`, Region `us-west-2`, a zero-finding account) are fill-ins for that template and are NOT part of it.

Emulator: the response's `$.investigation.summary` is a four-section Markdown document composed by this crate's own template. Replayed verbatim it was `"## Investigation summary\nGuardDuty investigated the request \"<TriggerPrompt>\" and analysed 0 findings in account <account> (<region>), assessing the activity as Info risk.\n\n## Affected resources\nNone: the pass analysed no findings, so no resource was implicated.\n\n## Threat assessment\nNo GuardDuty findings had been produced for this account and Region when the pass ran, so there was no threat activity to assess and the risk is Info.\n\n## Recommended remediation\n1. Keep GuardDuty enabled so later activity is analysed.\n"` — the fixed text being the four `## `-prefixed headings, the sentence frames ("GuardDuty investigated the request ... and analysed N finding(s) in account A (R), assessing the activity as L risk.", the "None: the pass analysed no findings..." / "No GuardDuty findings had been produced..." empty-account sentences and the numbered remediation step), and the variable parts being the trigger prompt, the finding count, the account, the Region and the risk level. That string is what fails the fixture's shaped expectation for the member; the status code and every other member match.

Why: `summary` is the member a caller displays or parses to learn what an investigation concluded. A client written against AWS — one that renders GuardDuty's summary, or scrapes it for the affected resources / assessment / remediation parts the documentation names — is handed an emulator-authored narrative with the emulator's own headings and sentences instead, so any parse keyed to GuardDuty's form finds nothing and any rendered output is wrong text attributed to GuardDuty. Because the rest of the response is correct, the defect is invisible until the summary's content is actually consumed.

Fix: the `Investigation$Summary` production in this crate's investigation-analysis state (the summary composition reached when the clock settles an investigation and stores its conclusions), not the `GetInvestigation` handler, which only copies the stored value onto the wire. The sibling conclusion members built in the same place (`risk`, `riskLevel`, `confidence`) already replay clean, so only the summary text needs to be brought onto GuardDuty's shape; keep it derived from the investigation's own prompt, account, Region and analysed findings rather than from the read request.

Traces: guardduty-tagging-created-with-tags#setup#4 (representative) and guardduty-tagging-round-trip#setup#4 — the same cluster, divergence key `service=guardduty|GetInvestigation|status=200->200|keys=$.investigation.summary`.
