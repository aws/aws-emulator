Failing check: config__sqs.config-stopped-recorder-records-no-configuration-item-until-restarted.

AWS: Smithy (com.amazonaws.configservice#StarlingDoveService) — ConfigurationRecorderStatus.lastStatus targets the RecorderStatus enum with values Pending | Success | Failure | NotApplicable, documented as 'The status of the latest recording event processed by the recorder', alongside lastStatusChangeTime ('The time of the latest change in status of an recording event processed by the recorder'), lastStartTime, lastStopTime, recording (boolean, default false), lastErrorCode and lastErrorMessage. DescribeConfigurationRecorderStatus takes optional ConfigurationRecorderNames/ServicePrincipal/Arn, returns ConfigurationRecordersStatus (HTTP 200) and declares only NoSuchConfigurationRecorderException / ValidationException (client, HTTP 400). StartConfigurationRecorder takes required ConfigurationRecorderName (@length 1..256), returns an empty output (HTTP 200) and declares NoAvailableDeliveryChannelException / NoSuchConfigurationRecorderException / UnmodifiableEntityException (client, HTTP 400). GetResourceConfigHistory takes required resourceType (enum ResourceType) and resourceId (@length 1..768) plus laterTime/earlierTime/chronologicalOrder/limit (@range 0..100)/nextToken, returns configurationItems (ConfigurationItemList) + nextToken, and declares InvalidLimitException / InvalidNextTokenException / InvalidTimeRangeException / NoAvailableConfigurationRecorderException / ResourceNotDiscoveredException / ValidationException (client, HTTP 400). For the recording side effect itself the model says nothing — recorded behavior only: on AWS, once ANY recording event has been processed by a recorder, lastStatus is 'Success' (not 'Pending') and lastStatusChangeTime is set; and once a stopped recorder is started again, recording resumes for the types its recordingGroup covers, so a change to an existing SQS queue causes Config to write a NEW configuration item for resourceType AWS::SQS::Queue whose `configuration` document carries the CHANGED attribute value, whose resourceName is that queue's name and whose configurationItemCaptureTime is AFTER the restart instant — GetResourceConfigHistory(resourceType='AWS::SQS::Queue', resourceId=<queue url>) then answers HTTP 200 with a non-empty configurationItems list. Nothing is backfilled for the stopped window. Where a resource genuinely is absent from Config's state, GetResourceConfigHistory answers HTTP 400 ResourceNotDiscoveredException with message `Resource <resourceId> of resourceType:<resourceType> is unknown or has not been discovered` — fixed text `Resource `, ` of resourceType:` and ` is unknown or has not been discovered`, with resourceId and resourceType substituted verbatim from the request.

Emulator: the legs BEFORE the restart behave correctly in this replay and isolate the defect — (a) the calibration barrier passed: a queue created while the recorder was RUNNING did acquire an AWS::SQS::Queue configuration item, so the recording pass processed a recording event; (b) StopConfigurationRecorder is honoured: the queue created during the stopped window is correctly undiscovered and GetResourceConfigHistory answers HTTP 400 ResourceNotDiscoveredException with Config's exact message (the check asserts that message byte-for-byte and that assertion passed); (c) StartConfigurationRecorder succeeds and DescribeConfigurationRecorderStatus reports recording=true. What diverges is the status the emulator itself returns at the moment of failure: DescribeConfigurationRecorderStatus answers [{'name': <recorder name>, 'recording': True, 'lastStatus': 'Pending', 'lastErrorCode': None, 'lastErrorMessage': None}] — lastStatus still 'Pending' although this very recorder had already recorded a configuration item in the same run, so it can never have been merely 'awaiting its first event'. The check's post-restart expectation (an item for the sqs:SetQueueAttributes change on the same queue) is reported unmet. HONEST SCOPE OF THIS RUN: the harness message is `... not met within 480s. Last result: None`, and `Last result: None` means the poll body never executed once — the wait is capped by ctx.time_left() minus a 10 s reserve, and the Config recorder/delivery-channel setup plus the calibrated absence window had consumed the per-check budget, so in THIS replay GetResourceConfigHistory was not actually re-read after the restart. What is grounded here is the emulator's own recorder status (recording=true, lastStatus pinned at 'Pending', no lastStatusChangeTime, no error) and the fact that the whole budget was consumed before the repair leg could read. The post-restart no-recording facet is the identical signature the two now-fixed issues above recorded with a full 480 s poll; it is named here as part of the same root cause, not as independently re-measured in this run. Hypothesis (neither the model nor the recording separates them): either StartConfigurationRecorder does not re-arm the recording pass after a stop and only flips the recording flag, or the recording pass captures resource CREATION only and never a configuration change to an existing resource; in either case the status machine behind lastStatus is not wired to recording events at all. Queue urls, queue and recorder names, the account id, the VisibilityTimeout values and the 480 s window are per-run values and are not part of the requirement.

Why: a client that stops recording for a maintenance window and starts it again gets a recorder that reports itself healthy — recording=true, no lastErrorCode, no lastErrorMessage — while nothing warns that it is inert. Anything that gates on lastStatus == 'Success' (the documented signal that a recording event was processed) to confirm the recorder came up waits on 'Pending' forever, and lastStatusChangeTime never gives a caller a point to measure staleness from. Because the post-restart change is not recorded, ResourceNotDiscoveredException becomes the answer to every GetResourceConfigHistory call for that resource, so a caller cannot distinguish 'this resource never existed' from 'Config stopped recording when I restarted it', and drift/audit/compliance tooling that waits for a resource's post-change snapshot blocks indefinitely.

Fix: the configuration-recorder status machine and recording pass in the configservice crate — the state behind DescribeConfigurationRecorderStatus must advance lastStatus out of 'Pending' to 'Success' (and set lastStatusChangeTime) whenever a recording event is processed, and must not report 'Pending' for a recorder that has already recorded items; StartConfigurationRecorder's handler must re-arm the recording pass for the recorder's recordingGroup after a stop rather than only flipping the recording flag; the pass must capture configuration CHANGES to already-existing resources of other emulated services (here AWS::SQS::Queue attribute changes owned by the SQS crate), not creations only; and GetResourceConfigHistory's handler must project those items — reserving ResourceNotDiscoveredException for ids genuinely absent from that state — without backfilling any item whose capture time falls inside the stopped window.
