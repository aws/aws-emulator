# rds parameter-group reads are served from the emulator's own parameter catalog, not the engine's (4 causes)

> _Note: this issue was identified against the code base at commit `92e6b2d8a55271b9e46b89d4e3342f522bc16f2a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBClusterParameters

## Description
This bundle carries 4 net-new causes, all on rds and all 200->200 content divergences on the parameter-group read surface (DescribeDBClusterParameters and DescribeDBParameters). They share ONE fault: the emulator's DB and DB-cluster parameter-group state is a bag of whatever a client wrote, decorated by an emulator-authored description table, rather than a projection of the engine-default parameter catalog for the group's DBParameterGroupFamily. Consequently the rows a Describe returns, the catalog attributes on each row and the description text on each row are all the emulator's own, and a narrowed read can return no rows at all. A fixer must close all FOUR causes below before submitting.

Smithy used throughout (services/service-com-amazonaws-rds-amazonrdsv19): DescribeDBParameters(DescribeDBParametersMessage{DBParameterGroupName required, Source, Filters, MaxRecords, Marker}) -> DBParameterGroupDetails{Parameters: ParametersList, Marker}; DescribeDBClusterParameters(DescribeDBClusterParametersMessage{DBClusterParameterGroupName required, Source, Filters, MaxRecords, Marker}) -> DBClusterParameterGroupDetails{Parameters: ParametersList, Marker}; both error DBParameterGroupNotFoundFault (awsQueryError DBParameterGroupNotFound, 404). Shape Parameter members: ParameterName, ParameterValue, Description ('Provides a description of the parameter.'), Source ('The source of the parameter value.'), ApplyType ('Specifies the engine specific parameters type.'), DataType ('Specifies the valid data type for the parameter.'), AllowedValues ('Specifies the valid range of values for the parameter.'), IsModifiable ('Indicates whether (true) or not (false) the parameter can be modified.'), MinimumEngineVersion, ApplyMethod, SupportedEngineModes. ModifyDBClusterParameterGroup(ModifyDBClusterParameterGroupMessage{DBClusterParameterGroupName required, Parameters required}) -> DBClusterParameterGroupNameMessage, errors DBParameterGroupNotFoundFault (404) and InvalidDBParameterGroupStateFault (400).

=== Cause 1 of 4: a DescribeDBClusterParameters read returns a group member whose name the engine catalog does not define ===
AWS: a DB cluster parameter group's membership is the engine-default parameter catalog for its family; a name outside that catalog can never become a member, because the write is refused. Recorded behavior for the write (same fixture, step task#5): 400 with ErrorResponse.Error{Type 'Sender', Code 'InvalidParameterValue', Message 'Could not find parameter with name: <ParameterName>'} - the fixed text is 'Could not find parameter with name: ' and the only variable part is the ParameterName taken from the request. So the Describe that follows returns exactly the catalog parameters the client actually changed: in the recording one Parameter row, log_min_duration_statement, carrying ParameterValue, Source 'user', ApplyMethod 'immediate' AND the catalog attributes Description, ApplyType 'dynamic', DataType 'integer', AllowedValues '-1-2147483647', IsModifiable 'true'. Because the list has exactly one element the recorded awsQuery XML carries a single <Parameter> child.
Emulator: 200 with TWO Parameter children - the real catalog row plus an extra row for the name that should never have been admitted (recorded run: ParameterName 'rdsenv_no_such_parameter', ParameterValue '1', Source 'user', ApplyMethod 'immediate', SupportedEngineModes member 'provisioned') which carries none of the catalog attributes because the emulator has no catalog entry to draw them from. The whole Parameters element therefore diverges as a type_mismatch (a single Parameter structure in the recording against a 2-element list from the emulator).
Why: a client that reads a parameter group back to verify what it applied sees a parameter that does not exist for the engine. Code that iterates the group and dereferences Parameter.DataType/AllowedValues/IsModifiable (a tuning UI, a drift detector, a compliance report) hits a row with those members absent and fails where it succeeds against AWS; a configuration-drift comparison reports a member AWS would never list.
Fix: the rds crate's DB-cluster parameter-group state together with ModifyDBClusterParameterGroup's validation - refuse a ParameterName that is not in the family's engine-default catalog at write time, and project Describe rows from that catalog so an unknown name can never become a member.
Traces: rds-cluster-parameter-group-mutation-envelopes#task#8. (In the same fixture, the missing 400 refusal at task#5 is owned by open issue 20261111T091517Z-rds-control-plane-refusals-are-missing-or-carry.md and the description-text mismatch at task#6 by 20261030T001542Z-rds-engine-parameter-and-event-category-catalogs-are.md; neither covers the membership of this task#8 read, which the replay reports unowned.)

=== Cause 2 of 4: DescribeDBParameters serves an emulator-authored Description instead of the RDS catalog's text ===
AWS: Parameter.Description is catalog data - 'Provides a description of the parameter.' (Smithy, shape Parameter). For the mysql-family parameter in the recording (back_log) the catalog text is 'The number of outstanding connection requests MySQL can have', with no trailing period; recorded behavior only for the exact string. The whole string is fixed text drawn from the engine-default catalog for the group's family - it has no variable part, so it is a requirement in full, not a per-run value.
Emulator: 200, same row, Description 'The number of outstanding connection requests the server can have.' - a re-worded, period-terminated paraphrase that never appears in AWS's catalog.
Why: the description is the only human-readable explanation a client gets for a parameter. Tooling that renders it, diffs it against a stored catalog snapshot, or generates documentation from a Describe sees text AWS never emits, and a parameter-catalog comparison between the emulator and AWS reports a difference on essentially every row.
Fix: the rds crate's engine-default parameter catalog data (the description column for each family's parameters), consumed by the DescribeDBParameters projection. The catalog text must be the engine-default text RDS publishes, not a locally written paraphrase.
Traces: rds-parameter-group-enforcement#task#7.

=== Cause 3 of 4: DescribeDBParameters returns a user-modified row with none of its catalog attributes ===
AWS: every Parameter in a DescribeDBParameters response carries the catalog-derived members as well as the written ones, including on a Source='user' row. For the postgres-family float parameter in the recording (random_page_cost): AllowedValues '0-1.79769e+308', ApplyType 'dynamic', DataType 'float', IsModifiable 'true', Description 'Sets the planners estimate of the cost of a nonsequentially fetched disk page.' (Smithy: Parameter.AllowedValues/ApplyType/DataType/IsModifiable/Description as quoted in the preamble; the attribute VALUES are catalog facts for that parameter, not per-run values).
Emulator: 200, and all five of AllowedValues, ApplyType, DataType, Description and IsModifiable are absent from the row - only what the client wrote survives.
Why: those five members are how a client decides whether it may touch a parameter at all: validating a candidate value against AllowedValues/DataType, deciding from ApplyType whether the change needs a reboot, hiding non-modifiable parameters via IsModifiable. Against the emulator each of those reads is None, so the check is skipped or the dereference raises, where against AWS it succeeds.
Fix: the rds crate's DB parameter-group state plus the DescribeDBParameters projection - seed the group from the engine-default catalog keyed by DBParameterGroupFamily, keep client writes as overlays (Source='user', ApplyMethod) and merge the catalog attributes onto every projected row.
Traces: rds-parameter-numeric-precision-round-trip#task#3. Related but NOT covering it: open issue 20261108T233943Z-rds-describedbparameters-omits-every-engine-default-parameter-attribute-and.md owns the same omission on the engine-default pages of the rds-db-parameters-pagination fixture; this user-modified-row cluster in a different fixture is reported unowned by the replay and is not closed by that issue's fix unless the overlay path is fixed too.

=== Cause 4 of 4: a narrowed DescribeDBClusterParameters read answers an empty Parameters element where AWS returns the group's modified parameters ===
AWS: 200 with Parameters carrying the group's two modified rows - in the recording log_min_duration_statement (ParameterValue '1000', ApplyMethod 'immediate', ApplyType 'dynamic', DataType 'integer', AllowedValues '-1-2147483647', IsModifiable 'true', Source 'user') and rds.logical_replication (ParameterValue '1', ApplyMethod 'pending-reboot', ApplyType 'static', DataType 'boolean', AllowedValues '0,1', IsModifiable 'true', Source 'user'). Smithy: DescribeDBClusterParameters -> DBClusterParameterGroupDetails.Parameters, narrowed by the request's Source/Filters; a row written by ModifyDBClusterParameterGroup has Source 'user' and must be selected by a user-scoped read.
Emulator: 200 with an EMPTY Parameters element (serialized as the empty string, i.e. no Parameter children at all). The rows do exist in the emulator's group - step task#9 of the same fixture returns both of them - so this later, narrowed read drops them. Hypothesis: the request narrows the read (a Source and/or Filters selection) and the emulator's selection logic does not match rows produced by ModifyDBClusterParameterGroup, so it matches nothing.
Why: reading back only the parameters one changed is the normal way to confirm a hardening or compliance change landed. Against the emulator that read reports an untouched group, so a client concludes its ModifyDBClusterParameterGroup had no effect (or that the setting must be re-applied) where against AWS it sees both parameters with their ApplyMethod, including the pending-reboot one it must act on.
Fix: the DescribeDBClusterParameters handler's Source/Filters selection in the rds crate, over the same catalog-plus-overlay state the other three causes need - a user-scoped read must return every overlay row, projected with its catalog attributes.
Traces: rds-refarch-aur-cluster-parameter-hardening-route#task#10. (task#2, task#3, task#6 and task#9 of that fixture are owned by open issues 20261102T104537Z-rds-cluster-parameter-group-and-catalog-reads-answer.md and 20261030T001542Z-rds-engine-parameter-and-event-category-catalogs-are.md; this task#10 cluster is reported unowned.)
