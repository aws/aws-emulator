# outposts success responses omit members AWS always projects

> _Note: this issue was identified against the code base at commit `7f3d8acfd1d18a62a70e68f35eeb77bb7bd3316f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSite

## Description
3 net-new root causes, all the same fault: a 2xx response of this service projects a stored resource WITHOUT a member AWS always reports for it, so the member comes back absent where AWS sends it (present-but-empty for a structure, defaulted for an enum). None of the three is covered by the open issues 20261122T134654Z-outposts-response-projections-diverge-createoutpost-availability-zone-identity (CreateOutpost AvailabilityZoneId value and UpdateSite tags), 20261029T191039Z-outposts-lifecycle-and-precondition-gates-diverge-across-capacity (status/precondition gates, renewal pricing) or 20261121T145507Z-outposts-listcatalogitems-publishes-an-invented-hardware-catalog-instead (the published catalog): those are about other members and other operations.

Cause 1 of 3: CreateSite answers a Site with no RackPhysicalProperties member when the request supplied none.
AWS: Smithy CreateSite (POST /sites, success 200) -> CreateSiteOutput{SiteId, Site}; Site$RackPhysicalProperties (target RackPhysicalProperties, doc "Information about the physical and logistical details for a rack at the site."), and RackPhysicalProperties is a structure of nine optional enum members (PowerDrawKva, PowerPhase, PowerConnector, PowerFeedDrop, UplinkGbps, UplinkCount, FiberOpticCableType, OpticalStandard, MaximumSupportedWeightLbs). The model marks the member optional and documents no default, so this is recorded behavior only: the recorded 200 for a CreateSite that supplies no RackPhysicalProperties carries the member PRESENT on the answered Site, as a structure with no member set — the site has a rack-properties record from the moment it exists, it is simply unfilled. The requirement is the member's PRESENCE in the projection, not any particular enum value inside it.
Emulator: 200 with the same Site, but $.Site.RackPhysicalProperties is absent — the replay reports `$.Site.RackPhysicalProperties: missing (expected {}, got None)`. The handler assigns the request's member straight through (`rack_physical_properties: input.rack_physical_properties`), so an omitted input means an omitted output member.
Why: a client that reads site.rackPhysicalProperties off a freshly created site (to fill in power/uplink details, or to diff a site against a desired rack configuration) gets a null structure instead of an empty one, so SDK code that dereferences the sub-structure without a null guard — which is safe against AWS — faults, and a site that AWS reports as "rack properties not yet specified" is indistinguishable from "no such concept".
Fix: the Site projection in the CreateSite handler — services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/create_site.rs (the `Site { ... rack_physical_properties: input.rack_physical_properties }` literal around line 196) and whatever the store keeps for a site's rack properties, so a stored site always projects a present RackPhysicalProperties structure (empty when nothing was supplied), and the same projection is used by every later read of the site.
Traces: outposts-cancel-capacity-task-malformed-identifiers#setup#1, and setup#1 of outposts-new-outpost-capacity-and-connectivity-reads and outposts-start-capacity-task-unknown-references.

Cause 2 of 3: CreateOutpost does not default SupportedHardwareType, so an Outpost created without one reports no hardware type.
AWS: Smithy CreateOutpost (POST /outposts, success 200) -> CreateOutpostOutput{Outpost}; input member SupportedHardwareType (enum SupportedHardwareType, values RACK|SERVER, optional) and Outpost$SupportedHardwareType (same enum, doc "The hardware type."). The model states no default, so this is recorded behavior only: the recorded 200 for a CreateOutpost that OMITS SupportedHardwareType answers an Outpost whose SupportedHardwareType is `RACK` — the rack form factor is what an Outpost is created as when the caller names none. (The fixtures that DO name a hardware type agree with the emulator, which is why only the omitting fixtures diverge.)
Emulator: 200 with the same Outpost, but $.Outpost.SupportedHardwareType absent — the replay reports `$.Outpost.SupportedHardwareType: missing (expected 'RACK', got None)`. The handler deliberately reports none when the caller named none (src/ops/create_outpost.rs: `supported_hardware_type: crate::state::non_empty(input.supported_hardware_type)`, commented "reports none rather than a guessed form factor"), and every later read of that Outpost repeats the absence.
Why: a client that branches on the Outpost's hardware type — rack vs server drives which capacity, asset and order operations make sense — sees an unset enum where AWS reports RACK, so form-factor-dependent logic takes the "unknown" path for every Outpost created with the default, and an Outpost round-tripped through create/read loses an attribute AWS treats as always present.
Fix: the Outpost projection and its stored record in the CreateOutpost handler — services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/create_outpost.rs (the `supported_hardware_type` assignment around line 277) — so an omitted SupportedHardwareType is persisted and reported as the recorded default RACK, which then flows through GetOutpost/ListOutposts.
Traces: outposts-cancel-capacity-task-malformed-identifiers#setup#2, and setup#2 of outposts-new-outpost-capacity-and-connectivity-reads and outposts-start-capacity-task-unknown-references.

Cause 3 of 3: GetPrivateConnectivityConfig answers an EMPTY body for an Outpost that has no private connectivity configured.
AWS: Smithy GetPrivateConnectivityConfig (GET /outposts/{OutpostId}/privateConnectivity, success 200) -> GetPrivateConnectivityConfigOutput{PrivateConnectivityConfig}, the structure PrivateConnectivityConfig{RoleArn, PrivateConnectivityStatus (ENABLED|DISABLED), VpcInformationList, ProvisioningRoleArn}. The member is optional in the model, so this is recorded behavior only: the recorded 200 for an Outpost nobody has called CreatePrivateConnectivityConfig on carries the PrivateConnectivityConfig member PRESENT in the body — an Outpost always has a private-connectivity configuration to report, it just has nothing set in it. The requirement is the member's presence; the recording asserts no values inside it.
Emulator: 200 with a completely empty JSON body — the replay reports `$: empty_body (expected {'PrivateConnectivityConfig': {}}, got {})`. The handler answers `private_connectivity_config: record.private_connectivity.clone()`, which is None for any Outpost CreatePrivateConnectivityConfig has not written (src/ops/get_private_connectivity_config.rs, around line 198; CreateOutpost stores `private_connectivity: None`), and the serializer then omits the member entirely.
Why: a client that reads the configuration to decide whether private connectivity must be enabled gets a null where AWS gives it a structure, so `getPrivateConnectivityConfig().privateConnectivityConfig().privateConnectivityStatus()` throws or short-circuits instead of reading an unset/DISABLED configuration, and "unconfigured Outpost" cannot be told apart from "no answer".
Fix: the GetPrivateConnectivityConfig handler's output projection and the per-Outpost private-connectivity state it reads — services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/get_private_connectivity_config.rs together with the `private_connectivity` field of the Outpost record in src/state.rs — so an Outpost with nothing configured still answers a present PrivateConnectivityConfig, and an Outpost that was configured keeps answering exactly what CreatePrivateConnectivityConfig persisted.
Traces: outposts-new-outpost-capacity-and-connectivity-reads#task#3.
