# payment-cryptography-data: 7 net-new causes — ResourceNotFoundException.ResourceId is not account-qualified, KeyModesOfUse/KeyUsage/PIN-block ValidationException messages diverge, VerifyAuthRequestCryptogram skips the multiple-of-16 check, AMEX/dynamic GenerateCardValidationData is a stub

> _Note: this issue was identified against the code base at commit `a069a9a0ca52a06ec1b3b6edb1946a214c0d1090`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DecryptData

## Description
The Payment Cryptography data plane answers, but its refusal paths diverge from AWS in seven independent ways: the not-found resource identifier is unqualified across every key-resolution path, four distinct ValidationException message templates are the emulator's own wording rather than AWS's, one documented input rule is not enforced at all (so a malformed request is answered with a verification failure instead of a validation refusal), and one generation-attribute family of GenerateCardValidationData is still an unimplemented scaffold. 7 causes.

Cause 1 of 7 — ResourceNotFoundException.ResourceId omits the caller's account id on every key/alias resolution path.
AWS: KeyIdentifier on these operations is a KeyArnOrKeyAliasType (Smithy: @length 7..322, @pattern allows a bare `alias/...` as well as a full key/alias ARN), and the modeled error is ResourceNotFoundException at httpError 404 with a single member ResourceId: String, documented as "The resource that is missing." The wording of what goes INTO ResourceId is recorded behavior only: when a request names an alias that does not exist (never created, or deleted), AWS answers HTTP 404 with error code ResourceNotFoundException, an EMPTY Error.Message, and ResourceId built as the caller's 12-digit account id, a literal '/', then the alias name exactly as the request spelled it — i.e. the template `<accountId>/<aliasName>`. The account id and the alias name are the variable parts, taken from the caller's credentials and from the request's KeyIdentifier respectively; the separating '/' is fixed.
Emulator: same 404 and same empty message, but ResourceId carries ONLY the alias name as supplied (replay saw values such as 'alias/sim2real-pcd-decalias-…', length 38, with no account id and no slash separator). The same unqualified form appears on DecryptData, GenerateCardValidationData, GenerateMac, VerifyMac and VerifyAuthRequestCryptogram, so this is one shared not-found construction, not five handler bugs.
Why: ResourceId is the only machine-readable field in this error (the message is empty by design), so a client that reports or routes on the missing resource gets an identifier that is not account-scoped. Cross-account tooling cannot tell whose alias was missing, and any client that parses `<account>/<alias>` to recover the account id reads the literal 'alias' segment as the account instead. Negative-path assertions on the identifier fail against the emulator while passing against AWS.
Fix: the shared construction of ResourceNotFoundException in the key/alias resolution helper of the payment-cryptography-data service — qualify the resource with the request's account id before serializing ResourceId, for every operation that resolves a KeyIdentifier/IncomingKeyIdentifier/VerificationKeyIdentifier.
Traces: payment-cryptography-data.decrypt-data-unknown-alias-rejected, payment-cryptography-data.generate-card-validation-data-unknown-alias-not-found-rejected, payment-cryptography-data.generate-mac-alias-never-created-not-found-rejected, payment-cryptography-data.verify-mac-deleted-alias-rejected, payment-cryptography-data.verify-auth-request-cryptogram-unknown-key-rejected.

Cause 2 of 7 — the ValidationException message for a key whose KeyModesOfUse do not permit the operation is the emulator's own wording.
AWS: ReEncryptData and VerifyMac both take a KeyIdentifier and model ValidationException at httpError 400 (Smithy: ReEncryptData POST /keys/{IncomingKeyIdentifier}/reencrypt, VerifyMac POST /mac/verify; both list ValidationException 400 [defaulted], ResourceNotFoundException 404, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500). The refusal wording is recorded behavior only: when the named key exists but its KeyModesOfUse lack the mode the operation needs, AWS answers HTTP 400 / ValidationException with the message "KeyModesOfUse of the input key <keyArn> is invalid for the operation. Refer to https://docs.aws.amazon.com/payment-cryptography/latest/userguide/crypto-ops-validkeys-ops.html for valid key modes of use for this operation." Fixed text: "KeyModesOfUse of the input key " … " is invalid for the operation. Refer to https://docs.aws.amazon.com/payment-cryptography/latest/userguide/crypto-ops-validkeys-ops.html for valid key modes of use for this operation." The one variable part is the key ARN, resolved from the request's key identifier. AWS names neither the specific missing mode nor the operation.
Emulator: same 400 and same ValidationException code, but the message is "The KeyModesOfUse of key <keyArn> do not include <Mode>." — replay saw "The KeyModesOfUse of key <outgoing ARN> do not include Encrypt." for ReEncryptData's OutgoingKeyIdentifier and "The KeyModesOfUse of key <signer ARN> do not include Verify." for VerifyMac. Different fixed text, and it adds a mode name AWS never emits while dropping the documentation pointer AWS always emits.
Why: clients and operator tooling that match this sentence, or that surface it to a human to explain which permission set is wrong, see neither AWS's wording nor the userguide link that tells the operator which modes the operation accepts. The divergence is identical on two unrelated operations, so any mode-of-use negative test written against AWS fails against the emulator service-wide.
Fix: the shared key-modes-of-use validation error builder used by the ReEncryptData and VerifyMac handlers in the payment-cryptography-data service — emit AWS's template with the resolved key ARN as its only substitution.
Traces: payment-cryptography-data.re-encrypt-data-decrypt-only-outgoing-key-rejected, payment-cryptography-data.verify-mac-generate-only-key-mode-rejected.

Cause 3 of 7 — VerifyPinData's ValidationException for a key of the wrong KeyUsage substitutes the usage enum instead of the key ARN.
AWS: VerifyPinData (Smithy: POST /pindata/verify; VerificationKeyIdentifier required, KeyArnOrKeyAliasType; errors ValidationException 400 [defaulted], VerificationFailedException 400, ResourceNotFoundException 404, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500) refuses a verification whose VerificationAttributes do not match the key's KeyUsage — e.g. VisaPin attributes under a TR31_V1_IBM3624_PIN_VERIFICATION_KEY. The wording is recorded behavior only: HTTP 400 / ValidationException with message "KeyUsage of the input key <keyArn> is invalid for the operation." Fixed text "KeyUsage of the input key " … " is invalid for the operation."; the single variable part is the key ARN resolved from the request's VerificationKeyIdentifier. AWS names the offending KEY, not the usage value.
Emulator: same 400/ValidationException, message "KeyUsage <KEY_USAGE> is not valid for this operation." (replay: "KeyUsage TR31_V1_IBM3624_PIN_VERIFICATION_KEY is not valid for this operation."). Wrong fixed text and the key identity is absent from the message entirely.
Why: callers that pass an alias cannot learn which key the alias resolved to, so a key-selection mistake is undiagnosable; message matchers written against AWS never fire. NOTE: open issue 20261127T133841Z-payment-cryptography-data-generateauthrequestcryptogram-validationexception-refusals-diverge-from-aws describes this same template defect on GenerateAuthRequestCryptogram only — it does not cover VerifyPinData, whose handler repeats it.
Fix: the KeyUsage validation error construction in the VerifyPinData handler of the payment-cryptography-data service — substitute the resolved key ARN into AWS's template rather than formatting the KeyUsage enum.
Traces: payment-cryptography-data.verify-pin-data-visa-pvv-with-ibm3624-key-rejected.

Cause 4 of 7 — GeneratePinData's "PAN required for ISO_FORMAT_0" refusal uses the wrong sentence and attributes the requirement to the wrong thing.
AWS: on GeneratePinData (Smithy: POST /pindata/generate; PinBlockFormat required enum, PrimaryAccountNumber OPTIONAL — PrimaryAccountNumberType @length 12..19, @pattern ^[0-9]+$, @sensitive; errors include ValidationException 400 [defaulted]) the PAN is optional in the model because only some PIN block formats mix it in. ISO format 0 does, so a request with PinBlockFormat=ISO_FORMAT_0 and no PrimaryAccountNumber is refused. Recorded behavior: HTTP 400 / ValidationException with message "Primary Account Number is required for PIN block format ISO_FORMAT_0. Please provide a valid PAN value." The requirement is attributed to the PIN BLOCK FORMAT; the variable part is the format name from the request's PinBlockFormat, the rest is fixed text (note the spaced-out words "Primary Account Number", not the member name).
Emulator: HTTP 400 / ValidationException with "PrimaryAccountNumber is required for VISA PIN verification value generation." — different fixed text, the member name in place of AWS's prose, no mention of the PIN block format, and it blames the Visa PVV generation attributes instead of the block format. The same request under a non-PAN block format must still succeed, so the emulator is also keying the rule off the wrong input.
Why: a client cannot tell from the emulator's message which input to change (AWS points at PinBlockFormat/the PAN pairing; the emulator points at the generation attributes), and the format name needed to decide whether to supply a PAN is missing. Any assertion on AWS's sentence fails.
Fix: the input validation of the GeneratePinData handler in the payment-cryptography-data service — gate the requirement on PinBlockFormat and emit AWS's two-sentence message with the requested format name substituted.
Traces: payment-cryptography-data.generate-pin-data-iso-format-0-without-pan-rejected.

Cause 5 of 7 — TranslatePinData's refusal for a block that the named incoming PEK cannot decrypt uses the wrong message.
AWS: TranslatePinData (Smithy: POST /pindata/translate; IncomingKeyIdentifier/OutgoingKeyIdentifier required, EncryptedPinBlock required HexEvenLengthBetween16And32 @length 16..32 @pattern ^(?:[0-9a-fA-F][0-9a-fA-F])+$ @sensitive; errors ValidationException 400 [defaulted], ResourceNotFoundException 404, …) decrypts the incoming block under the named incoming PEK. Recorded behavior: when the block was encrypted under a DIFFERENT PEK, so the decryption yields no well-formed PIN, AWS answers HTTP 400 / ValidationException with the message "Pin block provided is invalid." — that sentence is entirely fixed text with no part taken from the request, and in particular it names neither the block format nor the key.
Emulator: HTTP 400 / ValidationException with "The PIN block does not carry a PIN in PinBlockFormat ISO_FORMAT_0." — different fixed text, and it injects the incoming translation attributes' ISO format, which AWS's message never contains.
Why: the message is the only signal distinguishing a mis-paired key from a malformed block; clients matching AWS's sentence do not match, and the emulator's variant invites a caller to blame the declared block format when the real fault is the incoming key selection.
Fix: the incoming-block decryption failure path of the TranslatePinData handler in the payment-cryptography-data service — raise ValidationException with AWS's fixed sentence.
Traces: payment-cryptography-data.translate-pin-data-block-under-other-pek-rejected.

Cause 6 of 7 — VerifyAuthRequestCryptogram does not enforce the multiple-of-16 rule on TransactionData, so a malformed request is answered as a verification failure.
AWS: VerifyAuthRequestCryptogram (Smithy: POST /cryptogram/verify; TransactionData required, TransactionDataType @length 2..1024, @pattern ^[0-9a-fA-F]+$, @sensitive; errors ValidationException 400 [defaulted] AND VerificationFailedException 400, which carries a required Reason) takes EMV transaction data in whole 8-byte cipher blocks. Beyond the modeled constraints AWS enforces a block-alignment rule the model does not state (recorded behavior only): the hex string's character count must be a multiple of 16. A value that passes @length and @pattern but is not block-aligned is refused BEFORE any cryptographic verification, with HTTP 400 / error code ValidationException and the message "TransactionData should be of length multiple of 16." — entirely fixed text, nothing substituted.
Emulator: performs the verification anyway over the unaligned data and answers HTTP 400 with the WRONG error code, VerificationFailedException, message "Auth request cryptogram verification failed." The input is never validated; the mismatch surfaces as a cryptographic result.
Why: ValidationException and VerificationFailedException mean opposite things to a caller — the first says "your request is malformed, fix the field", the second says "this cryptogram is not authentic, decline the transaction". An EMV authorization client whose transaction-data assembly is off by a nibble will decline a legitimate transaction against the emulator instead of surfacing a client-side bug, and retry/alerting logic keyed on the error code takes the wrong branch. The sibling defect on GenerateAuthRequestCryptogram is filed as open issue 20261127T133841Z-payment-cryptography-data-generateauthrequestcryptogram-validationexception-refusals-diverge-from-aws (Cause 2 there); that issue does NOT cover the verify path, which is a separate handler and fails differently (wrong error code rather than a 200).
Fix: the input validation of the VerifyAuthRequestCryptogram handler in the payment-cryptography-data service — after the modeled @length/@pattern checks, reject a TransactionData whose hex length is not a multiple of 16 with ValidationException (400) carrying AWS's fixed message, before the cryptogram is computed.
Traces: payment-cryptography-data.verify-arqc-unaligned-transaction-data-rejected.

Cause 7 of 7 — GenerateCardValidationData answers NotImplemented for the AMEX and dynamic generation-attribute families.
AWS: GenerateCardValidationData (Smithy: POST /cardvalidationdata/generate; GenerationAttributes required, union CardGenerationAttributes with members AmexCardSecurityCodeVersion1, AmexCardSecurityCodeVersion2, CardVerificationValue1, CardVerificationValue2, CardHolderVerificationValue, DynamicCardVerificationCode, DynamicCardVerificationValue; ValidationDataLength target IntegerRangeBetween3And5Type @range 3..5, default 3; output ValidationData required @length 3..5 @pattern ^[0-9]+$). Every union member is a supported request; an AmexCardSecurityCodeVersion2 request against a TR31_C0_CARD_VERIFICATION_KEY with ValidationDataLength 5 answers HTTP 200 with a 5-digit ValidationData that VerifyCardValidationData then accepts.
Emulator: answers HTTP 400-class error code NotImplemented with the message "operation GenerateCardValidationData with American Express or dynamic card generation attributes is scaffolded but not implemented in this emulator" — an error code AWS does not model for this operation at all. The CardVerificationValue1 path does answer (it is exercised successfully by the cause-1 check), so only the AMEX and Dynamic* union members are stubbed.
Why: AMEX CSC and dynamic CVC/CVV generation are the whole point of those union members; a client cannot generate or verify AMEX card security codes against the emulator, and it receives an unmodeled error code its SDK cannot classify. The refusal also hides the operation's modeled ValidationDataLength @range 3..5 enforcement behind it: AWS refuses ValidationDataLength 6 with HTTP 400 / ValidationException / message "1 validation error detected. Value at '/ValidationDataLength' failed to satisfy constraint: Member must be between 3 and 5, inclusive" plus fieldList [{path: '/ValidationDataLength', message: '<that same constraint sentence>'}] — fixed text apart from the member path and the bounds, which come from the model. That assertion is unverified while the AMEX path is stubbed, so implement both together.
Fix: the GenerateCardValidationData handler in the payment-cryptography-data service — implement the AmexCardSecurityCodeVersion1/2, DynamicCardVerificationCode and DynamicCardVerificationValue branches of the CardGenerationAttributes union (and the matching VerifyCardValidationData branches), and surface the modeled ValidationDataLength range violation as ValidationException with fieldList rather than any NotImplemented code.
Traces: payment-cryptography-data.generate-card-validation-data-length-above-five-rejected.
