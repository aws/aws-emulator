# IoT TwinMaker data plane: Lambda data connectors are never invoked (dataWriter refusals dropped, dataReader series unread) and three refusal messages diverge from AWS's wording (5 causes)

> _Note: this issue was identified against the code base at commit `96e759e54960d5d1fd2a95fa47259d85e3163a48`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchPutPropertyValues

## Description
Five distinct root causes in the iottwinmaker crate, all grounded in failing behavioral checks. A fixer must close all five before submitting.

Cause 1 of 5: BatchPutPropertyValues never invokes the component type's dataWriter connector, so a connector's per-entry refusals never reach errorEntries and refused values are stored anyway.
AWS: BatchPutPropertyValues on a property whose definition carries isStoredExternally=true and whose component type declares a `dataWriter` connector delegates the write to that Lambda. The connector answers `{"errorEntries": [{"errors": [{"errorCode": ..., "errorMessage": ..., "entry": <the request entry>}]}]}` (data-connector-interfaces guide), and the service relays it: HTTP 200 with one ErrorEntry per refused entry, each BatchPutPropertyError carrying the connector's own errorCode and errorMessage and the REQUEST entry it refused (Smithy: BatchPutPropertyError.errorCode/errorMessage/entry all @required; errorCode/errorMessage @length 1..256; output errorEntries @required @length 1..10). A batch in which every entry is refused still answers 200; a batch mixing one refused with one accepted entry answers 200 with exactly one ErrorEntry, and only the accepted entry is readable afterwards; nothing the connector refused is readable through GetPropertyValueHistory.
Emulator: the handler writes every entry into its own series store and answers HTTP 200 with errorEntries == [] in all three shapes (every entry refused, one refused beside one accepted, refusal matched to its request position). The dataWriter connector is only ever CHECKED for existence (crate::state::component_type_has_data_writer, state.rs:2271-2280) and never called, so the connector's verdict is lost and the refused values are stored.
Why: a client whose connector enforces domain rules (here: reject a negative reading) is told every value was accepted, and then reads back values the external store never took. Both the error channel and the stored data are wrong, in opposite directions.
Fix: the BatchPutPropertyValues handler (ops/batch_put_property_values.rs) must route an entry whose resolved property is isStoredExternally through the component type's dataWriter Lambda and build errorEntries from the connector's answer (one ErrorEntry per refused entry, echoing the request entry), storing only the entries the connector accepted.
Traces: iottwinmaker.batch-put-property-values-every-entry-refused-still-answers, iottwinmaker.batch-put-property-values-refusal-matches-its-request-entry, iottwinmaker.batch-put-property-values-refused-entry-beside-accepted-entry. Code: ops/batch_put_property_values.rs (module doc lines 29-48 state errorEntries is built only from value-shape failures), state.rs:2271-2280.

Cause 2 of 5: GetPropertyValueHistory never invokes the dataReader connector, so an externally stored series the connector serves reads back empty.
AWS: GetPropertyValueHistory on a property with isStoredExternally=true and isTimeSeries=true whose component type declares a `dataReader` connector invokes that Lambda with the entityId, componentName, selectedProperties, the window, orderByTime, maxResults and the connector's own nextToken, and relays `propertyValues` from it; it pages by maxResults, hands the caller its OWN opaque nextToken (never the connector's raw token) and ends the walk with no token (Smithy: GetPropertyValueHistory output propertyValues @required, nextToken @length 0..17880; errors include ConnectorFailureException/ConnectorTimeoutException 424, which exist precisely because the read goes through a connector).
Emulator: the read is served only from the crate's own series store (ops/get_property_value_history.rs handle -> scope/series read -> page), so a series that exists only behind the reader Lambda comes back as one page of 0 values with no nextToken (HTTP 200). Observed page sizes [0] where 7 points at maxResults 3 must page [3, 3, 1].
Why: every connector-backed historical read answers "no data" instead of the external store's series, and a paginating client sees a completed walk over an empty result rather than the connector's points; nothing distinguishes a working connector from a dead one.
Fix: the GetPropertyValueHistory read path must delegate to the component type's dataReader (dataReader/dataReaderByEntity/dataReaderByComponentType) connector for externally stored properties, mint its own page token over the connector's continuation, and surface a throwing/slow connector as the modelled 424 ConnectorFailureException/ConnectorTimeoutException.
Traces: iottwinmaker.get-property-value-history-pages-connector-series-without-repeat-or-loss, iottwinmaker.get-property-value-history-unissued-next-token-rejected (its first page of the connector series held [] where the first 3 points were expected). Code: ops/get_property_value_history.rs:214-265, 1031-1087.

Cause 3 of 5: the nextToken refusal of GetPropertyValueHistory uses an emulator-invented message instead of AWS's.
AWS: a nextToken this query did not issue is refused 400 ValidationException with the message "Pagination token provided is invalid: <nextToken>" — fixed text "Pagination token provided is invalid: " followed by the token value the request carried (recorded behavior; the check asserts exactly that construction for a connector's own plain offset token). Status 400 and code ValidationException match.
Emulator: 400 ValidationException with "nextToken is not a token this listing minted" — the shared crate::state::invalid_next_token_message() (src/state/page_tokens.rs:302-313), whose doc deliberately excludes the token. That rule came from 20261027T145624Z-iottwinmaker-listentities-error-response.md (fixed) and is applied to the data-plane history read too, where AWS's own message does name the token.
Why: a client that matches on the refusal message (or logs it to see which cursor it replayed) gets neither AWS's fixed text nor the offending token; a message is part of the contract.
Fix: the history read's invalid-token refusal (ops/get_property_value_history.rs page()) must carry AWS's wording with the request's nextToken interpolated, clamped to ValidationException.message's modelled 2048-character bound (nextToken is modelled up to 17880 characters), rather than the crate-wide listing message. Only the data-plane history read is evidenced here.
Traces: iottwinmaker.get-property-value-history-rejects-unissued-next-token. Code: src/state/page_tokens.rs:302-313, ops/get_property_value_history.rs:1037-1046.

Cause 4 of 5: GetPropertyValue's undefined-selectedProperty refusal uses an emulator-invented message and names no component.
AWS: selecting a property the component does not define is refused 400 ValidationException with "Following properties not present in component <componentName>: [<name>, ...]." — fixed text "Following properties not present in component ", the componentName from the request, ": [", the undefined selected property names, "]." (recorded behavior). The sibling refusal for a component the entity lacks is "Component <componentName> of Entity <entityId> in workspace <workspaceId> not found."-shaped and does pass.
Emulator: 400 ValidationException with "selectedProperties <name> is not a property of the component this request addresses" — built in ops/get_property_value.rs selected_properties() (lines 582-594), which refuses at the first offender and drops the component name entirely.
Why: the code and status are right but the message is not AWS's; a client cannot tell from it WHICH component rejected the selection, and a message-matching client fails.
Fix: the selected-property validation in the GetPropertyValue handler must report AWS's fixed text with the request's componentName and the list of selected properties the component does not define.
Traces: iottwinmaker.get-property-value-unknown-selection-rejected. Code: ops/get_property_value.rs:579-594.

Cause 5 of 5: UpdateEntity's wrong-dataType refusal uses an emulator-invented message.
AWS: a propertyUpdates value whose DataValue member contradicts the property's declared dataType is refused 400 ValidationException with "Missing <TYPE> data value for <TYPE> data type property <propertyName> in Component: <componentName>" — fixed text "Missing ", the declared Type, " data value for ", the declared Type, " data type property ", the property name from the request, " in Component: ", the component name from the request (recorded behavior; Smithy: PropertyDefinitionRequest.dataType is the property's type, UpdateEntity models ValidationException 400). The refusal must leave the stored value untouched, which the emulator does do.
Emulator: 400 ValidationException with "the value written to property <name> is a <carried> where that property's dataType is <declared>", from the shared crate::state::data_value_type_violation() (state.rs:3190-3209).
Why: AWS words this class of refusal from the DECLARED type's point of view and names the component; a client matching the message, or surfacing it to an operator, sees text AWS never emits. The same helper is reached by CreateEntity and the data plane, so the divergence is crate-wide, but only the UpdateEntity path is evidenced here.
Fix: the shared data-value/dataType violation message builder in state.rs (and the UpdateEntity component-property validation that calls it) must produce AWS's wording, with the component name available to the message.
Traces: iottwinmaker.update-entity-value-of-wrong-data-type-rejected. Code: state.rs:3190-3209.
