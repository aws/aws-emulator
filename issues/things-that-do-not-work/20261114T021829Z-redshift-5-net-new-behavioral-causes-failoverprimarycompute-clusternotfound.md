# Redshift: 5 net-new behavioral causes — FailoverPrimaryCompute ClusterNotFound wording, CreateEventSubscription SNSTopicArnNotFound message, GetClusterCredentialsWithIAM DbUser not identity-derived, unassociated CustomDomainName misclassified, and the published cluster endpoint is an AWS-owned host

> _Note: this issue was identified against the code base at commit `3c44e49694959b3de2a0545e79b8c4fbe0cf166e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetClusterCredentialsWithIAM

## Description
Five net-new root causes in the redshift (query-protocol) control plane and its cluster data plane, each grounded in a failing behavioral check the suite did NOT mark "ALREADY FILED" and did NOT mark "OWNED by". All five belong to the one service `redshift`, so they are bundled here: a fixer must close ALL FIVE before submitting.

=== Cause 1 of 5: FailoverPrimaryCompute's ClusterNotFound message uses the read-path wording instead of the act-on-a-cluster wording ===
Failing check: redshift.cluster-scoped-triaged-ops-not-found-semantics
AWS: FailoverPrimaryCompute naming a ClusterIdentifier that does not exist in the account is refused with HTTP 404 and error code ClusterNotFound (Smithy: FailoverPrimaryCompute errors ClusterNotFoundFault, httpError 404, awsQueryError code `ClusterNotFound`) and the message `Cluster not found: <ClusterIdentifier>` — fixed text `Cluster not found: `, variable part the ClusterIdentifier copied verbatim from the request. Recorded behavior fixes the message text; the model fixes only the status and code. The same check confirms the OTHER wording variant is correct where AWS uses it: ModifyClusterDbRevision and GetClusterCredentialsWithIAM on the same nonexistent identifier must answer `Cluster <ClusterIdentifier> not found.` and the emulator already does (those two assertions pass).
Emulator: right status and right code, wrong message — it answers `Cluster <ClusterIdentifier> not found.` for FailoverPrimaryCompute too, i.e. the handler selects the describe/read wording variant (`ClusterNotFoundWording::IdentifierThenNotFound`) instead of the act-on-a-named-cluster variant.
Why: the fixed text of a refusal is a requirement of the error class. A client that matches the documented sentence (CLI transcript tests, log scrapers, error-mapping layers) diverges, and the per-operation wording difference AWS really exhibits (act-on vs. describe) is erased, so a caller cannot tell from the text which family refused.
Fix: the FailoverPrimaryCompute handler's not-found path — pick the act-on wording for its ClusterNotFoundFault message.
Traces: redshift.cluster-scoped-triaged-ops-not-found-semantics. Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/failover_primary_compute.rs (the ClusterNotFoundFault construction) and the wording enum in src/state.rs (`ClusterNotFoundWording`). Related OPEN issue 20261109T041550Z-redshift-failoverprimarycompute-clusternotfound-wording-enablelogging-cloudwatch-creates-no.md describes this same wording divergence for OTHER checks; it does not carry this check's replay key and the suite did not mark this failure owned, so it is filed here and that issue is named for context.

Why: the message is the part of the refusal an operator and a log scraper read; code written against AWS's wording (or a transcript test) diverges, and a documentation sentence used as a refusal message is a tell that the refusal is emulator-authored rather than reproduced.
Fix: the CreateEventSubscription handler's SNSTopicArnNotFoundFault construction — emit AWS's message template above instead of the model's doc string.
Traces: redshift.event-subscription-missing-topic-fails. === Cause 3 of 5: GetClusterCredentialsWithIAM's DbUser is derived from the presented access key id, not from the caller's IAM identity ===
Failing check: redshift.get-cluster-credentials-with-iam-federated-access
AWS: this operation takes no DbUser; "the database user is mapped 1:1 to the source IAM identity" (Smithy: ClusterExtendedCredentials$DbUser — "A database user name that you provide when you connect to a database. The database user is mapped 1:1 to the source IAM identity."). The returned DbUser is the plain `IAM:` form whose name part is the IAM identity's OWN name as it appears in the caller's ARN — for a caller whose STS GetCallerIdentity Arn is `arn:aws:iam::<account>:user/<user-name>` the DbUser is `IAM:<user-name>` (for an assumed role, the role-session form with the `IAMR:` prefix); it is never the auto-create `IAMA:` form, and it is stable across calls by the same identity. The name part is therefore a substring of the caller's own ARN.
Emulator: returns `IAM:<uppercased access-key-id-derived token>` (replay: DbUser `IAM:EMULATOR4B25A380D9B1` for caller ARN `arn:aws:iam::<account>:user/emulator`). The prefix and the stability across calls are right, but the name is minted from the SigV4 access key id rather than resolved to the signing identity's name, so it appears nowhere in the caller's ARN.
Why: the DbUser is the database principal a client then grants to, owns objects as, and audits by (GRANT/pg_user/svv_user_info, STL attribution). A name that is not the IAM identity's name breaks the documented 1:1 identity mapping: grants written for `IAM:<user-name>` never match the session, and audit rows cannot be joined back to the IAM principal. It also leaks an emulator-internal credential id into a database user name.
Fix: GetClusterCredentialsWithIAM's identity resolution — resolve the signing credential to its IAM identity and use that identity's name (the ARN's resource name) for the `IAM:`/`IAMR:` DbUser instead of deriving it from the access key id.
Traces: redshift.get-cluster-credentials-with-iam-federated-access. Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/get_cluster_credentials_with_iam.rs (lines 219-220, `extract_akid` → `st::iam_identity_db_user`) and the helper it calls in src/state.rs.

=== Cause 4 of 5: GetClusterCredentialsWithIAM scoped to a CustomDomainName no cluster serves is refused as ClusterNotFound instead of InvalidParameterValue ===
Failing check: redshift.get-cluster-credentials-with-iam-unsupported-rejected
AWS: GetClusterCredentialsWithIAM(ClusterIdentifier=<an existing, available cluster>, CustomDomainName=<a domain never associated with any cluster>) is refused with HTTP 400, error code InvalidParameterValue and the message `To use get credentials, you must provide an active custom domain name.` — the whole sentence is fixed text, with no variable part. Recorded behavior fixes the code and message; the model lists only ClusterNotFoundFault/UnsupportedOperationFault for this operation plus the service-common query-protocol InvalidParameterValue, so it does not by itself state which applies. The unscoped call on the same cluster succeeds both before and after the refusal (that positive control passes against the emulator today).
Emulator: refuses with error code ClusterNotFound (404) — the handler resolves CustomDomainName as a cluster NAME and reports the resource missing, rather than reporting that the request named an inactive/unassociated custom domain.
Why: the two refusals mean different things. ClusterNotFound tells a client its cluster is gone, so credential-refresh and failover logic branches on a nonexistent-warehouse path (re-provision, give up) instead of fixing the custom-domain argument; nothing ever surfaces AWS's remediation sentence, and code that branches on InvalidParameterValue for this case has an unreachable path.
Fix: GetClusterCredentialsWithIAM's custom-domain resolution branch — when the request carries a CustomDomainName that is not an ACTIVE association of a cluster of this account, raise the query-protocol InvalidParameterValue with the fixed sentence above instead of ClusterNotFoundFault.
Traces: redshift.get-cluster-credentials-with-iam-unsupported-rejected. Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/get_cluster_credentials_with_iam.rs, `resolve_cluster` (lines 305-319, the `(named, Some(domain))` arm that calls `cluster_not_found(st::custom_domain_association_not_found_message(domain))`).

=== Cause 5 of 5: an available cluster publishes an Endpoint.Address on an AWS-owned domain the emulator does not serve, so the IAM-federated login cannot be attempted at all ===
Failing check: redshift.get-cluster-credentials-with-iam-federation
AWS: a cluster that reaches ClusterStatus=available publishes Endpoint{Address,Port} that the caller can actually reach, and the DbUser/DbPassword GetClusterCredentialsWithIAM just minted authenticate over the PostgreSQL wire protocol on it and execute SQL. Recorded behavior only (the Smithy model describes the control-plane shapes, not the wire protocol). The requirement that binds the emulator here is narrower: whatever host an emulator publishes in Endpoint.Address must be a host the emulator itself serves — an address it does not answer on is an address it has announced falsely.
Emulator: publishes `<cluster-id>.<token>.<region>.redshift.amazonaws.com:5439`, an AWS-owned host the emulator does not serve and the harness refuses to dial: `simparity.published.PublishedUrlRejected: endpoint_host was given <cluster-id>.<token>.us-west-2.redshift.amazonaws.com:5439 (published by the emulator or built by the check): its host is not one of the emulator's own hosts`. The credential-minting assertions ahead of it (DbUser, DbPassword, Expiration within the requested DurationSeconds window) pass, so the operation itself is served; only the endpoint the response points at is unreachable.
Why: every client that takes the published endpoint and connects (psql/JDBC, ETL jobs, BI tools, IaC smoke tests) is sent to real AWS or to nothing at all. The emulator reports a usable warehouse while announcing an address other than the one it is reached on, so no data-plane behavior can be exercised and the failure mode is an unrelated connect error rather than a diagnosable refusal.
Fix: the cluster endpoint-publishing path in the service's state — Endpoint.Address must be a host the emulator serves (its own host/port for the cluster's SQL listener), and that listener must accept the minted credentials; publishing an `*.redshift.amazonaws.com` host is only correct against real AWS.
Traces: redshift.get-cluster-credentials-with-iam-federation. Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/state.rs (the cluster endpoint/address synthesis) and whatever listener backs the cluster data plane. Related OPEN issues 20261110T231942Z-redshift-getclustercredentials-expiration-login-check-cannot-run-the.md and 20261109T125831Z-redshift-6-net-new-behavioral-causes-cluster-endpoint.md describe the same AWS-owned endpoint host for OTHER checks; neither carries this check's replay key and the suite did not mark this failure owned, so it is filed here and both are named for context.
