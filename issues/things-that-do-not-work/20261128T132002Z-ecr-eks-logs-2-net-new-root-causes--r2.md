Cause 1 of 2: a Fargate pod admitted by an ACTIVE Fargate profile never delivers its stdout to the log group named by the cluster's aws-logging ConfigMap, so the 'pod execution role lacks CloudWatch Logs write permission' differential reaches no verdict at all — neither the denied half nor the granted half.
  AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend): CreateFargateProfile POST /clusters/{clusterName}/fargate-profiles -> 200 {fargateProfile: FargateProfile}, required members fargateProfileName, clusterName, podExecutionRoleArn, plus subnets/selectors; the Fargate profile's podExecutionRoleArn is the identity every pod matching its selectors runs its log router under. For the log delivery itself: recorded behavior only — the EKS model describes no data-plane emission. The recordings show that on a Fargate-only cluster whose aws-observability namespace holds an aws-logging ConfigMap with an [OUTPUT] block 'Name cloudwatch_logs / Match kube.* / log_group_name <group> / log_stream_prefix from-fluent-bit- / auto_create_group true', a pod admitted by the profile reaches phase Running or Succeeded and, IF the pod execution role is authorized for logs:CreateLogStream and logs:PutLogEvents, its stdout arrives as events in <group> under a stream whose name starts with the configured prefix; if that role carries only the baseline AmazonEKSFargatePodExecutionRolePolicy (no logs write), the pod still runs but NOTHING is delivered to <group>, and attaching logs:CreateLogGroup/CreateLogStream/DescribeLogStreams/PutLogEvents to that same role makes a newly created pod's output arrive. The group name and the stream prefix are values taken from the ConfigMap; 'from-fluent-bit-' here is one recording's prefix, not a requirement.
  Emulator: the check builds a private-subnet VPC, an ACTIVE cluster and an ACTIVE Fargate profile, creates the aws-observability namespace and the aws-logging ConfigMap through the served cluster Kubernetes API, then creates an echo pod and waits up to 420s for its phase to become Running or Succeeded before it ever looks at CloudWatch Logs. That wait never resolves (the pod stays Pending), so the 600s 'nothing was delivered while the role is unauthorized' hold and the 600s 'the marker appears after the permission is granted' poll are never reached, and the check ends on the suite budget with no emulator error response to grade.
  Why: a client cannot distinguish 'the pod execution role is not authorized to write logs' from 'Fargate pods never run and never emit anything'. Any workflow that gates on a Fargate pod's log output — a Fluent Bit sidecar configuration test, a log-based assertion, or an IAM negative control proving the pod execution role's permissions are enforced — hangs forever instead of resolving, although the identical code settles on AWS.
  Fix: the served cluster Kubernetes API's Fargate pod admission/runtime path and the log-router side effect it owns — an admitted Fargate pod must progress out of Pending to Running/Succeeded, and its stdout must be delivered into cloudwatchlogs state under the aws-logging ConfigMap's log_group_name with the configured log_stream_prefix, gated on the Fargate profile's podExecutionRoleArn being authorized for logs:CreateLogStream/PutLogEvents.
  Traces: ecr__eks__logs.eks-fargate-logging-without-execution-role-permission-no-delivery.

Cause 2 of 2: a pod on a managed nodegroup never reports an image-pull outcome — the public-image control pod records no 'Pulled' event, and the private-ECR pod whose node role lacks ecr:BatchGetImage/ecr:GetDownloadUrlForLayer never reaches ImagePullBackOff.
  AWS: Smithy: CreateNodegroup POST /clusters/{clusterName}/node-groups -> 200 {nodegroup: Nodegroup}, required members clusterName, nodegroupName, subnets, nodeRole; nodeRole is the instance identity kubelet pulls images under. For the pull outcome: recorded behavior only — the EKS model describes no data-plane event. The recordings show that once the cluster and the nodegroup are ACTIVE, a pod referencing a public image records a core/v1 Event with reason 'Pulled' naming the image; a pod referencing a private ECR image on a node whose role holds ecr:GetAuthorizationToken but NOT ecr:BatchGetImage/ecr:GetDownloadUrlForLayer for that account's repositories is refused the layers, so its container status reports waiting reason 'ImagePullBackOff' and no 'Pulled' event is ever recorded for it; attaching ecr:BatchGetImage and ecr:GetDownloadUrlForLayer to that SAME node role and recreating the same pod then produces the 'Pulled' event. 'Pulled' and 'ImagePullBackOff' are the fixed strings; the image reference, pod name and repository are values from the request and state.
  Emulator: the check pushes an image to a private ECR repository, stands up an ACTIVE cluster and an ACTIVE AL2023_x86_64_STANDARD nodegroup on the restricted node role, and creates both pods. It then polls the served cluster Kubernetes API for the control pod's 'Pulled' event for up to 600s; that event never appears, so the ImagePullBackOff assertion on the private pod and the post-grant restore half (delete the pod, recreate it after attaching the two ECR actions, expect 'Pulled') are never reached. The check ends on the suite budget while still polling an empty event list.
  Why: a client cannot tell an authorized pull from an unauthorized one, because both look like a pod with no events and no container status. Any workflow that waits for a pod's image to be pulled, or that asserts a missing ECR permission is what broke a deployment, hangs rather than resolving — and the negative control that proves ECR authorization is enforced at pull time cannot be expressed at all.
  Fix: the served cluster Kubernetes API's pod runtime path on a nodegroup node and the ECR authorization it consults — a scheduled pod must attempt an image pull and record the outcome as a core/v1 Event ('Pulled' on success) and as a container status (waiting reason 'ImagePullBackOff' when the node role is not authorized for the repository's account), for both public and private-ECR image references.
  Traces: ecr__eks__logs.eks-pod-image-pull-fails-without-ecr-permission-rejected.
