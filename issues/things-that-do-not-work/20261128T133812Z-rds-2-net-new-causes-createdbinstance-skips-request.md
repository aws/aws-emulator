# rds: 2 net-new causes — CreateDBInstance skips request-parameter validation, and StartExportTask judges the KMS key before resolving the export source

> _Note: this issue was identified against the code base at commit `ff49842cf7656b5a010943ef9d0fd100550d134a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
Two independent net-new root causes on the RDS control plane, found by replaying the wire fixture corpus (simparity-wire-aws-v1) against the emulator built from this checkout. A fixer must close BOTH before submitting. Both share one fault shape: the emulator answers an ill-formed or unresolvable request without running (or without first running) the validation AWS runs, so a request that AWS refuses is either accepted outright or refused with the wrong error. Neither of the two divergence clusters below was reported as blocked by an unimplemented stub, nor OWNED by any open issue.

---
Cause 1 of 2: CreateDBInstance performs no request-parameter validation of the create request — an invalid DBName, and an EnableCloudwatchLogsExports log type that the requested Engine does not support, are both accepted with HTTP 200 and a created DB instance instead of being refused with HTTP 400 InvalidParameterValue.
AWS: Smithy (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json) models CreateDBInstance with input members DBName (String) and EnableCloudwatchLogsExports (LogTypeList), and the service-common InvalidParameterValue sender error; the per-engine DBName documentation on CreateDBInstanceMessage.DBName states the constraints explicitly — for MySQL/MariaDB/Db2 "Must contain 1 to 64 letters or numbers", "Must begin with a letter. Subsequent characters can be letters, underscores, or digits (0-9)", "Can't be a word reserved by the specified database engine"; for PostgreSQL 1 to 63 letters, numbers or underscores beginning with a letter; for RDS Custom for SQL Server and RDS for SQL Server "Not applicable. Must be null." A DBName violating those constraints is refused on the CreateDBInstance call itself and no instance is created. Recorded refusal envelope for the DBName class: HTTP 400 with body $.ErrorResponse.Error = {Type 'Sender', Code 'InvalidParameterValue', Message 'DBName must begin with a letter and contain only alphanumeric characters.'} plus $.ErrorResponse.RequestId. That whole sentence is fixed text for this error class (it names no request value); RequestId is a per-run value and is not asserted. For the log-export class the recording expects the same refusal envelope — HTTP 400 with an $.ErrorResponse carrying a Sender-type InvalidParameterValue — on a CreateDBInstance whose EnableCloudwatchLogsExports names a log type the requested Engine does not export; its message's fixed text must be taken from that recorded response, with the variable parts being the log type(s) and the engine named in the request.
Emulator: both request shapes are answered HTTP 200 with a normal CreateDBInstance result and NO $.ErrorResponse at all (replay: 'status: expected 400, got 200' / '$.ErrorResponse: missing ... got None'), i.e. the handler never validates DBName's character/leading-character rule and never cross-checks EnableCloudwatchLogsExports against Engine; the bad instance is created and remains in state.
Why: a client gets a success for a request AWS rejects. The failure is deferred and silently mutated: application code that relies on CreateDBInstance to reject a bad database name (a user-supplied name, a templated name, a CloudFormation/Terraform parameter) proceeds as if the database were valid, and the emulator's state now holds an instance that could never exist in AWS. Negative tests of this surface cannot pass against the emulator at all, and the InvalidParameterValue path for this operation is unreachable.
Fix: the input-validation stage of the CreateDBInstance handler in the RDS crate (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/ — the create-DB-instance operation), before any state mutation: validate DBName against the per-engine rule for the requested Engine and validate every entry of EnableCloudwatchLogsExports against the log types the requested Engine supports, answering the modeled InvalidParameterValue sender fault with the recorded sentence and creating nothing.
Traces: rds-create-db-instance-dbname-constraint-violations#task#1 and #task#2 (invalid DBName), rds-create-db-instance-log-export-wrong-engine#task#3 and #task#4 (log type not valid for the engine) — one cluster, 4 affected steps.

---
Cause 2 of 2: StartExportTask does not resolve its SourceArn before judging the KmsKeyId, so an export whose source snapshot does not exist is refused with KMSKeyNotAccessibleFault (HTTP 400) instead of the snapshot-not-found fault (HTTP 404).
AWS: Smithy models StartExportTask with required input members ExportTaskIdentifier, SourceArn, S3BucketName, IamRoleArn, KmsKeyId, and among its errors DBClusterSnapshotNotFoundFault (errorKind client, httpError 404, awsQueryError code 'DBClusterSnapshotNotFoundFault'), DBSnapshotNotFoundFault (client, 404, awsQueryError code 'DBSnapshotNotFound'), DBClusterNotFoundFault (client, 404) and KMSKeyNotAccessibleFault (client, 400). The export source named by SourceArn is resolved first: when it does not exist the call is refused 404 with the not-found fault matching the ARN's resource type, and nothing about the KMS key, bucket or role is reported. Recorded refusal: HTTP 404, Error.Code 'DBClusterSnapshotNotFoundFault', Error.Message 'DBClusterSnapshot <snapshot identifier> not found.' — fixed text 'DBClusterSnapshot ' and ' not found.', with the single variable part being the snapshot identifier taken from the request's SourceArn.
Emulator: the same request is answered HTTP 400 with Error.Code 'KMSKeyNotAccessibleFault' and Error.Message 'The specified KMS key [<kms key arn>] does not exist, is not enabled or you do not have permissions to access it.' — the KMS probe runs before (or instead of) resolving the source, so the one broken thing in the request (a snapshot that does not exist) is never named. The specific key ARN and snapshot identifier in the recording are per-run values; the requirement is the 404 status, the not-found error code for the ARN's resource type, and the message template above.
Why: the refusal misdiagnoses the request and changes its class. A client branching on Error.Code — or on the 4xx class, since 404 and 400 drive different retry/remediation paths — is told its KMS key is missing or unauthorized when the real fault is a typo'd, deleted or not-yet-created source snapshot. An operator follows that to the wrong resource (re-granting a key that is fine) while the missing snapshot is never mentioned, and DBClusterSnapshotNotFoundFault/DBSnapshotNotFound become unreachable for the one condition they exist for.
Fix: the input-validation order of the StartExportTask handler in the RDS crate (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/start_export_task.rs): resolve SourceArn against the snapshot/cluster state and answer the matching modeled not-found fault (404) with the recorded sentence BEFORE probing KmsKeyId, the destination bucket or the IAM role. Related OPEN issue a fixer should read first, which does NOT cover this cause — the replay did not bind these steps to it: 20261125T121533Z-rds-s3-2-net-new-causes-startexporttask-refuses.md (its Cause 1 is the bucket-existence check running after the ROLE probe; this cause is the SOURCE resolution running after the KMS probe, a different ordering defect and a different status class). See also 20261122T005804Z-rds-s3-4-net-new-causes-in-snapshot.md and 20261123T220118Z-rds-3-net-new-causes-rebootdbinstance-publishes-in.md.
Traces: rds-export-task-cluster-source-not-found#task#2 and #task#3 — one cluster, 2 affected steps.
