# wafv2 managed-product and managed-rule-group catalog reads serve a locally synthesized catalog instead of AWS's published one

> _Note: this issue was identified against the code base at commit `abcf655460e962663cf1a42e4ceed79db956738d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAllManagedProducts

## Description
The two read-only WAFv2 catalog operations that project AWS's published managed-rules/managed-products catalog both serve emulator-authored catalog content rather than AWS's. Both operations take only a Scope and are pure catalog projections, so their entire response body is a fidelity requirement: there is no request- or account-derived variation in them for a client to absorb. 2 causes.

Cause 1 of 2: DescribeAllManagedProducts serves only the AWS-vendor rule sets and omits the Amazon Web Services Marketplace managed products entirely.
AWS: Smithy: DescribeAllManagedProducts(Scope: Scope, required) -> ManagedProducts: ManagedProductDescriptors; ManagedProductDescriptor members VendorName, ManagedRuleSetName, ProductId, ProductLink, ProductTitle, ProductDescription, SnsTopicArn, IsVersioningSupported, IsAdvancedManagedRuleSet. The model documents ManagedProductDescriptor as "The properties of a managed product, such as an Amazon Web Services Managed Rules rule group or an Amazon Web Services Marketplace managed rule group", and ProductLink as "For Amazon Web Services Marketplace managed rule groups only, the link to the rule group product page" — i.e. the response is required to carry third-party Marketplace vendor products alongside the AWS-vendor ones. The recording confirms it: the recorded ManagedProducts list carries Marketplace entries whose VendorName is a third-party seller, whose ProductId is a vendor-assigned GUID rather than the rule-set name, which carry a ProductLink to the vendor's Marketplace product page, and whose SnsTopicArn lives in the vendor's own AWS account — for example an entry with VendorName of a third-party security vendor, ManagedRuleSetName in that vendor's own naming form, a GUID ProductId, a ProductLink under aws.amazon.com/marketplace/pp/, and a SnsTopicArn in the vendor's account. Recorded behavior only for the exact catalog membership and ordering; the recorded status is 200.
Emulator: answers 200, but every element of the returned list diverges — the replay reports $.ManagedProducts[0] through $.ManagedProducts[45] all as 'missing', because the emulator serves a different, shorter, differently ordered list consisting only of AWS-vendor entries (VendorName 'AWS', ProductId equal to the rule-set name, no ProductLink member at all, and SnsTopicArn pinned into the emulator's own 000000000000 account). No Marketplace-vendor product appears anywhere in the response.
Why: a client that enumerates the managed-product catalog to let a user pick a rule group — a console-style picker, a Terraform/CDK data source, or a compliance scan that asserts which vendors are offered — sees only the AWS first-party sets. Any code path keyed on a Marketplace ProductId (a GUID) or on ProductLink finds nothing, and ProductId values that AWS returns as GUIDs and the emulator returns as rule-set names are not interchangeable, so a selection made against the emulator is not valid against AWS. Subscribing to change notifications is also impossible, since every SnsTopicArn points at the emulator's placeholder account rather than the vendor's.
Fix: the DescribeAllManagedProducts handler's catalog data — the seeded managed-product catalog it projects — must carry the full published catalog, Marketplace vendor entries included, with each entry's VendorName, ManagedRuleSetName, ProductId, ProductLink, ProductTitle, ProductDescription, SnsTopicArn, IsVersioningSupported and IsAdvancedManagedRuleSet as AWS publishes them, and in AWS's order.
Traces: wafv2-catalog-describe-all-managed-products#task#1; also wafv2-catalog-describe-all-managed-products-cloudfront#task#1 (same divergence under Scope=CLOUDFRONT).

Cause 2 of 2: ListAvailableManagedRuleGroups returns re-worded Description text for six AWS Managed Rules rule groups.
AWS: Smithy: ListAvailableManagedRuleGroups(Scope required; NextMarker @length 1..256 @pattern \S; Limit @range 1..100) -> ManagedRuleGroups: ManagedRuleGroupSummaries. ManagedRuleGroupSummary.Description is EntityDescription (@length 1..256) and is documented as "The description of the managed rule group, provided by Amazon Web Services Managed Rules or the Amazon Web Services Marketplace seller who manages it" — the text is the vendor's published string, not something the service composes. Recorded behavior only for the exact wording; the recorded status is 200.
Emulator: answers 200 with the right rule-group names and vendor, but paraphrased descriptions for AWSManagedRulesUnixRuleSet, AWSManagedRulesPHPRuleSet, AWSManagedRulesAnonymousIpList, AWSManagedRulesACFPRuleSet, AWSManagedRulesATPRuleSet and AWSManagedRulesAntiDDoSRuleSet. The paraphrases are semantically close but textually different — e.g. for AWSManagedRulesUnixRuleSet AWS ends the sentence "...execute code for which access should not been allowed." while the emulator serves "...execute code for which the attacker should not have had access."; for AWSManagedRulesPHPRuleSet AWS says "specific to the use of the PHP, including injection of unsafe PHP functions ... remotely execute code or commands." where the emulator says "specific to the use of the PHP programming language ... remotely execute code or commands for which they are not authorized."; for AWSManagedRulesAnonymousIpList AWS says "services that allow obfuscation of viewer identity ... request originating from VPN, proxies, Tor nodes, and hosting providers" where the emulator says "services that permit the obfuscation of viewer identity ... requests originating from VPNs, proxies, Tor nodes, and hosting providers".
Why: these Description strings are fixed published text with no variable parts — nothing in them comes from the request or from account state — so they are a requirement in full. A client that snapshots the catalog, diffs it to detect that AWS changed a rule group, surfaces the description in a UI, or asserts on it in a test sees a permanent spurious difference against the emulator; a diff-based change detector reports six phantom catalog changes on every run.
Fix: the ListAvailableManagedRuleGroups handler's seeded rule-group catalog must hold each rule group's published Description verbatim rather than a re-worded equivalent, for every AWS Managed Rules group it lists.
Traces: wafv2-catalog-list-available-managed-rule-groups#task#1; also wafv2-catalog-list-available-managed-rule-groups-cloudfront#task#1, wafv2-managed-rule-group-and-marketplace-product-discovery#task#1 and wafv2-webacl-full-lifecycle-with-managed-rules#task#1.
