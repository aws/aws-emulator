# healthlake: 3 net-new causes — UpdateProfileWithAgent's event stream omits the initial-response frame, FHIR export never writes to S3, and PublishDataTransformationProfile refuses a CSV publish with the wrong rule

> _Note: this issue was identified against the code base at commit `a648c95e8281c95edbf892975ca6b5e5d5c3850b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateProfileWithAgent

## Description
Three independent net-new root causes in the healthlake emulator, found by replaying the behavioral suite (24/34 passed; all 10 healthlake failures cluster into these three). None is marked ALREADY FILED or OWNED, and none is covered by the open issues: 'HealthLake UpdateProfileWithAgent mints an unknown ConversationId instead of refusing it' (20261127T112220Z-...-mints-an-unknown-conversationid...) covers the refusal of a stale ConversationId, not the framing of the stream itself, and 'HealthLake ValidationException message text diverges from AWS wording' (20261127T112220Z-...-validationexception-message-text...) covers the @length/enum clause renderer, not the publish rule in cause 3.

=== Cause 1 of 3: UpdateProfileWithAgent answers an event stream with no leading `initial-response` event, so no AWS SDK can parse any turn ===
AWS: Smithy: UpdateProfileWithAgent output member AgentResponse -> AgentOutputMessageStream, @streaming @httpPayload, required; it is the output's ONLY member; service protocol awsJson1_0, host prefix `datatransformation.`. Under the AWS JSON protocols an event-stream response ALWAYS begins with one `vnd.amazon.eventstream` message whose headers are `:message-type: event` and `:event-type: initial-response`, carrying the JSON of the output's non-stream members (here the empty object `{}`), and only then the union's data events. The model does not spell the framing, so this is protocol/SDK behavior: botocore's JSON parser calls `EventStream.get_initial_response()` first and raises `ResponseParserError('First event was not of type initial-response')` when that frame is absent — i.e. a real AWS response for this operation always carries it.
Emulator: the handler builds only the union's data frames (ProgressEvent, then TextMessageEvent or ErrorEvent, then EndOfOutputEvent) and returns them through `event_stream_only_response(frames)` — the first frame on the wire is `ProgressEvent`. Every SDK call therefore dies in the parser: `botocore.parsers.ResponseParserError: First event was not of type initial-response`, before any assertion about the turn's content can run. The response's status (200) and content-type (application/vnd.amazon.eventstream) are right; the stream's first message is missing.
Why: the operation is completely unusable from any AWS SDK — not one agent turn can be read, so the whole chat-based profile-update surface (open a conversation, continue it, refuse a conversation that belongs to another profile, refuse a turn on a deleted profile, assemble the final response from the text events) is unreachable behind a parse error rather than diverging in content. Any client that calls update_profile_with_agent raises instead of iterating the stream.
Fix: the event-stream serializer the handler calls — `service_common::event_stream` (`event_stream_only_response`, the sibling of `frame_event`) and its use in the UpdateProfileWithAgent handler — must emit, as the FIRST message of the stream, an `initial-response` event (`:message-type: event`, `:event-type: initial-response`, `:content-type: application/json`) whose payload is the serialized non-stream members of UpdateProfileWithAgentResponse (an empty JSON object for this operation), ahead of the union's events; the same must hold for the in-band ErrorEvent path, which is also served as a 200 stream.
Traces: healthlake.agent-new-conversation-streams-progress-before-end, healthlake.agent-text-events-assemble-final-response, healthlake.agent-conversation-id-continues-and-omission-starts-new, healthlake.agent-conversation-from-other-profile-rejected, healthlake.agent-conversation-of-other-profile-rejected, healthlake.agent-turn-on-deleted-profile-not-found, healthlake.agent-unknown-conversation-id-not-found. Code: services/service-com-amazonaws-healthlake-healthlake/src/ops/update_profile_with_agent.rs lines 358-405 (frames built, then `event_stream_only_response(frames)` with nothing prepended).

=== Cause 2 of 3: a FHIR export job writes nothing to the destination bucket, and FAILS outright whenever the data store holds any resource ===
AWS: Smithy: StartFHIRExportJob.OutputDataConfig (required) carries S3Configuration{S3Uri, KmsKeyId}, DataAccessRoleArn (required) is the role the service assumes to write there; JobStatus enum includes SUBMITTED/IN_PROGRESS/COMPLETED/FAILED; DescribeFHIRExportJob reports JobStatus and Message. The model does not state the output layout, so recorded behavior only: a job started on an ACTIVE data store settles in COMPLETED, and after it completes at least one object exists under the S3Uri prefix it was given (the exported resources), including for a store that holds a single stored Patient resource.
Emulator: the export performs no transmission at all. When the data store holds resources the job settles in FAILED with Message 'This emulator cannot transmit the data store FHIR resources to the destination Amazon S3 bucket. Resources held: <n>.' — the sentence is the emulator's own fixed text and <n> is the count read from its state, neither of which AWS ever returns; when the store holds no resource the job settles in COMPLETED but still leaves the output prefix empty. The behavior is deliberate in the handler's own documentation ('WRITING THE EXPORTED DATA to the destination bucket is a transmission this emulator cannot perform'), but the emulator serves S3 itself, so the destination bucket in these runs IS reachable in-process.
Why: export is the only way a client gets bulk data out of a data store. A client that starts an export and polls DescribeFHIRExportJob sees FAILED where AWS reports COMPLETED, and a client that then reads the output prefix finds nothing where AWS has written the exported resources; any pipeline or test built on export-then-read cannot run, and the FAILED status plus its emulator-authored Message is a refusal AWS never emits for a well-formed call on an ACTIVE store.
Fix: the export job's state machine — the StartFHIRExportJob handler and the job-transition clock in the service's state — must actually materialise the export into the bucket named by OutputDataConfig.S3Configuration.S3Uri (writing the data store's FHIR resources under that prefix) and settle the job in COMPLETED, instead of short-circuiting to FAILED with the 'cannot transmit' sentence; the empty-store case must likewise leave the output AWS leaves. The refusal path for a non-ACTIVE store must keep writing nothing.
Traces: healthlake.fhir-export-job-writes-stored-patient-to-s3 (job ended 'FAILED' with the 'cannot transmit' Message where COMPLETED was recorded), healthlake.fhir-export-job-on-deleted-datastore-rejected (the completed control export on the ACTIVE data store left no object under its output prefix). Code: services/service-com-amazonaws-healthlake-healthlake/src/ops/start_fhir_export_job.rs (module doc lines 26-33 state the short-circuit) and crate::state::export_not_transmitted_message.

=== Cause 3 of 3: PublishDataTransformationProfile refuses a CSV publish by comparing SourceFormat with the profile's stored format, instead of validating the draft mapping against the requested format ===
AWS: Smithy: PublishDataTransformationProfile.SourceFormat -> SourceFormat (enum CCDA | CSV), required, documented as 'The source data format of the profile'; ValidationException (httpError 400, member Message). The model does not state the publish-time rule, so recorded behavior only: publishing a profile whose DRAFT holds C-CDA templates (mapping keys like 'Resources/Patient.vm') with SourceFormat=CSV is refused with code ValidationException and message "CSV profile mapping must contain exactly one key: 'mapping-config.yaml'" — the whole sentence is fixed text, 'mapping-config.yaml' being the key name the CSV format requires, not a value from the request. AWS validates the DRAFT's mapping shape against the SourceFormat the publish names; it does not require that SourceFormat equal the format the profile was created with. The same draft then publishes successfully as version 1 under SourceFormat=CCDA, and the refused publish creates no version (the profile still lists only [0] and version 1 reads back as ResourceNotFoundException).
Emulator: answers ValidationException with message "SourceFormat must be the source data format of the profile, '<the profile's stored format>'" — the status (400) and the code match, but the message is an emulator-authored sentence for a rule AWS does not enforce, and the CSV mapping-key rule is not implemented at all, so no request can ever reach AWS's refusal. The replayed check saw ('ValidationException', "SourceFormat must be the source data format of the profile, 'CCDA'") where ('ValidationException', "CSV profile mapping must contain exactly one key: 'mapping-config.yaml'") was recorded.
Why: the message is a requirement. A caller is told the wrong reason for the refusal — it reads 'use the profile's own format' and will never discover that the real constraint is the single 'mapping-config.yaml' key a CSV mapping must carry; and a profile created under one SourceFormat can never be published under the other, which AWS allows when the draft's mapping has the right shape, so a legitimate publish is refused.
Fix: the PublishDataTransformationProfile handler's validation — replace the stored-format identity comparison with a check of the DRAFT (or FromExistingVersion) mapping against the requested SourceFormat: a CSV publish requires the mapping to contain exactly the one key 'mapping-config.yaml' and is refused with the sentence above; a CCDA publish accepts the template mapping. Neither path may create a version when it refuses.
Traces: healthlake.publish-ccda-mapping-under-csv-format-rejected. Code: services/service-com-amazonaws-healthlake-healthlake/src/ops/publish_data_transformation_profile.rs lines 232-239 (the `profile.source_format != input.source_format` refusal).
