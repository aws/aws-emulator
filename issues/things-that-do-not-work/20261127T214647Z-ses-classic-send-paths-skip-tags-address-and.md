# ses: classic send paths skip Tags, address and identity-ARN parameter validation and collapse every refusal into MessageRejected

> _Note: this issue was identified against the code base at commit `3c63a583c399d299d4ea298f38dfae7b708152ae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEmail

## Description
Three causes, all on service token ses, all on the classic (awsQuery, SimpleEmailService 2010-12-01) send paths SendEmail and SendRawEmail. They share one fault: the handlers perform no per-parameter validation of the send request's Tags, address and *Arn members, and every refusal they can produce is minted as the modeled MessageRejected error, so a request AWS refuses with the awsQuery sender error InvalidParameterValue (naming the offending parameter and its value) is instead refused with MessageRejected carrying the unverified-identity text, and a send authorized through an identity ARN reports the wrong identity.

Cause 1 of 3 — SendEmail: request-parameter refusals are reported as MessageRejected / unverified identity instead of InvalidParameterValue (fixture ses-message-tag-name-and-value-grammar-on-both-send-paths, step task#2; same cause on the steps listed under Traces, covering message-tag grammar, an address with no domain, the fifty-recipient cap and identity-ARN members).
AWS: Smithy (com.amazonaws.ses#SendEmail, protocol awsQuery, HTTP 400 for every client refusal) models exactly five errors — AccountSendingPausedException, ConfigurationSetDoesNotExistException (awsQueryError ConfigurationSetDoesNotExist), ConfigurationSetSendingPausedException, MailFromDomainNotVerifiedException and MessageRejected. InvalidParameterValue is NOT a modeled operation error: it is the awsQuery framework sender error the service raises when a REQUEST PARAMETER is malformed, and the recording shows it is what AWS uses for the tag grammar the model documents on com.amazonaws.ses#MessageTag$Name ("Contain only ASCII letters (a-z, A-Z), numbers (0-9), underscores (_), or dashes (-)" and "Contain 256 characters or fewer"; MessageTag$Value is documented the same way). Recorded behavior for a tag name that breaks that grammar: HTTP 400 with ErrorResponse.Error.Code "InvalidParameterValue" and ErrorResponse.Error.Message "Invalid tag name <campaign id>: only alphanumeric ASCII characters, '_',  '-' are allowed." — the fixed text is "Invalid tag name <", ">: only alphanumeric ASCII characters, '_',  '-' are allowed." (note the two spaces before '-'), and the ONLY variable part is the rejected tag name taken verbatim from the request's Tags member (here campaign id; a value violation words the same template for the value). The requirement AWS states is that a malformed request parameter is refused as a parameter fault, named by parameter and value, and that this refusal is reached BEFORE the sending identity's verification state is read — the recording's request would otherwise have been refused for its sender.
Emulator: answers HTTP 400 with ErrorResponse.Error.Code "MessageRejected" and ErrorResponse.Error.Message "Email address is not verified. The following identities failed the check in region US-WEST-2: <source address>" — replay: "$.ErrorResponse.Error.Code: value_mismatch (expected 'InvalidParameterValue', got 'MessageRejected')" and "$.ErrorResponse.Error.Message: value_mismatch (expected \"Invalid tag name <campaign id>: only alphanumeric ASCII characters, '_',  '-' are allowed.\", got 'Email address is not verified. The following identities failed the check in region US-WEST-2: sim2real-probe-ses-1a14f3e8@example.com')". The handler validates no Tags entry at all and resolves no *Arn member, so the first gate that can fire is the sender gate; where it does have a gate for the class under test (empty recipient set, recipient ceiling, address grammar) that gate mints MessageRejected with emulator-authored wording rather than the parameter fault AWS raises. 15 replayed steps are in this cluster.
Why: a client that sends with a malformed message tag, a recipient address with no domain, more than the recipient cap, or an *Arn member that names no SES identity is told its SENDING IDENTITY is unverified. The error code it switches on (InvalidParameterValue, a permanent request fault it must fix in the request) is replaced by MessageRejected, which SDK users and retry wrappers treat as a send-time rejection, and the message names an address that is not the problem, so the offending parameter is never identified and verification tooling is sent chasing an identity that is in fact verified.
Fix: the SendEmail handler's validation stage, which must gain per-parameter validation of Tags (name and value grammar and 256-char ceiling), of the address members and of SourceArn/ReturnPathArn, raise it as the awsQuery sender error InvalidParameterValue with AWS's own per-parameter wording, and run it before the account/configuration-set/verification gates — services/service-com-amazonaws-ses-simpleemailservice/src/ops/send_email.rs (the gate chain in handle(): the recipient checks, the illegal-address gate, then the sender gate at state.identities_refusing_send), with the refusal templates in services/service-com-amazonaws-ses-simpleemailservice/src/state.rs (illegal_address_message, unverified_identities_message).

Cause 2 of 3 — SendRawEmail: the same parameter refusals, on the raw send path (representative step ses-message-tag-name-and-value-grammar-on-both-send-paths#task#8; 9 replayed steps, also covering the address-without-domain, fifty-recipient-cap, identity-ARN and required-From/To fixtures).
AWS: Smithy (com.amazonaws.ses#SendRawEmail, awsQuery) models the same five errors and the same optional Tags / SourceArn / FromArn / ReturnPathArn members, with MessageTag$Name and MessageTag$Value carrying the grammar quoted above. Recorded behavior: HTTP 400, ErrorResponse.Error.Code "InvalidParameterValue", ErrorResponse.Error.Message "Invalid tag name <batch#9>: only alphanumeric ASCII characters, '_',  '-' are allowed." — same template as cause 1, variable part the rejected tag name from the request (here batch#9).
Emulator: HTTP 400 with Code "MessageRejected" and Message "Email address is not verified. The following identities failed the check in region US-WEST-2: <source address>" — replay: "$.ErrorResponse.Error.Code: value_mismatch (expected 'InvalidParameterValue', got 'MessageRejected')" / "$.ErrorResponse.Error.Message: value_mismatch (expected \"Invalid tag name <batch#9>: only alphanumeric ASCII characters, '_',  '-' are allowed.\", got 'Email address is not verified. The following identities failed the check in region US-WEST-2: sim2real-tagged@example.com')". src/ops/send_raw_email.rs has a single refusal constructor, fn rejected(), which always builds MessageRejected; there is no InvalidParameterValue path and no Tags/*Arn validation.
Why: identical client consequence to cause 1 on the raw path, which is the path SDK mail-composition helpers use; the refusal also hides which of the raw send's own parameter faults applies (tag grammar, an address parameter, the ARN members), so a client cannot tell a request it must repair from a transient send rejection.
Fix: the SendRawEmail handler's validation stage and its refusal vocabulary — services/service-com-amazonaws-ses-simpleemailservice/src/ops/send_raw_email.rs (fn rejected and the gate chain in handle()): validate Tags, the address parameters and SourceArn/FromArn/ReturnPathArn before the verification gate and emit the awsQuery InvalidParameterValue sender error with AWS's wording for the violated parameter.

Cause 3 of 3 — SendEmail: when the send is authorized through an identity ARN, the unverified-identity refusal names the Source address instead of the ARN (fixture ses-send-identity-arn-members-must-name-an-ses-identity, step task#1).
AWS: Smithy (com.amazonaws.ses#SendEmail) declares SourceArn and ReturnPathArn (target AmazonResourceName) as the sending-authorization members; the identity whose verification state governs the send is the identity those ARNs name, and MessageRejected's recorded message lists the identity that failed the check AS GIVEN in the request. Recorded behavior: HTTP 400, Code MessageRejected, Message "Email address is not verified. The following identities failed the check in region US-WEST-2: arn:aws:ses:us-west-2:000000000000:identity/example.com" — fixed text "Email address is not verified. The following identities failed the check in region ", then the Region from the request's credential scope (upper-cased), then ": " and the comma-separated list of the identities that failed, each rendered exactly as the request named it (an ARN when the request authorized through SourceArn/ReturnPathArn, an address otherwise). The account id, Region and domain in that recorded ARN are per-run values of the recording, not requirements.
Emulator: same status and code, but the failed-identity list carries the Source address — replay: "$.ErrorResponse.Error.Message: value_mismatch (expected 'Email address is not verified. The following identities failed the check in region US-WEST-2: arn:aws:ses:us-west-2:000000000000:identity/example.com', got 'Email address is not verified. The following identities failed the check in region US-WEST-2: sim2real-probe-ses-b0fea5e7@example.com')". The gate is called as state.identities_refusing_send(&source, &destinations, input.return_path) — the *Arn members are never passed in, so they are neither resolved to an identity nor reported.
Why: a client using SES sending authorization (sending on behalf of another account's identity via SourceArn) is told the wrong identity failed verification: it cannot tell whether the delegated identity's ARN or its own From address is the problem, and automated remediation verifies an identity that was never in question. It also means the ARN members have no effect on which identity is checked, so a delegated send is judged against the wrong identity.
Fix: the SendEmail handler's sender gate and the verification lookup behind it must take SourceArn/ReturnPathArn into account and report the identity as the request named it — services/service-com-amazonaws-ses-simpleemailservice/src/ops/send_email.rs (the state.identities_refusing_send call site) and services/service-com-amazonaws-ses-simpleemailservice/src/state.rs (identities_refusing_send, unverified_identities_message).
