## Description
One net-new root cause on the kinesisvideo data plane reached through GetDataEndpoint, grounded in the single failing check of this run that is neither ALREADY FILED nor OWNED (the other three kinesisvideo / cloudformation__kinesisvideo failures are OWNED by 20261107T191028Z-kinesisvideo-3-net-new-root-causes-the-discovered.md and 20261109T174330Z-cloudformation-kinesisvideo-no-aws-kinesisvideo-resource-type-is.md and were skipped).

NOTE on the related open issue, named so it is not read as covering this check: 20261107T191028Z-kinesisvideo-3-net-new-root-causes-the-discovered.md asked, in its Cause 1, for this refusal to carry the UnknownOperationException CODE where a restJson1 client reads it, because the emulator then answered a bare HTTP 404 with no classifiable code at all and the client reported Error.Code '404'. That part of the contract is now met — the check's `assert code == "UnknownOperationException"` passes and the replay key that issue carries for this check (`assert code == "UnknownOperationException", (`) no longer matches. What the check now fails on is the NEXT assertion in the same refusal, the absence of a message member, which that issue states as a requirement in prose but does not carry a replay key for. This is a distinct, newly observable defect in the same answer, not the state that issue describes.

=== Cause 1 of 1: the data-plane address's refusal of a control-plane route is rendered so that an AWS SDK reports an (empty) message member, where AWS's refusal carries no message member of any kind ===
AWS: recorded behavior only — UnknownOperationException is not a modeled kinesisvideo shape. The Smithy model (com.amazonaws.kinesisvideo#DescribeStream, POST /describeStream -> 200, errors ClientLimitExceededException 400 / InvalidArgumentException 400 / NotAuthorizedException 401 / ResourceNotFoundException 404; com.amazonaws.kinesisvideo#GetDataEndpoint, POST /getDataEndpoint -> 200, required APIName enum incl. PUT_MEDIA/GET_MEDIA/LIST_FRAGMENTS, output DataEndpoint) binds the control operations to the control endpoint only, so a control route asked for at an address GetDataEndpoint announced is refused by that endpoint. The recording shows the whole of that refusal is: HTTP 404, the error CODE UnknownOperationException (fixed text, the entire identification — restJson1 carries it in the x-amzn-ErrorType response header, there being no modeled body shape to hold a __type), and NO message member at all. There is no variable part: no stream name, ARN, path, operation name or member name appears anywhere in it, and a client reading the failure sees no Message.
Emulator: DescribeStream sent to the DataEndpoint returned for APIName=PUT_MEDIA is refused 404 with the x-amzn-errortype header set to UnknownOperationException (correct) but an EMPTY body and no content-type, and the SDK surfaces that failure with a message member whose value is the empty string. Replay: `AssertionError: DescribeStream on the media host must carry no message, got ''` — the check reads exc.response["Error"].get("Message") and requires it to be absent (None); the emulator's answer makes it present-and-empty. Hypothesis: botocore's rest-json error parser synthesizes Error.Message = '' whenever it parses an error body for a 4xx, so an answer whose body carries nothing at all still presents a message member; AWS's refusal, per the recording, is shaped such that no message member is surfaced. The fixer should take the wire form (status, x-amzn-ErrorType, body bytes, content-type) from the recording for this refusal — the requirement is that no message member reaches the client, not that the body merely be empty.
Why: a client cannot distinguish "this endpoint serves another plane, re-discover it" from a refusal that came with an explanatory sentence. KVS producers and consumers log and branch on the refusal's message as well as its code; an empty-string Message is a value AWS never sends, so error-formatting and log-scraping paths in a client render a blank reason, and any assertion that a wrong-plane refusal is message-free (the only thing distinguishing it from a modeled 404 such as ResourceNotFoundException, which always carries a sentence) is wrong against the emulator. The endpoint-discovery contract remains unverifiable from the client side in exactly this one respect.
Fix: the refusal rendering of the unrouted-on-a-data-plane-address answer in this service's routing seam — the same component Cause 1 of 20261107T191028Z already touched. It must keep status 404 and the UnknownOperationException class in x-amzn-ErrorType, and additionally render the answer so that an SDK reports NO message member for it, with nothing read from the request and nothing in the store touched.
