# eks: 3 net-new root causes — DeleteAccessEntry never revokes the principal's authorization at the cluster Kubernetes API, a managed nodegroup's UpdateNodegroupConfig/DeleteNodegroup lifecycle never converges, and the in-pod data-plane flows never reach a verdict

> _Note: this issue was identified against the code base at commit `965b3053fd6a88603311dd441a6858d4fb538678`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteAccessEntry

## Description
Three independent defects in the emulator's EKS service. Each cause below is a separate defect and must be closed separately; the failing check ids for each are listed with it. All three present as a wait that never settles: the emulator keeps answering, but it keeps answering the PRE-change value, so a client polling for the documented post-change state polls forever.

Cause 1 of 3: deleting an access entry does not revoke the principal's authorization at the cluster's Kubernetes API server.
AWS: Smithy: DeleteAccessEntry (DELETE /clusters/{clusterName}/access-entries/{principalArn}, HTTP 200, empty output; errors InvalidRequestException 400, ResourceNotFoundException 404, ServerException 500) removes the entry and with it every access policy associated to that principal. Beyond that the API server's side is recorded behavior only (it is not in the EKS Smithy model): on a real cluster, once the entry is gone the principal's IAM-derived bearer token no longer maps to any Kubernetes identity, so a request such as GET /api/v1/namespaces/default/pods?limit=1 is answered HTTP 401 with a Kubernetes Status object — kind "Status", apiVersion "v1", status "Failure", reason "Unauthorized", message "Unauthorized", code 401. (A 403 Forbidden is correct only where the token still authenticates and RBAC then denies it; after the entry is deleted the token authenticates to nothing.) The transition is eventually consistent but bounded — the checks allow minutes for it.
Emulator: after DeleteAccessEntry returns success, the same principal's pod read keeps returning HTTP 200 with the PodList. The verdict never changes, so the poll for the revocation runs until the run budget ends: TimeoutError: "the disassociated principal's pod read to stop succeeding: the run budget ended first; not graded" (eks.e2e-access-entry-kubectl-authorization-flow), and the dedicated revocation check never observes the 401 either (eks.eks-access-entry-deletion-leaves-the-principal-unauthorized). The authorizer in front of the served Kubernetes API evidently does not consult access-entry state when deciding a request, so removing the entry changes nothing.
Why: a client relying on AWS's behavior uses DeleteAccessEntry as the revocation primitive — it is how an operator cuts off a compromised or departing principal, and how CI asserts that de-provisioning worked. Against the emulator revocation is a no-op that reports success: a principal that was removed keeps full read access, every de-provisioning test passes vacuously, and a client that re-authenticates on 401 never learns its identity is gone.
Fix: the authorizer/authentication filter of the served cluster Kubernetes API data-plane handler — it must resolve the bearer token's principal against current access-entry state on every request (and invalidate any cached mapping when DeleteAccessEntry mutates it), rather than admitting a principal that was authorized when the token was minted. The DeleteAccessEntry handler's state mutation must be the authorizer's input. Related: 20261113T151622Z-eks-10-net-new-root-causes-in-the.md Cause 9 reports that an associated access POLICY is not enforced on writes; this cause is the complementary one — the ENTRY's removal is not enforced on reads — and neither check here is carried by that issue.
Traces: eks.e2e-access-entry-kubectl-authorization-flow (explicit: the disassociated principal's pod read never stopped succeeding), eks.eks-access-entry-deletion-leaves-the-principal-unauthorized.

Cause 2 of 3: a managed nodegroup's post-create lifecycle never converges — UpdateNodegroupConfig's UPDATING -> ACTIVE return and DeleteNodegroup's DELETING -> not-found are never observed.
AWS: Smithy: Nodegroup.status is NodegroupStatus with values CREATING, ACTIVE, UPDATING, DELETING, CREATE_FAILED, DELETE_FAILED, DEGRADED. UpdateNodegroupConfig (POST /clusters/{clusterName}/node-groups/{nodegroupName}/update-config, 200) returns an Update and moves the nodegroup to UPDATING; when the update's UpdateStatus reaches Successful the nodegroup returns to ACTIVE and DescribeNodegroup reports the NEW scalingConfig. DeleteNodegroup (DELETE /clusters/{clusterName}/node-groups/{nodegroupName}, 200) moves it to DELETING and, once removed, DescribeNodegroup is refused with ResourceNotFoundException at HTTP 404. Both transitions are asynchronous on real AWS but terminal.
Emulator: both checks that drive the whole sequence (create -> ACTIVE -> UpdateNodegroupConfig -> UPDATING -> ACTIVE with the new scaling config -> DeleteNodegroup -> DELETING -> 404) never reach the end state and are killed by the harness ("Check timed out after 60.0s"), while checks that only CREATE a nodegroup and then stop complete normally in the same run. Hypothesis: the nodegroup is parked in a non-terminal state — it stays UPDATING after UpdateNodegroupConfig (the Update never becomes Successful) and/or stays DELETING after DeleteNodegroup instead of DescribeNodegroup becoming ResourceNotFoundException/404.
Why: every client that manages node capacity waits on exactly these two transitions — the AWS CLI's `eks wait nodegroup-active`, Terraform, eksctl and CloudFormation all block until DescribeNodegroup reports ACTIVE after a scaling change and until it 404s after a delete. A nodegroup that never leaves UPDATING hangs the client's scale operation forever, and one that never 404s makes teardown (and therefore the surrounding stack/VPC delete) impossible, leaking the resource.
Fix: the nodegroup state machine in the EKS state/lifecycle component, and the UpdateNodegroupConfig and DeleteNodegroup handlers that must drive it to its terminal state (Update -> Successful, status -> ACTIVE; and removal of the nodegroup so DescribeNodegroup raises ResourceNotFoundException).
Traces: eks.nodegroup-full-lifecycle-transitions, eks.e2e-cluster-nodegroup-workload-scale-teardown.

Cause 3 of 3: the in-pod data-plane flows never reach a verdict — a pod never becomes observably Running with its projected token, and a pod IP is never reflected as a secondary address on a VPC ENI.
AWS: recorded behavior only (the cluster's Kubernetes API server and the CNI's ENI bookkeeping are not in the EKS Smithy model). On a real cluster a pod created on a managed node group's node reaches phase "Running" with status.podIP set; the projected service-account token under /var/run/secrets/eks.amazonaws.com/serviceaccount/token can be exchanged by sts:AssumeRoleWithWebIdentity from inside the pod, and a role condition on the token's `sub` that does not match the pod's service account is refused; and the pod's IP appears in the EC2 ENI description of the node's interface as a secondary private address (ec2:DescribeNetworkInterfaces -> PrivateIpAddresses), not as an address invented outside the VPC CIDR.
Emulator: neither check ever reaches its assertion — both are killed polling for the pod/ENI state ("Check timed out after 60.0s"). The proximate blockage is the served Kubernetes API's missing workload surface: GET /api/v1/nodes and the apps/v1 group are answered 404 and a returned Pod object omits spec.containers, so no pod ever becomes observably Running and no pod IP is ever published to correlate with an ENI.
Why: a client cannot verify that IRSA works for a real workload, nor that an `sts:AssumeRoleWithWebIdentity` sub-condition denies the wrong service account, nor that pod networking is VPC-native — the three properties these flows exist to prove. A poll that never terminates is also worse than a refusal: the client has no error to act on.
Fix: the served cluster Kubernetes API data-plane handler (pod admission/state so a pod reaches Running with a podIP and an echoed PodSpec, and the nodes collection) together with the CNI/ENI bookkeeping that must allocate the pod IP as a secondary address on the node's EC2 network interface. Related: 20261113T151622Z-eks-10-net-new-root-causes-in-the.md describes the 404 surfaces (its Causes 3, 4, 10) and already names eks.eks-pod-ip-is-a-secondary-address-on-a-real-vpc-eni in its trace ids, but neither check here was marked owned in this run and eks.eks-irsa-projected-token-assumed-inside-the-pod-and-sub-condition-denied is carried by no open issue; re-replay both after that surface is served.
Traces: eks.eks-irsa-projected-token-assumed-inside-the-pod-and-sub-condition-denied, eks.eks-pod-ip-is-a-secondary-address-on-a-real-vpc-eni.

## Evidence
Cause 1: DeleteAccessEntry on the principal returns success (HTTP 200, empty body); the SAME principal's subsequent GET <cluster endpoint>/api/v1/namespaces/default/pods?limit=1 continues to return HTTP 200 with a PodList for as long as it is polled. Expected HTTP 401 with {"kind":"Status","apiVersion":"v1","status":"Failure","reason":"Unauthorized","message":"Unauthorized","code":401} (the fixed text is the whole Status object; nothing in it is request-derived). Replay output: TimeoutError: the disassociated principal's pod read to stop succeeding: the run budget ended first; not graded (eks.e2e-access-entry-kubectl-authorization-flow, at _wait_for); eks.eks-access-entry-deletion-leaves-the-principal-unauthorized exhausted its budget without observing the 401.
Cause 2: create nodegroup -> ACTIVE succeeds; UpdateNodegroupConfig returns an Update, but DescribeNodegroup never returns to status ACTIVE carrying the new scalingConfig, and after DeleteNodegroup, DescribeNodegroup never becomes ResourceNotFoundException (HTTP 404). Both drivers were killed by the harness: "Check timed out after 60.0s" (eks.nodegroup-full-lifecycle-transitions, eks.e2e-cluster-nodegroup-workload-scale-teardown), while create-only nodegroup checks in the same run completed. Modelled terminal states: NodegroupStatus ACTIVE / ResourceNotFoundException 404; UpdateStatus Successful.
Cause 3: both in-pod flows were killed polling: "Check timed out after 60.0s" (eks.eks-irsa-projected-token-assumed-inside-the-pod-and-sub-condition-denied, eks.eks-pod-ip-is-a-secondary-address-on-a-real-vpc-eni). The surface they poll answers GET /api/v1/nodes with HTTP 404 {"kind":"Status",...,"reason":"NotFound","code":404} and returns Pod objects without spec.containers, so no pod ever reports phase Running with a status.podIP and no pod IP ever appears in the node ENI's PrivateIpAddresses.
