# Textract document-limit refusals and PDF reading diverge: DocumentTooLargeException message wording, a 5 MB inline Document.Bytes ceiling, every PDF refused as unsupported, and OCR glyph substitutions on two more paths

> _Note: this issue was identified against the code base at commit `8c63d5b7f8677a460355a4ac20e9a08b37d56b80`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AnalyzeDocument

## Description
This issue reports 4 distinct root causes in the textract service, grounded in 9 failing behavioral checks. A fixer must close ALL FOUR before submitting. Cause 3 below also carries a reopen note: REOPENS 20261022T105401Z-textract-synchronous-data-plane-rejects-supported-documents-with.md (and the related, also resolved 20261021T234200Z-textract-synchronous-data-plane-and-createadapter-validation-diverge.md): their fix made the raster paths return 200, but left every PDF document — a format AWS documents as supported — refused with a 400.

Already-filed work that does NOT cover anything below: the replay marked textract.analyze-document-combined-features-tables-and-forms and textract.detect-document-text-from-s3-object-source OWNED by 20261124T021047Z-textract-ocr-glyph-recognition-still-wrong-on-two.md, textract.detect-document-text-corrupt-image-rejected OWNED by 20261030T113700Z, and textract.analyze-id-page-over-size-limit-rejected ALREADY FILED against the unimplemented AnalyzeID stub; those four were skipped. The open 20261124T120152Z (DetectDocumentText Document.Bytes glyph substitution), 20261125T053817Z and 20261126T113734Z (Blocks geometry / templated feature blocks) issues carry no replay key for any check listed here.

Cause 1 of 4 — the DocumentTooLargeException Message for an S3-sourced document over the synchronous limit is not the sentence AWS uses.
AWS: Smithy (services/service-com-amazonaws-textract-textract/smithy-model/com-amazonaws-textract-textract.json): DocumentTooLargeException is a modeled client error at HTTP 400 with members Message/Code, documented "The document can't be processed because it's too large. The maximum document size for synchronous operations 10 MB." The recorded behavior for every synchronous operation reading Document.S3Object (AnalyzeDocument, DetectDocumentText, AnalyzeExpense) is: an object of exactly 10485760 bytes is analyzed (HTTP 200, DocumentMetadata.Pages 1, one PAGE block), and an object one byte larger is refused HTTP 400 DocumentTooLargeException whose Message is the template "S3 object size <size> is more than the maximum limit <limit>" — fixed text "S3 object size ", " is more than the maximum limit "; variable parts: <size> = the ContentLength Amazon S3 declares for the object version the request resolves to, <limit> = the synchronous ceiling 10485760. The status (400) and the code (DocumentTooLargeException) are correct today; only the Message diverges.
Emulator: HTTP 400 DocumentTooLargeException with Message "the document is <size> bytes; the maximum size of a document read from an Amazon S3 object is 10485760 bytes" — emulator-authored wording that names neither "S3 object size" nor "maximum limit". Built in services/service-com-amazonaws-textract-textract/src/state.rs at the ceiling check (the Unreadable::TooLarge format! around lines 1611-1621, with the channel label "read from an Amazon S3 object").
Why: a client that matches or logs the refusal text (or extracts the two numbers to report "object X is N bytes, limit M") sees a message AWS never sends; error-classification and user-facing messaging built on AWS's wording break, even though the code is right.
Fix: the shared document-read size check in the textract crate's state module (state.rs, the TooLarge branch that formats the message for DocumentChannel::S3Object) must emit AWS's sentence template; the per-operation handlers already map Unreadable::TooLarge onto the modeled DocumentTooLargeException and need no change.
Traces: textract.analyze-document-s3-object-over-size-limit-rejected, textract.analyze-document-s3-object-version-over-size-limit-rejected, textract.analyze-expense-document-over-size-limit-rejected, textract.detect-document-text-s3-object-over-size-limit-rejected.

Cause 2 of 4 — the inline Document.Bytes ceiling is enforced at 5 MB, so documents AWS accepts are refused, and the over-ceiling refusal is the wrong error.
AWS: Smithy: Document$Bytes targets ImageBlob with @length min 1, max 10485760 — the enforced inline ceiling is 10485760 bytes (the "maximum size ... in a blob of bytes is 5 MB" sentence in the member's prose is documentation only; the model constraint and the recorded behavior are 10485760). Recorded behavior: AnalyzeExpense with Document.Bytes of exactly 10485760 bytes returns HTTP 200 with DocumentMetadata {"Pages": 1} and one ExpenseDocuments entry; one byte more is refused HTTP 400 InvalidParameterException with Message "Request has invalid parameters" (fixed text, no variable part) — the constraint-violation sentence, not DocumentTooLargeException.
Emulator: an inline document of 10485760 bytes is refused HTTP 400 DocumentTooLargeException "the document is 10485760 bytes; the maximum size of a document provided as inline bytes is 5242880 bytes". The ceiling comes from MAX_INLINE_DOCUMENT_BYTES = 5 * 1024 * 1024 in state.rs (declared around line 136 and applied for DocumentChannel::Inline around line 1613), so every inline document between 5 MB and 10 MB is refused on every inline path (AnalyzeExpense, AnalyzeDocument, DetectDocumentText), and the refusal above the real ceiling would carry the wrong code and message too.
Why: a client submitting a legitimate 5-10 MB inline scan gets a 400 where AWS returns results, and a client that genuinely violates the blob constraint is told "document too large" instead of "invalid parameters", so retry/fallback logic keyed on the error class misroutes.
Fix: the inline ceiling constant and its refusal in the textract crate's state module (state.rs: MAX_INLINE_DOCUMENT_BYTES and the Inline branch of the channel ceiling check) — enforce 10485760 for the inline channel and answer a violation of that blob constraint with the modeled InvalidParameterException carrying "Request has invalid parameters".
Traces: textract.analyze-expense-inline-bytes-over-size-limit-rejected.

Cause 3 of 4 — every PDF document is refused as an unsupported format, on the synchronous and asynchronous paths alike.
AWS: Smithy: UnsupportedDocumentException is a modeled client error at HTTP 400 documented "The format of the input document isn't supported. Documents for operations can be in PNG, JPEG, PDF, or TIFF format." PDF is therefore a supported format. Recorded behavior: (a) AnalyzeDocument/DetectDocumentText with Document.Bytes holding a ONE-page PDF return HTTP 200 with DocumentMetadata.Pages 1 and PAGE/LINE/WORD blocks spelling the text drawn on that page; (b) the same synchronous call with a TWO-page PDF is refused HTTP 400 UnsupportedDocumentException with Message "Request has unsupported document format" (fixed text, no variable part); (c) StartDocumentAnalysis on the same two-page PDF in S3 succeeds and its GetDocumentAnalysis result reports DocumentMetadata.Pages 2 with each page's words carrying their own Page number; (d) an encrypted PDF (standard security handler) whose USER password is empty is decrypted and read like any other PDF, while one that needs a non-empty user password is refused HTTP 400 UnsupportedDocumentException "Request has unsupported document format".
Emulator: every PDF is refused HTTP 400 UnsupportedDocumentException "Request has unsupported document format", including the one-page PDF of (a) and the empty-user-password PDF of (d) — the checks errored on their first call, before reaching their negative case. This is deliberate in the current design: state.rs's module docs state "A PDF is answered there too: Textract accepts PDF, but this emulator has no page rasteriser and parses no PDF content stream, so it reads nothing out of one" (around lines 39-41), i.e. PDF is routed to Unreadable::UnsupportedFormat by the format dispatch in the document read path.
Why: PDF is the dominant document format for Textract clients. Every PDF pipeline — single-page synchronous reads, multi-page asynchronous jobs, and the common case of a PDF carrying an empty user password — fails closed against the emulator with an error that tells the client its input format is unsupported, which is false, so the client cannot distinguish "my file is broken" from "this service never reads PDFs".
Fix: the document read path in the textract crate's state module (state.rs: the format dispatch in read_content/DocumentChannel that classifies bytes and the page splitting feeding DocumentMetadata.Pages) must parse PDF — decrypt the standard security handler when the user password is empty, rasterise or extract the text of each page, and report the real page count — so the recogniser receives pages; the synchronous handlers then keep refusing only a MULTI-page PDF with UnsupportedDocumentException, and the asynchronous Start*/Get* paths read every page.
Traces: textract.analyze-document-two-page-pdf-rejected, textract.detect-document-text-password-protected-pdf-rejected.

Cause 4 of 4 — OCR glyph classification still substitutes characters on two paths no open issue holds a replay key for: AnalyzeDocument reading an S3 object, and the FORMS KEY_VALUE_SET VALUE words.
AWS: Smithy: Block$Text is documented "The word or line of text that's recognized by Amazon Textract", BlockType WORD is "one or more ISO basic Latin script characters that aren't separated by spaces", and KEY_VALUE_SET carries the KEY/VALUE EntityTypes linked by the VALUE relationship. The requirement is character-exact and general: for ANY ASCII text rasterised onto a page, each WORD block's Text spells exactly the characters drawn, through either Document source and whatever FeatureTypes are requested. These are HTTP 200 responses — no status or error code is involved, only the recognised text.
Emulator: characters that were never drawn come back. Reading an S3 object whose PNG renders the single word "BIRCH", AnalyzeDocument(FeatureTypes=[TABLES]) returns the WORD set {'DIFGH'} (B->D, R->F, C->G); reading inline bytes rendering a form line whose NAME value is "JOHN SMITH", the VALUE block's CHILD words join to 'JOHN SMILH' (T->L). The structure is correct in both (the S3 version is resolved, the KEY's VALUE relationship resolves to the right block) — only the per-glyph classification is wrong. The quoted strings are one run's output filling the template above, not the requirement.
Why: both calls are a 200 whose structure validates while the text is fabricated, so the corruption is silent: a version-pinned read returns the wrong document's apparent content, and a form consumer stores 'JOHN SMILH' as the person's name. Nothing in the response signals that recognition failed.
Fix: the per-glyph classifier/segmenter in the textract crate's OCR module (services/service-com-amazonaws-textract-textract/src/state/ocr.rs and the glyph matching it uses), shared by every read path; the S3-sourced read and the FORMS KEY_VALUE_SET derivation consume its output and need no change once the characters are right. Related: the open 20261124T021047Z-textract-ocr-glyph-recognition-still-wrong-on-two.md describes the same class but carries keys only for the two checks the replay marked OWNED, and the resolved 20261119T223911Z-textract-ocr-still-misclassifies-glyphs-inside-recognised-words.md claimed textract.analyze-document-forms-extracts-key-value-pairs — that check fails again here, still a 200 with substituted glyphs rather than a refusal.
Traces: textract.analyze-document-deleted-s3-version-rejected, textract.analyze-document-forms-extracts-key-value-pairs.
