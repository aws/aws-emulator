# iot: 5 net-new causes — the mTLS named-shadow REST route answers 404 UnknownService, MQTT CONNECT ignores the policy's thing-name client scope, a command execution's result map values are dropped, and neither a job's abort criteria nor its retry criteria ever take effect

> _Note: this issue was identified against the code base at commit `eef1405ac0806ef267777bba6aefe2b3b0754197`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateThingShadow

## Description
Five independent net-new root causes in service iot, all found by the behavioral suite under the `iot` service heading. Each cause must be closed before submitting. Related open issues are named per cause and none of them carries these checks.

Cause 1 of 5: the certificate-authenticated (mTLS) Device Shadow REST route is not served at the published iot:Data-ATS address — POST /things/{thingName}/shadow?name=<shadow> answers 404 UnknownService.
AWS: Smithy iot-data UpdateThingShadow is POST /things/{thingName}/shadow with shadowName bound as httpQuery `name` and the document as the httpPayload, answering 200 with the merged shadow document; it models InvalidRequestException (400), UnauthorizedException (401), ConflictException (409) and others. A device authenticates to this route with its X.509 certificate (mutual TLS) on the account's iot:Data-ATS host — no SigV4 credential scope and no X-Amz-Target are present on such a request, and the route is selected from the URI path alone.
Emulator: every such request is answered HTTP 404 with body {"__type": "UnknownService", "message": "could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"} — the front door tries to resolve a service from signing metadata the device does not send, so the whole mTLS shadow path is unreachable.
Why: a device holding a certificate cannot read, write or version any shadow over HTTPS; the merge-and-version semantics the data plane exists for are unobservable and every client built on certificate-authenticated shadow updates diverges at the first call. Open issue 20261110T222008Z-iot-the-published-data-plane-address-serves-no.md reports the same 404 for POST /topics/{topic} (publish) but names no shadow route; this cause is the /things/{thingName}/shadow route and must be closed on its own.
Fix: the mTLS listener's request routing — resolve iot-data operations from the URI path (and client certificate) rather than from SigV4/X-Amz-Target, and bind the shadow routes on it (the emulator's data-plane listener/router plus services/service-com-amazonaws-iotdataplane-iotmoonrakerservice/src/ops/update_thing_shadow.rs and get_thing_shadow.rs).
Traces: iot.device-certificate-shadow-update-over-https-merges-and-versions-the-named-shadow.

Cause 2 of 5: the MQTT broker accepts a CONNECT whose client id is not the certificate's attached thing name, where the attached policy scopes iot:Connect to that thing.
AWS: recorded behavior only (IoT policy evaluation is not in the Smithy model). A certificate attached to a thing and to a policy whose iot:Connect resource is the client ARN of that thing (equivalently written with the ${iot:Connection.Thing.ThingName} policy variable) may open an MQTT 3.1.1 session ONLY with a client id equal to the attached thing's name. A CONNECT presenting any other client id is refused by the broker — the connection is closed / CONNACK is not a success — repeatably, not once.
Emulator: the same certificate connects successfully with client id "<thing>-other": three consecutive CONNECT attempts all return rc 0 with no disconnect and no error, so the thing-scoped client restriction is not evaluated at CONNECT at all.
Why: any device certificate can impersonate any other client id, which is exactly the isolation the thing policy variable exists to provide; a client testing that its fleet policy confines a device to its own client id sees it pass when it does not hold. Open issue 20261122T200530Z-iot-the-iot-data-ats-mqtt-broker-never.md covers the client-ARN form of this for the check mqtt-connect-is-refused-when-the-client-id-falls-outside-the-policy-client-arn; it does not carry this check (the thing-policy-variable form, where the permitted client id comes from the certificate's attached thing).
Fix: the MQTT broker's CONNECT authorization — evaluate the attached policies' iot:Connect statements, resolving thing policy variables from the certificate's attached thing, before sending a success CONNACK (the emulator's MQTT broker authorization path plus the certificate/thing/policy state it reads).
Traces: iot.mqtt-connect-with-a-client-id-other-than-the-attached-thing-name-is-rejected.

Cause 3 of 5: a command execution's device-reported `result` reads back with empty value structures — the typed value members are dropped.
AWS: Smithy GetCommandExecution (GET /command-executions/{executionId}?targetArn=&includeResult=) returns `result` of shape CommandExecutionResultMap (map, @length min 1) whose key is CommandExecutionResultName and whose value is the CommandExecutionResult structure with members S (string), B (boolean) and BIN (blob). Recorded behavior: when a device reports {"result": {"position": {"S": "40"}}} with its terminal status, GetCommandExecution reads the result back unchanged — {"position": {"S": "40"}} — with the typed member the device sent and its value.
Emulator: the map key survives but the value structure is empty — the result reads back as {"position": {}} — so every S/B/BIN value the device reported is lost.
Why: the result field exists so a device can return a value (a remote function's return value) to the caller; a client reading it gets a well-formed but empty structure and cannot tell a reported value from an absent one. This is a silent data loss on the read path, on an execution that is otherwise correctly terminal.
Fix: the command-execution result deserializer on the device-report path and/or GetCommandExecution's projection of the stored CommandExecutionResultMap — persist and serialize the S/B/BIN members (services/service-com-amazonaws-iot-awsiotservice/src/ops/get_command_execution.rs plus the command-execution state record and the $aws/commands response handler that writes it).
Traces: iot.command-execution-device-reported-failure-is-terminal.

Cause 4 of 5: a job's abortConfig criteria never fire — a device-reported FAILED execution does not cancel the job or its queued sibling execution.
AWS: Smithy CreateJob accepts abortConfig (AbortConfig with a @required criteriaList) whose criteria carry failureType, action, thresholdPercentage and minNumberOfExecutedThings. Recorded behavior: with a criterion {failureType: FAILED, action: CANCEL, thresholdPercentage: 50.0, minNumberOfExecutedThings: 1} over two targeted things, the device reporting FAILED on the first execution drives DescribeJob to status CANCELED (with forceCanceled not true), leaves that execution FAILED with its statusDetails.detailsMap, moves the still-QUEUED execution on the other thing to CANCELED, drops the job from that thing's GetPendingJobExecutions, and settles jobProcessDetails to numberOfFailedThings 1 / numberOfCanceledThings 1 / numberOfQueuedThings 0.
Emulator: after the FAILED report the job never leaves its in-progress status and the queued execution never leaves QUEUED, so the check's polls never satisfy and it is cut off at the harness budget (reported as "Check timed out after 60.0s"). No abort evaluation happens on an execution status change.
Why: a client relying on abort criteria to stop a bad rollout sees the rollout continue to every remaining target; the job, its sibling executions and its process counters all stay in a state AWS would have left behind.
Fix: evaluate the job's abortConfig criteria when an execution reaches a terminal failure — cancel the job (not force-cancel), cancel still-queued executions, remove them from the device's pending set, and maintain jobProcessDetails (the job-execution update path in the jobs data plane plus job state: services/service-com-amazonaws-iot-awsiotservice job/job-execution state and services/service-com-amazonaws-iotjobsdataplane-iotlaserthingjobmanagerexternalservice/src/ops/update_job_execution.rs).
Traces: iot.job-abort-on-failed-execution-cancels-queued-twin.

Cause 5 of 5: a job's jobExecutionsRetryConfig never requeues — a FAILED execution is not retried, and a REJECTED one is not spared.
AWS: Smithy CreateJob accepts jobExecutionsRetryConfig (JobExecutionsRetryConfig with a @required criteriaList of 1..2 RetryCriteria, each a failureType plus numberOfRetries). Recorded behavior: with a retry criterion on FAILED, a device-reported FAILED execution is automatically requeued (its status returns to QUEUED and it reappears in the device's pending executions) up to the configured retry count, while an execution whose failureType is not covered — a REJECTED report — stays terminal and is never requeued.
Emulator: the FAILED execution stays FAILED, is never requeued, so the check's wait for the retried execution never satisfies and it is cut off at the harness budget ("Check timed out after 60.0s"). No retry evaluation happens on an execution status change.
Why: a client configuring retries to absorb transient device failures gets none; its devices are left in a terminal state AWS would have retried, and the contrast with a non-retried failure class (REJECTED) that the configuration exists to express is lost.
Fix: evaluate jobExecutionsRetryConfig when an execution reaches a terminal failure — requeue the execution for the matching failureType up to numberOfRetries, leave uncovered failure types terminal, and reflect the requeue in DescribeJobExecution and GetPendingJobExecutions (same job-execution update path and job state as Cause 4).
Traces: iot.job-retry-requeues-failed-execution-but-not-rejected-one.
