# appsync__lambda: 2 net-new causes — Direct Lambda / pipeline / BatchInvoke resolvers never invoke their data-source function, and an AWS_LAMBDA Lambda authorizer is never invoked

> _Note: this issue was identified against the code base at commit `2ac91d382b67c33b3b1ad8ceed805222f48956bf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GraphQL (AppSync data-plane POST on the API's GRAPHQL uri)

## Description
Two net-new root causes in the AppSync GraphQL data plane. Both are observed only through the data plane; the control-plane calls (CreateGraphqlApi/CreateDataSource/CreateResolver/StartSchemaCreation) all succeed, so the divergence is in resolution, not in configuration.

Cause 1 of 2: a resolver bound to an AWS_LAMBDA data source never invokes the function, so every field it owns resolves to null and the response carries no `errors` entry.
AWS: for a resolver on an AWS_LAMBDA data source with no request/response mapping templates and no code (a Direct Lambda resolver, operation Invoke), AppSync invokes the data source's function once per field resolution, passing the whole resolver context document (`arguments`, `identity`, `source`, `request`, `prev`, `info` with `fieldName`/`parentTypeName`/`selectionSetList`), and answers HTTP 200 with the handler's return value as the field value. When the handler raises, AppSync answers HTTP 200 with the field null and exactly one `errors` entry whose `errorType` is the raised exception's class name and whose `message` is the exception text. With `operation: BatchInvoke` and `maxBatchSize >= N`, AppSync merges N sibling field resolutions into exactly ONE invocation whose event is a bare JSON list of N context documents, and a per-item error in the returned list nulls only that sibling and yields exactly one `errors` entry. When the data source's service role cannot `lambda:InvokeFunction`, AppSync answers 200 with the field null and an `errors` entry naming the authorization failure. This is the documented resolver/data-source contract (AppSync developer guide, 'Direct Lambda resolvers' and the JS resolver batching guide); the Smithy model for appsync covers only the control plane, so the data-plane wire shape above is recorded behavior only.
Emulator: no invocation ever reaches the function. Checks that poll for the function's side effect or for the resolved field exhaust their budget ('Check timed out after 60.0s' / TimeoutError '… the run budget ended first; not graded'). Where the endpoint does answer, it answers HTTP 200 with every field null and NO `errors` key at all — e.g. `{'data': {'open': None, 'secret': None}}` for a query whose two fields both have resolvers, and `errors` absent (length 0) where exactly one entry is required for a per-item batch error.
Why: a client using AppSync as a Lambda front end gets a successful-looking 200 whose data is entirely null and whose error channel is empty, so neither the happy path nor any failure classification (unhandled exception type, per-item batch error, service-role denial) can be distinguished from a legitimately null field.
Fix: the AppSync data-plane resolver executor — the AWS_LAMBDA data-source dispatch path (Invoke and BatchInvoke), its context-document builder, its pipeline `prev.result` threading and its error-to-`errors[]` mapper.
Traces: appsync__lambda.appsync-batch-invoke-merges-sibling-fields-into-one-invocation, appsync__lambda.appsync-batch-invoke-partial-item-error-isolates-the-failing-sibling, appsync__lambda.appsync-pipeline-direct-lambda-functions-thread-prev-result, appsync__lambda.xsvc-appsync-3-direct-lambda-resolver-error-propagates-exception-type, appsync__lambda.xsvc-appsync-3-direct-lambda-resolver-receives-full-context-event, appsync__lambda.xsvc-appsync-3-service-role-without-lambda-invoke-permission-denied.

Cause 2 of 2: an API configured with the AWS_LAMBDA authorization mode never invokes its authorizer function, so no authorization decision, no `deniedFields` projection and no `ttlOverride` caching behaviour is observable.
AWS: with `authenticationType: AWS_LAMBDA` and a `lambdaAuthorizerConfig`, AppSync invokes the authorizer function with the request's authorization token before resolving; the function returns `{isAuthorized, resolverContext, deniedFields, ttlOverride}`. `isAuthorized: false` makes AppSync answer 200 with null data and an UnauthorizedException-class `errors` entry and NEVER invoke the field resolver. `deniedFields` nulls exactly the listed fields and leaves the rest resolved — with `deniedFields` empty every field must resolve and no `errors` key appears. `ttlOverride: 0` disables caching so the authorizer is invoked on EVERY request, and a positive `ttlOverride` caches the decision for that many seconds (exactly one invocation inside the window). An `identityValidationExpression` that the presented token does not match is refused before the authorizer is invoked at all. Documented in the AppSync developer guide ('Lambda authorization'); recorded behavior only as far as the on-disk model goes.
Emulator: the authorizer function is never invoked. Requests either never settle (the checks' readiness polls exhaust the run budget) or answer 200 with every field null and no `errors` key even when `deniedFields` is empty, which is the control leg that proves the authorizer result was never applied: `with deniedFields empty both fields must resolve and no errors key appear, got {'data': {'open': None, 'secret': None}}`.
Why: a client that gates an AppSync API on a Lambda authorizer gets neither the grant nor the denial — unauthenticated callers are indistinguishable from authorised ones, and a field the authorizer explicitly allowed comes back null.
Fix: the AppSync data-plane request pipeline — the AWS_LAMBDA authorization-mode pre-resolution hook, its authorizer-response handling (isAuthorized / resolverContext / deniedFields / ttlOverride) and its identityValidationExpression gate.
Traces: appsync__lambda.appsync-lambda-authorizer-denial-blocks-resolver-rejected, appsync__lambda.appsync-lambda-authorizer-identity-validation-expression-rejects-before-invoke, appsync__lambda.appsync-lambda-authorizer-result-ttl-caches-exactly-one-invocation, appsync__lambda.deep-appsync-2-appsync-authz-denied-fields-nulls-only-the-denied-field.

Related open issue 20261111T065707Z-apigateway-appsync-the-graphql-api-s-published-uris.md records that the published uris.GRAPHQL is a real-AWS hostname; it does not cover either cause above (these checks do reach the emulator's GraphQL endpoint and get 200s with null data).

## Steps to Reproduce
1. Create a GraphQL API, a Lambda function, an AWS_LAMBDA data source pointing at it with a service role that may lambda:InvokeFunction, and a resolver with no templates and no code (Direct Lambda, operation Invoke).
2. POST a query to the API's GRAPHQL uri and observe the response: AWS returns the handler's value; the emulator returns 200 with the field null and no errors key, and the function is never invoked.
3. Repeat with operation BatchInvoke and maxBatchSize >= 2 over sibling fields: AWS performs ONE invocation with a bare list event; the emulator performs none.
4. Reconfigure the API with authenticationType AWS_LAMBDA and a lambdaAuthorizerConfig whose function returns {"isAuthorized": true, "deniedFields": []}: AWS resolves every field with no errors key; the emulator returns every field null.
5. Replay the check ids in trace_ids.
