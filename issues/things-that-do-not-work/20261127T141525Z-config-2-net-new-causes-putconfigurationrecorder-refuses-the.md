# config: 2 net-new causes — PutConfigurationRecorder refuses the supported resource type AWS::SSM::Parameter, and PutDeliveryChannel refuses a same-account bucket whose delivery grant is on the recorder's IAM role

> _Note: this issue was identified against the code base at commit `87d71c43287cb88d437f1b22d9a50457d3db170d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutConfigurationRecorder

## Description
TWO distinct root causes on AWS Config's recorder/delivery-channel bring-up paths, grounded in three failing behavioral checks. TWO CAUSES must be closed before submitting. Each cause blocks its checks during bring-up, so the behaviour the checks were written for is never reached at all.

Neither is covered by an existing open issue. The nearest neighbours were checked and do NOT cover them: 20261022T190340Z-config-putconfigrule-and-putdeliverychannel-are-overly-permissive-inconsistent.md covers PutDeliveryChannel being too PERMISSIVE about ARN fields and bucket names (it accepts what AWS refuses), not the opposite over-strict refusal below; 20261127T023436Z-config-sqs-a-stopped-then-restarted-configuration-recorder.md covers a restarted recorder staying inert, not the resource-type admission set or delivery authorization; 20261030T093351Z-config-6-net-new-behavioral-root-causes-putconfigrule.md covers PutConfigRule/TagResource/PutConfigurationAggregator validation renderings only.

--- Cause 1 of 2: PutConfigurationRecorder refuses an INCLUSION recording group that names AWS::SSM::Parameter, so a recorder for that type can never be created (checks config.start-remediation-execution-batch-with-no-noncompliant-key-rejected, config.start-remediation-execution-mixed-batch-runs-only-the-noncompliant-key).
AWS: recorded behavior only — PutConfigurationRecorder with ConfigurationRecorder={name, roleARN, recordingGroup:{allSupported:false, resourceTypes:['AWS::SSM::Parameter']}} is ACCEPTED and answers 200 with an empty JSON body; both checks then go on to deploy a conformance pack and exercise StartRemediationExecution. The shipped Smithy model does not enumerate that value (smithy_query query='shape' shape='ResourceType' on services/service-com-amazonaws-configservice-starlingdoveservice/smithy-model/com-amazonaws-configservice-starlingdoveservice.json lists AWS::SSM::Document, AWS::SSM::FileData, AWS::SSM::ManagedInstanceInventory, AWS::SSM::AssociationCompliance, AWS::SSM::PatchCompliance, AWS::SSM::ResourceDataSync — but no AWS::SSM::Parameter), i.e. the modelled enum lags Config's published supported-resource-type catalogue. That is exactly the premise the emulator's own state/resource_type.rs module documentation states ("Config records the resource types its published catalogue covers and that catalogue GROWS"), but it applies the widened admission only to the LISTING members. PutConfigurationRecorder models InvalidRecordingGroupException and ValidationException (both client, httpError 400, defaulted).
Emulator: answers 400 ValidationException with the fixed, request-independent sentence "The resource type you specified is not supported by AWS Config. Verify the resource type, and try again." (no variable parts; it is state/resource_type.rs::UNSUPPORTED_RESOURCE_TYPE_MESSAGE), raised at the request boundary because RecordingGroup.resourceTypes targets the closed ResourceType enum — state/resource_type.rs says so in its own words: "The members that take a resource type to RECORD it ... stay inside the modelled set and are refused outside it at the request boundary." The handler itself (src/ops/put_configuration_recorder.rs) performs no resource-type check, so the refusal is purely the modelled enum's closed value set.
Why: a client cannot create a recorder for any resource type AWS Config supports but this checkout's model snapshot does not enumerate — and since the recorder is the precondition for rules, discovery, evaluation and remediation, the whole remediation surface for such a type is unreachable rather than merely unrecorded. The refusal is also indistinguishable from the genuine "this is no resource type at all" refusal, which carries the same sentence.
Fix: the resource-type admission rule and the request-boundary validation of RecordingGroup.resourceTypes (services/service-com-amazonaws-configservice-starlingdoveservice/src/state/resource_type.rs, applied for PutConfigurationRecorder / AssociateResourceTypes / DisassociateResourceTypes) — admit a well-formed AWS resource-type name that the modelled enum does not happen to list, as the listing paths already do, and keep the fixed sentence only for values that name no resource type at all. A type the recorder cannot OBSERVE must still be storable in the recording group (it simply records nothing), which is what AWS does.

--- Cause 2 of 2: PutDeliveryChannel refuses a same-account delivery bucket whose delivery permission is granted by the configuration recorder's IAM role policy rather than by a bucket policy, so a documented same-account Config setup can never be completed (check config.resource-config-unicode-and-binary-blob-round-trip).
AWS: PutDeliveryChannel models InsufficientDeliveryPolicyException (client, 400) — "Your Amazon S3 bucket policy does not allow Config to write to it". That refusal is for a bucket whose policy withholds the delivery; for a bucket in the SAME account as the recorder, Config assumes the configuration recorder's own IAM role and performs the delivery under that role's identity, so an identity-based grant of s3:GetBucketAcl on arn:aws:s3:::<bucket> plus s3:PutObject on arn:aws:s3:::<bucket>/AWSLogs/<account-id>/* is sufficient and no bucket policy is required (a bucket policy naming config.amazonaws.com is what cross-account delivery needs). Recorded behavior: the check's bring-up creates the bucket with NO bucket policy, grants exactly those two actions on the recorder role as an inline policy, and AWS accepts the channel with 200 and an empty body, after which StartConfigurationRecorder reports recording=true.
Emulator: PutDeliveryChannel keeps refusing with InsufficientDeliveryPolicyException, because its delivery decision reads the BUCKET POLICY only. services/service-com-amazonaws-configservice-starlingdoveservice/src/state/delivery_authorization.rs states the rule it implements: "Config makes the S3 calls a delivery needs AS ITS OWN SERVICE PRINCIPAL, and a service principal holds no identity-based policies, so the ONLY source of that permission is the policy in force on the named bucket ... a bucket carrying no policy at all withholds the first of them", and explicitly "What that role is ALLOWED is a different question, and not this one: the S3 calls below are not made under the role's identity, so a grant it states permits none of them." The check retries exactly that error code on a 90 s poll, so it never converges and the harness kills the check: "Error: Check timed out after 60.0s" — no assertion of the check is ever reached. Hypothesis (the loop is not named in the report, only the timeout is): the bring-up's only polls that can spin forever are the PutDeliveryChannel poll (retrying InsufficientDeliveryPolicyException) and the StartConfigurationRecorder poll (retrying NoAvailableDeliveryChannelException, which follows from no channel existing); PutConfigurationRecorder's own poll retries only InvalidRoleException, which this handler raises solely for a blank roleARN, so it cannot be the one spinning.
Why: a client that sets Config up the documented same-account way — service role with S3 permissions, no bucket policy — can never create a delivery channel, so no recorder can be started and every operation that requires a running recorder (PutResourceConfig, resource discovery, rule evaluation, snapshot/history delivery) is unreachable. The refusal also mis-reports WHY: it names the bucket policy for a setup in which AWS never consults one.
Fix: services/service-com-amazonaws-configservice-starlingdoveservice/src/state/delivery_authorization.rs — for a bucket in the same account as the recorder, decide the two delivery checks under the recorder role's identity-based policies as well (assume the role, then evaluate the role's grants for s3:GetBucketAcl and s3:PutObject on the delivery path), and keep the bucket-policy requirement where AWS keeps it (a bucket in another account); a permission established either way must take the channel. Closing this cause also requires the check's own assertions, which have never run, to hold: PutResourceConfig for an unregistered custom type refused 400 ValidationException with "Cannot find registered Resource Type with name " + the submitted ResourceType + ". Please register the Resource Type with Cloudformation and try again." (fixed text; the type name is from the request), GetResourceConfigHistory for a never-ingested resource refused 400 ResourceNotDiscoveredException with "Resource " + the submitted resourceId + " of resourceType:" + the submitted resourceType + " is unknown or has not been discovered" (fixed text; both values from the request), and BatchGetResourceConfig fabricating no baseConfigurationItems for that key.

Traces (failing check ids, as examples): config.start-remediation-execution-batch-with-no-noncompliant-key-rejected and config.start-remediation-execution-mixed-batch-runs-only-the-noncompliant-key (cause 1), config.resource-config-unicode-and-binary-blob-round-trip (cause 2).
