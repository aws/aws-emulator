# kms__stepfunctions: 3 net-new causes — StartExecution on a CMK-encrypted machine is refused KmsAccessDeniedException for a granted execution role, an un-assumable role is reported as a KMS resource-policy denial instead of the assume-role failure, and the relayed denial names the emulator's own IAM user

> _Note: this issue was identified against the code base at commit `3bfb7cd772781c7f8fd33f0bb610479e140a70f3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
REOPENS 20261109T164957Z-kms-stepfunctions-2-net-new-causes-an-execution.md: its fix left the call refused.

Three net-new root causes about how Step Functions acquires and reports its KMS data key when it starts an execution of a CUSTOMER_MANAGED_KMS_KEY state machine. All four grounding checks were left unmarked by the replay report (no ALREADY FILED marker, no OWNED marker). Smithy model used: services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json. Neighbouring issues that do NOT cover these: 20261111T004529Z-kms-stepfunctions-startsyncexecution-on-a-cmk-encrypted-express.md (same family of defect but on StartSyncExecution and on the CALLER's key-policy grant, not StartExecution and the execution role's identity-policy grant), 20261110T140310Z-kms-stepfunctions-2-net-new-causes-createactivity-with.md (open; its Cause 2 names the same check as Cause 1 below but describes the opposite emulator behaviour — a poll that never settles — and does not carry this refusal), and 20261111T062437Z-kms-stepfunctions-3-net-new-causes-updatestatemachine-back.md (mid-execution key state / authorization, not the start path).

Cause 1 of 3: StartExecution on a CMK-encrypted state machine is refused HTTP 400 KmsAccessDeniedException even though the execution role's identity policy grants kms:GenerateDataKey and kms:Decrypt on exactly that key and the key's default key policy delegates authorization to the account root.
Failing check ids: kms__stepfunctions.cmk-trust-removed-then-restored-execution-redrive-succeeds, kms__stepfunctions.sfn-execution-role-trust-honors-source-account-and-source-arn.
AWS: Smithy models StartExecution{stateMachineArn (required), name, input, traceHeader} -> {executionArn (required), startDate (required)} with KmsAccessDeniedException / KmsInvalidStateException / KmsThrottlingException all HTTP 400; KmsAccessDeniedException is documented as "Either your KMS key policy or API caller does not have the required permissions." A key created by kms:CreateKey with no explicit policy carries the default policy that allows kms:* to arn:aws:iam::<account>:root, which delegates authorization to IAM, so a role whose inline policy allows kms:GenerateDataKey+kms:Decrypt on that key ARN IS authorized and StartExecution returns 200 with an executionArn; KmsAccessDeniedException is reserved for a principal whose grant is actually missing or explicitly denied. Recorded behaviour confirms the positive leg: a CMK-encrypted STANDARD execution under such a role runs and SUCCEEDS.
Emulator: StartExecution answers 400 KmsAccessDeniedException with message "User: states.amazonaws.com is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> because no resource-based policy allows the kms:GenerateDataKey action (Service: Kms, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)". Two things are wrong in it besides the refusal itself: the denied principal is rendered as the service principal states.amazonaws.com rather than the STS session that makes the call, and the reason is "no resource-based policy allows" — i.e. the key policy is required to name the principal explicitly and neither the role's identity policy nor the default policy's root delegation is consulted. Because the refusal never clears, the sibling check that retries only KmsAccessDeniedException while a fresh grant propagates spins until the harness kills it ("Check timed out after 60.0s", its own budget being 150 s).
Why: the whole CMK path is unusable from the configuration AWS documents. A client that grants kms:GenerateDataKey/kms:Decrypt to the execution role in an identity policy — the normal setup — can never start an execution of its encrypted state machine, and because the code returned is the one AWS uses for a genuinely missing grant, the client is sent to re-check a policy that is already correct. Everything downstream of a start (DescribeExecution, redrive, history) is unreachable for encrypted machines.
Fix: the StartExecution handler's KMS authorization for CUSTOMER_MANAGED_KMS_KEY machines — the data-key acquisition must be authorized as the execution role's assumed-role session against BOTH the key policy (including root delegation) and the role's identity policies, and only an actually-unauthorized principal may be refused KmsAccessDeniedException.
Traces: kms__stepfunctions.cmk-trust-removed-then-restored-execution-redrive-succeeds, kms__stepfunctions.sfn-execution-role-trust-honors-source-account-and-source-arn.

Cause 2 of 3: when the execution role genuinely cannot be assumed (its trust policy's aws:SourceAccount / aws:SourceArn Condition does not match the starting state machine), the refusal is reported as a generic KMS resource-policy denial instead of the assume-role failure AWS relays.
Failing check ids: kms__stepfunctions.sfn-execution-role-trust-source-account-mismatch-blocks-cmk-execution, kms__stepfunctions.sfn-execution-role-trust-honors-source-account-and-source-arn.
AWS: recorded behaviour only (the Smithy model constrains roleArn only as an Arn). On a CMK-encrypted machine the un-assumable role surfaces at StartExecution as HTTP 400 KmsAccessDeniedException whose message is the relayed STS failure, fixed text "com.amazonaws.sfn.invoker.sts.AssumeRoleFailedCacheableException: The principal states.amazonaws.com is not authorized to assume the provided role. (role: <role ARN>)" — every word fixed except <role ARN>, which is the state machine's configured roleArn. The denial is permanent: unlike a propagation race it never clears on retry, which is exactly how a client distinguishes the two.
Emulator: the refusal carries the Cause 1 wording instead ("User: states.amazonaws.com is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> because no resource-based policy allows ..."), so the assume-role failure is never named and a client cannot tell a permanent trust mismatch from a transient KMS/IAM propagation window. The checks that wait for the permanent message are consequently killed at the harness cap ("Check timed out after 60.0s").
Why: aws:SourceAccount/aws:SourceArn on a service trust policy is the standard confused-deputy guard. A client that hardens or audits a role this way gets an error that names KMS and the key instead of the role it must fix, and a retry loop that is correct against AWS (retry the transient code, stop on the permanent message) never terminates.
Fix: the role-assumption step of the StartExecution path — evaluate the trust policy's Condition block, and when the assume fails, serialize the relayed AssumeRoleFailedCacheableException message as the KmsAccessDeniedException message rather than falling through to the data-key authorization message.
Traces: kms__stepfunctions.sfn-execution-role-trust-source-account-mismatch-blocks-cmk-execution, kms__stepfunctions.sfn-execution-role-trust-honors-source-account-and-source-arn.

Cause 3 of 3: the KMS explicit-deny message relayed by StartExecution names the emulator's own IAM user as the denied principal instead of the execution role's assumed-role session.
Failing check id: kms__stepfunctions.start-execution-cmk-key-denies-or-disabled-create-nothing.
AWS: recorded behaviour only for the principal field. With a key policy that explicitly denies kms:GenerateDataKey, StartExecution is refused HTTP 400 KmsAccessDeniedException — that part the emulator gets right — and the message's fixed text is "User: <principal> is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)", where <principal> is the STS assumed-role ARN of the execution role's session, arn:aws:sts::<account>:assumed-role/<role-name>/<session>, <key ARN> is the key from the machine's encryptionConfiguration, and <session>/<request-id>/<n> are the only per-call values (the check masks exactly those three).
Emulator: <principal> is rendered as 'arn:aws:iam::<account>:user/emulator' — the emulator's own service identity, not the caller at all. (The earlier fix for this member, filed as Cause 2 of 20261109T164957Z-kms-stepfunctions-2-net-new-causes-an-execution.md, changed the rendering from the IAM role ARN to this emulator user; it is still not the assumed-role session form.)
Why: a client that attributes a KMS denial to a principal — to find which session was denied, or to generate the policy statement that would allow it — is handed an identity that does not exist in its account and that no policy can reference.
Fix: the principal-rendering helper used when a KMS authorization failure is serialized into a Step Functions error message — it must render the execution role's STS assumed-role session identity.
Traces: kms__stepfunctions.start-execution-cmk-key-denies-or-disabled-create-nothing.

## Evidence
Cause 1 — kms__stepfunctions.cmk-trust-removed-then-restored-execution-redrive-succeeds, verdict error.
Setup (from the check): kms:CreateKey (SYMMETRIC_DEFAULT, ENCRYPT_DECRYPT, no explicit key policy); iam:CreateRole trusting states.amazonaws.com; iam:PutRolePolicy allowing [kms:Decrypt, kms:GenerateDataKey] on that key ARN; sfn:CreateStateMachine(type=STANDARD, definition={"StartAt":"Pass","States":{"Pass":{"Type":"Pass","End":true}}}, encryptionConfiguration={type:CUSTOMER_MANAGED_KMS_KEY, kmsKeyId:<key>, kmsDataKeyReusePeriodSeconds:300}).
Expected: StartExecution returns 200 with an executionArn and the baseline execution SUCCEEDS.
Actual: botocore.errorfactory.KmsAccessDeniedException: An error occurred (KmsAccessDeniedException) when calling the StartExecution operation: User: states.amazonaws.com is not authorized to perform: kms:GenerateDataKey on resource: arn:aws:kms:<region>:<account>:key/<key-id> because no resource-based policy allows the kms:GenerateDataKey action (Service: Kms, Status Code: 400, Request ID: <id>) (SDK Attempt Count: 1). (The key id, account and request id in the recorded text are per-run values; the requirement is that a role granted the key by its identity policy is not refused at all.) The check's own retry loop tolerates KmsAccessDeniedException for 90 s before re-raising, so the refusal is steady, not a propagation window.

kms__stepfunctions.sfn-execution-role-trust-honors-source-account-and-source-arn, verdict mismatch: "Error: Check timed out after 60.0s". Its positive leg calls _start_execution_retrying_kms(), which retries ONLY KmsAccessDeniedException for up to 150 s, so a run that consumes the whole 60 s harness budget in that loop means StartExecution kept answering KmsAccessDeniedException for a role whose identity policy grants kms:GenerateDataKey/kms:Decrypt on the key and whose trust matches (aws:SourceAccount == this account, aws:SourceArn ArnLike arn:aws:states:<region>:<account>:stateMachine:*).

Cause 2 — kms__stepfunctions.sfn-execution-role-trust-source-account-mismatch-blocks-cmk-execution, verdict mismatch: "Error: Check timed out after 60.0s".
Expected: with the trust's aws:SourceAccount naming another account (111122223333), StartExecution is refused KmsAccessDeniedException whose Error.Message is exactly "com.amazonaws.sfn.invoker.sts.AssumeRoleFailedCacheableException: The principal states.amazonaws.com is not authorized to assume the provided role. (role: <role ARN>)", and a same-account twin SUCCEEDS.
Actual: the check's _start_until_permanent_failure() loop returns only when Error.Message equals that text and otherwise keeps retrying; it never matched within the budget, i.e. the emulator's KmsAccessDeniedException message is some other text (the Cause 1 "no resource-based policy allows kms:GenerateDataKey" wording). The same assertion is the negative leg of sfn-execution-role-trust-honors-source-account-and-source-arn, where the mismatched aws:SourceArn names arn:aws:states:<region>:<account>:stateMachine:no-such-machine.

Cause 3 — kms__stepfunctions.start-execution-cmk-key-denies-or-disabled-create-nothing, verdict mismatch.
Expected message (per-call parts masked by the check): 'User: arn:aws:sts::<account>:assumed-role/<role-name>/<session> is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)'.
Actual: 'User: arn:aws:iam::<account>:user/emulator is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <id>) (SDK Attempt Count: 1)'. HTTP 400 and the KmsAccessDeniedException code match; the whole fixed text matches; only the <principal> substitution diverges — 'arn:aws:iam::<account>:user/emulator' where the assumed-role session ARN of the state machine's execution role is required.
