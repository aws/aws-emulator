# ListCommonControls substitutes emulator-minted common controls for the published catalog entries

> _Note: this issue was identified against the code base at commit `0e0bbca79734649b97ab70170a0bc1f3e6da2e9e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCommonControls

## Description
For four distinct CommonControlFilter objectives the emulator answers ListCommonControls with HTTP 200 and a NON-EMPTY CommonControls list that contains none (or almost none) of the common controls AWS publishes under that objective, and instead contains entries whose ARNs exist in no published ControlCatalog. This is a different defect from the already-open issue "ListCommonControls returns an empty CommonControls list for every objective filter" (20261030T021409Z-controlcatalog-listcommoncontrols-returns-an-empty-commoncontrols-list-for-every--r2.md), which covers the filters where the list comes back empty; the four filters bundled here come back populated with substituted content, and none of them is covered by that issue or by any other open issue. Each objective's slice of the seed table has to be corrected, so this bundle carries 4 causes.

Shared AWS baseline for all four causes. Smithy (services/service-com-amazonaws-controlcatalog-controlcatalog/smithy-model/com-amazonaws-controlcatalog-controlcatalog.json): ListCommonControls is POST /common-controls, @readonly, success code 200, input ListCommonControlsRequest {MaxResults (httpQuery maxResults, @range 1..100), NextToken (httpQuery nextToken, @length max 1024), CommonControlFilter}, output ListCommonControlsResponse {CommonControls (CommonControlSummaryList) @required, NextToken}. CommonControlFilter.Objectives takes exactly one objective ARN at a time. CommonControlSummary requires Arn (CommonControlArn, @length 41..2048, @pattern ^arn:(aws(?:[-a-z]*)?):controlcatalog:::common-control/[0-9a-z]+$), Name, Description, Domain (AssociatedDomainSummary), Objective (AssociatedObjectiveSummary), CreateTime and LastUpdateTime. ControlCatalog's common-control taxonomy is an AWS-published, account- and region-independent read-only catalog (the ARNs carry no account or region and the op is @readonly), so for a given objective ARN the response must enumerate exactly the published common controls that belong to that objective, each with its own published ARN, name and description and with Domain/Objective pointing at its real owners. The recordings show those published sets. Modeled errors are AccessDeniedException(403), InternalServerException(500), ThrottlingException(429) and ValidationException(400); none is at issue here - the status is the modeled 200 in every cause and the defect is entirely the list's content.

Cause 1 of 4: the "Change management" objective filter. AWS: filtering on objective arn:aws:controlcatalog:::objective/14qj3s9axkdma059lhktc14dx must return that objective's published common controls - the recording shows entries such as .../common-control/1nxqoydhsjdyboc4frsrrmev "Change request and approval", .../8xy67kb7kojr38ozqpmrm60d7 "Change deployment and automation" and .../2o50zyyv219ir9r7brjq0y37f, each nested under Domain "Secure development lifecycle and change management" and Objective "Change management". Emulator: 200, but every published common control the recording expects resolves to None when looked up by its Arn, while the list carries entries under ARNs that appear in no published catalog (.../125bde0f7915c91b7ee1fda3d, .../2d9833b5482e415a92ab1f774, .../7e467a0d7b39dff863530a8a0, .../949043c1f069338a0ebe2c6ed, .../ec8290942827d11187c4c6dff - all 25 hexadecimal digits, the shape of a locally minted digest rather than of a published control id). Why: a client that walks domains -> objectives -> common controls to render or audit a control catalog, or that resolves a common-control ARN it obtained from ListControlMappings, gets a plausible-looking 200 whose every ARN is unresolvable anywhere else in the catalog; cross-referencing silently produces wrong results instead of failing. Fix: the ListCommonControls handler's backing ControlCatalog taxonomy state/seed data - the common-control table must hold the published common controls keyed by their real ARNs with their real Name/Description/Domain/Objective/CreateTime/LastUpdateTime, and the handler must select by CommonControlFilter.Objectives and page per MaxResults/NextToken. Traces: controlcatalog-catalog-list-common-controls#task#1.
