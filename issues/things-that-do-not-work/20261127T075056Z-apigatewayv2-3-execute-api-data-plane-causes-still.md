# apigatewayv2: 3 execute-api data-plane causes still reach no verdict — the DisableExecuteApiEndpoint 404 gate, the per-route 429 throttle, and an Origin-bearing GET on a CFN-deployed CORS API

> _Note: this issue was identified against the code base at commit `28555b6df12d0a3aa7f5205e37cfb844ff12ed87`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateApi

## Description
Three root causes in the apigatewayv2 execute-api data plane, each grounded in a failing behavioral check of this replay that is NOT marked ALREADY FILED and NOT marked OWNED by any open issue. A fixer must close ALL THREE before submitting.

Shared suspicion (one sentence, labelled Hypothesis, because the replay detail carries no status): all three checks end as 'Check timed out after 60.0s' with no frame, no status and no body, which is what the harness reports when the address the control plane PUBLISHED for the API's data plane is never dialled successfully — so these three behaviours may share one upstream defect in what CreateApi/GetApi announce as Api$ApiEndpoint. That upstream symptom is itself already filed and open (20261126T140544Z-apigatewayv2-the-published-apiendpoint-names-an-unserved-api.md; 20261127T014922Z-apigatewayv2-cloudcontrol-cloudformation-apigatewayv2-getapi-publishes-apiendpoint-as-a-path-style.md), and neither of those carries these three checks' replay keys; the three behaviours below are filed on their own terms because each has a distinct AWS contract that is still not demonstrated at whatever address the emulator publishes. Prior art that claimed these exact three checks and is now marked FIXED: 20261125T223834Z-apigatewayv2-3-net-new-execute-api-data-plane.md (its Issue-Trace-Ids are exactly these three check ids); its resolution argues the behaviours are implemented in-process and were driven end-to-end in a Rust test, yet the replayed checks still produce no verdict, so the behaviour is still not observable to a client at the published address. This filing is not described as a new defect in the in-process logic; it records that the three contracts remain ungraded on the wire.

=== Cause 1 of 3: an HTTP API whose default execute-api endpoint is disabled never answers the documented 404 {"message":"Not Found"} on that URL, and the disable/restore transition reaches no verdict. Failing check: apigatewayv2.deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore.

AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json, com.amazonaws.apigatewayv2#ApiGatewayV2): UpdateApi (PATCH /v2/apis/{ApiId}, 200) takes DisableExecuteApiEndpoint (__boolean, jsonName disableExecuteApiEndpoint) and echoes it in UpdateApiResponse; GetApi reports the same member, so the flag is per-API state readable immediately after the update. UpdateApi's modelled errors are BadRequestException 400, ConflictException 409, NotFoundException 404, TooManyRequestsException 429 — none applies, the control-plane call succeeds. The data-plane consequence is recorded behavior only (the execute-api data plane is not modelled in Smithy; docs: https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-disable-default-endpoint.html): once the flag is set, every request to that API's default execute-api URL is refused HTTP 404 with the gateway envelope body {"message":"Not Found"} — that body is entirely fixed text, it carries no value from the request or from state — and the integration is NOT invoked, so nothing of a refused request reaches the backend (no log line, no backend body). The refusal is scoped to the one API: a twin API over the same backend with the flag clear keeps answering 200 with the backend's body in the same instant. Clearing the member (DisableExecuteApiEndpoint=false) returns the same URL to 200 from the integration.

Emulator: the check reaches no verdict — replay detail 'Error: Check timed out after 60.0s'. After the successful UpdateApi the check polls the target URL for a settled run of 404s, and after re-enabling for a settled run of 200s; neither run materialises inside the harness budget, so the whole disable/restore transition is ungradeable. Hypothesis: either no request reaches the gate at the published address (see the shared suspicion above), or the gate answers a refusal class other than 404 {"message":"Not Found"} — an earlier filing records 403 {"message":"Forbidden"} from this gate — so the status the poll waits for never appears.

Why: a client cannot tell that disabling an API's default endpoint took effect the way AWS defines it, nor that re-enabling restored it. Endpoint-lockdown and custom-domain-only cutovers key on 404/{"message":"Not Found"} to separate 'the default endpoint is off' from an authorization failure or a missing route; against the emulator that signal never arrives and the restore path is unobservable.

Fix: the execute-api front door's DisableExecuteApiEndpoint gate for HTTP APIs, together with the address the control plane publishes for that front door — the status and envelope it answers for a request to a disabled default endpoint, refusing BEFORE invoking the integration, its per-API scoping (an enabled twin must be unaffected), and the path back to serving when UpdateApi clears the member. Related open filings that do NOT carry this check's key: 20261122T132825Z-apigatewayv2-an-http-api-with-disableexecuteapiendpoint-true-never.md and 20261112T190000Z-apigatewayv2-the-disableexecuteapiendpoint-check-still-hangs-on-the-front-door-upgrade.md; a fixer may close them together.

Traces: apigatewayv2.deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore.

=== Cause 2 of 3: a per-route throttle on a live stage never sheds part of an over-limit burst with 429, and the two routes under test never settle into a gradeable state. Failing check: apigatewayv2.route-throttling-returns-429-while-twin-route-serves.

AWS: Smithy: CreateStage (POST /v2/apis/{ApiId}/stages, 201) takes RouteSettings (RouteSettingsMap, jsonName routeSettings) and DefaultRouteSettings (RouteSettings, jsonName defaultRouteSettings); shape com.amazonaws.apigatewayv2#RouteSettings carries ThrottlingRateLimit (__double, jsonName throttlingRateLimit, doc 'Specifies the throttling rate limit') and ThrottlingBurstLimit (__integer, jsonName throttlingBurstLimit, doc 'Specifies the throttling burst limit'); DeleteRouteSettings (DELETE /v2/apis/{ApiId}/stages/{StageName}/routesettings/{RouteKey}, 204; errors NotFoundException 404, TooManyRequestsException 429) removes one route's override. Enforcement itself is recorded behavior only (docs: https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html): a route whose settings cap it far below the offered rate has the excess of a burst shed by the gateway with HTTP 429 and the gateway's 'Too Many Requests' envelope — that text is fixed, no value from the request appears in it — shed BEFORE the integration runs, so no backend body appears in a throttled response, while the remainder of the burst is served 200 from the integration. The limit is scoped to the one RouteKey: a twin route on the same stage and same integration, under the stage's generous DefaultRouteSettings, sheds nothing in the same instant. Requests paced well under the route's rate are never shed. After DeleteRouteSettings the same burst against that route sheds nothing.

Emulator: the check reaches no verdict — replay detail 'Error: Check timed out after 60.0s'. Its legs, in order: poll each of 'GET /limited' and 'GET /twin' for 200 with the backend marker; a slow run of five requests to each route that must ALL answer 200 with that marker; then an interleaved 24-request burst expecting at least one 429 on the limited route and none on the twin. No settled state the check waits for is reached inside the budget. Hypothesis: either nothing reaches the metered front door at the published address, or the meter sheds the slow, well-under-rate pre-burst run as well — which a 1 rps / burst-1 route must NOT do for requests spaced seconds apart.

Why: a client cannot verify that a per-route throttle protects a backend, and cannot distinguish 'shed by the gateway' (429 + Too Many Requests, integration not invoked) from a backend error. Load-shedding and quota-regression suites pass against the emulator while the same stage configuration sheds traffic on AWS — or, in the other direction, a correctly paced caller is refused where AWS serves it.

Fix: the execute-api front door's rate-limiting stage — the per-route and per-stage token buckets derived from a stage's RouteSettings/DefaultRouteSettings (refill at ThrottlingRateLimit, depth ThrottlingBurstLimit), the 429 'Too Many Requests' refusal emitted before the integration is invoked, the per-RouteKey scoping against the stage default, and DeleteRouteSettings taking effect on a live AutoDeploy stage — reachable at the address the control plane publishes.

=== Cause 3 of 3: a CloudFormation-deployed HTTP API with a CorsConfiguration never serves an Origin-bearing GET on its $default AutoDeploy stage, so the in-place removal of CORS and the subsequent Api replacement are both ungradeable. Failing check: apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced.

AWS: Smithy: CreateApi/UpdateApi member CorsConfiguration : com.amazonaws.apigatewayv2#Cors — AllowOrigins (CorsOriginList, jsonName allowOrigins), AllowMethods (CorsMethodList, jsonName allowMethods), AllowHeaders, ExposeHeaders, AllowCredentials, MaxAge (IntegerWithLengthBetweenMinus1And86400, @range -1..86400, doc 'The number of seconds that the browser should cache preflight request results'), every member documented 'Supported only for HTTP APIs', the shape doc linking https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html. The data plane is recorded behavior only, and CORS is a BROWSER mechanism: API Gateway never refuses a request because of its Origin. A GET on a route with AuthorizationType NONE is served 200 with the integration's body whether or not an Origin header is present; the only Origin-dependent difference is the RESPONSE decoration — access-control-allow-origin equal to the request's Origin when that origin is in AllowOrigins, and no access-control-* header at all when it is not. An OPTIONS preflight (Origin + Access-Control-Request-Method) that no route matches is answered by the gateway itself 204 carrying access-control-allow-origin / -allow-methods / -allow-headers / -max-age taken from the API's own CorsConfiguration; once CorsConfiguration is removed and no OPTIONS route exists, the same preflight falls through to route matching and is answered 404 with body {"message":"Not Found"} and NO access-control-* header, while the plain GET keeps answering 200 with the integration's body and no CORS headers. The statuses, the header names and the JSON error shape are the fixed part; the origin string, the method/header lists, the max-age number and the handler's marker are values taken from the request and from the API's own configuration.

Emulator: the check reaches no verdict — replay detail 'Error: Check timed out after 60.0s'. Its first data-plane leg polls the stack's $default stage URL for 200 on 'GET /a' WITH header Origin: <the stack's allow-listed origin>; that 200 never arrives, so every later leg — the 204 preflight with the configured MaxAge, the in-place stack update that removes CorsConfiguration while keeping the ApiId, the preflight then falling through to 404 with no access-control-allow-origin, the GET losing its CORS headers, and the Route-repointing replacement that must yield a new ApiId with GetApi on the old one refused NotFoundException 'Invalid API identifier specified <account>:<api-id>' (fixed text plus the account and api id from the request) — is never exercised. Hypothesis: either nothing reaches the front door at the published address, or the same-origin gate open issue 20261124T103252Z-apigatewayv2-the-execute-api-front-door-still-refuses.md records is still ahead of route matching, answering any Origin-bearing execute-api request HTTP 403, content-type 'text/plain; charset=utf-8', body 'cross-site origin' — a status, body and content type AWS never produces on this surface, where the only refusals are 403 {"message":"Forbidden"} (unsigned AWS_IAM route) and 404 {"message":"Not Found"} (nothing matched), both JSON. That open issue carries other CORS checks' replay keys and not this one.

Why: the very requests CORS exists to permit are destroyed — a browser page, or any client that forwards Origin, cannot call an HTTP API whose allowlist explicitly names its origin — and server-side Origin enforcement is not a CORS mechanism, so an application written against the emulator treats AllowOrigins as access control where AWS serves the request regardless and only decorates the response. The whole CFN lifecycle this check grades (CORS removed in place keeping the ApiId, then the Api replaced) is unobservable.

Fix: the execute-api front door ahead of the apigatewayv2 invoke path — no server-side Origin check before stage/route resolution, the authorizer and the integration; the API's CorsConfiguration shapes only the RESPONSE decoration on the 200, on the gateway's own 204 preflight and on the 404 {"message":"Not Found"} fall-through; plus the published address at which all of this is reachable.

Traces: apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced.

## Evidence
Cause 1 — check apigatewayv2.deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore, verdict mismatch, detail 'Error: Check timed out after 60.0s'.
Expected (AWS): after UpdateApi(ApiId=<target>, DisableExecuteApiEndpoint=True) succeeds and GetApi reports DisableExecuteApiEndpoint=true on the target and false on the twin, every GET of the target's execute-api URL answers HTTP 404 with body {"message":"Not Found"} (fixed text, no variable part) and never the backend's body; the twin API's URL answers 200 with the backend's body in the same instant; no refused request's nonce ever appears in the backend's log group (the integration was not invoked); then after UpdateApi(DisableExecuteApiEndpoint=False), GetApi reports false and the same URL answers a settled 200 with the backend's body, that request visible in the backend's log.
Actual (emulator): no verdict inside the harness cap — the settled run of 404s the check polls for on the disabled target URL is never answered, so the restore leg is never reached. The 404 status and the {"message":"Not Found"} envelope are the requirement; the API ids, the generated marker and the per-request nonces are per-run environment values.

Cause 2 — check apigatewayv2.route-throttling-returns-429-while-twin-route-serves, verdict mismatch, detail 'Error: Check timed out after 60.0s'.
Expected (AWS): on a $default AutoDeploy stage with DefaultRouteSettings {ThrottlingRateLimit 500.0, ThrottlingBurstLimit 200} and RouteSettings {'GET /limited': {ThrottlingRateLimit 1.0, ThrottlingBurstLimit 1}} (GetStage reports the override for 'GET /limited' only), single requests spaced seconds apart are served 200 with the backend's body on BOTH routes; an interleaved ~24-request burst then sheds at least one request on GET /limited with HTTP 429 whose body carries the gateway's 'Too Many Requests' envelope and never the backend's body, serves the remainder 200 from the backend, and sheds nothing on GET /twin in the same instant; after DeleteRouteSettings(RouteKey='GET /limited') (204) the same burst sheds nothing.
Actual (emulator): no verdict inside the harness cap — neither the pre-burst run in which every request to both routes must answer 200 with the marker, nor any 429 on the limited route, is ever observed. The 429 status and the 'Too Many Requests' envelope are the requirement; the marker string, the API id and the exact shed counts are environment values (the check asserts only '>= 1 shed on the limited route, 0 on the twin').

Cause 3 — check apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced, verdict mismatch, detail 'Error: Check timed out after 60.0s'.
Expected (AWS): a CFN stack creating an HTTP API with CorsConfiguration {AllowOrigins:[<allowed origin>], AllowMethods:['GET'], MaxAge:300}, an AWS_PROXY Lambda integration, route 'GET /a' and a $default AutoDeploy stage serves 'GET /a' carrying header Origin: <allowed origin> as 200 with the Lambda's body (marker, routeKey 'GET /a', version '2.0') plus access-control-allow-origin == <allowed origin>; the OPTIONS preflight is 204 with that origin echoed, 'GET' present in access-control-allow-methods and access-control-max-age == the configured MaxAge; a stack update that only removes CorsConfiguration and changes Description previews as Modify with Replacement False, keeps the ApiId, GetApi no longer returns CorsConfiguration, the same preflight now answers 404 {"message":"Not Found"} with no access-control-allow-origin, and GET /a still answers 200 with the marker and no CORS headers; the later Route-repointing update yields a new ApiId and GetApi on the old one is refused NotFoundException with message 'Invalid API identifier specified <account>:<api-id>'.
Actual (emulator): no verdict inside the harness cap — the very first Origin-bearing GET never reaches 200, so nothing after it runs. Per the related open filing the front door answers such a request HTTP 403, content-type 'text/plain; charset=utf-8', body 'cross-site origin'. Host:port, API ids, the marker, the origin string and the MaxAge number are per-run values, not requirements.
