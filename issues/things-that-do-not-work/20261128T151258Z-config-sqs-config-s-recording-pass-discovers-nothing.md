AWS: Smithy (com.amazonaws.configservice#StarlingDoveService) models the read paths, not discovery, so the recording side effect itself is recorded behavior only. GetResourceConfigHistory takes required resourceType (enum ResourceType) and resourceId (@length 1..768) plus laterTime/earlierTime/chronologicalOrder/limit (@range 0..100)/nextToken, returns configurationItems (ConfigurationItemList) + nextToken at HTTP 200, and declares InvalidLimitException / InvalidNextTokenException / InvalidTimeRangeException / NoAvailableConfigurationRecorderException / ResourceNotDiscoveredException / ValidationException (all errorKind client, httpError 400). BatchGetResourceConfig takes required resourceKeys (@length 1..100) and returns baseConfigurationItems + unprocessedResourceKeys at HTTP 200, declaring only NoAvailableConfigurationRecorderException / ValidationException. SelectResourceConfig takes required Expression (@length 1..4096) and returns Results at HTTP 200. DescribeConfigurationRecorderStatus returns ConfigurationRecordersStatus (HTTP 200); ConfigurationRecorderStatus.lastStatus targets the RecorderStatus enum, values Pending | Success | Failure | NotApplicable, documented as "The status of the latest recording event processed by the recorder", beside lastStatusChangeTime ("The time of the latest change in status of an recording event processed by the recorder"), lastStartTime, lastStopTime, recording (boolean, default false), lastErrorCode and lastErrorMessage. Recorded behavior: on AWS, once such a recorder is recording, creating a queue causes Config to discover it asynchronously and write a configuration item for resourceType AWS::SQS::Queue, so GetResourceConfigHistory(resourceType='AWS::SQS::Queue', resourceId=<that queue url>) answers HTTP 200 with a non-empty configurationItems list whose newest item's `arn` equals that queue's QueueArn; BatchGetResourceConfig for the same resourceKey answers HTTP 200 with exactly one baseConfigurationItem whose `configuration` document's QueueArn equals it; and once ANY recording event has been processed, lastStatus is 'Success' (not 'Pending') with lastStatusChangeTime set. Emulator: PutConfigurationRecorder, PutDeliveryChannel and StartConfigurationRecorder all succeed and DescribeConfigurationRecorderStatus confirms recording=true, but the queue created immediately afterwards produces nothing in Config — no AWS::SQS::Queue configuration item exists for it — and the emulator's own DescribeConfigurationRecorderStatus response read at the moment of failure is [{'name': <recorder name>, 'recording': True, 'lastStatus': 'Pending', 'lastErrorCode': None, 'lastErrorMessage': None}]: a recorder that reports itself healthy and recording, with no error code and no error message, while having recorded nothing and never leaving 'Pending' and never setting lastStatusChangeTime. Hypothesis (neither the model nor the recording states it): Config's configuration-item state only ever grows from an explicit PutResourceConfig write, so no cross-service recording pass exists at all, and the status machine behind lastStatus is not wired to recording events. Queue urls, queue/recorder/bucket names, the account id, the VisibilityTimeout value 137 and the 0.0 s window are per-run values and are not part of the requirement.

Why: a client that uses Config as its inventory sees an account that contains no SQS queues while Config insists it is recording. Because nothing is ever recorded, ResourceNotDiscoveredException becomes the answer to EVERY GetResourceConfigHistory call, so the error loses its meaning — a caller cannot distinguish "this resource never existed" from "Config records nothing at all" — and the HTTP 200 omission answers of BatchGetResourceConfig and SelectResourceConfig are indistinguishable from an empty account. Drift, audit and compliance tooling blocks on its first wait for a resource to be discovered, and anything gating on lastStatus == 'Success' (the documented signal that a recording event was processed) to confirm the recorder came up waits on 'Pending' forever, with no lastStatusChangeTime to measure staleness from.

Fix: the configuration-recorder recording pass and status state in the configservice crate — while a customer-managed recorder is RECORDING and its recordingGroup covers the type, create/change/delete of resources owned by the other emulated service crates (here AWS::SQS::Queue) must be captured into Config's configuration-item state rather than that state growing only from an explicit PutResourceConfig; GetResourceConfigHistory's handler must project those items and reserve ResourceNotDiscoveredException for ids genuinely absent from that state, with BatchGetResourceConfig's and SelectResourceConfig's handlers answering the same state by omission at HTTP 200; and the status machine behind DescribeConfigurationRecorderStatus must advance lastStatus to 'Success' and set lastStatusChangeTime once a recording event is processed, never reporting 'Pending' for a recorder that has already recorded items.
