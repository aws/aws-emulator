# sagemaker: 2 net-new causes — the Studio Domain→UserProfile→App→Deleted lifecycle costs a polling client a full interval per transition so the state-machine scenario reaches no verdict, and a presigned domain URL's hand-off never lands on the domain's own studio-<domainId> host

> _Note: this issue was identified against the code base at commit `52a8df02a71c3b056a66eac5ed3c93ae1be7953c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDomain, DescribeUserProfile, DescribeApp, CreatePresignedDomainUrl

## Description
TWO root causes, both grounded in failing checks the suite report lists under `### sagemaker` that the report marked neither ALREADY FILED nor OWNED by an open issue. They are numbered and each carries its own failing check ids; BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: every clock-owed Studio transition is materialised only by a read that falls at/after a stored wall-clock instant, so the read that immediately follows each mutation always sees the transient status and a polling client pays its whole interval per transition — the Domain→UserProfile→App→Deleted walk therefore reaches no verdict ===
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json) models the lifecycle the check walks — DescribeDomain.Status → DomainStatus, DescribeUserProfile.Status → UserProfileStatus, DescribeApp.Status → AppStatus (`Deleted | Deleting | Failed | InService | Pending`). Recorded behavior: right after CreateApp the app reads `Pending` (never already a terminal status), it then reaches `InService`, and after DeleteApp it reaches `Deleted`; the same holds for the domain and the user profile the app hangs off. The transient status must stay observable to the describe that immediately follows the create WITHOUT costing a client that polls at a realistic interval a whole interval for each transition.
Emulator: no call is refused and no assertion fails — the whole budget is spent sleeping. Each transition is deferred behind a stored due instant that the first read after the mutation always misses: `USER_PROFILE_IN_SERVICE_AFTER: Duration = Duration::from_secs(3)` (src/state/user_profile.rs:78) with `DOMAIN_IN_SERVICE_AFTER = USER_PROFILE_IN_SERVICE_AFTER` (src/state/domain.rs:69) and the app's own span in src/state/app.rs; the status moves only on whichever reporting read runs at or after that instant (`Domain::settle_status`, `UserProfile::settle_status`, `App::settle_status`, also called from the handlers, e.g. src/ops/create_presigned_domain_url.rs:215 and :280). Hypothesis for the arithmetic: this check polls DescribeDomain at interval 20 s, DescribeUserProfile at 15 s, DescribeApp at 15 s and then DescribeApp again after DeleteApp at 15 s — four transitions, each observed as transient on the probe that follows the mutation, so ~65 s of pure sleeping on top of the IAM/VPC setup, and the replay is cut off with `Check timed out after 60.0s` before the App Pending→InService→Deleted assertions are ever reached.
Why: a client (or `aws sagemaker wait`) that polls at a realistic interval sees the transient status on the describe that immediately follows every create/delete and then sleeps its full interval; a Studio flow chaining domain → profile → app → delete pays that four times, so the flow is unobservably slow against an emulator that actually holds the settled state seconds later, and everything past the last wait cannot be verified at all.
Fix: the clock-owed spans of the Studio slices and the readers that materialise them — src/state/user_profile.rs (`USER_PROFILE_IN_SERVICE_AFTER`, `UserProfile::settle_status`), src/state/domain.rs (`DOMAIN_IN_SERVICE_AFTER`, `Domain::settle_status`), src/state/app.rs (`App::settle_status`) with src/ops/describe_domain.rs, src/ops/describe_user_profile.rs and src/ops/describe_app.rs. The transient status has to be observable to the read that immediately follows the mutation and then settle on the NEXT read, instead of on a read that happens to fall after a fixed wall-clock instant. Open issues 20261122T002913Z-sagemaker-3-net-new-causes-reopens-the-hyperpod.md (Cause 2) and 20261123T054636Z-sagemaker-2-net-new-causes-createpresigneddomainurl-s-not.md (Cause 2) describe the same mechanism for OTHER Studio checks; the suite report did not mark this failure as OWNED by either (their recorded replay keys name other checks/frames), so it is filed here and should be closed together with them.
Traces: sagemaker.app-lifecycle-state-transitions.

=== Cause 2 of 2: following the AuthorizedUrl CreatePresignedDomainUrl mints never lands on the domain's own Studio host — the hand-off is served 200 on the same host with the domain in the PATH, so the final host's first label never names the domain ===
AWS: the model says nothing about the redirect target (CreatePresignedDomainUrl's only output member is `AuthorizedUrl` (PresignedDomainUrl) and its only modelled error is ResourceNotFound, HTTP 400) — recorded behavior only: fetching the AuthorizedUrl follows a redirect chain that ends on THIS domain's own Studio host, whose first DNS label is `studio-<DomainId>` and whose remaining labels are the presigned host's own zone (`studio-<domain-id>.studio.<region>.sagemaker.aws`), not on a sign-in challenge on some other host. The status of that final response is not part of the requirement (AWS answers 403 for a correctly authenticated hand-off into a domain with no provisioned Studio app/space); the requirement is the host's SHAPE: first label = `studio-` + the domain id the request named, remaining labels identical to the presigned URL's own. The concrete host, port and domain id of any one run fill that template and are no part of it.
Emulator: the fetch of the AuthorizedUrl ends at `<the endpoint the emulator is reached on>/_aws/sagemaker/domain/<domain-id>/studio?authToken=<token>` with HTTP 200 — the domain is carried in the PATH and the host is the single endpoint host the emulator serves everything on, so the final host's first label is never `studio-<domain-id>`. This is the published-address design stated in src/service/studio_landing.rs:1-15 and src/ops/create_presigned_domain_url.rs:320-334 (`crate::state::presigned_session_url` / `crate::state::studio_domain_url`), which deliberately keeps AWS's `studio-d-<id>.studio.<region>.sagemaker.aws` out of the URL because it would resolve to nothing; the consequence is that no per-domain Studio host label is published at all.
Why: a client that does what the operation exists for — follow the AuthorizedUrl and end up in that domain's Studio — cannot tell from the landing address which domain it was signed in to, and anything keyed on the host (an allowlist of `studio-<domainId>` hosts, a per-domain cookie/origin scope, a proxy or browser-automation step that asserts the Studio host, CSP/same-origin reasoning) diverges: against AWS each domain lands on its own host, against the emulator every domain lands on the one shared host with no domain label.
Fix: the published Studio address and the hand-off that leads to it — `crate::state::presigned_session_url` / `crate::state::studio_domain_url` (src/state/domain.rs, src/state/user_profile.rs) with src/service/presigned_session.rs and src/service/studio_landing.rs (and src/ops/create_presigned_domain_url.rs:320-334 which mints the URL). The hand-off must land on a host whose first label is `studio-<DomainId>` in the same zone as the presigned host (prefixing that label onto the host the emulator is reached on, and serving/claiming that host), rather than on the bare endpoint host with the domain in the path.
Traces: sagemaker.deploy-domain-cfn-presigned-url-works.

## Steps to Reproduce
Against the booted emulator with boto3/botocore pointed at it (region and account as the harness signs for):

Cause 1 (replay: sagemaker.app-lifecycle-state-transitions): create an IAM role trusting sagemaker.amazonaws.com, pick a VPC with two subnets, then CreateDomain(DomainName=<name>, AuthMode='IAM', DefaultUserSettings={'ExecutionRole': <role arn>}, VpcId=<vpc>, SubnetIds=[<two subnets>], AppNetworkAccessType='PublicInternetOnly'). Poll DescribeDomain at interval 20 s until Status='InService': the FIRST probe, taken straight after the create, reports 'Pending', so the client sleeps a whole 20 s. Then CreateUserProfile and poll DescribeUserProfile at interval 15 s — again 'Pending' on the first probe, another 15 s. Then CreateApp(DomainId=<id>, UserProfileName=<profile>, AppType='JupyterServer', AppName=<app>); DescribeApp immediately after must report Status='Pending' (it does), then poll DescribeApp at interval 15 s for 'InService' — 'Pending' on the first probe, another 15 s. Then DeleteApp and poll DescribeApp at interval 15 s for 'Deleted' — 'Deleting' on the first probe, another 15 s. Four transitions, four full intervals (~65 s) on top of the IAM/VPC setup, so the replay is cut off with 'Check timed out after 60.0s' and the App InService and Deleted assertions are never reached. Expected: each transition is observable as transient on the describe that immediately follows the mutation and settled on the NEXT describe, so a client polling at a realistic interval completes the walk; App ends at Status='Deleted'.
