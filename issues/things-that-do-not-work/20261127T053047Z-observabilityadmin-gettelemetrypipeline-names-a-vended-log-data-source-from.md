# GetTelemetryPipeline names a vended log data source from the configuration document instead of the pipeline's vended-metadata identifier

> _Note: this issue was identified against the code base at commit `e5bd3f449037d977df62b379b9bbd75575215842`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTelemetryPipeline

## Description
1 cause, on observabilityadmin.

Cause 1 of 1: GetTelemetryPipeline reports Pipeline.ConfigurationSummary.DataSources[].Name for a pipeline whose source reads AWS-vended (CloudWatch Logs) log events from the name the submitted configuration document declares for that source, where AWS reports the identifier the vended log-event metadata of THAT pipeline carries. Fixture observabilityadmin-telemetry-pipeline-workflow, step task#5.

AWS: Smithy: GetTelemetryPipeline -> output member Pipeline (TelemetryPipeline); the model snapshot does not declare ConfigurationSummary on TelemetryPipeline, so that member is recorded behavior only, but the model DOES document the shape it carries. smithy_query(query="doc", shape="DataSource", member="Name", model_path="services/service-com-amazonaws-observabilityadmin-observabilityadmin/smithy-model/com-amazonaws-observabilityadmin-observabilityadmin.json"): "The name of the data source. For CloudWatch Logs sources, this corresponds to the data_source_name from the log event metadata. For third-party sources, this is either the configured data_source_name or defaults to the plugin name if not specified." DataSource$Type: "For CloudWatch Logs sources, this corresponds to the data_source_type from the log event metadata. For third-party sources, this field is empty." So the rule is split by the KIND of source, and the recorded 200 for this step shows which side of the split this pipeline falls on: it reports a data source that carries BOTH a Name and a Type ("default"), which per DataSource$Type is a CloudWatch Logs / AWS-vended source and not a third-party one, and the Name it reports is the requested pipeline's own resource name in IDENTIFIER form -- every '-' replaced by '_' (TelemetryPipelineName's pattern [a-z][a-z0-9\-]+, length 3..28, admits no '_' at all, so the identifier form is service-derived and never caller-sent). The requirement is that derivation -- for such a source the Name is the pipeline's vended-metadata identifier whatever data_source_name the document declares for the source, and the Type is the metadata's type ('default' when the metadata carries no other) -- NOT the suffix token any one recording happens to carry.

Emulator: the replayed GetTelemetryPipeline answers 200 with the same shape and every other member matching, but DataSources[0].Name is a different token from the recorded one, so the recorded list element is reported missing and the served one extra at $.Pipeline.ConfigurationSummary.DataSources[0] (recorded Name '...3cf46f5c' = the pipeline's resource name in identifier form, served Name '...c7fdf512'; Type is 'default' on both sides). The served token is the name the configuration document declares for that source, i.e. the emulator takes the third-party arm of DataSource$Name's split for a source AWS answers for on the vended arm.

Hypothesis (the mechanism, since the fixture's configuration document is not readable from the checkout): the NAME split itself is now implemented in services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/state.rs data_source() (~line 939-956: `if vended { data_source_identifier(pipeline) } else { name.unwrap_or(plugin) }`), so what remains wrong is the CLASSIFICATION that feeds it. `vended` comes from is_vended_log_source_type (src/ops/validate_telemetry_pipeline_configuration/vended_log_schema.rs:152), which answers true only for a source plugin the restriction table RESTRICTIONS happens to list -- today just cloudwatch_logs, amazon_vpc_flow, amazon_cloudfront and amazon_route53 (same file, lines 89-123). Any other AWS-vended log source plugin a recorded document declares is therefore classified third-party, and data_source() names it from the document and reports whatever data_source_type the document declares. The table's own comment anticipates exactly this ("a recording naming another vended source type extends the table").

Note on the per-run-value explanation: the resolved issue 20261118T192844Z-observabilityadmin-gettelemetrypipeline-still-names-a-vended-data-source-by.md closed this same step by asserting the residual difference is the hex suffix of a pipeline name the fixture GENERATES per run. The replay evidence does not support that: the served token is byte-identical ('sim2real_probe_pipe_c7fdf512') across three independent replays of this fixture weeks apart and against three different commits (c17029b, f4f9703 and the current checkout), while the recorded token is likewise always 'sim2real_probe_pipe_3cf46f5c'. A value generated per run does not repeat across runs, so the served name is the emulator's deterministic output from the replayed request, and every other name-bearing member of the same response (Pipeline.Name, Pipeline.Arn, Configuration.Body) matches the recording -- only this derived member does.

Why: a client that renders a pipeline's data sources, or correlates ConfigurationSummary with the data_source_name that appears in the vended log-event metadata of ingested events (dashboards, per-data-source filters, any join from the pipeline summary to its events), joins on the wrong key against the emulator: it sees the author-chosen document label where AWS reports the pipeline's metadata identifier, so the join finds nothing and the reported data-source identity is not the one real traffic carries. A caller also cannot tell a vended source (name + type) from a third-party one (name only, empty type) from the emulator's answer, because the emulator decides that split from a catalogue narrower than AWS's.

Fix: this service's ConfigurationSummary derivation and the vended-source classification it reads -- src/state.rs data_source()/data_sources_declared() plus the vended-source predicate in src/ops/validate_telemetry_pipeline_configuration/vended_log_schema.rs. Decide the kind of source by the source plugins AWS actually vends log events for (the catalogue must cover the plugin this fixture's document declares, not only the four types the processor-restriction table needs branches for), then name and type the data source by that kind exactly as DataSource$Name/$Type split it: a vended source reports the pipeline's resource name in identifier form and the metadata's type, a third-party source reports the configured data_source_name (falling back to the plugin name) and no type. ListTelemetryPipelines' TelemetryPipelineSummary.ConfigurationSummary is derived by the same code and changes with it. No state write is involved: the summary is derived on read.
