# sso-oidc RegisterClient: grant-type refusal that AWS defers to CreateToken, and four authorization_code validations missing entirely

> _Note: this issue was identified against the code base at commit `e0dbb6af3802ab132c756881984b5362646a383d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterClient

## Description
Five distinct root causes in the sso-oidc RegisterClient handler (services/service-com-amazonaws-ssooidc-awsssooidcservice/src/ops/register_client.rs). All five concern which registration requests RegisterClient accepts and which it refuses; none is covered by the one open sso-oidc issue (20261117T132850Z-sso-oidc-createtokenwithiam-token-exchange-with-no-subjecttoken.md, which is about CreateTokenWithIAM's subject-token message). A fixer must close all FIVE before submitting.

Cause 1 of 5: RegisterClient refuses grantTypes that AWS records.
AWS: Smithy: RegisterClient.grantTypes targets GrantTypes (a plain string list, no enum, no pattern); the member doc says the list "is used to restrict the token granting flows available to the client" and names authorization_code, urn:ietf:params:oauth:grant-type:device_code and refresh_token as the supported flows, but the model places no value constraint on the list and RegisterClient's modeled errors do not make an unlisted value a registration-time refusal. Recorded behavior: registration SUCCEEDS (HTTP 200, clientId/clientSecret minted) for grantTypes containing "password", "client_credentials", an OAuth-undefined value, or those mixed with the device-code grant; the refusal happens later, at the token endpoint, where CreateToken answers InvalidRequestException with message "Invalid request" (fixed text of the class, nothing from the request echoed) for such a grantType, while the device-code grant of the same registration still reaches device-code lookup and answers InvalidGrantException "Invalid device code provided".
Emulator: RegisterClient rejects the whole request with HTTP 400 UnsupportedGrantTypeException, message "Invalid grant type provided" (register_client.rs validates every entry against st::SUPPORTED_GRANT_TYPES before recording the client). The call never returns credentials, so the token-endpoint behavior the check then asserts is unreachable.
Why: a client that declares a wider grant list than it later uses (a common OAuth client-metadata pattern, and what the console-issued registrations do) cannot register at all. The client sees a registration-time UnsupportedGrantTypeException where AWS gives it credentials, so it never gets to the per-grant refusal it is written to handle, and its device-code or refresh-token flow is lost with it.
Fix: the grant-type validation block in RegisterClient's handler — record grantTypes as given rather than refusing unlisted entries; the per-grant refusal belongs to CreateToken's grant dispatch, which already answers InvalidRequestException "Invalid request" for an unknown grantType.
Traces: sso-oidc.register-client-accepts-grant-types-token-endpoint-refuses.

Cause 2 of 5: an authorization_code registration with no issuerUrl is accepted.
AWS: Smithy: RegisterClient.issuerUrl (URI) is optional and documented as "The IAM Identity Center Issuer URL associated with an instance of IAM Identity Center. This value is needed for user access to resources through the client"; InvalidRequestException (HTTP 400) is modeled for RegisterClient as "something is wrong with the input to the request. For example, a required parameter might be missing". Recorded behavior: when grantTypes contains authorization_code, issuerUrl is effectively required and its absence is HTTP 400 InvalidRequestException with message "Start URL is required" — fixed text, no value interpolated. The same request for the device-code grant needs no issuerUrl and registers.
Emulator: the request succeeds with HTTP 200 and a full RegisterClientResponse (clientId, clientSecret, clientIdIssuedAt, clientSecretExpiresAt, and authorizationEndpoint/tokenEndpoint synthesized from the service's regional endpoint). register_client.rs states explicitly that it records issuerUrl without validating it.
Why: the client believes it holds a usable authorization-code registration and walks the user agent to an authorization endpoint derived from nothing the operator configured; the failure surfaces far from the misconfigured RegisterClient call instead of at it, and a client written to catch InvalidRequestException "Start URL is required" and prompt for a start URL never does.
Fix: RegisterClient's input validation — a grant-dependent required-member check for issuerUrl when grantTypes names authorization_code.
Traces: sso-oidc.register-client-authorization-code-missing-start-url-rejected, sso-oidc.register-client-authorization-code-start-url-rejected.

Cause 3 of 5: an authorization_code registration with absent or empty scopes is accepted.
AWS: Smithy: RegisterClient.scopes targets Scopes (a list, optional, no minimum length modeled); InvalidScopeException (HTTP 400) is modeled for RegisterClient as "the scope provided in the request is invalid". Recorded behavior: with grantTypes containing authorization_code, both an omitted scopes member and an empty scopes list are HTTP 400 InvalidScopeException with message "Scopes are required for this grant" — fixed text of the class, no scope value or grant name interpolated. The identical request with only the device-code grant registers and its credentials reach CreateToken's device-code lookup.
Emulator: both requests succeed with HTTP 200 and return the full credential set (keys ResponseMetadata, authorizationEndpoint, clientId, clientIdIssuedAt, clientSecret, clientSecretExpiresAt, tokenEndpoint); scopes is stored as an empty vector with no check.
Why: AWS makes an authorization-code client state its scopes up front so that the access token it later gets is bounded; the emulator mints a registration with no scope restriction at all, so a caller's negative test passes against the emulator and the same code is refused by AWS, and a scope-less registration that the emulator later treats as unrestricted silently widens what the client appears to be allowed.
Fix: RegisterClient's input validation — require a non-empty scopes list when grantTypes names authorization_code, refusing with the modeled InvalidScopeException.
Traces: sso-oidc.register-client-authorization-code-requires-scopes-rejected, sso-oidc.register-client-authorization-code-without-scopes-rejected.

Cause 4 of 5: a malformed (schemeless) issuerUrl on an authorization_code registration is not refused.
AWS: Smithy: issuerUrl targets URI; InvalidRequestException (HTTP 400) is modeled. Recorded behavior: an authorization_code registration whose issuerUrl carries no URI scheme (e.g. a bare host-like string) is HTTP 400 InvalidRequestException with message "Invalid start url provided" — fixed text, the offending URL is NOT echoed. The form is checked only for the authorization-code grant: the same schemeless issuerUrl on a device-code registration is accepted and that client reaches CreateToken's device-code lookup (InvalidGrantException "Invalid device code provided").
Emulator: no URI-form check exists; register_client.rs records issuerUrl verbatim and, for an authorization_code client, builds authorizationEndpoint/tokenEndpoint by string-concatenating "/authorize" and "/token" onto it, so a schemeless value is both accepted and returned as an unusable endpoint pair. In the replay this cause is masked behind Cause 2 — the check is turned away at the missing-issuerUrl assertion first — so it must be verified after Cause 2 is fixed.
Why: the client is handed endpoint URLs with no scheme and cannot resolve them; the malformed start URL is reported by nothing, where AWS names it at registration.
Fix: RegisterClient's input validation, beside the Cause 2 check — validate issuerUrl's URI form (scheme present) for the authorization-code grant only.
Traces: sso-oidc.register-client-authorization-code-start-url-rejected.

Cause 5 of 5: an issuerUrl naming a non-existent Identity Center instance is not resolved for the authorization_code grant.
AWS: recorded behavior only — AccessDeniedException is NOT in RegisterClient's modeled error list (the model declares InternalServerException, InvalidClientMetadataException, InvalidRedirectUriException, InvalidRequestException, InvalidScopeException, SlowDownException, UnsupportedGrantTypeException), so this refusal is established by the recording. The recording shows RegisterClient RESOLVES issuerUrl against the caller's Identity Center instances only for the authorization-code grant: a well-formed issuerUrl naming an instance that does not exist in this account/region is HTTP 400 AccessDeniedException with message "Request refers to an Identity Center instance that does not exist or does not exist in this region." — fixed text, the instance id is not interpolated. The same issuerUrl on a device-code registration is NOT resolved: that client registers and reaches CreateToken's device-code lookup.
Emulator: the authorization_code registration naming an absent instance succeeds with HTTP 200 and returns authorizationEndpoint/tokenEndpoint derived from the unresolvable issuer; nothing in register_client.rs consults stored Identity Center instances. (The device-code half of this check already matches.)
Why: the grant-dependent resolution is the only place a caller learns it pointed at the wrong instance or region; the emulator hands back a registration bound to an instance that does not exist, so a misrouted deployment looks healthy until authorization fails with no diagnosis.
Fix: RegisterClient's handler/state lookup — for the authorization-code grant, resolve issuerUrl against the service state's known Identity Center instances and refuse an unresolvable one with that AccessDeniedException; leave the device-code path unresolved.
Traces: sso-oidc.register-client-device-code-issuer-url-not-resolved.

## Evidence
Cause 1 — expected: RegisterClient returns 200 with credentials for grantTypes ["password", "client_credentials", "urn:ietf:params:oauth:grant-type:device_code"] and for a single undefined grant value, and CreateToken then refuses each non-device grant of that client with (InvalidRequestException, "Invalid request"). Actual: botocore.errorfactory.UnsupportedGrantTypeException: An error occurred (UnsupportedGrantTypeException) when calling the RegisterClient operation: Invalid grant type provided — the registration never completes.

Cause 2 — expected: (InvalidRequestException, "Start URL is required") for clientType=public, grantTypes=["authorization_code"], redirectUris=[loopback], scopes=["sso:account:access"], no issuerUrl. Actual: HTTP 200 with {'clientId': <64-hex>, 'clientIdIssuedAt': <epoch>, 'clientSecretExpiresAt': <epoch>, 'authorizationEndpoint': 'https://oidc.<region>.amazonaws.com/authorize', 'tokenEndpoint': 'https://oidc.<region>.amazonaws.com/token'} (the ids/timestamps/host are per-run values, not requirements). Check assertion: "RegisterClient accepted a client with no issuer".

Cause 3 — expected: (InvalidScopeException, "Scopes are required for this grant") for grantTypes=["authorization_code"] with scopes omitted and again with scopes=[]. Actual: HTTP 200, response keys ['ResponseMetadata', 'authorizationEndpoint', 'clientId', 'clientIdIssuedAt', 'clientSecret', 'clientSecretExpiresAt', 'tokenEndpoint'] — "expected a refusal, but the call succeeded".

Cause 4 — expected: (InvalidRequestException, "Invalid start url provided") for an authorization_code registration with a schemeless issuerUrl. Actual: not reached in replay because Cause 2 refuses nothing first (the same check's earlier missing-issuerUrl assertion fails); the handler contains no URI-form validation and concatenates the value into authorizationEndpoint/tokenEndpoint.

Cause 5 — expected: (AccessDeniedException, "Request refers to an Identity Center instance that does not exist or does not exist in this region.") for an authorization_code registration whose issuerUrl names an absent Identity Center instance. Actual: HTTP 200 with authorizationEndpoint/tokenEndpoint built from that unresolvable issuer ('<issuerUrl>/authorize', '<issuerUrl>/token'); check assertion: "the call was accepted". The device-code control in the same check (registration accepted, then CreateToken → (InvalidGrantException, "Invalid device code provided")) already matches AWS.
