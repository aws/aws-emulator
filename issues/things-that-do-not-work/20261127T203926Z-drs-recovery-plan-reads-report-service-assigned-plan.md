Cause 1 of 3: CreateRecoveryPlan's 201 reports a recoveryPlanArn that is NOT the recovery-plan ARN the run already holds for that plan — it reports a freshly minted plan instead. (fixture drs-recovery-plan-lifecycle-and-tag-round-trip, step task#1)
AWS: Smithy (com.amazonaws.drs#CreateRecoveryPlan) -> POST /CreateRecoveryPlan, http code 201, output member recoveryPlan: RecoveryPlan (required); RecoveryPlan$recoveryPlanArn is StrictDRSARN (required, length 20..2048, pattern ^arn:aws(-[a-z0-9]+)*:drs:[a-z0-9-]+:[0-9]{12}:[a-zA-Z0-9_/.-]+$), documented "The ARN of the Recovery Plan."; clientToken is ClientIdempotencyToken with @idempotencyToken. Recorded behavior only for WHICH plan the 201 must describe: the fixture asserts that this step's $.recoveryPlan.recoveryPlanArn equals the ARN already bound for the run's recovery plan (the expected value is the fixture's binding {{recovery_plan_arn}}, not a literal ARN), i.e. the recorded service answered 201 describing the plan the run already established rather than an additional plan. The fixed part of the requirement is the identity of the resource reported (the ARN already bound for this plan); the variable parts are the partition/region/account the request was signed for and the plan id the service mints — never a literal ARN from one run.
Emulator: status agrees (201 expected, 201 actual) and every other member of the body matches, but the replay reports `$.recoveryPlan.recoveryPlanArn: value_mismatch (expected '{{recovery_plan_arn}}', got 'arn:aws:drs:us-west-2:000000000000:recovery-plan/plan-10000000000000000')`. The reported id, `plan-10000000000000000`, is the FIRST suffix crate::state::ComAmazonawsDrsElasticdisasterrecoveryserviceState::next_id mints (BASE = 62^16 with the id counter still at 0), so at the moment this create ran nothing had ever been minted in that store: the handler took the mint-and-insert path (create_recovery_plan.rs, the next_id/arn/or_insert block) rather than reporting an already-stored plan. Hypothesis: the create reported a brand-new plan where the recorded service reported the plan the run already holds — either the @idempotencyToken lookup (the `store.recovery_plans.values().find(|plan| plan.client_token...)` scan) did not match the create this step repeats, or the plan the fixture's binding names never reached the store in the first place, so the ARN the 201 hands back addresses a different resource than the one the fixture is tracking.
Why: the 201's ARN is the handle a client uses for the rest of the plan's life (GetRecoveryPlan, UpdateRecoveryPlan, TagResource and DeleteRecoveryPlan all address a plan by recoveryPlanArn). When a repeat of a create answers with a NEW plan instead of the one the account already holds, a caller that retries a create (an SDK retry, an idempotent provisioner re-running its workflow) silently ends up with two plans and keeps operating on the newer one, while the plan its earlier run recorded is leaked and never cleaned up; any bookkeeping keyed on the ARN from the first attempt now points at a resource the client no longer touches.
Fix: CreateRecoveryPlan's handler in services/service-com-amazonaws-drs-elasticdisasterrecoveryservice/src/ops/create_recovery_plan.rs — the decision between replaying a stored plan and minting a new one, together with whatever the plan store must hold for the preceding steps of this fixture to have landed; the ARN itself is built in crate::state::recovery_plans::arn and is well formed, so the defect is in WHICH plan is reported, not in how an ARN is rendered.
Traces: drs-recovery-plan-lifecycle-and-tag-round-trip#task#1.

Cause 2 of 3: CreateRecoveryPlan's 201 renders the plan's createdAt and updatedAt in a fractional-second form the recorded responses do not use. (fixture drs-recovery-plan-without-steps-execution-refusals, step setup#1)
AWS: Smithy RecoveryPlan$createdAt and RecoveryPlan$updatedAt are both ISO8601DatetimeString (required, length 19..32, pattern ^[1-9][0-9]*-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([0-1][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9](\.[0-9]+)?Z$), documented "The timestamp when the Recovery Plan was created." / "...was last updated.". The pattern leaves the fractional part optional and of any width, so the required RENDERING is recorded behavior only: the fixture asserts the SHAPE of these two members and not their value (expected '<shaped-not-asserted>' — the instant differs in every environment), and the emulator's rendering does not have that shape. The recorded responses carry a single, fixed-width UTC rendering for these members (a date-time with the same fractional-second width on every response); the fixed part of the requirement is that shape, the variable part is the instant itself, taken from the clock at the moment the plan is created.
Emulator: status agrees (201 expected, 201 actual); the replay reports `$.recoveryPlan.createdAt: value_mismatch (expected '<shaped-not-asserted>', got '2026-11-27T20:33:22.479043Z')` and the identical divergence on `$.recoveryPlan.updatedAt`. Both strings come from crate::state::recovery_plans::now() -> iso8601(), which formats through aws_smithy_types::DateTime::fmt(Format::DateTime): that renders the fraction with trailing zeros trimmed, so the width is whatever the clock reading happens to need (here six digits, microseconds; it can be nine, three, or absent entirely for a whole second). The plan is stored with that string (RecoveryPlanRecord::created_at / updated_at) and reported verbatim by RecoveryPlanRecord::to_wire and to_summary.
Why: a client that parses these members with a fixed-width ISO-8601/RFC-3339 pattern — or that compares, sorts or hashes the raw strings as the service rendered them — breaks on a width that varies from call to call: the same code path succeeds on one response and fails on the next, and a value that happens to land on a whole second loses its fractional part altogether. Timestamp handling is the one thing a plan-listing UI or a drift detector does with every plan it reads.
Fix: the timestamp rendering this service shares — crate::state::recovery_plans::iso8601/now in services/service-com-amazonaws-drs-elasticdisasterrecoveryservice/src/state/recovery_plans.rs — must emit one fixed fractional-second width for every instant, so every member rendered from it (createdAt, updatedAt, and the same members of RecoveryPlanSummary) has the recorded shape.
Traces: drs-recovery-plan-without-steps-execution-refusals#setup#1.

Why: every client that reads a plan back — the GetRecoveryPlan in any lifecycle, and ListRecoveryPlans through RecoveryPlanSummary — sees the same variable-width timestamp, so the parsing breakage in Cause 2 is not confined to the create response.
Fix: the same shared renderer named in Cause 2, with GetRecoveryPlan's read path (crate::ops::get_recovery_plan + RecoveryPlanRecord::to_wire) verified to report the stored, correctly rendered value unchanged.
