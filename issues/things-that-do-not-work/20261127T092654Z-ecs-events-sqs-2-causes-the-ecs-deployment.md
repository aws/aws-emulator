## Description
Two root causes under the ecs__events__sqs heading, both grounded in failing checks listed in trace_ids. Neither failure is marked ALREADY FILED, and the replay report did not mark either as OWNED by an open issue. Open issues that look adjacent but do NOT cover these: 20261110T163010Z-ecs-events-sqs-a-placed-fargate-task-publishes.md, 20261120T181150Z-ecs-events-sqs-ecs-task-state-change-events.md, 20261122T004908Z-ecs-events-sqs-no-ecs-task-state-change.md, 20261122T033830Z-ecs-events-sqs-the-ecs-task-state-change.md and 20261122T102325Z-ecs-events-sqs-stoptask-publishes-no-further-ecs.md all concern the TASK-level detail-type 'ECS Task State Change' only, not the two SERVICE-level detail-types below. For Cause 2 the closest open issue is 20261125T024526Z-ecs-events-sqs-no-ecs-service-action-event.md, which describes the same 'ECS Service Action' family and even carries this check's id, but the suite did not bind this run's failure to it (its recorded replay key no longer matches the frame the run stops in), so this report re-grounds the cause in the failure actually observed; if that issue is closed, Cause 2 is closed with it. Cause 1 has no counterpart at all in the open set (a keyword search for 'Deployment State Change' returns nothing).

Cause 1 of 2: a FARGATE service's deployment lifecycle is neither driven nor announced — no 'ECS Deployment State Change' envelope is ever delivered, and DescribeServices' PRIMARY deployment never advances out of IN_PROGRESS to COMPLETED, so neither the healthy nor the circuit-breaker-failed leg can be observed (failing check: ecs__events__sqs.ecs-deployment-state-change-events-deliver-in-progress-then-failed).
AWS: when a service created with deploymentCircuitBreaker {enable:true, rollback:true} starts its initial deployment, ECS publishes to the default bus an envelope with source 'aws.ecs', detail-type 'ECS Deployment State Change', resources exactly [the service's ARN], detail.eventName 'SERVICE_DEPLOYMENT_IN_PROGRESS', detail.eventType 'INFO' and detail.deploymentId equal to the id DescribeServices reports for the PRIMARY deployment; when the service reaches steady state it publishes the same detail-type with detail.eventName 'SERVICE_DEPLOYMENT_COMPLETED' and detail.eventType 'INFO' for that same deploymentId. A subsequent UpdateService onto a revision whose container image tag does not exist becomes a NEW PRIMARY deployment with a new id, the circuit breaker drives that deployment to rolloutState FAILED with a rolloutStateReason whose text says the circuit breaker failed it, and ECS publishes 'ECS Deployment State Change' with detail.eventName 'SERVICE_DEPLOYMENT_FAILED', detail.eventType 'ERROR' and detail.deploymentId equal to the FAILED deployment's id (never the id of the one that succeeded); with rollback:true the service then returns to the last completed revision. Smithy models the control-plane half of this: CreateService/UpdateService take deploymentConfiguration.deploymentCircuitBreaker (DeploymentCircuitBreaker.enable and .rollback both @required boolean, default false), and Deployment carries id, taskDefinition, rolloutState (enum DeploymentRolloutState = COMPLETED | FAILED | IN_PROGRESS, documented 'begins in an IN_PROGRESS state... transitions to a COMPLETED state... if the service fails to reach a steady state and circuit breaker is turned on, the deployment transitions to a FAILED state') and rolloutStateReason ('A description of the rollout state of a deployment'). The eventing envelope itself is not modelled — recorded/documented behavior only (AmazonECS developer guide, ecs_service_deployment_events).
Emulator: the scenario produces no observable step at all. CreateService is accepted and returns the predicted serviceArn, but the PRIMARY deployment never reports rolloutState COMPLETED, and the rule scoped to {"source":["aws.ecs"],"detail-type":["ECS Deployment State Change"],"resources":[<service ARN>]} delivers nothing to its queue, so the check sits in its poll/receive loop until the harness cuts it: the replay reports 'Error: Check timed out after 60.0s' as a mismatch with no assertion reached. Because the IN_PROGRESS/COMPLETED positive control never fires, the later SERVICE_DEPLOYMENT_FAILED leg is never even attempted.
Why: a client that watches 'ECS Deployment State Change' to tell a rollout that is progressing from one the circuit breaker killed gets nothing — a permanently broken deployment looks identical to a healthy one, automation that gates a release on SERVICE_DEPLOYMENT_COMPLETED hangs forever, and automation that pages on SERVICE_DEPLOYMENT_FAILED never pages. Reading DescribeServices instead does not help, because rolloutState never leaves IN_PROGRESS, so neither COMPLETED nor FAILED is ever reachable and the rollback to the last good revision never happens.
Fix: the ECS service-scheduler/deployment component in the ecs service crate — the code that advances a service's PRIMARY Deployment's rolloutState (IN_PROGRESS -> COMPLETED on steady state; -> FAILED with a circuit-breaker rolloutStateReason when deploymentCircuitBreaker.enable is set and tasks cannot start) and performs the rollback when rollback is set — together with the ECS -> EventBridge emitter for detail-type 'ECS Deployment State Change' (detail.eventName, detail.eventType, detail.deploymentId, and the per-service `resources` scoping).
Traces: ecs__events__sqs.ecs-deployment-state-change-events-deliver-in-progress-then-failed.

Cause 2 of 2: the 'ECS Service Action' detail-type is never observable, so neither a service's task-configuration failure nor a healthy service's steady state is delivered, and the per-service `resources` scoping that must withhold one service's failure from another service's rule cannot be exercised (failing check: ecs__events__sqs.xsvc-ecs-1-unpullable-image-task-configuration-failure-not-delivered-to-sibling).
AWS: a FARGATE service whose container image tag does not exist publishes to the default bus an envelope with source 'aws.ecs', detail-type 'ECS Service Action', detail.eventName 'SERVICE_TASK_CONFIGURATION_FAILURE', detail.eventType 'ERROR', detail.clusterArn equal to the cluster's ARN, resources exactly [the failing service's ARN], and detail.reason whose fixed text begins 'CannotPullContainerError' and whose variable part names the image reference from the task definition in the request that could not be pulled; a healthy sibling service publishes the same detail-type with detail.eventName 'SERVICE_STEADY_STATE', detail.eventType 'INFO' and resources exactly [its own service ARN]. Because `resources` is scoped to one service, a rule scoped to the healthy service's ARN must receive its SERVICE_STEADY_STATE and must never receive the sibling's failure, even when that rule's detail.eventName filter lists SERVICE_TASK_CONFIGURATION_FAILURE. Smithy models CreateService (serviceName @required, deploymentConfiguration, networkConfiguration; errors ClientException / ClusterNotFoundException / InvalidParameterException 400, ServerException 500) and the returned serviceArn, but says nothing about eventing: the envelope above is recorded/documented behavior only.
Emulator: the scenario is cut off by the harness — the replay reports 'Error: Check timed out after 60.0s' as a mismatch with no assertion reached. CreateService is accepted and returns the predicted service ARNs, but all three rules (bad-service-scoped, good-service-scoped, and the near-miss scoped to the good service while filtering detail.eventName on the failure) stay empty: no 'ECS Service Action' envelope is ever delivered to any target queue, so the check never clears its delivery barrier and evaluates neither the positive nor the negative leg.
Why: a client that alarms on SERVICE_TASK_CONFIGURATION_FAILURE gets no signal that a service cannot pull its image, and gets no SERVICE_STEADY_STATE for one that is healthy, so a permanently failing service is indistinguishable from a working one. Worse, because every rule is silent, an absence can never be read as correct scoping — the negative contract (one service's failure not reaching another service's rule) is unverifiable rather than satisfied.
Fix: the ECS service-scheduler path in the ecs service crate that records a task-configuration failure (CannotPullContainerError naming the offending image) and a service reaching steady state, plus the ECS -> EventBridge emitter for detail-type 'ECS Service Action' (detail.eventName, detail.eventType, detail.clusterArn, detail.reason and the per-service `resources` scoping).
Traces: ecs__events__sqs.xsvc-ecs-1-unpullable-image-task-configuration-failure-not-delivered-to-sibling.
