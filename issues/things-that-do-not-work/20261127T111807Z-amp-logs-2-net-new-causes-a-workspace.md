# amp__logs: 2 net-new causes — a workspace logging configuration provisions no vended-log-delivery resource policy on its log group (checks hang to the 60 s cap), and the ruler delivers no evaluation log events to the configured group

> _Note: this issue was identified against the code base at commit `0e14ec34ba796ebb423716588b97f90ad61f6019`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateLoggingConfiguration

## Description
Two distinct root causes in the Amazon Managed Service for Prometheus workspace-logging (vended logs) path. Both are emulator-side: the amp control plane answers 22/22 of its own checks, so the service is serving; what is missing is the vended-logging side effects a logging configuration is defined by. No existing open issue covers amp vended logging (the nearest, 20261125T155754Z-iot-logs-iot-v2-logging-still-delivers-no.md and 20261123T235920Z-bedrock-model-invocation-logging-delivers-no-record-to-805db4.md, are other services).

Cause 1 of 2: CreateLoggingConfiguration never provisions the log-delivery resource policy on the target log group, so a logging configuration never becomes observably ACTIVE-and-delivering.
AWS: CreateLoggingConfiguration is POST /workspaces/{workspaceId}/logging -> 202 with a required `status` (LoggingConfigurationStatus); DescribeLoggingConfiguration is GET on the same URI -> 200 with a required `loggingConfiguration` whose `status.statusCode` advances CREATING -> ACTIVE and whose `logGroupArn`/`workspace` echo what was created (Smithy: CreateLoggingConfiguration input logGroupArn @required @pattern ^arn:aws[a-z0-9-]*:logs:[a-z0-9-]+:[0-9]{12}:log-group:[A-Za-z0-9\.\-\_\#/]{1,512}\:\*$; errors ValidationException 400, ResourceNotFoundException 404, AccessDeniedException 403, InternalServerException 500). Per AWS's vended-logs contract (https://docs.aws.amazon.com/prometheus/latest/userguide/CW-logs.html and https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/AWS-logs-infrastructure-CWL.html), once the configuration is ACTIVE the destination log group carries a RESOURCE-scope policy — readable with logs:DescribeResourcePolicies(resourceArn=<group ARN without ':*'>, policyScope='RESOURCE') — holding exactly ONE statement with Effect 'Allow', Principal.Service 'delivery.logs.amazonaws.com', Action covering logs:CreateLogStream and logs:PutLogEvents, Resource '<group ARN>:log-stream:*', and Condition StringEquals aws:SourceAccount = the caller's account id plus ArnLike aws:SourceArn = 'arn:aws:logs:<region>:<account-id>:*'. The template is the requirement; the account id, region and group name are values taken from the request and the caller's identity, never literals from one run. Deleting the configuration and recreating it on the same group leaves exactly one such statement (not two).
Emulator: all three checks that exercise this consume the entire 60 s per-check budget and reach no verdict ('Check timed out after 60.0s'). Each blocks in the same shape of wait: first _wait_for(DescribeLoggingConfiguration -> status.statusCode == 'ACTIVE', 300 s), then _wait_for(DescribeResourcePolicies(policyScope='RESOURCE') -> a delivery.logs.amazonaws.com Allow statement, 120 s). Nothing in the emulator ever satisfies either, so no log-delivery grant is ever observable on the group, and the 'exactly one grant after delete+recreate' and 'Resource/Condition are scoped to this group, this account and this Region' requirements are unobservable.
Also inside this blocked path and therefore still unverified, so they must be re-checked once the hang is gone: (a) a logGroupArn lacking the ':*' suffix must be refused ValidationException with message 'Invalid logGroupArn: Member must satisfy regular expression pattern: arn:aws[a-z0-9-]*:logs:[a-z0-9-]+:[0-9]{12}:log-group:[A-Za-z0-9\.\-\_\#/]{1,512}\:\*' (fixed text; the pattern is the modeled one) and must leave no configuration and no grant behind; (b) DescribeLoggingConfiguration for a workspace with none must answer ResourceNotFoundException with message 'Workspace logging configuration not found.' (fixed text, no variable part).
Why: a client that enables workspace logging gets a configuration that never settles and a log group that is never granted to the log-delivery service. Anything that waits for ACTIVE, or asserts the delivery grant and its account/Region scoping before trusting the pipeline (the documented setup step for AMP rule logging), hangs or concludes logging is broken; an IaC or operator workflow that deletes and recreates the configuration cannot verify it did not accumulate duplicate grants.
Why (status): the required `status` member means a client legitimately polls to ACTIVE; a configuration stuck short of it is indistinguishable from a stalled service.
Fix: the amp CreateLoggingConfiguration / UpdateLoggingConfiguration / DeleteLoggingConfiguration handlers and the logging-configuration state they own — the status transition to ACTIVE, and the cross-service side effect that writes (and on delete removes, and on recreate does not duplicate) the delivery.logs.amazonaws.com statement in the cloudwatchlogs resource-policy state for the named group, plus the logGroupArn pattern validation in CreateLoggingConfiguration's input validation.
Traces: amp__logs.workspace-logging-configuration-grants-log-delivery-on-its-log-group, amp__logs.logging-configuration-recreated-on-plain-log-group-keeps-one-scoped-grant, amp__logs.create-logging-configuration-log-group-arn-without-wildcard-rejected.

Cause 2 of 2: the ruler emits no evaluation log events into the configured log group, so no vended log record ever arrives.
AWS: recorded behavior only for the event payloads (the AMP API model does not describe log content). With a workspace logging configuration ACTIVE, AMP's ruler writes rule-evaluation diagnostics into the configured CloudWatch Logs group — an evaluation that fails (e.g. a one-to-one vector match against two series) produces a WARN/ERROR event naming the failing rule, readable through logs:DescribeLogStreams + logs:FilterLogEvents/GetLogEvents on that group; successful evaluations produce no such event (only warning and error severities are vended); and after UpdateLoggingConfiguration repoints the configuration at another group, subsequent events land in the new group while the first group stops receiving them.
Emulator: the log group stays empty forever. The three checks fail on their delivery waits with 'AssertionError: a ruler event for the failing rule not reached in 27s; last read []', 'AssertionError: two logged evaluations of the failing rule not reached in 480s; last read []' and 'AssertionError: a ruler event in the first group not reached in 480s; last read []' — an empty list every poll, never a wrongly-shaped record. Consequently the severity filter (warning/error only, nothing for a succeeding rule) and the move-to-the-new-group behavior of UpdateLoggingConfiguration are both unobservable.
Why: a client that relies on AMP rule logging to diagnose rule groups sees a silent, permanently empty log group and cannot distinguish 'all rules healthy' from 'logging not delivering'; alarms and metric filters built over the vended group never fire, and a logging-configuration update appears to lose logging entirely.
Fix: the amp ruler/rule-group evaluation path and the vended-log delivery it drives — emit an evaluation event per failing rule evaluation, filter to warning/error severities, and write it through the cloudwatchlogs state (creating the stream in the group the ACTIVE logging configuration currently names, so an UpdateLoggingConfiguration retargets subsequent events).
Traces: amp__logs.ruler-evaluation-failure-is-logged-to-the-workspace-log-group, amp__logs.ruler-logs-only-warning-and-error-events, amp__logs.update-logging-configuration-moves-ruler-events-to-the-new-log-group.

## Steps to Reproduce
Cause 1:
1. logs.CreateLogGroup(logGroupName='/aws/vendedlogs/<name>'), then logs.DescribeLogGroups(logGroupNamePrefix=...) to read its ARN (ends ':*'); strip ':*' to get the group ARN.
2. logs.DescribeResourcePolicies(resourceArn=<group ARN>, policyScope='RESOURCE') — confirm no delivery.logs.amazonaws.com Allow statement yet.
3. amp.CreateWorkspace(alias=<name>); poll amp.DescribeWorkspace until status.statusCode == 'ACTIVE'.
4. amp.CreateLoggingConfiguration(workspaceId=<id>, logGroupArn=<ARN ending ':*'>); poll amp.DescribeLoggingConfiguration for status.statusCode == 'ACTIVE'.
5. Poll logs.DescribeResourcePolicies(resourceArn=<group ARN>, policyScope='RESOURCE') for an Allow statement whose Principal.Service is 'delivery.logs.amazonaws.com' — observe none ever appears; the check exhausts its budget.
6. Variant (one-grant rule): amp.DeleteLoggingConfiguration, wait for DescribeLoggingConfiguration -> ResourceNotFoundException 'Workspace logging configuration not found.', recreate, and assert exactly one delivery grant with Resource '<group ARN>:log-stream:*'.
7. Variant (rejection): call amp.CreateLoggingConfiguration with logGroupArn lacking the ':*' suffix and assert ValidationException with the modeled-pattern message, then that no configuration and no grant were left behind.

Cause 2:
1. Stand up a workspace with an ACTIVE logging configuration as above.
2. amp.CreateRuleGroupsNamespace with a rule whose expression fails on every evaluation (e.g. a one-to-one vector match with no labels against two series), plus a rule that always succeeds.
3. Poll logs.DescribeLogStreams / logs.FilterLogEvents on the configured log group for an event naming the failing rule — observe [] forever; no event for the succeeding rule is expected.
4. amp.UpdateLoggingConfiguration to a second log group and poll both groups — the first group never received an event, so the move cannot be observed.
