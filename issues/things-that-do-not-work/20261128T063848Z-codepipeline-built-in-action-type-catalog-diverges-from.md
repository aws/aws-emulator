# CodePipeline built-in action-type catalog diverges from AWS: wrong entries and order, missing settings URL templates, and GetPipelineState entityUrl is not a console deep link

> _Note: this issue was identified against the code base at commit `ed3ed06301643834f5ccb593614cfd988c817634`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListActionTypes

## Description
Three net-new causes, all rooted in the emulator's built-in CodePipeline action-type catalog: the catalog it serves from ListActionTypes does not match AWS's provider catalog (membership, order and the per-type ActionTypeSettings URL templates), and because GetPipelineState renders an action's entityUrl from that same catalog data, the state view emits a non-console URL too. All three steps answered HTTP 200, so no error code or message is at issue here; the divergence is wholly in the response payload.

Cause 1 of 3: ListActionTypes (AWS-owned catalog page). AWS: ListActionTypes returns the full catalog of action types available to the caller; each element is an ActionType with a required `id` (ActionTypeId: category/owner/provider/version), required `inputArtifactDetails` and `outputArtifactDetails` (ArtifactDetails minimumCount/maximumCount), optional `actionConfigurationProperties` (ActionConfigurationPropertyList, @length 0..10, each with name/required/key/secret/queryable/description) and optional `settings` (ActionTypeSettings with entityUrlTemplate / executionUrlTemplate / revisionUrlTemplate / thirdPartyConfigurationUrl, each a UrlTemplate @length 1..2048). Smithy: ListActionTypes -> ListActionTypesOutput.actionTypes (required, ActionTypeList), errors InvalidNextTokenException / ValidationException; shapes ActionType, ActionTypeSettings, ActionConfigurationProperty, ActionTypeId. The specific catalog membership and the exact entityUrlTemplate strings AWS ships are not in the model: recorded behavior only. The recording shows an AWS-owned catalog page of 28 entries whose first element is category=Source owner=AWS provider=S3 version=1, with actionConfigurationProperties S3Bucket (key, required), S3ObjectKey (key, required), PollForSourceChanges (key, not required) and AllowOverrideForS3ObjectKey (key, not required), inputArtifactDetails {minimumCount 0, maximumCount 0}, outputArtifactDetails {minimumCount 1, maximumCount 1} and settings.entityUrlTemplate an S3 console deep-link template; later elements carry settings.entityUrlTemplate (indices 1, 6, 8, 10, 11, 12, 16, 17, 18, 20, 21, 22, 23) and settings.executionUrlTemplate (indices 1 and 22). Emulator: the AWS-owned page is a different, shorter list in a different order — its first element is category=Approval owner=AWS provider=Manual version=1 with settings {} and outputArtifactDetails {minimumCount 0, maximumCount 0} — so every recorded index 0..27 is reported missing or mismatched, and the entries that do exist carry an empty/incomplete `settings` (no entityUrlTemplate, no executionUrlTemplate). Why: a client that enumerates ListActionTypes to discover which provider/category/version triples it may put in a pipeline declaration, to validate an action's configuration keys, or to render a deep link for an action, sees a catalog that omits providers AWS offers (so a legitimate declaration looks unsupported), reports artifact-count limits that differ from AWS's, and has no URL templates at all. Fix: the ListActionTypes handler's static action-type catalog (the seeded catalog data it serves, and its ordering), including each entry's ActionTypeSettings templates and ArtifactDetails counts. Traces: codepipeline-catalog-list-action-types#task#1.

Cause 2 of 3: ListActionTypes for the ThirdParty owner. AWS: ActionTypeId.owner is one of AWS, ThirdParty, Custom, and ListActionTypesInput.actionOwnerFilter (ActionOwner enum) selects the page for one owner; ThirdParty entries carry settings.thirdPartyConfigurationUrl (the sign-up/configuration page) alongside entityUrlTemplate / executionUrlTemplate / revisionUrlTemplate. Smithy: ListActionTypesInput.actionOwnerFilter -> ActionOwner; ActionTypeSettings.thirdPartyConfigurationUrl/revisionUrlTemplate. Catalog membership is recorded behavior only: the recording shows 5 ThirdParty entries whose first element is category=Test owner=ThirdParty provider=GhostInspector version=1, with config properties ClientId (required), ClientToken (required, secret), TestId (required) and ExtraParams, inputArtifactDetails {0,1}, outputArtifactDetails {0,0}, and settings carrying entityUrlTemplate, executionUrlTemplate and thirdPartyConfigurationUrl. Emulator: the ThirdParty page starts with category=Source owner=ThirdParty provider=GitHub version=1, and indices 1..4 of the recorded page are absent; element 0's settings is missing the recorded revisionUrlTemplate and thirdPartyConfigurationUrl. Why: the same discovery/validation break as cause 1, for third-party providers — a client cannot learn which ThirdParty providers are offered, which of their configuration keys are required or secret, or where to send a user to configure the external system. Fix: the same static catalog in the ListActionTypes handler, specifically its ThirdParty-owner entries and their ActionTypeSettings members. Traces: codepipeline-catalog-list-action-types#task#2.

Cause 3 of 3: GetPipelineState emits entityUrl pointing at the emulator's own data endpoint instead of a console deep link. AWS: ActionState.entityUrl is "A URL link for more information about the state of the action, such as a deployment group details page" (Url, @length 1..2048); it is produced by rendering the action type's ActionTypeSettings.entityUrlTemplate with the action's configuration values, and AWS therefore returns a console deep link — host console.aws.amazon.com (or the regional console host), with the provider-specific path and query the template defines (for a CodeCommit source action, the codesuite/codecommit repository-browse path for the configured RepositoryName and BranchName with the region query; for a Lambda invoke action, the Lambda console function path for the configured FunctionName). Smithy: GetPipelineState -> GetPipelineStateOutput.stageStates (StageStateList) -> ActionState.entityUrl (Url); ActionTypeSettings.entityUrlTemplate. Emulator: entityUrl is built against the emulator's own data listener — an IP-literal host:port origin — e.g. the CodeCommit source action's entityUrl and the Lambda invoke action's entityUrl are both served on that origin rather than on a console host, which is why the step's shape assertion on the field fails. The fixed requirement here is the FORM of the URL (console host plus the template's provider-specific path and query, with repository name, branch, function name and region taken from the action's configuration and the request's region); the particular host, port, repository name and function name in the recording are per-run values and are not themselves requirements. Why: a client or UI that follows entityUrl to show a user the underlying resource is sent to the emulator's API endpoint, which serves no such page, instead of to the resource page the field promises; the field is also unusable as the observable signal that an action's entityUrlTemplate was applied at all. Hypothesis: because the catalog entries in causes 1 and 2 carry no entityUrlTemplate, the state renderer has no template to apply and falls back to its own endpoint origin. Fix: the GetPipelineState handler's action-state projection (where entityUrl is rendered), driven by the action type's entityUrlTemplate restored in the catalog. Traces: codepipeline-gpn-traj-creation-run-failed-at-source-read-path#task#10.

Not covered by an existing issue: the open CreatePipeline issue 20261119T210011Z-codepipeline-createpipeline-refuses-a-well-formed-v2-codecommit.md owns the separate CreatePipeline HTTP 400 divergence in this corpus (skipped here as already owned) and says nothing about the action-type catalog or entityUrl; the other open CodePipeline issues concern execution progress, CloudFormation provisioning and job results.
