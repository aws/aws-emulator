Cause 1 of 6: PutTraceSegments accepts a segment document that carries neither `end_time` nor `in_progress`, instead of refusing it as MissingEndTime.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models PutTraceSegments as POST /TraceSegments, success 200, input TraceSegmentDocuments (required), output UnprocessedTraceSegments -> UnprocessedTraceSegment{Id, ErrorCode, Message}; its operation documentation states the required segment-document fields and that a document must "Specify either an end_time or in_progress". Recorded behavior: a document with neither member is not stored and is reported as one UnprocessedTraceSegment carrying the submitted segment's own `id` as Id, ErrorCode `MissingEndTime` and Message `Invalid segment. ErrorCode: MissingEndTime` — fixed text `Invalid segment. ErrorCode: ` plus the ErrorCode; the Id is the value the request's document carried. The call itself still answers HTTP 200.
Emulator: such a document produces NO entry at all (it is silently accepted). In the all-defective batch, four defective documents yielded only two entries — MissingStartTime and MissingName — with no MissingEndTime entry; in the interleaved batch three refusals were due and only two were returned (ParseError, MissingId), the open-ended segment's refusal missing.
Why: a producer that forgets to close a segment (and does not mark it in_progress) gets silence instead of the per-document refusal AWS returns, so the emulator stores a malformed segment that AWS would never hold; a client's ingest health check, which counts UnprocessedTraceSegments by ErrorCode, reports a clean batch for a batch AWS partly rejects, and the defective segment then pollutes every derived read (traces, summaries, graphs).
Fix: the per-document validation PutTraceSegments runs before ingest — `crate::state::parse_segment_document` and the required/complete-ness rules it applies — in the xray state module, reported through the operation's handler.
Traces: xray.put-trace-segments-batch-of-only-defective-documents-answers-each-by-id, xray.put-trace-segments-interleaved-refusals-stay-attributed-amid-accepted.

Cause 2 of 6: PutTraceSegments accepts a segment whose `id` is not 16 hexadecimal digits, instead of refusing it as InvalidId.
AWS: the operation's documentation requires `id` to be "A 64-bit identifier for the segment, unique among segments in the same trace, in 16 hexadecimal digits". Recorded behavior: a document whose `id` is present but not of that form is refused per-document with ErrorCode `InvalidId` and Message `Invalid segment. ErrorCode: InvalidId`, keyed under the Id exactly as submitted (the malformed value), and is not stored; the call answers 200.
Emulator: a document whose `id` was truncated to 5 hex digits is accepted — no UnprocessedTraceSegment entry is produced for it. The emulator does implement the sibling classes (MissingId is produced when `id` is absent), so what is missing is the FORM check on a present `id`.
Why: segment ids are the join key of a trace tree (`parent_id` references them). Accepting an id of the wrong width lets a client store segments AWS rejects, so the parenting/edge derivation a client later reads is built on ids production would never have admitted, and the client is never told its instrumentation emits malformed ids.
Fix: same per-document validation path as Cause 1 — add the `id` form check (16 hex digits) beside the existing MissingId check in `crate::state::parse_segment_document`, with the `InvalidId` code built through the same member-code helper.
Traces: xray.put-trace-segments-batch-of-only-defective-documents-answers-each-by-id.

Cause 3 of 6: a document that is well-formed JSON but is not a segment object is refused with the SEGMENT wording instead of the ENTITY wording.
AWS: ErrorCode/Message are modeled only as free-form strings (UnprocessedTraceSegment{Id, ErrorCode, Message}), so this is recorded behavior: a document that cannot be read as a segment/subsegment entity at all (here a JSON array, `[]`) is reported with no Id, ErrorCode `ParseError` and Message `Invalid entity. ErrorCode: ParseError` — fixed text `Invalid entity. ErrorCode: ` plus the code — while a document that IS a segment object but breaks a member rule takes `Invalid segment. ErrorCode: <code>`.
Emulator: the entity-level rejection is returned as ErrorCode `ParseError`, Message `Invalid segment. ErrorCode: ParseError`. The checkout states this single wording as intended for every per-document rejection (services/service-com-amazonaws-xray-awsxray/src/state.rs, the SEGMENT_ERROR_PARSE documentation), so the entity-level prefix is simply not modelled.
Why: the message text is the requirement. A client (or an SDK-level error classifier) that distinguishes an unreadable entity from an invalid segment by the message gets the wrong class, and a log-scraping assertion on AWS's wording can never match.
Fix: the UnprocessedTraceSegment message construction for the parse/entity class in the xray state module (the rejection built by `crate::state::parse_segment_document`), so an entity that is not a segment object carries `Invalid entity. ErrorCode: ParseError` and member-level refusals keep `Invalid segment. ErrorCode: <code>`.
Traces: xray.put-trace-segments-interleaved-refusals-stay-attributed-amid-accepted.

Cause 4 of 6: PutTraceSegments refuses a segment document that is under the 64 kB document limit with ErrorCode LimitExceeded when several such documents belong to one trace.
AWS: the operation models no length bound on TraceSegmentDocuments or on a document (Smithy: TraceSegmentDocuments -> TraceSegmentDocumentList of String, no @length), and its documentation publishes no per-trace segment cap; recorded behavior: four ~62 kB segment documents (each a root segment with 380 remote subsegments) sharing one trace_id are ALL accepted in one call — UnprocessedTraceSegments is empty — and all four become readable in the trace graph.
Emulator: one of the four documents is refused with Id = that segment's id, ErrorCode `LimitExceeded`, Message `Invalid segment. ErrorCode: LimitExceeded`, so the call reports a partial batch and the trace is missing a service. Hypothesis (neither the model nor the recording states it): the per-trace ingest cap counts the INFERRED downstream segments the handler synthesises for each remote subsegment (`crate::state::inferred_segments`, 380 per document here, ~1520 for the batch) against the trace's segment budget, so a trace that AWS admits comfortably is declared full after three documents.
Why: a realistically instrumented service graph (a handful of services each calling hundreds of hosts in one request) is partly rejected, so the client loses whole services from the trace while the call still answers 200 — the hardest failure mode to notice. Anything that asserts an empty UnprocessedTraceSegments for a legal batch fails against the emulator.
Fix: the trace-level ingest bound in the xray state store (`ingest_segment` and the cap whose refusal code is SEGMENT_ERROR_LIMIT_EXCEEDED, services/service-com-amazonaws-xray-awsxray/src/state.rs) — bound the trace by what the caller actually submitted rather than by the service's own inferred segments, and at a size that admits documents under the documented 64 kB per-document limit.
Traces: xray.trace-graph-single-read-holds-every-node-once.

Cause 5 of 6: GetTraceGraph refuses a NextToken the service never issued with the wrong message.
AWS: Smithy models GetTraceGraph as POST /TraceGraph, success 200, paginated (inputToken/outputToken NextToken, items Services), errors InvalidRequestException (400) and ThrottledException (429). Recorded behavior: a NextToken the service never handed out is refused with HTTP 400, error code `InvalidRequestException` and message `NextToken is currently not supported` — entirely fixed text that interpolates NOTHING from the request.
Emulator: the code is right (`InvalidRequestException`) but the message is `Invalid token <the submitted token>`, i.e. different fixed text plus an echo of the request's token.
Why: the message is a requirement; a client that matches AWS's text (or logs it for operators) sees an unknown refusal, and echoing the caller's token back is not what AWS reports.
Fix: the NextToken validation/refusal in the GetTraceGraph handler and the shared token decoder it uses (services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_graph.rs with crate::state::pagination).
Traces: xray.get-trace-graph-unissued-next-token-rejected.

Cause 6 of 6: GetTraceGraph never derives a caller's edge to a downstream segment that was parented on one of the caller's SUBSEGMENT ids.
AWS: Smithy models GetTraceGraph output Services -> Service{ReferenceId, Name, Names, Root, Type, State, Edges -> Edge{ReferenceId, ...}}; Edge is documented as "Information about a connection between two services" and Service$Edges as "Connections to downstream services". Recorded behavior: the trace graph is not frozen at its first read — after a second segment whose `parent_id` is the caller segment's subsegment id is accepted, a later GetTraceGraph holds one node for the downstream service (Root not true) AND the caller node (Root true) with exactly one Edge whose ReferenceId is the downstream node's ReferenceId.
Emulator: the downstream node DOES appear on the later read (the check got past that wait), the caller stays Root, but the caller node's Edges is empty/absent — `the caller's edges must point at exactly the downstream node 0; they point at []`. So the parent/child relation across a subsegment boundary is not translated into a graph edge.
Why: edges ARE the service map. A client reading GetTraceGraph sees two unconnected services instead of a caller->callee dependency, so dependency discovery, downstream-latency attribution and any console-style map built on the trace graph show no call at all between services that demonstrably called each other.
Fix: the trace-graph edge derivation — resolve a segment's `parent_id` against the subsegment ids of the other segments in the trace (not only against top-level segment ids) when building nodes and edges (services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_graph.rs and the graph derivation in src/state/graphs.rs with the tree assembly in src/state/assembly.rs).
Traces: xray.trace-graph-gains-a-downstream-service-written-after-the-first-read.
