# sns: 5 net-new causes — PublishBatch faults the whole call instead of per-entry Failed rows, CreateTopic attribute-conflict and MaximumMessageSize refusals wrong, Policy statement limit unenforced, DeleteTopic ignores an active ArchivePolicy

> _Note: this issue was identified against the code base at commit `255279eeed7e5207bd6ac2895e89724e049cf5ef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PublishBatch

## Description
Five independent root causes in the emulator's SNS topic/attribute and batch-publish surface. All five are grounded in failing behavioral checks listed under `### sns`.

Cause 1 of 5: PublishBatch rejects the ENTIRE call when a single entry is invalid, instead of reporting that entry in `Failed` and delivering its siblings.
  AWS: Smithy: PublishBatch takes `PublishBatchRequestEntries` (required list) and answers `PublishBatchResponse{Successful: PublishBatchResultEntryList, Failed: BatchResultErrorEntryList}` with HTTP 200. Per-entry faults are NOT call-level errors: the modeled call-level errors are the batch-wide ones (EmptyBatchRequest, BatchEntryIdsNotDistinct, TooManyEntriesInBatchRequest, BatchRequestTooLong, InvalidBatchEntryId, NotFound, AuthorizationError...). An entry whose own parameters are invalid comes back as a BatchResultErrorEntry `{Id: <the entry's Id>, Code: "InvalidParameter", Message: <the same message Publish would use for that parameter>, SenderFault: true}` while every valid sibling entry appears in `Successful` with its own MessageId and is delivered. The six recordings cover the per-entry messages (fixed text; only the request-supplied values vary): "Invalid parameter: Empty message"; "Invalid parameter: Subject" (Subject over 100 characters); "Invalid parameter: Message Structure - No default entry in JSON message body"; "Invalid parameter: Message Structure - JSON message body failed to parse"; "Invalid parameter: MessageDeduplicationId Reason: The request includes MessageDeduplicationId parameter that is not valid for this topic type" (standard topic); "Invalid parameter: The MessageGroupId parameter can only include alphanumeric and punctuation characters. 1 to 128 in length". AWS also still fails per entry when NO entry succeeds (`Successful` empty, `Failed` holding one row per entry).
  Emulator: the whole PublishBatch call is refused with HTTP 400 `InvalidParameter` and that per-entry message hoisted to the call level, e.g. `botocore.errorfactory.InvalidParameterException: An error occurred (InvalidParameter) when calling the PublishBatch operation: Invalid parameter: Empty message` / `... Invalid parameter: Subject` / `... Invalid parameter: Message Structure - No default entry in JSON message body` / `... Invalid parameter: MessageDeduplicationId Reason: ...` / `... Invalid parameter: The MessageGroupId parameter can only include alphanumeric and punctuation characters. 1 to 128 in length`. No `Failed` list is ever produced and the valid sibling entries are never published.
  Why: a client that batches publishes loses every good message in the batch when one entry is malformed, and never sees the `Failed`/`Successful` partition the API contract is built on; code that reads `response["Failed"]` to retry only the bad entries instead gets a thrown exception, and partial-failure handling cannot be exercised at all.
  Fix: PublishBatch's handler and its validation — per-entry parameter validation must run inside the entry loop and append a BatchResultErrorEntry (Code=InvalidParameter, SenderFault=true, the entry's Id, the Publish-equivalent message) rather than returning a call-level InvalidParameterException; only batch-wide faults abort the call. The response serializer must emit both Successful and Failed with HTTP 200.
  Traces: sns.publish-batch-empty-message-entries-fail-per-entry-even-when-no-entry-succeeds, sns.publish-batch-entry-subject-over-100-characters-fails-alone-and-its-sibling-is-delivered, sns.publish-batch-json-structure-entry-without-default-key-fails-alone-while-a-keyed-sibling-delivers-its-sqs-value, sns.publish-batch-malformed-group-id-on-a-standard-topic-fails-only-its-entry, sns.publish-batch-refused-entries-follow-their-ids-and-are-never-delivered, sns.publish-batch-dedup-id-on-a-standard-topic-fails-only-its-entry-while-publish-refuses-the-call.

Cause 2 of 5: the out-of-range MaximumMessageSize refusal from CreateTopic omits the `Attributes Reason:` qualifier.
  AWS: Smithy: CreateTopic takes `Attributes` (TopicAttributesMap) and models InvalidParameterException (awsQueryError code `InvalidParameter`, HTTP 400). An out-of-range MaximumMessageSize is refused with code `InvalidParameter` and message `Invalid parameter: Attributes Reason: MaximumMessageSize: <value> is not an integer between 1024 and 1048576 bytes` — fixed text "Invalid parameter: Attributes Reason: MaximumMessageSize: " ... " is not an integer between 1024 and 1048576 bytes", with <value> taken verbatim from the request's attribute value; the bounds 1024 and 1048576 are the service's limits. No topic is created.
  Emulator: same code, but the message drops the attribute-map qualifier: `Invalid parameter: MaximumMessageSize: 1023 is not an integer between 1024 and 1048576 bytes`.
  Why: clients and tests that match on SNS's attribute-rejection wording ("Attributes Reason:" is how SNS marks a fault inside the Attributes map, as it does for other attribute faults) do not recognise the refusal, and a message asserted against AWS fails.
  Fix: CreateTopic's attribute validation — render attribute-map faults through the `Attributes Reason:` prefix used for every Attributes-map rejection.
  Traces: sns.create-topic-maximum-message-size-outside-range-rejected.

Cause 3 of 5: CreateTopic on an existing topic name with an attribute value the topic does not hold succeeds instead of being refused.
  AWS: CreateTopic is idempotent only for an identical request: repeating it with the same name and no conflicting attributes returns the existing TopicArn, but supplying an attribute whose value differs from what the topic holds (here `DisplayName`, which the existing topic holds as the empty string) is refused with HTTP 400, code `InvalidParameter`, message `Invalid parameter: Attributes Reason: Topic already exists with different attributes` (entirely fixed text), and the topic keeps its stored attributes.
  Emulator: the call returns HTTP 200 with the existing topic's ARN, e.g. `{'TopicArn': 'arn:aws:sns:<region>:<account>:<name>', ...}`, so the conflicting attribute is silently accepted/ignored.
  Why: a client relying on CreateTopic as a create-or-verify step never learns that its declared attributes disagree with the live topic — it proceeds believing DisplayName was applied, while the topic is unchanged, and no InvalidParameter is ever raised for a genuine configuration conflict.
  Fix: CreateTopic's handler — compare each requested attribute against the existing topic's stored attributes and raise InvalidParameterException with the above message on any difference, leaving state untouched.
  Traces: sns.create-topic-with-an-unheld-attribute-is-refused-and-leaves-the-topic-unchanged.

Cause 4 of 5: SetTopicAttributes accepts a topic `Policy` with more than 100 statements.
  AWS: Smithy: SetTopicAttributes models InvalidParameterException (code `InvalidParameter`, HTTP 400). A topic access policy may hold at most 100 statements: a 100-statement policy is stored, and a 101-statement policy is refused with code `InvalidParameter` and message `Invalid parameter: Policy contains too many statements!` (fixed text, no variable part), leaving the previously stored policy in place.
  Emulator: the 101-statement SetTopicAttributes returns HTTP 200 (empty SetTopicAttributesResponse) and the oversized policy is stored.
  Why: a client can install a policy AWS would reject, so an IaC/policy-management path that is expected to fail at the statement quota appears to succeed against the emulator and then breaks against AWS; the stored-policy invariant after a refusal cannot be observed.
  Fix: SetTopicAttributes' validation of the `Policy` attribute — count the parsed policy's Statement entries and refuse above 100 with the message above before mutating topic state.
  Traces: sns.topic-policy-over-100-statements-rejected.

Cause 5 of 5: DeleteTopic deletes a FIFO topic whose ArchivePolicy is active instead of refusing with InvalidState.
  AWS: Smithy: DeleteTopic models InvalidStateException (awsQueryError code `InvalidState`, HTTP 400). A topic with an active archive policy (`ArchivePolicy` set to e.g. {"MessageRetentionPeriod": "<days>"}) cannot be deleted: DeleteTopic is refused with code `InvalidState`, the topic stays readable and its ArchivePolicy unchanged; after the policy is cleared (`ArchivePolicy` = "{}") the same DeleteTopic succeeds and GetTopicAttributes then answers `NotFound` / "Topic does not exist".
  Emulator: DeleteTopic on the archiving FIFO topic returns HTTP 200 and removes the topic; no InvalidState is ever raised.
  Why: archive-retention protection is absent — a client (or a CFN/IaC delete) destroys an archiving topic and its retained messages where AWS would stop it, and code that handles InvalidState by first clearing the archive policy is never exercised.
  Fix: DeleteTopic's handler/state check — refuse with InvalidStateException while the topic's ArchivePolicy is non-empty, and leave the topic and its attributes untouched.
  Traces: sns.topic-with-an-active-archive-policy-cannot-be-deleted.
