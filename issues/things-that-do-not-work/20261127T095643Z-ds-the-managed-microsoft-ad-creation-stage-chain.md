# ds: the Managed Microsoft AD creation stage chain is never observable as settled, so the ds-data group-membership duplicate-add / reused-token scenario reaches no verdict

## Description

--- Cause 1 of 1: a Managed Microsoft AD created by CreateMicrosoftAD does not present a settled, terminal creation stage to the client's probes, so the group-membership rejection scenario never gets past its creation wait (failing check id: ds.ds-data-group-membership-refuses-duplicate-adds-and-reused-tokens).

AWS: modelled. Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json): DirectoryStage = [Requested, Creating, Created, Active, Inoperable, Impaired, Restoring, RestoreFailed, Deleting, Deleted, Failed, Updating]; CreateMicrosoftAD input {Name @required, ShortName, Password @required @sensitive, Description, VpcSettings @required, Edition, NetworkType, Tags} / output {DirectoryId, pattern ^d-[0-9a-f]{10}$}; DescribeDirectories input {DirectoryIds, NextToken, Limit} / output {DirectoryDescriptions, NextToken}, errors include EntityDoesNotExistException (client, httpError 400); DirectoryDescription carries Stage, StageReason, LaunchTime, StageLastUpdatedDateTime; EnableDirectoryDataAccess / DescribeDirectoryDataAccess expose DataAccessStatus (Disabled/Enabling/Enabled/Disabling/Failed). AWS answers CreateMicrosoftAD BEFORE the directory is provisioned and exposes the walk only through DescribeDirectories. For the wall clock there is recorded behavior only: the check budgets 3000 s for creation and 900 s for data access, i.e. on real AWS a Standard Managed Microsoft AD takes tens of minutes, so the suite's 60 s per-check ceiling is this environment's, not AWS's.

Emulator: no status, error code, message or shape divergence is reported for this check. The only output is the creation wait giving up: 'AssertionError: directory creation: still {... "Stage": "Creating" ...} after 1s'. The DirectoryDescription served on that probe is already fully populated (DirectoryId, Name, ShortName, Size, Edition, Alias == DirectoryId, AccessUrl, DnsIpAddrs, VpcSettings with both subnets and their AvailabilityZones, DesiredNumberOfDomainControllers, RegionsInfo, OsVersion, NetworkType) while Stage reads 'Creating' and StageLastUpdatedDateTime is only a fraction of a second after LaunchTime — i.e. the emulator did move Requested -> Creating promptly but then never presents Created/Active to a probing client inside the check's budget. The check derives that budget from the runner's remaining time less a teardown margin (max(1.0, min(3000.0, time_left - 60.0))), so under the 60 s per-check ceiling it is clamped to ~1 s and the probe that follows CreateMicrosoftAD sees a non-terminal stage with no settled value behind it.

Why: a client gets no verdict on the entire Managed-AD-backed group-membership rejection contract, because none of it is reached. Unverified are: that CreateMicrosoftAD mints a DirectoryId matching ^d-[0-9a-f]{10}$ and the directory ends creation in Stage 'Active' rather than Inoperable/Impaired/Failed (and that StageReason explains a non-Active outcome); that EnableDirectoryDataAccess drives DescribeDirectoryDataAccess's DataAccessStatus out of 'Enabling' to exactly 'Enabled' (and that a directory still applying an update refuses the enable with ClientException rather than something else); that the ds-data data plane then stops answering AccessDeniedException; that the first AddGroupMember lands and ListGroupMembers settles on exactly that one member; that a SECOND add of the same member — and of the same member in a different letter case — is refused with HTTP 409 and Error.Code 'ConflictException' whose Message is AWS's duplicate-member sentence, fixed text 'Member already exists in directory ' + ' group.' with the directory id taken from the request between them (no single run's literal directory id is part of the requirement); and that a RemoveGroupMember ClientToken replayed for a DIFFERENT member answers as it first did instead of re-running the call, with the membership read afterwards proving the second call did not execute. A duplicate add that succeeded, a case-insensitive duplicate that slipped through, a mis-worded or mis-coded ConflictException, or an idempotency token that re-ran its call for a different member would all pass today.

Fix: this is not an operation-handler response defect — no ds handler is reported answering wrongly. The owner is the ds directory-stage state machine and its clock-owed-transition contract where it meets the suite's per-check ceiling: either settle/shorten the spans the ds state module applies to the creation chain (Requested -> Creating -> Created -> Active) and to the DataAccessStatus chain (Enabling -> Enabled) so a settled value is observable on the client's FIRST probe after the call that started it — accepting that the transient stages and the refusals that depend on them (DirectoryUnavailableException and friends) stop being observable, and loosening any in-tree suite that pins them — or the harness's per-check budget and the margin this check subtracts from it.
