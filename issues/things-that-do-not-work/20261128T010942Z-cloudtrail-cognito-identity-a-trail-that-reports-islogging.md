# cloudtrail__cognito-identity: a trail that reports IsLogging=true delivers no log file at all, so identity-pool Data events (GetId/GetOpenIdToken) and the logins redaction are never observable

> _Note: this issue was identified against the code base at commit `d27a7d35691220f03cf9c8538f2f1c73cf1a702f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause, the only failing check under this service heading that the replay report marks neither ALREADY FILED nor OWNED.

NOTE ON RELATED WORK: open issue 20261124T165729Z-cloudtrail-cognito-identity-an-advanced-event-selector-naming.md records the SAME check id in its Issue-Trace-Ids, but the replay report does not mark this check as OWNED by it (its stored replay key no longer matches the failing step), so by the report's accounting this check is carried by no issue and is filed here. Open issue 20261029T173328Z-cloudtrail-records-and-delivers-no-audit-record-for.md covers the neighbouring 'no audit record' surface and likewise does not own this check. A fixer should close all of these together if one fix covers them; this filing exists so the check is not left unowned.

Cause 1 of 1: a CloudTrail trail that was created, started and reports IsLogging=true writes ZERO objects to its S3 bucket, so neither management nor data events are ever delivered, and the whole default-off / advanced-selector-on partition for Cognito identity-pool data events has no observable effect.

AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101) — PutEventSelectors takes TrailName (required) plus EventSelectors / AdvancedEventSelectors and echoes the stored selectors in TrailARN/EventSelectors/AdvancedEventSelectors; GetTrailStatus returns IsLogging, LatestDeliveryTime, LatestDeliveryError, LatestDigestDeliveryTime; its refusals are TrailNotFoundException (404, awsQuery code TrailNotFound) and InvalidTrailNameException (400). The DELIVERY and CLASSIFICATION contract itself is recorded behavior only (AWS CloudTrail log-file reference + the Cognito identity-pools CloudTrail page): a logging trail writes GZIP log files (first bytes 1f 8b) under the key prefix AWSLogs/<account-id>/CloudTrail/<region>/<yyyy>/<mm>/<dd>/, whose inflated body is a JSON object with a top-level "Records" list. Management events (here cognito-identity:TagResource) are delivered by a brand-new trail's DEFAULT selector (eventCategory "Management", managementEvent true) with no selector change at all. cognito-identity GetId and GetOpenIdToken are DATA events: withheld while the trail has only the default management selector, and captured once an advanced event selector of {Field: eventCategory, Equals: ["Data"]} + {Field: resources.type, Equals: ["AWS::Cognito::IdentityPool"]} is accepted. A captured record carries eventSource "cognito-identity.amazonaws.com", eventCategory "Data", managementEvent false, and a resources entry of type "AWS::Cognito::IdentityPool" whose ARN is the pool the call addressed (template arn:aws:cognito-identity:<region>:<account-id>:identitypool/<pool-id>) and whose accountId is the caller's account. requestParameters is kept (not nulled) and its `logins` member stays a MAP: the provider-name KEY is preserved (template cognito-idp.<region>.amazonaws.com/<user-pool-id>) while its token VALUE is replaced by the exact fixed literal "HIDDEN_DUE_TO_SECURITY_REASONS"; the presented ID token must appear nowhere in the delivered bytes. Those data events must NOT appear in LookupEvents, which serves management events only, and GetTrailStatus on a trail that has delivered must report LatestDeliveryTime at or after the instant of the last delivered record with no LatestDeliveryError member.

Emulator: every control-plane and data-plane call the check makes SUCCEEDS — CreateUserPool, CreateUserPoolClient, AdminCreateUser, AdminSetUserPassword, InitiateAuth (an IdToken is returned), CreateIdentityPool x2, CreateBucket, PutBucketTagging, PutBucketPolicy, CreateTrail, StartLogging (GetTrailStatus then reports IsLogging=true), GetEventSelectors (DataResources [] and no AdvancedEventSelectors, as AWS defaults), PutEventSelectors (echoes the submitted AdvancedEventSelectors verbatim), GetEventSelectors (reads them back), cognito-identity TagResource, GetId, GetOpenIdToken. But ListObjectsV2 under AWSLogs/<account>/CloudTrail/<region>/ stays EMPTY forever. The check's WARM-UP barrier only needs ONE delivered MANAGEMENT record for cognito-identity:TagResource before it proceeds, and it never arrives, so the check spins on its delivery poll until the harness kills it (reported as "Check timed out after 60.0s"). Because no object exists, nothing downstream is reachable: the Data classification, managementEvent=false, the resources[].type/ARN/accountId entry, the logins-value redaction to "HIDDEN_DUE_TO_SECURITY_REASONS", the token-absence guarantee, the withheld-before-selector absence, the LookupEvents data-event exclusion and GetTrailStatus.LatestDeliveryTime advancing past the marker.

Why: a delivered log file is the ONLY place a data event is observable, so a client cannot distinguish "my selector matched nothing" from "the delivery pipeline is dead" — PutEventSelectors and GetTrailStatus both report healthy. Security tooling that reads identity-pool activity out of the trail bucket sees an account with no federated activity at all; the credential-redaction guarantee is unverifiable, so a consumer cannot confirm that ID tokens are not being written into an audit log; and the default-off/selector-on partition that governs data-event billing is unobservable, so a customer cannot tell enabled from disabled.

Fix: the CloudTrail trail delivery pipeline in the cloudtrail service crate — the S3 log-file writer (gzip a Records batch to AWSLogs/<account>/CloudTrail/<region>/<yyyy>/<mm>/<dd>/ and advance GetTrailStatus.LatestDeliveryTime) and the event-selector evaluator that must pass default-selector management events and advanced eventCategory=Data + resources.type matches — plus the cognito-identity side emitting GetId/GetOpenIdToken as Data events with the AWS::Cognito::IdentityPool resources entry and the logins-value redaction in its requestParameters serializer.
