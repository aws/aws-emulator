# controlcatalog serves an incomplete and rewritten control catalog (4 causes)

> _Note: this issue was identified against the code base at commit `003c8e8353427ede4b0f03e381eab6c52b460652`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetControl

## Description
The catalog data the emulator serves for service `controlcatalog` is neither complete nor verbatim: published control ARNs are absent from the inventory entirely (so the read path answers a not-found instead of the control), the release timestamps on the rows it does hold are emulator-chosen dates rather than the catalog's, and published common-control text is paraphrased. All four causes are the same stored artefact seen through three operations — the seeded control/common-control catalog behind GetControl, ListControls and ListCommonControls. FOUR net-new causes, all on service `controlcatalog`, each a distinct replay step.

All four clusters are reported un-owned by the replay (stub_path empty, owned_by empty). Related OPEN issues that do NOT cover them — none carries these replay keys, and each names different control ARNs and different steps: 20261124T130941Z-controlcatalog-listcontrols-rewrites-published-config-rule-control-text.md (ListControls, steps task#226/250/312/325/469/484/528/552), 20261124T130941Z-controlcatalog-listcommoncontrols-rewords-published-common-control-text-and.md (ListCommonControls, steps task#1/27/35), 20261122T055800Z-controlcatalog-listcontrols-serves-a-divergent-aws-config-configrule.md, 20261122T143633Z-controlcatalog-publishes-no-resource-control-policy-controls-no.md. The GetControl-404 family was filed before and is RESOLVED (20261123T051108Z-controlcatalog-serves-a-synthesized-control-catalog-getcontrol-404s.md, 20261115T014344Z-..., 20261114T092717Z-...), so it covers nothing here: the 404s are back for a further 17 recorded steps.

Cause 1 of 4: GetControl answers 404 for published control ARNs — fixture controlcatalog-catalog-get-control, step task#4 (this cluster also covers task#5 through task#20, 17 steps in all).
AWS: Smithy GetControl — POST /get-control, http code 200; output members Arn @required (@length 34..2048, @pattern ^arn:(aws(?:[-a-z]*)?):(controlcatalog|controltower):[a-zA-Z0-9-]*::control/[0-9a-zA-Z_\-]+$), Name @required ("The display name of the control"), Description @required ("A description of what the control does"), Behavior @required, RegionConfiguration @required, plus Aliases, Severity, Implementation, ParameterRequirementSummary, Parameters, CreateTime, GovernedResources, GovernedProviders. The modeled 404 is ResourceNotFoundException, documented "The requested resource does not exist" — i.e. it is reserved for an ARN that is NOT in the published catalog. Which ARNs the catalog contains is recorded behavior only: the recording shows a published control ARN of the form arn:aws:controlcatalog:::control/<identifier> answering 200 with a fully populated body (for the representative step, Aliases ["CT.EC2.PR.4"], Behavior "PROACTIVE", Severity "CRITICAL", Implementation {"Type":"AWS::CloudFormation::Type::HOOK"}, ParameterRequirementSummary "NONE", Parameters [], GovernedProviders ["AWS"], GovernedResources ["AWS::EC2::SecurityGroup","AWS::EC2::SecurityGroupIngress"], RegionConfiguration {Scope "REGIONAL", DeployableRegions a 34-entry region list}, CreateTime a release instant).
Emulator: answers HTTP 404 for those same ARNs, with none of the response members present (Aliases, Arn, Behavior, CreateTime, Description, GovernedProviders, GovernedResources, Implementation, Name, ParameterRequirementSummary, Parameters, RegionConfiguration and Severity all absent). The 404 is the modeled not-found class, whose message text is AWS's fixed "The requested resource does not exist" — but the status itself is the defect: a catalogued ARN must not take that path at all.
Why: a client that resolves a control it found via ListControls, or that reads a control by a documented ARN/alias (CT.* , SH.*) to show its behavior, severity, governed resources or deployable regions, is told the control does not exist. Control-governance tooling treats that as "the control was withdrawn" and skips enabling or reporting it, so an entire class of published controls silently disappears for 17 distinct recorded lookups.
Fix: the control inventory in the control-catalog state that GetControl's handler looks up — every published control ARN must be present with its full projection; ResourceNotFoundException belongs only to ARNs genuinely absent from the published catalog.
Traces: controlcatalog-catalog-get-control#task#4 (cluster members task#5..task#20).

Cause 2 of 4: GetControl returns an emulator-minted CreateTime — fixture controlcatalog-catalog-get-control, step task#3.
AWS: Smithy GetControl output member CreateTime -> Timestamp, doc "A timestamp that notes the time when the control was released (start of its life) as a governance capability in Amazon Web Services." The value is therefore the control's actual release instant, not a value the emulator may author; the instant itself is recorded behavior only — the recording shows a release date in late 2016 (epoch 1479772800.0).
Emulator: answers 200 — the row exists and every other member matches — but CreateTime is a mid-2021 date (epoch 1623542400), roughly four and a half years later. CreateTime is the sole diverging member, which isolates this from the missing-row fault in cause 1: it is a dating defect in the stored row, and it is a fixed stored value rather than a per-run clock reading.
Why: CreateTime is the only signal for when a governance capability became available, so a client that orders the catalog by release date, windows "controls released since <date>", or reports a control's age gets an answer AWS does not give.
Fix: the CreateTime seeded onto control rows in the control-catalog state (the same rows GetControl projects) — it must come from the catalog's published release date.
Traces: controlcatalog-catalog-get-control#task#3.

Cause 3 of 4: ListControls projects the same wrong release date for control/27lgd3oknluio5kzcl324kr0d — fixture controlcatalog-catalog-list-controls-aws-config-configrule, step task#246.
AWS: Smithy ListControls — POST /list-controls, http code 200, output Controls @required, paginated (NextToken/MaxResults, items=Controls); ControlSummary.CreateTime -> Timestamp with the same "time when the control was released (start of its life)" doc. Recorded behavior only for the value: CreateTime 1479772800.0 for that ARN.
Emulator: answers 200 with the row present but $.Controls[Arn="arn:aws:controlcatalog:::control/27lgd3oknluio5kzcl324kr0d"].CreateTime = 1623542400 — the only diverging key in the whole page.
Hypothesis: this is the same stored row as cause 2 read through the list projection (identical expected 1479772800.0 / actual 1623542400 pair), so one seeding correction may close both — but they are two distinct recorded steps on two operations and both must be re-replayed.
Why: the list projection is what clients page to build a control inventory, so the wrong release date propagates into inventories and date-filtered reports even for clients that never call GetControl.
Fix: the same seeded CreateTime on control-catalog rows, and the ListControls response projection that reads it.
Traces: controlcatalog-catalog-list-controls-aws-config-configrule#task#246.

Cause 4 of 4: ListCommonControls paraphrases published common-control Name/Description — fixture controlcatalog-catalog-list-common-controls, step task#37.
AWS: Smithy ListCommonControls — POST /common-controls, http code 200, output CommonControls @required, paginated (NextToken/MaxResults, items=CommonControls); CommonControlSummary.Name @required ("The name of the common control"), Description @required ("The description of the common control"), Arn @required @pattern ^arn:(aws(?:[-a-z]*)?):controlcatalog:::common-control/[0-9a-z]+$. The published strings are recorded behavior only — the model does not enumerate catalog content, but both members are the catalog's own published text, so neither is emulator-authorable. The recording for this page carries, among others: common-control/4kdrp1fqw2zy6shq95defui2y Description "Define and implement actions to prevent the accidental or malicious loss or theft of assets their recovery. Include notification reporting to the appropriate authorities and stakeholders."; common-control/6rxe3eaojbhyha52wtvahsjxn Description "Define and implement procedures for preventing, managing, and mitigating asset damage, including implementing asset protection mechanisms, assessing the extent of any identified damage, and taking steps to repair or replace the asset."; common-control/6i6o73iaofk1dk6h4rgm6sccd Name "Asset security incident response" and Description "Define and implement procedures for identifying, assessing, and responding to asset-related security incidents..".
Emulator: answers 200 with the same ARNs but rewritten prose — respectively "Protect assets against loss and theft while they are in the organization's custody, report a loss as soon as it is noticed, and recover the asset where it can be recovered.", "Protect assets against damage while they are in the organization's custody, and act on the exposure a damaged asset created.", and Name "Asset-related security incident procedures" with Description "Follow the procedures for a security incident that involves an organizational asset, including reporting it and recording what the response restored." The rewrites are not cosmetic: the published text states what the organization must DEFINE AND IMPLEMENT (including notification reporting to authorities and stakeholders, and assessing/repairing/replacing a damaged asset), and those obligations are dropped.
Why: common-control Name/Description is the text that compliance mappings, console views and audit exports reproduce verbatim; a client that renders or diffs the framework against AWS's catalog shows control language AWS never published and loses stated obligations, so generated evidence misstates the control.
Fix: the common-control rows in the control-catalog state behind the ListCommonControls response projection — Name and Description must be stored exactly as published, not authored.
