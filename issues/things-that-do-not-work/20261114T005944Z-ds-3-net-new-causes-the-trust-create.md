# ds: 3 net-new causes — the trust create/verify/delete flow, the state-machine trust flow and the RemoveRegion/DeleteDirectory leg each reach NO verdict because every clock-owed ds transition settles only after the probe that follows the call

## Description
THREE net-new causes in the ds control plane, all three in one service, grounded in the only failing checks the suite lists under '### ds' that this replay marks neither ALREADY FILED (stub-blocked on DescribeCAEnrollmentPolicy / EnableRadius) nor OWNED by an open issue. ds answers 119/157 behavioral checks in this run, so none of these is a bootstrap gap. A fixer must close all THREE before submitting; each cause carries its own failing check ids.

One mechanism underlies all three, and it is the emulator's, not the harness's: every status transition this crate owes the clock is made observable only by a call made AFTER the span elapses, and the spans are deliberately set so that a caller probing immediately after the call that starts the transition still reads the TRANSIENT value (services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state.rs:116-129 TRANSITION_SPAN = 500 ms, documented as falling due 250-750 ms after the call 'so a caller acting immediately after the create still observes the transient state'; :146-156 DIRECTORY_BUILD_SPAN = 3 s in Creating; :158-168 directory_active_at = now + TRANSITION_SPAN + DIRECTORY_BUILD_SPAN; src/state/directory_deletion.rs:58-111, the Deleting -> Deleted -> record-forgotten chain, one span per step; the trust transitions are materialised the same way by advance_clock). A client that calls, probes once, and then sleeps its poll interval therefore pays ONE FULL POLL INTERVAL per transition. Two to five such legs exhaust the suite's 60 s per-check ceiling before a single assertion runs, so these scenarios are ungraded rather than wrong.

--- Cause 1 of 3: the two-directory trust create/verify/delete HAPPY-PATH flow reaches no verdict (check id ds.e2e-trust-create-verify-delete-flow).
AWS: the state machine is modelled — Smithy com.amazonaws.directoryservice#TrustState = [Creating, Created, Verifying, VerifyFailed, Verified, Updating, UpdateFailed, Updated, Deleting, Deleted, Failed]; DirectoryStage = [Requested, Creating, Created, Active, Inoperable, Impaired, Restoring, RestoreFailed, Deleting, Deleted, Failed, Updating]; CreateTrust input {DirectoryId @required ^d-[0-9a-f]{10}$, RemoteDomainName @required, TrustPassword @required @sensitive, TrustDirection @required} / output {TrustId @pattern ^t-[0-9a-f]{10}$}; VerifyTrust input {TrustId @required} / output {TrustId}; DeleteTrust input {TrustId @required, DeleteAssociatedConditionalForwarder default false} / output {TrustId}; DescribeTrusts output {Trusts, NextToken} with EntityDoesNotExistException (client, httpError 400, members Message + RequestId). So AWS answers each call before the trust settles and exposes the walk through DescribeTrusts; for the wall clock there is recorded behavior only (a real Managed Microsoft AD takes 20-45 minutes to reach Active, which is why clients poll at 15-20 s intervals).
Emulator: no status, code, message or shape divergence is reported — the whole output is 'Error: Check timed out after 60.0s', with no exception frame, the signature of a kill inside a poll sleep. The scenario owes, in order: CreateMicrosoftAD x2 then DescribeDirectories polled for Stage 'Active' at 20 s intervals (2 x 20 s), CreateTrust x2 then DescribeTrusts polled for TrustState in {Created, Verified} at 15 s (2 x 15 s), VerifyTrust then a poll for 'Verified' at 15 s, DeleteTrust x2 then polls until the trusts are gone at 15 s. Every one of those transitions lands after the first probe, so >= 70 s of pure sleeping is owed inside a 60 s ceiling.
Why: a client gets no verdict on the contract the scenario exists to pin — that an Active directory reports non-empty DnsIpAddrs, that CreateTrust mints a ^t-[0-9a-f]{10}$ TrustId and the trust leaves Creating for 'Created', that VerifyTrust drives it to 'Verified', that DeleteTrust removes it from DescribeTrusts, and that a SECOND DeleteTrust on the same id is refused HTTP 400 / Error.Code 'EntityDoesNotExistException' with AWS's wording for that class, 'Trust: <trustId> does not exist : RequestId: <requestId>' — fixed text 'Trust: ' and ' does not exist : RequestId: ', the trust id taken from the request and the RequestId from the response; no single run's literal id belongs in the template. A trust that never changed state, or a deleted trust that kept reading back, passes today.

--- Cause 3 of 3: the RemoveRegion-on-the-primary-Region refusal and its DeleteDirectory control reach no verdict (check id ds.remove-primary-region-denied).
AWS: Smithy RemoveRegion input {DirectoryId @required ^d-[0-9a-f]{10}$}, output {}, errors AccessDeniedException(400), ClientException(400), DirectoryDoesNotExistException(400), DirectoryUnavailableException(400), ServiceException(500), UnsupportedOperationException(400, members Message + RequestId); DeleteDirectory input {DirectoryId @required} / output {DirectoryId}, errors ClientException / EntityDoesNotExistException / ServiceException. Per AWS's RemoveRegion documentation the primary (home) Region cannot be removed by RemoveRegion — it goes away only with the whole directory — and multi-region replication is an Enterprise-edition capability, so a Standard-edition directory is refused on edition alone.
Emulator: no response divergence reported, only 'Check timed out after 60.0s'. Two clock-owed legs at 30 s each — CreateMicrosoftAD then poll DescribeDirectories for 'Active' at 30 s, and DeleteDirectory then poll for 'Deleted' at 30 s — are exactly the ceiling, so the check dies in the second sleep.
Why: a client gets no verdict either on the refusal or on the documented alternative. Ungraded are: that RemoveRegion against a Standard-edition Managed Microsoft AD is refused HTTP 400 / Error.Code 'UnsupportedOperationException' with the edition sentence AWS words for this class, 'Multi-region replication is only supported for AWS Managed Microsoft AD (Enterprise edition) directories. : RequestId: <requestId>' (all fixed text except the RequestId, which is the response's); that the refused call leaves the directory's Stage unchanged and NOT in Deleting/Deleted; and that DeleteDirectory does drive the directory to Stage 'Deleted'. An emulator that silently accepted RemoveRegion on a primary Region, or that never reached 'Deleted', passes today.

Fix: no ds operation handler answers wrongly in any of the three — the owner is this crate's clock-owed-transition contract where it meets a polling client: services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state.rs (TRANSITION_SPAN, DIRECTORY_BUILD_SPAN, directory_active_at), the trust transitions advance_clock materialises, and src/state/directory_deletion.rs's teardown chain. A settled value must be reachable on the client's FIRST probe after the call that starts the transition, across the directory-stage chain (Requested/Creating -> Active, Deleting -> Deleted), the trust state machine (Creating -> Created, Verifying -> Verified, Deleting -> gone) and the data-access/LDAPS toggles — accepting that the transient values and the refusals that depend on them (DirectoryUnavailableException, DirectoryInDesiredStateException) stop being observable and that in-tree suites pinning them must be loosened. This is the transition-span contract decision; it has to be settled rather than left failing.

Traces: ds.e2e-trust-create-verify-delete-flow, ds.state-machine-trust-create-verify-delete-404, ds.remove-primary-region-denied — all verdict 'mismatch', all with detail 'Check timed out after 60.0s', all killed inside a poll helper's time.sleep(interval_s).
