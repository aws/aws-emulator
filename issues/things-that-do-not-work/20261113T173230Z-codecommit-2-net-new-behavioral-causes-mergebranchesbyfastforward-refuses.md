# CodeCommit: 2 net-new behavioral causes — MergeBranchesByFastForward refuses a tag-ref destination as CommitDoesNotExistException, and the IAM codecommit:References git-push authorization path never completes

> _Note: this issue was identified against the code base at commit `9ca58d7cf30a6ec744c8cbd01b69502e157676e2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
MergeBranchesByFastForward

## Description
Two net-new root causes in the codecommit emulator, both grounded in failing behavioral checks of this suite.

Cause 1 of 2: MergeBranchesByFastForward refuses a fully-qualified TAG reference in destinationCommitSpecifier with the wrong exception (failing check: codecommit.merge-branch-tag-name-rejected).
AWS: Smithy (com.amazonaws.codecommit#MergeBranchesByFastForward) models destinationCommitSpecifier (CommitName, required), documented as "The branch, tag, HEAD, or other fully qualified reference used to identify a commit", and targetBranch (BranchName, optional) as "The branch where the merge is applied". The operation models BranchNameIsTagNameException (client, HTTP 400), documented "The specified branch name is not valid because it is a tag name. Enter the name of a branch in the repository." When targetBranch is omitted the destination specifier is what names the branch the merge is applied to, so a destination specifier that resolves into the tag namespace (refs/tags/<tag>, as written by a real `git push origin <tag>`) is a tag name used as a branch name: real AWS answers HTTP 400 BranchNameIsTagNameException with the message "The specified branch name is not valid. Branch names cannot be tag names. Provide a valid branch name, and then try again." — that sentence is entirely FIXED text for this error class; it interpolates nothing from the request or from state.
Emulator: answers HTTP 400 CommitDoesNotExistException instead (replay: "destSpecifier got='CommitDoesNotExistException'"). The destination specifier is resolved with resolve_commit before any branch/tag classification happens, and that resolver does not see the repository's tag namespace, so a `refs/tags/<tag>` reference the repository really holds (the check pushed the tag over git and the push succeeded) reads as a nonexistent commit. A secondary divergence rides on the same cause: on the one path where the handler DOES raise BranchNameIsTagNameException it words it as emulator prose ("the name <target> is a tag name in the repository <repo>, not a branch name"), not AWS's fixed sentence above, so even resolving the ref correctly would still fail the message requirement.
Why: a client that classifies merge refusals by exception code sees "the commit does not exist" where AWS says "that is a tag, not a branch". Retry/repair logic keyed on BranchNameIsTagNameException never fires, and tooling that resolves tags as commit specifiers (documented as supported) cannot address any commit by its tag at all on this operation.
Fix: the MergeBranchesByFastForward handler's specifier resolution and its tag classification, plus the shared reference resolver the handler calls for tags, plus the BranchNameIsTagNameException message template.
Traces: codecommit.merge-branch-tag-name-rejected.

Cause 2 of 2: the IAM-conditioned git-push authorization path (codecommit:GitPush + codecommit:References) never completes — both real-git branch-protection checks exhaust their budget with no assertion reached (failing checks: codecommit.branch-protection-policy-denies-a-real-git-push-to-main, codecommit.git-push-deny-without-the-null-reference-guard-blocks-every-branch).
AWS: recorded behavior only (no Smithy modelling: this is the git transport plus IAM policy evaluation). An assumed role holding Allow codecommit:GitPull/GitPush on the repository can clone the announced cloneUrlHttp with the `aws codecommit credential-helper` credential helper; with the documented Deny on codecommit:GitPush conditioned on StringEqualsIfExists codecommit:References = refs/heads/main plus Null codecommit:References = false attached, `git push origin main` is REFUSED by the remote (git exits non-zero, main's tip unchanged) while `git push origin feature` still lands and GetBranch('feature') reports the pushed commit; dropping the Null guard widens the Deny to every branch, and removing the Deny lets the identical push to main succeed.
Emulator: neither check ever reaches that comparison — each ends "Check timed out after 60.0s" while still inside the bounded clone/push retry loop against the announced cloneUrlHttp, so the emulator produces no usable git transport for a SigV4/credential-helper principal and the References-conditioned decision is never observable. Open issues 20261025T040000Z-codecommit-announced-clone-url-is-served-with-an-untrusted-certificate.md and 20261107T223907Z-codecommit-the-announced-cloneurlhttp-is-served-over-tls.md report the announced clone URL's TLS certificate; neither carries these two checks' replay keys, and neither covers the IAM authorization half (a Deny on GitPush scoped by codecommit:References must refuse one branch and only that branch).
Why: a client cannot verify or exercise CodeCommit branch protection at all. Every git-based workflow against the emulator hangs instead of being allowed or refused, and a policy that AWS would honour as a one-branch Deny is indistinguishable here from an unreachable endpoint — a user testing branch protection gets a false "works"/"hangs" signal rather than a refusal.
Fix: the git transport the announced cloneUrlHttp serves (it must be reachable by a principal using SigV4 git credentials) and the authorization hook that evaluates codecommit:GitPush with the codecommit:References condition key per pushed reference, including the Null-guard semantics for the receive-pack call that carries no References key.
Traces: codecommit.branch-protection-policy-denies-a-real-git-push-to-main, codecommit.git-push-deny-without-the-null-reference-guard-blocks-every-branch.
