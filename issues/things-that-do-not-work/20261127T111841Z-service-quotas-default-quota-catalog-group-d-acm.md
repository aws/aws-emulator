The model describes the SHAPE of a ServiceQuota (ServiceCode, ServiceName, QuotaArn, QuotaCode, QuotaName, Value, Unit, Adjustable, GlobalQuota, UsageMetric, Period, Description) but does NOT enumerate the catalog rows, so the row set and each row's field values are "recorded behavior only": every recording shows AWS answering HTTP 200 with the COMPLETE published AWS-default quota set for the requested ServiceCode, each row carrying QuotaCode, QuotaName, QuotaArn (AWS-default form with an empty account segment), Value, Unit, Adjustable, GlobalQuota and a populated Description (and Period/UsageMetric where the row is a request-rate quota).

Emulator, in general: HTTP 200 (the status matches; the divergence is entirely in the body) but the Quotas list omits published rows for the requested ServiceCode, and some rows it does return omit ServiceQuota.Description. No error is raised and no NextToken continuation hides the rows, so this is a catalog-seed gap, not a serializer, pagination or routing fault.

Why, in general: ListAWSDefaultServiceQuotas is the discovery API for AWS-published limits. A client that walks it sees a service with fewer limits than AWS publishes (or limits with no human-readable description), so quota-inventory tooling, limit dashboards and "am I near my quota" checks silently under-report, and GetAWSDefaultServiceQuota for an omitted (ServiceCode, QuotaCode) pair cannot be reached at all.

Fix, in general: the seeded default-quota map in crate::state of the service-quotas crate (plus Description population for rows it already seeds), consumed by the ListAWSDefaultServiceQuotas handler at services/service-com-amazonaws-servicequotas-servicequotasv20190624/src/ops/list_aws_default_service_quotas.rs.
