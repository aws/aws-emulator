# redshift static reference catalogs are not served as AWS publishes them: DescribeEventCategories and DescribeReservedNodeOfferings

> _Note: this issue was identified against the code base at commit `ff49842cf7656b5a010943ef9d0fd100550d134a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEventCategories

## Description
2 net-new causes, both in the same place: the two Redshift read-only operations whose response body is a fixed, account-independent reference catalog published by the service (not derived from any request or from emulator state) return a body the emulator synthesizes instead of that catalog. Both replay at HTTP 200 with a well-formed query-protocol envelope, so a client cannot detect the substitution; it just reads a catalog that is empty or that describes node types and terms AWS does not offer.

Cause 1 of 2 - DescribeEventCategories returns no event-category maps at all.
AWS: Smithy: DescribeEventCategories (input DescribeEventCategoriesMessage, optional SourceType; output EventCategoriesMessage.EventCategoriesMapList of EventCategoriesMap), EventCategoriesMap{SourceType: "The source type, such as cluster or cluster-snapshot, that the returned categories belong to", Events: EventInfoMapList}, EventInfoMap{EventId, EventCategories, EventDescription, Severity: "Values: ERROR, INFO"}; the operation models no errors. With no SourceType filter AWS returns one EventCategoriesMap per Redshift event source type, each carrying that source type's complete EventInfoMap list. Recorded behavior: the response carries EventCategoriesMap entries at indices 0..5 (six source types, the first being SourceType 'cluster'), and each EventInfoMap carries an EventId of the documented REDSHIFT-EVENT-<n> form (REDSHIFT-EVENT-2000, -2001, -3000, -3001, -3014, -3015, -3016, -4000, -4502, ...), a Severity of INFO or ERROR, an EventCategories list naming the category ('management', 'monitoring', 'pending', 'security', ...), and an EventDescription that is the service's fixed template text with angle-bracket placeholders left in place, e.g. 'Cluster <cluster name> created at <time in UTC>.' for REDSHIFT-EVENT-2000 and 'Cluster <cluster name> deleted at <time in UTC>.' for REDSHIFT-EVENT-2001. The EventId values, their category assignment, their severity and their description templates are the requirement; they are service constants, not per-run values.
Emulator: 200 with an EventCategoriesMapList that does not contain those maps - every expected index is reported 'missing' with no counterpart value, i.e. $.DescribeEventCategoriesResponse.DescribeEventCategoriesResult.EventCategoriesMapList.EventCategoriesMap[0] through [5] are absent, so the list is served empty (or short of all six source types).
Why: a client that enumerates event categories to build a subscription gets nothing to choose from. Console-style and IaC flows that validate a CreateEventSubscription/ModifyEventSubscription EventCategories value against this list conclude that no category exists and either refuse the subscription or send an unvalidated value; monitoring tooling that maps an incoming EventId to a severity/category has no table to map with.
Fix: the DescribeEventCategories handler in the redshift service crate - it needs the static event-category catalog (source type -> event-info list, with the documented EventIds, categories, severities and description templates) as a built-in constant, and must honour the optional SourceType input as a filter over it.
Traces: redshift-catalog-describe-event-categories#task#1.

Cause 2 of 2 - DescribeReservedNodeOfferings serves a generated single-node-type offering list instead of the published offering catalog.
AWS: Smithy: DescribeReservedNodeOfferings (input ReservedNodeOfferingsMessage{ReservedNodeOfferingId, MaxRecords, Marker}, output ReservedNodeOfferingsMessage{Marker, ReservedNodeOfferings: ReservedNodeOfferingList}, paginated Marker/Marker/ReservedNodeOfferings/MaxRecords; errors DependentServiceUnavailableFault, ReservedNodeOfferingNotFound 404, UnsupportedOperation); ReservedNodeOffering{ReservedNodeOfferingId "The offering identifier", NodeType, Duration (seconds), FixedPrice, UsagePrice, CurrencyCode, OfferingType "The anticipated utilization of the reserved node, as defined in the reserved node offering", RecurringCharges, ReservedNodeOfferingType}. AWS returns the region's published offering catalog: one entry per (node type, term, payment option) combination it actually sells, with the offering's own stable ReservedNodeOfferingId - the same id is returned on every call and is what PurchaseReservedNodeOffering takes. Recorded behavior: 60 offerings at indices 0..59 spanning several node types (rg.large, rg.xlarge, ... alongside dc2 types) and both the 1-year and 3-year terms (Duration '31536000' and '94608000'), with OfferingType values 'All Upfront', 'No Upfront' and 'Partial Upfront', ReservedNodeOfferingType 'Regular', CurrencyCode 'USD', and FixedPrice/UsagePrice/RecurringCharges consistent with the payment option (e.g. an All Upfront 3-year rg.large offering with FixedPrice '3743.6', UsagePrice '0.0' and an Hourly RecurringCharge of '0.0'; a No Upfront 3-year rg.xlarge offering with FixedPrice '0.0' and an Hourly RecurringCharge). The requirement is that the catalog covers the node types and terms the service offers and that each offering's id is stable; the specific prices and ids of any one recording are that region's catalog values, not part of the template.
Emulator: 200 with a wholly different, synthesized list - every expected index is reported as not matching, and the entries the emulator does return are all NodeType 'dc2.large' with Duration '31536000' only, carrying ReservedNodeOfferingIds it generated (e.g. '0d99b00e-0f97-9735-3b0d-57239e32baa9' at index 0 where the recording has 'ba77a482-beaa-4bf0-a91d-38edd554c558', '87bf7fe3-d599-c4d4-3b15-60068625449d' at index 1) with prices unrelated to the offering catalog. No 3-year (94608000) term and no non-dc2 node type appears.
Why: a client pricing or purchasing reserved nodes cannot find an offering for the node type or term it runs - any ra3/rg/3-year selection comes back empty - and a PurchaseReservedNodeOffering built from a previously read ReservedNodeOfferingId does not resolve, because the ids are generated rather than the catalog's stable identifiers. Cost-planning code that joins FixedPrice/UsagePrice/RecurringCharges per payment option reads numbers that do not correspond to any real offering.
Fix: the DescribeReservedNodeOfferings handler in the redshift service crate - replace the generated offering list with a built-in offering catalog keyed by (NodeType, Duration, OfferingType) holding stable ReservedNodeOfferingIds, have the ReservedNodeOfferingId input select from it (404 ReservedNodeOfferingNotFound when absent) and have PurchaseReservedNodeOffering resolve against the same table.
Traces: redshift-catalog-describe-reserved-node-offerings#task#1.

Not the same as the open issue 20261122T081123Z-redshift-reports-generated-values-instead-of-the-request.md, which covers values the emulator generates in place of values supplied in the REQUEST (cluster Endpoint.Port, snapshot-copy-grant KmsKeyId); these two causes are service-published reference data that no request supplies, and that issue does not carry their replay keys.
