# lambda__lexv2-models__lexv2-runtime: 4 net-new causes — RecognizeText never invokes the alias's Lambda code hook, never refuses a malformed hook reply (DependencyFailedException) or a hook with no attached function (ValidationException), and ignores an intent's input-context gate

> _Note: this issue was identified against the code base at commit `fff8505842aad03b204d6100e6a2dc09c6204c11`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RecognizeText

## Description
The emulator's Lex V2 runtime now matches intents, but the entire Lambda code-hook leg of a turn is missing: no function is ever called, so nothing the hook would decide (messages, sessionState, intent state, active contexts) happens, and the two refusals that only exist because a hook exists are never produced. Four independent causes; all four must be closed before this issue is submitted.

Cause 1 of 4: RecognizeText never invokes the bot alias's Lambda code hook, so a turn carries nothing the function would have written.
AWS: Smithy lexv2-runtime `RecognizeText` — POST /bots/{botId}/botAliases/{botAliasId}/botLocales/{localeId}/sessions/{sessionId}/text, 200, output `messages` (0..10), `sessionState`, `interpretations` (0..5). When the alias's botAliasLocaleSettings for the addressed localeId carry a codeHookSpecification.lambdaCodeHook naming a function, and the matched intent has dialogCodeHook and/or fulfillmentCodeHook enabled, Lex synchronously invokes that function inside the turn and applies the sessionState and messages it returns. Recorded behaviour of the event Lex sends: `messageVersion` is "1.0"; `invocationSource` is "DialogCodeHook" on the dialog pass and "FulfillmentCodeHook" on the fulfillment pass (both happen, in that order, on a turn that fulfills); the event carries the live `sessionState` (including sessionAttributes the caller sent), `interpretations` with each slot's resolvedValues, and `sentimentResponse` only when the alias's sentimentAnalysisSettings enable detection. A Close reply with intent.state Fulfilled leaves the turn's sessionState.intent.state == "Fulfilled" (and "Failed" for a Failed close); a reply's messages are returned as the turn's `messages`; sessionAttributes the function writes are readable on the response and on the next GetSession. Each locale's own codeHookSpecification function is the one invoked for that locale.
Emulator: the function is never called. The turn comes back 200 with `messages: []`, `sessionState.dialogAction.type: "Close"`, `sessionState.intent.state: "ReadyForFulfillment"` (never "Fulfilled"/"Failed"), and sessionAttributes holding only what the caller sent — the hook's own keys are absent (replay shows the hook trail as `{}`, a `labels` key missing entirely, and both the dialog and fulfillment hook reporting `(None, None)` for a per-locale function). Nothing is written to the function's CloudWatch Logs group either, which is how the "skips the function" checks observe it.
Why: every client that puts business logic in a Lex code hook — slot validation, dynamic prompts, fulfillment, session bookkeeping, context activation — sees its function silently skipped and a half-finished turn that reports ReadyForFulfillment forever. The intent never settles, so a conversation driven by the response's intent.state loops.
Fix: the lexv2-runtime dialog engine behind RecognizeText (and RecognizeUtterance, which shares it): it must resolve the alias/locale codeHookSpecification, build and send the Lex V2 code-hook event (messageVersion 1.0, invocationSource per pass, sessionState, interpretations with resolvedValues, sentimentResponse only when enabled), invoke the named Lambda, and merge the returned sessionState/messages into the turn before serializing.

Cause 2 of 4: a code-hook reply Lex cannot read is served as a successful turn instead of being refused DependencyFailedException.
AWS: `RecognizeText` models DependencyFailedException with HTTP 424. When the invoked function returns something that is not a well-formed Lex V2 response — a bare JSON scalar instead of an object, or a dialogAction missing its required `type` — Lex refuses the turn with code `DependencyFailedException` and a message whose fixed lead is `Invalid Lambda Response: Received invalid response from Lambda: ` followed by the parser's account of what it could not read; that trailing part is derived from the actual reply and names the offending member (for a typeless dialogAction it names `type`). The refused turn must not leave the session holding a fulfilled intent.
Emulator: the call returns HTTP 200 with a normal turn body — `messages: []`, `sessionState.dialogAction.type: "Close"`, `sessionState.intent.state: "ReadyForFulfillment"` — so no 424 and no message is produced at all. (This is downstream of Cause 1 but is its own requirement: once the hook is invoked, its reply must be validated and a bad one converted into this refusal rather than ignored.)
Why: a client with a buggy hook is told its turn succeeded. It commits a conversation state Lex would never have accepted, and loses the one diagnostic AWS gives it — the parser detail naming the member the function omitted.
Fix: the code-hook reply deserializer/validator in the lexv2-runtime dialog engine: parse the Lambda payload against the Lex V2 code-hook response shape and map any parse/shape failure to DependencyFailedException (424) with the lead above plus the parser detail, leaving the session unchanged.

Cause 3 of 4: a fulfillment code hook with no Lambda attached to the alias/locale is served instead of refused ValidationException.
AWS: when the matched intent's fulfillmentCodeHook is enabled but the bot alias's botAliasLocaleSettings for that locale carry no codeHookSpecification.lambdaCodeHook, `RecognizeText` is refused with code `ValidationException` (HTTP 400) and the message `Cannot call FulfillmentCodeHook for Intent <intentName>. BotAlias/LocaleId <botAliasName>/<localeId> doesn't have an associated Lambda Function.` — the fixed text is `Cannot call FulfillmentCodeHook for Intent `, `. BotAlias/LocaleId `, `/` and ` doesn't have an associated Lambda Function.`; the variable parts are the matched intent's name, the alias's botAliasName and the requested localeId, all taken from the request and the emulator's own state. Because the turn is refused, no session is created: a following GetSession for that sessionId answers ResourceNotFoundException.
Emulator: the turn is answered HTTP 200 with intent `WaterPlants` in state `ReadyForFulfillment`, dialogAction Close and empty messages — the missing-function precondition is never checked.
Why: a misconfigured alias looks healthy. A client never learns that it forgot to attach the function, and it also gets a phantom session the refusal should not have created.
Fix: a precondition check in the RecognizeText fulfillment path, applied before any session is written — resolve the alias/locale codeHookSpecification when the intent's fulfillmentCodeHook is enabled and refuse with the ValidationException above when no lambdaCodeHook is present.

Cause 4 of 4: an intent's input-context gate is ignored, so a gated intent matches while its context is inactive.
AWS: an intent that declares an inputContext is only eligible while that context is active in the session's activeContexts (contexts become active because a previous turn's code hook or intent returned them, with a turnsToLive/timeToLive budget). With the context inactive, the gated utterance must not match the gated intent — the turn interprets as `FallbackIntent`. Only after the hook activates the context does the same utterance reach the gated intent.
Emulator: with the context inactive the gated utterance matched `{'name': 'PrintLabel', 'slots': {}, 'state': 'ReadyForFulfillment', 'confirmationState': 'None'}` instead of FallbackIntent — intent eligibility is computed without consulting activeContexts, and activeContexts comes back `[]` in every turn.
Why: context-gated dialog design is the standard way to stop an intent firing out of order. Here it never gates anything, so a client's conversation can jump straight into a step it was supposed to be locked out of — a correctness and authorization-shaped divergence, not a cosmetic one.
Fix: the intent-matching stage of the lexv2-runtime dialog engine: filter candidate intents by their inputContexts against the session's activeContexts before NLU scoring, fall back to FallbackIntent when every candidate is gated out, and maintain activeContexts (set by a hook/intent's outputContexts, decremented/expired by turnsToLive/timeToLive) in the session state it serializes.

## Steps to Reproduce
Common setup for all four causes: create a Lambda function and its execution role; create a Lex V2 bot with a DRAFT en_US locale, an intent with sample utterances, and build the locale; create a bot version and a bot alias.

Cause 1: attach the function to the alias via CreateBotAlias/UpdateBotAlias botAliasLocaleSettings[en_US].codeHookSpecification.lambdaCodeHook, enable the intent's dialogCodeHook and fulfillmentCodeHook, and have the function echo event['messageVersion']/event['invocationSource'] (and append to sessionAttributes) and return a Close with intent.state Fulfilled plus one message. Call RecognizeText with an utterance that matches the intent — observe messages: [], intent.state 'ReadyForFulfillment', none of the hook's sessionAttributes, and no CloudWatch Logs output for the function. Repeat with the alias's sentimentAnalysisSettings enabled and with a second locale having its own function: neither event is ever delivered.

Cause 2: with the function attached as above, make it return a bare JSON string (and, in a second run, a dialogAction object with no 'type'). Call RecognizeText — observe HTTP 200 and a normal turn instead of 424 DependencyFailedException whose message starts 'Invalid Lambda Response: Received invalid response from Lambda: '. Then GetSession and confirm the session must not hold a Fulfilled intent.

Cause 3: enable the intent's fulfillmentCodeHook but leave the alias's botAliasLocaleSettings[en_US] with NO codeHookSpecification.lambdaCodeHook. Call RecognizeText with a matching utterance — observe HTTP 200 instead of 400 ValidationException 'Cannot call FulfillmentCodeHook for Intent <intentName>. BotAlias/LocaleId <botAliasName>/en_US doesn't have an associated Lambda Function.', then GetSession for the same sessionId and observe a session exists where AWS answers ResourceNotFoundException.

Cause 4: declare an intent with an inputContext (e.g. 'returnOpen') and a second intent whose hook returns that context as an outputContext. Call RecognizeText with the gated utterance before the context is activated — observe the gated intent matching instead of FallbackIntent, and activeContexts: [] in the response.
