# amplify: 2 net-new causes — a Lambda-hosted DNS forwarder cannot open /etc/resolv.conf (no sandbox filesystem), and CreateDomainAssociation lands in FAILED with no certificateVerificationDNSRecord

> _Note: this issue was identified against the code base at commit `0e14ec34ba796ebb423716588b97f90ad61f6019`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDomainAssociation

## Description
Two independent root causes, both grounded in failing behavioral checks the suite lists under `### amplify`. Neither is marked ALREADY FILED or OWNED, and no open amplify issue covers them (the closest open ones — 20261111T130904Z-amplify-2-net-new-causes-app-defaultdomain-is--r2.md, 20261121T032742Z-amplify-the-branch-hosting-host-composed-from-app.md, 20261109T143214Z-amplify-s3-every-s3-sourced-deployment-check-stops.md — are all about the published branch/App.defaultDomain host and own the other failures in this run; these two causes are about DNS resolution from a Lambda sandbox and about the custom-domain lifecycle).

Cause 1 of 2: a function invoked in this emulator has no sandbox filesystem, so no code can read /etc/resolv.conf or learn its resolver.
Failing check ids: amplify.branch-default-domain-a-query-answers-the-hosting-addresses, amplify.subdomain-cname-resolves-to-the-distribution-and-an-unconfigured-prefix-is-rejected-with-nxdomain.
AWS: recorded behavior only (the Lambda execution-environment filesystem is not described by the Smithy model). In AWS Lambda the function runs in a sandbox with a POSIX filesystem: /etc/resolv.conf exists and names at least one `nameserver`, and the function can open a TCP connection to port 53 on that address. The recordings these checks replay show a python3.12 handler doing exactly `open("/etc/resolv.conf")` and then `socket.create_connection((server, 53))`, and returning `{"ok": true, "reply": <base64 DNS message>}`.
Emulator: the handler's `open("/etc/resolv.conf")` raises, and the function returns `{'ok': False, 'error': 'OSError: [Errno 38] a Lambda function in this emulator has no host filesystem to reach'}`. The fixed text of that message is the emulator's own (`a Lambda function in this emulator has no host filesystem to reach`, errno 38/ENOSYS); the only variable part is the path the handler opened. No AWS error code or status is involved — the invoke itself succeeds and the payload reports the failure — so the divergence is the absence of the filesystem, not a wire error.
Why: any client whose function code touches the filesystem of its own sandbox, or that resolves a name through the resolver named in /etc/resolv.conf, fails inside the emulator even though the same code works on AWS. In particular nothing in the emulator can be exercised through DNS from a function, so the whole Amplify default-domain/subdomain DNS surface is unverifiable from the data plane.
Fix: the Lambda invoke runtime's execution-environment setup — it must present the function a filesystem containing at least /etc/resolv.conf with a `nameserver` line pointing at a resolver the sandbox can actually reach on TCP/UDP 53, and that resolver must answer for the emulator's own hosted zones.
Traces: amplify.branch-default-domain-a-query-answers-the-hosting-addresses (query for the branch default-domain host `<branch-hash>.<appId>.<suffix>.` A record); amplify.subdomain-cname-resolves-to-the-distribution-and-an-unconfigured-prefix-is-rejected-with-nxdomain (query for `www.<domain>.` CNAME).

Cause 2 of 2: CreateDomainAssociation reports domainStatus FAILED with an ACM "additional verification required" statusReason and never populates certificateVerificationDNSRecord, so the custom-domain lifecycle cannot proceed.
Failing check id: amplify.domain-association-verification-record-is-served-by-the-zone-name-servers.
AWS: Smithy (com.amazonaws.amplify) — DomainAssociation.domainStatus is a required enum whose values include CREATING, REQUESTING_CERTIFICATE, PENDING_VERIFICATION, PENDING_DEPLOYMENT, AWAITING_APP_CNAME, AVAILABLE and FAILED; DomainAssociation.certificateVerificationDNSRecord is "The DNS record for certificate verification" (@length 0..1000); SubDomain.dnsRecord is required and is "The DNS record for the subdomain". For an AMPLIFY_MANAGED certificate on a domain the caller controls, AWS moves the association CREATING -> REQUESTING_CERTIFICATE -> PENDING_VERIFICATION and, while in the verification phase, returns certificateVerificationDNSRecord as a three-field record `<owner> CNAME <target>` whose owner is a name under the associated domain and whose target's first label starts with `_` (the ACM validation target). Each subDomains[].dnsRecord likewise resolves to `<prefix> CNAME <hosting target>` rather than staying a placeholder.
Emulator: GetDomainAssociation returns, immediately and terminally, `domainStatus: 'FAILED'` with `statusReason: 'We require additional verification to request a certificate for one or more domain names in this request. The following page describes this in more detail: https://docs.aws.amazon.com/acm/latest/userguide/troubleshooting-failed.html#failed-additional-verification-required'`, `certificateVerificationDNSRecord` absent entirely, and `subDomains: [{..., 'verified': False, 'dnsRecord': 'www CNAME <pending>'}]` — the literal token `<pending>` as the record target. In that message the entire sentence is fixed text copied from ACM's additional-verification failure; nothing in it is derived from the request, and the request here is an ordinary association for a domain under a hosted zone the account owns, which AWS does not refuse that way. The `www` in the dnsRecord is the request's subDomainSettings prefix; `<pending>` is a placeholder the emulator never replaces.
Why: a client following the documented third-party/Route 53 custom-domain flow polls GetDomainAssociation for certificateVerificationDNSRecord, publishes that CNAME in its zone, and waits for AVAILABLE. Against the emulator the poll never yields a record, the status is already terminal FAILED, and the subdomain record is an unusable placeholder, so no custom domain can ever be brought up and any error handling keyed on FAILED fires spuriously.
Fix: the CreateDomainAssociation/GetDomainAssociation handler and the domain-association state machine — mint a validation record at association time, expose it as certificateVerificationDNSRecord, drive domainStatus through the modeled non-terminal states, fill subDomains[].dnsRecord with the real hosting target, and reserve FAILED + the ACM additional-verification statusReason for inputs that actually warrant it.
Traces: amplify.domain-association-verification-record-is-served-by-the-zone-name-servers (CreateDomainAssociation for `<label>.<delegated apex>` with subDomainSettings [{prefix: www, branchName: <branch>}], then GetDomainAssociation polled for up to 420 s).

Cause 1 — expected: the invoked forwarder returns {"ok": true, "reply": <base64 DNS reply>} after reading a `nameserver` line from /etc/resolv.conf and exchanging one DNS message over TCP/53.
Actual (both checks): AssertionError: the forwarder could not exchange the query for '<name>.': {'ok': False, 'error': 'OSError: [Errno 38] a Lambda function in this emulator has no host filesystem to reach'} — raised at the `assert body["ok"]` in each check's _resolve().

Cause 2 — expected: GetDomainAssociation eventually returns a non-terminal domainStatus (CREATING/REQUESTING_CERTIFICATE/PENDING_VERIFICATION) together with certificateVerificationDNSRecord = '<owner under the domain> CNAME <_-prefixed validation target>', and subDomains[].dnsRecord naming the real hosting target.
Actual: AssertionError: no verification record was returned: {'domainAssociationArn': 'arn:aws:amplify:<region>:<account>:apps/<appId>/domains/<domain>', 'domainName': '<domain>', 'enableAutoSubDomain': False, 'domainStatus': 'FAILED', 'statusReason': 'We require additional verification to request a certificate for one or more domain names in this request.
