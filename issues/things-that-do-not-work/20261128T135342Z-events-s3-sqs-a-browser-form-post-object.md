# events__s3__sqs: a browser form POST Object upload produces no `Object Created` event with reason "POST Object", so the POST-scoped rule never fires and reason-scoped rules are not disjoint

> _Note: this issue was identified against the code base at commit `d0d4667ab363cbe19c93df6dd56832f68085ac3e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PostObject

## Description
Cause 1 of 1: a POST Object (browser HTML form / multipart-form-data) upload into an EventBridge-enabled bucket does not produce an `Object Created` notification carrying `detail.reason = "POST Object"`, so an EventBridge rule scoped to that reason literal never receives anything and the check cannot complete.

AWS: S3's EventBridge integration is documented to emit, for a bucket with `NotificationConfiguration.EventBridgeConfiguration` set, a `detail-type` of `Object Created` on `source` `aws.s3`, whose `detail.reason` names the API that created the object — one of `PutObject`, `POST Object`, `CopyObject` or `CompleteMultipartUpload` (https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventBridge.html). The creating call here is POST Object (https://docs.aws.amazon.com/AmazonS3/latest/API/API_PostObject.html): a SigV4-signed `multipart/form-data` POST to the bucket endpoint, whose `policy`/`x-amz-signature`/`x-amz-credential`/`x-amz-date` form fields are the request's authentication and whose `success_action_status=201` makes the success status HTTP 201. POST Object is not an SDK-modelled operation — there is no Smithy shape for it — so for the wire form and the `"POST Object"` reason literal this is recorded/documented behavior only. The reason literal is fixed text; the bucket name, object key and content length in the event detail are values taken from the request and from stored state. AWS therefore delivers that one event ONLY to a rule whose pattern names `reason: ["POST Object"]`, and delivers nothing for it to a rule whose pattern names `reason: ["PutObject"]`.

Emulator: the check reaches its harness budget and is reported `Error: Check timed out after 60.0s` — a poll that waits for an expected delivery never becomes satisfied. The check's earlier beats are its own positive controls (a plain `PutObject` on the same bucket is confirmed to reach the `PutObject`-scoped rule with `detail.reason == "PutObject"`, and the `POST Object`-scoped queue is confirmed empty for it), so the unsatisfied wait is the one for the form upload's `Object Created` event on the `POST Object`-scoped rule. Two outcomes are consistent with the observation and both are the same defect: either the POST-to-bucket-endpoint form upload is not served as POST Object at all (so no object is created and no event is emitted), or it creates the object but the emitted `Object Created` event carries `reason` `"PutObject"` instead of `"POST Object"`, which would route it to the wrong rule. Hypothesis: the S3 request router has no POST-on-bucket (form upload) route, so the object-creation notification path is only ever entered from the PutObject handler and the `reason` field is effectively hard-wired to `PutObject`.

Why: a client that relies on `detail.reason` to distinguish how an object was created — the documented way to separate browser/presigned form uploads from SDK `PutObject` writes, from server-side copies, and from multipart completions — gets silently wrong routing. A rule scoped to `reason: ["POST Object"]` never fires, so a pipeline that only processes form uploads processes nothing; and if the event is instead stamped `PutObject`, a rule scoped to `reason: ["PutObject"]` receives an upload it was written to exclude, so the two reason-scoped rules are no longer disjoint and the same object is handled by the wrong consumer. Browser direct-to-S3 upload flows, which are exactly what POST Object exists for, are the ones that break.

Fix: S3's object-creation request routing and its EventBridge notification emission. The bucket-level `POST /` multipart/form-data entry point must be routed and served as POST Object (policy/signature validation, `success_action_status` honoured, `201` on success, the object readable by `HeadObject` with the posted content length), and the notification the creation emits must carry the `reason` of the API that actually served it rather than a constant, so `Object Created` from a form POST reads `"POST Object"`. ## Evidence
Expected (AWS): the SigV4-signed multipart/form-data POST of key `<prefix>via-post-<suffix>.bin` to the bucket endpoint answers HTTP 201 (per `success_action_status=201`); `HeadObject` on that key reports `ContentLength` equal to the posted payload length; the EventBridge rule whose pattern is {"source":["aws.s3"],"detail-type":["Object Created"],"detail":{"bucket":{"name":[<bucket>]},"reason":["POST Object"]}} receives exactly one event, with `detail.reason == "POST Object"` (fixed text) and `detail.bucket.name == <bucket>` / `detail.object.key == <the posted key>` (values from the request); and the sibling rule whose pattern names `reason: ["PutObject"]` receives NOTHING for that upload, its queue depth staying 0 across a hold of 3x the measured S3->EventBridge->SQS latency, while a subsequent plain `PutObject` on the same bucket still reaches it (proving the empty leg was a filter decision, not a dead path).

Actual (emulator): the check never completes — the suite reports `[mismatch] events__s3__sqs.a-post-object-upload-is-withheld-from-a-putobject-scoped-rule` / `Error: Check timed out after 60.0s`. The bounded poll waiting for the form upload's `Object Created` event on the `POST Object`-scoped rule is never satisfied, so no event with `detail.reason == "POST Object"` is ever delivered for a POST Object upload. The check's own positive controls rule out the alternative explanations: the bucket reports an `EventBridgeConfiguration` after it is set, and a plain `PutObject` on the same bucket is delivered to the `PutObject`-scoped rule with `detail.reason == "PutObject"` while the `POST Object`-scoped queue stays empty for it.

## Steps to Reproduce
1. Create a bucket and set `PutBucketNotificationConfiguration` with `NotificationConfiguration={"EventBridgeConfiguration": {}}`; confirm `GetBucketNotificationConfiguration` reports `EventBridgeConfiguration`.
2. Create two SQS queues and give each a policy allowing `sqs:SendMessage` to principal `events.amazonaws.com` for `aws:SourceArn` ArnLike `arn:*:events:<region>:<account>:rule/*`.
3. Create two EventBridge rules on the default bus, identical except for the reason operand, and point each at one queue via `PutTargets`:
   - rule A: {"source":["aws.s3"],"detail-type":["Object Created"],"detail":{"bucket":{"name":[<bucket>]},"reason":["PutObject"]}}
   - rule B: same, but "reason":["POST Object"]
4. Positive control: `PutObject` an object under the bucket. Rule A's queue receives one `Object Created` event with `detail.reason == "PutObject"`; rule B's queue stays empty.
5. Subject: build a SigV4 POST Object policy for the bucket (conditions: {"bucket": <bucket>}, ["starts-with","$key",<prefix>], x-amz-algorithm/x-amz-credential/x-amz-date, {"success_action_status":"201"}, ["content-length-range",1,65536]), base64 it, sign it with the derived `AWS4-HMAC-SHA256` key, and send a `multipart/form-data` POST to the bucket endpoint with the form fields followed by `key` and then `file`.
6. Observe: the POST does not result in an `Object Created` event carrying `detail.reason == "POST Object"` on rule B's queue — the wait for it never completes (reported as a 60s timeout). Check whether the POST was served at all (status/body) and, if an object was created, whether the emitted event's `reason` reads `"PutObject"` instead.
7. Confirm rule A's queue depth and whether it leaked an event for the form-posted key during a hold of 3x the measured step-4 latency, then `PutObject` once more to confirm rule A is still live.
