# ECR Public: 2 net-new causes — the served catalog logo carries no Content-Type: image/png, and a resource-policy explicit deny is refused InvalidParameterException instead of AccessDeniedException

## Description
Behavioral replay of simparity-behavioral-aws-v1 (88/92 passed; ecr-public 87/91, so the emulator IS serving and ecr-public is bootstrapped as service-com-amazonaws-ecrpublic-spencerfrontendservice — this is not a bootstrap gap) leaves TWO net-new root causes after skipping the two failures the report marked OWNED by open issues (complete-layer-upload-not-found -> 20261029T173115Z-ecr-public-the-pattern-constraint-invalidparameterexception-message-omits.md; registry-catalog-display-name-round-trip-and-limit -> 20261029T104628Z-ecr-public-putregistrycatalogdata-still-refuses-the-suite-s.md). Both causes below belong to ecr-public.

=== Cause 1 of 2: the hosted catalog logo is served without a Content-Type of image/png ===
AWS: Smithy RepositoryCatalogDataInput.logoImageBlob is an input-only blob (@length 0..512000, "The base64-encoded repository logo payload"); the output shape RepositoryCatalogData models no logoImageBlob and instead carries logoUrl -> ResourceUrl (@length 0..2048, "The URL that contains the logo that's associated with the repository."). The hosting leg itself is outside the modeled API surface, so: recorded behavior only — an anonymous GET of the minted logoUrl answers HTTP 200 with the byte-identical uploaded PNG AND a response Content-Type header of image/png, i.e. the asset is published as a real image, with the media type of the bytes stored, not as an untyped or generic-octet payload.
Emulator: the storage and byte-identity legs now pass — the GET answers 200, the body is byte-identical to the uploaded PNG (same length, b'\x89PNG\r\n\x1a\n' signature, IHDR reading the uploaded width/height), so the previously filed 404 (open issue 20261107T170252Z-ecr-public-the-logoimageblob-accepted-by-putrepositorycatalogdata-is.md, which recorded the earlier never-served symptom and whose replay key no longer binds this check) has stopped reproducing. What remains is the response headers: the asset route sends NO Content-Type at all. The check reads headers.get("Content-Type") and gets None, where image/png is required. Everything downstream of that assertion in the same check is therefore still unverified: the undersized-logo refusal (InvalidParameterException) leaving the stored bytes and the logoUrl untouched, and an accepted replacement blob minting a DIFFERENT logoUrl that serves the new bytes while the description survives.
Why: a client that renders the logo (a console/gallery preview, a publish pipeline that validates the published asset, any browser <img> or HTTP library that dispatches on media type) relies on the served media type; with no Content-Type the bytes are untyped, so a browser will not render them as an image and a strict client treats the fetch as a non-image payload. Against AWS the same URL renders; against the emulator it does not, and because the body is correct the breakage looks like a client bug rather than a server one.
Fix: the emulator's HTTP front door route that serves the stored catalog logo (the asset-serving handler paired with the PutRepositoryCatalogData logo state) must set the response Content-Type to the image media type of the stored blob — image/png for a PNG payload — alongside the verbatim bytes it already returns.
Traces: ecr-public.catalog-logo-blob-is-stored-and-served-as-a-real-image.

=== Cause 2 of 2: a stored repository policy whose explicit Deny blocks SetRepositoryPolicy is refused with InvalidParameterException and an emulator-authored message instead of AccessDeniedException ===
AWS: SetRepositoryPolicy models exactly four errors in the ecr-public Smithy model — InvalidParameterException, RepositoryNotFoundException, ServerException, UnsupportedCommandException — i.e. no authorization error is bound to the operation, because an authorization refusal is produced by the service's auth layer as the service-common AccessDeniedException, not as an input-shaped error. Recorded behavior: with a forced self-locking repository policy in place (Effect Deny on ecr-public:SetRepositoryPolicy for the account root), the next SetRepositoryPolicy is refused with Error.Code 'AccessDeniedException' and the standard authorization message whose fixed text is "User: " ... " is not authorized to perform: " ... " on resource: " ... " with an explicit deny in a resource-based policy" — the variable parts being the calling principal's ARN (from the caller's identity), the action 'ecr-public:SetRepositoryPolicy' (the attempted operation) and the repository ARN (from the request/state). The unforced attempt to store the same self-locking document is a DIFFERENT class and is correctly InvalidParameterException ("You are about to set a repository policy that will prevent you from setting another one in the future. Use the force parameter to override this exception.") — that leg passes; the divergence is only on the enforcement refusal.
Emulator: the Deny IS enforced (the call is refused, so the policy is not merely stored), but it is classified as an input error: Code 'InvalidParameterException' with the emulator-authored message "The repository policy on the repository with name '<repositoryName>' in the registry with id '<registryId>' denies ecr-public:SetRepositoryPolicy to this account, so the policy can no longer be set; delete the repository policy first" (the repository name and registry id are per-run/state values; the quoted sentence structure is entirely emulator wording with no AWS counterpart). Neither the code nor any part of that message matches AWS, and the message is not an authorization message at all.
Why: clients branch on Error.Code. 'AccessDeniedException' means "this principal is not permitted" and is handled by retry-with-different-credentials, permission-diagnosis and policy-repair paths; 'InvalidParameterException' means "your request is malformed" and is typically non-retryable and surfaced to a user as a bad-input bug. Collapsing an explicit-deny authorization refusal into the input-validation class makes a locked-out repository indistinguishable from a malformed request or a missing repository, so permission tooling (and anything parsing the standard "with an explicit deny in a resource-based policy" clause to find the offending policy) silently misdiagnoses it.
Fix: the SetRepositoryPolicy handler's lockout-enforcement branch must raise the authorization refusal through the emulator's auth/AccessDenied path rather than its input-validation path — emitting Error.Code AccessDeniedException with AWS's authorization message template (principal ARN, action, resource ARN, explicit-deny-in-a-resource-based-policy clause) — and must keep the separate unforced-lockout InvalidParameterException branch as it is. The stored document must stay unchanged by the refusal (it does today) and DeleteRepositoryPolicy must remain the escape hatch (it does today).
Traces: ecr-public.repository-policy-self-lockout-with-force-actually-blocks-set-repository-policy.
