# accessanalyzer: a scanned resource with no resource-based policy is never served by GetAnalyzedResource, and the unsupported-analyzer-type refusal carries the wrong message (2 causes)

> _Note: this issue was identified against the code base at commit `74825bb7b17dbb57a26bde46f40a20da6c3d756d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetAnalyzedResource

## Description
REOPENS 20261110T151852Z-access-analyzer-getanalyzedresource-response-diverges-epoch-timestamps-and-missing-resourcenotfoundexception.md: its fix left the call refused. That issue made GetAnalyzedResource raise the modelled 404 for a resource the analyzer analyzed nothing for; the refusal is now also returned for a resource the analyzer DID analyze, so the positive path of the operation no longer answers at all.

Two distinct causes in the emulator's IAM Access Analyzer external-access read path. Both must be fixed and verified before this issue is closed. The other open accessanalyzer issues (20261127T121249Z-...-validatepolicy-emits-no-dynamodb-condition-key-findings.md, 20261127T225047Z-...-analyzer-invalid-type-create-failed-handler.md) cover ValidatePolicy findings and a CloudFormation CREATE_FAILED reason respectively and cover neither cause below.

Cause 1 of 2: GetAnalyzedResource refuses, with 404 ResourceNotFoundException, a resource of the analyzer's own account that the analyzer analyzed, whenever that resource holds no resource-based policy — so an on-demand scan of a freshly created, policy-less resource is never observable.
- AWS: Smithy models GetAnalyzedResource (GET /analyzed-resource, success 200) with output GetAnalyzedResourceResponse{resource: AnalyzedResource}; AnalyzedResource @required members are resourceArn, resourceType, createdAt, analyzedAt, updatedAt, isPublic, resourceOwnerAccount, while actions/sharedVia/status/error are optional, and isPublic is documented as "Indicates whether the policy that generated the finding grants public access to the resource." StartResourceScan is documented "Immediately starts a scan of the policies applied to the specified resource. This action is supported only for external access analyzers." The recorded behaviour the checks replay: after StartResourceScan of an SQS queue of the analyzer's account through an ACCOUNT (external access) analyzer, GetAnalyzedResource for that queue ARN answers 200 with resource.resourceArn = the scanned ARN, resource.resourceType = "AWS::SQS::Queue" and resource.isPublic = false — a queue that grants nothing externally is still an ANALYZED resource and is reported with the finding members (actions/sharedVia/status) simply absent. The 404 ResourceNotFoundException (fixed text "Resource not found", with resourceId taken from the request's resourceArn) is reserved for an ARN the analyzer analyzed nothing for; that negative case is asserted by the same checks and is correct today.
- Emulator: GetAnalyzedResource derives the record from crate::state::monitored_resources and refuses with ResourceNotFoundException (404, message "Resource not found") when the ARN is not in that walk. The walk's providers admit a resource ONLY when the owning service's store holds a non-empty resource-based policy for it: sqs_queues skips every queue whose policy() is None, s3_buckets skips every bucket whose policy is None. A queue created with no Policy attribute therefore never appears, so GetAnalyzedResource answers 404 forever after a successful StartResourceScan. Both failing checks poll GetAnalyzedResource for the scanned queue until it is served and are killed by the 60s check timeout instead of ever seeing the record ("Check timed out after 60.0s").
- Why: a client cannot observe the result of an on-demand scan of any resource that is not already shared — exactly the common case. Scan-then-read workflows (scan, poll GetAnalyzedResource, assert isPublic false) never terminate, and a client cannot distinguish "analyzed, grants no external access" from "never analyzed": both are the same 404. Code that treats the 404 as a retryable not-yet-analyzed signal spins until its own deadline.
- Fix: the analyzed-resource derivation that GetAnalyzedResource reads — the monitored-resource providers in the external-access state module must treat an ABSENT resource-based policy as a policy granting nothing (so the resource is analyzed and reported with isPublic false and no finding members) rather than excluding the resource from the walk; GetAnalyzedResource's miss path must then keep the 404 only for an ARN that names no resource of the analyzer's account. ListAnalyzedResources, which reads the same walk, must stay consistent with it.
- Traces: accessanalyzer.start-resource-scan-deleted-analyzer-rejected and accessanalyzer.start-resource-scan-unused-access-analyzer-rejected (both time out in their GetAnalyzedResource poll of the scanned, policy-less queue). Code: services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/state/external_access.rs lines 235-252 (monitored_resources), 318-344 (s3_buckets, `let Some(document) = bucket.policy ... else { continue }`), 353-378 (sqs_queues, `let Some(document) = queue.policy() else { continue }`); services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/ops/get_analyzed_resource.rs lines 234-253 (lookup in that walk, else analyzed_resource_not_found).

Cause 2 of 2: StartResourceScan and GetAnalyzedServiceResource through an analyzer that is not an external-access analyzer are refused with the service's generic fixed text "Unsupported operation" instead of this refusal's own message "Invalid analyzer type" (the status 400, code ValidationException and reason FIELD_VALIDATION_FAILED are already right). This is the assertion the second failing check makes after the poll in Cause 1, which it never reaches in this run because Cause 1 aborts it first; the emulator's wording is stated by its own shared constant.
- AWS: Smithy models ValidationException (errorKind client, httpError 400) with @required message and @required reason (ValidationExceptionReason), and documents both operations as "supported only for external access analyzers". Recorded behaviour the check replays: StartResourceScan with analyzerArn naming an ACCOUNT_UNUSED_ACCESS analyzer, and GetAnalyzedResource with the same analyzerArn, are both refused with ValidationException, message "Invalid analyzer type" and reason "FIELD_VALIDATION_FAILED". "Invalid analyzer type" is the whole of the fixed text for this refusal class — it carries no value from the request or the state (the analyzer's ARN and type do not appear in it). The refusal must leave the analyzer untouched (it stays type ACCOUNT_UNUSED_ACCESS, status ACTIVE).
- Emulator: both handlers refuse that family with crate::state::unsupported_action_exception(), whose message is the crate-wide constant UNSUPPORTED_OPERATION_MESSAGE = "Unsupported operation" (reason FIELD_VALIDATION_FAILED, no fieldList). So the status, code and reason match while the message text does not.
- Why: clients and operators match on the message for this class of refusal (it is the only part of the payload that says WHAT was wrong, since the refusal carries no fieldList); a different sentence breaks message-matching error handling, log-based alerting and test assertions, and misreports a type error as a generic unsupported operation.
- Fix: the message constructor these two handlers use for an analyzer of the wrong family — the external-access-only refusal needs its own fixed text ("Invalid analyzer type") rather than sharing the service's generic unsupported-operation constant; keep the 400 / ValidationException / FIELD_VALIDATION_FAILED / no-fieldList shape, and keep other operations on whatever text their own recordings fix.
- Traces: accessanalyzer.start-resource-scan-unused-access-analyzer-rejected (asserts the tuple (ValidationException, 'Invalid analyzer type', FIELD_VALIDATION_FAILED) for both StartResourceScan and GetAnalyzedResource through the unused-access analyzer). Code: services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/state.rs lines 1671 and 1685-1691 (UNSUPPORTED_OPERATION_MESSAGE / unsupported_action_exception); call sites services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/ops/start_resource_scan.rs lines 234-240 and src/ops/get_analyzed_resource.rs lines 220-225.
