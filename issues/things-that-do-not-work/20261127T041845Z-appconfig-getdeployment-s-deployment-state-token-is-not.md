# appconfig: GetDeployment's Deployment$State token is not the one the behavioral corpus records, so the zero-duration deployment settle barrier never releases and both experiment-run checks reach no verdict (1 cause)

> _Note: this issue was identified against the code base at commit `1cb2c89e78a43c5f64deffffb0f79f2010a0d95b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDeployment

## Description
One net-new root cause in the appconfig service, grounded in the two appconfig checks of this replay that are NOT marked ALREADY FILED and NOT marked OWNED by any open issue. Both die as "Check timed out after 60.0s" inside the same setup barrier, before any graded assertion is issued, so neither of the behaviours they exist to grade (the StartExperimentRun unknown-treatment refusal, and the StopExperimentRun double-stop refusal) is exercised at all.

Cause 1 of 1: the deployment-completion barrier every experiment-run check is built on can never release, because GetDeployment serves Deployment$State as the Smithy enum MEMBER NAME ('COMPLETE') while the behavioral corpus records the served token as the PascalCase 'Complete'.
Failing check ids: appconfig.start-experiment-run-invalid-treatment-allocation-rejected, appconfig.stop-experiment-run-double-stop-conflict.

  AWS: recorded behavior only for the wire TOKEN. Smithy (services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json): Deployment$State -> com.amazonaws.appconfig#DeploymentState, an enum whose values are [BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED], with no @enumValue override, so the model alone says only the member names; the sibling Environment$State -> EnvironmentState [READY_FOR_DEPLOYMENT, DEPLOYING, ROLLING_BACK, ROLLED_BACK, REVERTED] is modelled the same way. Both behavioral recordings state the served form explicitly and build their barriers on it: "despite the documented SCREAMING_SNAKE_CASE enums, the real wire values are PascalCase ('Complete', 'ReadyForDeployment') -- confirmed against real AWS". The requirement in that corpus is therefore the MAPPING member -> PascalCase token for DeploymentState ('Baking', 'Validating', 'Deploying', 'Complete', 'RollingBack', 'RolledBack', 'Reverted'), not any one run's state; the generated ids, deployment numbers and timestamps around it are per-run values.
  CORPUS CONFLICT a fixer must resolve before patching, stated here rather than hidden: this checkout currently serves the SCREAMING_SNAKE form on purpose. crate state.rs lines 64-92 declare DEPLOYMENT_COMPLETE = "COMPLETE" and argue the member name IS the wire value, while deliberately spelling Environment$State in CamelCase (ENVIRONMENT_READY_FOR_DEPLOYMENT = "ReadyForDeployment", lines 94-122). That split is the product of earlier, contradictory findings: behavioral issue 20261110T191755Z-appconfig-getdeployment-getenvironment-serve-state-as-the-model.md (status fixed) made both read paths PascalCase on exactly this cause and exactly this check id, and the wire-corpus issues 20261115T214126Z-appconfig-appconfigdata-getdeployment-serves-deployment-state-in-pascalcase.md / 20261115T213820Z-appconfig-lambda-2-net-new-causes-getdeployment-serves.md / 20261116T072120Z-appconfig-serves-deployment-state-in-pascalcase-complete-deploying.md (all fixed) then flipped Deployment$State back to 'COMPLETE' on recorded wire responses, leaving the still-open 20261116T014021Z-appconfig-serves-deployment-state-in-pascalcase-across-the.md for the write/list paths. The two corpora disagree about this one token; whichever way it is resolved, the resolution must be made ONCE for the whole DeploymentState seam, and the behavioral barrier here must be able to release.
  Emulator: GetDeployment answers 200 with $.State = 'COMPLETE' for a settled deployment (src/ops/get_deployment.rs projects `state: Some(deployment.state.clone())` straight out of the stored token, which crate::state sets from DEPLOYMENT_COMPLETE = "COMPLETE"). GetEnvironment's $.State already answers 'ReadyForDeployment', so the SECOND barrier in both checks would release; the deployment barrier is the only one that cannot. Both checks therefore spend their entire budget in _poll_until(GetDeployment(...)['State'] == 'Complete', timeout_s=60.0, interval_s=2.0) and are killed by the harness at exactly 60.0s with every assertion ungraded.
  Why: State is the only completion signal AppConfig offers for a deployment, and an experiment run can only be started once a configuration profile has a COMPLETED deployment in the target environment. A client that waits on the token real AWS sends — a deploy script, a CI gate, a poller, or the StartExperimentRun precondition here — never observes a settled deployment against this emulator, so it blocks until its own timeout and every code path gated behind a settled deployment is unreachable. Concretely it makes two whole negative contracts unobservable: StartExperimentRun's BadRequestException "Invalid treatment name: <name>. Valid treatment names are: [<control key>, <treatment keys>]" (fixed text with the rejected name and the definition's own treatment keys substituted; no run created, definition left IDLE), and StopExperimentRun's BadRequestException "Experiment run <run> for experiment definition <definition-id> is not running." (fixed text with the run number and definition id from the request/state) on a second stop of an already-DONE run.
  Fix: the appconfig DeploymentState wire-token seam — the single mapping crate::state uses for Deployment$State / DeploymentSummary$State and that src/ops/get_deployment.rs (and the sibling start/stop/list deployment projections) emits, plus the inverse wherever a state is interpolated into a refusal sentence. It belongs in one shared place for the whole enum rather than per handler, and must be decided together with the Environment$State spelling beside it so the two stop disagreeing.
  Traces: appconfig.start-experiment-run-invalid-treatment-allocation-rejected and appconfig.stop-experiment-run-double-stop-conflict (both [mismatch], "Check timed out after 60.0s"). Supporting citations: src/ops/get_deployment.rs:307-336 (the projection), src/state.rs:64-122 (the two state-token constant blocks).

with the in-source note "despite the documented SCREAMING_SNAKE_CASE enums, the real wire values are PascalCase ('Complete', 'ReadyForDeployment') -- confirmed against real AWS". The second check's source adds that polling for the documented casing "never matches, so both waits below previously burned their *entire* timeout budget on every run".

Expected (behavioral recording): GetDeployment reports State 'Complete' once the zero-duration/zero-bake deployment settles, the barrier releases in seconds, and the check proceeds to its graded call.
Actual (emulator): GetDeployment reports State 'COMPLETE'. The first barrier's 60 s budget is exactly the harness's per-check budget here, so the check is killed at 60.0s with nothing graded. The code path is unambiguous: src/ops/get_deployment.rs:321 serializes `state: Some(deployment.state.clone())`, and src/state.rs:84 defines `pub const DEPLOYMENT_COMPLETE: &str = "COMPLETE";` with a doc block (lines 64-80) stating the member name IS the served form for this enum, contrasted against src/state.rs:111 `pub const ENVIRONMENT_READY_FOR_DEPLOYMENT: &str = "ReadyForDeployment";` for the sibling enum.

Ungraded as a consequence (listed so the fixer knows what still has to be re-checked after the barrier releases, not as separate findings): StartExperimentRun with TreatmentOverrides naming an undefined treatment key must answer 400 BadRequestException "Invalid treatment name: <name>. Valid treatment names are: [<control key>, <treatment key>]", create no run, and leave the definition IDLE; a second StopExperimentRun on an already-DONE run must answer 400 BadRequestException "Experiment run <run> for experiment definition <definition-id> is not running." and leave Status DONE with EndedAt unchanged.

Smithy consulted: DeploymentState = [BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED]; EnvironmentState = [READY_FOR_DEPLOYMENT, DEPLOYING, ROLLING_BACK, ROLLED_BACK, REVERTED]; neither carries an @enumValue trait, so the PascalCase form asserted by the behavioral corpus is recorded behavior only — and it is contradicted by the wire corpus cited in the description. Resolving that contradiction is part of this issue.

## Steps to Reproduce

1. CreateApplication(Name=<new>); CreateEnvironment(ApplicationId=<app>, Name=<new>).

3. CreateDeploymentStrategy(DeploymentDurationInMinutes=0, GrowthFactor=100, FinalBakeTimeInMinutes=0, ReplicateTo='NONE'); StartDeployment of that hosted version into the environment.
4. THE GRADED READ: poll GetDeployment(ApplicationId=<app>, EnvironmentId=<env>, DeploymentNumber=<n>) and compare ['State'] against 'Complete', the token the behavioral recording waits for. EXPECTED: the barrier releases within seconds of the zero-duration/zero-bake deployment settling. OBSERVED: ['State'] is 'COMPLETE' on every read, so the comparison is false forever and the poll consumes its whole 60 s budget.
5. Confirm the sibling read is already PascalCase: GetEnvironment(ApplicationId=<app>, EnvironmentId=<env>)['State'] answers 'ReadyForDeployment', so only the deployment token blocks the barrier.
6. Decide the DeploymentState wire token once for the whole seam (see the CORPUS CONFLICT paragraph: behavioral issue 20261110T191755Z claimed PascalCase and was fixed, wire issues 20261115T214126Z / 20261115T213820Z / 20261116T072120Z claimed SCREAMING_SNAKE and were fixed afterwards, and 20261116T014021Z is still open for the write/list paths), apply it in the one shared mapping, and apply the inverse wherever a state is interpolated into a message (e.g. the StopDeployment terminal-state refusal "... cannot be stopped, it has a status of <state>.").
7. Re-replay appconfig.start-experiment-run-invalid-treatment-allocation-rejected and appconfig.stop-experiment-run-double-stop-conflict. With the barrier releasing, both proceed to their graded calls: the StartExperimentRun unknown-treatment BadRequestException (no run created, definition IDLE, then RUNNING for a valid key) and the StopExperimentRun double-stop BadRequestException (run left DONE with EndedAt unchanged). Any failure there is a further defect of those operations, not of this barrier.
