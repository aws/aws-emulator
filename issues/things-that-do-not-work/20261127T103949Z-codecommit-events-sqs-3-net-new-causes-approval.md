# codecommit__events__sqs: 3 net-new causes — approval-rule-template changes publish no EventBridge event, InvalidApprovalRuleTemplateContentException reports the wrong reason, and a matching custom event does not reach the rule's SQS target in one run

> _Note: this issue was identified against the code base at commit `ab3264a14a30dede061951437467343aaef14e5b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchAssociateApprovalRuleTemplateWithRepositories

## Description
Three net-new root causes behind the codecommit__events__sqs checks, all grounded in failing checks the replay report left unmarked.

Cause 1 of 3: no 'CodeCommit Approval Rule Template Change' event is ever published to the default event bus.
AWS: recorded behavior only (the Smithy model does not describe eventing); CodeCommit emits a 'CodeCommit Approval Rule Template Change' event on the default bus for each approval-rule-template change, with detail.event naming the API call ('approvalRuleTemplateCreated', 'approvalRuleTemplateUpdated', 'batchAssociateApprovalRuleTemplateWithRepositories'), detail.approvalRuleTemplateName, detail.approvalRuleTemplateId (the UUID the create returned), detail.approvalRuleTemplateContentSha256 (SHA-256 of the exact content stored), detail.callerUserArn (the identity that made the call), detail.creationDate / detail.lastModifiedDate in the 'Tue Nov 12 23:38:57 UTC 2019' form, and — for the batch-associate call — resources listing exactly the ARNs of the repositories that gained the rule and detail.repositories mapping each associated repository name to its repositoryId.
Emulator: the API calls succeed (the batch-associate response correctly associates the two real repositories and reports the missing name as RepositoryDoesNotExistException), but no event ever arrives on a rule that matches 'CodeCommit Approval Rule Template Change' with a detail.approvalRuleTemplateName prefix. The same check first proves the rule and its SQS target are live by putting a custom-source event through the identical rule and receiving it, so the missing piece is CodeCommit's publication, not the bus or the target.
Why: approval-rule governance is built on these events (auditing who changed a template, and reacting to a template being attached to repositories). A client that subscribes to them sees nothing while the control-plane calls report success, so the whole eventing surface for approval rule templates silently does not exist.
Fix: the event-publication seam of the codecommit crate's approval-rule-template handlers (src/ops/create_approval_rule_template.rs, update_approval_rule_template_content.rs, batch_associate_approval_rule_template_with_repositories.rs) — publish the detail-typed event to the default bus with the fields above.
Related: open issue 20261022T171422Z-codecommit-events-sqs-codecommit-createbranch-is-a-501-stub-and-no.md records that repository/pull-request events do not reach EventBridge and 20261126T173230Z-codecommit-events-sqs-a-reference-moving-putfile-publishes.md records the missing PutFile state-change event; neither carries the approval-rule-template check ids filed here, and neither names these operations.
Traces: codecommit__events__sqs.batch-associate-approval-rule-template-event-names-the-template-caller-and-its-dates, codecommit__events__sqs.approval-rule-template-create-and-update-reach-a-rule-queue-with-the-template-digest.

Cause 2 of 3: CreateApprovalRuleTemplate's InvalidApprovalRuleTemplateContentException message reports malformed JSON for well-formed JSON that is missing the content language's Version.
AWS: Smithy CreateApprovalRuleTemplate takes approvalRuleTemplateContent (@required, @length 1..3000) and models InvalidApprovalRuleTemplateContentException (client, httpError 400). For content that is valid JSON but carries no 'Version' member (e.g. {"Statements": "one approver please"}), AWS answers HTTP 400 InvalidApprovalRuleTemplateContentException with the fixed message 'A version for the approval rule template is required, but no version was provided.', and the template is never created (a following GetApprovalRuleTemplate answers ApprovalRuleTemplateDoesNotExistException).
Emulator: the code and status are right, and the template is correctly not created, but the message is 'The JSON in the approval rule template is not valid. Review the JSON and make sure it is valid, and then try again.' — AWS's message for content that is not parseable JSON at all, which this content is.
Why: the message is the only signal distinguishing 'your JSON is broken' from 'your rule document lacks its required Version'; a caller gets sent to re-check syntax that is already correct.
Fix: the approval-rule-template content validation in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/create_approval_rule_template.rs — validate parse, then required members, and emit the per-defect message.
Traces: codecommit__events__sqs.approval-rule-template-create-rejected-for-invalid-content-emits-no-change-event.

Cause 3 of 3: a custom PutEvents entry that the rule matches does not reach the rule's SQS target within the probe window in one of the three runs.
AWS: recorded behavior only. An ENABLED rule whose EventPattern matches {source: ["aws.codecommit", "com.example.review-gates"], detail-type: ["CodeCommit Approval Rule Template Change"], detail: {approvalRuleTemplateName: [{"prefix": "<stem>"}]}}, with an SQS queue target whose queue policy allows events.amazonaws.com to sqs:SendMessage, delivers every matching PutEvents entry to that queue, promptly and every time.
Emulator: in codecommit__events__sqs.approval-rule-template-create-and-update-reach-a-rule-queue-with-the-template-digest the probe put the matching entry (PutEvents reported FailedEntryCount 0) and polled the queue up to 18 times with 5-second long polls without the message ever arriving — 'no liveness event reached the rule's queue' — so the check never reached a single graded assertion. The identical prefix-matched probe DID deliver in the two sibling checks in this suite, so default-bus-to-SQS delivery is not uniformly broken but is not reliable either. Hypothesis: delivery of a matching entry is dropped or delayed past a ~90 s window under this rule/target shape (prefix content filter on a detail member plus a queue-policy-gated SQS target).
Why: a client cannot depend on a rule it has just created and confirmed delivering its events; an event that PutEvents accepted is silently lost, which makes every event-driven workflow non-deterministic.
Fix: the EventBridge rule-matching and target-delivery path (the events crate's PutEvents dispatch to SQS targets, including the detail prefix matcher and the delivery queue/retry), so a matching accepted entry is always delivered to its target.
Traces: codecommit__events__sqs.approval-rule-template-create-and-update-reach-a-rule-queue-with-the-template-digest.
