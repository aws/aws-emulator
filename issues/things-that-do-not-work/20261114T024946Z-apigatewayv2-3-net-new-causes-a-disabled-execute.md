# apigatewayv2: 3 net-new causes — a disabled execute-api endpoint never answers 404 Not Found, a per-route throttle makes its route ungradeable, and the inbound 32 KiB CLOSE 1009 carries emulator-authored reason text

> _Note: this issue was identified against the code base at commit `0bdb628a6eeeae829cbfa42cf4e1c8a43263b6d6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateApi

## Description
Three distinct root causes in the apigatewayv2 execute-api data plane. All three are net-new: none of the failing checks below is marked ALREADY FILED or OWNED by an open issue in this replay.

Cause 1 of 3: an HTTP API whose default execute-api endpoint is disabled never answers the documented 404, so the whole disable/restore transition is ungradeable. Failing check: apigatewayv2.deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore.
AWS: UpdateApi(DisableExecuteApiEndpoint=true) turns the api's default execute-api URL off; a request to that URL is refused with HTTP 404 and the gateway envelope body {"message":"Not Found"} — fixed text, no variable part — and the integration is NOT invoked (nothing from the refused request reaches the backend). A twin api on the same backend with the flag clear keeps serving 200. Clearing the flag (DisableExecuteApiEndpoint=false) restores 200 from the integration on the same URL. Smithy: UpdateApi input/output member DisableExecuteApiEndpoint (__boolean, jsonName disableExecuteApiEndpoint); modelled errors BadRequestException 400, ConflictException 409, NotFoundException 404, TooManyRequestsException 429. The 404/{"message":"Not Found"} refusal itself is the data plane's and is recorded behavior only (the execute-api data plane is not modelled in Smithy).
Emulator: the check reaches no verdict at all — 'Error: Check timed out after 60.0s'. It polls the target URL for a settled run of 404s (and later for a settled run of 200s after re-enabling) and never gets them inside the harness budget. Hypothesis: the emulator's disabled-endpoint gate refuses with 403 {"message":"Forbidden"} rather than 404 {"message":"Not Found"} — that is the refusal the already-filed issue 20261112T190000Z-apigatewayv2-the-disableexecuteapiendpoint-check-still-hangs-on-the-front-door-upgrade.md describes its gate as serving — so the 404 the check waits for never appears and the poll spins to the cap. Whatever the served status is, no 404 is produced for this check's HTTP-only api pair.
Why: a client cannot tell that disabling the default endpoint took effect in the way AWS defines it. Code and tests that key on 404/{"message":"Not Found"} (the documented refusal for a disabled default endpoint) see a different class of refusal, and a restore back to serving cannot be observed, so blue/green and endpoint-lockdown procedures are unverifiable.
Fix: the execute-api front door's DisableExecuteApiEndpoint gate for HTTP APIs — the status and envelope it answers on a disabled stage, and the path that restores serving when the member is cleared. Related open issues that do NOT carry this check's replay key: 20261110T153046Z-apigatewayv2-iam-lambda-logs-sts-updateapi-disableexecuteapiendpoint-true.md and 20261112T190000Z-apigatewayv2-the-disableexecuteapiendpoint-check-still-hangs-on-the-front-door-upgrade.md (both keyed to the apigatewayv2__iam__lambda__logs__sts WebSocket-twin check).
Traces: apigatewayv2.deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore.

Cause 2 of 3: a per-route throttle on an HTTP API stage never produces the AWS shedding pattern — the throttled route cannot even be observed serving its backend, so the check reaches no verdict. Failing check: apigatewayv2.route-throttling-returns-429-while-twin-route-serves.
AWS: CreateStage RouteSettings keyed by route key carry ThrottlingRateLimit (double, requests/second) and ThrottlingBurstLimit (integer) — Smithy: RouteSettings.throttlingRateLimit (__double), RouteSettings.throttlingBurstLimit (__integer); DeleteRouteSettings (DELETE /v2/apis/{ApiId}/stages/{StageName}/routesettings/{RouteKey}, 204) removes the override. Behaviour is recorded/documented only: a route whose override is far below the offered rate sheds PART of a burst with HTTP 429 and the gateway envelope {"message":"Too Many Requests"} (fixed text) before the integration runs — the shed responses never carry the backend's body — while the remaining requests of the same burst are served 200 from the integration. The throttle is per-route: a twin route of the same stage and the same integration, left on the stage's generous DefaultRouteSettings, sheds nothing in the same instant. After DeleteRouteSettings the formerly limited route sheds nothing.
Emulator: the check reaches no verdict — 'Error: Check timed out after 60.0s'. Its first beat only polls each of the two routes for a plain 200 carrying the backend marker, before any burst. Hypothesis: the limited route answers 429 to EVERY request from the outset — the behaviour the open issue 20261110T163347Z-apigateway-apigatewayv2-an-http-api-default-stage-throttle.md records for a rate=1/burst=1 stage-level override, and 20261109T152222Z-apigateway-stage-throttling-is-never-enforced-deleted-api.md records for the REST sibling — so the precondition poll for a 200 never accepts and the check burns the whole harness budget. Either way the emulator never exhibits the partial-shedding pattern (some 429 + some 200 on the limited route, zero 429 on the twin).
Why: a per-route throttle is unusable as AWS defines it. A route configured with a low rate either serves nothing (every caller sees 429 with no requests getting through) or sheds nothing; clients cannot distinguish per-route from per-stage limiting, and capacity-protection configuration cannot be validated against the emulator.
Fix: the execute-api data plane's throttling component — a token-bucket per (stage, route key) seeded from RouteSettings/DefaultRouteSettings that sheds only the excess with 429 {"message":"Too Many Requests"} before invoking the integration, plus the DeleteRouteSettings path that returns the route to the stage default.
Traces: apigatewayv2.route-throttling-returns-429-while-twin-route-serves.

Cause 3 of 3: the CLOSE 1009 that refuses an oversize inbound WebSocket message carries emulator-authored reason text. Failing check: apigatewayv2.websocket-inbound-message-32kb-boundary.
AWS: recorded behavior only (the WEBSOCKET data plane is not modelled in Smithy; the model declares neither the limit nor the reason). A client-to-server WebSocket frame on an API Gateway v2 WebSocket API tops out at 32768 bytes. A frame one byte over is not routed to the integration: the gateway answers an RFC 6455 CLOSE frame (opcode 0x8) with status code 1009 whose reason payload is 'Max frame length of 32768 has been exceeded.' — fixed text 'Max frame length of ' + '<the gateway's inbound frame limit>' + ' has been exceeded.', the only variable part being the limit itself — and then closes the connection.
Emulator: the limit and the close code are right (the 32768-byte frame is delivered, 32769 is refused with CLOSE 1009) but the reason payload is the string 'Message too big'. Replay: AssertionError: the 1009 close must carry the reason 'Max frame length of 32768 has been exceeded.', got 'Message too big'.
Why: the close reason is the only diagnostic a WebSocket client gets for this refusal. A client (or an SDK/test) that matches AWS's reason text to tell 'my message was too large, chunk and retry' from any other 1009 condition never matches, and the limit the message names — the number clients size their framing against — is not reported at all.
Fix: the WEBSOCKET frame reader/limit enforcement path in the execute-api data plane — the reason string it writes into the CLOSE 1009 payload. Note the fixed issue 20261113T112337Z-apigatewayv2-dynamodb-lambda-2-net-new-causes-on.md made the oversize message produce a CLOSE 1009 at all (it previously closed bare); this is the reason text that fix left diverging, on a different check, and the refusal itself now arrives.
Traces: apigatewayv2.websocket-inbound-message-32kb-boundary.
