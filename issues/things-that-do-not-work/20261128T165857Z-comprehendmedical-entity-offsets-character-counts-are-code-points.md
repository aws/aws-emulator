# ComprehendMedical: entity offsets/character counts are code points not UTF-16 units, encoding and text-size refusals are wrong, and async job starts never check the input S3 folder (6 causes)

> _Note: this issue was identified against the code base at commit `b60f6fc1d7d48b8ab01ee41fe8076d8fc438ec86`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DetectPHI

## Description
Six net-new root causes found by the behavioral suite against the comprehendmedical emulator, which DOES serve these operations (16/37 checks pass). None of them is the already-filed scaffold-stub cluster (DetectEntities, DetectEntitiesV2, StartICD10CMInferenceJob, StartRxNormInferenceJob, StartSNOMEDCTInferenceJob), and none is covered by the open issues `20261127T064015Z-comprehendmedical-rule-based-inference-engine-diverges-from-recorded.md` (confidence scores, concept tables, ModelVersion — nothing about offsets, character counts, encoding refusals, text-size limits or job-input validation) or `20261029T175936Z-comprehendmedical-phi-job-handlers-answer-501-notimplemented-on.md` (absent-job and absent-role refusals on the PHI job resolution paths — not the input-S3-folder check, and StartPHIDetectionJob here answers 200 with a JobId). A fixer must close all six before submitting.

Cause 1 of 6: Entity BeginOffset/EndOffset are counted in Unicode code points instead of UTF-16 code units, so every span past a non-BMP character is short.
  AWS: Smithy: Entity.BeginOffset / Entity.EndOffset are documented as "The 0-based character offset in the input text that shows where the entity begins/ends" (the model's prose then says "the offset returns the UTF-8 code point in the string", which names no concrete unit). Recorded behavior is unambiguous and is the requirement: AWS counts offsets in UTF-16 code units, so a character outside the Basic Multilingual Plane ahead of an entity advances the offsets by TWO, and slicing the UTF-16 encoding of the submitted text between BeginOffset and EndOffset reproduces that entity's Text exactly. HTTP 200 both ways; this is a body divergence, not a refusal.
  Emulator: offsets are the index of the character in a code-point walk of the text. For DetectPHI, prefixing the note with two astral symbols and a space (3 code points = 5 UTF-16 units) moved a NAME entity from 16..24 to 19..27 where AWS reports 21..29 — the shift was 3, not 5. For InferICD10CM, a note containing one astral symbol ahead of the mention reported "pneumonia" at 56..65 where AWS reports 57..66. For InferSNOMEDCT the same one-unit deficit appears on the entity offsets of a note beginning with an astral symbol.
  Why: a client that highlights, redacts or extracts the reported span does so in its own string type. Every mainstream SDK runtime that these offsets are documented for (Java, JavaScript, .NET, Python's surrogate-aware consumers) indexes UTF-16, so against the emulator each astral character before the entity shifts the slice one unit to the left: a PHI redaction cuts one unit short of the identifier and leaves a character of it in the clear, and an extracted entity string is off by one at both ends (often splitting a surrogate pair into a replacement character).
  Fix: the shared clinical-text pass's offset conversion — `character_starts`/`character_offset` in services/service-com-amazonaws-comprehendmedical-comprehendmedical-20181030/src/ops/infer_icd10_cm.rs (lines 1788-1796), which maps a byte position to a code-point index and is consumed by DetectPHI (src/ops/detect_phi.rs, `begin_offset`/`end_offset` construction around line 1825), by InferICD10CM and by InferSNOMEDCT. It must convert a byte position to a count of UTF-16 code units (sum of `char::len_utf16` over the preceding characters) for entities, attributes and traits alike.
  Traces: comprehendmedical.detect-phi-offsets-count-utf16-code-units, comprehendmedical.infer-icd10cm-offsets-count-utf16-units-past-astral-text, comprehendmedical.infer-snomedct-character-count-and-offsets-in-utf16-units.

Cause 2 of 6: InferSNOMEDCT reports Characters.OriginalTextCharacters in code points instead of UTF-16 code units.
  AWS: Smithy: InferSNOMEDCTResponse.Characters is a `Characters` structure whose `OriginalTextCharacters` (Integer) is "The number of characters present in the input text document as processed by Amazon Comprehend Medical". Recorded behavior: that count is the text's length in UTF-16 code units, so an astral symbol contributes 2. HTTP 200.
  Emulator: for a 33-code-point / 34-UTF-16-unit note beginning with one astral symbol it answered OriginalTextCharacters = 33 — the code-point count.
  Why: OriginalTextCharacters is the field a caller meters and bills ontology-linking usage on and the field it uses to check its own chunking against the service's accounting; a count that differs from AWS's for any text holding emoji, astral symbols or non-BMP scripts makes that accounting disagree with production and can make a client believe a chunk fits under the request limit when AWS will count it over.
  Fix: the InferSNOMEDCT handler's `Characters` construction (services/service-com-amazonaws-comprehendmedical-comprehendmedical-20181030/src/ops/infer_snomedct.rs), which must count UTF-16 code units of the submitted Text, consistently with Cause 1.
  Traces: comprehendmedical.infer-snomedct-character-count-and-offsets-in-utf16-units.

Cause 3 of 6: text carrying an unpaired UTF-16 surrogate is refused by the JSON deserializer as `ValidationException` instead of by the operation as `InvalidEncodingException`.
  AWS: Smithy: every synchronous text operation of this service (DetectPHI, DetectEntitiesV2, InferICD10CM, InferRxNorm, InferSNOMEDCT) declares `InvalidEncodingException` (@httpError 400) documented as "The input text was not in valid UTF-8 character encoding. Check your text then retry your request." Recorded behavior: a request whose JSON `Text` contains a lone `\ud83d` (high) or `\udccb` (low) surrogate escape is accepted at the protocol layer and refused by the operation with HTTP 400, error code `InvalidEncodingException` and the message `Please provide a valid utf-8 encoded text.` — that message is fixed text with no variable part. Both the unpaired-high and the unpaired-low case give the identical code and message, and a request carrying the complete surrogate pair in the same position is analysed normally before and after the two refusals.
  Emulator: the request never reaches the handler. The shared JSON deserializer rejects the escape, answering error code `ValidationException` with the message `invalid string escape: expected a UTF-16 surrogate pair, but got : John as the low word` — a code this service's model does not declare at all, and an implementation-detail message that even leaks a fragment of the submitted clinical text (`John`) back to the caller. src/ops/detect_phi.rs states the assumption explicitly in its handler comment ("it arrives as a Rust `String`, so it is valid UTF-8 and the modelled `InvalidEncodingException` is unreachable") — that assumption is the defect: the deserializer must not be the thing that refuses.
  Why: a client branches on the error code. `InvalidEncodingException` is a modelled, SDK-typed error that callers catch to re-encode and retry the document; `ValidationException` is not in this service's error set, so the SDK surfaces it as an unmodelled/unknown error, retry logic for bad encoding never fires, and the echoed text fragment is a PHI leak in an error message that this service's own validation module otherwise takes care never to echo.
  Fix: the request-deserialization boundary for this service's text operations plus the handlers' encoding check — the JSON string decoder must tolerate a lone surrogate escape and hand the operation the text (e.g. as lossily decoded bytes), and the operation must then answer the modelled `InvalidEncodingException` with the exact fixed message above. Also remove the "unreachable" assumption in src/ops/detect_phi.rs and the equivalent in the other four text handlers.
  Traces: comprehendmedical.detect-phi-lone-surrogate-invalid-encoding-rejected.

Cause 4 of 6: InferSNOMEDCT accepts text longer than its 5,000-character service limit instead of refusing it with TextSizeLimitExceededException.
  AWS: Smithy: InferSNOMEDCT.Text targets `OntologyLinkingBoundedLengthString` with @length min 1 max 10000, and the operation declares `TextSizeLimitExceededException` (@httpError 400) documented as "The size of the text you submitted exceeds the size limit. Reduce the size of the text or use a smaller document and then retry your request." Recorded behavior, which is narrower than that modelled maximum and is the requirement: a note of exactly 5000 characters is analysed (HTTP 200, Characters.OriginalTextCharacters = 5000), and a note of 5001 characters is refused with HTTP 400, code `TextSizeLimitExceededException` and the message `1 validation error detected: Value at 'text' failed to satisfy constraint: Member must have length less than or equal to 5000`. Fixed text: `N validation error(s) detected: Value at '<member path>' failed to satisfy constraint: Member must have length less than or equal to <limit>`; variable parts: the member path (`text`) and the limit (`5000` for InferSNOMEDCT). The submitted value is never echoed.
  Emulator: the 5001-character note is ANALYSED and returns HTTP 200 with a full Entities list (the suite captured `{'Entities': [{'Id': 2, 'Text': 'cough', ...}]}`). The limit actually enforced is the modelled 10000: src/service/validation.rs maps a `MaxLength` violation on `text` to `TextSizeLimitExceededException` and renders exactly the envelope above, so the wording machinery is right and only the bound is wrong — nothing refuses between 5001 and 10000 characters.
  Why: this is an overly-permissive boundary. A client sizes its own document chunking to whatever the emulator accepts, then fails in production the first time a chunk between 5001 and 10000 characters is submitted; the error it must handle (TextSizeLimitExceededException) is never exercised against the emulator at all.
  Fix: the InferSNOMEDCT input validation — the per-operation text limit consulted before/at the boundary walk for this operation (src/ops/infer_snomedct.rs together with the limit the constraint walk applies for `InferSNOMEDCTRequest.Text`), which must refuse past 5000 characters while src/service/validation.rs keeps producing the envelope and the `TextSizeLimitExceededException` code, with `5000` as the limit named in the clause.
  Traces: comprehendmedical.infer-snomedct-text-over-5000-characters-rejected.

Cause 5 of 6: StartEntitiesDetectionV2Job never checks that InputDataConfig names an existing S3 input folder, so an empty/absent prefix starts a job.
  AWS: Smithy: StartEntitiesDetectionV2Job declares `ResourceNotFoundException` (@httpError 404) documented as "The resource identified by the specified Amazon Resource Name (ARN) was not found", and `InputDataConfig.S3Key` is "The path to the input data files in the S3 bucket" — a FOLDER, not an object key. Recorded behavior: a request whose S3Key names a prefix under which the bucket holds no object is refused with code `ResourceNotFoundException` and the message `The input S3 folder specified does not exist` (fixed text, no variable part), no JobId is minted, and the job name does not appear in ListEntitiesDetectionV2Jobs; once a document is put under that prefix the identical request succeeds and returns a 32-lowercase-hex-digit JobId.
  Emulator: the request on the empty prefix `pending/` returned HTTP 200 and a JobId (the suite saw `00066159051a109b0000000000000001`), creating a job for input that does not exist. The handler (src/ops/start_entities_detection_v2_job.rs, handle() at lines 168-258) resolves the data-access role via `crate::state::data_access_role_is_unassumable` and then goes straight to minting the id and recording the job — there is no lookup of the input bucket/prefix at all.
  Why: this is an overly-permissive acceptance. A client's "did my input land?" guard is exactly this refusal: against the emulator a typo'd or not-yet-populated prefix silently produces a job that can never have results, so the client waits on a job AWS would have refused synchronously, and the 404 branch it must implement is never reached.
  Fix: StartEntitiesDetectionV2Job's input validation — add an input-location existence check (list the emulator's own S3 for at least one object under `InputDataConfig.S3Bucket`/`S3Key`, over the same in-process callback mechanism the role check already uses) before any id is minted or state is written, returning the modelled `ResourceNotFoundException` with the fixed message above and persisting nothing.
  Traces: comprehendmedical.start-entities-v2-job-absent-input-folder-rejected.

Cause 6 of 6: StartPHIDetectionJob never checks its input S3 folder either, so an object KEY passed as S3Key starts a job.
  AWS: Smithy: StartPHIDetectionJob declares the same `ResourceNotFoundException` (@httpError 404) and the same `InputDataConfig` shape, where `S3Key` is the path to the input data FILES (a prefix). Recorded behavior: passing the key of an existing object (e.g. a single note) as S3Key is refused with code `ResourceNotFoundException` and the message `The input S3 folder specified does not exist` (fixed text), no JobId is minted and nothing appears under that job name in ListPHIDetectionJobs, while passing the FOLDER that holds the same note starts a job and DescribePHIDetectionJob echoes that prefix back in InputDataConfig.S3Key.
  Why/Emulator: the emulator accepted the object key and returned HTTP 200 with JobId `0006615905f42be80000000000000001` — it treats S3Key as an opaque string and performs no input-location resolution, so the folder-vs-key distinction the API is built on does not exist. A client therefore cannot discover against the emulator that per-document keys are not accepted here, and will submit the same request to AWS and get a 404 it never coded for.
  Fix: StartPHIDetectionJob's input validation (src/ops/start_phi_detection_job.rs) — the same prefix-existence check as Cause 5, refusing a prefix with no objects under it AND a value that identifies a single object rather than a folder, with the modelled `ResourceNotFoundException` and the fixed message, before anything is minted or recorded. This is distinct from the open issue 20261029T175936Z-… , which covers the absent-job and absent-role resolution paths of the PHI job handlers.
  Traces: comprehendmedical.start-phi-job-object-key-as-input-folder-rejected.
