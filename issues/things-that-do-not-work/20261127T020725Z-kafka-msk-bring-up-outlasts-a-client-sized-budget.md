# MSK bring-up outlasts a client-sized budget on three more data-plane contracts: consumer-group offset handover, IAM group-scope authorization and per-partition FIFO ordering all reach no verdict (3 causes)

> _Note: this issue was identified against the code base at commit `f9578f32a46d780229c4a74cff5026358aaeb45d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeClusterV2

## Description
THREE net-new root causes on the emulated kafka (MSK) surface. Each is grounded in a failing behavioral check the suite lists under `### kafka` that the report marks NEITHER "ALREADY FILED" nor "OWNED by" an open issue, and each leaves a DIFFERENT data-plane contract unobservable. All three are killed on the harness's bare per-check ceiling (`Error: Check timed out after 60.0s`) with no stack frame, no HTTP status, no AWS Error.Code and not one assertion evaluated: the emulator owns both the control-plane lifecycle transitions these checks poll on (CreateClusterV2 -> DescribeClusterV2 State, UpdateConnectivity, BatchAssociateScramSecret, CreateTopic/DescribeTopic Status) and the native broker behind every address GetBootstrapBrokers advertises, so the stall is the emulator's and not the runner's.

Related open issues name this same family for OTHER check ids and carry none of the three replay keys below: 20261125T225220Z-kafka-msk-bring-up-never-completes-inside-a-client.md, 20261124T060000Z-kafka-msk-asynchronous-spans-outlast-a-client-sized-poll-scram-consume-and-the-cluster-replicator-guards.md, 20261124T075919Z-kafka-msk-end-to-end-cluster-topic-produce-consume.md, 20261118T164608Z-kafka-msk-native-data-plane-the-transactional-abort-isolation.md and 20261114T065925Z-kafka-msk-asynchronous-lifecycles-never-settle-channel-configuration-delete.md. None of them covers the three contracts below, which are the consumer-group offset/coordinator contract, the MSK IAM group-resource authorization split, and per-partition message ordering over a public SASL/SCRAM listener.

=== Cause 1 of 3: the consumer-group committed-offset handover reaches no verdict — the Serverless SASL/IAM bring-up never clears ===
AWS: Smithy kafka CreateClusterV2 (POST /api/v2/clusters; input member Serverless -> ServerlessRequest; output State -> ClusterState) answers CREATING for a Serverless cluster with ClientAuthentication.Sasl.Iam.Enabled=true, and DescribeClusterV2 (GET /api/v2/clusters/{ClusterArn}; output ClusterInfo -> Cluster) reports ACTIVE within a poll or two of an AWS-sized interval; GetBootstrapBrokers (GET /v1/clusters/{ClusterArn}/bootstrap-brokers) then publishes BootstrapBrokerStringSaslIam (jsonName bootstrapBrokerStringSaslIam), whose address accepts TCP, completes TLS and serves SASL_SSL / AWS_MSK_IAM (OAUTHBEARER) on tcp/9098 — MSK Serverless offers no other listener. The contract itself is recorded behavior plus the Apache Kafka group-coordinator protocol: a consumer that reads the first ten records of a single-partition topic and commits through offset 10, then leaves the group, leaves the coordinator reporting next-offset exactly 10 for that group/partition (OffsetFetch); a second consumer joining the SAME group with no explicit seek resumes AT the committed offset and reads only the uncommitted remainder, so nothing is redelivered and nothing is lost, and a committed read does not change the log (end offset stays at the number of records produced).
Emulator: `Error: Check timed out after 60.0s`, nothing asserted. The shared bring-up leg (CreateClusterV2 Serverless -> DescribeClusterV2 ACTIVE -> an advertised SASL/IAM endpoint that accepts TCP, completes TLS and answers a Metadata fetch) does not finish inside the budget, so neither the produce, the two consume sessions, nor the coordinator's OffsetFetch read is ever exercised.
Why: a client relying on MSK's at-least-once consumer-group semantics gets no signal at all. An emulator that loses committed offsets on a rebalance, or redelivers an already-committed record, is indistinguishable here from a correct one, so every consumer written against this emulator is validated against nothing.
Fix: the cluster-lifecycle timing in the kafka crate's state layer (services/service-com-amazonaws-kafka-kafka) — the Serverless CREATING -> ACTIVE span and the publication of bootstrapBrokerStringSaslIam must be consumable by a first or second AWS-sized poll instead of outlasting a client's whole budget — plus the native broker plane behind the advertised SASL/IAM address, specifically its group-coordinator state (JoinGroup/SyncGroup, OffsetCommit, OffsetFetch) and partition log offsets.
Traces: kafka.kafka-consumer-group-offsets-survive-a-rebalance-and-no-record-is-redelivered.

=== Cause 2 of 3: the MSK IAM group-resource authorization split is unobservable — the same Serverless SASL/IAM bring-up never clears ===
AWS: documented MSK IAM access control (https://docs.aws.amazon.com/msk/latest/developerguide/iam-access-control.html) gates the consumer-group actions separately: kafka-cluster:AlterGroup governs JoinGroup/SyncGroup/Heartbeat, kafka-cluster:DescribeGroup governs FindCoordinator and OffsetFetch. So, for an identity whose policy covers only some group-name patterns: subscribe() with a group id covered by NEITHER action is refused with Kafka GROUP_AUTHORIZATION_FAILED (protocol error 30 — a Kafka protocol constant, not an account-varying value) and reads nothing; assign() with that same fully-denied id is ALSO refused with GROUP_AUTHORIZATION_FAILED, because a consumer's first poll() issues FindCoordinator for its group id even when it never joins; assign() with a DescribeGroup-only id SUCCEEDS and reads the record (no JoinGroup fires, so AlterGroup is not needed); subscribe() with that same DescribeGroup-only id still fails with GROUP_AUTHORIZATION_FAILED at JoinGroup; and restoring a fully-authorized group id lets the identical subscribe succeed. The refused reads must leave the log intact — an independent authorized group still finds the one produced record, and the broker still reports end offset 1 for the single partition. Recorded behavior plus the Apache Kafka protocol; the Smithy model carries no member for Kafka-level authorization.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted — the run dies in the same pre-data-plane Serverless SASL/IAM bring-up, so not even the positive control (an authorized group id reading one record back byte-exactly, including its NUL 0x00 and 0xff bytes) is reached, let alone any refusal.
Why: a client that scopes an IAM role to group-name prefixes cannot tell whether the emulator evaluates the group resource at all. A broker that authorizes every JoinGroup, or refuses every one, produces the same result as a correct one here, so an IAM policy developed against this emulator carries no evidence that it denies what it is meant to deny.
Fix: the same Serverless bring-up path as Cause 1, plus the native broker plane's SASL/IAM authorizer — it must evaluate the caller's kafka-cluster group actions per group resource on FindCoordinator and JoinGroup independently and answer GROUP_AUTHORIZATION_FAILED (error 30) without consuming the log.
Traces: kafka.msk-iam-group-scope-denies-a-consumer-group-join-while-an-assigned-read-succeeds.

=== Cause 3 of 3: per-partition FIFO ordering over a public SASL/SCRAM listener reaches no verdict — the provisioned cluster / UpdateConnectivity / SCRAM chain never settles ===
AWS: the whole chain is observable within a client-sized polling budget — ListKafkaVersions shows 3.9.x ACTIVE; CreateConfiguration publishes allow.everyone.if.no.acl.found=false (MSK's precondition for public access); CreateClusterV2 provisioned (kafka.m5.large, 2 brokers, Sasl.Scram + Sasl.Iam, EncryptionInTransit.ClientBroker=TLS, PublicAccess DISABLED, that ConfigurationInfo) -> DescribeClusterV2 State ACTIVE; UpdateConnectivity (PUT /v1/clusters/{ClusterArn}/connectivity; required member CurrentVersion) with ConnectivityInfo.PublicAccess.Type=SERVICE_PROVIDED_EIPS returns a ClusterOperationArn and the cluster returns to ACTIVE; a KMS-encrypted AmazonMSK_* secret is attached with BatchAssociateScramSecret (POST /v1/clusters/{ClusterArn}/scram-secrets); CreateTopic (POST /v1/clusters/{ClusterArn}/topics; required TopicName, PartitionCount, ReplicationFactor; output Status -> TopicState) goes CREATING then DescribeTopic reports ACTIVE; GetBootstrapBrokers then publishes BootstrapBrokerStringPublicSaslScram (jsonName bootstrapBrokerStringPublicSaslScram) on tcp/9196 and the public SASL/IAM string on tcp/9198, where the run's IAM identity grants the SCRAM user ALLOW ALL ACLs via the Kafka CreateAcls API. The contract itself is the Apache Kafka per-partition FIFO guarantee: records produced in sequence to a SINGLE-partition topic are consumed back from the earliest offset in exactly that order.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted — the budget is spent in the create/ACTIVE/UpdateConnectivity/SCRAM/topic-activation waiters before any record is produced, so the ordering assertion is never evaluated.
Why: per-partition ordering is the one guarantee a faked data plane cannot meet, and it is exactly what a client that partitions by key depends on. Here it is unverifiable, and so is the public-access path (UpdateConnectivity to SERVICE_PROVIDED_EIPS and the public SASL/SCRAM bootstrap string) that reaches it.
Fix: the cluster- and topic-lifecycle timing in the kafka crate's state layer (the provisioned CREATING -> ACTIVE span, the UpdateConnectivity operation's return to ACTIVE, the SCRAM-secret association, the topic CREATING -> ACTIVE span and whatever gates bootstrapBrokerStringPublicSaslScram behind them) plus the native broker behind the advertised public SASL/SCRAM address, which must authenticate SCRAM-SHA-512 and append/serve a single partition's log in produce order.
Traces: kafka.topic-partition-message-ordering-preserved.

Note on what is NOT claimed: the 60.0 s figure is this runner's per-check ceiling and the checks' 5/10/15/20/30 s sleeps are their own poll intervals. No particular literal duration is a requirement — the requirement is that each CREATING -> ACTIVE transition, each UpdateConnectivity settle and each advertised endpoint's readiness be observable to a client polling at an AWS-sized interval, as they are on real MSK.
