# logs anomaly-detector and KMS-key paths diverge: ListLogAnomalyDetectors reports ANALYZING and omits defaults, AssociateKmsKey misclassifies an unusable key

> _Note: this issue was identified against the code base at commit `23d7c3ca3e68cb70ca93342274fc19d1394baa26`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListLogAnomalyDetectors

## Description
Two net-new root causes in the CloudWatch Logs surface. The shared fault is that a response the client branches on carries the emulator's own value instead of the service's: a lifecycle state and its modeled defaults on the anomaly-detector read path, and the error class plus message on the AssociateKmsKey refusal path. Cause count: 2 — both must be closed.

Neither cause is owned by an existing issue. The open issue 20261029T222444Z-logs-destinations-and-anomaly-detectors-missing-validation-and.md carries a RELATED but different cause (its cause 10, keyed logs|GetLogAnomalyDetector|2xx->2xx|$.anomalyDetectorStatus, replayed from logs-log-anomaly-detector-lifecycle#task#5) covering the GetLogAnomalyDetector single-item read reporting INITIALIZING. Cause 1 below is the ListLogAnomalyDetectors collection read, which reports a DIFFERENT wrong value (ANALYZING, not INITIALIZING) and additionally drops evaluationFrequency, and it carries its own replay key — closing that issue does not exercise or close this one.

=== Cause 1 of 2: ListLogAnomalyDetectors reports a freshly created detector as ANALYZING and omits anomalyVisibilityTime and evaluationFrequency ===
AWS: a detector listed shortly after CreateLogAnomalyDetector is still training, so AnomalyDetector.anomalyDetectorStatus is 'TRAINING'. Smithy: AnomalyDetectorStatus is an enum of INITIALIZING | TRAINING | ANALYZING | FAILED | DELETED | PAUSED; ANALYZING is the post-training steady state, not the state of a detector that has just been created. AWS also populates the two members that carry the detector's defaulted configuration on every element of the list: anomalyVisibilityTime (Smithy @range min 7, max 90; AWS defaults it to 7 when the create request omits it) and evaluationFrequency (Smithy enum ONE_MIN | FIVE_MIN | TEN_MIN | FIFTEEN_MIN | THIRTY_MIN | ONE_HOUR; AWS defaults it to FIVE_MIN). Smithy: AnomalyDetector members anomalyDetectorStatus, anomalyVisibilityTime, evaluationFrequency; ListLogAnomalyDetectors output anomalyDetectors: AnomalyDetectors, paginated items=anomalyDetectors.
Emulator: answers HTTP 200 but the element reports anomalyDetectorStatus 'ANALYZING', and omits anomalyVisibilityTime and evaluationFrequency entirely. Note the emulator is also self-inconsistent: on the single-item GetLogAnomalyDetector path it reports 'INITIALIZING' for the same detector, so the two read paths of one resource disagree.
Why: a client that polls ListLogAnomalyDetectors and waits for 'TRAINING' before proceeding waits forever on a status the emulator never produces, while a client that treats 'ANALYZING' as "model is trained, anomalies are being reported" proceeds too early. Because evaluationFrequency and anomalyVisibilityTime are absent, a client that reads back the detector's configuration to display or to re-submit in UpdateLogAnomalyDetector sees no value where AWS always supplies the default, and cannot distinguish "defaulted" from "unset".
Fix: the anomaly-detector state and the ListLogAnomalyDetectors serializer in the logs crate — seed the detector's initial status as TRAINING, default anomalyVisibilityTime to 7 and evaluationFrequency to FIVE_MIN at create time, and project all three members onto every AnomalyDetector element of the list (the same state the Get path reads, so the two agree).
Traces: logs-log-anomaly-detection-workflow#task#3 (also logs-log-anomaly-detection-workflow#task#6). The creationTimeStamp/lastModifiedTimeStamp differences in the same cluster are per-run clock values and are NOT part of this cause.

=== Cause 2 of 2: AssociateKmsKey with a KMS key that cannot be used answers InvalidParameterException with no Message ===
AWS: associating a kmsKeyId that does not exist, or that the caller is not allowed to use with the target log group, is refused HTTP 400 with error code AccessDeniedException and the message "The specified KMS key does not exist or is not allowed to be used with Arn '<resourceArn>'". The fixed text is "The specified KMS key does not exist or is not allowed to be used with Arn " followed by the single-quoted ARN; the one variable part is the ARN of the resource named by the request (the log group's ARN, derived from logGroupName / resourceIdentifier and the caller's account and region). The recorded body carries it under the key `Message`. Smithy: AssociateKmsKey input kmsKeyId is @required (length 0..256), logGroupName and resourceIdentifier identify the target; com.amazonaws.cloudwatchlogs#AccessDeniedException is modeled as a client error defaulting to HTTP 400 with a `message` member, and is a service-common error not listed among AssociateKmsKey's declared errors (InvalidParameterException, OperationAbortedException, ResourceNotFoundException, ServiceUnavailableException) — so the recorded response is the authority for the class and text here; recorded behavior only for the choice of AccessDeniedException over the declared InvalidParameterException.
Emulator: answers HTTP 400 but with `__type` 'InvalidParameterException' and NO `Message` member at all, so the response states neither the correct error class nor any explanation.
Why: a client distinguishing an authorization/key-usability failure (retry after fixing the key policy or grant, surface a permissions error to the operator) from a malformed-parameter failure (fix the request) branches on the error code and takes the wrong path. With the message member absent the caller also cannot tell which key or which log group ARN was rejected, which is the only actionable detail in the refusal.
Fix: the kmsKeyId resolution/authorization branch of the AssociateKmsKey handler in the logs crate — raise AccessDeniedException and populate the message from AWS's template with the target resource's ARN, rather than a bare InvalidParameterException.
Traces: logs-log-group-kms-and-data-protection#task#7 (also logspc-kms-key-associate-disassociate#task#3).
