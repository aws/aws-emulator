# sagemakertrainingsessionruntime: SampleTrainingSessionWithResponseStream refuses a Running session with 409 ConflictException because it demands a saved checkpoint, so the inference body is never validated and no stream is ever served

> _Note: this issue was identified against the code base at commit `f73c567c518c4ea32fbc68f3ca5cb3fd81df2cf2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SampleTrainingSessionWithResponseStream

## Description
One net-new behavioral root cause (Cause 1 of 1).

Cause 1 of 1: the streaming inference operation invents a precondition AWS does not have — it refuses any session that holds no emulator-written checkpoint with a 409 ConflictException — so a healthy Running session's stream request never reaches the body validation AWS performs and never opens a stream at all.
Failing checks: sagemakertrainingsessionruntime.stream-reports-session-not-found-once-training-session-deleted and sagemakertrainingsessionruntime.sample-training-session-stream-stopped-session-rejected-with-conflict.
AWS:      Smithy (com.amazonaws.sagemakertrainingsessionruntime#LegoRouterService, restJson1): SampleTrainingSessionWithResponseStream POST /training-sessions/{trainingSessionName}/sample-with-response-stream, input {trainingSessionName (required), body (InferenceBody), contentType, accept, modelPackageArn}, output {body (SampleResponseStream, required), contentType}; documented as "Streams inference responses from the model associated with the specified training session... The service passes the request body to the model without modification." SampleResponseStream: "delivered as Server-Sent Events (text/event-stream). Each event is a `data: {JSON}` line containing a chat completion chunk, and the stream is terminated by `data: [DONE]`... Errors that occur before streaming starts are returned as the operation's errors." ConflictException (409) is documented as "The training session is in a state that cannot accept new operations. The session must be in Running or Blocked state to accept requests" — i.e. the 409 is about the session's LIFECYCLE STATE, not about whether a checkpoint has been written; the model nowhere makes a saved checkpoint a precondition of inference, and ModelConfig.BaseModelArn already gives the session a model. Recorded behavior: for a session the control plane reports Running, the request reaches the model server's own body validation — a body that names no `model` is refused with HTTP 400, error code `ValidationException`, message "model is required" (fixed text; the member name `model` is the body field that is absent) — and a body that does name a model is answered 200 with contentType text/event-stream and a sequence of `data: {"object": "chat.completion.chunk", ...}` events whose last usage chunk reports 0 < completion_tokens <= the request's max_tokens, terminated by `data: [DONE]`. A name no session was ever created for is still refused first with 404 ResourceNotFoundException "Session not found: <trainingSessionName>", and a session that has been stopped with 409 ConflictException "Session is in Stopped state and cannot accept requests".
Emulator: every stream request against a session whose runtime record holds no checkpoint is refused with 409 `ConflictException` and the emulator's own message "Training session <trainingSessionName> has no model checkpoint to sample from: write one with a saveWeights or saveState operation, or name a model package on the X-Amzn-SageMaker-Model-Package header." (src/state.rs:1264-1276 `no_checkpoint_to_sample`, reached from crate::state::resolve_sample_checkpoint, which src/ops/sample_training_session_with_response_stream.rs:196-233 maps onto ConflictException). The refusal happens before any body validation, so the modelled ValidationException "model is required" is unreachable, and because this is the documented RETRYABLE condition for a session whose backend is still warming up, a client's bounded ConflictException retry loop spins until it gives up: that is what makes the second check above exhaust its 60 s budget ("Check timed out after 60.0s") on the very first stream open against a Running session, before it can even reach its stopped-session assertion.
Why:      the streaming data plane is unusable: no caller can ever open a stream, because the only way past the refusal is to write a checkpoint through a training operation this emulator does not execute. Worse, the refusal is reported in the one error class clients are told to RETRY (ConflictException = session not ready yet), so every client and test harness turns a permanent refusal into a retry storm and then a timeout instead of a deterministic error; and the two refusal classes AWS does serve here (400 ValidationException for a malformed inference body, 409 only for a lifecycle state) are both mis-reported.
Fix:      the shared checkpoint resolution in the service's state (crate::state::resolve_sample_checkpoint) and both inference handlers must stop treating "no checkpoint written yet" as a conflict: a session the control plane reports Running or Blocked must resolve to its ModelConfig base model and proceed, reserving ConflictException for a session whose TrainingSessionStatus is not Running/Blocked (message "Session is in <State> state and cannot accept requests") and ResourceNotFoundException for a name the control plane does not hold or a modelPackageArn that is not one of the session's checkpoints. The streaming handler must then validate the inference body (a body with no `model` -> 400 ValidationException "model is required") and frame its answer as the documented SSE stream: contentType text/event-stream, `data:` events carrying objects of type chat.completion.chunk with a usage chunk whose completion_tokens is in (0, max_tokens], terminated by `data: [DONE]` — not the single explanatory chunk crate::state::sample_response_stream_body builds today.

## Steps to Reproduce
1. git clone the repo and boot the emulator built from it.
2. Create the prerequisites: an IAM role trusted by training-session.sagemaker.amazonaws.com, an S3 output bucket, and a SageMaker model package group.
3. sagemaker CreateTrainingSession with LoraConfig, RoleArn, ModelConfig{BaseModelArn=<SageMakerPublicHub gpt-oss-20b model>, AcceptEula=true}, OutputConfig.S3Location and ModelPackageGroupArn; poll DescribeTrainingSession until TrainingSessionStatus == "Running".
4. POST /training-sessions/<session>/sample-with-response-stream (SampleTrainingSessionWithResponseStream) with contentType=application/json and a JSON body that names no `model` (e.g. {"messages": [...], "max_tokens": 12, "stream": true}) -> observe 409 ConflictException "Training session <session> has no model checkpoint to sample from: ...", where AWS answers 400 ValidationException "model is required".
5. Repeat with a body that DOES name a model ({"model": "openai/gpt-oss-20b", "messages": [{"role": "user", "content": "Name one primary color."}], "max_tokens": 12, "stream": true}) -> observe the same permanent 409 ConflictException, where AWS answers 200 contentType text/event-stream with `data: {..."object": "chat.completion.chunk"...}` events (a usage chunk with 0 < completion_tokens <= 12) terminated by `data: [DONE]`. A client that retries ConflictException as the documented transient backend-not-ready condition never succeeds.
6. Re-run the behavioral checks sagemakertrainingsessionruntime.stream-reports-session-not-found-once-training-session-deleted and sagemakertrainingsessionruntime.sample-training-session-stream-stopped-session-rejected-with-conflict.
