# connect-contact-lens: 2 net-new causes block the real-contact segment-lookup checks — connect DescribeContact is an unimplemented 501 stub, and a new instance's default CONTACT_FLOW inventory holds only one sample flow

> _Note: this issue was identified against the code base at commit `b2bfeaac456e7e589126ea50cb0c365f97af1ebe`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeContact

## Description
This issue bundles 2 net-new root causes, both reached from the suite's `connect-contact-lens` heading. All three failing checks here build a real contact on a freshly created Amazon Connect instance and then grade ListRealtimeContactAnalysisSegments' no-analysis refusal; none of them ever reaches that lookup, because the Connect setup calls diverge first. The defects therefore live in the connect service crate but are grounded in connect-contact-lens checks, which is the heading the suite reports them under. Neither cause was marked ALREADY FILED or OWNED by the suite.

Cause 1 of 2: connect DescribeContact answers HTTP 501 NotImplemented, so the control step of every chat-contact check aborts (failing checks: connect-contact-lens.chat-contact-has-no-voice-analysis-before-or-after-stop, connect-contact-lens.unissued-next-token-on-chat-contact-rejected).
AWS: DescribeContact is a published control-plane read (Smithy com.amazonaws.connect#DescribeContact, GET /contacts/{InstanceId}/{ContactId}, success 200; input InstanceId @required @httpLabel len 1..100 and ContactId @required @httpLabel len 1..256; output member Contact of shape Contact). For a contact that exists in the named instance it answers 200 with that Contact structure (its Id, Channel, InitiationMethod, and DisconnectTimestamp once the contact has ended); an absent contact or a bad input is refused with one of the operation's modeled errors (ResourceNotFoundException 404, InvalidRequestException 400, InvalidParameterException 400, ThrottlingException 429, InternalServiceException 500). NotImplemented is not an error code AWS emits for a published operation, and 501 is not a status it returns.
Emulator: the call answers HTTP 501 with code NotImplemented and the message "operation DescribeContact is scaffolded but not implemented in this emulator". services/service-com-amazonaws-connect-amazonconnectservice/src/ops/describe_contact.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED:` marker (line 4) and its handle() returns the scaffold error.
Why: a client cannot read back a contact it just started — the ordinary way to learn a chat's channel, initiation method and disconnect instant — and an SDK sees an unmodeled error class for a documented call. Downstream it makes a whole negative class of Contact Lens unreachable: neither check gets to grade that ListRealtimeContactAnalysisSegments on a chat contact with no voice analysis answers 404 ResourceNotFoundException with the fixed sentence "Real-time contact analysis not found." (whole message fixed text, naming neither instance nor contact), with no NextToken and with a well-formed but unissued NextToken, nor that a blank NextToken is instead refused 400 InvalidRequestException with the request-body constraint sentence the check records. An open issue names this same stub for a different service and replay key — 20261127T101140Z-connectparticipant-the-cancelparticipantauthentication-unissued-session-check-cannot-reach.md (Issue-Key connectparticipant|DescribeContact|NotImplemented) — and does not carry these two connect-contact-lens checks.
Fix: the operation's handler, services/service-com-amazonaws-connect-amazonconnectservice/src/ops/describe_contact.rs — resolve the instance and contact from the connect crate's contact state, serialize the modeled Contact, refuse an unknown contact id with the operation's modeled not-found error, and delete the SCAFFOLDED marker line.
Traces: connect-contact-lens.chat-contact-has-no-voice-analysis-before-or-after-stop, connect-contact-lens.unissued-next-token-on-chat-contact-rejected.

Cause 2 of 2: a new CONNECT_MANAGED instance is seeded with only ONE flow of type CONTACT_FLOW, so the sample flows a caller discovers to route a task contact to are absent (failing check: connect-contact-lens.task-contact-segment-lookup-not-found).
AWS: ListContactFlows (Smithy com.amazonaws.connect#ListContactFlows, GET /contact-flows-summary/{InstanceId}, output ContactFlowSummaryList, paginated) answers 200 from the instance's own inventory. A new instance is stood up as a complete contact center and ships with a SET of sample flows of type CONTACT_FLOW — not one — among them the queue-configurations sample the check selects by name; the Smithy model states the operations but not the inventory, so for the inventory itself this is recorded/documented behavior only (Amazon Connect Administrator Guide, "Sample flows"). The requirement is that filtering ContactFlowTypes=["CONTACT_FLOW"] on a fresh instance yields the sample CONTACT_FLOW set, with exactly one summary per distinct sample name, so a name lookup over the pages resolves to a single Id usable as StartTaskContact's ContactFlowId. The particular ids are per-instance values, never part of the requirement.
Emulator: crate::state::DEFAULT_CONTACT_FLOWS (services/service-com-amazonaws-connect-amazonconnectservice/src/state.rs lines 262-299) holds 9 defaults of which exactly one has flow_type "CONTACT_FLOW" ("Sample inbound flow (first contact experience)"); the other eight are the AGENT_HOLD/AGENT_WHISPER/CUSTOMER_HOLD/CUSTOMER_QUEUE/CUSTOMER_WHISPER/OUTBOUND_WHISPER/AGENT_TRANSFER/QUEUE_TRANSFER defaults. seed_instance_defaults (same file, ~line 1642, called from create_instance.rs line 249) writes exactly that set, so ListContactFlows(ContactFlowTypes=["CONTACT_FLOW"]) answers 200 with a one-entry ContactFlowSummaryList and any other sample flow name resolves to nothing. The check aborts with `AssertionError: a new instance should hold one 'Sample queue configurations flow', got []`.
Why: a client that discovers a sample flow to start a non-voice contact on a fresh instance finds only the inbound sample, so the normal Connect bootstrap path for task/queue routing is unavailable; here it also leaves Contact Lens's task-contact refusal ungraded — the check never reaches StartTaskContact, DescribeContact on the TASK contact, or the assertion that ListRealtimeContactAnalysisSegments for a task contact answers 404 ResourceNotFoundException with "Real-time contact analysis not found.". A fixed issue covers the earlier, coarser version of this gap — 20261022T172040Z-connectcampaigns-connect-createinstance-provisions-no-default-resources-a-new.md, whose requirement was only that the list be non-empty; the list is non-empty now, and this cause is the remaining divergence: the seeded CONTACT_FLOW-type sample inventory is incomplete. No status or code diverges here; the divergence is the contents of a 200 response.
Fix: the instance-default seeding in the connect crate's state (DEFAULT_CONTACT_FLOWS and seed_instance_defaults in services/service-com-amazonaws-connect-amazonconnectservice/src/state.rs), extended to the sample CONTACT_FLOW-type flows a new instance ships with, so ListContactFlows/DescribeContactFlow answer for each from storage.
Traces: connect-contact-lens.task-contact-segment-lookup-not-found.
