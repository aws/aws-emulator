# ebs: 3 net-new causes — CompleteSnapshot words the out-of-enum ChecksumAlgorithm refusal itself, its constraint-walk refusals carry a Reason AWS omits, and both block listings word the unissued-page-token refusal themselves

> _Note: this issue was identified against the code base at commit `5cb989982ca164b028438556d2b2a85d4de8b473`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CompleteSnapshot

## Description
Three distinct root causes in the ebs data plane, all about the refusal bodies a client branches on. Each is numbered with its own failing check ids; all three must be closed.

Cause 1 of 3: an out-of-enum `ChecksumAlgorithm` on CompleteSnapshot is refused with the service's own sentence instead of the modeled enum constraint walk.
AWS: Smithy `CompleteSnapshotRequest$ChecksumAlgorithm` targets `com.amazonaws.ebs#ChecksumAlgorithm`, an enum whose only value is SHA256 (@length 0..32, @pattern ^[A-Za-z0-9]+$); error `ValidationException` (HTTP 400). A value that satisfies length and pattern but is not in the enum is refused with the framework constraint-walk message: fixed text "1 validation error detected: Value '" + the rejected value from the request + "' at 'checksumAlgorithm' failed to satisfy constraint: Member must satisfy enum value set: [SHA256]" — the member path and the admitted value set are fixed text, only the rejected value comes from the request — and the response carries NO `Reason` member.
Emulator: answers HTTP 400 ValidationException with its own sentence "Unsupported Checksum Algorithm 'SHA1', supported algorithms are SHA256" (fixed text "Unsupported Checksum Algorithm '" + request value + "', supported algorithms are SHA256") and additionally sets Reason = "INVALID_PARAMETER_VALUE".
Why: a client matching the standard AWS constraint-walk wording (or parsing the member path out of it) does not recognise the refusal, and a client branching on the presence of `Reason` sees a reason AWS never sends for this class.
Fix: the `CompleteSnapshot` handler's own ChecksumAlgorithm judgement and the shared message helper it calls — the enum member belongs back on the request boundary's constraint walk (remove it from the operation's `skip_validation`) so the modeled enum produces the refusal, rather than being re-worded in the handler.
Traces: ebs.complete-snapshot-unsupported-checksum-algorithm-rejected. Code: services/service-com-amazonaws-ebs-ebs/src/ops/complete_snapshot.rs:212-224; services/service-com-amazonaws-ebs-ebs/src/state.rs:979-986 (`unsupported_checksum_algorithm_message`); services/service-com-amazonaws-ebs-ebs/src/ops/types/complete_snapshot_types.rs (`skip_validation`). Context: this wording and the attached Reason were introduced by the fixes for 20261120T183501Z-ebs-completesnapshot-error-response.md and 20261119T114443Z-ebs-completesnapshot-parameter-ignored.md, which reasoned from the crate's sibling operation rather than from the recorded refusal; the recording shows AWS refusing through its generic constraint walk here, with no Reason.

Cause 2 of 3: CompleteSnapshot's modeled-form/enum refusals carry a `Reason` where AWS's response has none.
AWS: `ValidationException` has members `Message` (ErrorMessage, @length 0..256) and `Reason` (`ValidationExceptionReason`, values include INVALID_PARAMETER_VALUE and INVALID_PAGE_TOKEN). `Reason` is OPTIONAL and the recording shows it ABSENT for CompleteSnapshot's header constraint refusals: an out-of-enum `ChecksumAggregationMethod` is refused 400 with exactly "1 validation error detected: Value '<value>' at 'checksumAggregationMethod' failed to satisfy constraint: Member must satisfy enum value set: [LINEAR]" and no `Reason` member at all; the snapshot stays `pending` and a subsequent LINEAR completion seals it.
Emulator: produces the right message (it renders the same constraint walk in the handler) but raises it through the service's modeled error with Reason = "INVALID_PARAMETER_VALUE", so the response carries a member AWS does not send. (For comparison, the page-token refusal of ListSnapshotBlocks DOES carry Reason INVALID_PAGE_TOKEN in the recording, so the defect is attaching a Reason to this class, not populating Reason in general.)
Why: a client that branches on `Reason` being present/absent — or that treats INVALID_PARAMETER_VALUE as a distinct, machine-readable class — takes a different path on the emulator than on AWS for the very same request.
Fix: `CompleteSnapshot`'s header validation path — the members whose refusal is a pure modeled-form/enum violation must be refused by the request boundary's envelope (no `Reason`), not re-raised through the handler's `validation("INVALID_PARAMETER_VALUE", ...)`.
Traces: ebs.complete-snapshot-unsupported-aggregation-method-rejected (and the same extra Reason appears on the Cause 1 check). Code: services/service-com-amazonaws-ebs-ebs/src/ops/complete_snapshot.rs:200-224 (`header_constraint_refusal` -> `validation("INVALID_PARAMETER_VALUE", ...)`).

Cause 3 of 3: both block listings word the unissued-page-token refusal themselves instead of AWS's pagination-token sentence.
AWS: `ListSnapshotBlocks` and `ListChangedBlocks` both take `NextToken` -> `com.amazonaws.ebs#PageToken` (@length 0..256, @pattern ^[A-Za-z0-9+/=]+$) and both model `ValidationException` (HTTP 400). A well-formed token the service never issued is refused 400 ValidationException with Reason "INVALID_PAGE_TOKEN" and the message template: fixed text "The pagination token " + the NextToken value from the request + " is invalid." — the only variable part is the rejected token, and the snapshot id does not appear.
Emulator: answers 400 ValidationException with Reason INVALID_PAGE_TOKEN (correct) but the message "NextToken is not a page token this service issued for snapshot <snapshot id>" — its own sentence, which omits the rejected token and interpolates the snapshot id instead. Both listings share the one helper, so both diverge identically.
Why: a client or SDK that surfaces/matches the invalid-pagination-token sentence, or that echoes the offending token back to its caller, gets a different sentence from the emulator and loses the token value entirely.
Fix: the shared page-token refusal message helper used by both listings' pagination resume path — it must word AWS's template around the token the request carried (held to ErrorMessage's @length 0..256 by the crate's existing message fit, since PageToken alone may be 256 characters).
Traces: ebs.list-changed-blocks-unissued-page-token-rejected, ebs.list-snapshot-blocks-unissued-page-token-rejected. Code: services/service-com-amazonaws-ebs-ebs/src/state.rs:1176-1188 (`invalid_page_token_message`) and :1216-1234 (`page_resume_index` / `PageTokenRefusal`).

Cause 1: POST /snapshots {"VolumeSize":1}; PUT one 524288-byte block at index 0 with its correct x-amz-Checksum; POST /snapshots/completion/{SnapshotId} with x-amz-ChangedBlocksCount: 1, x-amz-Checksum-Aggregation-Method: LINEAR and x-amz-Checksum-Algorithm: SHA1. Observe the message is the service's own "Unsupported Checksum Algorithm 'SHA1', supported algorithms are SHA256" with Reason INVALID_PARAMETER_VALUE instead of the enum constraint walk "1 validation error detected: Value 'SHA1' at 'checksumAlgorithm' failed to satisfy constraint: Member must satisfy enum value set: [SHA256]" with no Reason.

Observe the Message matches AWS exactly while the body additionally carries Reason "INVALID_PARAMETER_VALUE"; AWS sends no Reason for this refusal. The snapshot correctly remains `pending`.
