# controlcatalog control reads miss AWS's published catalog: GetControl 404s on published ARNs and a ListControls page comes back empty (2 causes)

> _Note: this issue was identified against the code base at commit `db695ebaafb06a378036ed97fdfaee3dfb3329ce`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetControl

## Description
The emulator serves a locally synthesized ControlCatalog control dataset instead of the catalog AWS publishes, and both of this service's control-read operations diverge as a result: a read by a published control ARN resolves nothing, and a filtered ListControls page that AWS fills with a catalog control comes back with no element at that position. TWO divergence clusters are bundled here, numbered as causes below; BOTH must be closed and re-replayed before this issue is done.

Shared AWS basis (cited once, applies to both causes): Smithy model services/service-com-amazonaws-controlcatalog-controlcatalog/smithy-model/com-amazonaws-controlcatalog-controlcatalog.json. GetControl: POST /get-control, success code 200, @readonly; input GetControlRequest.ControlArn @required (ControlArn, @length 34..2048, @pattern ^arn:(aws(?:[-a-z]*)?):(controlcatalog|controltower):[a-zA-Z0-9-]*::control/[0-9a-zA-Z_\-]+$); output GetControlResponse with Arn, Name, Description, Behavior and RegionConfiguration @required plus Aliases, Severity, Implementation, ParameterRequirementSummary, Parameters, CreateTime, GovernedResources, GovernedProviders; modeled errors AccessDeniedException 403, ResourceNotFoundException 404, ValidationException 400, ThrottlingException 429, InternalServerException 500. ListControls: POST /list-controls, success code 200, @readonly, paginated (inputToken/outputToken NextToken, pageSize MaxResults @range 1..100, items Controls); output ListControlsResponse.Controls is @required. The Control Catalog is an AWS-published, account-independent read-only dataset (its ARNs carry no account or region), so a control ARN AWS publishes must resolve in every account and must appear in the filtered listings that select it; the model gives the field set and the recording gives the catalog content.

Shared Why: a client cannot use the emulator as a stand-in for the catalog. Control Tower / Security Hub / Config tooling enumerates controls and then reads each one by ARN; against the emulator a published ARN is reported as nonexistent, and an enumeration page that AWS fills is empty, so the client concludes the control was withdrawn from the catalog (or that its own ARN is wrong) and skips it — a governance tool silently reports fewer controls than the account actually has available, with no error to signal the gap.

Shared Fix: the ControlCatalog control seed state the service reads (services/service-com-amazonaws-controlcatalog-controlcatalog/src/state.rs) must hold the catalog's own control records keyed by their published ARNs, and the two readers over it — the GetControl handler's ARN lookup (src/ops/get_control.rs) and the ListControls handler's filter-and-page projection (src/ops/list_controls.rs) — must resolve and emit those records rather than emulator-minted ones. This is state/seed-data plus the lookup in each handler; no serializer change is implicated, since the status and shape are otherwise correct.

Cause 1 of 2 — GetControl on a published control ARN is refused as not found (fixture controlcatalog-catalog-get-control, step task#1; 20 steps in the cluster). AWS: GetControl answers 200 with the catalog record for the requested ARN — every @required member populated (Arn, Name, Description, Behavior, RegionConfiguration) plus the optional metadata the catalog publishes for it (Aliases, Severity, Implementation{Type,Identifier}, ParameterRequirementSummary, Parameters, CreateTime, GovernedResources, GovernedProviders). In the recorded run the ARN requested was arn:aws:controlcatalog:::control/1038h7d21e6g8i10g6v3xsssi and the response carried Behavior DETECTIVE, Severity MEDIUM, ParameterRequirementSummary OPTIONAL, Implementation {Type: AWS::Config::ConfigRule, Identifier: COGNITO_USER_POOL_ADVANCED_SECURITY_ENABLED}, Aliases ['CONFIG.COGNITO-IDP.DT.1'], one Parameters entry {Name: SecurityMode, Requirement: OPTIONAL}, and a REGIONAL RegionConfiguration listing the control's deployable regions — those are the recording's values filling the template, not the requirement; the requirement is that a published ARN resolves to the catalog's own record for it. Emulator: HTTP 404 with no response payload at all — every output member is absent. GetControl's only modeled 404 is ResourceNotFoundException, i.e. the emulator reports the control as absent from the catalog. AWS reserves that error for an ARN the catalog does not publish; the correct message for that class names the resource the caller asked for, taking the ARN verbatim from the request (fixed text plus the request's ControlArn as its only variable part), and it must not be returned for an ARN the catalog does publish. Why: as shared above — a direct read of a real control fails, so no client can confirm or inspect a control it discovered elsewhere. Traces: controlcatalog-catalog-get-control#task#1 (representative), and task#2..task#20 of the same fixture.

Cause 2 of 2 — a filtered ListControls page omits the catalog control AWS places at that position (fixture controlcatalog-catalog-list-controls-aws-config-configrule, step task#2; 1285 steps in the cluster). AWS: ListControls with the implementation filter for AWS::Config::ConfigRule answers 200 and the @required Controls list carries, at that page position, the catalog's ControlSummary — in the recording control/6yl9xxuky13vzaxi3n6lm73k5, alias CONFIG.ACM-PCA.DT.2, Behavior DETECTIVE, Severity LOW, ParameterRequirementSummary OPTIONAL, Implementation {Type: AWS::Config::ConfigRule, Identifier: ACMPCA_CERTIFICATE_AUTHORITY_TAGGED}, GovernedResources ['AWS::ACMPCA::CertificateAuthority'], GovernedProviders ['AWS']. Again those values are the recording filling the ControlSummary template; the requirement is that each page of the filtered listing carries the catalog's entries for the controls the filter selects, in a page sequence that walks the whole filtered set. Emulator: status matches (200) but there is no element at that index — $.Controls[0] is reported missing with nothing extra in its place, so the page is shorter than AWS's (empty at that offset): the emulator's synthesized catalog holds fewer AWS::Config::ConfigRule controls than AWS publishes, so once its own entries are consumed the remaining pages of the walk carry nothing. Why: the paginated enumeration terminates early and under-reports the catalog, so a client that drives ListControls to exhaustion sees a fraction of the Config-rule controls the account can actually enable. Traces: controlcatalog-catalog-list-controls-aws-config-configrule#task#2 (representative), plus task#3..task#26 and the remainder of the 1285-step cluster.

Related open issue, which does NOT carry the replay key of either cause above (the replay reports owned_by empty and stub_path empty for both clusters): 20261106T180948Z-controlcatalog-listcontrols-replaces-aws-config-catalog-controls-with-emulator.md describes emulator-minted ControlSummary content for OTHER steps of the same ListControls fixture (its causes are the paired missing/extra signature at task#1, task#153, task#156, ...). That issue does not cover the GetControl 404 cluster, nor the empty-page cluster at task#2. Fixing the catalog seed will likely close all of them, but these two clusters are separate and each must be re-replayed.
