# CodeArtifact external connections ingest nothing: the npm and pypi repository endpoints resolve no upstream package, so pull-through caching and origin upstream=BLOCK are both unobservable (2 causes)

> _Note: this issue was identified against the code base at commit `23d7c3ca3e68cb70ca93342274fc19d1394baa26`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateExternalConnection

## Description
Two net-new root causes in codeartifact, both reached through a repository that has a public external connection associated. Related open issues cover OTHER checks of the same family and do NOT carry these four replay keys: 20261029T095746Z-codeartifact-npm-external-connection-ingests-nothing.md (npm, owns `ingested-package-defaults-to-publish-block-...` and `e2e-external-connection-upstream-fetch-then-disassociate-blocks`) and 20261027T083906Z-codeartifact-reopens-codeartifact-pypi-repository-endpoint-still-ingests-nothing.md (pypi). The four checks below are unowned and are filed here so they are re-replayed when the gap is closed.

Cause 1 of 2: a repository with `public:npmjs` associated resolves nothing on its npm endpoint, so no EXTERNAL-origin version is ever cached and the post-disassociation cached-vs-never-fetched distinction cannot exist.
AWS: Smithy: AssociateExternalConnection POST /v1/repository/external-connection, required members domain/repository/externalConnection, output RepositoryDescription; errors ResourceNotFoundException(404), ConflictException(409), ValidationException(400). The npm registry protocol served on the host GetRepositoryEndpoint(format='npm') returns is recorded behavior only (not modeled): with the GetAuthorizationToken token as the bearer credential, `GET <endpoint>/<package>` for a package held only by the public registry answers HTTP 200 with the packument, every `versions[<v>].dist.tarball` rewritten to that repository's own endpoint; GETting that tarball ingests the version. ListPackageVersions then reports it with `origin.originType` = EXTERNAL and `origin.domainEntryPoint.externalConnectionName` = public:npmjs (Smithy: ListPackageVersions has an `originType` query filter and PackageVersionSummary carries `origin`). Before any fetch, DescribePackage is ResourceNotFoundException with the sentence `Package not found in repository. Package = {format=npm, name=<package>}` — fixed text `Package not found in repository. Package = {format=` + the request's format + `, name=` + the request's package name + `}`. After DisassociateExternalConnection the already-cached version stays retrievable via GetPackageVersionAsset while a sibling version never fetched while the connection was live is refused ResourceNotFoundException(404).
Emulator: the packument GET answers HTTP 404 with body `{"error":"Package not found in repository. Package = {format=npm, name=<package>}"}` for any package no repository inside the domain already holds — the external connection is accepted and echoed by the control plane but is never consulted as a resolution source. Consequently nothing is ingested, no version with originType EXTERNAL ever exists, and the disassociate leg is never reached (one check dies on the unhandled `urllib.error.HTTPError: HTTP Error 404: Not Found` at the packument GET).
Why: pull-through caching is the main reason to attach an external connection. A client validating that `npm install` of a public dependency works through CodeArtifact, that cached versions survive removal of the connection, or that EXTERNAL-origin versions are partitioned from PUBLISHED ones, gets a uniform 404 — or, worse, reads the absence of a blocked package as proof that a restriction is enforced when in fact nothing is ever ingested either way.
Fix: the npm repository-endpoint data-plane resolution path for externally-connected repositories (the npm registry handler and its upstream/external-connection resolution), plus the ingestion that records `origin.originType`/`origin.domainEntryPoint` in package-version state. The existing npm issue records a platform blocker (no outbound network, and hand-written packuments fitted to one recording are not a fix); if that still holds, the honest exit is the documented won't-fix on the npm registry source rather than leaving these checks unowned.
Traces: codeartifact.codeartifact-external-connection-upstream-fetch-then-disassociate-blocks (mismatch — `assert pm_status == 200` with the 404 package-not-found body), codeartifact.external-connection-caches-fetched-package (error — HTTPError 404 on the packument GET).

Cause 2 of 2: the pypi endpoint of an externally-connected repository resolves no PEP 503 index, so the positive control of `PutPackageOriginConfiguration(restrictions={publish: BLOCK, upstream: BLOCK})` never ingests and the restriction's effect is unverifiable.
AWS: Smithy: PutPackageOriginConfiguration POST /v1/package with required domain/repository/format/package/restrictions, output PackageOriginConfiguration; DescribePackage echoes `package.originConfiguration.restrictions`. The pypi protocol on GetRepositoryEndpoint(format='pypi') is recorded behavior only: with HTTP Basic `aws:<authorizationToken>`, `GET <endpoint>simple/<project>/` answers HTTP 200 with a PEP 503 index listing files for an unrestricted project reachable over `public:pypi`, and downloading one of those files ingests that version (ListPackageVersions then returns it). For a project whose restrictions say upstream=BLOCK, nothing is ingested and GetPackageVersionAsset is refused ResourceNotFoundException(404) with the sentence `Package version not found in repo. repoId = '<repoId>', packageCoordinate = 'PackageVersionCoordinateEntity{name=<package>, type=<FORMAT>, version=<version>, displayName=<package>==<version>}'.` — the fixed text is that frame; repoId is the repository's internal id from service state, and name/type/version/displayName come from the request. The upstream restriction must still read BLOCK after the attempt.
Emulator: the control plane legs all succeed (PutPackageOriginConfiguration and DescribePackage report upstream=BLOCK), but the unrestricted CONTROL project's index returns HTTP 404 with no files, and polling ListPackageVersions for it never yields a version (one check reports `the control project's index returned 404 with [] files`; the other exhausts its ingestion budget and raises `TimeoutError: control package ingested from the upstream connection: the run budget ended first`). Because nothing is ever ingested, the blocked project's emptiness is vacuous and the ResourceNotFoundException sentence for the blocked asset is never graded.
Why: a client cannot distinguish an emulator that enforces origin restrictions from one that simply never ingests anything. Dependency-substitution protection — the entire point of upstream=BLOCK — appears to pass while being completely unexercised, and `pip install` of any public project through the repository endpoint 404s.
Fix: the pypi repository-endpoint data-plane (PEP 503 simple-index and file-download handlers) and its external-connection resolution/ingestion path, which must consult the package's `originConfiguration.restrictions.upstream` before ingesting. Same platform blocker as Cause 1 applies; the pypi half is tracked by the REOPENS issue named above, which does not own these two checks.
Traces: codeartifact.codeartifact-package-origin-configuration-blocks-upstream-ingestion (mismatch), codeartifact.package-origin-configuration-blocks-upstream-ingestion (error/TimeoutError; its runner budget ran out only because ingestion never happens).

## Evidence
Cause 1 (npm):
- codeartifact.codeartifact-external-connection-upstream-fetch-then-disassociate-blocks [mismatch]
  Setup all 200: CreateDomain -> CreateRepository -> AssociateExternalConnection(externalConnection='public:npmjs') -> GetRepositoryEndpoint(format='npm') -> GetAuthorizationToken(durationSeconds=900).
  Expected: GET <endpoint><package> -> HTTP 200 packument, dist.tarball rewritten under <endpoint>; tarball GET -> 200 with bytes; the version then appears in ListPackageVersions; after DisassociateExternalConnection the cached version is still downloadable while a never-fetched sibling is ResourceNotFoundException.
  Actual: AssertionError at `assert pm_status == 200` — "the packument for '<package>' through the external connection returned 404: b'{\"error\":\"Package not found in repository. Package = {format=npm, name=<package>}\"}'".
- codeartifact.external-connection-caches-fetched-package [error]
  Same setup; the pre-fetch DescribePackage refusal is as expected, then the packument GET raises `urllib.error.HTTPError: HTTP Error 404: Not Found` instead of returning 200, so the EXTERNAL-origin assertions (origin.originType == 'EXTERNAL', origin.domainEntryPoint.externalConnectionName == 'public:npmjs') are never reached.

Cause 2 (pypi):
- codeartifact.codeartifact-package-origin-configuration-blocks-upstream-ingestion [mismatch]
  Setup all 200: CreateDomain -> CreateRepository -> AssociateExternalConnection('public:pypi') -> PutPackageOriginConfiguration(format='pypi', package=<blocked>, restrictions={publish: BLOCK, upstream: BLOCK}) -> DescribePackage confirms upstream=BLOCK -> GetRepositoryEndpoint(format='pypi') -> GetAuthorizationToken.
  Expected: the unrestricted control project's PEP 503 index -> HTTP 200 with >=1 file, its download -> 200 with bytes, and ListPackageVersions for the control project eventually non-empty; the blocked project stays empty and GetPackageVersionAsset on it -> ResourceNotFoundException with "Package version not found in repo. repoId = '<repoId>', packageCoordinate = 'PackageVersionCoordinateEntity{name=<package>, type=PYPI, version=<version>, displayName=<package>==<version>}'."
  Actual: AssertionError at `assert control_index == 200 and control_files` — "the control project's index returned 404 with [] files, so nothing can be concluded from the blocked project's absence".
- codeartifact.package-origin-configuration-blocks-upstream-ingestion [error]
  Same shape; the control project is re-downloaded on a retrigger loop and ListPackageVersions for it stays empty until the budget ends: `TimeoutError: control package ingested from the upstream connection: the run budget ended first; not graded`. The emptiness is the emulator's: no external-connection ingestion exists for pypi.

3. 5. ca.disassociate_external_connection(...) -> the cached version must stay downloadable via get_package_version_asset while a version never fetched while the connection was live must be refused ResourceNotFoundException.
