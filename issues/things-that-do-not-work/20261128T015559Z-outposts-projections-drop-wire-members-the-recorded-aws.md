# outposts projections drop wire members the recorded AWS response carries: CreateSite SiteId and GetCatalogItem rack descriptors

> _Note: this issue was identified against the code base at commit `429bdfecbf56545571d755c8b6ad852b4e3ed1bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSite

## Description
3 net-new root causes, all one fault: an outposts 2xx body is projected STRICTLY from the members this repo's on-disk Smithy model declares, so every member the recorded AWS wire response carries but the on-disk model does not declare (or that the handler leaves unset) is dropped from the answer. The client sees a 200 whose body is missing fields AWS always sends.

None of these three clusters is owned by an open issue. The closest open issues cover other members/operations and do NOT cover these: 20261127T162729Z-outposts-success-responses-omit-members-aws-always-projects (Site.RackPhysicalProperties, Outpost.SupportedHardwareType, GetPrivateConnectivityConfig body — it says nothing about the top-level CreateSite SiteId, and does not own either CreateSite cluster below), 20261121T145507Z-outposts-listcatalogitems-publishes-an-invented-hardware-catalog-instead (which catalog ListCatalogItems publishes, not which members a CatalogItem has), 20261122T134654Z-outposts-response-projections-diverge-createoutpost-availability-zone-identity (CreateOutpost AvailabilityZoneId, UpdateSite tags) and 20261029T191039Z-outposts-lifecycle-and-precondition-gates-diverge-across-capacity (status/precondition gates).

Cause 1 of 3: CreateSite's 200 body omits the TOP-LEVEL SiteId member, so the minted site id reaches the caller only nested under Site.
AWS: Smithy CreateSite (POST /sites, success 200, errors AccessDeniedException 403 / ConflictException 409 / ServiceQuotaExceededException 402 / ValidationException 400 / InternalServerException 500). smithy_query(query="shape", shape="CreateSiteOutput") shows the on-disk CreateSiteOutput declaring ONE member, Site -> Site{SiteId, AccountId, Name, Description, Tags, SiteArn, Notes, OperatingAddress*, RackPhysicalProperties}. The model therefore says nothing about a top-level SiteId: recorded behavior only. The recording shows the real 200 body carrying SiteId ALONGSIDE Site, holding the same site identifier the response's Site.SiteId reports (an `os-` id matching Site$SiteId's pattern ^(arn:...:site/)?(os-[a-f0-9]{17})$). The requirement is the member's presence and that it equals the created site's id; the particular id value in any one recording is minted per run and is not part of the requirement.
Emulator: 200, same Site, but no top-level SiteId at all. Replay reports `$.SiteId: missing (expected '{{asset_site_id}}', got None)` — the expectation is a fixture variable, i.e. "whatever id this run minted", not a literal. The handler builds `CreateSiteOutput { site: Some(site) }` and comments that "the output declares the created site and nothing beside it, so the minted id reaches the caller exactly once" — i.e. the omission is deliberate and follows the stale model shape.
Why: a client (or SDK-shaped caller, or a CloudFormation-style chain) that reads `createSite().siteId()` to feed the next call gets null and cannot proceed, even though its AWS-recorded flow works; it has to know to dig into the nested Site instead. Fixtures that go on to use the created site id are exactly the ones that break.
Fix: the CreateSite output projection — the CreateSiteOutput construction in the operation handler, plus the output shape/serializer so a top-level SiteId member exists and is populated with the same id written onto the stored Site.
Traces: outposts-assets-and-connection#setup#1 (cluster of 5: also setup#1 of outposts-quote-and-order-lifecycle, outposts-renewal-and-billing, outposts-site-lifecycle and task#1 of outposts-outpost-lifecycle).

Cause 2 of 3: the same CreateSite omission on a request that supplies NO RackPhysicalProperties, where the answered Site loses both the top-level SiteId and the Site.RackPhysicalProperties structure.
AWS: same operation/model evidence as Cause 1, plus Site$RackPhysicalProperties (target RackPhysicalProperties, doc "Information about the physical and logistical details for a rack at the site."). The member is optional in the model, so again recorded behavior only: the recorded 200 for a CreateSite that supplies no rack properties carries RackPhysicalProperties PRESENT as an empty structure, and carries the top-level SiteId. Presence is the requirement, not any enum value inside it.
Emulator: 200, with `$.Site.RackPhysicalProperties: missing (expected {}, got None)` and `$.SiteId: missing (expected '<shaped-not-asserted>', got None)` — the step asserts the SiteId's shape, not a value. The handler assigns `rack_physical_properties: input.rack_physical_properties` straight through, so an omitted input member means an omitted output member, and the output struct has nowhere to put a top-level SiteId.
Why: a client reading `site.rackPhysicalProperties().powerDrawKva()` off a freshly created site faults on a null structure that is non-null against AWS, and "rack properties not yet specified" is indistinguishable from "no such concept"; combined with the missing SiteId, the create response is unusable as the handle for the site.
Fix: the same CreateSite handler projection and the site record it stores — a stored site must always project a present (possibly empty) RackPhysicalProperties and a top-level SiteId, and every later read of the site must use that same projection.
Traces: outposts-cancel-capacity-task-malformed-identifiers#setup#1 (cluster of 3: also setup#1 of outposts-new-outpost-capacity-and-connectivity-reads and outposts-start-capacity-task-unknown-references).

Cause 3 of 3: GetCatalogItem answers a CatalogItem with none of its rack-describing members.
AWS: Smithy GetCatalogItem (GET /catalog/item/{CatalogItemId}, success 200, errors AccessDeniedException 403 / NotFoundException 404 / ValidationException 400 / InternalServerException 500) -> GetCatalogItemOutput{CatalogItem}. smithy_query(query="shape", shape="CatalogItem") shows the on-disk CatalogItem declaring only CatalogItemId, ItemStatus, EC2Capacities, PowerKva, WeightLbs, SupportedUplinkGbps, SupportedStorage, RackScalingType — it declares NO CurrentType, Dimensions, ItemClass, RackUnitHeight or SupportedUplinkGiB, so for those members this is recorded behavior only. The recorded 200 for a published rack SKU carries all five: CurrentType ('AC' for an AC-powered rack), Dimensions ('OUTPOST_RACK'), ItemClass ('RACK'), RackUnitHeight ('HEIGHT_42U') and SupportedUplinkGiB (the same uplink-speed list the item reports in SupportedUplinkGbps). The requirement is that a published catalog item reports these members, each describing that item's own hardware; the specific SKU and numbers in one recording are catalog data, not the template.
Emulator: 200 with a CatalogItem that has the modelled members only — replay reports `$.CatalogItem.CurrentType: missing (expected 'AC', got None)`, `$.CatalogItem.Dimensions: missing (expected 'OUTPOST_RACK', got None)`, `$.CatalogItem.ItemClass: missing (expected 'RACK', got None)`, `$.CatalogItem.RackUnitHeight: missing (expected 'HEIGHT_42U', got None)`, `$.CatalogItem.SupportedUplinkGiB: missing (expected [10, 40, 100], got None)`. The handler reports the stored record whole (`catalog_item: Some(catalog_item)`), so the gap is in the catalog records and the CatalogItem shape they are projected through, not in the lookup.
Why: a client choosing hardware to order filters and displays on exactly these fields — rack vs server (ItemClass), form factor (Dimensions), power type (CurrentType), rack height (RackUnitHeight) and uplink options (SupportedUplinkGiB). Every one reads null, so catalog browsing, SKU selection and order validation built against AWS silently see an untyped, undimensioned item.
Fix: the catalog seed data the store publishes plus the CatalogItem shape/serializer used by GetCatalogItem and ListCatalogItems, so each published item carries these five members with values consistent across both operations.
Traces: outposts-catalog-and-instance-types-browsing#task#2.
