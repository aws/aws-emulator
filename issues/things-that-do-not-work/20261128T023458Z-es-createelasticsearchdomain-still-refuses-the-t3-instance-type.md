# es CreateElasticsearchDomain still refuses the T3 instance-type family from a stale ESPartitionInstanceType enum, blocking 7 of 9 behavioral checks

> _Note: this issue was identified against the code base at commit `7da368b21ee7d04c70045aa1c38fe932bbd09ef4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateElasticsearchDomain

## Description
REOPENS 20261029T185309Z-es-three-net-new-root-causes-createelasticsearchdomain-refuses.md: its fix left the call refused.

The Amazon Elasticsearch Service emulator (crate services/service-com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015) answers, but every domain-scoped behavioral check in this suite is still blocked at its very first CreateElasticsearchDomain call by the same stale instance-type enum the resolved issue above claimed to close. 1 cause is filed here; it must be closed.

Cause 1 of 1: CreateElasticsearchDomain refuses a valid T3 instance type because the service's instance-type enum omits the t3.* family (failing checks es.associate-package-rejected-on-processing-domain-leaves-association-unset, es.describe-domains-batch-scoped-to-requested-names-only, es.domain-tag-lifecycle-add-list-remove, es.duplicate-create-domain-returns-existing-config-unchanged, es.es-index-document-search-roundtrip, es.get-compatible-versions-reflects-created-domain-version, es.index-name-uppercase-rejected-lowercase-control-indexes).

AWS: CreateElasticsearchDomain accepts ElasticsearchClusterConfig.InstanceType = "t3.small.elasticsearch" for an ElasticsearchVersion 7.10 domain and answers HTTP 200 with DomainStatus. The T3 burstable family (t3.small.elasticsearch, t3.medium.elasticsearch) is a generally-available Amazon ES instance type and is a member of ESPartitionInstanceType in the current AWS model. Recorded behavior: all seven checks create a domain with ElasticsearchClusterConfig={"InstanceType": "t3.small.elasticsearch", "InstanceCount": 1}, EBSOptions={EBSEnabled:true, VolumeType:"gp2", VolumeSize:10} and then proceed to assert on the created domain, i.e. real AWS returned 200 for exactly this request shape. Smithy (as checked in, re-verified at this commit): smithy_query(query="shape", shape="ESPartitionInstanceType", model_path="services/service-com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015/smithy-model/com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015.json") still returns 58 values, running from m3.medium.elasticsearch to i3.16xlarge.elasticsearch with NO t3.* member; ElasticsearchClusterConfig.InstanceType and .DedicatedMasterType both target that enum. The checked-in model slice is older than the API it emulates, so the framework's model-driven pre-handler constraint validation rejects a value AWS accepts.

Emulator: the request is refused with HTTP 400, error code ValidationException and the message "1 validation error detected: Value 't3.small.elasticsearch' at 'elasticsearchClusterConfig.instanceType' failed to satisfy constraint: Member must satisfy enum value set: [i3.2xlarge.elasticsearch, m5.4xlarge.elasticsearch, ... m4.4xlarge.elasticsearch]". In that message the fixed text is "1 validation error detected: Value '<value>' at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [<members>]"; the quoted value and the member path come from the request and the member list comes from the model — none of those are requirements of a single run. The message SHAPE is AWS-like; the defect is that the call is refused at all, so no domain is ever created and no 2xx DomainStatus is ever served.

Why: a client that creates a T3 domain — the cheapest class, and the one every tutorial, CI harness and cost-capped test fixture uses — cannot create any domain at all. Everything downstream of a domain is therefore unreachable against the emulator: AddTags/ListTags/RemoveTags, DescribeElasticsearchDomains, GetCompatibleElasticsearchVersions, AssociatePackage/ListPackagesForDomain/ListDomainsForPackage, and the whole signed data plane on the domain endpoint (index, _refresh, _search, GET _doc). Provisioning code that relies on AWS accepting a T3 cluster config fails at step one with an input-validation error it cannot correct, because the instance type it names is in fact valid.

Fix: the service's checked-in Smithy model slice — ESPartitionInstanceType must carry the full current member set including the t3.* family — so the framework's enum validation stops refusing instance types AWS accepts. No change is needed in the handler body, which never inspects the instance type. Note that the two further causes the resolved issue bundled (the duplicate-create echo in CreateElasticsearchDomain's existing-domain branch, and the state behind the data-plane checks) remain MASKED by this refusal and cannot be verified until the call returns 200, so the checks listed above must be re-replayed in full after this is fixed rather than assumed closed.
