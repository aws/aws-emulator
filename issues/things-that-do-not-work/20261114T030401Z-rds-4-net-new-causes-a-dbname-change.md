# rds: 4 net-new causes — a DBName change set is classified non-replacing, SwitchoverReadReplica answers 501, a read replica reuses its source's endpoint address, and the oracle-ee replica lifecycle never progresses

> _Note: this issue was identified against the code base at commit `3c44e49694959b3de2a0545e79b8c4fbe0cf166e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SwitchoverReadReplica

## Description
4 net-new root causes in the rds service. None of the five checks below is marked OWNED or ALREADY FILED in the replay report; every other failing rds check in this run is.

Cause 1 of 4: a CloudFormation change set classifies a DBName-only change on AWS::RDS::DBInstance as a non-replacing modification.
AWS: DBName on AWS::RDS::DBInstance is an immutable property — the CloudFormation resource reference documents it as "Update requires: Replacement". So an UPDATE change set that changes only the DBName parameter lists exactly one change, LogicalResourceId of the DBInstance, with Action "Modify" and Replacement "True"; executing it creates a new instance (new Ref, new DbiResourceId, new Endpoint.Address) serving the new, empty database, while the change set itself leaves the live instance untouched. The RDS Smithy model carries no CloudFormation update semantics (recorded behavior only for the plan's shape); the modeled surface involved is CreateDBInstance/DescribeDBInstances returning DBInstance.DBName and DBInstance.DbiResourceId.
Emulator: DescribeChangeSet returns the single DBInstance change with Action "Modify" but Replacement "False" — the plan says the DBName change is applied in place.
Why: a client reads Replacement off a change set precisely to gate a destructive update (CI approval steps, CDK diff, manual review). Told "False", it executes what it believes is a harmless property update and either silently keeps the old database and endpoint or destroys data it was never warned about; the standard plan-then-approve-then-execute workflow becomes unsound for RDS instances.
Fix: the change-set classifier for AWS::RDS::DBInstance in the CloudFormation resource handler's update-requires metadata — DBName must be marked replacement-requiring so the computed ResourceChange carries Replacement "True" (and RequiresRecreation Always on that property target). None of the open CloudFormation replacement issues (e.g. 20261111T110051Z-cloudformation-lambda-sqs-a-batchsize-only-change-to.md, 20261110T232651Z-cloudformation-sqs-an-update-that-replaces-a-resource.md) names AWS::RDS::DBInstance or the DBName property.
Traces: rds.deploy-rds-2-cfn-mysql-sql-then-dbname-change-replaces-instance.

Cause 2 of 4: SwitchoverReadReplica is an unimplemented scaffold stub, so it answers 501 NotImplemented where AWS refuses with a parameter-validation error.
AWS: SwitchoverReadReplica "Switches over an Oracle standby database in an Oracle Data Guard environment, making it the new primary database." It is only supported for Oracle read replicas; for a plain same-Region RDS for PostgreSQL read replica AWS refuses with HTTP 400, error code InvalidParameterValue (the service-common parameter-validation code; the operation additionally models DBInstanceNotFoundFault → 404 DBInstanceNotFound and InvalidDBInstanceStateFault → 400 InvalidDBInstanceState) and the message "You can't switch over the DB instance <DBInstanceIdentifier> because the operation is not supported for <engine> engine." In that message the fixed text is "You can't switch over the DB instance " … " because the operation is not supported for " … " engine."; the variable parts are the replica's DBInstanceIdentifier taken from the request and the engine name taken from that instance's state ("postgres" for the replica this check builds). On a supported Oracle replica the operation instead succeeds and exchanges the primary/standby roles.
Emulator: HTTP 501 with error code 'NotImplemented'. The handler services/service-com-amazonaws-rds-amazonrdsv19/src/ops/switchover_read_replica.rs still carries the SCAFFOLDED marker and returns Scaffolded::not_implemented("SwitchoverReadReplica").
Why: a client cannot tell "this engine does not support switchover" from "the service is broken" — error-class handling (retry vs. abort vs. surface a validation message) goes the wrong way — and an Oracle Data Guard role transition cannot be performed at all.
Fix: implement the SwitchoverReadReplica handler (that one file): refuse an unsupported engine with the InvalidParameterValue message above, refuse an unknown identifier with DBInstanceNotFoundFault and a non-available instance with InvalidDBInstanceStateFault, and on a supported Oracle replica exchange the source/replica roles and return the DBInstance. The open stub issue 20261109T135215Z-rds-switchoverbluegreendeployment-stub.md is a DIFFERENT operation (SwitchoverBlueGreenDeployment) and does not cover this one; the report left this check unowned.
Traces: rds.read-replica-promote-and-switchover.

Cause 3 of 4: a read replica publishes the same Endpoint.Address as its source instance.
AWS: every DB instance, read replica included, gets its own endpoint — Smithy CreateDBInstanceReadReplica returns a DBInstance whose Endpoint (Address/Port/HostedZoneId) is that replica's own per-instance address, distinct from the source's, which is the whole point of a replica: readers are pointed at it while writers stay on the primary.
Emulator: DescribeDBInstances for the replica returns an Endpoint.Address identical to the source instance's address (both instances advertise the same host; in this run the shared value was the loopback '127.0.0.1' — the particular host is a per-environment value, the defect is that two distinct instances publish one address).
Why: a reader dialled at the replica's advertised endpoint lands on the primary. Everything that distinguishes a replica then silently disappears: the replica does not refuse writes (no read-only refusal), pg_is_in_recovery()/replication-lag observations describe the primary, and an uncommitted primary write is visible where AWS would hide it. Code that is correct against AWS writes to what it believes is a standby.
Fix: endpoint assignment in the CreateDBInstanceReadReplica handler and the instance endpoint publisher in the RDS service state — allocate the replica its own address (an address the emulator itself serves) instead of copying the source instance's.
Traces: rds.read-replica-replication-query-and-promote, rds.replica-uncommitted-primary-write-absent-until-commit.

Cause 4 of 4: the oracle-ee primary + mounted read replica lifecycle never progresses, so the flow exhausts its budget in a Describe poll with nothing refused.
AWS: CreateDBInstance for engine oracle-ee (LicenseModel bring-your-own-license, gp3) returns an instance that autonomously and promptly reaches DBInstanceStatus "available" with no PendingModifiedValues; CreateDBInstanceReadReplica with ReplicaMode "mounted" likewise reaches "available", reports ReadReplicaSourceDBInstanceIdentifier = the source and StatusInfos[0].Status "replicating"; a subsequent ModifyDBInstance(BackupRetentionPeriod=1, ApplyImmediately=true) settles back to "available" with BackupRetentionPeriod > 0. These are advance-to-terminal-state contracts, not error contracts — AWS never parks the resource.
Emulator: the check ends as "Check timed out after 60.0s". No error code and no non-2xx is returned at any point; the check's own waits are 2400 s/600 s at 15-30 s intervals, so the harness budget, not its own deadline, ends it — the terminal state simply never arrives while it polls DescribeDBInstances.
Why: the wait-until-available idiom every AWS waiter, CDK deployment and CloudFormation provisioning step uses never returns, so a client hangs instead of failing fast; no Oracle Data Guard topology can be built.
Fix: the state progression for an oracle-ee DB instance and for a mounted read replica in the RDS service state (the CreateDBInstance / CreateDBInstanceReadReplica paths and the pending-modification applier) must drive the instance to "available" with cleared PendingModifiedValues and populate the replica's StatusInfos "read replication" entry, as the create paths that do pass already do. Open issue 20261112T074631Z-rds-snapshot-copy-restore-read-replica-flows-never.md describes the same never-reaches-available shape for snapshot copy/restore and a PostgreSQL replica, but does not carry this check's replay key and the report left it unowned, so it is filed here; one fix in the progression may close both.
Traces: rds.read-replica-promote-lifecycle.

## Evidence
Cause 1 — rds.deploy-rds-2-cfn-mysql-sql-then-dbname-change-replaces-instance: after a mysql AWS::RDS::DBInstance stack is CREATE_COMPLETE and serving SQL, CreateChangeSet(ChangeSetType=UPDATE, UsePreviousTemplate=true, Parameters=[DBName=appb]) yields one change for LogicalResourceId "DBInstance" with Action "Modify". Expected Replacement == "True"; actual: AssertionError: DBInstance Replacement was 'False', expected 'True'.

Cause 2 — rds.read-replica-promote-and-switchover: a postgres primary and a read replica are created, the replica reaches available with StatusInfos "read replication" = replicating, then rds.switchover_read_replica(DBInstanceIdentifier=<replica>). Expected: HTTP 400, Error.Code "InvalidParameterValue", Error.Message "You can't switch over the DB instance <replica-id> because the operation is not supported for postgres engine." Actual: AssertionError: expected InvalidParameterValue, got 'NotImplemented' (HTTP 501 from the scaffold stub in src/ops/switchover_read_replica.rs, whose header still reads "SCAFFOLDED, NOT IMPLEMENTED").

Cause 3 — rds.replica-uncommitted-primary-write-absent-until-commit: AssertionError: "the replica must serve its own endpoint so a reader can be pointed at it; it advertises '127.0.0.1', the same host as the source". rds.read-replica-replication-query-and-promote fails the same assertion one line earlier in its flow: AssertionError: "the replica must serve its own endpoint so readers can be pointed at it" — in both cases DescribeDBInstances reports Endpoint.Address equal for source and replica (the replica's ReadReplicaSourceDBInstanceIdentifier and the source's ReadReplicaDBInstanceIdentifiers are already correct, so only the endpoint diverges).

Cause 4 — rds.read-replica-promote-lifecycle: "Error: Check timed out after 60.0s" with no AWS error returned. The flow is CreateDBSubnetGroup → DescribeDBEngineVersions(oracle-ee, DefaultOnly) → CreateDBInstance(oracle-ee, db.m5.large, BYOL, gp3) → poll DescribeDBInstances for "available" (own deadline 2400 s, 30 s interval) → CreateDBInstanceReadReplica(ReplicaMode=mounted) → poll for "available" with no PendingModifiedValues. The budget is consumed inside those polls, before SwitchoverReadReplica is ever reached.

Cause 4: DescribeDBEngineVersions(Engine=oracle-ee, DefaultOnly=true); CreateDBInstance(Engine=oracle-ee, EngineVersion=<that>, DBInstanceClass=db.m5.large, LicenseModel=bring-your-own-license, StorageType=gp3, AllocatedStorage=20, BackupRetentionPeriod=1, in a 2-AZ DB subnet group); poll DescribeDBInstances for DBInstanceStatus == "available" with empty PendingModifiedValues, then CreateDBInstanceReadReplica(ReplicaMode=mounted) and poll the replica the same way — neither poll ever observes the terminal state.
