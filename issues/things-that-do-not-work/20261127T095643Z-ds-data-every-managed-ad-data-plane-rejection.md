# ds-data: every Managed-AD data-plane rejection scenario reaches no verdict — the directory it must run against is still Stage 'Requested' on the only probe the check's budget allows

> _Note: this issue was identified against the code base at commit `130a310eec895f2e766ea320ed7bc974cb95bb07`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListGroupsForMember

## Description
Both failing ds-data checks in this replay reach NO verdict. Neither is a ds-data response divergence: each is killed in the ds directory-stage wait that must complete before the ds-data data plane can be exercised at all, with the directory reading Stage 'Requested' on the one probe the clamped budget allows. The entire directory-data rejection surface these two scenarios exist to pin — ResourceNotFoundException(404) wording and no-side-effect guarantees for DisableUser / DescribeUser / ListGroupMembers / RemoveGroupMember / ListGroupsForMember, and the ValidationException/INVALID_REALM class — is therefore unexercised, and a regression in any of it passes unnoticed.

--- Cause 1 of 2: the ListGroupsForMember unknown/just-deleted-member rejection scenario never reaches its assertions (failing check id: ds-data.list-groups-for-member-unknown-member-rejected).

AWS: modelled. Smithy (services/service-com-amazonaws-directoryservicedata-directoryservicedata/smithy-model/com-amazonaws-directoryservicedata-directoryservicedata.json): ListGroupsForMember POST /GroupMemberships/ListGroupsForMember, input {DirectoryId @required @httpQuery pattern ^d-[0-9a-f]{10}$, SAMAccountName @required length 1..63 pattern ^[^:;|=+"*?<>/\\,\[\]@]+$, Realm length 1..255, MemberRealm, NextToken length 1..6144 @sensitive, MaxResults range 1..250} / output {DirectoryId, Realm, MemberRealm, Groups, NextToken}, @paginated(items=Groups), @readonly; errors AccessDeniedException(403), DirectoryUnavailableException(400), InternalServerException(500), ResourceNotFoundException(404), ThrottlingException(429), ValidationException(400). DescribeUser and DeleteUser declare the same ResourceNotFoundException(404). The scenario's precondition is modelled on the ds side: DirectoryStage = [Requested, Creating, Created, Active, ...] and CreateMicrosoftAD answers only a DirectoryId, so the walk to 'Active' is exposed through DescribeDirectories; for the wall clock there is recorded behavior only (the check reserves 1200 s and caps at 3000 s, i.e. real AWS provisions a directory for tens of minutes).

Emulator: no status, error code, message or shape divergence is reported for this check. The only output is 'AssertionError: directory still \'Requested\', never \'Active\'' from _await_stage at check_ds_data_list_groups_for_member_unknown_member_rejected.py:79, reached from _exercise at :162 — i.e. the first DescribeDirectories probe after CreateMicrosoftAD returns Stage 'Requested' and the wait's deadline (ctx-derived, reserve 1200 s, cap 3000 s) is already past under the 60 s per-check ceiling, so the check dies before EnableDirectoryDataAccess is even called.

Why: a client gets no verdict on the member-lookup rejection contract. Unverified are: that ListGroupsForMember lists exactly the groups a real member belongs to, across every NextToken page; that an UNKNOWN SAMAccountName is refused with HTTP 404 and Error.Code 'ResourceNotFoundException' rather than an empty 200 Groups list; that a JUST-DELETED member is refused the same way, and that DescribeUser and a repeated DeleteUser on that user refuse identically; and that a Realm the directory does not trust is refused with HTTP 400, Error.Code 'ValidationException' and Reason 'INVALID_REALM'. An emulator that answered 200 with an empty Groups list for an unknown member, or classified an untrusted realm as 404, would pass today.

--- Cause 2 of 2: the DisableUser / ListGroupMembers / RemoveGroupMember absent-name rejection scenario never reaches its assertions (failing check id: ds-data.user-and-membership-operations-refuse-names-the-directory-lacks).

AWS: modelled. DescribeUser output carries {DirectoryId, Realm, SID length 1..256, SAMAccountName, DistinguishedName, UserPrincipalName, EmailAddress, GivenName, Surname, Enabled, OtherAttributes}; CreateUser output {DirectoryId, SID, SAMAccountName}. For the directory provisioning duration there is recorded behavior only.

Emulator: again no response divergence is reported — only 'AssertionError: gave up after 30s waiting for directory d-... to reach Stage Active; last \'Requested\'' from _wait_for at check_ds_data_user_and_membership_operations_refuse_names_the_directory_lacks.py:76, reached from run at :188. The wait's budget is _budget(ctx, _DIRECTORY_BUDGET_S, 1200.0) = max(30.0, min(budget, time_left - 1200.0)), which the 60 s per-check ceiling clamps to the 30 s floor, while its poll interval is 60 s — so exactly one probe is made, it reads 'Requested', and the next sleep cannot fit the budget. The emulator presents no settled stage to that single probe.

Why: a client gets no verdict on the absent-name rejection contract or on its no-side-effect guarantee. Unverified are: that DisableUser on a name the directory lacks is refused HTTP 404 / Error.Code 'ResourceNotFoundException' with AWS's user-not-found sentence — fixed text 'User not found in directory ' followed by the directory id from the request and a full stop (no single run's literal id is part of the requirement) — and creates no user, so a following DescribeUser is refused identically; that CreateUser then ResetUserPassword leave the user readable with Enabled true and a domain-form SID, and that the identical DisableUser flips Enabled to false while KEEPING that SID (i.e. disable mutates the existing user rather than replacing it); that ListGroupMembers on a group the directory lacks is refused 404 / 'ResourceNotFoundException' worded 'Group not found in directory ' + <directory id> + '.'; that RemoveGroupMember from an absent group is refused 404 / 'ResourceNotFoundException' worded 'Member, group, or membership does not exist in directory ' + <directory id> + '.'; that those refusals create no group (ListGroups must not list it) and leave the user disabled with its SID intact; and that once the group exists the same calls succeed — AddGroupMember makes the group hold exactly that user, RemoveGroupMember drops the group from ListGroupsForMember and leaves ListGroupMembers empty. An emulator that answered 200 with an empty Members list for a missing group, auto-created the missing object, re-minted the SID on disable, or re-worded any of the three distinct not-found sentences would pass today.

Fix: neither cause is a ds-data operation-handler response defect — no ds-data handler is reported answering wrongly in either check. The owner is the ds directory-stage state machine's clock-owed-transition contract where it meets the suite's per-check ceiling: settle/shorten the spans applied to the creation chain (Requested -> Creating -> Created -> Active) and to DataAccessStatus (Enabling -> Enabled) so a settled value is observable on the client's FIRST probe after the call that started it — accepting that transient stages and the refusals depending on them (DirectoryUnavailableException and friends) stop being observable, and loosening any in-tree suite that pins them — or, alternatively, the harness's per-check budget together with the large teardown reserves these two checks subtract from it (1200 s each).

Traces: ds-data.list-groups-for-member-unknown-member-rejected and ds-data.user-and-membership-operations-refuse-names-the-directory-lacks (both verdict 'mismatch', both killed in the directory-stage wait with the last observation 'Requested').
