# omics: 7 net-new root causes — read-set upload refusals carry emulator-authored messages, CompleteMultipartReadSetUpload/UploadReadSetPart accept invalid part lists, DeleteRun misclassifies an active run, and no run can ever reach COMPLETED

> _Note: this issue was identified against the code base at commit `e5dfc362f7e10f15c9ea986ec22a5550bf857429`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CompleteMultipartReadSetUpload

## Description
Seven distinct net-new root causes in the HealthOmics (omics) emulator, all grounded in failing behavioral checks of suite simparity-behavioral-aws-v1. The already-filed scaffold-stub issues (AbortMultipartReadSetUpload, CancelRun, StartRunBatch, CreateReferenceStore, ListRunCaches, GetReadSet) and the open issues 20261029T184954Z-omics-4-net-new-root-causes-startrun-refuses.md (StartRun/CreateWorkflowVersion/CFN RunGroup), 20261124T224008Z-omics-tagresource-on-a-deleted-resource-s-arn.md, 20261124T171120Z-omics-getreadsetmetadata-returns-a-malformed-sequence-store-s3.md and 20261126T233811Z-omics-getreadset-serves-the-read-set-part-with.md are NOT these causes and do not cover them. Each cause below must be closed on its own before submitting.

=== Cause 1 of 7: CompleteMultipartReadSetUpload's part-checksum refusal uses emulator prose instead of AWS's fixed sentence ===
AWS: CompleteMultipartReadSetUpload refuses a parts list whose listed checksum is not the checksum of the part the upload holds (or that names a part/part-number pair the upload never received) with ValidationException (Smithy: CompleteMultipartReadSetUpload errors include ValidationException, httpError 400; input parts -> CompleteReadSetUploadPartList @required). Recorded behavior: the message is the single fixed sentence "One or more of the specified parts could not be found. The part might not have been uploaded, or the specified checksum might not have matched the part's checksum" — entirely fixed text, carrying NO value from the request (no part number, no part source, no upload id). The same sentence covers the unknown-part case and the stale-checksum case (a part re-uploaded under the same partSource/partNumber, where the superseded checksum is then invalid).
Emulator: the status (400) and code (ValidationException) are right, but the handler composes its own sentence of the form "the checksum listed for part <partNumber> of <partSource> is not the checksum of the part upload <uploadId> holds" (and, for a pair the upload does not hold, "upload <uploadId> holds no part <partNumber> of <partSource>"). Replay observed: ('ValidationException', 'the checksum listed for part 1 of SOURCE1 is not the checksum of the part upload 2000000000 holds') — the part number, part source and upload id in that string are values from the request/state filling the emulator's own template, not part of AWS's requirement; AWS's message interpolates nothing.
Why: a client, SDK error handler, test or runbook that matches or surfaces this refusal's message sees text AWS never produces, and the emulator also discloses which of the two causes applied — a distinction AWS deliberately collapses into one sentence.
Fix: the message construction in the operation's handler validation (the unknown-part and checksum-mismatch branches of CompleteMultipartReadSetUpload's handle); both branches must answer AWS's one fixed sentence.
Traces: omics.complete-multipart-read-set-upload-mismatched-parts-rejected, omics.complete-multipart-read-set-upload-wrong-part-checksum-rejected, omics.complete-read-set-upload-mismatched-checksum-rejected, omics.complete-read-set-upload-with-replaced-part-checksum-rejected, omics.complete-read-set-upload-wrong-part-checksum-rejected.

=== Cause 2 of 7: the "upload does not exist" message is truncated to its first sentence on every upload operation ===
AWS: an upload operation whose uploadId names no reachable in-progress upload — because it was completed, aborted, or never existed — is refused with ResourceNotFoundException (Smithy: both CompleteMultipartReadSetUpload and UploadReadSetPart declare ResourceNotFoundException, httpError 404). Recorded behavior: the message is two fixed sentences, "The specified upload does not exist. The upload ID may be invalid, or the upload may have been aborted or completed." — all fixed text, no request value interpolated.
Emulator: the shared constant crate::state::MULTIPART_READ_SET_UPLOAD_NOT_FOUND_MESSAGE is only "The specified upload does not exist."; the second sentence is missing. Status 404 and code ResourceNotFoundException are correct. Replay observed, on a second CompleteMultipartReadSetUpload of an upload already completed and on an UploadReadSetPart sent to a completed upload: ('ResourceNotFoundException', 'The specified upload does not exist.') where the expectation is the two-sentence text.
Why: a client that asserts on, logs or displays the refusal message of a spent upload gets a message AWS never returns, and loses the half of the sentence that tells a caller WHY the upload is unreachable (invalid id vs aborted vs completed) — the only diagnostic AWS gives for that class.
Fix: the shared not-found message for multipart read set uploads in the service state module (crate::state::MULTIPART_READ_SET_UPLOAD_NOT_FOUND_MESSAGE), which both operations' handlers read.
Traces: omics.complete-read-set-upload-twice-rejected, omics.completed-read-set-upload-refuses-second-completion-and-new-part, omics.upload-read-set-part-to-completed-upload-rejected.

=== Cause 3 of 7: CompleteMultipartReadSetUpload accepts a parts list that names no first-source part ===
AWS: the first source file is mandatory for a read set: a completion whose parts list carries only SOURCE2 parts is refused with 400 ValidationException and the fixed message "The provided parts list must contains parts for the first source." (fixed text, no request value interpolated; Smithy: ReadSetPartSource = SOURCE1 | SOURCE2, ValidationException httpError 400). Recorded behavior: after that refusal the upload is still open and no read set exists; once a SOURCE1 part is uploaded the same upload completes and the read set is a FASTQ pair.
Emulator: the handler validates only that each listed part exists in the upload with the listed checksum; it never requires a SOURCE1 part. The call is ACCEPTED with HTTP 200 and a readSetId, so a read set is created from the second mate alone. Replay observed: "the call was accepted and returned {... 'readSetId': '3000000000'}; a refusal was expected".
Why: an over-permissive acceptance. A client that mistakenly omits the first mate gets a 200 and a read set that AWS would never create, so the error surfaces far later (as corrupt/half-paired genomic data) instead of at the API boundary, and the negative class AWS defines is unobservable.
Fix: CompleteMultipartReadSetUpload's validation in its handler — after resolving the listed parts, refuse a list containing no part whose partSource is SOURCE1 with the modeled ValidationException and AWS's fixed sentence, before any read set is inserted into state.
Traces: omics.complete-read-set-upload-without-first-source-rejected.

=== Cause 4 of 7: CompleteMultipartReadSetUpload's empty-parts-list refusal uses emulator prose ===
AWS: a completion with an empty parts list is refused with 400 ValidationException and the fixed message "The provided parts list is empty." (fixed text; the model puts no @length on CompleteReadSetUploadPartList, so this is a handler rule, and the member is @required).
Emulator: the handler does refuse an empty list with 400 ValidationException, but with its own sentence "parts lists no part; a read set is formed from the parts uploaded for it".
Why: same class as Cause 1 — a caller matching or surfacing the refusal message sees text AWS never produces. At replay this assertion sits after the checksum assertion of Cause 1 in the same check, so Cause 1 masks it; fixing Cause 1 alone will leave this check failing on the empty-list message.
Fix: the empty-parts branch of CompleteMultipartReadSetUpload's handler validation — emit AWS's fixed sentence.
Traces: omics.complete-multipart-read-set-upload-mismatched-parts-rejected.

=== Cause 5 of 7: UploadReadSetPart accepts partSource=SOURCE2 on a non-FASTQ upload ===
AWS: a second source file is a FASTQ-only concept. UploadReadSetPart with partSource=SOURCE2 against an upload whose sourceFileType is not FASTQ (e.g. UBAM) is refused with 400 ValidationException and the fixed message "SOURCE2 part source can only be used for FASTQ multipart read set uploads." (fixed text, no request value interpolated; Smithy: UploadReadSetPart.partSource -> ReadSetPartSource SOURCE1|SOURCE2 @required, @httpQuery partSource; ValidationException httpError 400). Recorded behavior: nothing is stored — ListReadSetUploadParts(partSource=SOURCE2) on that upload lists no part — while the same bytes are accepted as SOURCE1 on the UBAM upload and as SOURCE2 on a FASTQ upload.
Emulator: UploadReadSetPart's handler checks only the payload length, the store, the upload's existence and the per-upload byte cap; it never consults the upload's sourceFileType. The SOURCE2 part on the UBAM upload is ACCEPTED with HTTP 200 and a checksum, and is stored. Replay observed: "the call was expected to be refused but was accepted: {'checksum': 'hhGFhxtE36l5mirE6iT9AAXfPjGYutpCsm8slB1zkyA='}" (the checksum value is per-run; the acceptance is the defect).
Why: another over-permissive acceptance. A caller that sends a mate file for a single-file format is told the part was stored, and the upload then completes into a read set shape AWS cannot produce; the modeled negative class is unreachable.
Fix: UploadReadSetPart's validation in its handler — once the upload is resolved, refuse partSource=SOURCE2 when the upload's sourceFileType is not FASTQ, with the modeled ValidationException and AWS's fixed sentence, storing nothing.
Traces: omics.upload-read-set-part-source2-on-ubam-upload-rejected.

=== Cause 6 of 7: DeleteRun on a run that is still in flight answers 409 ConflictException with emulator prose instead of 400 ValidationException "Run <id> is active" ===
AWS: DeleteRun on a run that has not reached a terminal stage is refused with ValidationException (Smithy: DeleteRun declares both ConflictException httpError 409 and ValidationException httpError 400; success 202). Recorded behavior: the refusal is 400 ValidationException whose message is the fixed text "Run " + the run id from the request + " is active" — fixed words "Run" and "is active", with the run id taken verbatim from the request path.
Emulator: the handler classifies the same condition as 409 ConflictException with its own sentence of the form "run <id> is <status>; only a run that has reached one of [COMPLETED, FAILED, CANCELLED] can be deleted". Replay observed: ('ConflictException', 'run 1500000 is PENDING; only a run that has reached one of [COMPLETED, FAILED, CANCELLED] can be deleted') where ('ValidationException', 'Run <id> is active') is required. The run id and the status in that string are values from state filling the emulator's own template.
Why: the HTTP status, the error code and the message all differ. An SDK caller branching on ConflictException vs ValidationException takes the wrong branch (and retry/backoff policies differ between 409 and 400), and the emulator additionally leaks the internal deletable-status list.
Fix: the terminal-status guard in DeleteRun's handler and the status classification it reads from crate::state (DELETABLE_RUN_STATUSES / is_deletable_run_status) — raise the modeled ValidationException with AWS's wording for a run that is still active.
Traces: omics.delete-run-while-active-rejected.

=== Cause 7 of 7: a run's status progression is hard-wired to end in FAILED, so no run can ever reach COMPLETED ===
AWS: a run of a workflow that needs no compute (a WDL workflow with no task calls, whose only output is a literal) progresses PENDING -> STARTING -> RUNNING -> COMPLETED. Recorded behavior: the check polls GetRun until a terminal RunStatus and requires COMPLETED, then requires CancelRun on that COMPLETED run to answer HTTP 202 while GetRun keeps reading COMPLETED across repeated reads (Smithy: GetRun.status -> RunStatus; CancelRun success 202).
Emulator: crate::state::RUN_STATUS_SEQUENCE is &["PENDING", "STARTING", "RUNNING", "FAILED"] — the clock-driven progression terminates in FAILED for every run, with failureReason/statusMessage saying no workflow engine is emulated. Replay observed: "AssertionError: the task-free run ended 'FAILED', expected COMPLETED".
Why: COMPLETED is unreachable, so every client behavior that keys off a successful run is unobservable and every waiter that treats FAILED as fatal fails against the emulator: a run-completion poller, CancelRun-is-a-no-op-on-a-finished-run, DeleteRun of a COMPLETED run, and anything asserting the success path of a workflow. A caller cannot distinguish "my workflow failed" from "this emulator fails all runs". The deliberate trade-off recorded in the comment above that constant (no engine is executed, so no outputs exist) is still a fidelity divergence: a run that AWS completes must settle COMPLETED here, with the absence of real outputs expressed elsewhere (e.g. the output location), not by terminating every run in the modeled failure status.
Fix: the run status progression in the service state module (crate::state::RUN_STATUS_SEQUENCE and the settle() step that advances a run through it, plus the failureReason/statusMessage it stamps) — a recorded run with no engine-level failure must reach COMPLETED.
Traces: omics.cancel-run-on-completed-run-leaves-it-completed.
