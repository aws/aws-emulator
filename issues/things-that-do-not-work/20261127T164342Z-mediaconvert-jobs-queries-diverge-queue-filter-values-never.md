# MediaConvert jobs queries diverge: queue filter values never resolved, filter keys combined with OR instead of AND, and results ordered by Order instead of newest-first

> _Note: this issue was identified against the code base at commit `5bf95535a88c836b855c8cd193d84d7babf276ba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobsQuery

## Description
Three distinct root causes in the emulator's MediaConvert jobsQueries surface (StartJobsQuery + GetJobsQueryResults): an unresolvable queue filter value is not rejected, filters on different keys are unioned instead of intersected, and the answer is sorted by the requested Order instead of newest-first. They are independent defects and ALL THREE must be closed before this issue is submitted.

Cause 1 of 3: StartJobsQuery never resolves the values of a 'queue' filter, so a query naming a deleted or never-created queue is accepted (201) instead of refused with NotFoundException/404.
AWS: Smithy (services/service-com-amazonaws-mediaconvert-mediaconvert): StartJobsQuery POST /2017-08-29/jobsQueries, success code 201, input member FilterList (jsonName filterList) -> __listOfJobsQueryFilter; JobsQueryFilter has Key (enum JobsQueryFilterKey, whose documentation defines 'queue - Your Queue's name or ARN') and Values; modelled errors include NotFoundException (httpError 404, doc "The resource you requested doesn't exist"). The resolution rule is recorded behavior only: MediaConvert resolves every value of a queue filter against queue state before starting the query and refuses the WHOLE query when any one of them does not resolve — by name or by ARN, and even when the other values in the same Values array do resolve — with HTTP 404, error code NotFoundException, message 'The resource you specified in queue was not found.' Fixed text: 'The resource you specified in ' and ' was not found.'; the single variable part is the filter key name taken from the request (queue). No queue name, ARN or count appears in it.
Emulator: answers 201 with a query id ({'Id': '<query id>'}) for a queue that it had itself just reported gone — in the same checks GetQueue on that name correctly answers NotFoundException 'The resource you specified in name was not found.', so queue state knows the queue is absent and only the query path skips the lookup.
Why: a hard error becomes a plausible empty (or partial) result page. A client polling jobs per queue sees 'no jobs' for a misspelled or deleted queue and reports a healthy idle queue; worse, a query whose Values mix a live queue with an absent one returns the live queue's jobs, so the client never learns part of its request was meaningless. Monitoring and alarms built on such a query never fire.
Fix: StartJobsQuery's input validation in its handler — resolve each JobsQueryFilter value whose Key is 'queue' (by name and by ARN) against queue state and raise NotFoundException before the query is created in state. Relation to open issues: 20261127T134532Z-mediaconvert-jobs-query-and-search-request-validation-diverges covers the same gap for SearchJobs' 'queue' httpQuery parameter (its Cause 6) and for duplicate filter keys (its Cause 3); neither covers StartJobsQuery's filterList queue VALUES, which is this cause.
Traces: mediaconvert.jobs-query-filter-on-deleted-queue-rejected, mediaconvert.jobs-query-unknown-queue-among-filter-values-rejected.

Cause 2 of 3: a jobs query combines filters on DIFFERENT keys with OR instead of AND, so it returns jobs that satisfy only one of them.
AWS: Smithy: FilterList -> __listOfJobsQueryFilter; JobsQueryFilter doc 'Provide one or more JobsQueryFilter objects, each containing a Key with an associated Values array. Note that MediaConvert queries jobs using OR logic.' — the OR applies to the values WITHIN one filter's Values array. The cross-key rule is recorded behavior only: values inside one JobsQueryFilter match any (OR), while separate JobsQueryFilter objects on different keys must all match (AND), so a job is listed only when it satisfies every key named in the request. Consequently a FilterList whose keys no single job satisfies returns an empty Jobs list in a COMPLETE query, not an error.
Emulator: unions across keys. [{queue: A}, {fileInput: X}] where A's job has a different input and X's job is on another queue returned 2 jobs (both of them) where AWS returns none; [{queue: east}, {status: SUBMITTED}] returned both the east and the west queue's jobs, because the west job is also SUBMITTED. Single-key multi-value OR is correct in the same checks (a queue filter naming both queues returns one job of each), which isolates the defect to the cross-key combination.
Why: every narrowing query a client writes is silently widened. Operators use queue+status to count what is actually queued on one queue, and queue+fileInput to find the job for one asset; against the emulator both return unrelated jobs, so clients act on the wrong job (cancel, retry, bill) and any test asserting a narrowed result set passes against semantics production does not have.
Fix: the jobsQueries query evaluation (StartJobsQuery's filter planning / the predicate GetJobsQueryResults evaluates over job state) — intersect the per-key predicates and keep OR only within one key's Values.
Traces: mediaconvert.jobs-query-filter-values-or-and-keys-and, mediaconvert.jobs-query-values-match-any-and-keys-match-all.

Cause 3 of 3: GetJobsQueryResults sorts the answer by the requested Order instead of always newest-first.
AWS: Smithy: StartJobsQuery input member Order (jsonName order) targets the Order enum (ASCENDING | DESCENDING, doc 'Optional. When you request lists of resources, you can specify whether they are sorted in ASCENDING or DESCENDING order. Default varies by resource.'); GetJobsQueryResults GET /2017-08-29/jobsQueries/{Id} returns Jobs plus NextToken. The ordering is recorded behavior only: a jobs query lists jobs by descending CreatedAt — newest first — whichever Order value is requested, and the NextToken pages walk that same newest-first sequence, each page but the last holding MaxResults jobs and the last page carrying no token.
Emulator: honours Order literally. With Order=ASCENDING and MaxResults=1 over a 3-job PAUSED queue it walked the jobs oldest-first (creation order) instead of newest-first; the token mechanics themselves are right (one job per page, a token on every page but the last).
Why: a client that asks for the first page to see the most recent job gets the oldest one, so a 'latest job' lookup, a most-recent-failure dashboard or any cursor that stops after page one reads the wrong end of the queue — silently, since the page is well-formed.
Fix: the jobsQueries result ordering (where GetJobsQueryResults materialises and pages the query's job list) — order by CreatedAt descending regardless of the request's Order, and page that sequence.
Traces: mediaconvert.jobs-query-next-token-pages-in-creation-order.
