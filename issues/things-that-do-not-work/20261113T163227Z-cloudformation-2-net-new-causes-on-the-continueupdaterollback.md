# cloudformation: 2 net-new causes on the ContinueUpdateRollback path — the resource the failed update added is never deleted in the cleanup phase, and the completing UPDATE_ROLLBACK_COMPLETE event carries no skipped-resources reason

> _Note: this issue was identified against the code base at commit `b5b438418db974c5623067148485e4df5aeb5fcd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ContinueUpdateRollback

## Description
TWO distinct net-new root causes on the ContinueUpdateRollback path. A fixer must close both before submitting.

Cause 1 of 2: when a resumed rollback reaches UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS, the resource that existed only in the failed update's template is never deleted and emits no events. Failing check: cloudformation.stack-continue-update-rollback-client-request-token-marks-its-events.
AWS: ContinueUpdateRollback(StackName, ResourcesToSkip=[<logical-id>], ClientRequestToken=<tok>) resumes the rollback of a stack in UPDATE_ROLLBACK_FAILED. The skipped resource is marked UPDATE_COMPLETE with ResourceStatusReason 'Resource skipped during UpdateRollback'; the stack then enters UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS and CloudFormation DELETES the resources that only the failed update introduced, emitting a DELETE_IN_PROGRESS and then a DELETE_COMPLETE event for each of them, and only afterwards the stack's UPDATE_ROLLBACK_COMPLETE. Every one of those events carries the ContinueUpdateRollback call's ClientRequestToken. Smithy (services/service-com-amazonaws-cloudformation-cloudformation): ContinueUpdateRollback input models StackName, RoleARN, ResourcesToSkip, ClientRequestToken (length 1-128) and ForceRollback, with TokenAlreadyExistsException as its only modeled error; the event sequence is recorded behavior only.
Emulator: the event rows produced by the resumed rollback are exactly — stack UPDATE_ROLLBACK_IN_PROGRESS ('User Initiated'), the skipped resource UPDATE_COMPLETE ('Resource skipped during UpdateRollback'), stack UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS (no reason), stack UPDATE_ROLLBACK_COMPLETE (no reason). The two per-resource DELETE events for the resource the failed update added are absent, so the cleanup phase does no work and that resource is left behind. The statuses, the skip reason and the ClientRequestToken on every row are correct.
Why: the rollback claims to have returned the stack to its pre-update shape while a resource created only by the failed update survives — it is untracked by the template the stack now reports, it keeps costing and holding names, and a client that watches the event stream for the cleanup deletions (the documented way to know the rollback finished disposing of the failed update's resources) waits forever and then concludes the resource was never created.
Fix: the rollback-cleanup phase of the ContinueUpdateRollback path in the cloudformation crate's stack-update engine — it must delete the resources present only in the failed update's template during UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS and emit their DELETE_IN_PROGRESS/DELETE_COMPLETE events (with the call's ClientRequestToken) before the stack's UPDATE_ROLLBACK_COMPLETE.
Traces: cloudformation.stack-continue-update-rollback-client-request-token-marks-its-events.

Cause 2 of 2: the stack's completing UPDATE_ROLLBACK_COMPLETE event carries no ResourceStatusReason after a rollback that skipped resources. Failing check: cloudformation.stack-continue-update-rollback-force-rollback-skips-failed-resource.
AWS: when ContinueUpdateRollback completes a rollback that skipped resources (via ResourcesToSkip or ForceRollback=true), the stack's final UPDATE_ROLLBACK_COMPLETE event carries ResourceStatusReason exactly 'One or more resources were skipped during UpdateRollback. These resources were not rolled back and may have drifted from the template. Run drift detection (DetectStackDrift) to review their current state before your next update.' — all fixed text, no variable parts. Smithy doc for ContinueUpdateRollbackInput.ForceRollback: 'Specifies whether CloudFormation forces the rollback to continue by skipping resources currently in the UPDATE_FAILED state... CloudFormation sets the status of the skipped resources to UPDATE_COMPLETE and continues to roll back the stack... Drift detection reports skipped resources as NOT_CHECKED.' The sentence itself is recorded behavior only.
Emulator: the forced continue does reach UPDATE_ROLLBACK_COMPLETE and does mark the skipped resource UPDATE_COMPLETE with 'Resource skipped during UpdateRollback', but the stack's final event's ResourceStatusReason is absent (None) — the observed stack rows are [('UPDATE_ROLLBACK_IN_PROGRESS','User Initiated'), ('UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS', None), ('UPDATE_ROLLBACK_COMPLETE', None)].
Why: that reason is the only statement in the event stream that the completed rollback is INCOMPLETE — that some resources were not rolled back, may have drifted, and must be reconciled before the next update. Without it a caller reading the terminal event sees an ordinary clean rollback and performs the next update against resources CloudFormation itself warns are inconsistent.
Fix: the event writer for the rollback-completion event in the cloudformation crate's ContinueUpdateRollback path — set the skipped-resources ResourceStatusReason on the stack's UPDATE_ROLLBACK_COMPLETE event whenever at least one resource was skipped, whether by ResourcesToSkip or by ForceRollback.
Traces: cloudformation.stack-continue-update-rollback-force-rollback-skips-failed-resource.

Neither cause is in the open ContinueUpdateRollback issues 20261112T002904Z-cloudformation-2-net-new-causes-continueupdaterollback-s-wrong.md or 20261112T092815Z-cloudformation-continueupdaterollback-s-wrong-state-refusal-is-re-worded.md, which concern the wrong-STATE refusal wording, nor do they carry these check ids.
