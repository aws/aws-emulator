# bedrock-agent-runtime: InvokeInlineAgent never hands control back for a RETURN_CONTROL action group and never emits a trace event when enableTrace is set (2 causes)

> _Note: this issue was identified against the code base at commit `eadb2d0c274461491404935b82a39edede7a2374`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeInlineAgent

## Description
Two net-new root causes in the InvokeInlineAgent event-stream plane, both reached through the behavioral check bedrock-agent-runtime.invoke-inline-agent-return-control-result-reenters-the-next-turn-prompt. Smithy model consulted: services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/smithy-model/com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice.json. NOTE: this is NOT a refusal regression of the fixed issue 20261101T114357Z-bedrock-agent-runtime-invokeinlineagent-stub.md / 20261023T004328Z-...-InvokeInlineAgent-validates-a-member... — the call now reaches the handler and answers 200 with a streaming body; what diverges is the CONTENT of that stream.

=== Cause 1 of 2: an action group whose actionGroupExecutor is customControl=RETURN_CONTROL is accepted, but control is never returned — the stream carries only `chunk` ===
AWS: Smithy: InvokeInlineAgent (POST /agents/{sessionId}) returns `completion` -> InlineAgentResponseStream, a @streaming union whose members include `returnControl` -> InlineAgentReturnControlPayload alongside `chunk` and `trace`. ActionGroupExecutor.customControl documents: "To return the action group invocation results directly in the InvokeInlineAgent response, specify RETURN_CONTROL." The returned payload carries `invocationId` (a service-issued identifier) and `invocationInputs` (@length min 1, max 5), each a functionInvocationInput whose `actionGroup` is the declared action-group name, whose `function` is the declared function name and whose `parameters` carry the declared parameter names — all values taken from the request's actionGroups/functionSchema, never literals. When the model elicits a function from a RETURN_CONTROL action group, `returnControl` is the LAST member of that turn's stream (the agent is waiting on the caller). The caller then supplies inlineSessionState.invocationId plus inlineSessionState.returnControlInvocationResults (InlineSessionState, @length 1..5) on the next turn, and the function result re-enters the next turn's orchestration prompt; an invocationId the service never issued, or a list longer than the modeled maximum of 5, is ValidationException (400).
Emulator: across 3 progressively more explicit asks against a single declared action group with actionGroupExecutor {customControl: RETURN_CONTROL} and a one-function functionSchema, the stream carried event keys [['chunk'], ['chunk'], ['chunk']] — no `returnControl` member ever appeared, and the agent answered directly with the emulator's own completion notice. services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/src/ops/invoke_inline_agent.rs frames only CHUNK_EVENT ("chunk", line 172 and the framing loop at lines 258-278) and its module docs state actionGroups are "SERVED" merely by being counted in the notice. The same file's unservable_leg() (lines 432-441) then refuses ANY inlineSessionState with an emulator-authored ValidationException sentence ("inlineSessionState: its attributes replace the placeholders of a prompt nothing reads here, ... and this service returns control for no action ..."), so the second half of the AWS contract — supplying returnControlInvocationResults under the issued invocationId, and the modeled ValidationException wording for a wrong invocationId or an over-length (>5) result list — is unreachable too.
Why: a client that uses the documented RETURN_CONTROL pattern (the only way to run an action group without a Lambda executor) never receives the invocation it must execute, so its tool-calling loop silently degrades into a plain text answer; and when it does try to return a result, it gets a 400 on a request AWS accepts. Both the happy path and the modeled ValidationException classes around invocationId/result-list length are unobservable.
Fix: the InvokeInlineAgent handler and its state plane — services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/src/ops/invoke_inline_agent.rs (the response framing, and unservable_leg's blanket inlineSessionState refusal) together with crate::state::inline_agent: elicit the declared function of a customControl=RETURN_CONTROL action group, frame a `returnControl` event carrying a service-issued invocationId and one functionInvocationInput per offered function as the terminal member of the turn, remember that invocationId on the conversation, and accept inlineSessionState.returnControlInvocationResults that match it (rejecting an unissued invocationId and a list over the modeled maximum of 5 with ValidationException in AWS's wording).
Traces: bedrock-agent-runtime.invoke-inline-agent-return-control-result-reenters-the-next-turn-prompt.

=== Cause 2 of 2: enableTrace=true produces no `trace` event at all ===
AWS: Smithy: InvokeInlineAgent input has `enableTrace` (Boolean) and InlineAgentResponseStream models a `trace` -> InlineAgentTracePart member whose trace carries orchestrationTrace, including modelInvocationInput.text — the prompt the service assembled for the model. With enableTrace=true AWS interleaves trace events with the answer; the orchestration prompt it exposes there is what lets a client see the caller-supplied function result re-enter the next turn.
Emulator: for three separate InvokeInlineAgent calls made with enableTrace=true, the observed event keys were only ['chunk'] on each — not a single `trace` member was emitted, so no orchestrationTrace and no modelInvocationInput.text exists. The handler's own module docs state a trace event "is never invented", and the request's enableTrace flag is only recorded into the notice text (ServedInvocation.trace_requested, invoke_inline_agent.rs line 379).
Why: a client that enables tracing to observe or debug orchestration (and any tooling that reads orchestrationTrace.modelInvocationInput) receives nothing, with no error to indicate the flag was ignored — enableTrace is accepted and silently dropped.
Fix: the same handler's response framing plus crate::state::inline_agent — emit `trace` events (InlineAgentTracePart with an orchestrationTrace whose modelInvocationInput.text is the prompt the turn was assembled from, including any returnControlInvocationResults the caller supplied) whenever enableTrace is true.
Traces: bedrock-agent-runtime.invoke-inline-agent-return-control-result-reenters-the-next-turn-prompt.

## Evidence
Cause 1 — expected: with one action group declared as {"actionGroupName": <name>, "actionGroupExecutor": {"customControl": "RETURN_CONTROL"}, "functionSchema": {"functions": [{"name": <fn>, "parameters": {"project": {...required...}}}]}} and an input asking for that function, the completion stream yields exactly one `returnControl` member, as the LAST member of the turn, with a non-empty invocationId, exactly one invocationInputs entry whose functionInvocationInput.actionGroup == the declared action-group name, .function == the declared function name and .parameters containing the declared parameter name. actual: AssertionError "across 3 increasingly explicit asks the inline agent never handed control back: no returnControl member appeared. Event keys seen per attempt: [['chunk'], ['chunk'], ['chunk']]" — 200 with chunk-only framing on all three attempts.
Cause 1 (second leg, from the handler) — AWS accepts inlineSessionState={invocationId: <issued id>, returnControlInvocationResults: [{functionResult: {...}}]} and refuses an unissued invocationId / a >5-entry list with ValidationException; the emulator refuses EVERY inlineSessionState with its own sentence beginning "inlineSessionState: its attributes replace the placeholders of a prompt nothing reads here" (src/ops/invoke_inline_agent.rs:432-441), so the correct-invocationId turn 2 can never succeed.
Cause 2 — expected: at least one `trace` event per enableTrace=true invocation, carrying trace.orchestrationTrace.modelInvocationInput.text. actual: event keys seen across three enableTrace=true invocations were only ['chunk'], ['chunk'], ['chunk'] — no `trace` member, so trace_keys is empty.
