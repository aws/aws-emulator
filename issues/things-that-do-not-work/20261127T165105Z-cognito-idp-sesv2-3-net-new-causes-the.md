# cognito-idp__sesv2: 3 net-new causes — the SES sender gate is never evaluated, so SetRiskConfiguration and Create/UpdateUserPool accept SES SourceArns AWS refuses

> _Note: this issue was identified against the code base at commit `43ebd6ce98e7173c42d111a904ff9f0222d298b2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetRiskConfiguration

## Description
Three net-new root causes on service token cognito-idp__sesv2. In every one, the emulator's cognito-idp accepts an email-sender configuration that names an SES identity by ARN without evaluating any of the gates AWS applies to that ARN (does the ARN belong to SES in this account, does the identity's sending-authorization policy let Cognito send, is the identity verified), so a configuration AWS refuses is stored and returned 200.

Cause 1 of 3: SetRiskConfiguration accepts an AccountTakeoverRiskConfiguration.NotifyConfiguration whose SourceArn is an SES identity of this account that grants Cognito no sending authorization.
AWS: Smithy (cognito-idp): SetRiskConfiguration models InvalidEmailRoleAccessPolicyException (errorKind client, httpError 400, doc "This exception is thrown when Amazon Cognito isn't allowed to use your email identity. HTTP status code: 400.") and CodeDeliveryFailureException (client, 400); NotifyConfigurationType.SourceArn is documented as "The Amazon Resource Name (ARN) of the identity that is associated with the sending authorization policy. This identity permits Amazon Cognito to send for the email address specified in the From parameter." Recorded behavior: with no sending-authorization policy on that identity the call is refused with code InvalidEmailRoleAccessPolicyException and the message "'cognito-idp.amazonaws.com' principal is not authorized to send emails from the configured 'from email address'. Please review sending authorization policy on your Amazon SES identity" — that whole sentence pair is fixed text with no variable part. Once the identity's policy does authorize this user pool (Principal email.cognito-idp.amazonaws.com, Condition aws:SourceAccount = the caller's account and aws:SourceArn matching the pool ARN), the gate moves on and SES's own refusal is surfaced as CodeDeliveryFailureException with the message "Cognito received the following error from Amazon SES when attempting to send email: Email address is not verified. The following identities failed the check in region <REGION>: <identity ARN>" — fixed text up to the colon, with <REGION> the request's region in upper case and the identity ARN taken from the request; a policy that authorizes only a different user pool returns to the InvalidEmailRoleAccessPolicyException above. Either way the stored AccountTakeoverRiskConfiguration is left exactly as it was before the refused update.
Emulator: answers HTTP 200 and stores the notifying configuration — replay reports "expected a refusal, but the call succeeded: {'RiskConfiguration': {'UserPoolId': ..., 'AccountTakeoverRiskConfiguration': {'NotifyConfiguration': {'From': ..., 'SourceArn': 'arn:aws:ses:<region>:<account>:identity/<domain>'}, ...}}}" with HTTPStatusCode 200. No SES identity policy is consulted at all.
Why: a client is told Cognito will send account-takeover notification mail from an identity that has not authorized Cognito and is not verified. On AWS that configuration can never be saved, so code (and infrastructure tests) that rely on the refusal to detect a missing SES sending-authorization policy sees a false success, and the pool silently ends up configured to notify through a sender that would never deliver.
Fix: the SetRiskConfiguration handler's NotifyConfiguration validation in the cognito-idp service (the operation's handler plus the shared SES-sender gate it must call to read the SES identity's policy and verification state), which must run the sending-authorization check — and then the verification check — before anything is persisted.
Traces: cognito-idp__sesv2.risk-notify-ses-identity-without-sending-authorization-rejected (the same refusal is also the final assertion of cognito-idp__sesv2.risk-notify-source-arn-outside-ses-rejected).

Cause 2 of 3: SetRiskConfiguration accepts a NotifyConfiguration.SourceArn that is not an SES identity ARN at all.
AWS: Smithy (cognito-idp): SetRiskConfiguration models NotAuthorizedException (errorKind client, httpError 403); SourceArn is modeled and documented as an SES identity ARN (see Cause 1). Recorded behavior: an ARN of another service in the same account — e.g. the user pool's own arn:aws:cognito-idp:<region>:<account>:userpool/<pool-id>, or an arn:aws:sns:<region>:<account>:<topic> — is refused with code NotAuthorizedException and the message "Email arn does not belong to your account." (entirely fixed text, no variable part), and the previously stored AccountTakeoverRiskConfiguration is unchanged.
Emulator: answers HTTP 200 and stores the foreign ARN verbatim — replay reports "expected a refusal, but the call succeeded: {'RiskConfiguration': {... 'NotifyConfiguration': {'From': ..., 'SourceArn': 'arn:aws:cognito-idp:<region>:<account>:userpool/<pool-id>'}, ...}}". The service of the ARN is never examined.
Why: a typo or a copy-pasted ARN of the wrong service is accepted, so the client believes its notification sender is configured; AWS rejects it outright. Any caller that distinguishes "wrong ARN" (NotAuthorizedException) from "missing sending policy" (InvalidEmailRoleAccessPolicyException) cannot do so against the emulator, because neither refusal happens.
Fix: the SetRiskConfiguration handler's NotifyConfiguration validation (the same gate as Cause 1), which must reject a SourceArn whose service is not ses (or whose account is not the caller's) with NotAuthorizedException before the sending-authorization check.
Traces: cognito-idp__sesv2.risk-notify-source-arn-outside-ses-rejected.

Cause 3 of 3: CreateUserPool and UpdateUserPool accept an EmailConfiguration of {EmailSendingAccount: COGNITO_DEFAULT, SourceArn: <SES identity ARN>} that the SES identity does not authorize.
AWS: Smithy (cognito-idp): both CreateUserPool and UpdateUserPool model InvalidEmailRoleAccessPolicyException (client, 400) and InvalidParameterException (client, 400). Recorded behavior: naming an SES identity whose policy does not let Cognito send is refused with code InvalidEmailRoleAccessPolicyException and the message "Cognito is not allowed to use your email identity" (fixed text); the refused CreateUserPool leaves NO pool of that name behind (ListUserPools shows none), and the refused UpdateUserPool leaves the pool's EmailConfiguration as it was (EmailSendingAccount COGNITO_DEFAULT with no SourceArn member). Once the identity's policy authorizes email.cognito-idp.amazonaws.com for that account, what is left to refuse is the missing verification, and the answer becomes InvalidParameterException with the message "Cognito received the following error from Amazon SES when attempting to send email: Email address is not verified. The following identities failed the check in region <REGION>: <source ARN>" — fixed text up to the colon, with <REGION> the request's region upper-cased and the ARN from the request.
Emulator: answers HTTP 200 and creates the pool — replay reports "expected a refusal, but the call succeeded: ['ResponseMetadata', 'UserPool']" for the CreateUserPool whose EmailConfiguration names an unauthorized, unverified SES identity.
Why: a pool is created (or switched) onto a sender that cannot send, and the client gets no signal. On AWS neither call can succeed until the SES identity both authorizes Cognito and is verified, so sign-up/verification email paths built against the emulator appear configured and then fail at send time with no corresponding API refusal.
Fix: the CreateUserPool and UpdateUserPool handlers' EmailConfiguration validation in the cognito-idp service, which must apply the same SES-sender gate as Cause 1/2 to EmailConfiguration.SourceArn before creating or mutating the pool, and must not persist anything when it refuses.
Traces: cognito-idp__sesv2.unverified-ses-identity-as-pool-sender-refused.

No open issue carries these checks (the replay report lists all three as unowned and none is marked ALREADY FILED). The nearest filed sesv2-side work, 20261127T073132Z-sesv2-deleteemailidentity-is-not-refused-while-the-identity.md and 20261124T235503Z-sesv2-send-path-s-unverified-identity-refusal-wrong.md, concern SESv2's own identity and send paths, not cognito-idp's sender gate.
