# apigateway__kinesis: 7 net-new causes — the integration role's kinesis:GetRecords grant is denied, a GET backend verb is served instead of refused with UnknownOperationException, PutRecords answers 500, and streams created through the stage never reach ACTIVE

> _Note: this issue was identified against the code base at commit `9bfc3dcca28986b1e030db2b6d5b17f08a507141`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutIntegration

## Description
Seven independent causes on the REST API AWS-integration path to Kinesis (type AWS, credentials = an integration role, action/URI-style integrations).

Cause 1 of 7: the integration role's kinesis:GetRecords (and other Kinesis) grants are not honoured — every read is refused AccessDeniedException, and the refusal is served with the wrong HTTP status.
AWS: recorded behavior only. With a credentialsArn role whose identity-based policy allows the Kinesis action on the stream, the integration call succeeds and the stage returns the Kinesis response (a GetRecords page, a ShardIterator, a PutRecord result). A genuine denial is an HTTP 400 `AccessDeniedException` whose Message names the assumed role and the action; it is never served with HTTP 200.
Emulator: the stage answers `{"__type":"AccessDeniedException","Message":"User: arn:aws:sts::<account>:assumed-role/<role>/BackplaneAssumeRoleSession is not authorized to perform: kinesis:GetRecords on resource: arn:aws:kinesis:<region>:<account>:stream/* because no identity-based policy allows the kinesis:GetRecords action"}` for roles that do grant it, and serves that refusal body with HTTP 200 in several cases (and HTTP 400 in others). The same misevaluation also preempts input validation: CreateStream with no StreamName answers `(400, 'AccessDeniedException', None)` where AWS answers `(400, 'ValidationException', "1 validation error detected: Value null at 'streamName' failed to satisfy constraint: Member must not be null")` — the fixed text being `1 validation error detected: Value null at '` + `' failed to satisfy constraint: Member must not be null` with the member path as the only variable part.
Why: no Kinesis read through an API Gateway AWS integration can ever succeed, and a client sees a refusal body under a 200 status, so it parses a denial as data.
Fix: the execute-api AWS-integration credential/authorization path (the IAM evaluation for the assumed integration role) and the status mapping for a relayed Kinesis error.

Cause 2 of 7: an integration declaring a non-POST backend verb is served instead of refused by Kinesis.
AWS: recorded behavior only. Kinesis's JSON-RPC endpoint only accepts POST; an integration whose integrationHttpMethod is GET (or any verb other than POST) makes the backend answer HTTP 400 with the body `<UnknownOperationException/>\n`, which the stage relays — regardless of the client's own verb. With integrationHttpMethod POST the same operation succeeds for any client verb.
Emulator: the GET-backed integration is executed as if it were POST — CreateStream answers `200 {}`, DeleteStream answers `200 {}`, PutRecord answers 200 with a ShardId/SequenceNumber, DescribeStreamSummary and ListStreams answer 200 with their normal payloads — so the refusal never occurs and switching an integration to a GET backend changes nothing.
Why: a client that mis-declares integrationHttpMethod gets a working API in the emulator and a 400 `<UnknownOperationException/>` in AWS; a negative test for this can never pass.
Fix: the Kinesis front door's HTTP-method gate (refuse non-POST with the UnknownOperationException body) — or the AWS-integration request builder that must send the declared verb unchanged.

Cause 3 of 7: a stream created in these scenarios never leaves StreamStatus CREATING.
AWS: recorded behavior only. A stream created with CreateStream transitions CREATING -> ACTIVE, and DescribeStream/DescribeStreamSummary report ACTIVE within a short settling period.
Emulator: DescribeStreamSummary keeps reporting `StreamStatus: 'CREATING'` indefinitely (observed with OpenShardCount 1 and a full StreamDescriptionSummary otherwise), so every scenario that waits for ACTIVE before driving the stage stalls.
Why: no client can wait for a stream to become usable; every create-then-use flow hangs.
Fix: the Kinesis CreateStream state machine — settle the stream to ACTIVE.
