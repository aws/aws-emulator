# A boundary-refused ValidationException carries no RequestId, though every handler-raised exception of this service mints one

_Filed: 2026-11-28T10:26:31Z_
_Operation: CreateUser | Class: error-response_

> _Note: this issue was identified against the code base at commit `687333e2232d3fadb3887f8d91f372124a7f50c2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

This service answers two kinds of `ValidationException`: one a HANDLER builds (an unsupported `AttributePath`, an unsearchable `Filters` path, a `NextToken` the listing cannot resume at) and one the boundary validator raises before any handler runs (an absent `@required` member, a value outside a declared `@length`/`@pattern`/`@range`). The handler-built one carries a `RequestId`, because every handler goes through the single `crate::state::validation` constructor, which stamps `request_id: Some(new_request_id())`. The boundary-refused one carries NO `RequestId`: `EmulatedService::override_refusal` is the only seam that sees that refusal and it answers with a `Refused`, which is a code and a message and nothing else. So the most common failure a client of this service meets — a malformed request — comes back without the member the model documents as returned inside the exception when a request fails, and the crate's own doc for the shared constructor asserts the opposite: that a handler refusal 'carries the same exception members as one the boundary validator raises'. The same hole applies to every operation of the service, since the seam is service-wide; `CreateUser` names it because a `@pattern`/`@required` refusal on `UserName`/`IdentityStoreId` is the common way to reach it. Note this is NOT the gap a fixed issue already closed: that one moved the ~6 handler-side constructors in `state.rs` from `request_id: None` to a minted id (and they now do mint one); the pre-handler path was never covered.

## Evidence

Smithy, `ValidationException$RequestId` (`smithy_query(query="doc",shape="ValidationException",member="RequestId")`): "The identifier for each request. This value is a globally unique ID that is generated by the identity store service for each sent request, and is then returned inside the exception if the request fails." The same member with the same sentence is modelled on `ConflictException` and `ResourceNotFoundException`.

Handler side — services/service-com-amazonaws-identitystore-awsidentitystore/src/state.rs:1232-1243:
```
/// The one constructor every handler calls, so a refusal a HANDLER raises carries the
/// same exception members as one the boundary validator raises: `reason` stays absent
/// ... and `RequestId` is this call's
/// ([`new_request_id`]).
pub fn validation(message: impl Into<String>) -> ValidationException {
    ValidationException {
        message: Some(message.into()),
        request_id: Some(new_request_id()),
        reason: None,
    }
}
```

Boundary side — services/service-com-amazonaws-identitystore-awsidentitystore/src/service.rs:151-157:
```
        let Refusal::Invalid(violations) = refusal else {
            return None;
        };
        Some(Refused {
            code: "ValidationException".to_string(),

```
and the type it fills in, vendor/smithy-server-runtime/src/pre_dispatch.rs:183-188:
```
pub struct Refused {
    /// Error code / `__type` shape name.
    pub code: String,
    /// Human-readable message, unescaped — each protocol escapes it itself.
    pub message: String,

```
There is no third member, so the body this service returns for a pre-handler refusal cannot carry a `RequestId` as written.

Test coverage: services/.../tests/all/exception_envelope.rs:17-19 states the rule — "every modelled exception this service returns carries a `RequestId` in the modelled form" — and `every_modelled_exception_carries_a_request_id_minted_per_call` (lines 254-356) asserts it, but all eight of its rows are handler-raised refusals (DescribeGroup/ListGroups not-found, CreateGroup/CreateUser/UpdateGroup conflicts, ListGroups filter path, ListUsers bad cursor, UpdateGroup unowned attribute path). No row sends a request the boundary validator refuses, so the gap is unpinned.

## Steps to Reproduce

1. POST / with X-Amz-Target: AWSIdentityStore.CreateUser and body {"IdentityStoreId": "d-9067f3a1c2", "UserName": "has a space"} — a value the modelled `UserName` @pattern refuses, so the boundary validator refuses it before the handler runs.
2. Observe the 400 body: `__type` ValidationException and the `1 validation error detected: ...` message this service words, with NO `RequestId` member.
3. POST / with X-Amz-Target: AWSIdentityStore.CreateUser twice with the same valid `UserName` so the second call is refused by the HANDLER with ConflictException; observe that body DOES carry a `RequestId` in the modelled 8-4-4-4-12 form.
4. Same contrast with any handler-raised ValidationException, e.g. ListUsers with {"IdentityStoreId": "d-9067f3a1c2", "NextToken": "notacursor"}: RequestId present. Only the pre-handler refusal omits it.
