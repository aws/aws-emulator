# athena__glue__s3: Athena never decompresses GZIP (.gz) objects under a table's location — the scan feeds gzip magic bytes into the text parser and the query ends FAILED with an emulator-authored CSV-parse message

> _Note: this issue was identified against the code base at commit `20727daa37e83c71ce6574f25fa4da3d0a65d3f6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartQueryExecution

## Description
The emulator's Athena query engine now resolves the Glue Data Catalog table and reaches its scan, but the scan reads every object under StorageDescriptor.Location as raw bytes: a GZIP-compressed object is never decompressed, so the gzip container's magic bytes are handed to the delimited-text parser and the query dies as bad data. 1 cause.

Cause 1 of 1: a GZIP-compressed (.gz) object under the table location is not decompressed before parsing.
AWS: Athena reads a Hive table declared with StorageDescriptor.InputFormat 'org.apache.hadoop.mapred.TextInputFormat' and SerdeInfo.SerializationLibrary 'org.apache.hadoop.hive.serde2.lazy.LazySimpleSerDe' through the Hadoop codec factory, which selects a decompressor from the object key's suffix — '.gz' is GZIP — and only then applies field.delim and skip.header.line.count. This is documented AWS behaviour (Athena supports GZIP-compressed text data; CloudFront standard logging writes exactly such objects, keyed '<distribution-id>.<yyyy-MM-dd-HH>.<hash>.gz', tab-delimited, with two leading '#Version:'/'#Fields:' header lines skipped by skip.header.line.count=2). The Athena Smithy model says nothing about compression, so the wire requirement is only the outcome it produces: QueryExecutionStatus.State reaches SUCCEEDED (Smithy: QueryExecutionState enum) with no StateChangeReason and no AthenaError, and GetQueryResults returns one row per log record — for 'SELECT "$path", count(*), count(DISTINCT x_edge_request_id), min(sc_status) FROM <db>.<table> GROUP BY 1', one group per log object whose first column is that object's 's3://<bucket>/<key>' URI and whose counts are the number of data rows in the decompressed body (the header lines excluded). When a text object genuinely is malformed, AWS fails the query with State FAILED and a message of the fixed form 'HIVE_BAD_DATA: Error parsing field value '<value>' for field <n>: <detail>' (AthenaError.ErrorCategory 2, Retryable false, with an ErrorType set); the identifiers, field index and value come from the data, the 'HIVE_BAD_DATA: ' prefix and 'Error parsing field value ... for field ...' wording are fixed.
Emulator: the query ends State FAILED with StateChangeReason == AthenaError.ErrorMessage == 'HIVE_BAD_DATA: Error reading the data of <db>.<table>: CSV parse error: record 0 (line 1, field: 0, byte: 0): invalid utf-8: invalid UTF-8 in field 0 near byte index 1', AthenaError {ErrorCategory: 2, Retryable: false} and NO ErrorType. The failure is at byte index 1 of record 0 — the gzip header (0x1f 0x8b) — which is exactly what reading the '.gz' object without inflating it produces. The fixed text 'Error reading the data of <db>.<table>: CSV parse error: record <r> (line <l>, field: <f>, byte: <b>): invalid utf-8: invalid UTF-8 in field <f> near byte index <i>' is the emulator's own CSV reader's and appears in no AWS response; only the database/table names come from the request, and the record/line/field/byte offsets are the emulator's parser state.
Why: a client that registers the standard CloudFront/ELB/S3-access-log layout in Glue (every one of which is GZIP text) and then queries it through Athena gets a hard FAILED query for data AWS reads successfully, so no compressed dataset can be analysed at all. A client that parses StateChangeReason to classify the failure also sees an unknown message shape and a missing AthenaError.ErrorType, so it cannot tell 'compression/codec problem' from 'genuinely malformed row'.
Fix: the athena crate's query-execution scan path — codec selection from the object key suffix (GZIP for '.gz', and the other codecs Hive recognises) before the delimited-text reader runs, and the bad-data classification that maps a real parse failure onto AWS's HIVE_BAD_DATA message and AthenaError.ErrorType rather than echoing the local CSV reader's diagnostics.
Traces: athena__glue__s3.e2e-athena-table-cloudfront-logs-lifecycle (fails in phase 3/6 'solve', on the analysis query over the table whose location holds one gzip-compressed CloudFront log object).
