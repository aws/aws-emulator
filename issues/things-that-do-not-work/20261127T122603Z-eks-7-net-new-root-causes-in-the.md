## Description
SEVEN separate net-new root causes in the Kubernetes API the emulator serves at the address DescribeCluster publishes as cluster.endpoint. Smithy (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json) types only DescribeCluster -> Cluster.endpoint / Cluster.certificateAuthority.data; everything reached THROUGH that endpoint is recorded behavior only. Each cause below is a SEPARATE defect and must be closed separately; each carries its own failing check ids.

These are net-new: the `kubectl apply` client-side validation failure that previously stopped these checks (open issue 20261122T113249Z-eks-3-net-new-root-causes-in-the.md, Cause 1, the unserved OpenAPI document) no longer stops them — the applies now reach the server and the checks fail further along, on the surfaces below. That issue, 20261123T142524Z-eks-4-net-new-root-causes-in-the--r2.md (POST on core/v1 services) and 20261124T090000Z-eks-the-kubernetes-data-plane-serves-no-hpa-and-four-checks-still-time-out.md (autoscaling/v2 and four OTHER timed-out checks) are the nearest filed issues; none of them routes or covers the verbs, resources, subresources or checks named here.

Cause 1 of 7: the core/v1 pod `log` subresource accepts no GET — a pod's output cannot be read at all.
  AWS:      recorded behavior only. A real apiserver answers GET /api/v1/namespaces/<ns>/pods/<pod>/log with HTTP 200 and the container's stdout/stderr as text/plain (and 400 BadRequest with a Status object when the pod has more than one container and no container= query parameter). A method-level refusal is never the answer: GET is the only verb this subresource routes.
  Emulator: HTTP 405 with {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"the server does not allow GET on /api/v1/namespaces/<ns>/pods/<pod>/log","reason":"MethodNotAllowed","details":null,"code":405}. The fixed text is "the server does not allow GET on " + the request path; the namespace and pod name in that path are per-run values. `kubectl logs <pod> -n <ns>` renders it as `Error from server (MethodNotAllowed): ...`.
  Why:      reading a workload's output is how a client verifies that the workload ran and what it produced — `kubectl logs`, a CI smoke test, a log shipper, any operator that inspects a failing pod. With 405 there is no way to observe anything a container emitted, so a sentinel a pod prints can never be confirmed and a failure can never be diagnosed.
  Fix:      the request routing of the served cluster Kubernetes API (the EKS cluster data-plane handler's verb/resource table for core/v1 pods subresources) plus the pod log store it must read: route GET on pods/<name>/log and answer 200 text/plain with the container's output.
  Traces:   eks.k8s-deployment-apply-runs-pods-on-real-nodes, eks.nodegroup-taint-effect-is-translated-and-repels-an-untolerating-pod.

Cause 2 of 7: the core/v1 pod `exec` subresource accepts no POST — no command can be run inside a pod.
  AWS:      recorded behavior only. A real apiserver answers POST /api/v1/namespaces/<ns>/pods/<pod>/exec?command=...&stdout=true&stderr=true by upgrading the connection (SPDY or WebSocket) with HTTP 101 Switching Protocols and streaming the command's output, so `kubectl exec <pod> -n <ns> -- <cmd>` exits 0 with that output. A method-level refusal is never the answer.
  Emulator: the upgrade never happens: `error: unable to upgrade connection: the server does not allow POST on /api/v1/namespaces/<ns>/pods/<pod>/exec` (HTTP 405 MethodNotAllowed, same Status body shape as Cause 1 with "POST" and the exec path). The fixed text is "the server does not allow POST on " + the request path.
  Why:      `kubectl exec` is how a client reads state that exists only inside the pod — a mounted ConfigMap/Secret volume, a projected service-account token, a file a sidecar wrote. Without it, nothing about a running container's filesystem or environment can be observed, so the entire class of "the value reached the workload" verification is impossible.
  Fix:      the request routing and connection-upgrade path of the served cluster Kubernetes API (the EKS cluster data-plane handler's pods/exec subresource): accept POST on pods/<name>/exec, upgrade the connection, and stream the command's result.
  Traces:   eks.k8s-configmap-mounted-value-readable-inside-the-pod.

Cause 3 of 7: the core/v1 `endpoints` resource accepts no GET — a Service's backing endpoints cannot be read.
  AWS:      recorded behavior only. A real apiserver answers GET /api/v1/namespaces/<ns>/endpoints/<service> with HTTP 200 and the Endpoints object the endpoints controller maintains for the Service of that name: subsets[].addresses[] holding one entry per ready backing pod (ip plus targetRef naming the pod) and subsets[].ports[] mirroring the Service's ports. Reading a named object is a GET, which this resource always routes.
  Emulator: HTTP 405 with {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"the server does not allow GET on /api/v1/namespaces/<ns>/endpoints/<service>","reason":"MethodNotAllowed","details":null,"code":405}. Fixed text is "the server does not allow GET on " + the request path.
  Why:      Endpoints is the authoritative answer to "which pods is this Service actually sending traffic to". A client cannot confirm a Service has any ready backend before sending traffic, cannot tell an empty selector from an unready pod, and every readiness/rollout gate built on endpoint membership is blind.
  Fix:      the request routing of the served cluster Kubernetes API (the EKS cluster data-plane handler's core/v1 resource table) plus the endpoints projection in its state: route GET on endpoints/<name> and answer 200 with subsets derived from the Service's selector and the ready pods matching it.
  Traces:   eks.eks-deployment-pod-is-reachable-through-a-cluster-service.

Cause 4 of 7: the discovery.k8s.io/v1 `endpointslices` resource is not served at all — it is absent from API discovery, so a client cannot even name it.
  AWS:      recorded behavior only. Every supported EKS Kubernetes version serves the discovery.k8s.io/v1 group, and the EndpointSlice controller maintains one or more EndpointSlices per Service, labelled kubernetes.io/service-name=<service>. GET /apis/discovery.k8s.io/v1/namespaces/<ns>/endpointslices?labelSelector=kubernetes.io/service-name=<svc> answers 200 with an EndpointSliceList whose items[].endpoints[] carry addresses[] (the backing pod IPs), conditions.ready and targetRef, and items[].ports[] the Service's ports. The resource appears in GET /apis/discovery.k8s.io/v1, which is why `kubectl get endpointslices` resolves the type.
  Emulator: the type does not resolve: `error: the server doesn't have a resource type "endpointslices"` — i.e. the resource is missing from the group's discovery document (or the group is unserved), so the request is never even dispatched. The fixed text is kubectl's rendering of an unknown type; the requirement is that discovery.k8s.io/v1 lists endpointslices and serves the list.
  Why:      EndpointSlice has been the scalable replacement for Endpoints since Kubernetes 1.21 and is what current clients, kube-proxy replacements, ingress controllers and service meshes read to learn a Service's backends. A client that targets a modern cluster finds the API it is written against does not exist on the emulator, so load-balancing and backend-membership behaviour cannot be observed through the supported path.
  Fix:      the discovery and routing of the served cluster Kubernetes API (the EKS cluster data-plane handler's API-group table) plus the slice projection in its state: serve discovery.k8s.io/v1 with endpointslices, honour labelSelector on kubernetes.io/service-name, and derive each slice's endpoints from the Service's ready backing pods.
  Traces:   eks.k8s-service-clusterip-load-balances-across-pods.

Cause 5 of 7: the apps/v1 Deployment `scale` subresource is not routed — scaling a Deployment is answered 404 NotFound.
  AWS:      recorded behavior only. A real apiserver routes GET/PUT/PATCH on /apis/apps/v1/namespaces/<ns>/deployments/<name>/scale and answers 200 with an autoscaling/v1 Scale object whose spec.replicas is the requested count and status.replicas the observed one; the Deployment's controller then converges its pods to that count. `kubectl scale deployment/<name> --replicas=<n> -n <ns>` uses exactly this subresource and prints `deployment.apps/<name> scaled`.
  Emulator: HTTP 404 — `Error from server (NotFound): the server could not find the requested resource: /apis/apps/v1/namespaces/<ns>/deployments/<name>/scale`. The fixed text is "the server could not find the requested resource: " + the request path; the namespace and deployment name are per-run values. The Deployment object itself exists and is readable, so the missing route is specifically the scale subresource.
  Why:      scaling through the scale subresource is the standard way every client, autoscaler and `kubectl scale` changes a workload's replica count. A 404 means a replica count can never be changed through the supported API, and a client cannot distinguish "this deployment does not exist" from "this server cannot scale".
  Fix:      the request routing of the served cluster Kubernetes API (the EKS cluster data-plane handler's apps/v1 subresource table) plus the Deployment replica reconciliation: route the scale subresource, return an autoscaling/v1 Scale object, and converge the Deployment's pods to spec.replicas.
  Traces:   eks.k8s-deployment-scale-converges-to-the-requested-replicas.

Cause 6 of 7: a ServiceAccount's own token is not accepted as a bearer credential — authenticating as system:serviceaccount:<ns>:<sa> is refused 401 Unauthorized.
  AWS:      recorded behavior only. A token issued for a ServiceAccount (TokenRequest on serviceaccounts/<name>/token, or a mounted projected token) authenticates against the cluster's own apiserver as the user system:serviceaccount:<ns>:<sa> with group system:serviceaccounts. With a Role granting `get` on pods and a RoleBinding to that ServiceAccount, `kubectl auth can-i get pods` as that identity prints `yes` (a SelfSubjectAccessReview answered allowed=true), and the verbs the Role does not grant are refused 403 Forbidden with the apiserver's sentence — never 401, because the identity itself is valid.
  Emulator: the request is rejected before authorization: `error: You must be logged in to the server (Unauthorized)` (rc=1, empty stdout) for `kubectl auth can-i get pods` as system:serviceaccount:<ns>:<sa>, even though the Role grants `get`. The ServiceAccount token the cluster itself minted is not a credential its own apiserver accepts.
  Why:      in-cluster identity is the basis of everything a workload does: every pod, controller, operator and Helm hook authenticates to the apiserver with its ServiceAccount token. With 401 no in-cluster client can talk to its own cluster, and RBAC cannot even be exercised — a denied verb is indistinguishable from an unusable credential, so a permitted-vs-denied contrast proves nothing. Note the open issue 20261123T045518Z-eks-iam-sts-the-served-cluster-kubernetes-api-89ba98.md concerns the OPPOSITE defect (anonymous requests wrongly answered 200) and does not cover a valid ServiceAccount token being refused.
  Fix:      the authentication path of the served cluster Kubernetes API (the EKS cluster data-plane handler that validates the Authorization bearer token): accept a token the cluster minted for a ServiceAccount, resolve it to system:serviceaccount:<ns>:<sa> with group system:serviceaccounts, and let the RBAC authorizer decide the request.
  Traces:   eks.k8s-rbac-get-only-role-rejects-deleting-a-pod.

Cause 7 of 7: two end-to-end data-plane flows never finish — the check is interrupted at the suite's 60-second budget with no answer asserted.
  AWS:      recorded behavior only. Each flow settles: a kubectl-applied Deployment's pods reach Running, the Service in front of them gets a ClusterIP and ready endpoints, in-cluster DNS resolves <svc>.<ns>.svc.cluster.local to that ClusterIP, and the check then asserts the settled representation.
  Emulator: `Check timed out after 60.0s` for both checks, with no response recorded — the flow is still polling for convergence when the budget expires, so none of the assertions at its end ever run. Hypothesis: these are the downstream effect of Causes 1-5 above plus the already-filed non-running pods (20261126T013437Z-eks-5-net-new-root-causes-the-non.md) — each flow waits for a pod to report Running or for a Service to report endpoints that this data plane never produces. No specific wrong ANSWER of this service is identified in them; what is reported is that the flow does not converge inside the budget. Both checks previously failed with a concrete 405 (POST on core/v1 services), so they now get further and hang instead.
  Why:      a flow that cannot finish is reported as a timeout, so the behaviour it exists to verify is simply unverified — a client sees a cluster that accepts its manifests and then never reaches a serving state.
  Fix:      the convergence of the served cluster Kubernetes API's workload state (the EKS cluster data-plane handler's pod/Deployment/Service reconciliation) — measure which wait each check is interrupted in and make that object settle; expect Causes 1-5 to be prerequisites.
  Traces:   eks.eks-coredns-resolves-a-service-to-the-clusterip-the-api-reports, eks.kubectl-applied-deployment-pod-runs-and-serves-its-configmap-through-a-service.
