# The in-Lambda AWS SDK has no 'ses' client, so a handler calling SES SendEmail fails with UnknownServiceError instead of sending

> _Note: this issue was identified against the code base at commit `dcecf1852a9f86e80d5d906dc10b7044742585db`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEmail

## Description
Cause 1 of 1: the AWS SDK the emulator's Lambda Python runtime provides to function code does not register the `ses` (Amazon SES, API version 2010-12-01) service, so `boto3.client('ses')` raises before any call is made. Failing checks: cloudwatch__events__lambda__logs__s3__ses.cdk-scheduled-report-email-rule-config-workflow, cloudwatch__events__lambda__logs__s3__ses.cdk-scheduled-report-email-workflow.

AWS: `ses` is a first-class service in every AWS SDK shipped with the Lambda managed Python runtimes, so `boto3.client('ses')` constructs a client and `send_email(Source=..., Destination={'ToAddresses':[...]}, Message={'Subject':{'Data':...},'Body':{'Text':{'Data':...}}})` returns a 200 whose body carries the required `MessageId`. Smithy: the emulator already carries this service model — `SendEmail` input requires `Source` (Address), `Destination` (Destination) and `Message` (Message); its output requires `MessageId` (MessageId); its modeled refusals are MessageRejected, MailFromDomainNotVerifiedException, ConfigurationSetDoesNotExist, AccountSendingPausedException and ConfigurationSetSendingPausedException, all 400 client errors. None of those is what the handler sees. So the API surface exists over the wire; only the in-function SDK's service catalog omits it.

Emulator: the handler's `boto3.client('ses')` raises botocore `UnknownServiceError` with the message "Unknown service: 'ses'. Valid service names are: sqs, sns, events, eventbridge, dynamodb, logs, cloudwatchlogs, cloudwatch, apigateway, apigatewaymanagementapi, secretsmanager, ssm, opensearch, es, stepfunctions, sfn, sesv2, s3, xray, rds-data, appconfigdata, appconfig, config, configservice, codedeploy, cloudfront, lambda". The fixed text of that message is botocore's "Unknown service: '<name>'. Valid service names are: <list>"; the variable parts are the requested service token (`ses`) and the catalog the runtime registered — note that `sesv2` is present and `ses` is absent, so this is a missing catalog entry, not a missing dependency. The scheduled run therefore writes its S3 report object and then returns `{"event":"report_failed","stage":"ses_send_failed","errorCode":"UnknownServiceError"}`; `report_sent` is never produced, no `sesMessageId` is ever issued, the log-metric filter over "report_sent" stays empty and the dependent schedule/logs/metrics/alarm legs never reach a verdict.

Why: any function whose code mails through SES v1 — the shape generated by CDK/SAM samples and by the overwhelming majority of existing handlers — cannot run at all on the emulator. The client raises at construction time, before credentials, IAM or endpoint resolution are consulted, so a caller cannot distinguish a missing permission from a missing service and cannot work around it other than by rewriting the handler to sesv2. Every downstream signal of a mail-sending pipeline (the success-path structured log line, the metric filter it feeds, the alarm over that metric) is silently absent.

Fix: the Lambda runtime sandbox's bundled AWS SDK service catalog / endpoint registry — the component that decides which service tokens in-function `boto3.client(<token>)` can resolve and where it points them. `ses` must be registered there (and aliased consistently with how `sesv2`, `sfn`/`stepfunctions`, `es`/`opensearch` are already aliased) and routed to the emulator's existing SES front door, so SendEmail is served and returns a MessageId. A related but distinct open issue, 20261107T212447Z-lambda-sns-sqs-4-net-new-causes-async-destinations-dlq-never.md, records the same catalog missing an 'sns' client under the lambda__sns__sqs heading; it does not cover `ses` or this heading.

Traces: both cdk-scheduled-report-email checks below; the first shows the raised UnknownServiceError verbatim in the handler's report_failed record, the second shows only `events seen: ['report_failed']` after 420 s of polling for report_sent.

## Evidence
