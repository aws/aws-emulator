# swf: decisions that AWS fails are applied silently — no RequestCancelActivityTaskFailed/UNHANDLED_DECISION, no ScheduleLambdaFunctionFailed(ID_ALREADY_IN_USE), no StartChildWorkflowExecutionFailed, and a child cancel request never reaches the child or the parent (4 causes)

> _Note: this issue was identified against the code base at commit `a24aa969c7ede1b0812774a0cc80ce835cb01596`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RespondDecisionTaskCompleted

## Description
Four net-new causes in the decision-application path of RespondDecisionTaskCompleted and the child-workflow machinery. In each one AWS records a `*Failed` history event (and keeps the run open with a fresh decision task); the emulator records nothing of the kind, so the decider is never told and the next decision task never arrives.

Cause 1 of 4: RequestCancelActivityTask naming an activityId that was never scheduled, batched with CompleteWorkflowExecution, neither fails nor blocks the close. Failing check: swf.unhandled-decision-blocks-complete-on-cancel-and-schedule-failures.
AWS: the batch records, in order, `RequestCancelActivityTaskFailed` with `cause=ACTIVITY_ID_UNKNOWN`, `activityId` = the decision's activityId and `decisionTaskCompletedEventId` = that call's own DecisionTaskCompleted eventId, then `CompleteWorkflowExecutionFailed` with `cause=UNHANDLED_DECISION` and the same `decisionTaskCompletedEventId`; no `ActivityTaskCancelRequested` is recorded, the execution stays OPEN and `DescribeWorkflowExecution.openCounts.openDecisionTasks` becomes 1 so the decider gets a fresh task carrying both failures. Smithy: `RequestCancelActivityTaskFailedCause` models `ACTIVITY_ID_UNKNOWN`; `CompleteWorkflowExecutionFailedCause` models `UNHANDLED_DECISION`. RespondDecisionTaskCompleted itself answers 200/empty in both cases — the divergence is in the history and in DescribeWorkflowExecution.
Emulator: after the batch, `openCounts.openDecisionTasks` stayed 0 for 30 s and no new decision task was scheduled, i.e. the close was applied and the cancel failure was swallowed.
Why: a decider that batches bookkeeping with a close relies on SWF refusing the close so it can react; here the run is already closed and the follow-up task never comes.
Fix: the decision loop in services/service-com-amazonaws-swf-simpleworkflowservice/src/ops/respond_decision_task_completed.rs must (a) validate RequestCancelActivityTask against the open activity ids and append RequestCancelActivityTaskFailed(ACTIVITY_ID_UNKNOWN) instead of requesting a cancellation, and (b) count that freshly appended failure as an unhandled event for the following close decision. This is the same family as the open issue 20261117T125351Z-swf-a-failed-decision-earlier-in-the-same.md (which carries only the four CancelTimer replay keys); this check adds RequestCancelActivityTask and the ACTIVITY_ID_UNKNOWN event itself, so closing that issue does not close this one.
Traces: swf.unhandled-decision-blocks-complete-on-cancel-and-schedule-failures.

Cause 2 of 4: two ScheduleLambdaFunction decisions sharing one `id` are both scheduled — the duplicate-id check is missing. Failing check: swf.schedule-lambda-duplicate-id-fails-in-history.
AWS: within one decision list, the first use of an `id` records `LambdaFunctionScheduled`; a second decision reusing it records `ScheduleLambdaFunctionFailed` with `cause=ID_ALREADY_IN_USE`, `id` = the reused id, `name` = the function named by the decision and `decisionTaskCompletedEventId` = that call's DecisionTaskCompleted eventId; a third decision with a distinct id is scheduled normally, and the execution stays OPEN. Smithy: `ScheduleLambdaFunctionFailedCause` enumerates `ID_ALREADY_IN_USE` first; `ScheduleLambdaFunctionFailedEventAttributes` requires `id`, `name`, `cause` and `decisionTaskCompletedEventId`.
Emulator: all three decisions were scheduled — the history settled at ['WorkflowExecutionStarted', 'DecisionTaskScheduled', 'DecisionTaskStarted', 'DecisionTaskCompleted', 'LambdaFunctionScheduled', 'StartLambdaFunctionFailed', 'LambdaFunctionScheduled', 'StartLambdaFunctionFailed', 'LambdaFunctionScheduled', 'StartLambdaFunctionFailed', 'DecisionTaskScheduled'] with no `ScheduleLambdaFunctionFailed` event at all (three LambdaFunctionScheduled events for ids dup-id, dup-id, solo-id).
Why: the Lambda-task id is the decider's handle for correlating the result; accepting a duplicate produces two scheduled tasks under one id, so result correlation is ambiguous in the emulator and impossible to reproduce against AWS.
Fix: the ScheduleLambdaFunction branch of the decision loop in respond_decision_task_completed.rs must reject an id already in use by an open Lambda task (including one scheduled earlier in the same decision list) with ScheduleLambdaFunctionFailed(ID_ALREADY_IN_USE) instead of scheduling it.
Traces: swf.schedule-lambda-duplicate-id-fails-in-history.

Cause 3 of 4: a StartChildWorkflowExecution decision naming an unregistered workflow type produces no outcome event and no follow-up decision task. Failing check: swf.start-child-unregistered-type-records-start-child-failed-rejected.
AWS: the decision records `StartChildWorkflowExecutionFailed` with `cause=WORKFLOW_TYPE_DOES_NOT_EXIST`, `workflowType` = the unregistered type, `workflowId` = the decision's child workflow id, `control` = the decision's control and `decisionTaskCompletedEventId` = that call's DecisionTaskCompleted eventId; no `StartChildWorkflowExecutionInitiated`/`ChildWorkflowExecutionStarted` is recorded, the parent counts 0 open children, and a NEW decision task is scheduled on the parent's task list carrying that failure. Smithy: `StartChildWorkflowExecutionFailedCause` models `WORKFLOW_TYPE_DOES_NOT_EXIST`.
Emulator: the check reached the 60 s wall while long-polling the parent's task list for the decision task that must follow the phantom-type decision (`Check timed out after 60.0s`), so no outcome event and no rescheduled decision task were observable. Hypothesis: the decision is dropped without appending StartChildWorkflowExecutionFailed, so nothing makes the parent decidable again.
Why: the decider learns of an unregistered child type only through this event; without it the parent hangs forever with no decision task, which is exactly what the replay saw.
Fix: the StartChildWorkflowExecution branch of the decision loop in respond_decision_task_completed.rs must resolve the named type in the domain and, when it is absent (or deprecated), append StartChildWorkflowExecutionFailed with the modeled cause and schedule the parent's next decision task.
Traces: swf.start-child-unregistered-type-records-start-child-failed-rejected.

Cause 4 of 4: a cancel request addressed to a child execution is not propagated to the child or back to the parent. Failing check: swf.child-cancel-request-reports-child-canceled-to-parent.
AWS: a parent's `RequestCancelExternalWorkflowExecution` decision naming its running child sets the child's `executionInfo.cancelRequested=true` (child still OPEN), records `WorkflowExecutionCancelRequested` on the child whose `externalWorkflowExecution` is the parent, records `ExternalWorkflowExecutionCancelRequested` on the parent, and after the child answers with a CancelWorkflowExecution decision the child closes CLOSED/CANCELED and the parent records exactly one `ChildWorkflowExecutionCanceled` (naming the child execution, its workflow type, the decision's details, and the `initiatedEventId`/`startedEventId` of the child's start events) with `openCounts.openChildWorkflowExecutions` back to 0.
Emulator: the check reached the 60 s wall (`Check timed out after 60.0s`) while waiting for the first observable step of that chain — the child's `cancelRequested` flag read through DescribeWorkflowExecution — so none of the chain's events were observable. Hypothesis: the RequestCancelExternalWorkflowExecution decision is accepted but never delivered to the addressed execution.
Why: parent/child cancellation is the standard way a parent winds down work; against the emulator the child never learns it was asked to cancel and the parent never learns the child canceled, so the whole pattern is untestable.
Fix: the RequestCancelExternalWorkflowExecution branch of the decision loop in respond_decision_task_completed.rs must mark the addressed execution cancel-requested, append WorkflowExecutionCancelRequested to it (with the requester) plus ExternalWorkflowExecutionCancelRequested to the requester, schedule the target's decision task, and the child-close path must report ChildWorkflowExecutionCanceled to the parent.
Traces: swf.child-cancel-request-reports-child-canceled-to-parent.
