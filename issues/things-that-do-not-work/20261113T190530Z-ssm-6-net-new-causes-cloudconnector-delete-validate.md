# SSM: 6 net-new causes — CloudConnector delete/validate answer NotImplemented, CreateCloudConnector accepts refused roles, DescribePatchProperties and UpdateOpsItem refusal messages are emulator-authored

> _Note: this issue was identified against the code base at commit `4e1dd611e90d7ff289f41b5cfbbd8402822bfd14`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCloudConnector

## Description
Six net-new root causes in the ssm crate, all grounded in failing behavioral checks the suite report lists under '### ssm'. 6 CAUSES — each must be closed before submitting.

Cause 1 of 6 — DeleteCloudConnector answers NotImplemented where AWS refuses an unknown id with ResourceNotFoundException.
AWS: Smithy (services/service-com-amazonaws-ssm-amazonssm/smithy-model/com-amazonaws-ssm-amazonssm.json): DeleteCloudConnector input CloudConnectorId required, @length 36..36, @pattern ^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$; modelled errors ResourceNotFoundException (awsQueryError httpResponseCode 404), ConflictException, InternalServerError. A well-formed CloudConnectorId that names no connector in the account is refused with error code ResourceNotFoundException and, recorded behavior only for the text, the message 'CloudConnector not found for account.' — that sentence is entirely fixed text with no variable parts (it deliberately does not echo the id).
Emulator: the call is refused with error code 'NotImplemented' — the handler is a scaffold stub, so no not-found path exists at all.
Why: a client cannot distinguish 'this connector does not exist' from 'this API does not exist'; delete-if-present and idempotent teardown code paths that catch ResourceNotFoundException propagate a NotImplemented fault instead, and negative tests for the 404 class can never pass.
Fix: the DeleteCloudConnector handler (services/service-com-amazonaws-ssm-amazonssm/src/ops/delete_cloud_connector.rs) and the cloud-connector state it must look the id up in — resolve CloudConnectorId against stored connectors and take the ResourceNotFoundException path with AWS's sentence when it misses.
Related but not covering: open issue 20261104T121102Z-ssm-deletecloudconnector-stub.md records the operation as an unimplemented scaffold stub but carries neither this check id nor the required refusal code/message, so it does not gate this behavior.
Traces: ssm.cloud-connector-delete-nonexistent-rejected.

Cause 2 of 6 — ValidateCloudConnector answers NotImplemented where AWS refuses an unknown id with ResourceNotFoundException.
AWS: Smithy: ValidateCloudConnector is @readonly and paginated (ValidationFindings / NextToken), input CloudConnectorId required @length 36..36 with the uuid @pattern, MaxResults @range 0..75; modelled errors ResourceNotFoundException (awsQueryError httpResponseCode 404) and InternalServerError. A well-formed but unknown CloudConnectorId is refused with error code ResourceNotFoundException and message 'CloudConnector not found for account.' (fixed text, no variable parts) — recorded behavior only for the text. AWS does NOT answer an empty/success validation result for a connector that does not exist.
Emulator: the call is refused with error code 'NotImplemented'.
Why: the only way a client can tell a connector id is stale is the ResourceNotFoundException; a NotImplemented fault reads as an outage of the whole validation API, and a caller that treats 'validate returned no findings' as healthy gets no signal either way.
Fix: the ValidateCloudConnector handler and its lookup against the cloud-connector state — resolve CloudConnectorId first and emit ResourceNotFoundException with AWS's sentence on a miss. No open issue names this operation.
Traces: ssm.validate-cloud-connector-nonexistent-rejected, ssm.validate-cloud-connector-unknown-id-rejected.

Cause 3 of 6 — CreateCloudConnector accepts a RoleArn that names no IAM role and answers 200.
AWS: Smithy: CreateCloudConnector requires DisplayName, RoleArn (CloudConnectorIamRoleArn, @length 20..2048, @pattern ^arn:aws[a-z0-9-]*:iam::\d{12}:role\/[\w-\/.@+=,]{1,1017}$), Configuration and ConfigConnectorArn (@pattern ^arn:aws(-cn|-us-gov)?:config:([^:]+):\d{12}:connector/.+$); the modelled error list (ConflictException, ServiceQuotaExceededException, InternalServerError) does NOT include the refusal AWS actually sends, so for this cause: recorded behavior only. A syntactically valid RoleArn that resolves to no role (or whose trust policy omits the ssm service principal) is refused with error code ValidationException and the message 'Nonexistent role or missing ssm service principal in trust policy: <RoleArn>' — fixed text 'Nonexistent role or missing ssm service principal in trust policy: ' followed by the RoleArn value taken verbatim from the request. The refusal class is specifically ValidationException, not ServiceQuotaExceededException and not ConflictException, and a refused create leaves no connector behind (an independent ListCloudConnectors scan for the DisplayName finds nothing).
Emulator: HTTP 200 with a freshly minted CloudConnectorId, and the connector is then readable through GetCloudConnector and listed by ListCloudConnectors — no IAM resolution happens at all.
Why: a connector wired to a role that does not exist is created and reported healthy, so the operator learns of the broken wiring only when cross-cloud traffic silently fails; every client-side handler for the ValidationException is dead code and the account accumulates connectors AWS would never have minted.
Fix: the CreateCloudConnector handler's input validation — resolve RoleArn against IAM state and check its trust policy for the ssm service principal BEFORE any connector state is written.
Related but not covering: cause 2 of open issue 20261104T073124Z-ssm-skips-existence-checks-getdocument-on-a-deleted.md and cause 8 of open issue 20261104T121102Z-ssm-10-net-new-root-causes-across-getdocument.md describe the same rule from the wire corpus and from other check ids respectively; neither carries this check id, so this failure is re-replayed only from here. The same handler change closes all of them.
Traces: ssm.create-cloud-connector-quota-exceeded-blocked.

Cause 4 of 6 — CreateCloudConnector accepts a role that cannot obtain a cross-cloud web identity token and answers 200.
AWS: recorded behavior only (the model binds no ValidationException on this operation). When the RoleArn names a real role that trusts ssm but is not permitted to call sts:GetWebIdentityToken — and the ConfigConnectorArn names no real AWS Config connector — the create is refused at the federation step with error code ValidationException and the fixed message "Unable to obtain an AWS web identity token for cross-cloud federation. Please verify the cloud connector's AWS IAM role is permitted to call sts:GetWebIdentityToken." (no variable parts). A refused create must leave the ListCloudConnectors id set byte-identical to what it was before the call.
Emulator: HTTP 200 with a new CloudConnectorId (observed response body carried only CloudConnectorId), so the federation step is never attempted and the connector lands in the listing.
Why: this is the refusal that tells an operator the connector's IAM role is missing an sts permission — the single most common cross-cloud misconfiguration. The emulator reports success, so the diagnostic never reaches the client and a connector that can never federate is persisted.
Fix: the CreateCloudConnector handler's validation — after resolving the role, evaluate the cross-cloud federation (web identity token acquisition for the ConfigConnectorArn/Configuration pair) and emit ValidationException with the sentence above, writing no state.
Related but not covering: cause 8 of 20261104T121102Z-ssm-10-net-new-root-causes-across-getdocument.md lists this sentence among several CreateCloudConnector refusals but carries different check ids.
Traces: ssm.cloud-connector-list-reflects-created-connectors.

Cause 5 of 6 — DescribePatchProperties refuses an OperatingSystem/Property mismatch with an emulator-authored message that names a global valid-value list instead of the operating system.
AWS: Smithy: DescribePatchProperties input OperatingSystem (OperatingSystem enum, required), Property (PatchProperty enum, required), optional PatchSet, MaxResults @range 1..50; the only modelled error is InternalServerError, so the refusal class and text are recorded behavior only. A Property that is valid in the enum but not supported for the requested operating system (PRIORITY is Debian/Ubuntu-only) is refused with error code ValidationException and the message 'Property <Property> is not supported for operating system <OperatingSystem>' — fixed text 'Property ', ' is not supported for operating system ', with the Property and OperatingSystem values taken from the request. AWS does not silently return an empty catalog for the mismatch.
Emulator: the error code ValidationException is right, but the message is 'Property PRIORITY is invalid, valid values are PRODUCT, PRODUCT_FAMILY, CLASSIFICATION, MSRC_SEVERITY' — it reports the Property as globally invalid and recites a fixed four-value list, never naming the operating system that actually rejected it. (The same check's positive assertions on the WINDOWS/PRODUCT catalog and the five AMAZON_LINUX_2 CLASSIFICATION values passed; only the refusal message diverges.)
Why: a client reading the message concludes PRIORITY is not a valid patch property anywhere and stops asking for it on Debian/Ubuntu, where AWS does serve it; the message also omits the one piece of information needed to fix the request, the operating system.
Fix: the DescribePatchProperties handler's validation — validate the Property against the per-OS supported set and construct the OS-specific ValidationException message, rather than rejecting the Property against one global enum list.
Traces: ssm.describe-patch-properties-returns-catalog-for-os.

Cause 6 of 6 — UpdateOpsItem's OpsItemConflictException message is authored prose instead of AWS's wrapped service message.
AWS: Smithy: UpdateOpsItem input OpsItemId required @pattern ^(oi)-[0-9a-f]{12}$; modelled errors include OpsItemConflictException (awsQueryError httpResponseCode 409) alongside OpsItemNotFoundException. Mutating an OpsItem whose deletion is already in progress is refused 409 OpsItemConflictException — not OpsItemNotFoundException, because the deletion is still settling — with the SDK-wrapped message 'Deletion of the provided OpsItem is already in progress (Service: AmazonSSM; Status Code: 409; Error Code: OpsItemConflictException; Request ID: <request id>; Proxy: null)'. The fixed text is 'Deletion of the provided OpsItem is already in progress (Service: AmazonSSM; Status Code: 409; Error Code: OpsItemConflictException; Request ID: ' plus the trailing '; Proxy: null)'; only the request id varies per call (the check normalises exactly that span and nothing else).
Emulator: the error code OpsItemConflictException is right, but the message is 'The specified OpsItem is in the process of being deleted.' — the documentation sentence, with none of the wrapped Service/Status Code/Error Code/Request ID/Proxy suffix AWS appends for this class.
Why: a client that matches or logs AWS's message sees text AWS never emits, and the wrapped suffix — the only place the backend request id for the conflicting call appears — is lost, so the conflict cannot be correlated with a support case.
Fix: the UpdateOpsItem handler's deletion-in-progress conflict path plus the shared error renderer that must append the '(Service: AmazonSSM; Status Code: <status>; Error Code: <code>; Request ID: <id>; Proxy: null)' suffix for this OpsItem error class.
Related but not covering: cause 4 of open issue 20261104T121102Z-ssm-10-net-new-root-causes-across-getdocument.md records the same missing wrapped suffix for GetOpsItem's OpsItemNotFoundException; it names neither UpdateOpsItem nor this check id.
Traces: ssm.e2e-ops-item-related-items-and-event-trail-flow.
