# internetmonitor: 2 net-new query-interface causes — StartQuery accepts an empty FilterParameters list instead of refusing it BadRequestException "Invalid request body", and the minted QueryId is a sequential UUID instead of an opaque long URL-safe base64 token

> _Note: this issue was identified against the code base at commit `eef1405ac0806ef267777bba6aefe2b3b0754197`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartQuery

## Description
Two independent defects in the internetmonitor query interface, both grounded in behavioral checks of the StartQuery/GetQueryStatus/GetQueryResults flow. Note on an adjacent open issue: 20261127T054551Z-internetmonitor-startquery-refuses-a-valid-query-with-http.md covers StartQuery answering 400 for a request AWS accepts (its recorded request omits FilterParameters). It does NOT cover either cause below — cause 1 is the opposite direction for a DIFFERENT request shape (FilterParameters present and empty), and cause 2 is about the identifier the successful 200 carries. The recorded checks pin both directions simultaneously, so the discriminator is the request, not the monitor: the two checks that expect a refusal both send FilterParameters=[], and the two that expect a 200 omit FilterParameters entirely; all four monitors were created with no monitored Resources, so an "empty monitor" is NOT what AWS refuses on.

Cause 1 of 2: StartQuery accepts an explicitly empty FilterParameters list.
AWS: Smithy (services/service-com-amazonaws-internetmonitor-internetmonitor20210603/smithy-model/com-amazonaws-internetmonitor-internetmonitor20210603.json) StartQuery — POST /v20210603/Monitors/{MonitorName}/Queries, success 200, output StartQueryOutput with required QueryId; required input MonitorName (@httpLabel, @length 1..255, @pattern ^[a-zA-Z0-9_.-]+$), StartTime, EndTime, QueryType; FilterParameters is an optional list. The model states no rule for an empty list, so this is recorded behavior only: the recording shows a StartQuery carrying FilterParameters=[] (with QueryType=MEASUREMENTS and with QueryType=OVERALL_TRAFFIC_SUGGESTIONS, StartTime/EndTime a one-hour past window) refused with HTTP 400, error code BadRequestException, message "Invalid request body". The whole message is fixed text — it interpolates nothing from the request or from state — and the refusal is per request shape, not per QueryType (the recording exercises two query types and both are refused). The same recording shows the monitor left ACTIVE after the refusal, and a later GetQueryResults for a QueryId that was never minted refused ValidationException (400) "Invalid query ID provided" — also entirely fixed text.
Emulator: the call is accepted. It answers HTTP 200 with a StartQueryOutput body (content-type application/json, 50-byte body) carrying a QueryId, so the check's expected refusal never arrives ("expected StartQuery to be rejected, but it succeeded and returned {... 'QueryId': ...}" and "expected this call to be rejected, but it succeeded and returned {...}"). No BadRequestException is produced for an empty FilterParameters list at all.
Why: a client that sends an empty filter list — the natural encoding of "no filters" in several SDKs and in generated code — is told on AWS that its request body is invalid and must drop the member, but against the emulator it gets a QueryId and proceeds. Any code that branches on that refusal (retry with the member omitted, surface a user-facing validation error, or distinguish "request rejected" from "query started with no data") takes the wrong branch, and a test suite written against AWS records a pass where AWS fails.
Fix: StartQuery's input validation and handler for this crate (the StartQuery handler and the shared refusal text it draws on in the crate's state module). Gate on the request — an explicitly present but empty FilterParameters list — rather than on the monitor's Resources, and answer HTTP 400 with code BadRequestException and the fixed message "Invalid request body". Requests that omit FilterParameters must still be accepted with a 200 and a minted QueryId (see the open issue above), and the monitor's own Status must be untouched by the refusal.
Traces: internetmonitor.start-query-measurements-reaches-succeeded, internetmonitor.get-query-results-schema-for-empty-monitor.

Cause 2 of 2: the QueryId minted by StartQuery is a sequential UUID, not AWS's opaque URL-safe token.
AWS: Smithy StartQueryOutput$QueryId is a required String, documented as "the internally-generated identifier of a specific query", and it is carried as an @httpLabel in GetQueryStatus (/v20210603/Monitors/{MonitorName}/Queries/{QueryId}/Status) and GetQueryResults (.../{QueryId}/Results) — so it must be path-safe. The model pins no pattern, so the form is recorded behavior only: the recording shows AWS answering a long, unpadded URL-safe base64 token — at least 64 characters drawn only from [A-Za-z0-9_-], opaque and non-guessable, with no account- or sequence-derived structure.
Emulator: StartQuery answers QueryId '00000000-0000-4000-8000-000000000001' — a zero-padded, hyphenated, monotonically numbered UUID (characters outside the recorded alphabet, 36 characters, and trivially enumerable). The checks fail at the identifier assertion: "StartQuery answered QueryId '00000000-0000-4000-8000-000000000001', not an opaque URL-safe base64 token" and "the started query's QueryId '00000000-0000-4000-8000-000000000001' is not a long URL-safe base64 token". (Only the FORM is the requirement here, never the literal digits of one run.)
Why: a client that validates, stores in a fixed-width/charset column, or regex-matches the identifier it is handed rejects the emulator's value, and a client that guesses the next identifier succeeds against the emulator where AWS's opaque token makes that impossible — which is exactly what the cross-monitor scoping contract depends on. Because the two checks stop at this assertion, the contracts behind it reach no verdict and a fixer must re-replay them after minting a proper token: a QueryId is scoped to the monitor that ran it (GetQueryResults naming it under a second monitor of the same account must be refused ValidationException, 400, "Invalid query ID provided" — all fixed text — while the owning monitor keeps serving its results and the second monitor stays ACTIVE); a forged, never-issued NextToken must be refused ValidationException, 400, "Invalid next-token provided" — also all fixed text — with the untokened read answering the same Fields before and after; and a SUCCEEDED MEASUREMENTS query's Fields must include the recorded field names (timestamp, availability, rtt_p50, bytes_in).
Fix: the StartQuery handler's id minting and the crate's query state (the id generator the query store uses), so the identifier is an opaque, unpadded URL-safe base64 token of at least 64 characters that remains addressable as the {QueryId} path label in GetQueryStatus/GetQueryResults and still resolves in the query store.
Traces: internetmonitor.get-query-results-query-of-other-monitor-rejected, internetmonitor.get-query-results-unissued-next-token-rejected.

2. Run the behavioral suite; service internetmonitor reports 19/23 with the four checks named below failing.
3. Cause 1, by hand: CreateMonitor(MonitorName=<name>, TrafficPercentageToMonitor=100, MaxCityNetworksToMonitor=500); poll GetMonitor until Status=ACTIVE; call StartQuery(MonitorName=<name>, StartTime=<now-1h>, EndTime=<now>, QueryType=MEASUREMENTS, FilterParameters=[]). Then GetMonitor and confirm the monitor is still ACTIVE.

Inspect the returned QueryId: AWS returns a >=64-character unpadded URL-safe base64 token matching [A-Za-z0-9_-]{64,}; the emulator returns '00000000-0000-4000-8000-000000000001' (and the next call returns ...0002).
5. After fixing cause 2, re-replay internetmonitor.get-query-results-query-of-other-monitor-rejected and internetmonitor.get-query-results-unissued-next-token-rejected to reach the contracts blocked behind the id assertion: poll GetQueryStatus to SUCCEEDED, GetQueryResults on the owning monitor (Fields include timestamp, availability, rtt_p50, bytes_in), GetQueryResults for the same QueryId under a second monitor of the same account (expect 400 ValidationException "Invalid query ID provided"), and GetQueryResults with NextToken="eyJvZmZzZXQiOjUwMCwicXVlcnkiOiJub3QtaXNzdWVkIn0=" (expect 400 ValidationException "Invalid next-token provided").
