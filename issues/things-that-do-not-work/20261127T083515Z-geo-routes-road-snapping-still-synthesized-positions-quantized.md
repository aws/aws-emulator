# geo-routes road snapping still synthesized: positions quantized, confidence index-derived, snapped geometry not interpolated

> _Note: this issue was identified against the code base at commit `468af82aaa1d7b60e9b7f70a7d90101f16ac1d70`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CalculateRoutes

## Description
geo-routes answers CalculateRoutes and SnapToRoads with HTTP 200 and a structurally valid body on every affected step, so no status, error code or error message diverges; the divergence is entirely in the geographic values. The common fault is that neither operation resolves a submitted coordinate against a road network: the handlers quantize the request coordinate, add a fixed arithmetic offset to it, score the result with a value that depends on the point's INDEX rather than on any match, and encode the resulting vertices directly as the snapped geometry without interpolating along a road. This bundle carries THREE causes.

NOTE ON RELATED ISSUES: the issue 20261116T014451Z-geo-routes-synthesized-positions-are-the-request-coordinates.md describes this same defect class on exactly these operations, but it is RESOLVED/fixed, so it covers none of the failures below — the emulator's emitted values have visibly changed since that fix (Position is no longer byte-identical to OriginalPosition, snapped positions now carry a 6-decimal offset, and the confidence stream is different), yet all three clusters still diverge, so they are re-filed here. The OPEN issue 20261124T112417Z-geo-routes-calculateisolines-snappedorigin-is-not-the-road-snapped-position.md records the same class on CalculateIsolines.SnappedOrigin only and does not cover any cluster below (replay reports owned_by: [] for all three).

=== Cause 1 of 3: CalculateRoutes leg Arrival/Departure Place.OriginalPosition is re-quantized and Place.Position is a fixed offset from it, not a road-snapped point ===
AWS: Smithy com.amazonaws.georoutes#CalculateRoutes (POST /v2/routes, success 200; modeled errors ValidationException 400, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500 — none exercised, both sides answer 200). A vehicle leg's RouteVehicleLegDetails.Arrival/Departure.Place is RouteVehiclePlace. RouteVehiclePlace.OriginalPosition (target Position23, list of Double, @length 2..3, @sensitive) is documented 'Position provided in the request'; RouteVehiclePlace.Position (required, Position23) is documented 'Position in World Geodetic System (WGS 84) format: [longitude, latitude]' and is the point on the road network that the requested position was matched to (its siblings SideOfStreet and AccessPointDetails are only meaningful relative to such a matched point). Both members are lists of Double, so the model imposes no quantization: OriginalPosition must reproduce the submitted coordinate digit-for-digit, and Position must be an independently derived road-network point. The recording shows exactly that contract — OriginalPosition carries the submitted 7-decimal coordinates (-122.3410001 departure, -122.3088001 / 47.4501999 arrival) while Position is a distinct nearby snapped coordinate (-122.3409556 / 47.6089359 departure, -122.3029601 / 47.45124 arrival), displaced differently on each axis and at each end.
Emulator: OriginalPosition is the request coordinate quantized to 4 decimal places (-122.341, -122.3088, 47.4502), i.e. the echo loses the precision it was given. Position is then derived arithmetically from that quantized value by adding a constant offset to the longitude only (-122.340836 = -122.341 - 0.000836; -122.308836 = -122.3088 - 0.000836) while the latitude is left at the quantized input (47.4502, 47.6089). The arrival Position is therefore ~0.6 km from the recorded snap on longitude and off by 0.001 degrees on latitude, and the offset is identical at both ends of the leg, which no road match would produce. Hypothesis: the handler applies a fixed delta to a rounded input instead of resolving the point against a road graph; the model states only the members' semantics and the recording only shows the values, so the emulator's formula is recorded behavior only.
Why: a client that joins a returned leg back to its request waypoint by matching OriginalPosition against the coordinate it submitted never gets an exact match, so legs cannot be attributed to waypoints. A client that derives anything from the offset between Position and OriginalPosition — side-of-street selection, access-point or walk-to-road distance, map-pin correction — gets a constant east-west displacement with no latitude component regardless of where the point is, and a client that round-trips Position into a follow-up CalculateRoutes/CalculateIsolines call silently moves its waypoint off the road. The response is a 200 with a plausible Position of legal length, so the failure is silent.
Fix: the CalculateRoutes handler's place/position serialization in the geo-routes service crate (services/service-com-amazonaws-georoutes-routesservice) — echo OriginalPosition at the precision received (remove the rounding step on the response path) and populate Position from an actual road-match of the request position rather than from a constant offset.
Traces: geo-routes-calculate-routes-truck-travel-mode-options-wiring-success#task#1 (representative) and geo-routes-calculate-routes-zero-max-alternatives-returns-single-route#task#1 (same seven keys; affected_count 2).

=== Cause 2 of 3: SnapToRoads SnappedPosition is the quantized trace point, Confidence is index-derived, and SnappedGeometry.Polyline is the un-interpolated result ===
AWS: Smithy com.amazonaws.georoutes#SnapToRoads (POST /v2/snap-to-roads, success 200; same four modeled errors, none exercised). RoadSnapSnappedTracePoint.SnappedPosition (Position, required, @length 2..2) is 'Snapped position of the TracePoint provided within the request, at the same index'; .Confidence (SensitiveDouble, required, @range min 0 max 1) is 'Confidence value for the correctness of this point match' — so it is a property of the match of THAT point, and points matched with differing quality must score differently. RoadSnapSnappedGeometry is documented 'Interpolated geometry for the snapped route that is overlay-able onto a map', with Polyline (@length min 1, sensitive) 'An ordered list of positions used to plot a route on a map in a lossy compression format' — the encoded line is interpolated ALONG the matched roads, not merely the snapped points joined. The recording shows all of this: snapped positions at 5 decimals offset from the submitted points (-122.33662/47.61009, -122.33718/47.61071, -122.33678/47.61293, -122.33605/47.61324), graded confidences (1 for a point lying on the carriageway, 0.05 / 0.04 / 0.12 for points the matcher is unsure of), and a long polyline whose decoded vertex run follows the road. Hypothesis: AWS derives the confidence from the distance between the trace point and the segment it matched; the model states only the 0..1 range and the 'correctness of this match' meaning, so the exact function is recorded behavior only.
Emulator: SnappedPosition is the submitted trace point quantized and then offset by a constant per axis (-122.3366/47.610164 where the record has -122.33662/47.61009; -122.336336/47.6111 where the record has -122.33718/47.61071), i.e. still the raw input rather than a road point. Confidence is a full-width generated double that does not correspond to the point: 0.5234972736788034, 0.5625839607644028, 0.2617495495966861, 0.14239185930791512 against the recorded 1, 0.05, 0.04, 0.12 — it scores the point AWS scores 1 at ~0.52 and the point AWS scores 0.04 at ~0.26, so the RANKING of the points by match quality is wrong. The same index-0 value 0.5234972736788034 reappears for an unrelated request in Cause 3, confirming the score is a function of the index, not of the match. SnappedGeometry.Polyline is correspondingly short ('BGoz856Cv16qpHAwQofAobAgEAofAofAAgVAoKofAofAAwI', ~46 chars) against the recorded interpolated line (~78 chars), and begins at the wrong first vertex because the snapped positions themselves are wrong.
Why: Confidence is the only signal a caller has for discarding bad matches, so the standard client rule 'drop trace points scoring below a threshold' keeps the bad points and drops the good ones. The un-snapped positions mean a caller that re-renders or re-measures the track gets its own GPS noise back instead of road geometry — the entire purpose of the call — and a caller that draws or length-measures SnappedGeometry gets a straight-line zig-zag between samples, under-measuring the travelled distance by the road curvature that was never interpolated.
Fix: the SnapToRoads handler in the geo-routes service crate — match each trace point to a road segment and derive SnappedPosition and Confidence from that match, then build SnappedGeometry by interpolating along the matched segments between consecutive snapped points before encoding; the geometry builder must not simply encode the snapped point list.
Traces: geo-routes-snap-to-roads-basic-success#task#1 (13 diverging keys; affected_count 1).

=== Cause 3 of 3: the same SnapToRoads synthesis on the shorter two-point trace, where confidence repeats across requests ===
AWS: as Cause 2 — SnapToRoadsResponse.SnappedTracePoints[*].SnappedPosition must be the road-matched position of the trace point at the same index, .Confidence must be that match's own 0..1 score, and SnappedGeometry must be interpolated along the matched roads. The recording for this trace carries confidences 0.14 and 1 for its two points (the first point poorly matched, the second lying on the road) and snapped positions -122.34181/47.60998 and -122.34277/47.61098.
Emulator: answers 200 but returns Confidence 0.5234972736788034 for index 0 — the IDENTICAL value it returns for index 0 of the unrelated four-point trace in Cause 2 — and 0.9161272675671959 for index 1 against the recorded 1, inverting the two points' relative match quality. SnappedPosition is again the quantized-plus-offset input (-122.3421/47.610164 and -122.342836/47.611 against the recorded -122.34181/47.60998 and -122.34277/47.61098), and the polyline is the short un-interpolated encoding 'BGoz856CntlrpHA3OAnfofAgVA' against the recorded road-following line. This cluster is reported separately from Cause 2 because it is a distinct key set and a distinct fixture pair, and it is the evidence that the confidence is per-index rather than per-point.
Why: a caller that filters by confidence across requests sees a stable, request-independent score pattern, so confidence conveys no information at all; combined with un-snapped positions, a two-point trace comes back indistinguishable from its input.
Fix: same component as Cause 2 (the SnapToRoads snapping, confidence computation and geometry interpolation in the geo-routes service crate); the confidence must be computed from each point's own match distance, never from its position in the list.
Traces: geo-routes-snap-to-roads-invalid-coordinate-rejected#task#3 (representative) and geo-routes-snap-to-roads-snap-radius-out-of-range-rejected#task#2 (affected_count 2).

All coordinates, polylines and confidence numbers quoted above are the recordings' and the emulator's values, used as examples. The requirements are the rules: OriginalPosition echoes the request coordinate exactly; Position / SnappedPosition is a point derived from the road network; Confidence is that point's own match score in [0,1]; SnappedGeometry is interpolated along the matched roads.
