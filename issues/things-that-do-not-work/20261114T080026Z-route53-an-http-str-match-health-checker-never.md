Cause 1 of 1 — failing check route53.health-check-str-match-searchstring-governs-the-reported-health.

AWS: Smithy HealthCheckConfig$Type, HTTP_STR_MATCH — "Route 53 tries to establish a TCP connection. If successful, Route 53 submits an HTTP request and searches the first 5,120 bytes of the response body for the string that you specify in SearchString." Smithy GetHealthCheckStatus returns HealthCheckObservations, "one HealthCheckObservation element for each Amazon Route 53 health checker that is reporting a status about the health check endpoint", and StatusReport$Status is "a description of the status of the health check endpoint as reported by one of the Amazon Route 53 health checkers" (free text the model constrains in no way). HealthCheckObservation$IPAddress is "the IP address of the Amazon Route 53 health checker", and GetCheckerIpRanges publishes "a list of the IP ranges used by Amazon Route 53 health checkers to check the health of your resources" — that publication exists precisely so a customer can ADMIT the checkers and nobody else, which is the documented way to keep a monitored endpoint non-public. So a checker's request arrives FROM an address inside a block GetCheckerIpRanges publishes, and an endpoint whose access control admits exactly those blocks answers it normally. For a request answered 200 whose body carries SearchString, every checker reports a status whose fixed opening text is "Success: " (recorded behavior for an answered probe: "Success: HTTP Status Code 200, OK", where "Success: HTTP Status Code " is fixed text and the numeric status and reason phrase are values taken from the probed response). GetHealthCheckStatus answers HTTP 200 in every phase; no error code is involved — the divergence is the reported value.

Emulator: a checker's probe is made over the emulator's own in-process transport and is attributed NO source address at all. services/service-com-amazonaws-route53-awsdnsv20130401/src/state/endpoint_probe.rs module docs and fetch(): the request is built as a bare GET with only a Host header, "carries NO credential", "no socket is opened, no name is resolved". Nothing on that path sets, or lets a peer service read, an address inside the blocks this same service publishes from GetCheckerIpRanges (state.rs checker_address()/CHECKER_IP_RANGES are used ONLY to decorate the observation after the fact, never to address the probe). Consequently a monitored endpoint whose access is conditioned on the checker ranges refuses the probe: for the S3 static-website endpoint this check monitors, the bucket's only Allow is `s3:GetObject` with `Condition.IpAddress.aws:SourceIp` = the GetCheckerIpRanges blocks, and S3's bucket-policy gate does not answer `aws:SourceIp` at all — it is absent from services/service-com-amazonaws-s3-amazons3/src/service/authorization.rs PUBLISHED_CONDITION_KEYS, so a grant conditioned on it is UNDECIDED and grants nothing. The website endpoint then answers the anonymous read 403 AccessDenied (services/service-com-amazonaws-s3-amazons3/src/service/website_endpoint.rs resolve() -> Resolved::Failed{403, AccessDenied}), the probe assesses that answer as a failure, and endpoint_probe::http_status_description stamps every checker's StatusReport.Status as "Failure: HTTP Status Code 403, Forbidden". No SearchString, no body and no RequestInterval can turn that into a "Success: "-prefixed report, so the FIRST phase of the three-phase flip — every checker reporting Success while the body contains the marker — is unreachable, and the replayed check sat in that poll (its own budget is 240 s) until the harness cut it off at 60 s. Hypothesis (the report's detail carries no traceback frame, so the exact poll it died in is not stated): it is that first Success poll; the code above makes it unsatisfiable in any case, and the later Failure/Success phases are equally unreachable because they are defined relative to it.

Why: a client relying on AWS's behavior believes a Route 53 health check can monitor an endpoint that is NOT open to the world — the published checker ranges are the documented mechanism for exactly that, and it is the configuration AWS's own static-website + health-check guidance produces. Against this emulator such an endpoint is permanently reported unhealthy from every checker, so DNS failover driven by it never has a healthy state to fail back to, GetHealthCheckLastFailureReason reports a 403 that AWS would never produce, and the AWS/Route53 HealthCheckStatus series an alarm is built on sits at 0 forever. Worse, the failure is silent and inverted: a target that correctly serves the SearchString is graded unhealthy, so the one fact the health check exists to report is wrong in the safe-looking direction for a deployment gate (never promote) and in the unsafe direction for an inverted check.

Fix: the route53 health-checker probe plane — endpoint_probe::probe/fetch and the ProbeTarget it builds — must attribute each probe the checker identity the service already publishes, so the request a peer service of this emulator sees carries a source address inside the block checker_address()/checker_ip_ranges() assign to the checker Region the observation is reported under (one probe per reporting checker, or one probe attributed to a published checker address), rather than an unattributed in-process request. The cooperating half is in the S3 bucket-policy gate, which must answer `aws:SourceIp` from that attributed address (services/service-com-amazonaws-s3-amazons3/src/service/authorization.rs PUBLISHED_CONDITION_KEYS and the anonymous-read refusal the website endpoint calls) instead of leaving every IpAddress-conditioned grant undecided; without it an IP-gated endpoint stays unreadable however the probe is addressed. Nothing in the GetHealthCheckStatus serializer needs changing — it faithfully reports the probe it is given.

## Evidence
Failing check: route53.health-check-str-match-searchstring-governs-the-reported-health — verdict mismatch, detail "Check timed out after 60.0s". The check's own per-phase poll budget is 240 s, so the harness limit is what ended it, not the check's own wait.

What the check does: creates an S3 bucket, tags it, reads GetCheckerIpRanges and puts a bucket policy whose single statement is {Effect: Allow, Principal: "*", Action: "s3:GetObject", Resource: "arn:aws:s3:::<bucket>/*", Condition: {IpAddress: {"aws:SourceIp": <the CheckerIpRanges just read>}}}, puts a website configuration with IndexDocument.Suffix=index.html, puts index.html with a body containing a marker string, then creates a health check with HealthCheckConfig {Type: HTTP_STR_MATCH, FullyQualifiedDomainName: <bucket>.s3-website-<region>.amazonaws.com, Port: 80, ResourcePath: "/", SearchString: <the marker>, RequestInterval: 10, FailureThreshold: 1, MeasureLatency: false, Inverted: false} and polls GetHealthCheckStatus.

Expected (AWS):
  Phase 1 (body contains SearchString) — every HealthCheckObservations[].StatusReport.Status begins with the fixed text "Success: " (recorded form "Success: HTTP Status Code 200, OK"; the status number and reason phrase are values from the probed response), observations come from at least three Regions, and every HealthCheckObservation.IPAddress lies inside a block GetCheckerIpRanges publishes.
  Phase 2 (only the object body is rewritten so it no longer contains SearchString; the health check is not touched) — within a few RequestIntervals every checker reports a status beginning with the fixed text "Failure: " whose remainder names STRING MATCHING as the reason, while GetHealthCheck still reports the same SearchString, Inverted=false and the unchanged HealthCheckVersion.
  Phase 3 (the marker is restored in the body) — every checker returns to a "Success: "-prefixed status, again with HealthCheckVersion unchanged.

Actual (emulator): no checker ever reports a "Success: "-prefixed status for this endpoint, so Phase 1 never completes and Phases 2 and 3 are never reached; the check is cut off at the harness's 60 s limit. The probe is refused before the body is ever searched: it is an unattributed in-process request, the bucket's only grant is conditioned on aws:SourceIp, and that condition key is not answered, so the website endpoint answers 403 AccessDenied and every checker's StatusReport.Status is "Failure: HTTP Status Code 403, Forbidden" — the fixed text "Failure: HTTP Status Code " with the status and reason phrase taken from the refused answer. AWS produces no 403 here at all, because its checkers come from the addresses the policy admits.

Controls that hold, isolating the divergence to how the probe is addressed: the website endpoint itself IS served (services/service-com-amazonaws-s3-amazons3/src/service.rs can_handle/override_operation route a <bucket>.s3-website-<region> host to website_endpoint::WEBSITE_ENDPOINT, and website_endpoint.rs implements the index-document rule), the probe plane really does search a body for SearchString case-sensitively within the first 5,120 bytes (endpoint_probe.rs holds_search_string/MAX_SEARCHED_BODY_BYTES and its unit tests), and GetHealthCheckStatus reports one observation per checker Region with an address inside a published block. What is missing is the checker's ADDRESS on the request, and the condition key that would read it.

## Steps to Reproduce
1. s3 CreateBucket <bucket> (with CreateBucketConfiguration.LocationConstraint=<region> outside us-east-1).
2. route53 GetCheckerIpRanges -> CheckerIpRanges.
3. s3 PutBucketPolicy on <bucket> with the single statement {"Effect":"Allow","Principal":"*","Action":"s3:GetObject","Resource":"arn:aws:s3:::<bucket>/*","Condition":{"IpAddress":{"aws:SourceIp": <the CheckerIpRanges from step 2>}}} — i.e. the endpoint is readable by the published Route 53 health checkers and by nobody else.
4. s3 PutBucketWebsite on <bucket> with WebsiteConfiguration.IndexDocument.Suffix=index.html, then PutObject Key=index.html with a body containing the marker string MARKER.
5. route53 CreateHealthCheck with HealthCheckConfig {Type: HTTP_STR_MATCH, FullyQualifiedDomainName: "<bucket>.s3-website-<region>.amazonaws.com", Port: 80, ResourcePath: "/", SearchString: "MARKER", RequestInterval: 10, FailureThreshold: 1, Inverted: false}. Note the Id.
6. Poll route53 GetHealthCheckStatus(HealthCheckId=<id>). AWS: within a few RequestIntervals every HealthCheckObservations[].StatusReport.Status is "Success: "-prefixed ("Success: HTTP Status Code 200, OK"), from at least three Regions, each IPAddress inside a block step 2 published. Emulator: every checker reports "Failure: HTTP Status Code 403, Forbidden" and never a "Success: "-prefixed status, so the poll never terminates.
7. Confirm the refusal is the probe's and not the endpoint's: s3 GetObject(Bucket=<bucket>, Key=index.html) as the bucket owner returns the body containing MARKER, so the endpoint really does serve the SearchString.
8. route53 GetHealthCheckLastFailureReason(HealthCheckId=<id>): the emulator reports the 403 observation, a failure class AWS does not produce for an endpoint that admits its checkers.
9. Rewrite index.html so it no longer contains MARKER, then restore it. Neither rewrite changes any reported status, so the SearchString-governs-health behaviour the check exists to observe is not observable at all.
10. Negative control: drop the bucket policy's Condition (an unconditional public Allow) and repeat step 6 — the probe is then answered 200 and the reports become "Success: "-prefixed, which pins the divergence to the checker's missing source address rather than to the probe or the string match.
