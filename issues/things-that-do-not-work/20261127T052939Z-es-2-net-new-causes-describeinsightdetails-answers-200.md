# es: 2 net-new causes — DescribeInsightDetails answers 200 for an insight address AWS refuses, and DescribeDomainChangeProgress mis-renders PendingProperties

> _Note: this issue was identified against the code base at commit `e5bd3f449037d977df62b379b9bbd75575215842`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInsightDetails

## Description
Two root causes, both on the es (OpenSearch Service) domain read surface: a read that AWS refuses as a missing resource is answered successfully, and a read that AWS answers with stringified-JSON property entries is answered with bare values in a different order. Both are net-new: the replay reports each cluster unowned (owned_by empty) and unblocked (stub_path empty).

Cause 1 of 2: DescribeInsightDetails answers HTTP 200 with the console-guidance field for an insight address that names no insight, where AWS refuses the read as a missing resource.
AWS: Smithy com.amazonaws.opensearch#DescribeInsightDetails — http POST /2021-01-01/opensearch/insight-details, success code 200; input Entity -> InsightEntity @required, InsightId -> GUID @required (@length 36..36, @pattern ^\p{XDigit}{8}-\p{XDigit}{4}-\p{XDigit}{4}-\p{XDigit}{4}-\p{XDigit}{12}$), ShowHtmlContent -> Boolean; output Fields -> InsightFieldList @required; modeled errors BaseException(client, 400, defaulted), DisabledOperationException(client, 409), LimitExceededException(client, 409), ResourceNotFoundException(client, 409), ValidationException(client, 400), InternalException(server, 500). What AWS does for an insight address it holds no insight for is recorded behavior only, and the recording is unambiguous: HTTP 404 with header x-amzn-errortype: ResourceNotFoundException and body member message = "Resource not found". That message is entirely fixed text — it carries no part of the request, no insight id and no entity — so the requirement is the sentence exactly as written, with no variable part to fill in. Note the wire status: the recorded refusal arrives on 404 even though ResourceNotFoundException carries @httpError 409 in the model, so for THIS refusal the recorded 404 is the requirement and the modeled 409 is not what the service puts on the wire.
Emulator: answers HTTP 200 with no error at all. The replay reports 'status: expected 404, got 200', '$.message: missing (expected \'Resource not found\', got None)' and '$headers.x-amzn-errortype: missing (expected \'ResourceNotFoundException\', got None)'. The handler resolves only the ENTITY half of the address and treats the ID half as purely selective: every id inside the GUID form that the entity holds no insight under falls through to the fixed console-guidance field, so no insight address can ever be reported as missing. The two refusal paths it does keep are also mis-statused for this operation: the entity refusal is raised as the modeled ResourceNotFoundException, which serializes on 409, not the recorded 404.
Why: a client reading an insight that does not exist (or was deleted, or whose id was mistyped inside the GUID form) is told the read succeeded and handed a payload that looks like a real detail view carrying a single 'Message' text field. Nothing distinguishes 'this insight has no detail fields' from 'this insight does not exist', so error handling never runs, a console-equivalent or scripted flow renders guidance for an insight it should have reported as gone, and a caller cannot detect a stale insight id. Because the refusal also never reaches the wire as 404 with x-amzn-errortype: ResourceNotFoundException, an SDK cannot classify it as the modeled ResourceNotFoundException either.
Fix: the DescribeInsightDetails handler in the opensearch service crate — the address-resolution branch and the guidance fallback. An insight address the service holds no insight under must be refused as the missing resource with the recorded wire status 404, the x-amzn-errortype: ResourceNotFoundException header and the fixed message text, while a well-formed address that DOES resolve to a raised insight with no detail fields of its own keeps answering 200 with the guidance field; a malformed InsightId (right length, not 8-4-4-4-12 hex) keeps being refused ValidationException on 400. The refusal serialization for this operation must put the not-found refusal on 404 as recorded, not on the modeled 409.
Related open issue (does NOT cover this cluster — it is the opposite direction, a recorded address AWS answers 200 that the emulator refused): 20261126T155222Z-es-describeinsightdetails-refuses-a-recorded-insight-address-with.md. That issue's fixture (opensearch-domain-insights-operations#task#3) now passes in this replay, so the guidance fallback is in place and it is the not-found refusal that has gone missing; the fix must satisfy both recordings, not trade one for the other.

Cause 2 of 2: DescribeDomainChangeProgress renders a change's PendingProperties entries as bare values (and an unset member as empty text) in an enumeration order that diverges from AWS, instead of as the single-member stringified-JSON document AWS reports.
AWS: Smithy com.amazonaws.opensearch#DescribeDomainChangeProgress — http GET /2021-01-01/opensearch/domain/{DomainName}/progress, success code 200; input DomainName -> DomainName @required @httpLabel (@length 3..28, @pattern ^[a-z][a-z0-9\-]+$), ChangeId -> GUID @httpQuery changeid; output ChangeProgressStatus -> ChangeProgressStatusDetails; modeled errors BaseException(400, defaulted), ResourceNotFoundException(409), ValidationException(400), InternalException(500). How each PendingProperties entry is TEXTUALLY composed is recorded behavior only, and the recording shows one rule applied uniformly: an entry is '<PropertyPath> : <value>' where the value of a leaf property of an option block is a compact single-member JSON object keyed by the LEAF member's own name — 'ClusterConfig.InstanceCount : {"InstanceCount":1}', 'ClusterConfig.InstanceType : {"InstanceType":"t3.small.search"}', 'ClusterConfig.MultiAZWithStandbyEnabled : {"MultiAZWithStandbyEnabled":false}', 'ClusterConfig.ZoneAwarenessEnabled : {"ZoneAwarenessEnabled":false}' — and a leaf the domain holds no value for is reported as the empty JSON object '{}', not as empty text: 'ClusterConfig.DedicatedMasterCount : {}', 'ClusterConfig.DedicatedMasterType : {}', 'ClusterConfig.WarmCount : {}', 'ClusterConfig.WarmStorage : {}', 'ClusterConfig.WarmType : {}'. In each of those the fixed text is the property path, the ' : ' separator and the JSON object's key (the leaf member name); the only value taken from state is the member's stored value inside the object. The recording also fixes the enumeration: a non-block property follows the cluster block's leaves — index 22 of the recorded list is 'EngineVersion : OpenSearch_2.11' — so the change's property order and membership past the cluster leaves is part of what the read answers.
Emulator: answers HTTP 200 whose ChangeProgressStatus.PendingProperties entries diverge from index 11 through index 31. It renders each leaf as the bare value — 'ClusterConfig.InstanceCount : 1', 'ClusterConfig.InstanceType : t3.small.search', 'ClusterConfig.DedicatedMasterEnabled : false', 'ClusterConfig.MultiAZWithStandbyEnabled : false', 'ClusterConfig.WarmEnabled : false', 'ClusterConfig.ZoneAwarenessEnabled : false' — never wrapping it in the single-member object keyed by the leaf name, and renders an unset leaf as the empty string ('ClusterConfig.DedicatedMasterCount : ', 'ClusterConfig.DedicatedMasterType : ', 'ClusterConfig.WarmCount : ', 'ClusterConfig.WarmStorage : ', 'ClusterConfig.WarmType : ') rather than '{}'. The order diverges as well: where the recording has 'EngineVersion : OpenSearch_2.11' at index 22 the emulator emits a 'TAGS : ' entry, and every index from there to 31 is shifted onto a different property.
Why: PendingProperties is the only machine-readable statement of what a configuration change is applying, and clients parse it — split on ' : ', then JSON-parse the right-hand side, which the sibling PropertyValueType STRINGIFIED_JSON classification invites. Against the emulator that parse fails or silently yields a plain string for every leaf property, an unset leaf is indistinguishable from a leaf set to the empty string, and a caller that indexes the list (or diffs two reads) reads a different property than AWS would hand it at the same index. A deployment-progress UI or a wait-for-change loop built on AWS's entries therefore misreports which properties are in flight.
Fix: the change-progress property rendering in the opensearch service crate's domain-configuration service module — the value-text helper that composes a property entry's right-hand side, and the change's own property enumeration used for PendingProperties/CompletedProperties. The value text for a leaf property of an option block must be the compact single-member JSON object keyed by that leaf member's name, with '{}' for a leaf the domain holds no value for, and the enumeration (order and membership) must match the recorded change property list past the cluster leaves. The same rule governs CompletedProperties, which is built from the same helper.
