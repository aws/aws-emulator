# rds-data: 3 net-new causes — the Data API data plane rejects pg_sleep(), left() and DEFERRABLE constraints, so statement timeouts, the 1 MB result limit and deferred-constraint commits are all unreachable

> _Note: this issue was identified against the code base at commit `ff49842cf7656b5a010943ef9d0fd100550d134a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
The Data API's data plane is an in-process SQLite database per (cluster, database) (documented in services/service-com-amazonaws-rdsdata-rdsdataservice/src/ops/execute_statement.rs, which names crate::state as the owner of that plane), and it is exposed as an Aurora PostgreSQL engine: every cluster below is created with Engine='aurora-postgresql'. SQL that any PostgreSQL engine accepts is therefore refused with the engine's own fault, and whole AWS behaviours that can only be reached THROUGH that SQL — the synchronous statement timeout, the 1 MB result-set limit, and a commit that fails on a deferred unique constraint — are unreachable. Three net-new causes, all in rds-data, all in the data plane's SQL surface.

Cause 1 of 3: the PostgreSQL function pg_sleep() does not exist, so no statement can outrun the call limit and StatementTimeoutException is never produced.
AWS: Smithy: ExecuteStatement and BatchExecuteStatement both model StatementTimeoutException (errorKind client, httpError 400, doc 'The execution of the SQL statement timed out.', with a dbConnectionId member). On Aurora PostgreSQL, 'SELECT pg_sleep(<seconds>)' is a valid statement; a statement that runs past the Data API's documented 45 s synchronous call limit is refused with HTTP 400 StatementTimeoutException whose message is the engine's cancellation text 'canceling statement due to statement timeout' (fixed text, no variable part), nothing of a cancelled batch is committed, and no backend is left running the statement. With continueAfterTimeout=true the DDL the statement was performing survives past that refusal.
Emulator: every statement containing pg_sleep() is refused up front with HTTP 400 DatabaseErrorException 'ERROR: function pg_sleep() does not exist; SQLState: 42883' — both for a batch parameter set that sleeps and for a single long statement — so the timeout path is never entered and the modelled StatementTimeoutException is never observable.
Why: a client that handles StatementTimeoutException (retry with continueAfterTimeout, or report the cancelled statement) sees a DatabaseErrorException naming a missing function instead, i.e. a permanent client fault where AWS raises a transient, retryable timeout. Any test of long-running statements, of continueAfterTimeout, or of the atomicity of a cancelled batch cannot run at all.
Fix: the data plane's SQL function surface in crate::state (register pg_sleep, honouring the sleep so the statement really outruns the call budget) and the statement-budget path that must answer StatementTimeoutException instead of the engine's fault.
Traces: rds-data.batch-execute-statement-past-call-timeout-rejected-and-batch-not-applied, rds-data.continue-after-timeout-preserves-ddl-past-the-call-timeout.

Cause 2 of 3: the PostgreSQL function left() does not exist, so results cannot be sized and the 1 MB result limit is never reached.
AWS: Smithy: ExecuteStatement models UnsupportedResultException (errorKind client, httpError 400, doc listing 'The size was too large.' among its conditions) and the operation's own doc says 'If the binary response data from the database is more than 1 MB, the call is terminated.' On Aurora PostgreSQL 'SELECT left(body, n)' and 'md5(...)' are valid; a result over the limit is refused with HTTP 400 UnsupportedResultException and the message 'The result exceeds the size limit 1 MB.' (fixed text), while a result under the limit returns whole and the stored row is unchanged.
Emulator: 'SELECT length(body), md5(left(body, 1000000)) FROM payload WHERE id = 1' is refused with HTTP 400 DatabaseErrorException 'ERROR: function left() does not exist; SQLState: 42883', so neither the inside-the-limit read nor the over-the-limit refusal can be exercised.
Why: a client cannot size or slice text through the Data API, and the whole result-size limit — the behaviour that forces clients to paginate — is unobservable; a client that works against the emulator can ship a query AWS terminates.
Fix: the same SQL function surface in crate::state (left(), and the standard PostgreSQL string/hash builtins alongside it), plus the result-set size accounting that must answer UnsupportedResultException 'The result exceeds the size limit 1 MB.' once a serialized result exceeds 1 MB.
Traces: rds-data.execute-statement-one-mib-text-result-rejected-while-smaller-result-returns-whole.

Cause 3 of 3: a UNIQUE constraint declared DEFERRABLE INITIALLY DEFERRED is a syntax error, so no deferred constraint can be violated at COMMIT.
AWS: recorded behavior only for the DDL itself (the Smithy model does not describe SQL dialect): Aurora PostgreSQL accepts 'CONSTRAINT <name> UNIQUE (<col>) DEFERRABLE INITIALLY DEFERRED' in CREATE TABLE, defers the check to COMMIT, and CommitTransaction then fails with HTTP 400 DatabaseErrorException whose message is the engine's text 'ERROR: duplicate key value violates unique constraint "<constraint name>"; SQLState: 23505' — fixed text 'ERROR: duplicate key value violates unique constraint ' plus the constraint name from the DDL, then '; SQLState: 23505' — and nothing of the transaction persists.
Emulator: the CREATE TABLE itself is refused with HTTP 400 DatabaseErrorException 'near "DEFERRABLE": syntax error in CREATE TABLE "<table>" (...) at offset <n>' — the underlying SQLite parser's message shape, which is not a PostgreSQL message either — so the deferred-violation-at-commit behaviour cannot be reached.
Why: a client that models invariants with deferred constraints (the standard way to allow transient duplicates inside a transaction) cannot create its schema at all, and the commit-time failure class it depends on is untestable. The message shape also leaks the emulator's engine, so a client matching on PostgreSQL SQLSTATE/message text misbehaves.
Fix: the DDL/statement translation layer of the data plane in crate::state — accept PostgreSQL table constraint syntax including DEFERRABLE / INITIALLY DEFERRED, defer those checks to the transaction's commit, and report a violation at COMMIT as DatabaseErrorException with the PostgreSQL duplicate-key message and SQLState 23505.
Traces: rds-data.commit-transaction-deferred-unique-violation-rejected-and-nothing-persists.
