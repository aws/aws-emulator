# appsync__cognito-idp__dynamodb: VTL mapping-template resolvers are never executed, Cognito user-pool token validation is missing on the data plane, and no realtime subscription ever completes (3 causes)

> _Note: this issue was identified against the code base at commit `36cbc41e18f8f7f03eaee998bf950ce282c69b6c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PostGraphQL (AppSync GraphQL data plane) / CreateResolver

## Description
Three net-new root causes on the AppSync GraphQL data plane of this suite. All three must be closed before submitting. Cause 2 is security-relevant (forged and foreign-pool tokens are served), so the bundle is HIGH.

Cause 1 of 3: a UNIT or PIPELINE resolver defined by VTL request/response mapping templates is never run — the field resolves to null and the response carries an emulator-authored error demanding APPSYNC_JS code.
AWS: mapping templates are a fully modeled, supported way to define a resolver — Smithy: Resolver$requestMappingTemplate and Resolver$responseMappingTemplate target MappingTemplate (@length min 1, max 65536, @pattern "^.*$"), while Resolver$code is documented as the alternative ("The resolver code that contains the request and response functions. When code is used, the runtime is required. The runtime value must be APPSYNC_JS") — APPSYNC_JS is one option, never a precondition for running a resolver. For Resolver$kind UNIT ("run a GraphQL query against a single data source") over an AMAZON_DYNAMODB data source, AWS evaluates the VTL request template (the "version": "2018-05-29" PutItem/GetItem/DeleteItem/UpdateItem/Query/BatchPutItem operations and the $util.dynamodb.* helpers), performs the DynamoDB call under the data source's serviceRoleArn, and renders the result through the response template. A successful field is HTTP 200 with data.<field> populated and NO `errors` member; a data-source failure (role without permission, nonexistent table) is HTTP 200 with data.<field> null and an `errors` entry whose errorType/message come from the DynamoDB failure (an access-denied class for a role lacking the action).
Emulator: every such field answers HTTP 200 with data.<field> null and errors: [{"path": ["<field>"], "message": "This field's resolver is defined by mapping templates, which this endpoint does not run; define it with APPSYNC_JS code."}] (for a pipeline function the message is prefixed with the function name and a colon). The whole sentence is fixed emulator-authored text — the only variable parts are the `path` (the field being resolved) and that function-name prefix; AWS has no such error. CreateResolver accepts the templates, so the divergence is purely in execution: no item is ever written, read, updated or deleted, so neither the positive legs nor the negative legs (missing role permission, ghost table ARN) can be observed.
Why: a client using the documented VTL resolver style gets a 200 whose payload says the field could not be resolved and whose side effect never happened, and a client asserting an access-denied rejection sees this message instead of the AccessDenied/not-authorized error AWS returns — so both success and refusal paths of the whole DynamoDB-backed API are wrong.
Fix: the GraphQL data-plane resolver-execution path needs a VTL mapping-template engine alongside the APPSYNC_JS runtime: evaluate requestMappingTemplate with the $util/$ctx bindings (including $ctx.identity for a Cognito caller), dispatch the rendered operation to the resolver's data source under its serviceRoleArn (including the IAM evaluation that produces the access-denied error), then render responseMappingTemplate into data/errors.

Cause 2 of 3: an AMAZON_COGNITO_USER_POOLS GraphQL API performs no validation of the presented ID token — a token whose signature was tampered with, and a valid token minted by a DIFFERENT user pool, are both admitted to resolver execution instead of being refused.
AWS: recorded behavior (the data-plane authorization contract is not in the control-plane Smithy model): a request to a user-pool-authorized API whose Authorization token fails signature verification, or whose iss/aud do not match the API's configured userPoolConfig, is refused with HTTP 401 and an UnauthorizedException GraphQL error; the field is never resolved. Only a token signed by the configured pool's JWKS and issued to the configured app client reaches a resolver.
Emulator: both requests are answered HTTP 200 and proceed into resolver execution — the body is {'data': {'putItem': None}, 'errors': [{'path': ['putItem'], 'message': "This field's resolver is defined by mapping templates, which this endpoint does not run; define it with APPSYNC_JS code."}]}, i.e. the request got past authorization (Cause 1 is why it then fails). No 401 and no UnauthorizedException is ever produced for an unverifiable or foreign-pool token.
Why: the API's authorization mode is inert, so any bearer string shaped like a JWT is as good as a real one — a client (or a test asserting that a forged/foreign token is rejected) sees success against the emulator and 401 against AWS, and an API that must be closed to other pools' users is open to them.
Fix: the data plane's AMAZON_COGNITO_USER_POOLS authorizer must verify the token's signature against the configured user pool's JWKS and check issuer/audience against the API's userPoolConfig before any resolver runs, returning 401 with the UnauthorizedException error body when it fails.

Fix: the realtime endpoint's WebSocket connect/subscribe path and the mutation-to-subscription publish fan-out (including the Cognito-group and filter gating), together with Cause 1's resolver execution that each of these checks drives first.
