# directconnect: DescribeLocations publishes a wrong us-west-2 location catalog past the three recorded rows

> _Note: this issue was identified against the code base at commit `63c382ed122999b7d1a982f7eb7d539bb2d07203`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
ONE net-new root cause of service `directconnect`, grounded in the single divergence cluster the wire replay reports for it (fixture `directconnect-catalog-describe-locations`, step `task#1`, cluster key `service=directconnect|DescribeLocations|status=200->200|keys=$.locations[3],$.locations[4],$.locations[5],$.locations[6],$.locations[7],$.locations[8],$.locations[9]`). The cluster carries no `stub_path` and no `owned_by`, and no open `directconnect` issue covers it: the three open issues naming directconnect are about CloudFormation resource types (20261109T120136Z-cloudformation-directconnect-ec2-..., 20261121T140427Z-cloudformation-directconnect-the-property-validation-reason-for-an.md) and Service Quotas' default-quota catalog (20261111T131231Z-service-quotas-listawsdefaultservicequotas-...), none of which touches DescribeLocations' location catalog.

=== Cause 1 of 1: the us-west-2 Location rows after the third are a different set of locations than AWS publishes, and the us-west-2 flat-rate ladder's tier membership and per-mode port speeds do not match ===

AWS: recorded behavior only for the catalog CONTENT — the Smithy model fixes only the envelope, not which locations exist. Smithy: `DescribeLocations` input `smithy.api#Unit` (no members), output `Locations` with a single member `locations` targeting the list `LocationList` of `Location`, whose members are `locationCode`, `locationName`, `region`, `availablePortSpeeds`, `availableProviders`, `availableMacSecPortSpeeds` and `availableBillingModes`; modeled errors `DirectConnectClientException` (HTTP 400) and `DirectConnectServerException` (HTTP 500). The operation is documented as "Lists the Direct Connect locations in the current Amazon Web Services Region. These are the locations that can be selected when calling CreateConnection or CreateInterconnect", so the list is public catalog data selected by the signed Region and is identical for every caller — it is NOT a per-run, per-account or generated value, and therefore IS a requirement. The recording for the signed `us-west-2` request returns the locations in AWS's published order; its first three elements are the ones the emulator already seeds (the Seattle carrier hotel's two demarcations and the Las Vegas building), and from the FOURTH element on it publishes locations the emulator does not have at all. Element index 3 of the recording is `locationCode` `ECPO1`, `locationName` `EdgeConnex, Hillsboro, OR`, `region` `us-west-2`, `availablePortSpeeds` `[100G, 1G, 10G]`, `availableMacSecPortSpeeds` `[100G, 10G]`, `availableProviders` `[Datapath.io GmbH, Megaport, Zayo Group, CenturyLink, EdgeConneX, Comcast, Cox Business, XO Communications, Arelion]` (a roster naming the delivery partners `Datapath.io GmbH` and `EdgeConneX`, which appear on no row the emulator seeds), and `availableBillingModes` `[{PayAsYouGo, availablePortSpeeds [100G, 1G, 10G]}, {FlatRateTier1, [10G, 100G], includedRegions [us-west-2]}, {FlatRateTier2, [10G, 100G], includedRegions [us-east-2, eu-west-1, us-east-1, eu-west-2, us-west-1]}, {FlatRateTier3, [10G, 100G], includedRegions [eu-north-1, eu-west-3, eu-central-1, sa-east-1, ap-northeast-3, eu-south-1, ap-northeast-1, ca-central-1, ca-west-1, eu-south-2, eu-central-2]}, {FlatRateTier4, [10G, 100G], includedRegions [ap-south-1, af-south-1, ap-east-1, ap-northeast-2, ap-southeast-4, mx-central-1, ap-southeast-1, ap-southeast-2, il-central-1]}, {FlatRateTier5, [10G, 100G], includedRegions [ap-southeast-6, me-south-1, ap-southeast-7, ap-southeast-3, me-central-1, ap-south-2, ap-southeast-5, ap-east-2]}]`. Two general facts follow from that element and hold for the class: (a) a flat-rate billing mode is published with `availablePortSpeeds` restricted to the 10G/100G ports it is offered on, NOT with the location's whole port-speed set, which only `PayAsYouGo` carries; and (b) the `us-west-2` flat-rate ladder's bands are those listed above — tier 1 covers the location's OWN Region `us-west-2`, tier 2 carries `eu-west-2` and `us-west-1`, tier 3 carries `ap-northeast-1` but neither `eu-west-2` nor `ap-southeast-1`, tier 4 carries `ap-southeast-1` but not `ap-south-2`, and tier 5 carries `ap-south-2`.
Emulator: answers HTTP 200 with a well-formed `locations` list whose first three `us-west-2` elements match, then diverges on every remaining element — the replay reports a mismatch on `$.locations[3]` through `$.locations[9]`, seven of the ten elements. Where AWS publishes `ECPO1` / `EdgeConnex, Hillsboro, OR` at index 3, the emulator publishes `EqSe3-EQ` / `Equinix SE3, Seattle, WA | Equinix, SE3, Seattle, WA`, and the whole tail of the list is shifted onto a different roster of locations (`EqSe3-EQ`, `EqSe3-CL`, `FlexHB1`, `Pittock-PB`, `Pittock-OPX`, `T5PDX`, `TierPointSEA`). Its `us-west-2` flat-rate ladder also disagrees with the recording's bands: tier 1 is seeded as `[us-west-1]` instead of `[us-west-2]`, tier 2 as `[us-east-2, eu-west-1, us-east-1, us-west-2]` (missing `eu-west-2` and `us-west-1`), tier 3 additionally carries `eu-west-2` and `ap-southeast-1`, tier 4 carries `ap-south-2` and omits `ap-southeast-1`, and tier 5 omits `ap-south-2`. The status, the error-free envelope and the per-element field set are correct; only the catalog data is wrong.
Why: `DescribeLocations` is the operation a client calls to discover which `locationCode` values `CreateConnection` and `CreateInterconnect` accept, so a client that enumerates it against the emulator is handed location codes AWS does not publish and is denied the ones it does — a provisioning flow that picks `ECPO1` (or any real location past the third) finds it absent, while a flow that picks a code the emulator invents cannot be ported to AWS. Because the flat-rate tiers are wrong too, a client that reads `availableBillingModes` to decide which billing mode covers a target Region draws the wrong conclusion for `us-west-2`, `us-west-1`, `eu-west-2`, `ap-southeast-1` and `ap-south-2`, and a client that reads a flat-rate mode's `availablePortSpeeds` is told a 1G port is eligible for flat-rate billing when AWS offers flat rate only on 10G/100G.
Fix: this service's seeded location catalog and its rendering — the `BUILT_IN_LOCATIONS` table and the `us-west-2` flat-rate tier constants that feed `built_in_location_catalog()`, plus the per-mode port-speed rendering reached from `location_output`. The `DescribeLocations` handler itself is correct: it is a pure read of the catalog for the signed Region, in the catalog's published order, so nothing in the handler or the serializer needs to change. The rows past the third `us-west-2` row are self-described in the source as CATALOGUED rather than recorded, which is exactly the data this recording now pins down.
Traces: directconnect-catalog-describe-locations#task#1.
