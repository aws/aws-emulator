# iot: 7 net-new causes — ListCommandExecutions' three ValidationException messages are emulator-authored, ListThings' maxResults @range message drops the rejected value, UpdateAuthorizer replaces tokenSigningPublicKeys instead of merging, UpdateThingShadow enforces no nesting limit, and a late command-execution report is refused as a job-execution state error

## Operation
ListCommandExecutions

## Description
Seven independent net-new root causes in service iot, all found by the behavioral suite under the `iot` service heading. Each cause must be closed before submitting. None is named by any open issue (checked: the iot open issues on fleet metrics, CA certificates, authorizer timestamps, V2 logging, GetV2LoggingOptions wording, and the data-plane/MQTT issues).

Cause 1 of 7: ListCommandExecutions refuses a listing scoped to BOTH commandArn and targetArn with the right class but emulator-authored text.
AWS: Smithy ListCommandExecutions (POST /command-executions) takes both `targetArn` (TargetArn, @length 0..2048) and `commandArn` (CommandArn) as optional input members and models ValidationException (httpError 400). The model does not state the mutual exclusion, so the wording is recorded behavior only: a request carrying both is refused 400 ValidationException with the message "Both 'targetArn' and 'commandArn' parameter values were provided. Only one valid parameter value is accepted." That sentence is entirely FIXED text — the only variable parts are the two member names, which are the two members the request supplied together ('targetArn' and 'commandArn', named in that order); no request value is interpolated. The command itself remains readable afterwards (GetCommand still returns its commandArn).
Emulator: correct code ValidationException, but the message is "only one of commandArn and targetArn may be provided" — different fixed text, lower-cased, member names unquoted and in the opposite order, and no "Only one valid parameter value is accepted." sentence.
Why: a client, SDK test, or log scraper that matches AWS's refusal sentence never matches; the message is the only place AWS reports which of the two scopes it rejected, and the emulator's prose is a sentence AWS never emits.
Fix: ListCommandExecutions' input validation / refusal-message construction (services/service-com-amazonaws-iot-awsiotservice/src/ops/list_command_executions.rs).
Traces: iot.list-command-executions-command-and-target-scope-together-rejected.

Cause 2 of 7: the same operation's both-time-windows refusal is emulator-authored in the same way.
AWS: ListCommandExecutions takes `startedTimeFilter` and `completedTimeFilter`, both of shape TimeFilter {after, before}, and models ValidationException (400). Each window alone is accepted and answers an empty `commandExecutions` list for a command with no executions. Recorded behavior: a request carrying both windows is refused 400 ValidationException with "Both 'startedTimeFilter' and 'completedTimeFilter' parameter values were provided. Only one valid parameter value is accepted." — same template as Cause 1, with the two conflicting member names as its only variable parts.
Emulator: code ValidationException, message "only one of startedTimeFilter and completedTimeFilter may be provided".
Why: same as Cause 1 — exact-match clients and assertions keyed to AWS's wording break. Filed separately from Cause 1 because the two refusals are raised on different member pairs and both have to be re-worded.
Fix: ListCommandExecutions' input validation / refusal-message construction (same handler, the time-filter branch).
Traces: iot.list-command-executions-started-and-completed-filters-together-rejected.

Cause 3 of 7: the same operation's invalid-pagination-token refusal is emulator-authored.
AWS: ListCommandExecutions is @paginated (inputToken nextToken / outputToken nextToken / items commandExecutions / pageSize maxResults) and models ValidationException (400). Recorded behavior: a `nextToken` the listing never issued (a token fabricated by the caller, or one issued for another listing) is refused 400 ValidationException with the message "Next token is invalid." — four words of fixed text, no variable part at all, and in particular the token is NOT echoed.
Emulator: code ValidationException, message "nextToken is not a continuation token of this listing".
Why: AWS's sentence for a bad continuation token is a short fixed string clients and SDK paginator tests key on; the emulator substitutes prose AWS never emits.
Fix: the nextToken decode/validate path of ListCommandExecutions and the message it raises (same handler, plus whatever shared pagination-token helper it calls).
Traces: iot.list-command-executions-unissued-next-token-rejected.

Cause 4 of 7: ListThings' maxResults @range violation message DROPS the rejected value that AWS quotes.
AWS: Smithy ListThings.maxResults is RegistryMaxResults with @range(min 1, max 250), bound as httpQuery maxResults, and ListThings models InvalidRequestException (httpError 400). Recorded behavior: maxResults above the maximum is refused 400 InvalidRequestException with "1 validation error detected: Value '<maxResults>' at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 250". Fixed text: "1 validation error detected: Value '", "' at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 250"; the ONLY variable part is the rejected maxResults value copied from the request query string (the bound 250 is the modeled maximum).
Emulator: correct status and code InvalidRequestException, but the message is "1 validation error detected: Value at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 250" — the "'<value>' " segment is missing, so the sentence reads "Value at 'maxResults'".
Why: the operator loses the one piece of information the message exists to carry (WHICH value was rejected), and every exact-match client diverges. Note the shared @range formatter appears to omit the value unconditionally: the resolved issue 20261116T234638Z-iot-4-net-new-causes-constraint-violation-messages.md recorded that CreateRoleAlias.credentialDurationSeconds must NOT quote its value, so the formatter cannot be flipped globally — the value-echo decision has to be made per member/operation, with maxResults quoting it.
Fix: the service's constraint-violation report serializer in its @range branch and ListThings' input validation path that feeds it (services/service-com-amazonaws-iot-awsiotservice/src/ops/list_things.rs plus the shared validation-message builder).
Traces: iot.list-things-max-results-out-of-range-rejected.

Cause 5 of 7: UpdateAuthorizer REPLACES tokenSigningPublicKeys with the submitted map instead of merging the named keys into the stored map.
AWS: Smithy UpdateAuthorizer (PUT /authorizer/{authorizerName}) has all body members optional — authorizerFunctionArn, tokenKeyName, tokenSigningPublicKeys (PublicKeyMap: KeyName -> KeyValue), status, enableCachingForHttp — i.e. it is a partial update that applies only the members the request names. Recorded behavior: an authorizer created with two signing keys (say key A and key B present), then updated with tokenSigningPublicKeys naming ONLY key B, reads back from DescribeAuthorizer with BOTH key names still present — the named key is added/overwritten, keys not named in the request are retained. (The model documents no removal semantics, so this is recorded behavior only.)
Emulator: after a single-key update, DescribeAuthorizer's tokenSigningPublicKeys contains only the key named in that update; every key not re-sent is dropped.
Why: a client rotating one signing key of a multi-key custom authorizer silently loses every other key, so devices presenting a token signed with a retained key are refused at the authorizer — a data-losing update that AWS does not perform.
Fix: UpdateAuthorizer's merge semantics over the stored authorizer record — apply only the members present in the request and merge tokenSigningPublicKeys key-by-key into the stored PublicKeyMap (services/service-com-amazonaws-iot-awsiotservice/src/ops/update_authorizer.rs plus the authorizer state record).
Traces: iot.authorizer-update-applies-named-fields-only.

Cause 6 of 7: UpdateThingShadow enforces no JSON nesting limit — a state section nested one level past the limit is accepted (200) instead of refused.
AWS: Smithy iot-data UpdateThingShadow (POST /things/{thingName}/shadow, optional ?name=<shadowName>) models InvalidRequestException (httpError 400). The nesting limit itself is documented in the IoT Core service quotas, not the model, so this is documented/recorded behavior: a desired (or reported) section nested at most 9 JSON object levels deep is stored verbatim, and one level deeper is refused 400 InvalidRequestException with the message "Json contains too many levels of nesting. Maximum allowed is 9." — fixed text with the documented maximum (9) as its only numeral — leaving the stored document and its version untouched.
Emulator: the over-deep update is ACCEPTED with HTTP 200 and a shadow payload body; no refusal is raised, so the document is mutated and its version advances where AWS rejects the write.
Why: a client gets a shadow the real service would never have stored, and the depth guard that protects downstream shadow consumers (and the version/state invariants the check asserts after a refusal) never fires; code written against AWS's refusal path is untested and the stored shadow diverges permanently.
Fix: UpdateThingShadow's payload validation — count the nesting depth of the state sections before merging and raise InvalidRequestException with the message above (services/service-com-amazonaws-iotdataplane-iotmoonrakerservice/src/ops/update_thing_shadow.rs plus the shadow document validator).
Traces: iot.shadow-state-nested-past-depth-limit-rejected.

Cause 7 of 7: a command-execution status report that arrives after the execution reached a terminal state is refused with the JOB-execution error code and sentence instead of the command-execution one.
AWS: IoT Commands device reports are published to $aws/commands/<target>/<executionId>/response/json and answered on .../response/accepted/json or .../response/rejected/json. Recorded behavior: after the device reports REJECTED (terminal), a later report of SUCCEEDED for the same executionId is answered on the rejected topic with a body whose `executionId` is the execution's id, whose `error` is "TerminalStateReached", and whose `errorMessage` is "Command Execution status cannot be updated to SUCCEEDED since execution has already completed with status REJECTED." Fixed text: "Command Execution status cannot be updated to ", " since execution has already completed with status ", "."; the variable parts are the status the late report asked for and the terminal status already stored, both from the request and the stored execution. The refused report changes no field of the execution.
Emulator: the report is refused on the rejected topic, but the body carries `code`: "InvalidStateTransition" with `message`: "The status of job execution cannot be changed to be SUCCEEDED" — the wrong member names (code/message rather than error/errorMessage), the wrong error identifier, and the jobs-data-plane sentence, which names neither the command execution nor the status it already completed with.
Why: a device or fleet-management client that distinguishes a terminal-state refusal (stop retrying) from a transient one keys on error == "TerminalStateReached"; it sees an unknown identifier from a different API family and cannot tell why the report was rejected. It also shows the Commands response path is being served by the job-execution update path.
Fix: the $aws/commands/.../response handler's terminal-state guard and its rejected-topic body serializer — emit the command-execution error identifier and sentence, not UpdateJobExecution's (services/service-com-amazonaws-iot-awsiotservice command-execution update path / the reserved-topic handler for $aws/commands, plus the command-execution state record).
Traces: iot.command-execution-update-after-device-rejection-rejected.
