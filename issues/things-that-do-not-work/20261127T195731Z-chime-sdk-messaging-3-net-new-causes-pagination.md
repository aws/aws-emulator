# chime-sdk-messaging: 3 net-new causes — pagination-token refusals use the wrong error class and wording, malformed AppInstanceArn is served an empty page instead of refused, and SendChannelMessage never enforces the UTF-8 byte ceilings

> _Note: this issue was identified against the code base at commit `736b28b40b20576fe554bad4abfa7fe4ba2cddb1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListChannels

## Description
Three independent defects in the Chime SDK messaging emulator, all grounded in failing behavioral checks. Each cause is numbered and carries its own failing check ids; all three must be closed before this issue is submitted.

Cause 1 of 3: a NextToken this service never issued (or an issued one that was altered) is refused with a synthetic BadRequestException instead of AWS's ValidationException pagination-token refusal.
AWS: the pagination-token refusal is framework-level and NOT in the Smithy model — Smithy for ListChannels/ListChannelFlows/ListChannelBans/ListChannelMemberships/ListChannelMessages/ListChannelModerators/SearchChannels models NextToken as a @sensitive string (@length 0..2048, pattern '.*') and models only BadRequestException(400)/ForbiddenException(403)/UnauthorizedClientException(401)/ThrottledClientException(429)/ServiceFailureException(500)/ServiceUnavailableException(503); so this is recorded behavior only. The recordings show AWS answering error code 'ValidationException' with a message of the fixed form "Pagination token exception in operation '<OperationName>': <reason>". Fixed text: "Pagination token exception in operation '", then the operation name as invoked, then "': ", then the reason. The reason is a function of HOW the supplied token fails, not of the request's values: (a) a token whose base64/wrapper payload cannot be decoded at all -> "decoding error; possible tampering detected" (recorded for ListChannelBans and ListChannelFlows); (b) a token that decodes but whose leading two bytes are read as an unknown envelope/schema id -> "invalid payload wrapping schema <n>", where <n> is that big-endian two-byte number taken from the supplied token (an internal schema number — never a fixed literal; the checks grade it as <n>) (recorded for ListChannels, ListChannelMemberships, ListChannelModerators); (c) an otherwise well-formed token whose ciphertext does not decrypt, i.e. an issued token with its tail altered -> "decryption error" (recorded for ListChannelMessages). SearchChannels is recorded with the same "Pagination token exception in operation 'SearchChannels': " prefix.
Emulator: every one of the seven listings answers error code 'BadRequestException' with the message 'NextToken is not a token this service issued' — one emulator-authored sentence for all operations and all failure modes, with no operation name and no reason clause.
Why: a client that branches on the error code (ValidationException vs BadRequestException) to tell a stale/forged cursor from a bad request never takes that branch; retry and resume logic keyed on ValidationException, and any log scraping or alarm keyed on the "Pagination token exception in operation ..." sentence, silently never fires. The message also loses the operation name and the reason, so an operator cannot tell a tampered token from an undecryptable one.
Fix: the shared pagination-token decode/validate path used by the listing handlers (it is one path — all seven operations emit the identical sentence) must classify the decode failure and raise the service's ValidationException with the operation name and the matching reason clause, not a single BadRequestException sentence.
Traces: chime-sdk-messaging.list-channel-bans-unissued-next-token-rejected, chime-sdk-messaging.list-channel-flows-unissued-next-token-rejected, chime-sdk-messaging.list-channel-memberships-unissued-next-token-rejected, chime-sdk-messaging.list-channel-messages-unissued-next-token-rejected, chime-sdk-messaging.list-channel-moderators-unissued-token-rejected, chime-sdk-messaging.list-channels-unissued-next-token-rejected, chime-sdk-messaging.search-channels-unissued-next-token-rejected.

Cause 2 of 3: an AppInstanceArn that satisfies the modelled ARN pattern but names no App Instance is answered HTTP 200 with an empty page instead of being refused.
AWS: Smithy models ListChannels.AppInstanceArn and ListChannelFlows.AppInstanceArn as required ChimeArn (@length 5..1600, pattern '^arn:[a-z0-9-\\.]{1,63}:[a-z0-9-\\.]{0,63}:[a-z0-9-\\.]{0,63}:[a-z0-9-\\.]{0,63}:[^/].{0,1023}$'), and both operations model BadRequestException with httpError 400. The recordings show AWS refusing an ARN that matches that pattern yet names no Chime App Instance resource with HTTP 400, code 'BadRequestException', message "An invalid App Instance ARN was supplied for the input parameter." — that whole sentence is fixed text, with no value from the request interpolated.
Emulator: both operations accept it and answer HTTP 200 with an empty collection — ListChannelFlows returns {'ChannelFlows': []} and ListChannels returns {'Channels': []}.
Why: a client that passed a wrong, truncated or mis-built App Instance ARN is told the App Instance exists and is empty. Provisioning and reconciliation loops read 'no channels' as authoritative and delete or recreate state; the misconfiguration is never surfaced where AWS would fail fast with a 400.
Fix: the AppInstanceArn input validation / resource resolution shared by the ListChannels and ListChannelFlows handlers — resolve the ARN to an App Instance before listing and refuse a non-App-Instance ARN with the modelled BadRequestException(400), instead of listing against a non-existent owner and returning an empty page.
Traces: chime-sdk-messaging.list-channels-malformed-app-instance-arn-rejected, chime-sdk-messaging.list-channel-flows-malformed-app-instance-arn-rejected.

Cause 3 of 3: SendChannelMessage never enforces the Content size ceilings, so an over-limit body is accepted and persisted.
AWS: Smithy constrains SendChannelMessage.Content only as NonEmptyContent (@length min 1, pattern '^[\\s\\S]*$', @sensitive) and declares BadRequestException(400), so the ceilings themselves are recorded/documented behavior only: AWS caps a CONTROL message's Content at 30 bytes and a STANDARD message's Content at 4096 bytes, counting UTF-8 BYTES rather than characters, and refuses an over-limit body with HTTP 400 code 'BadRequestException'. The messages are fixed text with nothing interpolated: "Control Messages size limit exceeded." for Type=CONTROL and "Channel Messages size limit exceeded." for Type=STANDARD. A body exactly at its byte ceiling is accepted.
Emulator: a CONTROL body of multi-byte characters that is under the limit in characters but over it in bytes is accepted — HTTP 201 with Status.Value 'SENT' and a MessageId — and the message is persisted into channel history. No size refusal is emitted at all (the limit is either unchecked or counted in characters, so no body short enough in characters can ever be refused).
Why: a client relying on AWS to reject over-sized bodies instead sees them succeed in the emulator and fail in production; worse, oversized CONTROL/STANDARD messages enter channel history, so history read-backs and consumers that assume the documented ceilings diverge, and code paths that handle the BadRequestException are never exercised.
Fix: SendChannelMessage's input validation in its handler — measure Content in UTF-8 bytes and refuse above 30 bytes for Type=CONTROL and above 4096 bytes for Type=STANDARD with the modelled BadRequestException(400) and the corresponding sentence, before the message is written to channel state.
Traces: chime-sdk-messaging.message-size-limits-count-utf8-bytes-rejected.

## Steps to Reproduce
Region us-east-1 (Chime SDK messaging is served from us-east-1 / eu-central-1 only).

Cause 1: create an AppInstance (chime-sdk-identity), an AppInstanceUser, and a channel with a couple of members/messages. Then call each of ListChannelBans, ListChannelFlows, ListChannelMemberships, ListChannelModerators, ListChannels and SearchChannels with MaxResults=1 and NextToken set to a base64 string the service never issued (e.g. base64 of 'page-cursor-this-service-never-minted'), and call ListChannelMessages with a NextToken the service DID issue but with its last 8 characters replaced. Observe the error code and message: each should be ValidationException with "Pagination token exception in operation '<Op>': <reason>"; the emulator answers BadRequestException 'NextToken is not a token this service issued' for all seven. A subsequent call with the genuine token must still page normally.

Cause 2: create an AppInstance and a public channel in it. Call ListChannelFlows(AppInstanceArn='arn:aws:chime:x:y:z') and ListChannels(AppInstanceArn='arn:aws:chime:x:y:z', ChimeBearer=<an AppInstanceUser ARN>) — an ARN that satisfies the modelled ChimeArn pattern but names no Chime App Instance. Both should answer HTTP 400 BadRequestException 'An invalid App Instance ARN was supplied for the input parameter.'; the emulator answers HTTP 200 with an empty list.

Cause 3: create an AppInstance, an AppInstanceUser and a channel. Call SendChannelMessage with Type='CONTROL', Persistence='PERSISTENT' and Content of 10 EURO SIGN characters (30 UTF-8 bytes) — accepted, as AWS does. Then send 11 EURO SIGN characters (33 UTF-8 bytes, still only 11 characters): AWS refuses with HTTP 400 BadRequestException 'Control Messages size limit exceeded.'. Repeat with Type='STANDARD', Content of 4096 ASCII characters (accepted) and then 1366 EURO SIGN characters (4098 bytes), which AWS refuses with 'Channel Messages size limit exceeded.'. Finally walk ListChannelMessages: only the accepted bodies may appear in history.
