# connectparticipant: 4 net-new causes — SendEvent, SendMessage, StartAttachmentUpload and CompleteAttachmentUpload all accept requests AWS refuses

> _Note: this issue was identified against the code base at commit `1d46c777556b138301c0ca0bdf752665685bd84a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEvent

## Description
Four independent over-permissive root causes on connectparticipant's chat data plane, each found by replaying behavioral suite simparity-behavioral-aws-v1 against this emulator. In every one of them the emulator answers HTTP 200 for a request AWS refuses with HTTP 400 ValidationException, so the refusal class is simply absent. A fixer must close ALL FOUR before submitting. Smithy model consulted: services/service-com-amazonaws-connectparticipant-amazonconnectparticipantservicelambda/smithy-model/com-amazonaws-connectparticipant-amazonconnectparticipantservicelambda.json (sdkId ConnectParticipant, restJson1; ValidationException is a service-common error on every operation, errorKind client, httpError 400, Message required).

Cause 1 of 4: SendEvent accepts ANY ContentType instead of refusing one outside the supported event set. Failing checks: connectparticipant.send-event-message-content-type-rejected, connectparticipant.send-event-unsupported-content-type-rejected.
AWS: Smithy SendEventRequest$ContentType (ChatContentType, @length 1..100, required) documents exactly four supported types — "Supported types are: application/vnd.amazonaws.connect.event.typing, application/vnd.amazonaws.connect.event.connection.acknowledged (is no longer maintained since December 31, 2024), application/vnd.amazonaws.connect.event.message.delivered, application/vnd.amazonaws.connect.event.message.read". Anything else is refused 400 ValidationException whose message is the field-enumeration form: fixed text "Unsupported value for field: [" + the rejected member name + "] specified, supported value(s) [" + the comma-joined supported list + "]" — i.e. for this operation "Unsupported value for field: [ContentType] specified, supported value(s) [application/vnd.amazonaws.connect.event.typing,application/vnd.amazonaws.connect.event.connection.acknowledged,application/vnd.amazonaws.connect.event.message.read,application/vnd.amazonaws.connect.event.message.delivered]". The member name and the supported list are the only non-literal parts and both are fixed for this operation; nothing from the request's value is interpolated. This holds both for a message content type (text/plain) and for an invented event type under the application/vnd.amazonaws.connect.event. prefix.
Emulator: the call SUCCEEDS 200 and answers a fresh item Id and AbsoluteTime. src/ops/send_event.rs classifies ContentType only by receipt_kind() (lines 276-284): the two receipt types take the receipt path and EVERY other value falls through to the "transient event" branch, which mints an Id and records an idempotency entry. There is no supported-set check anywhere in handle().
Why: a client that sends a mistyped or unsupported event type is told the event was accepted and is handed an item Id that correlates to nothing; the SDK's error branch for an unsupported event type is unreachable, and because the "event" is silently manufactured, a caller cannot distinguish a real typing/receipt event from a typo. It also makes SendEvent a second, unvalidated write path for message content types that belong to SendMessage.
Fix: SendEvent's input validation in the operation handler — reject a ContentType outside the four modeled event types with the modeled ValidationException before any state is touched.
Traces: connectparticipant.send-event-message-content-type-rejected (ContentType="text/plain" with a body; the emulator answered {'Id': <uuid>, 'AbsoluteTime': <instant>}), connectparticipant.send-event-unsupported-content-type-rejected (ContentType="application/vnd.amazonaws.connect.event.customer.waved"; the emulator answered {'Id': <uuid>, 'AbsoluteTime': <instant>}). Code read for grounding: services/service-com-amazonaws-connectparticipant-amazonconnectparticipantservicelambda/src/ops/send_event.rs lines 211-268 (receipt branch, then the unconditional transient-event branch) and lines 276-284 (receipt_kind).

Cause 2 of 4: SendMessage ignores the contact's SupportedMessagingContentTypes, so a content type the chat was not started with is stored instead of refused. Failing check: connectparticipant.send-message-content-type-not-enabled-on-contact-rejected.
AWS: SendMessageRequest$ContentType is required and documented as constrained to the content types the contact was started with (Connect's StartChatContact SupportedMessagingContentTypes). A content type not enabled on that contact is refused 400 ValidationException with the fixed sentence "Specified request parameter(s) are invalid." — the whole message is fixed text, with no part taken from the request or from state. A twin chat started WITH text/markdown accepts the identical request.
Emulator: SendMessage returns 200 and appends the item. src/ops/send_message.rs handle() resolves the session, applies ClientToken idempotency and the transcript-room check, then calls session.append(... input.content_type ...) — the session's enabled content types are never consulted, and no code path can produce this refusal.
Why: a client's negative path for an unenabled content type never fires, and worse, the message is PERSISTED: the transcript of a text/plain-only chat ends up carrying a text/markdown item that AWS would never have stored, so transcript readers and agent UIs render content the contact never admitted.
Fix: SendMessage's handler validation plus the session state that must carry the contact's SupportedMessagingContentTypes from StartChatContact (src/ops/send_message.rs and crate::state's ChatSession).
Traces: connectparticipant.send-message-content-type-not-enabled-on-contact-rejected — SendMessage(ContentType="text/markdown") on a chat started with the default text/plain set answered HTTP 200 with {'Id': <uuid>, 'AbsoluteTime': <instant>} where ('ValidationException', 'Specified request parameter(s) are invalid.') was due. Code: src/ops/send_message.rs lines 161-229.

Cause 3 of 4: StartAttachmentUpload does not enforce the instance's chat attached-files configuration — neither the maximum size nor the allowed extension list. Failing checks: connectparticipant.start-attachment-upload-size-and-extension-limits-rejected, connectparticipant.start-attachment-upload-outside-chat-file-config-rejected.
AWS: StartAttachmentUploadRequest carries AttachmentSizeInBytes (required, @range min 1) and AttachmentName (required, @length 1..256), and the upload is validated against the Connect instance's attached-files configuration (Connect UpdateAttachedFilesConfiguration: MaximumSizeLimitInBytes and ExtensionConfiguration.AllowedExtensions for AttachmentScope CHAT). A file one byte over the configured ceiling is refused 400 ValidationException with the message "Files cannot exceed <N> MB." — fixed text around one variable, the configured ceiling rendered in whole megabytes (so 1 for a 1 MiB ceiling). A file whose extension is not in AllowedExtensions is refused 400 ValidationException with "The file extension .<ext> is not supported." — fixed text around one variable, the extension taken from the request's AttachmentName. Raising the limit and allowing the extension makes the identical requests succeed, so the rule is read from live configuration, not hard-coded.
Emulator: both calls SUCCEED 200 and publish a pre-signed upload target. src/ops/start_attachment_upload.rs validates only that ContentType is a legal header value (lines 183-191), that the connection token authenticates a session with attachments_shared (lines 205-224), ClientToken replay (lines 227-236) and a per-contact attachment count quota (lines 238-247); it then stores the Attachment with size_in_bytes taken verbatim from the request (line 274). Neither the instance's MaximumSizeLimitInBytes nor its AllowedExtensions is read anywhere.
Why: a client is handed a working pre-signed URL for a file AWS would have refused outright, so an oversized or disallowed file is uploaded and completed and ends up in the transcript; a caller cannot test or exercise its own over-limit handling, and an operator's attached-files policy (the control that bounds attachment storage and file types) has no effect in this emulator.
Fix: StartAttachmentUpload's input validation in its handler, against the chat's instance attached-files configuration as carried into the participant session (src/ops/start_attachment_upload.rs, plus the configuration propagation from the connect crate's UpdateAttachedFilesConfiguration into crate::state).
Traces: connectparticipant.start-attachment-upload-size-and-extension-limits-rejected (instance configured extensions [txt], max 1048576; StartAttachmentUpload(AttachmentName="over-limit.txt", AttachmentSizeInBytes=1048577) answered 200 with an AttachmentId and UploadMetadata instead of ('ValidationException', 'Files cannot exceed 1 MB.'); the later .pdf assertion, expecting ('ValidationException', 'The file extension .pdf is not supported.'), is ungraded because the check aborts at the size assertion), connectparticipant.start-attachment-upload-outside-chat-file-config-rejected (same 200 for AttachmentSizeInBytes = configured limit + 1). Code: src/ops/start_attachment_upload.rs lines 180-293.

Cause 4 of 4: CompleteAttachmentUpload confirms an attachment whose bytes were never uploaded. Failing checks: connectparticipant.complete-attachment-upload-before-file-put-rejected, connectparticipant.complete-attachment-upload-unsent-and-repeat-rejected.
AWS: CompleteAttachmentUpload "Allows you to confirm that the attachment has been uploaded using the pre-signed URL provided in StartAttachmentUpload" (AttachmentIds @length 1..1, ClientToken required). Confirming an upload whose bytes were never PUT to that URL is refused 400 ValidationException with the fixed sentence "Specified request parameter(s) are invalid." (whole message fixed; nothing from the request appears in it), and the never-sent upload must NOT appear in the transcript. Recorded behavior additionally shows the same fixed refusal for a repeat confirmation of an attachment already APPROVED.
Emulator: the call SUCCEEDS 200 with an empty body and the attachment is moved to APPROVED and appended to the transcript. src/ops/complete_attachment_upload.rs looks the attachment up by id and contact (lines 215-224), refuses an already-approved one, checks transcript room, then sets ARTIFACT_STATUS_APPROVED and appends the ATTACHMENT item (lines 256-264). The stored Attachment has an `uploaded` field (set at StartAttachmentUpload to None, src/ops/start_attachment_upload.rs line 284) that this handler never reads, so "bytes received" is not a precondition of confirmation at all.
Why: a client that forgets, or fails, to PUT the file still gets a success and a transcript entry; the attachment then exists with no content behind it, GetAttachment later hands out a download URL for nothing, and the documented confirm-after-upload contract is unenforceable. A caller cannot distinguish a completed upload from an abandoned one.
Fix: CompleteAttachmentUpload's handler must require that the attachment data plane actually received the file (the `uploaded` marker crate::service writes when the pre-signed PUT lands) and refuse otherwise with the modeled ValidationException; see src/ops/complete_attachment_upload.rs. Note for the fixer: the same handler's already-APPROVED repeat currently answers 409 ConflictException with emulator-authored text while the recording expects 400 ValidationException 'Specified request parameter(s) are invalid.'; that assertion is reached only after this cause is fixed (it is ungraded today).
Traces: connectparticipant.complete-attachment-upload-before-file-put-rejected (HTTP 200, empty body, where ('ValidationException', 'Specified request parameter(s) are invalid.') was due), connectparticipant.complete-attachment-upload-unsent-and-repeat-rejected (accepted with {}). Code: src/ops/complete_attachment_upload.rs lines 190-270; src/ops/start_attachment_upload.rs lines 269-292.
