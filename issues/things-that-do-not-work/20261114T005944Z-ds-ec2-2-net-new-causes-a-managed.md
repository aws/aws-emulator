# ds__ec2: 2 net-new causes — a Managed Microsoft AD places NO network interfaces in the caller's VPC, and DeleteDirectory never releases the controllers security group it provisioned, so the directory-network flows hang and the deleted directory leaks its EC2 group

> _Note: this issue was identified against the code base at commit `4722d4d18b8a45cc32ce261babae5e464505eabf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMicrosoftAD

## Description
TWO net-new causes spanning ds and ec2, grounded in the three failing checks the suite lists under '### ds__ec2' that this replay marks neither ALREADY FILED nor OWNED. Not a bootstrap gap: ds answers CreateMicrosoftAD/DescribeDirectories, EC2 answers the describes, and ds now DOES mint the controllers security group in EC2 — what is missing is the rest of the cross-service effect and its teardown. A fixer must close BOTH causes before submitting.

Related open issues that this replay does NOT mark as owning these checks, so none of them covers these failures: 20261111T020957Z-ds-ec2-a-managed-microsoft-ad-never-materialises.md describes the whole network presence as absent and lists the two directory-network check ids, but the security-group half has since been implemented (src/state/ec2_security_groups.rs) and the suite reports both checks unowned in this run; 20261109T135909Z-ds-ec2-describedirectories-never-reports-vpcsettings-securitygroupid-so.md covers the ds-side SecurityGroupId member, which now reports; 20261028T083859Z-ds-2-net-new-behavioral-root-causes-an.md covers the e2e LDAPS lifecycle dying in its SOLVE phase on empty DnsIpAddrs, whereas that check now reaches phase 4 and fails in DESTROY. They should be landed together as the one cross-service provisioning work item.

--- Cause 1 of 2: CreateMicrosoftAD creates no network interfaces for the directory's servers, so EC2's view of the directory holds no ENI and both directory-network flows hang with nothing graded (check ids ds__ec2.microsoft-ad-creates-a-controllers-security-group-and-one-eni-per-subnet-in-the-vpc, ds__ec2.delete-directory-releases-its-controllers-security-group-and-enis-from-the-vpc).
AWS: recorded behavior only for the cross-service effect (the ds Smithy model describes the envelope, not what is placed in EC2); the modelled anchors are DirectoryVpcSettings$SubnetIds, whose own documentation says 'Directory Service creates a directory server and a DNS server in each of these subnets', and DirectoryVpcSettingsDescription$SecurityGroupId (target SecurityGroupId, @pattern ^(sg-[0-9a-f]{8}|sg-[0-9a-f]{17})$, 'The domain controller security group identifier for the directory'). Recorded behavior: once a Managed Microsoft AD created with VpcSettings has left Requested, EC2 holds ONE network interface per chosen subnet whose Description names the directory and whose Groups include the directory's controllers security group, each interface sitting in its own chosen subnet; DeleteDirectory then releases them, after which ec2:DescribeNetworkInterfaces on a released id is refused with Error.Code 'InvalidNetworkInterfaceID.NotFound' and the message "The networkInterface ID '<eni-id>' does not exist" (fixed text; the id is taken from the request), which is what lets the caller delete its own subnets and VPC instead of hitting DependencyViolation. Per-run ids are not requirements; the existence, the per-subnet placement, the group membership and the release are.
Emulator: ds's only interface-level hops into EC2 are the read-only subnet resolution (src/state/ec2_subnets.rs) and the CreateSecurityGroup call (src/state/ec2_security_groups.rs:84-121). There is no ec2:CreateNetworkInterface anywhere in the crate — src/state.rs:83-99 declares directory_network, directory_servers, ec2_security_groups and ec2_subnets and nothing else for the network, and src/state/directory_network.rs:34-91 keeps only the subnet id, CIDR block, zone and VPC per subnet and counts server addresses out of the block ('this one GATES no create'). So ec2:DescribeNetworkInterfaces(Filters=[{vpc-id}]) never returns an interface whose Description names the directory. Both checks consequently die at the 60 s budget with 'Check timed out after 60.0s' and no exception frame: their SecurityGroupId poll (5 s interval) is now satisfied, their ENI poll (>= 2 interfaces naming the directory, 10 s interval, 300 s nominal timeout) never is, and the delete-side check never reaches its release assertions at all.
Why: the directory's servers have no presence on the caller's network for any client to work from. Anything that resolves the controllers' interfaces, reconciles the directory against EC2, or reads which addresses/subnets the servers really occupy finds nothing; a client that waits for the interfaces — as AWS callers must, because they appear asynchronously during Creating — hangs instead of being served; and the teardown half is invisible, so a caller cannot tell whether the interfaces that otherwise block DeleteSubnet/DeleteVpc with DependencyViolation have been released.
Fix: the cross-service provisioning in the CreateMicrosoftAD/CreateDirectory handler and the ds state module that owns the directory's network presence (src/state/directory_network.rs beside src/state/ec2_security_groups.rs) — a create must mint one network interface per requested subnet in the EC2 service state over the same in-process callback the security group is created through, each in its own subnet, each carrying the controllers group, each with the directory id in its Description — plus the release counterpart in src/state/directory_deletion.rs, so EC2 afterwards answers InvalidNetworkInterfaceID.NotFound for them.

--- Cause 2 of 2: DeleteDirectory never deletes the controllers security group it provisioned in EC2, so a deleted directory leaks the group and the e2e lifecycle's destroy phase can never observe the network released (check id ds__ec2.e2e-managed-ad-with-ldaps-and-resets-lifecycle).
AWS: recorded behavior only. Directory Service provisions the group '<DirectoryId>_controllers' on the caller's behalf and removes it with the directory, so after DeleteDirectory no security group whose GroupName carries the directory id remains in the VPC and ec2:DescribeSecurityGroups on the released id is refused with Error.Code 'InvalidGroup.NotFound' and the message "The security group '<sg-id>' does not exist" (fixed text; the id taken from the request). The modelled anchor is again DirectoryVpcSettingsDescription$SecurityGroupId; Smithy DeleteDirectory input {DirectoryId @required ^d-[0-9a-f]{10}$} / output {DirectoryId}, errors ClientException / EntityDoesNotExistException / ServiceException.
Emulator: ds creates the group (src/state/ec2_security_groups.rs:34-121 — name '<DirectoryId>_controllers', description 'AWS created security group for <DirectoryId> directory controllers') but its teardown removes ds-side records ONLY: src/state/directory_deletion.rs:113-142 forget_directory drops the directory record and its snapshots, trusts and shares, and there is no ec2:DeleteSecurityGroup call anywhere in the crate. The check reaches phase 4/4 (deploy, solve and cleanup all pass now) and dies there: '[phase 4/4 destroy] TimeoutError: the directory's ENIs and security group leave: the run budget ended first; not graded' — the poll whose predicate is _directory_footprint(ec2, vpc, directory_id) == ([], []), i.e. no ENI whose Description names the directory and no security group whose GroupName contains it. Hypothesis (from the checkout, since the probe's own values are not in the report): the groups half is the non-empty one, because the group the create minted is still in the VPC after the directory is gone, while the ENI half is empty for Cause 1's reason. The budget exhaustion that turns this into 'not graded' is the clock-owed-span overrun filed for ds in the sibling issue of this sweep; the leak itself is independent of it.
Why: a client that deletes a directory and then deletes its own VPC is blocked or left with an orphan: the group outlives the directory it belongs to, the account accumulates one '<DirectoryId>_controllers' group per create/delete cycle, and the documented end state — DescribeSecurityGroups on the released group refusing InvalidGroup.NotFound "The security group '<sg-id>' does not exist" — is unreachable. The assertions after the footprint poll (the stack delete reaching DELETE_COMPLETE, and CloudFormation refusing the deleted stack with ValidationError 'Stack with id <name> does not exist') are ungraded as a consequence.
Fix: the directory teardown's cross-service half — src/state/directory_deletion.rs, which currently removes only ds-side records, must release what the create provisioned in EC2 through the same in-process callback src/state/ec2_security_groups.rs uses (delete the controllers group, and the per-subnet interfaces once Cause 1 is fixed), at the point of the teardown chain where the directory record leaves the store.

Traces: ds__ec2.microsoft-ad-creates-a-controllers-security-group-and-one-eni-per-subnet-in-the-vpc and ds__ec2.delete-directory-releases-its-controllers-security-group-and-enis-from-the-vpc (Cause 1, both killed in the ENI poll); ds__ec2.e2e-managed-ad-with-ldaps-and-resets-lifecycle (Cause 2, phase 4/4 destroy).
