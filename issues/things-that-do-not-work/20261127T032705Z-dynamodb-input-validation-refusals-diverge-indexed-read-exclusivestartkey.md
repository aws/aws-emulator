# DynamoDB input-validation refusals diverge: indexed-read ExclusiveStartKey messages are swapped, and the ValidationException envelope is wrong on UpdateItem and TransactWriteItems

> _Note: this issue was identified against the code base at commit `0ebf0829cad241d824be0f94d62bd70dc38785d4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Scan

## Description
Four net-new causes on dynamodb, all of them request-validation refusals where the emulator returns AWS's status (HTTP 400) and AWS's error class (com.amazon.coral.validate#ValidationException) but assembles a `message` AWS does not use — either by applying the wrong refusal of a pair, or by rendering the Coral validation envelope differently. None of the four is claimed by the replay report (empty stub_path, empty owned_by).

THIS BUNDLE CONTAINS 4 CAUSES. All four must be closed before submitting.

Related open issues that do NOT carry these replay keys and therefore do not cover these causes: 20261120T225636Z-dynamodb-validationexception-envelope-diverges-member-paths-value-rendering.md (same family of fault, but keyed on GetItem/BatchWriteItem/UpdateTable/PutItem/TransactGetItems only — not UpdateItem and not TransactWriteItems) and 20261109T055139Z-dynamodb-validation-refusal-messages-are-emulator-authored-for.md.

Cause 1 of 4 — Scan with an ExclusiveStartKey whose index-key attribute has the wrong AttributeValue type is refused with the generic cursor message instead of the type-mismatch message.
AWS: Smithy: Scan.ExclusiveStartKey targets Key (a map of AttributeName -> AttributeValue); Scan.IndexName targets IndexName @length 3..255 @pattern ^[a-zA-Z0-9_.-]+$. The refusal text is recorded behavior only (the model states the shape, not the message). When a Scan on an index supplies an ExclusiveStartKey whose index key attribute carries a different AttributeValue arm than the type that attribute is declared with in the table's AttributeDefinitions, AWS refuses 400 ValidationException with the message template "One or more parameter values were invalid: Type mismatch for Index Key <keyAttributeName> Expected: <declared type> Actual: <submitted type> IndexName: <indexName>". Fixed text: "One or more parameter values were invalid: Type mismatch for Index Key", " Expected: ", " Actual: ", " IndexName: ". Variable parts, taken from the request and the table's stored schema: the index key attribute's name, its declared scalar type (S/N/B) from AttributeDefinitions, the arm actually submitted, and the request's IndexName. (In the recording these happen to be gsk, N, S and gsi1 — those are fixture values filling the template, not part of it.)
Emulator: 400 ValidationException with "The provided starting key is invalid" — the generic structural-cursor refusal. The type-mismatch check is never reached on the Scan path, so the caller is never told WHICH key attribute has the wrong type, nor what type was expected.
Why: a paginating client that builds a cursor from the wrong attribute type cannot tell from the refusal which attribute or index is at fault, and any client or suite that matches AWS's wording sees unrelated text.
Fix: the Scan handler's ExclusiveStartKey validation — the index-key type check must run (and win) before the generic "starting key is invalid" fallback.
Traces: ddb-gsi-lsi-scan-esk-malformed-cursor-variants#task#9 (representative), cluster of 18 affected steps including ddb-index-cursor-key-type-mismatch-scan-and-query#task#9, dynamodb-query-scan-exclusive-start-key-attributevalue-validation-rejected#task#10, ddbdepth-scan-pagination-boundary#task#11.

Cause 2 of 4 — Query, given the same malformed index cursor, is refused with the type-mismatch message instead of the generic cursor message. This is the exact inverse of cause 1: the two refusals are swapped between the two read operations.
AWS: Smithy: Query.ExclusiveStartKey targets Key, Query.IndexName targets IndexName @length 3..255 @pattern ^[a-zA-Z0-9_.-]+$. Recorded behavior only: on Query, an ExclusiveStartKey whose index key attribute carries the wrong AttributeValue arm is refused 400 ValidationException with the fixed text "The provided starting key is invalid" — the whole message is fixed text, with no request or state values interpolated. The same fixture (ddb-index-cursor-key-type-mismatch-scan-and-query) exercises both operations against the same table and index, so the per-operation difference in wording is the recorded requirement: Scan details the mismatch, Query does not.
Emulator: 400 ValidationException with "One or more parameter values were invalid: Type mismatch for Index Key <keyAttributeName> Expected: <declared type> Actual: <submitted type> IndexName: <indexName>" (recorded instance: "... Index Key gsisk Expected: N Actual: S IndexName: gsi1") — i.e. it emits on Query precisely the message AWS reserves for Scan.
Why: the two refusals are interchanged, so no client can rely on either operation's wording; a suite pinned to AWS text fails on both reads, and a client that branches on the message mis-classifies the failure.
Fix: Query's ExclusiveStartKey validation — it must raise the generic cursor refusal, with the detailed index-key type mismatch message belonging to Scan only. Most likely one shared cursor-validation helper is reached with the two messages wired to the wrong callers.
Traces: ddb-index-cursor-key-type-mismatch-scan-and-query#task#5 (representative), cluster of 34 affected steps including dynamodb-query-key-condition-value-first-function-and-value-only-rejected#task#4, gsi-query-exclusive-start-key-outside-boundary-rejected#task#12, dynamodb-query-scan-index-name-length-and-pattern-rejected#task#4.

Cause 3 of 4 — UpdateItem: an empty TableName must mask the other field errors, and is reported with the wrong member path and an interpolated value.
AWS: Smithy: UpdateItem.TableName targets TableArn, @required, @length 1..1024; UpdateItem.ReturnValues targets the ReturnValue enum. When an empty-string TableName is submitted together with an out-of-set ReturnValues, AWS emits exactly ONE clause: "1 validation error detected: Value at 'TableName' failed to satisfy constraint: Member must have length greater than or equal to 1". Fixed text of the class: "<n> validation error(s) detected: Value at '<member path>' failed to satisfy constraint: Member must have length greater than or equal to <min>"; variable parts are the violation count, the API-cased member path and the minimum from the @length trait. Two rules are requirements here: AWS names the API-cased path `TableName` and renders NO value token for it, and an unusable TableName SUPPRESSES the remaining field checks so the enum violation is not reported in the same response.
Emulator: "2 validation errors detected: Value '' at 'tableName' failed to satisfy constraint: Member must have length greater than or equal to 1; Value 'BOGUS_RV' at 'returnValues' failed to satisfy constraint: Member must satisfy enum value set: [ALL_NEW, UPDATED_OLD, ALL_OLD, NONE, UPDATED_NEW]" — wrong count, both fields reported, lower-camelled paths, and a rendered value interpolated where AWS renders none. ('BOGUS_RV' is the fixture's submitted value; the defect is the extra clause and the path/value rendering, not that literal.)
Why: the violation count, the set of reported fields and the member paths all differ from AWS, so a client cannot match the refusal or learn the single blocking field, and it is handed member names (`tableName`, `returnValues`) that do not exist in the API.
Fix: the item-write input validator for UpdateItem — short-circuit on an absent/empty TableName, and use the shared Coral message renderer's API-cased path with no value token for @length violations. The PutItem twin of this fault is cause 4 of open issue 20261120T225636Z-dynamodb-validationexception-envelope-diverges-member-paths-value-rendering.md, which does not carry UpdateItem's replay key.
Traces: dynamodb-empty-tablename-masks-invalid-returnvalues#task#6 (representative), cluster of 17 affected steps including dynamodb-update-item-table-name-pattern-violation-reported#task#1, dynamodb-legacy-attribute-updates-action-type-validation#task#4, dynamodb-update-item-validation-error-aggregation-forms#task#4.

Cause 4 of 4 — TransactWriteItems: the TransactItems constraint message does not reproduce AWS's rendering of the offending value.
AWS: Smithy: TransactWriteItems.TransactItems targets TransactWriteItemList, @required, @length 1..100. An over-cap list is refused 400 com.amazon.coral.validate#ValidationException whose message is the Coral envelope carrying the service model's own structural rendering of the submitted list: "1 validation error detected: Value '<rendered TransactItems>' at '<member path>' failed to satisfy constraint: ...", where the rendering spells out every structure member and renders every unset arm as null — `[TransactWriteItem(conditionCheck=null, put=Put(item={<attr>=AttributeValue(s=<v>, n=null, b=null, iNT=null, dECIMAL=null, dOUBLE=null, sS=null, nS=null, bS=null, iNTSET=null, dECIMALSET=null, dOUBLESET=null, m=null, l=null, nULL=null, bOOL=null)}, tableName=<table>, conditionExpression=null, expressionAttributeNames=null, expressionAttributeValues=null, returnValuesOnConditionCheckFailure=null, workloadProfileName=null), delete=null, update=null), ...]`. The REQUIREMENT is that rendering shape plus the constraint clause; the table name, attribute values and list length come from the request, never from one recording.
Emulator: 400 whose `message` is emulator-authored and does not reproduce that rendering — the replay reports `$.message: value_mismatch` for this cluster. The replay detail is truncated past the expected value, so the emulator's exact text must be re-read by replaying the step.
Why: callers that surface the refusal verbatim, and suites that pin it, see text unrelated to AWS's; the rendered value is how AWS shows WHICH transaction actions were submitted and rejected.
Fix: the TransactWriteItems input-validation message renderer (value rendering for the list member), the same renderer cause 2 of 20261120T225636Z-dynamodb-validationexception-envelope-diverges-member-paths-value-rendering.md names for BatchWriteItem — that issue does not carry the TransactWriteItems replay key.
Traces: dynamodb-batch-caps-and-unprocessed#task#12 (representative), dynamodb-transact-write-items-mixed-update-delete-member-rejected#task#5.
