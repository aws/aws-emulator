# emr__glue__s3: 3 net-new causes — an S3 Batch Operations job, a Glue job run and a Glue-job-driven EventBridge delivery never converge, so all three permission-boundary checks burn the whole harness budget

> _Note: this issue was identified against the code base at commit `c25092682df62c5e37a98aae2aa377f0a9463dd0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetJobRun

## Description
Three independent asynchronous workflows reached by the emr__glue__s3 'permission-boundary' checks never converge in the emulator. Each check polls a modeled state machine that real AWS advances within seconds; in the emulator nothing advances, so each check consumes its entire 60 s harness budget and reports `Error: Check timed out after 60.0s` without ever reaching its assertions. THIS ISSUE BUNDLES 3 CAUSES. All three must be closed.

Cause 1 of 3: an S3 Control Batch Operations job never reaches a terminal status, so a role that Batch Operations cannot assume is indistinguishable from a healthy one.
  AWS: s3control CreateJob with ConfirmationRequired=false returns a JobId and the job then advances through the modeled status machine (Smithy: com.amazonaws.s3control#JobStatus = Active, Cancelled, Cancelling, Complete, Completing, Failed, Failing, New, Paused, Pausing, Preparing, Ready, Suspended) to a TERMINAL status: Complete when the RoleArn's trust policy names batchoperations.s3.amazonaws.com and its permissions allow Operation.S3PutObjectTagging on the manifest's objects, or Failed carrying Job.FailureReasons when the role cannot be assumed (for example a role trusting only ec2.amazonaws.com), tagging nothing. Recorded behavior: the check submits one job per role and polls s3control DescribeJob until Status is one of Complete/Failed/Cancelled; the recording reaches one within the per-attempt 120 s poll.
  Emulator: DescribeJob never reports a terminal Status for either role, so the check's bounded poll (6 attempts x 120 s) never returns and the harness cuts the check at 60 s. Neither the positive outcome (Complete + the target object carrying the sim2real=tagged tag) nor the negative outcome (Failed + FailureReasons + no tag) is ever observable. Hypothesis: the job is created and parked in a non-terminal status (an earlier replay of the sibling check recorded Status 'Ready' for the whole budget) because no dispatcher moves a ConfirmationRequired=false job forward.
  Why: a client that submits a Batch Operations job and waits on it hangs forever — no bulk tagging/copy/restore side effect lands, no completion report is written, and the trust contract of the job role is never enforced, so a misconfigured role looks exactly like a working one.
  Fix: the s3control Batch Operations job runner behind CreateJob/DescribeJob (the job state machine in the s3control service state), which must advance a ConfirmationRequired=false job to Complete after applying Operation to each manifest entry, and settle Failed with FailureReasons when RoleArn cannot be assumed by batchoperations.s3.amazonaws.com.

  Traces: emr__glue__s3.s3-batch-operation-role-missing-s3-trust-rejected.

Cause 2 of 3: a Glue job run never reaches a terminal JobRunState, so the trust-principal differential on the run role never produces a verdict.
  AWS: glue StartJobRun returns a JobRunId and GetJobRun reports JobRun.JobRunState progressing through the modeled enum (Smithy: com.amazonaws.glue#JobRunState = STARTING, RUNNING, STOPPING, STOPPED, SUCCEEDED, FAILED, TIMEOUT, ERROR, WAITING, EXPIRED) to a terminal value: SUCCEEDED for a pythonshell job whose Role trusts glue.amazonaws.com (its script's s3:PutObject marker lands), and FAILED with a non-empty JobRun.ErrorMessage (Smithy: JobRun.ErrorMessage -> ErrorString, 'An error message associated with this job run') naming the role Glue cannot assume for a role trusting only ec2.amazonaws.com, with the script never executed so the marker key is absent (HeadObject answers 404). Recorded behavior: the check starts each job and polls GetJobRun to a terminal state within a calibrated ~80 s window (4x IAM's documented 20 s propagation ceiling).
  Emulator: the run never settles into a terminal JobRunState within that window — the inner poll loop keeps reading a non-terminal state and the harness cuts the check at 60 s, before either the positive control (SUCCEEDED + marker present) or the negative (FAILED + ErrorMessage + marker absent) is evaluated. Hypothesis: StartJobRun records the run but no executor advances it, or it is re-settled into a state the check must retry past (a FAILED whose ErrorMessage contains 'assume role' is retried by design until the window closes).
  Why: any client that starts a Glue job and waits for it blocks until its own timeout; the job's side effects never appear, and the run role's trust configuration is never enforced or reported, so a permanently mistrusted role cannot be told from a healthy one.
  Fix: the Glue job-run execution path behind StartJobRun/GetJobRun (the job-run state machine in the glue service state), which must run the job's Command.ScriptLocation under its Role, settle the run SUCCEEDED or FAILED, and report the trust/assume-role failure in JobRun.ErrorMessage.

  Traces: emr__glue__s3.glue-job-start-with-role-missing-glue-trust-rejected.

Cause 3 of 3: the Glue-job-run -> 'Glue Job State Change' -> EventBridge rule -> SQS target path produces nothing, so the target-permission differential never reaches a verdict.
  AWS: when a Glue job run reaches SUCCEEDED, Glue publishes an event with source 'aws.glue', detail-type 'Glue Job State Change' and detail.jobName/detail.state taken from the run; an ENABLED EventBridge rule whose EventPattern matches it delivers the event to each SQS target whose queue policy allows sqs:SendMessage for the events.amazonaws.com principal (so ReceiveMessage on that queue returns a body whose detail.jobName equals the job's name and detail.state equals 'SUCCEEDED'), and delivers nothing to an otherwise identical sibling queue with no such resource policy. Recorded behavior: the check creates the job, the rule and both queues, runs the job to SUCCEEDED (300 s poll), then polls the permitted queue for the delivery (120 s) and the unpermitted one for 60 s to assert absence.
  Emulator: the check never gets as far as the delivery assertions — it is cut at the 60 s harness budget, with neither queue inspected. Hypothesis: the budget is consumed upstream, either by glue CreateJob being retried through the check's 120 s not-yet-assumable retry loop or by the job run never reaching SUCCEEDED (Cause 2); on top of that, no 'Glue Job State Change' event is published at all, so even a settled run would leave the permitted queue empty and the positive control unprovable.
  Why: an event-driven pipeline keyed on Glue job completion never fires in the emulator, and because the permitted target receives nothing either, a client cannot distinguish 'correctly blocked by a missing queue policy' from 'the whole event path is dead' — EventBridge target-permission behavior is unverifiable.
  Fix: the Glue job-run completion hook that must publish the 'Glue Job State Change' event into the EventBridge bus, plus the EventBridge rule-matching/target-delivery path to SQS and its queue-policy authorization check (and the Glue job-run state machine named in Cause 2, which gates it).
  Related open issues (neither carries this check id; both are filed under other service tokens): 20261109T185037Z-glue-sqs-3-net-new-causes-glue-job-state-change.md and 20261110T132412Z-glue-sqs-a-cloudformation-deployed-eventbridge-rule-never.md.
  Traces: emr__glue__s3.eventbridge-rule-missing-target-permission-negative.

3. For each, call s3control CreateJob with ConfirmationRequired=false, Operation.S3PutObjectTagging(TagSet sim2real=tagged), Manifest format S3BatchOperations_CSV_20180820 and a Report, then poll s3control DescribeJob. 4. Cause 2: put a pythonshell script that writes a marker object, create two IAM roles with AWSGlueServiceRole attached differing only in trust principal (glue.amazonaws.com vs ec2.amazonaws.com), glue CreateJob for each with Command {Name: pythonshell, PythonVersion: 3.9, ScriptLocation: s3://<bucket>/scripts/<label>.py}, then StartJobRun and poll GetJobRun. Run the job to SUCCEEDED, then ReceiveMessage on both queues. Expect exactly one delivery, to the permitted queue, carrying detail.jobName and detail.state=SUCCEEDED; observe the check exhausting its budget before any delivery, with no 'Glue Job State Change' event published (replay emr__glue__s3.eventbridge-rule-missing-target-permission-negative).
