## Description
Two distinct net-new root causes on the AppSync control plane, both grounded in failing behavioral checks that the replay report marked neither ALREADY FILED nor OWNED. 2 causes in this issue; BOTH must be closed before it is submitted.

=== Cause 1 of 2: the asynchronous introspection failure detail diagnoses a disabled Data API HTTP endpoint for an RDS cluster that does not exist ===
Failing check ids: appsync.data-source-introspection-lifecycle, appsync.get-schema-status-and-association-not-found
AWS: Smithy (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/smithy-model/com-amazonaws-appsync-awsdeepdishcontrolplaneservice.json) models StartDataSourceIntrospection = POST /v1/datasources/introspections, code 200, single optional input member rdsDataApiConfig -> RdsDataApiConfig{resourceArn, secretArn, databaseName}; GetDataSourceIntrospection = GET /v1/datasources/introspections/{introspectionId}, code 200, output {introspectionId, introspectionStatus: enum DataSourceIntrospectionStatus (PROCESSING|FAILED|SUCCESS), introspectionStatusDetail: String, introspectionResult}. No trait constrains the text of introspectionStatusDetail, so for the wording this is recorded behavior only: when the job is started against a well-formed RDS cluster ARN that names no existing cluster, AWS accepts the request (introspectionStatus PROCESSING or FAILED), settles the job FAILED, and serves the fixed sentence 'RDS cluster was not found for supplied resource arn.' — the WHOLE string is fixed text, with no value interpolated from the request.
Emulator: the status part is right (200, introspectionStatus FAILED), but introspectionStatusDetail diagnoses a different condition and interpolates the request's ARN: 'HttpEndpoint is not enabled for resource <rdsDataApiConfig.resourceArn>.' Here '<resourceArn>' is a request value and 'HttpEndpoint is not enabled for resource ' / the trailing '.' are the emulator's own fixed text. Hypothesis: the job handler tests the cluster's Data API (HTTP endpoint) flag before it tests that the cluster resolves at all, so an unresolvable ARN is reported as a resolvable cluster with the Data API switched off.
Why: the detail string is the only thing that tells a client whether to correct the ARN (typo, wrong account/region, deleted cluster) or to enable the Data API on an existing cluster and retry. Against the emulator every unresolvable ARN is reported as the latter, so automation that branches on the detail takes the wrong remediation path, and a condition AWS never reports for this input becomes the default answer.
Fix: the StartDataSourceIntrospection/GetDataSourceIntrospection job handler and the introspection state it records — resolve the cluster named by rdsDataApiConfig.resourceArn first and record AWS's not-found detail sentence when no such cluster exists, keeping the HttpEndpoint detail only for a cluster that exists with the Data API disabled.

If that issue is fixed, re-replay the two check ids here to confirm.

=== Cause 2 of 2: the implicit-deny AccessDeniedException message for GetFunction/GetResolver names the resource as the GraphqlApi-ARN form instead of the operation's /v1 URI path ===
Failing check ids: appsync.unauthorized-function-resolver
AWS: Smithy models GetFunction = GET /v1/apis/{apiId}/functions/{functionId} and GetResolver = GET /v1/apis/{apiId}/types/{typeName}/resolvers/{fieldName} (both code 200; modeled errors ConcurrentModificationException 409, NotFoundException 404, UnauthorizedException 401 — AccessDeniedException is NOT in the modeled set, so for the error CODE this is recorded behavior only: AWS answers 403 AccessDeniedException for a principal with no identity-based policy granting the action). The message is the standard implicit-deny sentence. Its FIXED text is: 'User: ' … ' is not authorized to perform: appsync:' … ' on resource: ' … ' because no identity-based policy allows the appsync:' … ' action'. Its VARIABLE parts come from the request and IAM state: the caller's principal ARN, the action (the operation name), and the resource the action is evaluated against. For these sub-resource operations the resource is the operation's REST URI path hung off the service ARN prefix — arn:aws:appsync:<region>:<account>:/v1/apis/<apiId>/functions/<functionId> and arn:aws:appsync:<region>:<account>:/v1/apis/<apiId>/types/<typeName>/resolvers/<fieldName> — the leading slash and the /v1 prefix are part of it, and <region>/<account>/<apiId>/<functionId>/<typeName>/<fieldName> are the request's and state's values.
Emulator: status 403 and code AccessDeniedException are correct, but the resource segment is rendered in the api-ARN form with the sub-resource path appended and no '/v1' prefix or leading slash: '… on resource: arn:aws:appsync:<region>:<account>:apis/<apiId>/functions/<functionId> because no identity-based policy allows the appsync:GetFunction action'. Only the resource segment of the message diverges; GetResolver is refused the same way (the check stops at the GetFunction assertion, so the GetResolver message must be re-verified once GetFunction is corrected).
Why: the implicit-deny message is the only place AWS states WHICH resource the denial was evaluated against. A client or least-privilege tool that parses the resource out of the message to author the missing IAM statement derives a Resource that AWS's authorizer never evaluates, so the policy it writes does not lift the denial; any assertion or snapshot on the refusal text fails.
Fix: the AppSync authorization/error layer that renders the implicit-deny AccessDeniedException message — the resource must be derived per-operation from the action's modeled HTTP URI path (/v1/apis/{apiId}/functions/{functionId}, /v1/apis/{apiId}/types/{typeName}/resolvers/{fieldName}) hung off the arn:aws:appsync:<region>:<account>: prefix, rather than defaulting to the parent GraphqlApi ARN with the path appended.
Related open issue that does NOT own this check: 20261111T140910Z-appsync-3-net-new-causes-implicit-deny-message.md, Cause 1, is the same class of defect but scoped to Get/PutGraphqlApiEnvironmentVariables and grounded in appsync.access-denied-graphql-api; it does not carry appsync.unauthorized-function-resolver, and the function/resolver resource paths are a separate rendering. 20261025T022306Z-appsync-graphql-api-control-plane-operations-are-not.md covers a MISSING deny gate on api-level reads; here the gate fires correctly and only the message's resource is wrong.
