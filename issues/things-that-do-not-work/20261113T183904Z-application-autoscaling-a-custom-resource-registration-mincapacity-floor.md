=== Cause 1 of 1: RegisterScalableTarget with MinCapacity above a custom-resource endpoint's current capacity performs no enforcement — no endpoint PATCH and no scaling activity ===
AWS: Smithy (com.amazonaws.applicationautoscaling#AnyScaleFrontendService) — RegisterScalableTarget {ServiceNamespace (required enum, includes the `custom-resource` value), ResourceId (required, ResourceIdMaxLen1600 @length 1..1600), ScalableDimension (required enum, includes `custom-resource:ResourceType:Property`), MinCapacity/MaxCapacity (ResourceCapacity integer)} -> {ScalableTargetARN}; errors ValidationException/LimitExceededException (client, httpError 400) and ConcurrentUpdateException/InternalServiceException (server, 500). ScalableTarget documents MinCapacity as 'The minimum value to scale to in response to a scale-in activity' and carries a required RoleARN ('The ARN of an IAM role that allows Application Auto Scaling to modify the scalable target on your behalf'). DescribeScalingActivities returns ScalingActivity {ActivityId, ServiceNamespace, ResourceId, ScalableDimension, Description, Cause, StartTime, StatusCode all required; StatusMessage optional}, StatusCode from ScalingActivityStatusCode = Pending|InProgress|Successful|Overridden|Unfulfilled|Failed. The custom-resource wire contract and the activity wording are recorded behavior only: in the `custom-resource` namespace Application Auto Scaling calls the caller's own endpoint, GET and PATCH on `/scalableTargetDimensions/{id}`. When a target is registered with a MinCapacity ABOVE the capacity the endpoint currently reports, the service raises the resource to that floor as part of registration: it sends ONE PATCH whose body is exactly `{"desiredCapacity": <min>}` (the floor is the only variable part), and records exactly ONE activity that settles StatusCode `Successful` with Cause of fixed text `minimum capacity was set to ` + the registered MinCapacity, Description of fixed text `Setting desired capacity to ` + the floor + `.`, and StatusMessage of fixed text `Successfully set desired capacity to `, `. Change successfully fulfilled by `, `.` with the floor and the fulfilling namespace (`custom-resource`) as the variables. DescribeScalableTargets then reads the target back with the registered bounds and a RoleARN whose path ends in the custom-resource service-linked role name `AWSServiceRoleForApplicationAutoScaling_CustomResource`.
Emulator: registration is accepted and then nothing is enforced. The check registers MinCapacity=3/MaxCapacity=6 against a custom-resource endpoint reporting capacity 2 and then polls two things: the backing item for its capacity leaving 2.0, and DescribeScalingActivities for all activities being `Successful`. Neither predicate is ever satisfied — no PATCH arrives at the endpoint (the item keeps desired=2.0, patch count 0, no recorded body — the previous recorded run of this same check reported exactly that from the same probe) and the activity list stays EMPTY — so the in-check bounded poll never returns and the harness terminates the check: `Error: Check timed out after 60.0s`. Because the floor leg never completes, the later legs (the exact PATCH body `{"desiredCapacity": 3.0}`, the single Successful activity triple, the read-back bounds (3, 6) and the `AWSServiceRoleForApplicationAutoScaling_CustomResource` RoleARN) are never reached and must be re-replayed with the fix. Hypothesis: the registration path persists the target and returns the ARN without ever comparing the floor to the capacity read from the endpoint, so the custom-resource branch of capacity enforcement is not invoked by registration at all (the sibling `cassandra` floor now works, so the namespace-specific downstream write is what is missing, not the floor comparison in general).
Why: a client that scales a resource AWS does not model natively uses the custom-resource contract, and registering MinCapacity is how it asserts a floor. On AWS the resource is pulled up to the floor immediately and the move is auditable in DescribeScalingActivities; against the emulator the endpoint is never called and the activity history is empty, so capacity silently stays below the configured minimum, no audit record exists, and any client that waits for the floor to be applied (or for the activity to settle Successful) hangs indefinitely rather than failing.
Fix: the RegisterScalableTarget handler's enforcement step and its `custom-resource` namespace branch — on registration read the endpoint's current capacity (GET /scalableTargetDimensions/{id}), and when the registered MinCapacity exceeds it, issue the PATCH with a `{"desiredCapacity": <min>}` body and record the activity through the scaling-activity recorder with AWS's Cause/Description/StatusMessage templates, settling it `Successful`; also make the custom-resource target's RoleARN the custom-resource service-linked role.
