# lightsail: eight behavioral divergences — GUI session accepted on non-research instances, no Lightsail-for-Research catalog, RDS-style DB log stream names, unenforced load-balancer datapoint limit, and non-AWS refusal codes/messages (8 causes)

> _Note: this issue was identified against the code base at commit `e2f414c8e0d435baa8e4d1479bd7220d9eecc351`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartGUISession

## Description
Eight distinct root causes found by replaying the behavioral suite against the Lightsail emulator. All eight are in the `lightsail` service and all eight must be closed before this issue is submitted.

Related open issues that do NOT cover these (named per cause below): 20261127T163509Z-lightsail-constraint-rejections-return-validationexception-instead-of-invalidinputexception.md, 20261127T163509Z-lightsail-metric-validation-errors-carry-non-aws-error.md, 20261127T163509Z-lightsail-missing-resource-refusals-use-notfoundexception-and-precede.md, 20261126T210300Z-lightsail-published-catalogs-diverge-from-aws-wrong-blueprint.md.

=== Cause 1 of 8: a bucket that does not exist is refused with the wrong NotFoundException message template ===
AWS: Smithy: GetBucketMetricData.bucketName -> BucketName (@length 3..54, @pattern ^[a-z0-9][a-z0-9-]{1,52}[a-z0-9]$), required; errors include NotFoundException (client, httpError 404, members {code, docs, message, tip}) and InvalidInputException (400). The message text itself is recorded behavior only: a bucket name the account does not hold — never created, or already deleted — is refused with error code `NotFoundException` and message `Requested resource not found: {<bucketName>}`. Fixed text: `Requested resource not found: {` ... `}`; the only variable part is `<bucketName>`, copied verbatim from the request. The same template is what GetBuckets answers for a deleted bucket.
Emulator: refuses with code `NotFoundException` (so the code matches) but message `The Bucket does not exist: <bucketName>` — a different template, no braces, and the resource-type word "Bucket" that AWS does not use here.
Why: a client that surfaces or matches the service's own not-found text (log scrapers, user-facing error panels, tests that pin the documented message) sees text AWS never emits, and a client that parses the braced name out of the message to retry against the right bucket finds no braces to parse.
Fix: the not-found error construction shared by the bucket operations' handlers (GetBucketMetricData, GetBuckets) in the lightsail service crate's ops module — it must emit AWS's `Requested resource not found: {<name>}` template rather than a generic "The <Type> does not exist: <name>".
Note: open issue 20261127T163509Z-lightsail-missing-resource-refusals-use-notfoundexception-and-precede.md concerns GUI-session and metric handlers answering NotFoundException where AWS answers InvalidInputException; it carries no bucket operation and does not cover this template.
Traces: lightsail.bucket-metric-data-unknown-bucket-rejected.

=== Cause 2 of 8: GetBucketMetricData rejects an out-of-range period as ValidationException instead of InvalidInputException ===
AWS: Smithy: GetBucketMetricData.period -> MetricPeriod, required, @range min 60 max 86400; the operation's modelled client input error is InvalidInputException (httpError 400). A period below 60 (and above 86400) is refused with HTTP 400, error code `InvalidInputException`, message `Invalid period, must be between 60 and 86400.` — the whole message is fixed text and names no request value.
Emulator: HTTP 400 with error code `ValidationException` and the generic generated message `1 validation error detected: Value '59' at 'period' failed to satisfy constraint: Member must have value greater than or equal to 60` — an error type the operation does not model at all, and a message that leaks the member path and the raw constraint.
Why: every client branch keyed on InvalidInputException falls through to a generic unknown-error path, so a bad argument looks like an unmodelled server-side fault and no repair/retry logic fires.
Fix: GetBucketMetricData's request validation in the lightsail ops module — the modelled @range rejection must be mapped onto InvalidInputException with Lightsail's own fixed message instead of being surfaced by the generic Smithy constraint validator.
Note: open issue 20261127T163509Z-lightsail-constraint-rejections-return-validationexception-instead-of-invalidinputexception.md describes this same wire-level cause from the wire corpus; it is still open and does not carry this behavioral check's replay key, so this check is recorded here.
Traces: lightsail.bucket-metric-period-outside-range-rejected.

=== Cause 3 of 8: GetContainerServiceMetricData rejects an out-of-range period as ValidationException instead of InvalidInputException ===
AWS: Smithy: GetContainerServiceMetricData.period -> MetricPeriod, required, @range min 60 max 86400; errors include InvalidInputException (400) and NotFoundException (404). A sub-minute period is refused with HTTP 400, error code `InvalidInputException`, message `Period must be between 60 and 86400 and must be a multiple of 60` — all fixed text, no request values; note this operation's wording differs from the bucket operation's (Cause 2), so each operation's text must be reproduced per operation.
Emulator: HTTP 400 with error code `ValidationException` and message `1 validation error detected: Value '59' at 'period' failed to satisfy constraint: Member must have value greater than or equal to 60`.
Why: as Cause 2, on the container-service metric path; additionally the emulator never states the multiple-of-60 rule, so a caller that fixes only the minimum (e.g. retries with 90) is refused again without being told why.
Fix: GetContainerServiceMetricData's request validation in the lightsail ops module.
Note: GetContainerServiceMetricData is NOT among the six operations bundled in 20261127T163509Z-lightsail-constraint-rejections-...md, so that issue does not cover it.
Traces: lightsail.container-service-metric-query-out-of-contract-rejected.

=== Cause 4 of 8: GetRelationalDatabaseLogStreams reports RDS log-FILE paths instead of Lightsail log STREAM names ===
AWS: Smithy: GetRelationalDatabaseLogStreams -> GetRelationalDatabaseLogStreamsResult.logStreams (StringList); GetRelationalDatabaseLogEvents.logStreamName (required string) takes one of those values. The values themselves are recorded behavior only: a managed MySQL database publishes exactly the stream names `error`, `general`, `slowquery`, and a managed PostgreSQL database publishes exactly `postgresql`. They are bare stream names — one per log class, no directory prefix and no `.log` suffix — and a name outside the published set is refused by GetRelationalDatabaseLogEvents with InvalidInputException `Sorry, the input log stream name is not valid.`
Emulator: a MySQL database answers `['error/mysql-error-running.log', 'error/mysql-error.log', 'general/mysql-general.log', 'slowquery/mysql-slowquery.log']` and a PostgreSQL database answers `['error/postgresql.log']` — Amazon RDS's `<class>/<file>.log` log-file paths, four entries where AWS publishes three for MySQL and a prefixed path where AWS publishes `postgresql`.
Why: the published list is the input domain of GetRelationalDatabaseLogEvents. A client that lists streams and then reads one works against the emulator but is refused by AWS (`Sorry, the input log stream name is not valid.`) because it passes a path AWS does not accept; conversely a client that hardcodes AWS's documented `error`/`general`/`slowquery`/`postgresql` is refused by the emulator. Either direction breaks log collection entirely.
Fix: the relational-database log-stream catalog in the lightsail service crate's state (the per-engine stream list GetRelationalDatabaseLogStreams reports and GetRelationalDatabaseLogEvents validates against) — publish Lightsail's bare per-engine stream names, not RDS file paths.
Traces: lightsail.database-log-streams-listed-then-refused-after-delete, lightsail.database-log-events-unknown-stream-rejected, lightsail.postgres-log-events-from-head-rejected.

=== Cause 5 of 8: the GUI-session operations are ACCEPTED on a standard (non Lightsail-for-Research) instance ===
AWS: Smithy: StartGUISession / StopGUISession / CreateGUISessionAccessDetails each take resourceName -> ResourceName (required) and model InvalidInputException (400) among their errors; Blueprint.appCategory -> AppCategory (enum, sole value `LfR`) is documented "Virtual computer blueprints that are supported by Lightsail for Research... This parameter only applies to Lightsail for Research resources." GUI sessions exist only for those resources. An instance created from an ordinary OS blueprint (e.g. amazon_linux_2023) is therefore refused on all three operations with HTTP 400, error code `InvalidInputException`, message `<resourceName> isn't a Lightsail for Research resource.` — fixed text `isn't a Lightsail for Research resource.` after the one variable part, `<resourceName>` copied from the request. No operation record is created, so the refused calls never appear in GetOperationsForResource.
Emulator: all three calls answer HTTP 200 with an `operations` list, e.g. one entry with operationType `StartGUISession`, resourceType `Instance`, status `Started`, isTerminal false, against a plain amazon_linux_2023 instance. The GUI-session gate on appCategory is simply absent.
Why: this is a false SUCCESS. A client receives an operation id for a session that cannot exist and then polls it forever, or treats "GUI available" as true for every instance and offers users a DCV session on a resource AWS refuses. It also pollutes the instance's operation history with GUI operations AWS never records there.
Fix: the StartGUISession, StopGUISession and CreateGUISessionAccessDetails handlers in the lightsail ops module — each must check the target instance's blueprint appCategory before doing anything and refuse a non-LfR resource with InvalidInputException and the message above, leaving state and operation history untouched.
Traces: lightsail.gui-session-on-os-instance-rejected, lightsail.gui-session-on-standard-instance-rejected.

=== Cause 6 of 8: the Lightsail-for-Research catalog is empty, so no research computer can be created ===
AWS: Smithy: GetBlueprints and GetBundles both take appCategory -> AppCategory (enum, sole value `LfR`); Blueprint.appCategory marks the rows that belong to it. GetBlueprints(appCategory='LfR') answers a non-empty blueprint list including the Ubuntu research-desktop image `lfr_ubuntu_1_0` (type `os`, isActive true), and GetBundles(appCategory='LfR') answers a non-empty bundle list including the research plans such as `app_standard_xl_1_0` (isActive true). CreateInstances with that blueprint/bundle pair succeeds and yields a research computer on which the GUI-session operations of Cause 5 are accepted.
Emulator: GetBlueprints(appCategory='LfR') answers an empty `blueprints` list and GetBundles(appCategory='LfR') an empty `bundles` list (the unfiltered catalog still returns the 11 ordinary OS blueprints). Because the rows do not exist, CreateInstances(blueprintId='lfr_ubuntu_1_0') is refused with `NotFoundException: The specified blueprint does not exist or is deprecated: lfr_ubuntu_1_0`.
Why: the entire Lightsail for Research surface is unreachable. A client that enumerates research images to build a launch menu finds none; a deployment script that names a published research blueprint/bundle fails against the emulator only, with a not-found error for an image AWS offers. It also makes Cause 5's positive side untestable: there is no resource on which a GUI session may legitimately be started.
Fix: the published blueprint and bundle catalogs in the lightsail service crate's state (the blueprint and bundle tables GetBlueprints/GetBundles report and CreateInstances resolves) — add the Lightsail-for-Research rows with appCategory `LfR`, and make the appCategory filter select them; the same tables must resolve those ids for CreateInstances, not merely list them.
Note: open issue 20261126T210300Z-lightsail-published-catalogs-diverge-from-aws-wrong-blueprint.md covers wrong blueprint productUrl/licenseUrl values and missing memory-optimized bundle rows in the UNFILTERED catalogs; it says nothing about appCategory=LfR and does not cover this cause.
Traces: lightsail.gui-session-refused-for-standard-instance, lightsail.gui-session-research-computer-lifecycle, lightsail.research-gui-session-start-stop-operations-succeed, lightsail.gui-session-refused-on-standard-accepted-on-research-computer, lightsail.gui-session-start-stop-on-research-computer.

=== Cause 7 of 8: GetLoadBalancerMetricData does not enforce the 1,440-datapoint request limit ===
AWS: Smithy: GetLoadBalancerMetricData.period -> MetricPeriod (required, @range 60..86400) with required startTime/endTime, so the number of datapoints requested is a derived request-level rule; errors include InvalidInputException (400). A window/period combination asking for more than 1,440 datapoints is refused with HTTP 400, error code `InvalidInputException`, message `There were <n> issues found with your request. Your requested number of datapoints exceeds the limit of 1,440. Please reduce the datapoints requested by increasing Period, or decreasing the time range..` — the prefix `There were <n> issues found with your request. ` is fixed text with `<n>` the number of issues AWS found in the request, followed by one fixed sentence per issue; 1,440 is the service's fixed quota, not a value from the request (the doubled final period is AWS's own text). 1,440 periods exactly is accepted.
Emulator: a query of 1,441 one-minute periods is ACCEPTED, answering HTTP 200 `{'metricName': 'RequestCount', 'metricData': []}`. The limit is not checked at all.
Why: another false success — a client is allowed to build a query AWS rejects, so a dashboard or exporter developed against the emulator fails in production on its first wide window, and the emulator can never exercise the repair path (increase Period / shrink the range) it is supposed to teach.
Fix: GetLoadBalancerMetricData's request validation in the lightsail ops module — compute the datapoint count from startTime/endTime/period and refuse over 1,440 with the aggregated InvalidInputException message; the same handler must also accumulate issues into the `There were <n> issues ...` envelope rather than stopping at the first.
Traces: lightsail.load-balancer-metric-datapoint-limit-refused.

=== Cause 8 of 8: GetLoadBalancerMetricData's empty/unknown-statistic refusal uses the emulator's own wording ===
AWS: Smithy: GetLoadBalancerMetricData.statistics -> MetricStatisticList of MetricStatistic (enum Minimum, Maximum, Sum, Average, SampleCount), required; errors include InvalidInputException (400). An empty `statistics` list (and one naming a statistic outside the enum) is refused with HTTP 400, error code `InvalidInputException`, message `There were <n> issues found with your request. You must provide at least 1 statistic from the set Minimum, Maximum, Sum, Average, SampleCount.` — fixed `There were <n> issues found with your request. ` prefix with `<n>` the issue count, then the fixed sentence naming the modelled statistic set. No request values appear.
Emulator: HTTP 400 `InvalidInputException` (type and status match) with message `statistics must name at least one statistic of the metric to return` — its own wording, outside the aggregated envelope, and it never names the statistic set the caller may choose from.
Why: the caller cannot repair the request from the error (it is not told which statistics are legal), and a client parsing the issue count / per-issue sentences AWS guarantees on this operation finds neither.
Fix: GetLoadBalancerMetricData's statistics validation and error construction in the lightsail ops module — emit AWS's aggregated message with the modelled statistic set.
Note: open issue 20261127T163509Z-lightsail-metric-validation-errors-carry-non-aws-error.md bundles this same wording defect for GetInstanceMetricData (its Cause 4) and for start/end-window checks on GetLoadBalancerMetricData (its Cause 5); it does NOT carry the statistics rule on GetLoadBalancerMetricData, so this cause is not covered there.
Traces: lightsail.load-balancer-metric-query-mismatch-rejected.
