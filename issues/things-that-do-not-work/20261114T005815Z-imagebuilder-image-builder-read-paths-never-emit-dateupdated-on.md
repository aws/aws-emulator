# Image Builder read paths never emit dateUpdated on pipelines or distribution configurations

> _Note: this issue was identified against the code base at commit `7eb3f68345fb0e1e7b2dcd6e02146b3b6c63cb69`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetImagePipeline

## Description
This bundle carries FOUR distinct net-new root causes from the wire replay of trace set simparity-wire-aws-v1 against the emulator built from this checkout. All FOUR must be closed before this issue is submitted. The shared fault: the Image Builder resource projections the read paths serve never carry the `dateUpdated` mutation timestamp — neither the ImagePipeline view (GetImagePipeline, ListImagePipelines) nor the DistributionConfiguration view (GetDistributionConfiguration) — so a client can never see when a resource was last modified, and on the update path the whole mutation is invisible. Every other diverging cluster in this replay is already owned by an open issue that carries its replay key, or is blocked by a filed stub, so only these four are filed.

Adjacent open issues that do NOT carry these four replay keys and therefore do not cover these causes: 20261105T162014Z-imagebuilder-image-builder-distribution-configuration-validation-deletion-and-update.md (its cause 6 covers GetDistributionConfiguration's missing distributions[1] under the replay key `GetDistributionConfiguration|2xx->2xx|$.distributionConfiguration.distributions[*]`, and its cause 7 covers GetImagePipeline's extra consecutiveFailures, but neither key covers the `dateUpdated` omission that makes clusters 3 and 4 below diverge today), 20261103T104956Z-imagebuilder-4-net-new-wire-divergences-on-image.md (image-pipeline create/read and GetComponent output; carries no dateUpdated key), 20261106T010945Z-imagebuilder-updatedistributionconfiguration-stub.md and 20261107T064925Z-imagebuilder-listimagepipelines-stub.md (both merely stand a stub up and state no output-shape requirement).

Cause 1 of 4: GetImagePipeline omits imagePipeline.dateUpdated. Fixture imagebuilder-create-image-pipeline-rejects-a-test-timeout-above-1440-minutes, step task#9.
AWS: Smithy (imagebuilder, GET /GetImagePipeline, success 200) returns output member `imagePipeline` targeting structure ImagePipeline, whose member `dateUpdated` targets DateTime and is documented "The date on which this image pipeline was last updated." (smithy_query shape="ImagePipeline" on services/service-com-amazonaws-imagebuilder-imagebuilder/smithy-model/com-amazonaws-imagebuilder-imagebuilder.json). Recorded behavior: the 200 body carries imagePipeline.dateUpdated as an ISO-8601 DateTime on a pipeline that has only ever been created — AWS sets it at creation time alongside dateCreated and re-stamps it on every subsequent mutation. The fixture asserts the member's presence and shape, not a value: the value is a per-run clock reading and is not part of the requirement.
Emulator: the member is absent from the 200 body (status and every other asserted imagePipeline member match).
Why: a client cannot tell when a pipeline last changed. Reconciliation loops that compare dateUpdated against their own last-seen stamp to decide whether to re-read see None and either re-sync on every poll or never notice a change, and a strict decoder that treats the modeled timestamp as present fails to deserialize the pipeline at all.
Fix: the ImagePipeline projection the read paths share — `crate::state::image_pipeline_view` in the imagebuilder service crate's state module (called from ops/get_image_pipeline.rs) must populate dateUpdated from the pipeline's stored last-modified instant, defaulting to its creation instant for a pipeline that has never been updated.
Traces: imagebuilder-create-image-pipeline-rejects-a-test-timeout-above-1440-minutes#task#9 (cluster also covers imagebuilder-ibp-traj-poll-before-start-and-start-mistakes#task#14); projection call site services/service-com-amazonaws-imagebuilder-imagebuilder/src/ops/get_image_pipeline.rs lines 176-196.

Cause 2 of 4: ListImagePipelines omits dateUpdated on every listed pipeline. Fixture imagebuilder-ibp-traj-pipeline-create-mistakes, step task#14.
AWS: Smithy (imagebuilder, POST /ListImagePipelines, success 200) returns `imagePipelineList` -> ImagePipelineList of the same ImagePipeline structure, so each listed element carries the same dateUpdated member as the single-resource read; the list view and the get view are the same projection in AWS. Recorded behavior: the 200 body's imagePipelineList[0] carries dateUpdated as a DateTime (presence and shape asserted, value not).
Emulator: imagePipelineList[0].dateUpdated is absent; the rest of the listed pipeline matches.
Why: a client that lists pipelines to pick the most recently changed one, or that caches a list and diffs timestamps, has no timestamp to compare, so it either re-fetches every pipeline individually or silently treats all of them as unchanged.
Fix: the same shared ImagePipeline projection used by the ListImagePipelines handler — populate dateUpdated there rather than in one operation's serializer, so the get and list views cannot drift apart.
Traces: imagebuilder-ibp-traj-pipeline-create-mistakes#task#14.

Cause 3 of 4: on a pipeline that has never run, GetImagePipeline both omits dateUpdated and emits consecutiveFailures. Fixture imagebuilder-image-pipeline-round-trips-its-three-configurations-before-any-run, step task#9.
AWS: Smithy: ImagePipeline.dateUpdated (DateTime) is populated as in cause 1; ImagePipeline.consecutiveFailures targets ConsecutiveFailures (integer, @range min 0), the count Image Builder tracks for SCHEDULED executions. Recorded behavior: for a pipeline created and read before any run, the imagePipeline object carries dateUpdated and OMITS consecutiveFailures entirely — absent means "nothing has been tracked yet", which is distinguishable from a tracked count of 0.
Emulator: dateUpdated is absent and consecutiveFailures is present with value 0 — exactly inverted on both members.
Why: a client reading this pipeline sees a resource that has apparently never been modified but has a tracked execution-failure counter, i.e. it reads "has run, zero consecutive failures" where AWS says "never ran". Round-trip comparisons of the pipeline object fail on both the missing and the extra key.
Fix: the same ImagePipeline projection — set dateUpdated, and leave consecutiveFailures unset until a scheduled execution has actually been tracked. (The consecutiveFailures half is described as cause 7 of 20261105T162014Z-imagebuilder-image-builder-distribution-configuration-validation-deletion-and-update.md, but that issue's replay keys do not cover this cluster, which diverges on dateUpdated as well and is reported unowned; closing only the extra member leaves this step failing.)
Traces: imagebuilder-image-pipeline-round-trips-its-three-configurations-before-any-run#task#9.

Cause 4 of 4: after UpdateDistributionConfiguration, GetDistributionConfiguration returns neither the updated distributions list nor a dateUpdated stamp. Fixture imagebuilder-update-distribution-configuration-persists-new-region, step task#4.
AWS: Smithy (imagebuilder, PUT /UpdateDistributionConfiguration, success 200) takes `distributions` -> DistributionList (required) and replaces the stored list with it; GET /GetDistributionConfiguration then returns structure DistributionConfiguration, whose `distributions` member holds every entry of the new list and whose `dateUpdated` member (DateTime) is documented "The date on which this distribution configuration was last updated." Recorded behavior: after an update that appends a second target Region, the 200 body's distributions has two entries — the added one carrying its region and its amiDistributionConfiguration.name — and dateUpdated is re-stamped to the time of that update. The recorded ISO-8601 instant is a per-run clock reading and only the member's presence and its "last mutation time" meaning are the requirement.
Emulator: distributions[1] is absent (only the original single-Region entry is returned) and dateUpdated is absent — the update is wholly invisible to the following read.
Why: a client is told the update succeeded, then reads back the pre-update configuration with no timestamp movement to hint otherwise; it believes the second-Region distribution is configured when the emulator's state still holds the original list, and image distribution later targets one Region instead of two.
Fix: the UpdateDistributionConfiguration handler's state write (replace the stored distributions list and re-stamp the resource's last-modified instant) and the DistributionConfiguration projection GetDistributionConfiguration serves (emit dateUpdated). Note UpdateDistributionConfiguration is still an unimplemented scaffold stub in this checkout (services/service-com-amazonaws-imagebuilder-imagebuilder/src/ops/update_distribution_configuration.rs), so standing it up is a prerequisite; the dateUpdated omission on the read side is independent of it and must be fixed in the projection. (The distributions[1] half is cause 6 of 20261105T162014Z-...-validation-deletion-and-update.md; that issue carries no dateUpdated key, so this cluster is reported unowned and is not closed by it.)
Traces: imagebuilder-update-distribution-configuration-persists-new-region#task#4.
