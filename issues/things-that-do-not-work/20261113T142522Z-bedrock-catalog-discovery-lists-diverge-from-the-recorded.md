# bedrock catalog discovery lists diverge from the recorded AWS catalog: ListFoundationModels and ListInferenceProfiles (2 causes)

> _Note: this issue was identified against the code base at commit `8519584554abb240da771f66a4fe7c47c54f612d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListFoundationModels

## Description
This issue bundles 2 net-new causes that share one fault: the static catalogs the emulator seeds for Bedrock's two read-only discovery lists (GET /foundation-models and GET /inference-profiles) are not the catalogs AWS serves, neither in which entries are present/ordered nor in the per-entry projection. Both steps answer 200, so a client sees a well-formed but wrong catalog.

Cause 1 of 2 — ListFoundationModels: catalog membership and per-model summary projection (fixture bedrock-catalog-list-foundation-models, step task#1).
AWS: Smithy ListFoundationModels -> http {GET, /foundation-models}, code 200, output ListFoundationModelsResponse.modelSummaries: FoundationModelSummaryList; errors AccessDeniedException 403 / InternalServerException 500 / ThrottlingException 429 / ValidationException 400; readonly. Smithy FoundationModelSummary models only modelArn (required), modelId (required), modelName, providerName, inputModalities, outputModalities, responseStreamingSupported, customizationsSupported, inferenceTypesSupported, modelLifecycle. The other members the recording carries — converse (maxTokensDefault, maxTokensMaximum, stopSequencesDefault, reasoningSupported.embedded, additionalRequestFieldsSchema, userImageTypesSupported, userDocumentTypesSupported, userVideoTypesSupported), featuresSupported (batchInference, provisionedThroughput, promptCaching, promptOptimization, countTokens, intelligentPromptRouting), batchSupported (baseModelSupported, customModelSupported, crossRegionSupported), explicitPromptCaching, intelligentPromptRouting, guardrailsSupported, inferenceAPIsSupported, latencyOptimizationSupported, modelFamily, description, modelLifecycle.startOfLifeTime — are NOT in the checked-in model, so for those this is recorded behavior only and the recorded 200 body is the authority. The recording shows AWS (a) listing catalog entries the emulator does not serve, (b) typing featuresSupported.batchInference as a STRUCTURE {"crossRegion": <bool>, "inRegion": <bool>} rather than a bare boolean, (c) populating converse metadata for every listed model, and (d) ordering converse.userImageTypesSupported as ["jpeg", "png"] while omitting converse.userDocumentTypesSupported entirely for models that accept no documents.
Emulator: answers 200 with a different body. For modelId "openai.gpt-6-astra" it omits converse.additionalRequestFieldsSchema, converse.maxTokensMaximum and converse.reasoningSupported.embedded; it adds a 9-element converse.userDocumentTypesSupported list where AWS returns none; it orders converse.userImageTypesSupported png,jpeg instead of jpeg,png; and it serializes featuresSupported.batchInference as the boolean false where AWS returns the {crossRegion, inRegion} structure (type_mismatch). The same classes of diff repeat across the catalog: whole $.modelSummaries[modelId=...] entries the recording carries are absent or replaced (among them ai21.jamba-1-5-mini-v1:0, amazon.nova-canvas-v1:0, amazon.titan-image-generator-v1, amazon.titan-image-generator-v1:0, amazon.titan-text-lite-v1, amazon.titan-text-lite-v1:0:4k, amazon.titan-text-premier-v1:0, anthropic.claude-3-5-sonnet-20240620-v1:0, anthropic.claude-3-5-sonnet-20241022-v2:0, anthropic.claude-3-haiku-20240307-v1:0, anthropic.claude-3-sonnet-20240229-v1:0); converse is wholly missing for the sonic/lite/micro entries; and modelFamily, description, inferenceAPIsSupported, guardrailsSupported, latencyOptimizationSupported, explicitPromptCaching, intelligentPromptRouting, batchSupported.*, featuresSupported.* and the modelLifecycle.* instants diverge per model.
Why: ListFoundationModels is the discovery call a Bedrock client makes before it invokes anything. A client that reads featuresSupported.batchInference as the modelled structure gets a JSON type error (boolean where an object is expected) and fails to deserialize the entire list; a client that filters on inferenceTypesSupported / outputModalities / modelLifecycle selects the wrong model or finds none; a client that reads converse.maxTokensMaximum or converse.additionalRequestFieldsSchema to build a Converse request has no value and either drops required inference config or sends fields the model refuses. The failure shows up as a parse error or an empty model list, not as a recognisable service error.
Fix: the bedrock foundation-model catalog seed/state that backs ListFoundationModels plus the FoundationModelSummary serializer — align catalog membership with the recording, emit featuresSupported.batchInference as a {crossRegion, inRegion} structure, populate converse metadata for every catalogued model, omit converse.userDocumentTypesSupported for models that take no documents, and preserve AWS's member order in the converse.user*TypesSupported lists. Note: the open issue 20261108T085833Z-bedrock-listfoundationmodels-catalog-diverges-from-aws-for-newly.md (and the older 20261102T055258Z / 20261106T204258Z ListFoundationModels issues) describe this same operation, but this replay reports the cluster as UNOWNED — no open issue carries its replay key — and the diverging set still includes every path listed here, so it is filed again and should be reconciled with them.
Traces: bedrock-catalog-list-foundation-models#task#1 (expected 200 / actual 200, body mismatch).

Cause 2 of 2 — ListInferenceProfiles: the SYSTEM_DEFINED inference-profile catalog does not match AWS's (fixture bedrock-catalog-list-inference-profiles, step task#1).
AWS: Smithy ListInferenceProfiles -> http {GET, /inference-profiles}, code 200, output ListInferenceProfilesResponse.inferenceProfileSummaries: InferenceProfileSummaries + nextToken; paginated {inputToken nextToken, outputToken nextToken, pageSize maxResults, items inferenceProfileSummaries}; readonly. Smithy InferenceProfileSummary requires inferenceProfileName, inferenceProfileArn, models, inferenceProfileId, status and type, and models description, createdAt and updatedAt (both date-time). Which profiles the account-level catalog contains is recorded behavior only: the recording returns a full page of 93 SYSTEM_DEFINED cross-region profiles, including the Meta Llama 3.2 routing profiles (e.g. inferenceProfileId us.meta.llama3-2-11b-instruct-v1:0 / us.meta.llama3-2-90b-instruct-v1:0, each with a models list of per-region foundation-model ARNs, status ACTIVE, type SYSTEM_DEFINED and matching createdAt/updatedAt date-time instants), and a toolboxArn member that is null for system-defined profiles.
Emulator: answers 200 but its seeded profile list only agrees with the recording for the first two entries; every summary from $.inferenceProfileSummaries[2] through [92] fails to match, i.e. the whole remainder of the page. At index 2 the recording has the US Meta Llama 3.2 11B Instruct profile while the emulator serves the US Anthropic Claude 3.5 Sonnet profile, and at index 3 the recording has US Meta Llama 3.2 90B Instruct — so the catalog the emulator seeds contains a different set of profiles and/or presents them in a different order, and it omits the toolboxArn member the recording carries.
Why: inference profiles are how a client addresses cross-region inference: it lists them and then passes an inferenceProfileId/ARN as the modelId on Converse or InvokeModel. If the profile the client needs is not in the listing it cannot route cross-region at all, and if the listing is ordered differently a client that indexes or page-slices the result (maxResults/nextToken) picks a profile that routes to models it did not ask for — all while the call reports success.
Fix: the bedrock inference-profile catalog seed/state behind ListInferenceProfiles (and the InferenceProfileSummary projection): seed the system-defined profile set and ordering the recording shows, and serialize the full summary including toolboxArn.
Traces: bedrock-catalog-list-inference-profiles#task#1 (expected 200 / actual 200, body mismatch).
