# lambda: durable execution is unusable end to end — the bundled Python SDK, the invoke event, checkpoint validation, the callback plane and execution history all diverge (10 causes)

> _Note: this issue was identified against the code base at commit `35f7de95e926ecd075d4f0c5efe73729faf5e0c1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendDurableExecutionCheckpoint

## Description
Ten net-new root causes in Lambda durable execution. Open issues 20261107T135301Z-lambda-9-net-new-root-causes-in-durable.md, 20261027T203721Z-lambda-a-durable-execution-is-accepted-but-never-runs.md and 20261114T170500Z-lambda-durable-execution-callback-plane-never-fires.md describe neighbouring problems and carry none of the replay keys below.

Cause 1 of 10: the Python runtime's bundled `aws_durable_execution_sdk_python` is missing names a durable handler must import.
AWS: the managed python runtime ships the durable SDK with `InvokeConfig` and `CallbackConfig` in `aws_durable_execution_sdk_python.config` and an `aws_durable_execution_sdk_python.exceptions` module.
Emulator: the handler fails at import — `Unable to import module 'app': cannot import name 'InvokeConfig' from 'aws_durable_execution_sdk_python.config' (unknown location)`, the same for `CallbackConfig`, and `No module named 'aws_durable_execution_sdk_python.exceptions'`; the execution then ends FAILED with ErrorType Runtime.ImportModuleError.
Why: any durable workflow written against the published SDK cannot start, so the behavior the client is testing is replaced by an import error.
Fix: the durable SDK bundled into the python runtime layer of the invoke sandbox.
Traces: lambda.checkpoint-durable-execution-chained-invoke-tenant-id-pattern-rejected, lambda.durable-callback-heartbeat-lapse-records-callback-timed-out-event, lambda.durable-chained-invoke-of-a-timed-out-durable-target-reports-timed-out.

Cause 2 of 10: the durable invoke event delivered to the handler omits `DurableExecutionArn`.
AWS: a durable invocation's event carries the execution's `DurableExecutionArn`, which the handler (and the SDK) uses to checkpoint.
Emulator: the key is absent, so every durable handler raises `KeyError: 'DurableExecutionArn'` and the execution ends FAILED with `{'ErrorMessage': "'DurableExecutionArn'", 'ErrorType': 'KeyError'}`.
Why: no durable handler can checkpoint, wait, cancel a wait, or chain — the whole feature is inert from inside the function.
Fix: the durable invoke event construction in the invoke path that hands the payload to the runtime.
Traces: lambda.checkpoint-durable-execution-malformed-token-rejected, lambda.checkpoint-durable-execution-parent-id-over-length-rejected, lambda.checkpoint-durable-execution-token-length-bounds-rejected, lambda.checkpoint-durable-execution-unknown-operation-type-rejected, lambda.checkpoint-repeated-client-token-has-one-effect, lambda.durable-checkpoint-after-execution-failed-rejected, lambda.durable-wait-cancel-checkpoint-records-wait-cancelled, lambda.durable-wait-cancel-checkpoint-records-wait-cancelled-without-its-error, lambda.durable-stopping-a-chained-child-records-chained-invoke-stopped.

Cause 3 of 10: the invocation context has no `run_in_child_context`.
AWS: the durable LambdaContext exposes `run_in_child_context`, so a handler can run a child context and catch its failure.
Emulator: the handler raises `AttributeError: 'LambdaContext' object has no attribute 'run_in_child_context'` and the execution ends FAILED where it must have succeeded.
Why: child-context composition — the way failures are contained inside a durable workflow — is unavailable.
Fix: the LambdaContext object the python runtime builds for durable invocations.
Traces: lambda.durable-history-reports-failed-child-context-error.

Cause 4 of 10: SendDurableExecutionCheckpoint does not range-validate OperationUpdate options and refuses CALLBACK updates outright.
AWS: option values outside their modelled ranges are refused 400 ValidationException with `1 validation error detected: Value '<value>' at '<memberPath>' failed to satisfy constraint: Member must have value less than or equal to <max>` — recorded paths and maxima: `updates.<n>.member.callbackOptions.timeoutSeconds` ≤ 99999999, `updates.<n>.member.callbackOptions.heartbeatTimeoutSeconds` ≤ 99999999, `updates.<n>.member.stepOptions.nextAttemptDelaySeconds` ≤ 31622400; an Action outside the enum is refused against the set recorded for `updates.<n>.member.action`.
Emulator: answers InvalidParameterValueException with prose of its own — `A callback's id is generated by the DurableContext when a durable function calls ctx.waitForCallback, and an OperationUpdate carries none, so a checkpoint update of operation type CALLBACK is not supported by this emulator: ...` — or `Invalid checkpoint token`, and for WaitSeconds 0 answers `Invalid checkpoint token` rather than the range refusal.
Why: the client gets neither the error class nor the member path, so it cannot tell which option it got wrong; and a whole operation type (CALLBACK) is refused with emulator-specific prose that no AWS client handles.
Fix: OperationUpdate option validation and CALLBACK support in the SendDurableExecutionCheckpoint handler (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/send_durable_execution_checkpoint.rs).
Traces: lambda.durable-checkpoint-callback-timeout-over-max-rejected, lambda.durable-checkpoint-heartbeat-timeout-above-max-rejected, lambda.durable-checkpoint-step-retry-delay-above-max-rejected, lambda.checkpoint-durable-execution-wait-seconds-outside-range-rejected, lambda.checkpoint-durable-execution-unknown-update-action-rejected.

Cause 5 of 10: malformed checkpoint identifiers are reported as a missing execution instead of a validation failure.
AWS: an over-long DurableExecutionArn, an 8192-character trace header and a malformed chained function name are refused by request validation before any execution lookup.
Emulator: resolves them and answers InvalidParameterValueException `Durable execution not found: <arn>` — i.e. a lookup failure for a request that never should have been looked up.
Why: a client cannot distinguish 'my identifier is malformed' from 'the execution is gone', so it retries against an ARN that can never resolve.
Fix: identifier validation ahead of resolution in the SendDurableExecutionCheckpoint handler.
Traces: lambda.checkpoint-durable-execution-arn-over-1024-chars-rejected, lambda.checkpoint-chained-invoke-trace-id-over-8192-characters-rejected, lambda.checkpoint-durable-execution-malformed-chained-function-name-rejected.

Cause 6 of 10: the callback plane's refusals and its size limit are wrong.
AWS: SendDurableExecutionCallbackSuccess/Failure with a CallbackId Lambda never issued, with an over-long CallbackId, or for a callback of a deleted function is refused with AWS's own callback refusal; a callback failure whose Error object exceeds one MiB is refused; and a callback sent after the execution was stopped is refused.
Emulator: answers ResourceNotFoundException `Callback not found: <id>` (echoing the opaque id back) for all three not-found variants, accepts the over-one-MiB error object (answering `{}`), and on the after-stop path the execution ends FAILED with `{'ErrorMessage': 'the JSON object must be str, bytes or bytearray, not dict', 'ErrorType': 'TypeError'}` — an internal type error, not a refusal.
Why: a client that distinguishes a stale callback from an unknown one cannot; and an oversize callback payload is accepted here and refused in production.
Fix: the SendDurableExecutionCallbackSuccess / SendDurableExecutionCallbackFailure handlers — refusal selection, the one-MiB Error bound, and the after-stop state check.
Traces: lambda.callback-success-with-unissued-callback-id-rejected, lambda.durable-callback-failure-callback-id-over-1024-chars-rejected, lambda.durable-callback-failure-after-function-deleted-rejected, lambda.durable-callback-failure-error-object-over-one-mib-rejected, lambda.durable-callback-after-stop-rejected.

Cause 7 of 10: execution history records the wrong events for chained invokes, stops and callbacks.
AWS: a chained invoke whose child times out records a timed-out outcome; stopping a chained child records ChainedInvokeStopped; ExecutionStopped names the execution and carries the caller's error payload; a failed callback records CallbackFailed and a lapsed heartbeat records CallbackTimedOut with its error type.
Emulator: records `['ChainedInvokeStarted', 'ChainedInvokeFailed']` for the timed-out child; `ExecutionStopped` names None and carries no caller error; and the callback events never appear — the checks time out waiting for the execution to open its callback (`timed out after 30s until the execution opens its callback; last=None`).
Why: the history is the only durable audit trail; a client replaying it to resume or to report sees a failure where AWS reports a timeout, and cannot find the stop reason at all.
Fix: event emission in the durable execution state machine (chained-invoke outcome classification, StopDurableExecution's history write, and the callback lifecycle events).
Traces: lambda.durable-chained-invoke-child-execution-timeout-reports-timed-out, lambda.durable-chained-invoke-of-a-stopped-target-reports-stopped, lambda.chained-invoke-of-stopped-execution-records-stop-error, lambda.durable-stop-during-wait-records-caller-error, lambda.stop-durable-execution-error-payload-reaches-history, lambda.durable-callback-closed-by-failure-rejects-a-late-success, lambda.durable-callback-failure-is-recorded-as-callback-failed-in-history, lambda.durable-history-reports-callback-timeout-error-type.

Cause 8 of 10: the pagination-marker refusal message is not AWS's.
AWS: a Marker the service never issued is refused 400 InvalidParameterValueException with the message `Invalid Marker`.
Emulator: answers `Invalid marker value from user.`
Why: a client that keys its 'restart the listing' path on the message never matches.
Fix: the marker-validation message in the durable history/list handlers (and the shared marker validator they use).
Traces: lambda.durable-history-marker-not-issued-rejected, lambda.durable-history-unissued-marker-rejected.

Cause 9 of 10: ListDurableExecutions' status filter has the wrong enum set and does not reject multiple statuses.
AWS: the `statuses` filter accepts exactly one status, and an off-enum value is refused 400 ValidationException with `1 validation error detected: Value '[<value>]' at 'statuses' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [SUCCEEDED, TIMED_OUT, DELETING, STOPPED, PAUSED, PAUSING, FAILED, RUNNING], Member must not be null]`.
Emulator: offers only `[RUNNING, SUCCEEDED, FAILED, TIMED_OUT, STOPPED]` (DELETING, PAUSED and PAUSING are missing, and the order differs) and accepts a request carrying several statuses, answering 200 with a DurableExecutions list.
Why: a client filtering for PAUSED/DELETING executions is refused for a legal value, and a multi-status filter silently returns unfiltered results.
Fix: the status enum and arity validation in the ListDurableExecutions handler.
Traces: lambda.durable-list-unknown-status-filter-rejected, lambda.list-durable-executions-multiple-statuses-rejected.

Cause 10 of 10: durable invoke and read preconditions are missing, and the timeout/name-conflict messages are wrong.
AWS: a synchronous durable invoke with ExecutionTimeout over 30 minutes is refused, and so is one past the account execution limit; InvokeWithResponseStream against a durable function is refused; GetDurableExecution for an ARN in a foreign partition is refused and for a non-durable function is refused on the function, not on the execution; a non-durable function never returns a DurableExecutionArn; an execution past its timeout ends TIMED_OUT carrying `{'errorMessage': 'Execution timed out after <N> seconds.'}`; reusing a closed execution name with a different payload is refused with `Execution already started: <arn>`; StopDurableExecution on an unknown but well-formed name is refused with AWS's own not-found sentence.
Emulator: accepts all of them — the over-timeout and over-limit sync invokes answer 200 with a DurableExecutionArn header, InvokeWithResponseStream on a durable function answers 200 with an event stream, the foreign-partition GetDurableExecution answers 200 with the execution, a non-durable function returns a DurableExecutionArn, the timed-out execution reports `Error None` or the sandbox's `{'errorType': 'Sandbox.Timedout', 'errorMessage': 'RequestId: <id> Error: Task timed out after 10.00 seconds'}` instead of the durable timeout message, the closed-name reuse message is not `Execution already started: <arn>`, and Stop answers ResourceNotFoundException `Durable execution not found: <arn>`.
Why: a client gets durable executions AWS would refuse, reads executions from other partitions, and sees sandbox timeout text where AWS reports a durable execution timeout — so retry, resume and alerting logic all misfire.
Fix: the durable preconditions and message templates in the Invoke/InvokeWithResponseStream, GetDurableExecution, ListDurableExecutions and StopDurableExecution handlers and in the durable execution state machine's timeout path.
Traces: lambda.durable-sync-invoke-execution-timeout-over-30-minutes-rejected, lambda.durable-sync-invoke-over-execution-limit-rejected, lambda.durable-function-response-stream-invoke-rejected, lambda.get-durable-execution-arn-in-a-foreign-partition-rejected, lambda.get-durable-execution-under-a-non-durable-function-rejected, lambda.non-durable-function-runs-every-invoke-despite-reused-execution-name, lambda.durable-execution-past-its-timeout-ends-timed-out-with-its-timeout-message, lambda.durable-sync-invoke-past-execution-timeout-reports-function-error, lambda.durable-closed-execution-name-with-other-payload-rejected, lambda.stop-durable-execution-name-past-64-chars-rejected, lambda.stop-durable-execution-unknown-execution-rejected.
