# athena: 4 net-new causes — disabling a workgroup kills an already-admitted RUNNING query, and three terminal-failure texts (CTAS partition order, Parquet incompatible type, Parquet narrowing) are emulator-authored

> _Note: this issue was identified against the code base at commit `92bb40e21becebccd15ea15fe975333e26f54e48`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartQueryExecution

## Description
Four net-new root causes in the Athena query-execution plane, reached through StartQueryExecution / GetQueryExecution / UpdateWorkGroup. All four surfaced on behavioral checks that the suite reported as neither ALREADY FILED nor OWNED by any open issue. There are 4 causes; each must be closed separately before this issue is submitted.

=== Cause 1 of 4: UpdateWorkGroup State=DISABLED kills a query the workgroup had already admitted ===
AWS: Smithy (services/service-com-amazonaws-athena-amazonathena/smithy-model/com-amazonaws-athena-amazonathena.json) models UpdateWorkGroupInput.State as enum WorkGroupState ENABLED|DISABLED ("The workgroup state that will be updated for the given workgroup"). The DISABLED state governs ADMISSION only: new StartQueryExecution calls into that workgroup are refused with InvalidRequestException and the message `WorkGroup <workGroupName> is disabled.` (fixed text `WorkGroup ` + the workgroup name from the request + ` is disabled.`), while an execution already in QUEUED/RUNNING in that workgroup keeps running and settles on its own merits — for a well-formed statement, Status.State SUCCEEDED (Smithy: QueryExecutionState QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED; the doc notes CANCELLED means "a user input interrupted query execution", which a workgroup state change is not), with its full correct result set and with Statistics.DataScannedInBytes accounting every byte the plan read. Recorded behavior only for the per-run byte totals.
Emulator: the refusal half is correct (InvalidRequestException with AWS's exact message), but the in-flight query is destroyed by the state change: the self-join that read RUNNING immediately before `UpdateWorkGroup(WorkGroup=<wg>, State='DISABLED')` settles Status.State FAILED with Status.StateChangeReason `interrupted` — an emulator-authored one-word reason that is not any Athena failure text — and therefore yields no result set and no scan statistics. Re-enabling the workgroup afterwards does restore admission, so only the in-flight execution is affected.
Why: disabling a workgroup is the documented operator action for stopping NEW work (cost control, maintenance, incident response) precisely because it does not disturb work in progress. Against the emulator any long-running query in that workgroup is silently failed the instant the state changes, so a client that disables a workgroup loses in-flight results it keeps on AWS, and its retry/alerting logic sees a FAILED execution with a reason (`interrupted`) it cannot classify against any documented Athena error.
Fix: the workgroup-state update path in the Athena service crate (services/service-com-amazonaws-athena-amazonathena — the UpdateWorkGroup handler and the query-execution state it mutates). Disabling a workgroup must gate ADMISSION of new executions only; executions already in a non-terminal state must be left to run to their own terminal state, with their result set and Statistics intact.
Traces: athena.disabled-workgroup-preserves-running-query-and-rejects-new-start-rejected.

=== Cause 2 of 4: a CTAS whose partition key is not the last column fails with the wrong error code and a re-worded message ===
AWS: StartQueryExecution accepts the statement and the rejection is the asynchronous terminal state (Status.State FAILED). The failure text is the Hive layout-rule error, with Status.StateChangeReason and Status.AthenaError.ErrorMessage identical: `HIVE_COLUMN_ORDER_MISMATCH: Partition keys must be the last columns in the table and in the same order as the table properties: [<partition keys>]. You may need to manually clean the data at location '<OutputLocation>tables/<QueryExecutionId>' before retrying. Athena will not delete data in your account.` Fixed text: the `HIVE_COLUMN_ORDER_MISMATCH: ` code prefix, `Partition keys must be the last columns in the table and in the same order as the table properties: `, `. You may need to manually clean the data at location '`, `' before retrying. Athena will not delete data in your account.`. Variable parts, taken from the request and from the emulator's own state: the partition-key list from the statement's `partitioned_by` property, and the staging location derived from the request's ResultConfiguration.OutputLocation plus `tables/` plus the query id this call minted. Envelope (Smithy AthenaError): ErrorCategory 2 (User — doc: 1=System, 2=User, 3=Other, @range 1-3), ErrorType 1002 (@range 0-9999), Retryable false (default false); recorded behavior only for the exact ErrorType integer.
Emulator: the state is FAILED, but the reason is an emulator-authored sentence under a different error code: `INVALID_TABLE_PROPERTY: Partition keys must be the last columns in the table and in the same order as the table property 'partitioned_by': [<partition keys>]`. The code is INVALID_TABLE_PROPERTY instead of HIVE_COLUMN_ORDER_MISMATCH, the rule clause says `the table property 'partitioned_by'` instead of `the table properties`, and the whole clean-up sentence naming the staged data under `<OutputLocation>tables/<query id>` is missing, so the customer is never told where the FAILED CTAS left bytes Athena will not delete.
Why: Athena error codes are the contract clients classify failures by (docs, runbooks, retry rules and the Athena error-reference tables all key on the HIVE_* code). A client that matches HIVE_COLUMN_ORDER_MISMATCH never recognises this failure, and because the clean-up sentence is dropped, orphaned staged objects under the output location are never reported and accumulate silently.
Fix: the CTAS validation/failure-text construction in the Athena query-execution engine of services/service-com-amazonaws-athena-amazonathena (the StartQueryExecution statement path that detects the partition-column-order violation, and the component that fills QueryExecutionStatus.StateChangeReason plus the AthenaError envelope).
Traces: athena.ctas-partition-key-not-last-column-rejected.

=== Cause 3 of 4: the Parquet incompatible-type failure text drops Athena's `Malformed Parquet file.` prefix and the trailing `[s3://<bucket>/<key>]` locator ===
AWS: reading a Parquet column through a declaration whose type contradicts the file's physical type settles FAILED with Status.StateChangeReason = `HIVE_BAD_DATA: Malformed Parquet file. Field <field>'s type <PHYSICAL PARQUET TYPE> in parquet file s3://<bucket>/<key> is incompatible with type <declared type> defined in table schema [s3://<bucket>/<key>]`. Fixed text: `HIVE_BAD_DATA: Malformed Parquet file. Field `, `'s type `, ` in parquet file `, ` is incompatible with type `, ` defined in table schema `, and the bracketed repetition of the object URI. Variable parts: the field, its physical Parquet type (BINARY, INT32, ...), the declared catalog type (integer, varchar, ...) and the S3 URI of whichever file under the table location the reader failed on. Envelope: AthenaError.ErrorCategory 2 (User), ErrorType 1002, Retryable false; Smithy models StateChangeReason as free-form String, so the text itself is recorded behavior only.
Emulator: it reaches FAILED, but the reason omits both the `Malformed Parquet file. ` sentence after the code and the trailing ` [s3://<bucket>/<key>]` locator — e.g. `HIVE_BAD_DATA: Field name's type BINARY in parquet file s3://<bucket>/<key> is incompatible with type integer defined in table schema` for a UTF-8 column declared `int`, and the same truncated shape for the INT32-vs-varchar case. Only the envelope words differ; the code and the body are otherwise right.
Why: this is the error customers are told to match when a Parquet declaration contradicts the files; tooling that recognises Athena's `HIVE_BAD_DATA: Malformed Parquet file.` form, or that parses the bracketed object URI to locate the offending file, gets neither against the emulator, so automated schema-repair and bad-file quarantine paths that work on AWS do nothing here.
Fix: the Parquet reader's incompatible-type failure-text construction in the Athena query-execution engine (services/service-com-amazonaws-athena-amazonathena), i.e. the component that builds QueryExecutionStatus.StateChangeReason / AthenaError.ErrorMessage for a HIVE_BAD_DATA read failure.
Traces: athena.schemaevo-cross-family-type-change-fails-instead-of-reinterpreting-bytes, athena.schemaevo-index-access-reorder-fails-while-name-based-reorder-resolves.

=== Cause 4 of 4: under parquet.column.index.access the HIVE_BAD_DATA text names the DECLARED column instead of the file's field at the contradicted position ===
AWS: with TBLPROPERTIES ('parquet.column.index.access'='true') the reader resolves columns by ORDINAL POSITION, so the error it raises identifies the field it actually read out of the file at that position: for files physically ordered (id INT32, name BINARY) read through a declaration reordered to (`name` string, `id` int), the reason is `HIVE_BAD_DATA: Malformed Parquet file. Field id's type INT32 in parquet file s3://<bucket>/<key> is incompatible with type varchar defined in table schema [s3://<bucket>/<key>]` — the field name comes from the FILE's schema at the contradicted ordinal, paired with that field's physical type and with the declared type at the same ordinal. Recorded behavior only for the exact text; the rule is that the named field, its physical type and the declared type all describe the same ordinal position.
Emulator: it pairs the file's physical type with the DECLARED column's name: `HIVE_BAD_DATA: Field name's type INT32 in parquet file s3://<bucket>/<key> is incompatible with type varchar defined in table schema`. `name` is the declared column at that position while INT32 is the physical type of the file's `id` field, so the message describes a column that does not exist in either schema. (The missing prefix/locator in the same string is Cause 3; this cause is the wrong field identity and must be fixed too.)
Why: under position-based resolution the field name is the only thing telling the customer WHICH file column the declaration collides with; naming the declared column instead makes the diagnosis point at the wrong column, so the schema fix a client derives from the message is wrong.
Fix: the index-access (ordinal) resolution path of the Parquet reader in the Athena query-execution engine (services/service-com-amazonaws-athena-amazonathena) — the error must be raised with the file-schema field at the failing ordinal, not with the catalog declaration's column name.
Traces: athena.schemaevo-index-access-reorder-fails-while-name-based-reorder-resolves.
