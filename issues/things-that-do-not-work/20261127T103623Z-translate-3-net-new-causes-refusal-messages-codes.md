# translate: 3 net-new causes — refusal messages/codes for StartTextTranslationJob and no HTML translation in TranslateDocument

> _Note: this issue was identified against the code base at commit `7f2f9e8fbacb5ccb6dc94ed688d25f78f8760a08`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartTextTranslationJob

## Description
Three distinct net-new defects in the translate emulator, all grounded in failing behavioral checks. None is covered by an open issue (see the cross-references under each cause).

Cause 1 of 3: StartTextTranslationJob's UnsupportedLanguagePairException message omits the INVALID_REQUEST prefix.
AWS: Smithy (services/service-com-amazonaws-translate-awsshinefrontendservice-20170701) models StartTextTranslationJob error UnsupportedLanguagePairException, errorKind=client, httpError=400 ("Amazon Translate does not support translation from the language of the source text into the requested target language"). Recorded behavior: the batch submission naming an unsupported target among TargetLanguageCodes is refused HTTP 400 / UnsupportedLanguagePairException with the message `INVALID_REQUEST: Unsupported language pair: <SourceLanguageCode> to <unsupported target code>.` The fixed text is `INVALID_REQUEST: Unsupported language pair: ` + ` to ` + the trailing `.`; the two variable parts are the request's SourceLanguageCode and the offending entry of TargetLanguageCodes (en and zz in the recording — those values fill the template, they are not part of it).
Emulator: same status and same error code, but the message is `Unsupported language pair: en to zz.` — the `INVALID_REQUEST: ` prefix the batch (asynchronous job) refusal carries is missing.
Why: a client that parses or matches on the refusal text (or logs/propagates it) sees a message AWS never emits for this class; the INVALID_REQUEST prefix is the marker callers use to distinguish batch-plane input rejections, so parity-sensitive clients and test fixtures diverge.
Fix: the shared refusal constructor for this class used by the batch job handler — crate::state::unsupported_language_pair as invoked from the StartTextTranslationJob handler's unsupported_pair helper (see Traces for file/line). The synchronous TranslateText/TranslateDocument wording must not be changed by the fix: only the batch submission path takes the INVALID_REQUEST prefix.
Traces: check translate.start-text-translation-job-unknown-target-language-rejected. Relevant code: services/service-com-amazonaws-translate-awsshinefrontendservice-20170701/src/ops/start_text_translation_job.rs lines 251-261 (pair validation) and 490-497 (unsupported_pair helper).

Cause 2 of 3: StartTextTranslationJob refuses two TerminologyNames with the wrong error shape and wrong message.
AWS: Smithy models both InvalidRequestException (client, httpError 400) and InvalidParameterValueException (client, httpError 400) for StartTextTranslationJob; the model's TerminologyNames doc states "This parameter accepts only one custom terminology resource." Recorded behavior: a submission carrying two terminology names is refused HTTP 400 with error code InvalidRequestException and the message `INVALID_REQUEST: The provided input has multiple Custom Terminologies. Only 1 Custom Terminology can be used in a job.` — that text is entirely fixed for this class (no values from the request appear in it).
Emulator: refuses with error code InvalidParameterValueException and the message `The value of the parameter TerminologyNames is not valid: a batch translation job applies at most 1 custom terminology resource. Review the value of the parameter you are using to correct it, and then retry your operation.` The refusal happens (so the job is correctly not created) but both the modeled error type and the message are wrong.
Why: the error code is part of the contract — botocore surfaces it as Error.Code and SDK users catch translate.exceptions.InvalidRequestException. A client with a retry/branch on InvalidRequestException does not catch the emulator's InvalidParameterValueException at all, and generic error handling reports a different failure class to the caller.
Fix: the TerminologyNames arity validation in the StartTextTranslationJob handler must raise the modeled InvalidRequestException with the INVALID_REQUEST-prefixed fixed text instead of routing through the generic invalid_parameter_value constructor.
Traces: check translate.start-translation-job-rejects-two-terminologies. Relevant code: services/service-com-amazonaws-translate-awsshinefrontendservice-20170701/src/ops/start_text_translation_job.rs lines 289-300 (MAX_TERMINOLOGIES_PER_TRANSLATION check) and 481-488 (invalid_parameter helper).

Cause 3 of 3: TranslateDocument with ContentType text/html returns the source HTML unchanged apart from a synthetic marker, so neither the surrounding text is translated nor is translate="no" honoured.
AWS: Smithy models TranslateDocument with required output TranslatedDocument ("The document format matches the source document format") and echoes SourceLanguageCode/TargetLanguageCode. AWS documents HTML tag handling (customizing-translations-tags): for an HTML input document the markup is preserved and the text content of elements is translated, except that the text inside an element carrying translate="no" is returned verbatim; an identical span WITHOUT the attribute is translated like the rest. Recorded behavior: the response document keeps the html/body/p/span structure, the translate="no" span still holds the source phrase verbatim, and the text before and after it is replaced by its translation (so the source words outside the span no longer appear).
Emulator: the response document is the request bytes with a synthetic `[mt:<source>-><target>] ` marker inserted into the first text node and nothing translated — `<html><body><p>[mt:en->de] Every summer we walk across <span translate="no">the old wooden bridge</span> to the village market.</p></body></html>`. Text outside the protected span is untouched, and because nothing is translated the translate="no" distinction is not implemented either: the unmarked span comes back holding the source phrase too.
Why: a client translating HTML gets back source-language content with an injected marker in its markup. Content pipelines that render the result publish untranslated text containing a non-HTML-meaningful `[mt:...]` token, and any client depending on translate="no" protection cannot observe the difference between protected and unprotected content.
Why / scope note: this is NOT covered by open issue 20261103T181229Z-translate-translatedocument-does-not-translate-the-response-document-is.md, which is grounded in the plain-text round trip; this cause is the text/html document path, including the markup-preserving transform and translate="no" handling, and must be closed on the HTML check as well. It is also distinct from 20261029T192448Z (TranslateText) and 20261029T184304Z (success payload ARNs).
Fix: the document transform behind the TranslateDocument handler — the shared synthetic translation in crate::state applied per text node for text/html, plus the handler's content-type dispatch; the marker must not be injected into the document and the translate="no" subtree must be excluded from the transform.
Traces: check translate.translate-document-html-do-not-translate-span-kept-verbatim. Relevant code: services/service-com-amazonaws-translate-awsshinefrontendservice-20170701/src/ops/translate_document.rs and services/service-com-amazonaws-translate-awsshinefrontendservice-20170701/src/state.rs (shared transform).

## Evidence
Cause 1 — expected ('UnsupportedLanguagePairException', 'INVALID_REQUEST: Unsupported language pair: en to zz.') with HTTP 400; got ('UnsupportedLanguagePairException', 'Unsupported language pair: en to zz.'). Only the INVALID_REQUEST prefix differs; en/zz are the request's SourceLanguageCode and the offending TargetLanguageCodes entry.

Cause 2 — expected ('InvalidRequestException', 'INVALID_REQUEST: The provided input has multiple Custom Terminologies. Only 1 Custom Terminology can be used in a job.'); got ('InvalidParameterValueException', 'The value of the parameter TerminologyNames is not valid: a batch translation job applies at most 1 custom terminology resource. Review the value of the parameter you are using to correct it, and then retry your operation.'). The positive control (one terminology) is accepted and no job is created under the refused name, so only the error type and wording diverge.

Cause 3 — expected: the translated HTML keeps html/body/p/span, the translate="no" span holds 'the old wooden bridge' verbatim, and the source words outside it ('Every summer', 'village market') are gone, replaced by German; the same span without translate="no" holds a translation. Got: '<html><body><p>[mt:en->de] Every summer we walk across <span translate="no">the old wooden bridge</span> to the village market.</p></body></html>' — assertion 'text outside the protected span should be translated' failed.
