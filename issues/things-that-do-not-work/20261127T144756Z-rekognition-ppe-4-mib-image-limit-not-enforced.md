# Rekognition: PPE 4 MiB image limit not enforced, StartFaceDetection/Video refusal messages wrong, token-reuse message is "Service Unavailable", and GetLabelDetection reports no labels or VideoMetadata (4 causes)

> _Note: this issue was identified against the code base at commit `fc909f682d274824e0181cbb84eb6914c2fe111f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DetectProtectiveEquipment

## Description
Four distinct net-new root causes in the emulated Rekognition service, each grounded in a failing behavioral check. None is covered by an open issue: the open rekognition issues cover DetectModerationLabels/ListProjectPolicies stubs, DetectLabels on still images (20261121T045409Z-…, 20261127T000000Z-…, 20261127T065852Z-…) and celebrity recognition (20261125T185721Z-…), all of which are different operations/paths from the four below.

=== Cause 1 of 4: DetectProtectiveEquipment accepts inline image bytes above the 4 MiB PPE limit ===
AWS: DetectProtectiveEquipment analyses an image of at most 4 MiB of raw bytes — smaller than the 5 MiB the model's ImageBlob @length allows for the generic image surface (Smithy: DetectProtectiveEquipment.Image required, errors include ImageTooLargeException, httpError 400; ImageTooLargeException docs: "The input image size exceeds the allowed limit. If you are calling DetectProtectiveEquipment, the image size or resolution exceeds the allowed limit"). Recorded behavior: an image of exactly 4 MiB is analysed (HTTP 200), and one byte more is refused with HTTP 400, error code ImageTooLargeException and the message "Image size is too large" (entirely fixed text — it interpolates nothing from the request). Past the 5 MiB member limit the request fails member validation instead, with ValidationException and the standard constraint sentence "1 validation error detected: Value at 'image.bytes' failed to satisfy constraint: Member must have length less than or equal to <ImageBlob max>" (fixed text with the member path and the modelled limit as its variable parts).
Emulator: the 4 MiB+1 image is ACCEPTED — HTTP 200 with {"ProtectiveEquipmentModelVersion": "1.0", "Persons": []} — so no ImageTooLargeException is ever raised on this path.
Why: a client that sizes or downsamples images against the documented PPE limit sees the emulator accept an image real Rekognition rejects, so its too-large handling (resize/retry/report) is never exercised and ships untested; the operation also silently reports "no persons" for input AWS refuses outright.
Fix: DetectProtectiveEquipment's validation — the operation-specific byte ceiling is missing from the shared image-source size check that this handler's TooLarge mapping depends on; the handler already has the mapping, only the per-operation limit is absent.
Traces: rekognition.detect-protective-equipment-image-bytes-over-4-mib-rejected-too-large. (services/service-com-amazonaws-rekognition-rekognitionservice/src/ops/detect_protective_equipment.rs:236-246 calls the shared reader; services/.../src/state/image_source.rs:30-36 bounds only an S3 read at 15 MiB and relies on the model's 5 MiB ImageBlob constraint, so no 4 MiB ceiling exists.)

=== Cause 2 of 4: StartFaceDetection refuses an incomplete Video with the generic parameter sentence instead of the per-condition messages ===
AWS: StartFaceDetection takes a required Video whose S3Object, Bucket and Name are each modelled optional, so an incomplete reference reaches the service and is refused with HTTP 400 InvalidParameterException (Smithy: StartFaceDetection.Video required; errors include InvalidParameterException and InvalidS3ObjectException). Recorded behavior shows one message per condition, each pure fixed text interpolating nothing from the request: a Video with no S3Object -> "S3 location of input video file not specified."; an S3Object with Name but no Bucket -> "The bucket name parameter must be specified when requesting an object's metadata"; an S3Object with Bucket but no Name -> "The key parameter must be specified when requesting an object's metadata" — all three under error code InvalidParameterException.
Emulator: the Video-without-S3Object call answers code InvalidParameterException with the service-wide generic message "Request has invalid parameters"; the missing-Bucket and missing-Name conditions are additionally mapped to a different error CLASS, InvalidS3ObjectException with "Unable to get object metadata from S3. Check object key, region and/or access permissions.", so neither the code nor the message matches.
Why: the message and code are the only things that tell a client WHICH half of the video reference it failed to send; collapsing three conditions onto one generic sentence (and two of them onto the wrong exception class) makes a caller's error branching and its user-facing diagnostics diverge from AWS, and code-based retry logic treats a malformed request as an S3 access problem.
Fix: StartFaceDetection's input validation / the shared stored-video source that resolves a Video for the whole Start… family — it needs a wording per condition and the InvalidParameterException class for a reference that is merely incomplete.
Traces: rekognition.start-face-detection-without-bucket-or-key-rejected-invalid-parameter. (services/.../src/ops/start_face_detection.rs:249-258 maps NoObject to InvalidParameterException and Unreadable to InvalidS3ObjectException; services/.../src/state/video_source.rs:50-59 words NoObject with the generic INVALID_PARAMETERS_MESSAGE and 108-113 routes a missing Bucket/Name into Unreadable.)

=== Cause 3 of 4: IdempotentParameterMismatchException of the stored-video Start… family carries the message "Service Unavailable" ===
AWS: reusing a ClientRequestToken with changed parameters on a stored-video start is refused with HTTP 400, error code IdempotentParameterMismatchException (Smithy: StartLabelDetection is @idempotent, ClientRequestToken @length 1-64 @pattern ^[a-zA-Z0-9-_]+$, errors include IdempotentParameterMismatchException). Recorded behavior: the message is the sentence that QUOTES the reused token — fixed text "The ClientRequestToken: '" + the token taken verbatim from the request + "' you have supplied is already in use." An identical repeat with the same token is not an error at all: it answers the first JobId.
Emulator: the code is right but the message is the constant "Service Unavailable" for every operation that takes a token, so the token-in-use sentence (and the token it must quote) is never emitted.
Why: "Service Unavailable" reads as a transient server condition; a client that logs or surfaces the message, or that matches on it to distinguish "token reused with different parameters" from a throttle/outage, will retry or alarm instead of correcting the mismatched parameter, and it never learns which token collided.
Fix: the shared modelled-error wording for the idempotency refusal (one wording per family, not one for the whole service) — the Start… video family must word it with the reused token interpolated.
Traces: rekognition.start-label-detection-reused-token-changed-confidence-rejected. (services/.../src/state/modeled_error.rs:262-268 pins IDEMPOTENT_PARAMETER_MISMATCH_MESSAGE = "Service Unavailable" for every caller.)

=== Cause 4 of 4: GetLabelDetection reports a SUCCEEDED job with an empty Labels list and no VideoMetadata/LabelModelVersion ===
AWS: "GetLabelDetection returns an array of detected labels (Labels) sorted by the time the labels were detected" (operation documentation; Smithy: GetLabelDetection output Labels: LabelDetections, VideoMetadata, LabelModelVersion, JobStatus: VideoJobStatus, paginated by NextToken/MaxResults). Recorded behavior: a job started on a real stored H.264 MP4 reaches JobStatus SUCCEEDED and its Labels list is non-empty, and VideoMetadata reports the clip's own measured Codec, FrameWidth, FrameHeight, FrameRate and DurationMillis.
Emulator: the job reaches SUCCEEDED but Labels is always the empty list, and VideoMetadata and LabelModelVersion are omitted entirely — the handler hard-codes an empty result vector because no decoder runs in the process.
Why: a SUCCEEDED job with zero labels is indistinguishable from "the video genuinely contains nothing", so any client that counts, filters, thresholds or paginates video label results — and any client that reads the clip's dimensions/duration back out of VideoMetadata — gets a wrong answer with a success status rather than an error it could handle. This is the video-job analogue of the still-image gaps already filed as 20261127T000000Z-rekognition-detectlabels-names-no-real-world-entity-of-a-photograph.md, but on a different operation pair (StartLabelDetection/GetLabelDetection), so it is not covered by that issue.
Fix: the StartLabelDetection job's result state and GetLabelDetection's serializer — the job must carry detected labels and the measured video metadata for the object it was started on.
Traces: rekognition.start-label-detection-job-reaches-terminal-state. (services/.../src/ops/get_label_detection.rs:249-285 sets `let detected: Vec<LabelDetection> = Vec::new();` and leaves video_metadata/label_model_version None.)

## Evidence
Cause 1 — expected (recorded AWS): one byte over 4 MiB -> HTTP 400, ("ImageTooLargeException", "Image size is too large"). Actual (emulator): HTTP 200, body {'ProtectiveEquipmentModelVersion': '1.0', 'Persons': []}; suite assertion: "the request was expected to be refused but was accepted".

Cause 2 — expected: StartFaceDetection(Video={}) -> ("InvalidParameterException", "S3 location of input video file not specified."); Video={'S3Object':{'Name':k}} -> ("InvalidParameterException", "The bucket name parameter must be specified when requesting an object's metadata"); Video={'S3Object':{'Bucket':b}} -> ("InvalidParameterException", "The key parameter must be specified when requesting an object's metadata"). Actual: Video={} -> ('InvalidParameterException', 'Request has invalid parameters') (suite: "a Video without S3Object answered ('InvalidParameterException', 'Request has invalid parameters')"); the other two conditions are mapped in the handler to InvalidS3ObjectException with "Unable to get object metadata from S3. Check object key, region and/or access permissions."

Cause 3 — expected: code IdempotentParameterMismatchException with message starting "The ClientRequestToken: '" and ending "' you have supplied is already in use.", the quoted value being the token the request sent. Actual: code IdempotentParameterMismatchException, message 'Service Unavailable'; suite assertion: "the mismatch message 'Service Unavailable' is not the token-in-use sentence".

Cause 4 — expected: GetLabelDetection on a SUCCEEDED job over a real stored MP4 -> len(Labels) >= 1, plus VideoMetadata with the clip's Codec/FrameWidth/FrameHeight/FrameRate/DurationMillis. Actual: JobStatus SUCCEEDED, Labels == [] (suite assertion: "expected at least one detected label, got []"), VideoMetadata and LabelModelVersion absent.
