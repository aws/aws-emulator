# AppFlow CancelFlowExecutions refusal paths diverge from AWS

> _Note: this issue was identified against the code base at commit `62b8fd1bee90f6a3c328782ecbef66ab1ccab400`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelFlowExecutions

## Description
Every refusal/edge path of AppFlow CancelFlowExecutions answers differently from AWS. The shared fault is the handler's result-and-refusal construction in services/service-com-amazonaws-appflow-sandstoneconfigurationservicelambda/src/ops/cancel_flow_executions.rs: it always emits an explicit (possibly empty) invalidExecutions list, it lets the generic Smithy constraint layer answer before the flow lookup runs, and it reuses another operation's not-found prose. 5 causes.

Cause 1 of 5: the success body always carries an explicit empty invalidExecutions list where AWS returns an empty document. AWS: Smithy CancelFlowExecutions -> CancelFlowExecutionsResponse, whose only modeled member is invalidExecutions (ExecutionIds, @length min 0 max 100), httpError-free success code 200. Recorded behavior only for the serialization rule: when a cancel-all request has no run it failed to cancel, AWS answers 200 with the body {} - the member is omitted entirely, not sent as []. Emulator: 200 with {"invalidExecutions": []}; the handler unconditionally builds Some(invalid_executions) (cancel_flow_executions.rs, the Ok(...) at the end of handle), so the empty vector is serialized as a present empty list. Why: a client that distinguishes "field absent" from "field present but empty" - the AWS SDKs' hasInvalidExecutions()/presence checks, and any assertion on the raw response document - sees a member AWS never sends; code that branches on presence takes the "some runs could not be cancelled" path on a fully successful cancel-all. Fix: the CancelFlowExecutions handler's output construction (or the response serializer's empty-list handling) must leave invalidExecutions unset when nothing was reported back. Traces: appflow-cancel-flow-executions-refusals#task#6.

Cause 2 of 5: a batch of named, unknown execution ids is rejected with 400 instead of being classified and returned with 200. AWS: Smithy CancelFlowExecutions.executionIds targets ExecutionIds (list of ExecutionId, @length min 0 max 100, member @pattern ^\S+$) and is OPTIONAL; the documented contract is that runs the request named and the flow could not cancel "come back in invalidExecutions" rather than failing the call. Recorded behavior only for the batch itself: AWS answers 200 and returns validExecutions: [] plus every unknown run id in invalidExecutions (and an invalidExecutionsWithContext entry per id - members this crate's model predates), i.e. an unknown or ineligible run id is DATA in the response, never a request-level error. Emulator: 400 for the whole request; none of validExecutions/invalidExecutions/invalidExecutionsWithContext is produced. Hypothesis: the generated executionIds @length max-100 check is applied at the boundary with an exclusive comparison (an inclusive modeled max enforced as "must be fewer than max"), so a full-size batch is refused before the handler's per-id classification loop ever runs. Why: the only supported way to cancel a known set of runs is to send their ids; a client that sends a full batch, or one containing ids that have already finished, gets a hard 400 and cannot tell which runs were cancelled and which were not - the per-run classification AWS guarantees is unavailable, and a retry loop keyed on invalidExecutions never terminates. Fix: the CancelFlowExecutions input validation (the executionIds list-length bound) and the handler's per-id classification path, which must answer 200 with each unnameable run reported back. Traces: appflow-cancel-flow-executions-refusals#task#7, appflow-cancel-flow-executions-refusals#task#11.

Cause 3 of 5: a flowName that violates the modeled pattern is answered with a 400 ValidationException instead of the 404 not-found AWS returns. AWS: Smithy CancelFlowExecutions.flowName is @required, targets FlowName (@length min 0 max 256, @pattern ^[a-zA-Z0-9][\w!@#.-]+$); modeled errors include ResourceNotFoundException (httpError 404, "The resource specified in the request (such as the source or destination connector profile) is not found.") and ValidationException (httpError 400). Recorded behavior: AWS does NOT front-validate flowName against that pattern on this operation - a name that cannot match it (here one with a leading '-') is simply looked up, not found, and refused with 404 ResourceNotFoundException whose message has the fixed text "No Flow Definition with flow name found: " followed by the flowName taken verbatim from the request (the flow name is the only variable part). Emulator: 400 with x-amzn-errortype: ValidationException and the generic constraint message "1 validation error detected: Value '<flowName>' at 'flowName' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9][\w!@#.-]+". Why: the status class flips from 404 to 400, so a client's not-found branch (delete-if-exists, poll-until-gone, idempotent teardown) sees an unretryable validation failure for a flow that merely does not exist, and error-shape dispatch on ResourceNotFoundException never fires. Fix: CancelFlowExecutions input validation must not enforce the flowName @pattern ahead of the handler's store lookup; the lookup-miss branch owns this response. Traces: appflow-cancel-flow-executions-refusals#task#8.

Cause 4 of 5: a request body with no flowName is refused with the generic Smithy constraint message and error type instead of AWS's missing-member message. AWS: flowName is @required on CancelFlowExecutionsRequest. Recorded behavior: AWS's AppFlow REST-JSON front door refuses a body that omits it with 400 and the message "Missing flowName in request body" - that text is entirely FIXED (no values from the request or state are interpolated: it names the member, not a value) - and with an x-amzn-errortype whose shape is NOT the ValidationException the emulator sends. Emulator: 400 with x-amzn-errortype: ValidationException and the constraint-violation template "1 validation error detected: Value null at 'flowName' failed to satisfy constraint: Member must not be null". Why: the message and error type both differ, so a client matching AWS's missing-parameter wording, or dispatching on the recorded error type, treats a malformed request as an unclassified failure; it is also the reply a malformed-request regression test asserts on. Fix: the CancelFlowExecutions request-deserialization/required-member path - a missing required member must produce AppFlow's missing-member refusal rather than the shared constraint-violation formatter. Traces: appflow-cancel-flow-executions-refusals#task#9, appflow-cancel-flow-executions-refusals#task#10.

Cause 5 of 5: the not-found message reuses DescribeFlow's sentence instead of this operation's. AWS: ResourceNotFoundException (httpError 404) is modeled for CancelFlowExecutions. Recorded behavior only for the text: when the named flow does not exist, AWS answers 404 with the fixed text "No Flow Definition with flow name found: " followed by the request's flowName - the flow name is the only variable part. Emulator: correct 404 and shape, but message "There is no flow with the name <flowName>", produced by the shared helper crate::state::no_such_flow called from the handler's lookup-miss branch (cancel_flow_executions.rs, the store.flows.get_mut(...).ok_or_else(...) arm). That wording is DescribeFlow's AWS sentence, which the open issue 20261029T192701Z-appflow-error-message-text-diverges-from-aws-wording.md establishes for DescribeFlow; neither that issue nor any other open AppFlow issue covers CancelFlowExecutions, so the per-operation message is still wrong here. Why: clients and tests that match AppFlow's cancel-path not-found sentence (or parse the flow name out of its documented position after the colon) do not recognise the error; status and code being right makes the divergence silent. Fix: the CancelFlowExecutions handler's lookup-miss branch needs its own message template rather than the shared DescribeFlow-shaped helper. Traces: appflow-cancel-flow-executions-refusals#task#13.
