# rds reference-catalog reads regress: orderable-option rows drop modeled members and the Aurora cluster engine-default parameter set is wrong

> _Note: this issue was identified against the code base at commit `7f12483397bb96822437e9db6c30e833880315b6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeOrderableDBInstanceOptions

## Description
RDS's STATIC reference-catalog reads still do not serve AWS's published catalog. Every affected step answers HTTP 200, so no client ever sees an error — it silently reads reference rows whose member set and values are authored by the emulator. 4 causes in this bundle: three clusters of DescribeOrderableDBInstanceOptions (each a separately recorded cluster that must be re-replayed on its own) and one of DescribeEngineDefaultClusterParameters.

This is a REGRESSION of ground previously covered: issue 20261119T221450Z-rds-static-catalog-reads-serve-emulator-authored-rows.md is RESOLVED, yet the same two operations diverge again on the same fixtures, and a resolved issue never covers a live failure. The open RDS catalog issues 20261114T091417Z-rds-6-of-the-9-reference-catalog-causes-remain-open.md and 20261126T074046Z-rds-reserved-offering-and-db-parameter-catalog-reads.md are about other operations (parameter/major-version/option catalogs, reserved offerings, DescribeDBParameters) and carry none of the replay keys below, so they do not cover this finding either.

Cause 1 of 4: DescribeOrderableDBInstanceOptions option rows omit modeled OrderableDBInstanceOption members (fixture rds-catalog-describe-orderable-db-instance-options-db-c6gd-12xlarge-db-r5d-4xlarge, step task#1; 7 steps in this cluster).
AWS: Smithy: DescribeOrderableDBInstanceOptions(Engine required) -> OrderableDBInstanceOptionsMessage{OrderableDBInstanceOptions: list<OrderableDBInstanceOption>, Marker}; @paginated items=OrderableDBInstanceOptions. OrderableDBInstanceOption models OutpostCapable, MinStorageSize, MaxStorageSize, MinIopsPerDbInstance, MaxIopsPerDbInstance, MinIopsPerGib, MaxIopsPerGib, MinStorageThroughputPerDbInstance, MaxStorageThroughputPerDbInstance, SupportsKerberosAuthentication, SupportsStorageAutoscaling, SupportsGlobalDatabases, SupportsClusters, SupportsHttpEndpoint, SupportsDedicatedLogVolume, SupportsAdditionalStorageVolumes, SupportedNetworkTypes, SupportedActivityStreamModes and AvailableProcessorFeatures in addition to the identity members. The concrete per-class values are recorded behavior only (the model states no values): the recording shows AWS populating EVERY one of those members on EVERY row of the result.
Emulator: each row carries only a subset — identity members (Engine, EngineVersion, DBInstanceClass, LicenseModel, AvailabilityZones), MultiAZCapable, ReadReplicaCapable, Vpc, SupportsStorageEncryption, StorageType, SupportsIops, SupportsStorageThroughput, SupportsEnhancedMonitoring, SupportsIAMDatabaseAuthentication, SupportsPerformanceInsights, SupportsOptimizedReads/Writes and RequiresCustomProcessorFeatures — and omits the storage-size bounds, the IOPS and storage-throughput bounds, OutpostCapable, SupportsClusters, SupportsGlobalDatabases, SupportsHttpEndpoint, SupportsKerberosAuthentication, SupportsStorageAutoscaling, SupportsDedicatedLogVolume, SupportsAdditionalStorageVolumes, SupportedNetworkTypes, SupportedActivityStreamModes and AvailableProcessorFeatures. The replay reports the whole row as 'missing' at the matching index.
Why: a client that sizes storage from the catalog (MinStorageSize/MaxStorageSize), provisions IOPS or throughput within the advertised bounds, or decides Outposts / Multi-AZ-cluster / global-database / Kerberos / dedicated-log-volume / IPv6 eligibility reads an absent member and either faults on the null or concludes the capability does not exist, then picks an instance class RDS would reject.
Fix: the DescribeOrderableDBInstanceOptions handler's backing catalog table and its row serializer in the rds crate — every modeled OrderableDBInstanceOption member must be emitted per (engine, engine version, instance class, storage type) row.
Traces: rds-catalog-describe-orderable-db-instance-options-db-c6gd-12xlarge-db-r5d-4xlarge#task#1 (keys OrderableDBInstanceOption[1], [2], [3]).

Cause 2 of 4: the same read over the db.m5 slice ALSO reports the wrong optimized-writes capability (same fixture, step task#9; 48 steps in this cluster).
AWS: recorded behavior only — for mysql 8.4.9 / db.m5.12xlarge / gp2, AWS reports SupportsOptimizedWrites 'false' (the class does not support RDS Optimized Writes) along with the full member set named in Cause 1.
Emulator: serves SupportsOptimizedWrites 'true' for that class and again omits the Cause-1 members, so the row diverges both in membership and in a capability boolean the emulator does emit.
Why: a client that enables Optimized Writes because the catalog advertised it gets a CreateDBInstance refusal from real RDS, and a capability matrix built from this catalog is wrong per instance family rather than merely incomplete.
Fix: same catalog table — the per-instance-class capability flags must come from the published catalog, not from a name/size-derived rule.
Traces: rds-catalog-describe-orderable-db-instance-options-db-c6gd-12xlarge-db-r5d-4xlarge#task#9 (keys OrderableDBInstanceOption[0]..[3]).

Cause 3 of 4: the same read over the db.r5 slice (same fixture, step task#127; 7 steps in this cluster).
AWS: recorded behavior only — the mysql 8.4.9 / db.r5.12xlarge / gp2 row carries OutpostCapable 'true', MinStorageSize '5', MaxStorageSize '65536', SupportsClusters 'false', SupportsGlobalDatabases 'false', SupportsHttpEndpoint 'false', SupportsKerberosAuthentication 'true', SupportsStorageAutoscaling 'true', SupportsDedicatedLogVolume 'false', SupportsAdditionalStorageVolumes 'false', SupportedNetworkTypes [IPV4, DUAL], and empty SupportedActivityStreamModes / AvailableProcessorFeatures lists.
Emulator: omits all of those; here SupportsOptimizedWrites happens to agree ('true'), which shows the divergence is the per-row member SET and not just the capability booleans of Cause 2. Recorded as its own cluster, so it needs its own re-replay.
Why: as Cause 1 — the row a client reads for this family is structurally short of AWS's.
Fix: same catalog table and serializer.
Traces: rds-catalog-describe-orderable-db-instance-options-db-c6gd-12xlarge-db-r5d-4xlarge#task#127 (key OrderableDBInstanceOption[0]).

Cause 4 of 4: DescribeEngineDefaultClusterParameters serves the wrong parameter set for the aurora-mysql5.7 family (fixture rds-db-parameter-group-lifecycle-and-engine-defaults, step task#11).
AWS: Smithy: DescribeEngineDefaultClusterParameters(DBParameterGroupFamily required) -> DescribeEngineDefaultClusterParametersResult{EngineDefaults}; EngineDefaults{DBParameterGroupFamily, Marker, Parameters: list<Parameter>}; @paginated outputToken=EngineDefaults.Marker, items=EngineDefaults.Parameters. Parameter models ParameterName, ParameterValue, Description, Source, ApplyType, DataType, AllowedValues, IsModifiable, MinimumEngineVersion, ApplyMethod, SupportedEngineModes. The concrete rows are recorded behavior only: the recording returns the Aurora CLUSTER-level default set with AWS's own published Description text per parameter — e.g. aurora_enable_repl_bin_log_filtering with 'Enable filtering of replication records that are unusable by Aurora replicas on the master.', the aurora_binlog_read_buffer_size/aurora_binlog_use_large_read_buffer pair with their published texts, and the binlog-dump yield parameter whose description states the 2.04.5-2.04.8 / 2.05-2.08.* maximum of 45 and its dependency on aurora_binlog_use_large_read_buffer.
Emulator: answers 200 with a DIFFERENT parameter set at the same indices — Parameter[3].ParameterName is 'aurora_disable_hash_join' where the recording has 'aurora_enable_repl_bin_log_filtering', and the Description values are the emulator's own paraphrases ('Maximum number of seconds the binlog dump thread waits for the current binlog file to be filled with transactions before yielding to other threads.', 'When this switch is ON, the master dump thread reads from the binlog with a buffer of aurora_binlog_read_buffer_size bytes.', 'Turns off the hash join optimization for the DB cluster.'). The divergence key lists Parameter[1] through Parameter[19] with ParameterName, ParameterValue, Description, Source, ApplyType, DataType, AllowedValues, MinimumEngineVersion and SupportedEngineModes.member diverging, i.e. the whole served page is the wrong set, not a few fields.
Why: a client that enumerates the Aurora cluster engine defaults and then builds a ModifyDBClusterParameterGroup from them targets parameters that are not in the family (and misses the ones that are), and an operator console shows parameter text, allowed ranges and minimum engine versions that are not AWS's — so a value accepted here is rejected by real Aurora.
Fix: the DescribeEngineDefaultClusterParameters handler and its backing engine-default catalog in the rds crate — the aurora-mysql5.7 CLUSTER default set with each parameter's published ParameterName/Description/ApplyType/DataType/AllowedValues/MinimumEngineVersion/Source.
Traces: rds-db-parameter-group-lifecycle-and-engine-defaults#task#11.
