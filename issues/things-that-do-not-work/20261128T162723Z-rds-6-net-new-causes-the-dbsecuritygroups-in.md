# rds: 6 net-new causes — the DBSecurityGroups-in-VPC and AZ-not-covered refusals are re-worded, the unsupported-engine backup-replication refusal names the wrong fault condition, StartExportTask judges the KMS key before resolving the source and never validates ExportOnly table names, and published DB endpoint host names resolve to nothing

> _Note: this issue was identified against the code base at commit `f2a96a9f1fdbdd444ddfeaed949096426fea7442`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExportTask

## Description
Six net-new root causes on the RDS control plane and its published endpoint names, found by replaying the behavioral suite (simparity-behavioral-aws-v1) against the emulator built from this checkout. A fixer must close ALL SIX before submitting; each is numbered with its own failing check ids. None of these checks was reported blocked by an unimplemented stub, and none is marked OWNED by an open issue.

---
Cause 1 of 6: the "DB Security Groups can only be associated with VPC DB Instances using API versions ..." refusal names the wrong API-version range.
AWS: recorded behavior only for the sentence (Smithy models CreateDBInstance's DBSecurityGroups member as a DBSecurityGroupNameList and InvalidParameterCombination as a service-common sender error). A CreateDBInstance that names DBSecurityGroups for a VPC instance is refused with HTTP 400, code InvalidParameterCombination, message "DB Security Groups can only be associated with VPC DB Instances using API versions 2012-01-15 through 2012-09-17." The whole sentence is fixed text — it names no request value — and the closing version is 2012-09-17.
Emulator: the code is right but the range ends at the wrong version: "DB Security Groups can only be associated with VPC DB Instances using API versions 2012-01-15 through 2012-04-23." Two independent checks assert the same sentence and both fail on the same substitution.
Why: the message is the requirement for this error class; a client or negative test matching AWS's sentence matches nothing, and the text misinforms an operator about which API versions ever allowed the combination.
Fix: the refusal path in the CreateDBInstance handler (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/ — the create-DB-instance operation) where the DBSecurityGroups-in-VPC InvalidParameterCombination message is built; the same constant is reached from the overly-permissive path the second check exercises.
Traces: rds.create-instance-missing-authorization-rejected, rds.security-group-not-supported-in-vpc-blocked.

Cause 2 of 6: the CreateDBInstance refusal for an AvailabilityZone the DB subnet group does not cover drops AWS's closing clause listing the zones that ARE available.
AWS: recorded behavior only; the refusal (InvalidVPCNetworkStateFault class) reads "You can't create a <DBInstanceClass> database instance because there are no subnets with available IP addresses in the specified Availability Zone <az>. Create a new subnet in <az> and target that Availability Zone again, or retry the launch with no availability zone, or choose from these Availability Zones: <az>, <az>." The fixed text is that whole template including the final ", or choose from these Availability Zones: " clause; the variable parts are the instance class and requested AZ from the request and the list of AZs the named DB subnet group actually covers, taken from state.
Emulator: the message stops early and re-words the tail: "... or retry the launch with no availability zone specified." — the phrase is "no availability zone specified" instead of "no availability zone", and the covered-zone list AWS appends is absent entirely.
Why: the clause AWS appends is the remediation: it tells the caller which zones the subnet group covers. Without it a caller (or an operator reading a CloudFormation failure reason) has to go discover the subnet group's zones by hand, and a test asserting AWS's sentence fails.
Fix: the AZ/subnet-group validation message in the CreateDBInstance handler — emit the full template and append the sorted list of AZs covered by the request's DB subnet group.
Traces: rds.create-db-instance-az-not-in-subnet-group-rejected.

Cause 3 of 6: StartDBInstanceAutomatedBackupsReplication on an engine that does not support it is refused with a same-Region complaint instead of the feature-unavailable refusal.
AWS: Smithy models StartDBInstanceAutomatedBackupsReplication with required SourceDBInstanceArn and the errors DBInstanceNotFoundFault (404), InvalidDBInstanceStateFault (400), KMSKeyNotAccessibleFault (400) and the service-common InvalidParameterValue; the message text is recorded behavior only. For an available DB instance whose engine does not offer cross-Region automated-backup replication (here Engine='docdb'), the call is refused with code InvalidParameterValue and message "Feature is not available in region <region>." — fixed text "Feature is not available in region " and ".", the variable part being the request's Region. The same operation naming an instance that does not exist still reaches the instance lookup first and answers DBInstanceNotFound "Requested DB Instance <id> not found in source region <region>" (that control step passed), so the refusal is reached after the source is resolved, not instead of resolving it.
Emulator: the code is right (InvalidParameterValue) but the condition reported is a different one — "The source DB instance arn:aws:rds:<...>:db:<id> is located in the Region this request was made to. Automated backups are replicated to a different AWS Region." The handler judges the source Region before (or instead of) the engine's support for the feature, so the engine restriction is never reported.
Why: the two sentences carry different instructions under one code: "the feature does not exist here" is terminal, while "the source is in this Region" tells the caller to retry the call against a different destination Region — which, for this engine, can never succeed. A client following the emulator's advice loops over Regions forever, and the unsupported-engine condition is unreachable.
Fix: the validation order and messages of the StartDBInstanceAutomatedBackupsReplication handler (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/ — the start-DB-instance-automated-backups-replication operation): resolve the source instance, then check the resolved instance's engine against the engines the feature supports and answer the feature-unavailable sentence, keeping the same-Region sentence for a supported engine whose source really is in the destination Region. Related OPEN issues that do NOT cover this cause (they are about the Stop counterpart's source resolution): 20261125T233840Z-rds-stopdbinstanceautomatedbackupsreplication-never-resolves-the-source-instance-so.md and 20261127T014232Z-rds-stopdbinstanceautomatedbackupsreplication-again-resolves-the-source-instance-first.md.
Traces: rds.automated-backups-replication-rejected-for-unsupported-engine.

Cause 4 of 6: StartExportTask judges the KmsKeyId before resolving SourceArn — and reports a key that exists in the emulator's own KMS as not existing.
AWS: Smithy models StartExportTask with required ExportTaskIdentifier, SourceArn, S3BucketName, IamRoleArn, KmsKeyId and the errors DBClusterNotFoundFault (client, 404), DBClusterSnapshotNotFoundFault (404), DBSnapshotNotFoundFault (404, awsQuery code 'DBSnapshotNotFound'), InvalidExportSourceStateFault (400), InvalidS3BucketFault (400), IamRoleNotFoundFault (404), IamRoleMissingPermissionsFault (400), KMSKeyNotAccessibleFault (400). The export source named by SourceArn is resolved first: a cluster ARN naming a cluster that does not exist is refused with DBClusterNotFoundFault and a message of the form "DB cluster <identifier> was not found." (fixed text "DB cluster " and " was not found.", variable the identifier from SourceArn), and nothing about the KMS key, bucket or role is reported.
Emulator: the request is refused with KMSKeyNotAccessibleFault, "The specified KMS key [<key arn>] does not exist, is not enabled or you do not have permissions to access it." — for a CMK the check had just created with kms:CreateKey in the same run. So two things are wrong together: the KMS probe runs before the source is resolved, and the probe does not recognise a key that exists in the emulator's KMS state, which makes EVERY StartExportTask of this shape unreachable past the key check.
Why: the refusal misdiagnoses the request and changes its class (404 source-not-found vs 400 key-not-accessible drive different remediation). An operator is sent to re-grant a key that is fine while the nonexistent source is never named; and because an existing CMK is rejected, the operation cannot be driven to its real verdicts at all (the check never reaches the InvalidExportSourceStateFault case it exists to grade). Related OPEN issue, whose Cause 2 is the same ordering defect seen from the wire corpus with a snapshot ARN and which the replay did NOT bind to this check: 20261128T133812Z-rds-2-net-new-causes-createdbinstance-skips-request.md — this cause adds the cluster-ARN form and the "existing CMK reported absent" half.
Fix: the validation order of the StartExportTask handler (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/start_export_task.rs): resolve SourceArn against cluster/snapshot state and answer the matching modeled not-found fault BEFORE probing KmsKeyId, and resolve KmsKeyId against the emulator's KMS state (accepting a key ARN or id that exists and is enabled) rather than failing it unconditionally.
Traces: rds.export-of-cluster-without-instances-rejected.

Cause 5 of 6: StartExportTask does not validate ExportOnly table names against the character set AWS allows.
AWS: Smithy models StartExportTask's ExportOnly as a StringList and the error InvalidExportOnlyFault (client, 400); the message is recorded behavior only. An ExportOnly entry containing a character outside the allowed set is refused with HTTP 400, code InvalidParameterValue, message "<name> isn't a valid valid table name for the export table task. Table names can contain only basic Latin letters, digits 0-9, dollar symbols ($), and underscores (_)." — the fixed text is that sentence pair exactly as AWS words it (including AWS's doubled "valid valid"), with the single variable part being the offending ExportOnly entry copied from the request; no export task is created.
Emulator: the request is accepted — HTTP 200 with an ExportTask in Status 'STARTING' echoing ExportOnly ['sim2real-db'] (the hyphenated name), so the task exists and later appears in DescribeExportTasks.
Why: the export silently proceeds with a selector AWS would never accept; the caller learns nothing about the bad name, the resulting export is attributed to a table that cannot exist, and the InvalidParameterValue/InvalidExportOnlyFault path for this condition is unreachable. A negative test of the selector cannot pass.
Fix: the input-validation stage of the StartExportTask handler, before the task record is created: validate every ExportOnly entry against the allowed character set (basic Latin letters, digits, '$', '_' plus the schema/table separator) and refuse with AWS's sentence, creating no export task.
Traces: rds.export-only-name-outside-charset-refused.

Cause 6 of 6: the endpoint host name RDS publishes for a DB instance is not answered with an address by the emulator's resolver.
AWS: recorded behavior only for the DNS surface; Smithy models DBInstance.Endpoint.Address as the host name clients connect to. In AWS that name resolves inside the VPC to an address in the instance's own subnets, and a name for an instance that was never published is answered NXDOMAIN — the difference between the two answers is what the checks grade.
Emulator: querying the published endpoint name through the resolver (the checks relay one UDP query via a Lambda to its own resolver, so no runner egress is involved) returns no address at all within the poll budget — "gave up after 32s waiting for the published endpoint name to be answered with an address; last=None". Because a published name is never answered, the NXDOMAIN-for-an-unpublished-name contrast cannot be observed either.
Why: a client that does what AWS tells it to do — connect to DBInstance.Endpoint.Address — cannot resolve the host, so the data plane is reachable only by bypassing the published name. Any test or application asserting that the endpoint name resolves to an address in the instance's subnets (private connectivity, VPC-scoped DNS) fails, and the ability to distinguish a live endpoint from a nonexistent one by DNS is lost.
Fix: the endpoint publication/DNS component behind DBInstance.Endpoint (the address the RDS state publishes in services/service-com-amazonaws-rds-amazonrdsv19/src/state.rs and the resolver that serves those names): publish a name the emulator's resolver answers with an address in the instance's subnets, and answer NXDOMAIN for a name no instance published. Related OPEN issues a fixer should read first, which the replay did NOT bind to these two checks and which cover the ADDRESS/host published in API responses rather than DNS resolution of the published name: 20261118T181500Z-rds-the-published-endpoint-of-a-served-engine-is-the-core-listeners.md, 20261123T132332Z-rds-a-served-engine-s-dbinstance-endpoint-address.md, 20261126T074046Z-rds-db-cluster-envelopes-publish-an-ephemeral-listener.md.
Traces: rds.rds-endpoint-domain-answers-an-unpublished-instance-name-with-nxdomain, rds.rds-private-instance-endpoint-resolves-to-an-address-in-its-own-subnets.
