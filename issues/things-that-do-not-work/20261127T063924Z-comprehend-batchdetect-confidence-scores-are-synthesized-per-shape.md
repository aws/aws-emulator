# Comprehend BatchDetect* confidence scores are synthesized per shape instead of computed from each document (4 causes)

> _Note: this issue was identified against the code base at commit `7fb2ed4170396fe0a0c384ff71365204f905b96a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchDetectDominantLanguage

## Description
FOUR net-new root causes in the comprehend crate's BATCH synchronous-inference layer (the BatchDetect* handlers exercised by fixture comprehend-batch-detect-suite). Every one of the four steps answers HTTP 200 exactly as recorded, the ResultList/ErrorList shape is correct, per-document Index values line up and the key-phrase/token spans and texts match, so the divergence is entirely in the analysed confidence VALUES. One fault recurs through all four: the confidence a batch handler emits is produced by the response builder from a per-shape/per-type table rather than computed from the document it is reporting on, so (a) confidences that AWS reports as distinct per document collapse toward a shared magnitude, (b) saturation is applied where AWS reports a middling confidence and vice versa, (c) the SentimentScore distribution no longer describes the text and its residual members are floored or hard-zeroed, and (d) part-of-speech confidences are pinned to an exact 1.0, which AWS never reports for these tokens. A fixer must close all FOUR causes.

PRIOR ART (named, NOT covering): 20261120T175104Z-comprehend-batchdetectentities-emits-uncalibrated-per-entity-confidence-scores--r2.md is OPEN and owns ONLY task#2 (BatchDetectEntities) of this same fixture - replay reports task#2 as owned and the four steps below as owned_by EMPTY, so that issue does not cover them. 20261125T014337Z-comprehend-single-document-detect-confidence-scores-are-drawn.md and 20261126T023639Z-comprehend-single-document-detectsyntax-and-detecttargetedsentiment-mislabel-tokens.md are OPEN but own the SINGLE-DOCUMENT fixture comprehend-detect-suite-single-document only. stub_path is empty for all four steps below, so none is blocked by an unimplemented operation.

Cause 1 of 4: BatchDetectDominantLanguage returns per-document language confidences that do not track each document's evidence - one document is pulled down from near-certainty and two others are pushed in opposite directions, so the batch's confidences cluster instead of spreading. Fixture comprehend-batch-detect-suite, step task#1.
  AWS: Smithy: BatchDetectDominantLanguage(TextList required, CustomerInputStringList @length min 1, sensitive) -> ResultList: ListOfDetectDominantLanguageResult (required) + ErrorList: BatchItemErrorList (required); errors BatchSizeLimitExceededException / InvalidRequestException / TextSizeLimitExceededException (400) and InternalServerException (500). Each DominantLanguage carries LanguageCode (RFC 5646) and Score, documented as 'The level of confidence that Amazon Comprehend has in the accuracy of the detection'. The batch form is a fan-out: the Score for document i must be the SAME value the single-document DetectDominantLanguage would produce for that text, so documents giving different amounts of evidence for their language get visibly different confidences. Recorded behavior: the three documents come back at three clearly separated confidences.
  Emulator: all three documents' $.ResultList[*].Languages[0].Score diverge and the batch's spread is lost - the document AWS is MOST confident about comes back lower than recorded while a document AWS is LESS confident about comes back higher, leaving the three values bunched within a narrow band near the same magnitude. That is the signature of a score assigned by the response path per shape rather than derived from each document's own detection.
  Why: clients gate on Languages[0].Score per document ('auto-translate above the threshold, queue for human review below it') and also compare documents within one batch to pick the one whose language is most reliably identified. A confidence that does not track the document makes the review branch fire on the wrong documents, and bunching the values destroys any within-batch ranking - the same TextList is routed differently against the emulator than against AWS.
  Fix: the BatchDetectDominantLanguage handler's language-detection scorer in the comprehend crate - compute each ResultList entry's Score from that entry's own text, delegating to the same detection path the single-document DetectDominantLanguage uses, instead of filling the member from a shape-level constant in the serializer.
  Traces: comprehend-batch-detect-suite#task#1.

Cause 2 of 4: BatchDetectKeyPhrases scores every key phrase from a saturation table, so phrases AWS separates by orders of magnitude of residual uncertainty become indistinguishable and the within-document ranking inverts. Fixture comprehend-batch-detect-suite, step task#3.
  AWS: Smithy: BatchDetectKeyPhrases(TextList required @length min 1 sensitive, LanguageCode required) -> ResultList: ListOfDetectKeyPhrasesResult + ErrorList; errors BatchSizeLimitExceededException / InvalidRequestException / TextSizeLimitExceededException / UnsupportedLanguageException (400), InternalServerException (500). KeyPhrase = {Score 'The level of confidence that Amazon Comprehend has in the accuracy of the detection', Text 'the text of a key noun phrase', BeginOffset, EndOffset}. Recorded behavior: each extracted phrase carries its own confidence computed from that span; strongly delimited noun phrases sit extremely close to 1.0 while a weakly delimited one sits distinctly lower, and the values are not shared between phrases.
  Emulator: six key-phrase Scores across three documents diverge. The returned values all sit in one very narrow band just below 1.0 regardless of the phrase, and the one phrase AWS reports materially below the rest is returned at essentially the same near-1.0 value as its strongly evidenced neighbours - the gap AWS reports between a confident and an uncertain phrase is erased. Within documents the pairwise ordering also flips: a phrase AWS ranks above its sibling comes back below it.
  Why: key-phrase extraction clients threshold Score to drop noise and rank by Score to choose the phrases to index, tag or show. Erasing the separation between a confident and an uncertain phrase makes every phrase survive any threshold a client sets, and inverting the ranking makes 'the top key phrase of this document' a different phrase on the emulator than on AWS, for the same text.
  Fix: the BatchDetectKeyPhrases handler's key-phrase scorer - one confidence per extracted phrase, computed from that span in that document, never drawn from a per-shape/per-type ladder; share the single-document DetectKeyPhrases scoring path so batch and single-document agree.
  Traces: comprehend-batch-detect-suite#task#3.

Cause 3 of 4: BatchDetectSentiment returns distributions that are not the documents' - the dominant member is diluted or over-saturated, mass leaks into the wrong sentiment, and the residual members collapse onto a floor constant or an exact 0.0. Fixture comprehend-batch-detect-suite, step task#4.
  AWS: Smithy: BatchDetectSentiment(TextList required @length min 1 sensitive, LanguageCode required) -> ResultList: ListOfDetectSentimentResult + ErrorList; errors as for the other batch ops. Each result carries Sentiment (SentimentType) and SentimentScore{Positive, Negative, Neutral, Mixed}, each member documented 'The level of confidence that Amazon Comprehend has in the accuracy of its detection of the <SENTIMENT> sentiment'. Recorded behavior: the four members form ONE normalised distribution concentrated on the reported Sentiment, with the residual members at small but MUTUALLY DISTINCT magnitudes spanning several orders (the recording's residuals run from ~2e-05 through ~3e-03), never zero.
  Emulator: all twelve SentimentScore members across the three documents diverge, in three distinct ways. (i) Dilution/leakage: the document AWS reports as predominantly MIXED has that member pulled down by roughly a sixth while an order of magnitude more mass appears in Neutral and Positive than recorded. (ii) Over-saturation: the document AWS reports as clearly NEUTRAL comes back with Neutral pushed even closer to 1.0 and its Negative and Positive residuals cut to a single shared floor value, so two residual members that AWS separates become equal. (iii) Hard zeros: Mixed is returned as exactly 0.0 for two documents where the recording has small non-zero confidences, and the same floor literal recurs across documents - a fixed table, not a computed distribution. The identical floor/zero pattern appears in the single-document DetectSentiment step, confirming one shared table behind both paths.
  Why: clients branch on the whole distribution, not only on Sentiment: 'ambiguous if a second sentiment exceeds 0.05', 'confident only above 0.99', or a log-scale comparison of residuals between documents. Diluting the dominant member flips a decisive verdict to ambiguous; over-saturating it flips an ambiguous one to decisive; and zeroing or flooring residuals makes any residual comparison meaningless and makes two different documents compare as identical. For one batch, the emulator classifies documents differently from AWS.
  Fix: the BatchDetectSentiment handler's sentiment scorer - compute one normalised distribution per document from that document's text, concentrated on the reported Sentiment and with distinct non-zero residual members, instead of filling SentimentScore members from a floor/ladder table in the response builder.
  Traces: comprehend-batch-detect-suite#task#4.

Cause 4 of 4: BatchDetectSyntax pins PartOfSpeech.Score to an exact 1.0, reporting absolute certainty where AWS always reports a value strictly below 1.0 for these tokens. Fixture comprehend-batch-detect-suite, step task#5.
  AWS: Smithy: BatchDetectSyntax(TextList required @length min 1 sensitive, LanguageCode: SyntaxLanguageCode required) -> ResultList: ListOfDetectSyntaxResult + ErrorList; errors as for the other batch ops. SyntaxToken = {TokenId, Text, BeginOffset, EndOffset, PartOfSpeech: PartOfSpeechTag}, and PartOfSpeechTag = {Tag: PartOfSpeechTagType (ADJ, ADP, ADV, AUX, CONJ, CCONJ, DET, INTJ, NOUN, NUM, O, PART, PRON, PROPN, PUNCT, SCONJ, SYM, VERB), Score 'The confidence that Amazon Comprehend has that the part of speech was correctly identified'}. Recorded behavior: the tagger reports a residual uncertainty per token - even its most certain tags come back just below 1.0 (the recording's values are of the form 0.99999x), and tokens differ from one another in the last digits; an exact 1.0 is not what the tagger emits for these tokens.
  Emulator: three tokens' $.ResultList[*].SyntaxTokens[*].PartOfSpeech.Score are returned as the literal 1.0 where the recording has values just below 1.0. Every token the emulator is confident about receives the identical constant 1.0 rather than its own near-1.0 confidence, so the per-token residual the tagger is supposed to report is discarded. All Tag values, token texts and offsets of this step match, which isolates the defect to the score field alone. The same 1.0 pinning appears in the single-document DetectSyntax step, so the constant lives in the shared syntax-scoring path.
  Why: a client that compares PartOfSpeech.Score between tokens to find the tokens its tagging is least sure of, or that treats <1.0 as 'model-reported confidence' and 1.0 as a sentinel/override, gets a uniform 1.0 for every token: the least-certain-token query returns nothing, and any downstream check that distinguishes a reported confidence from a hard-coded certainty misreads the whole token stream.
  Fix: the BatchDetectSyntax handler's part-of-speech scorer - emit the tagger's own per-token confidence (strictly below 1.0, differing between tokens) rather than clamping or defaulting the PartOfSpeechTag.Score member to 1.0 in the serializer; the same path backs single-document DetectSyntax, so fix it once there.
  Traces: comprehend-batch-detect-suite#task#5.

In all four causes the recorded numbers quoted under Evidence are THIS recording's values for ITS OWN input texts and are not themselves the requirement. The requirement is the convention: one confidence per detection, computed from that detection in the document being reported on and identical to what the single-document Detect* path would return for the same text; a normalised SentimentScore concentrated on the reported Sentiment with distinct non-zero residual members; a per-token part-of-speech confidence strictly below 1.0; and never a literal that recurs across unrelated detections, documents or operations. HTTP status (200), the absence of any error code or error message, and the ResultList/ErrorList shape are already correct and must stay correct.
