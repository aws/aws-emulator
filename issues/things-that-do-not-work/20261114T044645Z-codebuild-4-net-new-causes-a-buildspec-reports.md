# codebuild: 4 net-new causes — a buildspec `reports:` section creates no report, the PRE_BUILD failure phase flow ignores `on-failure` in both directions, and artifacts.location embeds the full build id instead of the build UUID

> _Note: this issue was identified against the code base at commit `75f948824b47006d8e5270a6b1242dd4c041c19f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartBuild

## Description
Four distinct defects in the CodeBuild build-execution/phase engine and in the Build projection it serves back through BatchGetBuilds. All four are observed on builds that the emulator now DOES run to buildComplete (so they are not the older 'builds FAULT at PROVISIONING' family: open issues 20261025T014438Z-codebuild-builds-never-execute-so-no-report-or-test-case-flow-is-observable.md, 20261107T233000Z-codebuild-builds-never-execute-so-no-report-override-or-artifact-free-build-is-observable.md and 20261113T085141Z-codebuild-a-well-formed-buildspec-build-fails-in.md describe builds that never execute or fail outright; here the build SUCCEEDS and the divergence is in what it produced and in the phase record). Four causes, each with its own failing check ids.

=== Cause 1 of 4: a build whose buildspec declares a `reports:` section ingests nothing — Build.reportArns is empty and no Report is created ===
AWS: Smithy: Build.reportArns (target BuildReportArns) is documented 'An array of the ARNs associated with this build's reports'; Report.reportGroupArn / Report.executionId / Report.status / Report.testSummary are the report a build mints. There is no CreateReport API — per the AWS buildspec reference, a build whose buildspec carries a top-level `reports:` block keyed by a report-group ARN (or name) with `files:` and `file-format: JUNITXML` parses the named results file during the build, creates exactly ONE report in that report group, and returns that report's ARN in the build's reportArns. The report's status is FAILED when any ingested test case failed while the BUILD itself stays SUCCEEDED (an ingested test failure does not fail the build), and DescribeTestCases on that report ARN lists one test case per `<testcase>` with its exact status and, for a failure, the `<failure message=...>` text. The build's service role carrying codebuild:CreateReport, codebuild:UpdateReport and codebuild:BatchPutTestCases on that report group arn is what authorizes it.
Emulator: the build runs and ends buildStatus SUCCEEDED, but the Build it serves carries NO reportArns at all (`build.get("reportArns")` is `[]`), so no report exists in the report group the buildspec named and the whole report/test-case surface downstream of a build (BatchGetReports, DescribeTestCases) has nothing to read. Replay: 'AssertionError: expected exactly one report arn, got []' and 'AssertionError: expected exactly one report arn from the build, got []'.
Why: a client that runs tests in CodeBuild and reads results through reports — a CI gate that polls BatchGetReports for the build's reportArns, or DescribeTestCases to see which case failed — sees a build that claims success and produced no test evidence at all. It can never distinguish 'no tests ran' from 'all tests passed', and a test-report-driven release gate silently passes. It also makes every negative test on a report ARN unreachable, because no real report ARN can be minted.
Fix: the build-execution engine behind StartBuild (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build.rs) must parse the buildspec's top-level `reports:` block, ingest the declared files from the build's working directory in the declared file-format, create a Report in the named report group recording reportGroupArn/executionId/status/testSummary plus its test cases in the service state (services/service-com-amazonaws-codebuild-codebuild-20161006/src/state.rs), and the Build projection must list that report's ARN in reportArns.
Traces: codebuild.codebuild-junit-report-ingestion-reports-each-test-case-with-its-exact-status, codebuild.describe-test-cases-absent-report-not-found (the latter only needs ONE real report to exist in order to reach its not-found assertion at all).

=== Cause 2 of 4: a PRE_BUILD failure under the default `on-failure: ABORT` still ATTEMPTS UPLOAD_ARTIFACTS ===
AWS: Smithy: BuildPhaseType enum is SUBMITTED, QUEUED, PROVISIONING, DOWNLOAD_SOURCE, INSTALL, PRE_BUILD, BUILD, POST_BUILD, UPLOAD_ARTIFACTS, FINALIZING, COMPLETED, and Build.phases is documented as 'all previous build phases that are complete and ... any current build phase'. Per the buildspec reference, `on-failure` defaults to ABORT: when PRE_BUILD fails with ABORT the build stops there, so BUILD, POST_BUILD and UPLOAD_ARTIFACTS are never ATTEMPTED — they are absent from Build.phases entirely, not merely present with a non-SUCCEEDED phaseStatus. The phases AWS records are the prefix through the failed PRE_BUILD plus FINALIZING and COMPLETED.
Emulator: the phase record of the aborting build is ['SUBMITTED', 'QUEUED', 'PROVISIONING', 'DOWNLOAD_SOURCE', 'INSTALL', 'PRE_BUILD', 'UPLOAD_ARTIFACTS', 'FINALIZING', 'COMPLETED'] — an UPLOAD_ARTIFACTS phase is emitted (and reported SUCCEEDED) after a phase whose failure must have aborted the build.
Why: a client reading Build.phases to learn how far a failed build got concludes the artifact-upload stage was reached and succeeded for a build AWS never let out of PRE_BUILD. Any tooling that keys 'were artifacts produced?' or 'where did it stop?' off the presence of UPLOAD_ARTIFACTS misattributes the failure, and a publish step gated on that phase runs on a build that produced nothing.
Fix: the phase sequencer in the build-execution engine behind StartBuild (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build.rs) must stop appending phases at the aborting phase and append only FINALIZING and COMPLETED.
Traces: codebuild.failing-pre-build-phase-skips-later-phases-and-reports-the-exit-code.

=== Cause 3 of 4: `on-failure: CONTINUE` on a phase is ignored — BUILD and POST_BUILD are skipped after a failed PRE_BUILD ===
AWS: per the buildspec reference, `phases/<phase>/on-failure: CONTINUE` means 'Continue to the next phase': a PRE_BUILD that fails under CONTINUE keeps phaseStatus FAILED, and BUILD and POST_BUILD STILL RUN and reach phaseStatus SUCCEEDED. The overall build is FAILED in both the ABORT and the CONTINUE arm — CONTINUE changes the phase flow, not the verdict — so the phase flow is the only observable difference between the two arms. `on-failure` is accepted in a buildspec supplied through buildspecOverride on a NO_SOURCE project.
Emulator: the CONTINUE arm's phase record is identical to the ABORT arm's: [('SUBMITTED','SUCCEEDED'), ('QUEUED','SUCCEEDED'), ('PROVISIONING','SUCCEEDED'), ('DOWNLOAD_SOURCE','SUCCEEDED'), ('INSTALL','SUCCEEDED'), ('PRE_BUILD','FAILED'), ('UPLOAD_ARTIFACTS','SUCCEEDED'), ('FINALIZING','SUCCEEDED'), ('COMPLETED', None)] — BUILD and POST_BUILD appear nowhere, so its SUCCEEDED set is ['DOWNLOAD_SOURCE','FINALIZING','INSTALL','PROVISIONING','QUEUED','SUBMITTED','UPLOAD_ARTIFACTS']. The emulator does not read `on-failure` at all.
Why: a client that marks a soft phase CONTINUE precisely so the later phases still run (lint/report phase allowed to fail, build still produced) gets a build in which the later phases never ran, and cannot tell CONTINUE from ABORT from the API. Every buildspec relying on CONTINUE silently loses its main work.
Fix: the buildspec phase interpreter in the build-execution engine behind StartBuild (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build.rs) must honour per-phase `on-failure` (ABORT default, CONTINUE proceeds to the next phase while leaving the failed phase's phaseStatus FAILED and the build's buildStatus FAILED).
Traces: codebuild.on-failure-continue-runs-the-next-phase-while-the-failed-phase-stays-failed.

=== Cause 4 of 4: Build.artifacts.location embeds the FULL build id (`<projectName>:<uuid>`) instead of the build UUID ===
AWS: Smithy: BuildArtifacts.location is 'Information about the location of the build artifacts'. For a project with S3 artifacts of type S3, location is the S3 ARN of the artifact prefix, built from the artifact bucket, the build's UUID ALONE (the portion of Build.id after the ':' separating projectName from the build UUID) and the artifact name: `arn:aws:s3:::<bucket>/<build-uuid>/<artifactName>`; the uploaded object key is correspondingly `<build-uuid>/<artifactName>/<file>`.
Emulator: location is served with the whole Build.id (projectName and UUID joined by ':') as the first path segment: the replay shows `arn:aws:s3:::<bucket>/<projectName>:<build-uuid>/out` where AWS serves `arn:aws:s3:::<bucket>/<build-uuid>/out`. (The project name and UUID in the recording are per-run values filling that template; the defect is the extra `<projectName>:` segment, not the specific name.)
Why: a client that parses artifacts.location, or derives the artifact object key from it to fetch the build output from S3, addresses a key that differs from the published layout — a GetObject at the AWS-shaped key misses, and a key containing ':' is an invalid path for consumers that build filesystem paths from it.
Fix: the artifact-location serializer in the build-execution/Build projection path (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build.rs and the Build projection served by BatchGetBuilds) must use only the build UUID as the prefix segment.
Traces: codebuild.start-build-artifacts-override-rejected-without-a-location-and-no-artifacts-uploads-nothing (its two InvalidInputException refusal assertions pass; the divergence is the location of the default build's artifacts).

## Evidence
Cause 1 — expected: Build.reportArns holds exactly one report ARN for a build whose buildspec declares `reports: { "<report-group-arn>": { files: [sim2real-results.xml], file-format: JUNITXML } }`, and that report lists one test case per <testcase>. Actual: buildStatus SUCCEEDED with reportArns == [] — 'AssertionError: expected exactly one report arn, got []' / 'AssertionError: expected exactly one report arn from the build, got []'.

Cause 2 — expected: after a PRE_BUILD failure under the default ABORT, BUILD, POST_BUILD and UPLOAD_ARTIFACTS never appear in Build.phases. Actual: 'AssertionError: a default-ABORT PRE_BUILD failure must never attempt BUILD, POST_BUILD or UPLOAD_ARTIFACTS at all (not merely fail to succeed at them); the failing build reported phases ['SUBMITTED', 'QUEUED', 'PROVISIONING', 'DOWNLOAD_SOURCE', 'INSTALL', 'PRE_BUILD', 'UPLOAD_ARTIFACTS', 'FINALIZING', 'COMPLETED']'.

Cause 3 — expected: with `on-failure: CONTINUE` on pre_build, PRE_BUILD is FAILED and BUILD and POST_BUILD both reach SUCCEEDED (build overall FAILED). Actual: 'AssertionError: with `on-failure: CONTINUE` on pre_build, BUILD and POST_BUILD must still run to SUCCEEDED; that arm's SUCCEEDED set is ['DOWNLOAD_SOURCE', 'FINALIZING', 'INSTALL', 'PROVISIONING', 'QUEUED', 'SUBMITTED', 'UPLOAD_ARTIFACTS']; phases=[('SUBMITTED','SUCCEEDED'), ('QUEUED','SUCCEEDED'), ('PROVISIONING','SUCCEEDED'), ('DOWNLOAD_SOURCE','SUCCEEDED'), ('INSTALL','SUCCEEDED'), ('PRE_BUILD','FAILED'), ('UPLOAD_ARTIFACTS','SUCCEEDED'), ('FINALIZING','SUCCEEDED'), ('COMPLETED', None)]' — identical to the ABORT arm.

Cause 4 — expected: artifacts.location == arn:aws:s3:::<artifact-bucket>/<build-uuid>/<artifactName>. Actual: 'AssertionError: the default build reports artifact location 'arn:aws:s3:::sim2real-behav-cb-art-f65d5b2edf2e/sim2real-behav-cb-art-67cd16f4c322:430da812-9ed5-8a2c-aa9a-d40009b6e499/out'' — i.e. <bucket>/<projectName>:<build-uuid>/<artifactName>; bucket, project name and UUID are per-run values, the extra `<projectName>:` segment is the defect.

## Steps to Reproduce
Cause 1: CreateReportGroup(type=TEST, exportConfig NO_EXPORT); CreateProject with a NO_SOURCE project whose buildspec writes a JUnit XML with 2 passing and 1 failing <testcase> and declares `reports: { "<the report group arn>": { files: [sim2real-results.xml], file-format: JUNITXML } }`, with a service role granting codebuild:CreateReport/UpdateReport/BatchPutTestCases on that group; StartBuild; poll BatchGetBuilds to buildComplete; read builds[0].reportArns — it is empty where AWS returns one ARN resolvable through BatchGetReports and DescribeTestCases.

Causes 2 and 3: StartBuild twice on a NO_SOURCE project with buildspecOverride, one buildspec whose pre_build commands exit non-zero with no `on-failure` (default ABORT) and one identical buildspec with `on-failure: CONTINUE` on pre_build; poll both through BatchGetBuilds to buildComplete and compare Build.phases. The ABORT arm must omit BUILD/POST_BUILD/UPLOAD_ARTIFACTS (it emits UPLOAD_ARTIFACTS); the CONTINUE arm must show PRE_BUILD FAILED plus BUILD and POST_BUILD SUCCEEDED (it shows neither).

Cause 4: create an S3 bucket, CreateProject with artifacts {type: S3, location: <bucket>, name: 'out'} and a buildspec producing result.txt; StartBuild with no artifactsOverride; poll to buildComplete and read builds[0].artifacts.location and the bucket's keys.
