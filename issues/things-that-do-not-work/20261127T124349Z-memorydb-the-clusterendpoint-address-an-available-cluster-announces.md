# memorydb: the ClusterEndpoint address an available cluster announces does not resolve or serve RESP — in-VPC clients cannot connect at all

> _Note: this issue was identified against the code base at commit `6f83a022eb84b0ee9d2dc920d122919bec61aa30`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Replaying the behavioral corpus (simparity-behavioral-aws-v1) against this checkout left 8 checks failing; 6 are already owned by open issues and are skipped. The 2 surviving memorydb failures share ONE root cause, described below. A fixer must close that one cause and re-replay both checks in trace_ids.

Related open issue that does NOT own these two checks: `20261115T013411Z-memorydb-omitted-subnet-group-description-fabricated-tls-less.md`. Its Cause 3 is the same family (an available cluster serving no RESP data plane), but it carries only the replay keys for `memorydb.redis-oss-cluster-identifies-as-redis-over-the-wire` and `memorydb.valkey-cluster-serves-acl-enforced-resp-over-tls-and-runs-its-lifecycle`, and the emulator symptom it recorded was a connect refused with `OSError: a Lambda function in this emulator has no host network to reach`. In this replay the two checks below fail at a DIFFERENT point in the connect path — name resolution of the hostname the control plane announced — and neither check is marked owned by any open issue, so they are filed here and must be re-replayed in their own right.

Cause 1 of 1: the `Cluster.ClusterEndpoint.Address` an `available` cluster reports is a fabricated public AWS-shaped DNS name that does not exist in the emulator's network, so an in-VPC client cannot even resolve it, let alone speak RESP to it.
  AWS: Smithy (com.amazonaws.memorydb) models `Endpoint` as `{Address: String "The DNS hostname of the node", Port: Integer "The port number that the engine is listening on"}` inside `Cluster$ClusterEndpoint`, documented "Represents the information required for client programs to connect to the cluster and its nodes." The data plane itself is not in the model, so for its behavior: recorded behavior only — the recordings show that once `DescribeClusters` reports `Status == "available"`, the address and port in `ClusterEndpoint` accept a TCP connection from inside the cluster's VPC (TLS-wrapped when the cluster was created with `TLSEnabled=true`) and speak RESP2 there. The recordings then drive real engine conversations on that socket: `AUTH <user> <password>` answers `+OK` for a user in the cluster's ACL; string commands honour their options and error classes (`SET k v NX` on an existing key answers a null bulk, `SET k v XX` on a missing key answers a null bulk, `SET k v GET` answers the previous value, `GETDEL`, `STRLEN`, `GETRANGE`, `SETRANGE`, `INCRBY`, `INCRBYFLOAT`, `SET ... EX`/`KEEPTTL` with `TTL` reporting the remaining seconds and `-1`/`-2` for no-TTL and missing keys, and the documented errors `ERR value is not an integer or out of range`, `WRONGTYPE Operation against a key holding the wrong kind of value`, `ERR invalid expire time in 'set' command`, `ERR syntax error`); and the cluster's ACL is enforced per user, so after `UpdateUser(AccessString="on ~* &* +@all -set")` settles, that user's `SET` is refused on the socket with `-NOPERM User <UserName> has no permissions to run the 'set' command` (fixed text `NOPERM User ` … ` has no permissions to run the 'set' command`; the only variable part is the user name from the request) while the user's other commands (`GET`, `APPEND`, `DEL`, `EXISTS`) and an unchanged twin user in the same ACL keep working, and restoring the access string lets the same `SET` through again.
  Emulator: the control plane is fine up to the connect — CreateSubnetGroup, CreateUser, CreateACL and CreateCluster all succeed, the cluster leaves `creating` as `available`, and `ClusterEndpoint` carries an address and port. But the address is synthesized to look like a real AWS endpoint and points nowhere: `state.rs::cluster_endpoint_address` builds `<ClusterName>.<sha256-derived suffix>.clustercfg.memorydb.<region>.amazonaws.com` (and `node_endpoint_address` the analogous per-node name), and `create_cluster.rs` stores that string on `StoredCluster.endpoint_address`, which every describe reports. An in-VPC probe (a Lambda created with a `VpcConfig` on the cluster's own subnets and security group, using only `socket`/`ssl`) fails at `socket.create_connection((Address, Port))` with `gaierror: [Errno -2] Name or service not known` — the hostname does not resolve inside the emulator — so the session breaks after ZERO replies and not a single RESP command is answered. No RESP listener is bound for the cluster either, so even a resolvable address would answer nothing.
  Why: the control plane only tells a client where to connect; every real MemoryDB client then uses that socket. A client built against the emulator gets a cluster that reports itself `available` with a complete `ClusterEndpoint` and is then entirely unusable: connects die at DNS, so AUTH/ACL enforcement, key reads and writes, expiry and the engine's error classes are all unobservable. Application boots that wait for a successful PING hang or crash, and any test that asserts a command's reply or a NOPERM refusal after `UpdateUser` cannot run — while `DescribeClusters` keeps insisting the cluster is healthy. Announcing an address other than one the emulator is reachable on is itself the defect: the emulator published a name it does not serve.
  Fix: the memorydb cluster data-plane listener plus the endpoint naming in the cluster state projection. An `available` cluster must bind and serve RESP at exactly the address and port it advertises in `ClusterEndpoint` (and at each shard/node endpoint), TLS-wrapped when `TLSEnabled=true`, and that advertised name must be one the emulator's in-VPC compute can actually resolve and reach rather than a fabricated `*.clustercfg.memorydb.<region>.amazonaws.com` host. The served engine must enforce the cluster's ACL for AUTH and per-user command permissions (re-read after `UpdateUser`/`UpdateACL` so a narrowed access string produces the NOPERM refusal above and a restore lifts it) and implement the string/expiry/type semantics listed under AWS, reading engine and version from the same stored cluster fields the control plane serializes so the data plane cannot disagree with `DescribeClusters`.
  Traces: memorydb.access-string-update-without-set-rejects-set-until-restored, memorydb.string-commands-honour-set-options-expiry-and-type-errors.
