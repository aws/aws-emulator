# appsync: control-plane request validation — 10 net-new causes (wrong error class, wrong message wording, and validation not enforced at all)

> _Note: this issue was identified against the code base at commit `85a8ef40f44f446d2f7f13d4131def4b1abce9f7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateGraphqlApi

## Description
The AppSync control plane's request-validation layer diverges from AWS in ten distinct ways. Every cause below is grounded in failing behavioral checks; each must be closed before submitting.

Cause 1 of 10: out-of-enum members answered with a generic Smithy ValidationException instead of AppSync's BadRequestException.
AWS: for these members AppSync does NOT emit a modeled-constraint ValidationException; it refuses with BadRequestException and its own fixed message (recorded behavior, confirmed by each check's expected pair): AssociateMergedGraphqlApi sourceApiAssociationConfig.mergeType -> "Invalid MergeType value"; CreateDataSource metricsConfig -> "Invalid metricsConfig for data source given."; CreateFunction syncConfig.conflictDetection -> "Conflict Detection specified must be a valid Conflict Detection type."; CreateGraphqlApi apiType -> "Invalid API type specified."; enhancedMetricsConfig.dataSourceLevelMetricsBehavior -> "Invalid dataSourceLevelMetricsBehavior given."; enhancedMetricsConfig.resolverLevelMetricsBehavior -> BadRequestException; enhancedMetricsConfig.operationLevelMetricsConfig -> "Invalid operationLevelMetricConfig given."; CreateResolver kind -> "Invalid Resolver kind."; ListGraphqlApis owner -> "Invalid owner input.". For CreateGraphqlApi with authenticationType=AWS_IAM and a userPoolConfig whose defaultAction is outside ALLOW/DENY, AWS does not validate it at all: the create SUCCEEDS, echoes userPoolConfig verbatim in the response, and the stored API carries no userPoolConfig. These messages are fixed text; nothing in them comes from the request.
Emulator: every one of them is refused with code ValidationException and the generic text "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [...]" — and CreateGraphqlApi raises that for userPoolConfig.defaultAction instead of creating the API.
Why: a client that branches on BadRequestException vs ValidationException takes the wrong branch, and the AWS_IAM case fails a call AWS accepts, so an API that should exist never gets created.
Fix: the enum handling in these operations' input validation — these members must be excluded from the generic enum-constraint pass and refused by the operation's own validation (or, for userPoolConfig on an AWS_IAM API, not validated and not stored).
Traces: appsync.associate-merged-graphql-api-merge-type-outside-enum-rejected, appsync.create-data-source-metrics-config-outside-enum-rejected, appsync.create-function-unknown-conflict-detection-rejected, appsync.create-graphql-api-lowercase-api-type-rejected, appsync.create-graphql-api-unknown-data-source-metrics-behavior-rejected, appsync.create-graphql-api-unlisted-resolver-metrics-behavior-rejected, appsync.create-resolver-unknown-kind-rejected, appsync.graphql-api-operation-metrics-config-outside-enum-rejected, appsync.list-graphql-apis-owner-outside-enum-rejected, appsync.create-graphql-api-iam-auth-does-not-store-user-pool-config

Cause 2 of 10: where ValidationException IS correct, the enum value set is listed in the wrong order.
AWS: CreateChannelNamespace with an unknown handlerConfigs.onPublish.behavior / onSubscribe.behavior is refused with ValidationException and "1 validation error detected: Value at 'handlerConfigs.onPublish.behavior' failed to satisfy constraint: Member must satisfy enum value set: [DIRECT, CODE]" — the listed set is DIRECT then CODE (recorded behavior only; note the Smithy enum com.amazonaws.appsync#HandlerBehavior declares CODE, DIRECT, so the rendering is NOT the model's declaration order and must not be derived from it).
Emulator: same code and same sentence but renders "[CODE, DIRECT]".
Why: the message is part of the error contract; a client or test asserting on AWS's text sees a mismatch.
Fix: the enum-value-set rendering used by the constraint-message formatter for HandlerBehavior.
Traces: appsync.channel-namespace-on-publish-behavior-outside-enum-rejected, appsync.channel-namespace-on-subscribe-unknown-behavior-rejected

Cause 3 of 10: the generic constraint message renders the wrong error code, echoes the offending value, uses the wrong member path for maps/lists, and anchors regex patterns.
AWS (recorded behavior, one rule per member): CreateChannelNamespace codeHandlers over 32768 -> ValidationException "1 validation error detected: Value at 'codeHandlers' failed to satisfy constraint: Member must have length less than or equal to 32768" (no value echo). CreateChannelNamespace name of 51 chars -> ValidationException "2 validation errors detected: Value at 'name' failed to satisfy constraint: Member must have length less than or equal to 50; Value at 'name' failed to satisfy constraint: Member must satisfy regular expression pattern: ([A-Za-z0-9](?:[A-Za-z0-9\-]{0,48}[A-Za-z0-9])?)" — no value echo and the pattern is rendered WITHOUT ^ and $ anchors. EvaluateCode context over 28000 -> BadRequestException "1 validation error detected: Value at 'context' failed to satisfy constraint: Member must have length less than or equal to 28000". TagResource tag value over 256 -> BadRequestException "1 validation error detected: Value '{<k>=<v>}' at 'addedTags' failed to satisfy constraint: Map value must satisfy constraint: [Member must have length less than or equal to 256, Member must have length greater than or equal to 0]" — the whole map is echoed, the path is the internal member name 'addedTags', and the constraint is the bracketed list form. UntagResource tag key over 128 (and the empty key) -> BadRequestException "1 validation error detected: Value '[<keys>]' at 'removedTagKeys' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]" — path 'removedTagKeys', the whole key list echoed, no element index.
Emulator: uses BadRequestException where AWS uses ValidationException (codeHandlers, namespace name), echoes the offending value ("Value '<32769 bytes of code>' at 'codeHandlers'", "Value 'nnn...' at 'name'", the 28001-char context), renders patterns anchored as ^...$, and addresses map/list members per element: "at 'tags.sim2real'" instead of 'addedTags' and "at 'tagKeys.1.member'" instead of 'removedTagKeys', with the single-constraint form instead of the bracketed list.
Why: every one of these is the error message a client logs or matches on, and the member path tells the client which field to fix — 'tags.sim2real' and 'tagKeys.1.member' are paths AWS never emits.
Fix: the shared constraint-violation message renderer (value echoing, map/list member naming, pattern rendering, and the ValidationException/BadRequestException choice per operation).
Traces: appsync.create-channel-namespace-code-handlers-over-32768-chars-rejected, appsync.create-channel-namespace-name-over-50-characters-rejected, appsync.evaluate-code-context-over-max-length-rejected, appsync.evaluate-mapping-template-over-65536-characters-rejected, appsync.create-api-tag-value-over-256-characters-rejected, appsync.untag-resource-tag-key-beyond-128-chars-rejected

Cause 4 of 10: PutGraphqlApiEnvironmentVariables key validation uses a hand-written message where AWS uses the map-constraint message.
AWS: an environment-variable key outside 2..64 characters or outside ^[A-Za-z]+\w*$ is refused with BadRequestException "1 validation error detected: Value '{<KEY>=<value>}' at 'environmentVariables' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 64, Member must have length greater than or equal to 2, Member must satisfy regular expression pattern: ^[A-Za-z]+\w*$]" — fixed text apart from the echoed map.
Emulator: answers BadRequestException "Invalid environment variable key <KEY>: a key must be between 2 and 64 characters long, must begin with a letter, and can only contain letters, numbers, and the underscore character (_)."
Why: a client matching AWS's constraint text never recognises the refusal.
Fix: PutGraphqlApiEnvironmentVariables input validation — route key/value bounds through the map-constraint renderer instead of a bespoke message.
Traces: appsync.put-environment-variables-hyphenated-key-rejected, appsync.put-environment-variables-key-length-bounds-rejected

Cause 5 of 10: AppSync's own "not specified" / "invalid" refusals are worded differently.
AWS (recorded behavior; fixed text, no request values in it): CreateDataSource with name="" -> BadRequestException "Data source name not specified."; CreateType with format=YAML -> BadRequestException "Unable to parse provided type definition."; CreateFunction with a requestMappingTemplate over 65536 -> BadRequestException "Invalid request template given, must be less than 64kb in size."; CreateResolver with code="" -> BadRequestException "Code must be provided for the provided runtime." and with code over 32768 bytes -> BadRequestException "Code must be 32768 bytes or less"; CreateResolver with fieldName="" -> BadRequestException "Field name not specified."
Emulator: answers its own wording instead — "The data source name is invalid. Please refer to the documentation for more details.", "Invalid format YAML given", "Invalid requestMappingTemplate given. Must be between 1 and 65536 characters long.", and the generic "1 validation error detected: Value '' at 'code' failed to satisfy constraint: Member must have length greater than or equal to 1".
Why: AWS distinguishes "not specified" from "invalid"; clients and fixtures key off that text.
Fix: the message strings in CreateDataSource / CreateType / CreateFunction / CreateResolver validation.
Traces: appsync.create-data-source-empty-name-rejected, appsync.create-type-unlisted-format-rejected, appsync.create-function-request-template-over-max-length-rejected, appsync.create-function-response-template-length-bounds-rejected, appsync.create-resolver-code-beyond-32768-bytes-rejected

Cause 6 of 10: pattern-constrained identifiers are pattern-checked instead of being looked up or refused in AppSync's words.
AWS: these members are not refused with the modeled regex message. CreateFunction with a hyphenated dataSourceName -> the name is LOOKED UP, so NotFoundException "Data source not found.". DeleteFunction with a digit-led functionId -> NotFoundException "Function not found." and the existing function survives. CreateResolver with a hyphenated or over-long fieldName -> BadRequestException "The field name name is invalid. Please refer to the documentation for more details." (fixed text; "name" is literal in AWS's message). ListApiKeys with a nextToken holding a space, and CreateResolver with a digit-led typeName, are likewise not refused with the generic "Member must satisfy regular expression pattern" text.
Emulator: refuses each with BadRequestException "1 validation error detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[_A-Za-z][_0-9A-Za-z]*$" (or ^[\S]+$ for nextToken), and in the fieldName-at-65536-characters case ACCEPTS the call and creates the resolver.
Why: a client asking for a resource under a malformed id gets a validation error instead of the not-found it handles, and a 65536-character field name becomes a resolver AWS would never have created.
Fix: these operations' handlers — resolve identifiers by lookup and use AppSync's own messages; drop the generic pattern pass on these members.
Traces: appsync.create-function-data-source-name-pattern-rejected, appsync.delete-function-pattern-violating-function-id-rejected, appsync.create-resolver-type-name-leading-digit-rejected, appsync.resolver-field-name-outside-pattern-rejected, appsync.create-resolver-field-name-at-model-maximum-rejected, appsync.list-api-keys-whitespace-next-token-rejected

Cause 7 of 10: an over-long dataSourceName is a not-found instead of an invalid-input.
AWS: CreateFunction with a dataSourceName of 65536 or more characters -> BadRequestException "The DataSource is invalid. Please refer to the documentation for more details.", while a short name that simply matches nothing -> NotFoundException "Data source not found.".
Emulator: answers NotFoundException "Data source not found." for the over-long name too, collapsing the two classes.
Why: a client cannot tell a malformed request from a missing resource, so it retries a request that can never succeed.
Fix: CreateFunction's dataSourceName validation, ahead of the lookup.
Traces: appsync.create-function-long-data-source-name-rejected

Cause 8 of 10: tag key charset and length are not enforced, and the charset refusal is worded wrongly.
AWS: Smithy com.amazonaws.appsync#TagKey is @length 1..128 with pattern ^(?!aws:)[ a-zA-Z+-=._:/]+$, so a 129-character key or a key holding '#' is refused. AppSync's message for a charset violation is BadRequestException "Tags can only contain letters, numbers, spaces, and the following special characters: _ . : / = + - @" (fixed text, names no key).
Emulator: CreateApi ACCEPTS a 129-character tag key and ACCEPTS the key 'cost#centre' (the API is created carrying it), and UntagResource refuses a '#' key with its own "Invalid tag key <key>: a key must be between 1 and 128 characters long, cannot begin with aws:, and can only contain letters, numbers, spaces and the characters + - = . _ : /".
Why: tags AWS rejects become real state here, so a client's tag-based addressing and policy checks behave differently than on AWS.
Fix: tag-key validation shared by CreateApi/CreateGraphqlApi/TagResource/UntagResource, plus the charset message text.
Traces: appsync.create-api-tag-key-over-128-characters-rejected, appsync.create-event-api-tag-key-outside-charset-rejected, appsync.untag-resource-tag-key-outside-charset-rejected

Cause 9 of 10: tag/key count caps are applied in the wrong direction.
AWS: CreateApi carrying 51 tags -> BadRequestException "The resultant tag set must not have more than 50 user tags.", and an empty tag map -> ValidationException "1 validation error detected: Value at 'tags' failed to satisfy constraint: Member must have length greater than or equal to 1". UntagResource naming 51 keys SUCCEEDS with HTTP 204, removing the keys the resource holds and ignoring the absent ones (Smithy models TagKeyList @length max 50, but the recording shows the cap is not enforced on this call — do not derive it from the model).
Emulator: refuses 51 tags with the generic "1 validation error detected: Value '{...}' at 'tags' failed to satisfy constraint: Member must have length less than or equal to 50", and refuses the 51-key UntagResource with BadRequestException "1 validation error detected: Value '[...]' at 'tagKeys' failed to satisfy constraint: Member must have length less than or equal to 50" instead of performing it.
Why: a legitimate bulk untag is rejected outright, so the client's tags are never removed.
Fix: CreateApi tag-count validation message, and removal of the tagKeys list cap in UntagResource.
Traces: appsync.create-event-api-tag-count-outside-bounds-rejected, appsync.untag-resource-fifty-one-keys-in-one-call

Cause 10 of 10: UntagResource's bad-ARN message omits the expected region.
AWS: UntagResource given a resourceArn that is longer than the ARN maximum / names another region -> BadRequestException "Invalid input resource arn: expected region <region>", where <region> is the endpoint's region taken from the request context.
Emulator: answers BadRequestException "Invalid input resource arn" with the ": expected region <region>" tail missing.
Why: the client loses the one piece of information in the message that says why the ARN was refused.
Fix: UntagResource's resourceArn validation message.
Traces: appsync.untag-resource-overlong-foreign-region-arn-rejected
