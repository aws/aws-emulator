# stepfunctions: a Task's Credentials.ExternalId (reference form ExternalId.$) is rejected by CreateStateMachine's ASL schema validator, so no cross-account/ExternalId task-credentials behaviour can exist

> _Note: this issue was identified against the code base at commit `1ade082ac7b155d62ba7589cf4124913a2bd40fe`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStateMachine

## Description
One net-new root cause, reached through CreateStateMachine alone.

Cause 1 of 1: the ASL definition validator does not know the `ExternalId` member of a Task state's `Credentials` object, so every state machine that supplies one is refused at creation and the whole ExternalId behaviour behind it (the default Step Functions passes, a caller override, and STS's own ExternalId character bound) is unreachable. Failing check ids: lambda__stepfunctions.task-credentials-external-id-default-and-custom-match-succeed, lambda__stepfunctions.task-credentials-external-id-mismatch-and-too-short-rejected.

AWS:      Smithy com.amazonaws.sfn#CreateStateMachine takes `definition` (Definition, @length 1-1048576, @sensitive) and models InvalidDefinition (client error, HTTP 400) for a definition the service refuses; the ASL schema itself is not in the Smithy model, so what the schema admits is recorded behavior only plus AWS's documentation of Task credentials (https://docs.aws.amazon.com/step-functions/latest/dg/tutorial-access-cross-acct-resources.html). A Task state's `Credentials` object accepts BOTH `RoleArn` and `ExternalId`, each in a literal form and in the `.$` reference/intrinsic form. The recordings create, with no error at all, a state machine whose Task carries `"Credentials": {"RoleArn.$": "$.roleArn", "ExternalId.$": "$.extid"}` — i.e. CreateStateMachine answers 200 and returns a stateMachineArn. The behaviour that definition then exhibits, also from the recordings: (a) with NO Credentials.ExternalId, Step Functions assumes the task role passing the state machine's own ARN as the ExternalId, so a role whose trust Condition is `StringEquals sts:ExternalId == <that state machine ARN>` is assumed successfully and the Task's output carries the Lambda Payload; (b) a role whose trust Condition requires some other ExternalId is refused, the execution ends FAILED with error `States.TaskFailed` and cause exactly `The role <execution-role ARN> is not authorized to assume the task state's role, <task-role ARN>.` (fixed text: `The role `, ` is not authorized to assume the task state's role, `, and the closing period; the two ARNs are the variable parts, taken from the state machine's roleArn and the Task's resolved Credentials.RoleArn), and the execution carries no `output`; (c) a supplied `ExternalId.$` REPLACES that default, so the role of (a) then refuses with the same States.TaskFailed cause; (d) a role with no sts:ExternalId condition is assumed either way; (e) an ExternalId outside STS's own 2-1224 character bound is refused before the assume is attempted — status FAILED, error `States.Runtime`, cause `An error occurred while executing the state '<state name>' (entered at the event id #<id>). The Credentials '<the Credentials map, JSON-serialized with its members sorted: {"ExternalId":"<value>","RoleArn":"<arn>"}>' could not be used to start the Task: ['ExternalId' must be between 2 and 1224 characters, containing only letters, numbers, plus (+), equals (=), comma (,), period (.), at (@), colon (:), forward slash (/), and hyphen (-)]` (fixed text: everything outside the angle brackets, including the bracketed STS constraint sentence; the state name, event id, and the serialized Credentials map are filled from the definition and the resolved input).

Emulator: CreateStateMachine refuses the definition outright with HTTP 400 InvalidDefinition and the message `Invalid State Machine Definition: 'SCHEMA_VALIDATION_FAILED: Field 'ExternalId.$' is not supported at /States/Invoke/Credentials'` — `ExternalId.$` is reported as an unsupported field of `Credentials`, where AWS accepts it. Both checks die on that call before any execution is started, so none of (a)-(e) is observed; by the second check's own comment the literal (non-`.$`) `ExternalId` form is likewise refused at CreateStateMachine time.

Why:      a client relying on AWS's behavior cannot deploy any state machine that uses Task credentials with an ExternalId — the standard confused-deputy pattern AWS documents for cross-account Task roles. CreateStateMachine fails at deploy time with InvalidDefinition, so a CDK/CloudFormation/SDK deploy of such a workflow rolls back, and a client that validates the ExternalId boundary (that the default is the state machine ARN, that an override replaces it, that a mismatch is denied, that a too-short value is rejected) can observe none of it. The refusal also mislabels a valid definition as a schema violation, so an operator debugging it edits a definition that is already correct.

Fix:      the ASL definition schema/validator for the Task state's `Credentials` object in the Step Functions service (the seam that produces `SCHEMA_VALIDATION_FAILED: Field '<x>' is not supported at /States/<state>/Credentials`): admit `ExternalId` and `ExternalId.$` alongside `RoleArn`/`RoleArn.$`. Then the interpreter's task-credentials assume seam must pass the state machine ARN as the default ExternalId, let a resolved `ExternalId.$` override it, evaluate the target role's `sts:ExternalId` trust condition, and validate the resolved value against STS's 2-1224 character/charset bound before the assume — surfacing the two failure shapes above (States.TaskFailed with Step Functions' not-authorized-to-assume sentence; States.Runtime with the Credentials-could-not-be-used sentence).

Related open issues that do NOT carry these two checks: 20261109T210043Z-lambda-stepfunctions-8-net-new-causes-step-functions-ignores-task.md (Task Credentials ignored) and 20261125T001009Z-stepfunctions-5-net-new-causes-credentials-assume-denial.md (its cause 1 is the WORDING of a refused assume for a Credentials.RoleArn-only definition). Neither reports that `ExternalId` is rejected by the definition schema, and neither names these check ids.

Traces:   lambda__stepfunctions.task-credentials-external-id-default-and-custom-match-succeed, lambda__stepfunctions.task-credentials-external-id-mismatch-and-too-short-rejected.

## Steps to Reproduce
1. CreateRole an execution role trusting states.amazonaws.com (inline grant: sts:AssumeRole on the task roles below). CreateFunction a trivial python handler returning {"ok": True} with its own lambda.amazonaws.com role.
2. Call CreateStateMachine (type STANDARD, roleArn = the execution role) with definition:
   {"StartAt":"Invoke","States":{"Invoke":{"Type":"Task","Resource":"arn:aws:states:::lambda:invoke","Credentials":{"RoleArn.$":"$.roleArn","ExternalId.$":"$.extid"},"Parameters":{"FunctionName":"<function ARN>","Payload.$":"$"},"End":true}}}
   Expected: HTTP 200 with a stateMachineArn.
   Actual:   HTTP 400 InvalidDefinition, message "Invalid State Machine Definition: 'SCHEMA_VALIDATION_FAILED: Field 'ExternalId.$' is not supported at /States/Invoke/Credentials'".
3. Repeat step 2 with the literal form "Credentials":{"RoleArn":"<task role ARN>","ExternalId":"my-external-id"}: AWS accepts it; the emulator refuses it the same way.
4. Once step 2 is accepted, the behaviour behind it must hold. Create a second machine whose Credentials is {"RoleArn.$": "$.roleArn"} only, and three task roles trusting the execution role: (a) Condition {"StringEquals":{"sts:ExternalId":"<machine-2 ARN>"}}, (b) Condition {"StringEquals":{"sts:ExternalId":"<a custom id>"}}, (c) no Condition. Each grants lambda:InvokeFunction on the function.
   - StartSyncExecution machine-2 with {"roleArn":"<role a>"}: expect SUCCEEDED and output["Payload"]["ok"] == true (proves the default ExternalId is the state machine's own ARN).
   - StartSyncExecution machine-1 with {"roleArn":"<role b>","extid":"<that custom id>"}: expect SUCCEEDED.
   - StartSyncExecution machine-2 with {"roleArn":"<role c>"}: expect SUCCEEDED.
   - StartSyncExecution machine-1 with {"roleArn":"<role a>","extid":"<the custom id>"}: expect FAILED, error "States.TaskFailed", cause "The role <exec-role ARN> is not authorized to assume the task state's role, <role a ARN>.", and no "output" member.
   - StartSyncExecution machine-1 with {"roleArn":"<role c>","extid":"a"}: expect FAILED, error "States.Runtime", cause "An error occurred while executing the state 'Invoke' (entered at the event id #2). The Credentials '{\"ExternalId\":\"a\",\"RoleArn\":\"<role c ARN>\"}' could not be used to start the Task: ['ExternalId' must be between 2 and 1224 characters, containing only letters, numbers, plus (+), equals (=), comma (,), period (.), at (@), colon (:), forward slash (/), and hyphen (-)]", and no "output" member.
