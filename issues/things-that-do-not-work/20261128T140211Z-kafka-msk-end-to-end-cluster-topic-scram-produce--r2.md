=== Cause 1 of 2: the PROVISIONED cluster / SCRAM-association / topic / delete lifecycle never settles, so every waiter burns the whole budget and the post-delete NotFoundException contract is unverifiable ===
AWS: Smithy com.amazonaws.kafka#Kafka — CreateClusterV2 (POST /api/v2/clusters, code 200; input member ClusterName @length 1..64, Provisioned → ProvisionedRequest; output State → enum ClusterState) returns the ClusterArn with the cluster CREATING, and the cluster then reaches ACTIVE observably through DescribeClusterV2 (GET /api/v2/clusters/{ClusterArn}, code 200; output ClusterInfo → Cluster; errors include NotFoundException httpError 404). BatchAssociateScramSecret (POST /v1/clusters/{ClusterArn}/scram-secrets, code 200) returns an empty UnprocessedScramSecrets for a well-formed KMS-encrypted AmazonMSK_* secret. CreateTopic (POST /v1/clusters/{ClusterArn}/topics, code 200; required TopicName, PartitionCount @range min 1, ReplicationFactor @range min 1; output Status → enum TopicState) returns CREATING and DescribeTopic (GET /v1/clusters/{ClusterArn}/topics/{TopicName}, code 200; output Status; errors include NotFoundException 404) then reports ACTIVE. After DeleteTopic and DeleteCluster, DescribeTopic and DescribeClusterV2 each answer HTTP 404 with Error.Code `NotFoundException`; AWS's message for that class is the entirely fixed text `The requested resource doesn’t exist.` — no ARN, cluster name or topic name is interpolated into it. Recorded behavior for the cadence: a client polling DescribeClusterV2 at ~30 s and DescribeTopic at ~5 s sees the whole create → ACTIVE → topic ACTIVE → delete → NotFound sequence complete in a handful of intervals.
Emulator: the sequence ListKafkaVersions → CreateConfiguration(allow.everyone.if.no.acl.found=false) → CreateClusterV2(kafka.m5.large, NumberOfBrokerNodes 2, two private ClientSubnets, Sasl.Scram+Sasl.Iam, EncryptionInTransit.ClientBroker=TLS, that ConfigurationInfo) → poll DescribeClusterV2 for State ACTIVE → BatchAssociateScramSecret → CreateTopic → poll DescribeTopic for Status ACTIVE → GetBootstrapBrokers → DeleteTopic/DeleteCluster → NotFoundException never produces a state the check can assert on: it is killed at the ceiling with no frame. Hypothesis (the replay output names no frame, so the evidence does not state this): each asynchronous transition is owed to a wall clock instead of being settled on the write path, so the FIRST probe after every write always observes the non-terminal value and the caller is charged a full poll interval per transition.
Why: a client that provisions an MSK cluster and a topic and waits for them at an AWS-appropriate cadence pays a full interval per transition the emulator had in fact already decided, so emulator-backed suites stall on sequences real MSK completes; and because the run never gets to the deletes, a client cannot verify that a deleted topic and a deleted cluster resolve to 404 NotFoundException with that fixed message at all.
Fix: the kafka crate's state layer plus the CreateClusterV2 / BatchAssociateScramSecret / CreateTopic / DeleteTopic / DeleteCluster handlers — settle these transitions on the write path (or make them complete-on-return) so a first probe after a write observes the terminal value, and make the deleted topic and deleted cluster resolve to NotFoundException with AWS's fixed message text.

=== Cause 2 of 2: nothing serves the Kafka wire protocol on the in-VPC SASL/SCRAM and SASL/IAM endpoints the emulator's own control plane advertises ===

The data-plane semantics are recorded behavior plus the Apache Kafka protocol: an in-VPC client reaching each advertised host:port has its TCP connection accepted, completes TLS, completes SASL_SSL/SCRAM-SHA-512 on the SASL/SCRAM listener and SASL_SSL/OAUTHBEARER (a SigV4-presigned kafka-cluster:Connect token) on the SASL/IAM listener, can grant Kafka ACLs through CreateAcls over the IAM listener (MSK exposes no control-plane API for Kafka ACLs), and a record produced to the control-plane-created topic is consumed back from `earliest` by a fresh consumer group.
Emulator: the check never reaches a produce or a consume, and never grants the SCRAM principal its ACLs over the advertised SASL/IAM listener — the run ends on the bare 60.0 s ceiling. Because the emulator itself announces those bootstrap addresses, a listener that does not answer is the emulator's own gap: it announced an address other than one it serves. The particular advertised host:port a run sees is a per-run value and is not a requirement; the requirement is that whatever endpoint GetBootstrapBrokers advertises accept a connection and complete the handshake.
Why: a client that configures itself from GetBootstrapBrokers hangs until its own timeout, and the one guarantee a faked data plane cannot meet — a record produced over SASL/SCRAM being read back from the topic the control plane created, and the topic/cluster then deleting cleanly — is unverifiable.
Fix: the kafka service must serve the Kafka wire protocol on the ports it advertises (a broker listener, per-scheme SASL authentication for SCRAM-SHA-512 and IAM OAUTHBEARER, the Kafka ACL admin APIs, and the record/partition/offset state the produce and fetch paths read and write), or advertise only endpoints it serves.
