# arc-region-switch: an approval step's timeout ends the execution planExecutionTimedOut instead of pausing it pausedByFailedStep, and GetPlanExecution's execution-not-found message is emulator-authored (2 causes)

## Description
Two distinct net-new root causes in the arc-region-switch emulator, both grounded in failing behavioral checks of this suite. Each cause must be closed before submitting; they are numbered Cause 1 of 2 and Cause 2 of 2 and each names its own failing check ids. Not part of this bundle and deliberately skipped: the CancelPlanExecution and ListPlansInRegion scaffold stubs (the suite marks their checks ALREADY FILED) and the open issue 20261109T123922Z-arc-region-switch-cloudformation-aws-arcregionswitch-plan-is.md, which owns the two arc-region-switch__cloudformation failures. === Cause 1 of 2: a manual-approval step that times out undecided is treated as a terminal plan timeout (step canceled, execution planExecutionTimedOut, endTime stamped) instead of a failed step that PAUSES the execution (step failed, execution pausedByFailedStep, no endTime, stepFailed + stepPausedByError events) ===
Failing checks: arc-region-switch.approval-step-timeout-pauses-execution-by-failed-step, arc-region-switch.skip-timed-out-approval-step-completes-with-exceptions, arc-region-switch.skip-not-started-step-rejected.
AWS: Smithy (com.amazonaws.arcregionswitch): ExecutionApprovalConfiguration.timeoutMinutes (Integer, range min 1, default 60) bounds how long a ManualApproval execution block waits; StepStatus models notStarted | running | failed | completed | canceled | skipped | pendingApproval, ExecutionState models inProgress | pausedByFailedStep | pausedByOperator | completed | completedWithExceptions | canceled | planExecutionTimedOut | pendingManualApproval | failed | pending | completedMonitoringApplicationHealth, and ExecutionEventType models both stepFailed and stepPausedByError. GetPlanExecution.endTime is optional ("The time (UTC) when the plan execution ended"), i.e. it is present only on an execution that has ended. Recorded behavior (AWS plan-execution lifecycle, https://docs.aws.amazon.com/r53recovery/latest/dg/plan-execution-lifecycle-rs.html): when nobody approves a ManualApproval step before its timeoutMinutes elapse, the STEP reaches its own negative outcome and reads status `failed`; the EXECUTION does NOT end — it moves to `pausedByFailedStep`, reports NO endTime, logs both a `stepFailed` and a `stepPausedByError` event (and no `executionSucceeded`), is listed by ListPlanExecutions(state="pausedByFailedStep") and no longer by ListPlanExecutions(state="pendingManualApproval"), and stays open to the operator: UpdatePlanExecutionStep(actionToTake="skip") on the failed step is accepted and moves it to `skipped` so the next step starts (and the later, not-yet-started step is refused with "Wait for the step to start before skipping" while it reads notStarted), and CancelPlanExecution ends it as `canceled`. `planExecutionTimedOut` is the state for the PLAN EXECUTION's own overall timeout, not for one approval block expiring.
Emulator: the approval-window branch of the clock-driven progression marks the step `canceled`, sets executionState to `planExecutionTimedOut`, stamps endTime, pushes a single `executionFailed` event (with the approval-timeout reason) and finishes the execution — releasing the plan and making the execution terminal. GetPlanExecution therefore reads ('planExecutionTimedOut', {<step>: 'canceled'}) where AWS reads ('pausedByFailedStep', {<step>: 'failed'}); no stepFailed/stepPausedByError events are recorded; the execution carries an endTime; and because it is terminal every operator action that AWS still allows on a paused execution (skip the failed step, then approve the next one; cancel to `canceled`) is unreachable.
Why: a client that drives an approval gate gets the opposite contract. A timed-out approval looks like a whole-plan timeout that has already ended, so an operator runbook can no longer skip the stuck step and continue the switch, state-machine code branching on pausedByFailedStep never fires, step-level triage that distinguishes `failed` (the step's own negative outcome) from `canceled` (stopped from outside) cannot tell them apart, event-driven tooling waiting on stepFailed/stepPausedByError sees only executionFailed, and the endTime a client uses to decide "this execution is over" is present on an execution AWS considers still running.
Fix: the plan-execution progression in the service state — the approval-window-closed transition in the settle/advance state machine must mark the step failed, set the execution to pausedByFailedStep WITHOUT an endTime, leave the execution non-terminal (keep it holding its plan and keep it out of the terminal/finish path), and append the stepFailed and stepPausedByError events; the UpdatePlanExecutionStep skip path must then accept a skip of that failed step and refuse a not-yet-started later step.
Traces: arc-region-switch.approval-step-timeout-pauses-execution-by-failed-step (assertion on executionState after the 1-minute timeout), arc-region-switch.skip-timed-out-approval-step-completes-with-exceptions (same assertion before the skip), arc-region-switch.skip-not-started-step-rejected (reads ('planExecutionTimedOut', {FirstGate: 'canceled', SecondGate: 'notStarted'})); file/line citation: services/service-com-amazonaws-arcregionswitch-arcregionswitch/src/state.rs lines 1544-1560 (the ApprovalWindowClosed arm) and src/ops/get_plan_execution.rs line 209 (the settle call that materialises it).

=== Cause 2 of 2: GetPlanExecution's ResourceNotFoundException message for an execution id the plan never issued uses an emulator-authored template that echoes the region-prefixed id and the plan ARN ===
Failing checks: arc-region-switch.get-plan-execution-unknown-execution-id-not-found, arc-region-switch.get-plan-execution-steps-follow-approvals-unissued-execution-rejected.
AWS: Smithy: GetPlanExecution declares ResourceNotFoundException (errorKind client, httpError 404, required member `message`, doc "The specified resource was not found. HTTP Status Code: 404"); executionId is required and is carried on the wire as "<region>/<16 hex digits>". Recorded behavior: for a well-formed executionId that the addressed plan never issued, AWS answers 404 ResourceNotFoundException whose message fixed text is "Execution not found for execution: " followed by ONE variable part — the BARE execution id, i.e. only the 16-hex-digit part after the "<region>/" prefix of the request's executionId. The message names neither the region nor the plan ARN.
Emulator: the status and code are correct (404 ResourceNotFoundException), but the message is "No execution <full region-prefixed executionId> found for plan <planArn>" — different fixed text, the region prefix left on the id, and an extra plan-ARN part AWS does not emit.
Why: a client that branches on, logs, localizes or asserts the service's execution-not-found text never matches, and anything that parses the id out of the message to retry or correlate reads a region-prefixed id plus noise instead of the bare id AWS reports. The emulator is also internally inconsistent with the plan-not-found wording this service already uses.
Fix: the ResourceNotFoundException construction in the GetPlanExecution handler's execution-lookup path (emit "Execution not found for execution: <bare execution id>", splitting the "<region>/" prefix off the request's executionId); the same template should be used wherever an execution lookup misses.
Traces: arc-region-switch.get-plan-execution-unknown-execution-id-not-found, arc-region-switch.get-plan-execution-steps-follow-approvals-unissued-execution-rejected; file/line citation: services/service-com-amazonaws-arcregionswitch-arcregionswitch/src/ops/get_plan_execution.rs lines 213-223.
