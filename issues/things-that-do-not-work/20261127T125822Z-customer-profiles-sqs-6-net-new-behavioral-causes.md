# customer-profiles__sqs: 6 net-new behavioral causes — the dead-letter queue is never probed or authorized on CreateDomain/UpdateDomain, FIFO queues are accepted, and no ingestion failure is ever dead-lettered

> _Note: this issue was identified against the code base at commit `cd3ed932ac942c4bb826a6f713c43cf93575b0d9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomain

## Description
Six distinct root causes in the customer-profiles emulator's dead-letter-queue surface, all grounded in failing behavioral checks of the customer-profiles__sqs suite (0/8 passed). THIS ISSUE HAS 6 CAUSES; all six must be fixed before it is closed.

Cause 1 of 6: CreateDomain accepts a DeadLetterQueueUrl that Customer Profiles may not send to — the queue is never probed for authorization.
AWS: Smithy CreateDomain -> POST /domains/{DomainName}; DeadLetterQueueUrl (sqsQueueUrl, length 0-255) is documented "The URL of the SQS dead letter queue, which is used for reporting errors associated with ingesting data from third party applications. You must set up a policy on the DeadLetterQueue for the SendMessage operation to enable Amazon Connect Customer Profiles to send messages to the DeadLetterQueue." BadRequestException (client, httpError 400) is modeled. Recorded behavior: CreateDomain publishes a test message to the named queue as part of the call; when that publish is not permitted — the queue policy has no sqs:SendMessage grant for the profile.amazonaws.com service principal, or explicitly denies it, or grants it only under a condition that names a different domain's source ARN — the call is refused 400 BadRequestException with Message "Failed to publish test SQS message to your queue: <queue-url>. Please check if the queue has a policy that enables Amazon Connect Customer Profiles to send messages to it. " (note the trailing space). Fixed text is everything but <queue-url>; the single variable part is the DeadLetterQueueUrl taken from the request, and no domain is created.
Emulator: HTTP 200, and the domain is created and echoes the DeadLetterQueueUrl in CreateDomain's and GetDomain's projection, for all three unauthorized queue shapes.
Why: the whole point of the member is a queue the service can actually write to. A client is told error reporting is wired up when nothing will ever be delivered; ingestion failures are then lost silently, and the modeled BadRequestException path AWS clients code against is unreachable.
Fix: CreateDomain's DeadLetterQueueUrl validation — perform the authorization-checked test publish (evaluating the queue's policy for sqs:SendMessage by profile.amazonaws.com with the request's source account/domain) and refuse with AWS's fixed sentence, creating no domain (services/service-com-amazonaws-customerprofiles-customerprofiles-20200815/src/ops/create_domain.rs).
Traces: checks customer-profiles__sqs.create-domain-with-dlq-closed-to-profiles-rejected, customer-profiles__sqs.domain-dead-letter-queue-without-send-grant-rejected, customer-profiles__sqs.dead-letter-grant-scoped-to-other-domain-arn-rejected.

Cause 2 of 6: CreateDomain accepts a FIFO queue as the dead-letter queue.
AWS: same CreateDomain surface and BadRequestException as Cause 1. Recorded behavior: a FIFO queue (name ending ".fifo", FifoQueue=true) is refused even when its policy does grant sqs:SendMessage to profile.amazonaws.com, with the same 400 BadRequestException and the same fixed sentence "Failed to publish test SQS message to your queue: <queue-url>. Please check if the queue has a policy that enables Amazon Connect Customer Profiles to send messages to it. " (the service's test publish carries no MessageGroupId, so a FIFO queue cannot accept it); afterwards the domain does not exist — GetDomain answers 404 ResourceNotFoundException "Domain <DomainName> is not found". A standard queue with the same grant is accepted.
Emulator: HTTP 200 and the domain is created naming the .fifo queue.
Why: a client wires error reporting to a queue AWS would have rejected; every later dead-letter publish is undeliverable, and the domain exists where AWS left none, so cleanup and idempotent-create logic diverge too.
Fix: the same CreateDomain dead-letter validation path — the test publish must fail for a FIFO queue and be reported with AWS's sentence.
Traces: check customer-profiles__sqs.domain-fifo-dead-letter-queue-rejected.

Cause 3 of 6: CreateDomain never publishes the test message to an authorized dead-letter queue.
AWS: recorded behavior — when the named queue does grant sqs:SendMessage to profile.amazonaws.com for the caller's account, CreateDomain succeeds AND exactly one message with body "{}" arrives on that queue; GetDomain then reports the same DeadLetterQueueUrl and the DefaultExpirationDays that was set.
Emulator: the queue stays empty; the check waits for the message and is cut off by its 60 s budget. The domain itself is created and echoes the URL.
Why: the test publish is the service's own proof that the queue is usable, and operators and automation assert on it. Without it a domain can be created against a queue nothing will ever reach, and the only positive signal AWS gives is missing. It is also the mechanism Cause 1 and Cause 2 rest on, so it must exist for those refusals to be real.
Fix: CreateDomain's dead-letter wiring — send the "{}" probe to the queue through the emulator's SQS state on success.
Traces: check customer-profiles__sqs.domain-dead-letter-queue-gets-test-message-and-reads-back.

Cause 4 of 6: UpdateDomain moves the dead-letter queue to one Customer Profiles may not send to, instead of refusing and keeping the prior queue.
AWS: Smithy UpdateDomain -> PUT /domains/{DomainName}, same DeadLetterQueueUrl member and BadRequestException. Recorded behavior: pointing an existing domain at a queue whose policy carries no send grant for profile.amazonaws.com is refused 400 BadRequestException with the same fixed sentence "Failed to publish test SQS message to your queue: <queue-url>. Please check if the queue has a policy that enables Amazon Connect Customer Profiles to send messages to it. " (variable part: the DeadLetterQueueUrl from the request), and GetDomain still names the previously configured queue. Once the grant is added the same UpdateDomain succeeds, answers the new URL, the new queue receives the "{}" test message, and an empty-string DeadLetterQueueUrl clears the member without touching DefaultExpirationDays.
Emulator: HTTP 200 and the domain is updated to the ungranted queue (the response and GetDomain both name it), so the prior queue is lost.
Why: a client can silently detach error reporting from a working queue and attach it to an unreachable one; the documented "refused, prior value kept" guarantee that makes the update safe to retry is gone.
Fix: UpdateDomain's DeadLetterQueueUrl validation — same authorization-checked test publish as CreateDomain, refusing without mutating state (.../src/ops/update_domain.rs).
Traces: check customer-profiles__sqs.update-domain-to-ungranted-queue-rejected-keeps-prior-queue.

Cause 5 of 6: a profile object that matches no profile under a type with AllowProfileCreation off is never dead-lettered.
AWS: recorded behavior (https://docs.aws.amazon.com/connect/latest/adminguide/profile-matching.html) — PutProfileObject of an object whose PROFILE key value matches no existing profile, for an object type created with AllowProfileCreation=false, is answered normally but the object is rejected into the domain's dead-letter queue: one SQS message whose Body is the submitted object JSON verbatim and whose message attributes are exactly DomainName=<the domain>, ObjectTypeName=<the object type> and Message="Profile Creation is not allowed" (that Message attribute is fixed text). No profile is created for it, while a twin object whose key names an existing profile attaches to that profile and is NOT dead-lettered; the queue settles back to zero messages.
Emulator: no message ever arrives on the domain's dead-letter queue; the check is cut off by its 60 s budget while polling the queue for the unmatched object.
Why: the dead-letter queue is the only channel reporting ingestion rejections. Without it a client sees an accepted PutProfileObject and no profile and no error — the data is dropped with no diagnosis, and the attribute contract (DomainName/ObjectTypeName/Message) that consumers route on does not exist.
Fix: the PutProfileObject ingestion path and the domain's dead-letter emitter — on an unattachable object, publish the object body plus those three message attributes to the domain's DeadLetterQueueUrl (.../src/ops/put_profile_object.rs and the domain dead-letter state).
Traces: check customer-profiles__sqs.unmatched-object-without-profile-creation-lands-in-domain-dlq.

Cause 6 of 6: a profile object whose only PROFILE key value is shared by two profiles is never dead-lettered.
AWS: recorded behavior — PutProfileObject of an object whose single PROFILE key value resolves to more than one profile attaches it to neither and dead-letters it: one SQS message whose Body is the submitted object JSON verbatim and whose attributes are exactly DomainName=<the domain>, ObjectTypeName=<the object type> and Message="All keys of this object are binding to more than one profiles" (fixed text, including the plural "profiles"). Both sharing profiles end up holding no objects, while an object whose key value names a single profile attaches to it and is not dead-lettered; the queue then settles at zero.
Emulator: no dead-letter message is produced for the ambiguous object; the check is cut off by its 60 s budget.
Why: ambiguous-key rejection is invisible — a client cannot tell an ambiguous object from a stored one, and the distinct Message attribute AWS uses to separate this failure class from "Profile Creation is not allowed" is never emitted, so consumers cannot route or alert on it.
Fix: the PutProfileObject key-resolution path — detect a key value binding to more than one profile, attach to neither, and dead-letter with that fixed Message attribute.
Traces: check customer-profiles__sqs.object-key-matching-two-profiles-attaches-to-neither-and-dead-letters.
