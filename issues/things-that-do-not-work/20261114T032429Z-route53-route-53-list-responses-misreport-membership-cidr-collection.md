## Description
FOUR net-new causes on the Route 53 listing surface, all service=route53, none carrying stub_path and none carrying owned_by in this replay. Causes 1-3 are the same defect observed on three separate fixtures; cause 4 is a distinct defect on the hosted-zone listing. ALL FOUR must be closed before this issue is submitted.

Cause 1 of 4 - ListCidrCollections reports no row a client can match to a collection the account holds (fixture route53-cidr-collection-basic-lifecycle, step task#3, ListCidrCollections, status 200 vs 200; the same cluster also covers task#4 of that fixture).

CollectionSummary carries Arn (target ARN, @length 20..2048, pattern \S, documented 'The ARN of the collection summary. Can be used to reference the collection in IAM policy or cross-account'), Id (UUID, pattern ^[0-9a-f]{8}-(?:[0-9a-f]{4}-){3}[0-9a-f]{12}$), Name (CollectionName) and Version (CollectionVersion, range min 1). The ARN layout itself is recorded behavior only: the recording shows one CollectionSummary per collection the account holds, with Arn made of the fixed text 'arn:aws:route53:::cidrcollection/' - Route 53 is a global service, so BOTH the region field and the account field are empty - followed by that collection's own Id, with Name as created and Version the collection's current counter. The ids, names and version numbers in the replay detail are per-run fixture values and are not requirements; the layout and the per-collection row are.
Emulator: every collection the fixture created is absent from the response when the reported rows are matched to the recorded ones by Arn. Replay detail for this step: '$.ListCidrCollectionsResponse.CidrCollections.member[Arn="arn:aws:route53:::cidrcollection/f7734658-832c-32e6-d3a5-d865597c1303"]: missing (expected {...}, got None)' and the same for the step's second collection. The projection builds each row's Arn through the shared helper cidr_collection_arn, which renders an account-populated ARN, so a reported row reads 'arn:aws:route53::<account>:cidrcollection/<id>' and matches no ARN a client holds.
Why: a client that enumerates CIDR collections and keys them by ARN - to look a collection up, to compare against the ARN another Route 53 response returned, or to write an IAM policy Resource element - finds no row for a collection that demonstrably exists, so account-wide enumeration and ARN-equality reconciliation both fail.
Fix: the ListCidrCollections response projection and the shared CIDR-collection ARN rendering it uses (the CollectionSummary construction in the operation's handler and the shared ARN helper in the service's state module): Route 53 resource ARNs must render both the region and the account fields empty. Hypothesis: the ARN layout is the whole of this divergence, because the collections are in state (the same fixtures' later per-collection calls succeed). If the rows are still absent after the layout is corrected, the deeper defect is in the listing's read of collection state and must be fixed there too - do not close causes 1-3 on the ARN edit alone without re-replaying all three fixtures.

Cause 4 of 4 - ListHostedZones serializes HostedZone.Features as an empty element instead of the zone's features configuration (fixture route53-list-hosted-zones-membership-and-by-vpc, step task#6, ListHostedZones, status 200 vs 200).
AWS: Smithy - ListHostedZones, GET /2013-04-01/hostedzone, success 200, output HostedZones (required) -> HostedZones of HostedZone; HostedZone.Features targets HostedZoneFeatures and is optional (required members are Id, Name, CallerReference only). The model's HostedZoneFeatures declares AcceleratedRecoveryStatus and FailureReasons and does NOT declare the member the wire carries here, so this one is recorded behavior only: the recorded ListHostedZonesResponse reports, for each hosted zone it lists, a Features element containing a PublicDNSFallbackStatus child whose value is the zone's fallback state ('DISABLED' for a zone on which it was never enabled). The requirement is that Features, when serialized, carries the zone's actual features configuration as child elements; the zone names in the replay detail are per-run fixture values.
Emulator: every listed zone's Features is present but empty. Replay detail: '$.ListHostedZonesResponse.HostedZones.HostedZone[Name="..."].Features: type_mismatch (expected {'PublicDNSFallbackStatus': 'DISABLED'}, got '')' for both zones of the step. The shared hosted-zone projection (zone.to_hosted_zone(), called per row at services/service-com-amazonaws-route53-awsdnsv20130401/src/ops/list_hosted_zones.rs:250) opens a HostedZoneFeatures container with no member set, so the serializer emits '<Features></Features>'.
Why: an SDK client deserializes the present-but-empty element into a non-null features object with every child null. Code that reads a zone's public-DNS fallback status from a listing - to report it, to decide whether to toggle it, or to reconcile a fleet of zones - reads null where AWS reports DISABLED, and a strict shape comparator sees a structure where a structure with one member is required.
Fix: the shared hosted-zone projection in the service's state module (to_hosted_zone) and the HostedZone features serialization it feeds, so Features reports the zone's stored features configuration including its public-DNS fallback status rather than an empty container. Related but NOT covering it: open issue 20261108T200652Z-route53-route-53-gethostedzone-serializes-an-empty-hostedzone-features.md owns the GetHostedZone step where AWS OMITS Features entirely; its replay key is GetHostedZone-only and its requirement is the opposite one (omit when unset), so it neither exercises nor fixes this listing step, where AWS emits Features WITH a child.
