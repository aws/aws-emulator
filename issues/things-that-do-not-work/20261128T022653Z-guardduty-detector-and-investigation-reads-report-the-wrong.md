# guardduty: detector and investigation reads report the wrong response member set (2 causes)

> _Note: this issue was identified against the code base at commit `7c00a94e367da23ce2c3f6798a9a0f3f9bd5c557`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDetector

## Description
Two causes (2 of 2 below), both in this GuardDuty crate's read-response projection: a 200 answer whose status line and most members agree with the recording, but whose MEMBER SET does not — one read drops members GuardDuty serves, the other invents a member GuardDuty does not serve for that read. Both are shaping defects in the projection that builds the response body, not in request handling: no status, error class or error message diverges in either cluster.

Cause 1 of 2 — GetDetector's deprecated `dataSources` view omits the per-source `updatedAt` instants and the whole `database` (RDS Protection) node. Fixture `guardduty-detector-basic-lifecycle`, step `task#3` (representative; 7 steps in the cluster).
AWS: RECORDED BEHAVIOR ONLY for the members at issue. Smithy (services/service-com-amazonaws-guardduty-guarddutyapiservice/smithy-model/com-amazonaws-guardduty-guarddutyapiservice.json) models GetDetector as GET /detector/{DetectorId}, success 200, output member `DataSources` -> `DataSourceConfigurationsResult` (jsonName `dataSources`, @deprecated "use Features instead"), whose declared members are only `cloudTrail`/`dnsLogs`/`flowLogs`/`s3Logs` (each required, each a structure carrying just `status`: DataSourceStatus), plus optional `kubernetes.auditLogs.status` and `malwareProtection.scanEc2InstanceWithFindings.ebsVolumes.{status,reason}` / `malwareProtection.serviceRole`. The public model therefore declares NEITHER an `updatedAt` on a data-source node NOR a `database` node — but the recorded GuardDuty response for this read carries both: an `updatedAt` on every data-source node (`cloudTrail`, `dnsLogs`, `flowLogs`, `s3Logs`, `kubernetes.auditLogs`, `malwareProtection.scanEc2InstanceWithFindings.ebsVolumes`), each held in the fixture as a shaped, non-asserted expectation (a timestamp whose value varies per run), and a `dataSources.database` node of the form `{"rds": {"databaseEvents": {"status": <DataSourceStatus>, "updatedAt": <timestamp>}}}`, the data-source view of RDS Protection. The requirement is the MEMBER SET and the derivation, not any one recording's instants: each node's `updatedAt` is the instant the switch governing that data source last changed (the same instant the `features` view reports for the governing feature), and `database.rds.databaseEvents.status` is the status of the RDS-login/database-events protection switch for the detector being read — `DISABLED` on a detector that never enabled it. The recording's literal timestamps are fill-ins and are not part of the contract.
Emulator: the 200 response's `dataSources` nodes carry `status` only, and there is no `database` node at all. Replay reports, on an otherwise matching 200: `$.dataSources.cloudTrail.updatedAt`, `$.dataSources.dnsLogs.updatedAt`, `$.dataSources.flowLogs.updatedAt`, `$.dataSources.s3Logs.updatedAt`, `$.dataSources.kubernetes.auditLogs.updatedAt` and `$.dataSources.malwareProtection.scanEc2InstanceWithFindings.ebsVolumes.updatedAt` all `missing (expected '<shaped-not-asserted>', got None)`, and `$.dataSources.database` `missing (expected {'rds': {'databaseEvents': {'status': 'DISABLED', 'updatedAt': '<shaped-not-asserted>'}}}, got None)`. The crate's own GetDetector header comment states the opposite of what it ships — it claims this service's model copy declares both an `updatedAt` on every data-source node and `dataSources.database.rds.databaseEvents` — so the omission is a half-finished intent, not a decision: the model copy does not declare them, and because the body is serialized from the schema a member the model copy does not carry cannot be emitted at all.
Why: a client reading the deprecated `dataSources` view to learn WHEN a data source last changed finds no `updatedAt` and has to treat the switch as timeless, so change-detection and drift-reporting code keyed to those instants silently sees nothing; a client that reads RDS Protection through this view (`dataSources.database.rds.databaseEvents.status`) finds the node absent and cannot distinguish "RDS Protection disabled" from "this response does not report it", which in a strongly-typed SDK surfaces as a missing-key/None where AWS always supplies a status. Both failures are invisible on the status code: the response is a clean 200.
Fix: the deprecated `DataSources` projection in state — `data_source_configurations_view` — together with this service's Smithy model copy, which must declare the two extra members before the schema-driven serializer can emit them (the sibling `member_data_source_configuration_view` reads the detector view through the same projection, so fixing it once fixes `GetMemberDetectors` too). The data this needs is already stored and already projected elsewhere: the per-feature `updated_at_millis` the `features` view reports, reachable through the existing `feature_data_source` helper that returns exactly a (status, updated_at_millis) pair and is not used by this view, and the RDS-protection feature switch. Do not derive the instants from the read's clock. Traces/line citations below.
Traces: guardduty-detector-basic-lifecycle#task#3 (representative), guardduty-detector-basic-lifecycle#task#5, guardduty-detector-duplicate-create-error#task#3, guardduty-detector-features-and-tags#task#2, guardduty-detector-features-and-tags#task#4, guardduty-detector-lifecycle-basic#task#2, guardduty-detector-lifecycle-basic#task#5 — divergence key `service=guardduty|GetDetector|status=200->200|keys=$.dataSources.cloudTrail.updatedAt,$.dataSources.database,$.dataSources.dnsLogs.updatedAt,$.dataSources.flowLogs.updatedAt,$.dataSources.kubernetes.auditLogs.updatedAt,$.dataSources.malwareProtection.scanEc2InstanceWithFindings.ebsVolumes.updatedAt,$.dataSources.s3Logs.updatedAt`.

Cause 2 of 2 — GetInvestigation serves an `investigation.scope` object on a read where GuardDuty serves none (operation GetInvestigation). Fixture `guardduty-tagging-created-with-tags`, step `setup#4` (representative; 2 steps in the cluster).
AWS: Smithy `Investigation$Scope` -> `InvestigationScope` (jsonName `scope`, OPTIONAL) is documented as "Information about what the investigation analyzed, including the investigation type, the finding, account, or organization that was analyzed, and, for ACCOUNT and ORGANIZATION investigations, the time window over which the investigation queried data. Returned only when the investigation status is COMPLETED"; `InvestigationScope` carries `investigationType` (FINDING|ACCOUNT|ORGANIZATION), `findingId`/`accountId`/`adminAccountId` — "Only the identifier that matches InvestigationType is set" — and `queryTimeWindow`. GetInvestigation is GET /detector/{DetectorId}/investigation/{InvestigationId}, success 200. Beyond "returned only when COMPLETED" the model states no rule for when the member is present, so for this read it is RECORDED BEHAVIOR ONLY: the recorded GuardDuty 200 for this read — the plain, non-STRUCTURED read of the same investigation that carries a `summary` — contains NO `scope` member at all. The requirement is that `scope` is an optional member GuardDuty omits for this read, so an emulator must omit it too rather than synthesize one. Hypothesis (neither modeled nor recorded): GuardDuty emits `scope` only alongside the structured summary form (SummaryFormat=STRUCTURED) or only for investigations whose pass resolved a reportable subject, which is why the recorded text-format read has none.
Emulator: the 200 response carries a fabricated scope on every settled investigation. Replay reports `$.investigation.scope: type_mismatch (expected None, got {'investigationType': 'ACCOUNT', 'accountId': '<account>', 'queryTimeWindow': {'startTime': <epoch>, 'endTime': <epoch>}})` — an ACCOUNT-type scope with the caller's account and a query window derived from the emulator's clock. The account id and the two epoch instants in the replayed value are this run's fill-ins, not part of any requirement; what diverges is the member's PRESENCE. The handler populates it unconditionally from the stored record (`scope: investigation.scope_details()`), gated on nothing but the pass having settled, and the same stored scope is also what the STRUCTURED branch zips with the analysis — so the member is served on the text-format read as well, where GuardDuty serves nothing.
Why: `scope` is how a caller learns what an investigation actually analyzed. A client written against AWS that branches on the member's presence — "did this read come back with a scope?" — takes the wrong branch against the emulator, and one that trusts the fabricated contents is told the investigation covered a whole ACCOUNT over a clock-derived time window that no GuardDuty pass reported. Code that round-trips the read back into a request, or that asserts the documented "only the identifier matching InvestigationType is set" invariant, is reasoning about a subject the service never claimed.
Fix: the `Investigation$Scope` projection in this crate's GetInvestigation handler (src/ops/get_investigation.rs, the `scope:` member of the `Investigation` it builds) and/or the stored scope the investigation pass settles: the member must be served only under the condition GuardDuty serves it, and omitted on the plain text-format read the fixture records. Every other member of the response — `investigationId`, `status`, `triggerPrompt`, `triggeredBy`, `metadata`, `cloud`, `riskLevel`, `risk`, `confidence`, `startTime`, `endTime` — replays clean and must not change.
Related, NOT a duplicate: the open issue 20261127T073833Z-guardduty-getinvestigation-serves-an-emulator-authored-investigation-summary.md covers the OTHER diverging key of this same cluster, `$.investigation.summary` (the emulator-authored Markdown report), and says nothing about `scope`; the replay no longer reports this cluster as owned by it, because the cluster's key now carries `$.investigation.scope` as well. Fixing the summary alone leaves this cluster mismatched. No other open guardduty issue (the entity-set ResourceNotFoundException bundle, the StartMalwareScan refusal, the malware-scan flow, the events/GuardDuty plan bundle) touches either cause in this issue.
Traces: guardduty-tagging-created-with-tags#setup#4 (representative) and guardduty-tagging-round-trip#setup#4 — divergence key `service=guardduty|GetInvestigation|status=200->200|keys=$.investigation.scope,$.investigation.summary`.
