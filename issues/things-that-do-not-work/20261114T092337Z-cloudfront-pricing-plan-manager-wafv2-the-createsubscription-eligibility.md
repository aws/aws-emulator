# cloudfront__pricing-plan-manager__wafv2: the CreateSubscription eligibility check never reaches a verdict — cancelling an ACTIVE FREE subscription never completes, so the check's post-cancel poll exhausts the run budget

> _Note: this issue was identified against the code base at commit `029c732db8092362c2d6a7aa89bcc4c3ae279d73`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelSubscription

## Description
One root cause, grounded in the single surviving failure of this suite run: check cloudfront__pricing-plan-manager__wafv2.create-subscription-without-webacl-association-rejected ends with "Check timed out after 60.0s" and never reaches a verdict on the behaviour it exists to assert.

Context, so this is not re-filed as something it is not: the eligibility refusal this check opens with was the subject of the FIXED issue 20261109T121305Z-cloudfront-pricing-plan-manager-wafv2-createsubscription-does-not.md, and that fix is in place (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/state/resource_eligibility.rs now asks CloudFront for the distribution's WebACLId and refuses with ValidationException "The following resources are not eligible for this subscription tier: <arn>."). The call is NOT refused any more, so this is not a REOPENS of that issue. What stops the check now is the end of the same scenario. The open WIRE issue 20261111T105841Z-pricing-plan-manager-cancelling-a-free-subscription-never-completes-and-publishes.md reports the same emulator behaviour from the wire corpus (fixture pricing-plan-manager-cloudfront-flat-rate-subscription-lifecycle) and carries no key for this behavioural check; this issue is the behavioural grounding of it and should be closed together with it.

Cause 1 of 1: CancelSubscription on an ACTIVE FREE-tier subscription parks the record on a calendar-month boundary instead of completing the cancellation, so GetSubscription keeps answering 200 ACTIVE forever and every client that cancels-then-waits-for-the-resource-to-disappear hangs.
AWS: Smithy (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/smithy-model/com-amazonaws-pricingplanmanager-awspricingplanmanager.json): CancelSubscription (POST /v1/CancelSubscription) takes arn @required and ifMatch @required bound to the If-Match header and answers 200 with the Subscription payload plus the ETag header; GetSubscription models ResourceNotFoundException (httpError 404, required members message + resourceId, doc "The specified subscription was not found. Verify that the ARN is correct and that the subscription belongs to your account."). CancelSubscription's own doc says "For active subscriptions, the cancellation is scheduled to take effect at the end of the current billing period" and "For subscriptions in PENDING_APPROVAL status, the subscription is deleted immediately"; ScheduledChange.effectiveDate is documented as "populated after the change is confirmed by the billing system". Recorded behavior for the FREE CloudFront tier this check exercises: after CancelSubscription with the CURRENT eTag the subscription reaches its terminal state inside the check's poll window — GetSubscription answers HTTP 404, Error.Code "ResourceNotFoundException", Error.Message "Subscription not found: <arn>. Verify the ARN is correct and the subscription exists in your account." (fixed text "Subscription not found: " and ". Verify the ARN is correct and the subscription exists in your account.", with the ARN copied from the request) — and ListSubscriptions stops reporting it. Hypothesis: a FREE-tier subscription carries no billing commitment, so there is no period to run out and the cancellation is processed promptly; what the recordings fix is that the terminal state IS reached, not an exact delay.
Emulator: services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/cancel_subscription.rs lines 215-225 attach a ScheduledChangeRecord{change_type: Cancellation, effective_date: Some(end_of_billing_period(now))} to any non-PENDING_APPROVAL record and leave status ACTIVE; src/state.rs lines 407-436 (apply_due_changes) only remove the record once the clock passes that stored instant, which is the first instant of the NEXT calendar month. Inside any one session the record is therefore never due, GetSubscription keeps answering 200 with status "ACTIVE" and the pending change attached, and the check's cancel-and-wait helper (its only remaining unbounded wait: a 120 s poll at 5 s intervals for ResourceNotFoundException, which outlives the suite's 60 s per-check cap) is what the run budget ends on — the check is reported as "Check timed out after 60.0s" with no verdict on the eligibility refusal or on the positive control it had already exercised. The 404 the emulator does eventually produce for a missing subscription also carries the emulator-authored message "no subscription with ARN <arn>" rather than AWS's sentence above (cancel_subscription.rs lines 183-191 and the GetSubscription handler); that wording is part of this same cause, not a separate claim.
Why: cancellation is the only observable end of a subscription's life. A client written against AWS cancels and then waits for the resource to disappear — that is what every teardown, every IaC destroy and every "is this resource still billing?" reconciliation does — and against the emulator it waits forever and is killed by its own timeout. Everything keyed on "a non-terminated subscription covers this resource" also stays armed forever: the CloudFront web-ACL removal lock and the resource-already-subscribed refusal can never be released in the correct order, the emulator's own MAX_SUBSCRIPTIONS capacity (src/state.rs line 46) is consumed by cancelled subscriptions, and dependent cross-service checks cannot clean up after themselves.
Fix: CancelSubscription's handler (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/cancel_subscription.rs, the arm that attaches the pending change) together with the scheduled-change processing in crate::state (src/state.rs apply_due_changes) — complete the cancellation for a subscription with no billing commitment (the FREE tier, alongside the PENDING_APPROVAL case the handler already deletes immediately) by removing the record, so GetSubscription answers the modeled ResourceNotFoundException (404) with AWS's message and ListSubscriptions stops reporting it; and in the handler's not-found/refusal arms use AWS's wording rather than the emulator's own.
Traces: cloudfront__pricing-plan-manager__wafv2.create-subscription-without-webacl-association-rejected.
