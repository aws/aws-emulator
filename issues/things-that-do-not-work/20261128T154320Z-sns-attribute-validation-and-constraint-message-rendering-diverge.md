# sns: attribute validation and constraint-message rendering diverge across PublishBatch, ArchivePolicy, tags and ReplayPolicy

> _Note: this issue was identified against the code base at commit `c8af1db729b355d4375dc5660957683cc548873e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PublishBatch

## Description
Seven independent root causes in the emulator's SNS validation and attribute surface: refusals that should happen do not, refusals that happen carry the wrong code, and the constraint-violation message renderer does not reproduce AWS's wording. All seven are grounded in replayed wire fixture steps, listed per cause under Traces. 9 divergence clusters in total.

Cause 1 of 7: PublishBatch faults the whole call instead of answering 200 with per-entry `Failed` rows.
  AWS: Smithy: PublishBatch takes `PublishBatchRequestEntries` (required list) and answers `PublishBatchResponse{Successful: PublishBatchResultEntryList, Failed: BatchResultErrorEntryList}`; its modeled call-level errors are the batch-wide ones (EmptyBatchRequest, BatchEntryIdsNotDistinct, TooManyEntriesInBatchRequest, BatchRequestTooLong, InvalidBatchEntryId, NotFound, AuthorizationError, InvalidParameter...). A per-entry parameter fault is NOT a call-level error: it comes back inside `Failed` as `{Id: <the entry's Id>, Code: "InvalidParameter", SenderFault: "true", Message: <the message Publish would use for that parameter>}`, with HTTP 200, and this holds even when EVERY entry is invalid — `Successful` is then empty and `Failed` holds one row per entry. The recorded response shows exactly that: three `Failed` rows keyed by the submitted entry Ids with messages `Invalid parameter: Empty message`, `Invalid parameter: Subject`, `Invalid parameter: Message Structure - No default entry in JSON message body` (fixed text per fault class; the `Id` values come from the request), an empty `Successful` member and a `ResponseMetadata.RequestId`.
  Emulator: the call is refused HTTP 400 with no `PublishBatchResponse` body at all — the first entry's per-entry message is hoisted to the call level — so no `Failed`/`Successful` partition is ever produced and valid sibling entries are not published.
  Why: a client that batches publishes loses every good message in the batch when one entry is malformed, and code that reads `response["Failed"]` to retry only the bad entries gets a thrown exception instead; partial-failure handling cannot be exercised at all.
  Fix: PublishBatch's handler and its per-entry validation — validate inside the entry loop and append a BatchResultErrorEntry (the entry's Id, Code=InvalidParameter, SenderFault=true, the Publish-equivalent message) instead of returning a call-level refusal; only batch-wide faults abort the call, and the serializer must emit both members at HTTP 200. The same root cause is described from the behavioral corpus in open issue 20261127T235209Z-sns-5-net-new-causes-publishbatch-faults-the.md (Cause 1 of 5); that issue does not carry these wire replay keys, so this bundle files them.
  Traces: publish-batch-every-entry-refused-answers-200#task#2 (expected 200 with three Failed rows, got 400; cluster also covers publish-batch-refused-entries-beside-accepted#task#2).

Cause 2 of 7: SetTopicAttributes accepts an `ArchivePolicy` whose `MessageRetentionPeriod` is not a valid value, and stores it.
  AWS: Smithy: SetTopicAttributes takes `AttributeName`/`AttributeValue` and models InvalidParameterException (awsQueryError code `InvalidParameter`, HTTP 400). An `ArchivePolicy` whose `MessageRetentionPeriod` is outside the accepted grammar (e.g. `0`, or a non-numeric string such as `abc`) is refused with HTTP 400, `ErrorResponse.Error` `{Type: Sender, Code: InvalidParameter, Message: "Invalid parameter: ArchivePolicy: MessageRetentionPeriod value is invalid"}` plus a `RequestId`. The message is entirely fixed text — it names the attribute and the member, not the submitted value. The topic keeps the previously stored policy, so a subsequent GetTopicAttributes still reports the last valid value (in the recording, `{"MessageRetentionPeriod":"1"}`).
  Emulator: every such SetTopicAttributes answers HTTP 200 with no `ErrorResponse`, and the invalid value is written into topic state — GetTopicAttributes then reports `ArchivePolicy` as `{"MessageRetentionPeriod":"0"}` and `{"MessageRetentionPeriod":"abc"}` instead of the retained valid value.
  Why: a client can install an archive policy AWS rejects; the topic then advertises a retention period that cannot exist, so retention/replay logic reads a meaningless value, and the refuse-and-keep-prior-state invariant every IaC update path depends on is absent.
  Fix: SetTopicAttributes' validation of the `ArchivePolicy` attribute (and the shared attribute-value validator it dispatches through) — parse `MessageRetentionPeriod`, refuse out-of-grammar values with the message above, and leave the stored policy untouched on refusal.
  Traces: sns-archive-policy-message-retention-period-grammar#task#4 (expected 400 InvalidParameter, got 200; cluster also covers task#6, task#8, task#10), sns-archive-policy-message-retention-period-grammar#task#5 (GetTopicAttributes reports the rejected value; cluster also covers task#7), sns-archive-policy-message-retention-period-grammar#task#9 (same, with the non-numeric value; cluster also covers task#11).

Cause 3 of 7: GetTopicAttributes never reports `BeginningArchiveTime` for a topic with an active archive policy.
  AWS: Smithy: GetTopicAttributes answers `Attributes` (TopicAttributesMap). While a topic holds an active `ArchivePolicy`, the attribute map additionally carries a `BeginningArchiveTime` entry giving the earliest timestamp still inside the archive window (its value is a per-run timestamp and is not part of the requirement — only the presence of the key is).
  Emulator: the `Attributes` map contains no `BeginningArchiveTime` entry at all.
  Why: a client cannot discover how far back a topic's archive reaches, so a replay whose StartingPoint must fall inside the archive window cannot be planned, and any code branching on the presence of `BeginningArchiveTime` to detect an archiving topic concludes archiving is off.
  Fix: GetTopicAttributes' attribute projection / topic state — derive and emit `BeginningArchiveTime` whenever the topic's ArchivePolicy is active.
  Traces: sns-archive-policy-message-retention-period-grammar#task#9 (BeginningArchiveTime entry missing; cluster also covers task#11).

Cause 4 of 7: the constraint-violation message truncates the offending value instead of rendering it in full.
  AWS: a value that violates a modeled length constraint is refused HTTP 400 with the standard validation wording `N validation error detected: Value '<the submitted value>' at '<member path>' failed to satisfy constraint: Member must have length less than or equal to <max>`. The fixed text is `... validation error detected: Value '`, `' at '`, `' failed to satisfy constraint: Member must have length less than or equal to `; the variable parts are the submitted value — quoted IN FULL, however long — the member path, and the limit from the model. Smithy: Tag.Value targets `TagValue` with `@length max 256`; ListTagsForResource.ResourceArn targets `AmazonResourceName` with `@length min 1 max 1011`.
  Emulator: the status, code and limit are right, but the value is cut off and replaced with an elision plus a byte count — `Value 'boundary-value-vvv...' at 'tags.1.member.value' ... [257 bytes]'` and `Value 'arn:aws:sns:...' at 'resourceArn' ... [1012 bytes]'` — so the message text differs from AWS's for exactly the inputs that trigger it.
  Why: the offending value is the one thing the message exists to report; a client or test that echoes, logs or asserts on the refusal text sees emulator-specific wording and a fabricated `[<n> bytes]` token that AWS never emits, and cannot recover which value was rejected from the message.
  Fix: the shared constraint-violation message renderer used by sns' input validation — quote the submitted value verbatim and in full, with no length cap and no byte-count suffix.
  Traces: sns-create-topic-tag-value-length-bounds#task#3 (CreateTopic, tags.1.member.value, max 256), sns-list-tags-for-resource-arn-length-bounds#task#3 (ListTagsForResource, resourceArn, max 1011).

Cause 5 of 7: a list-member constraint violation is reported at the member path instead of at the list path with the bracketed list value and the composite constraint clause.
  AWS: Smithy: UntagResource.TagKeys targets `TagKeyList`, whose member `TagKey` is `@length min 1 max 128`. A too-long key is refused HTTP 400 with the violation attributed to the LIST member and the whole list rendered: `1 validation error detected: Value '[<key>, ...]' at 'tagKeys' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]`. Fixed text: `validation error detected: Value '`, the bracketed rendering of the submitted list, `' at 'tagKeys' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]`; both bounds come from the model and both are always listed, in that order.
  Emulator: it reports the single member instead — `Value '<key>' at 'tagKeys.1.member' failed to satisfy constraint: Member must have length less than or equal to 128` — dropping the brackets, using the indexed member path, and emitting only the bound that was violated rather than the composite `Member must satisfy constraint: [...]` clause.
  Why: clients and tests that match SNS's list-constraint wording do not recognise the refusal, and the message no longer shows which list was submitted, only the one element the emulator picked.
  Fix: the constraint-violation renderer's handling of list-typed members in sns' input validation — attribute the violation to the list member, render the submitted list bracketed, and emit the composite `Member must satisfy constraint: [<max rule>, <min rule>]` clause.
  Traces: sns-untag-resource-tag-key-length-bounds#task#2 (cluster also covers task#3).

Cause 6 of 7: ListTagsForResource with an empty `ResourceArn` is refused as a length-constraint violation instead of an ARN-parse refusal.
  AWS: an empty ResourceArn is refused HTTP 400 with `Code: InvalidParameter` and `Message: "Invalid parameter: ResourceArn Reason: An ARN must have at least 6 elements, not 1"` — SNS parses the ARN and reports the structural fault; the fixed text is `Invalid parameter: ResourceArn Reason: An ARN must have at least 6 elements, not ` and the trailing count is the number of colon-delimited elements actually submitted. Smithy: ListTagsForResource models InvalidParameterException (awsQueryError code `InvalidParameter`, HTTP 400).
  Emulator: `Code: ValidationError` with `Message: "1 validation error detected: Value '' at 'resourceArn' failed to satisfy constraint: Member must have length greater than or equal to 1"` — a different error code and a different message class. `ValidationError` is not among ListTagsForResource's modeled errors.
  Why: a client that branches on the error code (retry, surface to the user, map to an exception type) takes the wrong branch, because the SDK raises a validation error rather than `InvalidParameterException`, and the message never says the ARN was unparseable.
  Fix: ListTagsForResource's input validation / ARN parsing — parse the ResourceArn and raise the InvalidParameter ARN-structure refusal above (the modeled error) instead of letting the generic length-constraint validator answer first.
  Traces: sns-list-tags-for-resource-arn-length-bounds#task#4.

Cause 7 of 7: Subscribe accepts a `ReplayPolicy` with an invalid `PointType` (and an invalid starting point) and mints a subscription.
  AWS: Smithy: Subscribe takes `Attributes` (SubscriptionAttributesMap) and models InvalidParameterException (awsQueryError code `InvalidParameter`, HTTP 400). A ReplayPolicy whose `PointType` is not one of the accepted values is refused with HTTP 400 and `ErrorResponse.Error` `{Type: Sender, Code: InvalidParameter, Message: "Invalid parameter: Attributes Reason: ReplayPolicy: Invalid PointType"}` plus a `RequestId`; the message is entirely fixed text, and `Attributes Reason:` is how SNS marks a fault inside the Attributes map. No subscription is created.
  Emulator: the call answers HTTP 200 with a `SubscriptionArn` and no `ErrorResponse`, so the unusable replay policy is stored on a live subscription.
  Why: a client can create a subscription whose replay configuration AWS would reject; the subscription then exists with a policy no replay can honour, replay never starts, and the configuration error surfaces only against real AWS.
  Fix: Subscribe's validation of the `ReplayPolicy` subscription attribute — validate `PointType` (and the starting point it implies) against the accepted values and refuse with the message above before any subscription is created.
  Traces: sns-replay-policy-point-type-and-starting-point-validation#task#3 (cluster also covers task#4 and task#5).
