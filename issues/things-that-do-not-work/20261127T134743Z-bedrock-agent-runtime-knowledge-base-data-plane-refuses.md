# bedrock-agent-runtime knowledge-base data plane refuses three modeled request members: 3 net-new causes — RetrieveAndGenerateStream rejects generationConfiguration.promptTemplate, GetDocumentContent rejects outputFormat=EXTRACTED, Rerank rejects an unissued nextToken

> _Note: this issue was identified against the code base at commit `461e190cfbed2a60f922688bafee74a0fd88eec8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RetrieveAndGenerateStream

## Description
Three distinct root causes, each an emulator refusal of a request member the Smithy model declares valid. All three are in the bedrock-agent-runtime service; each must be closed before this issue is submitted.

Cause 1 of 3: RetrieveAndGenerateStream refuses generationConfiguration.promptTemplate outright.
AWS: Smithy: RetrieveAndGenerateStream (POST /retrieveAndGenerateStream) takes retrieveAndGenerateConfiguration -> RetrieveAndGenerateConfiguration -> knowledgeBaseConfiguration -> generationConfiguration: GenerationConfiguration, whose members are promptTemplate (PromptTemplate{textPromptTemplate, @length 1..4000, @sensitive}), guardrailConfiguration, inferenceConfig, additionalModelRequestFields and performanceConfig. promptTemplate is an ordinary optional member, documented as "Contains the template for the prompt that's sent to the model for response generation" — AWS ACCEPTS it and streams the response; it is not a refusable member.
Emulator: any RetrieveAndGenerateStream carrying that member is refused with HTTP 400 ValidationException and the emulator-authored message "retrieveAndGenerateConfiguration.knowledgeBaseConfiguration.generationConfiguration.promptTemplate: it is the prompt a model is asked to generate the response from, and no model is asked anything in this emulator, so a template cannot change what the response says; omit it to take the response this service composes from the retrieved passages". The member path is the only request-derived part; the rest of the sentence is fixed text AWS never emits. Because the refusal is unconditional, it also masks the behavior other checks grade: the numberOfResults check gets this promptTemplate refusal where it expected numberOfResults=100 to be ACCEPTED (and numberOfResults=101 to be refused with "1 validation error detected: Value '101' at 'retrieveAndGenerateConfiguration.knowledgeBaseConfiguration.retrievalConfiguration.vectorSearchConfiguration.numberOfResults' failed to satisfy constraint: Member must have value less than or equal to 100"), and the additionalModelRequestFields check never reaches its own assertion.
Why: a client cannot use RetrieveAndGenerateStream at all with a prompt template — the standard way to control grounded generation — and every request carrying one fails validation; worse, the unrelated numberOfResults constraint can never be exercised because the request is rejected first.
Fix: the request validation of the RetrieveAndGenerateStream handler — accept generationConfiguration.promptTemplate (validating only textPromptTemplate's 1..4000 length) and stream the response rather than refusing.
Traces: retrieve-and-generate-stream-citation-events-locate-the-ingested-object, retrieve-and-generate-stream-number-of-results-above-limit-rejected, retrieve-and-generate-stream-rejects-an-unknown-model-field-in-stream.

Cause 2 of 3: GetDocumentContent refuses outputFormat=EXTRACTED, a value in its own modeled enum.
AWS: Smithy: GetDocumentContent.outputFormat targets DocumentOutputFormat, an enum with values [RAW, EXTRACTED]. EXTRACTED is served: the response carries mimeType "application/json" and a presignedUrl to the parsed JSON of the document. AWS refuses EXTRACTED only when it is combined with mediaId, with ValidationException "OutputFormat EXTRACTED cannot be used when mediaId is supplied" (fixed text, no interpolation), and refuses an out-of-enum value with "1 validation error detected: Value '<value>' at 'outputFormat' failed to satisfy constraint: Member must satisfy enum value set: [EXTRACTED, RAW]" (the submitted value is the only variable part).
Emulator: plain outputFormat=EXTRACTED (no mediaId) is refused with HTTP 400 ValidationException and the emulator-authored message "outputFormat: EXTRACTED is not an output format this service holds a document in — no document parser runs here, so the parsed text of a document does not exist to be handed out; ask for RAW to read the document as it was ingested". So a value in the modeled enum is unreachable, and the two refusals AWS does define (EXTRACTED+mediaId, and an out-of-enum value) can never be observed.
Why: a client reading the parsed form of an ingested document gets a 400 for a modeled enum value, and a client that keys on AWS's EXTRACTED-with-mediaId refusal sentence never sees it because the request dies earlier with different wording.
Fix: the outputFormat handling in the GetDocumentContent handler — serve EXTRACTED (application/json + presignedUrl), and reserve ValidationException for the mediaId combination and out-of-enum values, with AWS's wording.
Traces: get-document-content-media-id-with-extracted-format-rejected.

Cause 3 of 3: Rerank refuses a nextToken it did not issue instead of answering as the untokened request.
AWS: Smithy: Rerank.nextToken targets NextToken (@length 1..2048, pattern ^\S*$) and the operation is @paginated (inputToken nextToken / outputToken nextToken / items results). A well-formed nextToken that AWS never issued is not an error for Rerank: the request is answered exactly as the untokened one — every source ranked once, best match first, and no nextToken in the response, because a Rerank answer carries the complete ranking of the sources it was given. ValidationException is modeled (httpError 400) for malformed input, not for an unrecognised cursor.
Emulator: the request is refused with HTTP 400 ValidationException and the emulator-authored message "nextToken is not a pagination token this service issued: a Rerank response carries the complete ranking of the sources it was given". The member name is the only request-derived part; the rest is fixed text AWS never emits.
Why: any client, SDK paginator or retry layer that replays a cached or stale cursor gets a hard 400 where AWS returns the full ranking, so a resumable-looking call becomes a fatal error.
Fix: the nextToken handling in the Rerank handler's validation — validate only the modeled length/pattern and ignore an unrecognised token, answering as the untokened request with no nextToken in the response. (Distinct from the open issue 20261122T160452Z-bedrock-agent-runtime-rerank-relevancescore-values-diverge-from-aws-emulator-s.md, which concerns the relevanceScore VALUES of an accepted Rerank; this cause is the refusal of the request itself.)
Traces: rerank-unissued-next-token-ignored.
