# Lightsail static catalog reads serve emulator-authored rows: GetBlueprints, GetBundles, GetRegions

> _Note: this issue was identified against the code base at commit `2500a4daac20cde0616d8d78af54e2cda83d8b28`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprints, GetBundles, GetRegions

## Description
FOUR net-new root causes, all in the static reference tables behind Lightsail's read-only catalog operations (GetBlueprints, GetBundles, GetRegions). Every one of the four answers HTTP 200 with a correctly shaped, correctly membered envelope, so no client can detect any of them from the response envelope: the fault is entirely in the CONTENTS of the tables - wrong column values, derived instead of published numbers, and whole tiers of rows that are not served at all (which also shifts every later list index). All four causes must be closed before submitting.

Cause 1 of 4: GetBlueprints serves emulator-authored description prose and non-AWS product/licence URLs on every blueprint row, and the tail of the catalog is missing.
AWS: Smithy com.amazonaws.lightsail#GetBlueprints is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBlueprints, success 200, httpBindingsInert) whose output member `blueprints` is a BlueprintList of com.amazonaws.lightsail#Blueprint (members blueprintId, name, group, type [BlueprintType os|app], description "The description of the blueprint", isActive, minPower, version, versionCode, productUrl "The product URL to learn more about the image or blueprint", licenseUrl "The end-user license agreement URL for the image or blueprint", platform [InstancePlatform], appCategory). The model fixes no values, so the table's contents are recorded behavior only: the recording shows AWS serving, per row, its own full marketplace description paragraph for that image, a productUrl under the AWS Marketplace host (aws.amazon.com/marketplace/pp/<prodview-id>) and a licenseUrl under the AWS EULA host (d7umqicpi7263.cloudfront.net/eula/product/<id>/<id>.txt), and a catalog of 39 rows. The generic requirement is that these columns carry AWS's own catalog text and AWS-hosted URLs; the specific paragraphs, prodview ids and EULA ids in the recording are that template filled in by one capture, not requirements in themselves.
Emulator: blueprintId, name, group, type, isActive, minPower, version and versionCode are now served correctly, but `description` is a generated one-liner of the form "<name> operating system image for a Lightsail instance.", `productUrl` points at the upstream vendor's own site and `licenseUrl` at the vendor's licensing page. Replay reports verdict host_not_own for productUrl on essentially every row and for licenseUrl on the Windows/app rows (e.g. row 0 windows_server_2025: productUrl got 'https://www.microsoft.com/en-us/windows-server' where AWS serves 'https://aws.amazon.com/marketplace/pp/prodview-g76csvka4r3by'; licenseUrl got 'https://www.microsoft.com/licensing/docs/view/Product-Terms' where AWS serves the d7umqicpi7263.cloudfront.net EULA URL). The last asserted positions ($.blueprints[32]..$.blueprints[38]) are absent entirely: the emulator's list is shorter than AWS's.
Why: a client that renders a blueprint description to a user, or follows the product/licence link to present terms before launching an image, gets emulator prose and a link on a host AWS never returns - and a blueprint that is not listed at all cannot be selected, so any workflow that filters the catalog for a tail entry finds nothing.
Fix: the static instance-blueprint catalog table backing the GetBlueprints handler in the lightsail crate - the description, productUrl and licenseUrl columns on all rows, plus the missing tail rows. Not handler, validation or serializer logic: status, member set and envelope are already correct.
Traces: lightsail-catalog-get-blueprints#task#1.

Cause 2 of 4: the GetBlueprints table omits the Windows SQL Server application blueprint tier, so the Linux block starts early and every later index is shifted.
AWS: recorded behavior only - the model constrains no row set (Blueprint carries type os|app, platform WINDOWS|LINUX_UNIX and minPower, but no enumeration of rows). The recording shows the Windows SQL Server app blueprints positioned after the plain Windows Server OS blueprints and before the first Linux entry: at the asserted position AWS serves blueprintId 'windows_server_2022_sql_2019_express' (name 'SQL Server 2019 Express', group 'windows_2022_sql_exp_2019', type 'app', platform 'WINDOWS', minPower 2000) with its marketplace description and AWS-hosted product/licence URLs.
Emulator: that position holds 'amazon_linux_2023' (group 'amazon-linux', type 'os', platform 'LINUX_UNIX', minPower 0) - no Windows SQL Server row appears anywhere in the list - so the Linux block begins one tier early and every subsequent position is off by the number of absent rows. Status 200 -> 200.
Why: no SQL-Server instance workflow can be driven against the emulator at all, because the blueprint it must name is not offered. In addition a client reading the catalog by position gets an os/LINUX_UNIX row with minPower 0 where AWS serves an app/WINDOWS row with minPower 2000, which silently permits pairing a blueprint with a bundle whose `power` AWS would refuse.
Fix: the same static blueprint catalog table - add the missing Windows SQL Server app rows in AWS's order with their type/group/platform/minPower values. Listed separately from cause 1 because it is a missing-row fault rather than a wrong-column fault and correcting the served rows' columns does not close it.
Traces: lightsail-catalog-and-operations-lifecycle#task#4.

Cause 3 of 4: GetBundles derives diskSizeInGb (and transferPerMonthInGb on the top tier) from the instance size instead of serving the published bundle specs, and omits the Windows bundle tier and the rest of the list.
AWS: Smithy com.amazonaws.lightsail#GetBundles is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBundles, success 200) whose output member `bundles` is a BundleList of com.amazonaws.lightsail#Bundle; diskSizeInGb is documented as "The size of the SSD", transferPerMonthInGb as "The data transfer rate per month in GB", and supportedPlatforms as the platform (LINUX_UNIX / WINDOWS) the bundle supports, with the note that a WINDOWS bundle may only launch a WINDOWS blueprint. The model fixes no values, so the specs are recorded behavior only: the recording shows the published bundle table, in which the large Linux tiers share a fixed SSD size rather than one scaled with the instance size (8xlarge_3_0, 12xlarge_3_0 and 16xlarge_3_0 all carry diskSizeInGb 1280, and 16xlarge_3_0 carries transferPerMonthInGb 10240), and in which the Windows tiers (bundleId suffix _win_, e.g. 'nano_win_3_0', supportedPlatforms ['WINDOWS']) follow the Linux tiers.
Emulator: the top Linux tiers report a disk size computed from the instance size instead of the published cap - 8xlarge_3_0 got diskSizeInGb 2560, 12xlarge_3_0 got 3840, 16xlarge_3_0 got 5120 where AWS serves 1280 for all three - and 16xlarge_3_0 also got transferPerMonthInGb 11264 where AWS serves 10240. Every remaining asserted position from the first Windows bundle onward ($.bundles[11] .. $.bundles[99]) is reported missing: the WINDOWS-platform bundles and the tail of the table are not served at all. Price, cpuCount, power, ramSizeInGb, name, instanceType and publicIpv4AddressCount on the rows that are served match.
Why: a client sizing a Lightsail instance reads a disk and transfer allowance larger than the bundle it would actually get in AWS, so capacity planning and cost checks are wrong; and because no WINDOWS bundle is offered, no Windows instance can be created at all against the emulator (a WINDOWS blueprint requires a WINDOWS bundle), while any client indexing the bundle list by position reads off the end.
Fix: the static bundle catalog table backing the GetBundles handler in the lightsail crate - replace the size-derived diskSizeInGb/transferPerMonthInGb computation with the published per-bundle values, and add the missing WINDOWS-platform rows and the omitted tail rows with their supportedPlatforms.
Traces: lightsail-catalog-get-bundles#task#1.

Cause 4 of 4: GetRegions serves the wrong AWS-published region description for ca-central-1.
AWS: Smithy com.amazonaws.lightsail#GetRegions (awsJson RPC, POST /ls/api/2016-11-28/GetRegions, success 200) returns `regions`, a RegionList of com.amazonaws.lightsail#Region whose `description` member is documented as "The description of the Amazon Web Services Region" with the example "This region is recommended to serve users in the eastern United States and eastern Canada". The per-region text is recorded behavior only; the recording shows AWS describing ca-central-1 as 'This region is recommended to serve users in eastern and central Canada'. The requirement is that the description be AWS's current published sentence for that region, not an emulator paraphrase or an older revision of it.
Emulator: for the row with name 'ca-central-1' the description is 'This region is recommended to serve users in Canada and the northeastern United States'. Status 200 -> 200; name, displayName, continentCode and availability zones match, and the only diverging key is $.regions[name="ca-central-1"].description. The same cluster is observed from three fixtures, so every GetRegions caller sees it.
Fix: the static region table backing the GetRegions handler in the lightsail crate - the description column of the ca-central-1 row (and any sibling row whose sentence has been re-worded).
Traces: lightsail-catalog-get-regions#task#1 (same cluster also reached via lightsail-cloudformation-and-copy-error-paths#task#1 and lightsail-instance-error-paths#task#7).

Relation to open issues: replay reports stub_path empty and owned_by EMPTY for all four clusters, so no open issue carries any of these replay keys.
