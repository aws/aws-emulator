# events__ssm: 4 causes — Parameter Store policies are neither validated nor acted on, maintenance windows emit no state-change/registration events and never execute, and CreateOpsItem's priority refusal echoes the value

> _Note: this issue was identified against the code base at commit `7e5e0efa347a2e327a9b3588e8ef7ff7fc53eee8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutParameter

## Description
Cause 1 of 4: PutParameter accepts an ExpirationNotification policy whose Before unit is minutes. AWS: refuses the call with a 400 ValidationException — the ExpirationNotification policy's Unit must be one of the accepted units (Days/Hours), minutes is not accepted — and no parameter-policy change event is emitted. Recorded behavior for the refusal (the policy document is an opaque string in Smithy, so the unit rule is a service rule). Emulator: returns 200 `{'Version': 1, 'Tier': 'Advanced'}` — the invalid policy is stored. Checks: events__ssm.expiration-notification-in-minutes-is-rejected-and-emits-no-change-event.

Cause 2 of 4: Parameter Store policies never act and never publish their events. AWS: an Advanced-tier parameter with an ExpirationNotification policy publishes a `Parameter Store Policy Action` event on source `aws.ssm` to the default bus before the expiry, naming the parameter and the policy type (ExpirationNotification), and an Expiration policy DELETES the parameter at its time and publishes the corresponding policy-action event. Recorded behavior only (documented SSM Parameter Store policy events). Emulator: `no Parameter Store Policy Action event arrived for the parameter`, `no ExpirationNotification event reached the queue; saw 0 event(s) of policy types []`, and one check exhausts its 60s budget — the policies are inert. Checks: events__ssm.expiration-policy-deletes-parameter-and-emits-policy-action-event, events__ssm.parameter-expiration-notification-policy-event-arrives-before-expiry, events__ssm.expiration-notification-policy-emits-policy-action-event-before-expiry.

Cause 3 of 4: maintenance windows emit no state-change or target-registration events and never run a task. AWS: UpdateMaintenanceWindow enabling/disabling a window publishes a `Maintenance Window State-change Notification` on `aws.ssm` carrying the new status (ENABLED/DISABLED), RegisterTargetWithMaintenanceWindow/UpdateMaintenanceWindowTarget publish target-registration events whose status (REGISTERED/UPDATED/DEREGISTERED) a status-filtered rule can select, and a window whose schedule fires executes its registered task, publishing task/invocation state-change events that report the terminal status (SUCCESS/COMPLETE) and appear in the window execution history. Recorded behavior only (documented SSM maintenance-window event types). Emulator: `a DISABLED state-change event did not arrive; received [only the check's own probe event]`, `the unfiltered rule delivered statuses []; expected both ENABLED and DISABLED`, `no REGISTERED event; the unfiltered rule delivered []`, `the window never finished a run; executions: []`, `the one-time maintenance window never finished an execution`. (The open issue 20261122T161603Z-ssm-2-net-new-causes-a-maintenance-window.md records the missing WindowExecution under service `ssm`; it does not carry these events__ssm checks or the state-change/registration event causes.) Checks: events__ssm.maintenance-window-disable-and-enable-each-emit-a-state-change-event, events__ssm.disabled-only-rule-withholds-maintenance-window-enabled-event, events__ssm.window-target-registration-events-filtered-by-status-withhold-registered-and-updated, events__ssm.maintenance-window-automation-task-invocation-events-report-complete, events__ssm.maintenance-window-run-command-invocation-events-report-success, events__ssm.maintenance-window-task-execution-emits-state-change-events.

Cause 4 of 4: CreateOpsItem's priority range refusal echoes the offending value, where AWS omits it. AWS: refuses with ValidationException and the message `1 validation error detected: Value at 'priority' failed to satisfy constraint: Member must have value less than or equal to 5` — the fixed text has NO value between `Value` and `at`; the member path and the bound come from the model (OpsItem Priority @range max 5). The refused item is not stored and emits no `OpsItem Create` event. Emulator: answers `1 validation error detected: Value '6' at 'priority' failed to satisfy constraint: Member must have value less than or equal to 5` — it inserts the value. Checks: events__ssm.create-ops-item-priority-above-five-rejected-and-emits-no-create-event.

Why: parameter rotation/expiry automation (cause 2) and patch/maintenance automation (cause 3) are inert, so scheduled operational work silently never happens and nothing surfaces the failure; an invalid policy is stored and will be rejected by real AWS (cause 1); and message-asserting clients break on cause 4.
Fix: the ssm PutParameter policy validation, the parameter-policy scheduler and its event emission, the maintenance-window state/registration event emission and schedule executor, and the range-violation message renderer used by CreateOpsItem.
Traces: the eleven check ids listed per cause above.
