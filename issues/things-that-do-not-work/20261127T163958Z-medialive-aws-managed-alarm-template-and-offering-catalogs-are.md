# AWS-managed alarm-template and offering catalogs are generated placeholders, not the AWS catalog

> _Note: this issue was identified against the code base at commit `5bf95535a88c836b855c8cd193d84d7babf276ba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCloudWatchAlarmTemplates

## Description
Two divergence clusters, one shared fault: the two read-only, AWS-managed catalogs MediaLive serves (CloudWatch alarm templates and reserved offerings) are populated with sequentially generated placeholder rows instead of the catalog AWS returns, so every identity a client reads out of them is an id AWS does not have. 2 causes must be closed.

Related open issue: 20261125T002126Z-medialive-read-only-catalog-listings-still-serve-placeholder.md describes this same family (and its template-GROUP cluster is still owned by it), but the replay reports these two clusters as unowned - its recorded replay keys name the emulator's own synthetic ids (aws-2000030..aws-2000037) rather than the catalog identities the corpus now diverges on - so they are filed here and must be closed on their own replay keys.

Cause 1 of 2: ListCloudWatchAlarmTemplates returns none of the AWS-managed alarm templates
AWS: Smithy: ListCloudWatchAlarmTemplates (GET /prod/cloudwatch-alarm-templates, paginated on CloudWatchAlarmTemplates) returns __listOfCloudWatchAlarmTemplateSummary, each entry carrying arn, id, groupId, name, targetResourceType, comparisonOperator, evaluationPeriods, metricName, period, statistic, treatMissingData, createdAt, threshold, datapointsToAlarm and description; the id pattern shape documents that AWS-provided templates and groups have ids beginning 'aws-'. Recorded behavior: the response is the region's AWS-managed template catalog, every template bound to one of the real AWS-managed group ids, with its own createdAt and its documented description prose.
Emulator: answers 200, but every AWS-managed template of the recording is absent from the list ('missing ... got None' for each arn), and the entries it does return are sequentially generated ones (arn ...:cloudwatch-alarm-template:aws-2000001 upward).
Why: a client that discovers an AWS-managed alarm template by id - to create an alarm from it, to filter by groupIdentifier, or to attach it to a signal map - finds no template it expects, and every template it does find has an id and groupId that do not exist in AWS, so the follow-up call fails against the real service.
Fix: the seeded alarm-template catalog in the medialive crate's state (services/service-com-amazonaws-medialive-medialive/src/state.rs) plus the ListCloudWatchAlarmTemplates handler/projection in that crate's src/ops - serve the real AWS-managed catalog (ids, group bindings, metric and alarm fields, createdAt, descriptions) instead of generating rows.
Traces: medialive-catalog-list-cloud-watch-alarm-templates#task#1.

Cause 2 of 2: ListOfferings returns generated offerings instead of the region's reserved-offering catalog
AWS: Smithy: ListOfferings (GET /prod/offerings, paginated on Offerings) returns Offering entries with arn, offeringId, offeringDescription, resourceSpecification {resourceType, codec, resolution, maximumBitrate, maximumFramerate, channelClass, specialFeature, videoQuality}, region, offeringType, duration, durationUnits, usagePrice, fixedPrice and currencyCode; the request filters (resourceType, codec, resolution, channelClass, duration, maximumBitrate, ...) select within that fixed catalog. Recorded behavior: the response is the region's reserved-offering catalog, each offering carrying its own offeringId, human-readable offeringDescription, resource specification and pricing/term.
Emulator: answers 200, but none of the recorded offerings are present ('missing ... got None' for each offering arn); the list instead holds offerings whose ids are sequential synthetic numbers (arn ...:offering:10000000 upward) with fabricated specifications.
Why: PurchaseOffering takes an offeringId obtained from this list, so a list-then-purchase client sends an id AWS never issued, and any logic that reads offeringType, duration, usagePrice or the resource specification to choose a reservation reads invented values and cannot be exercised against the emulator.
Fix: the seeded offering catalog in the medialive crate's state (src/state.rs) plus the ListOfferings handler and its query-filter projection in src/ops - serve the real offering catalog and filter within it rather than generating sequential rows.
Traces: medialive-catalog-list-offerings#task#1.

The recorded ids, timestamps, descriptions and prices quoted under Evidence are the recordings' values, cited as evidence of what the catalogs are and where they come from, not as literals to hardcode: the requirement is that these read-only listings be the AWS-managed catalog for the region.
