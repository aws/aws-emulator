=== Cause 1 of 3: the scribe streaming endpoint cannot complete a TLS handshake with ALPN 'h2', so no Medical Scribe stream can be opened at all ===
Failing checks: connecthealth.scribe-stream-malformed-identifiers-rejected, connecthealth.scribe-stream-out-of-range-sample-rate-rejected, connecthealth.scribe-stream-to-deleted-domain-rejected, connecthealth.scribe-stream-unsupported-language-or-encoding-rejected (all four fail identically, before any request byte is sent).
AWS: Smithy models StartMedicalScribeListeningSession as POST /medical-scribe-stream/ with endpoint hostPrefix 'streaming.' and BOTH a streaming @httpPayload input member (inputStream -> MedicalScribeInputStream) and a streaming output member (responseStream -> MedicalScribeOutputStream): it is a bidirectional event-stream operation, which AWS serves only over HTTP/2 — a client therefore opens an h2 connection, i.e. a TLS handshake advertising ALPN 'h2', and signs the request with SigV4 using the STREAMING_AWS4_HMAC_SHA256_EVENTS body value. Its inputs are all headers: sessionId (x-amzn-medscribe-session-id, @length 36/36, @pattern [a-fA-F0-9]{8}-...-[a-fA-F0-9]{12}), domainId (x-amzn-medscribe-domain-id, @length 20..25, @pattern ^(hai-|dom-)[a-z0-9]+$), subscriptionId (x-amzn-medscribe-subscription-id, @length 25/25, @pattern ^sub-[a-zA-Z0-9]{21}$), languageCode, mediaEncoding (enums) and mediaSampleRateHertz (@range 8000..48000); modelled errors are AccessDeniedException 401, ValidationException 400, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ThrottlingException 429, InternalServerException 500. Recorded behavior the four checks assert behind the handshake: a well-formed but unknown subscription is refused 404 ResourceNotFoundException `Resource not found: subscriptionId with ID <subscriptionId> does not exist` (fixed text plus the submitted id), and a header breaking its modelled pattern is refused 400 ValidationException `1 validation error detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>` (fixed text plus the submitted value, the member name and the pattern from the model).
Emulator: the TLS handshake against the service's streaming host is never completed — awscrt reports AWS_IO_TLS_ERROR_NEGOTIATION_FAILURE: TLS (SSL) negotiation failed while constructing the Http2ClientConnection, so the stream request is never issued and none of the above refusals can be observed. The handshake is made to the address the emulator publishes for the scribe streaming endpoint, with the suite's own trust store, and the ONLY thing the client requires of it beyond a normal https handshake is ALPN 'h2'; every non-streaming connecthealth operation in the same run handshakes and answers fine over HTTP/1.1. Hypothesis: the emulator's TLS listener does not advertise the h2 ALPN protocol (or does not serve the 'streaming.'-prefixed host over TLS at all), so an HTTP/2-only operation cannot be reached. Note that 20261024T025747Z-connecthealth-startmedicalscribelisteningsession-missing.md (fixed) added the handler — this is the transport in front of it, and the four checks never get far enough to exercise that handler.
Why: the entire Medical Scribe streaming surface is unreachable for every client. An SDK or application doing exactly what AWS requires for a bidirectional event stream (h2 over TLS) gets a transport-level handshake failure instead of either a session or a modelled refusal, which it cannot distinguish from a broken network or a bad certificate; no validation, authorization or session behavior of the operation can be developed or tested against the emulator.
Fix: the emulator's HTTPS/TLS listener and host routing for the connecthealth 'streaming.' endpoint must negotiate ALPN 'h2' and serve HTTP/2 for POST /medical-scribe-stream/ so the StartMedicalScribeListeningSession handler is reachable; the handler's header validation and subscription lookup can then answer the recorded refusals above.
Traces: connecthealth.scribe-stream-malformed-identifiers-rejected, connecthealth.scribe-stream-out-of-range-sample-rate-rejected, connecthealth.scribe-stream-to-deleted-domain-rejected, connecthealth.scribe-stream-unsupported-language-or-encoding-rejected.

=== Cause 2 of 3: StartPatientInsightsJob accepts an outputDataConfig.s3OutputPath naming a bucket that does not exist, instead of refusing it with ValidationException 'S3 resource not found.' ===
Failing check: connecthealth.start-patient-insights-job-missing-output-bucket-rejected.
AWS: Smithy models StartPatientInsightsJob POST /domain/{domainId}/patient-insights-job (success 200, hostPrefix 'runtime.') with outputDataConfig -> OutputDataConfig whose only member s3OutputPath -> S3Uri is @required @length(max 1024) @pattern ^s3://[a-z0-9][\.\-a-z0-9]{1,61}[a-z0-9](/.*)?$, and ValidationException as a client error, httpError 400, single member `message`. The model states only the URI grammar, not the existence rule, so the existence rule is recorded behavior: the service resolves the output location before accepting the job and refuses an s3OutputPath whose BUCKET does not exist with 400 ValidationException whose message is exactly `S3 resource not found.` — the whole sentence is fixed text, with no part interpolated (no bucket name, no URI). The refusal also consumes nothing: the same clientToken replayed with only the output path corrected to an existing bucket is accepted and starts a job of its own, which runs to SUCCEEDED and records that corrected s3OutputPath.
Emulator: the request naming a never-created bucket is ACCEPTED — HTTP 200 with jobArn/jobId/creationTime (observed jobId '5deb8ae7-d4c3-4d57-b4eb-55cdadf8400d' under domain 'dom-1b54ae38b31a89f3'; those are per-run values, the defect is the 200-vs-400 class). No S3 resolution of outputDataConfig happens at all, so this refusal class is unreachable. The positive control in the same check (an existing output bucket) is accepted, as it should be.
Why: this is a refusal gap that hides a real failure until much later. A client with a typo'd, stale or not-yet-created output bucket gets a success and a job id from the emulator, then polls a job whose results can never be delivered anywhere a caller can read them; on AWS the same request is refused synchronously at submission with a message the caller can act on. Code paths that handle 'S3 resource not found.' (create the bucket, fall back to another prefix, surface a configuration error) are never exercised, and tests written against the emulator pass for requests AWS rejects.
Fix: StartPatientInsightsJob's validation path in the connecthealth crate must resolve the bucket named by outputDataConfig.s3OutputPath (after the modelled grammar check) before accepting the job and refuse a nonexistent bucket with 400 ValidationException and the fixed message `S3 resource not found.`, recording no job state and consuming no clientToken.
Traces: connecthealth.start-patient-insights-job-missing-output-bucket-rejected.

=== Cause 3 of 3: the unknown-HealthLake-datastore refusal is worded 'HealthLake datastore not found' without the sentence-final period ===
Failing check: connecthealth.start-patient-insights-job-unknown-healthlake-datastore-rejected.
AWS: Smithy models StartPatientInsightsJob's inputDataConfig -> InputDataConfig @required, carrying fhirServer (FHIRServer, with the fhirEndpoint the job reads patient data from) and s3Sources; ValidationException is a client error, httpError 400, single member `message`. The model does not word the refusal, so the wording is recorded behavior: when the HealthLake datastore named by inputDataConfig.fhirServer.fhirEndpoint cannot be resolved, the call is refused 400 ValidationException with message exactly `HealthLake datastore not found.` — a complete sentence, terminal period included, with no interpolated part.
Emulator: answers 400 ValidationException with `HealthLake datastore not found` — the same words, missing the trailing period.
Why: the error message is a requirement; a client or test comparing the refusal with AWS's sentence fails on a one-character difference that is invisible in logs, so it costs debugging time rather than failing loudly. This is the same wording defect the OPEN wire issue 20261127T101150Z-connecthealth-patient-insights-runtime-refusals-diverge-wrong-status.md describes as its Cause 4 (five fixture steps across three fixtures); that issue carries no behavioral replay key for this check and the suite does not report this check as owned, so it is filed here — if that issue's Cause 4 is fixed first, re-replay this check to confirm it closes with it.
Fix: the datastore-resolution refusal in StartPatientInsightsJob's validation path in the connecthealth crate — reproduce AWS's sentence verbatim, including the period.
Traces: connecthealth.start-patient-insights-job-unknown-healthlake-datastore-rejected.
