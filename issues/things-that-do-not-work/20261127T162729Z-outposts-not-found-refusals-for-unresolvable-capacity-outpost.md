# outposts not-found refusals for unresolvable capacity, outpost and order references diverge

> _Note: this issue was identified against the code base at commit `7f3d8acfd1d18a62a70e68f35eeb77bb7bd3316f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelCapacityTask

## Description
5 net-new root causes in how this service REFUSES a reference it cannot resolve: four of them word the 404 NotFoundException differently from AWS (a wrong sentence template, or the right template filled with a normalized rather than the supplied identifier), and the fifth refuses with the wrong STATUS and error class entirely because a lifecycle precondition is judged before the request's references are resolved. The open issue 20261029T191039Z-outposts-lifecycle-and-precondition-gates-diverge-across-capacity covers CreatePrivateConnectivityConfig/CreateQuote/GetRenewalPricing/CreateRenewal and the decommission and delete paths; it does not cover any of these five clusters (the replay reports no owner for them).

Cause 1 of 5: CancelCapacityTask words the capacity-task not-found with the identifier-echo form instead of AWS's sentence.
AWS: Smithy CancelCapacityTask (POST /outposts/{OutpostIdentifier}/capacity/{CapacityTaskId}) models NotFoundException (HTTP 404, member Message, ErrorMessage len 1..1000). A CapacityTaskId that names no task of the resolved Outpost is that 404, and the recorded message is the sentence "CapacityTask <capacityTaskId> not found" — fixed text "CapacityTask " and " not found", with the CapacityTaskId taken from the request (the recording's 'cap-0abc0abc0abc0abc0' is the request's value filling that template, not part of it).
Emulator: 404 NotFoundException, but Message is 'capacityTaskId=cap-0abc0abc0abc0abc0' — the replay reports `$.Message: value_mismatch (expected 'CapacityTask cap-0abc0abc0abc0abc0 not found', got 'capacityTaskId=cap-0abc0abc0abc0abc0')`. The handler builds it from the generic identifier-echo helper (`crate::state::identifier_not_found(crate::state::CAPACITY_TASK_ID_MEMBER, &input.capacity_task_id)`), which is a different template from AWS's.
Why: the status and error code match, but the message is part of the contract a client reads — operators and log/alert matchers that key on AWS's "CapacityTask ... not found" text see an unrecognizable `member=value` string, and anything that surfaces the message to a user shows wording AWS never emits.
Fix: the capacity-task not-found wording — services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/cancel_capacity_task.rs (the task-lookup `ok_or_else` arm around line 198) and the shared message helper it calls in src/state.rs (identifier_not_found / CAPACITY_TASK_ID_MEMBER) — so a capacity-task reference that resolves to nothing is refused with AWS's sentence, from one statement of it shared with Cause 2.
Traces: outposts-cancel-capacity-task-malformed-identifiers#task#5.

Cause 2 of 5: ListBlockingInstancesForCapacityTask words the same capacity-task not-found the same wrong way.
AWS: Smithy ListBlockingInstancesForCapacityTask (GET /outposts/{OutpostIdentifier}/capacity/{CapacityTaskId}/blockingInstances) models NotFoundException (HTTP 404). A CapacityTaskId naming no task of the resolved Outpost is that 404, recorded with the same sentence "CapacityTask <capacityTaskId> not found" — the same fixed text, the CapacityTaskId taken from the request.
Emulator: 404 NotFoundException with Message 'capacityTaskId=cap-0abc0abc0abc0abc0' — the replay reports `$.Message: value_mismatch (expected 'CapacityTask cap-0abc0abc0abc0abc0 not found', got 'capacityTaskId=cap-0abc0abc0abc0abc0')`, i.e. the same identifier-echo helper used here too.
Why: same as Cause 1, on the read path a client uses while a capacity task is blocked — the refusal text for an unknown task does not match AWS, so message-driven handling diverges on both the cancel and the list path.
Fix: the capacity-task not-found wording in services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/list_blocking_instances_for_capacity_task.rs, through the same shared helper in src/state.rs as Cause 1, so both operations state it identically.
Traces: outposts-new-outpost-capacity-and-connectivity-reads#task#5.

Cause 3 of 5: GetPrivateConnectivityConfig's not-found echoes the NORMALIZED Outpost id instead of the identifier the request supplied.
AWS: Smithy GetPrivateConnectivityConfig (GET /outposts/{OutpostId}/privateConnectivity) models NotFoundException (HTTP 404); OutpostId (len 1..180) accepts either form of `^(arn:aws([a-z-]+)?:outposts:[a-z\d-]+:\d{12}:outpost/)?op-[a-f0-9]{17}$` — a bare id or a full Outpost ARN. Recorded behavior: the 404 message is the identifier echo "outpostId=<OutpostId exactly as supplied>" — fixed text "outpostId=" plus the request's own label value, so a request made with the ARN form is refused with the ARN (the recording's arn:aws:outposts:<region>:<accountId>:outpost/op-... is that request's value, and its region/account are environment values, not part of the template).
Emulator: 404 NotFoundException with the right template but the wrong value — `$.Message: value_mismatch (expected 'outpostId=arn:aws:outposts:us-west-2:000000000000:outpost/op-0abc0abc0abc0abc0', got 'outpostId=op-0abc0abc0abc0abc0')`: the message names the bare id the ARN was resolved to rather than the identifier as supplied, even though the handler's own comment states the echo must be "of the value AS SUPPLIED — not of the bare id an ARN resolved to".
Why: a caller that addressed the Outpost by ARN cannot match the refusal back to the identifier it sent — the message names a different string from the request — so retry/bookkeeping logic that correlates refusals with the identifier it used, and any assertion on the echoed identifier, diverges from AWS.
Fix: the not-found closure of services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/get_private_connectivity_config.rs (around line 166) and the identifier-echo helper in src/state.rs it calls, so the echoed value is the request's OutpostId verbatim on both the ARN-not-here path and the store-miss path.
Traces: outposts-new-outpost-capacity-and-connectivity-reads#task#4.

Cause 4 of 5: StartCapacityTask prefixes the unknown-Outpost refusal with prose AWS does not send.
AWS: Smithy StartCapacityTask (POST /outposts/{OutpostIdentifier}/capacity) models NotFoundException (HTTP 404). An OutpostIdentifier that names no Outpost of this endpoint is that 404, and the recorded message is the bare identifier echo "outpostId=<identifier as supplied>" — fixed text "outpostId=" plus the request's value, with no surrounding sentence.
Emulator: 404 NotFoundException with Message 'No Outpost with outpostId=op-0abc0abc0abc0abc0' — the replay reports `$.Message: value_mismatch (expected 'outpostId=op-0abc0abc0abc0abc0', got 'No Outpost with outpostId=op-0abc0abc0abc0abc0')`. The handler words it with the prose helper (`crate::state::outpost_not_found(&input.outpost_identifier)`, src/ops/start_capacity_task.rs around line 255) where the recording shows the plain echo — the mirror image of Cause 3, so the service has two wordings and applies them to the wrong operations.
Why: the refusal text for the commonest capacity mistake (a mistyped or stale Outpost id) does not match AWS, so message matching and user-facing surfacing diverge; combined with Cause 3 a client cannot rely on either the sentence or the echoed identifier.
Fix: the outpost-not-found wording used by services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/start_capacity_task.rs (both the ARN-not-here and the store-miss arms, around lines 250-278) and the two helpers in src/state.rs (outpost_not_found vs identifier_not_found), so each operation uses the wording the recordings show for it.
Traces: outposts-start-capacity-task-unknown-references#task#3.

Cause 5 of 5: StartCapacityTask judges the Outpost lifecycle precondition BEFORE resolving the OrderId, so an unknown order is refused 400 ValidationException instead of 404 NotFoundException.
AWS: Smithy StartCapacityTask models NotFoundException (HTTP 404) and ValidationException (HTTP 400); OrderId is an optional input (pattern ^oo-[a-f0-9]{17}$). Recorded behavior: for a request naming an OrderId that no order of that Outpost matches, AWS answers 404 with the message "No such order for order id <orderId>" — fixed text "No such order for order id " plus the request's OrderId — for the SAME Outpost state in which the emulator reports a lifecycle refusal (the CreateOutpost step of this fixture agrees with the recording on LifeCycleStatus, so AWS resolves the named references first and the lifecycle of the Outpost does not pre-empt that 404).
Emulator: 400 ValidationException with Message "1 validation error detected: Value at 'outpostIdentifier' failed to satisfy constraint: the Outpost must have a subscription that can be renewed" is a DIFFERENT path; here the replay reports `status: expected 404, got 400`, `$.Message: value_mismatch (expected 'No such order for order id oo-0abc0abc0abc0abc0', got 'Failed to create capacity task for op-7ee005f5b9933244a. Outpost should have LifeCycleStatus being ACTIVE, but op-7ee005f5b9933244a has LifeCycleStatus PENDING')` and `$headers.x-amzn-errortype: shape_mismatch (expected '<shaped-not-asserted>', got 'ValidationException')`. The handler applies `if !record.is_active()` (src/ops/start_capacity_task.rs around line 291) before the OrderId lookup that would have produced the modeled 404 (`crate::state::order_not_found`, around line 334), so the order reference is never resolved.
Why: this is a wrong HTTP status AND a wrong error class, not just wrong text: a client distinguishing "the order I named does not exist" (404, fix the reference) from "this request is invalid" (400, do not retry) takes the wrong branch, SDK error-type dispatch lands on ValidationException where AWS raises NotFoundException, and the caller is told about the Outpost's lifecycle instead of the reference that is actually unresolvable.
Fix: the gate ORDER in the StartCapacityTask handler — services/service-com-amazonaws-outposts-outpostsolafservice/src/ops/start_capacity_task.rs: resolve the named references (OrderId via order_of_outpost, then AssetId) and raise their modeled 404s before the lifecycle precondition `record.is_active()` is judged, keeping each refusal's own wording ("No such order for order id <orderId>").
Traces: outposts-start-capacity-task-unknown-references#task#4.
