## Operation
CreateChangeSet

## Description
Nine net-new causes in CloudFormation's Lambda resource surface. (The AWS::Lambda::ResourcePolicy and AWS::Lambda::CapacityProvider unrecognized-type failures in this suite are owned by 20261109T210043Z-cloudformation-lambda-6-net-new-causes-cloudformation-s-lambda-resource.md and are not part of this issue.)

Cause 1 of 9: CloudFormation's own resource-schema property validation never runs for Lambda resources, so out-of-range, off-pattern, off-enum and unsupported properties are accepted.
AWS: before any handler is called, CloudFormation validates the template against the resource schema. A violating property makes CreateChangeSet settle (Status FAILED, ExecutionStatus UNAVAILABLE); for a CreateStack/UpdateStack it fails the stack with the stack-level reason `Validation failed with <N> error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation.` and DescribeEvents carries one VALIDATION_ERROR OperationEvent per violation with EventType VALIDATION_ERROR, ValidationName PROPERTY_VALIDATION, ValidationStatus FAILED, ValidationFailureMode FAIL and a ValidationPath of the form `/Resources/<LogicalId>/Properties/<member path>`. The violations exercised here are all schema facts: Function.Description max 256, Function.FunctionName/Version.FunctionName max 140 and its pattern, LoggingConfig.LogGroup max 512 and its character class, LoggingConfig.LogFormat/ApplicationLogLevel/SystemLogLevel enums, TracingConfig.Mode enum, Architectures (one item, enum), RuntimeManagementConfig.UpdateRuntimeOn enum, Permission.Action max 256 and the lambda: namespace pattern, Permission.FunctionName max 140 plus pattern, Permission.EventSourceToken max 256 and pattern, Permission.SourceArn min 12 / max 1024, Url.TargetFunctionArn pattern, Url Cors AllowHeaders/ExposeHeaders max 100 items and non-empty members, Cors AllowMethods max 6, tag keys non-empty, and a `Tags` property on AWS::Lambda::Permission / ::Version / ::LayerVersion / ::Url that the schema does not declare at all.
Emulator: every one of these settles ('CREATE_COMPLETE', 'AVAILABLE') for a change set or CREATE_COMPLETE/UPDATE_COMPLETE for a stack, and DescribeEvents returns an empty VALIDATION_ERROR list. For cfn-lambda-non-arn-kms-key-arn-validates-in-change-set-but-update-rejected an empty KmsKeyArn is even written through and configures a key; for cfn-lambda-function-runtime-outside-published-set-rejected the resource does fail but with a handler reason instead of the schema refusal.
Why: the whole point of pre-provision validation is that a bad template never touches a service. A caller gets a green change set and a green stack for a template real CloudFormation refuses, so a broken configuration is deployed and the schema violation is discovered only in production.
Fix: CloudFormation's pre-provision property-validation stage for the AWS::Lambda::* resource schemas, and the VALIDATION_ERROR OperationEvent emission that reports it.

Cause 2 of 9: a change to a CREATE-ONLY Lambda property is planned as an in-place Modify.
AWS: DescribeChangeSet reports such a change with Replacement `True` and a ResourceChangeDetail whose Target.RequiresRecreation is `Always`; executing it creates the replacement, repoints the logical id and deletes the original. The create-only members exercised are AWS::Lambda::Permission Action / FunctionName / Principal / SourceArn / SourceAccount / EventSourceToken / FunctionUrlAuthType, AWS::Lambda::Alias FunctionName, AWS::Lambda::EventInvokeConfig FunctionName and Qualifier, AWS::Lambda::Version FunctionName / Description / CodeSha256, and AWS::Lambda::Function TenancyConfig.
Emulator: each is planned ('Modify', Replacement 'False') with RequiresRecreation 'Never', so the preview tells the caller nothing will be recreated.
Why: Replacement is the signal every reviewer and CI gate reads before executing a change set. A plan that says `False` where AWS says `True` hides the destruction of a grant, alias, version or function behind an apparently safe update.
Fix: the create-only/replacement classification in each AWS::Lambda::* resource handler's change-set planner.

Cause 3 of 9: a custom resource's FAILED answer and its physical-id changes are not honoured.
AWS: when the responder PUTs a FAILED response, CloudFormation fails the resource with the reason `Received response status [FAILED] from custom resource. Message returned: <Reason>\n\nLogs: /aws/lambda/<function>\n\n` (fixed wrapper; the reason and the log group come from the response and the responder), rolls the stack back and deletes the resource; a FAILED answer to a Delete leaves the stack DELETE_FAILED with a DELETE_FAILED event for the resource; an Update that answers a NEW PhysicalResourceId makes CloudFormation send a Delete for the OLD id and record a DELETE_COMPLETE for it; an Fn::GetAtt of a key absent from the response Data fails the create; and an Update that changes ServiceToken is refused, leaving UPDATE_ROLLBACK_COMPLETE.
Emulator: the resource reaches CREATE_COMPLETE/DELETE_COMPLETE regardless of the FAILED answer, no CREATE_FAILED reason is recorded, no DELETE_FAILED event is emitted, no Delete is sent for the superseded physical id, a missing GetAtt key still completes the stack, a failed Update leaves the old properties unapplied, and a ServiceToken change reaches UPDATE_COMPLETE.
Why: custom resources are the extension point for every CDK construct and bespoke provisioning step. Ignoring FAILED means a failed provisioning step is reported as a successful deployment, and ignoring the physical-id change orphans the old resource.
Fix: the AWS::CloudFormation::CustomResource / Custom::* response handling in the CloudFormation provisioner — status, Reason, Data and PhysicalResourceId of the response, and the stack/resource state transitions they drive.

Cause 4 of 9: write-only Lambda properties appear in the drift read's ExpectedProperties.
AWS: DetectStackResourceDrift omits write-only members from both ExpectedProperties and ActualProperties, so Code (ZipFile, S3Bucket, S3Key, S3ObjectStorageMode, SourceKMSKeyArn) never shows up and a function whose code changed out of band still reads IN_SYNC with an empty Code block.
Emulator: the Code block and its write-only members are carried into ExpectedProperties (and in one case ActualProperties is null), producing a drift report AWS never produces.
Why: a drift gate that compares the two property sets reports spurious drift on every function with inline or S3 code, so the gate is unusable.
Fix: the write-only member projection in the AWS::Lambda::Function drift/read path.

Cause 5 of 9: an inline-ZipFile function package always bundles cfnresponse.py.
AWS: CloudFormation bundles the cfnresponse module into the deployment package ONLY when the inline code names it; otherwise the package holds exactly `index.py` (or index.js).
Emulator: the package holds `['index.py', 'cfnresponse.py']` whether or not the code references the module, and the presigned code location serves that package.
Why: a caller that downloads the function's code location, or that lists the package contents to verify what was deployed, sees a file it never supplied; package size and content hashing both diverge.
Fix: the inline-code packaging step of the AWS::Lambda::Function handler.

Cause 6 of 9: macro / Fn::Transform processing is broken.
AWS: a macro is invoked with an event carrying requestId, templateParameterValues, fragment and params; its SUCCESS answer's fragment REPLACES the transformed node (the Fn::Transform key and its siblings are gone from the processed template); a non-SUCCESS status fails the change set; a macro registered by an alias ARN runs that alias's version; and a template using Fn::Transform without CAPABILITY_AUTO_EXPAND is refused.
Emulator: three of these stacks roll back because the Invoke of the macro function is refused with `Resource handler returned message: "expected string, got object start (Service: Lambda, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)"` — the macro event payload is rejected by Lambda's own request deserialisation; where the invoke does happen the transformed node still holds its Fn::Transform key and siblings, a declined (non-SUCCESS) answer still yields CREATE_COMPLETE, the processed template's macro-produced value is null, and the macro event's Type/RequestId keys are absent (KeyError 'Type').
Why: SAM, the serverless framework and hosted-rotation templates are all macro transforms. None of them can deploy, and a macro that declines is treated as success.
Fix: the macro invocation path — the event payload the transform handler sends to Invoke, and the fragment substitution and status handling of the answer.

Cause 7 of 9: stack Outputs are returned without an OutputValue.
AWS: every entry of DescribeStacks Stacks[].Outputs carries OutputKey and OutputValue; an Output whose Value is Fn::GetAtt <Url>.FunctionUrl or .FunctionArn resolves to the minted URL / qualified ARN.
Emulator: the output entry exists with no OutputValue member at all (KeyError 'OutputValue') for AWS::Lambda::Url-derived outputs.
Why: a caller that reads a stack output to find the function URL gets a KeyError rather than a value; every consumer of the output breaks.
Fix: output resolution/serialisation for Fn::GetAtt attributes of AWS::Lambda::Url in the stack Outputs projection.

Cause 8 of 9: valid Lambda templates are refused. AWS: a PER_TENANT TenantIsolationMode deploys; a read-only LayerVersionArn or a Version value written into the template is ignored and the stack reaches CREATE_COMPLETE with the service-assigned value; changing InvokedViaFunctionUrl on a permission replaces the statement and the stack reaches CREATE_COMPLETE. Emulator: all four settle ROLLBACK_COMPLETE / UPDATE_ROLLBACK_COMPLETE (one with the emulator-authored reason `NotImplemented: this emulator does not change the properties of an existing AWS::Lambda::Version in place; the resource was left as it is.`). Why: valid templates cannot be deployed at all. Fix: the read-only member projection and the update classification of the AWS::Lambda::Function/Version/Permission handlers.

Cause 9 of 9: DetectStackResourceDrift refuses AWS::Lambda::LayerVersion with HTTP 400 ValidationError `Drift detection is not supported for ResourceType AWS::Lambda::LayerVersion`. AWS: the resource is drift-detectable and the call returns a StackResourceDrift. Why: a stack-wide drift detection that includes a layer version fails instead of reporting. Fix: the drift-support registration for AWS::Lambda::LayerVersion.
