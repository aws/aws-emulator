# ElastiCache: the loser of two concurrent ModifyReplicationGroupShardConfiguration calls is refused with the published-status sentence instead of AWS's reshard-collision message (1 cause)

> _Note: this issue was identified against the code base at commit `244eae870d957920c579d40eef12d136da6f5bab`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyReplicationGroupShardConfiguration

## Description
One net-new root cause in the elasticache emulator, grounded in the only failing behavioral check of this replay that the suite marked neither ALREADY FILED nor OWNED (all 27 other failures are OWNED by open issues). The error CODE is right and the race outcome is right; the error MESSAGE of the losing call is the wrong one of the two sentences this gate has to choose between.

Cause 1 of 1: when two ModifyReplicationGroupShardConfiguration calls are issued concurrently against one cluster-mode-enabled replication group, the loser is refused InvalidReplicationGroupState with 'Replication group must be in available state to modify.' instead of AWS's reshard-collision sentence 'Could not reshard replication group. Please try again later.'
  AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json) models ModifyReplicationGroupShardConfiguration with InvalidReplicationGroupStateFault -> awsQueryError code 'InvalidReplicationGroupState', httpResponseCode 400 ("The requested replication group is not in the available state."). The model does not distinguish WHICH sentence that fault carries, so the distinction is recorded behavior only: AWS words this fault two different ways on this operation, and which one a caller gets depends on how the second reshard arrived.
    - A second reshard issued CONCURRENTLY with the first (both requests leaving a barrier together, so the second lands inside the first's reshard admission) collides at the reshard admission itself and is refused HTTP 400, Error.Code 'InvalidReplicationGroupState', Error.Message 'Could not reshard replication group. Please try again later.' That message is wholly FIXED text: it interpolates no request or state value (no replication group id, no node group count), and the trailing period is part of it.
    - A second reshard issued AFTER the first has answered, against the 'modifying' status the first published, is refused with the same code but AWS's general modification gate sentence 'Replication group must be in available state to modify.' — also wholly fixed text. That second form is already the emulator's behavior and is asserted by elasticache.shard-reconfiguration-state-machine, which passes; the fix for this cause must not regress it. (It is the subject of fixed issue 20261120T174937Z-elasticache-state-gate-refusals-diverge-a-conflicting-reshard.md, which established that sentence for the sequential case; this cause is the complementary concurrent case, a different arrival path and a different sentence, so it is not a reopen of that issue — the call is correctly refused here, with the correct code.)
    Hypothesis: AWS's split is between an optimistic admission on the group's resharding coordinator (two simultaneous admissions collide, hence the retry wording) and the already-published group status (hence the precondition wording). The emulator models exactly this split, so only the WIDTH of the collision window is in question.
  Emulator: the race outcome is correct — of the two concurrent calls exactly one is accepted and exactly one is refused with Error.Code 'InvalidReplicationGroupState' — but the refused call carries 'Replication group must be in available state to modify.' The handler's gate (services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/modify_replication_group_shard_configuration.rs:296-310) picks the collision sentence (crate::state::RESHARD_COLLISION_MESSAGE) only while group.reshard_admission_in_flight() is true, and otherwise picks crate::state::replication_group_modify_state_refusal(). That admission is raised by crate::state::ReshardAdmission::raise (:488) and dropped at :505, i.e. it is scoped to the WINNING REQUEST'S OWN IN-PROCESS LIFETIME — the store write that sets 'modifying' plus the serve/ENI-settle pass that follows. In the emulator that span is sub-millisecond, so a genuinely concurrent second request, which still has to be read off the socket, deserialized and validated before it reaches the gate, essentially always arrives after the admission has been dropped and therefore reads the published-status branch. The collision branch is effectively unreachable for any real client, which is why the suite's barrier-synchronised check cannot hit it.
  Why: the message is part of this refusal's contract and the two sentences mean different things to a client. AWS's collision sentence tells the caller its reshard request lost a race and the same request can simply be retried; the sentence the emulator sends states a precondition, telling the caller to first poll the group back to 'available'. A client (or operator tooling, log scraper, or retry policy) that branches on the InvalidReplicationGroupState text to tell 'retry now' from 'wait for available' takes the wrong branch against the emulator, and a client written against the emulator's behavior — concluding AWS never sends the collision sentence — mishandles it in production. The divergence also hides the emulator's own collision path from every test: no client-observable sequence can reach it.
  Fix: the ModifyReplicationGroupShardConfiguration handler's state gate and the reshard-admission state it consults. The admission that selects the collision sentence must be bounded by the reshard actually being in progress on the group (the window in which the group reports 'modifying' because of THIS reshard and concurrent reshard requests are still colliding with it), not by the winning request's own handler lifetime, so that a second reshard arriving alongside the first gets the collision sentence while one arriving against an already-published 'modifying' status keeps getting the general modification sentence.
  Traces: elasticache.concurrent-shard-config-modification-conflict.
