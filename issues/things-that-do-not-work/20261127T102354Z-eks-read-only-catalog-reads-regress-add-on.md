# eks read-only catalog reads regress: add-on versions, cluster versions and add-on configuration schemas are not the published catalog (6 causes)

> _Note: this issue was identified against the code base at commit `96db52f5b4a4b596ab227bd8becc0930845733a7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
SIX net-new root causes in the eks service, all found by replaying the wire fixture corpus (trace set simparity-wire-aws-v1) against the emulator built from this checkout, and all reported unowned by the replay (owned_by empty, stub_path empty). They share one fault: the three read-only EKS catalog/discovery operations (DescribeAddonVersions, DescribeClusterVersions, DescribeAddonConfiguration) answer 200 from emulator-authored data instead of serving the published AWS catalog selected by the request's filters. Each cause below is a SEPARATE divergence cluster with its own fixture/step and must be re-replayed and closed individually.

The RESOLVED issues 20261125T022924Z-eks-describeaddonversions-describeclusterversions-and-describeaddonconfiguration-omit-published-catalog.md, 20261124T092047Z-eks-describeaddonversions-serves-a-synthesised-add-on-release.md and 20261123T162615Z-eks-read-only-catalog-and-schema-discovery-reads.md closed the same surface; a resolved issue covers nothing, so these six are regressions/residue on it.

Cause 1 of 6: on a paginated DescribeAddonVersions walk the record the catalog publishes at addons[0] is absent on essentially every page.
  AWS: DescribeAddonVersions is GET /addons/supported-versions, 200, with @httpQuery filters kubernetesVersion, addonName, types, publishers, owners, maxResults, nextToken, @paginated items=addons, errors InvalidParameterException 400 / ResourceNotFoundException 404 / ServerException 500 (Smithy: services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json). Each element is an AddonInfo (addonName, type, addonVersions, publisher, owner, marketplaceInformation, defaultNamespace) and addonVersions is an AddonVersionInfoList of that add-on's published releases, each AddonVersionInfo carrying addonVersion, architecture, computeTypes, compatibilities (clusterVersion / platformVersions / defaultVersion) and requiresConfiguration / requiresIamPermissions (both @default false). The requirement is that the page contents be the published catalog rows the request's filters select, in the catalog's order; the recording shows, for example, an observability add-on record whose addonVersions list is the add-on's multi-release history with the newest release flagged defaultVersion true per compatible cluster version and the older releases false. Status 200; no error class is at stake.
  Emulator: answers 200, but $.addons[0] is reported missing against the recorded page on 82 of the walk's steps — the catalog record for the requested filter set is not served at that index at all; a locally minted record stands in its place.
  Why: this listing is how a client discovers which add-ons exist and which versions may be installed on a given cluster version. With a different record served for the requested filter, a client that pins, upgrades or rolls back an add-on to a named version is told that version does not exist, and an installer enumerating add-ons for a cluster never sees the ones AWS publishes.
  Fix: the add-on catalog data behind the DescribeAddonVersions handler and that handler's filter/pagination selection over it (rows must be selected from the published catalog, not synthesised).
  Traces: eks-catalog-describe-addon-versions-accuknox-kubearmor-eg-innovations-eg-universal-agent-operator#task#2 (representative; 82 affected steps, task#2..task#26 and onward in the same fixture).

Cause 2 of 6: a filtered DescribeAddonVersions query serves a different add-on record at addons[0], and for a Marketplace-owned record marketplaceInformation.productUrl is not the catalog's URL.
  AWS: same operation and shapes as Cause 1; MarketplaceInformation.productUrl is documented as "The product URL from the Amazon Web Services Marketplace" — the catalog's published URL for that productId. The recorded page's addons[0] is a storage-type, Marketplace-published add-on whose addonVersions list is its full release history (per-release architecture, computeTypes, ten compatible cluster versions each with platformVersions and defaultVersion, requiresConfiguration true / requiresIamPermissions false on the newest).
  Emulator: answers 200 with that record absent at addons[0] ($.addons[0]: missing) and with $.addons[0].marketplaceInformation.productUrl in a different URL form than the catalog publishes for the same product.
  Why: a client resolving a Marketplace add-on for a subscription or legal check lands on a URL that does not identify the product, and the storage add-on it was filtering for appears not to exist.
  Fix: the DescribeAddonVersions handler's catalog data, including the Marketplace productId/productUrl pair each catalog record carries.
  Traces: eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni#task#20 (1 affected step).

Cause 3 of 6: DescribeClusterVersions serves none of the published cluster-version rows.
  AWS: DescribeClusterVersions is GET /cluster-versions, 200, @httpQuery filters clusterType, clusterVersions, defaultOnly, includeAll, status (deprecated since 2025-02-15) and versionStatus, @paginated items=clusterVersions, errors InvalidParameterException 400 / InvalidRequestException 400 / ServerException 500 (same model file). Each element is a ClusterVersionInformation: clusterVersion, clusterType, defaultPlatformVersion, defaultVersion (@default false), releaseDate, endOfStandardSupportDate, endOfExtendedSupportDate, status and versionStatus (both enums, which must agree), kubernetesPatchVersion, controlPlaneScalingTiers (list, @length max 10, each tier carrying tierName, apiRequestConcurrency, podSchedulingRatePerSecond, clusterDatabaseSizeGb and controlPlaneComponentConfigOverrides) and controlPlaneComponentConfig. The recording shows a full supported-version ladder, newest first, each row carrying its support-lifecycle dates, its patch version, and its scaling-tier table with the per-tier component-config overrides and their default/min/max constraints.
  Emulator: answers 200, and every one of the recorded rows is missing: the divergence key names $.clusterVersions[0] through $.clusterVersions[6] — the whole served list diverges from the published one (rows absent, and where a row is served its lifecycle dates, versionStatus/status pair, kubernetesPatchVersion and controlPlaneScalingTiers are not the catalog's).
  Why: this is the operation a client uses to decide which Kubernetes version to create or upgrade a cluster to and when support for it ends. Wrong or absent rows make version-selection and end-of-support planning logic choose a version AWS does not offer, and a client sizing a provisioned control plane reads scaling tiers that do not exist.
  Fix: the cluster-version catalog data behind the DescribeClusterVersions handler and its filter/pagination selection over it.
  Traces: eks-catalog-describe-cluster-versions#task#1 (1 affected step).

Cause 4 of 6: DescribeAddonConfiguration serves a configuration JSON Schema that is not the add-on version's published schema, and drops a podIdentityConfiguration entry.
  AWS: DescribeAddonConfiguration is GET /addons/configuration-schemas with REQUIRED @httpQuery members addonName and addonVersion, 200, output addonName, addonVersion, configurationSchema (a String holding the add-on version's JSON Schema document) and podIdentityConfiguration : AddonPodIdentityConfigurationList, whose AddonPodIdentityConfiguration carries serviceAccount and recommendedManagedPolicies; errors InvalidParameterException 400 / ResourceNotFoundException 404 / ServerException 500 (same model file). The schema document is the add-on version's own published one: the recording for the EFS CSI driver version requested here declares $schema draft/2019-09, additionalProperties false, the controller and node objects with their logLevel/nodeSelector/podAnnotations/tolerations properties, replicaCount, useFIPS, and deleteAccessPointRootDir nested UNDER controller for this version. A driver that mounts a service account per component also publishes one podIdentityConfiguration entry per service account.
  Emulator: answers 200 but $.configurationSchema is a different document (value_mismatch — the served text diverges from the published schema beyond the leading $schema line, including which object the deleteAccessPointRootDir property belongs to and whether the per-component properties are declared), and $.podIdentityConfiguration[1] is missing, so only one of the add-on's service accounts is reported.
  Why: clients and CDK/Helm tooling validate the configurationValues they pass to CreateAddon/UpdateAddon against this schema; a different schema accepts configuration AWS rejects and rejects configuration AWS accepts. A missing podIdentityConfiguration entry means a client provisioning pod-identity associations creates one for only one of the add-on's service accounts, so that component has no credentials.
  Fix: the per-add-on-version configuration-schema and pod-identity data behind the DescribeAddonConfiguration handler (the schema must be keyed on the exact addonName+addonVersion requested, and every published service account must be listed).
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#1 (1 affected step).

Cause 5 of 6: the configurationSchema served for a SECOND add-on version of the same add-on is also not that version's published schema — the response does not vary with addonVersion as AWS's does.
  AWS: same operation/shapes as Cause 4. addonVersion is @required precisely because the schema is per release: the recorded schema for this version declares deleteAccessPointRootDir as a TOP-LEVEL property (not under controller as in the other recorded version), with the same additionalProperties false envelope and the same controller/node/replicaCount/useFIPS members.
  Emulator: answers 200 with $.configurationSchema diverging from the published document for this addonName+addonVersion pair (value_mismatch past the leading $schema line), and the same cluster recurs in a second fixture's discovery step, so the divergence is not specific to one trajectory.
  Why: a client that reads the schema for the exact version it is installing is validated against the wrong contract, so configuration that is valid for one release is accepted or refused as if it were another release's.
  Fix: the DescribeAddonConfiguration handler's schema lookup and data — one published schema document per (addonName, addonVersion), not one shared document per add-on.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#2 (representative; 2 affected steps, the other being eks-eks-catalog-read-only-discovery#task#3).

Cause 6 of 6: the addonVersions release history served for a filtered DescribeAddonVersions query is a synthesised release list, not the add-on's published releases.
  AWS: same operation/shapes as Cause 1. For a given addonName and kubernetesVersion filter, addonVersions holds the published releases of that add-on that apply, each AddonVersionInfo with its own addonVersion string, architecture, computeTypes and compatibilities list (one entry per compatible clusterVersion, with platformVersions and the defaultVersion flag), plus requiresConfiguration / requiresIamPermissions. The recorded response's addonVersions[0] and addonVersions[1] are consecutive published releases of the requested add-on whose compatibilities span the older cluster-version range the add-on actually supports, with defaultVersion false on those rows.
  Emulator: answers 200 but serves entirely different rows at $.addons[0].addonVersions[0] and $.addons[0].addonVersions[1]: a different version string, a different computeTypes set and a compatibilities list covering a different (newer) cluster-version range with defaultVersion true — i.e. the rows are generated rather than read from the catalog, so neither the version a client asked about nor its compatibility range is reported truthfully.
  Why: CreateAddon/UpdateAddon callers choose addonVersion from this list; a generated list makes them install a version the add-on never published, or refuse one it did, and the defaultVersion flag misidentifies which release EKS defaults to for the cluster's version.
  Fix: the DescribeAddonVersions handler's per-add-on release-history data and the kubernetesVersion/addonName filter applied to it.
  Traces: eks-mbes-traj-create-addon-request-mistakes#task#7 (1 affected step).

Note on recorded values: the literal add-on names, version strings, cluster-version numbers, URLs, dates and schema texts quoted above are the recorded catalog rows, cited only to identify WHICH rows diverge. The requirement is that these reads serve the published AWS catalog selected by the request's filters, not these literal values.
