# swf: IAM authorization is never evaluated — unpermitted/condition-denied SWF calls answer 200 instead of AccessDeniedException, and an unpermitted decision pseudo-action is applied instead of failing (3 causes)

> _Note: this issue was identified against the code base at commit `a24aa969c7ede1b0812774a0cc80ce835cb01596`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeWorkflowExecution

## Description
Three net-new causes, all in the SWF request path's (missing) authorization step. The emulator never consults the signing principal's identity-based policy, so every call that AWS refuses is served normally.

Cause 1 of 3: identity-based ALLOW is not required for SWF API actions. Failing checks: swf.describe-workflow-execution-without-permission-rejected, swf.signal-from-role-lacking-signal-permission-rejected, swf.respond-activity-failed-from-role-lacking-permission-rejected, swf.respond-decision-completed-without-permission-rejected.
AWS: a request signed by an assumed-role session whose policy does not allow the action is refused by IAM before the service acts. Recorded behavior: HTTP 400, error code `AccessDeniedException`, message `User: <caller-arn> is not authorized to perform: <swf:Action> on resource: <domain-arn> because no identity-based policy allows the <swf:Action> action`. Fixed text of that template: `User: `, ` is not authorized to perform: `, ` on resource: `, ` because no identity-based policy allows the `, ` action`; the variable parts come from the request and state — the caller ARN (`arn:aws:sts::<account>:assumed-role/<role>/<session>` for a role session, `arn:aws:iam::<account>:user/<name>` for a user), the action name (`swf:DescribeWorkflowExecution`, `swf:SignalWorkflowExecution`, `swf:RespondActivityTaskFailed`, `swf:RespondDecisionTaskCompleted`), and the resource ARN `arn:aws:swf:<region>:<account>:/domain/<domain>`. Smithy (com.amazonaws.swf) models no AccessDeniedException — this refusal is the IAM front door, not a modeled service fault — but every one of these operations documents "If the caller doesn't have sufficient permissions to invoke the action ... the action fails" and models `OperationNotPermittedFault` (HTTP 400) as its service-side equivalent.
Emulator: each call is served as if fully authorized. DescribeWorkflowExecution returned 200 with the complete `executionInfo`/`executionConfiguration`/`openCounts` body for a role allowed only `swf:GetWorkflowExecutionHistory`; SignalWorkflowExecution, RespondActivityTaskFailed and RespondDecisionTaskCompleted each returned HTTP 200 with the modeled empty body (`content-length: 2`) for roles whose only statement allowed other actions.
Why: a client that uses least-privilege roles sees no refusal at all. Negative-path tests of SWF authorization pass against AWS and silently invert here, and an emulator used to validate a policy before deployment reports a policy as sufficient when AWS will reject it.
Fix: the SWF service's request pipeline needs an authorization step that resolves the signing principal (including STS session credentials) to its identity-based policy and refuses the request with 400 `AccessDeniedException` and the message template above before any operation handler runs; today no handler under services/service-com-amazonaws-swf-simpleworkflowservice/src/ops/ consults the caller at all.
Traces: swf.describe-workflow-execution-without-permission-rejected, swf.signal-from-role-lacking-signal-permission-rejected, swf.respond-activity-failed-from-role-lacking-permission-rejected, swf.respond-decision-completed-without-permission-rejected.

Cause 2 of 3: SWF's policy condition keys are ignored, so a grant narrowed by a condition behaves as an unconditional grant. Failing checks: swf.poll-for-activity-task-outside-task-list-condition-denied, swf.poll-for-decision-task-outside-permitted-task-list-rejected, swf.start-workflow-execution-of-unpermitted-type-rejected, swf.list-closed-executions-outside-permitted-tag-filter-rejected.
AWS: `swf:taskList.name` (PollForActivityTask/PollForDecisionTask), `swf:workflowType.name` (StartWorkflowExecution) and `swf:tagFilter.tag` (ListClosedWorkflowExecutions) are evaluated against the request's own parameters; a request whose parameter falls outside the condition is refused with the same 400 `AccessDeniedException` template as Cause 1, naming that operation's action. The SWF operation docs state this directly ("Use an Action element to allow or deny permission to call this action. You can use IAM policy condition keys to constrain this action's parameters"; when the parameter values fall outside the specified constraints the action fails).
Emulator: every conditioned call succeeded. PollForActivityTask on a withheld task list handed out a real task (200, `taskToken`, `activityId`, `startedEventId`); PollForDecisionTask on a withheld task list returned a decision task with its full `events` list; StartWorkflowExecution of a workflow type outside `swf:workflowType.name` was accepted and started the run; ListClosedWorkflowExecutions with a tag outside `swf:tagFilter.tag` answered the matching execution id instead of refusing.
Why: the condition keys are the only way to fence SWF workers to their own task list and callers to their own workflow types/tags. Against the emulator a worker reaches every task list in the domain and a caller starts any type, so a tenant-isolation design verified here is not the one AWS enforces.
Fix: the same authorization step must bind the request's parameters as condition-key values (taskList.name, workflowType.name/version, tagFilter.tag, activityType.name/version) and evaluate policy conditions against them, refusing with 400 `AccessDeniedException`.
Traces: swf.poll-for-activity-task-outside-task-list-condition-denied, swf.poll-for-decision-task-outside-permitted-task-list-rejected, swf.start-workflow-execution-of-unpermitted-type-rejected, swf.list-closed-executions-outside-permitted-tag-filter-rejected.

Cause 3 of 3: a decision pseudo-action is applied without authorizing it, so no `*Failed` event with cause `OPERATION_NOT_PERMITTED` is ever recorded. Failing check: swf.record-marker-decision-without-permission-fails.
AWS: a decider whose role allows only `swf:PollForDecisionTask` and `swf:RespondDecisionTaskCompleted` may answer the decision task, but each decision it returns is itself authorized against a pseudo-action (here `swf:RecordMarker`). An unauthorized decision is not applied: history records `RecordMarkerFailed` with `cause=OPERATION_NOT_PERMITTED`, `markerName` = the decision's markerName and `decisionTaskCompletedEventId` = that call's own DecisionTaskCompleted eventId, and NO `MarkerRecorded`. Smithy: `RecordMarkerFailedCause` enumerates exactly one value, `OPERATION_NOT_PERMITTED`, and every `Schedule*/Start*/RequestCancel*FailedCause` carries that value too (`ScheduleLambdaFunctionFailedCause`, `RequestCancelActivityTaskFailedCause`, `StartChildWorkflowExecutionFailedCause`, ...), with the doc note "If cause is set to OPERATION_NOT_PERMITTED, the decision failed because it lacked sufficient permissions". RespondDecisionTaskCompleted itself answers 200 in both cases — the divergence is in the history.
Emulator: the history after the restricted decider's RecordMarker decision is ['WorkflowExecutionStarted', 'DecisionTaskScheduled', 'DecisionTaskStarted', 'DecisionTaskCompleted', 'MarkerRecorded'] — the marker was recorded and no `RecordMarkerFailed` event exists.
Why: `OPERATION_NOT_PERMITTED` is the only channel by which a decider learns its policy is too narrow; a workflow that should stall on an unpermitted decision instead proceeds as if permitted, so the emulator cannot reproduce that whole failure class.
Fix: the decision-application loop in the RespondDecisionTaskCompleted handler (services/service-com-amazonaws-swf-simpleworkflowservice/src/ops/respond_decision_task_completed.rs) must authorize each decision's pseudo-action against the calling principal and, when it is not allowed, append the decision's `*Failed` event with `cause=OPERATION_NOT_PERMITTED` instead of applying it.
Traces: swf.record-marker-decision-without-permission-fails.
