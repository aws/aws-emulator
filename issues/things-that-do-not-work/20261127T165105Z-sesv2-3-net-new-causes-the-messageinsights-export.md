# sesv2: 3 net-new causes — the MessageInsights export VDM gate is missing, SendBulkEmail checks the sending pause before sender verification, and SendCustomVerificationEmail is still a 501 stub

> _Note: this issue was identified against the code base at commit `43ebd6ce98e7173c42d111a904ff9f0222d298b2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateExportJob

## Description
Three net-new root causes on service token sesv2, none of them marked ALREADY FILED or OWNED by the replay report.

Cause 1 of 3: CreateExportJob with a MessageInsightsDataSource is accepted while the account has VdmEnabled=DISABLED.
AWS: Smithy (sesv2): CreateExportJob is POST /v2/email/export-jobs, success 200, output JobId; modeled refusals BadRequestException (errorKind client, httpError 400), LimitExceededException (400), NotFoundException (404), TooManyRequestsException (429). ExportDataSource.MessageInsightsDataSource is a Virtual Deliverability Manager surface ("An object that contains filters applied when performing the Message Insights export."); the gate's wording is recorded behavior only. Recorded behavior: with GetAccount reporting VdmAttributes.VdmEnabled=DISABLED, a MessageInsights CreateExportJob is refused with HTTP 400, code BadRequestException and the message "To use this feature you must enable Virtual Deliverability Manager" — that sentence is entirely fixed text, with no variable part — and NO job is created (the ListExportJobs(ExportSourceType=MESSAGE_INSIGHTS) id set is unchanged across the refusal). With VdmEnabled=ENABLED the same create succeeds.
Emulator: answers HTTP 200 with a minted JobId — replay reports "expected the call to be refused, but it succeeded: {'ResponseMetadata': {'HTTPStatusCode': 200, ...}, 'JobId': 'f4d68b4e-6bcc-419f-b06d-595fce1cd801'}" — so the VDM gate is not applied to the MessageInsights data source, and an export job exists that AWS would never have created. The fixed issue 20261110T191812Z-sesv2-createexportjob-with-a-metricsdatasource-is-accepted-while-account.md gated the MetricsDataSource branch only; that resolved issue does not cover this one, and this check fails on an ACCEPTANCE, not on a refusal it left behind.
Why: a client that uses the refusal to discover VDM is off (and must be enabled) is told its export was accepted, then gets a job AWS would not have; worse, a MessageInsights export silently appears to work on an account where the feature is disabled, so nothing tells the caller the data will not be there.
Fix: the CreateExportJob handler's data-source gating (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_export_job.rs), which must consult the account's VdmAttributes.VdmEnabled for the MessageInsightsDataSource branch exactly as it does for MetricsDataSource, refuse with BadRequestException before any job id is minted, and leave the export-job store untouched.
Traces: sesv2.export-job-message-insights-vdm-gate-and-job-id-errors.

Cause 2 of 3: SendBulkEmail evaluates a configuration set's sending pause BEFORE the sender-identity verification gate, so the paused set shadows the sender refusal.
AWS: Smithy (sesv2): SendBulkEmail is POST /v2/email/outbound-bulk-emails (success 200, output BulkEmailEntryResults required) and models both MessageRejected (client, 400, doc "The message can't be sent because it contains invalid content.") and SendingPausedException (client, 400); which one wins is recorded behavior. Recorded behavior: a SendBulkEmail from an unverified sender is refused for the SENDER regardless of the configuration set's sending switch — code MessageRejected with the message "Email address is not verified. The following identities failed the check in region <REGION>: <identity>[, <identity>...]", where everything up to and including the colon is fixed text, <REGION> is the request's region upper-cased and the identity list is the identities that failed verification for that request. The identical call through a set whose SendingEnabled is true gives that same refusal (the check's control assertion passes against the emulator), and the paused set still reports SendingOptions {SendingEnabled: false} and still answers SendingPausedException to SendEmail afterwards.
Emulator: through the paused set SendBulkEmail answers ('SendingPausedException', 'Sending is paused for configuration set <set-name>') instead — replay: "SendBulkEmail through the paused set gave ('SendingPausedException', 'Sending is paused for configuration set sim2real-bulk-off-33fc8a6463ed'), not the sender refusal". The pause check is ordered ahead of the identity gate on the bulk path.
Why: the client is told the configuration set is paused when the real and only reason AWS rejects the send is the unverified sender. Code that branches on MessageRejected (fix the identity) versus SendingPausedException (resume sending) takes the wrong branch, and resuming the set would not make the send succeed. Note open issue 20261124T235503Z-sesv2-send-path-s-unverified-identity-refusal-wrong.md covers the bulk gate being absent entirely and its message's identity list — it does not carry this check and does not describe this ordering, so it does not close this cause.
Fix: the SendBulkEmail handler's refusal ordering (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_bulk_email.rs and the shared send-path gate it calls), which must run the sender-identity verification gate before the configuration set's sending-pause check, as the single-send path's recorded ordering requires.
Traces: sesv2.send-bulk-email-through-paused-configuration-set-rejected-by-sender-verification.

Cause 3 of 3: SendCustomVerificationEmail is an unimplemented scaffold stub, so every call is refused with an unmodeled NotImplemented error.
AWS: Smithy (sesv2): SendCustomVerificationEmail is POST /v2/email/outbound-custom-verification-emails, success 200, output MessageId; required input EmailAddress and TemplateName (len 1..), optional ConfigurationSetName; modeled refusals BadRequestException (400), LimitExceededException (400), MailFromDomainNotVerifiedException (400), MessageRejected (400), NotFoundException (404), SendingPausedException (400), TooManyRequestsException (429). Documented behavior: it adds the address to the account's identities and sends a customized verification mail, and "To use this operation, you must first create a custom verification email template." Recorded behavior: with a TemplateName that was never created the call is refused with code BadRequestException (HTTP 400) — whether the sandbox gate or the template lookup refuses first is account standing, so the requirement graded here is the error class — and the refusal leaves no trace: the recipient is NOT created as an identity, so GetEmailIdentity on it answers NotFoundException with "Email identity <<EMAIL>> does not exist." (fixed text with the requested address between the angle brackets) and it is absent from ListEmailIdentities, while an identity created beside it reads and lists normally.
Emulator: the handler is the generated stub — services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_custom_verification_email.rs still carries the "SCAFFOLDED, NOT IMPLEMENTED" marker and returns Scaffolded::not_implemented("SendCustomVerificationEmail"), i.e. HTTP 501 with code NotImplemented. Replay: "SendCustomVerificationEmail with a template that was never created raised 'NotImplemented'". (This check is not marked ALREADY FILED by the report — the assertion text prints only the code, so the stub detector could not attribute it — and no open issue names this operation.)
Why: an error code no SESv2 client models, at a status the SDK treats as a server fault, instead of the modeled 400 BadRequestException. No caller can exercise custom-verification sending at all, and the "a refused send creates no identity" property cannot be observed.
Fix: implement the operation in its own handler file (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_custom_verification_email.rs) — resolve TemplateName against the custom-verification template store, refuse an unknown template as a modeled 400 BadRequestException without creating the recipient identity, otherwise create/verify the address and return MessageId — and delete the SCAFFOLDED marker line.
Traces: sesv2.send-custom-verification-email-unknown-template-recipient-reads-as-unknown-identity.
