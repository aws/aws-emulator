# MSK asynchronous lifecycles never settle: channel, configuration-delete, replicator, topic/reboot, multi-VPC connectivity and the public SASL/SCRAM broker all leave their callers polling, so nine checks reach no verdict (6 causes)

> _Note: this issue was identified against the code base at commit `d0b60cf4e620490598360e9e180ae29d3f253b9d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeReplicator

## Description
SIX distinct net-new root causes in the kafka service, each grounded in failing behavioral checks that the suite report marked neither ALREADY FILED nor OWNED by an open issue. Every one of the nine checks ends with the bare detail 'Error: Check timed out after 60.0s' — no HTTP status, no error code, no traceback frame — because an asynchronous resource state the check polls for (at AWS-sized cadences of 10-30 s with 300-4800 s budgets) never reaches its terminal value, so the first probe's deadline consumes the whole wall-clock ceiling and no assertion is ever evaluated. Each cause below must be closed separately before this issue is submitted.

=== Cause 1 of 6: a channel created on an Express cluster never settles to ACTIVE, so the ListChannels pagination contract is unverifiable. (Failing check: kafka.channel-list-pagination-and-filter-consistency.)
AWS: Smithy com.amazonaws.kafka#Kafka — DescribeChannel GET /v1/clusters/{ClusterArn}/channels/{ChannelArn}, code 200, with REQUIRED output members channelArn, channelName, status, destinationType, creationTime, topicConfigurationList; Status is the ChannelStatus enum [CREATING, ACTIVE, UPDATING, DELETING, FAILED, SUSPENDING, SUSPENDED], so a newly created channel moves CREATING -> ACTIVE. CreateChannel echoes no status, so DescribeChannel/ListChannels are the only observation path. ListChannels GET /v1/clusters/{ClusterArn}/channels, code 200, input MaxResults (@range 1..100, httpQuery maxResults), NextToken (httpQuery nextToken), TopicNameFilter; output channels + nextToken: five channels read with MaxResults=2 must take at least three pages and return each ChannelArn exactly once, with no duplicate or dropped entry at a page boundary. Modeled refusals are BadRequestException 400, ForbiddenException 403, NotFoundException 404, UnauthorizedException 401, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503 — none was served.
Emulator: the sequence CreateClusterV2(Provisioned, InstanceType express.m7g.large, KafkaVersion 3.8.x, 3 AZ-distinct ClientSubnets) -> wait State ACTIVE (DescribeClusterV2, 20 s interval, 3000 s budget) -> CreateTopic -> wait Status ACTIVE (DescribeTopic, 5 s/300 s) -> CreateChannel x5 -> wait Status ACTIVE (DescribeChannel, 10 s/900 s) -> paginate ListChannels never produces a response the check can assert on; it is killed at 60 s. Hypothesis (the replay output names no frame): the channel's CREATING -> ACTIVE transition (or, before it, the Express cluster's or the topic's) never happens, so _wait_channel_status burns its whole budget. ListChannels is never reached, so this is not the ListChannels stub issue.
Why: a client that creates MSK data-delivery channels and waits for them to be usable hangs on its own waiter, and because CreateChannel echoes no state it cannot tell 'still provisioning' from 'silently dropped'. The pagination guarantee — every channel exactly once across pages — is unverifiable.
Fix: the channel state machine in the kafka service's state layer plus the CreateChannel / DescribeChannel handlers (and the Express-cluster and topic settling in front of them): a created channel must settle CREATING -> ACTIVE within a probe or two at an AWS-sized cadence, and ListChannels must page it.

=== Cause 2 of 6: DeleteConfiguration leaves the configuration present forever — DescribeConfiguration keeps answering State DELETING and never refuses the deleted ARN. (Failing check: kafka.configuration-delete-in-use-conflict.)
AWS: Smithy DeleteConfiguration DELETE /v1/configurations/{Arn}, code 200, output {arn, state} where state is the ConfigurationState enum [ACTIVE, DELETING, DELETE_FAILED]; the delete is asynchronous, so DescribeConfiguration GET /v1/configurations/{Arn} answers State DELETING for a bounded window and then refuses the ARN with HTTP 400 BadRequestException and the message 'Configuration ARN does not exist.' (fixed text, no interpolation). The check's whole point then follows: with the configuration attached to a cluster via UpdateClusterConfiguration, DeleteConfiguration is refused 400 BadRequestException with the fixed message 'Configuration is in use by one or more clusters. Dissociate the configuration from the clusters.' and the configuration stays State ACTIVE; once the cluster is moved to another configuration the same delete succeeds.
Emulator: the check dies at the 60 s ceiling on its POSITIVE CONTROL — the very first delete of an unattached configuration — before any in-use refusal is exercised. Its probe asserts on every answer (a wrong code/message or a non-DELETING state would have raised an assertion immediately, with a frame), so the only outcome consistent with a bare timeout is that the probe keeps observing the same non-terminal answer: DescribeConfiguration answering State DELETING indefinitely, i.e. the configuration is marked DELETING but never removed. Hypothesis: the deleted configuration is never reaped from state (labelled a hypothesis because the replay detail carries no frame).
Why: a client that deletes an MSK configuration and waits for it to disappear (the documented way to confirm the delete, since the response only reports DELETING) waits forever, and it can never distinguish 'delete in flight' from 'delete lost'. The in-use protection itself — the refusal that keeps a cluster's configuration from vanishing underneath it — is left completely unexercised.
Fix: the DeleteConfiguration handler and the configuration store in the kafka service's state layer: a configuration marked DELETING must be removed, after which DescribeConfiguration must answer 400 BadRequestException 'Configuration ARN does not exist.'; the in-use case must stay ACTIVE and be refused with the in-use message above.

=== Cause 3 of 6: nothing accepts a SASL/SCRAM connection on the public bootstrap endpoint the emulator publishes, so SCRAM credential revocation cannot be observed. (Failing check: kafka.scram-secret-disassociation-immediate-auth-revocation.)
AWS: Smithy GetBootstrapBrokers GET /v1/clusters/{ClusterArn}/bootstrap-brokers, code 200, whose output member bootstrapBrokerStringPublicSaslScram is a comma-separated list of host:port pairs; the contract of that string is that each announced address is one the service itself accepts a Kafka wire-protocol connection on — a client takes it verbatim, completes the SASL/SCRAM-SHA-512 handshake with the username/password held in the associated AmazonMSK_* secret, and reads metadata. BatchDisassociateScramSecret PATCH /v1/clusters/{ClusterArn}/scram-secrets, code 200, removes the secret (output unprocessedScramSecrets empty on success), ListScramSecrets stops listing it at once, and within the documented propagation window the brokers answer that user's SASL exchange with an authentication failure while a still-associated secret keeps authenticating (recorded behavior for the data-plane half).
Emulator: the check is killed at 60 s with no verdict. After CreateClusterV2(Sasl.Scram enabled) -> wait ACTIVE -> UpdateConnectivity(PublicAccess SERVICE_PROVIDED_EIPS) -> wait ACTIVE -> GetBootstrapBrokers(BootstrapBrokerStringPublicSaslScram), the first act is a SASL_SSL probe with a 30 s bootstrap timeout retried for 180 s; the bare timeout means that probe never got an authentication verdict. Hypothesis: no listener answers on the published public SASL/SCRAM address (the address is routed through the harness's endpoint mapping before dialling, so the failure is a connection/handshake that never completes, not a rejected host name); alternatively the UpdateConnectivity operation or the cluster never returns to ACTIVE ahead of it. Either way it is the emulator's own data plane: it published an address and then served nothing there.
Why: a client configured from GetBootstrapBrokers points its producer, consumer and admin client at an address that answers nothing, so SASL/SCRAM authentication, the revocation of a disassociated secret and the positive control that an unrelated secret still authenticates are all unobservable — MSK's credential lifecycle is verifiable only on the control plane.
Fix: the kafka service's broker listener and the GetBootstrapBrokers broker-string assembly: the published public SASL/SCRAM host:port must be an address the emulator answers on, completing SCRAM-SHA-512 for associated secrets and failing authentication for disassociated ones.
