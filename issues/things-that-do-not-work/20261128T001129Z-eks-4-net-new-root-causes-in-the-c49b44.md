# eks: 4 net-new root causes in the served cluster Kubernetes API — projected ServiceAccount tokens omit the serviceaccount uid claim, core/v1 ResourceQuota and apps/v1 ReplicaSets are not served resource types, and pod-identity credential injection never converges

> _Note: this issue was identified against the code base at commit `5cb989982ca164b028438556d2b2a85d4de8b473`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TokenRequest (served cluster Kubernetes API)

## Description
FOUR separate net-new root causes in the eks service, each grounded in failing behavioral checks that no open issue carries the replay key for. Each cause is a SEPARATE defect and must be closed separately; its own failing check ids are listed with it.

Cause 1 of 4: the projected ServiceAccount token the cluster mints carries no `uid` inside its `kubernetes.io.serviceaccount` claim block, so the token is not bound to the ServiceAccount object the API server stored.
AWS:      recorded behavior only (no Smithy member models the token payload; Smithy only models the control-plane identity the token is signed for — DescribeCluster returns Cluster.identity.oidc.issuer). On a real EKS cluster a bound ServiceAccount token issued through the Kubernetes TokenRequest subresource (POST /api/v1/namespaces/<ns>/serviceaccounts/<sa>/token) carries, besides the registered claims, a `kubernetes.io` claim object of the form {"namespace": "<namespace>", "serviceaccount": {"name": "<serviceaccount name>", "uid": "<the metadata.uid the API server assigned that ServiceAccount>"}} (and a "pod" entry with name/uid when the token is projected into a pod). The requirement is that `kubernetes.io.serviceaccount.uid` be PRESENT and equal to the metadata.uid of the ServiceAccount the same API server reports for that namespace/name — the per-run uid value itself is not the requirement, the equality and the presence of the member are.
Emulator: the minted token's payload decodes with correct `iss`, `aud`, `sub` and `kubernetes.io.namespace` and `kubernetes.io.serviceaccount.name` (those assertions now pass), but the `serviceaccount` object has NO `uid` member at all — reading it raises KeyError: 'uid'. The token is therefore not bound to any stored object identity.
Why:      a client cannot tell a token minted for a ServiceAccount from a token minted for a recreated ServiceAccount of the same name: the uid is the only claim that distinguishes them, and it is what a controller, an admission webhook or an audit consumer matches a token against. Any consumer that validates the uid (or echoes it) sees an absent field and either crashes or silently accepts a stale token. Both IRSA negative-contrast flows below fail at this claim before they can exercise their intended denials.
Fix:      the token-minting seam of the served cluster Kubernetes API (the code that builds the JWT payload for the TokenRequest subresource): it must emit kubernetes.io.serviceaccount.uid from the stored ServiceAccount's metadata.uid, the same value the API server returns when the object is read.
Note:     the open issue 20261122T113249Z-eks-5-net-new-root-causes-minted-serviceaccount.md lists both checks below and states the ADJACENT `iss`-claim cause (the token naming a real-AWS OIDC host); its replay keys are the `claims["iss"] == issuer` assertions, which now pass. The replay reports these two checks unowned and they fail one assertion later, on the missing uid. The uid claim is not covered by that issue.
Traces:   eks.irsa-cross-namespace-serviceaccount-token-rejected, eks.irsa-web-identity-rejected-when-the-oidc-provider-is-deregistered.

Cause 2 of 4: the served cluster Kubernetes API does not serve the core/v1 ResourceQuota kind, so a namespace quota cannot be created and quota admission is unobservable.
AWS:      recorded behavior only (the Kubernetes data plane of an EKS cluster is not in the EKS Smithy model). A real EKS cluster's API server serves ResourceQuota in the core group at apiVersion v1 (discovery lists `resourcequotas` under /api/v1 as a namespaced resource), so `kubectl apply -f -` of a ResourceQuota manifest succeeds; the quota controller then populates .status.hard/.status.used and the admission plugin refuses a pod whose requests exceed the namespace quota with a 403 "exceeded quota: <quota name>, requested: ..., used: ..., limited: ..." (the quota name, the resource names and the three quantity lists are values from the request and the namespace's state; the sentence stem "exceeded quota: " is fixed text).
Emulator: `kubectl apply -n <namespace> -f -` of a ResourceQuota is refused by the served API with `unable to recognize no matches for kind "ResourceQuota" in version "v1"` — i.e. the kind is absent from the API's discovery/resource set, so the object can never be created and the over-quota pod refusal is never reached.
Why:      a client cannot set or enforce namespace resource limits at all. Multi-tenant namespace guardrails silently do not exist: a pod that AWS would refuse with a 403 quota error is admitted, and tooling that applies a quota as part of a namespace bootstrap fails at apply time with a kind-not-recognised error rather than any API error class.
Fix:      the served cluster Kubernetes API's core/v1 resource registry and discovery (the seam that enumerates namespaced core resources) must register `resourcequotas`, plus the quota status population and the admission check that refuses a pod exceeding it.
Traces:   eks.k8s-resourcequota-rejects-a-pod-over-the-namespace-limit.

Cause 3 of 4: the served cluster Kubernetes API has no `replicasets` resource type, so a Deployment produces no ReplicaSets and a rolling update cannot be observed.
AWS:      recorded behavior only. A real EKS cluster serves ReplicaSet in the apps group at apiVersion apps/v1 (discovery lists `replicasets` as a namespaced resource with the `rs` short name), and every Deployment is implemented through ReplicaSets: `kubectl get replicasets -n <ns> -o json` lists the Deployment's current and previous ReplicaSets, and a rolling update (maxSurge/maxUnavailable) is visible as the new ReplicaSet scaling up while the old one scales down, with the Service never losing all ready endpoints.
Emulator: `kubectl get replicasets -n <namespace> -o json` is answered `error: the server doesn't have a resource type "replicasets"` — the apps/v1 ReplicaSet resource is not served, so a Deployment's rollout has no intermediate objects to observe and the rollout's surge/unavailability behaviour cannot be verified.
Why:      a client cannot inspect or debug a Deployment rollout: `kubectl rollout`/`get rs`, rollback to a previous ReplicaSet, and any controller or dashboard that reconciles on ReplicaSets all break. A Deployment that appears to update may be replacing pods in a way that drops the Service, and nothing exposes it.
Fix:      the served cluster Kubernetes API's apps/v1 resource registry and discovery must register `replicasets`, and the Deployment controller seam must materialise a ReplicaSet per pod-template revision and drive the rolling update through them.
Traces:   eks.k8s-rolling-update-replaces-pods-without-dropping-the-service.

Cause 4 of 4: EKS Pod Identity never becomes usable inside a pod — with the eks-pod-identity-agent add-on installed and an association created, the pod never gains the injected credential environment, so neither the allowed access nor the intended denial is reachable.
AWS:      recorded behavior only for the data-plane effect; Smithy models the control-plane records it depends on (CreatePodIdentityAssociation / DescribePodIdentityAssociation echo clusterName, namespace, serviceAccount, roleArn). On a real cluster, once the eks-pod-identity-agent add-on is ACTIVE and an association exists for (namespace, serviceAccount), the pod-identity mutating webhook injects AWS_CONTAINER_CREDENTIALS_FULL_URI = http://169.254.170.23/v1/credentials and AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE into every container of a pod using that ServiceAccount, together with a projected `eks-pod-identity-token` volume with audience pods.eks.amazonaws.com; an SDK in the pod then obtains session credentials scoped to the association's role, so a read of an allowed bucket succeeds and a read of a bucket the role's policy does not allow is refused AccessDenied.
Emulator: the check is cut off with "Check timed out after 60.0s" while polling for the pod to become usable; the injected credential variables, the projected token volume and the in-pod credential fetch never converge, so neither the allowed-bucket success nor the unallowed-bucket AccessDenied is ever observed. The control-plane calls themselves answer.
Why:      a workload cannot get credentials through Pod Identity at all, and a client cannot distinguish a correctly scoped association from a misconfigured one: the denial that proves scoping is as unobservable as the success.
Fix:      the pod admission/mutation seam of the served cluster Kubernetes API (the eks-pod-identity-agent webhook injection of the credential URI/token-file environment and the projected eks-pod-identity-token volume) and the credential endpoint that serves the association's role, so a pod using the associated ServiceAccount reaches a usable state promptly.
Note:     the open issues 20261121T142446Z-eks-4-net-new-root-causes-admitted-pods.md and 20261122T113249Z-eks-5-net-new-root-causes-minted-serviceaccount.md both list this check among their trace ids and describe the pod-identity webhook half, but each carries a different (inner `_wait_for` frame) replay key for it; the replay reports the check unowned and it reproduces at this commit, so it is filed here.
Traces:   eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied.
