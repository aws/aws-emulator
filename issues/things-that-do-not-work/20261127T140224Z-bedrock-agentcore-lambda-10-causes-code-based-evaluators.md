# bedrock-agentcore__lambda: 10 causes — code-based evaluators are unresolvable by Evaluate, gateway interceptors never run, Lambda-target client context is unqualified, the HTTP passthrough path 404s, and gatewayUrl names no gateway

> _Note: this issue was identified against the code base at commit `461e190cfbed2a60f922688bafee74a0fd88eec8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Evaluate

## Description
Ten net-new root causes in the AgentCore surfaces that use a Lambda function (evaluators, gateway targets, gateway interceptors). Each cause is numbered with its own failing checks.

Cause 1 of 10: Evaluate cannot resolve a code-based (Lambda-backed) evaluator that CreateEvaluator just created.
AWS: recorded behavior only for the registry linkage; the recording shows CreateEvaluator returning an evaluatorId with status ACTIVE and Evaluate then running that evaluator's Lambda function, mapping the function's answer (label/value/explanation) into the evaluation result, and refusing a function answer without a label. ResourceNotFoundException is reserved for an evaluator that does not exist.
Emulator: every Evaluate call on a code-based evaluator fails with ResourceNotFoundException 'Custom evaluator not found: <evaluatorId>' for the id CreateEvaluator returned moments earlier.
Why: the whole code-based evaluation surface is unusable — a client cannot score any span, trace or session through its own Lambda evaluator, and the error claims the resource it created does not exist.
Fix: the evaluator lookup in the Evaluate handler and the state CreateEvaluator writes for CUSTOM/code-based evaluators (the two do not agree on the key).

Cause 2 of 10: CreateEvaluator accepts a code-based evaluator whose Lambda function does not exist.
AWS: recorded behavior only: CreateEvaluator naming a function ARN that does not exist is refused at create time (the evaluator is not created).
Emulator: the call answers HTTP 202 with status ACTIVE and an evaluatorArn for a function that was never created.
Why: the failure moves from create time to evaluation time (or nowhere at all), so a client's mis-typed function ARN is reported as a healthy evaluator.
Fix: function existence/permission validation in the CreateEvaluator handler.
Traces: bedrock-agentcore__lambda.code-based-evaluator-missing-lambda-function-rejected.

Cause 3 of 10: gateway request and response interceptors are never invoked — the target's own request/response passes through unchanged.
AWS: recorded behavior only (interceptor contract). The recording shows, for a gateway with a Lambda request interceptor attached: the interceptor receives a versioned event carrying gatewayRequest (raw and parsed body, including the MCP method, and the caller's headers only when passRequestHeaders is true), its transformed body is what the target Lambda receives, its denial short-circuits the call so the target is never invoked, and an interceptor output whose version is absent or not '1.0' makes the call fail (HTTP 500) rather than succeed. For a response interceptor: it receives the request plus the buffered target response (status code and body, isStreamingResponse for an SSE call), and its rewritten content is what the caller reads.
Emulator: the interceptors have no effect anywhere: the target receives the untransformed arguments, the caller receives the target's unrewritten result, a denial returns the tool's successful result, headers never reach the interceptor, an unsupported output version answers HTTP 200, and `gatewayRequest.body.method` is None.
Why: the entire interceptor feature — request transformation, header passing, authorization short-circuit, response rewriting, version negotiation — is silently inert, so policies a client enforces through interceptors do not apply.
Fix: invoke the configured request/response interceptor Lambdas in the gateway MCP request pipeline, and honour their output (version check, transformed body, short-circuit, rewritten response).

Cause 4 of 10: the client context a gateway passes to a Lambda target omits the gateway/target/message metadata and carries the unqualified tool name.
AWS: recorded behavior only: the gateway invokes the target function with the tool arguments as the event and a client context whose custom values are bedrockAgentCoreGatewayId, bedrockAgentCoreTargetId, bedrockAgentCoreToolName (the qualified name '<targetName>___<toolName>'), bedrockAgentCoreMcpMessageId (the JSON-RPC id of the tools/call) and bedrockAgentCoreMessageVersion ('1.0').

Why: a Lambda target cannot tell which gateway, target or MCP message invoked it, and code that parses the qualified tool name (or dispatches on it) breaks.
Fix: populate the client context in the gateway's Lambda-target invocation path.

Cause 5 of 10: the gateway's non-MCP HTTP passthrough path is not served.
AWS: recorded behavior only: a gateway with an HTTP/openapi passthrough target serves POST <gatewayUrl-host>/<target>/<path> by forwarding to the target (signing as the gateway role for IAM-auth function URLs) and returning the target's response, with request/response interceptors applied.

Cause 6 of 10: CreateGateway announces a gatewayUrl whose host does not name the gateway.
AWS: recorded behavior only: the gatewayUrl is an https URL whose host names the gateway (gateway id + the service's regional domain), so the MCP endpoint is addressable from the URL alone.

Related to open issue 20261102T055559Z-bedrock-agentcore-control-creategateway-and-getgateway-gateway-representation-diverges-gatewayurl-carries.md, which covers the trailing /mcp path; the host naming is the divergence these checks fail on.
Fix: gatewayUrl construction in the CreateGateway/GetGateway response serializer.
Traces: bedrock-agentcore__lambda.gateway-lambda-target-context-carries-message-version, bedrock-agentcore__lambda.gateway-request-interceptor-short-circuit-never-reaches-lambda-target, bedrock-agentcore__lambda.gateway-response-interceptor-receives-request-and-target-response.

Cause 7 of 10: inbound AUTHENTICATE_ONLY authorization of a gateway's MCP endpoint is not implemented.

Why: gateways using AUTHENTICATE_ONLY cannot serve any call, and 501/NotImplemented is not an error AWS returns here.
Fix: AUTHENTICATE_ONLY inbound authorization in the gateway MCP endpoint's auth path.
Traces: bedrock-agentcore__lambda.gateway-authenticate-only-defers-to-request-interceptor-denial-rejected.

Cause 8 of 10: an unsigned call to a gateway MCP endpoint is answered 403 instead of 401.
AWS: recorded behavior only: a request carrying no SigV4 signature is refused with HTTP 401 (unauthenticated), not 403.
Emulator: HTTP 403 with {"__type":"AccessDenied","message":"Sign the request with the emulator credentials"} — an emulator-authored message and the wrong status class.
Why: a client distinguishing 'not authenticated' (401, re-sign/retry) from 'not authorized' (403, give up) takes the wrong branch.
Fix: the unauthenticated-request path of the gateway MCP endpoint's auth handling.
Traces: bedrock-agentcore__lambda.gateway-authenticate-only-tool-call-without-ticket-rejected-by-interceptor.

Cause 9 of 10: an OpenAPI target over a Lambda function URL contributes no tools to tools/list.
