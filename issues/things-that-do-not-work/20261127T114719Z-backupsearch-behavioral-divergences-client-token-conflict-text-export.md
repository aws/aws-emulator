# BackupSearch behavioral divergences: client-token conflict text, export-job ARN resource type, length-constraint message rendering, missing ItemFilters/scope cross-validation and ListSearchJobBackups NextToken text (5 causes)

## Description

Each cause must be closed before this issue is done; each names its own failing check ids below.

Two open BackupSearch issues cover NEIGHBOURING but different paths and carry no replay key for anything below: 20261022T215802Z-backupsearch-refusal-fidelity-on-the-wire-not-found.md (not-found classification/text, the ENUM-in-list validation message path+bracketing, the @pattern anchors, TagResource's success status) and 20261127T090630Z-backupsearch-listsearchresultexportjobs-accepts-invalid-filter-inputs-malformed-searchjobidentifier.md (ListSearchResultExportJobs malformed SearchJobIdentifier, and the NextToken text of THAT operation only). === Cause 1 of 5: a ClientToken replayed with different input parameters is refused with an emulator-authored message instead of the service's fixed idempotency-conflict text ===
AWS: Smithy StartSearchJob (PUT /search-jobs, @idempotent, ClientToken -> String) and StartSearchResultExportJob (PUT /export-search-jobs, @idempotent, ClientToken -> String) both declare ConflictException (httpError 409). The model documents ConflictException's @required message only generically, so the text is recorded behavior only: when a ClientToken is replayed with ANY input parameter different from the previous call, both operations answer HTTP 409 ConflictException with the fixed text "At least one of the input parameters is different from the previous call to the operation. This is not allowed when clientToken is provided in the input." The whole string is fixed text — it has NO variable part: it does not name the token, the operation or the differing member.
Emulator: returns the right code and status (ConflictException, 409) but its own request-derived sentence that embeds the token value and the operation name: "ClientToken '<the token the client sent>' was already used for a different StartSearchJob request" for StartSearchJob and "... for a different StartSearchResultExportJob request" for StartSearchResultExportJob. The leading token value is taken from the request, so the string differs on every call.
Why: ConflictException carries no structured detail a caller can branch on beyond message/resourceId/resourceType, so the message is the whole explanation of why an idempotent retry was refused. A client (or SDK wrapper, or test suite) that distinguishes "same token, different request" from the other 409 conflicts this service raises — e.g. stopping an already-terminal job — by matching the service's fixed text never matches, and because the emulator interpolates the caller's token the string cannot be matched at all.
Fix: the shared client-token/idempotency conflict construction used by the StartSearchJob and StartSearchResultExportJob handlers — emit the service's fixed parameter-mismatch text instead of composing a sentence from the token and operation name.
Traces: backupsearch.start-search-job-reused-token-with-new-name-rejected (StartSearchJob), backupsearch.export-job-client-token-reuse-with-other-destination-rejected (StartSearchResultExportJob).

=== Cause 2 of 5: the export job's ARN uses resource type "export-job" instead of "search-export-job" ===
AWS: Smithy StartSearchResultExportJob output member ExportJobArn -> ExportJobArn, an @arnReference string of service com.amazonaws.backupsearch#CryoBackupSearchService; the same value is echoed by GetSearchResultExportJob.ExportJobArn and is the ResourceArn accepted by TagResource/ListTagsForResource. The model does not spell the ARN out, so the shape is recorded behavior only: an export job's ARN is arn:aws:backup-search:<region>:<account-id>:search-export-job/<ExportJobIdentifier> — the fixed parts are the partition/service segment "arn:aws:backup-search" and the resource type "search-export-job"; region, account id and the export job id come from the request context and the created job (search jobs correspondingly use the resource type "search-job").
Emulator: builds the ARN with the resource type "export-job": arn:aws:backup-search:<region>:<account-id>:export-job/<id>. Region, account and the trailing identifier are correct (the check confirms the ARN ends with the returned ExportJobIdentifier); only the resource-type segment diverges.
Why: this ARN is not decorative — it is the handle the tag APIs take. A caller that starts an export job and then calls ListTagsForResource/TagResource with the ARN the service just returned is passing a string whose resource type no account, policy or IAM condition ever matches, and any IAM policy, resource-group query, or log consumer written against the real "search-export-job" resource type fails to match the emulator's ARNs.
Fix: the export-job ARN construction in the StartSearchResultExportJob handler and wherever the export-job state renders ExportJobArn (GetSearchResultExportJob, ListSearchResultExportJobs) — plus the tag-API ARN parser, so the corrected form is still resolvable.
Traces: backupsearch.export-job-start-tags-and-completed-status-filter.

=== Cause 3 of 5: a @length violation on a list renders the rejected value as "N items" instead of the bracketed list of its elements ===
AWS: Smithy SearchScope.BackupResourceArns -> RecoveryPointArnList with @length min 0 max 50, and S3ItemFilter.ObjectKeys -> StringConditionList with @length min 1 max 10; StartSearchJob declares ValidationException (httpError 400). This message is built FROM THE REQUEST, so its rule is the requirement: AWS quotes the WHOLE rejected list value inside square brackets, comma-and-space separated, in the "Value '[...]'" segment — "1 validation error detected: Value '[<element>, <element>, ...]' at '<member path>' failed to satisfy constraint: Member must have length less than or equal to <max>". For a list of ARNs the elements appear as the ARN strings themselves; for a list of StringCondition structures each element is rendered as "StringCondition(value=<Value>, operator=<Operator>)". The fixed parts are "1 validation error detected: Value '[", "]' at '", "' failed to satisfy constraint: Member must have length less than or equal to " and the limit; the member path and the element list come from the request and the model's limit.
Emulator: returns the right code, status and member path, but substitutes a count summary for the value: "1 validation error detected: Value '51 items' at 'searchScope.backupResourceArns' failed to satisfy constraint: Member must have length less than or equal to 50" and "1 validation error detected: Value '11 items' at 'itemFilters.s3ItemFilters.1.member.objectKeys' failed to satisfy constraint: Member must have length less than or equal to 10".
Why: ValidationException has no structured field list, so the message IS the machine-readable description of what failed; CLI users, SDK wrappers and test suites read the quoted value to show the operator exactly which input was rejected. "51 items" names no input at all, so a caller that echoes or parses the rejected value shows nothing useful, and assertions on the service's rendering never match. (This is the @length branch of the same renderer whose @enum branch is filed as Cause 3 of 20261022T215802Z-backupsearch-refusal-fidelity-on-the-wire-not-found.md; that issue's cause is about the member path and nesting on an enum element and does not cover the value rendering for a length violation.)
Fix: the request-validation layer's message renderer for @length-constrained list members — render the rejected list as its bracketed, comma-separated elements rather than an item count.
Traces: backupsearch.start-search-job-fifty-one-recovery-point-arns-rejected, backupsearch.start-search-job-eleven-object-key-conditions-rejected.

=== Cause 4 of 5: ItemFilters that do not match the search scope's resource type are accepted with HTTP 200 instead of refused 400 ValidationException ===
AWS: Smithy StartSearchJob takes SearchScope (@required; BackupResourceTypes is @required, @length 1..1, enum values [S3, EBS]) and ItemFilters, whose documentation states it "Contains either EBSItemFilters or S3ItemFilters". The cross-member rule is recorded behavior only: when the scope's resource type is S3 and the request carries ItemFilters with only EBSItemFilters (no S3ItemFilters), the service refuses the call with HTTP 400 ValidationException and the fixed text "Invalid ItemFilters. S3 resource type specified but no S3ItemFilters provided" — all fixed text, naming the resource type from the request and the filter member that is missing — and starts no search job. The same filter expressed as an S3 ObjectKeys filter on that scope is accepted.
Emulator: accepts the mismatched request, answers HTTP 200 and creates a real search job: it returns a SearchJobIdentifier, SearchJobArn and CreationTime for input AWS never admits. No error is raised at all.
Why: the caller is told its search was created when AWS would have rejected it outright, and the emulator then owns a job whose item filters can never match its scope — so the run silently returns nothing instead of failing fast. Code that exercises the rejection path (validating user-built filters, surfacing the error, aborting a workflow) takes the success branch, and the resulting stray job pollutes ListSearchJobs and quota.
Fix: the StartSearchJob handler's input validation — cross-validate ItemFilters against SearchScope.BackupResourceTypes and raise the modeled ValidationException (HTTP 400) with the service's text before any job is created.
Traces: backupsearch.start-search-job-ebs-item-filter-on-s3-scope-rejected.

=== Cause 5 of 5: ListSearchJobBackups refuses an unissued NextToken with an emulator-authored message instead of the service's fixed malformed-token text ===
AWS: Smithy ListSearchJobBackups, GET /search-jobs/{SearchJobIdentifier}/backups, @paginated (inputToken/outputToken NextToken, pageSize MaxResults, items Results); NextToken is a plain String @httpQuery("nextToken") with no modeled constraint, and ValidationException (httpError 400) is a declared error. The text is recorded behavior only: a NextToken this service did not issue is refused with HTTP 400 ValidationException and the fixed text "Malformed Next Token. Please provide a valid Next Token". That string is entirely fixed — it has no variable part, and in particular does not echo the rejected token.
Emulator: returns the right code (ValidationException) but its own request-derived sentence: "NextToken '<the base64 token the client sent>' is not a pagination token this service issued".
Why: ValidationException's only content is its @required message, so the message is the entire refusal. Pagination loops and test suites that match the service's fixed malformed-token text never match, and because the emulator reflects the caller's token back the string differs on every call and cannot be matched at all. (The same defect was filed for ListSearchResultExportJobs as Cause 2 of 20261127T090630Z-backupsearch-listsearchresultexportjobs-accepts-invalid-filter-inputs-malformed-searchjobidentifier.md; that issue carries no replay key for ListSearchJobBackups, which has its own token validation.)
Fix: the ListSearchJobBackups pagination-token validation / error construction — emit the service's fixed malformed-next-token text for an unrecognized or undecodable NextToken instead of a per-request sentence; prefer the shared pagination-token error channel so the other @paginated operations of this service stay consistent.
Traces: backupsearch.list-search-job-backups-unissued-next-token-rejected.
