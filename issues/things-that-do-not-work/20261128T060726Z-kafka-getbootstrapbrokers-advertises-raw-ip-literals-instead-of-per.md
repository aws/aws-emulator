# GetBootstrapBrokers advertises raw IP literals instead of per-broker MSK broker DNS names, so b-1/b-2 broker hosts and the cluster DNS name do not exist in the VPC

> _Note: this issue was identified against the code base at commit `cb20f68e94bbc6cb070c362820a8401b3373aae4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBootstrapBrokers

## Description
ONE net-new root cause on the emulated kafka (MSK) surface. It is the only failing behavioral check under the `### kafka` heading in this run that the report marks neither ALREADY FILED nor OWNED by an open issue; every other kafka / cloudformation__kafka / kafka__lambda / kafka__logs__s3 failure in this sweep carries an owned_by and was skipped.

Cause 1 of 1: the bootstrap strings a provisioned cluster publishes name IP address literals rather than per-broker MSK broker hostnames, so there is no `b-<n>.<cluster-dns-name>` broker name and no shared cluster DNS name at all — and therefore nothing in the VPC resolver for a client to resolve, nor an unlisted broker index for it to refuse.

AWS: Smithy (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json) GetBootstrapBrokers = GET /v1/clusters/{ClusterArn}/bootstrap-brokers, success code 200; input ClusterArn (@httpLabel, required); output members BootstrapBrokerString / ...Tls / ...SaslScram / ...SaslIam (jsonName bootstrapBrokerStringSaslIam, target __string) and the Public*/VpcConnectivity*/*Ipv6 siblings; errors BadRequestException 400, ConflictException 409, ForbiddenException 403, UnauthorizedException 401, InternalServerErrorException 500. The model types each member only as __string, so the string's internal structure is recorded behavior only: on real MSK each member is a comma-separated `host:port` list with one entry per broker node, all entries sharing the one port of that access method (9098 for SASL/IAM), and every host is a DNS NAME of the documented per-broker form `b-<broker-index>.<cluster-name>.<id>.<n>.kafka.<region>.amazonaws.com` (https://docs.aws.amazon.com/msk/latest/developerguide/get-bootstrap-cli.html). The invariant a client depends on: the first label of every advertised host is that broker's index label (`b-1`, `b-2`, ... one per broker node, never repeated), and all brokers share ONE remainder — the cluster DNS name. Inside the cluster's VPC, the VPC resolver (the .2 address of the VPC CIDR) answers A records for those names: the cluster DNS name answers the addresses of ALL brokers (one A per broker, each inside a client subnet's CIDR), each `b-<n>` name answers exactly that broker's single address, and a broker index the cluster does not have (`b-3` on a 2-broker cluster) is refused with NXDOMAIN (DNS RCODE 3) and zero answer records.

Emulator: for a provisioned cluster (kafka.t3.small, KafkaVersion 3.9.x, NumberOfBrokerNodes=2 over 2 client subnets, SASL/IAM enabled, Unauthenticated disabled, ClientBroker TLS, PublicAccess DISABLED) GetBootstrapBrokers answers 200 with a BootstrapBrokerStringSaslIam whose two entries are IP literals: splitting each entry on ':' and taking the first dot-separated label of the host yields `['127', '127']` instead of `['b-1', 'b-2']`. No status or error code diverges — the 200's string CONTENT is wrong. Because the hosts are address literals, there is also no cluster DNS name shared by the brokers and no `b-<n>` name to resolve, so the VPC-resolver legs of the contract (two A records for the cluster name, one A per broker name, NXDOMAIN for an unlisted `b-3`) cannot even be attempted. The literal 127.0.0.1, the ports, the generated cluster name, the ARN and the VPC/subnet/security-group ids in the recording are per-run values of this environment and are NOT the requirement; the requirements are the per-broker `b-<n>` label, the single shared cluster DNS name suffix, the one shared access-method port, the per-name A answers inside the client subnets, and NXDOMAIN for an index the cluster does not have.

Why: a client cannot address broker N or the cluster by name. Every MSK client, admin tool and config file written against AWS uses the published broker DNS names; against the emulator they are environment-specific IP literals, so hostname-based TLS/SASL-IAM peer verification, per-broker addressing (replica placement, partition-leader affinity, per-broker health probes and metrics scrapers) and anything that resolves the cluster name to discover the broker set are all wrong or impossible. A client that asks for a broker index the cluster does not have gets no NXDOMAIN and so cannot distinguish "no such broker" from a resolution failure.

Fix: the GetBootstrapBrokers handler in the kafka crate (services/service-com-amazonaws-kafka-kafka) together with the broker-endpoint naming/allocation in that crate's state layer that renders each bootstrapBrokerString* member, and the in-VPC name-resolution component that must serve A records for the names it advertises: one distinctly named, dialable endpoint per broker node named `b-<index>.<cluster-dns-name>`, all sharing the access method's single port; the cluster DNS name resolving to every broker's address; each broker name resolving to exactly its own address; and an out-of-range broker index answered NXDOMAIN (RCODE 3) with no answer records.

Related but NOT covering this check: open issue 20261126T200529Z-kafka-getbootstrapbrokers-advertises-one-distinct-broker-host-for-a.md reports the neighbouring distinct-host-count defect on GetBootstrapBrokers, but it is grounded in kafka.msk-open-monitoring-jmx-exporter-serves-prometheus-and-the-disabled-node-exporter-refuses and carries only that replay key; it says nothing about the host being a DNS NAME of the `b-<n>.<cluster>` form nor about in-VPC resolution of those names, which is what this check asserts. Open issue 20261121T133835Z-kafka-msk-getbootstrapbrokers-advertises-an-unserved-host-and-createcluster.md adds the constraint the fix must also satisfy: every advertised name must be one the emulator really answers on.
