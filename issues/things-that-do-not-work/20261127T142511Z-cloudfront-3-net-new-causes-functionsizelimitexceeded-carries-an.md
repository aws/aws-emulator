=== Cause 1 of 3: CreateFunction's FunctionSizeLimitExceeded refusal carries an emulator-authored sentence where AWS sends no message at all ===
AWS:      HTTP 413 with error code FunctionSizeLimitExceeded and an EMPTY Error.Message. Smithy (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/smithy-model/com-amazonaws-cloudfront-cloudfront2020-05-31.json): CreateFunction — POST /2020-05-31/function, success 201; FunctionCode is @required with @length min 1 / max 40960; modeled errors include FunctionSizeLimitExceeded (client, httpError 413, shape doc "The function is too large. For more information, see Quotas ... in the Amazon CloudFront Developer Guide."), whose only member is an OPTIONAL Message. Recorded behavior: for code above the documented 10 KB (10240-byte) per-function quota but still inside the model's own 40960-byte maximum, AWS refuses with code FunctionSizeLimitExceeded and an EMPTY message — it emits no sentence for this class and interpolates nothing (no byte count, no limit, no function name). The shape's documentation prose is documentation, not the wire message.
Emulator: refuses with the right code but adds a message of its own: 'The function is too large: the code is 20480 bytes and at most 10240 bytes are allowed per function'. The byte counts in it are values from the request and from the emulator's own constant; neither they nor any other text belong on the wire for this class.
Why:      a client that logs, matches or asserts on Error.Message for this refusal sees text AWS never sends, and a client that distinguishes "no message" from "a message" (common when deciding whether to surface a service sentence to a user or synthesize its own) behaves differently against the emulator than against AWS. It also teaches fixtures a message contract that does not exist.
Fix:      CreateFunction's size validation in the cloudfront function handler / its error serializer — keep the 413 FunctionSizeLimitExceeded decision at the documented 10 KB quota (the check's positive control, code one byte under 10240, must stay accepted) but emit the error with no Message element.
Traces:   cloudfront.cf-function-size-over-documented-quota-rejected.

=== Cause 2 of 3: a multi-tenant origin DomainName carrying more TenantConfig parameters than the per-field limit is refused as an illegal origin-access configuration instead of InvalidArgument ===
AWS:      HTTP 400 with error code InvalidArgument and Error.Message "Your request exceeds the maximum number of parameters per field. Specify fewer parameters and try again." Smithy: CreateDistribution — POST /2020-05-31/distribution, success 201, models InvalidArgument (client, httpError 400, doc "An argument is invalid."), and UpdateDistribution — PUT /2020-05-31/distribution/{Id}/config — models the same error; IllegalOriginAccessConfiguration (400) is also modeled on both but its documented condition is different ("An origin cannot contain both an origin access control (OAC) and an origin access identity (OAI)."). Recorded behavior: for a ConnectionMode 'tenant-only' distribution whose origin DomainName (or OriginPath) interpolates MORE TenantConfig parameter placeholders than the per-field maximum, AWS refuses with the InvalidArgument sentence above; the sentence is fixed text in full — no parameter name, count or limit is interpolated — and the refusal creates nothing (ListDistributions shows no distribution with that Comment). A two-parameter field is accepted and round-trips, and widening an accepted two-parameter OriginPath to three on UpdateDistribution is refused the same way with the resource left unchanged.
Emulator: refuses the three-parameter DomainName create with error code IllegalOriginAccessConfiguration and message 'Illegal configuration: The origin type and OAC origin type differ' — a different error class, with a different message, describing a condition that does not hold: the origin is an S3 origin (S3OriginConfig) and the attached origin access control was created with OriginAccessControlOriginType 's3', so the types agree. The per-field parameter limit is evidently never evaluated; an unrelated OAC-type predicate fires first and decides the request. Because the create is refused for the wrong reason, the UpdateDistribution half of the contract (widening OriginPath to three parameters must be refused with the same InvalidArgument sentence and leave OriginPath unchanged) is not reached at all and must be verified on re-replay.
Why:      a caller is told to fix its origin/OAC pairing when the real fault is its tenant parameter count, so the diagnosis points at correct configuration and the actual limit is invisible. Worse, the OAC-type predicate as written rejects a legitimate S3-origin + s3-type-OAC pairing, which means ordinary tenant-only distributions over S3 origins cannot be created at all, and any client branching on InvalidArgument for the parameter limit never sees it.
Fix:      CreateDistribution's and UpdateDistribution's multi-tenant validation in the cloudfront distribution handler — correct the origin-type/OAC-type comparison so a matching S3 origin and s3-type OAC is accepted, and evaluate the per-field TenantConfig parameter limit, refusing with InvalidArgument 400 and its fixed sentence while creating/changing nothing. Related, NOT covering: 20261126T114713Z-cloudfront-a-direct-standard-distribution-carrying-a-templated.md concerns a DIRECT (standard) distribution carrying a templated OriginPath being refused with the TenantConfig message, i.e. the opposite route, and it does not carry this check's key.
Traces:   cloudfront.multi-tenant-domain-name-parameter-limit-and-origin-path-update-limit-rejected.

=== Cause 3 of 3: a field-level-encryption config with a non-empty QueryArgProfiles stores ForwardWhenQueryArgProfileIsUnknown=false instead of coercing it to true ===
AWS:      recorded behavior only — the model states no coercion rule. Smithy: GetFieldLevelEncryptionConfig — GET /2020-05-31/field-level-encryption/{Id}/config, success 200, output FieldLevelEncryptionConfig as httpPayload plus an ETag header; shape QueryArgProfileConfig has a @required boolean ForwardWhenQueryArgProfileIsUnknown and an optional QueryArgProfiles list. Recorded behavior: when a field-level-encryption config is created whose QueryArgProfileConfig.QueryArgProfiles is NON-EMPTY, CloudFront stores and reads back ForwardWhenQueryArgProfileIsUnknown = true whatever boolean the create sent; the sibling ContentTypeProfileConfig.ForwardWhenContentTypeIsUnknown created as true also reads back true (that half passes).
Emulator: GetFieldLevelEncryptionConfig reads back ForwardWhenQueryArgProfileIsUnknown = false — the literal value the create sent — for a config whose QueryArgProfiles holds one entry. CallerReference, Comment and the QueryArgProfiles item all round-trip correctly, so only this flag diverges.
Why:      a client reading its own configuration back cannot see the setting CloudFront actually enforces at the edge: it believes requests carrying an unknown fle-profile query argument are dropped when AWS forwards them (or the reverse), so drift detection and configuration-management tooling (CloudFormation/CDK/Terraform-style readback comparison) reports a permanent difference and may loop re-applying a value the service will not keep.
Fix:      the field-level-encryption config's state/normalization in the cloudfront FLE component (applied on create and update, so the stored record is what the reads serve) — whenever QueryArgProfileConfig.QueryArgProfiles is non-empty, store ForwardWhenQueryArgProfileIsUnknown as true, and have GetFieldLevelEncryptionConfig/GetFieldLevelEncryption serve the stored value.
Traces:   cloudfront.op-contract-get-field-level-encryption-config.
