# rds-data: 3 net-new causes — Data API serves statements on a cluster with no DB instance and on a stopped cluster, and never validates the secret's contents

> _Note: this issue was identified against the code base at commit `ff49842cf7656b5a010943ef9d0fd100550d134a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
The RDS Data API front end in this emulator runs the caller's SQL (or opens/ends the caller's transaction) without first checking the three per-request preconditions AWS checks: that the named DB cluster actually has a serving DB instance, that the cluster/instance is not stopped, and that the Secrets Manager secret named by secretArn holds usable credentials. Each missing gate turns a request AWS refuses at the envelope level into a 200 (or into an unrelated engine error), so the refusal class the operation models is unreachable. Three net-new causes, all in rds-data, all in the shared precondition chain that runs ahead of statement execution.

Related but NOT covering: open issue 20261023T045849Z-rds-data-skips-resource-secret-and-transaction-preconditions.md describes the same chain from the WIRE corpus (its causes 3 and 4 touch secret validation and the missing-instance 404). None of the behavioral checks below are owned by it, and cause 2 (stopped cluster / InvalidResourceStateException) appears in no open issue. A fixer closing this issue should re-replay exactly the check ids listed per cause.

Cause 1 of 3: a statement or batch against a DB cluster that has no DB instance is served instead of refused.
AWS: Smithy: ExecuteStatement and BatchExecuteStatement both model DatabaseNotFoundException (errorKind client, httpError 404, doc "The DB cluster doesn't have a DB instance."). AWS answers HTTP 404 with error code DatabaseNotFoundException and the message "Cannot find DBInstance in DBCluster <resourceArn>." — the fixed text is "Cannot find DBInstance in DBCluster " plus the cluster ARN from the request's resourceArn and a terminating period; the ARN is a request value, not part of the template. Nothing in the cluster is touched, so the statement never runs.
Emulator: with a cluster created EnableHttpEndpoint=True and zero DBClusterMembers, ExecuteStatement("CREATE TABLE ...") answers HTTP 200 {'numberOfRecordsUpdated': 0, 'generatedFields': []}, and BatchExecuteStatement with two parameter sets answers HTTP 400 DatabaseErrorException 'ERROR: relation "entries" does not exist; SQLState: 42P01' — i.e. it skipped the instance gate, went straight to the in-process engine and surfaced that engine's fault.
Why: a client that polls ExecuteStatement until it stops answering 404/DatabaseNotFoundException (the documented readiness signal for a freshly provisioned Aurora cluster) concludes the database serves before any instance exists; and a client branching on DatabaseNotFoundException to add a writer instead sees either a success or a generic SQL fault and reports a schema problem for a missing-instance problem. Statements also really run against a cluster AWS would never have touched.
Fix: the cluster-existence/serving-member leg of the shared precondition chain (crate::state::preconditions, reached from the ExecuteStatement and BatchExecuteStatement handlers), which must run before the statement reaches the data plane.
Traces: rds-data.execute-statement-on-cluster-without-instance-rejected-until-writer-added, rds-data.batch-execute-statement-on-a-cluster-without-an-instance-rejected.

Cause 2 of 3: a batch against a STOPPED cluster is accepted and its rows are written.
AWS: Smithy: BatchExecuteStatement models InvalidResourceStateException (errorKind client, httpError 400, doc "The resource is in an invalid state."). AWS answers HTTP 400 with error code InvalidResourceStateException and the message "The instance <DbiResourceId> is in stopped state. Please start the instance and try again once the instance is available." — the fixed text is "The instance " ... " is in stopped state. Please start the instance and try again once the instance is available.", with the writer's DbiResourceId (shape db- plus 26 upper-case alphanumerics, read from the emulator's own RDS state) as the only variable part. No parameter set is applied, so a later read after the cluster restarts shows only the rows written before the stop.
Emulator: after rds.stop_db_cluster leaves the cluster Status 'stopped', the identical BatchExecuteStatement answers HTTP 200 with {'updateResults': [{'generatedFields': []}, {'generatedFields': []}]} and persists both rows.
Why: a client cannot distinguish a stopped cluster from a running one; writes it believes were refused are silently committed, and operator-facing handling ("start the instance and retry") never fires. Tests that assert a stopped cluster rejects traffic pass against the emulator and fail against AWS.
Fix: a cluster/instance lifecycle-state leg in the same precondition chain, reading the RDS cluster and writer status before any statement or batch is executed.
Traces: rds-data.batch-execute-statement-on-a-stopped-cluster-rejected.

Cause 3 of 3: the contents of the secret named by secretArn are never inspected, so a secret that is not JSON or has no password authenticates every operation.
AWS: Smithy: ExecuteStatement, BatchExecuteStatement, BeginTransaction, CommitTransaction and RollbackTransaction all model InvalidSecretException (errorKind client, httpError 400, doc "The Secrets Manager secret used with the request isn't valid."). AWS retrieves the secret and refuses with HTTP 400 InvalidSecretException before it acts: the message is "The secret retrieved isn't valid JSON." when the SecretString does not parse as JSON, and "The secret retrieved is missing the username or password." when the JSON lacks either key. Both are fixed text with no variable part. A refused RollbackTransaction/CommitTransaction leaves the transaction OPEN, so a later call with a valid secret still commits it; repairing the secret in place makes the same ARN usable.
Emulator: BeginTransaction with a secret whose SecretString is the non-JSON text "<user>:<password>" answers HTTP 200 with a transactionId; RollbackTransaction with a secret holding only {"username": ...} answers HTTP 200 {'transactionStatus': 'Rollback complete'} and really rolls the transaction back. No secret is fetched or inspected on any Data API operation.
Why: a client relying on the Data API to authenticate through the secret gets success for credentials AWS rejects, so broken/rotated/wrong-shaped secrets are never surfaced in test or CI; worse, in the rollback case the emulator performs a state change (discarding the transaction) that AWS refuses, so the two diverge in persisted data and not just in the response.
Fix: the secretArn resolution/validation step of the shared precondition chain (crate::state::preconditions) — fetch the secret from the secretsmanager store, parse the SecretString, require username and password, and raise InvalidSecretException with the two messages above before the operation acts.
Traces: rds-data.transaction-calls-with-unusable-secrets-rejected-and-the-open-transaction-survives, rds-data.rollback-transaction-secret-without-password-rejected-and-transaction-kept.
