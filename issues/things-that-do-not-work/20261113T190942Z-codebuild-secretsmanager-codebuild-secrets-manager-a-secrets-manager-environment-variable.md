# CodeBuild/Secrets Manager: a SECRETS_MANAGER environment variable is never resolved into the build and exportedEnvironmentVariables come back with empty values on a SUCCEEDED build (1 cause)

> _Note: this issue was identified against the code base at commit `db48cb62da6c13229e331c427c12f5c2ca7c5371`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
ONE net-new root cause behind both failing checks of the codebuild__secretsmanager suite. Neither check is marked ALREADY FILED or OWNED in this replay.

Relationship to existing open issues (named, not covered): 20261022T172625Z-codebuild-secretsmanager-codebuild-secrets-manager-builds-fault-at-provisioning-so.md describes these same two checks failing because every build ended buildStatus FAULT at PROVISIONING, and its replay keys are the two `buildStatus == "SUCCEEDED"` assertions (run#23 / run#15). On this checkout those assertions PASS — the builds now reach a SUCCEEDED verdict with real phases — and both checks fail LATER, on the value the build container actually saw, so that issue's keys do not cover these failures. 20261113T085141Z-codebuild-a-well-formed-buildspec-build-fails-in.md and 20261109T181128Z-codebuild-buildspec-commands-are-not-run-through-a.md are filed under the `codebuild` heading and describe a build that ends FAILED with no exports; here the build ends SUCCEEDED and DOES report exportedEnvironmentVariables entries, whose values are empty strings, and neither issue carries a key for these two checks.

Cause 1 of 1: a project environment variable of type SECRETS_MANAGER is not resolved to the referenced secret's plaintext inside the build, and the variables a buildspec declares under `env/exported-variables` are reported back with empty values even though the build succeeds.
AWS: Smithy EnvironmentVariable{name (required), value (required), type: EnvironmentVariableType [PLAINTEXT, PARAMETER_STORE, SECRETS_MANAGER]}; the model documents for SECRETS_MANAGER: "An environment variable stored in Secrets Manager. For environment variables of this type, specify the name of the secret as the value of the EnvironmentVariable. The secret value will be substituted for the name at runtime." With a `<secret-name>:<json-key>` value the referenced key of the secret's SecretString JSON is substituted, so the shell in the build container sees the secret plaintext, not the reference string. Smithy ExportedEnvironmentVariable{name, value} is documented as the CodePipeline hand-off mechanism: "During a build, the value of a variable is available starting with the install phase... After the post_build phase ends, the value of exported variables cannot change" — i.e. Build.exportedEnvironmentVariables carries the value the build's own shell assigned to each name listed in `env/exported-variables`. Recorded behavior for the exercised project (NO_SOURCE + NO_ARTIFACTS, aws/codebuild/standard:7.0, BUILD_GENERAL1_SMALL, one SECRETS_MANAGER variable SIM2REAL_SECRET = `<secret-name>:token`, buildspec exporting SIM2REAL_DIGEST=sha256 of $SIM2REAL_SECRET and SIM2REAL_LEN=its byte count): buildStatus SUCCEEDED, exportedEnvironmentVariables SIM2REAL_DIGEST = the SHA-256 of the secret's plaintext and SIM2REAL_LEN = that plaintext's length (not the reference's length), while BatchGetProjects still stores only the reference typed SECRETS_MANAGER and no CodeBuild response contains the plaintext. The same recording shows that a build whose service role may read only a DECOY secret FAILS before the BUILD phase, with a phase context naming the denied action `secretsmanager:GetSecretValue`, exports nothing, and has no BUILD phase at all; re-granting secretsmanager:GetSecretValue on the referenced secret makes the identical project build SUCCEED with the correct digest.
Emulator: the build ends SUCCEEDED and reports exportedEnvironmentVariables entries for both declared names with value '' (empty string) — `exported={'SIM2REAL_DIGEST': '', 'SIM2REAL_LEN': ''}`. An empty value is not the digest of an empty variable either (that would be e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855 with SIM2REAL_LEN '0'), so the emulator neither substitutes the secret nor records what the build's shell assigned: it fabricates one entry per declared name with no value. Because the positive control never produces a digest, the permission barrier of the second check is unreachable: nothing distinguishes a build allowed to read the secret from one that is not.
Why: a client cannot inject a secret into a build at all — the documented 'secret value substituted at runtime' contract silently yields nothing, so every build that depends on a credential from Secrets Manager runs without it while still being reported SUCCEEDED. Hypothesis: a buildspec that would fail hard on the missing credential in AWS instead reports success here. The exported-variables contract that CodePipeline uses to pass values between stages also returns empty values on a succeeded build, so any downstream stage reading an exported variable sees nothing, and a caller cannot tell a missing secretsmanager:GetSecretValue grant from a working build.
Fix: the build-execution component of the codebuild crate — the environment-variable resolution step that must look up a SECRETS_MANAGER-typed variable's `<secret-name>[:<json-key>]` in Secrets Manager (under the project's service role, failing the build before the BUILD phase with a PhaseContext naming secretsmanager:GetSecretValue when the role cannot read it) and export the resolved plaintext into the build container, plus the exported-variable collection step that must populate Build.exportedEnvironmentVariables from the build shell's values instead of emitting empty placeholders. Entry points: services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build.rs (line 505 sets exported_environment_variables: None at start, with the comment that a running build fills it) and the BatchGetBuilds read-back.
Traces: codebuild__secretsmanager.codebuild-secrets-manager-environment-reference-resolves-inside-the-build, codebuild__secretsmanager.codebuild-secret-reference-denied-without-getsecretvalue-permission.
