# cognito-identity: 7 net-new identity-linking root causes — GetId refuses a mergeable login pair, conflict/link refusals are missing or carry non-AWS message text, a developer provider is accepted as a public Logins key, and vended sessions are let into the control plane

> _Note: this issue was identified against the code base at commit `7eb46ae4754f02cb00b49bce755f449d67bad34e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetId

## Description
This issue bundles 7 net-new root causes in the identity-linking/merging and vended-session paths of cognito-identity. Protocol is awsJson1_1, so each refusal's class appears both in the body `__type` and in the `x-amzn-errortype` header, and the `message` member is part of the requirement. None of these checks is marked ALREADY FILED or OWNED in the replay report. Open cognito-identity issues reviewed and NOT covering them (none carries these checks): '20261029T230931Z-cognito-identity-identity-merge-and-login-list-state.md' (wire corpus: ListIdentities/DescribeIdentity projections after developer-identity merges), '20261113T131245Z-cognito-identity-developer-identity-ownership-refusals-are-mis.md' (GetOpenIdTokenForDeveloperIdentity / LookupDeveloperIdentity ownership), '20261029T173827Z-cognito-identity-10-net-new-token-credential-refusal.md' and '20261124T070730Z-cognito-identity-3-net-new-causes-a-user.md' (token signing and GetCredentialsForIdentity key-class/role-mapping causes).

Cause 1 of 7: GetId refuses a MERGEABLE pair of logins instead of merging the two identities. AWS: when the Logins map carries one login per provider and each login already resolves to a different existing identity, and those two identities hold DISJOINT provider sets, GetId merges them — HTTP 200 returning one of the two existing IdentityIds (no third identity is minted); afterwards each login alone resolves to that identity, DescribeIdentity lists both provider names in Logins, and GetOpenIdToken with either login vends a token whose `sub` is the merged identity. Smithy (com.amazonaws.cognitoidentity#AWSCognitoIdentityService, awsJson1_1): GetId input Logins = LoginsMap @length 0..10 (key IdentityProviderName @length 1..128), output IdentityId @length 1..55 pattern ^[\w-]+:[0-9a-f-]+$; errors include ResourceConflictException (@httpError 409) but the model does not state when a merge is refused — the merge itself is recorded/documented behavior (API_GetId). Emulator: the call is refused with ResourceConflictException, message 'The supplied logins are already linked to 2 different identities.', so the merge never happens. Why: a client that signs a user in through a second provider and expects the two federated logins to converge on ONE identity instead gets a hard 409; the user's data stays split across two identity ids and the published AWS linking flow cannot be implemented against the emulator. Fix: the identity-resolution step of the GetId handler — when the resolved identities' provider sets are disjoint, merge them and return the surviving IdentityId; reserve ResourceConflictException for the non-mergeable case (cause 2). Traces: cognito-identity.get-id-merges-identities-of-two-providers-into-one.

Cause 2 of 7: GetId's genuine merge-conflict refusal carries the wrong message. AWS: when the supplied logins resolve to two different identities that cannot be merged (they would contribute two users of the SAME provider), GetId answers ResourceConflictException with the message 'Cannot merge these identities.' — that text is entirely fixed: it has no variable parts drawn from the request or from state, and it names neither the providers nor the identity ids. The refusal also changes nothing: the caller's identity keeps only its own login and the other identity keeps both of its logins. Smithy: GetId errors include ResourceConflictException (@httpError 409); the message text is recorded behavior only. Emulator: the class is right but the message is 'The supplied logins are already linked to 2 different identities.' — a different sentence that additionally leaks a count. Why: clients and negative tests match on the error message for this class (the two Cognito conflict messages, 'Cannot merge these identities.' and 'Cannot link these logins.', distinguish a merge conflict from a link conflict); a divergent sentence breaks that discrimination and any log/alarm pattern built on it. Fix: the error-message constant used by the GetId handler's conflict path. Traces: cognito-identity.get-id-logins-of-two-identities-conflict.

Cause 3 of 7: GetOpenIdToken's merge-conflict refusal carries the wrong message. AWS: GetOpenIdToken called with IdentityId = the caller's identity and a Logins map containing a login held by ANOTHER identity whose provider the caller's identity already holds (a second user of a held provider) is refused with ResourceConflictException and the message 'Cannot merge these identities.' — again entirely fixed text with no variable parts, and neither identity is modified. Smithy: GetOpenIdToken errors include ResourceConflictException (@httpError 409), NotAuthorizedException (@httpError 403), InvalidParameterException (400); the message text is recorded behavior only. Emulator: ResourceConflictException with the message "The login for provider '<provider name>' is already linked to identity '<identity id>'." — invented wording whose variable parts (the provider name and the identity id, e.g. the pool provider 'cognito-idp.<region>.amazonaws.com/<user-pool-id>' and 'us-west-2:<uuid>' in this run) AWS does not include at all. Why: as cause 2 — the message is part of the contract clients branch and assert on, and this one also discloses the id of an identity the caller does not own. Fix: the error-message constant used by the GetOpenIdToken handler's merge/conflict path (same text as cause 2). Traces: cognito-identity.get-open-id-token-merging-an-identity-of-the-same-provider-rejected.

Cause 4 of 7: GetId links a second user of an already-held provider instead of refusing. AWS: when the Logins map pairs a login that resolves to an existing identity with a login of a provider that identity ALREADY holds for a DIFFERENT user, the link is refused — ResourceConflictException with the message 'Cannot link these logins.' (entirely fixed text, no variable parts) — and nothing is linked: the refused login, presented alone, mints an identity of its own holding only its provider. Once the held login is removed with UnlinkIdentity, the same GetId call succeeds and links the newcomer. Smithy: GetId errors include ResourceConflictException (@httpError 409); the one-user-per-provider-per-identity rule and the message are recorded behavior only. Emulator: HTTP 200 with an IdentityId, i.e. the second user of the held provider is accepted. Why: an identity may hold at most one user per provider; accepting the link lets two distinct federated users collapse onto one identity, so credentials and data of one end user become reachable by another — a test asserting the refusal passes against AWS and fails only here. Fix: the link-validation step of the GetId handler (before identity state is written), raising ResourceConflictException with AWS's fixed message and leaving state untouched. Traces: cognito-identity.get-id-second-user-of-a-held-provider-rejected.

Cause 5 of 7: GetId accepts the pool's DeveloperProviderName as a Logins key. AWS: the Logins keys of GetId must be PUBLIC providers; a pool's DeveloperProviderName is only valid on the developer surface (GetOpenIdTokenForDeveloperIdentity), so GetId with Logins={<developer provider>: <developer user id>} is refused with InvalidParameterException and the message 'Please provide a valid public provider' (fixed text, no variable parts, no trailing period) and NO identity is created — the pool's identity listing is unchanged. The same developer user presented to GetOpenIdTokenForDeveloperIdentity is accepted and gets its own identity. Smithy: GetId errors include InvalidParameterException (@httpError 400); Logins = LoginsMap @length 0..10; the public-provider restriction and the message are recorded behavior only. Emulator: HTTP 200 with a fresh IdentityId, so a developer-provider key mints an identity through the public API. Why: the developer surface exists so the application server mediates developer identities; letting any unauthenticated GetId caller mint identities keyed by the developer provider bypasses that mediation and pollutes the pool with identities LookupDeveloperIdentity cannot resolve. Fix: the Logins-key validation in the GetId handler — reject a key equal to the pool's DeveloperProviderName with InvalidParameterException and AWS's fixed message, before any identity is created. Traces: cognito-identity.get-id-developer-provider-login-rejected.

Cause 6 of 7: GetCredentialsForIdentity does not refuse Logins carrying a login another identity owns. AWS: GetCredentialsForIdentity with IdentityId = the caller's identity and a Logins map that includes a login already owned by a DIFFERENT authenticated identity is refused with ResourceConflictException and the message 'Cannot merge these identities.' (fixed text); the refusal links nothing — the caller's identity still lists only its own provider and the other identity keeps both of its logins. The legal neighbour still works: the same call with a second-provider login no identity owns yet links that login and vends credentials for the caller's identity. Smithy: GetCredentialsForIdentity errors include ResourceConflictException (@httpError 409), NotAuthorizedException (@httpError 403), InvalidIdentityPoolConfigurationException (400); Logins = LoginsMap @length 0..10; the conflict rule and message are recorded behavior only. Emulator: HTTP 200 with a full Credentials structure (AccessKeyId/SecretKey/SessionToken/Expiration) for the caller's identity — the ownership conflict is not detected on this operation at all. Why: this is the credential-vending path, so the emulator hands out a session for a request that AWS refuses; a login belonging to another end user is treated as proof for the caller's identity, and clients never see the 409 that tells them to unlink first. Fix: apply the same login-ownership/conflict check used by GetId in the GetCredentialsForIdentity handler, before any role is assumed or state is written. Traces: cognito-identity.get-credentials-for-identity-login-of-another-identity-conflict.

Cause 7 of 7: Cognito-vended session credentials are admitted to the cognito-identity control plane. AWS: a session vended by GetCredentialsForIdentity may never call the Cognito Identity control plane, no matter what the mapped role's identity-based policy grants — ListIdentityPools under such a session is refused with AccessDeniedException whose whole message is 'These credentials are not valid for accessing this resource' (fixed text, no variable parts, and distinct from both IAM policy denials, which read '... because no identity-based policy allows ...' / '... because no session policy allows ...'). The check establishes this is a service-level guard, not an authorization decision, by first granting cognito-identity:ListIdentityPools on the role and showing s3:ListAllMyBuckets then succeeds for the same session. Smithy: ListIdentityPools errors are InvalidParameterException, NotAuthorizedException (@httpError 403), ResourceConflictException, TooManyRequestsException, InternalErrorException — the guard and its message are recorded behavior only. Emulator: ListIdentityPools under the vended session succeeds (no error at all), so the guard is absent. Why: a Cognito end-user session that reaches the identity-pool control plane can enumerate and (with any role grant) reshape the pools of the account; an emulator that allows it makes a privilege-escalation test that AWS refuses look safe. Fix: a request-time guard in the cognito-identity control-plane operations' authorization layer that refuses any caller whose session was vended by GetCredentialsForIdentity, with AccessDeniedException and AWS's exact message. Traces: cognito-identity.vended-credentials-bounded-by-role-policy.
