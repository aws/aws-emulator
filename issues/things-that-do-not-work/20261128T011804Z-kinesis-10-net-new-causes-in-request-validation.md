# kinesis: 10 net-new causes in request validation — constraint-message rendering (order, anchors, map/blob/elision), TagKey length unenforced, ARN-format and ExclusiveStartShardId misclassified, invented refusal prose

> _Note: this issue was identified against the code base at commit `35f7de95e926ecd075d4f0c5efe73729faf5e0c1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AddTagsToStream

## Description
Ten independent root causes, all in Kinesis' request-validation and refusal-rendering path. Each must be closed on its own; the counts and check ids per cause are below. None of these checks is marked ALREADY FILED or OWNED in the behavioral report.

=== Cause 1 of 10: two constraint violations on one member are emitted in the wrong ORDER ===
AWS: Smithy: AddTagsToStream.StreamName targets StreamName (string, @length min 1 max 128, @pattern "^[a-zA-Z0-9_.-]+$"); AddTagsToStream binds ValidationException (client error, HTTP 400). Recorded behavior: an empty StreamName violates both constraints and AWS answers HTTP 400 ValidationException with "2 validation errors detected: Value '<value>' at 'streamName' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9_.-]+; Value '<value>' at 'streamName' failed to satisfy constraint: Member must have length greater than or equal to 1" — the PATTERN violation is listed first, the LENGTH violation second, joined by "; ". The fixed text is the "<n> validation error(s) detected: " head and the two "... failed to satisfy constraint: ..." sentences; the variable parts are the wire member name, the declared pattern/bound and the submitted value.
Emulator: same status, code and sentences, but reversed: the length violation is emitted first and the pattern violation second.
Why: a client, CLI user or log scraper that matches AWS's whole message (the only machine-readable statement of which constraints a request broke) never matches, and the per-violation order is part of that text. The same inverted order is visible on DescribeStream.ExclusiveStartShardId (see cause 8's check, whose empty-id expectation is pattern-then-length).
Fix: the shared constraint-violation collector behind the awsJson1_1 request validator — order the violations of one member as the service does (pattern before length).
Traces: kinesis.add-tags-to-stream-name-length-bounds-rejected.

=== Cause 2 of 10: the pattern-constraint sentence prints the member's regex with its ^ and $ anchors stripped ===
AWS: Smithy: SequenceNumber @pattern "^(0|([1-9]\\d{0,128}))$" (GetShardIterator.StartingSequenceNumber, PutRecord.SequenceNumberForOrdering, StartingPosition.SequenceNumber) and HashKey @pattern "^(0|([1-9]\\d{0,38}))$" (PutRecord/PutRecords ExplicitHashKey); all bind ValidationException (400). Recorded behavior: the refusal reproduces the member's pattern VERBATIM as declared, anchors included, e.g. "1 validation error detected: Value '<value>' at 'startingSequenceNumber' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(0|([1-9]\\d{0,128}))$".
Emulator: identical except the regex is printed in its normalized, anchor-free matching form: "... regular expression pattern: (0|([1-9]\\d{0,128}))" (and "(0|([1-9]\\d{0,38}))" for hash keys), on every member that carries a pattern.
Why: that regex is the only machine-readable statement of the accepted grammar; a client that compiles or compares it gets a regex whose meaning differs (unanchored it matches any substring).
Fix: the pattern branch of the constraint-violation renderer — print the member's declared pattern text, not the anchor-stripped form used for matching. Open issue 20261127T132625Z-kinesis-refusal-responses-echo-values-patterns-and-codes.md reports this same renderer defect for DeregisterStreamConsumer.consumerARN (its cause 4) and carries only wire replay keys; it does not cover these members or these checks.
Traces: kinesis.get-shard-iterator-leading-zero-sequence-number-rejected, kinesis.get-shard-iterator-zero-padded-starting-sequence-number-rejected, kinesis.put-record-explicit-hash-key-off-pattern-rejected, kinesis.put-record-malformed-sequence-number-for-ordering-rejected, kinesis.put-records-hexadecimal-explicit-hash-key-rejected, kinesis.subscribe-to-shard-leading-zero-sequence-number-rejected.

=== Cause 3 of 10: a map member's constraint violation is reported per entry instead of on the map ===
AWS: Smithy: AddTagsToStream.Tags targets TagMap (map, @length min 1 max 200) with key TagKey (@length 1-128) and value TagValue (@length 0-256). Recorded behavior: a violation inside the map is reported ON THE MAP MEMBER, with the whole map rendered Java-map style and both bounds of the violated target listed: "1 validation error detected: Value '{<key>=<value>}' at 'tags' failed to satisfy constraint: Map value must satisfy constraint: [Member must have length less than or equal to 256, Member must have length greater than or equal to 0]"; the empty map renders as "Value '{}' at 'tags' failed to satisfy constraint: Member must have length greater than or equal to 1". Fixed text: "Map value must satisfy constraint: [...]" / "Map keys must satisfy constraint: [...]" and the bracketed bound list in model order; variable parts: the rendered map and the declared bounds.
Emulator: reports a synthesized per-entry path and a single bound — "Value '<the long value>' at 'tags.note' failed to satisfy constraint: Member must have length less than or equal to 256" — and for the empty map omits the rendered value entirely ("Value at 'tags' failed to satisfy ...").
Why: the member path 'tags.note' does not exist in AWS' diagnostics, so anything keyed on the member name or on the bracketed bound list mis-parses the refusal; the empty-map form also loses the '{}' token AWS serves.
Fix: the map branch of the constraint-violation renderer, shared by every TagMap-bearing operation (AddTagsToStream, CreateStream, TagResource, CreateChannel).
Traces: kinesis.add-tags-to-stream-tag-value-over-256-characters-rejected, kinesis.add-tags-to-stream-tag-count-beyond-stream-limit-rejected.

=== Cause 4 of 10: TagKey's length bound is not enforced at all ===
AWS: Smithy: TagMap key targets TagKey, @length min 1 max 128. Recorded behavior: AddTagsToStream with a 129-character key is refused HTTP 400 ValidationException "1 validation error detected: Value '{<key>=<value>}' at 'tags' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]" and the stream's tags are untouched; a 128-character key is accepted.
Emulator: the 129-character key is ACCEPTED — AddTagsToStream answers 200 with an empty body and stores the tag.
Why: an out-of-range tag key is silently persisted, so a client that relies on AWS rejecting it writes state AWS would never hold, and later reads disagree between emulator and AWS.
Fix: AddTagsToStream's input validation — apply the TagMap key/value length constraints before the handler mutates tag state.
Traces: kinesis.add-tags-to-stream-tag-key-outside-1-to-128-chars-rejected.

=== Cause 5 of 10: the offending value is interpolated into messages whose AWS template has no value slot ===
AWS: Smithy: PutRecord.Data @required targets Data (blob, @length min 0 max 10485760); CreateChannel.S3DestinationConfiguration.DeadLetterQueueS3Configuration.ErrorOutputPrefix is a string @length max 512. Both operations bind ValidationException (400). Recorded behavior: for these members the message carries NO rendered value — "1 validation error detected: Value at 'data' failed to satisfy constraint: Member must have length less than or equal to 10485760" and "1 validation error detected: Value at 's3DestinationConfiguration.deadLetterQueueS3Configuration.errorOutputPrefix' failed to satisfy constraint: Member must have length less than or equal to 512". The fixed text is "1 validation error detected: Value at '" + "' failed to satisfy constraint: Member must have length less than or equal to " + the declared bound; the only variable parts are the wire member path and the bound.
Emulator: always interpolates something after "Value ": a synthetic size token for the blob ("Value '10485761 bytes' at 'data'") and the full 513-character prefix for the nested string member.
Why: the extra quoted segment breaks any match on AWS' sentence, "10485761 bytes" is a token AWS never emits, and a rejected payload/prefix is reflected into a diagnostic AWS deliberately keeps value-free (so message size is unbounded).
Fix: the same constraint-violation renderer — emit the value-free form for the members AWS renders value-free (blob members and these nested configuration strings). Open issue 20261127T132625Z-kinesis-refusal-responses-echo-values-patterns-and-codes.md reports the same always-interpolate defect for channelARN/streamFilter/recordDistributionStrategy (causes 1-3) from the wire corpus; it does not cover 'data' or the channel dead-letter prefix and carries none of these replay keys.
Traces: kinesis.put-record-data-length-bounds-rejected, kinesis.create-channel-dead-letter-error-prefix-over-512-characters-rejected.

=== Cause 6 of 10: an oversized string value is ABBREVIATED in the message where AWS echoes it in full ===
AWS: Smithy: ListShards.NextToken targets NextToken (string, @length min 1 max 1048576); ListShards binds ValidationException (400). Recorded behavior: a token one character over the bound is refused with the submitted value echoed in full: "1 validation error detected: Value '<the entire submitted token>' at 'nextToken' failed to satisfy constraint: Member must have length less than or equal to 1048576".
Emulator: same code and bound but the value is replaced by a head-plus-summary form, "Value '<first ~120 characters>... [<n> bytes]' at 'nextToken' ...", reducing the message to a few hundred characters.
Why: the message is the contract for this error class; a client comparing it, or extracting the rejected token from it, sees text AWS never serves (and the "[<n> bytes]" token does not exist in AWS' vocabulary).
Fix: the same renderer — for members AWS echoes, echo the submitted value verbatim with no truncation or size annotation.
Traces: kinesis.list-shards-next-token-length-bounds-rejected.

=== Cause 7 of 10: a syntactically wrong ResourceARN is answered ResourceNotFoundException instead of the ARN-format refusal ===
AWS: Smithy: ListTagsForResource.ResourceARN @required, @length min 1 max 2048, @pattern "^arn:aws.*:kinesis:.*:\\d{12}:.*(stream|channel)/\\S+$"; the operation binds InvalidArgumentException and ResourceNotFoundException (both 400). Recorded behavior: an ARN that passes the length bound but cannot name any resource (its stream-name segment is longer than a stream name may be) is refused HTTP 400 InvalidArgumentException with the entirely fixed text "The format of the resource ARN is invalid." — nothing from the request is interpolated.
Emulator: answers ResourceNotFoundException with "Stream <the whole bogus name> under account <account> not found." — it parses the ARN, takes whatever follows "stream/" as a name and reports a lookup miss.
Why: the two classes are not interchangeable: InvalidArgumentException says the ARN is malformed (a client bug, never retried against another account), ResourceNotFoundException says a well-formed ARN names nothing (retryable after creating the resource). Clients branch on this.
Fix: ListTagsForResource's ARN parsing/validation — grade the ARN's grammar (including the per-segment limits) before resolving it in state. Open issue 20261127T132625Z-kinesis-malformed-kinesis-arns-are-answered-resourcenotfoundexception-instead-of.md reports the same misclassification from the wire corpus; it does not carry this check.
Traces: kinesis.list-tags-for-resource-arn-over-2048-chars-rejected.

=== Cause 8 of 10: DescribeStream requires ExclusiveStartShardId to name an existing shard ===
AWS: Smithy: DescribeStream.ExclusiveStartShardId targets ShardId (string, @length 1-128, @pattern "^[a-zA-Z0-9_.-]+$") and its documentation makes it the exclusive START of the listing, not a shard reference; DescribeStream binds InvalidArgumentException and ValidationException (400). Recorded behavior: any value satisfying those constraints is accepted and the page simply resumes after it in shard-id order — "0" (which sorts before every shardId-...) returns every shard, a 128-character "z...z" returns an empty list; only values breaking the shape constraints are refused, and then with the ValidationException constraint sentences (empty value: pattern error then length error; 129 characters: the max-length error).
Emulator: refuses a syntactically valid id that is not an existing shard — HTTP 400 InvalidArgumentException "ExclusiveStartShardId <value> is not a shard of stream <stream name>" — so paging from a cursor that is not itself a shard id is impossible and the operation never reaches its length/pattern validation.
Why: every paginator that computes a start key (rather than echoing a shard id) breaks, and the refusal class/message is emulator-authored prose AWS does not serve.
Fix: DescribeStream's handler — treat ExclusiveStartShardId as a lexicographic exclusive cursor after shape validation, not as a shard that must exist. Open issue 20261027T011654Z-kinesis-9-net-new-root-causes-cloudformation-aws.md owns the equivalent ListShards.ShardFilter/AFTER_SHARD_ID failure; it does not cover DescribeStream and does not carry this check.
Traces: kinesis.describe-stream-exclusive-start-shard-id-length-bounds-rejected.

=== Cause 9 of 10: CreateStream's over-the-tag-limit refusal uses emulator-authored prose ===
AWS: Smithy: CreateStream.Tags targets TagMap; the per-resource ceiling of 50 tags is a runtime rule (the shape's @length max is 200), and CreateStream binds InvalidArgumentException (400). Recorded behavior: HTTP 400 InvalidArgumentException with "Failed to add tags to resource <the stream's ARN> under account <account id> because a given resource cannot have more than 50 tags associated with it." The fixed text is "Failed to add tags to resource " + " under account " + " because a given resource cannot have more than 50 tags associated with it."; the variable parts are the target resource's ARN and the caller's account id (both taken from the request and the emulator's state, never a literal from one run).
Emulator: same status and code, message "a stream carries at most 50 tags" — invented wording that names neither the resource nor the account.
Why: the message is part of the contract for this error class; anything displaying or matching AWS' sentence, or extracting the resource from it, fails.
Fix: the tag-count check in CreateStream's validation (and the shared tag-limit error it raises).
Traces: kinesis.create-stream-with-fifty-one-tags-rejected.

=== Cause 10 of 10: the RecordDistributionStrategy-on-a-provisioned-stream refusal uses emulator-authored prose ===
AWS: Smithy: CreateStream.RecordDistributionStrategy is an optional enum and StreamModeDetails a separate optional member, so the on-demand-only pairing is a runtime rule; CreateStream binds InvalidArgumentException (400). Recorded behavior: HTTP 400 InvalidArgumentException with the entirely fixed text "RecordDistributionStrategy can only be set for On-Demand streams".
Emulator: same status and code, message "RecordDistributionStrategy is only supported for a ON_DEMAND stream".
Why: same as cause 9 — the exact sentence is the contract.
Fix: the capacity-mode/RecordDistributionStrategy pairing check in CreateStream's validation.
