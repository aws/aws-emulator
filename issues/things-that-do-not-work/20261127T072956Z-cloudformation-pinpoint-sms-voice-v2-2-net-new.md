# cloudformation__pinpoint-sms-voice-v2: 2 net-new causes — Ref of AWS::SMSVOICE::RcsAgent is the bare agent id instead of the RcsAgentArn (no listing row matches), and the emulator serves the degenerate all-zero account id so account redaction mangles SMS-and-Voice resource ids

> _Note: this issue was identified against the code base at commit `4b1e9c3fe42084e4e303fed95aa2e32f912a310a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two net-new root causes, both grounded in the two cloudformation__pinpoint-sms-voice-v2 checks that are not owned by an open issue (the three logs__pinpoint-sms-voice-v2 failures are OWNED by 20261120T210447Z-pinpoint-sms-voice-v2-sendtextmessage-refuses-every-send-that-omits-the-optional.md and are not part of this issue).

Cause 1 of 2: the CloudFormation resource provider for AWS::SMSVOICE::RcsAgent returns the agent's bare id as the resource's Ref value (and hence as its PhysicalResourceId / stack Output), where AWS returns the agent's Amazon Resource Name. Failing check: cloudformation__pinpoint-sms-voice-v2.deploy-cloudformation-smsvoice-registration-resources-round-trip-and-delete.
AWS: recorded behavior only for the CloudFormation Ref contract — the recording shows Ref of the AWS::SMSVOICE::RcsAgent resource is the value that appears as RcsAgentArn in End User Messaging SMS and Voice's own paged listing, while Fn::GetAtt RcsAgentId is the value that appears as RcsAgentId; the recorded check locates the agent by matching the Ref against DescribeRcsAgents' RcsAgentArn and only then compares the GetAtt id. Smithy (pinpointsmsvoicev2): DescribeRcsAgents output RcsAgents is a list of RcsAgentInformation, whose RcsAgentArn (required, "The Amazon Resource Name (ARN) of the RCS agent") and RcsAgentId (required, "The unique identifier for the RCS agent") are two distinct required members; an ARN member in this model has the shape arn:<partition>:sms-voice:<region>:<account>:<resource-type>/<id> (cf. TwoWayChannelArn pattern ^\S+$ / IamRoleArn pattern ^arn:\S+$). So the general requirement is: Ref resolves to the ARN form, GetAtt RcsAgentId to the id form, and the ARN Ref is findable in DescribeRcsAgents.
Emulator: after the stack reaches CREATE_COMPLETE, the RcsRef Output is a bare agent identifier with no 'arn:' prefix at all (observed form: 'rcsagent-' followed by a 32-character zero-padded counter), so no DescribeRcsAgents row has RcsAgentArn equal to it and the lookup set is empty: 'describe_rcs_agents entries with Ref <ref>: []'. The check fails on the very first of the three resource kinds, so the sibling AWS::SMSVOICE::Registration and AWS::SMSVOICE::RegistrationAttachment Refs, the tag reconciliation, the property assertions and the post-delete absence legs were never reached and may carry the same defect. Hypothesis (not stated by the model or the recording): the provider is publishing its primary identifier as the id instead of the ARN; a second possibility consistent with the same empty result is that the CFN-created agent is never registered in the SMS-and-Voice store that DescribeRcsAgents reads, so the fixer should confirm the listing contains exactly one agent for the stack before changing only the Ref.
Why: every client that consumes the stack's Ref/Output for an RCS agent — DependsOn/ResourceArn wiring, ListTagsForResource(ResourceArn=...), IAM policy resources, cross-stack exports — is handed a value that is not an ARN and is rejected or silently matches nothing; CDK/CFN templates that pass Ref where an ARN is required break, and an operator cannot correlate the stack's resource with the agent the service lists.
Fix: the AWS::SMSVOICE::RcsAgent resource provider in the CloudFormation service (its create path's primary-identifier/Ref resolution, and the state write that makes the agent visible to pinpoint-sms-voice-v2's DescribeRcsAgents), plus the same Ref choice for the sibling AWS::SMSVOICE::Registration and AWS::SMSVOICE::RegistrationAttachment providers the check asserts next.
Traces: cloudformation__pinpoint-sms-voice-v2.deploy-cloudformation-smsvoice-registration-resources-round-trip-and-delete.

Cause 2 of 2: the account the emulator serves is 000000000000, so the 12-digit account number is a literal substring of ordinary SMS-and-Voice resource identifiers, and any consumer that redacts the account out of a message corrupts the identifier with it. Failing check: cloudformation__pinpoint-sms-voice-v2.deploy-cloudformation-smsvoice-configurationset-invalid-protect-configuration-rejected. This is the same class as open issue 20261122T115717Z-cloudformation-ec2-rds-ec2-generated-resource-ids-are-a-zero-padded (filed for EC2's id allocator); that issue does not cover this one — it names EC2's allocator, and here the mangled identifier is not even minted by the emulator but echoed from the request, so only the degenerate account value is at fault.
AWS: recorded behavior only — an AWS account id is a 12-digit number that is never all zeros, and a protect-configuration identifier is 'protect-configuration-' followed by 32 hex characters, so the two never overlap textually and redacting the account from an error message leaves the identifier intact. The refusal itself is the requirement the check compares and the emulator already meets it: status 400, error code ResourceNotFoundException surfaced through the CloudFormation handler reason as HandlerErrorCode 'NotFound' with message 'Resource Not Found - ResourceType="protect-configuration" ResourceId="<id>" (Service: PinpointSmsVoiceV2, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)' — fixed text 'Resource Not Found - ResourceType=', the quoted resource type 'protect-configuration' and the SDK suffix are the template; ResourceId is the identifier taken verbatim from the request's ProtectConfigurationId, and the request id and attempt count are per-run values. NOTE FOR THE FIXER: the status, the error code, the HandlerErrorCode and the message template are all already correct on this path and must not be changed.
Emulator: the account served is all zeros, so when the harness masks the account id out of the handler reason the echoed identifier (32 zeros, the never-issued sentinel the template asked for) comes back as 'protect-configuration-<account><account>00000000' instead of staying 'protect-configuration-00000000000000000000000000000000', and the comparison fails. Nothing else about the message diverges. The same low-entropy, account-colliding shape is visible in the identifiers this service mints (an agent id of 'rcsagent-' plus a 31-zero-padded counter and a '1').
Why: any client, log pipeline or support workflow that scrubs the account number out of responses before storing or comparing them silently corrupts every resource identifier the emulator echoes or mints, because on the emulator the account is a prefix of those identifiers rather than a disjoint value as on AWS; identifiers also become guessable and cross-run collidable.
Fix: the emulator's account-identity component — stop serving the degenerate all-zero account id (serve a 12-digit account that is not all zeros) — and, for the identifiers this service mints, the pinpoint-sms-voice-v2 id allocator in its state component, so a minted id does not contain the account number as a substring.
Traces: cloudformation__pinpoint-sms-voice-v2.deploy-cloudformation-smsvoice-configurationset-invalid-protect-configuration-rejected.

## Steps to Reproduce
Cause 1:
1. CreateStack with a template holding AWS::SMSVOICE::RcsAgent (DeletionProtectionEnabled false, a tag), AWS::SMSVOICE::Registration (RegistrationType US_TEN_DLC_BRAND_REGISTRATION) and AWS::SMSVOICE::RegistrationAttachment (a tiny PNG AttachmentBody), with Outputs {Ref} and {Fn::GetAtt <Resource>.<Kind>Id} for each.
2. Poll DescribeStacks until CREATE_COMPLETE, then read the Outputs.
3. Observe the RcsRef Output: on AWS it is the agent's ARN; on the emulator it is a bare 'rcsagent-<32 chars>' identifier with no 'arn:' prefix.
4. Page DescribeRcsAgents over the whole account and look for the row whose RcsAgentArn equals that Ref: AWS returns exactly one row (whose RcsAgentId equals the GetAtt Output); the emulator returns none.
5. Repeat for Reg/Attach: DescribeRegistrations.RegistrationArn and DescribeRegistrationAttachments.RegistrationAttachmentArn versus the stack's RegRef / AttachRef.

Cause 2:
1. CreateStack with a template holding an AWS::SMSVOICE::ProtectConfiguration and an AWS::SMSVOICE::ConfigurationSet whose ProtectConfigurationId is the never-issued 'protect-configuration-' + 32 zeros.
2. Poll DescribeStacks until ROLLBACK_COMPLETE, then read the Config resource's CREATE_FAILED ResourceStatusReason from DescribeStackEvents — the wrapped PinpointSmsVoiceV2 ResourceNotFoundException message and HandlerErrorCode NotFound are already correct.
3. Call GetCallerIdentity (or any account-bearing response) and compare: the emulator's account is 000000000000, a literal substring of the identifier echoed in that message.
4. Redact the account id out of the reason, as any log scrubber does: on the emulator the identifier is rewritten to 'protect-configuration-<account><account>00000000'; against AWS it is left intact.
